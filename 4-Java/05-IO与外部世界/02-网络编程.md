# 网络编程

> 前置：[01-文件与NIO](./01-文件与NIO.md)（Channel/Buffer 的定义处） · 后续：[03-HTTP客户端](./03-HTTP客户端.md)

> **版本基准**：Java 21 stable / Java 25 latest（均为 LTS）。示例实测环境：Temurin JDK 25.0.4.1（Windows），示例以 `javac -encoding UTF-8 --release 21` 编译验证，全部走本机回环（loopback）。

协议本身——TCP 的三次握手、序列号/确认、滑动窗口，UDP 的无连接数据报——定义在 [03-TCP与UDP](../../0-计算机基础/06-计算机网络/03-TCP与UDP.md)，本篇不重复。本篇的对象是 Java 暴露给应用的两套 socket 接口：阻塞式 `java.net` 与非阻塞式 `java.nio.channels`，以及它们在 JDK 21（2023-09）之后被虚拟线程重新洗牌的选型关系。

## 本质

**Socket** 是进程到 TCP 连接的句柄：四元组（源 IP、源端口、目的 IP、目的端口）在内核里唯一标识一条连接，Java 侧的 `Socket` 对象把它包装成一对输入/输出流。**ServerSocket** 只做一件事——`accept()` 阻塞监听端口，每来一个连接产出一个 `Socket`。**DatagramSocket** 对应 UDP：无连接、按数据报收发、不保证送达与顺序。

## 机制

### 阻塞模型：一个连接一个线程

阻塞语义来自内核：`accept()` 没有新连接就不返回，`read()` 没有数据就不返回。因此服务端的标准结构是 accept 循环 + 每连接派一个处理线程：

实测（Temurin 25.0.4.1，回环 TCP 回声 + UDP 数据报）：

```text
TCP 客户端收到: echo: hello tcp
UDP 接收: hello udp
```

模型直白、代码即流程，但连接数 = 线程数，撞上平台线程数千量级的上限（见 [01-线程模型与同步](../04-并发编程/01-线程模型与同步.md)）。这是 NIO 诞生的动机。

### NIO：单线程看管所有连接

NIO 把"等数据"从每个连接里抽出来，交给一个 **Selector**（对 OS 多路复用的封装：Linux 是 epoll）。连接设为**非阻塞**后注册到 Selector，单线程 `select()` 阻塞等待"哪些通道就绪"，然后遍历就绪集合分发处理：

```text
ServerSocketChannel ──register(OP_ACCEPT)──┐
                                           ├── Selector ──select()──> 就绪的 SelectionKey 集合
SocketChannel ────register(OP_READ)───────┘                            │
                                              逐 key 处理：accept / read / write
```

实测（Temurin 25.0.4.1，单线程 Selector 回声服务 + 回环客户端）：

```text
NIO 服务端读到: hello nio
NIO 客户端收到: nio-echo
```

使用纪律：`select()` 返回后必须遍历 `selectedKeys()` 并 `it.remove()` 每个处理完的 key——就绪集合不会自动清空，不移除会在下一轮被重复处理。

**选型账**：NIO 用编程复杂度换线程数——非阻塞读写可以只传部分数据，应用要自己处理半包/粘包与状态机。它适合连接极多、单连接计算极轻的场合（代理、网关）。Netty 等框架正是把这套状态机封装掉之后的产物。

### 虚拟线程重新洗牌

Java 21 起，JDK 的阻塞 socket 操作对虚拟线程是 unmount 点（见 [05-虚拟线程与结构化并发](../04-并发编程/05-虚拟线程与结构化并发.md)）：阻塞写法不再占用 OS 线程。结论一句话——**"一个连接一个虚拟线程 + 阻塞代码"重获竞争力**，手写 Selector 的必要性大幅下降；NIO 退回到它真正不可替代的位置：Netty 这类框架的内部，以及需要精细背压控制的场景。
