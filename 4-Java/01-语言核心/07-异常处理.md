# 异常处理

> 前置：[06-泛型](06-泛型.md) · 后续：[08-Lambda与函数式接口](08-Lambda与函数式接口.md)

> **版本基准**：Java 21 stable / Java 25 latest（均为 LTS）。示例实测环境：Temurin JDK 25.0.4.1（Windows），stable 口径示例以 `javac -encoding UTF-8 --release 21` 验证。

## 本质

异常（exception）是**非局部控制流**：`throw` 把执行从出错点直接弹到最近匹配的 `catch`，中间跨越的调用层由 JVM 逐帧**栈展开**（stack unwinding）清理。它把"出错"从返回值体系里分离出来——不用每个方法都在返回值里夹带错误码、每个调用点都手写判断，错误沿调用链自动上浮到有能力处理它的那一层。

异常对象都是 `Throwable` 的子类，层次分三支，各有明确的语义分工：

```text
Throwable
├── Error                    // JVM 级故障：StackOverflowError、OutOfMemoryError——程序一般不该 catch
└── Exception
    ├── RuntimeException     // 非受检：NullPointerException、IllegalArgumentException——程序 bug
    └── 其他（IOException…）  // 受检：环境性失败——编译器强制处理
```

**受检异常**（checked）是 javac 的契约：方法声明 `throws IOException`，调用方必须 `catch` 或继续声明，否则编译不过。这条约束只存在于编译期——字节码里的 `throws` 信息（`Exceptions` 属性）只给编译器看，JVM 执行 `athrow` 时不检查任何声明。选择标准：调用方**有能力就地恢复**的失败（文件不存在→换路径）用受检，逼着处理；程序逻辑错误（下标越界、空指针）用非受检，因为正确的响应是修 bug 而不是 catch。

## try/catch/finally

`catch` 按书写顺序**首个类型匹配者**获胜——子类异常的 catch 必须写在父类之前，否则编译错误（不可达代码，见 [03-控制流程](03-控制流程.md) 的编译期防线）。

`finally` 在控制离开 try 时**总是执行**：正常走完、异常被捕获、`return` 半路离开，三条路径都过它。实测（`--release 21`）：

```text
normal path:    finally 执行 → return "normal"
exception path: finally 执行 → return "caught: io failed"
```

推论两条：`finally` 是释放资源的正确位置；**`finally` 里写 `return` 或抛异常会吞掉 try 里正在上浮的东西**（返回值或异常都被覆盖），这是事故写法。

### 字节码落点：异常表

try/catch 在字节码里没有"try 指令"——编译器把每个保护区登记为方法 `Code` 属性里的一张**异常表**。实测 `javap -v`：

```text
Exception table:
   from    to  target type
       0    17    27   Class java/io/IOException   // try 段 [0,17) 抛 IOException → 跳到 27
       0    17    48   any                          // 任何类型（含 finally 路径）→ 跳到 48
      27    38    48   any
```

`athrow` 抛出时 JVM 查当前方法的表：程序计数器落在哪一行 `[from, to)` 区间、异常类型是否是该行 `type` 的实例，命中就跳到 `target`；本方法没有命中行就弹出当前栈帧、去调用者的方法里继续查——栈展开就是这张表沿调用链的递归查询，直到有 handler 接住或栈空（线程死亡，打印堆栈轨迹）。`finally` 没有专门指令，编译器把 finally 体复制到正常出口、catch 出口，外加一行 `any` 类型的表项兜住"异常穿过"的路径。

## try-with-resources 与抑制异常

实现了 `AutoCloseable` 的资源可写进 try 头，编译器保证它在离开 try 时被 `close()`——等价于一段展开后相当繁琐的 finally 代码，且处理了一个手工版几乎必错的细节：**主异常与 close 异常同时发生时的取舍**。实测：

```java
try (BadRes r = new BadRes()) {   // work() 抛 "work failed"，close() 抛 "close failed"
    r.work();
}
```

```text
primary: work failed        // try 体的异常是主异常
suppressed: close failed    // close 的异常挂到主异常的 suppressed 列表
```

主异常继续上浮，close 的异常通过 `addSuppressed` 挂上去不丢失——`getSuppressed()` 可取回。若 try 体正常而只有 close 失败，则 close 异常直接作为主异常抛出。这套语义手工写 finally 极难写对，这正是 try-with-resources（Java 7 起）存在的理由。

异常链是另一条信息保全机制：低层异常包装成高层异常时用构造器传入 `cause`——`new IllegalStateException("service down", io)`，`getCause()` 一路找回根因，堆栈轨迹完整保留。实测 `cause: disk gone`。

## 使用纪律

- **不当流程控制用**：异常路径的代价远高于正常返回（构造时要填充堆栈轨迹，抛出要查表展开）；`NumberFormatException` 式"用异常判断输入"在热路径上是性能事故。
- **不吞异常**：`catch (Exception e) {}` 让失败无声消失，调用方在错误状态上继续跑——至少记录，或包装重抛。
- **catch 具体类型**：`catch (Exception)` 一把抓会顺带兜住你没预料的 `RuntimeException`，掩盖 bug。

Lambda 中抛受检异常受函数式接口签名约束，见 [08-Lambda与函数式接口](08-Lambda与函数式接口.md)。
