# 安装与环境

## 定义

JDK 的安装与版本选择本质上是**运行时能力**和**维护成本**的权衡。Java 开发环境配置涉及 JDK 的获取和环境变量设置。JDK 是 Java 程序的**编译和运行环境集合**，但这个集合内部存在严格的层次划分：JVM 是规范（specification），HotSpot/OpenJ9/GraalVM 是实现（implementation），理解这一区分是深入 Java 运行时的基础。

```
JDK = javac (编译器) + tools (诊断工具) + JRE
```

- 运行时数据区（Runtime Data Areas）
- 帧栈结构（Frame Stack）
- 异常处理机制
- 类加载协议（Class Loader Architecture）

### JIT 编译的 Tiered Compilation 模型

JVM 的 JIT（Just-In-Time）编译采用分层策略，将代码编译阶段分为多个层级：

| 层级 | 触发条件 | 编译方式 | 优化级别 |
|------|----------|----------|----------|
| Tier 0 | 方法入口 | 解释执行 | 无 |
| Tier 1 | 热点计数 > 1500 | C1（Client JIT） | 轻度优化 |
| Tier 2 | 热点计数 > 10000 | C1 + profiling | 中度优化 |
| Tier 3 | 热点计数 > 15000 | C2（Server JIT） | 深度优化 |

**数学约束**：Tier 0 到 Tier 1 的转换阈值通常为 1500 次调用，这是基于**Amdahl 定律**的经验值——解释执行的单次开销约 100-200 周期，只有热点方法才值得 JIT 编译开销。

## 机制

### javac 编译器

将 Java 源代码编译为字节码（.class 文件）。输入是 .java 源文件，输出是包含栈式指令集的字节码。

**编译阶段**：
1. **词法分析（Tokens）**：源码字符串序列 → token 流
2. **语法分析（AST）**：token 流 → 抽象语法树
3. **语义分析**：类型检查、不变量验证、注解处理
4. **字节码生成**：AST → bytecode

**关键约束**：javac 编译时进行**前端类型检查**，但不做优化。优化是 JVM 的职责（JIT 阶段）。这意味着 `final` 关键字在 javac 眼中只是编译时约束，不影响字节码生成（final 方法只是多了 `ACC_FINAL` 标志）。

**为什么 javac 不做优化**：Java 的跨平台特性要求字节码是统一的中间表示。优化依赖于目标平台的特性（如 CPU 指令、寄存器数量），这些在 javac 阶段不可知。将优化延迟到 JIT 阶段，可以使用运行时的实际profile信息进行更精准的优化。

### java 运行器

启动 JVM，加载主类，执行字节码。负责类加载、字节码验证、JIT 编译启动。

**启动流程**：
1. 创建 JVM 实例
2. 加载引导类（`sun.launcher.LauncherHelper`）
3. 验证主类字节码
4. 执行 main 方法

**JVM 启动的数学约束**：JVM 启动时必须完成**类加载的初始化阶段**，这包括：
- 加载：找到类的字节码
- 链接：验证字节码、分配静态字段内存、解析符号引用
- 初始化：执行静态初始化器

这一过程形成偏序关系：加载 → 链接 → 初始化。初始化必须等待加载完成，链接必须等待加载完成，初始化必须等待链接完成。

### jarsigner

JAR 文件签名工具，用于代码签名和安全部署。签名过程：
1. 计算 JAR 中每个文件的摘要
2. 将摘要列表签名
3. 将签名块插入 JAR

**验证时机**：类加载时，若 SecurityManager 启用，JVM 会验证字节码的签名。

**数学本质**：签名验证是基于**非对称加密**的数字签名。设消息摘要为 $h(m)$ ，签名算法为 $Sign_{private}(h(m))$ 。验证时使用公钥 $Verify_{public}$ 检查： ，签名算法为 $Sign_{private}(h(m))$ 。验证时使用公钥 $Verify_{public}$ 检查： 。验证时使用公钥 $Verify_{public}$ 检查： 检查：

 $Verify_{public}(Sign_{private}(h(m))) = h(m)$ 

若等式成立，则签名有效，消息未被篡改。

### 模块系统（JDK 9+）

Java 9 引入模块化系统（Jigsaw），通过 `module-info.java` 声明模块依赖：

```java
module com.example.myapp {
    requires com.example.lib;      // 依赖其他模块
    exports com.example.api;        // 导出包
    exports com.example.internal to com.example.tool;  // 限定导出
}
```

**模块化的约束**：
- 未声明 `requires` 的模块不可访问
- 未声明 `exports` 的包不可访问
- `exports ... to ...` 可限定导出目标
- `requires static` 表示可选依赖（编译时必需，运行时可选）

**违反约束的后果**：
- `IllegalAccessError`：尝试访问未导出的包
- `ModuleNotFoundException`：模块未找到
- `ServiceConfigurationError`：服务提供者配置错误

**设计动机**：模块系统解决了 JDK 9 之前的"类路径地狱"问题。在类路径机制下，所有类都处于同一命名空间，JAR 之间的版本冲突只能靠运行时发现。模块系统通过强制的显式声明，将类加载错误提前到编译时或启动时。

### 虚拟线程与并发模型（Java 21 LTS）

虚拟线程（JEP 444）是 Java 21 LTS 引入的**用户态协程**，是 Java 并发模型的重大变革：

**与 OS 线程的对比**：

| 维度 | Platform Thread | Virtual Thread |
|------|-----------------|----------------|
| 创建成本 | $O(1)$ syscall | $O(1)$ heap allocation | syscall | $O(1)$ heap allocation | heap allocation |
| 栈大小 | 固定 1MB | 按需增长（KB 级别） |
| 调度权 | 内核抢占式 | JVM 协作式（yield on blocking） |
| 阻塞操作 | 阻塞 OS 线程 | 挂起虚拟线程，释放 carrier |

**数学约束**：若要支持 $N$ 并发任务： 并发任务：
- Platform Thread 模型： $N$ 个 OS 线程，内存 $O(N \cdot 1MB)$ 个 OS 线程，内存 $O(N \cdot 1MB)$ 
- Virtual Thread 模型： $M$ 个 OS 线程（  $M \ll N$），内存 $O(N \cdot 1KB)$ 个 OS 线程（  $M \ll N$ ），内存 $O(N \cdot 1KB)$），内存 $O(N \cdot 1KB)$ 

这使得单 JVM 可支持百万级并发虚拟线程。

**底层实现**：虚拟线程通过 `Continuation` 实现。Continuation 有两个状态：
- `RUNNING`：在 carrier thread 上执行
- `SUSPENDED`：在堆上保存栈帧，carrier thread 可执行其他虚拟线程

Continuation 的状态转移是**原子操作**，由 JVM 在特定 yield 点（park、sleep、blocking I/O）自动触发。

**违反约束的后果**：
- 在虚拟线程中执行阻塞系统调用（如同步文件 I/O），会阻塞整个 carrier thread
- 解决方案：使用虚拟线程兼容的 NIO（`Files.mismatch()` 等）

**归约终点**：虚拟线程是**协作式多任务**的实现。与抢占式多任务（OS 线程时间片）相比，协作式多任务依赖程序主动让出执行权。这意味着：
- 设计良好的虚拟线程代码无需修改即可享受性能提升
- 设计不良的代码（长时间占用 CPU 不yield）会导致其他虚拟线程饥饿

### AOT 编译（Java 9+ jaotc）

`jaotc` 是 Java 9 引入的 AOT（Ahead-of-Time）编译器，将 Java 代码编译为原生机器码：

```bash
jaotc --output libHelloWorld.so HelloWorld.class
jaotc --output libHelloWorld.so --class-name HelloWorld HelloWorld.class
```

**约束**：
- AOT 编译的代码无法享受 Profile-Guided Optimization（PGO）
- 动态类加载可能引入未 AOT 编译的代码（deoptimization 回退到 JIT）
- 仅支持 HotSpot 的 Server Compiler（C2）输出格式

**与 JIT 的对比**：

| 维度 | JIT 编译 | AOT 编译 |
|------|----------|----------|
| 编译时机 | 运行时 | 构建时 |
| 优化信息 | 运行时 profile | 无（保守估计） |
| 启动时间 | 慢（解释执行预热） | 快（直接执行） |
| 峰值性能 | 高（激进优化） | 中等（保守优化） |

### jlink 与自定义运行时（Java 9+）

`jlink` 将模块组装为自定义运行时镜像：

```bash
jlink --output my-runtime --add-modules java.base,java.sql
```

**数学价值**：镜像大小 = $\sum_{\text{模块}} \text{模块大小}$ ，可显著小于完整 JRE。 ，可显著小于完整 JRE。

**设计约束**：jlink 只能链接实际需要的模块，无法链接未声明的传递依赖。这保证了镜像的最小化和安全边界。

## 版本选择策略

| 场景 | 推荐版本 | 原因 |
|------|----------|------|
| 新项目 | Java 25 或 Java 21 LTS | 最新特性，长期支持 |
| 企业维护 | Java 21 LTS | 虚拟线程，长期支持稳定版 |
| Android 开发 | Java 17 | Android Studio 最低要求 |
| 学习 | Java 21 或 25 | 包含现代特性 |

**版本约束**：
- Java 版本只能向前（不能降级运行）
- 字节码版本由 javac 决定，JVM 向下兼容（高版本 JVM 可运行低版本字节码）
- 使用新语言特性需要对应版本的 javac，但编译产物可在旧版 JVM 运行
