# 集成测试

## 定义

集成测试通过**启动完整或部分容器环境**，验证组件间交互的正确性——介于单元测试（隔离单个类）和E2E测试（隔离整个系统）之间。

**层次定位**：
- 单元测试：验证**组件内部**逻辑（算法、边界条件）
- 集成测试：验证**组件之间**契约（接口兼容性、数据流）
- E2E测试：验证**系统整体**用户旅程

**集成测试的本质**：在受控的集成环境中验证组件协作，核心挑战是**控制环境复杂度**与**隔离外部依赖**。

**集成测试的认知目标**：验证组件间的**契约**是否被遵守——接口契约、数据格式契约、行为契约。这些契约在单元测试中被 Mock 替代，在集成测试中才暴露真实问题。

## 数学模型

### 环境差异的形式化

设：
- $E_{\text{test}}$ ：测试环境
- $E_{\text{prod}}$ ：生产环境
- $\Delta E = E_{\text{prod}} \setminus E_{\text{test}}$ ：环境差异集合

**理想目标**： $\Delta E = \emptyset$ （测试环境与生产环境完全一致）

**现实约束**：

| 环境因素 | 差异来源 | 隔离成本 |
|----------|----------|----------|
| 真实数据库 | 每个测试需要独立 DB 实例 | 高 |
| 真实外部服务 | 第三方 API，不可控 | 极高 |
| 真实时间 | CI 环境时间漂移 | 中 |
| 真实文件系统 | 并行测试冲突 | 中 |
| 真实网络 | 延迟、丢包、分区 | 高 |

**环境差异的风险度量**：

$$
\text{Risk}(E_{\text{test}}) = \sum_{f \in \Delta E} \text{Severity}(f) \times P(\text{failure} | f)
$$

即：每种环境差异都有其严重性和触发概率，环境差异越大，集成测试的预测价值越低。

### 事务隔离的数学边界

`@Transactional` 使测试在独立事务中执行：

$$
\text{TestMethod} \rightarrow \text{BEGIN TX} \rightarrow \text{执行测试} \rightarrow \text{ROLLBACK}
$$

**事务隔离级别的选择**（ANSI SQL 标准）：

| 级别 | 脏读 | 不可重复读 | 幻读 |
|------|------|------------|------|
| READ UNCOMMITTED | 可能 | 可能 | 可能 |
| READ COMMITTED | 不可能 | 可能 | 可能 |
| REPEATABLE READ | 不可能 | 不可能 | 可能 |
| SERIALIZABLE | 不可能 | 不可能 | 不可能 |

Spring Boot Test 默认使用 `READ_COMMITTED`（数据库默认级别）。

**隔离级别的形式化**：

| 级别 | 写锁范围 | 读锁范围 | MVCC |
|------|----------|----------|------|
| READ COMMITTED | 行级 | 无 | 是 |
| REPEATABLE READ | 行级 | 快照 | 是 |
| SERIALIZABLE | 范围锁 | 范围锁 | 否 |

### 切片测试的启动时间模型

设启动时间为 $T_{\text{startup}}$ ，组件数为 $N$ ：

| 注解 | 启动组件数 | $T_{\text{startup}}$ 量级 |
|------|------------|---------------------------|
| `@SpringBootTest` | 全部 | 10秒级 |
| `@WebMvcTest` | Controller层 | 1-2秒 |
| `@DataJpaTest` | JPA层 + 内存DB | 1-2秒 |
| `@JsonTest` | Jackson | <1秒 |

**启动时间与组件数的数学关系**：

$$
T_{\text{startup}} \approx T_0 + \sum_{i=1}^{N} T_i
$$

其中 $T_0$ 是 JVM 启动开销， $T_i$ 是第 $i$ 个组件的初始化时间。

### Docker 隔离的数学保证

TestContainers 为每个测试类创建独立容器实例：

$$
\forall c_1, c_2 \in \text{Containers}: c_1 \neq c_2 \implies \text{namespace}(c_1) \cap \text{namespace}(c_2) = \emptyset
$$

| 资源 | 隔离方式 | 隔离强度 |
|------|----------|----------|
| 网络 | Linux network namespace | 端口冲突不可能 |
| 进程 | PID namespace | 进程 ID 独立 |
| 文件系统 | mount namespace | 根文件系统独立 |
| IPC | IPC namespace | 信号量、共享内存隔离 |

## 数据流

### MockMvc 请求-响应流程

<pre>
mockMvc.perform(get("/users/1"))
        │
        ▼
MockHttpServletRequest (模拟请求)
        │
        ├──> FilterChain 代理
        │         │
        │         ▼
        │    DispatcherServlet
        │         │
        │         ├──> HandlerMapping → 找到 Controller
        │         │
        │         ├──> HandlerAdapter → 执行 Controller
        │         │
        │         └──> ViewResolver (如需渲染)
        │
        ▼
MockHttpServletResponse (模拟响应)
        │
        ▼
andExpect() 断言
</pre>

**关键路径**：FilterChain → DispatcherServlet → Controller → Response

**所有权流转**：
1. `MockMvc` 持有请求构建器
2. `perform()` 执行时，临时持有请求/响应对象
3. `andExpect()` 注册断言，不立即执行
4. 所有断言执行后，结果归测试上下文

### @DataJpaTest 事务边界

<pre>
@Test 方法入口
        │
        ▼
BEGIN TRANSACTION (隔离)
        │
        ├──> Repository 调用
        │         │
        │         ▼
        │    H2 内存数据库
        │         │
        │         ▼
        │    SQL 执行结果
        │
        ▼
ROLLBACK (测试后自动)
</pre>

每个测试方法在独立事务中执行，测试结束后自动回滚，保证测试间隔离。

**事务隔离的语义保证**：
- 测试看到的数据库状态 = 提交前的状态（READ_COMMITTED）
- 测试的写操作不会暴露给其他测试
- 测试结束后，所有变更被回滚

### TestContainers 生命周期

<pre>
@Testcontainers 启动
        │
        ▼
Docker Daemon 创建容器
        │
        ├──> PostgreSQL 容器启动
        │         │
        │         ▼
        │    容器内进程运行
        │
        ▼
@DynamicPropertySource 注入配置
        │
        ▼
@Test 执行
        │
        ▼
容器销毁 (测试结束)
</pre>

**容器生命周期的资源管理**：

| 阶段 | 资源状态 | 谁管理 |
|------|----------|--------|
| 创建 | 分配网络、PID、挂载点 | Docker Daemon |
| 运行 | 容器进程活跃 | 容器内进程 |
| 销毁 | 资源释放 | Docker Daemon |

## 机制

### @SpringBootTest WebEnvironment 选项的语义

| 选项 | Servlet容器 | HTTP服务 | 适用场景 |
|------|-------------|---------|----------|
| `MOCK`（默认） | Mock | 是 | 快速集成测试，不启动真实服务器 |
| `RANDOM_PORT` | 真实 | 是 | 真实HTTP测试，使用随机端口避免冲突 |
| `DEFINED_PORT` | 真实 | 是 | 使用 application.yml 中定义的端口 |
| `NONE` | 无 | 否 | 纯业务逻辑测试，不启动Web环境 |

**MOCK 模式的本质**：MockMvc 是 DispatcherServlet 的内存替代，HTTP 层的路由/Filter 都被保留，但不经过真实网络栈。

### MockMvc 的链式 API 语义

```java
mockMvc.perform(get("/users/{id}", 1L))           // HTTP方法+URL
    .andExpect(status().isOk())                   // 断言响应状态
    .andExpect(header().string("Content-Type", ...))
    .andExpect(jsonPath("$.name").value("Alice")) // 断言JSON body
    .andDo(print())                               // 打印请求/响应详情
```

**执行模型**：每一步 `andExpect()` 都向 `ResultActions` 注册断言，全部执行后报告失败。

### @DataJpaTest 的内存数据库隔离

每个测试在独立事务中执行，测试结束后自动回滚：

**约束**：若测试需要保留数据（如人工验证），使用 `@Rollback(false)`。

### TestContainers 的 Docker 隔离价值

**真实数据库测试的不可替代性**：
- SQL方言兼容性（PostgreSQL vs MySQL 差异）
- 索引优化器行为
- 字符集/排序规则
- 约束执行（外键、唯一索引）
- 触发器和存储过程

**Docker 隔离的数学保证**：
- 每个测试类获得独立容器实例
- 容器间网络隔离，无端口冲突
- 测试结束后容器销毁，无状态残留

### REST Assured 的 BDD 语义

```java
given()
    .contentType(ContentType.JSON)
    .body(userDto)
.when()
    .post("/users")
.then()
    .statusCode(201)
    .body("name", equalTo("Alice"));
```

`given-when-then` 结构对应 BDD 的 **Given-When-Then** 模式：
- `given`：前置条件（输入准备）
- `when`：操作执行
- `then`：结果验证

### 异步测试的分发模型

Spring MVC 的 `DeferredResult`/`CompletableFuture` 返回类型需要异步等待：

1. `asyncStarted()` 触发异步处理
2. `asyncDispatch()` 等待异步结果并分发到下一过滤器

```java
MvcResult result = mockMvc.perform(get("/async/data"))
    .andExpect(request().asyncStarted())
    .andReturn();

mockMvc.asyncDispatch(result)
    .andExpect(status().isOk());
```

## 深度：集成测试的环境隔离策略

### 隔离策略对比

| 策略 | 隔离强度 | 成本 | 适用场景 |
|------|----------|------|----------|
| 进程隔离 | 高 | 高（每个测试独立进程） | DB、MQ等有状态服务 |
| 事务隔离 | 中 | 低（同一进程内） | 数据库读写测试 |
| 容器隔离 | 高 | 中（Docker容器启动） | 需要真实服务的测试 |
| 网络隔离 | 高 | 高（WireMock等） | 外部API模拟 |

**成本-效益分析**：

$$
\text{Strategy} = \arg\max_{\text{strategy}} \frac{\text{Defect Detection Rate}}{\text{Cost}}
$$

### @DirtiesContext 的语义

每个测试前重建Spring上下文，防止Bean状态泄漏：

**约束**：频繁重建上下文会显著延长测试时间，适用于有状态Bean的测试。

**上下文重建的数学模型**：

$$
T_{\text{total}} = \sum_{i=1}^{n} (T_{\text{test},i} + T_{\text{context},i})
$$

其中 $T_{\text{context},i}$ 是第 $i$ 次上下文重建的时间。

## 参考存根

```java
// 事务边界的最小化演示
public class TransactionBoundary {
    public static void main(String[] args) {
        // 模拟 @DataJpaTest 的事务行为
        String[] operations = {
            "BEGIN TRANSACTION",
            "INSERT INTO users VALUES ('Alice')",
            "SELECT COUNT(*) FROM users",  // 可看到刚插入的数据
            "ROLLBACK"  // 测试结束，数据回滚
        };

        for (String op : operations) {
            System.out.println("[SQL] " + op);
        }
        System.out.println("其他测试看不到 Alice（已回滚）");
    }
}
```
