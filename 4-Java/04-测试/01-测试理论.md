# 测试理论

## 定义

测试是通过**执行受控输入、观察实际输出、与预期结果比对**来验证系统行为的过程。其数学本质是：对被测系统 $S$ 的规格说明 $\phi$，构造测试用例集 $T$，若所有 $t \in T$ 均通过，则在测试覆盖范围内 $S \models \phi$（系统满足规格）。

**形式化验证的局限**：测试是**有穷采样**，无法穷举无限输入空间。测试通过只能说明**在采样范围内**系统行为符合预期，不能证明**所有情况下**都正确。这是由有限计算资源决定的根本性约束——哥德尔不完备性定理的工程推论：任何足够复杂的系统，其行为空间都是无限的，但测试资源是有限的。

**测试的哲学定位**：测试不是证明正确性，而是**证伪**——通过构造能够暴露缺陷的输入来提高系统可信度。每一次通过的测试都是对系统的一次"投票"，但投票结果永远是临时的。

## 数学模型

### 测试充分性的形式化边界

设被测输入空间为 $D$，测试用例集为 $T \subseteq D$。令 $\text{Coverage}(T, D) = |T| / |D|$ 表示覆盖率。

对于无限输入空间（如整数范围、字符串空间），$|D| = \infty$，因此：
$$\lim_{|T| \to \infty} \text{Coverage}(T, D) = 0$$

这揭示了测试的根本矛盾：**覆盖率永远无法达到 100%**，即使测试用例数量趋于无穷。

**实践推论**：
- 边界值测试优先：缺陷集中在边界附近（$\epsilon$-邻域）
- 等价类划分：每个等价类只需一个代表性用例
- 组合测试：$N$ 个布尔参数的全对偶组合测试只需 $O(N \log N)$ 用例

### 测试质量的贝叶斯解释

设测试通过为事件 $P$，系统无缺陷为假设 $H$。根据贝叶斯定理：
$$P(H | P) = \frac{P(P | H) \cdot P(H)}{P(P)}$$

其中 $P(P|H)$ 是"给定系统无缺陷，测试通过"的概率（接近 1），$P(H)$ 是先验概率（系统无缺陷的初始信念），$P(H|P)$ 是后验概率。

**关键洞察**：$P(H|P)$ 永远无法达到 1——测试通过只能提高信念，无法提供确定性证明。每次失败的测试（发现缺陷）都降低了 $P(H)$，但每次通过的测试只是维持或轻微提升 $P(H)$。

## 测试金字塔

### 定义

测试金字塔是按执行成本（速度/维护代价）分层组织测试的模型——底层单元测试数量多、成本低、速度快；顶层E2E测试数量少、成本高、速度慢。

### 成本模型

$$
C_{\text{e2e}} \gg C_{\text{integration}} \gg C_{\text{unit}}
$$

$$
T_{\text{e2e}} \gg T_{\text{integration}} \gg T_{\text{unit}}
$$

成本差异来源于：
- **环境启动开销**：E2E需启动完整应用栈（DB、MQ、外部服务），单元测试仅需构造单个类
- **并行化程度**：单元测试可完全并行（无共享状态），E2E受资源限制且常串行
- **不确定性**：E2E涉及更多外部依赖（网络、时钟、随机数），失败率更高（flaky test）
- **故障定位成本**：E2E失败时需追踪整个调用链，单元测试失败直接定位到类方法

### 数据流

<pre>
        /\
       /  \      E2E（少量）
      /----\     端到端用户旅程
     /      \    关键路径验证
    /--------\
   /          \  集成测试（适量）
  /------------\ 组件契约、DB交互
 /              \
/----------------\ 单元测试（大量）
 每个类/方法独立验证
</pre>

**分层语义**：
- 单元测试验证：**组件内部逻辑**（算法正确性、边界条件）
- 集成测试验证：**组件间契约**（接口兼容性、数据一致性）
- E2E测试验证：**用户旅程完整性**（跨系统业务流程）

## 测试核心概念

### AAA 模式

测试通过 **Arrange-Act-Assert** 结构将测试行为显性化：

1. **Arrange** —— 构造被测系统的输入状态：创建mock对象、构造输入数据、初始化被测类
2. **Act** —— 对被测系统执行操作：调用方法、发送消息
3. **Assert** —— 验证系统行为符合预期：返回值、状态变化、调用参数

**AAA的本质**：将测试结构化，消除测试内部的隐式依赖，使失败原因可直接定位。

### FIRST 原则

| 原则 | 约束 | 违反后果 |
|------|------|----------|
| **F**ast | 单个测试执行时间 < 10ms | CI反馈周期延长，开发者不耐烦，导致推迟测试 |
| **I**ndependent | 测试间无共享可变状态 | 顺序敏感，间歇性失败（flaky），难以并行 |
| **R**epeatable | 每次执行结果确定 | 随机性导致不可靠，无法复现问题 |
| **S**elf-validating | 自动化断言，无需人工判断 | 无法集成到CI，丧失自动化价值 |
| **T**imely | 测试先于或与实现同步编写 | 实现难以测试，测试马后炮，回购成本高 |

### 测试隔离

测试隔离防止测试间的**隐式依赖**导致误报（false positive）。每个测试应在独立状态副本上执行：

$$
\forall i, j: i \neq j \implies \text{Test}_i.\text{state} \cap \text{Test}_j.\text{state} = \emptyset
$$

**违反此约束的症状**：
- 测试按某特定顺序执行才通过
- 在CI通过但本地失败（或反之）
- 增加新测试后现有测试开始失败

**隔离机制**：
- 单元测试：每个测试方法创建新实例（JUnit 5默认PER_METHOD）
- 集成测试：每个测试方法在独立事务中执行，测试后回滚
- E2E测试：每个测试使用独立数据或独立环境

### 测试替身（Test Double）

Test Double用伪对象替代真实依赖，隔离被测单元：

| 类型 | 调用真实实现 | 返回值 | 使用场景 |
|------|-------------|--------|----------|
| **Dummy** | 否 | 从不调用 | 填充参数列表 |
| **Fake** | 部分 | 简化实现 | 内存数据库（SQLite）、内存队列 |
| **Stub** | 否 | 预设返回值 | 返回固定测试数据 |
| **Spy** | 是 | 真实或预设 | 记录调用、验证调用次数 |
| **Mock** | 否 | 预设期望 | 验证方法调用顺序/参数 |

**Fake vs Stub 的本质区别**：
- Stub：预设值的**查表表**（输入→输出，无逻辑）
- Fake：包含简化版**业务逻辑**（如内存数据库的SQL解析）

**归约视角**：Test Double是将复杂依赖**归约**为可控行为的技术——将"真实数据库"归约为"内存Map"，将"真实HTTP服务"归约为"固定响应"。

## 测试质量

### 好的测试特征

- **唯一性**：每个测试验证一个具体行为（单一职责）
- **可读性**：测试名称清晰描述被测内容（`whenX_thenY`）
- **可靠性**：不受环境影响，结果稳定（无flaky）
- **独立性**：不依赖其他测试的执行顺序
- **快速性**：毫秒级执行完成

**测试可读性的量化标准**：测试应该能回答"这个测试验证了什么"，而不需要阅读测试代码。

### 常见反模式

| 反模式 | 问题 | 解决方案 |
|--------|------|----------|
| 断言泥潭 | 大量断言混在一起 | 分离为多个测试，每个测试一个断言 |
| 魔法值 | 数字含义不明确 | 使用命名常量或枚举 |
| 顺序依赖 | 测试必须按顺序执行 | 清理共享状态，使用测试夹具 |
| 隐藏依赖 | 测试依赖外部状态 | 使用依赖注入，显式传入 |
| 测试替身滥用 | Mock过度，测试的是Mock而非真实逻辑 | 保留关键集成测试，使用真实依赖 |

## 测试策略

### 边界值测试

边界值测试聚焦输入范围的**极端点**——缺陷在边界处发生概率高于内部：

$$
D_{\text{boundary}} = \{-\infty, \text{min}, \text{min}+1, \text{max}-1, \text{max}, +\infty\}
$$

**边界值定理**：函数 $f$ 在边界附近的行为往往与其内部行为不同——因为：
1. 程序员容易犯"边界混淆"错误（`<` vs `<=`）
2. 数据类型存在极值（`Integer.MAX_VALUE + 1` 溢出）
3. 资源限制往往在边界处触发

**Java 17 边界值参考**：
```java
Integer.MIN_VALUE, -1, 0, 1, Integer.MAX_VALUE
Long.MIN_VALUE, -1L, 0L, 1L, Long.MAX_VALUE
Double.MIN_VALUE, -0.0, 0.0, Double.NaN, Double.MAX_VALUE
```

### 等价类划分

将输入空间划分为有效类和无效类，每个等价类只需一个代表性测试用例：

$$
D = D_{\text{valid}} \cup D_{\text{invalid\_1}} \cup D_{\text{invalid\_2}} \cup \dots
$$

$$
|T_{\text{representative}}| \ll |D|
$$

**等价类的定义**：若两个输入 $x_1, x_2$ 对被测系统产生相同的行为输出，则它们属于同一等价类。

**组合测试的数学**：
- 全因子组合：$2^N$（$N$个布尔参数）
- 成对组合（Pairwise）：覆盖所有2元组合，复杂度 $O(N \log N)$
- 混合强度组合：$N$-wise（通常 $N=3$）作为折中

### 错误处理测试

验证异常场景：
- 异常类型是否正确（`ExpectedException` vs `assertThrows`）
- 异常消息是否包含关键信息（可本地化的错误描述）
- 异常是否导致资源泄漏（文件句柄、连接未关闭）
- 异常传播是否正确（调用栈是否保留）

**异常测试的完备性**：
```java
// 验证异常类型
assertThrows(IllegalArgumentException.class, () -> validator.validate(null));

// 验证异常消息（深度检查）
IllegalArgumentException ex = assertThrows(
    IllegalArgumentException.class,
    () -> validator.validate("")
);
assertTrue(ex.getMessage().contains("must not be blank"));

// 验证资源释放
assertThrows(SomeException.class, () -> {
    var resource = new Resource();
    resource.process(); // 异常抛出
});
assertTrue(resource.isClosed()); // 验证无泄漏
```

## 测试覆盖率

### 覆盖率类型

| Counter | 定义 | 数学含义 |
|---------|------|----------|
| **LINE** | 执行到的源代码行数占总行数比例 | $\frac{|L_{\text{covered}}|}{|L_{\text{total}}|}$ |
| **BRANCH** | 执行到的分支数占总分支数比例 | $\frac{|B_{\text{covered}}|}{|B_{\text{total}}|}$ |
| **CLASS** | 至少被调用一次的类占总类数 | $\frac{|C_{\text{covered}}|}{|C_{\text{total}}|}$ |
| **METHOD** | 至少被调用一次的方法占总方法数 | $\frac{|M_{\text{covered}}|}{|M_{\text{total}}|}$ |
| **INSTRUCTION** | JVM字节码指令是否被执行 | $\frac{|I_{\text{covered}}|}{|I_{\text{total}}|}$ |

### 覆盖率标准

| 级别 | 行覆盖率 | 分支覆盖率 |
|------|----------|------------|
| 最低 | 50% | 40% |
| 良好 | 70% | 60% |
| 优秀 | 80% | 70% |
| 严格 | 90% | 80% |

**分支覆盖的特殊性**：每个 `if/while/for/?:` 产生两个分支（true/false）。100%分支覆盖意味着每个条件的每个结果都被执行过。

### 覆盖率的深层局限

覆盖率衡量的是**执行广度**，不是**验证深度**：

- **覆盖不等于正确**：错误结果被执行同样增加覆盖
- **覆盖不保证逻辑**：代码执行了，但断言可能永远为真
- **覆盖存在盲区**：未测试的代码 = 不知道行为的代码

**覆盖率与缺陷发现率的关系**（经验数据）：
```
行覆盖率  →  缺陷发现率
50%       →  30-40%
70%       →  50-60%
80%       →  65-75%
90%       →  75-85%
```

## 测试与调试的对比

| 维度 | 测试 | 调试 |
|------|------|------|
| 时机 | 编写时（Test-Driven） | 发现Bug后 |
| 目的 | 验证行为，防止回归 | 定位缺陷根因 |
| 方法 | 构造输入→观察输出 | 追踪执行路径 |
| 产出 | 测试套件（持久化） | 修复代码 |
| 自动化 | 自动化执行 | 半自动/手动 |
| 目标 | 覆盖率最大化 | 故障定位精确化 |

**TDD的三定律**：
1. 编写生产代码前，先写一个失败的测试
2. 编写刚好足以通过测试的生产代码
3. 重构改进代码，同时保持测试通过

## 缺陷分类

| 类型 | 描述 | 测试策略 |
|------|------|----------|
| 功能缺陷 | 行为与规格不符 | 正面/负面用例、决策表测试 |
| 边界缺陷 | 边界值处理错误 | 边界值分析 |
| 性能缺陷 | 响应时间超过SLA | 性能测试、压力测试 |
| 安全缺陷 | 漏洞（注入、XSS等） | 安全测试、模糊测试 |
| 竞态缺陷 | 并发下行为不确定 | 压力测试、重复执行 |
| 内存泄漏 | 资源未正确释放 | 长时间运行监控 |
| 逻辑缺陷 | 条件判断错误 | 路径覆盖测试 |

**缺陷严重性与测试优先级**：
$$\text{Priority} = \text{Severity} \times \text{Likelihood}$$

高严重性 × 高可能性 = 必须立即测试
