# 测试理论

## 定义

测试是通过**执行受控输入、观察实际输出、与预期结果比对**来验证系统行为的过程。其本质是**对无限行为空间的有穷采样**——在有限计算资源下，通过构造有限的测试用例集来逼近对系统行为的置信度。

**形式化边界**：设被测系统 $S$ 的规格说明为 $\phi$ ，测试用例集为 $T$ 。若所有 $t \in T$ 均通过，则在测试覆盖范围内 $S \models \phi$ 。但这只能证明**采样范围内的正确性**，无法证明**全域正确性**。这由有限计算资源的根本约束决定——哥德尔不完备性定理的工程推论：任何足够复杂的系统，其行为空间都是无限的，但测试资源是有限的。

**测试的哲学定位**：测试不是证明正确性，而是**证伪**——通过构造能够暴露缺陷的输入来提高系统可信度。每一次通过的测试都是对系统的一次"投票"，但投票结果永远是临时的。每一次失败的测试（发现缺陷）都直接证明了系统的某种错误行为。

**测试神谕问题（Oracle Problem）**：测试需要知道每个输入的"正确答案"，但对于复杂系统（如机器学习模型、物理仿真），正确答案本身可能未知或不可计算。这是测试理论中尚未完全解决的深层问题。

## 数学模型

### 测试充分性的形式化边界

设被测输入空间为 $D$ ，测试用例集为 $T \subseteq D$ 。令 $\text{Coverage}(T, D) = |T| / |D|$ 表示覆盖率。

对于无限输入空间（如整数范围、字符串空间）， $|D| = \infty$ ，因此：
$\lim_{|T| \to \infty} \text{Coverage}(T, D) = 0$

这揭示了测试的根本矛盾：**覆盖率永远无法达到 100%**，即使测试用例数量趋于无穷。

**实践推论**：
- 边界值测试优先：缺陷集中在边界附近（ $\epsilon$-邻域），此处函数行为往往与其内部行为不同
- 等价类划分：每个等价类只需一个代表性用例，将无穷空间压缩为有限集合
- 组合测试： $N$ 个布尔参数的全对偶组合测试只需 $O(N \log N)$ 用例，远小于 $2^N$

### 测试质量的贝叶斯解释

设测试通过为事件 $P$ ，系统无缺陷为假设 $H$ 。根据贝叶斯定理：
$P(H | P) = \frac{P(P | H) \cdot P(H)}{P(P)}$

其中：
- $P(P|H)$ 是"给定系统无缺陷，测试通过"的概率（接近 1）
- $P(H)$ 是先验概率（系统无缺陷的初始信念）
- $P(H|P)$ 是后验概率

**关键洞察**： $P(H|P)$ 永远无法达到 1——测试通过只能提高信念，无法提供确定性证明。每次失败的测试都降低了  $P(H)$，但每次通过的测试只是维持或轻微提升  $P(H)$。

**缺陷发现率的边际效益**（经验数据）：

| 行覆盖率 | 缺陷发现率 | 95% 置信区间 |
|----------|------------|--------------|
| 50% | 30-40% | [28%, 42%] |
| 70% | 50-60% | [47%, 63%] |
| 80% | 65-75% | [62%, 78%] |
| 90% | 75-85% | [72%, 88%] |

**边际效益递减**：从 80% 提升到 90% 覆盖率的成本，远高于从 50% 提升到 80%。

### 缺陷优先级量化

缺陷严重性与测试优先级的数学关系：
$\text{Priority} = \text{Severity} \times \text{Likelihood}$

高严重性 × 高可能性 = 必须立即测试

### 测试采样作为优化问题

给定测试预算 $B$ （时间/用例数），采样策略的目标是最大化缺陷发现率：

$\text{MAXimize} \quad \mathbb{E}[\text{defects found}]$
$\text{subject to} \quad |T| \leq B$

**贪婪近似解**：优先采样边界值，因为边界附近的概率密度函数往往最尖锐（缺陷概率密度最高）。

## 数据流

<pre>
输入空间 D                      测试用例集 T                 测试执行结果
+-------------+                +-------------+             +-------------+
| x₁         |                | t₁          |             | PASS/FAIL  |
| x₂         |  采样策略      | t₂          |  执行       | ...        |
| ...        | -------------> | ...         | ----------> | t_n 结果   |
| x_|D|     |                | t_|T|       |             |             |
+-------------+                +-------------+             +-------------+
  无限或巨大                                                     |
  |                                                             |
  +-- 采样策略决定哪些输入被选中 --------------------------------+
  |  边界值优先 | 等价类代表 | 组合覆盖                        |
  v                                                             |
  违反约束时：测试无法覆盖的输入空间 = 盲区                       |
</pre>

**数据形态变换**：
1. 输入空间 $D$ （概念上的所有可能输入）
2. 测试用例集 $T$ （从 $D$ 中选取的有限子集）
3. 执行结果（PASS/FAIL 的有限序列）
4. 覆盖率度量（ $|T|/|D|$ 的近似计算）

**所有权转移**：
1. 输入空间 $D$ 中的候选输入属于"问题域"
2. 采样后进入测试用例集 $T$ ，所有权归测试框架
3. 执行时，结果的所有权归断言引擎
4. 最终报告时，所有权归测试执行上下文

## 机制

### 测试金字塔的成本模型

$$
C_{\text{e2e}} \gg C_{\text{integration}} \gg C_{\text{unit}}
$$
$$
T_{\text{e2e}} \gg T_{\text{integration}} \gg T_{\text{unit}}
$$

成本差异的根源：
- **环境启动开销**：E2E需启动完整应用栈（DB、MQ、外部服务），单元测试仅需构造单个类
- **并行化程度**：单元测试可完全并行（无共享状态），E2E受资源限制且常串行
- **不确定性**：E2E涉及更多外部依赖（网络、时钟、随机数），失败率更高（flaky test）
- **故障定位成本**：E2E失败时需追踪整个调用链，单元测试失败直接定位到类方法

### AAA 模式的本质

测试通过 **Arrange-Act-Assert** 结构将测试行为显性化：
- **Arrange**：构造被测系统的输入状态（数据准备、依赖注入）
- **Act**：对被测系统执行操作（方法调用、消息发送）
- **Assert**：验证系统行为符合预期（返回值、状态变化、调用参数）

**AAA的本质**：将测试结构化，消除测试内部的隐式依赖，使失败原因可直接定位。违反此结构会导致测试内部出现隐式状态共享，难以诊断间歇性失败。

### FIRST 原则的约束

| 原则 | 约束 | 违反后果 |
|------|------|----------|
| **F**ast | 单个测试执行时间 < 10ms | CI反馈周期延长，开发者不耐烦，导致推迟测试 |
| **I**ndependent | 测试间无共享可变状态 | 顺序敏感，间歇性失败（flaky），难以并行 |
| **R**epeatable | 每次执行结果确定 | 随机性导致不可靠，无法复现问题 |
| **S**elf-validating | 自动化断言，无需人工判断 | 无法集成到CI，丧失自动化价值 |
| **T**imely | 测试先于或与实现同步编写 | 实现难以测试，测试马后炮，回购成本高 |

**违反独立性的数学表达**：
$\forall i, j: i \neq j \implies \text{Test}_i.\text{state} \cap \text{Test}_j.\text{state} = \emptyset$

违反此约束的症状：测试按某特定顺序执行才通过；在CI通过但本地失败；增加新测试后现有测试开始失败。

### 测试替身的归约视角

Test Double是将复杂依赖**归约**为可控行为的技术——将"真实数据库"归约为"内存Map"，将"真实HTTP服务"归约为"固定响应"。

| 类型 | 调用真实实现 | 返回值类型 | 使用场景 |
|------|-------------|------------|----------|
| **Dummy** | 否 | 从不调用 | 填充参数列表 |
| **Fake** | 部分 | 简化实现 | 内存数据库（SQLite）、内存队列 |
| **Stub** | 否 | 预设查表返回值 | 返回固定测试数据 |
| **Spy** | 是 | 真实或预设 | 记录调用、验证调用次数 |
| **Mock** | 否 | 预设期望 | 验证方法调用顺序/参数 |

**Fake vs Stub 的本质区别**：
- Stub：预设值的**查表表**（输入→输出，无逻辑）
- Fake：包含简化版**业务逻辑**（如内存数据库的SQL解析）

### 边界值定理

函数 $f$ 在边界附近的行为往往与其内部行为不同：
1. 程序员容易犯"边界混淆"错误（`<` vs `<=`）
2. 数据类型存在极值（`Integer.MAX_VALUE + 1` 溢出）
3. 资源限制往往在边界处触发

**边界值集合**：
$D_{\text{boundary}} = \{-\infty, \text{min}, \text{min}+1, \text{max}-1, \text{max}, +\infty\}$

### 组合测试的数学

- 全因子组合： $2^N$ （  $N$个布尔参数）
- 成对组合（Pairwise）：覆盖所有2元组合，复杂度 $O(N \log N)$
- **数学保证**：若每个参数的取值集合为 $V_i$ ，则成对组合测试覆盖所有 $(x_i \in V_i, x_j \in V_j)$ 对，其中 $i \neq j$
- **经验结论**：研究表明，80%以上的缺陷可由成对组合触发

### 测试神潭问题的形式化

对于某些被测系统 $S$ ，正确的输出 $\phi(x)$ 本身不可计算或未知：

**已知**：
- 输入空间 $D$
- 被测系统 $S: D \to Y$
- 规格 $\phi$ ： $D \to Y$ （可能部分未知）

**问题**：若 $\phi$ 本身未知或不可计算，如何验证 $S$ 的正确性？

**工程解**：
- 参考实现（Reference Implementation）：用已知正确的实现 $S_{\text{ref}}$ 作为 oracle
- 蜕变测试（Metamorphic Testing）：验证 $S(x)$ 与 $S(f(x))$ 的关系，而非单个输出
- 不变量验证（Invariant Testing）：验证 $S$ 满足某些不随输入变化的性质

## 参考存根

```java
// 测试质量的贝叶斯更新模拟
public class BayesianTestQuality {
    public static void main(String[] args) {
        double prior = 0.9;  // 初始信念：系统无缺陷的概率
        double pPassGivenNoDefect = 0.99;
        double pPass = 0.95;  // 总体测试通过率

        // 贝叶斯更新：测试通过后，系统无缺陷的后验概率
        double posterior = (pPassGivenNoDefect * prior) / pPass;
        System.out.printf("后验概率: %.4f%n", posterior);
        // 输出：后验概率: 0.9368
    }
}
```
