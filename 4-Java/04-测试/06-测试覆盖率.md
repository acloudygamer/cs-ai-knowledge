# 测试覆盖率

## 定义

测试覆盖率是**已执行代码与总代码的比例**度量，用于发现未测试的代码路径。其数学本质：

$$
C_{\text{line}} = \frac{|L_{\text{covered}}|}{|L_{\text{total}}|}
$$

覆盖率是**下限指标**——高覆盖率只能证明某些代码被执行过，不能证明这些代码被正确测试。

**根本局限**：覆盖率测量的是**执行广度**，不是**验证深度**。100%覆盖率不等于100%正确性。

## JaCoCo 机制

### 字节码插桩原理

JaCoCo在类加载时通过Java Agent（`java.lang.instrument`）注入字节码，为每个分支插入计数器：

<pre>
源代码:
if (x > 0) { a(); } else { b(); }

字节码插桩后:
if (x > 0) { a(); [分支计数器+1] } else { b(); [分支计数器+1] }
</pre>

每次分支执行时，对应计数器递增。测试结束后，JaCoCo Agent将覆盖率数据写入文件或通过TCP推送。

**插桩时机**：
- 运行时插桩：Java Agent 在类加载时注入
- 离线插桩：编译后使用工具注入

### Maven配置

```xml
<plugin>
    <groupId>org.jacoco</groupId>
    <artifactId>jacoco-maven-plugin</artifactId>
    <executions>
        <execution>
            <goals>
                <goal>prepare-agent</goal>      <!-- 设置 jacoco.agent.args -->
            </goals>
        </execution>
        <execution>
            <id>report</id>
            <phase>test</phase>
            <goals>
                <goal>report</goal>             <!-- 生成 HTML/CSV/XML 报告 -->
            </goals>
        </execution>
        <execution>
            <id>check</id>
            <phase>verify</phase>
            <goals>
                <goal>check</goal>              <!-- 质量门禁 -->
            </goals>
            <configuration>
                <rules>
                    <rule>
                        <element>CLASS</element>
                        <limits>
                            <limit>
                                <counter>LINE</counter>
                                <value>COVEREDRATIO</value>
                                <limit>0.80</limit>
                            </limit>
                        </limits>
                    </rule>
                </rules>
            </configuration>
        </execution>
    </executions>
</plugin>
```

## 覆盖率类型

### Counter类型

| Counter | 含义 | 公式 |
|---------|------|------|
| **LINE** | 源代码行是否被执行 | $\frac{\text{covered lines}}{\text{total lines}}$ |
| **BRANCH** | 每个条件分支的true/false是否都被覆盖 | $\frac{\text{covered branches}}{\text{total branches}}$ |
| **CLASS** | 类是否被加载调用 | $\frac{\text{covered classes}}{\text{total classes}}$ |
| **METHOD** | 方法是否被调用 | $\frac{\text{covered methods}}{\text{total methods}}$ |
| **INSTRUCTION** | JVM字节码指令是否被执行 | $\frac{\text{covered instructions}}{\text{total instructions}}$ |
| **COMPLEXITY** | 圈复杂度覆盖 | 分支覆盖与行覆盖的综合 |

### 分支覆盖率详解

每个`if`/`while`/`for`/`?:`产生两个分支（true/false）。100%分支覆盖要求所有分支都被执行至少一次：

```java
if (age < 0 || age > 150) {  // 2个分支
    return false;
}
return age >= 18;              // 1个分支（>=18：true/false）
```

**分支 vs 条件覆盖**：
- BRANCH：覆盖每个boolean表达式**结果**的组合
- CONDITION：覆盖每个条件的**每个操作数**的true/false

```java
if (a && b) { ... }
// BRANCH 覆盖：整体 true/false
// CONDITION 覆盖：a true/false + b true/false
```

### 覆盖比率

| Value | 含义 |
|-------|------|
| **TOTAL** | 总数 |
| **COVERED** | 已覆盖数量 |
| **MISSED** | 未覆盖数量 |
| **COVEREDRATIO** | 覆盖率（COVERED / TOTAL） |

## 覆盖率标准

| 级别 | 行覆盖率 | 分支覆盖率 |
|------|----------|------------|
| 最低 | 50% | 40% |
| 良好 | 70% | 60% |
| 优秀 | 80% | 70% |
| 严格 | 90% | 80% |

### 标准的选择依据

覆盖率标准的选取应基于**缺陷容忍度**和**测试成本**的平衡：

$$
\text{目标覆盖率} = \arg\max_{c} \left( \text{缺陷发现率}(c) \times \text{测试成本效率}(c) \right)
$$

通常80%行覆盖 + 70%分支覆盖是成本与收益的较优平衡点。

## SonarQube 质量门禁

SonarQube在代码质量维度之上增加覆盖率维度：

```xml
<rule>
    <metric>coverage</metric>
    <operator>LESS_THAN</operator>
    <value>80</value>
    <priority>MAJOR</priority>
</rule>
```

## 常见问题

### 私有方法覆盖

私有方法通过反射调用测试：

```java
Method privateMethod = MyClass.class.getDeclaredMethod("methodName", paramTypes);
privateMethod.setAccessible(true);
privateMethod.invoke(instance, args);
```

使用`@TestVisibleForTesting`标记测试用途的私有方法（虽然该注解本身不改变可见性，仅作文档）。

### Lombok 问题

Lombok生成的方法（`getter`/`setter`/`equals`/`hashCode`）应从覆盖率排除：

```xml
<rule>
    <element>CLASS</element>
    <namePattern>.*DTO|.*VO|.*Entity</namePattern>
    <excludes>
        <exclude>**/get*</exclude>
        <exclude>**/set*</exclude>
        <exclude>**/equals</exclude>
        <exclude>**/hashCode</exclude>
    </excludes>
</rule>
```

### 枚举覆盖

枚举的所有值都需要测试，确保每个分支case都被覆盖：

```java
enum Status { PENDING, APPROVED, REJECTED }
// switch 语句若缺少 REJECTED 分支，分支覆盖率 < 100%
```

## 最佳实践

### 不要追求 100%

覆盖率是**发现工具**，而非目标本身：

- 100%覆盖不等于100%正确
- 测试业务逻辑（边界、异常）比覆盖样板代码更重要
- 关注关键路径和缺陷高发区

### 增量提升

每次新增代码时补充对应测试，逐步提升覆盖率——一次性达到高覆盖率往往不可持续。

### 关注分支覆盖

分支覆盖率低意味着存在**未测试的条件分支**，是缺陷隐藏的高风险区：

$$
\text{未覆盖分支数} = |B_{\text{total}}| - |B_{\text{covered}}|
$$

### 增量覆盖率

CI流水线应追踪增量覆盖率（新增代码的覆盖率），而非仅总覆盖率：

$$
C_{\text{incremental}} = \frac{\text{新增代码覆盖行数}}{\text{新增代码总行数}}
$$

---

## 覆盖率与代码质量的关系

| 场景 | 覆盖率 | 代码质量 |
|------|--------|----------|
| 测试通过但未验证结果 | 高 | 低 |
| 测试边界和异常 | 低 | 高 |
| 测试实现细节 | 高 | 中 |
| 测试业务逻辑 | 中 | 高 |

覆盖率衡量的是**执行广度**，不是**验证深度**。高质量测试需要同时关注覆盖率和断言质量。

## 深度：覆盖率的贝叶斯解释

设覆盖率 $c$ 下发现缺陷的概率为 $P(\text{defect} | c)$。

根据经验数据：
- $c < 50\%$：$P(\text{defect} | c) \approx 30\%$
- $c = 70\%$：$P(\text{defect} | c) \approx 55\%$
- $c = 80\%$：$P(\text{defect} | c) \approx 70\%$
- $c = 90\%$：$P(\text{defect} | c) \approx 80\%$

**边际效益递减**：从 80% 提升到 90% 覆盖率的成本，远高于从 50% 提升到 80%。

**实用建议**：优先保证核心业务逻辑的高覆盖率，而非追求全面高覆盖率。
