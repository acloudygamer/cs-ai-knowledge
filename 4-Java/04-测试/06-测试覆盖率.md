# 测试覆盖率

## 定义

测试覆盖率是**已执行代码与总代码的比例**度量，用于发现未测试的代码路径。其数学本质：

$$
C_{\text{line}} = \frac{|L_{\text{covered}}|}{|L_{\text{total}}|}
$$

覆盖率是**下限指标**——高覆盖率只能证明某些代码被执行过，不能证明这些代码被正确测试。

**根本局限**：覆盖率测量的是**执行广度**，不是**验证深度**。100%覆盖率不等于100%正确性。测试通过但未验证结果的代码同样增加覆盖。

**覆盖率的认知价值**：覆盖率作为**必要非充分条件**——它告诉你"哪些代码没被测过"，但不能告诉你"被测过的代码是否被正确测试"。

## 数学模型

### 覆盖率的下限语义

覆盖率是**必要非充分条件**：

$$
\text{高覆盖} \nRightarrow \text{高质量测试}
$$

| 场景 | 覆盖率 | 代码质量 |
|------|--------|----------|
| 测试通过但未验证结果 | 高 | 低 |
| 测试边界和异常 | 低 | 高 |
| 测试实现细节 | 高 | 中 |
| 测试业务逻辑 | 中 | 高 |

### 缺陷发现率的边际效益

设覆盖率 $c$ 下发现缺陷的概率为 $P(\text{defect} | c)$ ： 下发现缺陷的概率为 $P(\text{defect} | c)$ ： ：

| 行覆盖率 | $P(\text{defect} | c)$ | 边际收益 | | 边际收益 |
|----------|--------------------------|----------|
| < 50% | ≈ 30% | 高 |
| 70% | ≈ 55% | 中 |
| 80% | ≈ 70% | 中低 |
| 90% | ≈ 80% | 低 |

**边际效益递减**：从 80% 提升到 90% 覆盖率的成本，远高于从 50% 提升到 80%。

### 覆盖率目标的选择

覆盖率标准的选取应基于**缺陷容忍度**和**测试成本**的平衡：

$$
\text{目标覆盖率} = \arg\max_{c} \left( \text{缺陷发现率}(c) \times \text{测试成本效率}(c) \right)
$$

通常 80% 行覆盖 + 70% 分支覆盖是成本与收益的较优平衡点。

### 控制流图（CFG）的形式化

代码覆盖率基于**控制流图**：

$$
\text{CFG} = (V, E, v_{\text{entry}}, v_{\text{exit}})
$$

其中：
- $V$ ：基本块顶点集 ：基本块顶点集
- $E \subseteq V \times V$ ：有向边 ：有向边
- $v_{\text{entry}} \in V$ ：入口块 ：入口块
- $v_{\text{exit}} \in V$ ：出口块 ：出口块

**路径覆盖**：
$$
P = \{ \text{path}(v_{\text{entry}}, v_{\text{exit}}) \}
$$
$$
C_{\text{path}} = \frac{|P_{\text{covered}}|}{|P|}
$$

对于循环结构，路径数可能无限。

### 分支覆盖的计算

每个 `if`/`while`/`for`/`?:` 产生两个分支（true/false）。100%分支覆盖要求所有分支都被执行至少一次：

$$
C_{\text{branch}} = \frac{|B_{\text{covered}}|}{|B_{\text{total}}|}
$$

其中 $B_{\text{total}}$ 是总分支数（每个条件分支点 × 该点的分支数）。 是总分支数（每个条件分支点 × 该点的分支数）。

## 数据流

### JaCoCo 字节码插桩流程

<pre>
源代码:
if (x > 0) { a(); } else { b(); }

编译后字节码:
ICONST_0
ILOAD_1
IFLE else_branch    ; 条件跳转
INVOKE a()
GOTO end
else_branch:
INVOKE b()
end:
NOP

JaCoCo Agent 注入后:
ICONST_0
ILOAD_1
IFLE else_branch    ; 分支计数器 A +1
INVOKE a()
GOTO end
else_branch:        ; 分支计数器 B +1
INVOKE b()
end:
NOP
</pre>

每次分支执行时，对应计数器递增。

**插桩的语义**：JaCoCo 在每个分支处插入计数器，记录该分支被执行了多少次。这本质上是**运行时剖分（Runtime Profiling）**。

### 分支覆盖 vs 条件覆盖的数据流差异

<pre>
BRANCH 覆盖:

## 机制

### JaCoCo 字节码插桩原理

JaCoCo 在类加载时通过 Java Agent（`java.lang.instrument`）注入字节码，为每个分支插入计数器：

**插桩时机**：
- 运行时插桩：Java Agent 在类加载时注入
- 离线插桩：编译后使用工具注入

**插桩范围**：
- 所有方法的所有分支（if/while/for/?:）
- 每个 boolean 表达式的 true/false 分支

**插桩的代价模型**：
$$
T_{\text{overhead}} \approx \alpha \times |E_{\text{instrumented}}|
$$

其中 $\alpha$ 是每次分支计数的平均开销， $|E_{\text{instrumented}}|$ 是被插桩的分支数。 是每次分支计数的平均开销， $|E_{\text{instrumented}}|$ 是被插桩的分支数。 是被插桩的分支数。

### 分支覆盖 vs 条件覆盖

| 类型 | 含义 | 覆盖内容 |
|------|------|----------|
| **BRANCH** | 每个条件的**结果组合** | `a && b` → true,true / true,false / false,true / false,false |
| **CONDITION** | 每个条件的**每个操作数** | `a` true/false + `b` true/false |

```java
if (a && b) { ... }
// BRANCH 覆盖：整体 true/false
// CONDITION 覆盖：a true/false + b true/false
```

**MC/DC（Modified Condition/Decision Coverage）**：航空电子领域常用的覆盖标准，要求每个条件能独立影响整个表达式的结果。

### 覆盖率的深层局限

- **覆盖不等于正确**：错误结果被执行同样增加覆盖
- **覆盖不保证逻辑**：代码执行了，但断言可能永远为真
- **覆盖存在盲区**：未测试的代码 = 不知道行为的代码

**覆盖率作为启发式指标**：它是一个有价值的**否定指标**——低覆盖率直接说明有问题，但高覆盖率不保证没问题。

### SonarQube 质量门禁

SonarQube 在代码质量维度之上增加覆盖率维度，作为 CI 质量门禁的一部分：

**增量覆盖率追踪**：
$$
C_{\text{incremental}} = \frac{\text{新增代码覆盖行数}}{\text{新增代码总行数}}
$$

只关注新增代码的覆盖率，而非总覆盖率，防止历史债务拖累新代码质量。

### 突变测试（Mutation Testing）的关系

覆盖率是**静态执行指标**，突变测试是**动态缺陷注入指标**：

| 维度 | 覆盖率 | 突变测试 |
|------|--------|----------|
| 本质 | 记录代码是否被执行 | 注入缺陷验证测试能否发现 |
| 代价 | 低（仅计数） | 高（需多次执行） |
| 信息 | 哪些代码被跳过 | 测试能否检测真实缺陷 |

**突变得分**：
$$
\text{Mutation Score} = \frac{\text{被杀死（检测到）的突变体数}}{\text{总有效突变体数}}
$$

## 常见问题

### 私有方法覆盖

私有方法通过反射调用测试：

```java
Method privateMethod = MyClass.class.getDeclaredMethod("methodName", paramTypes);
privateMethod.setAccessible(true);
privateMethod.invoke(instance, args);
```

使用 `@TestVisibleForTesting` 标记测试用途的私有方法（该注解本身不改变可见性，仅作文档）。

**设计原则**：优先测试公开接口，私有方法通过公开接口间接验证。仅在私有方法包含复杂独立逻辑时才直接测试。

### Lombok 生成代码的排除

Lombok 生成的方法（`getter`/`setter`/`equals`/`hashCode`）应从覆盖率排除：

```xml
<rule>
    <element>CLASS</element>
    <namePattern>.*DTO|.*VO|.*Entity</namePattern>
    <excludes>
        <exclude>**/get*</exclude>
        <exclude>**/set*</exclude>
        <exclude>**/equals</exclude>
        <exclude>**/hashCode</exclude>
    </excludes>
</rule>
```

### 枚举覆盖的完整性

枚举的所有值都需要测试，确保每个分支 case 都被覆盖：

```java
enum Status { PENDING, APPROVED, REJECTED }
// switch 语句若缺少 REJECTED 分支，分支覆盖率 < 100%
```

## 深度：覆盖率的贝叶斯解释

设覆盖率 $c$ 下发现缺陷的概率为 $P(\text{defect} | c)$ 。 下发现缺陷的概率为 $P(\text{defect} | c)$ 。 。

**先验假设**：测试工程师对代码质量的初始信念 $P(\text{defect})$ 。 。

**贝叶斯更新**：
 $P(\text{defect} | c) = \frac{P(c | \text{defect}) \cdot P(\text{defect})}{P(c)}$ 

其中 $P(c | \text{defect})$ 是"给定存在缺陷，测试达到覆盖率 $c$"的概率。 是"给定存在缺陷，测试达到覆盖率 $c$ "的概率。"的概率。

## 参考存根

```java
// 覆盖率计算的最简化演示
public class CoverageDemo {
    public static void main(String[] args) {
        // 模拟分支覆盖计数
        int[] branchCount = {0, 0};  // [条件true次数, 条件false次数]
        int totalBranches = 2;

        // 模拟执行流
        int[] results = {1, 0, 1, 1};  // 1=true, 0=false
        for (int r : results) {
            branchCount[r]++;
        }

        // 计算覆盖率
        int covered = (branchCount[0] > 0 ? 1 : 0) + (branchCount[1] > 0 ? 1 : 0);
        double coverage = (double) covered / totalBranches;

        System.out.printf("分支覆盖: %d/%d = %.0f%%%n", covered, totalBranches, coverage * 100);
        // 输出: 分支覆盖: 2/2 = 100%
    }
}
```
