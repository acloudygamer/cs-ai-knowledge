# 测试覆盖率

## 定义

测试覆盖率是**已执行代码与总代码的比例**度量，用于发现未测试的代码路径。其数学本质：

$$
C_{\text{line}} = \frac{|L_{\text{covered}}|}{|L_{\text{total}}|}
$$

覆盖率是**下限指标**——高覆盖率只能证明某些代码被执行过，不能证明这些代码被正确测试。

**根本局限**：覆盖率测量的是**执行广度**，不是**验证深度**。100%覆盖率不等于100%正确性。测试通过但未验证结果的代码同样增加覆盖。

---

## 数学模型

### 覆盖率的下限语义

覆盖率是**必要非充分条件**：

$$
\text{高覆盖} \nRightarrow \text{高质量测试}
$$

| 场景 | 覆盖率 | 代码质量 |
|------|--------|----------|
| 测试通过但未验证结果 | 高 | 低 |
| 测试边界和异常 | 低 | 高 |
| 测试实现细节 | 高 | 中 |
| 测试业务逻辑 | 中 | 高 |

### 缺陷发现率的边际效益

设覆盖率 $c$ 下发现缺陷的概率为 $P(\text{defect} | c)$：

| 行覆盖率 | $P(\text{defect} | c)$ |
|----------|--------------------------|
| < 50% | ≈ 30% |
| 70% | ≈ 55% |
| 80% | ≈ 70% |
| 90% | ≈ 80% |

**边际效益递减**：从 80% 提升到 90% 覆盖率的成本，远高于从 50% 提升到 80%。

### 覆盖率目标的选择

覆盖率标准的选取应基于**缺陷容忍度**和**测试成本**的平衡：

$$
\text{目标覆盖率} = \arg\max_{c} \left( \text{缺陷发现率}(c) \times \text{测试成本效率}(c) \right)
$$

通常 80% 行覆盖 + 70% 分支覆盖是成本与收益的较优平衡点。

## 机制

### JaCoCo 字节码插桩原理

JaCoCo 在类加载时通过 Java Agent（`java.lang.instrument`）注入字节码，为每个分支插入计数器：

**插桩时机**：
- 运行时插桩：Java Agent 在类加载时注入
- 离线插桩：编译后使用工具注入

**插桩范围**：
- 所有方法的所有分支（if/while/for/?:）
- 每个 boolean 表达式的 true/false 分支

### 分支覆盖 vs 条件覆盖

| 类型 | 含义 | 覆盖内容 |
|------|------|----------|
| **BRANCH** | 每个条件的**结果组合** | `a && b` → true,true / true,false / false,true / false,false |
| **CONDITION** | 每个条件的**每个操作数** | `a` true/false + `b` true/false |

```java
if (a && b) { ... }
// BRANCH 覆盖：整体 true/false
// CONDITION 覆盖：a true/false + b true/false
```

### 分支覆盖的计算

每个 `if`/`while`/`for`/`?:` 产生两个分支（true/false）。100%分支覆盖要求所有分支都被执行至少一次：

```java
if (age < 0 || age > 150) {  // 2个分支
    return false;
}
return age >= 18;              // 1个分支（>=18：true/false）
```

**公式**：
$$
C_{\text{branch}} = \frac{|B_{\text{covered}}|}{|B_{\text{total}}|}
$$

其中 $B_{\text{total}}$ 是总分支数（每个条件分支点 × 该点的分支数）。

### 覆盖率的深层局限

- **覆盖不等于正确**：错误结果被执行同样增加覆盖
- **覆盖不保证逻辑**：代码执行了，但断言可能永远为真
- **覆盖存在盲区**：未测试的代码 = 不知道行为的代码

### SonarQube 质量门禁

SonarQube 在代码质量维度之上增加覆盖率维度，作为 CI 质量门禁的一部分：

**增量覆盖率追踪**：
$$
C_{\text{incremental}} = \frac{\text{新增代码覆盖行数}}{\text{新增代码总行数}}
$$

只关注新增代码的覆盖率，而非总覆盖率，防止历史债务拖累新代码质量。

## 常见问题

### 私有方法覆盖

私有方法通过反射调用测试：

```java
Method privateMethod = MyClass.class.getDeclaredMethod("methodName", paramTypes);
privateMethod.setAccessible(true);
privateMethod.invoke(instance, args);
```

使用 `@TestVisibleForTesting` 标记测试用途的私有方法（该注解本身不改变可见性，仅作文档）。

### Lombok 生成代码的排除

Lombok 生成的方法（`getter`/`setter`/`equals`/`hashCode`）应从覆盖率排除：

```xml
<rule>
    <element>CLASS</element>
    <namePattern>.*DTO|.*VO|.*Entity</namePattern>
    <excludes>
        <exclude>**/get*</exclude>
        <exclude>**/set*</exclude>
        <exclude>**/equals</exclude>
        <exclude>**/hashCode</exclude>
    </excludes>
</rule>
```

### 枚举覆盖的完整性

枚举的所有值都需要测试，确保每个分支 case 都被覆盖：

```java
enum Status { PENDING, APPROVED, REJECTED }
// switch 语句若缺少 REJECTED 分支，分支覆盖率 < 100%
```

## 深度：覆盖率的贝叶斯解释

设覆盖率 $c$ 下发现缺陷的概率为 $P(\text{defect} | c)$。

**先验假设**：测试工程师对代码质量的初始信念 $P(\text{defect})$。

**贝叶斯更新**：
$$P(\text{defect} | c) = \frac{P(c | \text{defect}) \cdot P(\text{defect})}{P(c)}$$

其中 $P(c | \text{defect})$ 是"给定存在缺陷，测试达到覆盖率 $c$"的概率。

**关键洞察**：覆盖率提供的是**条件概率**，而非确定性保证。$P(\text{defect} | c = 0.9)$ 远小于 1——即使 90% 覆盖率的测试套件，仍有约 20% 的概率遗漏缺陷。

## 参考存根

```java
// 覆盖率计算的最简化演示
public class CoverageDemo {
    public static void main(String[] args) {
        // 模拟分支覆盖计数
        int[] branchCount = {0, 0};  // [条件true次数, 条件false次数]
        int totalBranches = 2;

        // 模拟执行流
        int[] results = {1, 0, 1, 1};  // 1=true, 0=false
        for (int r : results) {
            branchCount[r]++;
        }

        // 计算覆盖率
        int covered = (branchCount[0] > 0 ? 1 : 0) + (branchCount[1] > 0 ? 1 : 0);
        double coverage = (double) covered / totalBranches;

        System.out.printf("分支覆盖: %d/%d = %.0f%%%n", covered, totalBranches, coverage * 100);
        // 输出: 分支覆盖: 2/2 = 100%
    }
}
```
