# 面向对象

## 定义

面向对象编程（OOP）是一种将**状态**（数据）和**行为**（方法）封装在**抽象数据类型**（类）中的编程范式。核心概念是**对象**——拥有自身状态且能响应消息的实体。

从抽象代数视角，类是**代数结构**（algebraic structure），定义了数据的表示和操作的不变式。子类通过**扩展**（extends）或**实现**（implements）建立**子类型关系**，构成类型层次。

## 数学模型

### 封装的约束形式化

封装是**信息隐藏**的实现机制。设类 $C$ 的内部表示为 $R$，对外接口为 $I$。封装要求：

$$\forall r \in R, \forall i \in I: \text{valid}(i, r) \Rightarrow \text{不变量}(r)$$

即：所有通过接口的操作必须维持不变量。形式化约束：

$$\forall c \in C, \forall m \in \text{methods}(C): \text{pre}(m, c) \Rightarrow \text{post}(m, c)$$

违反封装的典型场景：字段直接暴露为 public，外部代码可绕过不变量检查直接修改状态。

### 继承的谓词逻辑形式化

继承建立 **is-a** 关系：若 $S$ extends $T$，则：

$$S \models p \Rightarrow T \models p$$

其中 $p$ 是类型 $T$ 的所有可见谓词（方法规格）。子类继承父类的**规约**（specification），但不一定继承其实现。

Liskov 替换原则（LSP）的谓词逻辑形式化：

$$\forall x: S, \forall P: \text{predicate on } T: P(x) \Rightarrow P(T(x))$$

即：$S$ 的所有实例在 $T$ 出现的上下文中，必须保持 $T$ 的行为性质。

### 多态的表驱动分派形式化

方法调用 `obj.method()` 的分派可建模为**虚函数表查找**：

$$\text{dispatch}(obj, m) = \text{vtable}[\text{type}(obj)][m]$$

其中 vtable 是类到方法实现的映射表：

$$\text{vtable}: \text{Type} \times \text{Method} \rightarrow \text{Implementation}$$

动态分派保证：运行时根据对象的**实际类型**（而非引用类型）选择方法实现。

### 子类型关系的 Liskov 替换原则

Liskov 替换原则（LSP）：若 $S$ 是 $T$ 的子类型，则 $T$ 的所有对象都可替换为 $S$ 的对象，而不改变程序性质。

形式化：对于 $T$ 上的所有操作 $op$ 和 $S$ 上满足规格的替换 $op'$：

$$\forall x: T, P(x) \Rightarrow P(S(x))$$

违反 LSP 的典型案例：正方形是矩形的子类型，但 setWidth() 和 setHeight() 的行为不一致（正方形要求宽高相等）。

### 方法分派的数学描述

方法调用 `obj.method(args)` 的分派过程：

1. 从 obj 的**实际类型** $T$ 开始
2. 在 $T$ 的方法表中查找 method
3. 若找到，调用；否则在父类中继续查找
4. 直到找到或到达 Object

这形成了一个**继承链上的线性查找**，复杂度 $O(depth)$。虚函数表（vtable）实现：

| 类 | vtable 起始偏移 | method1 | method2 | ... |
|----|-----------------|---------|---------|-----|
| A | 0 | A::m1 | A::m2 | ... |
| B extends A | 偏移 | B::m1 | A::m2 | ... |

### 访问修饰符的可见性代数

| 修饰符 | 同类 | 同包 | 子类 | 其他包 |
|--------|------|------|------|--------|
| private | ✓ | ✗ | ✗ | ✗ |
| default | ✓ | ✓ | ✗ | ✗ |
| protected | ✓ | ✓ | ✓ | ✗ |
| public | ✓ | ✓ | ✓ | ✓ |

protected 的设计：**子类可能在不同包**，需要继承访问权；同包非子类用 default 即可。

**对象创建过程**：
1. 分配内存（ Eden 区）
2. 初始化字段为默认值（0/null/false）
3. 执行构造器链（super() → 字段初始化 → 构造器体）
4. 返回引用

## 机制

### 封装的信息隐藏

封装的本质是**不变量维护**：类对外提供受控接口，隐藏内部表示和约束条件。外部代码不能绕过不变量直接操作内部状态。

```java
public class Counter {
    private int count;  // 不变量：count >= 0
    public void increment() { count++; }
    public int getCount() { return count; }
}
```

若 count 直接暴露为 public，可以设为负数，破坏业务约束。

### 继承 vs 组合

继承建立 **is-a** 关系，组合建立 **has-a** 关系。

| 考量 | 继承 | 组合 |
|------|------|------|
| 耦合度 | 高（子类依赖父类实现） | 低（依赖接口） |
| 灵活性 | 编译时绑定 | 运行时可替换 |
| 多态 | 自动获得 | 需接口实现 |

**优先使用组合**的原因：继承使子类脆弱地依赖父类实现细节；组合允许通过接口解耦。

### 接口的默认方法与多继承冲突

Java 8 引入默认方法后，接口可以提供实现。这引入了**多继承冲突**（diamond problem）：

```java
interface A { default void foo() { } }
interface B { default void foo() { } }
interface C extends A, B { }  // 编译错误：foo() 冲突
interface C extends A, B {
    @Override
    default void foo() { A.super.foo(); }  // 消歧
}
```

**冲突解决规则**：
1. 同签名默认方法：子类必须显式覆盖
2. 抽象方法优先于默认方法
3. 若两个默认方法冲突，子类必须显式消歧

### 内部类的闭包语义

局部内部类和匿名内部类可以访问**隐式 final**（effectively final）的局部变量：

```java
int x = 10;  // effectively final
Func f = () -> x;  // 捕获 x 的值
// x = 20;  // 修改后，f 的闭包行为未定义
```

**为什么需要 effectively final**：内部类实例的生命周期可能超过方法执行。如果变量可修改，内部类持有的引用将指向不确定的值。
