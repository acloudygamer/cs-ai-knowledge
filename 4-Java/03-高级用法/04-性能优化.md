# 性能优化

## 定义

Java性能优化的核心思维是**"减少浪费"**——减少对象创建减少GC压力，减少锁竞争减少调度开销，减少虚调用减少解释执行开销，将热点代码从解释执行提升到编译执行。

性能优化的本质是在**吞吐量**、**延迟**和**内存占用**三者之间取得项目相关的最优平衡——没有通用最优解，只有场景最优解。

## 数学模型

### Amdahl定律

并行系统的加速比 $S$ 取决于串行部分的比例 $F$ 和并行 worker 数 $N$：

$$
S = \frac{1}{F + \frac{1-F}{N}} \quad \Rightarrow \quad \lim_{N \to \infty} S = \frac{1}{F}
$$

**含义**：如果5%的代码是串行的，则最大加速比不超过20倍。无论如何增加线程数，超过这个上限后CPU利用率都会趋于饱和。

### 对象分配速率与GC频率的量化模型

设对象分配率为 $A$（字节/秒），GC回收率为 $R$（字节/秒），堆大小为 $H$：

$$
\text{GC间隔} = \frac{H}{A - R}
$$

每次Young GC的停顿时间 $T_{\text{ygc}}$ 与存活对象量成正比：

$$
T_{\text{ygc}} = \alpha \cdot \text{存活对象大小} + \beta \cdot \text{并行协调开销}
$$

**关键约束**：Survivor区容量为 $S_{\text{survivor}}$，若每次GC存活对象超过 $S_{\text{survivor}}$，对象直接进入老年代（premature promotion），导致老年代GC频率上升。

### 锁竞争的开销模型

设线程竞争某锁的概率为 $p$，每次阻塞涉及：

| 损耗来源 | 量级 |
|---------|------|
| 上下文切换 | $1\!-\!10\,\mu s$ |
| 内核态切换 | $0.5\!-\!1\,\mu s$ |
| 缓存失效（被阻塞线程的L1/L2数据移出） | $10\!-\!100\,\mu s$ |

$$
\text{每次竞争代价} = p \cdot (T_{\text{ctx}} + T_{\text{kernel}} + T_{\text{cache}})
$$

**锁粒度设计约束**：锁内保护的临界区越长、访问频率越高，$p$ 越大。当 $p \cdot T_{\text{cache}}$ 超过临界区执行时间本身时，分段锁优化的收益急剧上升。

### JIT编译热点检测阈值

JIT编译触发基于方法调用计数器和循环回边计数器：

$$
T_{\text{compile}} = \frac{C_{\text{threshold}}}{\text{call rate}}
$$

Server模式阈值：$10{,}000$ 次；Client模式阈值：$1{,}500$ 次。超过阈值触发 OSR（On-Stack Replacement）。

### 对象分配逃逸分析

<pre>
new Object()
    │
    ├── [不逃逸] ──> 栈上分配（Scalar Replaceable）
    │           或 TLAB分配（线程本地分配缓冲）
    │
    └── [逃逸] ──> 堆上分配 ──> GC管理
                        │
                        └── 年龄≥阈值 ──> 老年代
</pre>

**逃逸分析（Escape Analysis）**是JIT编译器判断对象是否仅在单线程内使用的优化技术。如果对象不逃逸，JIT可能：
- 栈上分配（Stack Allocation）
- 标量替换（Scalar Replacement）：对象字段分解为独立变量
- 锁消除（Lock Elision）：消除不必要的 synchronized

## 机制

### 循环内创建对象的真实代价

```java
// ❌ 每次迭代创建新对象
for (int i = 0; i < 1000; i++) {
    String s = new String("hello"); // 每个String在堆分配
}
```

**为何有害**：
1. **GC压力增加**：每 iteration 创建一个对象，假设每对象 48 字节，1000 次迭代 = 48KB 垃圾需 GC 管理。若 GC 回收器跟不上分配速率，对象进入老年代。
2. **TLAB 耗尽**：线程本地分配缓冲（TLAB）耗尽后需同步申请新 TLAB，若多线程同时耗尽会导致竞争。
3. **JIT 编译产物膨胀**：JIT 编译时，每个 new Object() 的快速路径被内联，但大量短命对象的析构和 GC marking 仍消耗编译产物缓存。

```java
// ✅ 复用对象或预分配
String s = "hello"; // 栈上或字符串常量池，无分配压力
for (int i = 0; i < 1000; i++) {
    process(s); // 复用同一个引用
}
```

### StringBuilder 拼接的量化优势

```java
// ❌ 每次 + 创建新 String 对象（O(n²)）
String s = "";
for (String item : items) {
    s = s + item; // 每次创建新 String，内容复制
}
```

**为何低效**：每次 `s + item` 的执行路径是：
1. 创建 StringBuilder（堆分配）
2. append s 的内容（字符数组复制）
3. append item 的内容（字符数组复制）
4. toString() 创建新 String（又一次复制）

总复杂度 $T(n) = O(n^2)$，每次拼接都有 O(目标字符串长度) 的复制。

```java
// ✅ 单一 StringBuilder，预估容量
StringBuilder sb = new StringBuilder(items.size() * 16); // 预分配减少扩容
for (String item : items) {
    sb.append(item).append(",");
}
```

**为何高效**：StringBuilder 内部 char[] 会自动扩容（通常 1.5 倍或 2 倍），但只要预估合理，扩容次数有限。总复杂度降至 O(n)。

### 自动装箱的性能陷阱

```java
// ❌ 频繁装箱/拆箱
int sum = 0;
for (int i = 0; i < 10000; i++) {
    sum += i; // 自动装箱：Integer.valueOf(i) — 堆分配!
}
```

**为何有害**：`Integer.valueOf()` 在 -128 到 127 范围内有 IntegerCache 缓存（静态 final Integer 数组），但超出范围每次都 new Integer()。10000 次循环中约 98.7% 的值会触发堆分配。

```java
// ✅ 使用原始类型集合
IntArrayList list = new IntArrayList(); // 不装箱
for (int i = 0; i < 10000; i++) {
    list.add(i); // 纯原始类型，无装箱
}
int sum = list.stream().mapToInt(Integer::intValue).sum();
```

**量化差异**：每 10000 次自动装箱 ≈ 10000 次堆分配 + 10000 次 GC 对象管理。原始类型避免所有这些开销。

### 锁竞争的性能损耗与优化原理

锁竞争导致线程阻塞，涉及：
- **上下文切换**：约 $1\!-\!10\,\mu s$
- **内核态切换**：用户态→内核态→用户态，约 $0.5\!-\!1\,\mu s$
- **缓存失效**：被阻塞线程的栈数据和L1/L2缓存行被移出

**为何减少锁粒度能提升性能**：若临界区内操作时间为 $T_{\text{crit}}$，锁持有概率 $p \approx \frac{\lambda \cdot T_{\text{crit}}}{N}$（$\lambda$为请求率，$N$为并发线程数）。$p$ 越高，线程越容易阻塞。

分段锁将单一锁拆为 $K$ 个子锁，每个子锁的竞争概率降为 $p/K$，但同时引入新问题：跨子锁的操作（如 size()）需要组合，增加复杂度。

```java
// ConcurrentHashMap 的分段锁思想
// JDK 8+: 使用 synchronized + CAS，不再是旧版 Segment 分段
// 但思想一致：缩小锁保护范围
Node<K,V>[] tab = table;
if ((f = tabAt(tab, i = (n - 1) & hash)) == null) {
    synchronized (f) { // 只锁单个 bucket，而非整表
        // ...
    }
}
```

### 并发容器的无锁化原理

ConcurrentHashMap 的 `get()` 操作完全无锁（volatile 读取），`putIfAbsent()` 使用 CAS：

$$
\text{CAS}(\text{expected=null}, \text{new=node}) = \begin{cases}
\text{true} & \text{位置为空，直接插入} \\
\text{false} & \text{位置已有值，失败重试}
\end{cases}
$$

**为何无锁优于有锁**：无锁操作的线程不会因竞争失败而被挂起，因此不会出现上下文切换、缓存失效等连锁损耗。对于读多写少场景，volatile 读取的延迟通常在 $10\!-\!50\,ns$，而一次线程阻塞的代价在 $1\!-\!10\,\mu s$，相差 $100\!-\!1000$ 倍。

### JIT编译的优化层级

JIT编译器将字节码逐步优化：

| 层级 | 名称 | 优化程度 | 编译耗时 |
|------|------|----------|----------|
| 0 | 解释执行 | 无 | 0 |
| 1 | C1（Client编译器）| 快速轻量 | 短 |
| 2 | C1 + 少量profiling | 中等 | 中 |
| 3 | C1 + 完整profiling | 深 | 中长 |
| 4 | C2（Server编译器）| 激进深度优化 | 长 |

**C2的激进优化**：
- 内联（inline）：消除调用开销，允许更多优化
- 逃逸分析：栈上分配、锁消除
- 循环展开：减少分支判断
- 矢量化和SIMD：利用CPU向量指令

### 虚调用的去虚化

Java的接口调用默认是**虚调用**（需要查虚表）：

$$
\text{invokevirtual} \Rightarrow \text{vtable lookup} \Rightarrow O(1) \text{ 但有常数}
$$

JIT在运行时通过**类型推断**和**单态/多态内联缓存**将虚调用去虚化为直接调用。如果一个调用点只见过一种具体类型，JIT将其内联为直接调用。

## 最佳实践总结

| 优化维度 | 手段 | 约束边界 |
|----------|------|----------|
| 对象分配 | 对象池/StringBuilder/预分配 | 内存占用↑，需要正确释放 |
| 锁竞争 | ConcurrentHashMap/Atomic* | 代码复杂度↑ |
| GC | 合理堆大小/选对收集器 | 无通用最优解 |
| JIT | 热点代码保持简洁 | 庞大方法无法内联 |
| 缓存 | 合理数据结构设计 | 复杂度↑，可能浪费内存 |

## 参考存根

```java
// 减少GC压力的对象复用（≤30行）
public class ObjectPool<T> {
    private final Queue<T> pool;
    private final IntFunction<T> factory;
    private final Consumer<T> reset;

    public ObjectPool(IntFunction<T> factory, Consumer<T> reset, int size) {
        this.pool = new ConcurrentLinkedQueue<>();
        this.factory = factory;
        this.reset = reset;
        for (int i = 0; i < size; i++) pool.add(factory.apply(0));
    }

    public T acquire() { return pool.poll() != null ? pool.poll() : factory.apply(0); }
    public void release(T obj) { reset.accept(obj); pool.add(obj); }
}
```
