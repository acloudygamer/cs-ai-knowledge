# 响应式编程

> 响应式编程的本质是"异步数据流编程"——将数据视为时间轴上的事件序列，通过声明式操作符描述转换逻辑，而非命令式的循环和回调。

## 定义

响应式流（Reactive Streams）是一套基于**背压（backpressure）的异步流处理规范**（JEP与Java 9 Flow API），核心目标是解决快速生产者压垮慢消费者的问题。Flux表示0到N个元素的异步序列，Mono表示0或1个元素，两者都是Publisher的实现，共同构成Reactor（Spring WebFlux的底层）核心类型。

---

## 发布-订阅模型

### 核心语义

响应式流的核心是**非阻塞、背压驱动的异步数据交换**。Publisher产生数据，Subscriber消费数据，Subscription承载请求控制权，Processor承上启下。

<pre>
Publisher ──subscribe(Subscriber)──> Subscriber
                  │
                  ├── onSubscribe(Subscription)  // 首次信号，建立控制通道
                  ├── onNext(T)                // 数据（可零次或多次）
                  ├── onError(Throwable)        // 终止：错误
                  └── onComplete()             // 终止：正常结束

Subscription ──request(n)─────────────────────> Publisher  // 背压控制
Subscription ──cancel()──────────────────────> Publisher  // 取消订阅
</pre>

### 协议状态机

Subscription生命周期是一个确定性有限状态机：

$$
\text{Subscription.state} \in \{\text{INITIAL}, \text{ACTIVE}, \text{CANCELLED}\}
$$

$$
\text{INITIAL} \xrightarrow{\text{onSubscribe}} \text{ACTIVE}
$$

$$
\text{ACTIVE} \xrightarrow{\text{request(n>0)}} \text{ACTIVE (继续接收 onNext)}
$$

$$
\text{ACTIVE} \xrightarrow{\text{cancel()}} \text{CANCELLED}
$$

$$
\text{ACTIVE} \xrightarrow{\text{onError 或 onComplete}} \text{CANCELLED}
$$

**约束**：任何状态转换后，所有后续信号均为非法操作——若在 CANCELLED 状态后收到 onNext，Subscriber应抛出 `java.lang.IllegalStateException`。

## 冷发布者 vs 热发布者

### 数学模型

**冷发布者（Cold）**：每次订阅独立生成完整序列。设序列长度为 $N$ ，订阅次数为  $s$，则数据产生总量：

$$
\text{total emitted} = s \times N
$$

**热发布者（Hot）**：订阅共享同一数据源，订阅后仅接收新到达的数据：

$$
\text{total emitted} = \begin{cases}
0 & \text{订阅前已产生的数据丢失} \\
\infty & \text{如果数据无限产生}
\end{cases}
$$

### 数据流对比

<pre>
Cold Publisher (Flux.just(1, 2, 3))
    │
    Subscriber A 订阅 ──> 收到 [1, 2, 3]
    Subscriber B 订阅 ──> 收到 [1, 2, 3]  (独立序列)

Hot Publisher (Sinks.Many)
    │
    发射 1, 2, 3 (无订阅者，数据丢失)
    Subscriber A 订阅 ──> 收到 4, 5, 6 (仅订阅后的数据)
    Subscriber B 订阅 ──> 收到 5, 6 (订阅更晚，丢失更多)
</pre>

## 背压（Backpressure）

### 定义

背压是**消费者向生产者通告处理能力**的机制——通过`Subscription.request(n)`告诉生产者"我当前最多处理n个元素"，生产者不得超过此上限发送数据。

### 数学模型

设消费者处理速率为 $\lambda_c$ （元素/秒），生产者产生速率为 $\lambda_p$ （元素/秒），缓冲容量为 $B$ ：

$$
\text{背压生效} \iff \lambda_p > \lambda_c \land \text{缓冲未满}
$$

若 $\lambda_p > \lambda_c$ 持续，生产者必须实施流控制策略：
- **丢弃策略**：丢弃新元素（TTL/Window）
- **累积策略**：累积待处理元素直至内存压力
- **反压传播**：向上游传播`request(0)`完全停止

### 实现机制

```java
Flux.range(1, 1000)
    .flatMap(i -> process(i), 10)  // 并发上限 10
    .limitRate(100);                // 每次 request(100)，消费 80% 时自动补充
```

`limitRate(n)`实现：每次`request(n)`，当已交付 $n \times 0.75$ 个元素时自动补充request。

## Mono与Flux

### Mono语义

Mono表示最多一个元素或一个错误/完成信号。其状态机：

$$
\text{Mono.state} \in \{\text{UNSUBSCRIBED}, \text{REQUESTED\_MAYBE}, \text{HAS\_VALUE}, \text{HAS\_ERROR}, \text{COMPLETED}\}
$$

```java
Mono<String> mono = Mono.just("hello");
Mono<User> userMono = Mono.just(userId)
    .flatMap(this::fetchUser)       // 异步转换
    .map(User::toDTO)               // 同步转换
    .onErrorReturn(defaultUser)     // 错误时返回默认值
    .switchIfEmpty(Mono.just(defaultUser)); // 空值时切换
```

### Flux语义

Flux表示零到无限个元素序列，支持多种发射场景：

```java
Flux<Integer> flux = Flux.just(1, 2, 3);
Flux<String> flux1 = Flux.fromIterable(users)
    .map(User::getName)
    .filter(name -> name.startsWith("A"));
```

## 操作符

### 分类体系

| 类别 | 典型操作符 | 变换类型 |
|------|-----------|----------|
| 创建 | `just`, `range`, `interval`, `fromIterable` | 无输入→有输出 |
| 转换 | `map`, `flatMap`, `scan`, `reduce` | $T \rightarrow U$ |
| 过滤 | `filter`, `distinct`, `take`, `skip`, `sample` | 序列裁剪 |
| 组合 | `merge`, `zip`, `combineLatest`, `concat` | 多源合并 |
| 条件 | `takeUntil`, `defaultIfEmpty`, `switchIfEmpty` | 逻辑分支 |
| 错误处理 | `retry`, `onErrorReturn`, `onErrorResume` | 错误恢复 |

### flatMap并发模型

```java
flux.flatMap(concurrentOperation, maxConcurrency)
```

其中`maxConcurrency`控制并发订阅数。数学上：同一时刻最多有`maxConcurrency`个内部Publisher活跃。

### scan vs reduce

- `scan`：对每个元素应用累加器，**立即发射中间结果**
- `reduce`：仅在序列完成后发射**最终结果**

```java
Flux.just(1, 2, 3).scan((a, b) -> a + b);
// 发射: 1, 3, 6

Flux.just(1, 2, 3).reduce((a, b) -> a + b);
// 发射: 6 (仅最后一个)
```

## 调度器

### 定义

调度器（Scheduler）决定操作在哪个线程执行，通过`publishOn`/`subscribeOn`切换执行上下文。

### 线程模型

| 调度器 | 用途 | 线程来源 |
|--------|------|----------|
| `Schedulers.immediate()` | 当前线程 | 调用线程 |
| `Schedulers.single()` | 单后台线程 | 重用单线程 |
| `Schedulers.parallel()` | 并行操作 | 固定线程数（CPU核数） |
| `Schedulers.boundedElastic()` | 阻塞操作 | 弹性线程池（上限CPU×10） |
| `Schedulers.fromExecutorService()` | 自定义 | 用户指定 |

```java
Mono.just("hello")
    .publishOn(Schedulers.boundedElastic())  // 切换后续操作到弹性线程池
    .map(this::heavyOperation);              // 在 boundedElastic 线程执行
```

### subscribeOn vs publishOn

- `subscribeOn`：影响**上游**（源）的订阅线程，整个链从该线程开始
- `publishOn`：影响**下游**（后续操作）的执行线程，多次调用仅最近一次有效

## 错误处理

### 策略分类

| 策略 | 方法 | 语义 |
|------|------|------|
| 返回默认值 | `onErrorReturn` | 错误发生时发射固定值然后完成 |
| 切换到备选Publisher | `onErrorResume` | 用另一个Publisher替换错误流 |
| 重试 | `retry` / `retryWhen` | 重新订阅上游 |
| 抛出 | `onErrorMap` | 将错误转换为另一种异常 |

### retry数学约束

`retry(n)`重试 $N$ 次后仍失败，则向下游发射最终错误。重试总次数：

$$
\text{total attempts} = 1 + N
$$

backoff策略可使用`retryWhen(Retry.backoff(...))`，实现指数退避：

$$
t_i = \min(t_{\max}, t_0 \times 2^i + \text{jitter})
$$

## WebFlux控制器

```java
@GetMapping("/users/{id}")
public Mono<ResponseEntity<User>> getUser(@PathVariable Long id) {
    return userService.findById(id)
        .map(ResponseEntity::ok)
        .defaultIfEmpty(ResponseEntity.notFound().build());
}
```

### 响应式CRUD语义

- `findById` → `Mono<User>`（0或1个用户）
- `findAll` → `Flux<User>`（0到N个用户）
- `save` → `Mono<User>`（单实体保存返回Mono）
- 批量操作 → `Flux<savedEntity>`

## Java响应式生态

| 库 | 特性 |
|-----|------|
| RxJava | ReactiveX Java实现，最成熟 |
| Project Reactor | Spring WebFlux内置，Mono/Flux发源地 |
| Java 9 Flow API | JDK标准，但API最小化（仅接口，无实现） |

所有实现均遵循`Reactive Streams TCK`（Technology Compatibility Kit）规范，保证不同库之间的互操作性。

## 性能考量

### 并发上限

```java
flux.flatMap(i -> process(i), 10)  // 最多10个并发
    .limitRate(100);                // 背压阈值
```

### 阻塞操作隔离

```java
flux.publishOn(Schedulers.boundedElastic())
    .map(i -> blockingOperation());  // 阻塞操作不污染响应式线程池
```

### 背压实践

`limitRate(n)`实现自动补充：当已交付 $n \times 0.75$ 个元素时，自动`request(n)`补充，始终保持  $n$个元素在处理中。
