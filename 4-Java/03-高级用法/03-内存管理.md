# 内存管理

## 定义

JVM内存管理的本质是**分代假设**——大多数对象朝生夕灭，少数存活久远。基于此假设的垃圾回收器用不同策略处理不同代龄对象，在吞吐量和停顿时间之间取得平衡。

**GC Roots** 是可达性分析的起始点：栈帧中的本地变量表引用的对象、方法区静态属性引用的对象、方法区常量引用的对象、JNI引用。

**对象头（Object Header）** 包含Mark Word（对象自身状态）和Klass Pointer（指向类元数据的指针），在64位JVM中占用12字节（未开启指针压缩时为16字节含对齐填充）。

## 数学模型

### Mark Word 状态机

$$
\text{Mark Word}_{64\text{bit}} = \begin{cases}
\text{hashCode:25 + age:4 + biased\_lock:1 + lock:2} & \text{无锁态} \\
\text{thread:54 + epoch:2 + age:4 + biased\_lock:1 + lock:2} & \text{偏向锁} \\
\text{ptr\_to\_lock\_record:62 + lock:2} & \text{轻量级锁} \\
\text{ptr\_to\_monitor:62 + lock:2} & \text{重量级锁} \\
\text{unused:62 + lock:2} & \text{GC标记}
\end{cases}
$$

### 分代回收的死亡率假设

设对象在第 $i$ 次Young GC后被回收的概率为 $p_i$：
$$
p_i \approx 90\% \sim 99\% \quad \text{（大多数对象在第一次或第二次Young GC时死亡）}
$$

分代收集的理论基础：绝大多数对象是**孤儿对象**——创建后立即使用一次即无用。

### G1回收时间模型

$$
T_{\text{g1}} \approx \frac{\text{存活对象大小}}{\text{回收速度}} + \text{并行协调开销} + \text{STW停顿}
$$

G1通过**Remembered Sets**追踪Region间的引用关系，避免全堆扫描。

### JVM内存布局

<pre>
堆 (Heap)                              方法区 (Method Area)
┌──────────────────────────────────┐   ┌───────────────────────────┐
│  Eden区 (对象分配首选)            │   │  类信息                    │
│  ┌────────────────────────────┐  │   │  运行时常量池               │
│  │  S0 Survivor 区            │  │   │  JIT编译产物               │
│  └────────────────────────────┘  │   │  静态变量                  │
│  ┌────────────────────────────┐  │   └───────────────────────────┘
│  │  S1 Survivor 区            │  │
│  └────────────────────────────┘  │
│  ┌────────────────────────────┐  │
│  │  Old Generation (老年代)    │  │
│  └────────────────────────────┘  │
└──────────────────────────────────┘

栈 (Stack)                            程序计数器 (PC)
┌──────────────────────────────────┐   ┌───────────────────────────┐

│  - 操作数栈                        │   └───────────────────────────┘
│  - 动态链接                        │
│  - 返回地址                        │
└──────────────────────────────────┘
```

### 对象分配与回收流程

<pre>
new Object()
    │
    ├── TLAB（线程本地分配缓冲）──> Eden区 ──> Young GC ──> Survivor区
    │                                                         │
    │                                              age≥阈值 ──> Old区
    │                                                         │
    └──────────────────────────────────────────────────> 老年代GC
                                                            │
                                                      Mixed GC
                                                            │
                                                      回收失败 ──> Full GC
```

### ZGC着色指针读取屏障

<pre>
应用线程                              ZGC
    │                                  │
    │ 读取对象引用 ref = obj.field      │
    │──────────────>                   │
    │                [Load Barrier拦截] │
    │                检查着色位          │
    │                ───────────────>   │
    │                [标记/转发/重试]    │
    │<───────────────                  │
    │ 返回真实引用（或转发地址）        │
    │
    继续执行（无需STW停顿）
</pre>

**关键**：ZGC的着色指针将对象状态编码在引用自身中，Load Barrier在读取引用时即时检查，避免了传统GC的STW暂停。

## 机制

### 为何需要分代收集？

如果对整个堆使用统一的标记-整理算法：
- **停顿时间长**：所有存活对象都需要整理，停顿时间与堆大小成正比
- **吞吐量低**：大量短命对象反复整理，浪费

分代收集的核心洞察：**大多数对象朝生夕灭**，只有少部分进入老年代。因此：
- Young区用**复制算法**（存活对象少，整理快）
- Old区用**标记-整理算法**（存活对象多，整理慢但频率低）

### 着色指针（Colored Pointers）原理

ZGC在64位指针中使用未使用的高位（47-45）存储标记信息：

$$
\text{引用指针} = \underbrace{\text{unused:18}}_{\text{扩展}} | \underbrace{\text{mark:3}}_{\text{着色位}} | \underbrace{\text{地址:43}}_{\text{实际堆地址}}
$$

三个着色位：
- **Marked0/Marked1**：用于并发标记
- **Remapped**：指向对象是否已重定位到新地址

Load Barrier根据着色位判断：
- 若对象正在被移动：协助重定位（请求自旋等待）
- 若对象已移动：直接跟随转发指针

### Shenandoah的Brooks Pointer

与ZGC不同，Shenandoah在对象头中添加一个**转发指针**：

$$
\text{对象头} = \text{Klass Pointer} + \text{Brooks Pointer} + \text{其他}
$$

存活对象被移动后，旧位置的Brooks Pointer指向新位置。读取时检查Brooks Pointer是否指向新地址，若是则直接跟随。

**缺点**：额外指针开销，且并发移动时需要更复杂的同步。

## 对比参照

### GC算法对比

| 收集器 | 引入 | 算法 | 停顿 | 适用场景 |
|--------|------|------|------|----------|
| Serial | 1.3 | 复制 | 长 | 小型应用 |
| Parallel | 1.5 | 复制 | 中等 | 吞吐量优先 |
| CMS | 7 | 标记-清除 | 短（并发） | 低停顿（已移除） |
| G1 | 9 | 标记-整理+复制 | 可控 | 大型应用（默认） |
| ZGC | 11 | 标记-整理 | <1ms | 超大堆低延迟 |
| Shenandoah | 12 | 标记-整理 | 低 | 低延迟（OpenJDK） |

### G1 vs ZGC的核心设计差异

| 维度 | G1 | ZGC |
|------|----|----|
| 停顿控制 | 可预测（MaxGCPauseMillis） | <1ms（着色指针） |
| 堆规模 | 数十GB | 16TB |
| 内存布局 | 固定大小Region | 逻辑分区，颜色指针 |
| 整理方式 | 导出-复制（evacuation） | 并发标记+引用处理 |
| 对象移动 | STW时移动 | 并发移动（Brooks指针） |
| Shenandoah | 12 | 标记-整理 | 低 | 低延迟（OpenJDK） |

## 参考存根

```java
// JOL查看对象布局（≤30行）
import org.openjdk.jol.info.ClassLayout;
import org.openjdk.jol.vm.VM;

public class JolDemo {
    public static void main(String[] args) {
        System.out.println(VM.current().details());
        Object obj = new Object();
        System.out.println(ClassLayout.parseInstance(obj).toPrintable());
    }
}
// 输出示例：
// [OBJECT HEADER]  12 bytes (3 fields)
//   6 bytes: mark word
//   2 bytes: compressed class pointer
//   4 bytes: padding
```
