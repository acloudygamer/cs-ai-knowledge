# 安全编码实践

> 安全编码的本质是"对所有外部输入和输出保持不信任"——输入要验证和净化，输出要编码，权限要最小化，敏感数据要保护。

---

## SQL注入

### 定义

SQL注入的根本原因是**SQL语义边界被突破**——用户输入未经语义验证直接拼入SQL字面量，导致攻击者可以注入额外语义，使原SQL查询的本意被篡改。

### 数学模型

设合法输入空间为 $D_{\text{valid}}$，实际输入为 $i$，拼接后的SQL语义为 $\Sem(i)$：

$$
\text{安全} \iff \forall i \in D_{\text{valid}}: \Sem(i) = \text{预期查询}
$$

当直接拼接时：

$$
\Sem("admin' OR '1'='1") \neq \text{预期查询}
$$

攻击成功的原因是字符串拼接绕过了SQL的**词法边界**——输入中的单引号'闭合了字面量字符串，后续内容成为SQL语法的一部分。

### 防御：参数化查询

参数化查询（PreparedStatement）将SQL结构与数据语义分离：

$$
\text{SELECT} \; * \; \text{FROM} \; \text{users} \; \text{WHERE} \; \text{name} = \textbf{?}
$$

其中`?`是占位符，数据绑定到占位符时**不进入SQL词法分析器**，仅作为字面数据处理——单引号被转义或绑定为参数值，永不改变SQL结构。

```java
String query = "SELECT * FROM users WHERE name = ?";
PreparedStatement ps = connection.prepareStatement(query);
ps.setString(1, username);  // username 作为数据绑定，永不改变 SQL 结构
ResultSet rs = ps.executeQuery();
```

### 动态表名列名

表名列名**无法参数化**（它们是SQL语法的标识符，而非字面量），必须使用白名单验证：

$$
\text{allowed\_fields} = \{"id", "name", "email", "createTime"\}
$$

$$
\text{input} \in \text{allowed\_fields} \iff \text{允许使用}
$$

```java
private static final Set<String> ALLOWED_SORT_FIELDS =
    Set.of("id", "name", "email", "createTime");
public List<User> search(String sortField, String direction) {
    if (!ALLOWED_SORT_FIELDS.contains(sortField)) {
        throw new IllegalArgumentException("Invalid sort field");
    }
}
```

## XSS（跨站脚本攻击）

### 定义

XSS的本质是**HTML上下文语义混淆**——当用户输入未经转义直接插入HTML时，浏览器将输入内容解析为HTML标签或脚本代码执行。

### 攻击模型

用户输入作为不同上下文插入HTML时，有不同转义要求：

| 上下文 | 危险字符 | 转义方式 |
|--------|----------|----------|
| 元素内容（`<div>userInput</div>`） | `<`, `>`, `&` | `&lt;`, `&gt;`, `&amp;` |
| 属性值（`<div class="userInput">`） | `"`, `<` | `&quot;`, `&lt;` |
| URL参数（`<a href="?q=userInput">`） | `"`, `&`, `#` | URL编码 |
| JavaScript（`<script>var x='userInput'</script>`） | `'`, `\`, `<` | JS转义 |

**关键约束**：转义规则因上下文而异，错误的上下文选择会导致绕过。例如，在URL参数上下文中使用HTML转义是无效的。

### 防御：输出编码

```java
import org.owasp.encoder.Encode;
String safeOutput = Encode.forHtml(userInput);  // 上下文感知转义
response.getWriter().write("<div>" + safeOutput + "</div>");
```

OWASP Java Encoder对每个上下文使用对应转义规则，防止上下文混淆。

### 框架级防护

现代框架（Thymeleaf、Angular、Vue）默认启用上下文感知转义，开发者应避免使用`v-html`（Vue）等绕过自动转义的机制。

## CSRF（跨站请求伪造）

### 定义

CSRF利用浏览器自动发送同源Cookie的机制——攻击者构造恶意页面，诱导用户向目标站点发起请求，浏览器自动携带有效Cookie，服务器无法区分合法请求与伪造请求。

### 攻击条件

$$
\text{CSRF成立条件} = \text{用户在目标站点登录} \land \text{存在仅验证Cookie的接口} \land \text{请求参数可预测}
$$

### 数据流

<pre>
受害者访问恶意网页（攻击者控制的域）
    │
    ├── 自动提交表单 POST https://bank.com/transfer
    │   浏览器自动携带 bank.com 的会话 Cookie
    │
    目标服务器验证 Cookie 有效 → 执行转账
    （服务器认为这是受害者的合法操作）
</pre>

### 防御：CSRF Token

服务器生成随机令牌 $t$，绑定到用户会话 $S$：

$$
t \in_R \text{Random bits}, \quad (S, t) \in \text{session store}
$$

请求必须携带匹配的 $t$：

```java
@Configuration
@EnableWebSecurity
public class SecurityConfig {
    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http.csrf(csrf -> csrf
            .csrfTokenRepository(CookieCsrfTokenRepository.withHttpOnlyFalse())
            .ignoringRequestMatchers("/api/public/**")
        );
        return http.build();
    }
}
```

### SameSite Cookie

`SameSite=Strict`使浏览器在跨站请求时不发送Cookie，从根本上堵住CSRF攻击向量：

$$
\text{Cookie}::\text{SameSite=Strict} \implies \text{跨域请求不携带该Cookie}
$$

## 敏感数据处理

### 密码存储：BCrypt

密码哈希的核心约束：**哈希函数必须慢且不可逆**。BCrypt的工作因子（cost factor）控制计算时间：

$$
t = O(2^{\text{costFactor}}) \quad \text{每次哈希耗时随 costFactor 指数增长}
$$

典型配置：`BCryptPasswordEncoder` 默认 `strength = 10`（2^10 = 1024轮循环）。

```java
@Bean
public PasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder();  // strength=10
}
```

**关键约束**：MD5/SHA-1属于快速哈希，不适用于密码存储——攻击者可用GPU每秒计算数十亿次，无法抵抗暴力破解。

### AES-GCM加密

AES-GCM同时提供**机密性**（AES对称加密）和**完整性**（GCM模式内的GMAC认证标签），防篡改：

$$
\text{Enc}(k, m) = (c, t) \quad \text{其中 } t = \text{GMAC}(k, \text{associated\_data}, c)
$$

解密时验证 $t$，篡改密文导致 $t$ 验证失败，抛出 `AEADBadTagException`。

```java
private static final String ALGORITHM = "AES/GCM/NoPadding";
private static final int GCM_TAG_LENGTH = 128;   // bits
private static final int GCM_IV_LENGTH = 12;    // bytes (推荐值)

public String encrypt(String plaintext) {
    byte[] iv = new byte[GCM_IV_LENGTH];
    new SecureRandom().nextBytes(iv);
    Cipher cipher = Cipher.getInstance(ALGORITHM);
    cipher.init(Cipher.ENCRYPT_MODE, new SecretKeySpec(secretKey, "AES"),
        new GCMParameterSpec(GCM_TAG_LENGTH, iv));
    byte[] ciphertext = cipher.doFinal(plaintext.getBytes(StandardCharsets.UTF_8));
    byte[] encrypted = ByteBuffer.allocate(iv.length + ciphertext.length)
        .put(iv).put(ciphertext).array();
    return Base64.getEncoder().encodeToString(encrypted);
}
```

**关键约束**：IV必须每次加密随机生成，不可重用——重用IV会导致认证标签失效。

### 日志脱敏

敏感字段（邮箱、手机、身份证、银行卡）在日志中必须脱敏：

$$
\text{mask}(s) = \begin{cases}
s[0:2] + "***" + s[\text{at}] & \text{邮箱} \\
s[0:3] + "****" + s[-4:] & \text{手机/银行卡}
\end{cases}
$$

## 输入验证

### 定义

输入验证是对**数据语义边界**的检查——验证数据是否在预期范围、格式、类型内，拒绝任何不符合约束的输入。

### Bean Validation约束组合

```java
@Entity
public class User {
    @NotBlank @Size(min = 3, max = 20)
    @Pattern(regexp = "^[a-zA-Z][a-zA-Z0-9_]*$")
    private String username;          // 字母开头，字母数字下划线

    @NotBlank @Email
    private String email;            // 格式验证

    @Min(0) @Max(150)
    private int age;                 // 范围验证
}
```

多个约束是**AND关系**——必须全部满足。

### 自定义验证器

```java
@Target({ElementType.FIELD, ElementType.PARAMETER})
@Retention(RetentionPolicy.RUNTIME)
@Constraint(validatedBy = StrongPasswordValidator.class)
public @interface StrongPassword { }

public class StrongPasswordValidator implements ConstraintValidator<StrongPassword, String> {
    @Override
    public boolean isValid(String value, ConstraintValidatorContext context) {
        if (value == null) return true;  // null 由 @NotBlank 处理
        boolean hasUpper = false, hasLower = false, hasDigit = false;
        for (char c : value.toCharArray()) {
            if (Character.isUpperCase(c)) hasUpper = true;
            else if (Character.isLowerCase(c)) hasLower = true;
            else if (Character.isDigit(c)) hasDigit = true;
            if (hasUpper && hasLower && hasDigit) break;
        }
        return hasUpper && hasLower && hasDigit && value.length() >= 8;
    }
}
```

## XXE（XML外部实体）

### 定义

XXE是XML解析器在处理外部实体时的**边界突破**——攻击者通过构造包含外部实体（EXTERNAL ENTITY）的XML，使解析器读取本地文件或向内部网络发起请求。

### 攻击向量

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE foo [
    <!ENTITY xxe SYSTEM "file:///etc/passwd">
]>
<foo>&xxe;</foo>
```

解析器展开`&xxe;`为文件内容，攻击者获取敏感数据。

### 防御：禁用外部实体

```java
DocumentBuilderFactory dbf = DocumentBuilderFactory.newInstance();
dbf.setFeature(XMLConstants.FEATURE_SECURE_PROCESSING, true);
dbf.setFeature("http://apache.org/xml/features/disallow-doctype-decl", true);
dbf.setFeature("http://xml.org/sax/features/external-general-entities", false);
dbf.setFeature("http://xml.org/sax/features/external-parameter-entities", false);
dbf.setNamespaceAware(true);
```

**防御的数学模型**：禁用了DTD（Document Type Definition）后，外部实体无法被声明和引用，XML解析器的攻击面大幅缩小。

## 依赖安全

### 依赖审计

已知漏洞库（CVEs）可通过OWASP Dependency-Check自动扫描：

```bash
mvn org.owasp:dependency-check-maven:check
gradle dependencyCheckAnalyze
```

### 最小权限原则

引入依赖时，遵循最小版本原则（Minimal Version Selection，MVS）：仅引入实际使用的依赖，指定明确版本防止供应链攻击：

```xml
<dependency>
    <groupId>com.fasterxml.jackson.core</groupId>
    <artifactId>jackson-databind</artifactId>
    <version>2.16.1</version>  <!-- 明确版本，防止依赖传递升级 -->
</dependency>
```

## 异常处理原则

对外返回**通用错误消息**，详细信息仅记录日志：

```java
catch (SQLException e) {
    log.error("Database error", e);  // 完整信息进日志
    throw new RuntimeException("操作失败，请稍后重试");  // 用户看到通用消息
}
```

**约束**：错误信息中的堆栈细节可能暴露系统内部结构（如类名、方法名、SQL表名），攻击者可利用这些信息进行针对性攻击。
