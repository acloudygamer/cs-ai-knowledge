# 注解、反射与动态代理

## 定义

**注解（Annotation）** 是Java语言层面的一类特殊接口，其本质是在程序代码中嵌入**带外（out-of-band）元数据**——注解本身不参与程序运行，但可被编译器、工具链或运行时读取，从而改变编译行为或运行时决策。

**反射（Reflection）** 是程序在运行时通过JVM的Class对象检查和操作自身结构的能力，其本质是**延迟绑定的自省机制**：所有类型信息在编译时确定，但访问权在运行时授予。

**动态代理（Dynamic Proxy）** 是在运行时通过字节码生成技术创建代理对象的设计模式，其本质是**调用拦截与转发链的运行时编织**。

三者共同构成Java的元编程体系：注解提供元数据来源，反射提供自省能力，动态代理提供行为编织——共同替代了其他语言中的装饰器、宏、模板等编译期机制。

## 数学模型

### 注解的生命周期状态机

注解的保留策略构成一个确定性有限状态机（Deterministic Finite Automaton, DFA）：

$$
\text{RetentionPolicy} \in \{\text{SOURCE},\ \text{CLASS},\ \text{RUNTIME}\}
$$

$$
\text{可见性}(P) = \begin{cases}
\text{仅工具链} & P = \text{SOURCE} \\
\text{字节码工具} & P = \text{CLASS} \\
\text{运行时反射} & P = \text{RUNTIME}
\end{cases}
$$

**约束**：RUNTIME级注解需要类加载器加载类后才能通过反射读取，SOURCE级注解在编译后即被丢弃。

**违反约束的后果**：若在 `RetentionPolicy.SOURCE` 注解上调用反射API（如 `getAnnotation()`），返回null——因为注解在编译后已被丢弃，不存在于Class文件的常量池中。

### 反射的访问代价

反射调用的性能损耗来自三个层面的线性叠加：

| 损耗来源 | 量级 | 收敛性 |
|---------|------|--------|
| 方法签名字符串查找 | $O(1)$ 但常数大 | 首次调用后被JIT内联缓存 | 但常数大 | 首次调用后被JIT内联缓存 |
| 安全检查（Module/SecurityManager） | $O(1)$ 每次调用 | 不可优化（安全边界必须每次检查） | 每次调用 | 不可优化（安全边界必须每次检查） |
| 自动装箱/拆箱 | 取决于类型 | JIT可部分优化 |

$$

### 动态代理的字节码生成

$$
\text{代理类字节码} = \text{GenerateClass}(\text{接口集}, \text{InvocationHandler})
$$

生成的类满足：
- 实现所有指定接口的笛卡尔积： $\text{Proxy} \subseteq \prod_{i} \text{Interface}_i$ 
- 所有方法体调用 `InvocationHandler.invoke(this, method, args)`
- 类名格式：` $Proxy$ N`（N为自增序号，确保同一接口集生成的类名唯一）N`（N为自增序号，确保同一接口集生成的类名唯一）

**归约终点**：动态代理的调用链可归约为**函数式组合**——`InvocationHandler.invoke()` 接收原始方法签名和参数，返回转换后的结果。代理对象本身不存储业务逻辑，仅做路由。

## 数据流

### 注解→反射→动态代理的完整数据流

<pre>
源代码 (.java)
    │
    ├─ 编译期 ──> 注解处理器 (APT) ──> 生成新源文件
    │                    ↑
    │              读取元注解
    │              (@Retention)
    │
    └─ 字节码 (.class)
             │
             ├─ 类加载器加载 ──> Class对象
             │                          │
             │   getAnnotation() ───────┘
             │          │
             │          ▼
             │   反射读取 (RUNTIME级)
             │          │
             └──────────┴──> 动态代理生成
                                │
                                ▼
                         $Proxy$ N 字节码N 字节码
                                │
                                ▼
                         Class对象加载
                                │
                                ▼
                         代理对象实例
                                │
                     ┌──────────┴──────────┐
                     │  proxy.doSomething() │
                     │         ↓            │
                     │  InvocationHandler   │
                     │       .invoke()      │
                     │         ↓            │
                     │   目标对象转发       │
                     └─────────────────────┘
</pre>

**数据所有权变换**：
1. 注解元数据：编译时从源码进入 `.class` 常量池，生命周期由 `@Retention` 决定，所有权归Class文件
2. Class对象：类加载器的产物，只读共享，生命周期与类加载器绑定
3. 代理实例：由 `Proxy.newProxyInstance()` 在堆上分配，所有权归调用方

### 反射调用数据流

<pre>
调用方                   Class对象                目标对象
  │                         │                        │
  │ getDeclaredMethod() ──> │                        │
  │<────────────────────────┘                        │
  │                         │                        │
  │ setAccessible(true) ───────────────────────────> │
  │                         │                        │
  │ method.invoke(obj, args) ─────────────────────> │
  │                         │         ┌──────────────┘
  │                         │         │
  │<─────────────────────────────────┘
  │
  返回值 (或异常)
</pre>

**所有权转移**：反射调用本身不改变对象所有权，但 `Method.invoke()` 会触发类初始化（如果尚未初始化且该类有 `<clinit>`）。

## 机制

### 注解为何需要@Retention？

@Retention解决的是**谁需要这些元数据**的问题——这是一个**消费者问题**，而非注解自身的属性问题：

| 保留级别 | 消费者 | 典型场景 | 生命周期边界 |
|----------|--------|----------|--------------|
| SOURCE | 编译器/IDE | 语法检查、Lombok APT | 编译结束后消失 |
| CLASS | 字节码工具 | ASM插桩、cglib、Mockito | 类加载时从字节码读取，内存中无 |
| RUNTIME | 反射API | Spring DI、JPA映射 | 随Class对象存活 |

**违反约束**：若设计者将本应为 RUNTIME 的注解误设为 SOURCE，然后尝试在运行时通过反射读取——得到 null，而非空列表或抛异常。这导致运行时框架（如Spring）失效，但编译期工具链正常。

### 反射的性能为何这么高？

反射的性能损耗不是来自"解释执行"（JVM早已JIT编译反射调用），而是来自三个**不可消除的边界检查**：

1. **Method签名查找**：首次调用时需在类的方法表中线性搜索或哈希查找。JIT通过"方法内联缓存"将查找结果绑定到调用点，后续调用 $O(1)$ 。 。
2. **安全检查**：每次调用检查模块系统（`Module.canReflect()`）和安全管理器。这是**安全边界**，不可优化——恶意代码可能通过反射调用本应限制的方法。
3. **类型转换**：Object[] 参数需要每次进行运行时类型检查（`checkcast`指令），确保类型安全。

**关键约束**：反射调用可能阻止JIT的内联优化——因为反射调用的目标在运行时才能确定，无法进行静态分析。这是反射性能损失的根源。

### 动态代理的调用链编织原理

动态代理的本质不是继承，而是**接口实现+方法转发**的字节码编织：

```
调用方: proxy.doSomething()
            │
            ▼
Generated Proxy类:
    public doSomething() {
        h.invoke(this, method, args);
        // h = InvocationHandler（由JVM在构造时注入）
    }
            │
            ▼
InvocationHandler.invoke():
    - method.getName() == "doSomething"  // 方法名路由
    - 前置通知 (before)
    - 目标方法调用 (target.doSomething())  // 业务逻辑转发
    - 后置通知 (afterReturning) 或 异常通知 (afterThrowing)
```

**约束**：JDK动态代理只能代理接口（不能代理类），因为 ` $Proxy$ N` 继承自 `java.lang.reflect.Proxy` 并实现指定接口。这是**继承结构约束**，不可绕过——Proxy 只有一个父类，无法再继承目标类。N` 继承自 `java.lang.reflect.Proxy` 并实现指定接口。这是**继承结构约束**，不可绕过——Proxy 只有一个父类，无法再继承目标类。

CGLIB/ByteBuddy通过**继承目标类并重写方法**突破此限制，但其生成的字节码更复杂，且无法代理 final 方法。

### APT（注解处理器）的编译期执行

APT在Java 6引入，在**解析和填充语义**之后、**字节码生成**之前运行：

$$
\text{编译期阶段} = \underbrace{\text{parse} \rightarrow \text{enter}}_{\text{词法/语法分析}} \rightarrow \textbf{APT} \rightarrow \underbrace{\text{process} \rightarrow \text{generate} \rightarrow \text{compile}}_{\text{语义分析和字节码生成}}
$$

APT的**约束边界**：
- 只能读取已有注解（通过 `RoundEnvironment.getAnnotationsAnnotated()`）
- 只能生成新 `.java` 文件（通过 `Filer.createSourceFile()`）——不能直接修改已有源文件
- 新生成的文件参与同一编译单元的后续处理，形成**多轮迭代**

Lombok利用APT生成getter/setter，但**代价**是IDE需要插件同步感知（因为javac生成的字节码与源码不同步），且调试时看到的是生成后的字节码而非源码——这违反了**透明性原则**。

## 对比参照

| 维度 | JDK动态代理 | CGLIB/ByteBuddy |
|------|-------------|-----------------|
| 原理 | 继承 `Proxy`，实现接口 | 继承目标类，重写方法 |
| 限制 | 仅接口 | 可代理类（但无法代理final方法/final类） |
| 字节码量 | 少（仅方法转发） | 多（完整方法体生成） |
| 性能 | 略优（直接转发） | 略低（方法入口更长） |
| 依赖 | 仅JDK | 需第三方库 |
| 反射依赖 | 低（接口方法少） | 高（继承链复杂） |

## 参考存根

```java
// 最小化JDK动态代理示例（≤30行）
public class ProxyDemo {
    interface Service { void doSomething(); }

    static class LoggingHandler implements InvocationHandler {
        private final Object target;
        LoggingHandler(Object t) { this.target = t; }
        public Object invoke(Object p, Method m, Object[] a) throws Throwable {
            System.out.println("Before: " + m.getName());
            return m.invoke(target, a);
        }
    }

    public static void main(String[] args) {
        Service impl = () -> System.out.println("real");
        Service proxy = (Service) Proxy.newProxyInstance(
            Service.class.getClassLoader(),
            new Class<?>[]{Service.class},
            new LoggingHandler(impl)
        );
        proxy.doSomething();
    }
}
```
