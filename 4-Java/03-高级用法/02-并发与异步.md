# 并发与异步

## 定义

Java并发体系围绕**资源稀缺性**这一核心矛盾展开：CPU核数有限但任务无限，线程是抢占资源的最小单位，锁/原子操作/CAS是解决资源争用的手段，而异步是让阻塞任务释放线程以承接更多工作的策略。

**线程（Thread）** 是CPU调度的最小单位，其本质是一个函数调用栈与CPU寄存器状态的组合。创建成本约1MB栈空间，切换成本约数千CPU周期。

**线程池（ExecutorService）** 是将"创建线程的高昂成本"摊销到"多次任务复用同一线程"的管理模式。

**CompletableFuture** 是Java 8引入的异步编程模型，其本质是将"命令式代码"转换为"声明式数据流"——每个操作返回新的CompletableFuture，形成链式调用。

## 数学模型

### 线程池的稳态分析

设核心线程数为 $c$ ，最大线程数为 $m$ ，队列容量为 $q$ ，任务到达率为 $\lambda$ ，服务率为 $\mu$ （每个线程）。

**稳态条件**（系统不崩溃的必要条件）：
$$
\lambda < c \cdot \mu + (m - c) \cdot \mu
$$

当任务堆积时，线程池经历三个阶段的**状态转移**：

$$
n \begin{cases}
n \le c & \Rightarrow & \text{核心线程处理} \\
c < n \le c + q & \Rightarrow & \text{队列等待} \\
n > c + q & \Rightarrow & \text{扩容至}m\text{或拒绝}
\end{cases}
$$

**违反稳态条件的后果**：若 $\lambda \ge c \cdot \mu + (m - c) \cdot \mu$ ，任务涌入速度持续超过处理速度，队列无限增长，最终触发拒绝策略（RejectedExecutionException）。

### 线程状态机

线程在其生命周期内经历以下状态转移（确定性有限状态机）：

<pre>
NEW ──[start()]──> RUNNABLE ──[synchronized获取锁失败]──> BLOCKED
  │                    ↑                                      │
  │                    └──[synchronized释放]────────────────────┘
  │                    (wait/notify) ──> WAITING
  │                    (sleep/yield) ──> TIMED_WAITING
  └─[run()结束]──> TERMINATED
</pre>

**关键不变量**：BLOCKED 状态仅由 `synchronized` 的锁获取失败触发，不涉及其他同步机制（ReentrantLock等使用AQS的会进入WAITING）。

### CAS的硬件保证

CAS（Compare-And-Swap）操作在硬件层面由**总线锁**或**缓存锁**实现——这是一个**原子性原语**，不可分解：

$$
\text{CAS}(\text{addr}, \text{expected}, \text{new}) = \begin{cases}
\text{true} & \text{if } M[\text{addr}] == \text{expected} \Rightarrow M[\text{addr}] := \text{new} \\
\text{false} & \text{otherwise}
\end{cases}
$$

Java的 `AtomicInteger` 等原子类封装此操作，失败时重试（自旋）或退化为阻塞。**关键约束**：CAS保证原子性，但不保证顺序——需要 `volatile` 或内存屏障来保证可见性。

### CompletableFuture的数据流模型

$$
\text{CompletableFuture}_A \xrightarrow{\text{thenApply/f}} \text{CompletableFuture}_B
$$

声明式链式调用的执行模型：
- `supplyAsync` 将任务提交到 ForkJoinPool 或自定义 Executor
- 每个 `thenX` 返回新的 CompletableFuture，不阻塞当前线程
- 异常通过 `exceptionally` / `handle` 传播，可被 `allOf` / `anyOf` 组合

**数学约束**：`CompletableFuture` 的完成状态一旦到达（正常完成或异常完成），状态不可变。这保证了链式调用的确定性。

## 数据流

### 线程池任务提交流程

<pre>
submit(task)
    │
    ├─ [n < corePoolSize] ──> 创建核心线程 ──> 执行任务
    │
    ├─ [n >= corePoolSize] ── [队列不满] ──> 入队等待
    │
    └─ [队列满] ── [n < maxPoolSize] ──> 创建临时线程 ──> 执行任务
              │
              └─ [n >= maxPoolSize] ──> 执行拒绝策略
</pre>

### 虚拟线程（Virtual Threads）数据流

虚拟线程是Java 21引入的轻量级执行单元，其调度由JVM内置的Scheduler完成（默认使用 ForkJoinPool）：

<pre>
虚拟线程 VT_1                    虚拟线程 VT_2
    │                                │
    └───────── Carrier Thread ───────┘
              (平台线程池)
                   │
                   ▼
             OS线程 (内核调度)
</pre>

**所有权转移**：虚拟线程不持有 OS 线程，当它执行阻塞 I/O 时，JVM 挂起 VT 并调度另一个 VT 到同一个 Carrier Thread，实现**用户态协作式调度**。

### ThreadLocal 数据流

<pre>
Thread_1 ──> ThreadLocalMap
    │              │
    │         ┌────┴────┐
    │    [key=TL, val=x]  [key=TL2, val=y]
    │              │
    └──────────────┘ 独立副本，互不干扰

Thread_2 ──> ThreadLocalMap
    │              │
    │         [key=TL, val=z]  (独立副本)
</pre>

**约束**：虚拟线程场景下，每个 VT 都有独立 ThreadLocal 副本。百万 VT 即百万副本，可能造成内存爆炸。Java 22 引入 ScopedValue 作为替代——数据绑定到词法作用域而非线程。

## 机制

### 为何需要线程池？

直接创建线程的问题：
- **创建成本高**：约1MB栈空间 + OS调度开销
- **资源失控**：无限制创建导致 OOM
- **缺乏管理**：无法统一取消、监控、优先级控制

线程池通过**复用**解决以上问题：将任务队列化，复用已有线程执行新任务。**本质是空间换时间**：预先分配线程池占用的内存，换取任务到达时无需等待线程创建的低延迟。

### synchronized 的锁升级路径

JVM对synchronized采用**锁膨胀（Lock Escalation）**策略——这是一个**单向状态机**（除了偏向锁可撤销）：

| 阶段 | 条件 | 代价 | 特性 |
|------|------|------|------|
| 无锁 | 对象刚创建 | 0 | 匿名对象头 |
| 偏向锁 | 只有一个线程访问 | 0 | 对象头记录线程ID |
| 轻量级锁 | 多线程但无竞争 | 自旋 CAS | 栈帧中存储锁记录 |
| 重量级锁 | 竞争激烈或自旋失败 | 系统调用 | OS mutex |

**约束**：锁升级是**单向的、不可逆的**——一旦升级到重量级锁，不会降级（但可重入）。

**违反约束的后果**：在高竞争场景下，自旋失败后升级为重量级锁，若原线程很快释放锁，会导致不必要的性能损耗。这是 synchronized 的设计权衡。

### AQS（AbstractQueuedSynchronizer）框架

AQS是Java并发工具的通用骨架，其核心是**状态变量+等待队列**的组合：

- **状态变量** `state`：整数，表示资源的可用量（ReentrantLock 表示重入计数，Semaphore 表示许可数）
- **等待队列**：CLH队列变体，存储阻塞的线程（FIFO顺序）
- **两种模式**：独占（ReentrantLock）和共享（Semaphore/CountDownLatch）

```java
// AQS核心逻辑（伪代码）
tryAcquire() {
    if (cas(state, 0, 1)) {  // CAS保证原子性
        Thread.currentThread()设为持有者;
        return true;
    }
    return false;
}
```

### 虚拟线程 vs 平台线程

| 维度 | 平台线程 | 虚拟线程 |
|------|----------|----------|
| 栈大小 | 固定 ~1MB | 动态增长，通常 ~1KB |
| 调度 | OS 内核抢占 | JVM 用户态协作 |
| 阻塞代价 | 高（占用OS线程） | 低（挂起VT，复用Carrier） |
| 适用场景 | CPU密集型 | I/O密集型（特别是高并发） |

**关键约束**：虚拟线程内执行 `synchronized` 阻塞会**阻塞 Carrier Thread**——因为 synchronized 的底层是 OS mutex，虚拟线程无法在用户态挂起它。应使用 `ReentrantLock`（可中断、可超时）。

**归约终点**：虚拟线程的调度可归约为**协作式多任务**——任务主动让出控制权，而非被时钟中断抢占。这与协程的模型一致。

### synchronized vs ReentrantLock（虚拟线程场景）

| 维度 | synchronized | ReentrantLock |
|------|-------------|---------------|
| 阻塞行为 | 阻塞 Carrier Thread | 仅挂起虚拟线程 |
| 可中断 | 否 | 是（lockInterruptibly） |
| 超时 | 否 | 是（tryLock） |
| 公平性 | 非公平 | 可配置公平/非公平 |
| 重入性 | 是 | 是 |

**设计选择**：若应用大量使用虚拟线程，应优先选择 ReentrantLock 替代 synchronized，以避免阻塞 Carrier Thread。

## 参考存根

```java
// 虚拟线程 + CompletableFuture 组合（≤30行）
ExecutorService executor = Executors.newFixedThreadPool(4);

CompletableFuture<String> future = CompletableFuture
    .supplyAsync(() -> {
        try { Thread.sleep(100); } catch (InterruptedException e) {}
        return "Hello";
    }, executor)
    .thenApply(s -> s + " World")
    .thenApply(String::toUpperCase);

System.out.println(future.join()); // HELLO WORLD
executor.shutdown();
```
