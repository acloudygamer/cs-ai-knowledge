# 虚拟线程与结构化并发

> 前置：[04-CompletableFuture异步](./04-CompletableFuture异步.md) · 后续：[01-文件与NIO](../05-IO与外部世界/01-文件与NIO.md)

> **版本基准**：Java 21 stable / Java 25 latest（均为 LTS）。虚拟线程 Java 21 转正（JEP 444）；synchronized 不 pin 载体线程为 Java 24 变更（JEP 491）；Scoped Values Java 25 转正（JEP 506）；StructuredTaskScope 至 Java 25 仍为预览（JEP 505，第五次预览），示例需 `--enable-preview`。实测环境：Temurin JDK 25.0.4.1（Windows，12 核）。

异步编排（CompletableFuture、响应式）很大程度上是为了绕开一个物理事实：平台线程太贵，阻塞不起。虚拟线程直接改写了这个事实——线程变便宜之后，"一个任务一个线程、同步写法"重新成为可选项，这是它在连接链上的位置。

## 本质

**虚拟线程（virtual thread）** 是由 JVM 而非 OS 调度的 `Thread` 实例。物理构成：它的栈不是预留的 MB 级内存段，而是堆上可伸缩的对象（起步约几百字节，随调用深度伸缩）。调度模型：

- JVM 内置调度器把虚拟线程 **mount（挂载）** 到平台线程上执行，被挂载的平台线程称为**载体线程（carrier）**；载体来自一个 ForkJoinPool，默认并行度 = CPU 核数。
- 虚拟线程执行到 JDK 已适配的阻塞点（socket I/O、`Thread.sleep`、`BlockingQueue.take`、JUC 锁等）时，栈被复制回堆里，虚拟线程 **unmount（卸载）**，载体立刻去跑别的虚拟线程；阻塞解除后重新入队、挂回某个载体（不一定是原来那个）续跑。

所以阻塞的成本从"占住一个 OS 线程"降为"占住一个堆对象"。线程数的上限从数千跳到百万量级。

实测（Temurin 25.0.4.1，50 000 个任务各 sleep 200ms）：

```text
50000 个任务(sleep 200ms) @ 512 平台线程池: 20111 ms   ← 吞吐被线程数卡住
50000 个任务(sleep 200ms) @ 虚拟线程: 478 ms           ← 50000 个并发"阻塞"，载体只有 12 个
CPU 核数(载体线程并行度) = 12
```

## 机制

### 创建方式与使用纪律

```java
Thread vt = Thread.ofVirtual().start(task);            // 单个
try (var pool = Executors.newVirtualThreadPerTaskExecutor()) {
    pool.submit(task);                                  // 每个任务一个新虚拟线程
}                                                       // close() 会等所有任务结束
```

两条纪律，都由机制直接推出：

1. **不要池化虚拟线程**。池化的理由是摊销创建成本，而虚拟线程的创建本就廉价；池化只会把上限重新加回来。写法是"每个任务一个新的"。
2. **它不为 CPU 密集型任务提速**。载体并行度仍等于核数，计算任务在虚拟线程上不会更快——它解决的是 I/O 等待期的吞吐，不是延迟。

### Pinning：synchronized 的历史问题与现状

unmount 的前提是 JVM 能安全地把栈搬离载体。Java 21~23 里有一个例外：**进入 `synchronized` 后无法 unmount**——因为监视器的持有者记录在载体平台线程上而非虚拟线程上，一旦卸载，挂载到同一载体的下一个虚拟线程会被误判为锁的持有者，互斥就丢了。这种"虚拟线程把载体一起钉住"的现象叫 **pinning**：synchronized 块内再发生阻塞（如等待监视器、块内 I/O），载体线程被连带阻塞，高并发下载体池会被钉光，虚拟线程失去意义。当时的对策是把关键路径的 synchronized 换成 `ReentrantLock`（JUC 锁是适配过的 unmount 点）。

**Java 24（JEP 491）重写了监视器实现**：监视器归属改为记录虚拟线程本身，mount/unmount 负责账本切换，synchronized 内阻塞、等锁、`Object.wait()` 全部可以正常 unmount。该变更还移除了 JDK 21 引入的诊断开关 `jdk.tracePinnedThreads`；JFR 的 `jdk.VirtualThreadPinned` 事件保留，用于剩余场景。Java 24 之后剩下的 pinning 来源：经 JNI / Foreign Function API 进入的 native 帧，以及类加载/类初始化中的短暂阻塞——这两处栈上有 JVM 无法搬移的本地帧。

实测（Temurin 25.0.4.1；96 个虚拟线程，各自持**独立**监视器，synchronized 内 sleep 300ms。若 pin，并发度塌缩到 12，总耗时约 2.4s）：

```text
96 个虚拟线程(独立锁 + synchronized 内 sleep 300ms)，载体并行度=12
总耗时 317 ms → 未发生 pin（全部并发睡眠）
```

即：Java 24 起 synchronized 与 ReentrantLock 的选择回到纯语义层面（可中断、可超时、公平性，见 [02-JUC并发工具](./02-JUC并发工具.md)），不再被 pinning 左右。Java 21~23 上的存量代码才需要排查 synchronized 内的长阻塞。

### ThreadLocal 的新账单与 Scoped Values

`ThreadLocal` 的语义是"每个线程一份副本"。平台线程时代这份账单可以忽略；虚拟线程时代百万线程 × 每线程一份副本，内存与传递成本都变得真实。更本质的问题是 ThreadLocal 可随意 set/remove，生命周期不受控。

**Scoped Values**（Java 25 转正，JEP 506；此前历经 JEP 446/464/481/487 四轮预览）是面向这个场景的新机制：值绑定到**词法作用域**，`run`/`call` 结束时自动解绑，作用域内只读（可嵌套重绑定）：

```java
ScopedValue.where(REQUEST_ID, "req-42").run(() -> { ... });
```

实测（Temurin 25.0.4.1，嵌套重绑定）：

```text
handler 读到 REQUEST_ID = req-42
handler 读到 REQUEST_ID = req-43-nested   ← 内层绑定遮蔽外层
handler 读到 REQUEST_ID = req-42          ← 内层结束，外层恢复
作用域外 isBound = false                  ← 出作用域自动解绑
```

### 结构化并发：StructuredTaskScope（预览）

CompletableFuture 不管生命周期：父任务失败时，已派生的子任务照跑不误，错误处理散落在各条链上。**结构化并发**的对策是把"一组子任务"收进一个词法作用域：作用域结束 = 所有子任务完成或被取消，错误沿作用域汇聚——并发代码的生命周期纪律向顺序代码看齐。

API 形态自 JDK 25（JEP 505）改为静态工厂 + Joiner 策略（此前为 `new ShutdownOnFailure()` 构造器，迁移时注意）：

```java
try (var scope = StructuredTaskScope.open()) {
    var user   = scope.fork(() -> fetchUser());
    var orders = scope.fork(() -> fetchOrders());
    scope.join();                       // 等全部子任务
    render(user.get(), orders.get());   // Subtask.get() 取结果
}
```

实测（Temurin 25.0.4.1，`javac --enable-preview --release 25` 编译运行）：

```text
两个子任务结果: 用户, 订单
join() 抛出: FailedException: java.lang.RuntimeException: 子任务失败   ← Joiner.awaitAllSuccessfulOrThrow() 时任一失败即传播
```

`fork()` 默认派生虚拟线程。Joiner 决定聚合策略：`awaitAllSuccessfulOrThrow()`（全成才返回，一败即抛）、`anySuccessfulResultOrThrow()`（任一先成）。再次强调版本口径：**Java 21~25 均为预览**（JEP 453/462/480/499/505），编译运行都要 `--enable-preview`，生产采用需自担 API 变动风险。

## 边界

虚拟线程不替代线程池的全部场景：CPU 密集型任务仍按核数配平台线程池；需要限流时用 `Semaphore` 而不是缩虚拟线程数（线程本身已不再稀缺，稀缺的是下游资源）。诊断侧：虚拟线程不进传统的线程转储摘要视图，JFR 的 `jdk.VirtualThreadPinned` 事件（自虚拟线程孵化期即存在，JDK 24 后只覆盖剩余 pin 场景）与 `jcmd Thread.dump_to_file`（JDK 21 起）是观察手段。
