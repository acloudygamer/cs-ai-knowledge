# 线程模型与同步

> 前置：[04-Java内存模型](../03-JVM与运行时/04-Java内存模型.md)（可见性与 happens-before 规则的定义处） · 后续：[02-JUC并发工具](./02-JUC并发工具.md)

> **版本基准**：Java 21 stable / Java 25 latest（均为 LTS）。示例实测环境：Temurin JDK 25.0.4.1（Windows），stable 口径示例以 `javac -encoding UTF-8 --release 21` 验证。

并发问题的来源是一笔资源账：CPU 核数有限，而任务无限。多个执行流同时读写同一份内存时，"读-改-写"三步之间可以被任意打断，结果取决于运气。本篇定义 Java 里最底层的两个执行流工具——线程与监视器锁，以及它们失效的方式（死锁）。在此之上的 CAS、AQS、线程池、虚拟线程见后续各篇。

## 本质

**线程（Thread）** 是操作系统调度的最小单位，物理构成 = 一个调用栈 + 一套 CPU 寄存器上下文（程序计数器、栈指针等）。Java 的**平台线程**（platform thread）在 HotSpot 中与 OS 线程一一对应：创建平台线程就是 `pthread_create` / `CreateThread`，调度、阻塞、切换全部由内核完成。代价锚点：Windows x64 上每个线程默认预留约 1 MB 栈地址空间（OS 默认值），上下文切换在内核态完成。这决定了平台线程的数量上限在数千量级——虚拟线程（[05-虚拟线程与结构化并发](./05-虚拟线程与结构化并发.md)）正是为突破这个上限而生。

**监视器（monitor）** 是 JVM 给每个对象附带的一把互斥锁。`synchronized` 是语言级入口：进入 synchronized 块 = 获取该对象的监视器（`monitorenter`），离开 = 释放（`monitorexit`）。它同时管两件事：

1. **互斥**：同一时刻只有一个线程持有监视器，临界区串行执行。
2. **可见性**：释放监视器前的写，对之后获取同一监视器的线程可见——这条规则的形式化（happens-before）见 [04-Java内存模型](../03-JVM与运行时/04-Java内存模型.md)，本篇只用结论。

## 机制

### 竞争：没有互斥时发生什么

`count++` 在字节码层是读、加、写三条指令，两个线程交错执行会丢更新。实测（Temurin 25.0.4.1，两线程各自增 100 万次）：

```text
无同步计数 = 1278521（期望 2000000）   ← 每次运行丢的数量都不同
synchronized 计数 = 2000000
```

synchronized 版本把三步收进临界区，串行化换正确性。这正是互斥的定义性后果，不是优化问题。

### 锁的实现：从无竞争到竞争的三级路径

synchronized 的性能来自 HotSpot 的分级实现（实现细节，锚点：HotSpot，JDK 21 口径）：

- **无竞争**：轻量级锁，一次 CAS 把锁记录地址写入对象头（mark word），无系统调用。
- **有竞争**：自旋失败后膨胀为重量级锁，等待者挂起在 OS 互斥量上，由内核唤醒。
- **历史包袱**：偏向锁（只记录"上次持有者"以省掉 CAS）在 JDK 15 被默认禁用（JEP 374）、JDK 18 移除——它收益递减且撤销成本高。这是被移除的设计，不是现行机制。

升级在竞争期内是单向的：膨胀到重量级后，只要竞争还在就不会退回轻量级路径。但重量级不是终身判决——空闲的重量级监视器会被 JVM 异步解除关联（monitor deflation，JDK 15 起由 ServiceThread 执行），下次加锁可重新走轻量级路径。这条路径解释了为什么 synchronized 在无竞争时接近免费、在高竞争时退化到内核调度。

### wait/notify：监视器上的条件等待

互斥解决"不能同时进"，但解决不了一个线程需要**等某个条件成立**的问题——比如消费者等队列非空。`Object.wait()/notify()` 是挂在监视器上的条件队列：

- `wait()`：原子地**释放监视器**并进入该对象的等待集，直到被 `notify()`/`notifyAll()` 唤醒；唤醒后重新竞争监视器，拿到后才从 `wait()` 返回。
- `notifyAll()`：唤醒等待集中的所有线程，让它们重新竞争——被唤醒不等于拿到锁。

两个使用纪律，都由机制直接推出：

1. **必须在 synchronized 内调用**：wait/notify 的操作对象是当前线程持有的监视器，否则抛 `IllegalMonitorStateException`。
2. **必须用 `while` 而非 `if` 检查条件**：notifyAll 唤醒的多个线程里只有一个能让条件保持成立，其余线程醒来时条件可能已被破坏；`while` 让被唤醒者重新验证。

实测（容量 3 的有界队列，一生产者一消费者）：

```text
生产 item-1，队列=1
生产 item-2，队列=2
生产 item-3，队列=3        ← 队列满，生产者 wait
    消费 item-1，队列=2    ← 消费者取走并 notifyAll
生产 item-4，队列=3
...
    消费 item-6，队列=0
```

JUC 的 `Lock` + `Condition`（见 [02-JUC并发工具](./02-JUC并发工具.md)）是同一机制的显式版本：一个锁可以挂多个条件队列，语义等价于"监视器 + 等待集"的一般化。

### 死锁：环形等待

两个线程各持一把锁、又要对方的锁，就互相等待到永远。死锁成立的四个必要条件（资源互斥、持有并等待、不可剥夺、循环等待）里，工程上最常拆的是最后一条：**全局一致的加锁顺序**（所有线程都按同一顺序获取多把锁）让环无法形成。

实测（两线程按相反顺序加锁，用 `ThreadMXBean.findDeadlockedThreads()` 检测）：

```text
检测到死锁: thread-A-then-B 持有锁，等待 java.lang.Object@2c7b84de（被 thread-B-then-A 持有）
检测到死锁: thread-B-then-A 持有锁，等待 java.lang.Object@7a81197d（被 thread-A-then-B 持有）
```

注意死在 synchronized 上的线程**无法被 interrupt 唤醒**——monitor 竞争不响应中断（`ReentrantLock.lockInterruptibly()` 才可中断，见 [02-JUC并发工具](./02-JUC并发工具.md)）。线上排查用 `jstack <pid>` 或 JFR，两者都报告同样的锁持有环。

### 线程生命周期与本篇的关系

`Thread.State` 枚举里，本篇的三个机制各占一格：进不去监视器是 **BLOCKED**；`wait()` 无限等待是 **WAITING**；`sleep(ms)` / `wait(ms)` 是 **TIMED_WAITING**。区分它们的工程意义：BLOCKED 指向锁竞争，WAITING 指向条件等待，排查死锁与活锁时看的列不同。
