# 线程池

> 前置：[02-JUC并发工具](./02-JUC并发工具.md)（BlockingQueue 是线程池的传送带） · 后续：[04-CompletableFuture异步](./04-CompletableFuture异步.md)

> **版本基准**：Java 21 stable / Java 25 latest（均为 LTS）。示例实测环境：Temurin JDK 25.0.4.1（Windows），示例以 `javac -encoding UTF-8 --release 21` 编译验证。

平台线程的创建与销毁走内核，栈空间以 MB 计（锚点见 [01-线程模型与同步](./01-线程模型与同步.md)）。任务粒度是毫秒级时，为每个任务建一个线程，调度开销会吞掉任务本身。线程池的回应是**复用**：预先建一组线程常驻，任务排队进门，干完活的线程回池等下一单——把创建成本摊销到多次执行上，同时给并发度一个硬上限。

## 本质

**ExecutorService** 是"提交任务、拿回 Future"的服务接口，上游是调用方的 `submit(Callable)`，下游是若干个常驻工作线程，中间隔着一座 `BlockingQueue`（[02-JUC并发工具](./02-JUC并发工具.md)）。继承链：`Executor`（只有 `execute(Runnable)`）→ `ExecutorService`（加生命周期与 Future）→ `ThreadPoolExecutor`（参数全暴露的实现）。另有一支 `ScheduledExecutorService` 管定时/周期任务，本篇不展开。

**ThreadPoolExecutor** 的全部行为由七个参数决定，其中四个决定线程数如何伸缩：`corePoolSize`（常驻线程数）、`maximumPoolSize`（峰值线程数）、`workQueue`（等待队列）、`handler`（拒绝策略）。

## 机制

### 任务进门后的真实顺序

直觉以为"先扩到 max，满了再排队"，实际相反——**队列优先于扩容**。execute() 的决策链：

```text
线程数 < core ──> 新建核心线程执行
否则队列未满 ──> 入队等待
否则线程数 < max ──> 新建临时线程执行
否则 ──> 拒绝策略
```

这个形状需要辩护：为什么先排队再扩容？因为队列是廉价缓冲（内存），临时线程是昂贵资源（内核对象）；设计意图是让 max 只在"突发洪峰、队列兜不住"时出手，平时压在 core 规模运行。

实测（Temurin 25.0.4.1；core=2，max=4，队列容量 2，任务均 sleep 300ms）：

```text
提交任务1：活跃=1 池大小=1 队列=0   ← 建核心线程
提交任务2：活跃=2 池大小=2 队列=0   ← 建核心线程
提交任务3：活跃=2 池大小=2 队列=1   ← core 满，入队
提交任务4：活跃=2 池大小=2 队列=2   ← 队列满
提交任务5：活跃=3 池大小=3 队列=2   ← 队列满才扩临时线程
提交任务6：活跃=4 池大小=4 队列=2
任务7 被拒绝: RejectedExecutionException  ← max 也满，拒绝
```

容量口径：同时接纳的上限 = max + 队列容量 = 4 + 2 = 6，第 7 个任务无处可去。

### 拒绝策略：洪峰时的四种选择

| 策略 | 行为 | 适用 |
|---|---|---|
| AbortPolicy（默认） | 抛 `RejectedExecutionException` | 让调用方知道过载，由上层降级 |
| CallerRunsPolicy | 提交任务的线程自己执行 | 天然背压：调用方被拖慢，提交速率自动降下来 |
| DiscardPolicy | 静默丢弃新任务 | 可丢失的遥测类任务 |
| DiscardOldestPolicy | 丢掉队列里最老的，塞入新的 | 只关心最新数据的刷新类任务 |

### Executors 工厂方法的两个坑

`Executors` 的便捷工厂在配置上是危险的默认值（JDK 源码可查）：

- `newFixedThreadPool(n)`：队列是**无界** LinkedBlockingQueue——max 参数失效，任务洪峰时队列无限增长，结局是 OOM 而非拒绝。
- `newCachedThreadPool()`：队列容量为 0（SynchronousQueue 直交），max = Integer.MAX_VALUE——洪峰时线程无限创建，同样失控。

工程做法：显式 `new ThreadPoolExecutor(...)`，队列有界、拒绝策略写明。需要弹性且任务以阻塞 I/O 为主时，Java 21 起更直接的答案是虚拟线程（[05-虚拟线程与结构化并发](./05-虚拟线程与结构化并发.md)），它本来就不该被池化。

### 生命周期

`shutdown()` 停止接收新任务、跑完存量后退出；`shutdownNow()` 试图中断正在执行的任务并返回队列残余；之后用 `awaitTermination(timeout)` 等待真正结束。不调用 shutdown 的池会让 JVM 无法退出（非守护线程常驻）。

### ForkJoinPool：分治任务的专用池

ThreadPoolExecutor 假设任务彼此独立；**ForkJoinPool**（JDK 7）面向可递归拆分的任务：`RecursiveTask.compute()` 里拆成左右两半，`fork()` 异步提交、`join()` 等结果。它的机制特色是**工作窃取**（work-stealing）：每个工作线程有自己的双端队列，空闲线程从别人队尾偷任务——拆分产生的子任务自动在核间均衡。

实测（Temurin 25.0.4.1，12 核，1000 万元素求和，阈值 10 万拆分）：

```text
ForkJoin sum = 10000000，并行度=12，耗时 22 ms
单线程 sum = 10000000，耗时 9 ms
```

诚实的读法：纯加法这种每元素 O(1) 的任务，拆分与入队的开销盖过了并行收益，单线程（还被 JIT 向量化）反而更快。ForkJoin 的收益出现在**每元素计算量重**或可并行深度大的场景（排序、树遍历）。它的另一个身份是公共基础设施：`ForkJoinPool.commonPool()` 是 CompletableFuture 默认执行器（[04-CompletableFuture异步](./04-CompletableFuture异步.md)）与并行 Stream 的宿主。
