# 观察者模式

## 定义

**观察者模式是一种定义对象间一对多依赖关系，当一个对象（主题）状态改变时，所有依赖它的对象（观察者）都会自动收到通知的响应型设计模式。**

## 本质断言

- 主题（Subject）维护观察者列表，持有观察者引用
- 观察者（Observer）定义更新接口
- 主题状态变化时，主动通知所有观察者，无需观察者轮询

## 机制解释

### 核心问题：对象间耦合导致的维护困难

当多个对象需要响应某个对象的状态变化时，常见的反模式是在状态变化对象中直接调用所有依赖对象的方法。这导致状态变化对象与所有依赖对象强耦合——每新增或删除一个依赖对象都需要修改状态变化对象的代码。

### 观察者模式如何解耦

把"谁需要知道"从主题中分离出来。主题只负责两件事：维护观察者列表、在状态变化时通知观察者。观察者自己决定是否订阅（attach）和如何处理通知（update）。主题不需要知道观察者的具体类型。

<pre>
Subject 状态变化
    │
    ├─ 遍历 observers 列表
    └─ 调用 observer.update()
            │
            ├─ EmailObserver
            ├─ SmsObserver
            └─ LogObserver
</pre>

### 推 vs 拉：通知内容的粒度

通知方式有两种：
- **推（Push）**：主题主动把变化数据推送给观察者，观察者无需再查询
- **拉（Pull）**：主题只通知变化发生，观察者按需从主题获取数据

推模式效率高但耦合紧（观察者需要知道数据结构），拉模式灵活但通知开销大（观察者可能多次查询）。

### 发布-订阅：观察者模式的变体

发布-订阅模式是观察者模式的进一步解耦：主题和观察者之间增加了一个消息中间件（Message Broker）。发布者和订阅者不直接通信，而是通过中间件传递消息。这使得发布者和订阅者完全解耦，可独立部署。

### 别名澄清

- **观察者模式（Observer）**：同步阻塞式，观察者和主题直接通信
- **发布-订阅模式（Pub-Sub）**：通常异步，有消息中间件做中介
- **模型-视图模式（Model-View）**：观察者模式的GUI特定应用，Model是主题，View是观察者

## 版本基准

- Stable: Java 21
- Latest: Java 25

## 技术正确性

- ✅ Java已废弃`Observable`类（设计有问题），推荐自己实现或使用`PropertyChangeSupport`
- ✅ Spring事件机制是观察者模式的企业级应用
- ✅ RxJava Subject是观察者模式的响应式扩展

## 适用场景

<pre>
一对多通知场景
    │
    ├─ GUI事件处理（按钮点击通知多个监听器）
    ├─ 模型-视图同步（数据变化自动更新显示）
    ├─ 消息推送（新闻发布通知订阅者）
    └─ 分布式事件（微服务间的事件传播）
</pre>

## 潜在问题

- **内存泄漏**：观察者未及时取消订阅，主题被垃圾回收时观察者仍被保留
- **通知顺序**：多观察者时通知顺序不确定，不应依赖特定顺序
- **循环依赖**：观察者和主题相互引用可能导致死循环
