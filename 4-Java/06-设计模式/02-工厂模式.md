# 工厂模式

## 定义

**工厂模式是一种将对象创建逻辑封装到专用类型中，使客户端代码无需了解具体类实现细节的创建型设计模式。**

## 本质断言

- 对象创建与对象使用分离，降低耦合
- 工厂类型本身也是多态的，支持扩展
- 客户端依赖抽象接口，不依赖具体实现

## 机制解释

### 简单工厂：集中创建逻辑

将产品创建集中在一个工厂类中，客户端通过参数（如字符串）指定产品类型。问题在于：每新增一种产品必须修改工厂类——这违反了开闭原则（对扩展开放，对修改关闭）。违反开闭原则的根本原因是：创建逻辑与产品类型绑定在同一位置，新增类型必须修改已有代码。

### 工厂方法：让子类决定创建什么

定义创建产品的抽象方法，由子类实现具体创建逻辑。客户端依赖工厂接口而非具体工厂——这使得新增产品只需新增工厂子类，无需修改现有代码。符合开闭原则的代价是类数量增加，但这是可管理的结构复杂度换取可维护性的权衡。

### 抽象工厂：创建产品族

产品族是一组相关联的产品（如Windows风格的Button和TextField）。抽象工厂定义创建整个产品族的接口，具体工厂实现创建特定风格的产品族。这保证了一个工厂创建的产品相互兼容——代价是新增产品族（而非单个产品）需要修改抽象工厂接口。

### 反射工厂：运行时动态创建

通过Class对象在运行时动态实例化对象，避免了编译时硬编码产品类型。配置文件+反射实现了解耦：产品类型由配置决定，代码无需修改。代价是性能略低（反射调用），且类型安全检查推迟到运行时。

### Lambda工厂：函数式替代

用`Supplier<T>`替代工厂接口，配合`Map<String, Supplier<Product>>`实现类型到创建函数的映射。这是把工厂方法模式函数式化的简洁实现，减少了接口和实现类的数量。

## 数据流

<pre>
客户端请求产品
    │
    ├─ 简单工厂：create("A") → 工厂内部switch → 返回产品
    │
    ├─ 工厂方法：factory.create() → 子类实现 → 返回产品
    │
    └─ 抽象工厂：factory.createButton() + factory.createTextField()
                 → 保证产品族一致性
</pre>

## 版本基准

- Stable: Java 21
- Latest: Java 25

## 技术正确性

- ✅ 工厂方法模式符合开闭原则
- ✅ 抽象工厂保证产品族一致性
- ✅ 反射工厂实现配置与代码分离

## 简单工厂 vs 工厂方法对比

| 维度 | 简单工厂 | 工厂方法 |
|------|----------|----------|
| 扩展方式 | 修改工厂类 | 新增工厂子类 |
| 符合开闭原则 | 否 | 是 |
| 类数量 | 少 | 多 |
| 适用场景 | 产品类型稳定 | 产品类型扩展 |

## 抽象工厂适用场景

<pre>
需要风格一致的产品族
    │
    ├─ UI组件库（Windows/Mac/Linux各有完整组件集）
    ├─ 数据库访问（MySQL/PostgreSQL/Oracle各有完整操作集）
    └─ 文档导出（Word/PDF/HTML各有完整格式支持）
</pre>

## 避免过度工程

当产品类型极少且稳定时，简单工厂足够好用。工厂方法的抽象代价只在真正需要扩展时才值得。
