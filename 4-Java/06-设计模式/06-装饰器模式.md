# 装饰器模式

## 定义

**装饰器模式是一种动态地给对象添加额外职责，通过在对象外包裹装饰器类来增强对象行为，比继承更灵活的structural设计模式。**

## 本质断言

- 装饰器与被装饰对象实现相同接口，客户端无法区分
- 装饰器持有被装饰对象的引用，通过委托实现透明增强
- 可以嵌套多个装饰器，组合出不同功能

## 机制解释

### 核心问题：继承的静态性与类爆炸

如果要给一个类添加多种可选功能（咖啡加牛奶、糖、奶油），用继承会导致类爆炸：MilkCoffee、SugarCoffee、WhipCoffee、MilkSugarCoffee...每种组合都需要一个新类。这违反了单一职责原则，也难以维护。

继承是编译时静态的，无法在运行时动态添加或移除功能。

### 装饰器如何解决

把"增强"抽象为装饰器类，每个装饰器持有被装饰对象的引用。装饰器在调用被装饰对象方法的同时，添加自己的增强逻辑。多个装饰器可以层层嵌套。

<pre>
Client → WhipDecorator
              └→ SugarDecorator
                     └→ MilkDecorator
                            └→ SimpleCoffee
</pre>

每层装饰器只关注自己的增强，调用时通过委托链完成全部逻辑。

### 为什么装饰器与代理不同

| 维度 | 装饰器 | 代理 |
|------|--------|------|
| 意图 | 动态增强功能 | 控制对对象的访问 |
| 接口 | 实现相同接口 | 实现相同接口 |
| 关系 | 可嵌套组合 | 通常单一代理 |
| 侧重点 | 增强行为 | 访问控制/延迟加载 |

装饰器的核心是可以无限组合，代理通常只代理一个对象。

### 装饰器的本质：委托链

装饰器的运作机制是委托：每个装饰器调用被装饰对象的方法，然后添加自己的处理。这种链式委托使得：
- 添加功能只需添加新装饰器
- 移除装饰器只需不包裹
- 顺序不同结果不同

## 版本基准

- Stable: Java 21
- Latest: Java 25

## 技术正确性

- ✅ Java I/O类是装饰器模式的经典应用（BufferedInputStream装饰FileInputStream）
- ✅ 装饰器实现相同接口是正确的设计
- ✅ 嵌套顺序会影响最终结果

## 适用场景

<pre>
需要动态组合功能
    │
    ├─ I/O流（缓冲、压缩、加密）
    ├─ Coffee订单（牛奶、糖、奶油组合）
    ├─ Web请求（日志、认证、缓存）
    └─ 数据源（缓存、日志、监控）
</pre>

## 继承 vs 装饰器

| 维度 | 继承 | 装饰器 |
|------|------|--------|
| 时机 | 编译时静态 | 运行时动态 |
| 类数量 | 类爆炸 | 类数量少 |
| 灵活性 | 低 | 高 |
| 组合 | 困难 | 简单嵌套 |
</pre>
