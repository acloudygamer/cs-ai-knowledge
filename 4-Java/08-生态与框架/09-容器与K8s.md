# 容器与 Kubernetes

> 前置：[08-可观测性](08-可观测性.md)、[03-垃圾回收](../03-JVM与运行时/03-垃圾回收.md)、[03-线程池](../04-并发编程/03-线程池.md) · 后续：[10-响应式编程](10-响应式编程.md)

> **版本基准**：容器运行时与 Kubernetes 的机制叙述不绑小版本；JVM 容器感知以 JDK 21/25 现状为准（容器支持自 JDK 8u191 / 10 起引入，默认开启）。YAML/Dockerfile 示例为**骨架，未实测**。

容器的本质不是"轻量虚拟机"，而是**一个被 Linux 命名空间隔离、被 cgroup 限额的普通进程**：namespace 让它看见假的独立世界（自己的 PID 空间、网络栈、挂载点），cgroup 给它划资源配额，镜像给它打包文件系统。Kubernetes 的本质是**声明式状态机集群**：你提交期望状态（YAML 对象），控制器们不停比较期望与实际、把实际推向期望。Java 应用进容器有一个特有的磨合问题——JVM 过去按"独占整机"做资源决策，容器时代它必须先学会读 cgroup。

## 镜像：分层与构建缓存

镜像是只读层的堆叠，容器在其上加一个可写薄层；读文件时从上往下找，写文件时把下层文件拷上来再改（Copy-on-Write）。两条工程推论：

- **层即缓存单位**：构建时逐层缓存，变动层之后的所有层重建。所以 Dockerfile 的写法是"变化频率升序排列"——依赖层（`pom.xml`）先于源码层（`src/`），改代码不破坏依赖缓存。
- **构建环境与运行环境分离**（多阶段构建）：编译要 JDK+Maven（大），运行只要 JRE（小），最终镜像只带运行层：

```dockerfile
FROM maven:3.9-eclipse-temurin-25 AS build      # 骨架，未实测
COPY pom.xml .
RUN mvn -q dependency:go-offline
COPY src ./src
RUN mvn -q package -DskipTests

FROM eclipse-temurin:25-jre
COPY --from=build /target/app.jar /app.jar
ENTRYPOINT ["java", "-XX:MaxRAMPercentage=75", "-jar", "/app.jar"]
```

## JVM 容器感知：三个磨合点

JDK 8u191 / 10 起 JVM 默认读取 cgroup 限制而非整机资源（`UseContainerSupport`，默认开）。仍有三处常见坑：

**堆大小**。默认堆上限 = 容器内存限额的 25%（`MaxRAMPercentage` 默认值 25.0）——这个默认值按"容器里还要跑别的"设计；单进程 Java 容器里它白白浪费内存，常规做法是显式提到 `-XX:MaxRAMPercentage=75`（给元空间、线程栈、直接内存留余量，见 [02-内存区域与对象](../03-JVM与运行时/02-内存区域与对象.md)）。

**CPU 核数**。`Runtime.availableProcessors()` 返回 cgroup CPU 配额折算的核数，而 ForkJoinPool 公共池、GC 线程数、JIT 编译线程数都按它定容（[03-线程池](../04-并发编程/03-线程池.md)）。配额是小数时按向上取整——`limits: 1500m` 被当成 2 核。更隐蔽的是 **CPU 节流（throttling）**：cgroup 按 100ms 周期结算配额，瞬时突发即使平均远低于限额也会被掐断，延迟毛刺由此而来。K8s 社区的通行建议是**设 requests 不设 CPU limits**（让 CFS 按权重分配空闲算力），或显式 `-XX:ActiveProcessorCount` 接管 JVM 的核数判断。

**内存超限即 OOMKill**。容器内存超限没有交换余地，cgroup 直接杀进程——JVM 的 `OutOfMemoryError` 都来不及抛。诊断入口是退出码 137（128+SIGKILL）与 K8s 事件的 `OOMKilled` 原因，而不是 JVM 日志。

## Kubernetes 对象模型：一条委托链

核心对象不是并列的清单，而是一条管理委托链：

```text
Deployment（声明：N 个副本、镜像版本、更新策略）
  → ReplicaSet（维持 N 个 Pod 存活，滚动更新时新旧两个 RS 交接）
    → Pod（最小调度单位：一组共享网络命名空间的容器，同 IP 同 localhost）
Service（一组 Pod 的稳定虚拟 IP 与名字；endpoints 只收 readiness 通过的 Pod）
```

**调谐循环（reconcile loop）** 是统一工作机制：每个控制器不断执行"读期望状态 → 读实际状态 → 计算差异 → 执行动作"。这解释了 K8s 的自愈语义——Pod 挂了不是"被修复"，而是 ReplicaSet 发现 `实际 < 期望` 后新建了一个；也解释了为什么 K8s 操作是"最终一致"：声明之后有一致收敛的延迟，没有同步事务。

**Service 的流量闸门是 readiness**：Service 的 endpoints 列表由 kubelet 的就绪探针驱动——探针不过，Pod IP 被摘除，流量绕行。探针三兄弟的分工：

| 探针 | 失败后果 | 语义 | 误用 |
|---|---|---|---|
| `startupProbe` | 通过前禁用另两个 | 给慢启动应用（大堆 JVM）争取时间 | 不配它却给 liveness 设超长 initialDelay——启动期裸奔 |
| `readinessProbe` | 从 Service 摘除，不重启 | "我暂时接不了客"（依赖未就绪/过载） | 不查关键依赖——未就绪实例照样接流量 |
| `livenessProbe` | kubelet 重启容器 | "我死了，救不活了" | 检查外部依赖——DB 挂 → 全体重启 → DB 更挂，雪崩放大器 |

滚动更新的可用性由两个参数保证：`maxUnavailable`（更新期间最多少几个）与 `maxSurge`（最多临时多几个）——任意时刻可用副本 ≥ `replicas - maxUnavailable`。Java 侧还要接住停机信号：Pod 被终止时先收 SIGTERM，Spring Boot 开 `server.shutdown=graceful` 可在宽限期内拒绝新请求、处理完存量请求再退出，否则进行中的请求被硬切。

**QoS 等级**由 requests/limits 的填写方式决定：两者都设且相等 = Guaranteed（OOM 时最后被杀）；都不设 = BestEffort（最先被杀）。生产服务至少把 requests 写实——它同时是调度依据与保命符。
