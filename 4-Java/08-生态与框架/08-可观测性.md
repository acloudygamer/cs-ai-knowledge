# 可观测性：指标、追踪、日志

> 前置：[07-SpringSecurity](07-SpringSecurity.md)、[06-日志框架](../05-IO与外部世界/06-日志框架.md) · 后续：[09-容器与K8s](09-容器与K8s.md)

> **版本基准**：Micrometer 1.16 / Micrometer Tracing 1.6（Spring Boot 4.0 配套）；OpenTelemetry Java Instrumentation 2.x（agent 线，核心 SDK 为 1.5x）；Prometheus 3.x（3.0 GA 2024-11）。示例均为**骨架，未实测**。

可观测性（Observability）的对象是分布式系统的内部状态，手段是三条互补的数据通道：**指标（Metrics）** 回答"整体表现如何"（聚合数值，便宜可长期存）；**追踪（Traces）** 回答"这个请求死在哪一步"（单请求路径，贵，要采样）；**日志（Logs）** 回答"那一刻具体发生了什么"（离散事件，细节最全）。三者不是并列选项而是分工：指标发现异常 → 追踪定位到哪段 → 日志给出那段的具体现场。

## 本质

三支柱能拼成完整图景，靠的是一根共同的线——**trace id**。请求入口生成全局唯一 trace id，沿调用链传播（HTTP 头走 W3C Trace Context 的 `traceparent`），日志框架把它写进每行日志，指标把它（采样时）挂为 exemplar。没有这个关联键，三条通道就是三座孤岛。

Java 侧的组件分层（Spring Boot 4 口径）：

```text
业务代码
  ├─ Micrometer（指标门面 API）──→ Prometheus Registry ──被抓取──→ Prometheus ──→ Grafana
  ├─ Micrometer Tracing（桥接层）──→ OpenTelemetry SDK ──OTLP──→ 后端（Tempo/Jaeger…）
  └─ SLF4J/Logback（含 MDC 里的 trace id）──→ 收集器 ──→ Loki/ES
```

Micrometer 是 SLF4J 在指标界的同款角色：代码只依赖门面，底层注册表可换（Prometheus、OTLP、Datadog）。OpenTelemetry（OTel）是 CNCF 的统一采集规范——trace、metrics、logs 三类信号的 API、SDK 与传输协议（OTLP）都由它定义，厂商后端任选；Micrometer Tracing 是 Spring 世界通往 OTel 的桥。

## 机制

### 指标：Prometheus 的拉模型与基数纪律

Prometheus 主动**拉取**（scrape）各实例的 `/actuator/prometheus` 端点，把指标存成时间序列：`(指标名, 标签集, 时间戳) → 值`。拉模型的推论：实例必须被发现（K8s 里靠服务发现自动注册，见 [09-容器与K8s](09-容器与K8s.md)），且短生命周期进程（Job）拉不到——后者用 Pushgateway 补。

两类最常用的查询模式（骨架）：

```text
rate(http_server_requests_seconds_count{status=~"5.."}[5m])   # 5 分钟窗口的错误率
histogram_quantile(0.99, rate(http_server_requests_seconds_bucket[5m]))  # P99 延迟
```

`histogram_quantile` 的估算是**桶内线性插值**——P99 的精度上限由直方图分桶决定，不是真实排序值；要真实分位数得在进程内用 Micrometer 的 `publishPercentiles`（内存聚合，不可跨实例合并）。**基数（cardinality）纪律**：标签每个取值组合都是一条独立时间序列，`user_id` 这类高基标签会让序列数爆炸、拖垮存储——标签只放低基维度（状态码、路径模板，而非原始 URL）。

### SLI/SLO：把"稳定"写成数字

- **SLI**（Indicator，指标）：如"5 分钟窗口内非 5xx 请求占比"。
- **SLO**（Objective，目标）：如"30 天内 SLI ≥ 99.9%"。
- **错误预算**：SLO 的补集。99.9% 的 30 天 SLO 意味着全月允许约 43 分钟的等效故障时间（ $43200 \times 0.001 \approx 43$ 分钟）；预算花完就冻结发布、专修可靠性，预算充裕就放心发版——SLO 的工程价值是把"稳不稳"的争吵换成一条可计算的额度。

### 追踪：span 树与采样的取舍

一个 trace 是一棵 span 树：入口 span 是根，每次出站调用（HTTP、DB、MQ）开一个子 span，记录名称、起止时间、属性与异常。Micrometer Tracing / OTel 的自动埋点在 Spring MVC/WebFlux 的过滤器层完成（[07-SpringSecurity](07-SpringSecurity.md) 的同款链式位置），出站客户端由 instrumentation 自动注入 `traceparent` 头。

**采样是必付的权衡**：全量追踪的开销（CPU 序列化 + 网络 + 存储）在高 QPS 下不可接受。

| 策略 | 位置 | 代价 | 偏差 |
|---|---|---|---|
| 头部采样（head-based） | 请求入口决定采不采 | 最省 | 随机丢失——罕见的慢请求/错误请求可能正好没采 |
| 尾部采样（tail-based） | 请求完成后由 Collector 决定 | 需缓冲全量 span，贵 | 可按规则保留"所有错误与慢请求"，运维价值最高 |

生产常见组合：低基头部采样（如 10%）保底统计意义，Collector 层尾部规则捞全错误样本。

### 日志：结构化与关联

日志侧的两条纪律：输出结构化（JSON）使字段可查（[06-日志框架](../05-IO与外部世界/06-日志框架.md)）；把 `traceId`/`spanId` 放进 MDC 使日志能被追踪反查。三支柱的回路由此闭合：Grafana 里指标告警 → 点开 exemplar 跳到 trace → trace 里某 span 一键看对应日志行。
