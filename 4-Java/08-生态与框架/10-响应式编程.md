# 响应式编程

> 前置：[09-容器与K8s](09-容器与K8s.md)、[05-虚拟线程与结构化并发](../04-并发编程/05-虚拟线程与结构化并发.md)（理解本篇结论的前提） · 后续：[11-GraalVM与云原生](11-GraalVM与云原生.md)

> **版本基准**：Project Reactor 2025.0（Spring Boot 4.0 配套）；Java 9+ 的 `java.util.concurrent.Flow` 实测于 Temurin JDK 25.0.4.1（`javac --release 21`）。Reactor/WebFlux 示例为**骨架，未实测**。

响应式流的本质是**一次对异步数据流的标准化**：把"异步地、一个接一个地吐数据"抽象成四个接口的协议，并用**背压（backpressure）**解决快生产者压垮慢消费者的问题。Reactive Streams 规范（2015 年发布）定义的就是这四个接口，Java 9 把它们原样收进 JDK（`java.util.concurrent.Flow`），Reactor、RxJava、Akka Streams 都是规范的实现。

## 本质：四个接口与一条控制回路

```text
Publisher ──subscribe──> Subscriber
              │ 先收到 onSubscribe(Subscription)
              ▼
Subscriber ──request(n)──> Publisher    ← 背压：我最多还能处理 n 个
Publisher ──onNext(t)×n──> Subscriber   ← 不得超过 n
Publisher ──onError | onComplete──> Subscriber（终止信号，二选一）
```

`Subscription` 是从消费者指回生产者的控制通道——**数据流向是推（push），配额流向是拉（pull）**，生产者不得发出超过累计 request 量的元素。这是它与普通回调（`CompletableFuture` 式）的分界线：回调没有这条控制回路，快生产者只能用无界缓冲硬扛，最终以 OOM 收场。

实测（Temurin 25.0.4.1，JDK 自带 `SubmissionPublisher`）：订阅者只 `request(2)`，之后每消费一个再要一个：

```java
try (SubmissionPublisher<String> pub = new SubmissionPublisher<>()) {
    pub.subscribe(new Flow.Subscriber<>() {
        private Flow.Subscription sub;
        public void onSubscribe(Flow.Subscription s) {
            sub = s; sub.request(2);
            System.out.println("onSubscribe, request(2)");
        }
        public void onNext(String item) {
            System.out.println("onNext: " + item);
            sub.request(1);                     // 消费 1 个补 1 个配额
        }
        public void onError(Throwable t) { }
        public void onComplete() { System.out.println("onComplete"); }
    });
    for (int i = 1; i <= 5; i++) {
        pub.submit("item-" + i);
        System.out.println("submit(item-" + i + "), estimateMinimumDemand="
                + pub.estimateMinimumDemand());
    }
    Thread.sleep(500);
}
```

输出（节选）：

```text
onSubscribe, request(2)
onNext: item-1
submit(item-1), estimateMinimumDemand=1
submit(item-2), estimateMinimumDemand=1
onNext: item-2
submit(item-3), estimateMinimumDemand=0     ← 配额耗尽，submit 进入缓冲
onNext: item-3
...
onComplete
```

`estimateMinimumDemand` 随订阅者 request 涨、随投递落——配额的收放就是背压的全部机制。JDK 只给接口与这一个参考实现，生产用途走 Reactor。

## Reactor 与 WebFlux

Reactor 在四个接口上加了两个具体类型与一百来个操作符：**`Mono<T>`**（0 或 1 个元素，替代 `CompletableFuture<T>`）与 **`Flux<T>`**（0..N 个元素）。操作符链（`map`/`flatMap`/`filter`…）声明的是"数据怎么流"，不是"现在执行"——**没有 subscribe，整条链一个字符都不会流动**（冷流语义），这是新手最常见的"代码没执行"之谜。

**WebFlux** 把这套模型接到 Web 层：底层是 Netty 的事件循环（少量线程轮询万级连接），控制器返回 `Mono<ResponseEntity>` 而不是同步值——线程不等待结果，结果到达时由事件循环写回 socket。配套约束是**全链路非阻塞**：事件循环线程一旦被阻塞调用（JDBC、Thread.sleep）占住，它负责的所有连接一起饿死——阻塞操作必须显式扔到 `Schedulers.boundedElastic()` 线程池，数据库访问要换 R2DBC 驱动。

```java
@GetMapping("/users/{id}")                      // 骨架，未实测
public Mono<User> getUser(@PathVariable Long id) {
    return userRepository.findById(id);         // 必须是响应式 repository
}
```

## 关键转折：虚拟线程落地后的适用面收窄

响应式模型在 2015-2021 年兴起，是因为它解决的问题——"阻塞 I/O 浪费平台线程，线程数撑不住高并发"——当时没有别的解。Java 21（2023-09）虚拟线程正式转正后，等式变了：**阻塞不再贵**——`userRepository.findById(id)` 这行同步代码跑在虚拟线程上，阻塞时载体线程被让出，万级并发用普通 Servlet 栈就能扛（机制见 [05-虚拟线程与结构化并发](../04-并发编程/05-虚拟线程与结构化并发.md)）。Spring Boot 3.2 起 `spring.threads.virtual.enabled=true` 一行开启，4.x 继续作为推荐路径之一。

于是两条路线的分工重排：

| 场景 | 推荐 | 理由 |
|---|---|---|
| 普通 CRUD / RPC 聚合，高并发 | Servlet 栈 + 虚拟线程 | 命令式代码、栈可读、异常栈完整、生态（JDBC/绝大多数库）原生兼容 |
| 真正的流式管道（SSE、WebSocket、持续数据流） | WebFlux | 数据本就是无限流，背压是语义的一部分而非性能手段 |
| 必须背压的端到端流（上游快下游慢且不能丢） | WebFlux / RSocket | 背压协议是虚拟线程给不了的东西 |

成本账也要摆平：响应式的代价不是学不会操作符，而是**全链路的排他性**——一个阻塞调用污染事件循环、同步库全不可用、调试栈被操作符切碎。虚拟线程把"为了并发度而响应式"这个最大动机拿走了，留下的是"为了流语义而响应式"这个原本就该是主理由的窄场景。存量 WebFlux 系统无需改写；新系统的默认起点应是 Servlet + 虚拟线程，遇到真流式需求再上响应式。
