# 持久化框架：JDBC、MyBatis、JPA 与 Spring Data

> 前置：[01-Spring核心](01-Spring核心.md)（容器与代理）、[05-JDBC](../05-IO与外部世界/05-JDBC.md)（JDBC 的驱动与连接层） · 后续：[03-Redis](03-Redis.md)

> **版本基准**：Spring Boot 4.0（2025-11）对应 Hibernate 7.1 / Spring Data 2025.1；MyBatis 3.5.x 线持续维护。示例均为**骨架，未实测**。

[05-JDBC](../05-IO与外部世界/05-JDBC.md) 讲了 JDBC 本身——驱动注册、`Connection` 会话、`PreparedStatement` 的参数绑定；本篇从它的肩膀往上：持久化框架的四代抽象各自把哪一段手工劳动吃掉了，又为每一段自动化付出了什么代价。

## 本质

持久化框架要消解的是**对象—关系阻抗失配**：Java 里是对象图（引用、继承、集合），数据库里是二维表（行、外键、连接），两个模型之间的翻译工作繁重且重复。四代方案按"自动化程度 vs SQL 控制权"排成一条光谱：

| 层 | 抽象 | SQL 归谁写 | 代价 |
|---|---|---|---|
| JDBC | 连接 + 语句 | 你写，且手工搬运 `ResultSet` 每一列 | 样板代码淹没业务 |
| MyBatis | SQL 映射 | 你写，框架做参数绑定与结果映射 | SQL 与代码分两处维护 |
| JPA/Hibernate | ORM（对象关系映射） | 框架从对象状态生成 | 生成的 SQL 不可直接控制，引入缓存语义 |
| Spring Data | 仓库（Repository） | 方法名/注解声明，框架推导 | 复杂查询超出推导能力时回落到前一层 |

共性结构：每一层都包着下一层——MyBatis 的执行终点是 `PreparedStatement`，Hibernate 的 flush 终点也是 JDBC batch。理解下层的连接（[05-JDBC](../05-IO与外部世界/05-JDBC.md) 的连接池、事务边界）是诊断上层一切怪象的前提。

## 机制

### MyBatis：SQL 留在你手里，搬运交给框架

MyBatis 的本质是 **SQL 映射器**：你在 XML 或注解里写原生 SQL，框架负责三件事——把参数绑进 `PreparedStatement`、执行、把 `ResultSet` 逐列映射回 Java 对象。执行链：

```text
Mapper 接口方法调用（JDK 动态代理）
  → Executor（SIMPLE / REUSE / BATCH 三种策略）
  → StatementHandler 组装 SQL → ParameterHandler 绑参
  → JDBC 执行
  → ResultSetHandler 按 resultMap 逐列装配对象
```

Mapper 接口没有实现类——`SqlSession` 为接口生成 JDK 动态代理（[01-Spring核心](01-Spring核心.md) 的同款机制），调用被转成上面这条链。两个可观察推论：

- **SQL 完全可控**：优化器提示、数据库方言、复杂连接都直接写，性能问题直接看 SQL 本身——这是 MyBatis 在重 SQL 优化场景（报表、数仓对接）存活至今的原因。
- **动态 SQL 是字符串拼装**：`<if test="...">` 里的表达式在运行期求值、拼接进 SQL 文本；用 `#{}` 走参数绑定（安全），用 `${}` 是文本替换（拼接即注入面，见 [12-安全编码](12-安全编码.md)）。

MyBatis 的扩展口是**拦截器链**：`Executor`、`StatementHandler`、`ParameterHandler`、`ResultSetHandler` 四个接口允许插件包装，分页插件（PageHelper 类）就是在 `StatementHandler` 上拦截、把 SQL 改写为 `LIMIT ? OFFSET ?` 的物理分页。注意逻辑分页（`RowBounds`）是查出全部再在内存截断——大表上等于不分页。

### JPA/Hibernate：用对象状态换 SQL 自动化

JPA（Jakarta Persistence）是规范，Hibernate 是其主流实现。核心不是"帮你写 SQL"，而是一个有状态的中介——**持久化上下文（Persistence Context）**：

1. **同一性保证**：同一事务内 `findById(k)` 两次，返回的是同一个 Java 引用（`e1 == e2`）。持久化上下文本质是以主键为键的缓存，实体改与读都走它。
2. **脏检查（dirty checking）**：实体加载时留一份快照；事务提交 flush 时逐字段比对当前值与快照，只为变化的实体生成 `UPDATE`。`entity.setName("x")` 之后不写任何保存调用，SQL 在提交时自动出现——自动化的代价正在这里：SQL 何时发出、发几条，由框架的快照比对决定，而不是由你的代码显式决定。
3. **实体状态机**：`new`（瞬态）→ `persist`（托管，纳入上下文）→ 事务外（游离）→ `remove`（删除）。只有托管态享受同一性与脏检查；游离实体改字段不会同步，须 `merge` 回上下文。

### N+1：自动化税的标志性形态

N+1 是 ORM 自动化最经典的账单。查 100 个订单（1 条 SQL），每个订单懒加载它的用户（100 条 SQL）——总往返 $1 + N$ 次，而连接层的往返延迟（[05-JDBC](../05-IO与外部世界/05-JDBC.md) 的网络一跳）被放大了 $N$ 倍。

成因链：关联默认 `LAZY` → 集合是代理对象 → 首次访问触发单条 `SELECT` → 循环中每个实体各触发一次。三种解法按代价排：

| 解法 | SQL 数 | 代价 |
|---|---|---|
| `JOIN FETCH` | 1 | 笛卡尔展开，多对多叠加时结果行数膨胀 |
| `@BatchSize(n)` | $1 + \lceil N/n \rceil$ | 折中，仍是多条 |
| 投影/DTO 查询 | 1 | 放弃实体托管态（无脏检查） |

诊断手段是机制决定的：打开 `hibernate.show_sql` 或在指标里盯每个事务的语句数——自动化框架的问题永远先暴露在"它实际发了什么 SQL"。

### 双向关联的 owning side

JPA 双向关联必须指定一方为 owning side（拥有 `@JoinColumn`，负责维护外键），另一方 `mappedBy` 只做视图。**只有 owning side 的改动会进数据库**：

```java
employee.setDepartment(dept);        // owning side，外键会更新
dept.getEmployees().add(employee);   // inverse side，只改内存视图，不落库
```

这不是 Bug，是规范取舍：两侧都写外键会生成重复/冲突的 UPDATE。纪律是两侧都改（内存一致 + 落库），或者封装 `addEmployee` 助手方法一次改两边。

### Spring Data：把"按主键查"这类查询也吃掉

Spring Data 在 JPA 之上再包一层：你只声明接口

```java
public interface OrderRepository extends JpaRepository<Order, Long> {
    List<Order> findByStatusAndCreatedAtAfter(String status, Instant since);
}
```

框架按方法名推导出 JPQL，运行时生成实现（仍是动态代理）。它消灭的是 CRUD 与简单条件查询的全部样板；当查询超出命名约定的表达力，回落到 `@Query` 手写 JPQL，再不行回落到 `EntityManager`——抽象层级在此处形成完整的逃生梯。

### 选型边界

- **SQL 重、优化敏感、报表型**：MyBatis——SQL 在你手里，慢查询直接可改。
- **领域模型重、CRUD 为主、团队接受 ORM 语义**：JPA + Spring Data——自动化吃掉样板，代价是学会读它生成的 SQL。
- **两者可共存**：同一项目里 Spring Data 管常规 CRUD，MyBatis 管复杂查询，共用同一个 `DataSource` 与事务管理器——它们终点的连接层是同一个（[05-JDBC](../05-IO与外部世界/05-JDBC.md)）。
