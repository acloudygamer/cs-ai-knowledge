# Redis

> 前置：[02-持久化框架](02-持久化框架.md) · 后续：[04-Kafka](04-Kafka.md)

> **版本基准**：Redis 8.x（写作时 2026-09 最新稳定线 8.8，2026-05；8.0 GA 2025-05 起许可改为 RSALv2/SSPLv1/AGPLv3 三选一，回归 OSI 认可的开源，并把原 Redis Stack 的 JSON、搜索、时序、向量集并入核心）。数据结构编码演进以 7.0/7.2 为关键节点（文中标注）。机制叙述不依赖具体小版本；示例命令为通用口径。

Redis 的本质是**一张放在内存里的全局哈希表，外面套一个单线程事件循环**：所有 key 登记在一张 O(1) 字典上，命令由单个线程串行执行——没有锁、没有并发写冲突，延迟的下限由内存访问而非磁盘决定。持久化、复制、过期都只是挂在这台循环上的后台作业。它在 Java 栈里的典型位置：挡在关系库（[02-持久化框架](02-持久化框架.md)）前面的缓存层，或独立承担会话、排行榜、限流、轻量队列。

## 本质

**为什么是单线程还能快**。命令执行单线程化消灭了两类开销：数据结构加锁与上下文切换；真正的瓶颈从来不在 CPU 而在网络 I/O 与内存带宽。6.0（2020）起 Redis 把 socket 读写拆给 I/O 线程池并行，**命令执行仍是单线程**——并行的是搬运，串行的是语义，原子性保证不变。

**内存即预算**。每个 value 不是裸数据，而是"逻辑类型 + 内部编码"两层：同一种逻辑类型按体量在两套编码间切换，小对象走紧凑编码省内存，超阈值自动转通用编码保速度。

## 机制

### 数据结构的内部编码与演进

| 逻辑类型 | 紧凑编码（小对象） | 通用编码（大对象） | 通用编码的查找复杂度 |
|---|---|---|---|
| String | `int` / `embstr` | `raw`（SDS） | O(1) |
| Hash | `listpack` | 哈希表 | O(1) |
| List | （3.2 起统一为 quicklist） | quicklist = 双向链表挂 listpack 段 | 端点 O(1) |
| Set | `intset` / `listpack`（7.2 起） | 哈希表 | O(1) |
| ZSet | `listpack` | skiplist + 哈希表 | O(log N)（跳表） |

编码切换对客户端透明，`OBJECT ENCODING key` 可见当前编码。两个演进节点值得记住：

- **ziplist → listpack（7.0，2022）**：ziplist 每个条目记录"前一条长度"，改头部可能引发级联重排（连锁更新，最坏 O(N²)）；listpack 改为每条只记自身长度，从结构上消除连锁更新。7.0 起 Hash/List/ZSet 的紧凑编码换成 listpack，7.2 扩展到 Set。这是"约束的产物"：换编码不是追新，是堵死一个病态复杂度。
- **ZSet 的通用编码是跳表加哈希表**：跳表保证按 score 的范围查询 O(log N)，哈希表保证按成员查 score O(1)——一份数据两种索引，各付一份内存。

### 过期与淘汰：内存有限时的两条链

过期键删除是**惰性 + 定期采样**的混合：访问时才检查（惰性，零额外开销但冷键赖着不走）；后台周期任务随机采样一批带 TTL 的键删除已过期的（主动，限量采样是 CPU 与回收速度的折中）。内存顶到 `maxmemory` 时走第二条链——淘汰策略：`allkeys-lru`（全体键里挑最久未用）、`volatile-ttl`（挑剩余寿命最短）等八个档位。缓存用法选 `allkeys-lru`，把 Redis 当持久存储用就必须接受"满了写不进去"或"满了我替你丢"的二选一。

### 持久化：RDB 快照与 AOF 日志

- **RDB**：定时 `fork` 出子进程，把整份内存写成二进制快照。`fork` 之后父子共享内存页，写时复制（Copy-on-Write）——快照期间写入越猛，复制出的页越多，内存峰值越高。恢复快、文件紧凑，代价是丢"上次快照到现在"的窗口。
- **AOF**：把每条写命令追加到日志，重放即可重建。`appendfsync everysec`（默认）由后台线程每秒落盘一次——最多丢 1 秒。7.0 起 AOF 改为多文件结构（base + incr + manifest 清单），重写不再阻塞增量写入。
- 两者可同时开：RDB 做冷备基线，AOF 保最近窗口，重启先装 RDB 再补 AOF。

### 缓存三问题：三个不同的失效位置

缓存的经典三事故不是同一件事，失效位置各不相同，对策也因机制而异：

**穿透——查的是不存在的数据**。缓存未命中正常，DB 也查不到，于是每次请求都穿透到 DB（典型：恶意构造不存在的 id）。缓存层对"不存在"没有记忆是根因。对策一：空值短 TTL 缓存（DB 查不到也写 `null` 占位）。对策二：布隆过滤器前置拦截——一个位数组加 $k$ 个哈希函数做集合成员判定，假阳性率

 $p = \left(1 - e^{-kn/m}\right)^k$ 

其中 $n$ 是元素数、 $m$ 是位数。比如 $n = 10^8$ 、 $p = 1\\%$ 时最优 $k \approx 7$ 、 $m \approx 9.6 \times 10^8$ 位 $\approx 120$ MB——用一块固定大小的内存换掉对 DB 的无效打击。注意它只会误报"存在"（放行后查空），绝不漏报"不存在"。

**击穿——一个热点 key 刚好过期**。某热门 key 过期的瞬间，几百个并发请求同时未命中、同时去 DB 重建——DB 被瞬时放大打满。对策是把"重建"变成单线程事件：第一个未命中者拿分布式锁（`SET lock NX PX`）去回源，其余请求短暂等待后读缓存；或改用逻辑过期（value 里带过期时间戳，后台异步刷新，不设物理 TTL）。

**雪崩——一大批 key 同时过期，或 Redis 本身宕机**。前者是 TTL 写入时刻对齐造成的（同一批预热数据同一时刻到期）：给基础 TTL 加随机抖动即可打散。后者是可用性问题：多级缓存（本地 Caffeine + Redis）、熔断降级（缓存不可用时限流直读 DB 并放行部分请求），到这一层已经超出 Redis 本身，进入 [06-SpringCloud微服务](06-SpringCloud微服务.md) 的熔断话题。

### 分布式锁：原子性在两条命令之间

`SETNX` 加 `EXPIRE` 分两条发，客户端在两条之间崩溃就留下永不过期的锁。正确形态是单条原子命令 `SET key value NX PX 30000`，value 用 UUID 标识持有者；释放时必须验证持有者再删，两步合并成 Lua 脚本（Redis 单线程执行脚本即原子）：

```lua
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

不验持有者就删的代价：A 的锁超时自动释放后 B 抢到锁，A 姗姗来迟的 `DEL` 删掉的是 B 的锁。跨多节点的 RedLock 方案有公开争议（Martin Kleppmann 与 antirez 之争），工程上更常见的答案是"单点 Redis 锁够用就用， fencing 级别需求交给 ZooKeeper/etcd 或数据库唯一约束"。

### 概率与扩展结构

- **HyperLogLog**：基数估计（UV 统计）， $2^{14} = 16384$ 个寄存器，固定约 12 KB 内存，标准误差约 $1.04 / \sqrt{16384} \approx 0.81\\%$——用可忽略的内存换不可精确的计数。
- **Stream**：5.0 引入的消息流，消费者组 + Pending Entries List 实现至少一次投递，轻量队列场景可替代引入专门 MQ；量级上来后仍应看 [04-Kafka](04-Kafka.md)。
- **Redis 8 的模块内化**：JSON 文档、全文搜索、时序、向量集（8.x 新增，面向向量检索）从外挂模块变内置数据类型。

### 版本线

| 版本 | 时间 | 关键变化 |
|---|---|---|
| 6.0 | 2020 | I/O 多线程（命令执行仍单线程）、ACL |
| 7.0 | 2022 | listpack 替换 ziplist、Functions、多文件 AOF |
| 7.2 | 2023 | 最后一个 BSD 许可版本；listpack 扩展到 Set |
| 7.4 | 2024 | 许可转 RSALv2/SSPLv1（源码可见非开源）——Linux 基金会分叉出 Valkey（BSD） |
| 8.0 | 2025-05 | 重回开源（AGPLv3 三选一），原 Stack 模块并入核心 |

选型旁注：Valkey（2024 年从 7.2 分叉，AWS/GCP 托管默认）与 Redis 8 协议兼容；纯缓存场景两者可互换，用到 Redis 8 内置的搜索/向量能力则只有 Redis 侧有。
