# 集成测试

> 前置：[Mockito 与 Test Double](./03-Mockito与TestDouble.md) · 后续：[测试覆盖率与质量门](./05-测试覆盖率与质量门.md)

> **版本基准**：Testcontainers 2.0.5（Maven Central 现行；2.0 起模块坐标加 `testcontainers-` 前缀、移除 JUnit 4 支持）。本机无 Docker，Testcontainers 与 Spring 示例为**骨架，未实测**，坐标与 API 已网查核实。

单元测试用替身换掉了依赖，这同时是它的盲区：被换掉的依赖本身的**契约**——SQL 方言、JSON 序列化格式、HTTP 状态码语义、事务行为——在单元测试里从未被真正执行过。集成测试就是补这个洞的层：**让真实组件在真实接缝上对接**，验证契约而非内部逻辑。它在测试金字塔（[01-测试理论](./01-测试理论.md)）的中部：比单元测试慢、比 E2E 快，数量应居中。

## 三条典型接缝

集成测试的价值密度取决于"接缝两边是否真的可能不一致"。三条最值得测的接缝：

**数据库**。JPA/Hibernate 的 HQL 与实体映射是可移植的，但落下去的 SQL 不是：分页语法、JSON 列类型、序列与自增、约束冲突的异常类型，H2 与 PostgreSQL 行为不同。在 H2 上全绿、上生产才炸的集成缺陷是这一层的经典事故——结论：持久层集成测试应该用与生产同款的数据库，而不是内存替身。

**Web 层**。Controller 的逻辑可以单测，但路由匹配、参数绑定、内容协商、过滤器链是框架与代码的接缝。Spring 的 MockMvc 在内存里驱动 DispatcherServlet（不经过网络栈），能验证路由与序列化；要验证真实 HTTP 行为（端口、连接、压缩）则需 `@SpringBootTest(webEnvironment = RANDOM_PORT)` 起真实容器。

**消息**。生产者的序列化格式与消费者的反序列化期望是否一致、重试与死信是否按配置工作——这些只有真实 broker 在场时才有意义。

## Testcontainers：用 Docker 起真实依赖

Testcontainers 的机制一句话：测试启动时通过本机 Docker API 拉起真实依赖的容器（PostgreSQL、Kafka、Redis……），测试结束销毁。它把"测试环境与生产同版本"从运维约定变成代码声明：

```java
// 骨架，未实测（本机无 Docker）；坐标：org.testcontainers:testcontainers-postgresql:2.0.5
// 配套：org.testcontainers:testcontainers-junit-jupiter:2.0.5（2.0 起旧坐标 junit-jupiter 改名）
@Testcontainers
class OrderRepositoryIT {

    @Container   // JUnit 扩展在类启动时拉起容器，类结束后销毁
    @ServiceConnection  // Spring Boot 3.1+：自动把连接串注入应用配置，免手写
    static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:17");

    @Test
    void savesAndFinds() { /* 用注入的数据源跑真实 SQL */ }
}
```

连接链条：容器监听的是**随机映射端口**（并行跑多个测试类不冲突），所以数据源 URL 不能写死在配置里——`@ServiceConnection`（或 JUnit 5 下的 `@DynamicPropertySource`）在容器启动后把实际 JDBC URL 注回应用上下文。隔离强度由 Docker 的 namespace 机制担保：每个测试类一套独立容器，端口、文件系统、进程互不可见，销毁后无状态残留。

成本账要认：拉镜像与起容器是秒级到分钟级开销，Docker 成为开发机与 CI 的硬前置。这正是金字塔把这一层数量压在中间的约束来源。折中手段：同模块测试类共享一个容器（单例容器模式），用事务回滚或清库脚本在测试间隔离数据。

## 与单元测试的分工

判据是看被测逻辑住在哪一侧：

- 分支、边界、计算 → 单元测试（[02-JUnit5](./02-JUnit5.md)），依赖用替身（[03-Mockito与TestDouble](./03-Mockito与TestDouble.md)）；
- "我发的 SQL/HTTP/消息，对方按不按契约理解" → 集成测试；
- 同一条行为两边都测是浪费：集成测试验证接缝连通即可，不重复穷举分支。

一个可操作的分配规则：**每条接缝至少一个集成测试（打通即够），每条业务规则全部走单元测试**。接缝测试失败指向契约两侧，规则测试失败指向一个类——失败定位成本是分配是否合理的日常反馈。
