# 测试覆盖率与质量门

> 前置：[集成测试](./04-集成测试.md) · 后续：[Spring 核心](../08-生态与框架/01-Spring核心.md)

> **版本基准**：JaCoCo 0.8.15（Maven Central 现行，本篇示例实测：org.jacoco.agent 0.8.15 runtime + org.jacoco.cli 0.8.15，Temurin JDK 25.0.4.1）。

测试覆盖率度量的是**测试执行触及了代码的多大比例**。它是一维数字，而"测得好不好"是多维问题——把两者混同是覆盖率一切误用的根源。本篇先给指标的精确定义，再讲 JaCoCo 怎么测出来，最后论证它正确的用法：下限告警，而非追求目标。

## 指标语义：四种覆盖各数什么

| 指标 | 计数单位 | 回答的问题 |
|---|---|---|
| 行覆盖（line） | 源码行 | 哪些行被执行过 |
| 分支覆盖（branch） | 每个条件跳转的各出口 | `if` 的真假两侧、`switch` 的各 case 是否都走过 |
| 方法覆盖（method） | 方法 | 哪些方法被调用过（最粗） |
| 指令覆盖（instruction） | 字节码指令 | JaCoCo 的默认主指标，数最细 |

关键的不等式：**行覆盖 100% 推不出分支覆盖 100%**。`if (a && b)` 只要整体走真一次就算行覆盖，但 `a=false`（短路导致 `b` 未求值）与 `a=true, b=false` 两条失败路径可能都未触及。分支覆盖仍不够——它不要求条件的每种组合，也不断言结果对错。

## 实测：没有断言的"测试"照样刷覆盖率

JaCoCo 的工作方式是**字节码插桩**：在类加载期给每个分支埋计数器，执行时累加，结束后汇总成报告。实测（Temurin 25.0.4.1，JaCoCo 0.8.15）：被测类只走一条路径、调用方连一个断言都没有——

```java
package demo;
public class Grade {
    public static String of(int score) {
        if (score < 0 || score > 100) throw new IllegalArgumentException();
        if (score >= 60) return "pass";
        return "fail";
    }
}
```

```bash
java -javaagent:jacocoagent.jar=destfile=jacoco.exec -cp classes demo.Main   # Main 只调用 Grade.of(80)
java -jar jacococli.jar report jacoco.exec --classfiles classes --sourcefiles src --csv report.csv
```

实测报告（CSV 节选）：

| 类 | 指令（漏/覆盖） | 分支（漏/覆盖） | 行（漏/覆盖） |
|---|---|---|---|
| Grade | 9 / 10 | 3 / 3 | 2 / 2 |

`Grade` 分支覆盖 50%（6 个分支出口走了 3 个：异常分支与 fail 分支全部未走），而这个"测试"没有做任何断言——**覆盖率照常累计**。这是覆盖率语义的最小实证：它记录"执行过"，对"验证过"一无所知。

插桩有两种时机：**on-the-fly**（如上，`-javaagent` 在类加载时改写字节码，构建零侵入，Maven Surefire/Gradle test 任务挂 agent 即用）与 **offline**（预先改写 class 文件再执行，用于无法挂 agent 的环境，如某些嵌入式容器）。产物 `.exec` 是计数器数据，报告（HTML/XML/CSV）由 CLI 或构建插件事后生成——执行与报告解耦，CI 里多个模块的 exec 文件可合并出全量视图。

## 覆盖率的正确用法：下限，不是目标

从上面的实测出发，论证分两步：

**高覆盖不证明什么。** 执行 ≠ 验证。没有断言的测试、断言恒真的测试、只断言"没抛异常"的测试都全额贡献覆盖率。把覆盖率当 KPI 追求，得到的是 Goodhart 定律的标准样本——指标变成目标后即失效：团队会批量生产无断言测试把数字推上去，缺陷检出能力反而下降（写正经测试的时间被挤占）。

**低覆盖一定说明什么。** 覆盖率的否定方向是可靠的：覆盖率为 0 的类**没有被任何测试执行过**——这是不需要任何推断的硬事实。因此覆盖率作为**下限告警**合法：新增代码覆盖率低于阈值就拦下合并，是在执行"新代码必须有人执行过它"这条最低纪律。

由此得到质量门的合理形状：盯**增量覆盖率**（本次变更新增/修改行的覆盖率，SonarQube 等平台的 New Code 口径即此）而非存量总覆盖率——存量是老账，增量是每次变更的当场纪律；阈值定在下限量级（常见实践 70%~80% 区间），不为最后几个百分点写扭曲的测试（getter/setter、不可达的防御分支）。

## 变异覆盖：回答"测试能不能抓住缺陷"

覆盖率回答不了的问题，换一个指标能回答：**变异测试**（mutation testing）系统性地给被测代码注入小缺陷（`>` 改 `>=`、条件取反、返回值改 null），每个变异体跑一遍测试套件——测试红了，变异体被"杀死"；测试仍绿，说明这个缺陷溜过了整个套件。**变异覆盖率 = 被杀死的变异体 / 有效变异体总数**，它直接度量测试套件的缺陷检出能力，而不是代码被执行的比例。Java 生态的代表工具是 PIT（PITest）。代价是算力：每个变异体一轮完整测试，成本随代码量线性放大，实践中只对核心模块、在 CI 夜间档跑。

它与行覆盖的连接正好互补：行覆盖是执行的广度，变异覆盖是验证的深度；前者便宜后者贵，前者日常后者抽查——两者各管一维，谁都不能替代谁。
