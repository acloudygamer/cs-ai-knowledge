# 日期时间

> 前置：[02-Stream-API](./02-Stream-API.md) · 后续：[04-正则表达式](./04-正则表达式.md)

> **版本基准**：Java 21 stable / Java 25 latest。java.time 自 Java 8（JSR 310）入场后 API 面基本冻结，本篇内容两个口径通用。示例实测环境：Temurin JDK 25.0.4.1（Windows，系统时区 +08:00），`--release 21` 验证。

`java.time`（JSR 310）是围绕一条物理时间轴和一套人类日历规则建成的**不可变**日期时间模型。它的三个核心类型对应三种不同的时间观：`Instant` 是时间轴上的点（机器视角，秒加纳秒）；`LocalDateTime` 是"挂钟读数"（人类视角，不含时区，不知道自己在时间轴上的哪一点）；`ZonedDateTime` 用 `ZoneId` 的时区规则把挂钟读数钉到时间轴上。三者之间的换算就是整个 API 的主干。

## 为什么重造：Date 与 Calendar 的历史包袱

旧 API 的问题不是设计哲学，是具体的坑，实测可见（Temurin 25.0.4.1，+08:00 时区）：

```text
new Date(124, 0, 15) = Mon Jan 15 00:00:00 HKT 2024   ← 年份减 1900，月份从 0 起
setTime(0) 后          = Thu Jan 01 08:00:00 HKT 1970  ← Date 可变，原地改写
```

`java.util.Date` 名为日期实为毫秒时间戳，年份从 1900 起算、月份从 0 起算（该构造器早已标记废弃）；更要命的是它**可变**——把它传给任何方法都可能被 `setTime` 原地改写，防御性拷贝成为每个 API 的必修课。`Calendar` 修了一部分但继承了可变性，时区处理同样混乱。JSR 310 的答案是釜底抽薪：**所有类型不可变**，`plusDays`、`withZoneSameInstant` 一律返回新实例。不可变带来两个直接收益：天然线程安全（对象不存在中间态），以及可以放心传递引用而不必防御性拷贝。

不可变的收益在格式化器上最直观：`SimpleDateFormat` 因内部可变的日历状态而线程不安全（多线程共享会产出错乱字符串），是旧 API 最著名的陷阱；`DateTimeFormatter` 不可变、无状态，实测 8 个线程共享同一个实例格式化 8 万次，输出只有一种且全部正确：

```text
8 线程共享一个 DateTimeFormatter，不同输出个数: 1
```

## 机制：三种时间观与时区规则

### 时间轴上的点：Instant

`Instant` 内部是 `epochSecond`（long）加 `nano`（int，0~999999999）的二元组，零点是 1970-01-01T00:00:00Z。实测：

```text
Instant.now(): epochSecond=1790441718 nano=285377300
```

两个 `Instant` 之差是 `Duration`——物理时长，秒/纳秒单位，加减乘除都有明确意义。注意 Java 的时间尺度官方说法是 UTC-SLS（把闰秒平滑摊进一天的 UTC 变体），`Instant` 上测不到闰秒——这不是 bug，是刻意选择：民用时间轴上"23:59:60"只制造混乱。

### 挂钟读数与时间轴的钉合：ZonedDateTime

`LocalDateTime` 不含时区，对"两点间隔多久"这类问题无法作答——同一个 `02:30` 在不同时区是不同瞬间，甚至在同一时区可能不存在。钉合由 `ZoneId` 完成，它背后是 JDK 内置的 IANA 时区数据库（每个时区的历史偏移与夏令时规则全集）。实测：

```text
上海: 2024-04-13T20:00+08:00[Asia/Shanghai]
UTC:  2024-04-13T12:00Z[UTC]
同一 Instant? true
不存在的 02:30 被解析为: 2024-03-10T03:30-04:00[America/New_York]
```

`withZoneSameInstant` 保持时间轴上的点不动、只换挂钟读数（上海晚 8 点与 UTC 正午是同一瞬间）；而美国东部 2024-03-10 凌晨 2:30 因时钟拨快根本不存在，`ZonedDateTime.of` 把它顺延到 3:30——时区转换不是固定偏移的加减，是查历史规则表，这正是不能用"自己加 8 小时"代替 `ZoneId` 的原因。

### 两种时长：Duration 与 Period

`Duration` 是物理时长（秒），`Period` 是日历时长（年/月/日三元组），区别在日历的不规则性上显形。实测：

```text
2024-01-31 + Period.ofMonths(1) = 2024-02-29    ← 日历修正到 2 月最后一天（2024 闰年）
跨越美国拨快当天的两个 UTC 瞬间: PT2H            ← Duration 只认物理流逝
```

1 月 31 日加一个月没有"2 月 31 日"，日历规则把它修到 2 月 29 日；而 Duration 不参与这种修正，它就是两个瞬间之间流过的物理时间。规则：**跟人约**用 `LocalDate`/`ZonedDateTime`/`Period`（"下个月今天"、"北京时间下午三点"），**跟机器算**用 `Instant`/`Duration`（超时、间隔、时间戳）。

## 用法边界

- 存数据库、打日志、做超时判断：`Instant` 或 `OffsetDateTime`，不要存本地时间（服务器换时区即数据失真）。
- 用户的"明天上午九点"：`ZonedDateTime` 带 `ZoneId` 存储，跨年跨夏令时都正确。
- 纯日期（生日、账单日）：`LocalDate`，不要动用 `Instant` 去近似。
- 解析与格式化统一走 `DateTimeFormatter`，它是不可变对象，定义成 `static final` 常量全局共享。
