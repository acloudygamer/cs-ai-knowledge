# 错误处理

## 定义

Java 异常机制是基于异常表（Exception Table）的非局部跳转。编译器将 try-catch 块编译为异常表，运行时通过抛出异常触发表查找，跳转到匹配的异常处理器。异常表的查找复杂度为 $O(\log n)$ ，其中 $n$ 为异常处理器数量。 ，其中 $n$ 为异常处理器数量。 为异常处理器数量。

## 数学模型

### 异常表查找

### 受检异常的语义约束

受检异常 (Checked Exception) 是 javac 强制的方法签名约束，JVM 层面不存在。设方法 $m$ 声明抛出类型集 $E$ ： 声明抛出类型集 $E$ ： ：

 $\text{compile-time: } \forall e \in E, \text{caller 必须处理或继续声明}$ 
 $\text{runtime: } \text{JVM 不验证签名，异常可传播到未声明的调用者}$ 

**JVM 层面的异常表结构**：`.class` 文件中存在两类相关但不同的表：

- **ExceptionIndexTable**（异常索引表）：属于 `Exceptions_attribute`，仅用于 javac 编译时验证受检异常的 `throws` 声明。存储形式为 `exception_index_table[]`，每个元素是指向 `CONSTANT_Class_info` 常量池的索引。**JVM 执行时不使用此表**——`athrow` 指令不查此表。
- **Exception Table**（异常表）：属于方法的 `Code_attribute`，是 JVM 执行 `athrow` 时实际查询的表。存储三元组 `(start_pc, end_pc, handler_pc, catch_type)`，其中 `catch_type` 是指向常量池中异常类名的索引（0 表示 finally）。

**StackMapTable 与异常表的区别**：StackMapTable 是类型推断验证 attribute，用于类型检查（Java 6+ strict JVM），与异常处理无关。两者的本质区别：

| 属性 | 用途 | 查找时机 | 查找方式 |
|------|------|----------|----------|
| ExceptionIndexTable | 编译期受检异常校验 | 编译期 | 直接索引常量池 |
| Exception Table | 运行时异常分发 | `athrow` 执行期 | 二分查找三元组 |
| StackMapTable | 类型安全验证 | 字节码验证期 | 帧类型匹配 |

这意味着 `throws IOException` 在字节码中不存在，仅存在于 .class 文件的 `ExceptionIndexTable`（用于 javac 验证）。

**所有权变换**：
- 异常对象从构造者转移到抛出点
- 栈展开时，异常对象作为值沿调用链传递
- 被捕获后，所有权转移给 catch 局部变量
- 若未捕获，异常对象被 JVM 的 uncaught handler 处理

## 机制

### try-with-resources 的抑制异常链

`try-with-resources` 编译后等效为：

```java
Resource r = acquire();
Throwable primary = null;
try {
    use(r);
} catch (Throwable t) {
    primary = t;
    throw t;
} finally {
    if (r != null) {
        Throwable suppressed = null;
        try {
            r.close();
        } catch (Throwable t) {
            suppressed = t;
        }
        if (primary != null) {
            primary.addSuppressed(suppressed);
        } else if (suppressed != null) {
            throw suppressed;
        }
    }
}
```

**执行序列**：
1. `acquire()` → `use()` → `close()`
2. 若 `use()` 抛异常 A，`close()` 抛异常 B → A 被保留，B 被抑制
3. 若 `use()` 正常，`close()` 抛异常 C → C 直接抛出

**try-with-resources 的字节码结构**：编译器将 try-with-resources 编译为 `monenter`/`monitorexit` 指令对，而非简单的 `enter`/`exit`：

```java
// 源代码
try (Resource r = acquire()) {
    use(r);
}
```

编译后的字节码等效结构：
```
aload_0          // 将 this（或Resource引用）压入操作数栈
dup              // 复制引用（enter 需要两个副本）
astore_1         // 存储第一个副本到局部变量 slot 1
monitorenter     // 获取 r 的管程锁 (monenter)
aload_1          // 重新加载 r
aconst_null      // 准备 null 标记
if_acmpeq L0     // 若 r == null，跳过 finally
aload_1          // 加载 r
invokevirtual Resource.close()   // 调用 close()
pop              // 丢弃 close() 返回值
L0:
monitorexit      // 释放管程锁 (monitorexit) — 在正常路径和异常路径均执行
...
Lcatch:
astore_2         // 存储抛出的异常
aload_1          // 加载 r（再次获取引用）
monitorenter     // 重新获取锁（防止异常时锁未释放）
aload_1
invokevirtual Resource.close()
pop
aload_2          // 重新加载异常
athrow           // 重新抛出
Lcatch2:
astore_3         // close() 自身抛出的异常
aload_1          // 加载原始异常
aload_3          // 加载 close() 的异常
invokevirtual Throwable.addSuppressed()  // 抑制 close() 异常
aload_3
athrow           // 抛出原始异常
```

**关键机制**：
- `monenter` 在获取锁成功后立即执行，确保 `use(r)` 期间资源被持有
- `monitorexit` 在正常路径和异常路径**均执行**，通过双重 `monitorenter`/`monitorexit` 配对实现
- 锁的获取/释放与 `close()` 调用交错，确保 close() 执行时仍持有锁（防止竞态）

**约束**：只有通过 `addSuppressed()` 添加的异常才被保留。直接调用 `suppressedExceptions.add()` 无效（该字段是私有副本）。

抑制异常的语义可以用集合代数描述。设 $E_{try}$ 为 try 块抛出的异常集合， $E_{close}$ 为 close() 抛出的异常集合： 为 try 块抛出的异常集合， $E_{close}$ 为 close() 抛出的异常集合： 为 close() 抛出的异常集合：

$$E_{result} = \begin{cases}
E_{try} \cup \text{suppressed}(E_{close}) & E_{try} \neq \emptyset \\
E_{close} & E_{try} = \emptyset
\end{cases}$$

其中 $\text{suppressed}(e)$ 表示将 $e$ 添加到 primary异常的抑制列表，而非作为主异常抛出。这保证了"最重要的异常不被掩盖"的原则。 表示将 $e$ 添加到 primary异常的抑制列表，而非作为主异常抛出。这保证了"最重要的异常不被掩盖"的原则。 添加到 primary异常的抑制列表，而非作为主异常抛出。这保证了"最重要的异常不被掩盖"的原则。

### 异常链的完整性保证

`Throwable.getCause()` 返回构造时传入的原始异常，形成单向链表：

```
ServiceException
  .initCause(IOException)
    .initCause(SocketException)
      .initCause(NullPointerException)  // 根因
```

这个链保留了完整的因果信息。堆栈追踪 (Stack-Walking) 由 JVM 的 `StackTraceElement[]` 构成，在异常构造时冻结。

**为什么用异常链而非字符串**：字符串消息无法保留堆栈结构，且容易被截断或修改。异常链使诊断工具（如 JStack、IDE debugger）能够完整展示错误传播路径。

### 异常设计的约束与违反后果

| 约束 | 违反后果 |
|------|----------|
| finally 中抛异常 | 若 try 块也抛异常，该异常被抑制（try-with-resources 语义）；若 try 块正常，finally 的异常成为主异常 |
| 构造器中抛异常 | 对象构造失败，已分配的子资源不会被自动释放（构造器无法执行 try-with-resources），需显式清理或使用静态工厂方法 |
| 吞掉异常 (`catch { }`) | 调用者无法感知异常发生，数据一致性需依赖其他机制保证 |
| 抛 `RuntimeException` | 调用者无法感知（编译器不强制处理），可能导致未知状态继续执行 |

### 受检异常 vs 非受检异常的设计选择

Java 的受检异常强制调用者显式处理，优点是调用者不会忽略错误，缺点是造成 API 污染。

现代 Java 趋势是使用非受检异常（`RuntimeException` 的子类），理由：
1. 调用者可以通过其他机制（文档、单元测试）保证正确性
2. 函数式风格中受检异常与 `Function<T, R>` 不兼容
3. `throws` 声明在 lambda 中不可用（Java 8）

**版本约束**：Java 8 中 lambda 表达式不能抛出受检异常；Java 9+ 可通过类型声明规避。
