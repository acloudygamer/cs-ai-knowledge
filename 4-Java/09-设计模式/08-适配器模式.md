# 适配器模式

> 前置：[07-装饰器模式](./07-装饰器模式.md) · 后续：[09-责任链模式](./09-责任链模式.md)

> **版本基准**：Java 21 stable / Java 25 latest。示例实测环境：Temurin JDK 25.0.4.1（Windows），`javac -encoding UTF-8 --release 21`。

适配器模式（Adapter）封装的变化点是**接口的形状**：客户端期望接口 $I_T$，已有的实现提供的是接口 $I_A$，两者不匹配又不能改（第三方库、遗留代码），于是在中间插一个适配器做转调。它不增加职责、不控制访问——只做转换，这是它与装饰器、代理的分界线（对照表见 [07-装饰器模式](./07-装饰器模式.md)）。

## 对象适配与类适配

GoF 给了两种结构：

- **对象适配**：适配器**组合**一个被适配者实例，方法体内转调。Java 里唯一常用的形态。
- **类适配**：适配器**继承**被适配者同时实现目标接口。需要多继承——Java 类不支持多继承，这条路只在被适配者是接口时走得通，实际等于退化为"实现两个接口 + 委托"，没有独立存在感。

对象适配的最小形态：

```java
interface Logger { void info(String msg); }        // 客户端期望的接口

class LegacyLogger {                                // 已有实现，接口不匹配
    void log(int level, String msg) { ... }
}

class LoggerAdapter implements Logger {             // 组合 + 转调
    private final LegacyLogger legacy;
    LoggerAdapter(LegacyLogger legacy) { this.legacy = legacy; }
    public void info(String msg) { legacy.log(1, msg); }   // 转换集中在这一行
}
```

连接关系：`Client → LoggerAdapter（实现 Logger）→ 持有 → LegacyLogger`。客户端只见 `Logger`，适配逻辑全部封闭在适配器的方法体里。实测：`[legacy level=1] 服务启动完成`。

## JDK 实例一：Arrays.asList——数组适配成 List 视图

`Arrays.asList(T...)` 返回一个把数组适配成 `List` 接口的对象。它是适配器，且适配得不完全——这恰好演示了适配器的一个重要性质：**适配器可以只实现目标接口的子集**。

实测（Temurin 25.0.4.1，--release 21）：

```text
asList 视图: [a, b, c]
改 list 后原数组: [A, b, c]              // list.set(0, "A") 写穿到底层数组
asList.add 抛异常: UnsupportedOperationException
```

两个行为都是结构决定的：

1. **写穿**：适配器不复制数据，`set()` 直接落在底层数组上——视图与数组是同一存储的两个接口。
2. **`add` 抛异常**：数组长度固定，`List` 的结构修改操作无法实现，适配器以 `UnsupportedOperationException` 显式拒绝。这不是 bug，是接口语义与底层能力不匹配时的诚实声明。

## JDK 实例二：InputStreamReader——字节流适配成字符流

`InputStreamReader` 把 `InputStream`（字节接口）适配为 `Reader`（字符接口），转换工作是按指定字符集解码：

```java
byte[] utf8 = "汉字abc".getBytes("UTF-8");
try (InputStreamReader r = new InputStreamReader(new ByteArrayInputStream(utf8), "UTF-8")) { ... }
```

实测：

```text
字节流适配为字符流读到: 汉字abc
GBK 解码 UTF-8 字节（乱码演示）: 姹夊瓧abc
```

第二行说明适配器的参数（字符集）是转换语义的一部分：适配器不是透明的管道，转换规则错了，输出就是错的。它与上篇的装饰器在同一条 I/O 栈里协作——`InputStreamReader` 管接口转换，`BufferedReader` 管职责叠加，一个栈里两种模式各管一段（见 [01-文件与NIO](../05-IO与外部世界/01-文件与NIO.md)）。

## "空实现适配器"已被 default 方法淘汰

GUI 时代有一种配套写法：接口方法太多，提供一个全空实现的抽象类（如 `MouseAdapter`），用户继承它只重写关心的方法。Java 8 的接口 `default` 方法让这层中间类失去存在理由——接口自己提供默认空实现：

```java
interface Callback {
    default void onStart() {}
    default void onComplete() {}
    default void onError(Exception e) {}
}
```

新写接口时直接给 `default` 空方法，不要再造 `XxxAdapter` 抽象类。这也是总览里"语言特性吃掉模式"的一例。

## 边界

适配器的信号是**接口不匹配且两头都不能改**。两头都归你管时，正确动作是改接口对齐，而不是加适配器——适配器是兼容性债务的容器，每多一层就多一次转调和一份需要维护的映射逻辑。
