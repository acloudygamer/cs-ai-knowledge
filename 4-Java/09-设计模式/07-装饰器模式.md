# 装饰器模式

> 前置：[06-观察者模式](./06-观察者模式.md) · 后续：[08-适配器模式](./08-适配器模式.md)

> **版本基准**：Java 21 stable / Java 25 latest。示例实测环境：Temurin JDK 25.0.4.1（Windows），`javac -encoding UTF-8 --release 21`。

装饰器模式（Decorator）封装的变化点是**对象的附加职责**：给对象包一层同接口的壳，壳在委托前后叠加自己的行为，层数与顺序在运行时决定。约束是继承做不到这件事—— $n$ 个可开关的附加职责用继承枚举需要 $2^n$ 个子类，且组合在编译期写死；装饰器把组合挪到运行时，只需要 $n+1$ 个类。

## 结构：组合 + 同接口

```java
interface Coffee {
    String description();
    double cost();
}

class Espresso implements Coffee {
    public String description() { return "浓缩咖啡"; }
    public double cost() { return 15.0; }
}

abstract class CoffeeDecorator implements Coffee {
    protected final Coffee next;        // 关键：持有同接口的下一层
    CoffeeDecorator(Coffee next) { this.next = next; }
}

class Milk extends CoffeeDecorator {
    Milk(Coffee next) { super(next); }
    public String description() { return next.description() + " + 牛奶"; }  // 委托 + 叠加
    public double cost() { return next.cost() + 3.0; }
}
```

结构上只有一个要点：装饰器**实现与下一层相同的接口**并**持有同接口的引用**。这两条合起来让装饰器对客户端透明——`Coffee` 引用指向的是裸 `Espresso` 还是包了三层的 `Sugar(Milk(...))`，调用方分不出来。调用沿壳逐层委托到底，返回值再逐层叠加回来。

实测组合叠加（Temurin 25.0.4.1，--release 21）：

```text
浓缩咖啡 = 15.0
浓缩咖啡 + 牛奶 = 18.0
浓缩咖啡 + 牛奶 + 糖 = 19.0
```

层数和顺序由 `new Sugar(new Milk(new Espresso()))` 这一行在运行时决定——这就是装饰器存在的全部理由。注意顺序**通常有影响**：`Milk(Sugar(x))` 与 `Sugar(Milk(x))` 的描述串不同；对有副作用的装饰器（日志、计时），顺序决定日志先后与计时口径。只有纯累加型的装饰器（如上面的 `cost()`）恰好满足交换律，别把这个特例当成模式的性质。

## java.io：最著名的装饰器实例

Java I/O 流体系（JDK 1.1，1997）是装饰器模式在 JDK 里最大的落地：`InputStream` 是组件接口，`FileInputStream` 是具体组件（字节从文件来），`FilterInputStream` 的子类全是装饰器——每个只做一件可叠加的事：

```java
try (BufferedReader r = new BufferedReader(        // 装饰：按行读取
        new InputStreamReader(                     // 桥：字节流 → 字符流（见下篇适配器）
            new BufferedInputStream(               // 装饰：8 KB 缓冲，减少系统调用
                new GZIPInputStream(               // 装饰：解压
                    new FileInputStream(path)))))) {  // 组件：字节从磁盘来
    // ...
}
```

数据流向与包装方向相反：字节从 `FileInputStream` 流出，依次穿过解压、缓冲、解码，最终以行的形式到达调用方。每一层只认识下一层的 `InputStream` 接口，不知道也不关心底下是什么。实测同一条栈先写后读：

```text
gzip 文件实际大小: 79 字节（已压缩）
读到: 第一行：装饰器栈写入
读到: 第二行：gzip+缓冲+编码
```

这套设计的约束背景是 I/O 职责的可组合性：缓冲、压缩、加密、解码彼此正交，任何两个都能叠加——继承表达不了正交组合，装饰器能。流体系的性能侧细节（缓冲如何减少系统调用）见 [01-文件与NIO](../05-IO与外部世界/01-文件与NIO.md)。

## 装饰器 vs 代理 vs 适配器

三者都是"包一层"，区分看意图和接口：

| | 装饰器 | 代理 | 适配器 |
|---|---|---|---|
| 意图 | **增加**职责 | **控制**访问 | **转换**接口 |
| 接口 | 与被包装者相同 | 与被代理者相同 | 不同（这正是它的存在理由） |
| 嵌套 | 可任意层叠加 | 通常一层 | 通常一层 |

JDK 动态代理（`java.lang.reflect.Proxy`，见 [05-反射与动态代理](../03-JVM与运行时/05-反射与动态代理.md)）是代理的工业化实现；适配器是下一篇的主题。
