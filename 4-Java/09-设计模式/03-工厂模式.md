# 工厂模式

> 前置：[02-单例模式](./02-单例模式.md) · 后续：[04-建造者模式](./04-建造者模式.md)

> **版本基准**：Java 21 stable / Java 25 latest。示例实测环境：Temurin JDK 25.0.4.1（Windows），`javac -encoding UTF-8 --release 21`。

工厂模式封装的变化点是**实例的类型**：调用方知道"我要一个能 `send()` 的通知器"，但不该知道它 `new` 的是哪个具体类。约束很直白——`new` 会把具体类名焊死在调用点，新增一种产品就得改所有调用点；把 `new` 挪进工厂，调用方只依赖接口。

工厂有三个复杂度递增的形态，选型依据是"变化到底在哪一层"。

## 简单工厂：分支集中在一处

```java
class SimpleFactory {
    static Notification create(String channel) {
        return switch (channel) {
            case "sms" -> new SmsNotification();
            case "email" -> new EmailNotification();
            default -> throw new IllegalArgumentException(channel);
        };
    }
}
```

结构：一个静态方法 + 一个 `switch`。客户端传入渠道名，拿回接口类型。实测输出：

```text
[短信] 验证码 1234
未注册的渠道 push 直接抛异常: push
```

代价写在结构里：所有产品类型的创建逻辑集中在同一个 `switch`，**新增渠道必须修改工厂方法本身**。这就是它与开闭原则（Open-Closed Principle，对扩展开放、对修改关闭）的冲突点——每加一种产品，这个文件就要被动一次。产品种类少且稳定（三五种、一年加不了一个）时这个代价可接受，简单工厂是开销最小的形态。

## 工厂方法：新增产品 = 新增文件

当产品种类持续增长，把 `switch` 拆散：每个产品配一个工厂类，工厂本身抽象为接口。

```java
interface NotificationFactory { Notification create(); }

class SmsFactory implements NotificationFactory {
    public Notification create() { return new SmsNotification(); }
}
class EmailFactory implements NotificationFactory {
    public Notification create() { return new EmailNotification(); }
}
```

客户端持有 `NotificationFactory` 接口，运行时注入哪个工厂决定创建哪种产品：

```text
[邮件] 周报已生成        // NotificationFactory f = new EmailFactory(); f.create().send(...)
```

对比简单工厂，变化的副作用从"修改 `switch`"变成"新增两个文件（产品类 + 工厂类）"，已有代码一行不动。代价是类的数量翻倍：每种产品两个类。产品种类多、迭代快时这笔账划算。

## 抽象工厂：约束是产品族的兼容性

抽象工厂（Abstract Factory）与工厂方法的区别不在复杂度而在约束：**同一工厂产出的多个产品必须来自同一族**。典型场景是跨平台 UI——`WindowsFactory` 产出的按钮和文本框都是 Windows 风格，不能与 `MacFactory` 的混用：

```java
interface GUIFactory {
    Button createButton();
    TextField createTextField();
}
```

`WindowsFactory` 与 `MacFactory` 各自实现全部方法，族的一致性由"客户端只持有一个工厂实例"这个结构保证——想混风格都拿不到另一个族的入口。JDK 里 `javax.xml.parsers.DocumentBuilderFactory` 是真实实例：`newDocumentBuilder()` 返回的解析器族由系统属性决定，客户端全程不见具体类。

适用判据：存在"必须成套使用"的对象族（UI 组件、数据库连接 + 语句、平台相关实现）。没有族的概念时用它只会得到一堆单方法的工厂接口——那是工厂方法的地盘。

## Lambda 注册表：工厂从"类"退化为"函数"

Java 8 之后，工厂接口若只有一个方法，整个工厂层可以压缩成一个 `Map<String, Supplier<T>>`：

```java
Map<String, Supplier<Notification>> registry = Map.of(
    "sms", SmsNotification::new,
    "email", EmailNotification::new
);
Notification n = registry.get("email").get();
```

实测输出：`[邮件] 会议提醒`。

工厂方法模式里"每产品一个工厂类"的骨架消失了——`SmsFactory` 这类只含一行 `new` 的类被一个方法引用取代。这是总览里说的"语言特性吃掉模式"的典型案例：策略/工厂这类"一个方法换一个行为"的模式，函数式接口是其最小表达。注册表换成可变的 `HashMap` 还能支持运行时注册新产品，比类加载扫描便宜。

## 与 DI 容器的关系

一句话：Spring 的 IoC 容器（见 [01-Spring核心](../08-生态与框架/01-Spring核心.md)）是工厂模式的工业化形态——对象创建逻辑集中到外部的容器配置与组件扫描中，工厂注册表由框架维护，调用方通过注入拿接口。写业务代码时绝大多数"工厂"已被容器接管；手写工厂的主场退到容器之外：静态工具方法（`List.of`、`Optional.of`）、JDK 风格的服务提供者加载、以及创建逻辑本身带业务规则的场景。

## 选型对照

| 场景 | 形态 | 理由 |
|---|---|---|
| 种类少且稳定 | 简单工厂 | 一个 `switch` 换最少的类 |
| 种类持续增长 | 工厂方法 / Lambda 注册表 | 新增 = 新文件，不动旧代码 |
| 产品必须成套 | 抽象工厂 | 族一致性由结构保证 |
| 在 Spring 内 | 容器注入 | 工厂已由框架承担 |
