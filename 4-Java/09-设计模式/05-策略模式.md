# 策略模式

> 前置：[04-建造者模式](./04-建造者模式.md) · 后续：[06-观察者模式](./06-观察者模式.md)

> **版本基准**：Java 21 stable / Java 25 latest。示例实测环境：Temurin JDK 25.0.4.1（Windows），`javac -encoding UTF-8 --release 21`。

策略模式（Strategy）封装的变化点是**算法**：把一族可互换的算法各自封装，让它们可以互相替换，且替换算法的决定权在使用方而不在算法内部。它在 Java 里有一个更常用的名字——**行为参数化**：`sort(list, comparator)` 的第二个参数就是策略。

本篇的重点是这个模式在 Java 里的三段演化：类 → Lambda → 模式匹配，每一段都有 JDK 特性在背后支撑。

## 经典形态：策略是接口，实现是类

```java
interface DiscountStrategy { double apply(double price); }

class VipDiscount implements DiscountStrategy {
    public double apply(double price) { return price * 0.8; }
}

class Checkout {
    private final DiscountStrategy strategy;
    Checkout(DiscountStrategy strategy) { this.strategy = strategy; }
    double pay(double price) { return strategy.apply(price); }   // 委托给策略
}
```

结构只有一层连接：`Checkout` 持有接口引用，运行时注入哪个实现决定走哪个算法。对比 `if (vip) ... else if (coupon) ...` 的分支写法，收益是新增算法时 `Checkout` 一行不改——分支集中在注入点而不是使用点。

## Lambda 形态：策略从"类"退化为"函数"

策略接口只有一个抽象方法，它就是函数式接口（[08-Lambda与函数式接口](../01-语言核心/08-Lambda与函数式接口.md)）。Java 8 起，一行 Lambda 取代一个策略类：

```java
DiscountStrategy halfOff = p -> p * 0.5;   // 不需要 halfOff 类
```

同一个 demo 的三种策略实测对比（Temurin 25.0.4.1，--release 21）：

```text
VIP 类策略: 80.0            // new Checkout(new VipDiscount())
优惠券类策略: 80.0          // new Checkout(new CouponDiscount())
Lambda 半价策略: 50.0       // new Checkout(p -> p * 0.5)
```

JDK 自己就是最大的策略用户：`Comparator` 是典型的策略接口，且自带组合器——策略可以像函数一样拼装：

```java
names.sort(Comparator.comparing(String::length)
                     .thenComparing(String.CASE_INSENSITIVE_ORDER));
// 实测输出：Comparator 组合策略排序: [al, Bob, Charlie]
```

`comparing(...).thenComparing(...)` 这种链式组合是类形态策略做不到的——类之间的组合得再写一个组合器类。判据：**策略无状态、单方法时用 Lambda；策略要带配置字段或多个协作方法时才回到类**。

## 第三种形态：sealed + 模式匹配

当"算法按数据类型分派"时，Java 21 转正的 switch 模式匹配（JEP 441）提供了不经过接口的分派方式——数据是 sealed 层级，算法集中在一个 switch 里：

```java
sealed interface Member permits Normal, Vip, SuperVip {}
record Normal() implements Member {}
record Vip() implements Member {}
record SuperVip() implements Member {}

static double discount(Member m, double price) {
    return switch (m) {
        case Normal n -> price;
        case Vip v -> price * 0.9;
        case SuperVip s -> price * 0.7;   // 少一个分支，编译器报错
    };
}
```

实测：`模式匹配 SuperVip: 70.0`、`模式匹配 Normal: 100.0`。

与接口形态的分工是两种扩展方向的取舍（表达式问题，expression problem）：

- **接口 + 实现类**：加新类型容易（新文件），加新操作难（改所有实现类）。
- **sealed + switch**：加新操作容易（新写一个 switch），加新类型编译器会标出所有没覆盖的 switch——这在类型集合封闭（如语法树节点、支付渠道枚举）时反而成了优点：遗漏分支在编译期暴露而不是运行期。

访问者模式（Visitor）在 Java 21 的生存空间主要被这条路径压缩：访问者解决的就是"类型封闭、操作开放"，而 sealed + switch 用语言机制直接给了答案，还免掉了 accept/visit 的双重分派样板。

## 与状态模式的边界

两者类图几乎一样（Context 持有一个接口引用），区分看切换的决定权：

- **策略**：换算法由外部决定（客户端注入、配置项指定），策略之间互不知道对方存在。
- **状态**：换行为由对象内部状态驱动（`TCP连接` 的 `ESTABLISHED → CLOSED`），状态对象自己决定后继状态。

一句话：切换逻辑在外是策略，在内是状态。本目录不展开状态模式，其复杂度与策略同构。
