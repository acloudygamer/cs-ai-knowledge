# 建造者模式

> 前置：[03-工厂模式](./03-工厂模式.md) · 后续：[05-策略模式](./05-策略模式.md)

> **版本基准**：Java 21 stable / Java 25 latest。示例实测环境：Temurin JDK 25.0.4.1（Windows），`javac -encoding UTF-8 --release 21`。

建造者模式（Builder）封装的变化点是**构造的参数组合**：必填与可选参数分离，可选参数逐个设置、最后一次性产出对象。它回应的约束是 Java 没有具名参数、没有可选参数——`new User("张三", null, 30, null)` 这种调用里每个参数的含义只能靠位置猜。

## 层叠构造器：建造者要消灭的东西

给每个参数组合写一个重载构造器，叫层叠构造器（Telescoping Constructor）：

```java
class TelescopingUser {
    TelescopingUser(String name) { this(name, null); }
    TelescopingUser(String name, String email) { this(name, email, 0); }
    TelescopingUser(String name, String email, int age) { this(name, email, age, null); }
    TelescopingUser(String name, String email, int age, String city) { ... }
}
```

问题随可选参数数 $k$ 增长：要覆盖全部组合需要 $2^k$ 个重载（10 个可选参数是 1024 个），实际只写常用子集，于是调用方被迫在"传 `null` 占位"和"找不到合适重载"之间选。即便重载存在，`new TelescopingUser("张三", null, 30)` 里 `null` 是哪个字段、`30` 是年龄还是别的，读代码时必须跳回签名确认——参数没有名字，这是 Java 语言层面的缺口，不是写代码的人懒。

## 手写 Builder：必填进构造器，可选走链式

```java
class User {
    final String name;    // 必填
    final String email;   // 可选
    final int age;        // 可选
    final String city;    // 可选

    private User(Builder b) {
        this.name = b.name; this.email = b.email;
        this.age = b.age; this.city = b.city;
    }

    public static Builder builder(String name) { return new Builder(name); }

    public static class Builder {
        private final String name;                  // 必填参数锁死在构造器
        private String email;
        private int age;
        private String city = "未填写";

        Builder(String name) { this.name = Objects.requireNonNull(name); }

        public Builder email(String email) { this.email = email; return this; }
        public Builder age(int age) {
            if (age < 0) throw new IllegalArgumentException("age 不能为负: " + age);
            this.age = age; return this;
        }
        public Builder city(String city) { this.city = city; return this; }
        public User build() { return new User(this); }
    }
}
```

结构上三个要点，各自回答一个真实问题：

1. **必填参数进 `Builder` 构造器**：`builder(name)` 里漏掉必填项在编译期就报错，而不是拖到运行期 `build()` 才炸。
2. **每个 setter 返回 `this`**：链式调用让每个可选参数自带名字——`age(28)` 比位置参数可读，设置顺序自由。
3. **`build()` 一次性产出不可变对象**：Builder 本身可变、可复用；产出的 `User` 全字段 `final`、无 setter。校验集中在 setter 或 `build()`，非法状态在产出前拦截。

实测（Temurin 25.0.4.1，--release 21）：

```text
telescoping: name=张三, age=30
User{name=李四, email=null, age=28, city=杭州}
Builder 校验拦截: age 不能为负: -1
```

## Lombok @Builder：同一件事的编译期生成

手写 Builder 的机械部分（私有字段、返回 `this` 的 setter、`build()`）可以由 Lombok 的 `@Builder` 注解在编译期生成，字节码与手写等价：

```java
@Builder
class User {
    private final String name;
    private final String email;
    private final int age;
}
```

代价是引入一个编译期注解处理器依赖，且生成的 Builder 默认把必填校验留给手写（`@NonNull` 标注或自定义 `build()`）。团队已用 Lombok 就用它；不愿意引入依赖，上面二十行手写代码就是全部成本。

## record 时代的定位

record（Java 14/15 预览、16 转正，见 [10-现代语言特性](../01-语言核心/10-现代语言特性.md)）吃掉建造者的一部分地盘：**参数少、全必填的对象**不再需要 Builder——

```java
record Point(int x, int y) {}
```

`new Point(3, 4)` 的调用点只有两三个参数，位置语义一目了然，record 连不可变性、equals/hashCode 一起给了。实测输出：`Point[x=3, y=4]`。

record 的紧凑构造器还能承担 `build()` 里的校验职责，必填性由编译器（少一个参数就编译失败）保证：

```java
record Range(int from, int to) {
    Range { if (from > to) throw new IllegalArgumentException("from > to"); }
}
```

实测：`new Range(10, 1)` 抛出 `record 紧凑构造器校验: from > to`。

剩下的才是建造者的主场：**可选参数多**（record 要求全给齐，可选参数得传 `null`，退回层叠构造器的老问题）、**构造过程分步**（如 `HttpRequest.Builder` 逐行加 header）、**同一构造过程产出不同表示**（GoF 的原始定义场景）。JDK 里的真实实例：`StringBuilder`（逐步追加、一次产出 `String`）、`java.net.http.HttpRequest.Builder`、`Stream.Builder`。
