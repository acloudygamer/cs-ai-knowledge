# 责任链模式

> 前置：[08-适配器模式](./08-适配器模式.md) · 后续：[07-SpringSecurity](../08-生态与框架/07-SpringSecurity.md)（过滤器链的工业级实例）

> **版本基准**：Java 21 stable / Java 25 latest。示例实测环境：Temurin JDK 25.0.4.1（Windows），`javac -encoding UTF-8 --release 21`。

责任链模式（Chain of Responsibility）封装的变化点是**处理器序列**：一个请求该由哪些处理器、按什么顺序过一遍，在运行时组装。发送方不点名接收方，请求沿链传递，每个处理器自己决定处理、放行还是拦截。

## 两种传递语义

责任链有两个子形态，区分看每个处理器做完之后链是否继续：

| | 选择性传递 | 全部通过（过滤器式） |
|---|---|---|
| 语义 | 第一个能处理的处理器处理后，链终止 | 每个处理器都执行自己的一段，然后放行 |
| 终止方式 | 被处理，或走到链尾 | 某处理器**拒绝调用** `proceed()`，或走到链尾 |
| 典型场景 | 审批流（谁有权批谁处理）、异常处理 | Servlet Filter、日志/监控切面 |

选择性传递是 GoF 教科书形态；Java 生态里真正的主场是第二种——过滤器式，工业实例见下文。

## 实测：过滤器式链的逐级传递

用 Lambda 当处理器（每个处理器就是"一段逻辑 + 是否放行"的决策），链用一个游标实现：

```java
record Request(String path, String user, String body) {}

interface Handler { void handle(Request req, Chain chain); }
interface Chain { void proceed(Request req); }

class HandlerChain implements Chain {
    private final List<Handler> handlers;
    private int index = 0;
    HandlerChain(List<Handler> handlers) { this.handlers = handlers; }

    public void proceed(Request req) {
        if (index >= handlers.size()) {
            System.out.println("    -> 到达链尾：业务处理 " + req.path());
            return;
        }
        handlers.get(index++).handle(req, this);   // 当前处理器决定是否再调 proceed
    }
}
```

三个处理器——日志（全放行）、认证（可拦截）、参数校验（可拦截）——组链后实测三种请求的传递路径（Temurin 25.0.4.1，--release 21）：

```text
=== 请求 1：正常请求 ===
[日志] 进入: /api/order
[认证] 用户 alice 通过
[校验] 通过
    -> 到达链尾：业务处理 /api/order
[日志] 离开: /api/order

=== 请求 2：未登录 ===
[日志] 进入: /api/order
[认证] 未登录，拦截（不调用 proceed）
[日志] 离开: /api/order

=== 请求 3：空请求体 ===
[日志] 进入: /api/order
[认证] 用户 alice 通过
[校验] 请求体为空，拦截
[日志] 离开: /api/order
```

输出里有三个结构性事实：

1. **嵌套调用栈**：`proceed()` 不是循环而是递归——请求 1 里 `[日志] 离开` 出现在业务处理**之后**，因为日志处理器的 `proceed()` 调用包住了整条后续链。请求在栈深处被处理，响应沿栈逐层返回。每个处理器因此天然拥有"前置 + 后置"两个时机。
2. **拦截 = 不调 `proceed()`**：请求 2 的认证处理器直接返回，链在栈上原地解开——校验和业务层根本没执行，但日志的"离开"照常打印（它在外层）。
3. **顺序即语义**：把认证放到日志后面，日志记录的就是未认证请求；过滤器链的顺序是配置的一部分，不是实现细节。

## 工业级实例：Servlet Filter 与 Spring Security

Servlet 规范（Jakarta EE）的 `Filter`/`FilterChain` 就是上面结构的标准化版本，接口签名几乎逐字对应：

```java
public interface Filter {
    void doFilter(ServletRequest req, ServletResponse res, FilterChain chain);
}
```

`chain.doFilter(req, res)` 就是上文的 `proceed()`。Servlet 容器按 `web.xml`/注解声明的顺序组装链，请求在到达 Servlet 之前穿过全部过滤器。

Spring Security 把这条链做到了工业强度：整个认证授权体系是一条约十几个过滤器组成的 `SecurityFilterChain`——上下文持久化、登出、用户名密码认证、匿名认证、会话管理、异常转换、授权拦截各是一个过滤器，**顺序错误就是安全漏洞**（比如授权过滤器跑到认证前面）。完整展开见 [07-SpringSecurity](../08-生态与框架/07-SpringSecurity.md)。

## 边界

责任链的代价藏在它的优点里：发送方不知道谁处理了请求，意味着**请求无人处理时默认静默落到链尾**——上面的实现只是打印一行，生产代码里"消息被吞了"会成为排查噩梦。对策是链尾加一个兜底的拒绝处理器（显式报错），而不是让请求无声消失。另外链长本身是线性开销： $n$ 个处理器 $O(n)$ 的逐层传递，好在 $n$ 通常在十几个以内，这不是真实瓶颈。
