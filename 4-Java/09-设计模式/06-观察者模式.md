# 观察者模式

> 前置：[05-策略模式](./05-策略模式.md) · 后续：[07-装饰器模式](./07-装饰器模式.md)

> **版本基准**：Java 21 stable / Java 25 latest。示例实测环境：Temurin JDK 25.0.4.1（Windows），`javac -encoding UTF-8 --release 21`。

观察者模式（Observer）封装的变化点是**通知对象集合**：一个对象（主题，Subject）状态变化时，要通知哪些对象（观察者）在运行时才确定，且集合会增删。结构是主题持有一个监听器列表，变化时遍历回调——订阅关系的建立和拆除都发生在运行时，这正是它没被语言特性吃掉的原因。

## 推模型与拉模型

通知发生时，数据怎么到观察者手里，有两种结构：

| | 推模型（Push） | 拉模型（Pull） |
|---|---|---|
| 数据流向 | 主题把变化的数据作为参数推给观察者 | 主题只发"我变了"的信号，观察者回主题上取 |
| 耦合 | 观察者依赖主题的推送协议（参数形状） | 观察者依赖主题的查询接口 |
| 多余数据 | 推了观察者不一定需要的数据 | 观察者只取需要的，但可能多次查询 |

推模型的典型是 GUI 事件（事件对象连同坐标、按键一起推过来）；拉模型的典型是 MVC 里视图收到通知后回模型查数据。选哪个取决于一笔账：推送的数据量 vs 观察者的查询次数。数据小且所有观察者都要——推；数据大且各取所需——拉。

实测推模型（两个订阅者收到同一条消息）：

```text
手机 App 收到: Java 25 发布
网页端收到: Java 25 发布
```

## Java 内置 Observer/Observable：已废弃

JDK 1.0 就带了 `java.util.Observable`/`Observer`，**Java 9 起被标记 `@Deprecated`**。实测核实（Temurin 25.0.4.1）：

```java
Deprecated d = Observable.class.getAnnotation(Deprecated.class);
// 输出：Observable @Deprecated since = 9, forRemoval = false
```

注意 `forRemoval = false`：截至 Java 25 只是"不建议使用"，并未宣布删除，但也没有任何理由在新代码里用它。废弃的原因写在它的类型形状里：

1. `Observable` 是**类**不是接口——Java 单继承，继承了它就不能继承别的。
2. `setChanged()` 是 `protected`——状态变化的触发权只能交给子类，外部无法组合使用。
3. 观察者列表的并发处理、通知顺序均无规范约束，线程安全要自己补。

## 替代一：PropertyChangeSupport

JDK 内置的可用替代是 JavaBeans 体系的 `java.beans.PropertyChangeSupport`——组合而非继承，线程安全（内部用 `CopyOnWriteArrayList` 风格的快照迭代），且事件自带**属性名 + 旧值 + 新值**：

```java
class TemperatureSensor {
    private final PropertyChangeSupport support = new PropertyChangeSupport(this);
    private double celsius;

    void addListener(PropertyChangeListener l) { support.addPropertyChangeListener(l); }

    void setCelsius(double newValue) {
        double old = this.celsius;
        this.celsius = newValue;
        support.firePropertyChange("celsius", old, newValue);
    }
}
```

实测（Temurin 25.0.4.1，--release 21）：

```text
监控告警: celsius 从 0.0 变为 36.5
监控告警: celsius 从 36.5 变为 39.2
值未变化时不触发通知（上一条监听器无输出）
```

最后一行展示 `firePropertyChange` 的一个内置机制：新旧值非空且 `equals` 相等时不触发通知（JDK 源码的判据是 `oldValue == null || newValue == null || !oldValue.equals(newValue)`，因此双 `null` 反而会触发），免掉了每个监听器自己去重。这是"属性变化"场景下开箱即用的观察者基础设施。

## 替代二：Reactive Streams

当"通知"变成**异步、持续、有流速控制**的数据流时，观察者模式的简单回调结构不够用了——快速生产者会压垮慢消费者。Java 9 的 `java.util.concurrent.Flow`（Reactive Streams 规范在 JDK 的落地）在观察者的"订阅-通知"上加了一层**背压**（backpressure）：订阅者通过 `request(n)` 主动声明处理能力，发布者按量推送。这已是响应式编程的范畴，完整展开见 [10-响应式编程](../08-生态与框架/10-响应式编程.md)。

一句话区分三者的适用面：

- 同进程、少量监听器、状态变化不频繁 → 手写回调列表或 `PropertyChangeSupport`。
- 异步流、流量需要控制、跨线程 → Reactive Streams（`Flow`/Reactor）。
- 跨进程 → 消息中间件（Kafka，见 [04-Kafka](../08-生态与框架/04-Kafka.md)），那已经是发布-订阅拓扑，不是本模式。

## 两个工程陷阱

**通知顺序不可依赖。** 遍历监听器列表的顺序在并发注册下无保证，业务逻辑若依赖"A 先于 B 收到通知"，那是时序耦合——该用显式的调用链而不是观察者。

**不取消订阅 = 内存泄漏。** 主题持有观察者的强引用，主题活得比观察者久时，观察者永远无法被 GC 回收。Swing 时代这是经典泄漏源；对策是成对出现 `add/remove`，或主题侧用弱引用持有观察者。
