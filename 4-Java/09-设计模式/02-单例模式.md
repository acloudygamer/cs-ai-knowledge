# 单例模式

> 前置：[01-设计模式总览](./01-设计模式总览.md) · 后续：[03-工厂模式](./03-工厂模式.md)

> **版本基准**：Java 21 stable / Java 25 latest。示例实测环境：Temurin JDK 25.0.4.1（Windows），`javac -encoding UTF-8 --release 21`。

单例模式（Singleton）封装的变化点是**实例数量**：把一个类的实例数压到恰好一个，并提供全局访问点。它回应的约束是真实存在的——某些对象复制出第二份就是错的：全局配置、线程池、硬件端口句柄。

这篇不写"单例是什么"的第八种讲法，只回答三个工程问题：哪种实现扛得住攻击，DCL（双重检查锁定）为什么必须有 `volatile`，以及单例的代价是什么。

## 三种实现与各自的防线

| 实现 | 懒加载 | 线程安全来源 | 抗反射攻击 | 抗反序列化 |
|---|---|---|---|---|
| 饿汉式（`static final` 字段） | 否 | JVM 类初始化锁 | 否 | 需 `readResolve` |
| 静态内部类（Holder） | 是 | JVM 类初始化锁 | 否 | 需 `readResolve` |
| 枚举 | 否（首次主动使用时） | JVM 类初始化锁 | **是（JVM 级）** | **是（JVM 级）** |

三者的线程安全都建立在同一块地基上：JVMS §5.5 规定类初始化阶段由 JVM 获取该 `Class` 对象的初始化锁，`<clinit>` 方法互斥执行——多线程同时触发初始化时只有一个线程真正执行（机制细节见 [01-字节码与类加载](../03-JVM与运行时/01-字节码与类加载.md)）。区别只在初始化时机与两条攻击路径上的防御。

### 枚举单例：为什么是最优解

```java
public enum Singleton {
    INSTANCE;
    public String greet() { return "hello from enum singleton"; }
}
```

枚举实例是 `Singleton` 类的 `static final` 字段，初始化由 JVM 类初始化锁保护。关键在于 JVM 为枚举堵死了两条绕过构造器私有化的攻击路径，实测（Temurin 25.0.4.1，--release 21）：

```text
反射攻击枚举: IllegalArgumentException - Cannot reflectively create enum objects
枚举反序列化后仍是同一实例: true
Holder 单例反序列化后仍是同一实例: false
```

1. **反射**：`Constructor.newInstance()` 在实例化前检查 `Modifier.ENUM` 标志，枚举类型直接抛 `IllegalArgumentException`。私有构造器防得住 `new`，防不住 `setAccessible(true)`——枚举由 JVM 在反射入口拦截，手写类做不到。
2. **反序列化**：`ObjectInputStream` 读到枚举类型时走专用分支，直接按名字查 `Enum.valueOf()` 返回已有实例，根本不经过"分配新对象"的流程。普通类（如上面实测的 Holder 写法）即使构造器私有，反序列化也会通过 JVM 内部通道造出第二个实例，除非手写 `readResolve()` 把新对象替换成已有实例。

Joshua Bloch 在《Effective Java》（第 3 版，条目 3）的结论至今成立：**单元素枚举是实现单例的最佳方式**——不是因为写法短，而是因为唯一性约束由 JVM 而不是程序员守护。

### 静态内部类（Holder）：需要懒加载时的首选

枚举的代价是失去懒加载之外的灵活性（不能继承、实例集合固定）。需要懒加载时用 Holder 写法：

```java
public class Singleton {
    private Singleton() {}
    private static class Holder {
        static final Singleton INSTANCE = new Singleton();
    }
    public static Singleton getInstance() { return Holder.INSTANCE; }
}
```

惰性来自 JVM 的类初始化规则：类只在**首次主动使用**时初始化，`Holder` 类在首次执行 `Holder.INSTANCE` 时才触发初始化。实测在 `<clinit>` 里埋打印：

```text
-- 访问 Singleton2 类但未触发 Holder --
-- 现在调用 getInstance --
[clinit] LazySingleton 类初始化
[clinit] Holder 类初始化（实例在此创建）
```

外层类初始化时 `Holder` 并未初始化，实例的创建时机被推迟到第一次 `getInstance()`，而线程安全仍由 JVM 类初始化锁兜底——不加锁、无 `volatile`，是开销最低的懒加载写法。

## DCL 与 volatile：JMM 层面的必要性

双重检查锁定（Double-Checked Locking）是另一种懒加载写法，历史上（Java 5 之前）它是坏的——问题出在对象创建不是原子操作：

```java
public class Singleton {
    private static volatile Singleton instance;  // volatile 不可省略
    private Singleton() {}

    public static Singleton getInstance() {
        if (instance == null) {                    // 第一次检查：读
            synchronized (Singleton.class) {
                if (instance == null) {            // 第二次检查：写
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}
```

`instance = new Singleton()` 编译后是三步：分配内存 → 执行构造器初始化字段 → 把引用写入 `instance`。JMM（Java 内存模型）允许 JIT 与 CPU 对无依赖的指令重排，步骤可能变成 分配 → 写引用 → 初始化。此时另一个线程在第一次检查处读到非 null 引用，拿到的却是**字段尚未初始化的对象**（字段全是零值）。

`volatile` 的作用是建立 happens-before 边：JLS 17.4.5 规定对 volatile 变量的写 happens-before 后续对同一变量的读，且 volatile 写之前的所有普通写（构造器里的字段初始化）随之对读者可见。少了它，两次检查之间没有任何同步边，第二次检查的"非 null"不能保证"已构造完"。JMM 的重排规则与 happens-before 的完整定义见 [04-Java内存模型](../03-JVM与运行时/04-Java内存模型.md)。

DCL 的价值只剩一个场景：实例创建本身需要参数或步骤、无法放进 `<clinit>`。无参懒加载请用 Holder，免掉这层心智负担。

## 代价与边界

单例的约束是"恰好一个实例"，这个约束在三种情况下失效，使用前先核对：

- **多类加载器**：唯一性的作用域是"每个 `Class` 对象"，同一个类被两个类加载器加载就有两个单例。OSGi、某些容器环境下这不是理论问题。
- **测试**：单例持全局可变状态后，测试之间互相污染，且无法在不重启 JVM 的情况下重置。这是单例被称为"全局变量的马甲"的原因。
- **生命周期**：实例何时创建（饿汉/懒加载）、何时销毁（实际上永不）都不归你管，与依赖注入容器的作用域管理冲突。Spring 里的"singleton"是容器作用域而非本模式——每容器一个，允许多个容器实例。

判断标准：唯一性是**业务约束**（两份状态会出错的，如硬件句柄），用单例；只是"碰巧只用一份"的，交给 DI 容器管理作用域。

## 参考实现

```java
// 首选：枚举单例
public enum Singleton {
    INSTANCE;
    public void doWork() { /* 业务方法 */ }
}

// 需要懒加载：静态内部类
public class Singleton {
    private Singleton() {}
    private static class Holder {
        static final Singleton INSTANCE = new Singleton();
    }
    public static Singleton getInstance() { return Holder.INSTANCE; }
}

// 手写类 + Serializable 时必须的补丁
public class Singleton implements java.io.Serializable {
    private static final Singleton INSTANCE = new Singleton();
    private Singleton() {}
    public static Singleton getInstance() { return INSTANCE; }
    private Object readResolve() { return INSTANCE; }  // 反序列化时替换新对象
}
```
