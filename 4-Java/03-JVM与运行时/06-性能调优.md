# 性能调优

> 前置：[05-反射与动态代理](./05-反射与动态代理.md) · 后续：[04-并发编程](../04-并发编程/01-线程模型与同步.md)

> **版本基准**：Java 21 stable / Java 25 latest。示例实测环境：Temurin JDK 25.0.4.1（Windows x64，12 核），`--release 21` 验证。

Java 的性能结构是"先冷后热"：字节码先解释执行保证零等待启动，热点代码再由 JIT（Just-In-Time）逐层编译为机器码——这是 [01-Java全景](../00-概览/01-Java全景.md) 里"启动与峰值分两笔账"的展开。本篇讲三层内容：JIT 把字节码变成机器码的机制（分层编译、内联、逃逸分析），以及观察这一切的工具链（jcmd、JFR）。调优的第一原理只有一句：**先测量，再动手**——JIT 的存在让"看代码猜热点"的命中率极低。

## 分层编译：从解释器到 C2

HotSpot 的执行引擎是四级流水线：解释器（0 级）立即执行；方法调用计数与循环回边计数过阈值后依次升档——C1 编译（1~3 级，快编译，3 级带完整 profiling 埋点）再到 C2（4 级，慢编译、激进优化）。阈值实测（PrintFlagsFinal）：`CompileThreshold = 10000`，分层口径下 `Tier3CompileThreshold = 2000`、`Tier4CompileThreshold = 15000`。

实测（`-XX:+PrintCompilation`，一个循环 2 万次调用的热点方法）：

```text
33   11       3       HotMethod::work (24 bytes)     ← 33ms 时升到 C1 带 profiling（3 级）
33   12 %     4       HotMethod::work @ 4 (24 bytes) ← % = OSR：循环还在跑，直接换编译版
34   13       4       HotMethod::work (24 bytes)     ← C2 版（4 级）
36   11       3       HotMethod::work (24 bytes)   made not entrant: not used
                                                       ↑ C2 版接管后 C1 版退役
```

`@ 4` 是 **OSR**（On-Stack Replacement）：方法还没返回，循环体本身已被替换为编译版——热点循环不必等下次调用才提速。`made not entrant` 则是代码缓存的淘汰机制：旧编译版被废弃，字节码入口改指新机器码。

## C2 的两个激进优化

**内联（Inlining）** 是一切后续优化的前提：把小方法体嵌进调用点，消除调用开销只是小头，大头是让跨方法的常量传播、死代码消除成为可能。门槛实测：`MaxInlineSize = 35`（字节码超过 35 字节的方法默认不内联）、`C1MaxInlineSize = 35`。"热点方法保持短小"这一军规的机制出处就在这里——不是因为调用开销本身，而是因为大方法断了内联链，连带后面一串优化全部失效。

**逃逸分析（Escape Analysis）** 判断对象的作用域是否逃出方法/线程；不逃逸的对象可以**标量替换**——拆解成几个栈上标量，堆分配整个消失（连锁收益：无 GC 压力、字段访问变寄存器访问）。`DoEscapeAnalysis` 与 `EliminateAllocations` 实测默认开启。效果实测（1 亿次循环每次 `new Point{int,int}`）：

```text
-Xint（纯解释，无 JIT）: 分配 2,400,000,000 字节（= 1 亿 × 24 字节，布局见 02-内存区域与对象）
默认（C2 热身后）:       分配 0 字节
```

循环里的对象分配在编译版里整个不存在——这就是"循环里 new 对象"在现代 JVM 上经常没有账面成本的机制，前提是这个对象真的不逃逸（逃逸了就是真分配，账本回到 [03-垃圾回收](./03-垃圾回收.md)）。

## 工具链：先测量

HotSpot 自带三套测量手段，均实测可用：

**jcmd**——对运行中的进程发诊断命令（`jcmd -l` 列进程）：

```text
$ jcmd 19792 GC.heap_info
garbage-first heap  total reserved 262144K, committed 262144K, used 64150K
 region size 1024K, 2 young (2048K), 0 survivors (0K)
$ jcmd 19792 VM.uptime        → 2.985 s
$ jcmd 19792 Thread.print     → 11 个线程的状态与栈
```

**JFR**（Java Flight Recorder）——低开销的持续事件记录（生产环境可用，开销设计目标 1% 量级）。`-XX:StartFlightRecording=filename=perf.jfr` 启动即录，`jfr summary perf.jfr` 查看：

```text
jdk.BooleanFlag                 493   ← JVM 标志快照
jdk.Deoptimization               11   ← 反优化事件：假设被证伪，机器码回退解释
jdk.ThreadAllocationStatistics   28   ← 线程分配速率
...
```

`jdk.Deoptimization` 值得单独说：JIT 的激进优化都建立在运行时假设上（"这个调用点只见过这一种类型"、"这个分支不会走"），假设被新数据证伪时机器码作废、回退解释执行——反优化风暴（大量代码反复编译-作废）是"越跑越慢"类问题的机制，JFR 里直接可见。

**GC 日志**——`-Xlog:gc*`（统一日志框架，Java 9 起），样例见 [03-垃圾回收](./03-垃圾回收.md)。

## 方法论收口

性能问题的定位顺序：JFR/GC 日志定位瓶颈层（CPU？GC 停顿？锁竞争？）→ `-XX:+PrintCompilation` 与反优化事件确认 JIT 行为 → 最小改动、复测。代码层的常见杠杆：减少分配速率（GC 压力的直接来源）、保持热点方法可内联、并发瓶颈用 JMM 语义正确的无锁结构（[04-Java内存模型](./04-Java内存模型.md)）。并行的天花板由 Amdahl 定律钉死：串行部分占比 $F$ 时，加速比上限是 $1/F$ 与核数无关——5% 串行则 20 倍封顶，加核之前先砍串行段。
