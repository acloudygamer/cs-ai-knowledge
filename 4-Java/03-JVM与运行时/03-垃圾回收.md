# 垃圾回收

> 前置：[02-内存区域与对象](./02-内存区域与对象.md) · 后续：[04-Java内存模型](./04-Java内存模型.md)

> **版本基准**：Java 21 stable / Java 25 latest。示例实测环境：Temurin JDK 25.0.4.1（Windows x64，12 核，`-Xmx256m`），`--release 21` 验证。

垃圾回收（GC）回答一个问题：堆上哪个对象死了、内存归谁。Java 的判死标准是**可达性**：从 GC Roots（栈帧里的局部变量引用、静态字段、JNI 引用等）出发沿引用链走，走不到的对象即死。回收策略的分野不在"怎么找死对象"，而在**停顿时间**与**吞吐量**的账本怎么算——所有收集器都是这笔账的不同解。

## 分代假设：GC 设计的地基

经验事实（弱分代假设）：绝大多数对象朝生夕灭，活过几次回收的对象倾向于一直活下去。由此堆分两块：对象生在**新生代**（Eden + 两个 Survivor），熬过若干次回收的晋升**老年代**。新生代对象多、死得快，用**复制算法**（把少数存活者拷到 Survivor，剩下的整片丢弃——成本正比于存活量而非垃圾量）；老年代对象少、死得慢，用**标记-整理**或增量回收。假设被违反（例如大缓存对象批量进入新生代）时 Survivor 装不下存活者，对象被迫提前晋升，老年代加速填满，Full GC 频率上升——这是"缓存撑爆堆"类事故的机制。

## G1：默认收集器

G1（Garbage-First）自 Java 9 起是默认收集器（PrintFlagsFinal 实测 `UseG1GC = true`，`MaxGCPauseMillis = 200` 为默认停顿目标）。它把堆切成等大 **Region**（大小按堆自适应：默认约 4 GB 堆下 PrintFlagsFinal 报 `G1HeapRegionSize = 2097152` 即 2MB；`-Xmx256m` 下 jcmd `GC.heap_info` 报 `region size 1024K`），不再物理分代而是逻辑分代：每个 Region 扮演 Eden/Survivor/Old 角色。回收时按"回收性价比"选一组 Region（Collection Set），把存活对象复制走、整 Region 腾空。跨 Region 引用由 **Remembered Set** 记录，回收时不必全堆扫描根。

实测（Temurin 25.0.4.1，`-Xmx256m -Xlog:gc*`，每轮分配 1MB 即弃的垃圾，周期留 1MB 存活）：

```text
[0.383s] GC(0) Pause Young (Concurrent Start) (G1 Humongous Allocation) 114M->3M(256M) 11.251ms
[0.657s] GC(2) Pause Full (System.gc()) 98M->7M(34M) 7.054ms
[0.683s] GC(3) Pause Young (G1 Humongous Allocation) 13M->7M(34M) 0.910ms
```

两点可读：1MB 的 `byte[]` 在 1MB Region 的堆里属于 **Humongous 对象**（超过 Region 一半即绕开新生代常规路径，见 [02-内存区域与对象](./02-内存区域与对象.md)），直接触发 Young GC；`System.gc()` 触发的 Full GC 把堆从 98M 压到 7M、顺带把堆缩到 34M——G1 会归还内存给 OS。

## ZGC 与 Shenandoah：低暂停路线

G1 的复制阶段仍是 STW（Stop-The-World，暂停全部应用线程），堆越大复制越多，停顿随存活量增长。ZGC 与 Shenandoah 的目标是把停顿与堆大小**解耦**——标记、整理、对象搬移全部与应用线程并发执行，STW 只剩毫秒级以下的根扫描与同步点。实现手段不同：

- **ZGC**（JDK 15 正式，JEP 377）：**着色指针**——64 位引用的高位存标记位（Marked0/Marked1/Remapped），对象是否已搬移编码在引用自身而非对象头；应用线程每次读引用经过**读屏障**（load barrier）检查着色位，遇到旧地址就地转发。代价是依赖 64 位地址空间与**多重映射**（multi-mapping：同一物理内存同时映射到三个着色位不同的虚拟视图，着色位即视图选择）。分代化演进：Java 21 引入分代 ZGC（JEP 439），Java 23 起分代模式为默认（JEP 474），Java 24 移除旧的非分代模式（JEP 490）——JDK 25 实测 `PrintFlagsFinal` 已无 `ZGenerational` 开关，分代是唯一形态。
- **Shenandoah**（OpenJDK 项目，Oracle JDK 不搭载，Temurin 等发行版有）：**加载引用屏障**（Load Reference Barrier，JDK 13 起的现行形态）——应用线程每次读引用都过一道屏障，检查对象 Mark Word 里的转发标记；对象已被搬移时，屏障从 Mark Word 编码中解出新地址、就地转发。早期的 Brooks Pointer 方案（对象头常驻一个转发指针、每对象多 8 字节、读操作恒多一次间接）已随这次改造移除，代价形态随之改变：不再付每对象 8 字节，而是读路径常驻一次屏障检查。

实测两个收集器在 Temurin 25.0.4.1 上都可用：

```text
-XX:+UseZGC:          [0.017s] Using The Z Garbage Collector
                      GC(2) Major Collection (Warmup) 78M(30%)->10M(4%) 0.003s
-XX:+UseShenandoahGC: [0.009s] Using Shenandoah
```

官方口径（JEP 439/474 与 OpenJDK ZGC 页面，典型值非实测）：ZGC 停顿目标亚毫秒级且不随堆大小增长，堆上限 16TB。选型规则：堆几 GB 以内、追求吞吐与简单——默认 G1 即可；堆数十 GB 以上或延迟敏感（交易、实时服务）——ZGC/Shenandoah。

## System.gc() 的语义

`System.gc()` 是**建议**，不是命令：规范只说 JVM 应"尽最大努力"回收，HotSpot 默认确实触发一次 Full GC（上面日志里的 `Pause Full (System.gc())` 即实证），但 `-XX:+DisableExplicitGC` 可让调用变成空操作——依赖 `System.gc()` 控内存的代码在这个开关下静默失效，反之框架里乱调 `System.gc()` 的库可以被这个开关一键无害化。真正的内存治理手段是堆大小、收集器选择与分配速率控制，不是手动触发回收。

## 引用强度：可达性的四个档位

`java.lang.ref` 把"被引用"细分为四档，给缓存与资源清理留了活口：强引用（默认，到不了即死）；软引用（`SoftReference`，堆要满才回收——堆敏感缓存）；弱引用（`WeakReference`，下一次 GC 即回收——`WeakHashMap` 的键）；虚引用（`PhantomReference`，只用于跟踪回收事件，配合 `ReferenceQueue` 做堆外资源清理，`Cleaner` 即建于其上）。finalize() 自 Java 9 废弃、Java 18 标记移除——资源释放的正确姿势是 try-with-resources 加 `Cleaner` 兜底。
