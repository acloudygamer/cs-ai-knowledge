# Java 内存模型

> 前置：[03-垃圾回收](./03-垃圾回收.md) · 后续：[05-反射与动态代理](./05-反射与动态代理.md)、[04-并发编程](../04-并发编程/01-线程模型与同步.md)

> **版本基准**：Java 21 stable / Java 25 latest。JMM 的规则自 Java 5（JSR 133）定型后未变，两个口径通用。示例实测环境：Temurin JDK 25.0.4.1（Windows x64，12 核）。

Java 内存模型（JMM，JLS 17.4）回答一个多线程的元问题：**一个线程的写，另一个线程何时能看见、按什么顺序看见**。它存在的根源是两层重排与缓存：编译器和 CPU 为了性能会重排指令（只要单线程语义不变），多核 CPU 的每核缓存让"写入主存"与"其他核可见"之间没有天然同步。JMM 不禁止这些优化，而是给出一套规则：**合法的执行结果集合**是什么，以及程序员用什么手段把不合法的结果排除掉。它是 [04-并发编程](../04-并发编程/01-线程模型与同步.md) 全部同步工具（`synchronized`、`volatile`、JUC）的语义地基。

## 问题实测：可见性失败与丢失更新

没有同步的跨线程通信不是"偶尔错"，是"保证错"。两个经典失败均可复现（Temurin 25.0.4.1）：

**可见性失败**——读线程自旋等一个非 `volatile` 标志位，写线程 1 秒后写入：

```text
main 已写 stop=true，等待 reader……
reader 仍在自旋——没有看到 stop=true（可见性失败）
```

JIT 把 `while (!stop)` 里的读取提升出循环（循环不变量外提），读线程永远等不到。这不是时序运气，是合法的优化——JMM 允许它，因为程序没有建立任何跨线程的序。

**丢失更新**——8 线程各执行 10 万次 `i++`（读-改-写三步，非原子）：

```text
期望值:        800000
plain:         395823        ← 无同步：更新大量丢失
volatile:      399927        ← volatile 管可见性，不管原子性
AtomicInteger: 800000        ← CAS 才保证读-改-写原子
```

`volatile` 那行是本篇最重要的实测结论之一：**它修好了"看不见"，修不了"丢更新"**。

## happens-before：JMM 给程序员的唯一工具

JMM 的核心关系是 **happens-before**（HB）：若操作 A happens-before 操作 B，则 A 的结果对 B 可见，且 A 在序上排在 B 前。它不是"时间上先发生"，而是"结果必须可见"的偏序——JMM 允许一切不违反 HB 的重排。程序的正确性论证全部归结为：我关心的两个操作之间有没有 HB 链。HB 由 JLS 17.4.5 逐条枚举，常用的五条：

1. **程序次序**：同一线程内，书写在前的操作 happens-before 书写在后的。
2. **监视器锁**：对同一锁的 unlock happens-before 后续所有 lock——`synchronized` 的可见性保证即此。
3. **volatile**：对同一 volatile 变量的写 happens-before 后续所有读。
4. **线程启动与终止**：`thread.start()` 之前的操作 happens-before 该线程内的一切；线程内的一切 happens-before 其他线程从它的 `join()` 返回。
5. **传递性**：A→B 且 B→C 则 A→C——HB 链靠这条拼接。

上面两个失败例套用此框架立即可判：`while(!stop)` 里写 `stop=true` 与读 `stop` 之间没有任何 HB 边（无锁、无 volatile），可见性无保证；`plain++` 的三步之间对别的线程同样无 HB，读到中间态合法。修复方式就是把对应规则接上：标志位加 `volatile`（规则 3），计数用锁（规则 2）或 `AtomicInteger`（CAS 的 HB 由 `java.util.concurrent.atomic` 包文档单独承诺）。

## volatile 的语义边界

`volatile` 读/写各带一对隐式屏障，合起来交付两样东西：**可见性**（写对其他线程的读立即可见）与**有序性**（写之前的操作不许排到写之后，读之后的不许排到读之前——禁止与邻近访问重排）。它明确**不**交付的：复合操作的原子性（上面 399927 那行）。另一个经典落点是双重检查锁：`instance` 字段必须 `volatile`，否则其他线程可能读到"引用已写、对象未构造完"的中间态——构造逃逸正是有序性缺位的症状。

## final 的安全发布

`final` 字段在 JMM 里有专门条款（JLS 17.5）：构造函数里对 `final` 字段的写入带一个 **freeze 动作**，happens-before 构造函数返回；只要 `this` 引用没有在构造期间逃逸，**任何**线程拿到该对象引用后，不加同步也能看到 `final` 字段的正确值。这是不可变对象（`String`、`Integer`、`java.time` 全家，见 [03-日期时间](../02-标准库/03-日期时间.md)）天然线程安全的规范依据——它们的字段全 final，发布即冻结。两个边界必须同时成立才有效：

- 只对 `final` 字段本身保证；`final` 引用指向的可变对象内部不享受此待遇。
- `this` 在构造函数里逃逸（注册监听器、启动线程、存入静态集合）则冻结失效——这是"构造函数里别启动线程"这一军规的规范出处。
