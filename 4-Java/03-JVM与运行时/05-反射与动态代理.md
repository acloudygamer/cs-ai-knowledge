# 反射与动态代理

> 前置：[04-Java内存模型](./04-Java内存模型.md) · 后续：[06-性能调优](./06-性能调优.md)

> **版本基准**：Java 21 stable / Java 25 latest。示例实测环境：Temurin JDK 25.0.4.1（Windows），`--release 21` 验证。

反射（Reflection）是程序在**运行时**检查与操作自身结构的能力：类加载后每个类在 JVM 里有一个 `Class` 对象（见 [01-字节码与类加载](./01-字节码与类加载.md)），反射 API 就是围绕它读取字段、方法、构造器元数据并调用它们。动态代理是在运行时生成"实现一组接口、把所有调用转发给一个处理器"的代理类。两者合起来是 Java 框架层（Spring DI、ORM 映射、RPC 桩）的地基：编译期不知道的类型与方法，运行期现场查、现场调。注解是这套体系的元数据来源，本身归 [09-注解](../01-语言核心/09-注解.md) 一篇，本篇只用其结论：反射是 `RUNTIME` 保留级注解的唯一消费者。

## 反射：入口、边界与代价

入口有三个：`obj.getClass()`（已有实例）、`Foo.class`（类字面量，加载但不初始化）、`Class.forName("...")`（加载并初始化——区别见 [01-字节码与类加载](./01-字节码与类加载.md) 的初始化时机实测）。拿到 `Class` 后，`getMethod`/`getDeclaredField` 系列查元数据，`Method.invoke`/`Field.get` 执行访问。

**边界一：模块系统的封装**。Java 9 起 JDK 内部字段不再默认可反射。实测（Temurin 25.0.4.1，试图打开 `ArrayList.elementData`）：

```text
java.lang.reflect.InaccessibleObjectException:
  Unable to make field ... accessible: module java.base does not "opens java.util" to unnamed module
```

绕过方式是启动参数 `--add-opens java.base/java.util=ALL-UNNAMED`（本篇 [01-集合框架](../02-标准库/01-集合框架.md) 的 ArrayList 扩容实测就用了它）。这不是建议日常这么做的意思——它是给框架与诊断工具的逃生门；业务代码撞这堵墙，正确的反应是换公共 API。

**边界二：JIT 优化受阻**。反射调用的目标运行时才知道，`Method.invoke` 的参数还要装箱进 `Object[]`——内联与逃逸分析都难以穿透（这两样优化的收益见 [06-性能调优](./06-性能调优.md)）。JVM 的缓解是**膨胀机制**：反射调用前若干次走 native 入口，超过阈值后动态生成一个字节码调用器（GeneratedMethodAccessor）顶替，让 JIT 能看到真实调用目标。热路径上的反射仍应缓存 `Method` 句柄并考虑 `MethodHandle`（ invokedynamic 的直连形态，JIT 可内联，`java.lang.invoke` 包）替代。

## 动态代理：调用拦截的运行时编织

`Proxy.newProxyInstance(loader, interfaces, handler)` 在运行时生成一个类：实现给定的全部接口，每个方法体只有一件事——调用 `InvocationHandler.invoke(this, method, args)`。实测：

```text
代理类名: jdk.proxy1.$Proxy0
拦截到调用: size
proxy.size() = 3
```

调用链因此从"调用方→目标对象"变成"调用方→代理→handler→目标对象"，handler 在转发前后可以织入任意横切逻辑（日志、事务、权限、远程调用）——这是 AOP 与 RPC 客户端桩的机制原形。

**约束：只能代理接口**。生成类继承 `java.lang.reflect.Proxy`（Java 单继承，父类名额已占）并实现指定接口，所以目标必须面向接口。要代理类（无接口）需第三方字节码工具（Byte Buddy、CGLIB），它们走"继承目标类、重写方法"路线，代价是代理不了 `final` 方法与 `final` 类——`final` 的不可覆写性在 [05-面向对象](../01-语言核心/05-面向对象.md) 的语言层定义，在这里变成框架层的真实边界。性能上 JDK 代理与字节码继承代理在现代 JVM 上差距不大，选型主要看目标是否有接口、是否介意第三方依赖。
