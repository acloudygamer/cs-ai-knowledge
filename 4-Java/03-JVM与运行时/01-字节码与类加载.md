# 字节码与类加载

> 前置：[01-Java全景](../00-概览/01-Java全景.md)、[02-标准库](../02-标准库/01-集合框架.md) · 后续：[02-内存区域与对象](./02-内存区域与对象.md)

> **版本基准**：Java 21 stable / Java 25 latest。示例实测环境：Temurin JDK 25.0.4.1（Windows），`--release 21` 验证。

字节码是 JVM 的指令集：每条指令一个字节操作码加零到几个操作数，操作数走**操作数栈**而非寄存器（零地址架构）。类加载是把 `.class` 字节流变成 JVM 内 `Class` 对象的过程，分加载、验证、准备、解析、初始化五步，由分层委托的类加载器完成。两者一起构成 [01-Java全景](../00-概览/01-Java全景.md) 里"执行链"的中间段：javac 的产物从这里进入 JVM。

## class 文件：字节码的容器

一份 6 行的演示源码经 `javac --release 21` 编译后，`javap -v` 看到的头部信息（实测）：

```text
minor version: 0
major version: 65              ← 65 = Java 21（Java 25 为 69）
this_class: #16                // BytecodeDemo
super_class: #2                // java/lang/Object
```

主体是**常量池**——类的符号数据中心，字符串字面量、类/字段/方法的符号引用全在这里编号集中存放：

```text
Constant pool:
   #7 = String             #8   // hello, jvm
   #9 = Fieldref   #10.#11      // java/lang/System.out:Ljava/io/PrintStream;
  #15 = Methodref  #16.#17      // BytecodeDemo.add:(II)I
  #21 = InvokeDynamic #0:#22    // makeConcatWithConstants:(...)Ljava/lang/String;
```

字节码指令里的 `#9`、`#15` 就是常量池编号——指令只带索引，符号实体集中管理，这是 class 文件紧凑的原因之一。`#21` 的 `invokedynamic` 值得注意：字符串拼接 `"..." + add(1,2)` 在现代 Java 里编译为 `makeConcatWithConstants` 引导方法（JEP 280，Java 9 起），运行时才决定拼接策略，而不是老式的 `StringBuilder` 指令序列。

## 指令集：栈式虚拟机实测

`static int add(int a, int b) { return a + b; }` 的字节码（`javap -c` 实测）：

```text
static int add(int, int);
  0: iload_0      // 局部变量槽 0（参数 a）压入操作数栈
  1: iload_1      // 槽 1（参数 b）压栈
  2: iadd         // 弹出两个 int，相加，结果压栈
  3: ireturn      // 栈顶 int 作为返回值弹给调用者
```

每条指令的输入输出都在栈顶，指令本身不带地址——这是"零地址架构"的含义。选栈式而非寄存器式，是 1995 年的移植性约束：目标机器的寄存器数量与约定千差万别，而栈模型对任何 CPU 都能简单映射。代价是同一段计算需要更多条指令（load/store 占了大头），这个亏空由 JIT 在编译为机器码时抹平（见 [06-性能调优](./06-性能调优.md)）。

每个方法的栈帧大小（局部变量表槽数、操作数栈最大深度）在**编译时**确定并写入 class 文件——这是栈内存可以精确预算的前提，也是 `StackOverflowError` 可预测的原因。实测（Temurin 25.0.4.1，单线程递归，每帧一个 `int`）：

```text
默认栈大小:   StackOverflowError，递归深度 = 22826
-Xss256k:     StackOverflowError，递归深度 = 3495
```

## 类加载：五步流水线与触发时机

```text
加载 → 验证 → 准备 → 解析 → 初始化
读字节流   魔数/语义  静态字段   符号引用→直接引用   执行 <clinit>
建Class    校验       置默认值    （可延迟到首用）     （恰好一次）
```

初始化的触发时机是规范的硬约束（JLS 12.4.1：首次主动使用时初始化，且恰好一次），实测三种"看起来都会碰类"的操作结果不同：

```text
1. 读取编译期常量 Holder.X（不应触发 <clinit>）: 42     ← 常量编译期内联，类都没初始化
2. Holder.class 字面量（加载但不初始化）                ← 无输出
3. Class.forName("...Holder")                           ← Holder <clinit> 执行
4. 读取 Holder.y: 7（<clinit> 只执行一次）
```

"<clinit> 恰好执行一次"由 JVM 对类初始化加锁保证——这正是"类加载器 + 静态字段"能实现线程安全单例的机制基础。

## 类加载器：分层与双亲委派

Java 9 模块化之后是三层（Java 8 及以前的 Extension ClassLoader 已被 Platform ClassLoader 取代）：

| 类加载器 | 管辖 | 实测加载来源 |
|---|---|---|
| Bootstrap（JVM 内实现） | `java.base` 核心类库 | `java.lang.Object source: shared objects file`（CDS 归档） |
| Platform | 平台模块（`java.sql` 等） | jrt:/ 虚拟文件系统 |
| Application（系统） | classpath/模块路径上的应用类 | `BytecodeDemo source: file:/C:/.../java-test/` |

加载一个类时先问父加载器"你加载过吗"，逐级上溯到顶，都不行才自己加载——**双亲委派**。"双亲"是翻译遗留，实际只有单父。它的收益是**唯一性**：`java.lang.String` 永远由 Bootstrap 加载，用户 classpath 上同名伪造类不会顶替它，核心 API 不可篡改；同时同一类不会重复加载（类的身份 = 全限定名 + 加载它的类加载器，两个加载器加载的同名类互不兼容——这是自定义加载器场景 `ClassCastException` 的经典来源）。

打破委派的合法场景存在（SPI 的线程上下文类加载器、模块层的 `ServiceLoader`），但都是框架级机制，业务代码不需要碰。
