# 监控与链路追踪

## 定义

可观测性（Observability）的本质是通过 **日志（Logs）**、**指标（Metrics）** 和 **链路追踪（Traces）** 三个维度重建分布式系统的内部状态。这三者分别回答：
- 日志："**发生了什么**"（离散事件）
- 指标："**表现如何**"（聚合数值）
- 链路追踪："**在哪一步出了问题**"（请求路径）

**核心价值**：
- **根因分析**：快速定位故障点
- **性能优化**：发现瓶颈和异常
- **容量规划**：趋势分析和预测
- **SLA 保障**：量化服务质量

## 数学模型

### 百分位数的统计学定义

对于延迟集合 $L = \{l_1, l_2, \ldots, l_n\}$，从小到大排序后，第 $p$ 百分位 $P_p$ 定义为：

$$P_p = l_{\lceil n \cdot p \rceil}$$

| 百分位 | 含义 | 告警场景 |
|-------|------|---------|
| P50（中位数） | 50% 请求低于此值 | 基准延迟 |
| P95 | 95% 请求低于此值 | 用户体验分界 |
| P99 | 99% 请求低于此值 | 异常检测 |
| P999 | 99.9% 请求低于此值 | SLA 保障 |

**P99 告警 vs P50 告警**：P50 反映整体分布，P99 反映尾部延迟。两者都高说明系统整体慢；P50 低但 P99 高说明存在少数极慢请求。

### 直方图与百分位数的关系

直方图将延迟范围划分为桶（bucket），统计落入每个桶的请求数：

```
Bucket:  [0-10ms) [10-50ms) [50-100ms) [100-500ms) [500ms+)
Count:   1000      5000       3000        800         200
Cum%:    10%       60%        90%         98%         100%
```

Prometheus 的 `histogram_quantile(0.99, rate(http_request_duration_bucket[5m]))` 从直方图估算 P99。

**直方图估算的误差界**：设桶宽为 $w$，真实 P99 位于某桶 $[b_l, b_u)$ 内，则：
$$\text{估算误差} \leq w$$

桶越细，估算越准确。

### 链路追踪的.span 树结构

Trace 是有根的 **.span 有向无环图（DAG）**：
- 根 Span（Root）：整个请求的入口
- 子 Span：各服务/操作单元
- Parent-Child 关系形成调用树

设 Span $s$ 的子 Span 集合为 $\text{children}(s)$，则：
$$|\text{children}(s)| \geq 0$$
$$\text{depth}(s) = \text{depth}(\text{parent}(s)) + 1$$

最大深度 = 请求经过的服务数（调用栈深度）。

### 指标的时间序列存储模型

时序数据库存储：(timestamp, labels, value) 三元组：

$$D = \{(t_i, l_i, v_i)\}$$

PromQL 查询转换为标签过滤 + 时间对齐：
$$\text{rate}(X[\text{window}]) = \frac{X_{t_2} - X_{t_1}}{t_2 - t_1}$$

## 机制

### RED 指标的计算模型

| 指标 | 公式 | 单位 |
|------|------|------|
| Rate | $\text{count} / \Delta t$ | 请求/秒 |
| Errors | $\text{error\_count} / \text{total\_count}$ | 百分比 |
| Duration (P99) | $\text{histogram\_quantile}(0.99, \text{bucket})$ | 毫秒 |

### USE 指标的形式化定义

USE（Utilization-Saturation-Errors）方法用于分析资源瓶颈：

| 维度 | 定义 | 公式 | 告警阈值 |
|------|------|------|---------|
| Utilization（利用率） | 资源繁忙时间占比 | $U = T_{\text{busy}} / T_{\text{total}}$ | $> 80\%$ |
| Saturation（饱和度） | 等待队列长度 | $Q = \text{queue\_length}$ | $> 0$ |
| Errors | 错误计数 | $E = \sum \text{error\_count}$ | $> 0$ |

**Saturation 的具体度量**：
- CPU Saturation：运行队列长度 $\text{runq.len} > 0$ 持续时间
- 内存 Saturation：换页率 $\text{pgscanned} > 0$
- I/O Saturation：IO 队列长度 $\text{io\_queue\_len} > 0$

**综合瓶颈指数**：
$$\text{Bottleneck} = \max(U_{\text{CPU}}, U_{\text{Memory}}, U_{\text{Disk}}, U_{\text{Network}})$$

当 $\text{Bottleneck} > 0.8$ 或 $\text{Saturation} > 0$ 时，系统存在资源瓶颈。

### Micrometer 的指标抽象

Micrometer 是 **门面模式（Facade Pattern）** 的应用——提供统一 API，底层可对接多种监控系统：

```java
// 代码只依赖 Micrometer
MeterRegistry registry = ...; // 注入，底层可能是 Prometheus/DataDog/OTLP

// 创建指标（与具体监控系统解耦）
Counter counter = registry.counter("orders.created");
Timer timer = registry.timer("payment.process");

// 使用
counter.increment();
timer.record(() -> processPayment());
```

**约束条件**：不同监控系统对指标类型的支持不同。Micrometer 在内部做兼容转换，如 DataDog 不直接支持 Timer 的百分位数，需要通过直方图模拟。

### Trace 传播的上下文注入

TraceId 在 HTTP Header 中传播，遵循 W3C Trace Context 标准：

```
traceparent: 00-0af7651916cd43dd8448eb211c80319c-b7ad6b7169203331-01
              ││                               │               │
              ││                               │               └─ trace-flags
              ││                               └─ span-id (当前操作)
              │└─ trace-id (全局唯一)
              └─ version
```

**传播协议**：每个微服务在接收请求时提取 Header 中的 trace-id 和 span-id，创建新 span 时将 trace-id 透传，span-id 作为新 span 的 parent-id。

### 健康检查与 Kubernetes 探针

| 探针 | 失败后果 | 适用场景 |
|------|---------|---------|
| livenessProbe | kubelet **重启**容器 | 进程僵死、无响应 |
| readinessProbe | 从 Service **摘除** | 启动中、过载、依赖不可用 |
| startupProbe | 禁用 liveness + readiness 直到成功 | 启动极慢的应用 |

**约束条件**：
- `livenessProbe` 不应检查外部依赖（否则依赖故障 → 重启 → 仍故障 → 无限重启）
- `readinessProbe` 应该检查所有必要依赖（否则未就绪实例接收流量 → 请求失败）

### 日志级别的数学阈值

日志级别定义了消息严重性的离散阈值：

| 级别 | 数值 | 触发条件 |
|------|------|---------|
| TRACE | 0 | 细粒度调试信息 |
| DEBUG | 1 | 开发调试信息 |
| INFO | 2 | 一般信息 |
| WARN | 3 | 警告（潜在问题） |
| ERROR | 4 | 错误（需要关注） |
| FATAL | 5 | 致命（系统不可恢复） |

**过滤表达式**：日志系统只输出级别 $\geq$ 阈值的日志。

## 参考存根

```java
// 展示 Micrometer 指标埋点
@Service
public class OrderService {
    private final MeterRegistry registry;
    private final Counter orderCounter;
    private final Timer orderTimer;

    public OrderService(MeterRegistry registry) {
        this.registry = registry;

        // 计数器：订单创建数
        this.orderCounter = Counter.builder("orders.created")
            .tag("service", "order-service")
            .description("Total orders created")
            .register(registry);

        // 计时器：订单处理延迟（含百分位数）
        this.orderTimer = Timer.builder("order.process")
            .publishPercentiles(0.5, 0.95, 0.99) // P50/P95/P99
            .publishPercentileHistogram() // 用于 histogram_quantile
            .register(registry);
    }

    public void createOrder(OrderRequest request) {
        orderCounter.increment();
        orderTimer.record(() -> {
            // 业务逻辑
        });
    }
}

// 展示链路追踪的 Span 管理
@Service
public class PaymentService {
    private final Tracer tracer;

    public PaymentResult pay(Order order) {
        Span span = tracer.nextSpan()
            .name("payment.process")
            .tag("order.id", order.getId().toString())
            .start();

        try (Tracer.SpanInScope scope = tracer.withSpanInScope(span)) {
            return doPay(order);
        } catch (Exception e) {
            span.error(e);
            throw e;
        } finally {
            span.end();
        }
    }
}
```

## 深度：APM 的采样策略与偏差分析

### 采样率的偏差问题

若采用简单随机采样 $p$：
- 采样率 $p$ 下，观测到的延迟分布可能与真实分布有偏差
- 慢请求更可能被采样（因为持续时间长）
- 导致高估平均延迟

**采样偏差的数学描述**：设请求持续时间为 $t$，被采样的概率与 $t$ 成正比：
$$P(\text{sampled} | t) \propto t$$

因此观测到的延迟分布是真实分布的加权版本：
$$\hat{f}(t) = \frac{t \cdot f(t)}{\int_0^\infty t \cdot f(t) dt}$$

### 尾部采样策略

尾部采样（Tail-based Sampling）优先采样慢请求：
1. 等待请求完成
2. 若延迟 > 阈值，采样
3. 保留上下文用于根因分析

**自适应采样**：
$$p(t) = \min\left(p_{\text{max}}, \frac{p_{\text{base}}}{\text{rate}(t)}\right)$$

高峰期降低采样率，低峰期提高采样率，保证采样开销可控。

### 指标聚合的误差传播

分布式追踪中，多个节点的 span 聚合为 trace 指标：

$$\text{trace.latency} = \sum_{\text{span} \in \text{trace}} \text{span.duration}$$

若采样不均匀，聚合结果会存在系统性偏差。需要偏差校正算法来修正。

### 可观测性的信息论视角

可观测性的核心是**信息增益**——从 Logs/Metrics/Traces 中获取关于系统状态的信息量。

设系统状态空间为 $S$，观测空间为 $O$，则可观测性定义为：
$$\text{Observability}(S, O) = I(S; O)$$

其中 $I$ 是互信息（Mutual Information）。当 $I(S; O)$ 足够大时，可以通过观测推断系统内部状态。

**三大支柱的信息互补性**：
- Logs：离散事件，高熵，擅长异常检测
- Metrics：聚合数值，低熵，擅长趋势分析
- Traces：因果链，中熵，擅长根因定位

三者结合才能完整覆盖可观测性空间。
