# 前端框架入门

> **版本基准**: React 18+ / Vue 3.4+ / Angular 17+ (stable) | React 19+ / Vue 3.5+ / Angular 18+ (latest)

## 定义

前端框架是封装了 DOM 操作与状态管理的 JavaScript 库，使开发者以声明式替代命令式 UI 编程。

---

# React 入门

> React 是 Facebook 推出的声明式 UI 库，核心机制是**虚拟 DOM 差异比对**与**组件状态驱动渲染**。

## 定义

React 的本质是一个**有限状态自动机**：给定当前状态（props + state）和新输入（用户事件/服务器响应），React 计算并输出下一帧 UI 描述（React Element 树），再由运行时将其映射为最小 DOM 操作序列。组件函数是状态到 UI 的纯函数映射，React 运行时负责在这个映射过程中插入高效的 DOM 更新。

---

## 数学模型

### 虚拟 DOM diff 复杂度

React 的 diff 算法将两棵树的比较问题从 $O(N^3)$ 降至 $O(N)$，通过两个假设实现：

1. **不同类型的元素产生不同的树**：若元素类型不同，React 假设整棵子树无需比较，直接替换。
2. **同层同级节点可用 key 标识稳定性**：若子元素列表在同层位置变化（增/删/移动），可通过 key 推断哪些节点实际改变。

设树高为 $h$，最坏情况下需要遍历所有节点，时间复杂度 $O(N)$，其中 $N$ 为总节点数。

**归约终点**：diff 的实质是**最小编辑距离问题在约束条件下的近似解**，通过启发式规则将 $O(N^3)$ 降为 $O(N)$。

### 调度模型

React 15 的协调（reconciliation）是同步的——若组件树极深，一次状态更新可能阻塞主线程数十毫秒。React 16 引入 **Fiber 架构**，将协调工作拆为多个最小工作单元（Fiber node），每单元完成后可中断、恢复，实现**增量渲染**。

**时间片模型**：每个工作单元有预算（约 5ms），用 `requestIdleCallback`（或 React 自己实现的 scheduler）在浏览器空闲时继续。未完成则推迟到下一帧。

## 数据流

<pre>
用户交互 / 事件触发
        │
        ▼
组件 dispatch 状态更新
   setState(newState)
        │
        ▼
React 创建新的 React Element 树
   { type: Component, props: {...}, children: [...] }
        │
        ▼
[Reconciliation / Fiber 协调]
  1. 构建 Fiber 链表（虚拟 DOM 的链表表示）
  2. 标记 WorkFlags（Placement, Update, Deletion...）
  3. 调度优先级排序
        │
        ▼
[Commit 阶段]
  遍历所有含 flags 的 Fiber，
  执行 DOM 操作（createElement / removeChild / appendChild）
</pre>

**数据形态变换**：
- `props/state`（普通 JS 值）→ `React Element`（JS 对象，字面量描述 UI）
- `React Element 树`（虚拟 DOM）→ `Fiber 链表`（运行时内部结构，含 child/sibling/return 指针）
- `Fiber` 上的 `WorkFlags` → `实际 DOM 操作`

**所有权流转**：props 不可变（React 保证），组件内部 state 在 `setState` 后立即变为旧值，Fiber 树由 React 运行时持有。

## 机制

### 虚拟 DOM 的本质

直接操作真实 DOM 代价高昂：每次 `.innerHTML` 赋值触发浏览器的**解析 + 样式计算 + 布局 + 绘制**，且无法增量——即使只改一个属性，浏览器也需重排/重绘整个区域。

虚拟 DOM 将"描述 UI"与"应用 UI"解耦。React 比较新旧虚拟 DOM 树（diff），计算出**最小操作集**，再批量执行 DOM API（`appendChild`、`removeChild`、`setAttribute` 等）。单次 diff 的结果可能产生多次 DOM 操作，但这些操作会在 commit 阶段**合并为一次批处理**（React 15 的 `batchedUpdates`，React 18 的自动批处理）。

### Fiber 架构的设计动机

Fiber 将组件树展开为链表而非递归树，使得：
- 工作可在任意节点中断/恢复（递归无法中断）
- 每个 Fiber 可携带**优先级信息**（`lanes` 模型），高优先级更新（如点击响应）可打断低优先级更新（如网络数据加载后刷新）

**违反约束**：若在 render 或 commit 阶段抛出异常，整个子树进入错误边界，不会影响其他部分。

### Hooks 的本质

`useState` 是对 `this.state` 的函数式替代，其核心是对组件Fiber节点上的 `memoizedState` 链表的按序访问：

```jsx
const [state, setState] = useState(initial);
// 等价于：
// Fiber.memoizedState = { baseState, queue: { pending: action } }
// queue 中的 action 在下一次 render 时被 reducer 应用
```

`useEffect` 的清理函数对应**副作用的注册与注销**：React 在 commit 阶段后执行 effect 回调，返回的清理函数在下次 effect 执行前或组件卸载时调用。

### 响应式更新的边界

React 的响应式更新是**悲观并发**的：一旦 `setState` 被调用，React 假定组件可能需要更新，后续的 render/compute 不会被短路。但在 Fiber 架构下，**可中断**意味着低优先级更新可被高优先级打断，产生"饥饿"现象（低优先级更新长期得不到调度）。

### Compound Components 与 Render Props 的归约

两者都是**控制反转**的实现：父组件不再直接决定子组件的渲染内容，而是将控制权交给外部。

- Compound Components：隐式通过 Context 共享状态，子组件自行决定如何使用
- Render Props：显式通过函数 prop 传递渲染逻辑

两者可相互替代，本质都是将"渲染什么"的决策点从组件内部移到外部调用点。

## 对比参照

| 维度 | React | Vue |
|------|--------|-----|
| **响应式粒度** | 组件级（setState 触发整组件重渲染，需 memo 优化） | 属性级（Proxy 追踪具体字段，细粒度更新） |
| **数据流** | 单向（props down, events up） | 双向（v-model，可直接修改） |
| **Diff 算法** | 虚拟 DOM 树比较 | 虚拟 DOM + 组件级脏检查 |
| **渲染时机** | Batch 更新，Fiber 调度 | 同步，依赖收集后微任务队列 |
| **类型支持** | PropTypes / TypeScript | TypeScript 原生支持 |

## 核心概念

### 组件化

**组件是输入 props/state 输出 UI 树的可复用函数。**

<pre>
props/state ──▶ [组件函数] ──▶ UI 树 (React Element)
                              │
                              ▼
                    [React 运行时] ──▶ [真实 DOM]
</pre>

React 通过组件函数描述 UI，运行时将其转化为真实 DOM 操作。组件化使 UI 问题被拆解为可独立开发、测试、复用的单元。

### 虚拟 DOM

**虚拟 DOM 是真实 DOM 的 JavaScript 对象镜像，React 通过对比新旧虚拟 DOM 树确定最小 DOM 操作集。**

<pre>
状态变化
    │
    ▼
创建新虚拟 DOM 树
    │
    ▼
[Diff 算法] ──→ 最小操作序列
    │
    ▼
批处理执行 DOM 更新
</pre>

为何需要虚拟 DOM？直接操作真实 DOM 代价高昂（触发重排重绘）。虚拟 DOM 将多次操作合并为一次批更新，React 保证只更新确实变化的 DOM 部分。

### JSX 语法

**JSX 是 React.createElement 的语法糖，编译后等价于嵌套函数调用。**

```jsx
// JSX
const element = <h1 className="title">Hello</h1>;

// 编译后
const element = React.createElement('h1', { className: 'title' }, 'Hello');
```

JSX 本身不是模板引擎，它只是允许在 JavaScript 中以类 HTML 标记书写 UI 描述，赋予 UI 代码与 HTML 相近的可读性。

## Hooks 基础

### useState

**useState 在函数组件中引入响应式状态，状态变更触发组件重新渲染。**

```jsx
const [count, setCount] = useState(0);
```

状态变更流程：用户交互 → 调用 setState → 组件重新执行 → 新 UI 树与旧树 Diff → 更新变化的 DOM 部分。

### useEffect

**useEffect 在渲染后执行副作用，return 的函数作为清理机制。**

```jsx
useEffect(() => {
  const id = setInterval(() => setCount(c => c + 1), 1000);
  return () => clearInterval(id); // 清理定时器
}, []);
```

依赖数组决定何时重新执行：空数组表示仅在挂载时执行一次；依赖变化时重新执行并清理上一个副作用。

### useContext

**useContext 跨越组件层级传递数据，无需逐层 prop 穿透。**

```jsx
const ThemeContext = createContext('light');
const theme = useContext(ThemeContext);
```

Context 解决了 props 层层传递的噪音问题，但滥用会导致数据流不清晰——应优先用于全局共识如主题、语言，而非业务状态。

## 组件模式

### Compound Components

**组合组件通过隐式共享状态，将多个子组件组合为统一交互单元。**

```jsx
const TabsContext = createContext(null);

function Tabs({ children }) {
  const [activeTab, setActiveTab] = useState('tab1');
  return <TabsContext.Provider value={{ activeTab, setActiveTab }}>{children}</TabsContext.Provider>;
}

function Tab({ id, children }) {
  const { activeTab, setActiveTab } = useContext(TabsContext);
  return <button onClick={() => setActiveTab(id)}>{children}</button>;
}
```

### Render Props

**Render Props 将渲染逻辑封装为函数，通过 props 传递渲染函数而非组件。**

```jsx
function MouseTracker({ render }) {
  const [pos, setPos] = useState({ x: 0, y: 0 });
  useEffect(() => {
    const handler = e => setPos({ x: e.clientX, y: e.clientY });
    window.addEventListener('mousemove', handler);
    return () => window.removeEventListener('mousemove', handler);
  }, []);
  return render(pos);
}
```

为何用 render prop 而非 Hook？render prop 可以在不修改组件树的情况下共享渲染逻辑。

### 自定义 Hooks

**自定义 Hook 是抽离状态逻辑到可复用函数的模式，命名以 use 开头。**

```jsx
function useLocalStorage(key, initial) {
  const [value, setValue] = useState(() => {
    const stored = localStorage.getItem(key);
    return stored ? JSON.parse(stored) : initial;
  });
  useEffect(() => localStorage.setItem(key, JSON.stringify(value)), [key, value]);
  return [value, setValue];
}
```

## 性能优化

### React.memo

**React.memo 缓存组件渲染结果，仅在 props 变化时重新渲染。**

```jsx
const MemoizedList = memo(({ items }) => (
  <ul>{items.map(i => <li key={i.id}>{i.name}</li>)}</ul>
));
```

memo 只做浅比较 props，对于引用类型需配合 useMemo/useCallback 保持引用稳定。

### 代码分割

**代码分割将子模块拆为独立 chunk，按需加载。**

```jsx
const Heavy = lazy(() => import('./HeavyComponent'));
```

# Vue 入门

> Vue 是渐进式 JavaScript 框架，核心机制是**基于 Proxy 的响应式依赖追踪**与**模板编译优化**。

## 核心概念

### 响应式系统

**Vue 3 的响应式基于 Proxy，属性访问与赋值自动触发依赖追踪。**

<pre>
Proxy(get) ──▶ 收集依赖 ──▶ 建立映射
Proxy(set) ──▶ 触发更新 ──▶ 找到依赖 ──▶ 重新渲染
</pre>

Vue 2 用 Object.defineProperty，存在无法追踪新增删除属性的缺陷。Vue 3 的 Proxy 完美解决了这个问题，且支持 Map、Set 等数据结构。

### ref 与 reactive

**ref 包装基本类型，reactive 代理对象；解构 reactive 会丢失响应式，需用 toRefs。**

```jsx
const count = ref(0);     // 基本类型 → ref
const state = reactive({  // 对象 → reactive
  name: 'Alice'
});
```

---

## Composition API

**Composition API 以函数组合替代 Options API 的选项拆分，相同逻辑可跨组件复用。**

```jsx
export default {
  setup() {
    const count = ref(0);
    const doubled = computed(() => count.value * 2);
    return { count, doubled };
  }
};
```

为何需要 Composition API？当组件逻辑复杂时，Options API 将同一功能的代码分散在不同选项中（data 与 methods 分离等），Composition API 允许相关逻辑聚合在一起。

### script setup

**script setup 是 setup 的语法糖，变量直接暴露给模板，无需 return。**

```vue
<script setup>
const count = ref(0);
</script>
```

编译后自动生成等价的 setup 函数，代码更简洁。

## 依赖注入

### provide 与 inject

**provide/inject 在祖先与后代组件间建立隧道，跨越多层传递数据。**

```jsx
const THEME_KEY = Symbol('theme');
provide(THEME_KEY, { theme, toggleTheme });
// 后代组件
const ctx = inject(THEME_KEY);
```

provide/inject 不像 Context 那样要求所有中间组件显式传递，但失去了可见性——后代组件直接依赖注入的值，组件树的数据流不直观。

## 高级模式

### Teleport

**Teleport 将组件渲染到 DOM 树的任意位置，不受组件层级约束。**

```vue
<Teleport to="body">
  <Modal />
</Teleport>
```

Modal 通常需要渲染到 body 以避免 z-index 问题，Teleport 解决了这个结构性需求而不需 Portal 组件。

### Suspense

**Suspense 在异步组件加载时渲染 fallback 内容。**

```vue
<Suspense>
  <template #default><AsyncUser /></template>
  <template #fallback><Spinner /></template>
</Suspense>
```

### 异步组件

**异步组件将加载推迟到首次渲染时，支持 loading/error 状态控制。**

```jsx
const AsyncList = defineAsyncComponent({
  loader: () => import('./List.vue'),
  loadingComponent: LoadingSpinner,
  errorComponent: ErrorBoundary
});
```

## 最佳实践

### 状态管理原则

**状态应放在需要它的最低层级。全局状态放 Context/Store，页面级状态放父组件，组件级状态放内部。**

为何有这个原则？状态位置影响更新范围：状态越高，更新影响的组件越多；状态越低，数据流越局部，但跨组件共享越麻烦。
