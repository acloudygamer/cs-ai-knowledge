# 前端框架入门

> **版本基准**: React 18+ / Vue 3.4+ / Angular 17+ (stable) | React 19+ / Vue 3.5+ / Angular 18+ (latest)

## 定义

前端框架是封装了 DOM 操作与状态管理的 JavaScript 库，通过**声明式**替代**命令式** UI 编程范式，使开发者描述"UI 应当呈现什么状态"而非"如何逐步操作 DOM"。

其本质是建立一个**有限状态自动机**：给定当前状态（props + state）和新输入（用户事件/服务器响应），框架计算并输出下一帧 UI 描述，再由运行时将其映射为最小 DOM 操作序列。

# React 入门

## 定义

React 的本质是一个**有限状态自动机**：给定当前状态（props + state）和新输入（用户事件/服务器响应），React 计算并输出下一帧 UI 描述（React Element 树），再由运行时将其映射为最小 DOM 操作序列。组件函数是状态到 UI 的纯函数映射，React 运行时负责在这个映射过程中插入高效的 DOM 更新。

## 数学模型

### 虚拟 DOM diff 复杂度

React 的 diff 算法将两棵树的比较问题从 $O(N^3)$ 降至 $O(N)$，通过两个假设实现：

1. **不同类型的元素产生不同的树**：若元素类型不同，React 假设整棵子树无需比较，直接替换。
2. **同层同级节点可用 key 标识稳定性**：若子元素列表在同层位置变化（增/删/移动），可通过 key 推断哪些节点实际改变。

设树高为 $h$，最坏情况下需要遍历所有节点，时间复杂度 $O(N)$，其中 $N$ 为总节点数。

**归约终点**：diff 的实质是**最小编辑距离问题在约束条件下的近似解**，通过启发式规则将 $O(N^3)$ 降为 $O(N)$。

### 调度模型

React 15 的协调（reconciliation）是同步的——若组件树极深，一次状态更新可能阻塞主线程数十毫秒。React 16 引入 **Fiber 架构**，将协调工作拆为多个最小工作单元（Fiber node），每单元完成后可中断、恢复，实现**增量渲染**。

**时间片模型**：每个工作单元有预算（约 5ms），用 `requestIdleCallback`（或 React 自己实现的 scheduler）在浏览器空闲时继续。未完成则推迟到下一帧。

### Fiber 链表的数学性质

Fiber 节点构成一个包含三个指针的结构：

```text
type Fiber = {
  child: Fiber | null,      // 第一个子节点
  sibling: Fiber | null,     // 相邻兄弟节点
  return: Fiber | null,     // 父节点
  // ... 其他字段
}
```

这个结构将递归树转化为**链表**，使得遍历可以：
- 在任意节点暂停（`child === null` 时沿 `sibling` 前进，无则沿 `return` 回溯）
- 优先级调度成为可能（链表节点可独立调度，递归则必须整棵完成）

## 数据流

<pre>
用户交互 / 事件触发
        │
        ▼
组件 dispatch 状态更新
   setState(newState)
        │
        ▼
React 创建新的 React Element 树
   { type: Component, props: {...}, children: [...] }
        │
        ▼
[Reconciliation / Fiber 协调]
  1. 构建 Fiber 链表（虚拟 DOM 的链表表示）
  2. 标记 WorkFlags（Placement, Update, Deletion...）
  3. 调度优先级排序
        │
        ▼
[Commit 阶段]
  遍历所有含 flags 的 Fiber，
  执行 DOM 操作（createElement / removeChild / appendChild）
</pre>

**数据形态变换**：
- `props/state`（普通 JS 值）→ `React Element`（JS 对象，字面量描述 UI）
- `React Element 树`（虚拟 DOM）→ `Fiber 链表`（运行时内部结构，含 child/sibling/return 指针）
- `Fiber` 上的 `WorkFlags` → `实际 DOM 操作`

**所有权流转**：
- props 不可变（React 保证），组件内部 state 在 `setState` 后立即变为旧值
- Fiber 树由 React 运行时持有，用户代码无法直接访问
- Commit 阶段 DOM 操作后，Fiber 树更新完成，进入下一轮空闲等待

## 机制

### 虚拟 DOM 的本质

直接操作真实 DOM 代价高昂：每次 `.innerHTML` 赋值触发浏览器的**解析 + 样式计算 + 布局 + 绘制**，且无法增量——即使只改一个属性，浏览器也需重排/重绘整个区域。

虚拟 DOM 将"描述 UI"与"应用 UI"解耦。React 比较新旧虚拟 DOM 树（diff），计算出**最小操作集**，再批量执行 DOM API（`appendChild`、`removeChild`、`setAttribute` 等）。单次 diff 的结果可能产生多次 DOM 操作，但这些操作会在 commit 阶段**合并为一次批处理**（React 15 的 `batchedUpdates`，React 18 的自动批处理）。

**约束**：diff 算法依赖两个假设，若假设不成立（如子元素类型相同但实际渲染逻辑完全不同），性能会退化。

### Fiber 架构的设计动机

Fiber 将组件树展开为链表而非递归树，使得：
- 工作可在任意节点中断/恢复（递归无法中断）
- 每个 Fiber 可携带**优先级信息**（`lanes` 模型），高优先级更新（如点击响应）可打断低优先级更新（如网络数据加载后刷新）

**违反约束**：若在 render 或 commit 阶段抛出异常，整个子树进入错误边界，不会影响其他部分。

### Hooks 的本质

`useState` 是对 `this.state` 的函数式替代，其核心是对组件Fiber节点上的 `memoizedState` 链表的按序访问：

```jsx
const [state, setState] = useState(initial);
// 等价于：
// Fiber.memoizedState = { baseState, queue: { pending: action } }
// queue 中的 action 在下一次 render 时被 reducer 应用
```

`useEffect` 的清理函数对应**副作用的注册与注销**：React 在 commit 阶段后执行 effect 回调，返回的清理函数在下次 effect 执行前或组件卸载时调用。

### 响应式更新的边界

React 的响应式更新是**悲观并发**的：一旦 `setState` 被调用，React 假定组件可能需要更新，后续的 render/compute 不会被短路。但在 Fiber 架构下，**可中断**意味着低优先级更新可被高优先级打断，产生"饥饿"现象（低优先级更新长期得不到调度）。

### Compound Components 与 Render Props 的归约

两者都是**控制反转**的实现：父组件不再直接决定子组件的渲染内容，而是将控制权交给外部。

- Compound Components：隐式通过 Context 共享状态，子组件自行决定如何使用
- Render Props：显式通过函数 prop 传递渲染逻辑

两者可相互替代，本质都是将"渲染什么"的决策点从组件内部移到外部调用点。

## 对比参照

| 维度 | React | Vue |
|------|-------|-----|
| **响应式粒度** | 组件级（setState 触发整组件重渲染，需 memo 优化） | 属性级（Proxy 追踪具体字段，细粒度更新） |
| **数据流** | 单向（props down, events up） | 双向（v-model，可直接修改） |
| **Diff 算法** | 虚拟 DOM 树比较 | 虚拟 DOM + 组件级脏检查 |
| **渲染时机** | Batch 更新，Fiber 调度 | 同步，依赖收集后微任务队列 |
| **类型支持** | PropTypes / TypeScript | TypeScript 原生支持 |

# Vue 入门

## 定义

Vue 是渐进式 JavaScript 框架，核心机制是**基于 Proxy 的响应式依赖追踪**与**模板编译优化**。与 React 的"纯函数映射"不同，Vue 在数据与视图之间建立直接绑定关系，通过拦截属性访问与赋值自动维护依赖图。

## 数学模型

### 响应式依赖追踪

Vue 3 的响应式基于 Proxy，其数学模型可形式化为：

**目标**：建立属性访问路径到副作用函数的映射 $M: \text{path} \rightarrow \text{Set}(\text{effect})$

**操作语义**：
- `Proxy(get)`：若当前存在依赖收集上下文 $C$，则 $M[\text{path}] \leftarrow M[\text{path}] \cup \{C\}$
- `Proxy(set)`：若新值 $\neq$ 旧值，则 $\forall e \in M[\text{path}]: e()$（触发所有依赖的副作用）

**归约终点**：响应式系统的本质是**发布-订阅模式**的自动建立，Proxy 拦截器替代了 Vue 2 中手动 `Object.defineProperty` 的 `get`/`set`，使得新增/删除属性也能被追踪。

### 模板编译的复杂度

Vue 模板在编译时生成两种代码：
- **静态提升**：不变的部分提取为常量
- **动态绑定**：生成 `createElement` 调用，标记需要追踪的路径

最坏情况下，模板解析为 AST 后遍历复杂度为 $O(N)$，其中 $N$ 为模板节点数。

---

## 数据流

<pre>
[依赖收集阶段]
Proxy(get) ──▶ 读取属性 path ──▶ 建立映射 M[path] ⊕ {当前effect}
        │
        ▼
[派发更新阶段]
Proxy(set) ──▶ 检测到值变化 ──▶ 查找 M[path] ──▶ 触发所有订阅的effect
        │
        ▼
[重新渲染]
effect 执行 ──▶ 组件重新执行 / patch ──▶ 更新 DOM
</pre>

**数据形态变换**：
- 普通 JS 对象 → reactive proxy（运行时包装）
- 属性读取 → 隐式建立依赖映射
- 属性赋值 → 隐式触发依赖更新

**所有权流转**：
- 原始对象由用户代码持有
- Proxy 由 Vue 运行时持有，对原始对象的访问必须通过 Proxy
- 依赖映射 $M$ 由 Vue 内部维护，不暴露给用户

---

## 机制

### Proxy vs Object.defineProperty

Vue 2 的 `Object.defineProperty` 存在根本缺陷：
- 无法追踪**新增/删除**属性（必须用 `Vue.set`/`Vue.delete`）
- 无法追踪**数组下标变化**（`arr[index] = value` 不会触发更新）

Vue 3 的 Proxy 完美解决了这些问题：
- `get` 拦截所有属性访问（包括新增）
- `set` 拦截所有属性赋值（包括新增和删除）
- 支持 `Map`、`Set`、`WeakMap`、`WeakSet` 等复杂数据结构

**约束**：Proxy 无法监视**对象解构**——`const { a } = reactive(obj)` 后，`a` 成为普通值，脱离响应式系统。

### ref 与 reactive 的选择

| 包装类型 | 适用场景 | 解构行为 |
|---------|---------|---------|
| `ref` | 基本类型（string/number/boolean） | 解构后保持响应式（通过模板 refs） |
| `reactive` | 对象/数组 | 解构后丢失响应式，需用 `toRefs` |

### Composition API 的设计动机

当组件逻辑复杂时，Options API 将同一功能的代码分散在不同选项中（`data` 与 `methods` 分离等），Composition API 允许相关逻辑聚合在一起。

```jsx
export default {
  setup() {
    const count = ref(0);
    const doubled = computed(() => count.value * 2);
    return { count, doubled };
  }
};
```

**归约终点**：Composition API 是**函数式组合**原则在 UI 框架中的实现，相同逻辑可跨组件复用，而不被迫按选项类型拆分。

# 框架共性模式

## 组件化

**组件是输入 props/state 输出 UI 树的可复用函数。**

<pre>
props/state ──▶ [组件函数] ──▶ UI 树 (React Element / Vue 模板)
                              │
                              ▼
                    [框架运行时] ──▶ [真实 DOM]
</pre>

组件化使 UI 问题被拆解为可独立开发、测试、复用的单元。

## 性能优化机制

### React.memo 与 v-memo

两者都是**记忆化**（memoization）的实现：

- `React.memo`：缓存组件渲染结果，仅在 props 变化时重新渲染（浅比较）
- `v-memo`：缓存模板子树，仅在指定依赖变化时更新

**约束**：记忆化本身有开销（内存占用 + 比较成本），若组件渲染成本低于记忆化开销，效果适得其反。

### 批量更新

React 18 的自动批处理将多次状态更新合并为一次渲染：

```jsx
setTimeout(() => {
  setCount(c => c + 1);  // 不触发渲染
  setFlag(f => !f);      // 不触发渲染
  // 合并为一次渲染
}, 0);
```

Vue 的响应式更新默认同步，但通过微任务队列批量处理。
