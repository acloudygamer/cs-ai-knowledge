# 错误处理

> 前置：[06-模块](./06-模块.md) · 后续：[02-对象模型与运行时/01-原型链与继承](../02-对象模型与运行时/01-原型链与继承.md)

> **版本基准**：Node 24 stable / Node 26 latest。本篇示例实测环境：Node v24.13.1（V8 13.6），Windows x64。

## 本质

错误处理回答一个问题：**函数失败时，怎么把这件事告诉调用方**。有两条路——返回值（返回 `null`、错误码）和异常（抛出）。JavaScript 选了后者：`throw` 立即终止当前执行路径，控制权沿调用栈**向上寻找最近的 `catch`**，中间所有帧被丢弃。

这个过程称为**栈展开**（stack unwinding），它是 [全景](../00-概览/01-JavaScript全景.md) 那条执行链的逆向操作——正向是调用层层压栈，反向是异常逐层弹栈。理解这一点就明白了两件事：为什么 `try` 只保护它**调用链下游**的代码，以及为什么异常比错误码"穿透力"强（中间的每一层都不必写转发代码）。

## 机制

### 错误对象

内建错误类型共八个，全部继承自 `Error`：

| 类型 | 触发场景 |
|---|---|
| `Error` | 通用基类，自定义错误继承它 |
| `TypeError` | 值的类型不是操作所需（`undefined.foo`） |
| `RangeError` | 数值超出允许范围 |
| `ReferenceError` | 访问不存在的绑定（TDZ 也抛这个） |
| `SyntaxError` | 语法错误，通常由解析器抛出，`try` 捕不到 |
| `URIError` | `decodeURI` 等函数收到畸形 URI |
| `EvalError` | 历史遗留，现代引擎不再抛出 |
| `AggregateError` | 聚合多个错误，如 `Promise.any` 全部失败时 |

```console
$ node -e 'console.log(Object.getPrototypeOf(TypeError.prototype) === Error.prototype)'
true
```

继承链意味着 `catch (e) { if (e instanceof TypeError) … }` 能按类型分派——但这只在**同一个 realm**（同一个全局环境）内成立，跨 realm 时见下文。

错误对象携带两个关键属性：`message`（人类可读描述）与 `stack`（抛出点的调用栈快照，**非标准但所有引擎都实现**）。`cause`（ES2022）用于把底层错误挂在包装错误上：

```console
$ node -e 'try { try { throw new Error("底层") } catch(e) { throw new Error("上层", { cause: e }) } } catch(e) { console.log(e.message, "|", e.cause.message) }'
上层 | 底层
```

`stack` 的生成有成本（要采集当前调用栈），因此高频抛出的路径会明显变慢——这是"异常不适合做常规控制流"的实测原因。

### `throw` 可以抛任意值

规范不要求抛出的是 `Error`：

```console
$ node -e 'try { throw "一个字符串" } catch(e){ console.log(typeof e, JSON.stringify(e)) }'
string "一个字符串"
```

**永远抛 `Error` 实例**。抛字符串或数字会丢掉 `stack`，且无法用 `instanceof` 分派——排查线上问题时，没有栈的错误等于没有信息。

### `try` / `catch` / `finally`

`finally` 在控制权离开 `try` 块前执行，**它的 `return` 会覆盖 `try` 里的 `return`**：

```console
$ node -e 'function f(){ try { return "try" } finally { return "finally" } } console.log(f())'
finally
```

同样的覆盖也适用于 `throw`——`finally` 里抛出的异常会顶替原来的异常。因此 `finally` 应当只做**清理**（关连接、释放锁），不要在里头 `return` 或 `throw`。

`catch` 的参数可以省略（`catch {}`，ES2019），用于"只关心是否出错、不关心是什么"的场合。

### 异步错误不在同一条栈上

`try` 保护的是**当前同步调用链**。回调里抛出的错误发生时，`try` 所在的帧早已返回：

```javascript
try {
  setTimeout(() => { throw new Error("回调里的错误"); }, 0);
} catch (e) {
  // 永远不会执行——抛错时这个 try 已经结束了
}
```

异步错误的传播归 Promise 链（`.catch` / `await` 的 `try`），机制见 [02-回调到 Promise](../04-异步与并发/02-回调到Promise.md) 与 [03-async/await 与异步模式](../04-异步与并发/03-async-await与异步模式.md)。**`await` 让异步错误重新回到同步的 `try` 里可捕获**——这是 `async` / `await` 相对裸 Promise 的主要收益之一。

### 跨 realm 的判断

`instanceof Error` 依赖原型链，而原型链是**每个 realm 各一份**。来自 `iframe`、`vm` 模块或 Worker 的错误对象，其原型不是当前 realm 的 `Error.prototype`：

```console
$ node -e 'const vm=require("node:vm"); const e=vm.runInNewContext("new Error(\"外部\")"); console.log(e instanceof Error, typeof Error.isError)'
false function
```

```console
$ node -e 'console.log(Error.isError(new Error("x")))'
true
```

`Error.isError()` 绕过原型链直接检查内部槽位，跨 realm 可靠。它是 **ES2026 特性，但 Node 24（V8 13.6）已经支持**——正是 [全景](../00-概览/01-JavaScript全景.md) 所述"引擎落地领先规范版本"的实例。

## 连接：与 Java 对照

| | JavaScript | Java |
|---|---|---|
| 受检异常 | 无——所有异常都是非受检的 | 有 `throws` 声明，编译期强制 |
| 声明 | 不需要（也无法）声明抛出什么 | 方法签名必须列出 |
| 抛出任意值 | 允许（不推荐） | 只能抛 `Throwable` |
| 栈展开代价 | 采集 `stack` 有成本 | 填充 stack trace 有成本 |
| 资源清理 | `finally`（或 ES2027 的 `using`） | try-with-resources |
| 跨模块判断类型 | 需 `Error.isError` | 无 realm 问题 |

"无受检异常"的后果是：**函数是否可能抛错，从签名上看不出来**。调用方要么读文档，要么防御性捕获。这是 JavaScript 与 Java 在错误处理上最大的实际差异。

## 边界

- **`SyntaxError` 捕不到**：语法错误发生在解析阶段，早于任何代码执行，`try` 根本没有机会运行（动态 `eval` / `import()` 例外）。
- **不要用异常做常规控制流**：`stack` 采集是实打实的开销，且异常路径会阻碍引擎的优化。
- **`finally` 里不要 `return` / `throw`**：会静默吞掉原有异常，这是最难排查的一类 bug。
- **`Promise` 的拒绝若无处理会变成未捕获异常**：Node 默认终止进程，浏览器打印到控制台。机制见 [02-回调到 Promise](../04-异步与并发/02-回调到Promise.md)。
