# 绑定与类型

> 前置：[01-安装与第一个程序](./01-安装与第一个程序.md) · 后续：[03-控制流程](./03-控制流程.md)

> **版本基准**：Node 24 stable / Node 26 latest。本篇示例实测环境：Node v24.13.1（V8 13.6），Windows x64。

## 本质

**绑定**（binding）是名字与值之间的关联：声明一个变量，就是在某个作用域里建立一个绑定，此后用名字访问它。JavaScript 的绑定有三个规定性特征：

| 特征 | 含义 |
|---|---|
| **词法作用域** | 绑定能被谁看见，由它在**源码里的位置**决定，与调用顺序无关（`this` 是这条规则的唯一例外，见 [03-this 与调用约定](../02-对象模型与运行时/03-this与调用约定.md)） |
| **块级作用域** | `let` / `const` 的绑定范围是最近的 `{}`；`var` 的绑定范围是最近的**函数** |
| **动态类型** | 绑定**不携带类型**——类型属于运行时的值，不属于名字。同一个名字先后可以绑到字符串、数字、对象 |

第三条是 JavaScript 与 Java、C++ 的分水岭。那些语言里"变量"是"一块有固定解释方式的内存"，类型决定这块内存的布局；JavaScript 里名字只是一个查找键，**类型是值的属性**。

这条差异的约束不是技术性的，是历史性的：JavaScript 1995 年为浏览器设计，代码由多方投递、加载即执行，没有编译期可以安放静态检查。类型检查后来由 [TypeScript](../../7-TypeScript/) 以**外挂**的方式补上——它编译后类型全部消失，运行时看到的仍是本节的规则。

## 机制

### 三种声明方式

| | 作用域 | 初始化前访问 | 重复声明 | 可重新赋值 |
|---|---|---|---|---|
| `var` | 函数 | 得到 `undefined` | 允许 | 是 |
| `let` | 块 | **抛 ReferenceError** | 抛 SyntaxError | 是 |
| `const` | 块 | **抛 ReferenceError** | 抛 SyntaxError | 否（对象内容可变） |

`var` 的"初始化前访问得到 `undefined`"称为**提升**（hoisting）：声明被提到函数顶部，赋值留在原处。

```console
$ node -e 'console.log(y); var y = 1;'
undefined
```

`let` / `const` 没有这个行为，访问未初始化的绑定直接抛错：

```console
$ node -e 'try { console.log(x); let x = 1; } catch (e) { console.log(e.constructor.name + ": " + e.message); }'
ReferenceError: Cannot access 'x' before initialization
```

从进入作用域到执行到声明语句之间，这段区间称为**暂时性死区**（TDZ，Temporal Dead Zone）。TDZ 不是"没提升"——绑定已经存在（所以外部同名变量被遮蔽），只是被标记为不可访问。这是 2015 年引入 `let` 时对 `var` 行为的**刻意修正**：让"用了还没声明的变量"从静默的 `undefined` 变成立即报错。

### 七种原始类型与对象

值分两类，判据是**赋值时复制的是什么**：

| 类别 | 成员 | 赋值语义 |
|---|---|---|
| 原始类型（7 种） | `undefined`、`null`、`boolean`、`number`、`bigint`、`string`、`symbol` | 复制值本身 |
| 对象 | 其余全部（含函数、数组、`Date`、`Map`） | 复制引用，赋值即别名 |

```console
$ node -e 'console.log(typeof null, "|", typeof function(){}, "|", typeof 1n, "|", typeof Symbol())'
object | function | bigint | symbol
```

两处 `typeof` 的反常都有出处：

- **`typeof null === "object"`**：1995 年首个实现用低位类型标签区分值类型，对象的标签是 `0`，而空指针也编码为 `0`，于是 `null` 被一并判为对象。**这是历史遗物，不是设计**——它此后被写进规范并冻结，因为修它会破坏既有代码。
- **`typeof function(){} === "function"`**：函数在规范里是对象，`"function"` 是 `typeof` 为可调用对象单独开的分支。

### 数值：一种类型，两个陷阱

`number` 是 IEEE 754 双精度浮点（64 位），**没有整数类型**。由此产生两个必须知道的行为：

```console
$ node -e 'console.log(0.1+0.2, "| === 0.3 ?", 0.1+0.2===0.3)'
0.30000000000000004 | === 0.3 ? false
```

十进制小数 $0.1$ 与 $0.2$ 在二进制浮点里都是无限循环小数，存储时被截断，相加后的误差落在第 17 位有效数字上。

```console
$ node -e 'console.log(2**53 === 2**53+1)'
true
```

`number` 能精确表示的整数上限是 $2^{53}-1$（`Number.MAX_SAFE_INTEGER`，即 9007199254740991）；超过之后相邻整数可能映射到同一个值。需要更大的整数用 `bigint`（字面量加 `n` 后缀，如 `9007199254740993n`），代价是不能与 `number` 混算。

### 隐式转换：`+` 与其它运算符分道扬镳

```console
$ node -e 'console.log("1"+1, "|", "3"*"2", "|", []+{})'
11 | 6 | [object Object]
```

`+` 有两种含义（数值加法、字符串拼接），规则是**只要有一侧是字符串就拼接**；其余算术运算符只有数值含义，于是把操作数转成数字。`[]+{}` 走的是"两侧都不是字符串 → 都转原始值 → 都成字符串 → 拼接"这条链。

转换成数字的规则里，三个空值各走各的：

```console
$ node -e 'console.log(Number(""), Number(null), Number(undefined))'
0 0 NaN
```

显式转换始终优于隐式：`Number(x)` / `String(x)` / `Boolean(x)` 意图明确，而隐式转换的触发点散布在运算符语义里。

### 三种相等

| 写法 | 规则 | `NaN` vs `NaN` | `-0` vs `0` |
|---|---|---|---|
| `===` 严格相等 | 类型不同即不等 | `false` | `true` |
| `==` 宽松相等 | 先做隐式转换再比 | `false` | `true` |
| `Object.is` | 不做转换，且区分特殊值 | `true` | `false` |

```console
$ node -e 'console.log(NaN===NaN, Object.is(NaN,NaN), Object.is(-0,0), -0===0)'
false true false true
```

`===` 对 `NaN` 恒假，因为 IEEE 754 规定 NaN 不等于自身。`Object.is` 是唯一能"认出" `NaN` 与 `-0` 的比较。**默认用 `===`**，`Object.is` 留给确实要区分 `-0` 或比较 `NaN` 的场合；`==` 的隐式转换规则难以在阅读时复现，除非确知两侧类型（如 `x == null` 同时匹配 `null` 与 `undefined`），否则不用。

## 连接：与静态类型语言对照

| | JavaScript | Java / C++ |
|---|---|---|
| 类型归属 | 值 | 变量（内存布局） |
| 检查时机 | 运行时 | 编译时 |
| 未声明即用 | 宽松模式下创建全局；严格模式报错 | 编译失败 |
| 数值模型 | 一种 `number`（float64）+ `bigint` | 按位宽分多种整型与浮点 |
| 类型错误的代价 | 运行时才发现，可能已执行到一半 | 编译期拦下 |

ESM 与类体内的代码默认是**严格模式**（`"use strict"`），CommonJS 默认宽松——这是"未声明即用"行为在两种模块里不同的原因。

## 边界

- **`const` 冻结的是绑定，不是值**：`const a = [1]; a.push(2)` 合法。要冻结对象内容用 `Object.freeze`（浅冻结，见 [04-属性描述符与元编程](../02-对象模型与运行时/04-属性描述符与元编程.md)）。
- **`typeof` 不是类型判断的通用手段**：它无法区分数组与对象、`null` 与对象；这些判断归 [04-属性描述符与元编程](../02-对象模型与运行时/04-属性描述符与元编程.md)。
- **原始类型也有方法**：`"abc".toUpperCase()` 合法，机制是引擎临时装箱为对象再调用——这个机制与原型链同在 [01-原型链与继承](../02-对象模型与运行时/01-原型链与继承.md)。
