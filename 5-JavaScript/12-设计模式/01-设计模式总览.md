# 设计模式总览

> 前置：[11-前端框架与状态管理/05-路由与 SSR](../11-前端框架与状态管理/05-路由与SSR.md) · 后续：[02-创建型模式](./02-创建型.md)

> **版本基准**：Node 24 stable / Node 26 latest。本篇示例实测环境：Node v24.13.1，Windows x64。

## 本质

设计模式是**对反复出现的问题的命名解法**。名字的价值在于沟通——说"这里用策略模式"比描述一遍实现快得多。

但模式有一个常被忽略的属性：**它是对语言缺陷的补偿**。经典设计模式的分类（创建型 / 结构型 / 行为型，23 个）总结自 C++ 与 Java 的实践，而这些语言的约束与 JavaScript 不同。**语言补上了某个能力，对应的模式就会溶解**。

判定一个模式在 JavaScript 里是否还需要，只需问一句：**它解决的问题，是不是语言已经内建了？**

## 机制

### 溶解：语言内建之后，模式退化为语法

以下七组在 Node 24 实测（见 [02](./02-创建型.md) / [03](./03-结构型.md) / [04](./04-行为型.md) 的展开）：

| 模式 | 它解决什么 | JavaScript 里退化为 |
|---|---|---|
| **单例** | 保证全局只有一个实例 | 模块（顶层只执行一次） |
| **策略** | 运行时替换算法 | 一等函数 |
| **装饰器** | 不修改原对象地附加行为 | 高阶函数 |
| **观察者** | 一对多依赖通知 | `EventTarget`（平台内建） |
| **代理** | 控制对另一对象的访问 | `Proxy`（语言内建） |
| **工厂** | 把构造逻辑与使用分离 | 构造函数 / 返回对象的函数 |
| **迭代器** | 统一遍历接口 | 迭代协议（`Symbol.iterator`） |

```javascript
// patterns.mjs
// 单例 → 模块级闭包：模块顶层只执行一次，闭包持有私有状态
let n = 0;
const counter = { inc: () => ++n, get: () => n };
console.log(`  模块级闭包即单例: ${counter.inc()} ${counter.inc()} -> ${counter.get()}`);

// 策略 → 一等函数：算法本身就是值
const add = (a, b) => a + b, mul = (a, b) => a * b;
console.log(`  策略即函数: ${add(2, 3)} ${mul(2, 3)}`);

// 观察者 → EventTarget：平台内建的一对多通知
const bus = new EventTarget();
const seen = [];
bus.addEventListener("tick", (e) => seen.push(`订阅A:${e.detail}`));
bus.addEventListener("tick", (e) => seen.push(`订阅B:${e.detail}`));
bus.dispatchEvent(new CustomEvent("tick", { detail: 7 }));
console.log(`  ${seen.join(" | ")}`);

// 代理 → Proxy：语言内建的访问拦截
const product = { price: 100 };
const taxed = new Proxy(product, {
  get: (t, k) => (k === "price" ? t[k] * 1.1 : t[k]),
});
console.log(`  原始: ${product.price} | 经代理: ${taxed.price.toFixed(1)}`);
```

```console
$ node patterns.mjs
  模块级闭包即单例: 1 2 -> 2
  策略即函数: 5 6
  订阅A:7 | 订阅B:7
  原始: 100 | 经代理: 110.0
```

**"模式消失"不是"这个解法消失了"，而是"不再需要为它发明一个名字与一套类结构"**。单例的诉求（全局唯一）仍在，但表达它只需一个模块文件，不再需要私有的构造函数、静态实例字段与 `getInstance()`。

### 为什么 C++/Java 里它们需要类结构

| 语言能力 | C++ / Java（经典模式的时代） | JavaScript |
|---|---|---|
| 函数作为值 | 需要函数对象或函数式接口包装 | 原生 |
| 闭包 | 无（或需手工捕获） | 原生，且捕获是隐式的 |
| 动态属性访问 | 需要反射 | 原生（对象即字典） |
| 运行时替换原型 | 不可 | 可（`Object.setPrototypeOf`） |
| 拦截属性读写 | 需要手写代理类 | `Proxy` |
| 遍历协议 | 需要实现 `Iterator` 接口 | 协议满足即可 |

**模式是"在缺少某个能力时，用已有的能力拼出它"**。缺一等函数，就用类加虚函数模拟（策略模式）；缺闭包，就用类字段保存状态（命令模式）。语言补上之后，模拟的脚手架就没有存在的必要了。

### 仍然需要的模式

不是所有模式都会溶解。剩下的分两类：

| 类别 | 例子 | 为什么仍在 |
|---|---|---|
| **与语言无关的协作结构** | 责任链、状态机、发布订阅的复杂形态 | 它们描述的是"多个对象如何协作"，与语言能力无关 |
| **跨模块的边界管理** | 模块模式、命名空间、依赖注入 | 语言只提供语法，组织方式仍需约定 |

**责任链**是典型：它描述"请求沿一条链传递，直到某个环节处理"，这在任何语言里都需要显式组织——JavaScript 没有内建机制自动做到。

### 反模式：为用而用

模式被误用的两种形态：

| 形态 | 表现 |
|---|---|
| **把简单事复杂化** | 一个函数能做的事，写成抽象工厂 + 具体工厂 |
| **用模式名当设计依据** | "这里应该用观察者模式"——而实际问题不需要解耦通知 |

**判断标准是"有没有第二个实现"**：只有一个实现的策略模式、只有一个产品的工厂，都是不必要的抽象。模式应当在**第二次遇到同样问题时**引入，而不是第一次就预防性地搭好。

## 连接：与经典模式分类对照

| 分类 | 经典内容 | JavaScript 的对应 |
|---|---|---|
| **创建型** | 单例、工厂方法、抽象工厂、建造者、原型 | 模块、函数返回对象、`Object.create`（见 [02-创建型模式](./02-创建型.md)） |
| **结构型** | 适配器、装饰器、代理、外观、组合、桥接、享元 | 高阶函数、`Proxy`、对象组合（见 [03-结构型模式](./03-结构型.md)） |
| **行为型** | 策略、观察者、责任链、命令、状态、模板方法、迭代器、中介者、访问者、备忘录、解释器 | 一等函数、`EventTarget`、生成器、迭代协议（见 [04-行为型模式](./04-行为型.md)） |

## 边界

- **模式是沟通词汇，不是设计目标**：用它是为了说清楚结构，不是为了"用了模式"。
- **语言内建的能力优先于手写模式**：能用一个函数解决就不要建类层次。
- **只在第二次遇到同样问题时抽象**：第一次就抽象容易建错。
- **框架已经替你用了很多模式**：React 的组件是组合模式、Vue 的响应式是观察者——理解这些有助于理解框架行为。
- **剩下的模式多与"多对象协作"有关**：它们不依赖语言缺陷，因而不会溶解。
- **本篇的"溶解"判断基于语言能力，不是风格偏好**：同一模式在不同语言里的必要性确实不同。
