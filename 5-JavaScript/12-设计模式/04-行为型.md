# 行为型模式

> 前置：[03-结构型模式](./03-结构型.md) · 后续：[13-版本演进/01-演进脉络与 TC39 流程](../13-版本演进/01-演进脉络与TC39流程.md)

> **版本基准**：Node 24 stable / Node 26 latest。本篇示例实测环境：Node v24.13.1，Windows x64。

## 本质

行为型模式解决**"对象之间怎么协作与分配职责"**——谁处理请求、谁通知谁、状态变化时行为怎么变。

这一类比创建型与结构型**保留了更多模式**，因为它们大多描述的是**协作结构**而非"用已有能力模拟缺失能力"。语言补上一等函数后，其中一部分退化了；剩下的与语言无关。

## 机制

### 策略 → 一等函数

经典策略模式要一个抽象类加 N 个子类。JavaScript 里算法就是值：

```console
$ node behav.mjs
  100 元： normal=100 | vip=80 | staff=50
```

```javascript
const pricing = { normal: (p) => p, vip: (p) => p * 0.8, staff: (p) => p * 0.5 };
const checkout = (kind, price) => pricing[kind](price);
```

**策略表是一个对象，值是函数**——没有类层次，没有 `implements`，没有 `context` 类。这是 [01-设计模式总览](./01-设计模式总览.md) 那条"语言内建即溶解"最典型的例子。

**它仍有约束**：所有策略必须有**相同的签名**。签名不一致时，调用方需要分支——那说明它们不是同一个策略。

### 观察者 → `EventTarget`

观察者模式的诉求（一对多通知）由平台内建：

```console
$ node patterns.mjs
  订阅A:7 | 订阅B:7
```

`EventTarget` 提供注册、派发、移除与一次性监听（见 [05-浏览器平台/01-DOM 与事件模型](../05-浏览器平台/01-DOM与事件模型.md)），在 Node 与浏览器都可用。**不需要自己实现订阅列表**。

**但有两件事需要自己决定**：

| 问题 | 要考虑的 |
|---|---|
| 内存泄漏 | 订阅者不注销会被一直持有（见 [07-引擎与性能/02-垃圾回收与内存](../07-引擎与性能/02-垃圾回收与内存.md)） |
| 通知顺序与错误 | 一个订阅者抛错，后续还通知吗？顺序有保证吗？ |

`EventTarget` 的 `{ signal }` 选项（用 `AbortSignal` 自动注销）解决了第一件事——这是它比手写观察者更好的地方。

### 责任链 → 显式组织

责任链让请求沿一条链传递，直到某个环节处理。**语言没有内建机制**，需要显式组织：

```console
$ node chain.mjs
  rate:ip      → 限流 处理了 rate:ip
  auth:token   → 鉴权 处理了 auth:token
  other        → 兜底 处理了 other
```

三个请求分别被链上的三个节点处理——首节点不处理则传给下一个，直到兜底。

**链的方向与顺序是设计决策**：上例中"限流"在最前（挡掉滥用请求，代价最小），"兜底"在最后。顺序错了会导致兜底把本该下传的请求拦下（本篇编写时第一版就把兜底放在了链首，实测三个请求全被它处理）。

**责任链的典型形态**是中间件（见 [06-Node.js平台/03-HTTP 服务](../06-Node.js平台/03-HTTP服务.md)）：每个中间件决定"处理"还是"交给下一个"。

### 状态 → 显式转移表

状态模式让**状态决定行为**，且状态转移是显式的：

```console
$ node behav.mjs
   idle --start--> running | running --pause--> paused | paused --stop--> idle
   非法转移: idle --pause--> ? （idle 不能 pause）
```

用一个转移表（`transitions[当前状态][动作] → 下一状态`）表达，**非法转移自然被拒绝**——表里没有的转移就是不允许的。

这与 [11-前端框架与状态管理/04-状态管理](../11-前端框架与状态管理/04-状态管理.md) 里的 reducer 是同一种思路：**把允许的变化穷举出来**，非法变化无处可去。区别是状态机显式区分"状态"与"动作"两个维度。

**状态多、转移复杂时用状态机库**（XState 一类）——手写转移表在状态数增长后难以维护，且难以可视化。

### 命令 → 函数 + 历史栈

命令模式把"操作"封装成值，从而能排队、记录、撤销：

```console
$ node behav.mjs
  执行后: 12
  撤销全部后: 5 （回到初值）
```

每个命令是一个带 `exec` 与 `undo` 的对象，执行时压入历史栈，撤销时弹出并反向执行。

**JavaScript 里命令就是函数**（或带元数据的对象）——不需要 `Command` 接口与 `Invoker` 类。**真正需要设计的是 `undo` 的语义**：能否精确还原？是否有副作用不可逆（如已发出的网络请求）？

### 其余模式

| 模式 | JavaScript 中的状态 |
|---|---|
| **模板方法** | 退化为**高阶函数**——把变化的部分作为回调参数传入 |
| **迭代器** | 由**迭代协议**内建（见 [02-对象模型与运行时/05](../02-对象模型与运行时/05-迭代协议与生成器.md)） |
| **中介者** | 退化为**一个共享的事件总线或 store** |
| **访问者** | 用**模式匹配 / 可辨识联合**替代（见 [08-TypeScript/02](../08-TypeScript/02-泛型与类型编程.md)） |
| **备忘录** | 用**不可变状态 + 快照**替代（见 [11-前端框架与状态管理/04](../11-前端框架与状态管理/04-状态管理.md)） |
| **解释器** | 少见；表达式解析通常用现成库或 `Function` 之外的手写解析器 |

## 连接：三个仍需要设计的模式

| 模式 | 语言没给什么 | 要自己决定什么 |
|---|---|---|
| **责任链** | 链的组织方式 | 顺序、终止条件、错误传播 |
| **状态机** | 状态与转移的表达 | 转移表、非法转移的处理 |
| **命令** | 撤销语义 | 如何还原、不可逆操作怎么办 |

其余的模式要么被语言内建（迭代器、观察者），要么退化为函数（策略、模板方法），要么被其他机制替代（访问者、备忘录）。

## 边界

- **策略表要求签名一致**：不一致说明它们不是同一个策略。
- **观察者要处理注销与错误**：`EventTarget` 的 `{ signal }` 解决注销。
- **责任链的顺序是设计决策**：兜底必须在最后。
- **状态机在状态多时要用库**：手写转移表难以维护。
- **命令的难点是 `undo`**：不可逆操作需要补偿而非撤销。
- **不要为已内建的能力造轮子**：迭代器、观察者都不必手写。
- **本篇的"退化"判断基于语言能力**：在缺少一等函数的语言里，这些模式仍有必要。
