# 事件循环与任务队列

> 前置：[03-标准库/07-Intl 国际化](../03-标准库/07-Intl国际化.md) · 后续：[02-回调到 Promise](./02-回调到Promise.md)

> **版本基准**：Node 24 stable / Node 26 latest。本篇示例实测环境：Node v24.13.1（V8 13.6），Windows x64。

## 本质

JavaScript 只有一个执行线程：一段代码在跑，别的代码无法插进来（见 [00-概览/01-JavaScript 全景](../00-概览/01-JavaScript全景.md)）。**并发不是靠多线程，而是靠把"什么时候执行什么"排进队列**——事件循环就是那个从队列里取任务的循环。

它做的一件事可以概括为：

```text
取一个宏任务 → 执行到底 → 清空微任务队列 → 取下一个宏任务 → …
```

理解这句话需要两个概念：

- **任务**（task，通常称宏任务）是排队执行的**一个**回调；
- **微任务**（microtask）是附着在当前任务末尾的**一串**回调，在当前任务结束、下一个任务开始之前**全部清空**。

ECMA-262 只定义微任务（Promise 的 job 队列），宏任务与整个循环由宿主定义——所以"事件循环"这个名字对应两套实现：浏览器的 HTML 事件循环与 Node.js 的 libuv 循环（见 [00-概览/01-JavaScript 全景](../00-概览/01-JavaScript全景.md) 的三层构成表）。

## 机制

### 顺序：同步 → 微任务 → 宏任务

```console
$ node ev.mjs
1 同步
2 同步结束
3 queueMicrotask
3b Promise.then
4 setTimeout(0)
```

两行同步代码先跑完（它们在**当前任务**里），然后清空微任务队列（`queueMicrotask` 与 `Promise.then`，按**入队顺序**），最后才轮到宏任务 `setTimeout`。

**微任务在每两个宏任务之间被完全清空**：

```console
$ node ev.mjs
A 宏任务开始
A 宏任务结束
  A 的微任务
  B 宏任务（嵌套 setTimeout）
```

宏任务 A 体内排的微任务，在 A 结束之后、B 开始之前执行。这条规则是"Promise 链上的回调总能在下一个宏任务之前跑完"的原因。

### `process.nextTick` 的位置比想象中微妙

Node 除微任务队列外还有一个 **`nextTick` 队列**。常规说法是它"优先于微任务"，实测只在**回调边界**成立：

```console
$ node tick.cjs
=== CommonJS 顶层 ===
1 同步
2 process.nextTick
3 Promise.then
3b queueMicrotask

=== 进入宏任务后 ===
  宏任务体结束
  nextTick
  microtask
```

CommonJS 顶层与宏任务体内，`nextTick` 都在微任务之前。但在 **ESM 顶层则反了过来**：

```console
$ node tick2.mjs
=== ESM 顶层 ===
  同步
  Promise.then
  queueMicrotask
  process.nextTick
```

原因是 **ESM 的模块求值本身就是一次微任务**。当代码已经运行在微任务里时，`nextTick` 队列要等当前微任务队列清空才轮到：

```console
$ node tick2.mjs
=== 嵌套在微任务里 ===
  微任务里排的 Promise
  微任务里排的 nextTick
```

**实践结论**：`process.nextTick` 与 `Promise.then` 的先后依赖"当前在哪个上下文"，不要依赖它们的相对顺序设计逻辑；需要"尽快但可预测"用 `queueMicrotask`，`nextTick` 只用于 Node 内部语义（如让回调在栈展开后立即执行）。

### 微任务可以饿死宏任务

微任务里再排微任务，会在本轮无限延长：

```console
$ node ev.mjs
宏任务在 4 轮微任务之后才执行
```

上例排了 4 轮，宏任务才轮到。若不加终止条件（`while (true) queueMicrotask(…)`），宏任务与定时器**永远不会执行**——事件循环被卡死。这是"不要在微任务里做长循环"的机制原因。

### 定时器不保证精确时间

```console
$ node ev2.mjs
  设定 10ms，实际 16 ms
```

`setTimeout(fn, 10)` 的含义是"**不早于** 10 毫秒后执行"，不是"10 毫秒后执行"。实际延迟受操作系统定时器精度（本机 Windows 上约 15.6 ms 一档）、当前任务长度、队列积压共同影响。**不要用 `setTimeout` 计时**——测量时间用 `performance.now()`。

### `setTimeout(0)` 与 `setImmediate`

```console
$ node ev2.mjs
  setImmediate
  setTimeout
```

顶层二者的顺序**不确定**（取决于进入事件循环时定时器是否已到期）。但在 **I/O 回调内部，`setImmediate` 恒先于 `setTimeout`**：

```console
$ node io.cjs
读到了 246 字节
  I/O 内 setImmediate
  I/O 内 setTimeout
```

因为 libuv 的循环有明确的阶段顺序：I/O 回调阶段之后就是 check 阶段（执行 `setImmediate`），而定时器阶段在下一轮。

## 连接：浏览器与 Node 的事件循环

| | 浏览器 | Node.js |
|---|---|---|
| 定义者 | HTML 规范 | Node.js（基于 libuv） |
| 宏任务来源 | 脚本、定时器、事件、渲染 | 定时器、I/O 回调、`setImmediate` |
| 微任务来源 | Promise、`queueMicrotask`、`MutationObserver` | 同左（`MutationObserver` 除外） |
| 额外队列 | — | `process.nextTick`（优先于微任务，见上文例外） |
| 渲染 | **在宏任务之间可能插入渲染帧** | 无渲染 |
| 特有 API | `requestAnimationFrame` | `setImmediate`、`process.nextTick` |

两套实现共享的抽象（"当前任务跑完才清空微任务队列"）足以解释绝大多数异步行为。差异集中在**渲染时机**（见 [05-浏览器平台/02-渲染管线与动画](../05-浏览器平台/02-渲染管线与动画.md)）与 **Node 的 I/O 阶段**（libuv 提供的轮询阶段，见 [06-Node.js平台/01-运行时与模块系统](../06-Node.js平台/01-运行时与模块系统.md)）。

## 边界

- **不要在微任务里做长循环**：会饿死宏任务与定时器，浏览器里还会冻结渲染。
- **`setTimeout` 不精确**：它只保证不早于给定时间；计时用 `performance.now()`。
- **不要依赖 `nextTick` 与 `Promise` 的相对顺序**：它随上下文（ESM 顶层 / 宏任务 / 微任务）变化。
- **`await` 之后的代码是微任务**：这是 `async` / `await` 与同步代码行为差异的根源，见 [03-async/await 与异步模式](./03-async-await与异步模式.md)。
- **事件循环是协作式的**：没有抢占，一段死循环即冻结整个线程——这是 JavaScript 无法用"多线程加锁"解决问题的原因，也是 [05-Worker 与共享内存](./05-Worker与共享内存.md) 存在的理由。
