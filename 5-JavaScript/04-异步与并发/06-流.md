# 流

> 前置：[05-Worker 与共享内存](./05-Worker与共享内存.md) · 后续：[05-浏览器平台/01-DOM 与事件模型](../05-浏览器平台/01-DOM与事件模型.md)

> **版本基准**：Node 24 stable / Node 26 latest。本篇示例实测环境：Node v24.13.1（V8 13.6），Windows x64。

## 本质

流（stream）是**数据分块、随时间到达**的抽象。它解决两个问题：

- **内存**：1 GB 的文件不能一次读进内存，但可以分成 64 KB 的块依次处理；
- **延迟**：视频不必等整个文件下载完才播放，第一块到了就能开始。

这两个问题在 [03-async/await 与异步模式](./03-async-await与异步模式.md) 里都没有答案——`await Promise.all(chunks)` 要求先把所有块**都拿到**。流的核心不是"异步"，而是**边生产边消费**，并且生产速度受消费速度约束。

## 机制

### 两种流，两个宿主

| | Web Streams | Node Streams |
|---|---|---|
| 定义者 | WHATWG Streams 规范 | Node.js（`node:stream`） |
| 可用范围 | 浏览器 + Node（Node 已内置实现） | 仅 Node |
| 主要构造 | `ReadableStream` / `WritableStream` / `TransformStream` | `Readable` / `Writable` / `Transform` |
| 管道 | `pipeThrough` / `pipeTo` | `pipe` / `pipeline` |
| 与 `fetch` 的关系 | `response.body` 就是 `ReadableStream` | 需转换 |

两者**模型一致、API 不同**。`fetch` 的响应体、`Blob.stream()`、`CompressionStream` 用的是 Web Streams；`fs.createReadStream`、`http` 的请求与响应用的是 Node Streams。

### 拉取与推送

**Web Streams 是拉取模型**：消费方主动要数据。

```console
$ node st.mjs
{ value: 'a', done: false }
{ value: 'b', done: false }
{ value: undefined, done: true }
```

`reader.read()` 每次返回 `{value, done}`——与迭代器协议同形（见 [02-对象模型与运行时/05-迭代协议与生成器](../02-对象模型与运行时/05-迭代协议与生成器.md)）。**要多少拿多少**，天然不会积压。

**Node Streams 是推送模型**：生产方推数据，通过 `pause` / `resume` 或返回 `false` 协调。

### 背压：流存在的真正理由

如果生产方不管消费方的速度，数据就会堆积在内存里。**背压**（backpressure）是"下游满了就暂停上游"的机制。

实测对照（1000 块 × 100 字节，写端 `highWaterMark = 4`）：

```console
$ node bp2.mjs
=== 尊重背压：pipeline ===
写端缓冲峰值: 100 字节  （highWaterMark = 4）

=== 忽略背压：on('data') 直接 write ===
写端缓冲峰值: 99900 字节  （highWaterMark = 4）
总数据量: 100000 字节
```

- 用 `pipeline` 连接时，写端缓冲峰值 **100 字节**——上游被暂停，数据没有被提前生产出来；
- 用 `on("data")` 手工 `write` 时，写端缓冲峰值 **99900 字节**——**几乎整个数据集都堆在内存里**。

`highWaterMark` 是"缓冲区上限"的提示值：超过它，`write()` 返回 `false`，`pipeline` 会据此暂停读端。**忽略这个返回值就等于放弃背压**。

**结论：用 `pipeline` / `pipeThrough`，不要手工 `on("data")` + `write`。**

### 两种流都能用 `for await...of` 消费

```console
$ node st.mjs
异步迭代: x,y,z
异步迭代: 10,20,30
```

Web `ReadableStream` 与 Node `Readable` 都实现了异步迭代器协议。**这是消费流最推荐的写法**——它自动处理背压与清理，不需要手工管理 `pause` / `resume`。

### 转换

```console
$ node st.mjs
TransformStream: 2,4,6
```

`TransformStream`（Web）与 `Transform`（Node）都是"可读可写"的中间段：写进去一块，吐出来一块。常见的变换有压缩、解压、加密、行切分、编码转换。

多个转换段可以串起来：

```javascript
await pipeline(
  fs.createReadStream("in.txt.gz"),
  zlib.createGunzip(),
  new Transform({ transform(c, e, cb) { cb(null, c.toString().toUpperCase()); } }),
  fs.createWriteStream("out.txt")
);
```

`pipeline` 的价值在于**自动传播错误与销毁所有段**——任一段出错，其余段都会被清理，不会留下悬挂的句柄。

### 取消

流是长寿命的资源，消费者中途退出时必须有取消通道。两体系各有一个动词：Web 侧是 `reader.cancel(reason)`（或 `stream.cancel()`），Node 侧是 `stream.destroy(err)`。取消后流的底层资源被释放，未读的数据被丢弃：

```console
$ node --input-type=module -e 'const rs = new ReadableStream({ start(c){ c.enqueue(1); c.enqueue(2); } }); const r = rs.getReader(); console.log("读到:", (await r.read()).value); await r.cancel("不要了"); console.log("取消后再读 done:", (await r.read()).done)'
读到: 1
取消后再读 done: true
```

`cancel()` 之后流即关闭，再读立刻得到 `done: true`。流的另一个取消入口是 `AbortSignal`——`fetch`、Node 的 `fs`/`http` 等产生流的 API 大多接受 `{ signal }`（信号机制见 [04-并发控制与取消](./04-并发控制与取消.md)），信号触发时流被取消、挂起的读取以 `AbortError` 结束。两条通道的分工：`cancel`/`destroy` 是**消费者主动退出**，`signal` 是**外部统一撤下**（超时、页面卸载）。

### 互操作

```console
$ node st.mjs
Node -> Web 转换可用: true
转换后消费: n1,n2
```

`Readable.toWeb()` / `Readable.fromWeb()`（以及 Writable 的对应方法）在两个体系之间转换。需要把 Node 的文件流交给期望 Web Streams 的 API（如 `fetch` 的请求体）时用它。

## 连接：什么时候用流

| 场景 | 用流 | 用一次性读取 |
|---|---|---|
| 大文件处理 | ✓ 内存恒定 | 文件必须小于可用内存 |
| 网络响应 | ✓ 边到边处理 | 必须等全部到达 |
| 需要看到全部数据才能决策 | ✗ | ✓ |
| 数据量小且确定 | ✗ | ✓ 更简单 |
| 需要随机访问（seek） | ✗ | ✓ |

**判断标准**：数据量是否可能超过内存，或首块数据是否在末块到达前就有用。两条都不满足时，一次性读取更简单也更快——流的每块都有调度开销。

## 边界

- **忽略背压等于没有流**：缓冲会一路涨到内存上限。
- **手工 `on("data")` 容易漏掉错误与清理**：用 `pipeline` / `for await`。
- **`pipe` 不传播错误**：`a.pipe(b)` 在 `a` 出错时不会销毁 `b`，用 `pipeline`（见 [01-语言核心/07-错误处理](../01-语言核心/07-错误处理.md)）。
- **流是一次性的**：消费完不能重放，需要重放就重新创建。
- **两种流不可直接混用**：`response.body`（Web）不能直接 `pipe` 进 Node 的 `fs.createWriteStream`，要先 `fromWeb`。
