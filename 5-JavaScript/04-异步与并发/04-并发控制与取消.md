# 并发控制与取消

> 前置：[03-async/await 与异步模式](./03-async-await与异步模式.md) · 后续：[05-Worker 与共享内存](./05-Worker与共享内存.md)

> **版本基准**：Node 24 stable / Node 26 latest。本篇示例实测环境：Node v24.13.1（V8 13.6），Windows x64。

## 本质

Promise **一旦发出就无法撤回**（见 [02-回调到 Promise](./02-回调到Promise.md)）。所以 JavaScript 的"取消"不是杀进程，而是**协作式**的：

```text
发起方 ──abort()──> 信号 ──通知──> 被取消方自行停止并清理
```

这是单线程模型的必然结果——没有抢占，任何代码都无法从外部中断另一段正在执行的代码（见 [01-事件循环与任务队列](./01-事件循环与任务队列.md)）。能做的只有"通知"，而响应通知需要**被取消方主动配合**。

承载这个通知的是 **`AbortSignal`**：一个可传递给异步操作的、只能从"未中止"翻转到"已中止"一次的信号对象。它由 `AbortController` 产生与触发。

**关键推论**：只有**声明支持 `signal` 选项的 API** 才真正可取消。对一个不读信号的异步操作传信号，什么也不会发生。

## 机制

### 基本形态

```javascript
const ac = new AbortController();
const { signal } = ac;

doSomething(signal);        // 把 signal 交给操作
ac.abort();                 // 触发中止
```

```console
$ node ab.mjs
signal.aborted 初始: false
被中止: Error 用户取消
abort 后 signal.aborted: true
```

信号有三个可观察的面：

- `signal.aborted`：布尔状态，只能从 `false` 翻到 `true`；
- `signal.addEventListener("abort", …)`：注册响应（`AbortSignal` 是 `EventTarget`，见 [05-浏览器平台/01-DOM 与事件模型](../05-浏览器平台/01-DOM与事件模型.md)）；
- `signal.reason`：中止的原因。

### `abort(reason)`：原因会被传递

不传参数时，原因是引擎构造的 `DOMException`，`name` 为 `"AbortError"`：

```console
$ node ab.mjs
默认 reason: DOMException AbortError
```

传入任意值时，该值**原样成为下游看到的拒绝原因**：

```console
$ node srv.mjs
错误类型: Error | 用户取消
```

这让调用方能区分"用户主动取消"与"系统超时"——只要在中止时给出不同的 `reason`。

### 信号是一次性的、可被多方共享

**一次 `abort()` 会中止所有监听该信号的操作**：

```console
$ node ab.mjs
结果: AbortError,AbortError,AbortError
```

三个任务共享同一个信号，一次中止全部停止。这是"页面离开时取消所有在途请求"这类需求的实现方式。反过来，**信号中止后无法复位**——需要重新发起就新建一个 `AbortController`。

### 内置的超时与合并信号

```console
$ node ab.mjs
typeof AbortSignal.timeout = function
超时: DOMException TimeoutError
```

```console
$ node ab2.mjs
merged.aborted 初始: false
ac.signal === merged ? false
触发 ac.abort()
合并信号触发: DOMException AbortError
merged.aborted 事后: true
```

- **`AbortSignal.timeout(ms)`**：到点自动中止，`reason` 是 `name` 为 `"TimeoutError"` 的 `DOMException`。它比自己用 `setTimeout` 拼一个信号更简洁，且不会泄漏定时器。
- **`AbortSignal.any([…])`**：合并多个信号，任一触发即全部生效。上例把"用户取消"与"5 秒超时"合并——两种原因都能中止同一个请求。

### 让自定义操作支持取消

自己写的异步函数要能被取消，需要**监听信号并清理资源**：

```javascript
function sleep(ms, signal) {
  return new Promise((resolve, reject) => {
    const timer = setTimeout(resolve, ms);
    signal?.addEventListener("abort", () => {
      clearTimeout(timer);            // 清理：取消定时器
      reject(signal.reason);          // 以中止原因拒绝
    }, { once: true });
  });
}
```

两个要点：**必须清理**（`clearTimeout`、关闭连接、释放句柄），否则"取消了"只是调用方不再等，资源照旧占用；**`{ once: true }`** 避免重复触发。

### 并发限流

不限流地发起大量异步操作会耗尽连接数、内存或对端配额。固定并发数的做法是**起 N 个 worker 拉取任务**：

```javascript
async function pool(items, limit, worker) {
  const results = new Array(items.length);
  let next = 0;
  const run = async () => {
    while (true) {
      const i = next++;
      if (i >= items.length) return;
      results[i] = await worker(items[i], i);
    }
  };
  await Promise.all(Array.from({ length: Math.min(limit, items.length) }, run));
  return results;
}
```

```console
$ node lim.mjs
结果: 10,20,30,40,50,60,70,80 | 峰值并发: 3 | 耗时: 99 ms
峰值并发: 8 | 耗时: 33 ms
```

8 个任务各耗时约 30 ms：限流 3 个并发耗时约 99 ms，全并发约 33 ms。**限流是用吞吐换稳定**——它不是免费的，只在需要保护资源或对端时使用。

注意 `pool` 里 `results[i] = …` 按原下标写回，因此**结果顺序与输入一致**，与 `Promise.all` 相同。

### 超时的两种实现，语义不同

| 手段 | 效果 |
|---|---|
| `Promise.race([op, timeout])` | 调用方不再等待，**底层操作仍在跑** |
| `fetch(url, { signal: AbortSignal.timeout(ms) })` | **真正中止**底层操作，释放连接 |

`race` 只是"不等了"——那个请求会继续占用连接直到自己结束，在重试场景下会堆积。**能用信号就用信号**：

```console
$ node srv.mjs
错误类型: DOMException | name: TimeoutError | The operation was aborted due to timeout
```

`race` 仍有位置：对**不支持信号**的操作，或者只是想让竞速逻辑决定采用哪个结果。

## 连接：三种"停止"手段

| 手段 | 能否中止底层操作 | 适用 |
|---|---|---|
| 忽略结果（不 `await`、不处理） | 否 | 无所谓副作用的场合 |
| `Promise.race` 超时 | 否 | 不支持信号的 API |
| `AbortSignal` | **是**（若 API 支持） | `fetch`、`fs`、流、自定义操作 |

## 边界

- **不是所有 API 都支持 `signal`**：传了也不生效。查文档确认（`fetch`、`node:fs`、`node:http`、`node:stream`、`node:timers/promises` 等支持）。
- **信号不可复位**：中止后要重新操作就得新建 `AbortController`。
- **被取消方必须自己清理资源**：只 `reject` 不清理等于泄漏。
- **`AbortSignal.timeout` 的定时器由引擎管理**，不会因为操作提前完成而留下悬挂的 `setTimeout`——这也是它优于手写 `setTimeout` 的地方。
- **注意 `await` 的挂起位置**：把 `setTimeout(() => ac.abort(), …)` 写在 `await` **之后**，它会等到 `await` 结束才被调度，永远不会及时触发。本篇编写过程中实测踩到过这个坑——中止的调度必须在 `await` 之前。
