# 路由与 SSR

> 前置：[04-状态管理](./04-状态管理.md) · 后续：[12-设计模式/01-设计模式总览](../12-设计模式/01-设计模式总览.md)

> **版本基准**：React Router 8.4 / Vue Router 5.3 / Next.js 16.3 / Nuxt 4.5。
> **实测范围说明**：**路由匹配、两种 URL 模式、查询参数、懒加载在本机 Node v24.13.1 实测**（都是纯 JavaScript）。**水合与渲染模式的实际行为**依赖浏览器与服务端环境，未在本机实测，依据 Next.js / Nuxt 公开文档陈述。

## 本质

单页应用（SPA）把"页面"从**服务端返回的文档**变成了**客户端渲染的视图**。好处是切换页面不必重新加载文档、状态得以保留；代价由**路由**与**渲染模式**两个机制分别承担：

| 问题 | 机制 |
|---|---|
| URL 变了，显示哪块界面 | **路由**——URL 与视图的映射 |
| 首屏空白与搜索引擎抓不到内容 | **SSR / SSG**——把渲染挪回服务端 |

两个问题都源于同一件事：**SPA 的 HTML 初始是空的，内容由 JavaScript 在浏览器里生成**。

## 机制

### 路由匹配：路径模式 → 参数

路由的核心是一个**模式匹配**：把 `/users/:id` 这样的模式与 `/users/42` 这样的实际路径匹配，提取出参数。

```console
$ node router.mjs
  /users/:id                   ← /users/42            → {"id":"42"}
  /users/:id/posts/:postId     ← /users/42/posts/7    → {"id":"42","postId":"7"}
```

`:` 开头的是**动态段**，匹配一段非 `/` 的字符；参数值需要 `decodeURIComponent` 解码（路径里可能有中文或空格）。路由库在这之上加了嵌套路由、优先级排序、通配符等。

### 两种 URL 模式

| 模式 | URL 形态 | 原理 |
|---|---|---|
| **history** | `https://app.com/users/42` | History API（`pushState` / `replaceState`） |
| **hash** | `https://app.com/#/users/42` | 修改 `location.hash` |

```console
$ node router.mjs
  history  pathname="/users/42"              hash="#top"                     → 路由串 "/users/42?tab=posts"
  hash     pathname="/"                      hash="#/users/42?tab=posts"     → 路由串 "/users/42?tab=posts"
```

两者提取出的**路由串完全相同**，差别在于 URL 长什么样：

| | history | hash |
|---|---|---|
| URL 观感 | 干净 | 带 `#` |
| 服务端要求 | **需要配置**：所有路径都返回同一个 HTML | 无需配置（`#` 之后不发给服务端） |
| SEO | 好 | 差 |
| 锚点跳转 | 与路由冲突 | 天然分离 |

**history 模式需要服务端配合**：直接访问 `https://app.com/users/42` 时，服务端收到的路径是 `/users/42`，如果它去磁盘找这个文件会 404。必须配置成"所有未匹配的路径都返回 `index.html`"，让客户端路由接手。

### 查询参数与路由参数

| | 位置 | 用途 |
|---|---|---|
| **路由参数**（`/users/:id`） | 路径的一部分 | 标识资源 |
| **查询参数**（`?tab=posts`） | `?` 之后 | 可选的筛选/排序/分页 |

```console
$ node router.mjs
  q = "你好 世界" | getAll('tag') = ["a","b"]
```

用 `URLSearchParams` 读写（见 [05-浏览器平台/03-网络与同源策略](../05-浏览器平台/03-网络与同源策略.md)），它处理编解码与重复参数。

**判断标准**：这个状态"是不是资源的一部分"。用户分享 URL 时应该带上的放路由参数，可选的展示偏好放查询参数。

### 懒加载：按路由切分产物

```console
$ node router.mjs
  静态 import  → 启动时全部加载
  动态 import() → 进入该路由时才加载（返回 Promise）
  动态加载 HeavyPage 耗时 11ms（真实场景是网络往返）
```

路由级懒加载是**首屏体积优化**的主要手段：把每个路由的代码切成独立产物，用户只下载当前需要的（见 [09-工程化/03-打包与转译](../09-工程化/03-打包与转译.md) 的代码分割）。

代价是**切换路由时多一次网络往返**，所以要配合加载态提示，并对可能马上要用的路由做预加载。

### SPA 的两个代价与渲染模式谱系

| 模式 | 何时渲染 | 首屏 | SEO | 数据新鲜度 |
|---|---|---|---|---|
| **CSR** | 浏览器 | 慢（等 JS 下载执行） | 差 | 实时 |
| **SSR** | 每次请求时服务端 | 快 | 好 | 实时 |
| **SSG** | 构建时 | 最快（可 CDN） | 好 | 构建时 |
| **ISR / 增量静态** | 构建时 + 后台按需重建 | 快 | 好 | 有延迟 |

选择依据是**内容的变化频率**与**是否个性化**：

- 内容几乎不变（博客、文档）→ SSG；
- 内容频繁变化且需要 SEO（电商、新闻）→ SSR；
- 登录后的个性化界面（后台管理）→ CSR 就够。

**SSR 不是免费的**：每个请求都要在服务端执行组件、等待数据，服务端成本显著上升；且代码要能在服务端运行（不能直接访问 `window` / `document`）。

### 水合：SSR 的关键步骤

SSR 返回的 HTML 是"死的"——没有事件监听、没有状态。**水合**（hydration）是浏览器下载完 JavaScript 后，把这份 HTML 接管过来的过程：

```text
服务端：执行组件 → 生成 HTML → 发给浏览器
浏览器：先显示 HTML（用户已能看到内容）
        下载 JS → 执行组件 → 与现有 HTML 比对 → 绑定事件
```

**水合的两条约束**：

| 约束 | 后果 |
|---|---|
| 服务端与客户端渲染结果必须一致 | 不一致会水合失败，React 会丢弃服务端 HTML 重新渲染 |
| 水合期间页面不可交互 | 用户看得到但点不动，称为"水合间隙" |

"服务端与客户端结果一致"排除了很多写法：`Date.now()`、`Math.random()`、`localStorage`、`window` 的判断，在两侧会得到不同结果。这类内容必须推迟到挂载后渲染。

### 元框架

Next.js、Nuxt 把路由、数据获取、渲染模式整合成一套约定：

| 能力 | 内容 |
|---|---|
| 文件系统路由 | 目录结构即路由表 |
| 数据获取约定 | 服务端预取、客户端缓存与重新验证 |
| 渲染模式选择 | 按路由或按页面选择 SSR / SSG / ISR / CSR |
| 构建与部署 | 产物形态与部署目标 |

**它们解决的问题是"把上面这些手工拼装变成配置"**，而不是引入了新的渲染原理。

**服务端组件**（React Server Components）是更进一步的方向：组件本身在服务端执行，其代码**不进客户端产物**——这对"数据获取逻辑不该发到浏览器"的场景有实质收益，但也引入了"哪些组件能在哪运行"的新心智负担。

## 连接：渲染模式选择

| 场景 | 选择 |
|---|---|
| 内容固定、可预生成 | SSG |
| 内容频繁变、需 SEO | SSR |
| 内容变化但不紧急 | ISR |
| 登录后个性化、无需 SEO | CSR |
| 首屏要求高 + 有交互 | SSR + 懒加载 + 代码分割 |

## 边界

- **history 模式需要服务端配置**：否则刷新页面 404。
- **路由参数要解码**：路径可能含非 ASCII 字符。
- **SSR 代码不能直接用浏览器 API**：`window` / `document` 在服务端不存在。
- **水合要求两侧渲染一致**：时间、随机数、本地存储都会破坏一致性。
- **水合期间不可交互**：这是 SSR 的固有代价。
- **SSR 增加服务端成本**：每请求都要执行组件与取数。
- **懒加载会带来切换延迟**：配合加载态与预加载。
- **服务端组件改变组件的心智模型**：需要区分"在哪运行"。
