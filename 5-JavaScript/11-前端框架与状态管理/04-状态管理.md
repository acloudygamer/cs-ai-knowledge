# 状态管理

> 前置：[03-Vue](./03-Vue.md) · 后续：[05-路由与 SSR](./05-路由与SSR.md)

> **版本基准**：Redux 5.0 / Redux Toolkit 2.12 / Pinia 4.0 / MobX 6.x。本篇示例实测环境：Node v24.13.1（V8 13.6），Windows x64。
> **实测范围说明**：**Redux 的 reducer 与 store 机制在本机 Node v24.13.1 实测**（它们是纯 JavaScript，与浏览器无关）。**框架集成部分**未在本机实测。

## 本质

状态管理要解决的是**跨组件的状态共享**。它回答三个问题：

| 问题 | 要决定什么 |
|---|---|
| **放哪** | 状态存在什么地方，谁能访问 |
| **怎么改** | 谁有权修改，修改的路径是什么 |
| **改完怎么通知** | 用到它的地方如何知道 |

不用任何库也能做：把状态提到共同祖先组件，通过 props 逐层传下去（称为 **prop drilling**）。层数一多，中间层组件被迫传递自己用不到的 props，这就是需要专门方案的临界点。

**但"需要状态管理库"的门槛比多数人以为的高**。组件本地状态、父子传值、`Context` / `provide-inject` 能解决绝大多数场景。引入全局 store 的代价是**状态的生命周期与来源变得模糊**——任何组件都能改它，也就没人知道它什么时候会变。

## 机制

### 三种模型

| 模型 | 代表 | 状态本身 | 如何知道变化 |
|---|---|---|---|
| **不可变快照 + 单向数据流** | Redux | 只读，每次产生新对象 | 引用比较 |
| **透明响应式** | MobX | 可变对象 | 属性被读写时自动追踪 |
| **组合式响应式** | Pinia | 可变对象（Vue 响应式） | 同 Vue（见 [01-框架原理](./01-框架原理.md)） |

三者的差别在**"变化如何被感知"**：Redux 靠"新对象与旧对象不是同一个"；另两者靠拦截属性的读写。

### Redux：纯函数 + 单向数据流

Redux 的全部约束可以压缩成一句话：**状态只能通过纯函数计算得出**。

```javascript
function counter(state = { count: 0, log: [] }, action) {
  switch (action.type) {
    case "inc": return { ...state, count: state.count + 1, log: [...state.log, "+1"] };
    case "add": return { ...state, count: state.count + action.n, log: [...state.log, `+${action.n}`] };
    default: return state;
  }
}
```

实测它带来的三条性质：

```console
$ node store.mjs
  s0 = {"count":0,"log":[]}
  s2 = {"count":6,"log":["+1","+5"]}
  旧状态未被修改（s0.count 仍为 0 ）: true
  新状态是新对象: true
```

**一、旧状态不被修改。** reducer 用展开运算符产生新对象，`s0` 始终是 `{count: 0}`。这是"不可变更新"的落实，也是虚拟 DOM 比对能工作的前提（见 [01-框架原理](./01-框架原理.md)）。

**二、同样的 action 序列得到同样的结果。**

```console
$ node store.mjs
  重放结果: {"count":6,"log":["+1","+5"]} | 与直接执行一致: true
```

这就是"可预测"的含义：状态是 `(初始状态, action 序列)` 的确定性函数。它让**时间旅行调试**（回放历史 action）与**状态快照测试**成为可能。前提是 reducer 必须**纯**——不能有随机数、当前时间、网络请求。

**三、未处理的 action 返回同一个对象。**

```console
$ node store.mjs
  counter(s2, {type:'unknown'}) === s2 ? true
```

返回原引用而非新对象，使订阅方可以**用引用相等判断"有没有变"**，避免无谓的重新渲染：

```console
$ node store.mjs
  两次有效 dispatch，通知次数: 2 （无效 action 不通知）
  取消订阅后通知次数: 2
```

这条"引用相等即未变"的约定，是 Redux 生态里 `connect` / `useSelector` 做优化的基础。

**Redux 的代价是模板代码**：一个简单状态要写 action type、action creator、reducer 分支。Redux Toolkit 用 `createSlice` 消除大部分样板，并内置 Immer 让"可变写法 + 不可变结果"成为可能。

### Pinia：Vue 的组合式响应式

Pinia 建立在 Vue 的响应式之上（见 [03-Vue](./03-Vue.md)），store 就是一个组合式函数：

- **没有 action type 与 reducer**——直接定义方法，方法里改状态；
- **没有单向数据流的强制**——响应式会自动通知；
- **模块化是天然的**——每个 store 是独立文件，互相引用。

它比 Redux 少一层间接，代价是**失去"可重放"**：状态变化不再是一个可序列化的 action 序列，时间旅行调试能力有限。

### MobX：透明响应式

MobX 追踪可观察对象的读写，自动推导"哪些计算依赖哪些状态"。写法最接近普通 JavaScript（直接改属性），但**响应式的边界不显式**——要理解 `observable` / `computed` / `action` 各自的作用，否则会遇到"改了但没更新"。

### 关键区分：客户端状态与服务端状态

这是现代前端状态管理最重要的一条分界：

| | 客户端状态 | 服务端状态 |
|---|---|---|
| 例子 | 主题、侧边栏开合、表单草稿 | 用户列表、订单详情 |
| 真相来源 | **前端** | **服务端** |
| 需要处理 | 持久化、跨组件共享 | 缓存、失效、重新获取、并发、乐观更新 |
| 工具 | Redux / Pinia / Context | TanStack Query / SWR 等数据获取库 |

**把服务端数据塞进 Redux 是常见错误**：它缺的正是"缓存什么时候过期""网络恢复了要不要重取""两个组件同时请求同一份数据怎么办"这些能力，而这些都要手工实现。

**先判断状态属于哪一类**：服务端状态交给数据获取库，客户端状态才考虑全局 store。

### 什么时候不需要状态管理库

| 场景 | 方案 |
|---|---|
| 单个组件用 | 组件本地状态 |
| 父子传值 | props / emit |
| 跨几层传值，但不常变 | Context / provide-inject |
| 服务端数据 | 数据获取库 |
| 真正的全局客户端状态，且多处读写 | store |

**先不加库**。等到"状态被多处修改、来源难以追踪"成为实际痛点时再加，比一开始就上全局 store 更容易得到清晰的架构。

## 连接：三种模型对照

| | Redux | MobX | Pinia |
|---|---|---|---|
| 状态 | 不可变 | 可变 | 可变 |
| 更新方式 | dispatch action → reducer | 直接改属性 | 调用方法改状态 |
| 变化感知 | 引用比较 | 属性读写追踪 | Vue 响应式 |
| 可重放 | **是** | 否 | 否 |
| 样板代码 | 多（RTK 已大幅减少） | 少 | 少 |
| 与框架 | 框架无关 | 框架无关 | Vue 专用 |
| 心智负担 | 理解单向数据流 | 理解响应式边界 | 理解 Vue 响应式 |

## 边界

- **不要过早引入全局 store**：组件状态与 Context 能解决大多数问题。
- **服务端状态不要放全局 store**：它需要的是缓存与失效策略。
- **reducer 必须纯**：副作用会破坏可重放性。
- **不可变更新不能直接改状态**：否则引用相等，比对无法识别变化（见 [01-框架原理](./01-框架原理.md)）。
- **store 不是垃圾桶**：什么都往里放会让状态的生命周期无从追踪。
- **调试能力有代价**：Redux 的可重放换来了样板代码，Pinia 的简洁换来了可调试性。
