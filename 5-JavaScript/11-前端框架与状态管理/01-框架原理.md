# 框架原理

> 前置：[10-测试与质量/04-覆盖率与质量门](../10-测试与质量/04-覆盖率与质量门.md) · 后续：[02-React](./02-React.md)

> **版本基准**：React 19.3 / Vue 3.5（截至 2026-09 的最新版）。本篇示例实测环境：Node v24.13.1（V8 13.6），Windows x64。
> **实测范围说明**：**本篇的机制部分在本机 Node v24.13.1 实测**——响应式与虚拟 DOM diff 都是纯 JavaScript 机制，与浏览器无关，可脱离框架直接演示。**组件渲染与浏览器集成**未在本机实测。

## 本质

前端框架解决的核心问题只有一个：**状态变了，界面怎么更新**。

不用框架的做法是"状态变了就手工改 DOM"。规模一大，同一份状态会散落在多处 DOM 更新代码里，改一处漏一处。

框架的解法是把这个过程自动化，两条主要路线：

| 路线 | 思路 | 代表 |
|---|---|---|
| **响应式** | 追踪状态的读与写，谁读了它、它变了就通知谁 | Vue、Svelte、Solid |
| **虚拟 DOM** | 状态变了就重新算出整棵新树，与旧树比对，只应用差异 | React |

两条路线的目标相同（**把"更新界面"从手工劳动变成状态变化的自动结果**），取舍在"怎么找出要改的部分"。

## 机制

### 响应式：读时收集依赖，写时触发

用 `Proxy` 拦截属性的读写即可实现最小响应式（实测）：

```javascript
const state = reactive({ count: 0, name: "甲" });
effect(() => { console.log(state.count); });   // 副作用读取了 count
state.count = 1;    // 触发副作用
state.count = 2;    // 再次触发
state.name = "乙";  // 不触发——该副作用没有读取 name
```

```console
$ node reactivity.mjs
  [副作用 1] count = 0
  [副作用 2] count = 1
  [副作用 3] count = 2
  改 name 未触发 count 的副作用，共执行 3 次
```

机制是三步：

1. **`get` 陷阱**：读取属性时，把"当前正在执行的副作用"记录为该属性的依赖；
2. **`set` 陷阱**：写入属性时，取出该属性的依赖集合，逐个重新执行；
3. **`activeEffect`**：一个全局变量标记"当前在跑哪个副作用"，`effect(fn)` 执行时设置它，执行完清空。

**依赖是惰性收集的**——只有副作用真正读到的属性才会被记录：

```console
$ node reactivity.mjs
  改 b 后 a 的副作用执行次数: 1 （未读取 b，故不被 b 触发）
```

这是响应式的核心优势：**更新粒度精确到属性**，不需要比对，也不需要重新计算整棵树。代价是**必须在同步执行中读取**——把状态访问放进 `await` 之后或回调里，依赖就收集不到（这也是 Vue 的 `watchEffect` 强调"同步执行"的原因）。

### 虚拟 DOM：算出新树，比对差异

另一条路线不追踪依赖，而是**重新渲染出整棵新树，与旧树比对，只应用差异**。

```javascript
const v1 = h("div", { class: "box" }, h("h1", null, "标题"), h("p", null, "第一段"), h("p", null, "第二段"));
const v2 = h("div", { class: "box active" }, h("h1", null, "标题"), h("p", null, "第一段改"), h("p", null, "第二段"));
```

```console
$ node vdom.mjs
    root: 属性 class: box → box active
    root>1>0: 文本 "第一段" → "第一段改"
  （h1 的文本、第二段未变，未产生补丁）
```

比对结果是**两条补丁**——未变化的部分不产生任何 DOM 操作。虚拟 DOM 的价值不在于"虚拟"比"真实"快（虚拟 DOM 操作本身有开销），而在于**把"哪里变了"的计算变成了一次廉价的树比对**，让"每次状态变化就重新描述整个界面"这种简单的心智模型成为可能。

### `key`：让比对知道"这是同一个东西"

diff 默认**按位置比对**。列表头部插入一项时，位置比对会得出完全错误的结论（实测）：

```console
$ node vdom.mjs
    root>0>0: 文本 "A" → "X"
    root>1>0: 文本 "B" → "A"
    root>2: 新建 <li>
  → 位置 0 被判为'文本 A→X'、位置 1 判为'B→A'、位置 2 新建，而非'头部插入一项'
```

三项都变了——**三次 DOM 操作**，而且如果这些 `<li>` 里有输入框，用户已经输入的内容会被错位保留。

带上 `key` 后，比对按标识匹配：

```console
$ node vdom.mjs
    ul: 插入 key=x
  → 准确识别为'插入一项'，既有两项不动
```

**一次 DOM 操作**，其余两项完全不动。

这就是"列表渲染必须加 key"的原因：**key 告诉框架"哪个元素对应哪个数据"**，让比对从"按位置猜"变成"按标识认"。

**key 必须稳定且唯一**：

| 做法 | 后果 |
|---|---|
| 用数据的唯一 ID | 正确 |
| 用数组下标 | 等于没有 key——插入/删除时下标全变 |
| 用随机数或 `Math.random()` | 每次渲染都视为全新元素，整个列表重建 |

用下标作 key 是常见错误：它在"只在尾部追加"时恰好正确，一旦在中间增删就退化成按位置比对。

### 两条路线的取舍

| | 响应式 | 虚拟 DOM |
|---|---|---|
| 找出变化的代价 | 收集依赖（运行时开销小） | 比对整棵树（与树大小相关） |
| 更新粒度 | 精确到属性 | 精确到节点 |
| 心智模型 | 需要理解依赖追踪 | "重新渲染整棵树"，更简单 |
| 与不可变数据 | 需要可变对象 | 天然契合（新树就是新对象） |
| 典型问题 | 依赖收集失败（异步中读状态） | 大列表的比对开销 |

实践中两者都在向对方靠拢：Vue 有编译期的静态分析优化，React 有 `memo` / `useMemo` 减少不必要的重新渲染。

## 连接：框架提供的三件事

| 能力 | 内容 |
|---|---|
| **状态 → 界面** | 响应式或虚拟 DOM（本篇） |
| **组件化** | 把界面拆成可复用的单元，各有自己的状态与生命周期 |
| **渲染调度** | 批量更新、优先级、并发渲染（见 [02-React](./02-React.md)） |

框架本身**不提供**状态管理方案、路由、数据获取——这些是生态层，见 [04-状态管理](./04-状态管理.md) 与 [05-路由与 SSR](./05-路由与SSR.md)。

## 边界

- **响应式依赖"同步读取"**：异步回调里读状态收集不到依赖。
- **虚拟 DOM 不是"更快"**：它比直接操作 DOM 慢，价值在开发模型。
- **列表必须用稳定唯一的 key**：下标作 key 等于没有 key。
- **框架不解决状态设计**：状态放哪里、怎么划分，是应用架构问题。
- **两条路线都不改变 JavaScript 的执行模型**：所有更新仍发生在事件循环上（见 [04-异步与并发/01-事件循环与任务队列](../04-异步与并发/01-事件循环与任务队列.md)）。
- **本篇的响应式与 diff 是最小实现**：真实框架在此之上有编译期优化、调度、错误处理，机制相同但工程复杂度高得多。
