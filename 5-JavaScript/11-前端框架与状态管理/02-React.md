# React

> **版本基准**：React 19.3 / react-dom 19.3。
> **实测范围说明**：**本篇无本机实测**——组件渲染依赖浏览器 DOM 环境。事实依据为 React 官方文档与 [01-框架原理](./01-框架原理.md) 中已实测的虚拟 DOM 机制。文中不给出控制台输出。

## 本质

React 的核心主张是一句话：**UI 是状态的函数**。

```text
UI = f(state)
```

它对应 [01-框架原理](./01-框架原理.md) 里的虚拟 DOM 路线：**每次状态变化，重新执行组件函数，得到一棵新的元素树，交给 React 比对并应用差异**。

这条主张推出 React 的全部设计特征：

- **组件是函数**：接收 `props`，返回"元素描述"（不是 DOM 节点）；
- **数据单向流动**：`props` 向下传，事件向上报；
- **状态不可变更新**：`state` 不能直接改，必须产生新值——因为比对的前提是"新树与旧树是两个不同的对象"。

理解"组件函数会被反复执行"是理解 React 的关键：**它不是"初始化一次然后更新"的模型**，而是"每次渲染都重新运行"。

## 机制

### 元素、组件、实例

| 概念 | 是什么 |
|---|---|
| **元素**（element） | 一个普通对象，描述"要渲染什么"（`{ type, props }`） |
| **组件**（component） | 返回元素的函数 |
| **实例** | 组件在界面中的一次具体存在（React 内部管理，代码里拿不到） |

JSX 是**语法糖**——`<div className="box">` 编译成一次函数调用（React 17 起用 `jsx` 运行时，不再需要显式 `import React`）。所以 JSX 里的一切都是 JavaScript 表达式，`{}` 里可以放任意表达式。

### 单向数据流

```text
父组件 ──props──▶ 子组件 ──回调 props──▶ 父组件更新 state ──▶ 重新渲染
```

**子组件不能直接改父组件的状态**，只能调用父组件传下来的回调。这让"数据从哪来、被谁改"有唯一答案——对照 [01-框架原理](./01-框架原理.md) 里"手工改 DOM"的散落更新，这是可维护性的来源。

`props` 是**只读的**：子组件改 `props` 是错误用法，React 会在开发模式下警告。

### Hooks：让函数组件拥有状态

函数组件每次渲染都重新执行，因此**普通局部变量无法跨渲染保留**。`useState` 提供了这个能力：

```javascript
const [count, setCount] = useState(0);
```

它返回的 `count` 是**本次渲染的快照**——不是"一个会变的变量"。这解释了几条容易困惑的行为：

| 行为 | 原因 |
|---|---|
| 调用 `setCount(count + 1)` 两次只加 1 | 两次都基于同一次渲染的 `count` 快照 |
| 连续三次 `setCount(count + 1)` 要用函数式写法 | `setCount(c => c + 1)` 基于**最新值**而不是快照 |
| `setState` 后立刻读 `state` 得到旧值 | 状态更新是**异步批量**的，本次渲染的 `state` 不变 |

**状态更新是批量的**：同一个事件处理函数里的多次 `setState` 会合并成一次重新渲染。这与 [04-异步与并发/01-事件循环与任务队列](../04-异步与并发/01-事件循环与任务队列.md) 的批量机制相关，也是"渲染次数比 `setState` 次数少"的原因。

**Hooks 的两条规则**：

| 规则 | 原因 |
|---|---|
| 只在顶层调用，不放循环/条件/嵌套函数 | React 靠**调用顺序**匹配状态，顺序变了就错位 |
| 只在 React 函数组件或自定义 Hook 里调用 | 依赖 React 的运行时上下文 |

第二条规则是"Hooks 是数组"这个实现方式的直接后果：第 N 个 `useState` 对应第 N 个状态槽，条件调用会让后续所有槽位错位。

### `useEffect`：与外部系统同步

`useEffect` 用于**副作用**（订阅、手动改 DOM、发请求）。它的语义由三部分构成：

| 部分 | 作用 |
|---|---|
| 回调函数 | 副作用本体 |
| 依赖数组 | 这些值变了才重新执行 |
| 返回的清理函数 | 在下一次执行前、组件卸载时调用 |

| 依赖数组 | 执行时机 |
|---|---|
| 不传 | 每次渲染后都执行 |
| `[]` | 仅挂载后执行一次 |
| `[a, b]` | `a` 或 `b` 变化时执行 |

**清理函数是必须的**，只要副作用持有外部资源：订阅要取消、定时器要清除、请求要中止。不做清理会导致内存泄漏与重复订阅（见 [07-引擎与性能/02-垃圾回收与内存](../07-引擎与性能/02-垃圾回收与内存.md)）。

**不要用 `useEffect` 做"派生状态"**：能通过 `props` / `state` 直接算出来的值，在渲染时直接算，不要放进状态再用 `useEffect` 同步——那会多一次渲染，且容易产生不一致的中间态。

### 渲染的两个阶段

| 阶段 | 做什么 | 可中断 |
|---|---|---|
| **渲染（render）** | 执行组件函数，算出新元素树，比对差异 | 可以（并发渲染） |
| **提交（commit）** | 把差异应用到真实 DOM | 不可以 |

**渲染阶段必须是纯的**——同样的输入产生同样的输出，不改外部变量、不发请求。因为渲染可能被中断、被丢弃、被重复执行。副作用必须放 `useEffect`（在提交后运行）。

React 18 起的**并发渲染**让渲染阶段可中断：高优先级更新（如输入）可以打断低优先级的重新渲染。这是"渲染阶段必须纯"从建议变成硬约束的原因。

### 性能优化的三个工具与它们的边界

| 工具 | 作用 | 何时用 |
|---|---|---|
| `React.memo` | 跳过 props 未变的组件重新渲染 | 组件渲染代价高且 props 稳定 |
| `useMemo` | 缓存计算结果 | 计算确实昂贵 |
| `useCallback` | 缓存函数引用 | 传给 `memo` 组件或作依赖 |

**它们都是优化，不是正确性要求**。默认不用，用之前先测量（见 [07-引擎与性能/03-性能剖析与优化](../07-引擎与性能/03-性能剖析与优化.md)）。常见反模式是到处包 `useMemo`，带来依赖数组维护成本却毫无收益——缓存本身也有开销。

## 连接：Hooks 的职责

| Hook | 用途 |
|---|---|
| `useState` | 组件本地状态 |
| `useReducer` | 复杂状态逻辑（多个字段联动） |
| `useEffect` | 与外部系统同步 |
| `useRef` | 跨渲染保留值 / 引用 DOM 节点（改它不触发渲染） |
| `useContext` | 读取跨层级共享值 |
| `useMemo` / `useCallback` | 缓存（优化，非必需） |
| `useId` | 生成稳定的无障碍属性 ID |

**状态放哪**是比"用哪个 Hook"更重要的问题：能由 `props` 算出来的不放状态；只被一个组件用的放它自己；多个组件共享的往上提或交给状态管理（见 [04-状态管理](./04-状态管理.md)）。

## 边界

- **组件函数会被反复执行**：不要在里面放副作用。
- **状态是快照，不是变量**：连续更新要用函数式写法。
- **Hooks 依赖调用顺序**：不能条件调用。
- **`useEffect` 的依赖数组要完整**：漏掉依赖会读到过期值。
- **优化工具默认不用**：先测量，再优化。
- **不要直接改状态**：必须产生新对象，否则比对无法识别变化。
- **React 只负责视图层**：路由、数据获取、状态管理都在生态层。
