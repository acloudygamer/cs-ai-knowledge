# 创建型模式

## 单例模式

### 定义

**单例模式保证一个类仅有一个全局实例，并提供全局访问点。** 实例延迟创建（懒汉式）或类加载时创建（饿汉式），由一个私有静态属性记录。

单例的本质是一个**全局唯一资源管理器**：在任意时刻，系统内只有一个实例存在，所有对该资源的访问都通过同一入口。

### 数学模型

设 $I$ 为实例存在性谓词，$I = \text{true}$ 当且仅当实例已创建。构造函数 $C$ 的行为定义为：

$$
C() \triangleq \begin{cases}
\text{return } s & \text{if } I = \text{true} \\
\text{create } s,\ I \leftarrow \text{true},\ \text{return } s & \text{if } I = \text{false}
\end{cases}
$$

其中 $s$ 为存储的实例引用。并发环境下，若无同步原语，多个线程可能同时观察到 $I = \text{false}$ 并创建多个实例——即**竞态条件**。设 $P_n$ 为 $n$ 个线程同时调用构造函数时创建超过一个实例的概率，在无锁情况下 $P_n$ 随线程数接近 $1$。

懒汉式首次访问时间 $T_{lazy} = O(1)$ 查询 + 潜在创建代价；饿汉式初始化代价均摊到类加载，不影响运行时访问延迟，但增加启动内存占用。

**归约终点**：单例的实质是全局资源的唯一性约束，满足 $\exists! x \in S: \text{accessible}(x)$。

### 数据流

<pre>
client ──new──▶ Singleton.constructor
                  │
                  ├─instance?──yes──▶ return instance
                  │
                  └─no──────────────▶ create instance → store → return
</pre>

### 机制

构造函数通过检查静态属性 `instance` 实现实例唯一性：首次构造时创建实例并缓存，后续构造直接返回缓存值。懒汉式延迟到首次使用时创建，适合实例创建代价高但未必被使用的场景；饿汉式在类加载时就创建，适合实例必定被使用的场景。

**闭包变体的私有化原理**：利用函数作用域（closure scope）将实例变量藏在函数内部，返回的 getter 函数形成唯一访问通道。从语义上，这等价于将"实例存在性"从显式属性收敛为词法作用域的不可达性——外部代码无法访问或篡改实例。

**违反约束的后果**：
- 反射或 `Object.getOwnPropertyDescriptors` 可绕过属性检查，直接修改 `instance` 导致单例失效。
- 序列化后再反序列化（默认 `JSON.parse`）会创建新实例，破坏单例语义，需要自定义 `revive` 逻辑。
- 多 iframe 或 Web Worker 环境中，每个上下文各有一个类加载器，单例跨上下文失效。

## 工厂模式

### 定义

**工厂模式将"创建哪个具体类"的选择权从调用方转移给工厂，调用方依赖抽象接口而非实现类。**

工厂的本质是一个**类型分发函数**：给定类型标识符，返回对应类的实例。调用方无需知道具体类的存在。

### 数学模型

简单工厂的创建逻辑是类型到构造函数的映射 $f: T \rightarrow C$（$T$ 为类型标识符集合，$C$ 为类构造函数集合）。设 $|T| = n$，新增类型需要修改工厂代码——这对应于 $f$ 的定义域扩展，每次扩展都违反开闭原则。

工厂方法将选择权延迟到子类：创建行为由接口 `Factory.create()` 抽象，子类通过重写决定实例化哪个具体类。这将选择代价从 $O(1)$ 条件分支推迟到子类覆盖，本质是**职责的延迟绑定**。

抽象工厂将相关对象簇的创建组合为接口：设产品族 $P = \{p_1, p_2, \dots, p_k\}$，工厂接口保证 $\forall i, j,\ p_i$ 与 $p_j$ 配套，避免混用不兼容产品。

**归约终点**：工厂的实质是**依赖反转**——高层模块（client）不依赖低层模块（具体类），两者都依赖抽象接口。

### 数据流

<pre>
client ──type──▶ createUser(type)
                    │
         ┌──────────┼──────────┐
         ▼          ▼          ▼
       Admin      Guest      User
</pre>

### 机制

简单工厂集中创建逻辑，调用方无需知道具体类名，但新增类型必须修改工厂——这违反了开闭原则（对扩展开放，对修改关闭）。工厂方法将创建逻辑抽象为接口，子类决定实例化哪个具体类，调用方依赖接口而非实现。抽象工厂更进一步，将相关对象簇的创建组合成一个接口，确保产品族的配套性。

**工厂方法的关键约束**：工厂接口的 `create()` 返回类型必须声明为抽象类型（基类或接口），而非具体子类——否则调用方仍会绑定到具体类，工厂方法形同虚设。

**违反约束的后果**：调用方依赖具体类而非抽象，新增/替换实现时必须修改调用方代码。

## 建造者模式

### 定义

**建造者模式将复杂对象的构建过程分解为独立步骤，构建者（Builder）负责每个步骤的具体实现，指挥者（Director）负责步骤顺序编排。**

建造者的本质是**多步骤对象的流水线组装**：每个步骤由专门对象负责，最终产品由指挥者按序调度各步骤产出。

### 数学模型

设复杂对象由 $k$ 个组件 $\{c_1, c_2, \dots, c_k\}$ 构成，组件 $c_i$ 的构建步骤序列为 $S_i = (s_{i,1}, s_{i,2}, \dots, s_{i,m_i})$。Builder 实现接口 $B$ 提供方法集合 $\{b_1, b_2, \dots, b_m\}$，每个方法对应一个原子构建步骤。

Director 的职责是将 $\{S_i\}$ 按产品要求编排为全序序列 $\Sigma$：

$$
\Sigma = \text{topoSort}(\{S_i\}, \text{dependencies})
$$

流式 API 变体将 `this` 作为返回值，使步骤调用链式化，本质是**建造步骤的函数式组合**：

$$
\text{result} = \text{step}_k(\text{step}_{k-1}(\dots \text{step}_1(\text{initial}) \dots ))
$$

**归约终点**：建造者模式将"构建什么"（产品）与"怎么构建"（步骤实现）分离。

### 数据流

<pre>
client ──new──▶ Director.construct(builder)
                       │
                  builder.step1()
                       │
                  builder.step2()
                       │
                  builder.getResult()
                       │
                       ▼
                    Product
</pre>

### 机制

将"如何构建"（步骤顺序）与"构建什么"（具体逻辑）分离。Director 定义步骤顺序但不涉及具体构建细节，不同 Builder 实现同一接口可产出不同表示。产品表示（Product）的变化无需改动 Director，只需新增 Builder。

**流式 API 变体的约束**：链式调用必须保证每个方法返回 `this`（或其代理对象），这要求 Builder 不能在构建中途抛出异常——否则链式调用会在中间断掉。常见解决方式是将验证延迟到 `getResult()` 一次性检查，或使用 Try 语义包装中间步骤。

**违反约束的后果**：
- 若 Builder 的某个步骤依赖前一步骤的结果（如先设置类型再设置该类型专属属性），但 Director 编排顺序有误，会导致中间产物处于不一致状态。
- 若 `getResult()` 没有防御性复制，返回的 Product 引用直接指向 Builder 内部状态，调用方可修改内部状态（破坏封装）。

## 参考存根

```javascript
// 单例模式（懒汉式）
class Singleton {
  constructor() {
    if (Singleton.instance) return Singleton.instance;
    this.data = [];
    Singleton.instance = this;
  }
}
```

```javascript
// 单例模式（闭包变体）
const Singleton = (() => {
  let instance = null;
  return {
    getInstance: () => {
      if (!instance) instance = { data: [] };
      return instance;
    }
  };
})();
```

```javascript
// 简单工厂
class User {}
class Admin extends User {}
class Guest extends User {}

function createUser(type) {
  if (type === 'admin') return new Admin();
  if (type === 'guest') return new Guest();
  return new User();
}
```

```javascript
// 工厂方法
class Product {
  create() { throw new Error('Abstract'); }
}
class ConcreteProductA extends Product {
  create() { return new ImplA(); }
}
class Factory {
  create(type) {
    return type === 'A' ? new ConcreteProductA() : null;
  }
}
```

```javascript
// 建造者模式
class QueryBuilder {
  constructor() { this.q = { select: [], from: '', where: [] }; }
  select(...f) { this.q.select.push(...f); return this; }
  from(t) { this.q.from = t; return this; }
  where(f, op, v) { this.q.where.push({ f, op }); return this; }
  build() { return { ...this.q }; }
}

// 使用
const query = new QueryBuilder()
  .select('id', 'name')
  .from('users')
  .where('age', '>', 18)
  .build();
```
