# 浏览器存储

> 前置：[03-网络与同源策略](./03-网络与同源策略.md) · 后续：[05-浏览器安全模型](./05-浏览器安全模型.md)

> **版本基准**：Node 24 stable / Node 26 latest。
> **实测范围说明**：**本篇无本机实测**——`localStorage`、`IndexedDB`、`Cache API` 都是浏览器专属，Node 不实现（见 [00-概览/01-JavaScript 全景](../00-概览/01-JavaScript全景.md) 的可用性对照）。事实依据为 WHATWG HTML 规范（Web Storage）、IndexedDB 规范与 Service Worker 规范。容量数值为**各浏览器实现的典型值**，非规范规定。

## 本质

浏览器提供多种**存储设施**，它们不是新旧替代关系，而是针对不同需求的设计。选型看三个维度：

| 维度 | 问题 |
|---|---|
| **容量** | 要存多少 |
| **生命周期** | 关掉标签页还在吗？清缓存会没吗？ |
| **同步性** | 读写会不会阻塞主线程 |

再加两条安全性维度：**能否被脚本读到**（防 XSS 窃取）与**能否被 Service Worker 访问**（离线场景）。

## 机制

### Cookie

最古老的机制，容量最小（典型值约 4 KB/条），但有一个别的设施都没有的特性：**随每个同源请求自动发送**。

| 特性 | 说明 |
|---|---|
| 容量 | 约 4 KB（典型值） |
| 发送 | 每次同源请求自动带上 |
| 读取 | `document.cookie`（除非 `HttpOnly`） |
| 生命周期 | 会话（默认）或 `Max-Age` / `Expires` |
| 作用域 | 域 + 路径 |

**它的唯一不可替代之处是"服务端能读到"**——会话标识必须靠它传给服务端（见 [03-网络与同源策略](./03-网络与同源策略.md) 的属性表）。除此之外的客户端数据都不该放 Cookie：它会让每个请求都变大。

### Web Storage：`localStorage` 与 `sessionStorage`

同步的键值存储，**只存字符串**：

| | `localStorage` | `sessionStorage` |
|---|---|---|
| 生命周期 | 永久，直到显式删除 | 标签页关闭即清空 |
| 作用域 | 同源的所有标签页共享 | 仅当前标签页 |
| 跨标签通知 | `storage` 事件 | — |

- **值只能是字符串**：存对象要 `JSON.stringify`（注意 [03-标准库/06-JSON](../03-标准库/06-JSON.md) 的丢值规则）。
- **同步 API**：读写会**阻塞主线程**，大数据量下明显卡顿。
- **`storage` 事件**：其它标签页修改同一键时触发，可用于多标签状态同步（触发它的那个标签页自己不会收到）。

`sessionStorage` 的一个实用特性是**刷新页面不丢、关标签页就丢**，适合放表单草稿。

### IndexedDB：异步事务型数据库

- **异步 API**：不阻塞主线程；
- **存结构化对象**：不用手动序列化，`Date`、`Blob`、`ArrayBuffer` 都能直接存（用的是结构化克隆，见 [04-异步与并发/05-Worker 与共享内存](../04-异步与并发/05-Worker与共享内存.md)）；
- **支持索引与事务**：可以按非主键字段查询；
- **容量大**：按配额分配，通常以可用磁盘空间的百分比计。

代价是 **API 冗长**：原生接口基于事件回调，打开数据库、建事务、发请求要写三层嵌套。实践中几乎总是通过一层封装使用。

**schema 只能随版本升级变更**：打开数据库时传入版本号，`onupgradeneeded` 回调是唯一能创建/删除对象仓库与索引的地方——浏览器比对版本号，新代码的版本号更高才触发迁移。这意味着表结构变更必须写成递增的迁移序列（v1 建 users 仓库、v2 加索引……），与服务端数据库的迁移纪律同构。

```javascript
const req = indexedDB.open("app", 2);            // 版本号 1 → 2
req.onupgradeneeded = (e) => {
  const db = e.target.result;
  if (e.oldVersion < 1) db.createObjectStore("users", { keyPath: "id" });
  if (e.oldVersion < 2) db.createObjectStore("orders", { keyPath: "id" });
};
```

### 配额与驱逐

所有源的存储共享一个**配额**（典型值按磁盘可用空间的比例，各浏览器不同）。两件事必须主动做：

- **查余量**：`navigator.storage.estimate()` 返回 `{ quota, usage }`——写大数据前先估，写之前不知道余量就会在中途撞 `QuotaExceededError`。
- **申请持久化**：`navigator.storage.persist()` 请求把本源的存储标记为持久。默认状态下浏览器在存储压力时**可以自动驱逐**源的数据（按最近使用排序逐出）；持久化批准后不再自动清，只能由用户手动清。批准与否由浏览器决定（典型判据：已安装、有通知权限、使用频繁）。

这正回应了边界里"存储会被清空"的那一条：不能阻止清空，但可以查余量、申请持久、并始终保留从服务端重建的路径。

### Cache API

专门缓存**请求/响应**，主要服务于 Service Worker 的离线能力：

```javascript
const cache = await caches.open("v1");
await cache.add("/app.js");
const hit = await cache.match("/app.js");
```

它缓存的是完整的 HTTP 响应（含头与状态码），因此能实现"离线时返回上次的页面"。它与 `fetch` 的关系见 [03-网络与同源策略](./03-网络与同源策略.md)——Service Worker 可以拦截请求，先查 Cache API，未命中再走网络。

### 对照

| | Cookie | `localStorage` | `sessionStorage` | IndexedDB | Cache API |
|---|---|---|---|---|---|
| 容量（典型值） | ~4 KB | ~5–10 MB | ~5–10 MB | 配额（大） | 配额（大） |
| 生命周期 | 可设 | 永久 | 标签页 | 永久 | 可设 |
| API | 同步（字符串） | 同步 | 同步 | **异步** | **异步** |
| 数据类型 | 字符串 | 字符串 | 字符串 | 结构化对象 | 请求/响应 |
| 随请求发送 | **是** | 否 | 否 | 否 | 否 |
| 可被 SW 访问 | 否 | 否 | 否 | 是 | 是 |
| 脚本可读 | 可设 `HttpOnly` | 是 | 是 | 是 | 是 |

## 连接：按需求选

| 需求 | 选择 |
|---|---|
| 会话标识（服务端要读） | Cookie + `HttpOnly` + `Secure` + `SameSite` |
| 少量用户偏好（主题、语言） | `localStorage` |
| 表单草稿、一次性流程状态 | `sessionStorage` |
| 大量结构化数据、需要查询 | IndexedDB |
| 离线可用的应用资源 | Cache API + Service Worker |
| 跨标签页同步状态 | `localStorage` + `storage` 事件 |

## 边界

- **存储按源隔离**：不同源的页面互不可见，这是同源策略的一部分（见 [03-网络与同源策略](./03-网络与同源策略.md)）。
- **`localStorage` 是同步的**：大对象读写阻塞主线程。
- **存储会被用户清空**：浏览器"清除浏览数据"、隐私模式、配额压力都可能清掉（配额查询与持久化申请见上文"配额与驱逐"）。**任何存储都不能当作唯一数据源**，重要数据必须能重新从服务端取回。
- **隐私模式下行为各异**：可能直接抛错，也可能只在会话内有效——写入要包 `try` / `catch`。
- **Cookie 不因标签页关闭而失效**（除非是会话 Cookie），且自动随请求发送——这也是 CSRF 的成因，见 [05-浏览器安全模型](./05-浏览器安全模型.md)。
- **不要把令牌放在 `localStorage`**：XSS 一旦发生即可读取全部令牌；`HttpOnly` Cookie 至少让脚本读不到。
