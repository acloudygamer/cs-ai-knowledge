# 浏览器安全模型

> 前置：[04-浏览器存储](./04-浏览器存储.md) · 后续：[06-Node.js平台/01-运行时与模块系统](../06-Node.js平台/01-运行时与模块系统.md)

> **版本基准**：Node 24 stable / Node 26 latest。
> **实测范围说明**：**本篇无本机实测**——同源策略、CSP、Trusted Types 的**执行**只发生在浏览器中（Node 不执行 CORS 的实测见 [03-网络与同源策略](./03-网络与同源策略.md)）。事实依据为 WHATWG HTML 规范、Fetch 标准与 CSP Level 3 规范。

## 本质

浏览器的安全模型只有一条主线：**同源策略划出一条边界，页面里的代码只能读写边界内的资源**（见 [03-网络与同源策略](./03-网络与同源策略.md)）。

安全问题的本质是**边界被绕过**，而绕过的核心手法只有一个：**让攻击者的代码以你的源的身份运行**。这就是 **XSS**（Cross-Site Scripting，跨站脚本）。

理解 XSS 的严重性，关键是看清它偷走的不是"一个页面"，而是**源身份**：

| 攻击者拿到 | 后果 |
|---|---|
| 当前页面的 DOM | 读取页面上的一切（含用户数据） |
| 同源 Cookie（非 `HttpOnly`） | 劫持会话 |
| `localStorage` / `sessionStorage` | 读取令牌与缓存数据 |
| 以该源发请求的能力 | 冒充用户执行任何操作 |

**XSS 比 CSRF 严重**：CSRF 只能借用户的身份发一个请求，XSS 是在你的源里执行任意代码——后者是前者的超集。

## 机制

### XSS 的三种形态

| 形态 | 载荷在哪 | 触发方式 |
|---|---|---|
| **存储型** | 服务端数据库（评论、昵称、文件名） | 任何访客打开该页面 |
| **反射型** | URL 参数，被服务端拼进响应 | 诱导点击特制链接 |
| **DOM 型** | 完全在客户端，不经过服务端 | 诱导点击特制链接 |

三者的注入点相同，区别只在载荷**存放的位置**与**到达 sink 的路径**。DOM 型最容易被忽视——服务端做的输出编码拦不住它，因为拼接发生在浏览器里：

```javascript
// 危险：URL 里的内容直接进入 HTML 解析
document.getElementById("out").innerHTML = new URLSearchParams(location.search).get("q");
```

### 注入点与安全替代

| 危险写法 | 为什么危险 | 安全替代 |
|---|---|---|
| `el.innerHTML = x` | **解析 HTML**，`<img onerror>` 可执行 | `el.textContent = x` |
| `el.outerHTML` / `insertAdjacentHTML` | 同上 | 同上 |
| `document.write(x)` | 同上，且会重写文档 | 用 DOM 方法 |
| `eval(x)` / `new Function(x)` | 直接执行代码 | 不执行动态代码 |
| `setTimeout("code", …)` | 字符串形式等价于 `eval` | 传函数 |
| `el.setAttribute("href", x)` 且 `x` 来自用户 | `javascript:` 伪协议可执行 | 校验协议白名单 |
| 模板引擎的"原始 HTML"插值 | 绕过转义 | 用默认的转义插值 |

**根本规则**：**数据与代码走不同的通道**。要把文本放进页面就用 `textContent`（它不解析）；确实要生成 HTML 时，用模板引擎的转义插值或先构造 DOM 节点。

一个补充规则：**上下文决定转义方式**。同一个字符串放进 HTML 文本、属性值、URL、`<script>` 里的 JS 字面量，需要的转义完全不同。靠手工转义极易出错，所以现代做法是**不手工转义**——用 `textContent` 或框架的自动转义，让"拼 HTML"这件事根本不发生。

### CSP：给页面装白名单

**内容安全策略**（Content Security Policy）通过响应头声明"这个页面允许加载什么"，从浏览器侧兜住漏网的注入：

```text
Content-Security-Policy: default-src 'self'; script-src 'self' 'nonce-随机值'; object-src 'none'; base-uri 'none'
```

| 指令 | 限制 |
|---|---|
| `default-src` | 其余指令的兜底 |
| `script-src` | 脚本来源 |
| `style-src` | 样式来源 |
| `img-src` / `connect-src` | 图片来源 / 请求目标 |
| `frame-ancestors` | 谁能用 iframe 嵌入本页（防点击劫持） |
| `base-uri` / `form-action` | 限制 `<base>` 与表单提交目标 |
| `object-src 'none'` | 禁用插件类嵌入 |

**关键点：`script-src 'unsafe-inline'` 会废掉 CSP 对 XSS 的防护。** 它允许页面内的内联 `<script>` 与 `onclick` 属性执行——而这正是注入最常见的落地形式。所以 CSP 的有效形态是**内联脚本必须带 `nonce`**（每次响应生成随机值，服务端同时把它写进标签）：

```html
<script nonce="随机值">…</script>
```

攻击者注入的脚本拿不到这次的 `nonce`，因此不会执行。代价是内联脚本要逐处加 `nonce`，不能有 `onclick="…"` 这类内联处理器。

**Trusted Types** 是更进一步的机制：在 CSP 里声明 `require-trusted-types-for 'script'` 后，`innerHTML` 等 sink **只接受**由策略函数产出的特殊对象，直接赋字符串会抛错。它把"记得转义"从人的纪律变成了**运行时的强制**——目前主要在 Chromium 系实现。

### 跨源隔离

同源策略本身是"读"的限制。有些攻击（如基于计时与推测执行的侧信道）能绕过它获取信息，所以浏览器引入了更强的隔离：

| 响应头 | 作用 |
|---|---|
| `Cross-Origin-Opener-Policy: same-origin`（COOP） | 切断与跨源窗口的引用关系 |
| `Cross-Origin-Embedder-Policy: require-corp`（COEP） | 跨源资源必须显式声明可嵌入 |
| `Cross-Origin-Resource-Policy`（CORP） | 声明本资源可被谁嵌入 |

**两个头同时设置**后，页面进入"跨源隔离"状态，`crossOriginIsolated` 为 `true`。这是 `SharedArrayBuffer` 可用的前提——共享内存配合高精度计时器能构成侧信道，所以浏览器只在隔离环境里放开它（见 [04-异步与并发/05-Worker 与共享内存](../04-异步与并发/05-Worker与共享内存.md)）。

### 其它边界加固

| 机制 | 作用 |
|---|---|
| `HttpOnly` Cookie | 脚本读不到，XSS 也偷不走（见 [04-浏览器存储](./04-浏览器存储.md)） |
| `SameSite` Cookie | 跨站请求不发送，防 CSRF（服务端侧见 [06-Node.js平台/05](../06-Node.js平台/05-服务端安全与认证.md)） |
| `frame-ancestors` | 防点击劫持 |
| `Referrer-Policy` | 控制跳转时泄露的 URL 信息 |
| SRI（`integrity` 属性） | 校验外部脚本的内容哈希，防 CDN 被篡改 |
| `upgrade-insecure-requests` | 把 HTTP 请求升级为 HTTPS |

## 连接：防护的层次

| 层次 | 手段 | 拦截什么 |
|---|---|---|
| 数据进入页面 | `textContent`、框架自动转义 | 注入本身 |
| 代码执行 | CSP（无 `unsafe-inline`） | 漏网的注入 |
| API 调用 | Trusted Types | 危险 sink 被误用 |
| 凭证保护 | `HttpOnly`、`SameSite` | 会话被窃取 / 被冒用 |
| 跨源信息 | COOP / COEP / CORP | 侧信道 |
| 传输 | HTTPS、SRI | 中间人篡改 |

**这些是叠加的，不是替代关系**。CSP 不能替代输出编码（它只是兜底），输出编码也不能替代 `HttpOnly`（会话保护是另一件事）。

## 边界

- **服务端的输出编码拦不住 DOM 型 XSS**：拼接发生在浏览器里。
- **`innerHTML` 不是"差不多安全"**：只要内容含用户输入就有风险，用 `textContent`。
- **`unsafe-inline` 等于没有 CSP**：脚本防护形同虚设。
- **CSP 是防线不是许可证**：它降低被利用的概率，不改变"不该拼接 HTML"这条规则。
- **前端无法单独完成安全加固**：CSP、COOP/COEP、Cookie 属性都是**响应头**，必须服务端设置。
- **`SharedArrayBuffer` 需要跨源隔离**：没有 COOP/COEP 就没有共享内存。
