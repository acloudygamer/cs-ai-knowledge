# 网络与同源策略

> 前置：[02-渲染管线与动画](./02-渲染管线与动画.md) · 后续：[04-浏览器存储](./04-浏览器存储.md)

> **版本基准**：Node 24 stable / Node 26 latest。本篇示例实测环境：Node v24.13.1（V8 13.6），Windows x64（本地 HTTP 服务器实测）。
> **实测范围说明**：`fetch`、`URL`、`Headers`、`Set-Cookie`、缓存头可在 Node 中实测（Node 已实现这些 Web 平台 API）。**同源策略与 CORS 的执行**只发生在浏览器中，Node 不执行（见下文实测），相关规则依据 WHATWG Fetch 标准陈述。

## 本质

**同源策略**（same-origin policy）是浏览器的一条安全边界：页面里的脚本**默认只能读取同源的资源**。没有它，任何一个网页的脚本都能悄悄读取你已登录的银行页面的内容——因为浏览器会自动带上该站点的 Cookie。

**同源**的判据是三个部分**全部相同**：

```text
https://app.example.com:8443/page
  ↑         ↑          ↑
 协议      主机        端口      三者全同才算同源
```

| 比较 | 是否同源 |
|---|---|
| `https://a.com/x` 与 `https://a.com/y` | ✓（路径不同不影响） |
| `https://a.com` 与 `http://a.com` | ✗（协议不同） |
| `https://a.com` 与 `https://b.a.com` | ✗（主机不同，子域也算不同源） |
| `https://a.com` 与 `https://a.com:8443` | ✗（端口不同） |

**CORS**（Cross-Origin Resource Sharing，跨源资源共享）是**服务端主动授权**跨源访问的机制：服务端返回特定的响应头，浏览器看到后才放行。所以"跨域问题"从来不是前端能单独解决的——**授权方是服务端**。

## 机制

### `URL`：解析与构造

```console
$ node net.mjs
origin: https://example.com:8443 | host: example.com:8443 | pathname: /a/b
searchParams.get('x'): 1 | hash: #frag
相对解析: https://example.com/a/c
URLSearchParams: a=1&b=x+y
```

- `origin` 就是同源判据的那三元组，**含端口**；
- `searchParams` 提供读写查询串的结构化接口，自动处理编解码（`"x y"` → `x+y`）；
- **相对路径解析**以第二个参数为基准，是拼接 URL 的正确方式（字符串拼接在路径含 `..` 或缺少斜杠时会出错）。

### `fetch`：请求与响应对象

```console
$ node net.mjs
status: 200 | ok: true | headers 是 Headers 实例: true
ACAO: https://app.example.com （Headers 名不区分大小写）
```

- **`fetch` 只在网络层面失败时拒绝**（DNS 失败、连接被拒、被 `AbortSignal` 中止）。HTTP 错误状态码（404、500）**不构成拒绝**，必须自己检查 `response.ok` 或 `response.status`。这与 [04-异步与并发/02-回调到 Promise](../04-异步与并发/02-回调到Promise.md) 里"Promise 拒绝表示失败"的直觉不同，是常见误区。
- `Headers` 的键**不区分大小写**。
- 响应体是一次性的：`json()` / `text()` / `arrayBuffer()` 只能调用其中一个，调用后流已消费（见 [04-异步与并发/06-流](../04-异步与并发/06-流.md)）。

### `Set-Cookie` 需要专门的方法

```console
$ node net.mjs
headers.get('set-cookie') 合并后: sid=abc; Path=/; HttpOnly; Sec …
getSetCookie() 逐个取: 2 条
```

一个响应可以带多个 `Set-Cookie` 头，但 `Headers.get()` 会把它们**用逗号合并**（因为其它头都是这么合并的）——而 Cookie 的值里本来就可能含逗号，合并后无法可靠拆分。`getSetCookie()` 返回数组，是读取它的唯一正确方式。

Cookie 的属性各有安全含义：

| 属性 | 作用 |
|---|---|
| `HttpOnly` | 脚本读不到（`document.cookie`），防 XSS 窃取 |
| `Secure` | 只在 HTTPS 下发送 |
| `SameSite=Lax/Strict` | 跨站请求不发送，防 CSRF |
| `SameSite=None` | 允许跨站，但**必须同时有 `Secure`** |
| `Max-Age` / `Expires` | 有效期 |

### CORS：简单请求与预检

浏览器把跨源请求分两类：

**简单请求**——方法为 `GET` / `HEAD` / `POST`，且头与 `Content-Type` 都在安全清单内（`text/plain`、`multipart/form-data`、`application/x-www-form-urlencoded`），直接发出，浏览器检查响应头后决定是否把结果交给脚本。

**预检请求**（preflight）——不满足上述条件时（如 `PUT`、自定义头、`application/json`），浏览器先发一个 `OPTIONS` 询问：

```text
OPTIONS /api HTTP/1.1
Origin: https://app.example.com
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: content-type
```

服务端答复后才发真实请求。**这就是"跨域请求发了两遍"的原因**——`Access-Control-Max-Age` 可以缓存预检结果，减少往返。

主要响应头：

| 响应头 | 含义 |
|---|---|
| `Access-Control-Allow-Origin` | 允许的源，`*` 或具体源 |
| `Access-Control-Allow-Methods` | 允许的方法（预检响应） |
| `Access-Control-Allow-Headers` | 允许的请求头（预检响应） |
| `Access-Control-Allow-Credentials` | 是否允许携带凭证 |
| `Access-Control-Max-Age` | 预检结果缓存秒数 |

**带凭证时的约束**：`Access-Control-Allow-Origin` **不能是 `*`**，必须是具体源，且 `Access-Control-Allow-Credentials` 为 `true`。因为 `*` 表示"任何源都可以"，而凭证请求需要精确授权。

### 缓存头

```console
$ node net.mjs
Cache-Control: public, max-age=60, stale-while-revalidate=30 | ETag: "v1"
```

| 头 | 作用 |
|---|---|
| `Cache-Control: max-age=N` | N 秒内直接用缓存，不发请求 |
| `ETag` + `If-None-Match` | 条件请求，未变更返回 304（省带宽，但仍有一次往返） |
| `Cache-Control: no-store` | 完全不缓存 |
| `Cache-Control: immutable` | 内容永不变化（配合带哈希的文件名） |
| `stale-while-revalidate=N` | 先返回过期缓存，后台更新 |

前端的**资源指纹**（文件名带内容哈希）配合 `immutable` 是缓存策略的常见做法：内容变则文件名变，文件名不变则内容一定不变。

### Node 不执行 CORS

上例中 `/cache`、`/cookie` 两个端点**没有返回任何 `Access-Control-*` 头**，Node 的 `fetch` 照样拿到了结果：

```console
$ node net.mjs
Cache-Control: public, max-age=60, stale-while-revalidate=30 | ETag: "v1"
```

**CORS 是浏览器的策略，不是 HTTP 协议的一部分。** 服务端不返回 CORS 头，请求本身在协议层面是成功的——是浏览器在收到响应后**拒绝把结果交给脚本**。

这条事实解释了两个常见困惑：

- 服务端日志里看到请求正常完成，浏览器控制台却报 CORS 错误——因为拦截发生在浏览器侧；
- 用 `curl` / Node 脚本能拿到数据，浏览器里却不行——因为它们不执行同源策略。

**推论**：CORS 不是访问控制机制（它拦不住非浏览器客户端），它是**保护用户浏览器里其它站点数据的机制**。

## 连接：跨源的合法手段

| 手段 | 原理 | 适用 |
|---|---|---|
| CORS | 服务端返回授权头 | 标准做法 |
| 同源代理 | 前端请求自己的服务器，由它转发 | 第三方 API 不支持 CORS 时 |
| `postMessage` | 跨源窗口/iframe 之间显式通信 | 嵌入第三方页面 |
| JSONP | `<script>` 不受同源限制 | 历史做法，只支持 GET，已不推荐 |

`<script>`、`<img>`、`<link>` 这些标签加载的资源**不受同源策略限制**（可以跨源加载），但**读取其结果**受限——JSONP 正是利用前者绕过后者的历史方案。

## 边界

- **`fetch` 不因 HTTP 错误状态码而拒绝**：必须检查 `response.ok`。
- **CORS 由服务端授权**：前端无法单方面解决跨域。
- **带凭证时 `Access-Control-Allow-Origin` 不能用 `*`**。
- **`Headers.get("set-cookie")` 会合并多个头**：用 `getSetCookie()`。
- **响应体只能读一次**：`json()` 与 `text()` 不能同时调用。
- **Node 不执行 CORS**：服务端能收到请求不代表浏览器会放行。
- **同源判据含端口与协议**：`http` 与 `https`、`80` 与 `8080` 都算跨源。
