# 渲染管线与动画

> 前置：[01-DOM 与事件模型](./01-DOM与事件模型.md) · 后续：[03-网络与同源策略](./03-网络与同源策略.md)

> **版本基准**：Node 24 stable / Node 26 latest。
> **实测范围说明**：**本篇无本机实测**——渲染管线只在浏览器引擎中存在，Node 不实现（见 [00-概览/01-JavaScript 全景](../00-概览/01-JavaScript全景.md) 的可用性对照）。事实依据为 WHATWG HTML 规范（事件循环与渲染时机）与各引擎的公开文档（渲染阶段划分）。文中不给出控制台输出。

## 本质

浏览器把 **DOM 树 + CSS 样式**变成屏幕上的像素，经过一条**流水线**。理解它的价值在于一个判断：**改动哪个属性，会让流水线从哪一步开始重跑**。

```text
HTML ──解析──> DOM ─┐
                    ├──样式计算──> 布局 ──> 绘制 ──> 合成 ──> 像素
CSS ──解析──> CSSOM ┘   (Style)   (Layout) (Paint) (Composite)
```

越靠前的阶段重跑，代价越大。这就是"用 `transform` 做动画比用 `left` 快"的全部原因——不是因为 `transform` 被优化过，而是它**跳过了布局与绘制两步**。

## 机制

### 五个阶段各做什么

| 阶段 | 输入 → 输出 | 何时重跑 |
|---|---|---|
| 样式计算 | DOM + CSS 规则 → 每个元素的最终计算样式 | 类名、样式表变化 |
| **布局**（Layout / Reflow） | 计算样式 → 每个元素的**几何位置与尺寸** | 几何属性、DOM 增删、字体、窗口尺寸变化 |
| **绘制**（Paint） | 布局结果 → 待填充的**绘制指令**（按层） | 颜色、背景、阴影、边框等视觉属性 |
| **合成**（Composite） | 各层 → 合并成最终帧 | 层的变换与透明度 |

**布局是流水线上最贵的一步**：它要遍历整棵树并解算约束关系，某个元素的尺寸变化会级联影响兄弟与祖先。

### 属性决定代价

| 改动 | 触发的阶段 | 相对代价 |
|---|---|---|
| `width`、`height`、`top`、`left`、`margin`、`padding`、`font-size` | 布局 → 绘制 → 合成 | 最高 |
| `color`、`background`、`box-shadow`、`border-radius` | 绘制 → 合成 | 中 |
| **`transform`、`opacity`、`filter`** | **仅合成** | 最低 |

`transform` 与 `opacity` 之所以能只走合成，是因为它们**不改变元素在文档流中的位置与尺寸**——引擎可以只重新组合已有的图层，不重新解算几何、不重新光栅化。

**动画用 `transform` 与 `opacity`**，这是唯一一条能稳定跑满 60 帧的规则。其余属性在动画中都会周期性触发布局或绘制。

### 布局抖动：读写交替的代价

浏览器**按批**处理 DOM 变更：一批写操作攒起来，在需要时统一做一次布局。但某些**读操作需要最新的布局结果**，于是强制浏览器立刻把攒着的变更算完：

| 读操作（强制同步布局） |
|---|
| `offsetTop` / `offsetLeft` / `offsetWidth` / `offsetHeight` |
| `scrollTop` / `scrollLeft` / `scrollWidth` / `scrollHeight` |
| `clientWidth` / `clientHeight` |
| `getComputedStyle()` |
| `getBoundingClientRect()` |
| `element.focus()` |

在循环里"写一点、读一点"，每一次读都会强制一次完整布局——称为**布局抖动**（layout thrashing）。典型症状是几十个元素的列表更新耗时数十毫秒。

**规避方式**：把读与写分成两批——先全部读进变量，再统一写回。

```javascript
// 坏：每次迭代读一次、写一次，读强制布局
items.forEach(el => { el.style.width = el.offsetWidth * 2 + "px"; });

// 好：先读后写
const widths = items.map(el => el.offsetWidth);
items.forEach((el, i) => { el.style.width = widths[i] * 2 + "px"; });
```

### 渲染时机：在宏任务之间

渲染不是持续进行的，而是**在事件循环的宏任务之间**按需发生（见 [04-异步与并发/01-事件循环与任务队列](../04-异步与并发/01-事件循环与任务队列.md)）。60 Hz 屏幕上大约每 16.7 ms 一个渲染机会。

由此推出两条实践规则：

- **长任务会掉帧**。一个耗时 100 ms 的同步任务会占掉约 6 个渲染机会，期间页面完全冻结。超过 50 ms 的任务称为**长任务**（long task），是卡顿的主要来源。CPU 密集的工作要移出主线程（见 [04-异步与并发/05-Worker 与共享内存](../04-异步与并发/05-Worker与共享内存.md)）。
- **不要在微任务里做重活**。微任务在渲染之前清空，微任务队列不空，渲染就被推迟（见 [04-异步与并发/01-事件循环与任务队列](../04-异步与并发/01-事件循环与任务队列.md) 的微任务饿死）。

### `requestAnimationFrame`：与渲染对齐

`setTimeout(fn, 16)` 只是"约 16 ms 后执行"，与渲染时机无关——它可能在某一帧之前、之中或之后执行，导致动画抖动（定时器精度问题见 [04-异步与并发/01-事件循环与任务队列](../04-异步与并发/01-事件循环与任务队列.md)）。

`requestAnimationFrame(fn)` 的回调**在下一帧渲染之前**执行，浏览器会把所有 rAF 回调集中在同一个时机调用：

- **与刷新率同步**：60 Hz 屏上约每 16.7 ms 一次，高刷屏上更快；
- **后台标签页自动暂停**：不可见时不再调用，省电；
- **同一帧内的多次 DOM 修改合并为一次渲染**。

**做动画用 rAF，不要用 `setTimeout` / `setInterval`。** 需要在回调里知道"距离上一帧过了多久"时，用回调参数（时间戳）或 `performance.now()`，不要用固定值累加。

## 连接：优化手段与它跳过的阶段

| 手段 | 作用 |
|---|---|
| 用 `transform` / `opacity` 做动画 | 跳过布局与绘制，只走合成 |
| 先读后写，分离读写批次 | 避免布局抖动 |
| 批量插入用 `DocumentFragment` | 把多次布局合并成一次 |
| 用 rAF 驱动动画 | 与渲染时机对齐，避免抖动与多余帧 |
| 把 CPU 密集任务放 Worker | 主线程保持可渲染 |
| 用 `will-change` 提前提升图层 | 让引擎预先分配合成层（**谨慎使用**：图层本身占内存） |

## 边界

- **`will-change` 不是越多越好**：每个提升的图层都要独立显存，滥用反而更慢。只在确实要动的元素上、临近动画时添加。
- **读布局属性会强制同步布局**：这是布局抖动唯一的成因。
- **`requestAnimationFrame` 的回调不是"恰好 16 ms 一次"**：它跟随屏幕刷新率，高刷屏上间隔更短。
- **合成层提升会改变定位基准**：`position: fixed` 的元素在被提升的祖先里会以该祖先为基准。
- **渲染时机由引擎决定**：以上是规范的保证范围，具体调度策略各引擎可优化，不应依赖精确的帧时序设计逻辑。
