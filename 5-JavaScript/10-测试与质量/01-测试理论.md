# 测试理论

> 前置：[09-工程化/05-发布与版本管理](../09-工程化/05-发布与版本管理.md) · 后续：[02-单元测试与断言](./02-单元测试与断言.md)

> **版本基准**：Node 24 stable / Node 26 latest。本篇示例实测环境：Node v24.13.1，Windows x64。

## 本质

测试是**用可执行的方式描述期望**。它的价值不在"证明代码是对的"，而在**改动时快速发现破坏**——没有测试的代码，每次修改都只能靠手工验证，改动成本随规模上升。

这个目的决定了两条实践准则：

- **测试要快**：反馈慢的测试没人跑，不跑的测试等于没有；
- **测试要能失败**：一条永远不会失败的断言没有价值，这是覆盖率与变异测试要区分的东西（见 [04-覆盖率与质量门](./04-覆盖率与质量门.md)）。

## 机制

### 测试的层次

| 层次 | 测什么 | 速度 | 成本 | 数量占比 |
|---|---|---|---|---|
| **单元测试** | 单个函数/模块，隔离依赖 | 毫秒 | 低 | 多 |
| **集成测试** | 多个模块协作、真实依赖 | 秒 | 中 | 中 |
| **端到端测试** | 完整链路（浏览器 → 服务 → 数据库） | 十秒到分钟 | 高 | 少 |

这个分布称为**测试金字塔**：底层多、顶层少。理由很直接——**上层测试慢、脆、贵**：

- 慢：一次 E2E 要起服务、连数据库、跑浏览器；
- 脆：任何一层的网络抖动、时序差异都会让它失败，与代码质量无关；
- 贵：维护成本随交互路径数量增长。

**上层的每一个测试都应该问"这一层非测不可吗"**。能用单元测试覆盖的逻辑放在 E2E 里测，是让整个测试套件变慢的常见途径。

但金字塔**不等于"不要 E2E"**。它测的是单元与集成测试都覆盖不到的东西：**各部分拼起来是否真的能工作**。单元测试全绿而线上全挂，最常见的原因就是没有一条 E2E 走过完整链路。

### 测试的三段式

一个测试通常写成三部分，称为 **AAA**（Arrange-Act-Assert）：

```javascript
it("加法对负数成立", () => {
  const a = -1, b = 1;                 // Arrange：准备
  const result = add(a, b);            // Act：执行
  assert.equal(result, 0);             // Assert：断言
});
```

它的价值是**结构一致**：读者能立刻定位"被测的是什么"（Act 那一行）与"期望是什么"（Assert 那一行）。当测试失败时，这三段能快速区分"是准备错了"还是"是被测代码错了"。

一个测试**只做一次 Act**。多个 Act 意味着它同时验证多件事，失败时无法判断是哪件坏了。

### 测试替身

被测代码依赖外部事物（数据库、网络、时间、随机数）时，用**替身**替换它们。五类替身：

| 类型 | 作用 |
|---|---|
| **Dummy** | 只为填参数，不被使用 |
| **Stub** | 返回预设值 |
| **Spy** | 记录调用情况，行为不变 |
| **Mock** | 预设期望，调用不符即失败 |
| **Fake** | 有真实实现的简化版（如内存数据库） |

实践中**优先用 Fake 与 Stub**：Fake 保留了真实行为（内存数据库仍是数据库语义），Stub 只提供返回值。**Mock 的预设期望会让测试与实现细节耦合**——被测代码换个调用顺序，测试就红，但它并没有坏。

**要替换的是"不确定的东西"**（时间、网络、随机数），不是"被测代码的所有依赖"。把依赖全部替换掉，测的就只剩"这段代码是否按我写的方式调用依赖"，而不是"它做对了吗"。

### 测试的独立性

三条硬要求：

| 要求 | 原因 |
|---|---|
| **不共享可变状态** | 共享状态让测试的执行顺序影响结果 |
| **可任意顺序运行** | 顺序依赖的测试无法并行，也难定位失败 |
| **可重复运行** | 同一份代码重复跑结果必须一致 |

第三条的常见违反者是**时间与随机数**：用当前时间的测试在不同时刻行为不同；用随机输入的测试失败后无法复现。这类依赖必须注入或固定。

### TDD：红-绿-重构

测试驱动开发的循环是：

```text
写一个失败的测试（红） → 用最少的代码让它通过（绿） → 在测试保护下重构
```

它的收益不在"测试覆盖率更高"，而在**设计压力**：先写测试迫使你从调用方的角度想接口——"我希望怎么调用它"。这比先写实现更容易得到好用的接口。

**不必教条地全盘采用**。更有价值的是它的一条推论：**难以测试的代码通常也是难以使用的代码**。一个函数需要构造五个对象才能测，说明它耦合过重。

### 该测什么

| 优先测 | 不必测 |
|---|---|
| 业务规则与分支 | 语言本身的行为 |
| 边界条件（空、零、极值） | 第三方库的内部实现 |
| 错误路径 | 简单的 getter / setter |
| 曾经的 bug（回归测试） | 纯展示、无逻辑的代码 |

**边界与错误路径的收益最高**：正常路径在开发时就被反复走过了，出问题的是"输入为空""并发调用""超时"这些没想到的情况。

## 连接：测试层次的取舍

| 问题 | 适合的层次 |
|---|---|
| 这个函数对边界输入算得对吗 | 单元测试 |
| 这两个模块拼起来对吗 | 集成测试 |
| 用户能不能完成下单流程 | E2E |
| 这个查询在真实数据库上对吗 | 集成测试 |
| 页面渲染出来了吗 | 组件测试（见 [03-端到端与组件测试](./03-端到端与组件测试.md)） |

## 边界

- **测试不能证明代码正确**：它只能证明"这些情况下符合期望"。
- **覆盖率不是质量**：见 [04-覆盖率与质量门](./04-覆盖率与质量门.md)。
- **慢测试会被跳过**：反馈时间超过几秒，人就会去干别的。
- **过度的测试替身会让测试失去意义**：替换掉全部依赖等于测了个空壳。
- **E2E 的失败要能归因**：无法定位的失败会让人习惯性重跑，最终无视。
- **测试也需要维护**：断言实现细节的测试会在重构时成批变红。
