# 端到端与组件测试

> 前置：[02-单元测试与断言](./02-单元测试与断言.md) · 后续：[04-覆盖率与质量门](./04-覆盖率与质量门.md)

> **版本基准**：Node 24 stable / Node 26 latest。本篇示例实测环境：Node v24.13.1（V8 13.6），Windows x64。
> **实测范围说明**：**等待策略部分在本机 Node v24.13.1 实测**（该问题的本质与浏览器无关，是"时间依赖"本身）。**浏览器自动化与组件渲染**需要真实浏览器，未在本机实测，依据 Playwright / Testing Library 的公开文档陈述。

## 本质

单元与集成测试验证"每个部件对不对"，但它们拼起来是否真能工作，只有走一遍完整链路才知道（见 [01-测试理论](./01-测试理论.md) 的金字塔）。**端到端测试**（E2E）从用户入口走到数据落库，覆盖这条链路；**组件测试**是它的缩小版，只测一个组件在真实 DOM 里的渲染与交互。

两者的共同特征是**依赖真实环境**（浏览器、服务、数据库），因此它们的主要难点不是"怎么断言"，而是**怎么让结果稳定**——一个时红时绿的测试，比没有测试更糟：它会训练团队忽略红灯。

## 机制

### 等待策略：不稳定测试的头号成因

E2E 里的操作几乎都是异步的（页面加载、请求返回、动画结束）。用"等固定时间"来同步，会同时犯两个错。

实测（模拟就绪时间在 30–120 ms 之间随机的资源）：

```console
$ node wait.mjs
=== 固定等待 100ms：结果不稳定 ===
  20 次中失败 2 次（就绪时间 30~120ms，固定等 100ms 必然有超出的）

=== 条件等待：轮询直到就绪或超时 ===
  20 次中失败 0 次 | 平均耗时 79ms

=== 固定等待的另一个代价：永远等满 ===
  固定等待总耗时 2179ms（无论资源多早就绪）
  条件等待总耗时 1614ms（就绪即返回）
```

（点值为单次运行的举例值：失败次数取决于随机就绪时间，复跑会得到不同的具体数字；量级与方向稳定。）

| | 固定等待 | 条件等待 |
|---|---|---|
| 资源比预期慢 | **失败**（实测 2/20） | 继续等，直到超时 |
| 资源比预期快 | **白等**（永远等满） | 立刻返回 |
| 总耗时 | 2179 ms | 1614 ms |

**固定等待既不可靠又慢**。它把"资源就绪"这件事赌在了一个猜出来的数字上。

**条件等待**是正解——轮询直到条件成立或超时：

```javascript
async function waitFor(predicate, { timeout = 5000, interval = 50 } = {}) {
  const deadline = Date.now() + timeout;
  while (Date.now() < deadline) {
    if (await predicate()) return;
    await new Promise(r => setTimeout(r, interval));
  }
  throw new Error("等待超时");
}
```

测试框架通常把这一步封装好了——Playwright 的 `expect(locator).toBeVisible()`、Testing Library 的 `findBy*` 都是**内建重试的断言**，会等到条件成立或超时。**用它们，不要自己写 `sleep`。**

超时值的作用也变了：条件等待下，超时是**兜底**（正常路径几百毫秒内就返回），可以设得宽松；固定等待下超时就是实际等待时长，设大了慢、设小了脆。

### 不稳定测试的处理

测试偶发失败时有两种反应：

| 反应 | 后果 |
|---|---|
| 加重试 | 掩盖问题，红灯越来越多，最终被无视 |
| 定位根因 | 正确，但需要时间 |

**重试是止痛药，不是解药**。如果一条测试 5% 概率失败，加重试后"看起来"绿了，但它掩盖的问题仍在——而且当失败率升到 50% 时，重试也救不了。

常见根因（按出现频率）：

| 根因 | 表现 | 对策 |
|---|---|---|
| 固定等待 | 机器慢时失败 | 改条件等待 |
| 测试间共享数据 | 单独跑通过，一起跑失败 | 每个测试独立的数据 |
| 依赖执行顺序 | 换顺序就失败 | 消除顺序依赖 |
| 外部依赖不稳定 | 第三方服务抖动 | 用 Fake 或契约测试 |
| 动画未结束 | 点击落到错误位置 | 禁用动画或等状态 |

### 测试数据隔离

E2E 通常连真实数据库，因此**数据隔离**是必须的。常见做法：

| 做法 | 说明 |
|---|---|
| 每个测试独立用户/租户 | 数据天然隔离，可并行 |
| 事务回滚 | 测试结束回滚，但 E2E 跨进程时难做 |
| 每次重建数据库 | 最干净，最慢 |
| 唯一标识前缀 | 简单，但需要清理 |

**优先"每个测试用独立数据"**：它让测试可以并行、可以任意顺序运行，符合 [01-测试理论](./01-测试理论.md) 里的独立性要求。

### 组件测试：从用户视角查询

组件测试在真实 DOM 环境里渲染组件并与之交互。关键约定是**按用户能感知的方式查询元素**：

| 查询方式 | 稳定性 |
|---|---|
| 按可见文本、角色（role）、标签 | **高**——与用户看到的一致 |
| 按 `data-testid` | 中——显式标记，但脱离了用户视角 |
| 按 CSS 类名、DOM 结构 | **低**——重构即失效 |

按类名查询的测试会在每次样式重构时变红，而组件行为没有任何变化。**优先按角色与文本查询**（这也顺带检查了可访问性——一个屏幕阅读器找不到的按钮，测试也找不到）。

**测行为不测实现**：断言"点击后出现成功提示"，而不是"点击后 `setState` 被调用了一次"。

### 截图对比

截图测试比对渲染结果的像素差异，能发现布局回归。局限是**对无关变化过于敏感**——字体渲染差异、动画中间态、不同平台的字形都会造成差异。实践中需要：

- 固定视口尺寸与设备像素比；
- 等待字体与图片加载完成；
- 对动态内容（时间、随机数）做遮罩。

它适合**视觉回归**这一特定目的，不适合替代功能断言。

## 连接：层次与代价

| | 单元 | 组件 | E2E |
|---|---|---|---|
| 环境 | 纯 Node | 浏览器 + DOM | 浏览器 + 服务 + 数据库 |
| 速度 | 毫秒 | 秒 | 十秒到分钟 |
| 稳定性 | 高 | 中 | 低 |
| 能发现 | 逻辑错误 | 渲染与交互错误 | 集成断裂 |
| 维护成本 | 低 | 中 | 高 |
| 数量 | 多 | 中 | 少 |

## 边界

- **不要用固定 `sleep`**：既不稳定又慢，用内建重试的断言或条件等待。
- **重试掩盖问题**：先定位根因，重试只用于确认已知的外部抖动。
- **测试要能独立运行**：共享数据与顺序依赖是不稳定的主要来源。
- **组件测试按用户视角查询**：类名与 DOM 结构会随重构变化。
- **截图测试对无关变化敏感**：需要固定环境并遮罩动态内容。
- **E2E 数量要克制**：它慢且脆，只覆盖关键路径。
- **E2E 失败要能归因**：无法定位的失败会训练团队忽略红灯。
