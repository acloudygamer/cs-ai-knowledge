# 覆盖率与质量门

> 前置：[03-端到端与组件测试](./03-端到端与组件测试.md) · 后续：[11-前端框架与状态管理/01-框架原理](../11-前端框架与状态管理/01-框架原理.md)

> **版本基准**：Node 24 stable / Node 26 latest。本篇示例实测环境：Node v24.13.1（`--experimental-test-coverage`），Windows x64。

## 本质

覆盖率回答的问题是：**代码被执行到了吗**。它**不**回答：**行为被验证了吗**。

这两个问题的差距是覆盖率作为质量指标失效的全部原因。一篇测试可以执行完所有代码行，却一条有效断言都没有。

```bash
node --test --experimental-test-coverage
```

```console
$ node --test --experimental-test-coverage calc.test.js
ℹ file      | line % | branch % | funcs % | uncovered lines
ℹ calc.js   |  85.71 |    80.00 |   66.67 | 6
```

**覆盖率的正确用途是"发现未被测试的区域"**——`uncovered lines` 那一列。把它当作需要冲刺的分数，就会得到本篇实测的那组数据。

## 机制

### 四种覆盖率

| 类型 | 衡量 |
|---|---|
| **行覆盖率** | 有多少行被执行 |
| **分支覆盖率** | `if` / 三元 / 逻辑运算符的每个分支是否都走到 |
| **函数覆盖率** | 有多少函数被调用过 |
| **语句覆盖率** | 与行覆盖率近似（一行多语句时不同） |

**分支覆盖率比行覆盖率有价值**：一行 `if (a && b)` 的"行"执行了，不代表 `b` 为假的路径走过。

### 空洞断言能拿到满分

实测对照。被测代码 `calc.js` 有三个函数，其中 `classify` 有三个分支：

**版本 A——有意义的断言**：

```javascript
test("classify 正数", () => assert.equal(classify(1), "正"));
test("classify 负数", () => assert.equal(classify(-1), "负"));
```

```console
ℹ calc.js   |  85.71 |    80.00 |   66.67 | 6
```

**版本 B——空洞断言**（三个调用都只检查返回类型）：

```javascript
test("只断言类型", () => {
  assert.equal(typeof classify(1), "string");
  assert.equal(typeof classify(-1), "string");
  assert.equal(typeof classify(0), "string");
});
```

```console
ℹ calc.js   | 100.00 |   100.00 |   33.33 |
```

**版本 B 的行覆盖率与分支覆盖率都是 100%**——因为它把三个分支都执行了一遍；而它**没有验证任何一个返回值**。`classify` 即使把"正"和"负"写反，这组测试依然全绿。

| | 行 | 分支 | 函数 | 实际验证了什么 |
|---|---|---|---|---|
| 有意义的断言 | 85.71% | 80.00% | 66.67% | 两个分支的返回值 |
| 空洞断言 | **100%** | **100%** | 33.33% | **什么都没有** |

**数字更高的一组，测试质量更低。** 这就是覆盖率不能作为质量指标的直接证据。

（函数覆盖率反而下降了，因为版本 B 只导入了 `classify`，另外两个函数没被调用——这也说明不同指标各有盲区。）

### 正确的用法：看未覆盖区域，不看百分比

| 用法 | 价值 |
|---|---|
| 打开 `uncovered lines` 列，逐个看"这行为什么没被测" | **高** |
| 要求整体覆盖率 ≥ N% | 低，且会催生空洞断言 |
| 比较同一次改动的覆盖率变化 | 中 |

**未被覆盖的行往往正是最难测、也最容易出错的地方**——错误分支、边界条件、异常路径。看到"这几行没被覆盖"然后思考原因，比看到"覆盖率 92%"有意义得多。

### 质量门：阈值怎么定

如果确实要设阈值，两条原则：

| 原则 | 说明 |
|---|---|
| **对新增/改动的代码设阈值**，不对存量设 | 存量代码补测试成本高，一刀切会逼出空洞测试 |
| **阈值设成"防倒退"，不设成"目标"** | 如"新代码分支覆盖率不低于 80%"，而不是"全项目达到 90%" |

CI 里可行的做法是**比较基线**：本次改动使覆盖率下降则失败，而不是要求一个绝对数字。

### 变异测试：真正衡量断言强度

变异测试回答"测试能发现错误吗"：**自动在源码里注入小改动**（把 `>` 改成 `>=`、把 `+` 改成 `-`、删掉一个函数调用），然后跑测试——如果测试仍然全绿，说明这处改动**没有被任何断言发现**。

| 指标 | 含义 |
|---|---|
| 变异得分 | 被测试"杀死"的变异体占比 |

它直接对应"断言够不够强"这个问题。上例的版本 B 在变异测试下会得到很低的分数——把 `classify` 的返回值互换，测试不会失败。

代价是**运行时间成倍增长**（每个变异体都要跑一遍测试），所以通常只对核心模块跑，或只在夜间构建里跑。

### 覆盖率与 CI

```bash
node --test --experimental-test-coverage --test-coverage-lines=80 --test-coverage-branches=70
```

Node 的测试运行器支持直接设阈值并在不达标时失败。无论用什么工具，有两点必须明确：

- **阈值是"防倒退"的下限**，不是要冲刺的目标；
- **不要为了让数字好看而写测试**——那正是覆盖率失去意义的过程。

## 连接：度量手段对照

| 度量 | 回答的问题 | 能被糊弄吗 |
|---|---|---|
| 测试数量 | 写了多少 | 容易（拆分测试即可） |
| 行/分支覆盖率 | 代码被执行到了吗 | **容易**（空洞断言） |
| 函数覆盖率 | 函数被调用过吗 | 容易 |
| **变异得分** | **断言能发现错误吗** | 难 |
| 缺陷逃逸率 | 线上发现了多少本可被测出的 bug | 难（但要等真实数据） |

**越难糊弄的指标越有价值**，也越贵。变异测试贵在运行时间，缺陷逃逸率贵在滞后。

## 边界

- **覆盖率不衡量断言强度**：空洞断言能拿 100%（实测）。
- **不要以覆盖率为目标**：它会被优化，但优化的是数字不是质量。
- **看未覆盖区域而非百分比**：那才是有信息量的部分。
- **阈值应对新代码设，不对存量设**：否则逼出补测试的形式主义。
- **变异测试更真实但更贵**：只对核心模块或夜间跑。
- **覆盖率高不代表没有 bug**：它只说明代码被执行过。
