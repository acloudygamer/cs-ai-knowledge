# 演进脉络与 TC39 流程

> 前置：[12-设计模式/04-行为型模式](../12-设计模式/04-行为型.md) · 后续：[02-ES2015 至 ES2020](./02-ES2015至ES2020.md)

> **版本基准**：Node 24 stable / Node 26 latest。本篇示例实测环境：Node v24.13.1（V8 13.6），Windows x64。

## 本质

版本演进要回答两个不同的问题，它们的答案来自两条**不同步**的时间线：

| 问题 | 由谁决定 |
|---|---|
| **规范里有没有这个特性** | TC39 的提案流程（每年 6 月定稿） |
| **我能不能用** | 引擎的实现进度（V8 / JavaScriptCore / SpiderMonkey） |

本库的版本口径因此写成**二元组**（Node 版本 + ES 版本），而不是单一版本号（见 [00-概览/01-JavaScript 全景](../00-概览/01-JavaScript全景.md)）。本篇讲这两条线各自的机制，以及它们为什么会错位。

## 机制

### TC39 的提案阶段

TC39 是负责 ECMAScript 标准的技术委员会，用分阶段流程管理提案：

| 阶段 | 名称 | 含义 |
|---|---|---|
| 0 | Strawman | 构想，尚未正式讨论 |
| 1 | Proposal | 正式提案，需说明问题背景与 API 设计 |
| 2 | Draft | 草案，语法与语义基本确定，有正式规范文本 |
| 2.7 | — | 编写测试与实现验证（2023 年底引入） |
| 3 | Candidate | 候选，规范冻结，实现者开始集成 |
| 4 | Finished | 完成，**进入当年的规范版本** |

**Stage 2.7 的引入**值得说明：它承担的是旧 Stage 3 的职责（规范已完成、需要真实实现来验证），编号取 2.7 而非把后续阶段整体重编号，是为了避免大量既有文档与链接失效。

**只有到 Stage 4 才进规范**。所以"某个提案"与"某个标准特性"是两回事——前者可能在任何阶段停滞多年，后者是既成事实。

### 每年一次，版本号与年份绑定

每年 6 月，Ecma 大会批准一个新版本。**ES2015 起停止使用递增版本号，改用年份**：

| 版本 | 批准 |
|---|---|
| ES2015（第 6 版） | 2015-06 |
| … | … |
| ES2025（第 16 版） | 2025-06-25（第 129 届大会） |
| ES2026（第 17 版） | 2026-06-30（第 131 届大会） |

改成年份是因为**递增版本号已失去意义**：ES5（2009）到 ES6（2015）隔了六年、变化巨大，而之后的每年一版大多只包含少量特性。用年份标记能直观表达"这是哪一年的版本"。

**"ES6"至今仍被广泛使用**，但它是一个历史名词——正式名称是 ES2015，而现在说"ES6+"通常泛指 ES2015 之后的所有版本。

### 两条时间线的错位

规范批准与引擎实现**两个方向都会偏**。以下是本机 Node 24（V8 13.6）实测的结果：

**方向一：引擎落后于规范**

```console
$ node -e 'console.log(typeof Math.sumPrecise)'
undefined
```

`Math.sumPrecise` 是 **ES2026** 特性（TC39 已完成、规范已批准），但截至 Node 26（V8 14.6）仍未实现。**规范批准不等于能写。**

**方向二：引擎领先于规范**

```console
$ node -e 'console.log(typeof Error.isError, typeof RegExp.escape)'
function function
```

- `Error.isError` 属 **ES2026**，而 Node 24 已有；
- `RegExp.escape` 属 **ES2025**，Node 24 已有。

更明显的例子是 ES2027 的提案：

```console
$ node --harmony-temporal -e 'console.log(typeof Temporal)'
object
$ node --input-type=module -e 'class R{ [Symbol.dispose](){} } using r = new R(); console.log("using 可用")'
using 可用
```

`Temporal` 与 `using` 声明**都归属 ES2027**（尚未批准的版本），但 `using` 在 Node 24 已可用，`Temporal` 加 `--harmony-temporal` 即可用、在 Node 26 已默认开启。

**错位的原因很直接**：特性是先有实现、再进规范。引擎厂商实现某个提案时它还在 Stage 3，等规范批准时引擎可能已经发了两个大版本。

### 这对写代码意味着什么

| 判断 | 依据 |
|---|---|
| 这段语法在当前 Node 上能跑吗 | **引擎支持矩阵**（见 [03-ES2021 至 ES2026](./03-ES2021至ES2026.md)） |
| 这段代码在目标浏览器上能跑吗 | 打包工具的 `target` + 特性检测（见 [09-工程化/03-打包与转译](../09-工程化/03-打包与转译.md)） |
| 这个特性算"标准"吗 | 是否到 Stage 4 |
| 我该不该用 | 目标环境的支持率，不是规范状态 |

**最后一行是实践要点**：一个 Stage 3 的特性如果在目标环境全部可用，用它没有错；一个已批准的 ES2026 特性如果目标环境不支持，就不能用。**规范状态决定"稳定性预期"，引擎状态决定"能不能用"。**

## 连接：阶段与可用性

| 阶段 | 规范稳定性 | 引擎可用性 | 建议 |
|---|---|---|---|
| 0–1 | 随时可能大改 | 通常无 | 只做了解 |
| 2 | 基本确定 | 少数引擎试验性实现 | 谨慎 |
| 2.7–3 | 规范完整，等待实现反馈 | 部分引擎已实现 | **看目标环境** |
| 4 | 已进入规范 | 通常一两年内普及 | 看目标环境 |

## 边界

- **规范批准 ≠ 能写**：`Math.sumPrecise` 是 ES2026 但未落地（实测）。
- **引擎实现 ≠ 已成标准**：`using` 可用但属 ES2027。
- **"ES6"是历史名词**：正式名称是 ES2015。
- **Stage 4 不等于立刻普及**：老环境仍需要转译。
- **不要按规范版本决定能不能用**：按目标环境的引擎支持矩阵决定。
- **每年一版意味着小步演进**：单个版本的新特性通常不多，多数是既有提案的落地。
