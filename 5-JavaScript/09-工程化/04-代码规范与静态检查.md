# 代码规范与静态检查

> 前置：[03-打包与转译](./03-打包与转译.md) · 后续：[05-发布与版本管理](./05-发布与版本管理.md)

> **版本基准**：Node 24 stable / Node 26 latest。本篇示例实测环境：Node v24.13.1，`npx eslint`，Windows x64。

## 本质

静态检查分三层，**职责不同、互相补充**：

| 层 | 工具 | 判什么 | 需要类型信息 |
|---|---|---|---|
| **格式** | Prettier | 缩进、换行、引号——纯机械 | 否 |
| **规则** | ESLint | 可疑写法、易错模式、风格约定 | 否（可选开启） |
| **类型** | `tsc` | 类型不匹配 | 是 |

三层中，**只有"规则"层是判断题**——它检查的是"这段代码是否可能有问题"。格式层没有对错（只是统一），类型层是数学上的可赋值性判断。

把它们分开的理由是**反馈速度**：格式检查与规则检查不做类型推导，毫秒级完成；类型检查要建整个项目的类型图，秒级到分钟级。混在一起会让日常编辑变得迟钝。

## 机制

### 格式与规则的分工

| | Prettier | ESLint |
|---|---|---|
| 关心 | 代码**长什么样** | 代码**做了什么** |
| 能自动修 | 全部 | 一部分 |
| 是否可争辩 | 不可（配置说了算） | 可（规则可以关） |
| 典型规则 | 缩进宽度、行宽、引号 | 未使用变量、`==`、未定义变量 |

**不要让两者管同一件事**。ESLint 历史上有一批格式类规则（`indent`、`quotes`、`semi`），现在都已废弃——格式交给 Prettier，ESLint 专注语义。

### ESLint 的 flat config

实测配置与输出：

```javascript
// eslint.config.js
export default [
  {
    files: ["**/*.js"],
    rules: {
      "no-unused-vars": "error",
      "no-undef": "error",
      "eqeqeq": ["error", "always"],
      "no-implicit-coercion": "warn",
      "prefer-const": "error",
    },
  },
];
```

```console
$ npx eslint bad.js
  1:7   error    'unused' is assigned a value but never used        no-unused-vars
  2:5   error    'x' is not defined                                  no-undef
  2:7   error    Expected '===' and instead saw '=='                 eqeqeq
  3:5   error    'neverReassigned' is never reassigned. Use 'const'  prefer-const
  5:13  warning  Unexpected implicit coercion encountered. Use `Boolean("字符串")`  no-implicit-coercion

✖ 8 problems (7 errors, 1 warning)
```

每条规则可设为 `"off"` / `"warn"` / `"error"`，或带选项的数组形式（`["error", "always"]`）。

**`warn` 与 `error` 的分界**：`error` 用于"会让 CI 失败、必须修"的规则；`warn` 用于"值得注意但不阻塞"的。**警告会累积**——长期没人看的警告等于没有警告，所以新加的规则要么是 `error`，要么先别加。

### `--fix` 能修什么

```console
$ npx eslint --fix fix.js && diff bad.js fix.js
3c3
< let neverReassigned = 2;
---
> const neverReassigned = 2;
5c5
< console.log(!!"字符串");
---
> console.log(Boolean("字符串"));
```

**规则分两类**：可自动修复的（`prefer-const`、`no-implicit-coercion`、引号统一）与需要人工判断的（`no-unused-vars`——变量真没用还是漏写了使用？）。

`--fix` 只应用安全的修复。实践中把它挂在保存时或提交前钩子上，可修复的自动改掉，剩下的报给人。

### lint 查不出类型错误

这是三层分工最需要理解的一处。实测：

```javascript
/** @type {number} */
const n = "字符串";          // 类型不符
function f(a) { return a.toFixed(2); }
f(null);                     // 运行时必崩
```

```console
$ npx eslint type-ok.js
  2:7  error  'n' is assigned a value but never used  no-unused-vars
✖ 1 problem
```

**ESLint 只报了"变量未使用"，两个真正的类型错误一个都没报**——因为它不做类型推导，看到的只是语法结构。

要让它检查类型，需要 **typescript-eslint** 的类型感知规则，代价是**显著变慢**（它要加载类型信息）。所以合理的配置是：

| 检查 | 何时跑 | 为什么 |
|---|---|---|
| 格式 + 基础规则 | 编辑器保存时、提交前 | 快，秒级反馈 |
| 类型感知规则 + `tsc` | CI | 慢，但必须做 |

### 规则集怎么选

不要一次开全部。推荐路径：

1. **从官方推荐集开始**（`eslint:recommended` 或各框架的推荐配置）——它们只包含公认有问题的规则；
2. **按项目实际踩过的坑加规则**——每加一条背后有一个真实 bug，团队才会认同；
3. **定期清理**：长期触发但没人修的规则，要么降级要么删掉。

`--fix` 之外，`--max-warnings 0` 在 CI 里很有用：**让警告也失败**，避免警告堆积。

### 提交前钩子与 CI

| 位置 | 跑什么 | 目的 |
|---|---|---|
| 编辑器 | 格式化 + 快速规则 | 即时反馈 |
| pre-commit 钩子 | 只跑改动文件的格式化与 lint | 拦住明显问题 |
| CI | 全部检查（含类型检查、测试、生产构建） | 最后一道关 |

**pre-commit 只跑改动文件**：全量检查在提交时太慢，会让人想办法绕过（`--no-verify`）。慢的检查放 CI。

## 连接：三层工具分工

| 问题 | 谁查 |
|---|---|
| 缩进不一致 | Prettier |
| 声明了没用到的变量 | ESLint |
| 用了 `==` | ESLint |
| 把 `string` 传给了要 `number` 的函数 | `tsc` |
| 可能为 `null` 的值没判空 | `tsc`（`strictNullChecks`） |
| 索引可能越界 | `tsc`（`noUncheckedIndexedAccess`，见 [08-TypeScript/04](../08-TypeScript/04-编译配置与严格模式.md)） |

## 边界

- **lint 不做类型检查**：类型错误必须靠 `tsc`，两者都要有。
- **类型感知的 lint 很慢**：放 CI，不要放编辑器保存钩子。
- **格式规则不要放进 ESLint**：与 Prettier 冲突且已被废弃。
- **警告会累积**：要么设为 `error`，要么别加；CI 用 `--max-warnings 0`。
- **pre-commit 要快**：只查改动文件，否则会被绕过。
- **规则不是越多越好**：每条规则都有维护成本，加规则要有理由。
