# 包管理与依赖语义

> 前置：[07-引擎与性能/03-性能剖析与优化](../07-引擎与性能/03-性能剖析与优化.md) · 后续：[02-模块解析与产物格式](./02-模块解析与产物格式.md)

> **版本基准**：Node 24 stable / Node 26 latest。本篇示例实测环境：Node v24.13.1，npm 11.8.0，Windows x64。

## 本质

包管理解决三件事，三件事各有载体：

| 问题 | 载体 |
|---|---|
| **声明**需要什么依赖、什么版本范围 | `package.json` |
| **锁定**实际装了哪个版本 | lockfile（`package-lock.json` / `pnpm-lock.yaml` / `yarn.lock`） |
| **解析与安装**到磁盘的什么位置 | `node_modules` 布局 |

npm、pnpm、yarn 是**同一套语义的不同实现**——`package.json` 的字段含义、semver 范围语法、依赖类型都通用。差别在安装布局、磁盘占用与速度。

**`node_modules` 是产物不是源码**：它由 lockfile 决定，可以随时删除重建。**lockfile 必须进版本控制**，它才是"这个项目实际用什么"的记录。

## 机制

### semver：三段与范围语法

版本号是 `主版本.次版本.修订号`：

| 位置 | 何时递增 | 含义 |
|---|---|---|
| 主版本 | 不兼容变更 | 破坏性改动 |
| 次版本 | 向后兼容地新增 | 新功能 |
| 修订号 | 向后兼容地修复 | bug 修复 |

范围语法（用 `semver` 包实测）：

| 写法 | 含义 | 实测匹配 |
|---|---|---|
| `1.2.3` | 精确 | 仅 `1.2.3` |
| `^1.2.3` | 次版本可升，主版本锁死 | `1.2.3` `1.2.4` `1.9.0`（不含 `2.0.0`） |
| `~1.2.3` | 仅修订号可升 | `1.2.3` `1.2.9`（不含 `1.3.0`） |
| `1.x` | 主版本锁死 | `1.0.0` `1.9.9` |
| `*` / 空 | 任意 | 全部 |
| `>=1.2.3 <2.0.0` | 区间 | 区间内 |

**`^` 在 `0.x` 上行为不同**——这是最容易踩的一处：

```console
$ npx semver -r "^0.2.3" 0.2.3 0.2.9 0.3.0
0.2.3
0.2.9

$ npx semver -r "^0.0.3" 0.0.3 0.0.4
0.0.3
```

| 范围 | 实际含义 |
|---|---|
| `^1.2.3` | `>=1.2.3 <2.0.0` |
| `^0.2.3` | `>=0.2.3 <0.3.0`（**次版本也锁死**） |
| `^0.0.3` | `>=0.0.3 <0.0.4`（**只有这一个版本**） |

规则是"**左边第一个非零位锁定**"：`0.x` 视为不稳定，因此 `^` 只允许在同一 `0.次` 内升级。依赖 `0.x` 版本时，`^` 的保护范围比预期窄得多。

**预发布版本默认不匹配任何范围**：

```console
$ npx semver -r "^1.0.0" 1.1.0-beta.1
（无输出）
```

`1.1.0-beta.1` 不满足 `^1.0.0`——需要显式写 `^1.0.0-0` 或 `>=1.1.0-beta.1` 才能纳入。

### 依赖的四种类型

| 字段 | 含义 | 何时安装 |
|---|---|---|
| `dependencies` | 运行时需要 | 总是 |
| `devDependencies` | 仅开发/构建/测试需要 | 开发环境（生产用 `--omit=dev` 跳过） |
| `peerDependencies` | **宿主必须提供**，本包不装 | 由使用者安装 |
| `optionalDependencies` | 装失败也不影响 | 尝试安装，失败则跳过 |

**`peerDependencies` 是给插件用的**：一个 React 组件库不把 `react` 放进 `dependencies`（那会导致同一项目里装进两份 React，而 React 的 hooks 依赖"全局只有一份"），而是声明 `peerDependencies: { "react": "^18" }`，要求使用方自己提供。

`devDependencies` 与 `dependencies` 的划分标准是：**这段代码在用户的应用运行时会执行吗**。构建工具、测试框架、类型定义放 `dev`；组件库、工具函数放 `dependencies`。分错的后果是生产环境装了一堆用不到的东西，或反过来运行时缺依赖。

### lockfile

```console
$ npm install && node -e '…'
lockfileVersion: 3
  node_modules/is-number -> 7.0.0 | resolved: true | integrity: true
```

lockfile 为每个包记录三样东西：

| 字段 | 作用 |
|---|---|
| `version` | **精确**版本（不再是范围） |
| `resolved` | 下载地址 |
| `integrity` | 内容哈希 |

`integrity` 是关键：它保证下载到的包与首次安装时**逐字节一致**。没有它，registry 被投毒或被中间人篡改时无从察觉（供应链安全的一环，见 [06-Node.js平台/05-服务端安全与认证](../06-Node.js平台/05-服务端安全与认证.md)）。

**lockfile 必须提交**。不提交的后果是每个开发者和 CI 装出的版本可能不同——`^` 范围会随时间解析到新版本，出现"我这儿能跑，CI 上挂了"。

**CI 里用 `npm ci` 而不是 `npm install`**：`ci` 严格按 lockfile 安装，且 lockfile 与 `package.json` 不一致时直接失败，不会悄悄更新 lockfile。

### `node_modules` 的布局

npm 早期是**嵌套**安装（每个包带自己的 `node_modules`），导致极深的目录树与大量重复。npm 3 起改为**扁平化**：能提升的依赖都放到顶层。

扁平化的代价是**幽灵依赖**（phantom dependency）：你 `require` 了一个没在自己 `package.json` 里声明的包，但因为它被别的包提升到了顶层，恰好能用。一旦那个包升级或换实现，你的代码就崩了——而 `package.json` 里看不出任何问题。

**pnpm 的解法**是**内容寻址存储 + 硬链接**：全机器只存一份包内容，各项目的 `node_modules` 里是指向它的硬链接。同时 `node_modules` 用符号链接严格按声明组织，**未声明的依赖访问不到**，从机制上消灭幽灵依赖。

| | npm / yarn | pnpm |
|---|---|---|
| 磁盘占用 | 每个项目一份 | 全局一份，硬链接复用 |
| 幽灵依赖 | 可能（扁平化） | 不可能（严格链接） |
| 安装速度 | 中 | 快（大量命中缓存） |
| 兼容性 | 最广 | 少数工具对符号链接敏感 |

### workspaces / monorepo

一个仓库放多个包时，用 workspaces 声明它们的关系：本地包之间直接互相引用，不必发到 registry 再装回来。

```json
{ "workspaces": ["packages/*"] }
```

关键收益是**本地链接**与**统一安装**——改一个包，依赖它的包立刻看到变化，不需要 `npm link` 或重新发布。

## 连接：三种包管理器

| | npm | yarn | pnpm |
|---|---|---|---|
| lockfile | `package-lock.json` | `yarn.lock` | `pnpm-lock.yaml` |
| 布局 | 扁平化 | 扁平化 | 严格符号链接 |
| 幽灵依赖 | 可能 | 可能 | 不可能 |
| 磁盘 | 每项目一份 | 每项目一份 | 全局共享 |
| 严格安装命令 | `npm ci` | `yarn install --immutable` | `pnpm install --frozen-lockfile` |

**不要混用**：一个项目只用一种包管理器，混用会产生多个 lockfile 与不一致的 `node_modules`。团队用 `packageManager` 字段或 CI 检查来约束。

## 边界

- **`^` 在 `0.x` 上保护范围更窄**：`^0.2.3` 不含 `0.3.0`。
- **预发布版本默认不匹配任何范围**：需显式指定。
- **lockfile 必须提交**，CI 用 `npm ci` 而非 `npm install`。
- **`node_modules` 是产物**：可删除重建，不要手工修改里面的文件。
- **幽灵依赖在 npm/yarn 下可能发生**：依赖必须显式声明，否则换个包管理器就崩。
- **`peerDependencies` 不会被自动安装**：使用方负责提供。
- **`devDependencies` 不装在生产环境**：运行时需要的包不能放这里。
