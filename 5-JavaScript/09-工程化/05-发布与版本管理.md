# 发布与版本管理

> 前置：[04-代码规范与静态检查](./04-代码规范与静态检查.md) · 后续：[10-测试与质量/01-测试理论](../10-测试与质量/01-测试理论.md)

> **版本基准**：Node 24 stable / Node 26 latest。本篇示例实测环境：Node v24.13.1，npm 11.8.0，Windows x64。

## 本质

发布是把代码打成 tarball 推到 registry。要控制两件事：

| 控制什么 | 手段 |
|---|---|
| **发什么文件** | `files` 字段（白名单） |
| **发什么版本号** | semver 规则 + 预发布流程 |

其中"发什么文件"最容易被忽视——`npm pack` 默认会带上项目里的很多东西，包括不该公开的。**发布前必须用 `npm pack --dry-run` 看一眼实际内容。**

版本号则是一个**对外承诺**：`^1.2.3` 的使用者会相信"1.x 内的升级不会破坏我"（见 [01-包管理与依赖语义](./01-包管理与依赖语义.md)）。所以版本号的选取依据不是"改了多少代码"，而是**"使用者的代码会不会坏"**。

## 机制

### `files`：白名单决定发布内容

```json
{ "files": ["dist"] }
```

实测效果（项目里还有 `secret.txt`、`src/`、`node_modules/`）：

```console
$ npm pack --dry-run
npm notice Tarball Contents
npm notice 32B dist/index.d.ts
npm notice 20B dist/index.js
npm notice 336B package.json
npm notice total files: 3
```

**只发了 3 个文件**——`secret.txt`、`src/` 都没进去。规则是：

| 情况 | 行为 |
|---|---|
| 有 `files` 字段 | **白名单**：只发列出的路径（加 `package.json`、`README`、`LICENSE`） |
| 无 `files` 字段 | 发全部，但排除 `.gitignore` 中的内容 |
| 有 `.npmignore` | 作为排除规则（在无 `files` 时生效） |

**用 `files` 而不是 `.npmignore`**：白名单是"明确要发什么"，新增文件默认不发；黑名单是"排除什么"，新增文件默认会发——后者是泄露源码与密钥的常见途径。

无论用哪种，**发布前跑一次 `npm pack --dry-run`**。这一步能拦住绝大多数误发布。

### 包的必要字段

| 字段 | 作用 |
|---|---|
| `name` / `version` | 唯一标识（作用域包用 `@scope/name`） |
| `exports` | 入口与封装边界（见 [02-模块解析与产物格式](./02-模块解析与产物格式.md)） |
| `types` | 类型声明入口；**必须在 `exports` 的 `types` 条件里放第一位** |
| `files` | 发布白名单 |
| `sideEffects` | 让使用方能 tree-shake（见 [03-打包与转译](./03-打包与转译.md)） |
| `engines` | 要求的 Node 版本范围 |
| `license` | 许可证，缺失时 npm 会警告 |
| `repository` | 源码地址，便于溯源 |

**`engines` 不是强制的**——npm 默认只警告不阻止。它表达的是"这个包在这些版本上测试过"，配合 `engine-strict` 配置才能变成硬约束。

### 版本号怎么选

| 变更 | 版本位 | 判据 |
|---|---|---|
| 破坏性变更（改签名、删导出、改行为） | **major** | 使用者的代码**会**编译失败或行为改变 |
| 新增功能（加导出、加可选参数） | **minor** | 使用者的代码**不会**坏 |
| 修 bug、内部重构 | **patch** | 行为修复，接口不变 |

判据是**"使用者的代码会不会坏"**，不是"我改了多少行"。一个字符的改动如果是破坏性的（如把默认值从 `true` 改成 `false`），就该发 major。

**`0.x` 的特殊约定**：主版本为 0 表示"尚未稳定"，此时 `^0.2.3` 只允许 `0.2.x` 内的升级（见 [01-包管理与依赖语义](./01-包管理与依赖语义.md) 的实测）。所以 `0.x` 阶段每个不兼容改动都该升**次**版本。

### 预发布流程

预发布版本在版本号后加 `-` 与标识符：

```console
$ npx semver 1.0.0-alpha.1 1.0.0-alpha.2 1.0.0-beta.1 1.0.0-rc.1 1.0.0
1.0.0-alpha.1 1.0.0-alpha.2 1.0.0-beta.1 1.0.0-rc.1 1.0.0
```

排序规则是**按标识符比较**：`alpha` < `beta` < `rc` < 正式版。常用约定：

| 阶段 | 含义 |
|---|---|
| `alpha.N` | 内部试用，接口可能大改 |
| `beta.N` | 功能冻结，等反馈 |
| `rc.N` | 候选发布，只修阻断性 bug |

**预发布版本默认不匹配任何范围**（实测见 [01-包管理与依赖语义](./01-包管理与依赖语义.md)）——使用者必须显式指定，不会误装。这正是预发布的意义。

### dist-tags

`npm publish` 默认打 `latest` 标签，使用者 `npm install pkg` 装的就是它。预发布应打别的标签：

```bash
npm publish --tag next      # 使用者要 npm install pkg@next 才装到
```

| 标签 | 用途 |
|---|---|
| `latest` | 稳定版（默认） |
| `next` | 预发布 |
| `beta` / `rc` | 更细的阶段 |

**预发布一定要用 `--tag`**，否则它会被当成稳定版推给所有人。

### 发布流程

```bash
npm pack --dry-run      # 1. 看要发什么
npm run build           # 2. 产出 dist
npx tsc --noEmit        # 3. 类型检查（见 08-04）
npm test                # 4. 测试
npm publish --dry-run   # 5. 模拟发布
npm publish             # 6. 真正发布
```

`prepublishOnly` 脚本可以自动跑前几步：

```json
{ "scripts": { "prepublishOnly": "npm run build && npm test" } }
```

**版本号一旦发布不能重用**。npm 允许 `unpublish` 但有严格限制（72 小时内、且该版本下载量低），且**撤销不能挽回已经下载的人**。所以发布前的检查清单不是形式。

### monorepo 下的发布

多包仓库里，改一个包往往需要连带发布依赖它的包。手工维护版本号与变更日志容易出错，工具化的做法是**基于变更文件自动推导版本**：

1. 每个改动在合并时附一份"变更说明"（改了哪个包、是 patch/minor/major）；
2. 发布时工具汇总，自动升版本、生成 changelog、按依赖顺序发布。

这类工具（Changesets 等）解决的核心问题是**依赖顺序**——被依赖的包必须先发，否则依赖它的包会指向一个不存在的版本。

## 连接：发布前检查清单

| 检查 | 命令 |
|---|---|
| 实际发布内容 | `npm pack --dry-run` |
| 是否含敏感文件 | 看上面的输出（密钥、`.env`、测试数据） |
| 类型检查 | `npx tsc --noEmit` |
| 测试 | `npm test` |
| 生产构建 | `npm run build`（见 [03-打包与转译](./03-打包与转译.md)） |
| 版本号是否符合 semver | 对照上表判据 |
| 预发布是否打了 `--tag` | 是则不会被当成稳定版 |
| `engines` 是否与实际支持范围一致 | 看测试矩阵 |

## 边界

- **用 `files` 白名单而非 `.npmignore`**：新增文件默认不发。
- **发布前必须 `npm pack --dry-run`**：这一步拦住大多数误发布。
- **`types` 条件必须放 `exports` 的第一位**。
- **预发布必须 `--tag`**：否则被当成稳定版。
- **版本号一旦发布不可重用**：`unpublish` 限制严格且不可挽回。
- **`0.x` 的每个不兼容改动升次版本**：因为 `^` 在 `0.x` 上只放开修订号。
- **`engines` 默认只是警告**：不是硬约束。
- **monorepo 要注意发布顺序**：被依赖的先发。
