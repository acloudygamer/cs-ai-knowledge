# 模块解析与产物格式

> 前置：[01-包管理与依赖语义](./01-包管理与依赖语义.md) · 后续：[03-打包与转译](./03-打包与转译.md)

> **版本基准**：Node 24 stable / Node 26 latest。本篇示例实测环境：Node v24.13.1，Windows x64。

## 本质

写 `import "x"` 时，**加载哪个文件不由这行代码决定，而由 `x` 自己的 `package.json` 决定**。同一个包可以准备多份产物（ESM / CJS / 浏览器版 / Node 版），由条件导出按消费方挑选。

这带来一个必须理解的后果：**同一份依赖在你的项目里可能被加载两次**（一次走 ESM 入口、一次走 CJS 入口），两份产物各有自己的模块级状态——称为**双包危险**（dual package hazard）。

模块系统的**语义**（活绑定、包装函数、顶层 `await`）见 [01-语言核心/06-模块](../01-语言核心/06-模块.md)；`exports` 字段的**解析规则**（只对裸名生效、条件顺序、封装边界）见 [06-Node.js平台/01-运行时与模块系统](../06-Node.js平台/01-运行时与模块系统.md)。本篇讲**产物格式本身**与它们带来的问题。

## 机制

### 四种产物格式

| 格式 | 加载方式 | 用途 |
|---|---|---|
| **ESM** | `<script type="module">` / `import` | 现代浏览器与 Node 的原生格式 |
| **CJS** | `require()` | Node 的传统格式 |
| **UMD** | 兼容前两者 + 全局变量 | 同时面向 Node 与浏览器的老式库 |
| **IIFE** | `<script src>` 挂全局变量 | 只需在浏览器直接引入 |

同一段源码转译成不同格式的样子（以导出一个函数为例）：

```javascript
// ESM（原生，不转译）
export function greet(name) { return "你好，" + name; }
```

```javascript
// CJS
"use strict";
Object.defineProperty(exports, "__esModule", { value: true });
exports.greet = greet;
function greet(name) { return "你好，" + name; }
```

```javascript
// IIFE
var MyLib = (function (exports) {
  "use strict";
  function greet(name) { return "你好，" + name; }
  exports.greet = greet;
  return exports;
})({});
```

三种形态的差异全在**导出机制**上：ESM 是语言级的静态绑定，CJS 是给 `exports` 对象挂属性，IIFE 是立即执行并返回一个对象赋给全局变量。CJS 产物里那行 `__esModule` 标记是**给转译器看的**——它用来区分"这个 CJS 模块是转译来的 ESM"与"原生 CJS"，从而正确处理默认导出。

**新项目只产出 ESM**。CJS 只在需要支持老版本 Node 或老工具链时保留。

### 双包危险

一个包同时提供 ESM 与 CJS 入口时，**两种加载方式各执行一次模块体**，得到两份独立的状态。实测：

```console
$ node use.cjs
[CJS 实例] count = 2
[ESM 实例] count = 1
两个实例是同一份状态吗: false
```

`require("dual-lib")` 与 `import("dual-lib")` 拿到的是**两个不同的模块实例**：CJS 那份被 `bump()` 两次，ESM 那份被 `bump()` 一次，`cjs.state === esm.state` 为 `false`。

后果包括：

| 场景 | 后果 |
|---|---|
| 模块级单例 | 变成两个单例 |
| 模块级缓存 | 两份缓存，互不可见 |
| `instanceof` 检查 | 跨格式的对象不匹配（构造函数不同） |
| 配置对象 | 改了一份，另一份不知道 |

**规避方式**（按推荐顺序）：

1. **只发一种格式**——现代包只发 ESM，由使用方的打包工具处理兼容；
2. **ESM 入口包一层 CJS**——让 CJS 是唯一实现，ESM 入口只做转发，状态只有一份；
3. **把状态外置**——模块级状态移到 `globalThis` 或显式传入，不依赖模块单例。

### 打包工具如何挑入口

当包同时声明了多个入口字段时，工具的优先级大致是：

```text
exports（条件导出） > module（打包器专用） > main（Node 传统入口）
```

`exports` 存在时**优先且封闭**——`main` 与 `module` 都会被忽略，未列出的子路径也不可达（见 [06-Node.js平台/01-运行时与模块系统](../06-Node.js平台/01-运行时与模块系统.md)）。`module` 字段是打包工具时代的历史产物，新包不必再写。

常见条件：

| 条件 | 命中者 |
|---|---|
| `import` / `require` | 按加载方式 |
| `node` / `browser` / `worker` | 按运行环境 |
| `development` / `production` | 按构建模式 |
| `types` | 类型声明（**必须放第一个**） |
| `default` | 兜底，**必须放最后** |

`types` 放第一位是硬性要求：条件按顺序匹配，放后面会被前面的条件抢走，导致类型解析失败。

### `type` 字段与扩展名

| 文件 | 模块类型 |
|---|---|
| `.mjs` | 恒为 ESM |
| `.cjs` | 恒为 CommonJS |
| `.js` | 看最近的 `package.json` 的 `"type"`；都没有时按语法自动判定 |

自动判定是 Node 的兼容措施（见 [01-语言核心/01-安装与第一个程序](../01-语言核心/01-安装与第一个程序.md) 的实测），但它会带来 `MODULE_TYPELESS_PACKAGE_JSON` 警告与额外的解析开销。**显式声明 `"type"`**。

## 连接：格式选择

| 场景 | 选择 |
|---|---|
| 新库，使用者是现代工具链 | 只发 ESM |
| 需要同时支持 `require` 与 `import` | 双入口 + 状态外置，或单 CJS 实现 + ESM 转发 |
| 浏览器 `<script>` 直接引入 | IIFE / UMD |
| Node 内部脚本 | 与项目 `"type"` 保持一致 |

## 边界

- **双包危险会导致状态分裂**：同一包被加载两次，`===` 比较失败。
- **`exports` 存在时 `main` 被忽略**：迁移时容易漏掉旧入口。
- **`types` 条件必须放第一位**，`default` 必须放最后。
- **`module` 字段是历史产物**：新包用 `exports`。
- **`.js` 的模块类型靠自动判定不可靠**：显式写 `"type"`。
- **IIFE / UMD 会污染全局**：只在必须支持无构建的浏览器环境时使用。
