# 打包与转译

> 前置：[02-模块解析与产物格式](./02-模块解析与产物格式.md) · 后续：[04-代码规范与静态检查](./04-代码规范与静态检查.md)

> **版本基准**：Node 24 stable / Node 26 latest。本篇示例实测环境：Node v24.13.1，`npx esbuild`，Windows x64。

## 本质

打包工具做三件事：

| 步骤 | 做什么 |
|---|---|
| **解析** | 从入口出发，沿 `import` / `require` 建出依赖图 |
| **打包** | 把多个文件合成少数几个产物 |
| **转译** | 按目标环境把语法降级 |

**转译（transpile）只做语法转换，不做类型检查**——这是它与 `tsc` 的根本分工（见 [7-TypeScript/08-编译配置与严格模式](../../7-TypeScript/08-编译配置与严格模式.md)）。打包器快，正是因为它跳过了类型检查。

需要打包的根源在 [00-概览/01-JavaScript 全景](../00-概览/01-JavaScript全景.md) 那条事实：**JavaScript 没有编译步骤，构建链全部来自生态**。浏览器直接执行源文本，因此"把源码整理成浏览器能高效加载的形态"这件事必须由外部工具完成。

## 机制

### 为什么需要打包

| 问题 | 打包如何解决 |
|---|---|
| 浏览器加载几十上百个模块 = 几十上百次请求 | 合成少数文件 |
| 裸名导入（`import "lodash"`）浏览器不认 | 打包时解析成实际路径并内联 |
| `node_modules` 里大量 CommonJS 包 | 转成浏览器可用的格式 |
| 新语法在老浏览器上不支持 | 按 `target` 降级 |
| 传输体积 | 压缩、去死代码、代码分割 |

浏览器**原生支持 ESM**（`<script type="module">`），所以"不打包"在技术上是可行的。实践中仍需打包的原因是：**依赖数量**与**`node_modules` 里的 CommonJS**。只有当依赖很少、且全为 ESM 时，才可以考虑直接发布源文件。

### Tree-shaking：删除未使用的导出

打包器做静态分析，把没被用到的导出删掉。实测：

```console
$ npx esbuild main.js --bundle --format=esm --minify
function o(e){return e*2}console.log(o(21));
```

`lib.js` 导出了四个东西（`used`、`unused`、`CONST`、`withSideEffect`），`main.js` 只用了 `used`——**产物里只剩它一个**。

Tree-shaking 成立的前提是**模块结构静态**（ESM 满足，CommonJS 不满足，见 [01-语言核心/06-模块](../01-语言核心/06-模块.md)）。但静态结构还不够，还需要工具知道"这个模块有没有副作用"：

```json
{ "sideEffects": false }
```

`package.json` 里声明 `sideEffects: false` 表示"本包的所有模块，只要没被用到就可以整体删除"。不声明时，打包器只能保守处理——因为一个模块**可能在被导入时执行了副作用**（注册全局、打补丁），删掉会改变行为。

**库作者应当声明 `sideEffects`**，否则使用者无法 tree-shake。有副作用的文件单独列出：

```json
{ "sideEffects": ["./src/polyfill.js", "*.css"] }
```

### 转译：语法降级与 helper 注入

按 `target` 把新语法改写成等价的老语法。降级到 ES2015 的实测产物：

```javascript
// 源码
class A { #x = 1; get v() { return this.#x } }
async function f() { return await Promise.resolve(v); }
```

```javascript
// --target=es2015 的产物（节选）
var __privateGet = (obj, member, getter) => (__accessCheck(obj, member, "read from private field"), getter ? getter.call(obj) : member.get(obj));
var __async = (__this, __arguments, generator) => {
  return new Promise((resolve, reject) => { /* 状态机 */ });
};
```

两点值得注意：

- **降级是"注入辅助代码"而非"简单改写"**：私有字段要维护一个 `WeakMap` 记录归属（`__accessCheck` 检查"这个私有成员属于这个对象吗"），`async` 要展开成基于生成器的状态机。产物因此变大。
- **目标越低，产物越大越慢**：降级后的代码不是等价性能，是"能在老环境跑"的代价。所以 **`target` 应按实际需要支持的浏览器定**，不要无脑降到 ES5。

现代工具（esbuild、SWC、Rolldown）用原生代码实现转译，速度比纯 JavaScript 的实现快一个数量级——这也是 [7-TypeScript/08-编译配置与严格模式](../../7-TypeScript/08-编译配置与严格模式.md) 里"`tsc` 只做类型检查、转译交给打包器"这套分工的动因。

### 开发与生产

| | 开发 | 生产 |
|---|---|---|
| 目标 | 改完立刻看到 | 体积与加载速度 |
| 压缩 | 否 | 是 |
| Source map | 完整（便于调试） | 视需要（可能不外发） |
| 模块 | 按需加载，不做 tree-shaking | 完整优化 |
| 更新方式 | HMR（热替换，保留状态） | 重新加载 |

**开发与生产的产物不同**，所以"开发能跑生产挂"是常见问题。CI 里应跑一次生产构建作为验证。

### 代码分割

动态 `import()` 让打包器把某部分代码切成独立的产物，按需加载：

```javascript
const { heavyFn } = await import("./heavy.js");
```

它同时是**路由级懒加载**与**条件加载**的实现手段。静态 `import` 会在启动时全部加载，动态 `import` 推迟到真正需要时——这是首屏体积优化的主要手段之一。

注意：动态 `import()` 返回 Promise，属于异步操作，时序问题归 [04-异步与并发/03-async/await 与异步模式](../04-异步与并发/03-async-await与异步模式.md)。

## 连接：工具分工

| 工具 | 职责 |
|---|---|
| `tsc --noEmit` | 类型检查 |
| esbuild / SWC / Rolldown | 转译 + 打包（不做类型检查） |
| Vite / Next.js 等 | 组合上述工具，提供开发服务器与构建流程 |
| Terser / esbuild | 压缩 |

**类型检查与转译分开跑**：CI 里两者都要有。只跑打包会漏掉类型错误；只跑 `tsc` 不会产出可部署的产物。

## 边界

- **转译不做类型检查**：`tsc --noEmit` 必须单独跑。
- **CommonJS 无法 tree-shake**：结构动态，静态分析无从下手。
- **库不声明 `sideEffects` 会失去 tree-shaking**：声明错了（把有副作用的模块标为无副作用）会导致运行时行为丢失。
- **`target` 越低产物越大越慢**：按实际支持范围定。
- **开发与生产产物不同**：CI 要跑生产构建。
- **动态 `import()` 是异步的**：加载失败要处理，见 [01-语言核心/07-错误处理](../01-语言核心/07-错误处理.md)。
- **Source map 可能泄露源码**：生产环境是否外发要明确决定。
