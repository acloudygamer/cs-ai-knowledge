# 测试覆盖率

> **版本基准**: Node24+ES2024 (stable) | Node26+ES2026 (latest)

## 定义

测试覆盖率是代码被执行路径占总路径比例的量化指标，用于**识别测试盲区而非衡量测试质量**。覆盖率是必要条件而非充分条件——100% 覆盖的代码仍可能有逻辑错误、边界 bug 或语义错误。

覆盖率本质是一个**路径可达性矩阵**：给定代码图 $G = (V, E)$（顶点为基本块，边为控制流），覆盖率为从入口到出口的可达路径中，被测试套件覆盖的路径比例。

## 数学模型

### Istanbul 覆盖率模型

Istanbul 在代码编译/解释时通过 `babel-plugin-istanbul` 插入计数器，跟踪每个基本块的命中状态。

设代码的基本块集合为 $B = \{b_1, b_2, ..., b_n\}$，测试执行后命中的块集合为 $H \subseteq B$。覆盖率指标定义为：

| 指标 | 公式 | 含义 |
|------|------|------|
| Statements | $\frac{|H_s|}{|B_s|}$ | 执行过的语句占总语句的比例 |
| Branches | $\frac{|H_b|}{|B_b|}$ | 执行过的分支占总分支的比例 |
| Functions | $\frac{|H_f|}{|B_f|}$ | 被调用过的函数占总函数的比例 |
| Lines | $\frac{|H_l|}{|B_l|}$ | 被覆盖行占总行数的比例 |

**分支的计算**：每个 `if/else` 产生 2 个分支；`&&`、`||` 的短路求值也算分支；`switch` 每个 case 对应一个分支，default 额外一个分支。

**归约终点**：覆盖率归结为**基本块的命中计数问题**。插桩代码在每个基本块入口插入计数器，测试运行时累加，汇总后计算比例。

### 覆盖率阈值约束

`coverageThreshold` 配置将覆盖率从"观测指标"变为"质量门槛"：

$$
\text{threshold}(m) = \begin{cases} \text{pass} & \text{if } \text{actual}(m) \geq \text{config}(m) \\ \text{fail} & \text{otherwise} \end{cases}
$$

其中 $m \in \{\text{statements}, \text{branches}, \text{functions}, \text{lines}\}$。

**约束**：覆盖率阈值是**下界约束**，通过不意味着测试质量高；未通过意味着存在明确的测试盲区。设置阈值时需权衡：过低（如 0%）无意义，过高（如 100%）可能导致开发者添加无意义的覆盖凑数。

### MC/DC 覆盖模型（扩展）

Modified Condition/Decision Coverage 是分支覆盖的更强变体，常用于航空/医疗等高可靠性领域。

对于布尔表达式 $E = C_1 \land C_2 \land ... \land C_n$，MC/DC 要求：
- 决策覆盖：至少一次真、一次假
- 条件覆盖：每个条件 $C_i$ 至少一次真、一次假
- MC/DC 覆盖：每个条件 $C_i$ 的变化**独立地**影响决策结果

**数学定义**：设 $E(C_i)$ 为固定其他条件时 $C_i$ 的真值对决策结果的影响。MC/DC 要求对每个 $i$，存在两组输入 $(C_1^1, ..., C_i^1, ..., C_n^1)$ 和 $(C_1^2, ..., C_i^2, ..., C_n^2)$，使得：
$$C_j^1 = C_j^2 \quad \forall j \neq i$$
$$C_i^1 \neq C_i^2$$
$$E(C^1) \neq E(C^2)$$

Istanbul 的分支覆盖不满足 MC/DC——它只计数分支是否被执行，不追踪条件间独立影响。

## 数据流

<pre>
源代码 (.js)
    │
    ▼
babel-plugin-istanbul 插桩（AST 遍历）
    │
    ├── 遍历 AST 节点
    ├── 每个基本块入口插入 __coverage__[id]++
    ├── 条件分支处插入分支标签
    └── 输出带计数器的代码
    │
    ▼
Jest 运行测试
    │
    ▼
执行被插桩的代码
    │
    ├── 每个语句执行 → 对应计数器 +1
    ├── 每个分支执行 → 分支计数器 +1
    └── 每个函数调用 → 函数计数器 +1
    │
    ▼
覆盖率数据汇总 (coverage/)
    │
    ├── lcov.info (行覆盖详情)
    ├── coverage-summary.json (汇总)
    └── index.html (人工审查)
    │
    ▼
coverageThreshold 比对
    │
    ├── actual >= threshold ──► 构建继续
    └── actual < threshold ──► 构建失败 (exit code 1)
</pre>

### 分支覆盖追踪（AST 层面）

<pre>
源代码:
if (x > 0) {        // 行 1
  doSomething();    // 行 2
} else {             // 行 3
  doOther();         // 行 4
}

AST 插桩后:
if (x > 0) {
  __coverage__['B1']++;  doSomething();
} else {
  __coverage__['B2']++;  doOther();
}

// 覆盖率为 0%: B1=0, B2=0
// 覆盖率为 50%: B1=1, B2=0 或 B1=0, B2=1
// 覆盖率为 100%: B1=1, B2=1
</pre>

### 圈复杂度与覆盖率的关联

设代码段 $S$ 的圈复杂度为 $V(G) = E - V + 2$（基本图 $G$ 的边数减顶点数加 2）。独立路径数的上界为 $V(G)$。覆盖率与复杂度的隐含关系：

- **低复杂度 + 高覆盖率** → 充分测试
- **高复杂度 + 高覆盖率** → 可能遗漏边界条件
- **任何复杂度 + 低覆盖率** → 测试盲区存在

覆盖率无法检测复杂度本身——一段 $V(G)=1$ 的代码（无分支）达到 100% 覆盖，但 $V(G)=20$ 的代码即使 80% 覆盖，独立路径仍可能有未测边界。

## 机制

### 插桩的基本块划分规则

Istanbul 的基本块定义：每个**没有内部分支的连续语句序列**。基本块边界出现在以下位置：

1. **分支目标**：`if`、`for`、`while`、`switch`、`catch` 的入口
2. **分支来源**：`if`/`else`、`?:`、`||`、`&&` 的条件表达式之后
3. **函数调用后**（为函数覆盖率计数的辅助边界）

```javascript
// 基本块划分示例
const a = 1;        // 块 1（赋值无分支）
const b = 2;        // 块 1（与上同行）
if (condition) {    // 块 2（分支入口）
  foo();            // 块 3
} else {            // 块 4
  bar();            // 块 5
}
baz();              // 块 6
```

**每行的尾端标识一个基本块边界**。空行和注释不影响基本块。同一行多个语句共享同一块。

### 覆盖率阈值的设计意图

`coverageThreshold` 防止覆盖率随时间劣化（"测试腐化"）：

```javascript
// jest.config.js
module.exports = {
  coverageThreshold: {
    global: {
      branches: 80,
      functions: 80,
      lines: 80,
      statements: 80,
    },
  },
};
```

**约束**：阈值是**下界约束**，通过不意味着测试质量高；未通过意味着存在明确的测试盲区。正确用法：与代码审查结合，将覆盖率作为"最低标准"而非"质量目标"。

### 覆盖率假象

覆盖率反映的是**执行路径可达性**而非**逻辑正确性**：

```javascript
function divide(a, b) {
  return a / b;  // 100% 覆盖（语句、分支、函数均覆盖）
                   // 但 b=0 时返回 Infinity 而非抛出错误
}
```

`expect(divide(1, 0)).toThrow()` 才能捕获这个 bug——即使这不影响覆盖率。

**根本局限**：覆盖率无法检测"做了错误的事情"——只能检测"某些路径没跑到"。100% 覆盖的代码可以全部执行错误逻辑。

### 未覆盖分支的危害

未覆盖的分支是潜在的 bug 盲区：

```javascript
function calculate(a, b, op) {
  if (op === 'add') return a + b;      // 分支 1
  if (op === 'sub') return a - b;      // 分支 2 (未覆盖)
  return 0;                             // 分支 3 (未覆盖)
}
```

只测试 add 时覆盖率 33%，但分支 2、3 可能隐藏实现错误（如 op 为 'mul' 时静默返回 0 而非报错）。

**风险量化**：设未覆盖分支比例为 $r$，则潜在 bug 密度期望为 $r \times D$，其中 $D$ 为每个分支的平均 bug 密度（经验值：防御性分支 $D$ 更高）。

### 插桩对运行时的影响

插桩代码在每个基本块插入计数器，引入的时间和空间开销：

| 指标 | 影响 | 量级 |
|------|------|------|
| 时间 | 每个计数器 +1 原子操作 | $\times 1.1 \sim \times 1.5$ |
| 内存 | `__coverage__` 对象存储所有计数器 | $\times 1 \sim \times 2$ |

对于大多数项目此开销可忽略；对于高频交易或嵌入式系统需评估。

## 对比参照

| 指标 | 含义 | 假阳性风险 |
|------|------|-----------|
| Statements | 多少语句被执行 | 三元表达式内部只算一语句 |
| Branches | 多少分支被执行 | 每个 if/else 算 2 分支 |
| Functions | 多少函数被调用 | 可能函数被调用但内部逻辑未覆盖 |
| Lines | 多少行被执行 | 空行、注释不计入；多语句行只算一 |
| MC/DC | 条件独立影响决策 | 仅手动分析工具支持，Istanbul 不原生支持 |

```javascript
// 识别未覆盖分支示例
function calculate(a, b, op) {
  if (op === 'add') return a + b;      // 分支1
  if (op === 'sub') return a - b;      // 分支2（未覆盖）
  return 0;                             // 分支3（未覆盖）
}
// 需补充：calculate(1, 2, 'sub') 和 calculate(1, 2, 'other')
```

```javascript
// 边界条件：b === 0 分支
function divide(a, b) {
  if (b === 0) throw new Error('div by zero');
  return a / b;
}
// 需覆盖 throw 分支：divide(1, 0)
```

```javascript
// 循环覆盖 0/1/多次
const arr = [];
process(arr);     // 0次
process([1]);     // 1次
process([1, 2, 3]); // 多次
```

// 避免假覆盖率：mock 外部依赖
jest.mock('./api');

```

```

```javascript
// 条件覆盖的完整路径
function test(x) {
  if (x > 0) return 'positive';    // T 分支
  if (x < 0) return 'negative';    // T 分支（x <= 0 时不进入）
  return 'zero';                    // 隐含分支
}
// 完整覆盖需要：test(1), test(-1), test(0)
```
