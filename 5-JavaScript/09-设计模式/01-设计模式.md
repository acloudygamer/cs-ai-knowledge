# 设计模式

> **版本基准**: JavaScript ES2024+ (stable) | JavaScript ES2026+ (latest)

## 定义

设计模式是针对软件设计中常见问题的**结构化解决方案**，是经过提炼的类层次与对象层次的设计经验总结。其核心价值在于将"某种场景下为什么应该这样做"的形式化表述固化下来，使设计者无需从第一性原理重新推导。

设计模式按其解决的本质问题可分为三个维度：

- **创建型**：控制"何时、由谁、创建什么"——将实例化决策从使用方转移至配置方
- **结构型**：控制"如何包装、如何连接"——通过组合改变对象接口而不改写内部实现
- **行为型**：控制"谁负责、何时通知、如何撤销"——将算法封装为可替换的对象

---

# 创建型模式

## 定义

创建型模式是一类将对象**实例化逻辑**封装并与使用者解耦的结构化方案。其核心目标是将"如何创建"的决策从使用方延迟到配置方，使系统能够在不修改已有代码的前提下替换或扩展对象的创建方式。

**版本差异说明**：ES2022+ 引入了私有类字段（`#field`）语法，使得单例等模式的实现可以从"闭包私有化"演进为"语言级访问控制"。ES2026+ 的类成员表达式进一步简化了工厂类型的声明，`Symbol.dispose` 为建造者的资源清理提供了确定性语义。

## 数学模型

### 单例的唯一性约束

设 $S$ 为系统中所有实例对象的集合， $\text{accessible}(x)$ 表示对象 $x$ 是否可被外部代码引用。则单例的唯一性约束可形式化为：

$$
\exists! s \in S:\ \text{accessible}(s)
$$

即**恰好存在一个**可访问的实例。在无并发干预的单线程环境中，此约束天然满足；但在多线程环境下，若无同步原语，则可能违背 $\exists!$ 的约束。

**并发竞态的量化描述**：设 $P_n$ 为 $n$ 个线程同时首次调用构造函数时创建超过一个实例的概率。在基于 `if (instance === null)` 的无锁实现中：

$$
P_n \approx 1 - \prod_{i=1}^{n-1}\left(1 - \frac{1}{i}\right) \xrightarrow{n \to \infty} 1
$$

推导：第 $i$ 个线程到达时，前 $i-1$ 个线程已分配了 $i-1$ 个不同地址（由于内存分配随机性），第 $i$ 个线程命中已有地址的概率为 $\frac{i-1}{i}$ ，故不冲突的概率为 $\prod_{i=1}^{n-1}\frac{i-1}{i}$ 。这意味着随着并发度增加，无同步的懒汉式单例几乎必然失效。

**懒汉式 vs 饿汉式的代价函数**：

| 模式 | 初始化代价 $C_{init}$ | 首次访问延迟 $T_{first}$ | 内存占用 |
|------|----------------------|--------------------------|----------|
| 懒汉式 | $O(1)$ （创建时） | $O(1) + C_{init}$ | $O(1)$ |
| 饿汉式 | $C_{init}$ （类加载时） | $O(1)$ | $O(1)$ |

### 工厂的类型分发

简单工厂的类型映射 $f: T \to C$ 是静态函数，其中 $T$ 为类型标识符集合， $C$ 为构造函数集合。每次新增类型必须修改 $f$ 的定义——即违反**开闭原则**（对扩展开放，对修改关闭）。

工厂方法通过延迟绑定解决此问题：选择行为由子类重写决定，调用方的类型分发从 $O(n)$ 条件分支退化为 $O(1)$ 虚表查找。

抽象工厂的产品族约束：设产品族 $P = \{p_1, p_2, \ldots, p_k\}$ ，工厂接口保证 $\forall i,j:\ \text{compatible}(p_i, p_j)$ ，即族内产品互不冲突。

### 建造者的步骤编排

设复杂产品由 $k$ 个组件 $\{c_1, c_2, \ldots, c_k\}$ 构成，组件 $c_i$ 的构建步骤序列为 $S_i = (s_{i,1}, s_{i,2}, \ldots, s_{i,m_i})$ 。则 Director 的全序编排 $\Sigma$ 必须满足组件间的**偏序依赖**：

$$
\Sigma = \text{topoSort}(\{S_i\}, \prec)
$$

其中 $s_{a,b} \prec s_{c,d}$ 表示"步骤 $(a,b)$ 必须在步骤 $(c,d)$ 之前执行"。若依赖图存在环，则不存在合法的拓扑序，Builder 无法保证产品一致性。

### 单例模式数据流

<pre>
┌─────────────────────────────────────────────────────────────┐
│                    首次调用（无实例）                          │

                   └──────────┬───────────┘
                              │ yes
                              ▼
                   ┌──────────────────────┐
                   │  分配内存 + 构造函数   │
                   └──────────┬───────────┘
                              │
                              ▼
                   ┌──────────────────────┐
                   │  instance = 新对象    │
                   └──────────┬───────────┘
                              │
                              ▼
                   ┌──────────────────────┐

                   └──────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│                    后续调用（有实例）                         │

**所有权转移**：构造函数执行后，实例的所有权从堆分配器转移到全局单例变量。后续调用仅传递引用，不发生所有权变更。

### 工厂模式数据流

<pre>
client ──type──▶ SimpleFactory.create(type)
                        │
            ┌───────────┼───────────┐
            ▼           ▼           ▼
         Admin       Guest        User
            │           │           │
            └───────────┴───────────┘
                        │
                        ▼
                 return new Constructor()

client ──type──▶ FactoryMethod.create()  [虚调用]
                        │
              ┌─────────┴─────────┐
              ▼                   ▼
       AdminFactory.create()  GuestFactory.create()
              │                   │
              ▼                   ▼
         new Admin()          new Guest()
</pre>

**虚分派机制**：调用 `FactoryMethod.create()` 时，JavaScript 运行时通过原型链查找实际的 `create` 方法。类型分发从调用方的条件分支转移到运行时查表，复杂度从 $O(n)$ 降为 $O(1)$ 。

### 建造者模式数据流

<pre>
client ──new Director(builder)──▶ Director
                                        │
                               ┌────────┴────────┐
                               ▼                 ▼
                         builder.stepA()   builder.stepB()
                               │                 │
                               └────────┬────────┘
                                        ▼
                               builder.getResult()
                                        │
                                        ▼
                                     Product
</pre>

**偏序依赖**：若步骤 B 依赖于步骤 A 的输出，则拓扑排序保证 A 先于 B 执行。违反此顺序会导致 Builder 访问到不一致的中间状态。

## 机制

### 单例模式的实现变体与约束

**双重检查锁定（DCLP）在 JavaScript 中的无效性**：JavaScript（ES2022+）的内存模型基于 **happens-before 顺序**，但仅通过 `Atomics` 操作和 `SharedArrayBuffer` 建立。DCLP 依赖于以下约束序列：

1. 写 `instance` 变量（构造完成后）
2. 读 `instance` 变量（检查非 null）

在 JavaScript 中，由于 JIT 编译器的指令重排和**弱内存序**（除了 `Atomics` 操作外），步骤 1 和 2 之间**不存在可预期的顺序保证**。具体而言：

- **JIT 重排**：JIT 编译器可能在不改变单线程观测行为的前提下重排指令顺序
- **处理器重排**：即使 JIT 生成了正确的指令序列，处理器的 store buffer 和 invalidation queue 也可能导致其他线程观察到**写指令对未按程序顺序完成**

**形式化分析**：设线程 A 执行构造函数，线程 B 执行 `getInstance()`。在缺乏 `Atomics` 同步的情况下：

- 线程 A 对 `instance` 的写操作 $W_A(\text{instance})$ 和对 `this` 的构造操作 $W_A(\text{obj})$ 之间没有 happens-before 关系
- 线程 B 对 `instance` 的读操作 $R_B(\text{instance})$ 和其他线程对 `instance` 的写操作之间也没有 happens-before 关系

因此线程 B 可能读到**未构造完成的 `instance`**（部分初始化的对象引用）或**另一个线程正在构造中的对象**。

**虚拟代理的延迟代价均摊**：设真实对象初始化代价为 $C_{init}$ ，若对象从未被访问，总代价为 $0$ ；若被访问 $n$ 次，初始化代价均摊为 $C_{init} / n$ 。

**ES2022+ 私有字段变体**：

```javascript
class Singleton {
  static #instance = null;

  constructor() {
    if (Singleton.#instance) return Singleton.#instance;
    this.data = [];
    Singleton.#instance = this;
  }

  static getInstance() {
    return Singleton.#instance;
  }
}
```

私有字段 `#instance` 的语义：类外部无法通过 `Singleton.#instance` 访问，确保实例引用不可被篡改。但调用方仍可通过以下方式绕过：

```javascript
// 绕过方式 1: Object.getOwnPropertyDescriptors
const descriptors = Object.getOwnPropertyDescriptors(Singleton);
// 绕过方式 2: Reflect.ownKeys
const keys = Reflect.ownKeys(Singleton.prototype);
// 绕过方式 3: 原型链注入
Singleton.prototype.bypass = () => Singleton.#instance;
```

这是语言级私有的**固有限制**——`#` 语法仅阻止了属性名访问，但无法防止通过 `Reflect` 和 `Object` 的元编程 API 枚举或修改。

**闭包变体的词法作用域原理**：利用函数作用域将 `instance` 变量束缚在 IIFE 内部，返回的对象字面量只暴露 `getInstance` 方法。这实现了"实例存在性从显式属性收敛为词法不可达性"——外部无法通过任何手段访问或修改内部实例引用。

**违反约束的后果**：

- **反射攻击**：`Reflect.construct` 可绕过构造函数检查，直接调用构造函数创建新实例
- **原型链断裂**：若单例类被子类继承，父类构造函数可能被调用多次
- **多环境失效**：每个 Web Worker、iframe、Service Worker 拥有独立的 JavaScript 全局上下文，单例跨环境失效——这是单例模式的**隐式环境边界假设**
- **模块循环依赖**：在 ES 模块的静态解析阶段，懒汉式单例可能尚未初始化，导致读取到不完整状态

### 工厂模式的类型分发策略

**简单工厂的 $O(n)$ 扩展问题**：每新增一个产品类型 $t_{new}$ ，需要在工厂函数内部分支添加 `if (type === 'new') return new NewProduct()`。这导致工厂函数随产品类型线性增长，违反开闭原则。

**工厂方法的虚分派本质**：调用 `factory.create()` 时，实际执行的代码路径由具体工厂类的 `create` 方法决定。这将类型选择的决策从调用方推迟到子类——调用方只知道接口，不知道具体实现类。

**抽象工厂的产品族保证**：抽象工厂接口声明的 `createProductA()`、`createProductB()` 等方法返回类型必须兼容——例如 UI 工厂创建的 Button 和 Checkbox 必须使用相同的主题风格。若混用不同工厂的产品，会导致主题不一致。

### 建造者模式的对称性约束

**流式 API 的链式调用约束**：每个 Builder 方法必须返回 `this`（或其代理对象），以支持链式调用。**关键约束**：Builder 不能在构建中途抛出异常——否则链式调用会在中间断掉。

解决方案：
1. **延迟验证**：在 `getResult()` 中一次性验证所有字段
2. **Try 语义**：使用 `Result` 类型包装中间步骤
3. **防御性复制**：`getResult()` 返回产品对象的深拷贝，而非内部引用

**Director 编排顺序的偏序依赖**：若组件间存在依赖关系（如先设置类型再设置该类型专属属性），Director 必须保证编排顺序满足偏序约束。违反此约束会导致 Builder 在某步骤执行时访问到不一致的中间状态。

# 结构型模式

## 定义

结构型模式是一类通过**组合已有对象**来构建更大结构的方案。其核心思想是将对象视为黑盒，通过接口匹配或包装来改变对象的外部表现，而不修改其内部实现。

**版本差异说明**：ES2022+ 的装饰器提案（`@decorator` 语法）处于 TC39 第二阶段，各浏览器和运行时支持不完整。ES2026+ 预计将装饰器推进到第三阶段并原生支持。Proxy API 在 ES2022+ 中已成为标准特性，是实现代理模式的语言级基础设施。

---

## 数学模型

### 装饰器的函数复合模型

设被装饰对象 $C$ 的原始方法为 $f: X \to Y$ 。装饰器 $D$ 在包装 $C$ 后，新方法 $f'$ 可表示为：

$$
f' = g \circ f \circ h
$$

其中：
- $h: X \to X$ （参数预处理，如验证、转换）
- $g: Y \to Y$ （返回值后处理，如缓存、日志）

**装饰器链的复合律**：设装饰器链 $(D_1, D_2, \ldots, D_n)$ ，则：

$$
f_n' = D_n \circ D_{n-1} \circ \cdots \circ D_1 \circ f
$$

注意 $D_i \circ D_j \neq D_j \circ D_i$ 通常不成立（不可交换），这意味着**装饰顺序影响最终行为**。例如 `Milk(Sugar(coffee))` ≠ `Sugar(Milk(coffee))`——两者价格可能相同，但若装饰器有副作用（缓存、日志），执行顺序会影响最终效果。

**装饰器链的执行代价**：设单次方法调用经过装饰器链的转发开销为 $c$ ，装饰器链长度为 $n$ ，则总转发开销为 $n \times c$ 。对于高频调用场景（如数据绑定中的 getter），装饰器链的性能影响不可忽略。

### 适配器的同构映射

适配器是一个函数 $A: X_{adaptee} \to X_{client}$ ，将 adaptee 的输入空间 $X_{adaptee}$ 映射为 client 期望的输入空间 $X_{client}$ ：

$$
A = \phi_{out} \circ f_{adaptee} \circ \phi_{in}
$$

其中 $\phi_{in}$ 和 $\phi_{out}$ 分别为输入和输出的**表示层翻译**。适配器本身不改变被包装系统的语义，只做表示层的转换。

**约束**：适配器的翻译必须保持**语义等价**——$A(x)$ 与直接调用目标对象的结果必须在所有输入上等价。

**双射要求**：适配器建立的映射 $A$ 必须是双射（bijection）——每个 adaptee 输出恰好对应一个 client 输入，且反之亦然。若映射不是双射：
- **信息丢失**：adaptee 的某些状态无法在 client 侧表达
- **歧义**（较少见）：不同的 adaptee 输入映射到相同的 client 输出

**适配器的复杂度界**：设 adaptee 接口方法数为 $m$ ，client 期望接口方法数为 $n$ ，适配器的实现复杂度为 $O(m \times n)$——每个 client 方法可能需要调用多个 adaptee 方法的组合翻译。

### 代理的访问控制模型

代理对外暴露的接口 $P$ 与真实对象接口 $R$ 相同（ $P = R$ ，同构）。代理在调用 $R$ 的方法前后插入访问控制逻辑 $g$ 和 $h$：

$$
\text{method}_{proxy} = g \circ \text{method}_R \circ h
$$

与装饰器的关键区别：
- **装饰器**：添加新行为（ $g$ 和 $h$ 是功能增强）
- **代理**：做访问控制（ $g$ 和 $h$ 是 gatekeeping）

**虚拟代理的延迟代价均摊**：设真实对象初始化代价为 $C_{init}$ ，若对象从未被访问，总代价为 $0$ ；若被访问 $n$ 次，初始化代价均摊为 $C_{init} / n$ 。

**缓存代理的命中率模型**：设缓存容量为 $C_{\max}$ （缓存条目数），缓存项的生命周期为 $T_{TTL}$ 。则在时间窗口 $[0, t]$ 内的命中率 $h$ 满足：

$$
h \leq \frac{\min(t, T_{TTL})}{t} \quad \text{（当缓存足够大时）}
$$

若缓存不足触发淘汰，命中率进一步下降，由缓存替换算法（LRU、LFU）决定淘汰策略。

## 机制

### 装饰器的组合爆炸与性能

**嵌套层数的性能影响**：每次方法调用都要穿越整个装饰器链。设单次转发开销为 $c$ ，装饰器链长度为 $n$ ，则总转发开销为 $n \times c$ 。对于高频调用场景（如数据绑定中的 getter），装饰器链可能成为瓶颈。

**ES 装饰器语法糖的本质**：`@decorator` 是编译时语法糖，等价于 `Class = decorator(Class)`。它允许在类定义时附加元编程行为，但底层仍是方法属性描述符的读写。**关键约束**：装饰器不能修改方法的行为语义，只能修改属性描述符（可枚举性、可写性等）。

**装饰器与 `this` 绑定**：若原始方法内部使用 `this`，装饰器若不显式 `.call(this)` 绑定，`this` 会指向装饰器代理而非原对象。常见修复：

```javascript
class LoggingDecorator {
  constructor(target) {
    this.target = target;
  }

  get(key) {
    // 显式绑定 this
    return this.target.get.call(this.target, key);
  }
}
```

**违反约束的后果**：

- 若装饰器链过长，每次方法调用的转发开销累积，在高频场景下可能造成显著性能下降
- 若装饰器之间有循环依赖（如 A 装饰 B，B 也装饰 A），会导致无限递归
- 若装饰器修改了被包装方法的 `length` 属性描述符，可能破坏依赖该元信息的代码

### 适配器的语义保持约束

**翻译的双射要求**：适配器建立的映射 $A$ 必须是**双射**（bijection）——每个 adaptee 输出恰好对应一个 client 输入，且反之亦然。若映射不是双射，会导致信息丢失或歧义。

**异常体系的适配**：若 adaptee 抛出特定异常而 client 只期望通用异常，适配器必须包装异常。这避免泄露底层实现细节，保持接口的**信息隐藏**。

**违反约束的后果**：

- 若适配器映射不是双射，client 可能丢失来自 adaptee 的部分状态信息
- 若适配器不处理 adaptee 的所有异常类型，client 可能收到未预期的异常，破坏错误处理逻辑
- 若适配器引入了额外的副作用（如日志、缓存），这些副作用可能被 client 视为 adaptee 行为的一部分

### 代理与装饰器的本质区别

| 特征 | 装饰器 | 代理 |
|------|--------|------|
| **接口关系** | 与原对象接口相同 | 与原对象接口相同 |
| **目的** | 功能增强 | 访问控制 |
| **调用时机** | 透明转发 | 可能拦截 |
| **决策位置** | 原对象执行主要逻辑 | 代理决定是否/如何调用原对象 |
| **实例创建** | 调用方创建被装饰对象 | 代理控制原对象的创建（虚拟代理） |

**代理的决策本质**：代理在转发请求前可以执行访问控制逻辑，包括：
- 权限检查（是否允许调用）
- 参数验证（调用参数是否合法）
- 限流检查（是否超出调用配额）
- 缓存查询（是否可直接返回缓存结果）

装饰器则不具备这些决策能力——它总是将请求转发给被装饰对象。

### 缓存代理的数据一致性约束

**缓存失效策略**：缓存代理的核心约束是**缓存与源的一致性**。常见失效策略：
- **TTL（Time-To-Live）**：固定时间后失效
- **LRU（Least Recently Used）**：按访问频率淘汰
- **写入失效**：写入操作时清除相关缓存

**缓存污染风险**：若失效策略不完善，缓存代理可能返回过期数据。特别是在并发写入场景下，缓存可能与实际数据状态产生不一致。

**缓存的数学边界**：
- 完美缓存（命中率 100%）：延迟降至 $O(1)$ ，但需要无限内存
- 有限缓存：命中率与内存占用的权衡，由缓存替换算法（LRU、LFU 等）决定

**违反约束的后果**：

- 若缓存未正确失效，client 可能读到过期数据，导致业务逻辑错误
- 若在分布式环境中多个缓存代理共享缓存（如 Redis），网络分区可能导致缓存不一致
- 若缓存 key 的生成逻辑不一致（如序列化顺序不同），相同的输入可能生成不同的 key，导致缓存未命中

| 维度 | 装饰器模式 | 适配器模式 | 代理模式 |

# 行为型模式

## 定义

行为型模式是一类关注**对象间职责分配与算法封装**的结构化方案。其核心思想是将"做什么"（行为）与"谁来做"（责任承担者）分离，使系统能够在不修改调用方的情况下替换或扩展行为实现。

**版本差异说明**：ES2022+ 引入了 Top-Level Await 和 `Array.prototype.at()` 等语法改进。ES2026+ 预计引入 `Symbol.dispose` 资源管理 API，这将增强命令模式的撤销语义（通过确定性资源释放实现可靠的 undo/redo）。

---

## 数学模型

### 策略模式的接口同构

设策略接口定义方法签名 $f: X \to Y$ ，具体策略集合 $S = \{s_1, s_2, \ldots, s_n\}$ 各实现 $f$ 。上下文对象维护指向当前策略的引用 $p \in S$ ，调用时执行：

$$
\text{context.execute}(x) = p.f(x)
$$

**策略切换的复杂度**： $O(1)$ 单纯指针替换，与 if/switch 分支的 $O(n)$ 线性扫描相比，在策略数量较多时优势明显。

**策略闭合性**：设复合策略 $s_{composite} = \text{compose}(s_a, s_b)$ ，复合结果仍满足接口 $f$ 。调用方无需知道内部是单策略还是组合策略——这是**策略的闭合性**，是装饰器不具备的特性。

### 观察者模式的多播通知

设 Subject 维护观察者集合 $O = \{o_1, o_2, \ldots, o_n\}$ 。状态变更触发通知，通知操作的时间复杂度：

$$
T_{\text{notify}} = O(|O|)
$$

**通知的事务性**：通知是**无事务性**的——若某个观察者的 `update()` 抛出异常，后续观察者仍会被通知（在大多数实现中）。这意味着通知的可靠性参数 $\rho < 1$ 。

**通知的原子性边界**：在通知过程中，若观察者集合被修改（新增或删除观察者），会导致：
- **ConcurrentModification**：迭代过程中集合被修改，可能导致部分观察者漏通知或重复通知
- **迭代器失效**：JavaScript 的 `forEach` 对正在修改的数组行为未定义

**推模式 vs 拉模式**：

| 模式 | 数据传输量 $D$ | 额外调用 | 适用场景 |
|------|---------------|----------|----------|
| 推模式 | 固定（推送全部数据） | 无 | 观察者需要全部数据 |
| 拉模式 | 按需（仅通知） | 一次（观察者主动拉取） | 观察者只需部分数据 |

### 命令模式的撤销语义

设命令历史栈 $H$ 和撤销栈 $U$ 。执行命令 `cmd` 的效果建模为状态转移：

$$
\text{state}' = \text{cmd.execute}(\text{state}),\quad H.\text{push}(\text{cmd}),\quad U.\text{clear}()
$$

撤销操作从 $H$ 弹出最近命令并调用其 `undo()`：

$$
\text{state} = \text{cmd.undo}(\text{state}),\quad U.\text{push}(\text{cmd}),\quad H.\text{pop}()
$$

**撤销的语义要求**：撤销不是简单回滚状态，而是执行与原操作**语义相反**的操作。例如打开文件的命令对应关闭文件的撤销操作。这要求每个命令的 `undo()` 必须精确对应对称操作。

**宏命令的复合律**：宏命令 $C = \text{MacroCommand}(c_1, c_2, \ldots, c_k)$ 的 execute 序列执行 $\sum_i c_i.\text{execute}$ ，undo 逆序执行 $\sum_i c_{k-i}.\text{undo}$ 。

**撤销栈的内存界**：设最大撤销步数为 $N_{\max}$ ，则撤销栈的空间复杂度为 $O(N_{\max} \times S_{\text{cmd}})$ ，其中 $S_{\text{cmd}}$ 为单个命令的平均状态大小。

### 状态机的形式化约束

设有限状态自动机 $M = (Q, \Sigma, \delta, q_0, F)$ ，其中：
- $Q$ ：状态集合
- $\Sigma$ ：输入字母表
- $\delta: Q \times \Sigma \to Q$ ：转移函数
- $q_0$ ：初始状态
- $F \subseteq Q$ ：接受状态集合

状态模式将状态建模为对象，状态转换建模为对象间的委托。设当前状态对象 $s \in Q$ ，当事件 $e \in \Sigma$ 到达时：

$$
\delta(s, e) = s' \quad \text{通过} \quad s.\text{handle}(e) \to s'
$$

**约束**：状态转换必须满足 $\delta$ 的定义域约束——若 $\delta(s, e)$ 未定义，则状态对象必须处理该事件（转移到一个错误处理状态或抛出异常）。

## 机制

### 策略模式与依赖注入的等价性

策略模式是依赖注入的其中一种表现形式。上下文对象不直接创建策略，而是由外部注入：

```javascript
// 策略模式
const cart = new ShoppingCart();
cart.setStrategy(new CreditCardStrategy());

// 依赖注入
const cart = new ShoppingCart(creditCardStrategy);
```

这使得策略的替换可以在不修改上下文代码的情况下完成，也便于单元测试时注入 mock 策略。

**策略接口臃肿问题**：若策略接口定义了过多方法，添加新策略时需要实现所有方法，即使新策略与某些方法无关。这是策略模式的主要扩展性缺陷。解决方案是**策略组合**：将大接口拆分为多个小接口，通过组合器将多个策略合并。

### 观察者模式的迭代器安全

**在通知过程中修改观察者列表**：若 `update()` 内调用 `attach/detach`，会导致迭代器失效（ConcurrentModificationException 语义），部分观察者可能漏通知或重复通知。

**安全迭代模式**：

```javascript
notify() {
  // 迭代副本，避免迭代过程中列表被修改
  [...this.observers].forEach(o => o.update(this.state));
}
```

**通知顺序不确定性**：若观察者依赖通知顺序，但实现中列表遍历顺序不确定，会导致不可重复的行为。在需要确定性顺序的场景下，应使用有序集合（如 `SortedSet`）并显式定义顺序。

**违反约束的后果**：

- 若通知过程中抛出异常且未捕获，后续观察者不会收到通知（可靠性参数 $\rho$ 下降）
- 若通知过程中修改观察者集合，可能导致迭代器失效，行为未定义
- 若观察者注册时未提供唯一的标识符，且未正确实现相等性检查，可能导致重复注册

### 命令模式的幂等性约束

**execute() 的幂等性要求**：若 `execute()` 不是幂等的，撤销后再重做可能产生与首次执行不同的结果。

| 操作类型 | 幂等性 | 撤销语义 |
|----------|--------|----------|
| 赋值 `x = 5` | 幂等 | 撤销：恢复旧值 `x = old` |
| 增删改（集合） | 非幂等 | 撤销：逆向增删改 |
| 随机数生成 | 非幂等 | 撤销：无法逆向（不应作为命令） |

**外部资源的撤销**：若命令持有外部资源（文件句柄、网络连接），撤销后资源已释放但历史栈仍持有命令引用。长时间运行可能导致资源泄漏。解决方案：使用 `Symbol.dispose`（ES2026+）实现确定性资源释放。

### 状态模式与状态机的形式化映射

**状态对象的手动 vs 自动转换**：

- **手动转换**：状态对象返回是否需要转换，由 Context 显式调用 `context.setState()`
- **自动转换**：状态对象直接持有对 Context 的引用，内部直接调用 `context.setState()`

自动转换更简洁，但引入了状态对象对 Context 的强耦合，违反了**依赖倒置原则**（高层模块 Context 不应依赖低层模块 State）。

**状态模式的约束**：

1. 每个状态必须处理所有可能的事件——否则事件会被吞掉
2. 状态转换必须是无环的——若存在环，状态机可能无法终止
3. 状态数必须是有界的——无限状态无法用有限自动机建模

**违反约束的后果**：

- 若状态未处理某事件，该事件被静默忽略，用户行为得不到响应
- 若状态转换形成环，可能导致状态机在两个状态间无限切换
- 若状态数无界（如计数器状态），内存占用随运行时间增长

### 策略组合的代数结构

策略可以通过**组合器**形成新的策略。设组合器 $\oplus: S \times S \to S$ ：

```javascript
// 限流装饰器组合
const throttled = throttle(strategyA, 100);
const debounced = debounce(strategyB, 50);

// 顺序组合
const pipeline = compose(strategyA, strategyB, strategyC);
```

组合后的策略仍满足原接口 $f$ ，调用方无需知道内部结构。这是策略模式相对于简单分支的核心优势。

| 维度 | 策略模式 | 观察者模式 | 命令模式 | 状态模式 |

| **典型用途** | 算法选择、支付方式 | 事件系统、响应式数据流 | 撤销/重做、宏命令 | 游戏状态机、工作流 |

const strategies = {
  credit: (amount) => ({ provider: 'stripe', amount }),
  paypal: (amount) => ({ provider: 'paypal', amount }),
  crypto: (amount) => ({ provider: 'coinbase', amount }),

  setStrategy(name) {
    if (!strategies[name]) throw new Error(`Unknown strategy: ${name}`);
    this.#strategy = strategies[name];

  checkout() {
    return this.#strategy(this.getTotal());

```javascript
// 观察者模式（安全迭代）
class Subject {
  #observers = new Set();
  #state = null;

  attach(observer) {
    this.#observers.add(observer);
  }

  detach(observer) {
    this.#observers.delete(observer);
  }

  notify() {
    // 迭代副本，避免迭代过程中被修改
    const observers = [...this.#observers];
    const state = this.#state;
    observers.forEach(o => o.update(state));
  }

  setState(state) {
    this.#state = state;
    this.notify();
  }
}
```

```javascript
// 命令模式（带 Symbol.dispose 支持）
class FileCommand {
  #file;
  #action;

  constructor(file, action) {
    this.#file = file;
    this.#action = action;
  }

  execute() {
    return this.#file[this.#action]();
  }

  undo() {
    const opposite = this.#action === 'open' ? 'close' : 'open';
    return this.#file[opposite]();
  }

  [Symbol.dispose]() {
    // 确定性资源释放（ES2026+）
    if (this.#file.isOpen()) {
      this.#file.close();
    }
  }
}
```

// 状态模式（简化版）
class State {
  handle(context) { throw new Error('Abstract'); }
}

class IdleState extends State {
  handle(context) {
    console.log('Idle: Starting...');
    context.setState(new ActiveState());
  }
}

class ActiveState extends State {
  handle(context) {
    console.log('Active: Stopping...');
    context.setState(new IdleState());
  }
}

class Context {
  #state = new IdleState();

  setState(state) { this.#state = state; }

  request() { this.#state.handle(this); }
}
