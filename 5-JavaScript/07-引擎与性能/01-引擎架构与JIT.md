# 引擎架构与 JIT

> 前置：[06-Node.js平台/06-数据库与缓存](../06-Node.js平台/06-数据库与缓存.md) · 后续：[02-垃圾回收与内存](./02-垃圾回收与内存.md)

> **版本基准**：Node 24 stable / Node 26 latest。本篇示例实测环境：Node v24.13.1（V8 13.6.233.17-node.40），Windows x64。
> **本篇讲什么**：ECMA-262 定义语言，**不定义引擎怎么实现**（见 [00-概览/01-JavaScript 全景](../00-概览/01-JavaScript全景.md)）。隐藏类、内联缓存、去优化都属"规范之外"——换一个引擎，行为不变，性能模型变。

## 本质

引擎的工作是把源码变成机器码。它的核心矛盾是：**编译得越彻底，运行越快，但启动越慢**。而代码的执行次数是高度不均的——少数热点循环占掉绝大部分时间。

V8 的解法是**分层编译**：先解释执行立刻能跑，同时收集"这段代码实际怎么被用"的信息，热到一定程度再花成本优化。这条流水线在 [00-概览/01-JavaScript 全景](../00-概览/01-JavaScript全景.md) 已有四档（Ignition / Sparkplug / Maglev / TurboFan），本篇讲**优化建立在哪两个假设上**，以及**假设被推翻时会发生什么**。

## 机制

### 隐藏类：对象的"形状"

JavaScript 是动态类型，对象的属性可以随时增删。如果每次读属性都真的去哈希表查，会很慢。V8 的做法是：**给每个对象一个隐藏类**（hidden class / map），记录"这个对象有哪些属性、各在什么偏移位置"。

对象字面量的写法决定了它拿到哪个隐藏类。**属性的添加顺序不同，形状就不同**：

```console
$ node --allow-natives-syntax -e '…'
同序: true
异序: false
```

```javascript
function A() { const o = {}; o.a = 1; o.b = 2; return o; }   // 形状 1
function B() { const o = {}; o.b = 2; o.a = 1; return o; }   // 形状 2
```

`%HaveSameMap` 显示两者**形状不同**——尽管它们有相同的属性。因为隐藏类是按"从空对象开始，依次添加 a、b"这条**转换路径**建立的，顺序不同就走到不同的类。

**推论**：**在构造函数或对象字面量里一次性声明所有属性**，不要在后续代码里逐个添加。

### 内联缓存：调用点的记忆

属性访问被编译成"查这个对象是什么形状，然后按固定偏移读"。引擎在**每个属性访问点**（调用点）缓存"上次见到的是什么形状"，下次同形状就直接用。

按见过的形状数量，调用点分为：

| 状态 | 见过的形状数 | 代价 |
|---|---|---|
| **单态**（monomorphic） | 1 | 最快，一次形状比对 |
| **多态**（polymorphic） | 2–4 | 逐个比对 |
| **超态**（megamorphic） | 更多 | 退化为哈希查找 |

实测（中位数，各 5 次测量，2×10⁶ 次调用）：

```console
$ node poly2.mjs
单态中位数: 15.4 ms  | 各次: 8.9,15.9,15.4,15.5,15.4
多态中位数: 20.7 ms  | 各次: 16.7,20.3,20.7,29.3,29.0
```

单态明显更快，且**方差更小**。把不同形状的对象混在同一个函数上处理，代价不只是平均值上升，还有波动。

### 去优化：假设被推翻

优化编译依赖**推测**：根据运行时收集到的反馈，"这个 `add` 一直被传数字，那就按数字加法生成机器码"。反馈错了就**去优化**（deoptimization）——退回解释执行。

```console
$ node --trace-deopt deopt.mjs
[bailout (kind: deopt-eager, reason: not a Smi): … deoptimizing <JSFunction add …>, <Code MAGLEV>, opt id 1, bytecode offset 2 …]
```

输出里可以读出三件事：**哪个函数**（`add`）、**哪一档代码**（`MAGLEV`）、**什么原因**（`not a Smi`——传进来的不是小整数）。在预热了 10 万次数字加法之后传一个字符串，立刻触发。

**这不是错误，是设计**。代价是那次调用的性能断崖，以及重新预热的时间。所以：

- **保持函数参数类型稳定**（"总是数字"或"总是字符串"，不要有时是 `null`）；
- 类型可能变化时，**在函数入口显式归一化**（如 `Number(x)`），让优化后的代码只看到一种类型。

### 观测手段

| 手段 | 看什么 |
|---|---|
| `node --print-bytecode` | 字节码（见 [01-语言核心/01-安装与第一个程序](../01-语言核心/01-安装与第一个程序.md)） |
| `node --trace-opt` | 哪些函数被优化、进了哪一档 |
| `node --trace-deopt` | 去优化的函数与原因 |
| `node --allow-natives-syntax` | `%HaveSameMap` 等内部断言（仅调试用） |
| `node --trace-gc` | GC 事件（见 [02-垃圾回收与内存](./02-垃圾回收与内存.md)） |

这些标志只在调试构建或加参数时可用，**不要在生产环境常开**——输出量极大。

### 引擎之间

| 引擎 | 使用者 | 与本篇相关 |
|---|---|---|
| V8 | Chrome、Node.js、Deno | Ignition + Sparkplug + Maglev + TurboFan |
| JavaScriptCore | Safari、Bun | 四级 JIT，与 V8 结构类似但实现不同 |
| SpiderMonkey | Firefox | 有自己的优化流水线 |

**本篇描述的是 V8 的实现，不是 JavaScript 的保证。** 隐藏类、内联缓存、去优化的具体阈值与策略各引擎不同，也可能随版本变化。写代码时应当依据的是**"形状稳定、类型稳定、避免超态"这些方向性规则**，而不是某个具体的性能数字。

## 连接：引擎友好的写法

| 做法 | 为什么 |
|---|---|
| 在构造器/字面量里一次声明全部属性 | 形状统一，避免转换路径分叉 |
| 不用 `delete` 删属性 | 会破坏形状；改为赋 `null` 或重建对象 |
| 数组保持同类型元素 | 避免从"紧凑元素"退化为"字典元素" |
| 不用稀疏数组 | 同上（见 [03-标准库/02-数组](../03-标准库/02-数组.md)） |
| 函数参数类型稳定 | 避免去优化 |
| 同一函数不处理多种形状 | 避免多态/超态调用点 |
| 避免在热路径上改原型 | 会让隐藏类与内联缓存失效（见 [02-对象模型与运行时/01-原型链与继承](../02-对象模型与运行时/01-原型链与继承.md)） |
| 热路径不用 `Proxy` | 代理对象无法进入快速属性访问（见 [02-对象模型与运行时/04-属性描述符与元编程](../02-对象模型与运行时/04-属性描述符与元编程.md)） |

## 边界

- **以上都是 V8 的实现细节，不是语言保证**：换引擎可能不同。
- **不要为引擎优化牺牲可读性**：先用 [03-性能剖析与优化](./03-性能剖析与优化.md) 的方法**测量**，确认是热点再动。
- **`--allow-natives-syntax` 只用于调试**：它依赖引擎内部，随时可能变。
- **去优化不是 bug**：它是"推测错了就退回去"的正常机制，偶尔一次无关紧要；**在热路径上反复发生**才是问题。
- **隐藏类不是可以手动控制的东西**：只能通过"写法稳定"来间接影响。
