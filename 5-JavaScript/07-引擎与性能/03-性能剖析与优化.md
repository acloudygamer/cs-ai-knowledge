# 性能剖析与优化

> 前置：[02-垃圾回收与内存](./02-垃圾回收与内存.md) · 后续：[09-工程化/01-包管理与依赖语义](../09-工程化/01-包管理与依赖语义.md)

> **版本基准**：Node 24 stable / Node 26 latest。本篇示例实测环境：Node v24.13.1（V8 13.6），Windows x64。

## 本质

性能工作的顺序是固定的：**测量 → 定位热点 → 修改 → 再测量验证**。跳过第一步的优化是猜测，跳过最后一步的优化是自我安慰——改动可能没有效果，甚至更慢。

JavaScript 的性能问题有一层额外的复杂性：**代码的实际执行方式取决于引擎的运行时决策**（见 [01-引擎架构与 JIT](./01-引擎架构与JIT.md)）。同一段代码，预热前后、类型稳定与否，性能可以差数倍。所以"看代码推断性能"尤其不可靠。

## 机制

### 计时

| 工具 | 用途 |
|---|---|
| `performance.now()` | 高精度单调时钟（微秒级小数） |
| `performance.mark` / `measure` | 命名区间，可在 DevTools 时间线上查看 |
| `console.time` / `timeEnd` | 快速临时计时 |
| `process.hrtime.bigint()` | 纳秒级整数 |

**用 `performance.now()` 而不是 `Date.now()`**：

```console
$ node perf.mjs
Date.now 示例: 1790452128319 | performance.now: 23.8339
```

`Date.now()` 只给整数毫秒，且受系统时间调整影响（可能回拨）；`performance.now()` 是微秒级小数、单调递增。

```console
$ node perf.mjs
name=区间 startTime=24.03 duration=3.150
```

`mark` / `measure` 产出的条目可被 `performance.getEntriesByType` 读取，也能在浏览器 DevTools 的 Performance 面板里看到。

### 剖析

| 手段 | 看什么 |
|---|---|
| `node --cpu-prof` | CPU 采样剖析，产出 `.cpuprofile` 文件 |
| `node --heap-prof` | 堆分配剖析，找"谁在分配" |
| `node --trace-gc` | GC 事件（见 [02-垃圾回收与内存](./02-垃圾回收与内存.md)） |
| `node --trace-deopt` | 去优化（见 [01-引擎架构与 JIT](./01-引擎架构与JIT.md)） |
| 浏览器 DevTools Performance | 火焰图、长任务、布局抖动 |

```console
$ node --cpu-prof --cpu-prof-dir=. -e '…'
CPU.20260927.034848.15252.0.001.cpuprofile
采样节点数: 62 | 采样数: 106
```

`.cpuprofile` 是 JSON 格式，可导入 Chrome DevTools 的 Performance 面板查看火焰图。

**剖析解决的是"改哪里"，计时解决的是"改好了没有"。** 不要靠阅读代码猜热点——真正的热点常常出人意料（序列化、正则、意外的同步 I/O）。

### 基准测试的四个陷阱

写一个可信的微基准比看起来难。以下四条都由实测确认：

**一、必须预热。** 同一段代码连续跑五次：

```console
$ node perf.mjs
  第 1 次: 2.67 ms
  第 2 次: 0.94 ms
  第 3 次: 0.94 ms
  第 4 次: 0.94 ms
  第 5 次: 0.93 ms
```

第一次是解释执行 + 逐层优化，**比稳定态慢近 3 倍**。把第一次的结果当作性能数据，会得出完全错误的结论。标准做法是**先跑足够的预热轮次，再开始测量**。

**二、结果未被使用可能被优化掉。** 引擎会消除没有副作用的计算：

```console
$ node perf.mjs
无副作用循环: 5.84 ms | 有副作用循环: 9.49 ms（结果 99999990000000）
```

两段循环做同样多的乘法，但"算了不用"的那段明显更快——部分计算被消除了。**基准测试必须让结果被使用**（累加到一个返回变量、写进全局、打印出来）。

**三、单次测量不可信。** 上例的第一次运行就说明了这点。应**多次测量取中位数**（中位数比平均值更抗离群值）。

**四、对照组设计不当会得出反直觉结论。** 这是本篇编写过程中实际踩到的：第一版多态测试用 `shapes[n % 4]` 在循环里取对象，测出"多态比单态更快"——因为取模运算的开销盖过了调用点的差异。**改掉取模、各自预热、交替测量之后**才得到符合预期的结果（见 [01-引擎架构与 JIT](./01-引擎架构与JIT.md) 的 15.4 vs 20.7 ms）。

教训是：**测量结果与理论不符时，先怀疑测量方法**。

### 优化的层次：先动大的

优化的收益按数量级递减，应自上而下：

| 层次 | 收益量级 | 例子 |
|---|---|---|
| **算法** | 数量级 | $O(n^2)$ → $O(n \log n)$；把循环里的查找改成 `Map`（见 [03-标准库/03-Object 与 Map/Set](../03-标准库/03-Object与Map-Set.md)） |
| **I/O 与网络** | 数量级 | 减少往返、并发发起、加缓存（见 [06-Node.js平台/06-数据库与缓存](../06-Node.js平台/06-数据库与缓存.md)） |
| **数据结构** | 常数倍 | 数组 vs `Set` 的去重；避免稀疏数组 |
| **减少分配** | 常数倍 | 复用对象、避免在热循环里创建闭包与临时数组（见 [02-垃圾回收与内存](./02-垃圾回收与内存.md)） |
| **引擎友好写法** | 百分比 | 形状稳定、类型稳定（见 [01-引擎架构与 JIT](./01-引擎架构与JIT.md)） |

**最后两行是常见的用力方向，但收益最小。** 在算法还是 $O(n^2)$ 的时候调隐藏类，是典型的抓错重点。

### 高收益的常见项

| 项 | 说明 |
|---|---|
| 把同步 I/O 移出请求路径 | 同步 API 会阻塞事件循环，影响所有并发请求（见 [06-Node.js平台/02-文件系统与流](../06-Node.js平台/02-文件系统与流.md)） |
| CPU 密集任务移入 Worker | 主线程保持可响应（见 [04-异步与并发/05-Worker 与共享内存](../04-异步与并发/05-Worker与共享内存.md)） |
| 没有依赖的异步操作并发发起 | 串行 `await` 白白累加等待时间（见 [04-异步与并发/03-async/await 与异步模式](../04-异步与并发/03-async-await与异步模式.md)） |
| 大文件用流 | 内存占用与文件大小解耦（见 [04-异步与并发/06-流](../04-异步与并发/06-流.md)） |
| 批处理代替逐条 | 数据库写入、DOM 操作都适用 |
| 缓存热点结果 | 但要处理失效（见 [06-Node.js平台/06-数据库与缓存](../06-Node.js平台/06-数据库与缓存.md)） |

## 连接：症状 → 手段

| 症状 | 先看什么 |
|---|---|
| 接口响应慢 | `--cpu-prof` 看时间花在哪；查是否有同步 I/O |
| 内存持续增长 | `--heap-prof` + `heapUsed` 趋势（见 [02-垃圾回收与内存](./02-垃圾回收与内存.md)） |
| 周期性的延迟尖峰 | `--trace-gc` 看 GC 停顿 |
| 整体吞吐上不去 | 单核瓶颈 → `cluster` 或 Worker（见 [06-Node.js平台/04-进程与集群](../06-Node.js平台/04-进程与集群.md)） |
| 某个函数忽快忽慢 | `--trace-deopt` 看去优化 |
| 页面卡顿 | DevTools 找长任务与布局抖动（见 [05-浏览器平台/02-渲染管线与动画](../05-浏览器平台/02-渲染管线与动画.md)） |

## 边界

- **没有测量的优化不要做**：先剖析，再动手。
- **微基准必须预热、防消除、多次取中位数**：否则数据不可信。
- **测量结果反直觉时先怀疑测量**：本篇的多态测试就是例子。
- **不要用 `Date.now()` 测短耗时**：分辨率不够，且非单调。
- **`--cpu-prof` 等标志不要常开**：有额外开销，输出量大。
- **优化要可回退**：保留改动前后的对比数据，无法证明有效的改动应当撤掉。
- **可读性也是成本**：为一个百分点牺牲可维护性通常不划算。
