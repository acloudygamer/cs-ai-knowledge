# 垃圾回收与内存

> 前置：[01-引擎架构与 JIT](./01-引擎架构与JIT.md) · 后续：[03-性能剖析与优化](./03-性能剖析与优化.md)

> **版本基准**：Node 24 stable / Node 26 latest。本篇示例实测环境：Node v24.13.1（V8 13.6.233.17-node.40），Windows x64。

## 本质

垃圾回收（GC）自动释放不再使用的内存。**"不再使用"的判据是"不可达"**：从一组**根**（全局对象、当前调用栈上的变量、闭包持有的环境）出发，顺着引用能走到的对象就是活的，走不到的可回收。

这条判据决定了 JavaScript 内存管理的全部特征：

- **程序员不控制释放时机**——只控制"还留不留引用"；
- **"泄漏"的含义是"留了不必要的引用"**，不是"忘了 free"；
- 引用是**传递**的：一个大数组被一个小对象引用着，小对象被全局变量引用着，那个大数组就活着。

GC 是**规范之外**的引擎实现（见 [00-概览/01-JavaScript 全景](../00-概览/01-JavaScript全景.md)）——ECMA-262 只要求"不可达的对象最终可被回收"，不规定怎么回收、什么时候回收。

## 机制

### 可达性

```console
$ node --expose-gc gc.mjs
仍有引用，对象存活
两个引用都去掉，对象不可达 -> 可回收
```

```javascript
let a = { name: "甲" };
let b = a;        // 两个绑定指向同一对象
a = null;         // 还有一个引用，对象活着
b = null;         // 没有引用了，可回收
```

### 分代回收

引擎按"对象活多久"把堆分成两代，用不同策略回收：

| | 新生代 | 老生代 |
|---|---|---|
| 存放 | 新分配的对象 | 熬过若干次回收的对象 |
| 算法 | **Scavenge**（复制存活对象到另一半） | **Mark-Compact**（标记存活、整理压缩） |
| 频率 | 高 | 低 |
| 单次耗时 | 短 | 长 |

依据是**分代假说**：绝大多数对象很快就死。所以对新对象频繁做便宜的回收，对老对象偶尔做昂贵的回收，总体最划算。

实测（`--max-old-space-size=64`，反复分配大数组并丢弃）：

```console
$ node --trace-gc --max-old-space-size=64 -e '…'
[20252:…]       13 ms: Scavenge 4.5 (5.6) -> 4.5 (6.6) MB, pooled: 0 MB, 0.53 / 0.00 ms  (average mu = 1.000, …) allocation failure;
[20252:…]       14 ms: Scavenge 6.3 (9.3) -> 6.3 (9.3) MB, pooled: 0 MB, 0.61 / 0.00 ms  (average mu = 1.000, …) allocation failure;
```

每行的读法：**回收类型 → 回收前堆用量（前总容量）→ 回收后用量（后总容量）→ 暂停耗时**。`Scavenge` 是新生代回收，暂停在毫秒以下。

同一进程累计的回收次数：

```console
$ node --trace-gc --max-old-space-size=64 -e '…' | grep -oE "Scavenge|Mark-Compact" | sort | uniq -c
     17 Mark-Compact
     10 Scavenge
```

`Mark-Compact` 出现在老生代压力大时——本例是反复分配大数组触发的。

### 暂停

GC 需要**暂停**应用代码才能安全地移动对象（复制、压缩都会改变地址）。这就是"GC 停顿"的来源，也是 [00-概览/01-JavaScript 全景](../00-概览/01-JavaScript全景.md) 里把"GC 暂停"列为自动内存管理代价的原因。

现代引擎大量使用**增量与并发**技术（标记分片进行、部分工作在后台线程完成）来缩短单次暂停，但**不能消除**。对延迟敏感的服务（如 P99 指标）而言，GC 停顿是需要观测的一类事件。

### 观测手段

| 手段 | 用途 |
|---|---|
| `node --trace-gc` | 每次 GC 的类型、堆用量、暂停耗时 |
| `process.memoryUsage()` | 进程级内存快照 |
| `node --expose-gc` + `global.gc()` | 手动触发回收（**仅调试**） |
| `node --heap-prof` | 堆分配剖析 |
| `--max-old-space-size=N` | 设置老生代上限（MB） |

`process.memoryUsage()` 的字段：

```console
$ node --expose-gc gc.mjs
rss: 46.45 MB | heapTotal: 6.07 MB | heapUsed: 4.22 MB
```

| 字段 | 含义 |
|---|---|
| `rss` | 进程占用的物理内存（含堆外） |
| `heapTotal` | V8 堆已申请的容量 |
| `heapUsed` | V8 堆实际使用的量 |
| `external` | 堆外对象占用（如 `Buffer` 的底层内存） |
| `arrayBuffers` | 类型化数组与 `ArrayBuffer` 占用的量 |

**`rss` 远大于 `heapUsed` 是正常的**——堆容量是分批申请的，已申请但未使用的部分仍计入 `rss`。判断泄漏要看 `heapUsed` 的**长期趋势**，不是单次快照。

### 分配与释放的实测对照

```console
$ node --expose-gc gc.mjs
基线: 3.88 MB -> 峰值: 49.65 MB -> 释放后: 5.40 MB
```

分配 30 个 20 万元素数组后 `heapUsed` 涨到 49.65 MB，把引用置空并回收后回落到 5.40 MB——**证明这些内存确实被回收了**。这条"分配 → 峰值 → 释放 → 回落"的曲线是验证"有没有泄漏"的基本方法：如果回落不到接近基线，就说明有引用没断开。

### 泄漏：留了不必要的引用

```console
$ node --expose-gc gc.mjs
闭包持有大数组时 heapUsed: 7.70 MB
释放闭包后 heapUsed: 4.07 MB
```

一个闭包持有 50 万元素数组，`heapUsed` 比释放后高 3.63 MB（约 50 万 × 8 字节，符合预期）。这就是 [02-对象模型与运行时/02-闭包与作用域链](../02-对象模型与运行时/02-闭包与作用域链.md) 里"闭包延长生命周期"的内存面。

常见泄漏来源：

| 来源 | 机制 | 对策 |
|---|---|---|
| 闭包持有大对象 | 外层变量被闭包引用 | 缩小闭包捕获范围，只捕获需要的 |
| 意外的全局变量 | 未声明赋值（宽松模式）会挂到全局 | 用 `let` / `const`，模块恒严格 |
| 事件监听器未移除 | `EventTarget` 持有回调，回调持有闭包 | `{ signal }` 或组件卸载时移除（见 [05-浏览器平台/01-DOM 与事件模型](../05-浏览器平台/01-DOM与事件模型.md)） |
| 定时器未清除 | `setInterval` 的回调与闭包一直活着 | `clearInterval`，或用 `AbortSignal` |
| 无界缓存 | 用 `Map` 做缓存却从不淘汰 | 用 `WeakMap` 或加容量上限 |
| 集合里只增不减 | 数组/`Set` 累积历史记录 | 定期清理或改环形缓冲 |

**`WeakMap` / `WeakSet` 的意义正在于此**：键是弱引用，不阻止回收（见 [02-对象模型与运行时/04-属性描述符与元编程](../02-对象模型与运行时/04-属性描述符与元编程.md)）。给外部对象挂私有数据时用它，对象被回收时条目自动消失。

### 堆上限

V8 的老生代有上限（默认值取决于平台与可用内存），到达上限且回收不出空间时抛 `JavaScript heap out of memory` 并终止进程。`--max-old-space-size` 可调。

**调大上限不是解决泄漏的办法**——它只是把崩溃推迟。先确认内存增长是"应该增长的"（如缓存预热）还是"泄漏的"。

## 连接：症状 → 手段

| 症状 | 可能原因 | 手段 |
|---|---|---|
| `heapUsed` 持续上升不回落 | 泄漏 | `--heap-prof` 找分配点 |
| GC 频繁、暂停明显 | 分配速率过高 | 减少临时对象、批处理 |
| `rss` 高但 `heapUsed` 正常 | 堆外内存（`Buffer`、`arrayBuffers`） | 查 `external` 字段 |
| 进程被 OOM 终止 | 单次分配过大或真泄漏 | 分块处理（见 [04-异步与并发/06-流](../04-异步与并发/06-流.md)） |

## 边界

- **泄漏 = 留了引用**，不是"忘了释放"：排查方向是"谁还引用着它"。
- **`rss` 高不等于泄漏**：看 `heapUsed` 的长期趋势。
- **`global.gc()` 仅调试用**：生产环境不要依赖手动回收。
- **`--trace-gc` 输出量极大**：只在排查时开。
- **GC 停顿不能消除**：延迟敏感的服务要观测它。
- **调大堆上限不解决泄漏**：只是推迟崩溃。
- **`WeakMap` 的键必须是对象**：原始值不能作弱引用键。
