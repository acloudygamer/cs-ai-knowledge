# 前端工程化

> **版本基准**: Node24+ES2024 (stable) | Node26+ES2026 (latest)

## 模块化

### 本质定义

**模块化是将程序分割为独立作用域单元的范式，每个单元通过显式接口暴露 API，隐藏内部实现。**

模块化的核心价值在于**隔离变化点** — 内部实现可自由修改而不影响消费者。

---

## 模块系统演进机制

```
全局函数/变量 → IIFE → CommonJS → AMD → UMD → ES Modules
```

这不是功能增强，而是**同步加载 → 异步加载 → 统一格式**的演进路径。

### 为什么需要模块系统？

**没有模块系统时**：所有变量共享全局作用域，命名冲突无法避免，依赖关系隐含在代码顺序中。

```javascript
// 隐式依赖：必须在 a.js 之后加载 b.js
<script src="a.js"></script>
<script src="b.js"></script>
```

## ES Modules（ESM）

**ESM 是 ECMAScript 标准化的模块系统，采用静态结构（编译时可确定导入/导出）实现确定性解析和 Tree Shaking。**

### 静态结构机制

```javascript
// 静态：导入/导出必须在模块顶层，不能在条件语句中
import { a } from './module';
export const b = 1;

// 动态导入返回 Promise，用于运行时条件加载
const module = await import('./module.js');
```

**为什么 ESM 选择静态设计？**
1. **确定性解析** — 导入路径在执行前已完全确定，支持循环依赖的静态分析
2. **Tree Shaking 可行** — 静态结构让 bundler 在打包时识别未使用导出并移除
3. **跨模块静态分析** — IDE 可在未执行代码前推断类型和引用

### 导入/导出的四种模式

| 模式 | 语法 | 用途 |
|------|------|------|
| 命名导出 | `export const a = 1;` | 多个相关常量/函数 |
| 默认导出 | `export default Cls;` | 模块只有一个主要出口 |
| 命名导入 | `import { a } from './m';` | 解构式使用 |
| 命名空间导入 | `import * as m from './m';` | 批量导入，避免命名冲突 |

### 循环依赖解析机制

<pre>
模块 A 加载流程：
1. A 开始执行，exports 对象创建（loaded=false）
2. A 遇到 `import { b } from './B'`，触发 B 加载
3. B 开始执行，exports 对象创建（loaded=false）
4. B 遇到 `import { a } from './A'`，获取 A 的当前 exports（a 未定义）
5. B 完成加载，设置 loaded=true
6. A 继续执行，定义 a，完成加载

结果：A.b 和 B.a 在对方模块执行时可能为 undefined
</pre>

**解决方案**：延迟访问（模块加载完成后才使用）或通过事件解耦。

## CommonJS（CJS）

**CJS 是 Node.js 原创的同步模块系统，采用运行时动态解析，导入/导出是对象赋值。**

### 核心机制

```javascript
// 导出是赋值（运行时）
module.exports.add = (a, b) => a + b;

// 导入是复制（运行时）
const { add } = require('./math');
```

**为什么 CJS 是运行时？**

`require()` 可以在任何位置调用，包括条件语句内：
```javascript
const fs = process.env.NODE_ENV === 'production'
  ? require('./prod')
  : require('./dev');
```

### CJS 与 ESM 的关键差异

| 特性 | ESM | CJS |
|------|-----|-----|
| 解析时机 | 编译时（静态） | 运行时（动态） |
| 导入绑定 | 只读引用（live bind） | 值复制 |
| Tree Shaking | 支持（静态分析） | 不支持 |
| 循环依赖 | 浅层支持 | 完全支持 |
| 条件导入 | 不支持 | 支持 |

## AMD / UMD

**AMD（异步模块定义）是 CJS 在浏览器异步场景下的妥协，UMD 是同时兼容 ESM/CJS/全局变量的适配层。**

```javascript
// AMD：先声明依赖，再使用
define(['./dep1', './dep2'], function(d1, d2) {
  return { result: d1.get() + d2.get() };
});

// UMD：环境检测桥接
(function(root, factory) {
  if (typeof define === 'function' && define.amd)
    define(['dep'], factory);
  else if (typeof module === 'object' && module.exports)
    module.exports = factory(require('dep'));
  else
    root.MyModule = factory(root.Dep);
})(this, function(dep) { return {}; });
```

这两种方案本质是**历史兼容性层**，现代项目应使用 ESM。

## 模块解析

### 解析路径算法

**模块解析是从导入路径到实际文件路径的映射规则，Node.js 采用逐级目录搜索。**

<pre>
导入 'module' 的解析流程：

1. 内置模块（fs, path, crypto）→ 直接返回 C++ bindings
2. 文件模块（./module, /module）→ 相对于当前文件解析
3. node_modules 向上搜索：
   - ./node_modules/module
   - ../node_modules/module
   - ../../node_modules/module
   - 直到根目录
4. 找不到 → Throw Error: Cannot find module
</pre>

### package.json 字段解析优先级

```json
{
  "exports": "./dist/index.js",
  "module": "./dist/index.mjs",
  "main": "./dist/index.cjs"
}
```

**为什么需要多个入口字段？**
- `exports` 精确控制子路径导出
- `module` 让 bundler 使用 ESM 版本（更好的 Tree Shaking）
- `main` 作为 CommonJS 的兜底

## 模块打包

### Bundler vs Bundleless

**Bundler 将所有模块合并为少量文件，代价是冷启动慢；Bundleless 跳过打包步骤，代价是运行时重复解析。**

| 特性 | Bundler 模式 | Bundleless 模式 |
|------|-------------|-----------------|
| 冷启动 | 扫描整个依赖图，慢 | 原生 ESM，浏览器直接加载，快 |
| 热更新 | 重新打包相关模块 | 仅重编译单文件，极快 |
| 生产构建 | 单文件/少量 chunks | 需要额外打包步骤 |
| 依赖缓存 | 哈希命名 | HTTP Cache |

### Tree Shaking 机制

**Tree Shaking 是利用 ESM 静态结构在打包时移除未使用导出的优化。**

<pre>
静态分析过程：

math.js          index.js
┌─────────┐      ┌─────────┐
│ export  │      │ import  │
│ add ─────┼──┐   │ {add}   │
│ sub      │  │   │ from    │
│ mul      │  └───│ 'math'  │
└─────────┘      └─────────┘

分析结果：add 被使用，sub/mul 未被引用 → 从输出中移除
</pre>

**为什么 CJS 不能 Tree Shaking？**

`require()` 可能是 `require(someVariable)`（运行时才知道），静态分析无法确定实际导入了什么。

### Code Splitting 机制

**Code Splitting 将代码按需分割为独立 chunk，实现并行加载和按需执行。**

```javascript
// 静态导入：同一步骤加载
import('./module').then(m => m.do());

// 打包后生成独立 chunk 文件
// chunk 可以在其他 chunk 加载后再加载
```

### 工具对比

| 工具 | 核心设计 | Tree Shaking | 适用场景 |

| Vite | ESM + native ESM dev server | 支持（Rollup） | 现代 SPA（Vue/React） |

### Vite 的 Dev Server 机制

<pre>
Vite 开发模式（Bundleless）：

       ↓

Vite 实时编译 .vue 文件并返回
       ↓
（无全量打包，HMR 只编译变化的文件）

rollup -- build entire dependency graph → optimized chunks

## Babel 与 PostCSS

### Babel 本质

**Babel 是 ES 版本兼容性编译器，将新语法转换为旧语法，使旧环境可以使用新语言特性。**

```
输入（ES2024）→ Babel 转换 → 输出（ES5）
```

**为什么 Babel 不转换 ESM 到 CJS？**

ESM 支持 `import` 静态分析；转换为 CJS 后 Tree Shaking 失效。应使用 `@babel/preset-env` 的 `modules: false` 保留 ESM。

### PostCSS 本质

**PostCSS 是 CSS 转换流水线，通过插件机制处理 CSS，每个插件负责单一转换任务。**

```javascript
// 输入 CSS
::part(foo) { color: red; }

// autoprefixer 插件后：无前缀需求，原样保留

// postcss-preset-env 插件后（stage: 3）
@property --color { syntax: '<color>'; inherits: false; initial-value: red; }
::part(foo) { color: var(--color); }
```

## 构建优化

### 公共依赖提取机制

**splitChunks 将多个 chunk 共享的模块提取到独立文件中，实现更好的缓存复用。**

```javascript
splitChunks: {
  cacheGroups: {
    vendor: {
      test: /[\\/]node_modules[\\/]/,
      name: 'vendors',
      chunks: 'all'
    }
  }
}
```

### CSS 提取机制

**MiniCssExtractPlugin 将 CSS 从 JS bundle 中分离为独立文件，解决 JS 加载阻塞渲染问题。**

```
原始：index.js 包含 style-loader 动态创建 <style> 标签
优化：独立 index.css，<link> 可并行下载，不阻塞 JS 执行
```

## 目录结构设计原则

```
src/
├── utils/           # 工具函数（纯函数，无副作用）
│   ├── index.js     # barrel 导出
│   └── format.js
├── services/        # 外部依赖（API、存储）
│   └── api.js
└── components/      # UI 组件（状态 + 渲染）
    └── Button.js
```

**Barrel 模式**：通过 index.js 统一导出子模块，消费者无需知道具体文件名。

**为什么分离 utils / services / components？**
- utils：无依赖，纯计算
- services：有副作用，测试需 mock
- components：有 UI 依赖，测试需 DOM 环境

## 循环依赖检测

**模块化项目中，循环依赖是静默 bug 的主要来源，检测工具在 CI 中运行。**

```javascript
// madge 检测原理
// 1. 解析所有 import 语句，构建有向图
// 2. 使用 Tarjan 算法找强连通分量（SCC）
// 3. SCC 大小 > 1 的组件即循环依赖

madge('./src/index.js').then(res => {
  const cycles = res.circular();
  if (cycles.length) throw new Error('循环依赖');
});
```
