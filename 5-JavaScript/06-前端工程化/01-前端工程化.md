# 前端工程化

> **版本基准**: Node24+ES2024 (stable) | Node26+ES2026 (latest)

## 定义

前端工程化是通过模块化规范、构建工具链、CI/CD 流程，将分散的静态资源转化为确定性、可重复、可审查的发布产物的系统。核心价值在于**将人工决策转化为机器可执行的确定性过程**——代码经过 lint → test → build → deploy 流水线，每个环节的输入输出均可被形式化验证。

## 数学模型

### 模块解析路径算法

模块解析是从 import 路径字符串到实际文件地址的映射，本质是**有约束的最短路径搜索**。

设当前文件路径为 $P_{cur}$，导入路径为 $r$，解析结果为 $P_{res}$。Node.js 解析规则：

$$
P_{res} = \begin{cases}
\text{builtin}(r) & \text{if } r \in \{\text{fs}, \text{path}, \text{crypto}, ...\} \\
P_{cur}.resolve(r) & \text{if } r \in \{./, ../, /\} \\
\text{searchUp}(P_{cur}, r) & \text{otherwise}
\end{cases}
$$

其中 $\text{searchUp}(P, r)$ 从当前目录向上逐级搜索 `node_modules` 目录，直到根目录：

$$
\text{searchUp}(P_{dir}, r) = \begin{cases}
P_{dir} + \text{node\_modules} + r & \text{if exists} \\
\text{searchUp}(\text{parent}(P_{dir}), r) & \text{if } P_{dir} \neq \text{root} \\
\text{throw Error} & \text{otherwise}
\end{cases}
$$

**解析复杂度**：
- 最好情况 $\mathcal{O}(1)$：内置模块或绝对路径
- 最坏情况 $\mathcal{O}(d)$：$d$ 为目录深度（向上搜索 node_modules）

### Tree Shaking 条件

Tree Shaking 得以实施的前提是 ESM 的**静态可分析性强**。设模块 $M$ 的导出集为 $E_M$，被使用（引用）的导出子集为 $U_M \subseteq E_M$。可被消除的导出为 $E_M \setminus U_M$。

可 Tree Shaking 的充要条件：
- 导入路径为字面量（不是变量）
- 导出为静态 `export` 声明（不是动态 `export {}`）
- 匹配器基于 AST 分析，不是运行时反射

**Tree Shaking 的数学定义**：
$$
E_{shaken} = E_M \setminus U_M
$$
$$
\text{bundle} = \bigcup_{M \in \text{dependencies}} (E_M \setminus E_{shaken})
$$

即：未使用的导出被消除，仅保留实际被引用的部分。

### 构建时间复杂度

对于 bundler，设依赖图节点数为 $|V|$（文件数），边数为 $|E|$（导入关系数）。单线程构建的时间下界为 $O(|V| + |E|)$，但实际受限于：
- 每个文件的解析：$O(size_i)$
- 每个模块的依赖解析：$O(degree_i)$
- Tree Shaking 的可达性分析：$O(|V| + |E|)$

**并行构建的理论加速比**：
$$
S_n = \frac{T_1}{T_n} \leq \frac{|V| + |E|}{|V| + |E| - \text{sequential\_deps}}
$$

其中 $\text{sequential\_deps}$ 是必须串行执行的部分（如按拓扑序处理的循环依赖）。

### Vite 的 Dev Server 性能模型

Vite 利用浏览器原生 ESM 加载，**在开发时跳过打包步骤**。设应用有 $N$ 个模块，依赖图深度为 $D$：

- 传统 bundler 冷启动：$\mathcal{O}(|V| + |E|)$（解析所有文件）
- Vite 冷启动：$\mathcal{O}(1)$（仅解析入口文件）

HMR（热模块替换）性能：
- 传统 bundler：$\mathcal{O}(\Delta V + \Delta E)$（重新打包依赖）
- Vite：$\mathcal{O}(1)$（仅重新编译变化的文件）

## 机制

### 为什么 ESM 选择静态设计？

CJS 的 `require()` 允许运行时条件导入：

```javascript
const module = process.env.NODE_ENV === 'prod'
  ? require('./prod')
  : require('./dev');
}
```

这意味着**在代码执行前，导入关系是未知的**。ESM 强制静态导入，使以下分析在编译时即可完成：
- 确定性依赖图构建
- 循环依赖检测
- Tree Shaking 的可达性分析
- 跨模块内联优化

**代价**：无法动态选择导入路径，失去 CJS 的条件加载灵活性。

### 循环依赖解析机制

ESM 循环依赖的本质是**模块初始化状态机**：

```
模块 A                    模块 B
────────                  ────────
创建 exports (空)    →    创建 exports (空)
执行顶层代码            →  执行顶层代码
  遇到 import B      →      遇到 import A
  获取 A 当前 exports        获取 B 当前 exports
  （此时 A 只有声明，        （此时 B 只有声明，
   无赋值）                  无赋值）
  继续执行 A           →    继续执行 B
  完成 exports           →   完成 exports
```

**约束**：循环依赖中，访问对方模块的变量可能得到 `undefined`（因为赋值还未执行）。解决方案是延迟访问（让模块完全初始化后再调用）或通过事件/回调解耦。

**循环依赖的数学分析**：
设模块 $A$ 和 $B$ 循环依赖，$V_A$、$V_B$ 为各模块的变量集。初始化顺序：
- 若 $A \rightarrow B$（A 依赖 B），则 B 先初始化
- 初始化时，被依赖模块的值可能是 undefined

### Vite 的 Dev Server 机制

Vite 利用浏览器原生 ESM 加载，**在开发时跳过打包步骤**：

- 浏览器直接请求源文件（.js, .vue, .css）
- Vite 拦截请求，对 .vue 文件执行单文件组件编译
- 对 .js 文件仅做 ESM 语法转换（如 object spread → ES5）
- 无全量依赖打包，HMR 只重新编译变化的文件

**生产模式**才使用 Rollup 全量打包优化。

**Vite 的依赖预构建**：
- 首次启动时，Vite 会预构建依赖（使用 esbuild）
- 将 CJS 依赖转换为 ESM 格式
- 将多文件依赖合并为单文件
- 减少浏览器请求数量

### Webpack splitChunks 策略

splitChunks 的目标是将**公共依赖提取为独立 chunk**，实现更好的 HTTP 缓存复用。

数学上：设 $C$ 为 chunk 集合，$M(c)$ 为 chunk $c$ 的模块集合，$p(c)$ 为 chunk $c$ 被访问的概率。优化目标：

$$
\max \sum_{c \in C} p(c) \cdot \text{cacheability}(c)
$$

实际配置通过 `splitChunks.cacheGroups` 按模块路径（`node_modules`）和访问频率切分。

**缓存复用条件**：
- chunk 内容不变（模块内容哈希不变）
- chunk 名称不变

### Babel 编译管线

Babel 本质是 **AST → AST 的转换器**：

```
源代码 (String)
    │
    ▼
Parse → AST
    │
    ▼
遍历 AST，对每个节点执行 plugins/presets 转换
    │
    ▼
生成目标代码 (String)
```

`@babel/preset-env` 根据 `targets` 配置决定需要转换的语法。例如：
- `ie: "11"` → 需要将 ES6+ 特性全部转换
- `chrome: "90"` → 仅转换 `chrome < 90` 不支持的特性

**陷阱**：Babel 默认将 ESM 转为 CJS，导致 Tree Shaking 失效。应使用 `modules: false` 保留 ESM 格式。

## 对比参照

| 维度 | Bundler 模式 (Webpack) | Bundleless 模式 (Vite dev) |
|------|----------------------|---------------------------|
| 冷启动 | 扫描整个依赖图，慢 | 原生 ESM，浏览器直接加载，快 |
| 热更新 | 重新打包相关模块 | 仅重编译单文件，极快 |
| 生产构建 | 单文件/chunks | 仍需打包（Rollup） |
| 依赖缓存 | 哈希命名 | HTTP Cache |
| 适用场景 | 复杂大型应用 | 现代 SPA |
