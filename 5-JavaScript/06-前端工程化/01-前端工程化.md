# 前端工程化

> **版本基准**: Node24+ES2024 (stable) | Node26+ES2026 (latest)

**Node26 在 ES2026 阶段引入了逐阶段导入（Phase Imports）提案，允许在模块初始化前声明依赖，改变了循环依赖的处理语义。同一模块图在 Node24 与 Node26 下行为可能不可互换。**

## 定义

前端工程化是通过**模块化规范**、**构建工具链**、**CI/CD 流水线**，将分散的静态资源转化为确定性、可重复、可审查的发布产物的系统。其本质是将人工决策转化为机器可执行的确定性过程——代码经过 `lint → test → build → deploy` 管线，每个环节的输入输出均可被形式化验证。

前端工程化的核心价值在于**消除开发环境与生产环境的行为差异**（The Nine Nines）：相同的源码经过相同的管线，产出相同的产物。若管线不确定，则测试通过不等于生产正常。

## 数学模型

### 模块解析路径算法

模块解析是从 import 路径字符串到实际文件地址的映射，本质是**有约束的最短路径搜索**。

设当前文件所在目录为 $P_{cur}$，导入路径为 $r$，解析结果为 $P_{res}$：

$$
P_{res}(P_{cur}, r) = \begin{cases}
\text{builtin}(r) & \text{if } r \in \mathbb{B} \quad (\mathbb{B} = \{fs, path, crypto, ...\}) \\
\text{absolute}(r) & \text{if } r[0] \in \{/,,~\} \\
\text{relative}(P_{cur}, r) & \text{if } r \in \{./, ../\} \\
\text{searchUp}(P_{cur}, r) & \text{otherwise}
\end{cases}
$$

其中 $\text{searchUp}$ 从当前目录向上逐级搜索 `node_modules` 目录：

$$
\text{searchUp}(P_{dir}, r) = \begin{cases}
P_{dir} + \text{node\_modules} + r & \text{if } \exists(P_{dir} + \text{node\_modules} + r) \\
\text{searchUp}(\text{parent}(P_{dir}), r) & \text{if } P_{dir} \neq \text{root} \\
\text{throw MODULE\_NOT\_FOUND} & \text{otherwise}
\end{cases}
$$

**解析复杂度**：
- 最好情况 $\mathcal{O}(1)$：内置模块或绝对路径（直接查表）
- 最坏情况 $\mathcal{O}(d)$：$d$ 为目录深度（向上搜索 node_modules，最坏到根目录）
- 平均情况 $\mathcal{O}(\frac{h}{2})$：假设均匀分布，$h$ 为目录树高度

**归约终点**：模块解析可归约为**带剪枝的深度优先搜索**，但剪枝规则由 import 路径的字首决定（`/` → 绝对路径，`./` → 相对路径，其余 → 向上搜索）。

### Tree Shaking 条件与数学定义

Tree Shaking 得以实施的前提是 ESM 的**静态可分析性**。设模块 $M$ 的导出集为 $E_M$，被实际引用的导出子集为 $U_M \subseteq E_M$（可达性分析的结果）：

$$
E_{shaken} = E_M \setminus U_M
$$
$$
\text{bundle} = \bigcup_{M \in \text{dependencies}} (E_M \setminus E_{shaken})
$$

可 Tree Shaking 的**充要条件**（三者缺一不可）：

| 条件 | 形式化 | 违反后果 |
|------|--------|---------|
| 导入路径为字面量 | $r \in \text{literal strings}$ | 路径在运行时才确定，bundler 无法静态追踪 |
| 导出为静态 `export` 声明 | $\text{typeof}(E_M) = \text{static exports}$ | 动态 `export {}` 不可预知 |
| 无运行时反射 | $\nexists \text{eval}, \text{Function}(r)$ | 运行时可注入任意模块引用 |

**为什么 CJS 无法 Tree Shaking**：CJS 的 `require()` 是函数调用，实参可为变量表达式。给定 `const m = condition ? './a' : './b'; require(m)`，静态分析无法确定 $m$ 的值，因此不可预知依赖图。ESM 的 `import` 是声明而非调用，顶层作用域的每个 `import` 路径在解析阶段即可枚举。

### 构建时间复杂度

对于 bundler，设依赖图节点数为 $|V|$（文件数），边数为 $|E|$（导入关系数）。

**单线程构建**的时间下界为 $T_1 = \Omega(|V| + |E|)$（拓扑遍历的线性下界），但实际上界受多重因素膨胀：

$$
T_1 = \sum_{i=1}^{|V|} \underbrace{\mathcal{O}(\text{parse}(s_i))}_{\text{文件解析}} + \sum_{(u,v) \in E} \underbrace{\mathcal{O}(1)}_{\text{边追踪}} + \underbrace{\mathcal{O}(|V|+|E|)}_{\text{可达性分析 (Tree Shaking)}}
$$

**并行构建**的理论加速比（Amdahl 定律）：

$$
S_n = \frac{T_1}{T_n} \leq \frac{1}{1-s}
$$

其中 $s$ 为不可并行部分（如含循环依赖的模块链）的占比。实际加速比远低于核心数，因为：
- **内存带宽瓶颈**：多核并行解析同一文件的不同区块时，共享 L2/L3 缓存竞争严重
- **IO 阻塞**：磁盘读取与 CPU 解析无法完全重叠
- **共享图结构**：模块依赖图本身是共享数据结构，写入时需加锁

### Vite 的 Dev Server 性能模型

Vite 利用浏览器原生 ESM 加载，在开发时**跳过打包步骤**。设应用有 $N$ 个模块，依赖图深度为 $D$：

| 指标 | Webpack/Rollup (dev) | Vite (dev) |
|------|----------------------|-------------|
| 冷启动复杂度 | $\Theta(|V|+|E|)$ — 解析所有文件 | $\Theta(1)$ — 仅解析入口文件 |
| HMR 复杂度 | $\Theta(\Delta V + \Delta E)$ — 重新打包相关模块 | $\Theta(1)$ — 仅重新编译变化文件 |
| 传输内容 | 打包后的单个/少量 chunk | 源文件 + 实时编译 |

Vite 冷启动为 $\mathcal{O}(1)$ 的原因：浏览器按需请求模块，Vite 只在请求到达时才编译，入口文件解析完毕即启动服务器。未被请求的模块永远不会被解析。

**预构建（Optimizing Dependencies）**：Vite 首次启动时用 esbuild 预构建 `node_modules` 中的 CJS 依赖，转换为 ESM 格式并合并多文件依赖。这一步骤的时间复杂度为 $\mathcal{O}(\frac{M}{p})$（$M$ = 依赖总大小，$p$ = esbuild 并行进程数），但只执行一次，后续启动直接使用缓存。

## 机制

### 为什么 ESM 选择静态设计

CJS 的 `require()` 是函数调用，实参可为任意表达式：

```javascript
const module = process.env.NODE_ENV === 'prod'
  ? require('./prod')        // 运行时才知道加载哪个
  : require('./dev');
```

这意味着**导入关系在代码执行前不可枚举**，以下优化全部无法进行：

| 优化 | CJS | ESM |
|------|-----|-----|
| 确定性依赖图构建 | ❌ | ✅ |
| 循环依赖检测 | 运行时才发现 | 解析时即发现 |
| Tree Shaking | ❌ | ✅ |
| 跨模块内联 | ❌ | ✅ |
| 延迟加载优化 | 手动实现 | 原生 `import()` |

**归约**：ESM 的静态性将"依赖分析"从**不可判定问题（CJS 需执行代码才知道）**降为**可判定问题（ESM 只需解析）**。这是一个从图灵完备运行时到上下文无关解析器的归约。

### 循环依赖解析机制

ESM 循环依赖的本质是**模块初始化状态机**。ESM 规范要求：

```
模块 A                    模块 B
────────                  ────────
1. 创建 exports 对象       1. 创建 exports 对象
   (初始为空 placeholder)    (初始为空 placeholder)
2. 执行顶层代码            2. 执行顶层代码
3. 遇到 import B   ────→   3. 遇到 import A
   获取 A 当前 exports        获取 B 当前 exports
   (此时 A 只有声明,           (此时 B 只有声明,
    无赋值, 故为 undefined)    无赋值, 故为 undefined)
4. 继续执行 A               4. 继续执行 B
5. exports 就绪              5. exports 就绪
```

**约束**：循环依赖中，访问对方模块的变量可能得到 `undefined`（因为赋值语句还未执行）。

**违反约束的后果**：
- 若模块 A 的导出依赖于模块 B 的导出，而 B 又间接依赖 A，则 A 可能读到 `undefined`
- 常见症状：`TypeError: Cannot read property 'xxx' of undefined`
- 解决方案：延迟访问（函数调用而非直接取值）或通过事件/回调打破循环

**数学分析**：设 $A \rightarrow B$ 表示"A 依赖 B"。拓扑排序后，被依赖的模块先初始化。若图中存在环，则环内节点的初始化顺序取决于图遍历的实现，不存在唯一解。Node.js 按文件系统中目录顺序作为 Tie-breaker。

### Vite 的 Dev Server 机制

Vite 的核心洞察：**开发时让浏览器做它原生能做的事**。

| 阶段 | Webpack (dev) | Vite (dev) |
|------|---------------|-------------|
| 入口处理 | 解析整个依赖图 | 仅解析入口文件 |
| 转换 | 所有文件打包为 bundle | 按需编译单个文件 |
| 请求响应 | 返回打包结果 | 返回源文件（语法转换后） |
| HMR | 重新打包相关模块 | 重新编译单文件 |

**生产模式**才使用 Rollup 全量打包（代码分割、Tree Shaking、压缩）。

**Vite 依赖预构建**：
- CJS 依赖（如 `lodash`）在预构建阶段转换为 ESM，解决浏览器原生 ESM 不支持 CJS 的问题
- 多文件依赖（如 `lodash/fp` 的多个文件）合并为单文件，减少 HTTP 请求数
- 预构建结果写入 `node_modules/.vite`，缓存于磁盘

**约束**：预构建依赖后，若直接修改 `node_modules` 中的文件（不通过 npm），缓存失效需手动清除。

### Webpack splitChunks 策略

splitChunks 的目标是将**公共依赖提取为独立 chunk**，实现更好的 HTTP 缓存复用。

数学上：设 $C$ 为 chunk 集合，$M(c)$ 为 chunk $c$ 的模块集合，$\text{hash}(c)$ 为 chunk 内容的哈希。优化目标：

$$
\max \sum_{c \in C} \underbrace{\text{hit\_rate}(c)}_{\text{缓存命中率}} \cdot \underbrace{|M(c)|}_{\text{模块数}}
$$

实际约束：
- 公共 chunk 过大 → 首屏加载慢
- chunk 过多 → HTTP/1.1 下连接数成为瓶颈（现代浏览器 HTTP/2 下无此问题）
- 动态导入（`import()`）的 chunk 名不可预知，需用 `output.manifest` 追踪

**缓存复用条件**（二者同时满足）：
1. chunk 内容不变（模块内容哈希不变）
2. chunk 名称不变（使用稳定的 chunk 命名策略）

### Babel 编译管线

Babel 本质是 **AST → AST 的纯函数转换器**，无副作用：

```
源代码 (String)
    │
    ▼
Parse → AST
    │
    ▼
遍历 AST，对每个节点执行 plugins/presets 转换
    │
    ▼
生成目标代码 (String)
```

`@babel/preset-env` 根据 `targets` 配置**智能判断**需要转换的语法：

| targets | 需要转换 | 不需要转换 |
|---------|---------|-----------|
| `ie: "11"` | 所有 ES6+ 特性 | — |
| `chrome: "90"` | `private class fields`、`logical assignment` 等 | `const/let`、`箭头函数` 等 |
| `"> 0.5%, not dead"` | 浏览器市场份额 < 0.5% 的特性 | — |

**关键陷阱**：Babel 默认将 ESM 转为 CJS（`import` → `require`），这会导致：
1. Tree Shaking 失效（`require` 无法静态分析）
2. 所有模块被包装为对象，字面量导出被破坏

**解决方案**：在 `preset-env` 中设置 `modules: false`，保留 ESM 格式，由 bundler 自行处理模块系统。

## 对比参照

| 维度 | Bundler 模式 (Webpack) | Bundleless 模式 (Vite dev) |
|------|----------------------|---------------------------|
| 冷启动 | $\Theta(|V|+|E|)$ | $\Theta(1)$ |
| 热更新 | $\Theta(\Delta V + \Delta E)$ | $\Theta(1)$ |
| 生产构建 | 打包优化 (Tree Shaking, minify) | 仍需 Rollup 打包 |
| 依赖缓存 | 哈希命名 | HTTP Cache |
| 适用场景 | 复杂大型应用 | 现代 SPA / 快速迭代 |

// Babel 保留 ESM 供 Tree Shaking

  ]
};
