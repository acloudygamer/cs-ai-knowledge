# 数据库与缓存

> 前置：[05-服务端安全与认证](./05-服务端安全与认证.md) · 后续：[07-引擎与性能/01-引擎架构与 JIT](../07-引擎与性能/01-引擎架构与JIT.md)

> **版本基准**：Node 24 stable / Node 26 latest。本篇示例实测环境：Node v24.13.1（V8 13.6），Windows x64（`node:sqlite` 内存库实测；该模块在 Node 24 仍标注实验性）。

## 本质

服务端的数据存储分三层，各有明确职责：

| 层 | 生命周期 | 共享范围 | 典型用途 |
|---|---|---|---|
| **进程内存** | 进程存活期间 | 单个进程 | 请求级缓存、计算中间结果 |
| **外部缓存**（Redis 等） | 可配 | 所有进程与服务 | 会话、热点数据、限流计数 |
| **持久化数据库** | 永久 | 所有进程与服务 | 业务数据 |

**进程内存不能当存储用**，理由有两条：进程重启即丢失；`cluster` 下各 worker 是独立进程，内存不共享（见 [04-进程与集群](./04-进程与集群.md)）。需要跨进程或跨重启存在的状态，必须外置。

## 机制

### SQL 注入：拼接字符串的后果

这是服务端最经典也最致命的漏洞，成因只有一个：**把数据拼进了 SQL 语句**。实测演示：

```console
$ node -e '…'
参数化查 甲: [{"id":1,"name":"甲","email":"a@x.com"}]
参数化传入注入串: [] （当作普通字符串，查不到）
拼接查询返回 2 行 —— 注入成功，全表泄露
```

同一个恶意输入 `' OR 1=1 --`：

| 写法 | 结果 |
|---|---|
| `db.prepare("… WHERE name = ?").all(evil)` | `[]`——**被当作普通字符串**，查不到 |
| `"… WHERE name = '" + evil + "'"` | **返回全表**——`OR 1=1` 让条件恒真，`--` 注释掉后续 |

参数化查询把"SQL 结构"与"数据"**分成两条通道**送给数据库：结构先编译，数据后绑定，数据永远不可能被解释成语法。这是根治，不是缓解。

**规则**：**任何来自外部的值都通过占位符传入**，包括看起来"肯定是数字"的 ID——类型转换判断本身就可能出错。表名、列名、排序方向这类无法参数化的部分，用**白名单**映射。

### 事务

```console
$ node -e '…'
回滚后行数: 2
```

事务把多个操作绑成**一个原子单元**：要么全部生效，要么全部回滚。实测中插入一行后 `ROLLBACK`，行数回到 2。

需要事务的场景：跨表的一致性更新、先查后改（避免竞态）、批量导入。**注意事务期间持有的锁**——长事务会阻塞其它请求。

### 连接池

数据库连接是**昂贵资源**：建立连接要 TCP 握手、认证、分配服务端资源。所以：

- **不要每个请求新建连接**；
- **不要全局共用一个连接**——连接上的事务会互相干扰，且同一连接无法并发。

连接池维护一组复用连接，请求时借用、用完归还。关键参数：

| 参数 | 含义 |
|---|---|
| 最大连接数 | 池的上限；超过则排队。**不能超过数据库的最大连接数** |
| 最小空闲数 | 预热保持的连接 |
| 空闲超时 | 长时间不用的连接被回收 |
| 获取超时 | 等不到连接时的等待上限（防止无限排队） |

最大连接数的选取是个权衡：**太小**则请求排队、吞吐上不去；**太大**则数据库侧连接数耗尽，且上下文切换开销上升。经验起点是"数据库核心数的若干倍"，再按实测调整。

### 缓存

外部缓存（Redis 一类）解决三个问题：**降低数据库压力**、**跨进程共享状态**、**加速热点读取**。

| 缓存问题 | 表现 | 对策 |
|---|---|---|
| **穿透** | 查不存在的数据，每次都打到数据库 | 缓存空结果（短 TTL）或布隆过滤器 |
| **击穿** | 热点键过期瞬间，大量请求同时回源 | 互斥锁重建，或逻辑过期 |
| **雪崩** | 大量键同时过期，数据库被压垮 | TTL 加随机抖动，避免同时失效 |

**TTL 加随机抖动**是最简单也最有效的一条：把固定 `TTL` 改成 `TTL + random(0, jitter)`，避免批量写入的键在同一秒集体失效。

**缓存的失效策略**比缓存本身更重要。两种基本做法：

- **过期失效**（TTL）：简单，但有窗口期读到旧数据；
- **主动失效**：写数据库时删缓存。**先更新数据库，再删缓存**——顺序反了会在并发下留下旧值。

`cluster` 下还有一条硬约束：**限流计数器必须放在共享存储**。放进程内存的话，N 个 worker 各算各的，实际限额是设定值的 N 倍（见 [04-进程与集群](./04-进程与集群.md)）。

### 访问方式的选择

| 方式 | 特点 | 适用 |
|---|---|---|
| 原生 SQL + 驱动 | 完全控制，需手工映射结果 | 复杂查询、性能敏感 |
| 查询构建器 | 链式拼 SQL，仍接近 SQL | 中等复杂度、需要动态条件 |
| ORM | 对象映射，抽象度高 | 以增删改查为主、模型稳定 |

**ORM 不消除 SQL**——它只是生成 SQL。复杂查询（多表聚合、窗口函数）在 ORM 里往往更难写且性能更差，最终仍需落到原生 SQL。**理解 SQL 是前提**，选哪种写法是次要的。

## 连接：存储层次

| 数据 | 放哪 | 理由 |
|---|---|---|
| 请求级中间结果 | 进程内存 | 生命周期与请求一致 |
| 会话 | 外部缓存（或数据库） | 需要跨 worker 共享且可吊销 |
| 限流计数 | 外部缓存 | 必须全局一致 |
| 热点只读数据 | 外部缓存 | 降低数据库压力 |
| 业务数据 | 持久化数据库 | 唯一真相来源 |

## 边界

- **任何外部输入都走参数化查询**：包括数字与"看起来安全"的 ID。
- **表名 / 列名无法参数化**：用白名单映射。
- **连接必须池化**：池上限不能超过数据库上限。
- **长事务会阻塞**：事务内不做网络调用等慢操作。
- **缓存 TTL 加随机抖动**：避免雪崩。
- **先更新数据库再删缓存**：顺序反了会留下旧值。
- **`cluster` 下限流计数必须外置**：否则限额失效。
- **缓存不是真相来源**：任何缓存数据都必须能从持久层重建。
