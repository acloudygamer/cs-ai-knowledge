# 进程与集群

> 前置：[03-HTTP 服务](./03-HTTP服务.md) · 后续：[05-服务端安全与认证](./05-服务端安全与认证.md)

> **版本基准**：Node 24 stable / Node 26 latest。本篇示例实测环境：Node v24.13.1（V8 13.6），Windows x64（12 核）。

## 本质

一个 Node 进程默认只用**一个 CPU 核心**——因为它只有一个执行线程（见 [04-异步与并发/01-事件循环与任务队列](../04-异步与并发/01-事件循环与任务队列.md)）。要利用多核，有两条路：

| 路径 | 手段 | 内存 |
|---|---|---|
| **多进程** | `cluster` / `child_process` | 各自独立 |
| **多线程** | `worker_threads`（见 [04-异步与并发/05-Worker 与共享内存](../04-异步与并发/05-Worker与共享内存.md)） | 除 `SharedArrayBuffer` 外独立 |

`cluster` 是**多进程方案的一个特例**：它让多个 Node 进程**共享同一个端口**，从而把同一个服务铺到多个核心上。它的价值在于"共享端口"这件事本身——手工 fork 多个进程各自 `listen` 同一端口会冲突。

## 机制

### 四种子进程 API

| API | 是否走 shell | 输出 | 适用 |
|---|---|---|---|
| `exec(cmd, cb)` | **是** | 缓冲，回调里一次性拿到 | 短命令，输出小 |
| `execFile(file, args, cb)` | 否 | 缓冲 | 调用可执行文件，参数安全 |
| `spawn(cmd, args)` | 否 | **流式** | 长任务、大输出 |
| `fork(modulePath)` | 否（起 Node） | 流式 + **IPC 通道** | Node 子进程，需要通信 |

```console
$ node proc.mjs
子进程 pid: 18332 | 父进程 pid: 1220 | 不同: true
参数原样: 含 空格 的参数
stdout 收到 2 个数据块（流式，可能合并）
```

三点值得注意：

- **`exec` 走 shell**，所以命令字符串里的用户输入会被 shell 解释——这是命令注入的入口。**参数由用户提供的场景用 `execFile`**，它把参数作为数组直接传给可执行文件，不经过 shell 解析。
- **`exec` 会缓冲全部输出**，默认上限约 1 MB，超限报错。输出可能很大时用 `spawn`（流式，见 [04-异步与并发/06-流](../04-异步与并发/06-流.md)）。
- **`spawn` 的数据块边界不确定**：两次 `console.log` 可能合并到一个 `data` 事件里，**不要假设"一个 data 事件 = 一行输出"**，要按换行符缓冲拆分。

### `fork` 与 IPC

```console
$ node proc.mjs
子进程回话: {"got":7,"doubled":14,"pid":24372}
```

`fork` 启动一个新的 Node 进程，并在父子之间建立一条 **IPC 通道**（`process.send` / `"message"` 事件）。传递的数据同样经过**结构化克隆**（见 [04-异步与并发/05-Worker 与共享内存](../04-异步与并发/05-Worker与共享内存.md)）——函数传不过去。

### 退出码与信号

```console
$ node proc.mjs
退出码: 3
被信号终止: SIGTERM
```

子进程的结束有两条路：**正常退出**（`close` 事件给退出码，`0` 为成功）或**被信号杀死**（给信号名，退出码为 `null`）。区分它们很重要：退出码非 0 是业务失败，信号终止通常是外部干预。

### `cluster`：共享端口的多个进程

```javascript
if (cluster.isPrimary) {
  for (let i = 0; i < cpus().length; i++) cluster.fork();
} else {
  createServer(handler).listen(3000);   // 每个 worker 都 listen 同一端口
}
```

主进程只负责**拉起与监督** worker，不处理请求。worker 是独立进程，各自有自己的事件循环、内存、V8 实例。

### 负载均衡：平台差异，实测踩到

Node 官方文档明确说明：主进程**自己**把进来的连接分发给 worker，默认轮询（`cluster.SCHED_RR`）——**但这一默认值在除 Windows 以外的所有平台上成立**。

实测确认了这个例外：

```console
$ node -e 'console.log(require("node:cluster").schedulingPolicy, require("node:cluster").SCHED_NONE)'
1 1
```

Windows 上默认策略是 **`SCHED_NONE`**（值为 1）：主进程**不**分发连接，各 worker 通过操作系统共享监听套接字，由系统决定谁接。实测结果是**极不均衡**——12 次全新连接的请求全部落到同一个 worker：

```console
$ node clus4.mjs
worker 数: 3 | 主进程 pid: 15548
处理者: 14064,14064,14064,14064,14064,14064,14064,14064,14064,14064,14064,14064
不同 worker 数: 1 / 3
```

**结论**：`cluster` 的轮询调度**在 Windows 上不生效**，需要均衡时必须显式设 `cluster.schedulingPolicy = cluster.SCHED_RR`，或改用反向代理做分发。这与 [04-异步与并发/05-Worker 与共享内存](../04-异步与并发/05-Worker与共享内存.md) 里 worker 的开销问题一样，属于"平台差异影响结论"的一类事实——**同一段代码在不同平台上行为不同**。

### 进程间不共享内存

这是 cluster 最重要的一条约束：**worker 是独立进程，内存不共享**。由此推出：

| 放进进程内存的东西 | 在 cluster 下的后果 |
|---|---|
| 会话（session） | 用户下次请求可能落到另一个 worker，会话丢失 |
| 内存缓存 | 各 worker 各有一份，命中率低且不一致 |
| 限流计数器 | 各算各的，实际限额是设定值的 N 倍 |
| 定时任务 | **每个 worker 都会跑一遍**，任务被执行 N 次 |

这些状态必须外置到共享存储（Redis 等，见 [06-数据库与缓存](./06-数据库与缓存.md)），或者干脆不用 cluster（改用单进程 + worker 池处理 CPU 密集任务）。

### 优雅重启

`cluster` 的经典用法是**零停机部署**：逐个替换 worker，而不是一次性重启全部。

```javascript
if (cluster.isPrimary) {
  cluster.on("exit", (worker) => {
    if (!shuttingDown) cluster.fork();     // 意外退出则补一个
  });
}
```

要点是"先拉起新 worker 并等它就绪，再关掉旧的"，保证任意时刻都有进程在监听。不做这件事的后果是部署期间出现请求失败窗口。

## 连接：三种并行方案

| | 单进程 | `cluster`（多进程） | `worker_threads`（多线程） |
|---|---|---|---|
| 利用多核 | 否 | 是 | 是 |
| 共享内存 | — | 否 | 可（`SharedArrayBuffer`） |
| 启动开销 | — | 高（进程） | 中（线程） |
| 崩溃影响 | 全挂 | 只挂一个 worker | 只挂一个线程 |
| 状态共享 | 天然 | **需外置** | 需原子操作 |
| 适用 | 开发、低负载 | 高并发 HTTP 服务 | CPU 密集计算 |

## 边界

- **`exec` 走 shell**：用户提供的参数必须用 `execFile`，否则是命令注入。
- **`exec` 缓冲输出且有上限**：大输出用 `spawn`。
- **`spawn` 的数据块边界不确定**：按分隔符缓冲，不要按事件切分。
- **`cluster` 的轮询在 Windows 上不生效**：需显式设策略或改用反向代理。
- **进程间不共享内存**：会话、缓存、限流器必须外置。
- **定时任务在 cluster 下会执行 N 次**：需加锁或改用独立进程。
- **没有优雅重启就有停机窗口**：部署流程必须处理。
