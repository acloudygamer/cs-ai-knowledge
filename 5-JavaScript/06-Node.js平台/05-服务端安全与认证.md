# 服务端安全与认证

> 前置：[04-进程与集群](./04-进程与集群.md) · 后续：[06-数据库与缓存](./06-数据库与缓存.md)

> **版本基准**：Node 24 stable / Node 26 latest。本篇示例实测环境：Node v24.13.1（V8 13.6），Windows x64。

## 本质

服务端的安全边界与浏览器不同（对比 [05-浏览器平台/05-浏览器安全模型](../05-浏览器平台/05-浏览器安全模型.md)）：

| | 浏览器防什么 | 服务端防什么 |
|---|---|---|
| 威胁 | 攻击者的代码以你的源身份运行（XSS） | 攻击者以你的**用户**身份发请求（CSRF） |
| 边界 | 同源策略 | 认证凭证 |
| 后果 | 读取页面数据 | 执行用户能做的任何操作 |

本篇讲三件事：**凭证怎么发**（会话 / JWT）、**请求怎么验**（CSRF 防护）、**密码怎么存**（哈希）。三者是独立的防线，缺一不可。

先立一条区分：**认证**（authentication，你是谁）与**授权**（authorization，你能做什么）是两件事。通过了认证不等于有权限——每个操作都要单独判权。

## 机制

### 密码存储：慢哈希 + 每用户随机盐

**绝不能用普通哈希存密码**。`sha256` 设计目标就是快，而"快"对攻击者同样有利——泄露的哈希库可以用 GPU 每秒尝试数十亿次。

```console
$ node sec.mjs
sha256('abc'): ba7816bf8f01cfea414140de5dae2223 …
scryptSync 耗时: 31 ms | 派生长度: 64
同一密码同一盐结果相同: true
换盐则不同: true
```

正确的做法有三个要素：

| 要素 | 作用 |
|---|---|
| **慢哈希** | `scrypt` / `argon2` / `bcrypt`，参数可调，单次验证耗时可观 |
| **每用户随机盐** | 同样的密码得到不同的哈希，抵御彩虹表与"批量比对" |
| **足够的参数强度** | 让单次计算耗时落在可接受范围的上限 |

本机实测 `scryptSync` 用 `N=16384` 耗时约 31 ms。**这个耗时要落在验证请求的可接受范围内**——太低起不到作用，太高会成为拒绝服务的入口（攻击者用大量登录请求消耗 CPU）。生产参数应当实测选定。

Node 内置 `scrypt`（异步版本更好，不阻塞事件循环），无需第三方依赖。`argon2` 是当前更被推荐的算法，需要额外依赖。

### 令牌生成：用密码学随机源

```console
$ node sec.mjs
randomUUID: 146eeb77-c5bc-4a76-a191-f2f4e6fc4390
randomBytes(8) hex: 7e7b9c11d1e165cc
```

会话 ID、重置令牌、CSRF token 都必须来自 `crypto` 模块的 **CSPRNG**（密码学安全伪随机数生成器）。**`Math.random()` 不是密码学安全的**——它的内部状态可被观测输出反推，用它生成的令牌可被预测。

### 定时安全比较

比较令牌时用普通 `===` 会**提前返回**：第一个字符不同就立刻返回，第一个字符相同则多比一位。理论上攻击者可以通过测量响应时间逐字节猜出令牌——称为**时序侧信道**。

```console
$ node -e '…'
同长: true
同长不等: false
长度不等 -> RangeError: Input buffers must have the same byte length
```

`crypto.timingSafeEqual` 比较耗时与内容无关。注意它**要求两个 Buffer 等长**，否则抛 `RangeError`——这本身会泄露长度信息，所以比较前要先把长度也拉平（如先各自哈希再比较）。

### JWT：签名，不是加密

JWT（JSON Web Token）是三个 base64url 段用点号连接：

```console
$ node sec.mjs
头部可解: {"alg":"HS256","typ":"JWT"}
载荷可解（不是加密！）: {"sub":"user1","exp":1790454761}
签名校验: true
换密钥校验: false
```

**载荷是 base64url 编码，任何人都能解出**——base64 是编码不是加密。所以：

- **JWT 里不能放敏感信息**（密码、密钥、身份证号）；
- 它的安全性来自**签名**：改一个字节，签名校验就失败（实测换密钥即不通过）。

JWT 的实际难点不在签名，在**失效**：

| 问题 | 原因 |
|---|---|
| 无法主动吊销 | 服务端不保存状态，签出去的令牌在过期前一直有效 |
| 改密码后旧令牌仍有效 | 同上 |
| 载荷过期时间只能靠 `exp` | 需要客户端配合或服务端维护黑名单 |

**吊销需求强时用会话**（服务端存状态，可随时删除）；**跨服务、无状态、短期**的场景才用 JWT。

### CSRF：Cookie 自动发送的副作用

CSRF（Cross-Site Request Forgery，跨站请求伪造）的成因是 Cookie 的机制：**浏览器会自动把同源 Cookie 附在请求上**（见 [05-浏览器平台/04-浏览器存储](../05-浏览器平台/04-浏览器存储.md)）。

于是攻击者只要诱导用户访问一个页面，该页面里向你的服务发一个请求，浏览器就会自动带上用户的会话 Cookie——服务端无法区分这个请求是用户本意还是被伪造的。

| 防御 | 机制 |
|---|---|
| `SameSite=Lax`（现代浏览器默认） | 跨站请求不发送 Cookie，挡住大多数场景 |
| `SameSite=Strict` | 更严，但从外部链接进入时也不发送 |
| **CSRF Token** | 服务端下发随机令牌，要求请求体/头里带回；跨站页面读不到它 |
| 校验 `Origin` / `Referer` | 检查请求来源 |

**CSRF Token 仍需要**：`SameSite` 是浏览器行为，老客户端或特殊场景下不可靠。Token 的要点是**放在请求头或请求体里**——跨站页面既读不到也设不了（受同源策略限制）。

### 凭证放在哪

| 位置 | XSS 能否窃取 | CSRF 风险 | 说明 |
|---|---|---|---|
| `HttpOnly` Cookie | **否** | 有（需 CSRF 防护） | 服务端可读，脚本不可读 |
| `localStorage` | **能**（脚本可读） | 无（不自动发送） | XSS 一旦发生即失守 |
| 内存（仅变量） | 能（同源脚本可访问） | 无 | 刷新即丢 |

**优先 `HttpOnly` + `Secure` + `SameSite` Cookie**，再配 CSRF Token。把令牌放 `localStorage` 是把"XSS 的影响范围"从"当前页面"扩大到"长期凭证"——XSS 本来就很严重，不该再让它拿到长期令牌。

### 其余服务端防线

| 项 | 做法 |
|---|---|
| 输入校验 | **白名单**优于黑名单；在边界处校验一次，内部信任 |
| SQL 注入 | 用参数化查询，**不要拼字符串**（见 [06-数据库与缓存](./06-数据库与缓存.md)） |
| 限流 | 按 IP / 用户 / 接口限速，防暴力破解与滥用 |
| 日志脱敏 | 密码、令牌、身份证号不进日志 |
| 错误信息 | 对外只给通用信息，细节进服务端日志（避免信息泄露） |
| 依赖审计 | `npm audit`，第三方包是供应链攻击面 |

## 连接：会话与 JWT 选型

| | 服务端会话 | JWT |
|---|---|---|
| 状态 | 服务端存储 | 无状态（令牌自包含） |
| 吊销 | 删除即可，立即生效 | 难，需黑名单或短有效期 |
| 跨服务 | 需共享存储 | 天然可验证 |
| 体积 | 一个 ID | 随载荷增长 |
| 适用 | 单体应用、需要强吊销 | 微服务、短期凭证 |

**常见折中**：短期 JWT（几分钟）做访问令牌 + 长期随机字符串做刷新令牌（服务端可吊销）。

## 边界

- **JWT 载荷不加密**：任何人可解，不放敏感信息。
- **`Math.random()` 不能生成令牌**：用 `crypto.randomBytes` / `randomUUID`。
- **比较令牌用 `timingSafeEqual`**：普通 `===` 有时序侧信道；注意它要求等长。
- **密码用慢哈希 + 每用户盐**：`scrypt` / `argon2` / `bcrypt`，参数需实测选定。
- **`SameSite` 不能替代 CSRF Token**：它是浏览器行为，且历史上默认值变过。
- **认证 ≠ 授权**：每个操作单独判权。
- **错误信息要克制**：区分"用户不存在"与"密码错误"会泄露账号存在性。
- **前端无法单独完成服务端安全加固**：Cookie 属性、CSRF Token、限流都在服务端。
