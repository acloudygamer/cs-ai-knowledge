# HTTP 服务

> 前置：[02-文件系统与流](./02-文件系统与流.md) · 后续：[04-进程与集群](./04-进程与集群.md)

> **版本基准**：Node 24 stable / Node 26 latest。本篇示例实测环境：Node v24.13.1（V8 13.6），Windows x64（本地服务器实测）。

## 本质

一个 HTTP 服务就是一个循环：**收到请求 → 处理 → 写回响应**。Node 的 `node:http` 模块把这件事降到最低——它给你原始的请求与响应对象，**不提供路由、中间件、请求体解析、模板**。

这不是缺陷，而是定位：`node:http` 是**协议层**，框架是**应用层**。理解协议层才能解释框架的行为（为什么请求体是流、为什么响应头必须在写正文前设置、为什么 `await` 一个请求体要小心）。

## 机制

### 最小的服务

```javascript
import { createServer } from "node:http";

const server = createServer((req, res) => {
  res.writeHead(200, { "Content-Type": "text/plain; charset=utf-8" });
  res.end("你好");
});

server.listen(3000);
```

`createServer` 的回调对**每个请求**调用一次，`req` 与 `res` 是这一对请求与响应的句柄。

### 请求对象

| 属性 | 说明 |
|---|---|
| `req.method` | `GET` / `POST` / … |
| `req.url` | **只有路径与查询串**，不含协议与主机 |
| `req.headers` | 请求头（键为小写） |
| `req` 本身 | **请求体是一条可读流**（见 [02-文件系统与流](./02-文件系统与流.md)） |

`req.url` 不含主机名，所以解析绝对 URL 要自己补：

```console
$ node http.mjs
{ method: 'GET', path: '/json', q: '你好' }
```

```javascript
const url = new URL(req.url, `http://${req.headers.host}`);
```

用 `new URL` 而不是手工拆字符串——查询串的编解码、重复参数、`%` 转义它都处理好了（见 [05-浏览器平台/03-网络与同源策略](../05-浏览器平台/03-网络与同源策略.md)）。

**请求体是流，不是字符串**：

```console
$ node http.mjs
收到 10 字节
```

```javascript
const chunks = [];
for await (const chunk of req) chunks.push(chunk);
const body = Buffer.concat(chunks).toString("utf8");
```

这带来两个后果：**要自己处理编码与解析**（表单、JSON、multipart），以及**要自己限制大小**——不限制的话，一个巨大的请求体会把内存吃光。这正是框架做的事之一。

### 响应对象

```console
$ node http.mjs
status: 404 | ok: false | body: 未找到
```

| 操作 | 方法 |
|---|---|
| 设状态与头 | `res.writeHead(status, headers)` 或分别设 `res.statusCode` / `res.setHeader` |
| 写正文 | `res.write(chunk)`（可多次） |
| 结束 | `res.end()` |

**顺序约束**：头必须在正文之前发送。第一次 `write()` 或 `end()` 会**隐式发送已设置的头**，之后再改 `statusCode` 或 `setHeader` 会抛错。所以 `writeHead` 应尽早调用。

**分块响应**：`res.write()` 可以调用多次，浏览器会边收边处理：

```console
$ node http.mjs
"块0\n块1\n块2\n"
```

这是流式响应（SSE、大文件下载）的基础。`res` 本身是一条可写流，可以把文件流直接 `pipe` 过去（见 [04-异步与并发/06-流](../04-异步与并发/06-流.md)）。

### 中间件是约定，不是框架特性

原生 `node:http` **没有中间件**。所谓中间件是这样一个约定：一组函数，每个接收 `(req, res, next)`，做自己的事，然后调用 `next()` 交给下一个。

它的形状来自**洋葱模型**：请求按顺序穿过各层，响应按相反顺序返回。

```text
请求 ──▶ 日志 ──▶ 鉴权 ──▶ 路由 ──▶ 处理
响应 ◀── 日志 ◀── 鉴权 ◀── 路由 ◀── 处理
```

`next()` 之前的代码在"进入"时执行，之后的代码在"返回"时执行。这个结构让"统一加日志"（前后都要）与"提前拦截"（鉴权失败不调 `next`）都能用同一个约定表达。

框架（Express、Koa、Fastify）把这套约定固化下来并补齐了请求体解析、路由匹配、错误处理中间件等。**选框架的理由是这些补齐的部分**，而不是中间件本身。

### 生产环境必须处理的四件事

| 事项 | 做法 |
|---|---|
| **请求体大小限制** | 读取时累计字节数，超限即断开 |
| **超时** | 服务器级 `server.requestTimeout` / `headersTimeout`，以及每个下游调用的 `AbortSignal.timeout`（见 [04-异步与并发/04-并发控制与取消](../04-异步与并发/04-并发控制与取消.md)） |
| **错误处理** | 每个请求的异常都要捕获并返回 5xx，否则未捕获异常会终止进程（见 [01-语言核心/07-错误处理](../01-语言核心/07-错误处理.md)） |
| **优雅关闭** | 收到终止信号后停止接受新连接，等在途请求完成再退出 |

优雅关闭的形态：

```javascript
process.on("SIGTERM", () => {
  server.close(() => process.exit(0));   // 停止接受新连接，等在途请求结束
});
```

没有它，部署时的滚动重启会切断正在处理的请求。

### HTTP/2

`node:http2` 提供 HTTP/2 支持：**多路复用**（一个连接上并发多个请求）、头部压缩、服务端推送。HTTP/1.1 的队头阻塞（同一连接上必须按顺序响应）由此解决。

实践中 HTTP/2 通常由反向代理（Nginx、Caddy、云负载均衡）终结，应用服务器仍跑 HTTP/1.1——因为收益主要在客户端到代理那一段，而代理到应用是内网、延迟极低。

## 连接：原生与框架

| 能力 | `node:http` | 框架 |
|---|---|---|
| 接收请求 | ✓ | ✓ |
| 路由匹配 | 自己写 `if` / `switch` | 内建 |
| 请求体解析（JSON / 表单） | 自己读流 + 解析 | 内建 |
| 中间件 | 自己约定 | 内建 |
| 错误处理 | 自己捕获 | 统一入口 |
| 静态文件 | 自己读 + 设头 | 内建 |
| 体积 / 依赖 | 零 | 有 |

**学习顺序是"先懂协议层，再用框架"**：框架的每个便利都对应协议层的一件事，知道那件事是什么，才知道框架替你做了什么、什么时候会失效。

## 边界

- **`req.url` 不含主机名**：解析要用 `new URL(req.url, base)`。
- **请求体是流**：不读它，请求就悬着；不限大小，内存会被吃光。
- **响应头必须在正文之前设置**：第一次 `write` / `end` 后改就晚了。
- **原生 `http` 没有路由与解析**：这些是框架的职责。
- **未捕获异常会终止进程**：请求处理里必须有兜底。
- **没有优雅关闭会切断在途请求**：部署前务必处理终止信号。
- **HTTP/2 通常由反向代理终结**：应用侧仍多是 HTTP/1.1。
