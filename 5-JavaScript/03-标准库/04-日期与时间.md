# 日期与时间

> 前置：[03-Object 与 Map/Set](./03-Object与Map-Set.md) · 后续：[05-正则表达式](./05-正则表达式.md)

> **版本基准**：Node 24 stable / Node 26 latest。本篇示例实测环境：Node v24.13.1（V8 13.6），Windows x64。

## 本质

`Date` 内部只存**一个数**：自 1970-01-01T00:00:00 UTC 起的毫秒数（时间戳）。所有 `getFullYear`、`getHours` 之类的方法都是"把这个数按某个时区、某种历法解释成人类可读的字段"。

它的复杂与易错来自三重身份叠在一个对象上：**时间戳**、**可变的时间点对象**、**格式化器**。其中第一重是本质，后两重是 1995 年为配合当时网页需求加上的——按 AGENTS.md 的分级，这属于**历史遗物而非设计**，规范后来冻结了它，只能靠 `Temporal` 另起炉灶（见文末）。

## 机制

### 月份从 0 开始，其它字段不

```console
$ node d.mjs
new Date(2026, 0, 15) = 2026-01-14 | getMonth() = 0
```

`new Date(2026, 0, 15)` 表示 **2026 年 1 月** 15 日——月份是 0~11。日、时、分、秒都从 1 或 0 正常计数，**只有月份偏移了一位**。这是最容易记错的一处。

### 解析：同一天的两个字符串得到不同时刻

`Date` 的字符串解析是规范里明确留有余地的一处，实测结果：

```console
$ node d.mjs
仅日期 -> 2026-01-15T00:00:00.000Z
带时间 -> 2026-01-14T16:00:00.000Z
斜杠格式 -> 2026-01-14T16:00:00.000Z
```

三行都写的是"2026 年 1 月 15 日"，却得到两个不同的时间戳（相差 8 小时，即本机时区 UTC+8）：

| 输入 | 被当作 | 结果（UTC） |
|---|---|---|
| `"2026-01-15"` | **UTC** 午夜 | 01-15T00:00:00Z |
| `"2026-01-15T00:00:00"` | **本地时区**午夜 | 01-14T16:00:00Z |
| `"2026/01/15"` | **本地时区**午夜（非标准格式） | 01-14T16:00:00Z |

规则是：**只有"纯日期"的 ISO 形式被当作 UTC，带时间部分的按本地时区**。这条差异在跨时区部署时会造成整天的偏差。

**结论：不要用 `Date` 解析字符串。** 需要构造确定时刻，用 `new Date(Date.UTC(y, m, d))` 或直接传时间戳；需要解析用户输入，用日期库或 `Temporal`。

### 可变性

`Date` 是**可变对象**，`setXxx` 系列方法就地修改自己：

```console
$ node d.mjs
setMonth 后原对象: 2026-01-15T00:00:00.000Z -> 2026-06-15T00:00:00.000Z
```

把 `Date` 存进状态、再传给别的函数，对方一次 `setHours` 就改掉了你的数据——这与 [02-对象模型与运行时/01-原型链与继承](../02-对象模型与运行时/01-原型链与继承.md) 里"赋值即别名"叠加，是难查的 bug 来源。

### 本地与 UTC：两套方法

每个字段都有两套读写方法：

| 字段 | 本地 | UTC |
|---|---|---|
| 年 | `getFullYear` | `getUTCFullYear` |
| 月（0 起） | `getMonth` | `getUTCMonth` |
| 日 | `getDate` | `getUTCDate` |
| 时 / 分 / 秒 | `getHours` / `getMinutes` / `getSeconds` | 前缀 `getUTC…` |
| 星期 | `getDay`（0 = 周日） | `getUTCDay` |

`getTimezoneOffset()` 返回**本地时间与 UTC 的差（分钟）**，且符号与直觉相反——东八区返回 `-480`：

```console
$ node d.mjs
本地时区偏移(分钟) = -480
```

服务端代码应统一用 UTC 方法或时间戳，只在**展示**时转成本地时区（用 `Intl`，见下）。

### 比较与运算

```console
$ node d.mjs
a == b ? false | a.getTime() === b.getTime() ? true | a < b ? false
```

两个内容相同的 `Date` **不相等**（对象按引用比较），但 `<`、`>` 能正常工作——关系运算符会调用 `valueOf` 得到时间戳。**判断相等用 `getTime()` 或 `Number(date)`**。

日期运算（加一天、加一个月）没有内建支持，只能自己算毫秒数：

```javascript
new Date(date.getTime() + 24 * 60 * 60 * 1000);   // 加一天
```

但"加一个月"不能这么做——月份长度不同，夏令时切换日甚至不是 24 小时。这正是 `Temporal` 要解决的问题之一。

### 范围与无效值

时间戳的可表示范围是 $\pm 8.64 \times 10^{15}$ 毫秒（约 ±27.6 万年）；越界或解析失败都得到 `Invalid Date`，且**它的 `getTime()` 是 `NaN`**——`NaN` 参与的比较全为假，`Invalid Date` 会静默地"不等于任何东西"：

```console
$ node d.mjs
最大可表示 = +275760-09-13T00:00:00.000Z | 超出 -> Invalid Date
```

判断有效性用 `Number.isNaN(date.getTime())`。

### 格式化：用 `Intl`，不要手写

```console
$ node d.mjs
2026年1月15日
```

`Intl.DateTimeFormat` 处理语言、时区、日历系统，是唯一正确的格式化途径（见 [07-Intl 国际化](./07-Intl国际化.md)）。手写 `getMonth() + 1 + "/" + …` 会在多语言与夏令时上出错。

### `Temporal`：替代方案的现状

```console
$ node d.mjs
typeof Temporal = undefined
$ node --harmony-temporal -e 'console.log(typeof Temporal)'
object
```

`Temporal` 是 `Date` 的替代 API：不可变、区分"时间点"与"本地日期时间"、时区与历法一等公民、支持日期运算。它的现状有两层：

- **规范层面**：属 **ES2027**（TC39 于 2026 年 3 月推到 Stage 4），不在 ES2026 内。
- **引擎层面**：Node 26（V8 14.6）**默认开启**；Node 24 需 `--harmony-temporal` 启动标志。

这正是 [00-概览/01-JavaScript 全景](../00-概览/01-JavaScript全景.md) 所述"引擎落地领先规范版本"的第二个实例（第一个是 `Error.isError`）。

## 连接：`Date` 与 `Temporal` 对照

| | `Date` | `Temporal` |
|---|---|---|
| 可变性 | 可变 | 不可变 |
| 月份编号 | 0~11 | 1~12 |
| 时区 | 隐式（本地/UTC 两套方法） | 显式类型（`ZonedDateTime`） |
| 日期运算 | 无，手算毫秒 | `add` / `subtract` / `Duration` |
| 解析 | 形式依赖，结果不确定 | 显式指定格式与历法 |
| "无时区的日期" | 无法表达 | `PlainDate` |
| 现状 | 全平台可用 | ES2027；Node 26 默认，Node 24 需 flag |

## 边界

- **月份从 0 开始**，其它字段不。
- **不要用 `Date` 解析字符串**：同一天的两种写法会得到不同时刻。
- **`Date` 可变**：传参前先 `new Date(date.getTime())` 复制。
- **`Invalid Date` 的 `getTime()` 是 `NaN`**，且与任何值比较都为假。
- **服务端统一用 UTC 存储与计算**，只在展示层用 `Intl` 转本地时区。
