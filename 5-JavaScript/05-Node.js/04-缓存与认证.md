# 缓存与认证

## 定义

缓存的本质是**时间局部性原理的应用**：最近访问的数据很可能再次被访问，通过存储计算结果或复制数据副本，减少重复计算或远程请求。

认证的本质是**可信身份声明的验证**：客户端证明持有密钥（密码/TOTP/私钥），或持有令牌（JWT/cookie），服务端验证后建立会话。

## 数学模型

**缓存命中率**：
$$hit\_rate = \frac{hits}{hits + misses}$$

**缓存淘汰策略**：LRU（Least Recently Used）基于访问时间的局部性，LFU（Least Frequently Used）基于访问频率的局部性。两者在不同的访问模式下的命中率不同。

**bcrypt 密钥拉伸成本**：bcrypt 的计算复杂度为 $O(cost \times 2^{cost})$。设 cost factor $= r$，则每次哈希计算耗时约 $0.1 \times 2^r$ 秒（近似值）。cost=12 时单次计算约 250ms，暴力破解成本显著提高。

**JWT 签名验证**：JWT 的 Signature 部分使用 HMAC-SHA256（或 RSA）计算，公式为：
$$\text{Signature} = \text{HMAC-SHA256}(base64url(Header) + "." + base64url(Payload), secret)$$

验证时重新计算签名并与提供的 Signature 比较，常量时间比较防止时序攻击。

## 机制

**缓存的物理约束**：
- 缓存空间有限（内存或磁盘），无法无限存储
- 当缓存满时，需要淘汰策略（LRU/LFU/Random）
- 缓存与数据源的一致性：更新数据时需考虑是否更新/失效缓存

**HTTP 强缓存 vs 协商缓存**：
- 强缓存（`Cache-Control: max-age=3600`）：浏览器直接使用本地缓存，不发任何请求到服务器。适用于不经常变化的静态资源。
- 协商缓存（`ETag/Last-Modified`）：每次请求仍到服务器验证，若未变化返回 304 Not Modified。适用于可能变化的资源。

**违反约束的后果**：
- 强缓存资源更新后，浏览器因缓存未过期而不获取新版本 → 解决方法：版本化 URL（文件名含 hash）或设置 `no-cache`
- 缓存未设置过期时间且数据源已更新 → 缓存与数据源不一致

**JWT 的设计约束**：
- JWT 内容（除签名外）是 Base64 编码的明文，任何人都可解码——不能存储敏感信息
- JWT 签名验证后才能信任 payload
- JWT 一旦签发在过期前无法撤销（无状态），解决方法是加入黑名单机制或缩短过期时间

**bcrypt 的 salt 机制**：
- 每次哈希使用随机 salt，相同密码每次哈希结果不同
- salt 存储在哈希字符串中（`$2b$12$...`），验证时取出使用
- 这防止了彩虹表攻击：攻击者无法预计算所有常见密码的哈希表

## HTTP 缓存

HTTP 缓存通过 Header 协商控制资源生命周期：**强缓存**（Cache-Control/Expires）直接使用本地副本，无需服务器确认；**协商缓存**（ETag/Last-Modified）每次仍需服务器验证。

```javascript
res.set('Cache-Control', 'public, max-age=3600, must-revalidate');
res.set('ETag', 'v1.0.0');
```

认证的本质是**可信身份声明的验证**...

## JWT 结构

JWT 的本质是**自包含的签名字符串**：Header.Payload.Signature 三部分，签名保证内容未被篡改，令牌本身可被任何人解析，但只有服务端能验证。

```javascript
const jwt = require('jsonwebtoken');
jwt.sign({ sub: userId }, secret, { expiresIn: '15m' });
jwt.verify(token, secret);
```

---

## 密码存储

密码存储的本质是**密钥拉伸**：bcrypt 通过 salt 防止彩虹表攻击，通过 cost factor 提高暴力破解成本。Node24+ 推荐 cost factor 12。

```javascript
const bcrypt = require('bcrypt');
bcrypt.hash(password, 12);
bcrypt.compare(password, hash);
```

---

## Session vs Token

Session 的本质是**服务端状态存储**：会话 ID 存在 cookie 中，会话数据存在内存/Redis；Token 的本质是**无状态声明**：所有认证信息编码在令牌本身，服务端无需存储状态。

Session 更适合需要立即撤销权限的场景；Token 适合跨服务认证和移动端场景。

## 参考存根

*展示 JWT 和 bcrypt 的最简可执行证明：*

```javascript
// 依赖：npm install jsonwebtoken bcrypt
const jwt = require('jsonwebtoken');
const bcrypt = require('bcrypt');

const secret = 'test-secret';
const payload = { sub: 'user-123', role: 'admin' };

// JWT 签名与验证
const token = jwt.sign(payload, secret, { expiresIn: '1h' });
console.log('token:', token.length, 'chars');
try {
  const decoded = jwt.verify(token, secret);
  console.log('verified:', decoded);
} catch (e) { console.log('invalid:', e.message); }

// bcrypt 哈希与验证
async function demo() {
  const hash = await bcrypt.hash('password123', 10);
  console.log('hash:', hash);
  const match = await bcrypt.compare('password123', hash);
  console.log('match:', match);
}
demo();
```
