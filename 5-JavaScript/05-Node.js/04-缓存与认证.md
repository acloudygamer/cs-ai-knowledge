# 缓存与认证

## 定义

缓存的本质是**时间局部性原理的应用**：最近访问的数据很可能再次被访问，通过存储计算结果或复制数据副本，减少重复计算或远程请求。

认证的本质是**可信身份声明的验证**：客户端证明持有密钥（密码/TOTP/私钥），或持有令牌（JWT/cookie），服务端验证后建立会话。

## 数学模型

**缓存命中率**：
$$
hit\_rate = \frac{hits}{hits + misses} = \frac{hits}{total\_requests}
$$

**缓存淘汰策略的数学模型**：

- **LRU（Least Recently Used）**：基于访问时间的局部性，淘汰最久未使用的项。

  设访问时间戳为 $t_{last}(item)$ ，淘汰目标： $\arg\max_{item} (now - t_{last}(item))$

- **LFU（Least Frequently Used）**：基于访问频率的局部性，淘汰访问次数最少的项。

  设访问计数为 $count(item)$ ，淘汰目标： $\arg\min_{item} count(item)$

- **Random**：随机淘汰，无额外计算开销，适用于极端场景。

**bcrypt 密钥拉伸成本**：bcrypt 的计算复杂度为 $O(cost \times 2^{cost})$ 。设 cost factor $= r$ ，则每次哈希计算耗时约 $0.1 \times 2^r$ 秒（近似值）。cost=12 时单次计算约 250ms，暴力破解成本显著提高。

| cost | 耗时（近似） | 安全性 |
|------|-------------|--------|
| 10 | ~60ms | 最低容忍 |
| 12 | ~250ms | 推荐（Node.js 24+ 默认） |
| 14 | ~1s | 高安全场景 |

**JWT 签名验证**：JWT 的 Signature 部分使用 HMAC-SHA256（或 RSA）计算，公式为：
$$
\text{Signature} = \text{HMAC-SHA256}(base64url(Header) + "." + base64url(Payload), secret)
$$

验证时重新计算签名并与提供的 Signature 比较，常量时间比较防止时序攻击。

**JWT 的三个部分**：
$$
JWT = base64url(Header) + "." + base64url(Payload) + "." + Signature
$$

Header 和 Payload 是 Base64URL 编码的 JSON，签名是 HMAC 摘要。

## 数据流

<pre>
缓存请求流程：
请求 ──▶ 缓存层 ──▶ 未命中 ──▶ 数据源
              │                      │
              └── 命中 ───────────────┘

认证流程：
注册 ──▶ 盐 + 哈希存储 ──▶ 登录验证
                        │
                     Token/JWT
                        │
                   请求携带 ──▶ 中间件验证 ──▶ 业务逻辑
</pre>

**缓存数据形态变换**：
1. 数据源（原始对象）
2. 序列化（JSON/二进制）
3. 缓存存储（内存/Redis/磁盘）
4. 反序列化（读取时）
5. 返回原始对象

**认证数据流**：
1. 注册：明文密码 → 加盐 → bcrypt 哈希 → 存储
2. 登录：明文密码 → 加盐 → bcrypt 哈希 → 与存储比对
3. 签发 JWT：payload + secret → HMAC 签名 → 组装 token
4. 验证 JWT：解析 token → 重算签名比对 → 检查过期

## 机制

**缓存的物理约束**：
- 缓存空间有限（内存或磁盘），无法无限存储
- 当缓存满时，需要淘汰策略（LRU/LFU/Random）
- 缓存与数据源的一致性：更新数据时需考虑是否更新/失效缓存

**缓存一致性的数学约束**：

设数据源版本为 $V_{source}$ ，缓存版本为 $V_{cache}$ 。一致性要求：

$$
V_{cache} = V_{source} \quad \text{或} \quad V_{cache} \leftarrow \text{失效}
$$

违反此约束会导致**脏读**：读取到过期数据。

**缓存穿透**：大量请求查询不存在的数据，缓存无数据，数据库压力过大。使用布隆过滤器或空值缓存解决。

**缓存击穿**：热点 key 过期瞬间，大量请求同时击穿到数据库。使用互斥锁或热点数据永不过期解决。

**缓存雪崩**：大量缓存同时过期或缓存服务宕机，请求全部打到数据库。使用多级缓存、过期时间随机化、熔断降级解决。

## HTTP 缓存

## 定义

HTTP 缓存通过 Header 协商控制资源生命周期：**强缓存**（Cache-Control/Expires）直接使用本地副本，无需服务器确认；**协商缓存**（ETag/Last-Modified）每次仍需服务器验证。

## 数学模型

**缓存新鲜度**：设资源在 $t_{fetch}$ 时获取，Cache-Control: max-age=$A$ ，则新鲜度截止时间为 $t_{fresh} = t_{fetch} + A$ 。

$$
freshness(t) = \begin{cases}
\text{true} & t < t_{fetch} + A \\
\text{false} & \text{otherwise}
\end{cases}
$$

**ETag 验证**：比较客户端和服务端的 ETag：
$$
match = (ETag_{client} == ETag_{server})
$$

## 机制

**Cache-Control 指令约束**：
- `max-age=N`：缓存有效期为 N 秒
- `no-cache`：每次使用前必须验证（仍会缓存，但使用前需 revalidate）
- `no-store`：禁止缓存
- `private`：只能被浏览器缓存，不能被 CDN 缓存

**Expires vs Cache-Control**：Expires 是 HTTP/1.0 产物，为绝对时间；Cache-Control 是 HTTP/1.1 产物，为相对时间。两者同时存在时，Cache-Control 优先。

**违反约束的后果**：
- 强缓存资源更新后，浏览器因缓存未过期而不获取新版本
- 缓存未设置过期时间且数据源已更新 → 缓存与数据源不一致，产生脏读

## JWT 结构

## 定义

JWT 的本质是**自包含的签名字符串**：Header.Payload.Signature 三部分，签名保证内容未被篡改，令牌本身可被任何人解析，但只有服务端能验证。

## 数学模型

**JWT 签名验证**：
$$
\text{verify}(token, secret) = (\text{compute\_sig}(header.payload, secret) == signature)
$$

常量时间比较防止时序攻击。

**JWT 生命周期**：
```
签发 (sign) ──▶ 传输 ──▶ 验证 ──▶ 业务逻辑
                    │
                 过期检查
                    │
                 权限验证
```

## 机制

**JWT 的设计约束**：
- Header 和 Payload 是 Base64URL 编码的明文，**不加密**——不能存储敏感信息
- 签名验证失败 → 拒绝请求
- JWT 一旦签发在过期前无法撤销（无状态），需黑名单或短过期时间

**时序攻击防护**：签名比较必须使用常量时间比较，防止攻击者通过响应时间推断正确签名。

**JWT 的过期时间策略**：
- Access Token：短过期时间（15min - 1h）
- Refresh Token：长过期时间（7d - 30d），用于获取新的 Access Token

**违反约束的后果**：
- 将敏感信息放入 Payload → 任何人可解码查看
- Access Token 过期时间过长 → 无法及时撤销权限
- 未验证签名 → 攻击者可伪造任意 token

## 密码存储

## 定义

密码存储的本质是**密钥拉伸**：bcrypt 通过 salt 防止彩虹表攻击，通过 cost factor 提高暴力破解成本。

## 数学模型

**bcrypt 密钥拉伸成本**：
$$
T(c) \approx O(2^c)
$$

每增加 1 点 cost，时间翻倍。cost=12 时单次计算约 250ms。

**哈希函数的数学约束**：
- 单向性：给定 $H(p)$ 难以推断 $p$
- salt 随机性： $H_s(p) \neq H_{s'}(p)$ 即使 $p = p'$

## 机制

**salt 的作用**：防止预计算攻击（彩虹表）。攻击者无法预计算所有常见密码的哈希表，因为每次哈希使用不同的 salt。

**bcrypt 哈希格式解析**：
- `$2b：版本标识（2a/2b/2y/2b$）
- `$12：cost factor（计算时间）
- `$`：salt 和 hash 的分隔符

**bcrypt 哈希字符串结构**：
$$
\$2b\$\$12\$\$22chars\_salt + 31chars\_hash = 60chars
$$

- 版本标识（2a/2b/2y）
- cost factor（计算时间参数）
- 22 字符 Base64 编码的 salt（128 位）
- 31 字符 Base64 编码的 hash（184 位）

**Argon2 作为更优选择**：Argon2 在 2015 年获得密码哈希竞赛冠军，比 bcrypt 更能抵抗 GPU 攻击。Node.js 24+ 推荐使用 Argon2。

**违反约束的后果**：
- 使用非加密哈希（MD5/SHA1） → 彩虹表攻击
- salt 过短 → 降低彩虹表攻击难度
- cost 过低 → 暴力破解成本低

## Session vs Token

## 定义

Session 的本质是**服务端状态存储**：会话 ID 存在 cookie 中，会话数据存在内存/Redis；Token 的本质是**无状态声明**：所有认证信息编码在令牌本身，服务端无需存储状态。

## 数学模型

**Session 验证延迟**： $T_{session} = T_{lookup}(session\_id) + T_{verify}$

**Token 验证延迟**： $T_{token} = T_{verify\_signature}$

Token 验证通常更快，因为它不需要查表。

## 对比参照

| 维度 | Session | Token |
|------|---------|-------|
| **存储** | 服务端（内存/Redis） | 客户端 |
| **验证速度** | 需查表 | 仅签名验证 |
| **撤销** | 立即（删除会话） | 困难（需黑名单） |
| **扩展性** | 多服务器需共享存储 | 无状态，易扩展 |

## 机制

**Session 的设计约束**：
- 会话数据存在服务端，安全但增加内存压力
- 多服务器部署时需共享会话存储（Redis）
- Cookie 大小受限（通常 4KB）
- Session ID 必须不可预测（加密随机值）

**Token 的设计约束**：
- 无状态，扩展简单，但无法撤销
- 令牌大小影响请求 Header 体积
- 适合跨服务认证和移动端场景

**选择策略**：需要立即撤销权限（支付、权限变更）用 Session；跨服务认证和无状态验证用 Token。

**CSRF 防护**：Session 使用 Cookie 时需要 CSRF 防护（SameSite Cookie + CSRF Token）；Token 放在 Authorization Header 时天然免疫。
