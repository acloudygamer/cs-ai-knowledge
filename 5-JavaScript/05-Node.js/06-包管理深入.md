# 包管理深入

## 定义

包管理器的本质是**依赖图的解析与构建**：解析 package.json 中的依赖声明，按版本规则（semver）确定具体版本，处理依赖的依赖，最终将产物安装到 node_modules。

## 数学模型

**semver 兼容性判定**：给定版本范围 `^x.y.z`，等价于 $[x.y.z, (x+1).0.0)$ 。即： 。即：
- `^1.2.3` 允许 $[1.2.3, 2.0.0)$ ，等价于 `>=1.2.3 <2.0.0` ，等价于 `>=1.2.3 <2.0.0`
- `~1.2.3` 允许 $[1.2.3, 1.3.0)$ ，等价于 `>=1.2.3 <1.3.0` ，等价于 `>=1.2.3 <1.3.0`

**semver 的数学定义**：
$$
\text{version} = major.minor.patch
$$
$$
\text{increment rules}:
\begin{cases}
major & \text{破坏性变更} \\
minor & \text{新增功能（向后兼容）} \\
patch & \text{修复（向后兼容）}
\end{cases}
$$

**依赖图求解**：依赖图可能包含循环（peerDependencies）和冲突（同一包的不同版本）。包管理器需要生成一个满足所有约束的版本列表，这是一个约束满足问题（CSP）。

**CSP 问题的数学形式**：
$$
\exists v_1, v_2, ..., v_n: \forall \text{dep} \in \text{dependencies}: v_{\text{dep}} \in S_{\text{dep}} \land \forall \text{peer}: v_{\text{peer}} = v_{parent}
$$

其中 $S_{\text{dep}}$ 是满足 semver 约束的版本集合。 是满足 semver 约束的版本集合。

**pnpm 硬链接模型**：pnpm 将全局 store 中的包通过硬链接（而非复制）到项目的 node_modules。这减少了磁盘占用，因为同一版本的包只存储一份。

$$
S_{\text{traditional}} = \sum_{p \in \text{packages}} size(p) \times \text{count}(p, \text{projects})
$$
$$
S_{\text{pnpm}} = \sum_{p \in \text{unique-versions}} size(p)
$$

节省比例： $\frac{S_{\text{traditional}} - S_{\text{pnpm}}}{S_{\text{traditional}}}$ 

## 数据流

<pre>
package.json ──▶ 依赖图解析 ──▶ 版本求解 ──▶ 目录结构
     │                                  │
     └── lock 文件 ─────────────────────┘ 确定性重建
</pre>

**npm 安装流程**：
1. 解析 package.json 中的 dependencies/devDependencies
2. 构建依赖图，遍历获取所有 transitives
3. 对每个包：根据 semver 范围从 registry 下载 tarball
4. 解压到 node_modules（npm 扁平化，pnpm 非扁平化）
5. 生成/更新 lock 文件

**lock 文件的作用**：
- 记录精确版本：每个包的 exact version
- 记录下载地址：registry URL + content hash
- 确保 `npm ci` 重建完全相同的依赖图

## 机制

**npm 依赖扁平化的代价**：
- npm 将所有包提升到 node_modules 根目录，避免嵌套路径
- 这导致同一包的不同版本同时存在（版本 A 在根，B 在某子目录）
- 可能出现"幽灵依赖"：项目未声明某包但可访问（因为被其他包依赖并提升）

**幽灵依赖的数学定义**：
$$
\exists p \in \text{project}: p \notin \text{declared\_deps} \land p \in \text{accessible\_from\_root}
$$

即：包 p 未在项目声明中，但可以被项目访问。

**pnpm 的严格隔离策略**：
- pnpm 不提升子目录中的包，子目录只能访问明确声明的依赖和祖先链中的包
- 这消除了幽灵依赖，但可能导致某些依赖 hoist 不上去的边缘情况
- 使用硬链接而非复制，节省磁盘空间

**pnpm 的目录结构**（pnpm 7.x+）：
```
node_modules/
├── .pnpm/
│   ├── lodash@4.17.21/node_modules/lodash
│   └── express@4.18.2/node_modules/express
└── package-a/ (通过符号链接访问 .pnpm 中的包)
```

**yarn 的确定性策略**：
- yarn 使用 yarn.lock 记录精确版本，而非 npm 的宽松更新策略
- `yarn install` 根据 lock 文件安装，确保所有开发者获得完全相同的依赖树
- `yarn upgrade` 会更新 lock 文件，npm 的 `npm install` 也会智能更新 lock

**exports 字段的设计约束**（Node.js 12+ 支持，Node.js 24+ 全面使用）：
- `exports` 在 Node.js 12+ 支持，是 `main` 字段的演进
- 条件导出确保 ESM 和 CJS 使用不同文件（ESM 不能导入 CJS 的 `.js` 文件）
- `require` 条件在 ESM 文件中不生效（ESM 不支持 `require`）

**exports 的数学语义**：
$$
\text{exports}[condition] = path \implies \text{当 } condition \text{ 满足时，导出 } path
$$

**违反约束的后果**：
- lock 文件与 package.json 不同步（手动修改 package.json 但不重新 install）→ 不确定的依赖树 → 幽灵依赖问题
- 在 exports 条件中使用不支持的条件 → Node.js 抛出 `ERR_PACKAGE_PATH_NOT_EXPORTED`

## npm vs yarn vs pnpm

## 定义

三者的核心差异在于**依赖解析策略**：npm 扁平化（可能存在重复副本）、yarn 同样扁平化但确定性更强、pnpm 坚持非扁平化（严格隔离 + 硬链接）。

## 对比参照

| 特性 | npm | yarn | pnpm |
|------|-----|------|-----|
| **安装速度** | 慢 | 中等 | 快 |
| **node_modules** | 扁平 | 扁平 | 非扁平 |
| **锁文件** | package-lock.json | yarn.lock | pnpm-lock.yaml |
| **幽灵依赖** | 可能 | 可能 | 不可能 |
| **磁盘占用** | 高 | 高 | 低 |

## 机制

**npm 扁平化的问题**：
- 幽灵依赖：未声明的包可能被提升到根目录
- 版本冲突：同一包的不同版本同时存在，占用空间
- 依赖解析不确定性：`npm install` 可能更新 lock 文件中的包版本

**pnpm 隔离的优势**：
- 严格隔离：只有明确声明的依赖才能被访问
- 硬链接：同一版本的包只存储一份
- 节省磁盘：大量项目共享依赖时效果显著

## 依赖版本语义

## 定义

semver 的本质是**API 兼容性承诺**：^1.2.3 表示 "兼容 1.x.x"，~1.2.3 表示 "兼容 1.2.x"。版本号递增规则：major（破坏性变更）/ minor（新增功能）/ patch（修复）。

## 数学模型

**版本范围语义**：
- `^1.2.3` → $[1.2.3, 2.0.0)$ 
- `~1.2.3` → $[1.2.3, 1.3.0)$ 
- `1.2.3` → 精确版本 $[1.2.3, 1.2.3]$ 
- `*` / `latest` → 任意版本

**pre-release 版本排序**：
$$
1.0.0-alpha < 1.0.0-alpha.1 < 1.0.0-beta.1 < 1.0.0
$$

pre-release 版本优先级：数字 < 字母，比较时逐部分对比。

## 机制

**pre-release 的约束**：
- `1.0.0-alpha` 不满足 `>=1.0.0` 的范围
- 只有稳定版满足大多数包管理器的默认范围

**版本范围解析优先级**：
1. 精确版本 `1.2.3`
2. `^1.2.3` 兼容版本
3. `~1.2.3` 补丁兼容版本
4. `>`, `<`, `<=`, `>=` 范围
5. `*` 任意版本

**违反约束的后果**：
- 依赖 `^1.0.0` 但实际安装了 `1.0.0-alpha` → 功能可能缺失
- major 版本升级 → 可能破坏兼容性

## package.json exports

## 定义

exports 字段的本质是**条件导出**：根据导入方式（import/require）和运行环境（node/browser）选择不同的入口文件，实现同一个包支持多种使用方式。

## 数学模型

**条件匹配的优先级**：当多个条件同时满足时，按定义顺序返回第一个匹配的条件。

$$
\text{resolve}(exports, conditions) = \text{first\_match}(conditions, exports)
$$

条件查找沿定义顺序进行，第一个匹配的生效。

## 数据流

<pre>
import "package"          require("package")
      │                        │
      ▼                        ▼
  ESM 条件 ──────────────▶ 读取 exports
      │                        │
      ▼                        ▼
  "import": "./esm/index.js"   "require": "./cjs/index.js"
</pre>

## 机制

**exports 的约束**：
- 路径必须是相对路径或以 `./` 开头
- 条件可以是 `import`、`require`、`default`、`types`、`node` 等
- ESM 不支持 `require` 条件

**Node.js 24+ 中 import conditions 的新行为**：
Node.js 24+ 引入了 `browser`、`worker`、`react-native` 等运行时条件，以及更好的 `module-sync` 支持。

**exports vs main**：
- `main`：单一入口，仅支持一种导出方式
- `exports`：多条件导出，可区分 ESM/CJS/类型

**违反约束的后果**：
- 使用 `require` 在 ESM 文件中导入包 → 错误
- 路径不存在 → `ERR_PACKAGE_PATH_NOT_EXPORTED`

## 锁文件的本质

## 定义

锁文件的本质是**依赖图的快照**：记录每个包的具体版本、下载地址、校验和，确保任何时间 `npm ci` 都能重建完全相同的依赖图。

## 数学模型

**完整性校验**：
$$
hash(\text{lock file content}) = expected hash
$$

任何对 lock 文件的手动修改都可能导致依赖不一致。

**内容寻址存储**：包内容通过 hash 寻址，确保不同来源的同一版本包被正确识别和去重。

## 机制

**lock 文件的约束**：
- 必须与 package.json 同步更新
- `npm ci` 忽略 package.json，仅根据 lock 文件安装
- 大型项目 lock 文件可能非常大

**lock 文件格式差异**：
- npm：`package-lock.json`（JSON 格式）
- yarn：`yarn.lock`（自定义格式，Nib 语法）
- pnpm：`pnpm-lock.yaml`（YAML 格式）

**违反约束的后果**：
- package.json 更新但未重新 install → lock 文件过期
- 手动修改 lock 文件 → `npm ci` 可能失败或安装错误版本

## monorepo 工作区

## 定义

monorepo 的本质是**代码共享与独立版本的平衡**：workspaces 允许同一个代码仓库中的多个包相互依赖，同时各自维护独立的版本号。

## 数学模型

**workspace 协议解析**：
- `workspace:*` → 本地包路径（精确版本）
- `workspace:^` → 本地包（兼容版本）
- `workspace:~` → 本地包（补丁版本）

**依赖解析优先级**：
$$
resolve(r) = \begin{cases}
\text{workspace}(r) & \text{if } r \in \text{workspace\_packages} \\
\text{registry}(r) & \text{otherwise}
\end{cases}
$$

本地包优先于远程包被解析。

## 机制

**workspace 的版本策略**：
- 固定版本：所有包同一版本
- 独立版本：每个包独立版本号
- 固定+独立：固定大版本，独立小版本

**workspace 的约束**：
- 子包相互依赖时，必须先构建被依赖的包
- 循环依赖 → 构建顺序问题
- hoisting 策略决定公共依赖是否提升到根目录

**Node.js 24+ 中 workspaces 支持更好的分组管理**（`dependencies`、`devDependencies`、`peerDependencies`）。

**违反约束的后果**：
- workspace 协议未正确配置 → 包管理器无法找到本地依赖
- 循环依赖 → 构建顺序问题，某些包可能无法正确解析
