# 包管理深入

## 定义

包管理器的本质是**依赖图的解析与构建**：解析 package.json 中的依赖声明，按版本规则（semver）确定具体版本，处理依赖的依赖，最终将产物安装到 node_modules。

## 数学模型

**semver 兼容性判定**：给定版本范围 `^x.y.z`，等价于 $[x.y.z, (x+1).0.0)$。即：
- `^1.2.3` 允许 $[1.2.3, 2.0.0)$，等价于 `>=1.2.3 <2.0.0`
- `~1.2.3` 允许 $[1.2.3, 1.3.0)$，等价于 `>=1.2.3 <1.3.0`

**依赖图求解**：依赖图可能包含循环（peerDependencies）和冲突（同一包的不同版本）。包管理器需要生成一个满足所有约束的版本列表，这是一个约束满足问题（CSP）。

**pnpm 硬链接模型**：pnpm 将全局 store 中的包通过硬链接（而非复制）到项目的 node_modules。这减少了磁盘占用，因为同一版本的包只存储一份。

$$S_{\text{traditional}} = \sum_{p \in \text{packages}} size(p) \times \text{count}(p, \text{projects})$$
$$S_{\text{pnpm}} = \sum_{p \in \text{unique-versions}} size(p)$$

## 数据流

<pre>
package.json ──▶ 依赖图解析 ──▶ 版本求解 ──▶ 目录结构
     │                                  │
     └── lock 文件 ─────────────────────┘ 确定性重建
</pre>

**npm 安装流程**：
1. 解析 package.json 中的 dependencies/devDependencies
2. 构建依赖图，遍历获取所有 transitives
3. 对每个包：根据 semver 范围从 registry 下载 tarball
4. 解压到 node_modules（npm 扁平化，pnpm 非扁平化）
5. 生成/更新 lock 文件

## 机制

**npm 依赖扁平化的代价**：
- npm 将所有包提升到 node_modules 根目录，避免嵌套路径
- 这导致同一包的不同版本同时存在（版本 A 在根，B 在某子目录）
- 可能出现"幽灵依赖"：项目未声明某包但可访问（因为被其他包依赖并提升）

**pnpm 的严格隔离策略**：
- pnpm 不提升子目录中的包，子目录只能访问明确声明的依赖和祖先链中的包
- 这消除了幽灵依赖，但可能导致某些依赖 hoist 不上去的边缘情况
- 使用硬链接而非复制，节省磁盘空间

**yarn 的确定性策略**：
- yarn 使用 yarn.lock 记录精确版本，而非 npm 的宽松更新策略
- `yarn install` 根据 lock 文件安装，确保所有开发者获得完全相同的依赖树
- `yarn upgrade` 会更新 lock 文件，npm 的 `npm install` 也会智能更新 lock

**exports 字段的设计约束**：
- `exports` 在 Node.js 12+ 支持，是 `main` 字段的演进
- 条件导出确保 ESM 和 CJS 使用不同文件（ESM 不能导入 CJS 的 `.js` 文件）
- `require` 条件在 ESM 文件中不生效（ESM 不支持 `require`）

**违反约束的后果**：
- lock 文件与 package.json 不同步（手动修改 package.json 但不重新 install）→ 不确定的依赖树 → 幽灵依赖问题
- 在 exports 条件中使用不支持的条件 → Node.js 抛出 `ERR_PACKAGE_PATH_NOT_EXPORTED`

## npm vs yarn vs pnpm

三者的核心差异在于**依赖解析策略**：npm 扁平化（可能存在重复副本）、yarn 同样扁平化但确定性更强、pnpm 坚持非扁平化（严格隔离 + 硬链接）。

| 特性 | npm | yarn | pnpm |
|------|-----|------|------|
| 安装速度 | 慢 | 中等 | 快 |
| node_modules | 扁平 | 扁平 | 非扁平 |
| 锁文件 | package-lock.json | yarn.lock | pnpm-lock.yaml |

## 依赖版本语义

semver 的本质是**API 兼容性承诺**：^1.2.3 表示 "兼容 1.x.x"，~1.2.3 表示 "兼容 1.2.x"。版本号递增规则：major（破坏性变更）/ minor（新增功能）/ patch（修复）。

```json
{ "lodash": "^4.17.21" }
```

---

## package.json exports

exports 字段的本质是**条件导出**：根据导入方式（import/require）和运行环境（node/browser）选择不同的入口文件，实现同一个包支持多种使用方式。

```json
{
  "exports": {
    ".": {
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs"
    }
  }
}
```

---

## 锁文件的本质

锁文件的本质是**依赖图的快照**：记录每个包的具体版本、下载地址、校验和，确保任何时间 `npm ci` 都能重建完全相同的依赖图。

---

## monorepo 工作区

monorepo 的本质是**代码共享与独立版本的平衡**：workspaces 允许同一个代码仓库中的多个包相互依赖，同时各自维护独立的版本号。

```yaml
# pnpm-workspace.yaml
packages:
  - 'packages/*'
```

## 参考存根

*展示 semver 范围解析的最简可执行证明：*

```javascript
// 执行：node app.js
// 依赖：npm install semver
const semver = require('semver');

console.log('^1.2.3 satisfies:', semver.satisfies('1.9.0', '^1.2.3')); // true
console.log('^1.2.3 satisfies:', semver.satisfies('2.0.0', '^1.2.3')); // false
console.log('~1.2.3 satisfies:', semver.satisfies('1.3.0', '~1.2.3')); // true
console.log('~1.2.3 satisfies:', semver.satisfies('1.2.3:', '~1.2.3')); // true

// exports 条件检查（Node.js 12+）
// node --experimental-conditional-exports app.js
import('./dist/index.mjs').then(m => console.log('esm ok')).catch(() => {
  import('./dist/index.cjs').then(m => console.log('cjs ok'));
});
```
