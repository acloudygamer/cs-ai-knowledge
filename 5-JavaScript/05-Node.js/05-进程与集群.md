# 进程与集群

## 定义

进程是**资源分配的最小单位**：每个进程拥有独立的内存空间、文件描述符、CPU 上下文。Node.js 单进程利用事件循环在单线程中处理并发，但 CPU 密集型任务会阻塞事件循环。

集群的本质是**水平扩展**：多个进程监听同一端口，操作系统负载均衡器（SO_REUSEPORT）将请求分发到不同 worker，充分利用多核 CPU。

## 数学模型

**进程创建成本**：fork 系统调用的直接开销为 $O(1)$，但写时复制（Copy-on-Write）意味着子进程在修改内存前与父进程共享全部内存页。实际内存成本取决于子进程的修改量。

**写时复制（COW）的数学模型**：
$$
M_{shared} = \min(M_{parent}, M_{child}) \quad \text{（修改前）}
$$
$$
M_{total} = M_{parent} + M_{child\_modified} \quad \text{（修改后）}
$$

其中 $M_{child\_modified}$ 是子进程修改的页面数 × 页大小。

**集群负载均衡**：设 $n$ 个 worker 处理请求率 $\lambda$（每秒请求），每个 worker 处理能力为 $\mu$（每秒请求）。系统稳定的条件为 $n \times \mu > \lambda$。超出此限制时，请求排队或被拒绝。

$$
\rho = \frac{\lambda}{n \times \mu} \quad \text{（利用率）}
$$

当 $\rho > 1$ 时，系统过载，请求开始堆积。

**libuv 线程池**：用于处理无法异步化的系统调用（文件 I/O、DNS 查询、加密等），Node.js 20+ 默认为 **1024** 线程（可通过 `UV_THREADPOOL_SIZE` 环境变量调整，上限 1024）。

$$
T_{threadpool} = \min(t_{cpu-bound}, n_{threads} \times t_{io-op})
$$

当线程池饱和时，后续 I/O 操作需等待。

## 数据流

<pre>
独立进程                              集群模式
+-----------+                       +-------------------+
|  V8       |                       |  Master           |
|  Event    |                       |    ├── Worker 1   |
|  Loop     |                       |    ├── Worker 2   |
|  (单线程)  |                       |    └── Worker N   |
+-----------+                       +-------------------+
                                        │
请求处理：独立进程(单核)    负载均衡 ─▶  多 worker(多核)
</pre>

**父子进程通信（IPC）**：
```
parent ──▶ pipe/socket ◀── child
          message (序列化后)
```

消息通过 `process.send()`/`child.send()` 发送，内部序列化为 JSON。

## 机制

**为什么 Node.js 选择单线程**：
- 多线程编程的复杂性（竞态条件、锁、死锁）在网络 I/O 场景下收益有限
- V8 的 GC 暂停在多线程环境下更难控制
- 单线程 + 事件循环的模型在 I/O 密集型场景下效率极高（无需线程切换开销）

**CPU 密集型任务为什么阻塞事件循环**：
- 事件循环在单一线程执行，CPU 密集型计算独占该线程
- 其他请求的回调无法被执行，被迫等待
- 解决：Worker Threads（独立 V8 实例，有自己的事件循环）或将任务分片（使用 `setImmediate` 让出时间片）

**Worker Threads 的内存模型**：
$$
M_{total} = M_{main} + \sum_{i=1}^{n} M_{worker_i}
$$

每个 Worker 有独立的 V8 实例、独立的堆内存、独立的事件循环。线程间通过 `MessageChannel` 传递数据（结构化克隆，非共享内存）。

**SO_REUSEPORT 的作用**：
- 多个进程可以同时 bind 同一端口
- 内核级别负载均衡（通常基于连接哈希）
- 避免单进程 accept 的惊群效应（多个进程同时唤醒但只有一个处理连接）

**惊群效应（Thundering Herd）**：当多个进程阻塞在 accept() 时，若有新连接到达，所有进程都被唤醒，但只有一个能处理连接，其余重新睡眠。SO_REUSEPORT 通过让每个进程独立竞争，减小惊群影响。

**违反约束的后果**：
- 在没有集群的情况下部署到多核 CPU → 只有单个核心被使用，其他核心空闲
- Worker 进程崩溃 → 若未做好进程管理，该端口的请求无人处理
- CPU 密集型任务阻塞事件循环 → 所有请求排队，延迟激增

## 子进程与 IPC

## 定义

子进程诞生的本质是**操作系统进程树**：spawn/fork/exec 创建子进程，通过 pipe 或 IPC 通道实现父子通信。fork 复制父进程内存（写时复制），exec 用新程序替换子进程镜像。

## 数学模型

**fork 的返回值语义**：
- 父进程中：返回子进程 PID（正值）
- 子进程中：返回 0

**COW 内存共享**：
- fork 后父子进程共享全部内存页（读）
- 任一方写入时，触发页面复制（写时复制）
- 这使得 fork 的实际成本远低于完整内存复制

## 数据流

<pre>
fork() 调用
     │
     ▼
复制进程描述符（PID、文件描述符、寄存器）
     │
     ▼
父子进程各自执行（写时复制）
     │
     ▼
父子进程通过 IPC 通信（pipe / socket）
</pre>

## 机制

**IPC 的序列化约束**：父子进程间通过 `process.send()`/`child.send()` 传递的消息需要序列化（JSON.stringify）和反序列化（JSON.parse）。大型数据传递的成本与数据大小成正比。

**exec 的本质**：在子进程中用新程序镜像替换现有代码。原有内存被完全丢弃。

**spawn vs fork vs exec**：
- `spawn`：创建新进程，不复用父进程
- `fork`：复制父进程，可选择是否加载新程序
- `exec`：在子进程中执行命令，替换进程镜像

**违反约束的后果**：
- 大型 JSON 序列化/反序列化导致 IPC 延迟
- 子进程崩溃未处理 → 僵尸进程（需 SIGCHLD 处理）
- fork 大量子进程 → 内存迅速耗尽（COW 未及时触发时）

## 集群的本质

## 定义

集群的本质是**水平扩展**：多个进程监听同一端口，操作系统负载均衡器（SO_REUSEPORT）将请求分发到不同 worker，充分利用多核 CPU。

## 数学模型

**负载均衡策略**：
- **轮询（Round Robin）**：依次分发到每个 worker
- **随机**：随机选择 worker
- **基于连接哈希**：同一客户端 IP 路由到同一 worker

$$
worker_i = hash(client\_ip) \mod n
$$

## 机制

**集群调度策略约束**：
- 轮询不考虑 worker 实际负载，可能不均衡
- IP 哈希保证会话粘性，但负载可能不均
- 现代负载均衡器支持最少连接数策略

**进程管理与故障转移**：
- Master 监控 worker 心跳，崩溃后重启
- Zero-downtime 重启：先启动新 worker，再关闭旧 worker

**worker 退出时的连接处理**：正在处理中的请求会被强制终止，客户端收到连接错误。优雅退出需要等待现有请求处理完毕。

**违反约束的后果**：
- 所有 worker 崩溃 → 服务中断
- Master 崩溃 → 无 worker 管理
- worker 过载但未被负载均衡 → 单点过载

## 流的本质

## 定义

流的本质是**数据分块处理**：不必将整个文件/请求加载到内存，通过 pipe 连接读写阶段，实现背压控制和内存效率最大化。

## 数学模型

**背压信号传播**：
$$
write\_available = buffer\_size - current\_buffer\_fill
$$
当 $write\_available < 0$ 时，`write()` 返回 `false`，触发背压。

**管道吞吐量**：
$$
throughput = \min(throughput_{readable}, throughput_{writable})
$$

管道吞吐量受最慢环节限制。

## 数据流

<pre>
Readable ──▶ Transform ──▶ Writable
   │              │              │
   └── 读取数据   └── 转换数据   └── 写入数据
                  │
                  └── 背压信号向上游传播
</pre>

**流的数据形态**：
- Readable：数据生产者，可读端
- Writable：数据消费者，可写端
- Duplex：同时可读可写
- Transform：在读写之间转换数据

## 机制

**流的类型约束**：
| 类型 | 方向 | 背压 |
|------|------|------|
| Readable | 数据源 | 被 pipe 控制 |
| Writable | 数据目标 | 发出 backpressure 信号 |
| Duplex | 双向 | 双向背压 |
| Transform | 转换 | 继承读写双向 |

**pipeline vs pipe**：
- `pipeline` 返回 Promise，支持错误回调，且自动解绑
- `pipe` 不返回 Promise，错误处理不完善，主动销毁流时可能泄露

**流的缓冲约束**：流内部有缓冲区，当写入速度快于读取速度时，缓冲区积压。缓冲区满后 write() 返回 false。

**违反约束的后果**：
- 不处理背压 → 内存溢出
- pipeline 错误未处理 → 流挂起，资源泄露
- 手动销毁流时不清理 pipe → 内存泄漏

## Worker Threads

## 定义

Worker Threads 的本质是**独立 V8 实例 + 独立事件循环**：与主线程共享进程资源（文件描述器、TCP 连接），但不共享内存，通过 MessageChannel 传递数据。

## 数学模型

**Worker 内存开销**：
$$
M_{worker} = M_{v8\_heap} + M_{c\_++\_heap} + M_{stack}
$$

每个 Worker 至少需要 ~4MB V8 堆内存。

**线程间通信成本**：
$$
T_{transfer} = T_{serialize} + T_{copy} + T_{deserialize}
$$

结构化克隆避免了共享内存的锁竞争，但序列化成本不可避免。

## 数据流

<pre>
Main Thread                          Worker Thread
+-----------+                        +-----------+
|  V8 Heap  |                        |  V8 Heap  |
|  Event    |◀── MessageChannel ───▶|  Event    |
|  Loop     |   (结构化克隆数据)     |  Loop     |
+-----------+                        +-----------+
</pre>

**MessageChannel 工作机制**：
- 创建时生成两个关联的端口（port1, port2）
- 一端发送的数据在另一端通过事件触发接收
- 数据经过结构化克隆算法序列化

## 机制

**Worker 的设计约束**：
- 适用于 CPU 密集型任务（计算、加密、压缩）
- 不适用于 I/O 密集型任务（已有事件循环）
- 数据传递需要序列化，不能直接共享内存

**MessageChannel 的本质**：一对全双工通道，一端发送的数据在另一端可立即接收（通过事件循环）。

**SharedArrayBuffer**：允许跨线程共享内存，绕过序列化，但需要手动同步（Atomics）。

**违反约束的后果**：
- 在 Worker 中执行 I/O 密集任务 → 浪费独立 V8 实例的资源
- 传递大型数据 → 序列化成本高，延迟大
- 共享内存无锁访问 → 数据竞争，未定义行为
