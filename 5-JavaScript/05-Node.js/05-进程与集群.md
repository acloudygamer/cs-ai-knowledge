# 进程与集群

## 定义

进程是**资源分配的最小单位**：每个进程拥有独立的内存空间、文件描述符、CPU 上下文。Node.js 单进程利用事件循环在单线程中处理并发，但 CPU 密集型任务会阻塞事件循环。

集群的本质是**水平扩展**：多个进程监听同一端口，操作系统负载均衡器（SO_REUSEPORT）将请求分发到不同 worker，充分利用多核 CPU。

## 数学模型

**进程创建成本**：fork 系统调用的直接开销为 $O(1)$，但写时复制（Copy-on-Write）意味着子进程在修改内存前与父进程共享全部内存页。实际内存成本取决于子进程的修改量。

**写时复制（COW）的数学模型**：
$$
M_{shared} = \min(M_{parent}, M_{child}) \quad \text{（修改前）}
$$
$$
M_{total} = M_{parent} + M_{child\_modified} \quad \text{（修改后）}
$$

其中 $M_{child\_modified}$ 是子进程修改的页面数 × 页大小。

**集群负载均衡**：设 $n$ 个 worker 处理请求率 $\lambda$（每秒请求），每个 worker 处理能力为 $\mu$（每秒请求）。系统稳定的条件为 $n \times \mu > \lambda$。超出此限制时，请求排队或被拒绝。

$$
\rho = \frac{\lambda}{n \times \mu} \quad \text{（利用率）}
$$

当 $\rho > 1$ 时，系统过载，请求开始堆积。

**libuv 线程池**：用于处理无法异步化的系统调用（文件 I/O、 DNS 查询、加密等），默认 4 线程，可通过 `UV_THREADPOOL_SIZE` 环境变量调整（最大 1024）。

$$
T_{threadpool} = \min(t_{cpu-bound}, n_{threads} \times t_{io-op})
$$

当线程池饱和时，后续 I/O 操作需等待。

**IPC 数据序列化**：父子进程间通过 `process.send()` 传递的消息需要序列化（JSON.stringify）和反序列化（JSON.parse）。大型数据传递的成本与数据大小成正比。

## 机制

**为什么 Node.js 选择单线程**：
- 多线程编程的复杂性（竞态条件、锁、死锁）在网络 I/O 场景下收益有限
- V8 的 GC 暂停在多线程环境下更难控制
- 单线程 + 事件循环的模型在 I/O 密集型场景下效率极高（无需线程切换开销）

**CPU 密集型任务为什么阻塞事件循环**：
- 事件循环在单一线程执行，CPU 密集型计算独占该线程
- 其他请求的回调无法被执行，被迫等待
- 解决：Worker Threads（独立 V8 实例，有自己的事件循环）或将任务分片（使用 `setImmediate` 让出时间片）

**Worker Threads 的内存模型**：
$$
M_{total} = M_{main} + \sum_{i=1}^{n} M_{worker_i}
$$

每个 Worker 有独立的 V8 实例、独立的堆内存、独立的事件循环。线程间通过 `MessageChannel` 传递数据（结构化克隆，非共享内存）。

**子进程 IPC 的实现**：
- Unix 系统使用 Unix Domain Socket 或匿名管道
- Windows 使用命名管道
- 消息通过 `process.send()`/`child.send()` 发送，内部序列化为 JSON

**SO_REUSEPORT 的作用**：
- 多个进程可以同时 bind 同一端口
- 内核级别负载均衡（通常基于连接哈希）
- 避免单进程 accept 的惊群效应（多个进程同时唤醒但只有一个处理连接）

**惊群效应（Thundering Herd）**：当多个进程阻塞在 accept() 时，若有新连接到达，所有进程都被唤醒，但只有一个能处理连接，其余重新睡眠。SO_REUSEPORT 通过让每个进程独立竞争，减小惊群影响。

**违反约束的后果**：
- 在没有集群的情况下部署到多核 CPU → 只有单个核心被使用，其他核心空闲
- Worker 进程崩溃 → 若未做好进程管理，该端口的请求无人处理

## 子进程与 IPC

子进程诞生的本质是**操作系统进程树**：spawn/fork/exec 创建子进程，通过 pipe 或 IPC 通道实现父子通信。fork 复制父进程内存（写时复制），exec 用新程序替换子进程镜像。

```javascript
const { fork } = require('child_process');
const child = fork('./worker.js');
child.send({ cmd: 'compute', data: 42 });
child.on('message', (m) => console.log('result:', m));
```

**fork 的数学语义**：
- fork 返回值：父进程中返回子进程 PID，子进程中返回 0
- 父子进程共享父进程 fork 前的内存（COW 机制）
- 父子进程独立执行，独立修改内存（写入时复制）

## 集群的本质

集群的本质是**水平扩展**：多个进程监听同一端口，操作系统负载均衡器（SO_REUSEPORT）将请求分发到不同 worker，充分利用多核 CPU。

```javascript
const cluster = require('cluster');
if (cluster.isMaster) {
  cluster.fork();
  cluster.fork();
} else {
  http.createServer((req, res) => res.end('ok')).listen(3000);
}
```

**集群调度策略**：
- **轮询（Round Robin）**：依次分发到每个 worker（默认）
- **随机**：随机选择 worker
- **基于负载**：选择当前负载最轻的 worker

## 流的本质

流的本质是**数据分块处理**：不必将整个文件/请求加载到内存，通过 pipe 连接读写阶段，实现背压控制和内存效率最大化。

**流的类型系统**：
| 类型 | 方向 | 背压 |
|------|------|------|
| Readable | 数据源 | 被 pipe 控制 |
| Writable | 数据目标 | 发出 backpressure 信号 |
| Duplex | 双向 | 双向背压 |
| Transform | 转换 | 继承读写双向 |

```javascript
const { pipeline } = require('stream/promises');
const fs = require('fs');
pipeline(
  fs.createReadStream('bigfile.txt'),
  new Transform({ transform: (c, _, cb) => cb(null, c.toString().toUpperCase()) }),
  fs.createWriteStream('out.txt'),
  () => {}
);
```

**pipeline vs pipe**：pipeline 返回 Promise，支持错误回调，且自动处理背压。pipe 不返回 Promise，错误处理不完善。
