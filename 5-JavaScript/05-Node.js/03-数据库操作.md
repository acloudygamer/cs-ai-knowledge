# Node.js 数据库操作

## 定义

数据库在 Node.js 中的本质是**进程外持久化存储的客户端抽象**。无论 SQL 还是 NoSQL，数据库暴露的是键值或文档的读写接口，数据本身驻留在独立进程（数据库服务）中，通过网络协议（TCP/Unix Socket）与 Node.js 进程通信。

## 数学模型

**连接池的队列模型**：设池大小为 $N$，并发请求数为 $R$。当 $R \le N$ 时，所有请求立即分配连接；当 $R > N$ 时，第 $N+1$ 至 $R$ 个请求在队列中等待可用连接。

平均响应时间 $T$ 随并发增加而增长，瓶颈在 $N$。合理的池大小应等于数据库服务的最大连接数限制。

$$
T_{avg} = \frac{R_{waiting} \times T_{wait} + R_{executing} \times T_{exec}}{R_{total}}
$$

其中 $R_{waiting}$ 为等待请求数，$T_{wait}$ 为平均等待时间，$R_{executing}$ 为执行中请求数，$T_{exec}$ 为平均执行时间。

**连接利用率与饱和度**：
$$
\rho = \frac{R_{active}}{N}
$$

当 $\rho \approx 1$ 时，池饱和，新请求必须等待。

**Redis 操作的原子性**：Redis 单命令执行是原子的，但复合操作（如先 GET 再 SET）不是。Lua 脚本在 Redis 中原子执行，因为 Redis 将整个 Lua 脚本作为单一命令执行。

$$
T_{\text{Lua script}} = T_{\text{eval}} = \text{单个 Redis 命令耗时}
$$

**Redis 内存复杂度**：
- 字符串操作：$\mathcal{O}(1)$（GET/SET）到 $\mathcal{O}(N)$（MGET/MSET）
- 哈希操作：$\mathcal{O}(1)$（单个字段）到 $\mathcal{O}(N)$（HGETALL）
- 有序集合：$\mathcal{O}(\log N)$（ZADD/ZRANGEBYSCORE）

## 数据流

<pre>
SQL: Query ──▶ TCP ──▶ 数据库进程 ──▶ B+ Tree 查找 ──▶ 磁盘页 ──▶ 结果集
                                                              │
NoSQL: Write ──▶ TCP ──▶ 数据库进程 ──▶ WAL (顺序写) ──▶ MemTable ──▶ SSTable
               │
               ▼
        Node.js 驱动反序列化
</pre>

**数据库查询的数据形态变换**：
1. Node.js 发送 SQL/NoSQL 协议消息（TCP 字节流）
2. 数据库进程解析消息、执行查询（可能涉及磁盘 I/O）
3. 结果集通过网络返回（序列化字节流）
4. Node.js 驱动将字节流反序列化为 JS 对象/数组

**连接生命周期状态机**：
```
空闲 ──▶ 借出 ──▶ 执行中 ──▶ 归还
  │         │           │         │
  └─ 超时 ──┴─ 错误 ────┴─ 重连 ──┘
```

## 机制

**为什么 SQL 数据库用 B+ 树**：B+ 树的所有数据节点都在同一深度，确保任意查询的磁盘 I/O 次数相近（$\log_{fanout} N$）。范围查询（如 `BETWEEN`）在 B+ 树中可以顺序遍历叶子节点，开销最低。

**B+ 树的数学性质**：
- 设 $N$ 为索引项总数，$fanout$ 为节点分支数
- 树高 $h \approx \lceil \log_{fanout} N \rceil$
- 查询复杂度 $\mathcal{O}(h) = \mathcal{O}(\log N)$
- 磁盘 I/O 次数等于树高（每个节点一次 I/O）

**为什么 NoSQL 用 LSM 树**：LSM 树的写入是顺序的（先写 WAL，再写 MemTable，定期合并为 SSTable），适合高写入场景。代价是读取需要检查多层结构（MemTable → 多个 SSTable），读性能低于 B+ 树。

**LSM 树的写放大问题**：每次写入实际写入多次（WAL + MemTable + SSTable），写放大系数：

$$
W_{amp} = \frac{\text{实际写入量}}{\text{逻辑写入量}}
$$

典型值：3-10 倍，取决于合并策略和数据特征。

**连接池的约束**：
- 每个数据库连接占用服务器资源（内存、文件描述符）
- 若池大小超过数据库最大连接数，部分连接会被拒绝
- 连接长时间空闲会被数据库服务端断开（timeout），客户端需要重连机制

**分布式锁的设计约束**：
- `SET NX EX` 保证加锁和设置过期时间是原子操作，防止死锁（锁持有者崩溃后锁无法释放）
- 释放锁时必须校验值（Lua 脚本），否则可能误删他人持有的锁
- 过期时间应大于正常操作时长，防止误删

**违反约束的后果**：
- 分布式锁过期时间设太短 → 业务还未完成锁已释放，其他客户端获取同一把锁 → 数据竞争
- 连接池耗尽 → 新请求排队或报错；数据库服务可能拒绝新连接
- 连接泄漏（未归还）→ 连接池逐渐耗尽，最终无法服务

## SQL 数据库连接

## 定义

连接池的本质是**有限资源的复用**：预先建立 N 个连接，请求借出、用完归还，避免频繁创建/销毁连接的开销，同时限制最大并发数保护数据库。

## 数学模型

连接利用率随并发增长：

$$
\rho = \frac{R_{active}}{N}
$$

当 $\rho \approx 1$ 时，池饱和，新请求必须等待。

**等待时间建模**：设请求到达率为 $\lambda$，服务率为 $\mu$（每个连接的查询处理速度）。当 $\rho = \lambda / (N \mu) < 1$ 时，系统稳定。

## 机制

**连接获取的约束**：
- 连接池有最大等待时间（通常可配置）
- 等待超时后请求被拒绝或报错
- 长时间空闲的连接可能被服务端关闭

**连接生命周期管理**：
- 借出：检查连接有效性，超时/错误则重建
- 归还：放回池中供复用
- 定期清理：移除死连接

**违反约束的后果**：
- 连接池耗尽且等待超时 → 请求失败，返回连接超时错误
- 持有连接但忘记归还 → 连接泄漏，最终池耗尽
- 池大小远大于数据库限制 → 数据库拒绝部分连接

## MongoDB 文档模型

## 定义

MongoDB 的本质是**无 Schema 的 BSON 文档集合**：文档自行包含完整结构，通过 MMAPv1/WiredTiger 引擎映射到磁盘，支持嵌套文档减少 JOIN 操作。

## 数学模型

**WiredTiger 的数学模型**：
- 默认压缩率约 40-60%（取决于数据特征）
- 文档级锁，支持更高并发写入
- Cache size 默认为 `(RAM - 1GB)` 的 60%

**BSON 编码效率**：BSON 是 JSON 的二进制扩展，支持更多数据类型（Date、Binary、ObjectId）。字符串在 BSON 中使用 C 风格长度前缀，而非 JSON 的引号边界。

## 机制

**嵌套文档的设计约束**：
- MongoDB 单文档限制 16MB（BSON 规范）
- 嵌套层级过深会导致查询和索引困难
- 适合"对象内聚"场景，不适合需要跨文档 JOIN 的场景

**索引策略**：
- `_id` 字段自动创建唯一索引
- 嵌套字段索引：`a.b.c` 语法
- 多键索引：数组字段自动创建多键索引

**违反约束的后果**：
- 文档超过 16MB → 写入错误
- 过度嵌套 → 查询性能劣化，索引无法覆盖
- 不当索引 → 写入变慢（维护索引开销）

## Redis 数据结构

## 定义

Redis 的本质是**内存中的持久化字典**：每种数据结构（string/hash/list/set/zset）都有对应的编码实现（int/embstr/hashtable/ziplist/quicklist），在内存效率和操作复杂度间动态选择。

## 数学模型

**编码选择策略**（Redis 7.x 行为）：

| 数据结构 | 小值编码 | 大值编码 | 切换阈值 |
|----------|----------|----------|----------|
| String | int | raw | 512 bytes |
| Hash | ziplist | hashtable | 512 fields |
| List | ziplist | quicklist | 512 items |
| Set | intset | hashtable | 512 members |

**编码切换的数学约束**：ziplist 使用连续内存，查找复杂度 $\mathcal{O}(N)$；hashtable 使用哈希表，查找复杂度 $\mathcal{O}(1)$。切换阈值保证小数据量使用紧凑编码节省内存，大数据量使用高效查找。

**ziplist 内存布局**：
```
+------+---------+-------+-------+-------+---------+---------+
| zlbytes | zltail | zllen | entry1 | entry2 | ... | zlend |
+------+---------+-------+-------+-------+---------+---------+
```
- `zlbytes`：总字节数（4 字节）
- `zltail`：到尾部的偏移量（快速尾部操作）
- `zllen`：元素数量
- `zlend`：结束标记（0xFF）

## 机制

**ziplist 的内存效率**：ziplist 将所有元素连续存储，无指针开销。小数据量时内存占用远低于 hashtable。但插入/删除复杂度为 $\mathcal{O}(N)$，因为需要移动后续元素。

**快速列表（quicklist）**：quicklist 是 ziplist 的双向链表，每个节点是一个 ziplist。这在插入性能和内存效率间取得平衡：
- 两端操作：$\mathcal{O}(1)$（ziplist 头部/尾部）
- 中间操作：$\mathcal{O}(N)$（可能需跨 ziplist 边界）

**违反约束的后果**：
- 哈希字段数超过阈值但数据量仍小时 → 编码切换导致内存占用增加
- List 元素过多 → quicklist 节点过多，遍历性能下降
- 大 value 使用 ziplist 编码 → 内存重分配成本高

## 分布式锁

## 定义

分布式锁的本质是**外部协调者的原子性承诺**：利用 Redis SET NX EX 原子操作获取锁，Lua 脚本保证释放锁时的值校验，防止误删他人持有的锁。

## 数学模型

**SET NX EX 的原子性**：
$$
\text{SET } k \text{ } v \text{ NX EX } t \equiv \text{if } \not\exists k \text{ then } k \leftarrow (v, t) \text{ else fail}
$$

这是 Redis 最基本的原子操作之一，由 Redis 单线程保证。

**锁的公平性**：Redis 的 SET NX 不保证 FIFO 顺序，多个客户端竞争时谁先获得锁取决于 Redis 的处理顺序，不保证先到先得。

## 机制

**获取锁的约束**：
- 值必须是唯一的（通常用 UUID 或时间戳+随机数）
- 过期时间必须大于正常操作时长
- 必须检查返回值确认获取成功

**释放锁的约束**：
- 必须原子地检查值是否匹配 + 删除
- 检查和删除必须是同一个操作（用 Lua 脚本保证）

**释放锁的 Lua 脚本**：
```lua
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

**锁续期问题**：若业务执行时间超过锁过期时间，锁被自动释放，但业务仍在执行。此时其他客户端获取同一把锁，导致数据竞争。

**红锁（Redlock）**：在多个独立 Redis 实例上加锁，降低单点故障风险。但增加了复杂度和延迟。

**违反约束的后果**：
- 锁值非唯一 → 可能释放他人持有的锁
- 过期时间太短 → 业务未完成锁已释放，数据竞争
- 非原子释放 → 可能删除他人刚获取的锁
