# 代码检查工具

## 定义

代码检查工具通过静态分析在代码**执行前**发现错误、漏洞和风格问题。区别于格式化工具，代码检查**不修改代码**，只报告问题。按分析深度分为：

- **Linter**：基于词法/语法分析的规则匹配（代码风格、未使用变量）
- **类型检查器**：基于类型注解一致性的深度分析（参数类型不匹配、返回值类型错误）

**归约视角**：代码检查是**在执行前发现缺陷**的静态分析过程，其核心约束是**不执行代码**——通过抽象解释或符号执行在代码的语法结构上推理可能的运行时错误。

## 数学模型

### 规则匹配的召回率与精确率

设规则集为 $R$，代码问题空间为 $P$（所有实际存在的问题）。工具检出问题为 $D$：

$$D = \bigcup_{r \in R} \text{match}(r, \text{AST})$$

- **召回率**（Recall）：$|D \cap P| / |P|$——漏检率
- **精确率**（Precision）：$|D \cap P| / |D|$——误报率

规则越多越严格，召回率上升但精确率下降。Ruff 选择高精确率（规则少但误报低），Pylint 选择高召回率（规则多但慢且可能有误报）。

**F1 分数**：精确率和召回率的调和平均，$F_1 = 2 \cdot \frac{\text{Precision} \cdot \text{Recall}}{\text{Precision} + \text{Recall}}$，综合衡量工具性能。

### 类型检查的约束满足

Python 类型注解构成约束系统。设函数签名：

```python
def f(x: int, y: str) -> bool: ...
```

类型检查器验证调用 `f(a, b)` 时，$a \in \text{int}$，$b \in \text{str}$，返回值 $r \in \text{bool}$。若约束不满足，报类型错误。

**约束求解的本质**：类型检查是**一阶谓词逻辑的模型检测**——给定函数签名（公理）和调用（查询），验证查询是否满足公理约束。这与 SAT 问题的复杂度等级相关，但实际中类型系统被设计为高效可判定。

渐进式类型系统的三档严格度：

| 模式 | 行为 |
|------|------|
| 无类型注解 | 完全不检查 |
| 基础模式（checked） | 仅检查有注解的函数调用 |
| 严格模式（strict） | 注解覆盖处必须匹配，未注解处报错 |

严格程度越高，类型安全越强，但迁移成本越高。

### Mypy 的流敏感类型推断

Mypy 使用**流敏感的类型推断**，对同一变量在不同分支中的类型分别追踪：

$$T_{\text{var}}(p) = \begin{cases} T_{\text{init}} & p = \text{初始化点} \\ T_1 & p \in \text{分支 1} \\ T_2 & p \in \text{分支 2} \\ T_1 \cup T_2 & p = \text{分支合并点} \end{cases}$$

其中 $T_1 \cup T_2$ 是联合类型。

**流敏感**意味着同一变量在不同位置可能有不同类型，与**类型注解的全局推断**形成对比。

**分支合并的类型交集**：若分支 1 返回 `int`，分支 2 返回 `str`，合并后类型为 `int | str`（联合类型）。这是流敏感推断的核心——类型随控制流路径动态扩展。

### 类型检查的停机性

类型检查算法必须对任意输入在有限时间内终止。这是通过**类型系统的设计**保证的：

- 类型注解是有穷的（类、函数签名、泛型参数）
- 泛型实例化有深度限制（防止无限递归展开）
- 联合类型数量有界（防止无限叉乘）

**不可判定性边界**：若 Python 支持任意递归类型（如 $T = \text{list}[T]$），则统一化算法可能不终止。现代 Python 类型系统通过禁止此类自引用来保证可判定性。

## 数据流

```
源代码（文本）
    │
    ▼
词法/语法分析 ──▶ AST
    │  Linter: 扫描特定模式（未使用变量、shadowing）
    │  类型检查: 额外构建符号表和类型环境
    │
    ▼
规则引擎 / 类型推理
    │
    ├── 风格规则（缩进、命名）
    ├── 安全规则（SQL注入、硬编码密码）
    ├── 活跃度分析（未使用导入）
    ├── 复杂度规则（函数过长、嵌套过深）
    └── 类型约束求解
    │
    ▼
问题报告（文件:行:列: 消息）
    │
    └── 0 个问题 → 通过
```

**核心约束**：静态分析在代码**执行前**运行，不依赖运行时输入。这是 linting 的本质——它比运行时错误早发现 $N$ 个部署周期，修复成本随阶段指数增长。

## 机制

### Ruff 的 Rust 重写策略

传统 Python linter（Pylint、Flake8）用 Python 编写，性能受 GIL 和解释器开销限制。Ruff 用 Rust 重写规则引擎，将 Python linting 从分钟级压缩到毫秒级：

| 工具 | 典型分析时间（10k 行） | 加速比 |
|------|----------------------|--------|
| Pylint | ~120s | 1× |
| Flake8 | ~30s | 4× |
| Ruff | ~0.1s | 1200× |

代价是规则数量受限——Ruff 实现约 500+ 规则（Pylint 3000+），但覆盖最常用的错误模式。

**架构**：Rust 的规则以插件形式注册，每个规则是一个 Rust 函数，接收 AST 节点并返回问题列表。共享底层数据结构（AST、符号表）减少重复计算。

**规则注册的约束**：新规则必须在规则表中注册，包含唯一 ID、规则名称、AST 节点类型、检测逻辑。这保证了规则的可枚举性和可禁用性。

### Mypy 的类型推断

Mypy 使用**流敏感的类型推断**：

1. **初始化推断**：第一次赋值时推断变量类型
2. **分支合并**：若分支 `if x > 0: s = "positive"` 和 `else: s = "negative"`，合并后 `s: Literal["positive", "negative"]`（联合类型）
3. **返回值推断**：函数所有返回路径的类型取并集

```python
def f(x):
    if x > 0:
        return "positive"
    return -x  # int

# Mypy 推断返回值类型为 str | int
```

Mypy 不运行代码，只做静态分析，因此对动态特性（如 `type(x) is int`）的处理有限。

**动态特性的盲区**：Mypy 无法追踪通过 `type()` 返回值进行的类型收缩，因为 `type()` 在运行时才求值，静态分析无法模拟。

### Pyright 的增量分析

Pyright（Pyright Language Server）使用**项目范围的增量分析**：
- 首次分析全量文件，缓存符号表
- 修改文件后，只重新分析受影响文件（依赖该文件的文件）
- 跨文件类型引用通过符号表快速解析，无需重新扫描

**符号表缓存的数学描述**：
设文件依赖图 $G = (V, E)$，修改节点 $v \in V$ 后，需重新分析 $\{v\} \cup \{u | (u, v) \in E\}$（即 $v$ 及其所有前驱节点）。

这使得大型代码库（>10k 文件）的增量检查在秒级完成。

**Python 编译器服务**：Pyright 实现了 LSP 的 Python 编译器服务协议，支持 VS Code 的 Pylance 插件，提供实时类型检查和代码补全。

### 误报与漏检的权衡

| 工具哲学 | 示例 | 优点 | 缺点 |
|----------|------|------|------|
| 高召回（Pylint） | 大量风格规则 | 全面 | 慢，误报多 |
| 高精确（Ruff） | 核心错误模式 | 快，误报少 | 规则少 |
| 渐进类型（Mypy） | 类型注解检查 | 安全 | 动态代码难处理 |

最佳实践：Ruff 处理格式+风格 → Mypy/Pyright 处理类型安全，分工明确。

### Ruff + Mypy 的协作矩阵

| 检查维度 | Ruff | Mypy |
|---------|------|------|
| 未使用变量 | 是 | 否 |
| import 顺序 | 是 | 否 |
| 类型注解一致性 | 否 | 是 |
| 可调用对象检查 | 部分 | 是 |
| 安全漏洞（SQL注入等） | 是 | 否 |
| 代码复杂度 | 是 | 否 |

### Python 3.14 兼容性

Python 3.14 为前沿版本，代码检查工具需关注：

- **类型系统演进**：3.14 可能引入新的类型语法（如改进的泛型语法），Mypy/Pyright 需要时间适配
- **标准库类型更新**：3.14 的新标准库可能带来新的类型注解

## 参考存根

```python
import subprocess

# Ruff 检查（极快）
r = subprocess.run(["ruff", "check", "src/"], capture_output=True)
print(r.stdout)  # 问题列表
print(r.returncode)  # 0=无问题

# Mypy 类型检查
r = subprocess.run(["mypy", "src/"], capture_output=True)
print(r.stdout)  # 类型错误

# Pyright 类型检查
r = subprocess.run(["pyright", "src/"], capture_output=True)

# 组合：先格式化，再检查
subprocess.run(["ruff", "format", "src/"], check=False)
r = subprocess.run(["ruff", "check", "src/"], capture_output=True)
r = subprocess.run(["mypy", "src/"], capture_output=True)
```
