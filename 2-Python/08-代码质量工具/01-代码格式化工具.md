# 代码格式化工具

## 定义

代码格式化工具通过将源代码解析为抽象语法树（AST），再按确定性规则重新生成风格一致的等价表示，消除人工风格决策，降低协作摩擦。其核心约束是**幂等性**：同一输入无论格式化多少次，输出必须完全相同（`fmt(src) = fmt(fmt(src))`）。

**归约视角**：格式化工具是**语义保持的纯外观变换**——解析为 AST 后重建代码文本，AST 的语义结构（表达式求值顺序、变量作用域）完全不变。格式化本质上是语法层面的规范化，不涉及任何语义分析。

## 数学模型

### AST 变换的不动点

设格式化函数为 $F: S \to S$（$S$ 为源代码字符串空间）。幂等性要求：

$$F(F(s)) = F(s) \quad \forall s \in S$$

即 $F$ 的不动点构成所有格式化后代码的集合。Black 等严格工具的规则设计保证代码在首次格式化后即进入不动点，再次格式化零改动。

**不动点定理的工程含义**：若 $F$ 是有限状态自动机上的单调映射（字符串长度不增或有限次迭代后长度不增），则 $F$ 必有不动点。Black 的行长度约束保证每次迭代输出长度不增，因此必然收敛。

**收敛速度**：大多数文件一次迭代即可到达不动点。极少数学公式化后仍超长的代码可能需要两次迭代（首次换行后产生新的可优化模式）。

### 树形变换的组合复杂度

代码格式化涉及多层 AST 变换：

$$\text{source} \xrightarrow{\text{parse}} \text{AST} \xrightarrow{\text{transform}} \text{modified AST} \xrightarrow{\text{unparse}} \text{output}$$

每层变换的复杂度：
- 解析：$O(n)$（线性扫描 tokens）
- AST 节点修改：$O(1)$（局部替换）
- 代码生成：$O(n)$（树遍历）

总复杂度 $O(n)$，与源文件长度线性相关。这是格式化工具能处理超大代码库的理论基础。

### Black 的行长度约束

Black 默认行长 88 字符（可配置），其决策模型为：

$$L_{\text{effective}} = \min(L_{\text{config}}, \text{自然行长}) \quad \text{若超出则换行}$$

**约束边界与违反行为**：

当一行代码超出限制且无有效断点时，Black 的行为是**报告错误而非静默换行**：

```python
# 这行无法自动格式化（长字符串字面量，无有效断点）
s = "This_is_a_very_long_string_literal_that_exceeds_the_line_length_limit_and_cannot_be_broken"
```

Black 会报告 `Line too long (92 > 88 characters)`，要求人工干预。这是一种**约束违反检测**而非自动修复——因为自动换行可能改变字符串语义。

**长行的可格式化条件**：
- 函数调用参数超长 → 逐行堆叠每个参数
- 嵌套调用超长 → 隐式换行
- 多行字符串 → 保持原样（Black 不修改字符串内容）
- 长字符串字面量 → 需人工处理，工具无法安全拆分

### isort 的 import 排序约束

isort 的排序规则基于**分组和字母序**：

$$G = \{(g_1, g_2, \dots, g_k) | \text{import 按分组排序}\}$$

默认分组顺序：
1. `__future__` imports
2. 标准库
3. 第三方库
4. 本地应用/库 imports

同组内按字母序排列。`force_single_line=True` 将每个 import 强制拆成单行，这可能与 Black 的行长度冲突。

**冲突约束**：isort 的单行模式与 Black 的行长约束可能同时满足，产生冲突。解决方案是使用 `isort --profile black`，该配置自动对齐两工具的冲突规则。

## 数据流

```
源代码（文本）
    │
    ▼
词法分析器（Lexer）──▶ Token 流
    │  逐字符扫描，识别关键字/标识符/字面量
    │  正则匹配，O(n) 复杂度
    │
    ▼
解析器（Parser）──▶ AST（抽象语法树）
    │  按语法规则组织 tokens，检测语法错误
    │  递归下降或 LALR(1) 解析
    │
    ▼
格式化规则引擎
    │
    ├── 行长度约束（Black: 88字符）
    │    └─ 约束违反检测：无法自动换行时报告错误
    ├── 缩进（4空格 vs 2空格）
    ├── 引号风格（单引号 vs 双引号）
    ├── 尾随逗号（trailing commas）
    ├── import 分组和排序（isort）
    └── 空行规则（空行数量、空行位置）
    │
    ▼
代码生成器（Unparser）──▶ 风格化代码
    │  按遍历顺序输出节点，累积为字符串
    │
    ▼
确定性输出（幂等）
```

**关键性质**：格式化是**语义保持的纯外观变换**——AST 的语义结构（表达式求值顺序、变量作用域）完全不变。

## 机制

### AST 表示与代码生成

Python 代码解析为 AST 后，每个节点携带位置信息（行号、列偏移）。格式化工具遍历 AST 时，按节点类型应用对应规则：

```python
# 源代码
x = [1, 2, 3]

# AST 表示（简化）
Module(body=[
  Assign(targets=[Name(id='x')], value=List(elts=[
    Constant(value=1), Constant(value=2), Constant(value=3)
  ]))
])
```

Black 的代码生成器从 AST 重新构建文本，遵循 Black 的行长度（默认88字符）和空行规则。生成的代码在语义上完全等价于原始代码。

### 确定性约束的工程价值

**确定性** 是格式化工具的核心工程约束：

- **CI 友好**：每次运行结果相同，格式检查不会因工具版本不同产生 diff
- **幂等保证**：格式化脚本可安全重复运行，无需担心累积效应
- **可预测性**：团队成员无论何时运行工具，输出稳定

Black 通过严格限制配置选项（"没得选就是最好的"）来保证确定性。选项越多，不同样本组合爆炸越多，维护成本越高。

### 多工具组合：isort + Black

isort 负责 import 分组和排序，Black 负责其余格式约束。两者必须协同：

- isort 的 `force_single_line=True`（单行 import）可能违反 Black 的行长度
- 正确组合：`isort --profile black`，自动对齐两工具的冲突规则

组合后处理顺序：**isort 先规范化 import → Black 格式化其余**。若顺序颠倒，isort 可能重新引入 Black 已格式化的换行。

**冲突仲裁规则**：
- isort 的 `profile = "black"` 使其在单行/多行决策上遵循 Black 的行长度
- import 内部换行由 Black 而非 isort 控制

### Python 版本的 target-version

Python 语法在不同版本间有差异（如 `match...case` 在 3.10+）。`pyproject.toml` 中的 `target-version` 告诉格式化工具按哪个 Python 版本解析代码：

```toml
[tool.black]
target-version = ["py312"]
```

这确保工具不会把旧版本的有效语法格式化为新版本语法。例如，3.12+ 的新语法特性（如更快的启动速度相关的优化）不会被格式化工具误处理。

### Ruff Format 的崛起

Ruff 0.1+ 内置 `ruff format` 命令，其定位与 Black 相同但性能更高（Rust 实现）：

| 工具 | 10k 行文件 | 100k 行代码库 |
|------|-----------|---------------|
| Black | ~0.5s | ~5s |
| ruff format | ~0.01s | ~0.1s |

Ruff Format 与 Black 的输出高度兼容（共享大部分格式化决策），可作为 Black 的替代品。

**架构差异**：Black 用 Python 实现，解析依赖 `blackd` 或 `blib2to3`；Ruff Format 用 Rust 实现，解析用 `rowan`（Rust 实现的 AST 库）。Rust 的 arena 分配模式使大规模代码处理更快，因为 AST 节点内存分配是一次性批量进行的。

### Python 3.14 兼容性

Python 3.14 为前沿版本，代码格式化工具需关注：

- **语法兼容性**：Ruff Format 和 Black 的 `target-version` 需设置为 `py314` 以正确解析新语法
- **类型注解增强**：3.14 可能引入新的类型注解形式，工具需相应更新解析器

## 参考存根

```python
import subprocess

# 检查（不修改）
r = subprocess.run(["black", "--check", "."], capture_output=True)
print(r.returncode)  # 0 = 已格式化，非0 = 需要格式化

# 格式化
r = subprocess.run(["black", "."], capture_output=True)

# isort + Black 组合
r = subprocess.run(["isort", "--profile", "black", "."], capture_output=True)
r = subprocess.run(["black", "."], capture_output=True)

# Ruff Format (替代 Black)
r = subprocess.run(["ruff", "format", "."], capture_output=True)

# 配置 pyproject.toml
# [tool.black]
# line-length = 88
# target-version = ['py312']
# [tool.isort]
# profile = "black"
```
