# 代码质量工具

> **版本基准**：Python 3.12 stable（latest=3.14，新特性章节保留并标注）

## 本质

代码质量工具通过**格式化**和**静态检查**在代码**执行前**保障质量。格式化工具（Formatter）将源代码解析为 AST 并按确定性规则重建，实现风格幂等统一；代码检查工具（Linter/类型检查器）通过静态分析发现错误、漏洞和风格问题。

**工程价值**：越早发现缺陷，修复成本越低。静态分析在部署前发现问题，修复成本是运行时错误的 $\frac{1}{10} \sim \frac{1}{100}$ （IBM Systems Sciences Institute 研究）。 （IBM Systems Sciences Institute 研究）。

# 代码格式化工具

## 定义

代码格式化工具将源代码解析为抽象语法树（AST），再按确定性规则重建风格一致的等价表示。核心约束是**幂等性**：`fmt(src) = fmt(fmt(src))` —— 同一输入无论格式化多少次，输出完全相同。

**本质**：格式化是**语义保持的纯外观变换**。解析为 AST 后重建代码文本，语义结构（表达式求值顺序、变量作用域）完全不变，仅改变视觉呈现。

## 数学模型

### 幂等变换的不动点定理

 $F(F(s)) = F(s) \quad \forall s \in S$

**收敛性证明思路**：格式化是单调映射（不减少"规范性程度"），在有限状态空间（代码的可能格式状态）上必有不动点，且从任意起点迭代有限次必达不动点。

### Ruff 的 1200× 加速来源

Ruff 用 Rust 重写规则引擎，性能提升来自：

| 优化点 | 效果 |
|--------|------|
| 无 GIL | 并行处理文件 |
| 编译为机器码 | 解释器开销为零 |
| 共享 AST | 减少重复解析 |

## 机制

### Black 的"无妥协"哲学

Black 是 Python 格式化的事实标准，核心约束：
- 行长度 88 字符（可配置）
- 不做语义分析，只做 AST 重建
- 最小diff原则：格式化结果与原代码的语义完全一致

**幂等性验证**：`black --check src/` 验证文件是否已格式化。

### Ruff Format 的兼容性

Ruff Format 100% 兼容 Black 配置，可作为 Black 的替代：

```bash
# 等价替换
ruff format src/    # 替代 black src/
ruff check src/     # 替代 flake8 / pylint
```

# 代码检查工具

## 定义

代码检查工具通过静态分析在代码**执行前**发现错误、漏洞和风格问题。区别于格式化工具，代码检查**不修改代码**，只报告问题。按分析深度分为：

- **Linter**：基于词法/语法分析的规则匹配（代码风格、未使用变量）
- **类型检查器**：基于类型注解一致性的深度分析（参数类型不匹配、返回值类型错误）

**本质**：代码检查是**在执行前发现缺陷**的静态分析过程。核心约束是**不执行代码** —— 通过抽象解释或符号执行在代码的语法结构上推理可能的运行时错误。

## 数学模型

### 规则匹配的精确率-召回率权衡

设规则集为 $R = \{r_1, r_2, \dots, r_m\}$，代码问题空间为 $P$ （所有实际存在的问题），工具检出问题为 $D$： ，代码问题空间为 $P$ （所有实际存在的问题），工具检出问题为 $D$： （所有实际存在的问题），工具检出问题为 $D$： ：

 $D = \bigcup_{r \in R} \text{match}(r, \text{AST})$ 

- **召回率**（Recall）： $\frac{|D \cap P|}{|P|}$ —— 漏检率，越高越好 —— 漏检率，越高越好
- **精确率**（Precision）： $\frac{|D \cap P|}{|D|}$ —— 误报率，越低越好 —— 误报率，越低越好

**精确率-召回率 tradeoff**：规则越多越严格，召回率上升（漏检减少）但精确率下降（误报增多）。工具设计哲学决定 tradeoff 点：

| 工具哲学 | 规则数 | 召回率 | 精确率 | 典型场景 |
|----------|--------|--------|--------|----------|
| 高召回（Pylint） | 3000+ | 高 | 低 | 全面代码质量审计 |
| 高精确（Ruff） | 500+ | 中 | 高 | CI/CD 快速检查 |

**F1 分数**：精确率和召回率的调和平均，综合衡量：

 $F_1 = 2 \cdot \frac{\text{Precision} \cdot \text{Recall}}{\text{Precision} + \text{Recall}}$ 

### 类型约束求解

Python 类型注解构成**一阶谓词约束系统**。设函数签名：

```python
def f(x: int, y: str) -> bool: ...
```

类型检查器验证调用 `f(a, b)` 时，约束 $\{a: \text{int},\ b: \text{str}\}$ 是否满足签名公理。若不满足，报类型错误。 是否满足签名公理。若不满足，报类型错误。

**约束求解本质**：这是**一阶谓词逻辑的模型检测** —— 给定函数签名（公理）和调用（查询），验证查询是否满足公理约束。复杂度等级属于 PSPACE，但实际 Python 类型系统通过限制递归类型来保证可判定性。

**渐进式严格度**：

| 模式 | 行为 | 类型安全强度 |
|------|------|-------------|
| 无类型注解 | 完全不检查 | 0 |
| 基础模式（checked） | 仅检查有注解的调用点 | 中 |
| 严格模式（strict） | 注解覆盖处必须匹配，未注解处报错 | 高 |

严格程度越高，类型安全越强，但迁移成本越高（需大量添加注解）。

### Mypy 流敏感类型推断

Mypy 使用**流敏感的类型推断**，对同一变量在不同程序点分别追踪类型：

 $T_{\text{var}}(p) = \begin{cases} T_{\text{init}} & p = \text{初始化点} \\ T_1 & p \in \text{分支 1} \\ T_2 & p \in \text{分支 2} \\ T_1 \cup T_2 & p = \text{分支合并点} \end{cases}$ 

其中 $T_1 \cup T_2$ 是联合类型（如 `int | str`）。 是联合类型（如 `int | str`）。

**流敏感 vs 非流敏感**：非流敏感系统中，变量类型一旦推断即为全局不变；流敏感系统中，类型随控制流路径动态扩展。

**分支合并的类型交集**：

```python
def f(x):
    if x > 0:
        return "positive"
    return -x  # int

# Mypy 推断返回值类型为 str | int（联合类型）
# 因为两个分支的返回类型在合并点取并集
```

### Pyright 增量分析的依赖图

Pyright 使用**项目范围的增量分析**，基于文件依赖图：

设文件依赖图 $G = (V, E)$ （节点为文件，边为导入关系），修改节点 $v \in V$ 后： （节点为文件，边为导入关系），修改节点 $v \in V$ 后： 后：

 $\text{重新分析} = \{v\} \cup \{u | (u, v) \in E\}$

### 类型检查的停机性保证

类型检查算法必须对任意输入在有限时间内终止。通过以下约束保证：

- 类型注解有穷（类、函数签名、泛型参数数量有限）
- 泛型实例化深度受限（防止无限递归展开，如 `class C[T: C[C[T]]]`）
- 联合类型项数有界（防止无限叉乘）

**不可判定性边界**：若 Python 支持任意递归类型（如 $T = \text{list}[T]$），则统一化算法可能不终止。现代 Python 类型系统通过禁止此类自引用来保证可判定性。 ），则统一化算法可能不终止。现代 Python 类型系统通过禁止此类自引用来保证可判定性。

## 数据流

<pre>
源代码（文本）
    │
    ▼
词法/语法分析 ──▶ AST + 符号表
    │
    ├── Linter 分支：
    │    │  扫描特定模式（未使用变量、shadowing、代码复杂度）
    │    │  基于正则或简单 AST 遍历，O(n) 复杂度
    │    ▼
    │  规则引擎 ──▶ 问题列表
    │
    └── 类型检查分支：
         │  构建符号表（作用域链、名称绑定）
         │  类型推断（流敏感）
         │  约束求解（可满足性检测）
         ▼
       类型推理引擎 ──▶ 类型错误列表
            │
            ▼
      诊断报告（文件:行:列: 消息）
            │
            └── 0 个问题 → 通过
</pre>

**关键性质**：静态分析在代码**执行前**运行，不依赖运行时输入。这是 linting 的本质约束 —— 分析器必须能在不知道程序会做什么的情况下，推理出程序可能出错的地方。

**Linter 与类型检查器的数据流差异**：
- Linter：AST 遍历 + 模式匹配，不维护类型信息
- 类型检查器：AST + 符号表 + 类型环境，需要跨文件的上下文

## 机制

### Ruff 的 Rust 重写策略

传统 Python linter（Pylint、Flake8）用 Python 编写，性能受 GIL 和解释器开销限制。Ruff 用 Rust 重写规则引擎：

| 工具 | 典型分析时间（10k 行） | 加速比 |
|------|----------------------|--------|
| Pylint | ~120s | 1× |
| Flake8 | ~30s | 4× |
| Ruff | ~0.1s | 1200× |

**性能差异来源**：
- Rust 无 GIL，可并行处理文件
- Rust 规则引擎编译为机器码，解释器开销为零
- 共享底层数据结构（AST、符号表），减少重复计算

**规则注册的约束**：新规则必须在规则表中注册，包含唯一 ID、规则名称、AST 节点类型、检测逻辑。这保证了规则的可枚举性和可禁用性，但也限制了规则数量（ Ruff 约 500+，Pylint 3000+）。

**规则覆盖范围 tradeoff**：Ruff 选择高精确率，覆盖最常用的错误模式；Pylint 选择高召回率，规则更全面但可能有误报。

### Mypy 的流敏感推断机制

Mypy 类型推断的三个核心规则：

1. **初始化推断**：第一次赋值时推断变量类型
   ```python
   x = 1       # 推断 x: int
   x = "foo"   # 推断 x: str（覆盖）
   ```

2. **分支合并推断**：不同分支的同一变量类型在合并点取并集
   ```python
   if cond:
       s = "positive"
   else:
       s = 0
   # s: str | int
   ```

3. **返回值推断**：函数所有返回路径的类型取并集
   ```python
   def f(x):
       if x > 0:
           return "positive"
       return -x  # int
   # 推断返回值: str | int
   ```

**动态特性的盲区**：Mypy 无法追踪通过 `type()` 返回值进行的类型收缩：

```python
def f(x: object):
    if type(x) is int:
        # Mypy 不知道 x 在这里是 int
        # 静态分析无法模拟 type() 的运行时行为
        return x + 1  # 可能报错
```

这是因为 `type()` 在运行时才求值，静态分析无法模拟。

### Pyright 增量分析的符号表缓存

Pyright（Pyright Language Server）的增量分析策略：

1. **首次全量分析**：构建所有文件的符号表缓存
2. **文件修改后**：只重新分析修改文件 + 依赖该文件的所有前驱
3. **符号表复用**：跨文件类型引用通过缓存的符号表快速解析，无需重新扫描

**符号表缓存失效条件**：
- 被依赖文件的公共 API 签名改变（所有依赖方需重新检查）
- 导入路径重排（影响符号解析结果）

### 误报与漏检的系统性来源

| 工具哲学 | 误报来源 | 漏检来源 |
|----------|----------|----------|
| 高召回（Pylint） | 规则过于宽松，无法区分真实错误和风格问题 | 少 |
| 高精确（Ruff） | 规则严格匹配，少误报 | 规则数量有限，部分错误模式无法检测 |

**误报的系统性后果**：高误报率导致开发者对工具失去信任，关闭规则或忽略输出，形成"狼来了"效应。Rust 重写策略在提升速度的同时，通常需要精简规则以维持精确率。

### Ruff + Mypy 的协作矩阵

两种工具分工明确，覆盖不同检查维度：

| 检查维度 | Ruff | Mypy |
|---------|------|------|
| 未使用变量/导入 | 是 | 否 |
| import 顺序 | 是 | 否 |
| 类型注解一致性 | 否 | 是 |
| 可调用对象检查 | 部分 | 是 |
| 安全漏洞（SQL注入等） | 是 | 否 |
| 代码复杂度 | 是 | 否 |

**推荐工作流**：Ruff 处理格式+风格+安全 → Mypy 处理类型安全，分工明确，各自发挥优势。

### 类型系统演进的前沿约束

Python 类型系统持续演进（3.10 match-case、3.11 性能优化、3.12~3.14 更快启动），类型检查器需要同步跟进：

- **语法兼容性**：新语法需要检查器能正确解析（如 `match...case` 的类型推断）
- **标准库类型更新**：新版本标准库带来的新类型注解需要能正确处理
- **类型语法演进**：3.12 引入的 `type` 注解改进、3.14 可能的新泛型语法

**检查器的版本对齐约束**：若代码库使用较新 Python 版本，但检查器未更新，会产生大量误报（无法理解新语法）。实践中建议检查器版本与 target Python 版本同步更新。
