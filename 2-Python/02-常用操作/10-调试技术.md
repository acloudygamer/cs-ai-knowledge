# 调试技术

## 定义

调试是在程序执行流中插入观测点，通过中断、步进、检查三种操作对程序状态空间进行约束搜索的过程。调试的本质是**受限的虚拟机解释执行**：调试器持有被调试进程的完整控制权，在特定条件下暂停执行流并允许检查/修改状态。

## 数学模型

### 断点命中条件

设程序执行路径为状态序列 $\pi = (s_0, s_1, \dots, s_n)$ 。断点 $b$ 命中当且仅当执行到达某个 $s_i$ 满足断点条件 $C(s_i)=\text{True}$ 。 。断点 $b$ 命中当且仅当执行到达某个 $s_i$ 满足断点条件 $C(s_i)=\text{True}$ 。 命中当且仅当执行到达某个 $s_i$ 满足断点条件 $C(s_i)=\text{True}$ 。 满足断点条件 $C(s_i)=\text{True}$ 。 。

断点条件：
- **无条件断点**： $C(s) = (PC(s) = b_{addr})$ 
- **条件断点**： $C(s) = (PC(s) = b_{addr}) \land P(s)$ ，每次到达断点地址时对 $P(s)$ 求值 ，每次到达断点地址时对 $P(s)$ 求值 求值

### 步进的数学定义

- `step`（单步）：沿 $\delta(s_i, \sigma_i)$ 前进一步（进入函数调用） 前进一步（进入函数调用）
- `next`（跳过）：执行直到 PC 到达与当前帧不同的源代码行号（跳过被调用函数内部）

**归约终点**：调试器可归约为**受限的虚拟机解释器**——通过 `ptrace`（Unix）或 `DebugActiveProcess`（Windows）注入控制权，在特定 PC 处将执行流暂停（注入软中断），将进程状态暴露给调试器。调试器不是直接修改被调试进程的内存，而是通过操作系统提供的调试接口进行只读检查或受限修改。

## 数据流

<pre>
被调试进程 P                      调试器 D (pdb / IDE debug adapter)
  执行字节码                        持有 P 的控制权
      │                                │
      │ <── ptrace / DebugActive ────│ D 在特定 PC 注入断点
      │                                │
      │  断点命中：P 暂停（SIGTRAP）  │
      │ ─────────────────────────────>│
      │                                │
      │  D 执行: 读取寄存器/内存/栈    │
      │ ─────────────────────────────>│
      │                                │
      │  D 执行: 修改寄存器/内存/PC    │
      │ <─────────────────────────────│
      │                                │
      │  P 恢复执行                   │
</pre>

**所有权流转**：
- 正常运行：CPU 执行权归 P 的主线程
- 断点命中：执行权转移至 D（P 被 OS 暂停）
- 检查/修改：D 持有 P 状态的只读/读写视图
- 继续执行：执行权归还 P

## 机制

### pdb 的实现原理

pdb 基于 `sys.settrace` 实现：`settrace` 在**每条字节码指令执行前后**插入回调。这使得启用 tracing 后程序以 $1/n$ 的速度运行（n 为平均每行字节码数）。 的速度运行（n 为平均每行字节码数）。

断点的实现：pdb 在目标行第一条字节码处动态修改指令，插入软中断（如 `INT 3`），命中时 OS 发送信号给调试器。

**约束**：`sys.settrace` 是**线程局部的**——每个线程独立持有 trace 函数。若在主线程设置 tracing，子线程的执行不会触发主线程的 trace 函数。多线程调试必须为每个线程单独设置 tracing，或依赖 IDE 的多线程-aware 调试协议（如 pydevd）。

### 多线程调试的困难

多线程调试的本质困难在于**线程调度的不可确定性**和**状态空间爆炸**：
- 线程随时可能被 OS 抢占调度，`step`/`next` 的语义在多线程下模糊（哪个线程在执行？）
- 断点命中时，其他线程仍在运行，可能同时修改共享状态
- Race condition 导致的 bug 在断点介入时可能消失（Heisenbug）——因为断点暂停改变了线程间时序关系

**归约**：这解释了为何**日志调试优于断点调试**用于多线程场景：日志记录不暂停被调试线程，不改变线程间时序关系，能够在接近生产环境的条件下观测并发行为。

### profiler 采样原理：统计采样 vs 插桩

Profiler 有两种实现范式：

**统计采样（Statistical Sampling）**：以固定频率（如 1000Hz）对进程中断，在中断点采样程序计数器（PC）。通过统计各函数被采样次数推断时间占比。

**插桩（cProfile/settrace）**：在函数入口/出口插入计数代码，精确记录每次调用。

| 维度 | 统计采样 | 插桩（cProfile/settrace） |
|------|----------|--------------------------|
| Overhead | 低（~1-5%） | 高（~10-100x） |
| 精度 | 统计近似，依赖采样频率 | 精确到每次函数调用 |
| 适用场景 | 生产环境快速定位热点 | 开发环境精确分析 |

**约束**：cProfile 通过 settrace 注入回调，每函数调用/返回事件触发记录。这意味着**profiling 是侵入式的观测**，对短程序（毫秒级）的测量结果可能严重失真。

### 日志调试适合生产环境的原因

日志调试的优势在于**非侵入性**和**可远程**：
- 不暂停进程，不改变线程时序（适合 race condition 诊断）
- 可在生产环境持续运行（对比：断点调试会冻结整个进程）
- 通过日志聚合系统（ELK）远程分析，无需直接访问进程
- 适合偶发性 bug（race condition、偶发超时）的复现

**约束**：日志调试依赖**先验知识**——必须在问题发生前在可能路径埋点。断点调试则可在事后动态插入观测点。

## 参考存根

```python
import pdb
import traceback
import tracemalloc
import cProfile
import pstats

# pdb：条件断点 + 多行步进
def buggy_function(data):
    breakpoint()  # 等价于 pdb.set_trace()
    for i, item in enumerate(data):
        if i > 100 and item < 0:
            breakpoint()  # 条件断点
        process(item)

# 堆栈打印（非断点介入）
def print_stack():
    for frame_summary in traceback.extract_stack():
        print(f"{frame_summary.filename}:{frame_summary.lineno} in {frame_summary.name}")

# tracemalloc：定位内存泄漏
tracemalloc.start()
snapshot1 = tracemalloc.take_snapshot()
# ... allocate objects ...
snapshot2 = tracemalloc.take_snapshot()
top_diff = snapshot2.compare_to(snapshot1, 'lineno')
for stat in top_diff[:5]:
    if stat.size_diff > 0:
        print(f"{stat.size_diff/1024:.1f}KB: {stat}")

# cProfile：统计分析采样
profiler = cProfile.Profile()
profiler.enable()
# ... 被测代码 ...
profiler.disable()
stats = pstats.Stats(profiler)
stats.strip_dirs().sort_stats('cumulative').print_stats(20)
```
