# 数据库操作

> **版本基准**：Python 3.12 stable（latest=3.14，新特性章节保留并标注）

## 本质

数据库操作是程序通过 SQL 语句与关系型数据库引擎交互，实现数据的持久化存储、查询和修改的过程。SQLite 是嵌入式关系数据库（无独立服务进程），文件即数据库；SQLAlchemy 等 ORM 层将 Python 对象操作转译为 SQL。事务提供了 ACID（原子性、一致性、隔离性、持久性）保证，隔离级别决定了并发事务之间的可见性。

## 数学模型

### 事务的 ACID 约束

**原子性**（Atomicity）：事务内的所有操作要么全部成功（commit），要么全部不执行（rollback）。从状态机角度：事务开始后，事务所做的修改都在内存的 WAL buffer 或锁保护的页面中，直到 commit 才写入主数据库文件。

**一致性**（Consistency）：事务执行前后，数据库必须从一致状态变为另一个一致状态。一致性约束（外键、CHECK 约束、UNIQUE 索引）由数据库引擎在事务内强制检查。

**隔离性**（Isolation）：并发事务的执行效果与串行执行等价。SQLite 提供 5 种隔离级别（`DEFERRED/IMMEDIATE/EXCLUSIVE`），默认是 DEFERRED（锁在第一次读/写时获取）。

**持久性**（Durability）：commit 成功后数据必须持久化到磁盘。SQLite 的 `journal_mode` 决定日志策略，WAL 模式下 commit 成功意味着数据已写入 WAL 文件（fsync 后）。

### 并发控制的锁模型

SQLite 采用文件级锁，锁状态机：

```
UNLOCKED → SHARED（多个读）→ RESERVED（一个写，待写）→ PENDING → EXCLUSIVE
```

WAL 模式改变了这一模型：读操作不阻塞写操作，写操作不阻塞读操作（因为写操作写入 WAL，不锁定主数据库文件）。这将读-写并发度从"互斥"提升为"可以同时存在"，但写-写仍需 EXCLUSIVE 锁。

> **洞察**：SQLite 的锁机制可归约为**二元信号量的状态机**，锁状态表示当前持有者的集合（多个 SHARED 或单一 EXCLUSIVE）。

### B-tree 的查询复杂度

SQLite 使用 B-tree（及 B+-tree 变体）存储索引和数据表。设节点扇出（每个内部节点子节点数）为 $f$，树高为 $h$，总记录数为 $N$：

 $h \approx \log_f N$ 

查询复杂度为 $O(h) = O(\log_f N)$，通常 $f$ 在 100-1000 量级，故树高 3-4 层即可支持百万级记录。磁盘 I/O 次数等于树高（每个节点一次磁盘读取），是数据库查询性能的关键指标。

WAL 模式的写路径： WAL buffer → WAL 文件（fsync） → checkpoint 时合并到主文件

**形态变换**：
- Python 对象 → SQL 语句字符串（由 ORM 生成）
- SQL 执行 → 字节码 → B-tree 操作（索引查找 + 行查找）
- 结果行 → SQLite 的 C 结构 → Python tuple/dict（光标 fetch）

## 机制

### 参数化查询与 SQL 注入防御

SQL 注入的根本原因是将数据与代码（SQL）混淆。参数化查询将 SQL 结构（静态）和数据（动态）分离：

```python
# 安全：数据不进入 SQL 语法解析器
cursor.execute("SELECT * FROM users WHERE id = ?", (user_id,))
# 编译时：SQL 结构已固定，"?" 是占位符
# 执行时：user_id 作为纯数据绑定，不会被解释为 SQL 代码
```

**约束**：参数化查询只适用于数据部分，SQL 结构本身（如表名、列名）不能参数化，需通过白名单验证：

```python
# 危险：表名不可参数化
table_name = "users"  # 来自用户输入
cursor.execute(f"SELECT * FROM {table_name}")  # SQL 注入风险！

# 安全：表名白名单
ALLOWED_TABLES = {"users", "posts", "comments"}
if table_name not in ALLOWED_TABLES:
    raise ValueError("invalid table")
cursor.execute(f"SELECT * FROM {table_name}")
```

### WAL 模式的 checkpoint 机制

WAL（Write-Ahead Logging）将修改先写入 WAL 文件（顺序追加，高效），然后通过 checkpoint 操作将 WAL 中的修改合并回主数据库文件。checkpoint 触发条件：
- WAL 文件达到 `wal_autocheckpoint` 页数（默认 1000）
- 另一个进程连接时请求写锁
- 显式调用 `PRAGMA wal_checkpoint`

**约束**：WAL 模式需要额外的 `.wal` 文件和共享内存文件（`.shm`），且不支持某些文件系统（如 NFS）。checkpoint 是唯一将 WAL 内容写入主文件的时机，未 checkpoint 的修改在崩溃时可能丢失（但最多丢失一个 checkpoint 周期，典型 1000 页）。

### SQLAlchemy 的查询编译

SQLAlchemy 的 `Query` 对象在执行时才生成 SQL 字符串。关键路径：
1. `session.query(User)` 构建 `Query` 对象（未生成 SQL）
2. `.filter(User.name == "Alice")` 添加条件（仍不生成 SQL）
3. `.all()` 或 `.first()` 触发 `Query.compile()`，生成 SQL 并执行

**N+1 查询问题**：若不显式 eager load 关联对象，遍历结果集时每个对象访问关联属性都会触发一次独立查询：

 $N \text{ 条记录} + 1 \text{ 次初始查询} = N+1 \text{ 次数据库往返}$ 

解决方式：`joinedload()`（JOIN 预加载）或 `selectinload()`（IN 子查询批量加载）。

### 连接管理与上下文管理器

`sessionmaker` 创建的 Session 是应用级对象，需显式管理生命周期：

```python
from sqlalchemy.orm import sessionmaker
Session = sessionmaker(bind=engine)

session = Session()
try:
    # ... 使用 session
    session.commit()
except:
    session.rollback()
    raise
finally:
    session.close()
```

**约束**：Session 不是线程安全的（不能跨线程共享），每个线程应创建自己的 Session。长期持有一个 Session（如全局单例）会导致连接资源泄漏，应使用 request-scoped session。

## 代码示例

```python
import sqlite3

# 原子事务：确保要么全部成功，要么全部回滚
def transfer_funds(conn, from_id, to_id, amount):
    cursor = conn.cursor()
    try:
        cursor.execute("UPDATE accounts SET balance = balance - ? WHERE id = ?", (amount, from_id))
        cursor.execute("UPDATE accounts SET balance = balance + ? WHERE id = ?", (amount, to_id))
        cursor.execute("SELECT balance FROM accounts WHERE id = ?", (from_id,))
        if cursor.fetchone()[0] < 0:
            raise ValueError("余额不足")
        conn.commit()
    except:
        conn.rollback()
        raise
```

```python
from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker

# WAL 模式 + ORM session
engine = create_engine("sqlite:///app.db", connect_args={"check_same_thread": False})
engine.execute("PRAGMA journal_mode=WAL")  # 启用 WAL

Session = sessionmaker(bind=engine)
session = Session()
# 使用 session.query() 进行 ORM 操作
```
