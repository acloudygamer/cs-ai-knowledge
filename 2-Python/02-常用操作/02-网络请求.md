# 网络请求

## 定义

网络请求是客户端通过传输层（TCP/UDP）连接远程主机，以应用层协议（HTTP/WebSocket）交换数据的通信过程。核心资源是 socket 缓冲区（接收/发送各一对）、TCP 连接状态机、文件描述符；约束边界由超时配置、重试策略、连接池大小共同决定。

## 数学模型

### 指数退避

设第 $i$ 次重试的延迟为 $T_i$，基础间隔为 $T_{base}$，退避因子为 $b$：
$$T_i = \min(T_{base} \times b^{i-1},\ T_{max})$$

其中 $T_{max}$ 是硬上限（通常 60s）。这是几何增长的离散时间序列，重试次数 $n$ 内的总等待时间为：

$$T_{total} = \sum_{i=1}^{n} T_i = T_{base} \times \frac{b^n - 1}{b - 1}$$

若 $b=2,\ T_{base}=1s$，则 5 次重试最多等待 31 秒。

### TCP 连接建立代价

TCP 三次握手耗时 $T_{handshake} = RTT_{client-server} \times 1.5$（不含数据）。设 RTT 为 $R$，则单次新建连接建立前必须等待 $1.5R$。HTTP/1.1 keep-alive 复用连接避免了该开销；HTTP/2 在单连接上复用多路复用流进一步降低连接数。

**归约终点**：TCP 连接建立代价本质是 $1.5 \times RTT$，其中 $RTT$ 由物理距离和网络拥塞程度决定，无法在协议层优化。

### socket 缓冲区背压

每个 socket 有一对固定大小的发送/接收缓冲区（Linux 默认约 `net.core.rmem_default = net.core.wmem_default = 262144` 字节）。当发送缓冲区满时，`send()` 阻塞或返回 `EAGAIN`（非阻塞模式）。这构成背压（backpressure）机制：快速发送者被慢速接收者限速，防止内存无限增长。

背压的数学描述：设缓冲区容量为 $B$，当前占用为 $b$，则可用空间为 $B - b$。当 $b = B$ 时，写操作阻塞或失败。

### HTTP/2 流复用模型

HTTP/2 在单一 TCP 连接上复用 $N$ 个流，每流有独立 Stream ID。设连接带宽为 $W$ bps，RTT 为 $R$，则单流吞吐量上界为：

$$T_{stream} \leq \frac{W \times RTT_{ack\_time}}{N \times RTT}$$

当单个流丢包时，TCP 拥塞窗口关闭影响所有复用流——这是 HTTP/2 的核心脆弱性。

## 数据流

<pre>
Client                      TCP Stack                   Server
  |                            |                          |
  |  socket()                  |                          |
  |------------->              |                          |
  |  connect()                 |                          |
  |--------------------------->| SYN                      |
  |              |<===========>|==========================>|
  |              |  (1.5 RTT)   |  SYN-ACK                 |
  |              |<===========>|==========================<|
  |              |             |  ACK                      |
  |<-------------|             |                          |
  |  HTTP Request              |                          |
  |--------------------------->|-------------------------->|
  |              |             |  [处理请求]               |
  |              |             |  HTTP Response           |
  |              |             |  [RST_STREAM 或 finish]  |
  |<=========== |<------------|<==========================|
  |  [连接关闭/复用]            |                          |

发送缓冲区满时背压链：
  发送方 send() ---> 内核缓冲区 --X--> 网络 --/--> 接收方
                        [满] = EAGAIN
</pre>

**形态变换**：
- Python dict/list → HTTP Request Body（bytes，Content-Length 确定长度）
- TCP 流 → 应用层协议解析 → Python dict（response.json()）
- 连接从 CLOSED → ESTABLISHED → CLOSED（或保持 ESTABLISHED 用于 keep-alive）

**所有权流转**：
1. `socket()` 创建 fd，分配内核 socket 缓冲区
2. `connect()` 执行三次握手，连接进入 ESTABLISHED 状态
3. `send()/recv()` 数据在内核缓冲区与应用buf间拷贝
4. `close()` 发送 FIN，等待对方 ACK，进入 TIME_WAIT（通常 2*RTT）

## 机制

### 连接池的约束边界

`requests.Session` 维护一个 `HTTPAdapter` 池（默认每个 host 10 个连接）。当并发请求超过池大小时，多余请求排队等待可用连接。**约束**：连接池是有限资源，过度并发导致请求排队甚至超时。httpx 的 `AsyncClient` 默认限制每 host 100 连接，通过 `limits` 参数可进一步配置。

**饥饿与死锁场景**：
- 连接池耗尽：所有连接被占用且未释放，新请求排队超时
- 连接泄漏：`close()` 未被调用，连接无法归还池
- keep-alive 超时：连接久不使用被服务器关闭，发送时收到 `ConnectionResetError`

### 超时的双重语义

- **硬超时**（`timeout.connect`）：TCP SYN 重试次数耗尽后强制关闭连接，抛出 `ConnectTimeout`。
- **软超时**（`timeout.read`）：在数据读取过程中计时，若超过指定时间无任何数据到达，抛出 `ReadTimeout`。

两超时独立计时，可同时配置。当服务器响应了但响应体非常大时，软超时无法保护，需配合流式读取和外部计时器。

### 重试的边界条件

`urllib3.Retry` 默认对所有 HTTP 状态码重试（`status_forcelist` 默认包含 413/429/500/502/503/504）。幂等性假设是重试的前提：GET/HEAD/OPTIONS 是幂等的；POST/PUT/DELETE 默认不重试（除非配置 `raise_on_status=False`）。**违反约束**：对非幂等请求盲目重试可能导致重复执行（如重复扣款），需业务层保证幂等。

**重试的数学边界**：
- 指数退避确保重试间隔指数增长，避免惊群效应
- 最大重试次数受 $T_{max}$ 约束：$n \leq \lfloor \log_b(T_{max}/T_{base}) \rfloor + 1$

### HTTP/2 多路复用

HTTP/2 在单一 TCP 连接上并发多个流（stream），每个流有唯一 ID。帧（frame）是基本传输单元，DATA 帧承载应用数据，HEADERS 帧承载元数据。多路复用使多个请求/响应 interleaving 在同一连接上，避免了 HTTP/1.1 的 HOL（Head of Line）阻塞，但共享 TCP 拥塞窗口——当单个流丢包时，所有流都被阻塞。

**HTTP/3（QUIC）**：
- HTTP/3 基于 UDP，通过 QUIC 协议实现 0-RTT 连接建立（首次连接）
- QUIC 的流复用独立于连接，丢包只影响单个流，不影响其他流
- Python 3.14 `http` 模块对 HTTP/3 的支持仍不完整（依赖底层的 `httpx`/`aioquic`）

### WebSocket 的握手机制

WebSocket 以 HTTP Upgrade 握手开始，客户端发送 `Upgrade: websocket` 和 `Sec-WebSocket-Key`，服务器返回 `Sec-WebSocket-Accept = base64(SHA1(key + GUID))`。成功后协议从 HTTP 切换为 WebSocket 帧协议。之后的每帧最高 125 字节（控制帧）或 65535 字节（数据帧），帧头包含掩码（客户端→服务器帧必须掩码）和 opcode（文本/二进制/关闭）。

**帧解析状态机**：
```
FIN=1, opcode=0x1 → 文本消息完整
FIN=0, opcode=0x1 → 文本消息起始/continuation
FIN=1, opcode=0x0 → continuation 结束
FIN=1, opcode=0x8 → 关闭握手
```

### 连接复用的 HTTP/1.1 keep-alive

HTTP/1.1 默认启用 keep-alive（`Connection: keep-alive`）。服务器通过 `Keep-Alive: timeout=5, max=1000` 告知连接复用策略。连接在以下情况关闭：
- 服务器 `timeout` 超时
- 客户端发送 `Connection: close`
- 请求数达到 `max`
- 任何一方 TCP 连接断开

**Python 3.14 增量**：`urllib.request` 模块对 HTTP/1.1 keep-alive 超时处理更严格，避免连接复用导致的资源泄漏。

## 参考存根

```python
import httpx

# 连接池与流式读取：避免大响应体一次性加载
with httpx.Client() as client:
    with client.stream("GET", "https://example.com/large.json") as response:
        # 逐块处理，不触发完整的响应体加载
        for chunk in response.iter_bytes(chunk_size=8192):
            process(chunk)
```

```python
import asyncio, httpx

# 异步并发请求：单线程多协程共享一个连接池
async def fetch_all(urls: list[str]) -> list[httpx.Response]:
    async with httpx.AsyncClient() as client:
        tasks = [client.get(url) for url in urls]
        return await asyncio.gather(*tasks)
```

```python
# Python 3.14: 使用 http 标准库进行基础请求
from http import client
import urllib.request

# 使用标准库发起请求
req = urllib.request.Request(
    "https://api.example.com/data",
    headers={"Accept": "application/json"}
)
with urllib.request.urlopen(req, timeout=10) as response:
    data = response.read()
    print(f"Status: {response.status}")
```

```python
# 指数退避重试：urllib3.Retry
from urllib3.util.retry import Retry
from requests.adapters import HTTPAdapter
from requests import Session

session = Session()
retry = Retry(
    total=5,
    backoff_factor=0.5,  # 0.5s, 1s, 2s, 4s, 8s
    status_forcelist=[429, 500, 502, 503, 504],
    allowed_methods=["HEAD", "GET", "OPTIONS"]
)
adapter = HTTPAdapter(max_retries=retry)
session.mount("http://", adapter)
session.mount("https://", adapter)
```
