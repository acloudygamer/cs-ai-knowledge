# 设计模式

## 定义

设计模式是针对**面向对象设计**中常见问题的**可复用解决方案**。GoF（Gang of Four，四人组）将模式分为三类：
- **创建型**：对象的创建机制（单例、工厂、建造者、原型）
- **结构型**：对象组合成更大结构（适配器、装饰器、代理、门面、桥接、组合、享元）
- **行为型**：对象间的职责分配与算法封装（策略、观察者、命令、模板方法、迭代器、中介者、备忘录、状态、职责链、访问者、解释器）

**版本基准**：universal

# 单例模式

## 定义

单例模式是一种**实例唯一性保证机制**：通过拦截对象构造路径，使得同一标识符（类名/模块路径）在整个程序生命周期内映射到同一块堆内存。形式上，它将类型到实例的映射约束为**唯一存在命题**（ $\exists!$ ）：

$\exists! x \in I:\ \text{instance}(x)$

这表示在整个程序状态空间 $\Sigma$ 中，存在恰好一个实例 $x$ 满足 instance 谓词。

## 数学模型

**唯一性不变式**：对于任意调用序列 $c_1, c_2, \dots, c_n$ （每次调用 `__new__` 或等价构造），有：

$\forall i, j:\ 1 \leq i < j \leq n \implies \text{addr}(S_i) = \text{addr}(S_j)$

其中 $S_k$ 是第 $k$ 次调用返回的实例地址。

**实例化状态机**：

$S_0 = \emptyset$
$S_{c+1} = \begin{cases} \text{allocate}() & \text{if } S_c = \emptyset \\ S_c & \text{otherwise} \end{cases}$

**线程安全约束的形式化**：设 $T$ 为并发线程集合， $L$ 为互斥锁。安全实例化当且仅当：

$\forall t \in T:\ t.\text{check}() \implies t.\text{acquire}(L) \land t.\text{create}() \land t.\text{release}(L)$

双重检查锁（DCLP）将"检查-分配"序列分解为无锁快速路径（首次）和加锁慢路径（竞争时），将竟态窗口压缩至最小。设 $W$ 为竟态窗口宽度，则 DCLP 将 $W$ 从整个构造过程压缩为两次检查之间的时间间隔。

**延迟初始化的代价模型**：设第 $i$ 次调用触发构造的概率为 $p_i$ ，则：

$\mathbb{E}[T_{\text{lazy}}(n)] = \sum_{i=1}^{n} p_i \cdot T_{\text{construct}} + (1-p_i) \cdot T_{\text{lookup}}$

其中 $T_{\text{lookup}}$ 是缓存查找的 O(1) 操作。首次调用承担全部构造代价，后续调用享受 O(1) 查找。

**归约终点**：单例的实质是**全局可见的弱求值缓存**——实例按需创建（lazy）或启动时创建（eager），之后所有访问定向到同一内存位置读写共享状态。这可进一步归约为**进程内全局命名绑定**——操作系统进程作为隔离域，类名作为命名空间，实例地址作为绑定值。

## 数据流

<pre>
调用方 A ──→ type.__new__(cls)          调用方 B ──→ type.__new__(cls)
     │                                      │
     │  首次构造                             │  实例已存在
     ▼                                      ▼
┌─────────────┐                    ┌─────────────┐
│ _instance   │                    │ _instance   │
│   is None?  │                    │   is None?  │
│     Yes     │                    │     No      │
└──────┬──────┘                    └──────┬──────┘
       │                                    │
       ▼                                    ▼
┌─────────────┐                    ┌─────────────┐
│ acquire(L)  │                    │ return      │
│ if held:    │                    │ _instance   │
│   wait      │                    │ (零拷贝)    │
│ ──────────  │                    └─────────────┘
│ allocate()  │
│ → 存储到    │
│   _instance │
│ release(L)  │
└─────────────┘
</pre>

**所有权流转**：
- 实例创建后，所有调用方通过 `__new__` 返回的同一引用访问共享状态，无所有权转移
- 实例的生命周期管理：Python 的 GC 负责回收，但单例模式通常在进程生命周期内不释放全局引用
- 状态修改通过共享的 `__dict__` 或类属性，所有调用方看到相同状态

**线程安全数据流分析**：
- 无锁路径（`_instance is not None`）：直接返回引用，零同步开销
- 加锁路径：互斥锁序列化所有竞争线程，确保构造操作的原子性
- DCLP 的关键优化：避免每次调用都加锁，将锁竞争限定在首次构造

## 机制

### 模块级单例：基于导入语义的天然单例

Python 的 `import` 机制本身就是单例实现：模块在首次导入时执行顶层代码并缓存于 `sys.modules`，后续所有导入获取同一对象引用。

**资源所有权**：模块对象的生命周期绑定程序进程，导入时创建，解释器退出时销毁。模块级单例的优势在于无需额外同步机制——import 是线程安全的（解释器级锁保护）。

**约束**：模块级单例在多进程环境下失效——每个 worker 进程独立导入模块，各自持有独立实例。若需跨进程共享单例，必须使用共享内存或进程间通信机制。

**适用场景**：应用配置、数据库连接池、logger 实例。

### 类装饰器单例：基于闭包的实例缓存

装饰器在函数对象外层维护 `instances` 字典，键为被装饰类，值为实例。关键性质：**实例缓存在闭包作用域内，不属于类属性**，因此不同类的单例互相独立。

**约束**：装饰器单例在多线程环境下存在竞态——两个线程同时判断 `cls not in instances` 可能同时为真，导致创建两个实例。解决方案：使用 `threading.Lock` 保护检查-创建序列。

### `__new__` 单例：实例级别的锁保护

`__new__` 是实例分配前的拦截点，双重检查锁（DCLP）在加锁前后各判断一次：

```python
def __new__(cls):
    if cls._instance is None:          # 检查1：无锁快速路径
        with cls._lock:                # 获取锁
            if cls._instance is None:  # 检查2：加锁后确认
                cls._instance = super().__new__(cls)
    return cls._instance
```

**约束**：Python 的 GIL 使得大多数对象操作线程安全，但 `if cls._instance is None` 这种读-分配序列在 C 层面不是原子的——极端情况下仍可能重入。真正安全的实现需要 `threading.Lock()`。

**DCLP 的底层原理**：检查1是"观察"，检查2是"确认"。在检查1和检查2之间存在竟态窗口，另一线程可能已完成构造。检查2是安全保证——即使窗口内发生重入，加锁后的二次检查确保只创建一个实例。

### Borg 模式：状态共享而非引用共享

Borg 不保证"同一引用"，而保证"同一状态"。所有实例共享同一个 `__dict__`，修改一个实例的状态，另一个立即可见：

$addr(b1.\__dict__) = addr(b2.\__dict__) = \text{addr}(Borg.\_shared)$

这在语义上等价于单例，但允许 `b1 is not b2`，利于测试（可以创建新实例而不污染全局引用）。

**数学本质**：Borg 将单例的等价关系从"引用相等"弱化为"状态相等"：

$\forall b1, b2 \in \text{Borg}:\ b1 \sim b2 \iff b1.\__dict__ = b2.\__dict__$

### 单例的销毁与重置

**标准单例的销毁问题**：程序退出前单例通常不执行清理；全局资源共享导致测试间状态污染。

**解决方案**：
- **方法一**：Borg 模式（推荐），每次测试前重置共享状态
- **方法二**：添加 `reset()` 类方法，显式清空 `_instance`
- **方法三**：使用 pytest fixture 管理单例生命周期

**设计权衡**：单例的"全局状态"本质上是隐式依赖——调用方通过类名而非参数显式获取状态。这使测试困难，因为无法在测试中替换单例实现。Borg 模式通过状态重置部分缓解此问题。

## 约束与违反后果

| 约束 | 违反后果 |
|------|---------|
| 线程安全实现 | 多实例同时存在，违反唯一性保证 |
| 延迟初始化时序确定 | 循环导入导致部分初始化，进程僵死 |
| 单例不应持有昂贵的资源 | 进程退出时资源泄漏（如未关闭的文件描述符） |
| 测试需可重置 | 测试间状态污染，测试隔离失效，测试结果不可靠 |
| 多进程环境需显式共享 | fork 后子进程各自创建实例，唯一性跨进程失效 |
| 装饰器单例需线程锁 | 多线程并发注册可能绕过检查，创建多个实例 |

## 参考存根

```python
import threading

class SafeSingleton:
    _lock = threading.Lock()
    _instance = None

    def __new__(cls):
        if cls._instance is None:
            with cls._lock:
                if cls._instance is None:
                    cls._instance = super().__new__(cls)
        return cls._instance

# Borg 模式
class Borg:
    _shared_state = {}

    def __new__(cls):
        obj = super().__new__(cls)
        obj.__dict__ = cls._shared_state
        return obj
```

# 工厂模式

## 定义

工厂模式是一类**对象创建解耦机制**的核心抽象：通过引入中间层（工厂），将"对象创建"这一操作从调用方的词法作用域中分离，使创建逻辑可配置、可替换、运行时可变。工厂本质是一个**偏函数**：

$f: \text{TypeId} \rightharpoonup \text{Object}$

其中 $\text{TypeId}$ 是类型标识符集合， $\text{Object}$ 是实例集合， $f$ 对未注册的标识符无定义（抛出异常）。

## 数学模型

**工厂函数性质**：设产品类型集合 $P = \{p_1, p_2, \dots, p_n\}$ ，工厂函数 $F: \text{TypeId} \rightarrow P$ 满足：

$\forall tid,\ F(tid) = p \iff p \in P \land \text{constructor}(p) \text{ 被调用}$

**唯一性**：同一 `tid` 两次调用返回的两个实例满足引用相等（若产品类自身非单例）或状态相等（若需要独立实例）：

$F(tid)_1 \sim F(tid)_2 \quad \text{或} \quad F(tid)_1 =_s F(tid)_2$

**开闭原则的数学表达**：令 $\mathcal{F}$ 为工厂函数空间， $\mathcal{P}$ 为产品类型空间。扩展产品集 $P' = P \cup \{p_{n+1}\}$ 只需扩展 $F$ 的定义域，无需修改 $F$ 的代码实现——这在范畴论中对应**自然变换**的延拓。形式化地：

$\text{extend}(F, p_{n+1}) = F' \quad \text{s.t.} \quad F'|_{\text{dom}(F)} = F \land F'(tid_{n+1}) = p_{n+1}$

**注册表工厂**：运行时映射 $R: \text{Name} \rightarrow \text{Class}$ 满足 $R[name] = cls$ 当且仅当 `register(name, cls)` 已被调用。`create(name)` 求值结果为 $R[name]()$ 。

**工厂方法的参数化多态**：设工厂方法签名 $m: \text{Context} \rightarrow \text{Product}$ ，在子类 $C_1, C_2$ 中有不同实现：

$m_{C_1}(ctx) = p_1,\quad m_{C_2}(ctx) = p_2$

同一调用表达式在不同子类的实例上有不同求值结果，这正是参数化多态的核心特征。

**抽象工厂的产品族约束**：设产品族 $F_i = \{p_{i1}, p_{i2}, \dots, p_{im}\}$ ，同一工厂创建的产品必须来自同一族：

$\forall i, j:\ \text{Factory}_i.create(k) \in F_i,\quad \text{Factory}_j.create(k) \in F_j$

且 $F_i \cap F_j = \emptyset$ （不同族产品不混用）。

**归约终点**：工厂方法可归约为**依赖倒置**——高层模块（调用方）不依赖低层模块（具体产品），两者都依赖抽象（工厂接口）。在 SOLID 原则中，这是 DIP（Dependency Inversion Principle）的具体实现。

## 数据流

<pre>
调用方 ──→ Factory.create("dog") ──→ 映射查找 ──→ Dog() ──→ Animal 实例
                │

                │ 工厂封装了 new Dog() 的细节
                ▼

         │  映射字典          │

</pre>

**调用方与产品类型的解耦**：
- 调用方持有 Factory 引用，不持有具体产品类的直接引用
- 产品类型标识符（字符串）是调用方与工厂之间的唯一契约
- 运行时可动态改变映射关系，实现热更新（需重启）

**工厂方法模式的数据流**：

## 机制

### 简单工厂：集中映射分发

简单工厂将类型标识符到类的映射维护在一个字典或 `if/elif` 链中。

**约束**：映射表是静态的——新增产品必须修改工厂代码，违反开闭原则。适用场景：产品类型相对稳定，创建逻辑简单的场景。

**静态映射的实现**：

```python
class SimpleFactory:
    _mapping = {
        "dog": Dog,
        "cat": Cat,
    }

    @classmethod
    def create(cls, name: str):
        cls_ = cls._mapping.get(name)
        if cls_ is None:
            raise ValueError(f"Unknown product: {name}")
        return cls_()
```

**工厂的返回类型协变**：若 `Dog extends Animal`，则工厂方法返回类型可协变为 `Animal`。调用方不应依赖具体子类的类型信息。

### 注册表工厂：运行时插件架构

注册表工厂将注册行为运行时化：通过 `register(name, cls)` 动态添加映射，工厂本身无需改动。这本质上是**插件架构**的雏形，新增产品无需重新编译工厂代码。

**注册机制的核心性质**：
- 注册与使用分离：插件可在工厂创建后注册
- 延迟加载：直到首次 `create()` 才触发类的导入
- 反射能力：`register` 内部使用 `__init_subclass__` 或元类自动注册

**约束**：注册表是非线程安全的——同时注册可能破坏映射一致性。若需线程安全，需要锁保护或使用线程安全的数据结构。

### 工厂方法模式：创建职责下放到子类

父类定义创建接口但不实现，具体创建逻辑由子类决定。

**数学含义**：工厂方法是一种**参数化多态**的实现——同一创建调用 `factory.create()` 在不同子类中有不同解释：

$f_{\text{CreatorA}} \rightarrow p_A,\quad f_{\text{CreatorB}} \rightarrow p_B$

**约束**：每新增一种产品就需要新增一个 Creator 子类，如果产品种类极多可能导致类爆炸。解决方案：使用注册表工厂替代类爆炸。

### 抽象工厂模式：产品族的统一分发

抽象工厂保证**产品族**内各产品间的兼容性——同一个工厂创建的所有产品属于同一主题（Windows 主题 vs Mac 主题）。

**数学本质**：抽象工厂定义了一个**笛卡尔积的分区**：

$\text{Factory}_{\text{Windows}} \rightarrow \{\text{WinButton}, \text{WinTextField}\}$
$\text{Factory}_{\text{Mac}} \rightarrow \{\text{MacButton}, \text{MacTextField}\}$

**约束**：如果要在已有工厂中新增产品（比如 WinComboBox），必须修改抽象工厂接口及其所有子类——这是抽象工厂的最大弱点。解决方案：使用**抽象工厂的注册表扩展**。

### 工厂 vs 建造者

| | 工厂 | 建造者 |
|--|------|--------|
| 创建结果 | 单一完整对象 | 多部件组合对象 |
| 创建过程 | 一次分发，无中间状态 | 分步构建，有中间态 |
| 关注点分离 | 创建逻辑 vs 使用逻辑 | 构建步骤 vs 表示 |
| 扩展方式 | 新增工厂/注册 | 新增 Builder 方法 |
| 参数化 | 类型标识符 | 链式方法调用 |

**核心区别**：工厂一次分发产生完整对象，建造者分步累积产生完整对象。这对应于数学上的**多元组构造**vs**累进构造**。

## 参考存根

```python
class AnimalFactory:
    _registry: dict[str, type] = {}

    @classmethod
    def register(cls, name: str, animal_cls: type):
        cls._registry[name] = animal_cls

    @classmethod
    def create(cls, name: str):
        cls_ = cls._registry.get(name)
        if cls_ is None:
            raise ValueError(name)
        return cls_()

# 使用
AnimalFactory.register("dog", Dog)
AnimalFactory.register("cat", Cat)
animal = AnimalFactory.create("dog")
```

# 建造者模式

## 定义

建造者模式是一种**分步对象构造协议**：将复杂对象的创建过程分解为一系列离散的、命名的步骤，主调用者通过声明式链式调用描述最终产物，而非传入位置参数。构建过程可形式化为产品状态空间 $\mathcal{S}$ 上的**偏序构建序列**。

## 数学模型

**偏序构建关系**：设部件集合 $\mathcal{P} = \{p_1, p_2, \dots, p_m\}$ ，构建步骤集合 $\mathcal{K} = \{k_1, k_2, \dots, k_m\}$ 。每个步骤 $k_i$ 定义偏序关系：

$k_i \prec k_j \iff \text{步骤 } i \text{ 必须在步骤 } j \text{ 之前完成}$

偏序的传递闭包 $\prec^*$ 约束 Builder 必须遵循的执行顺序。例如，在房屋建造中：

$\text{walls} \prec \text{roof} \prec \text{paint}$

这表示先砌墙才能盖屋顶，先盖屋顶才能粉刷。

**状态迁移函数**：设产品状态空间 $\mathcal{S}$ ，初始态 $s_0 \in \mathcal{S}$ 。每个步骤 $k_i$ 对应状态迁移函数 $f_i: \mathcal{S} \rightarrow \mathcal{S}$ ：

$s_{i+1} = f_i(s_i)$

完整构建序列的最终产物为：

$s_n = (f_n \circ f_{n-1} \circ \cdots \circ f_1)(s_0)$

**不变式验证**：Builder 在 `build()` 时验证产品不变式 $\phi: \mathcal{S} \rightarrow \{\text{True}, \text{False}\}$ 。仅当 $\phi(s_n) = \text{True}$ 时构建成功：

$\text{build}() \triangleq \phi(s_n) ? s_n : \bot$

其中 $\bot$ 表示构建失败（抛出异常）。

**链式调用的函数式视图**：设链式调用 `builder.step_a().step_b().step_c()`，每步返回 Builder 自身：

$\text{chain} = \lambda b.\ b.step\_c(b.step\_b(b.step\_a(b)))$

这本质上是函数组合的左倾形式。

**归约终点**：链式 Builder 可归约为**流畅接口（fluent interface）** + **建造者模式**——方法链返回 `self`，使调用可读性接近自然语言陈述。这与 Unix 的管道 `cmd1 | cmd2 | cmd3` 同构，只是用方法链替代了进程间管道。

## 数据流

<pre>

<pre>

**数据所有权流转**：
- `House()` 在 Builder 内部创建，所有权归 Builder
- `build()` 返回 `House` 实例，所有权转移给调用方
- Builder 内部状态在 build() 后可选择清空（复用）或保持（再次 build 同一配置）

## 机制

### Director（导演类）：构建流程封装

Director 封装预定义的**构建配方**（build recipe），调用者可选择标准模板而不必关心步骤细节。Director 本身不持有产品状态，只持有 Builder 引用：

$\text{Director.build\_luxury()} \triangleq \text{Builder.walls("stone").roof("copper").windows(8).build()}$

这将"构建步骤顺序"与"每个步骤的参数选择"解耦——换新产品只需新建 Builder，换配方只需调 Director 方法。

**Director 的数学本质**：Director 是构建步骤偏序 $\prec^*$ 的**具体实例化**。不同的 Director 方法对应不同的 $\prec^*$ 线性扩展。

### Builder 的不变式验证

复杂对象往往有内部不变式约束（如"房屋必须有门且数量≥1"）。Builder 在 `build()` 时统一验证：

```python
def build(self) -> House:
    if self._house.walls is None:
        raise BuildError("walls required")
    if self._house.windows < 1:
        raise BuildError("at least one window")
    return self._house
```

**验证策略的选择**：
- **即时验证**（每个 setter）：快速失败，违反约束时立即报错
- **延迟验证**（build() 时）：允许 Builder 内部临时状态合法，支持"先有墙再有窗"等中间态

**不变式的数学表示**：设产品状态空间 $\mathcal{S}$ ，不变式 $\phi$ 是 $\mathcal{S}$ 的一个子集：

$\phi(s) = \text{True} \iff s \in \mathcal{S}_{\text{valid}}$

只有 $s_n \in \mathcal{S}_{\text{valid}}$ 时，build() 才返回有效产品。

### dataclasses + Builder 分离

`@dataclass` 定义数据的静态结构（字段名、类型、默认值），Builder 负责运行时填充——这将"数据schema"与"数据填充逻辑"分离：

```python
@dataclass
class Pizza:
    size: str = ""
    cheese: bool = False
    pepperoni: bool = False
```

Builder 持有 `Pizza` 实例，链式方法逐步填充，最终 `build()` 返回完全初始化的 Pizza。dataclass 保证字段访问有类型提示，Builder 保证构建过程可读。

**这种分离的数学意义**：dataclass 定义了产品的**类型空间**，Builder 在该类型空间的子集上做**路径遍历**。

### Builder vs 工厂

| | 建造者 | 工厂 |
|--|------|------|
| 产品形态 | 多部件组合（对象结构复杂） | 单一对象 |
| 构建过程 | 可中断（有中间态） | 不可中断（原子构造） |
| 参数风格 | 声明式，命名参数 | 命令式，通常位置参数 |
| 表示分离 | 构建逻辑与表示分离 | 创建与表示合一 |
| 扩展方式 | 新增 Builder 方法 | 新增工厂/注册 |

**核心区别**：工厂一次分发产生完整对象，建造者分步累积产生完整对象。这对应于数学上的**多元组构造**vs**累进构造**。

## 参考存根

```python
class PizzaBuilder:
    def __init__(self, size: str):
        self._pizza = Pizza(size=size)

    def cheese(self) -> "PizzaBuilder":
        self._pizza.cheese = True
        return self

    def pepperoni(self) -> "PizzaBuilder":
        self._pizza.pepperoni = True
        return self

    def build(self) -> Pizza:
        return self._pizza

# 使用
pizza = PizzaBuilder("large").cheese().pepperoni().build()
```

# 策略模式

## 定义

策略模式是一种**算法可替换性抽象**：将一族算法 $A = \{a_1, a_2, \dots, a_n\}$ 各自封装为独立对象，并赋予调用方在运行时选择具体算法的能力。数学上，策略接口定义了一个**行为空间** $\mathcal{B}$ ，每个具体策略是 $\mathcal{B}$ 的一个实例：

$\text{Strategy}: \mathcal{B},\quad \forall s \in A,\ s: \text{Input} \rightarrow \text{Output}$

Context 持有策略引用但本身不实现算法，策略可随时替换而不影响 Context 的结构。

## 数学模型

**策略分派代价**：设策略集合 $\mathcal{S} = \{s_1, s_2, \dots, s_n\}$ ，Context 的 `execute(x)` 操作分派到策略 $s_i$ 的代价为：

$T_{\text{dispatch}}(x) = \underbrace{T_{\text{lookup}}(s_i)}_{\text{策略查找}} + \underbrace{T_{s_i}(x)}_{\text{算法执行}}$

其中 $T_{\text{lookup}}$ 是从当前策略引用到具体实现的跳转代价（虚函数表查表或字典查找）， $T_{s_i}$ 是策略 $s_i$ 自身的算法复杂度。

**策略选择复杂度**：运行时切换策略 $s_i \rightarrow s_j$ 的代价为 $O(1)$ （直接指针替换），不触发任何算法重计算。

**开放封闭原则的数学表达**：新增策略 $a_{n+1}$ 定义新映射 $s_{n+1}: \text{Input} \to \text{Output}$ ，无需修改 Context 代码——在 $\mathcal{B}$ 上做集合扩展：

$\mathcal{B}' = \mathcal{B} \cup \{s_{n+1}\}$

**策略接口的契约**：设策略接口方法签名为 $m: \ctx \times \text{Input} \rightarrow \text{Output}$ 。所有具体策略必须满足：

$\forall s \in \mathcal{S}:\ m_s \text{ 与 } m_{\text{interface}} \text{ 类型兼容}$

在 Python 的结构化类型中，这表现为参数和返回类型的协变/逆变关系。

**归约终点**：策略模式本质是**函数作为一等公民**的面向对象伪装——每个策略对象持有一个函数（算法），Context 调用该函数。这与高阶函数 `map(algorithm, data)` 同构，只是包装进了类和对象系统。在 lambda 演算的视角下，策略模式是 $\beta$-归约的面向对象实现。

## 数据流

<pre>
调用方                    Context                    Strategy
  │                          │                          │
  │ set_strategy(SortA)      │                          │
  │ ───────────────────────→ │                          │
  │                          │                          │
  │ sort([3,1,2])            │                          │
  │ ───────────────────────→ │                          │
  │                          │ self._strategy.sort(data) │
  │                          │ ───────────────────────→ │
  │                          │                          │
  │                          │        SortA.sort([3,1,2])│
  │                          │                          │
  │                          │ ←────────────────────────│
  │                          │        [1,2,3]           │
  │ ←──────────────────────── │                          │
  │        [1,2,3]           │                          │
</pre>

**策略替换的数据流**：

<pre>
StrategyA (当前)           StrategyB (新)
┌──────────────┐         ┌──────────────┐
│ sort([3,1,2])│         │ sort([3,1,2])│
│   → [1,2,3]  │   替换   │   → [3,2,1]  │

                            │

                    │ _strategy = B  │

                    └────────────────┘
</pre>

**所有权与生命周期**：
- Context 持有策略的引用（强引用或弱引用）
- 策略的生命周期由调用方管理，或与 Context 共享
- 策略替换不影响 Context 的其他状态

## 机制

### 策略接口：行为契约

策略接口（通常是 ABC）定义了算法的**签名契约**，确保所有具体策略可互换：

```python
class SortStrategy(ABC):
    @abstractmethod
    def sort(self, data: list) -> list: ...
```

契约的核心是**输入输出类型**：同输入类型，同输出类型，具体算法实现自由。这使策略间可相互替换而不影响调用方。

**约束**：策略接口的变化（增删方法）会导致所有具体策略都要修改——策略接口本身应设计为稳定的。设计良好的策略接口是"最小接口"——只暴露必要的方法，不暴露内部状态。

### 函数式策略：去类化的算法封装

Python 的函数是一等公民，可以直接作为策略传递，无需包装成类：

```python
class Sorter:
    def __init__(self, fn):
        self._fn = fn

    def sort(self, data):
        return self._fn(data)
```

这与策略模式的本质完全一致，只是**省略了策略接口的显式声明**——类型注解可作为隐式接口。在简单场景下，函数式策略避免了类膨胀。

**何时用类 vs 函数**：当策略有状态时用类（维护内部计数器、缓存等），当策略无状态时用函数。

### 策略选择策略

Context 如何选择策略有三种常见模式：

- **构造时注入**：调用方在创建 Context 时决定策略，策略生命周期与 Context 相当
- **运行时切换**：`set_strategy()` 支持动态替换，允许同一 Context 在不同阶段使用不同算法
- **委托选择**：Context 内部维护策略映射表，根据输入特征自动路由到对应策略（这是策略模式与简单工厂的组合）

**委托选择的数学模型**：设路由函数 $r: \text{Input} \rightarrow \text{StrategyId}$ ：

$\text{execute}(x) = \text{Strategy}_{r(x)}.\text{apply}(x)$

这将策略选择从"用户决定"变为"数据驱动"。

### 策略 vs 条件分支

| | 策略模式 | 条件分支 |
|--|---------|---------|
| 新增算法 | 新增策略类 | 修改原函数 |
| 可测试性 | 各策略独立单元测试 | 逻辑散落难以隔离 |
| 运行时切换 | 支持 | 需要变量重新赋值 |
| 开闭原则 | 扩展开放，修改封闭 | 每次改动都有修改风险 |
| 内存开销 | 策略对象额外内存 | 无额外对象 |

**条件分支的性能优势**：在分支数量少、场景固定时，条件分支的指令缓存局部性优于策略的虚函数分派。但在分支数量多、需运行时切换时，策略模式的可维护性优势显著。

### 策略模式与依赖注入

策略模式是依赖注入（DI）的特例——Context 依赖抽象的策略接口，具体策略由外部注入。这与 DI 容器结合时，策略实现可在配置文件中声明，实现声明式编程。

## 参考存根

```python
from abc import ABC, abstractmethod

class SortStrategy(ABC):
    @abstractmethod
    def sort(self, data: list) -> list: ...

class QuickSort(SortStrategy):
    def sort(self, data: list) -> list:
        if len(data) <= 1:
            return data
        pivot = data[len(data) // 2]
        return self.sort([x for x in data if x < pivot]) \
               + [x for x in data if x == pivot] \
               + self.sort([x for x in data if x > pivot])

class Sorter:
    def __init__(self, strategy: SortStrategy):
        self._strategy = strategy

    def set_strategy(self, strategy: SortStrategy):
        self._strategy = strategy

    def sort(self, data: list) -> list:
        return self._strategy.sort(data)
```

# 观察者模式

## 定义

观察者模式是一种**状态变更广播协议**：定义对象间的一对多依赖关系，当主题（Subject）的内部状态发生变更时，系统主动遍历所有已注册的观察者（Observer）并触发其更新回调。从集合论角度看，Subject 维护一个观察者集合 $\mathcal{O}$ ：

$\mathcal{O} = \{o_1, o_2, \dots, o_n\}$

状态变更时执行广播函数 $B: \text{State} \rightarrow \forall o \in \mathcal{O},\ o.\text{update}(state)$ 。

## 数学模型

**通知可靠性建模**：设 Subject 状态为 $s \in \mathcal{S}$ ，通知可靠性的度量指标为交付率 $\eta$ ：

$\eta = \frac{\text{成功交付的观察者数量}}{\text{注册观察者总数}}$

同步通知（所有观察者在同一调用栈内完成更新）时，若某观察者 $o_k$ 的 `update` 抛出异常且未捕获，通知链中断：

$\text{notify}(s) = \begin{cases} \{u_i(s) \mid i < k\} & \text{若 } o_k.\text{update} \text{ 抛出异常} \\ \{u_i(s) \mid i \in [1,n]\} & \text{否则} \end{cases}$

即异常导致 $\eta < 1$ （部分观察者未被通知）。

**异步通知的可靠性**：若通知改为异步，所有 $o_i.\text{update}(s)$ 并发执行，则：

$\eta_{\text{async}} = \prod_{i=1}^{n} \mathbb{P}(o_i.\text{update} \text{ 不抛出异常})$

观察者之间的执行独立无关联，任一异常不影响其他观察者的交付。

**广播操作的数学表达**：

$\text{notify}(s) \triangleq \{u_i(s) \mid o_i \in \mathcal{O}\}$

其中 $u_i: \mathcal{S} \rightarrow \mathcal{R}_i$ 是观察者 $o_i$ 的更新函数。

**订阅关系的动态性**：设注册函数 $\text{attach}: \mathcal{O} \rightarrow \text{Unit}$ ，注销函数 $\text{detach}: \mathcal{O} \rightarrow \text{Unit}$ 。观察者集合随时间变化：

$\mathcal{O}_{t+1} = \mathcal{O}_t \cup \{o_{\text{new}}\} \quad \text{或} \quad \mathcal{O}_{t+1} = \mathcal{O}_t \setminus \{o_{\text{old}}\}$

**归约终点**：观察者模式是**发布-订阅（pub-sub）语义**的特例——观察者是主动订阅方，Subject 是被动发布方。相比通用消息队列，观察者模式强调同步更新（所有观察者在同一调用栈内完成更新）。从信息流的角度，它是一种**有优先级的扇出（fan-out）广播**。

## 数据流

<pre>

## 机制

### 推模式 vs 拉模式

**推模式**（Push）：Subject 主动将变更数据推送给观察者。Subject 控制广播内容，观察者被动接收。

$u_i(s) = f_{\text{push}}(s_{\text{change}})$

**约束**：Subject 必须知道观察者需要什么数据，造成不必要的耦合。若 Subject 推送过多数据，观察者需过滤；若推送过少，观察者可能需额外查询。

**拉模式**（Pull）：Subject 只通知"状态已变更"，观察者自行获取所需数据。

$u_i(s) = f_{\text{pull}}(\text{subject.get\_data}())$

**约束**：观察者需知道 Subject 的内部结构（属性路径），增加耦合。

**混合模式**：Subject 推送足够的状态摘要，观察者按需拉取完整数据。这在语义上是一种**承诺（promise/future）模式**的变体。

### 弱引用观察者：内存泄漏防护

观察者生命周期通常由调用方管理，但如果观察者被遗忘（无引用也无 deregister），Subject 会一直持有引用导致内存泄漏。`weakref.ref` 允许 Subject 持有弱引用而不阻止垃圾回收：

```python
import weakref

class Subject:
    def __init__(self):
        self._observers = weakref.WeakSet()
```

**约束**：`WeakSet` 不支持同一对象的重复注册（去重），若需重复注册需使用 `WeakValueDictionary`。

**内存泄漏的数学分析**：设观察者集合 $\mathcal{O}$ 的生命周期为 $L_o$ ，Subject 的生命周期为 $L_s$ 。若持有强引用，则 $\forall o \in \mathcal{O},\ L_o \geq L_s$ （观察者至少与 Subject 一样长）。使用弱引用可打破此约束。

### 异步通知：非阻塞广播

同步通知的问题：当某个 Observer.update() 执行耗时操作，会阻塞整个通知链。异步通知将每个 update 封装为 Task：

```python
async def notify_async(self, message):
    tasks = [asyncio.create_task(obs.update(message)) for obs in self._observers]
    await asyncio.gather(*tasks)
```

**约束**：异步通知打破了"所有观察者同步完成更新"的假设，需要考虑并发安全问题（多个观察者同时读写共享状态）。

**异步通知的代价模型**：

$T_{\text{async\_notify}} = \max_i(T_{o_i.\text{update}}) + T_{\text{schedule}}$

其中 $T_{\text{schedule}}$ 是任务调度开销。同步通知的代价是 $\sum_i T_{o_i.\text{update}}$ （顺序执行）。

### 回调式实现：函数一等公民的直接应用

Python 中 `Callable` 可直接作为观察者，省去 Observer 接口的类包装：

```python
class EventManager:
    def subscribe(self, event: str, cb: Callable):
        self._callbacks.setdefault(event, []).append(cb)

    def emit(self, event: str, data=None):
        for cb in self._callbacks.get(event, []):
            cb(data)
```

这本质上是**命名事件的多播委托**，是观察者模式的 Pythonic 简化形式。

**闭包捕获的观察者**：当回调函数是闭包时，它可能捕获外部变量。这引入了一个隐式依赖——观察者的行为依赖于闭包捕获的变量值。

## 约束与违反后果

| 约束 | 违反后果 |
|------|---------|
| 观察者需及时 deregister | 内存泄漏（被遗忘的观察者仍被 Subject 引用） |
| update 内避免修改 Subject | 嵌套通知可能导致递归或状态不一致 |
| 观察者处理异常 | 一个观察者异常会中断后续通知（同步模式下） |
| 通知顺序依赖 | 观察者对通知顺序有隐式依赖，添加新观察者可能破坏假设 |
| 避免循环依赖 | A 观察 B 同时 B 观察 A，导致无限递归 |

## 参考存根

```python
from abc import ABC, abstractmethod
import weakref

class Observer(ABC):
    @abstractmethod
    def update(self, message: str): pass

class Subject:
    def __init__(self):
        self._observers: list[Observer] = []

    def attach(self, obs: Observer):
        if obs not in self._observers:
            self._observers.append(obs)

    def detach(self, obs: Observer):
        self._observers.remove(obs)

    def notify(self, message: str):
        for obs in self._observers[:]:  # 复制列表避免迭代中修改
            obs.update(message)
```

# 装饰器模式

## 定义

装饰器模式是一种**运行时功能组合协议**：通过递归包装（wrap）机制，在不修改被装饰对象本身的前提下，动态地为其附加新行为。每个装饰器实现与被包装对象相同的接口，调用方无需感知底层实际对象是哪一层。

装饰器链使对象在运行时获得叠加的行为能力，这对应于**组合模式**的一种应用：

$O \xrightarrow{D_1} D_1(O) \xrightarrow{D_2} D_2(D_1(O)) \xrightarrow{D_3} \cdots$

## 数学模型

**函数复合模型**：设原始操作为 $o: X \rightarrow Y$ ，装饰器 $d$ 在调用前后注入行为 $b_{\text{before}}: X \rightarrow X_{\text{mod}}$ 和 $b_{\text{after}}: Y \rightarrow Y_{\text{mod}}$ ：

$\tilde{d}(x) = b_{\text{after}}(o(b_{\text{before}}(x)))$

装饰器链 $(D_k \circ D_{k-1} \circ \cdots \circ D_1)(o)$ 的求值为：

$D_k(D_{k-1}(\dots D_1(o(x))\dots )) = (D_k \circ D_{k-1} \circ \cdots \circ D_1)(x)$

**接口同构性**：设 $\mathcal{I}$ 为接口类型， $O$ 为原始对象， $D_i$ 为装饰器。则：

$O \cong D_1(O) \cong D_2(D_1(O)) \cong \cdots \cong (D_k \circ \cdots \circ D_1)(O)$

其中 $\cong$ 表示"满足同一接口 $\mathcal{I}$"。这是装饰器可无限堆叠的数学基础。

**装饰器链的复杂度**：对输入 $x$ 的 $k$ 层装饰器链调用，时间复杂度为：

$T_{\text{decorated}}(x) = \sum_{i=0}^{k} T_{D_i}(x_i)$

其中 $T_{D_0} = T_o$ 是原始操作的复杂度， $T_{D_i}$ 是第 $i$ 层装饰器的附加代价。

**装饰器的代数性质**：
- **结合律**：(D1 ∘ D2) ∘ D3 = D1 ∘ (D2 ∘ D3)
- **单位元**： $D_{\text{identity}}(o) = o$
- **交换律不成立**： $D_1 \circ D_2 \neq D_2 \circ D_1$ （顺序影响结果）

**归约终点**：装饰器链是**函数复合**的面向对象实现。`decorator(decorated_func)(*args)` 等价于 $(g \circ f)(x) = g(f(x))$ ，只是以对象方法的形式表达。在 λ 演算中，装饰器是 **η-展开** 的运行时形式——将函数 f 重写为 g∘f 其中 g 注入副作用。

## 数据流

<pre>
调用 coffee.cost()
    │
    ▼
Whip.cost()          ←── 外层装饰器（最后调用）
  │
  ├── 前置行为（可选）
  │
  ▼
Sugar.cost()
  │
  ├── 前置行为（可选）
  │
  ▼
Milk.cost()
  │
  ├── 前置行为（可选）
  │
  ▼
Coffee.cost()        ←── 原始对象（无装饰）
  │
  ├── return 5.0
  │
  ▼
Milk 返回 5.0 + 1.5
  ▼
Sugar 返回 (5.0+1.5) + 0.5
  ▼
Whip 返回 (5.0+1.5+0.5) + 2.0
  │  = 9.0
  ▼
最终结果
</pre>

**所有权流转**：每层装饰器持有对内层对象的引用，但不持有外层引用。调用栈从外向内展开，结果从内向外逐层加工。

```
装饰器链结构（组合关系）：
┌─────────────────────────────────────────────────────┐
│ Whip (持有 Sugar)                                    │
│   └─► Sugar (持有 Milk)                              │
│         └─► Milk (持有 Coffee)                       │
│               └─► Coffee (原始对象)                   │
└─────────────────────────────────────────────────────┘

调用方向：Whip → Sugar → Milk → Coffee
返回方向：Coffee → Milk → Sugar → Whip
```

## 机制

### 类装饰器：同接口包装

装饰器类与被装饰类实现同一接口，内部持有被装饰对象引用。关键性质：**使用组合而非继承**——任何 Coffee 子类都能被任何 CoffeeDecorator 装饰，这是"装饰器可堆叠"的基础。

**约束**：装饰器必须完全实现被装饰类的接口，否则调用方可能遇到 `AttributeError`。这要求装饰器在设计时就知道目标接口的全部方法。

**委托转发的实现**：

```python
class CoffeeDecorator:
    def __init__(self, coffee: Coffee):
        self._coffee = coffee

    def cost(self) -> float:
        return self._coffee.cost()  # 默认：不添加额外行为
```

子类通过覆盖特定方法添加行为，其余方法透传给被包装对象。

### 函数装饰器：闭包中的 callable 包装

函数装饰器是闭包嵌套的产物。`functools.wraps` 复制原函数元数据（`__name__`、`__doc__`），保证装饰后的函数在反射/检查时行为与原函数一致：

```python
def retry(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        for attempt in range(max_attempts):
            try:
                return func(*args, **kwargs)
            except Exception:
                if attempt == max_attempts - 1:
                    raise
    return wrapper
```

**闭包捕获的约束**：装饰器函数捕获的变量（`max_attempts`）在装饰时确定，之后不可变。若需动态参数，使用类装饰器或偏函数。

### 类作为装饰器：`__call__` 的可调用对象

Python 类本身是 callable——装饰一个类时，`@decorator` 等价于 `decorator = decorator(ClassBeingDecorated)`，返回值替代原类：

```python
class log_calls:
    def __init__(self, func):
        self._func = func

    def __call__(self, *args, **kwargs):
        print(f"Calling {self._func.__name__}")
        return self._func(*args, **kwargs)

@log_calls
def my_func(): pass
# 等价于：my_func = log_calls(my_func)
```

### 装饰器链的执行顺序

装饰器从下到上应用，从上到下执行：

```python
@D1
@D2
@D3
def f(): pass

# 等价于：D1(D2(D3(f)))
# 执行顺序：f → D3 → D2 → D1 → 返回值
```

### 装饰器 vs 继承

| | 装饰器 | 继承 |
|--|-------|------|
| 行为添加时机 | 运行时（动态） | 编译时（静态） |
| 类数量 | 按需组合，不爆炸 | $2^n$ 种组合需 $2^n$ 个子类 |
| 对象关系 | 组合（has-a） | 继承（is-a） |
| 可撤销性 | 可在链中去掉某层 | 不可撤销 |
| 适用场景 | 可选功能、交叉关注点 | 永久性扩展 |
| 运行时成本 | 额外的函数调用跳转 | 无额外跳转 |

**正交分解的角度**：装饰器模式对应于 AOP（面向切面编程）的核心思想——将横切关注点（日志、缓存、事务）与核心业务逻辑分离。数学上，这是**直和分解**在软件架构中的应用。

## 参考存根

```python
import functools

def retry(max_attempts: int):
    def decorator(func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            for attempt in range(max_attempts):
                try:
                    return func(*args, **kwargs)
                except Exception:
                    if attempt == max_attempts - 1:
                        raise
        return wrapper
    return decorator
```

# 适配器模式

## 定义

适配器模式是一种**接口兼容层抽象**：当已有接口（Adaptee）与调用方期望接口（Target）不匹配时，在两者之间插入适配器（Adapter）做双向转换，使两者能正常交互。从类型论角度看，适配器在两个接口类型之间建立了**同构映射**。

## 数学模型

**接口同构映射**：设 Target 接口类型为 $T_A$ ，Adaptee 接口类型为 $T_B$ 。适配器建立双向同构：

$h: T_A \xrightarrow{\cong} T_B$

具体地，Target 侧调用 $t: T_A$ 经适配器转换后映射为 Adaptee 侧调用 $a: T_B$ ：

$h_T: T_A \rightarrow T_B,\quad h_B: T_B \rightarrow T_A$

两者互为逆映射：

$h_T \circ h_B = \text{id}_{T_B},\quad h_B \circ h_T = \text{id}_{T_A}$

**参数映射的形式化**：设 Target 方法签名为 $t: X_T \rightarrow Y_T$ ，Adaptee 方法签名为 $a: X_A \rightarrow Y_A$ 。适配器实现转换函数：

$f_T(x) \triangleq g_T(a(h_T(x))),\quad f_A(y) \triangleq g_A(t(h_A(y)))$

其中：
- $h_T: X_T \rightarrow X_A$ （参数结构转换）
- $h_A: Y_A \rightarrow Y_T$ （返回值结构转换）
- $g_T: Y_A \rightarrow Y_T$ （Target 侧返回值适配）
- $g_A: Y_T \rightarrow Y_A$ （Adaptee 侧返回值适配）

**约束**：适配器是**被动转换器**——它不改变 Adaptee 的行为，只改变其外观。如果 Adaptee 本身行为不符合调用方预期，适配器无法修复。

**适配器的代数分类**：
- **对象适配器**：使用组合， $Adapter \xrightarrow{\text{持有}} Adaptee$
- **类适配器**：使用继承， $Adapter \leftarrow \text{继承} \rightarrow Adaptee$

**双向适配器的约束**：双向适配器同时实现两个接口，要求 $T_A$ 和 $T_B$ 的方法集合可互表示：

$\text{MethodSet}(T_A) \subseteq \text{MethodSet}(Adapter) \cap \text{MethodSet}(T_B)$

**归约终点**：适配器本质是**正交分解**的具体应用——将"接口不匹配"与"功能实现"分离，适配器处理接口层，Adaptee 处理功能层。在范畴论中，适配器是一个**函子**（functor）——它保持结构，将 $T_A$ 的对象映射到 $T_B$ 的对象，保持箭头（方法调用）。

## 数据流

<pre>
Client（调用方）
期望: target.request()
        │
        │  调用 Target 接口
        ▼
┌─────────────────┐
│  Adapter        │

│                 │
│  ├─ 参数转换 h_T │
│  ├─ 转发给      │
│  │  adaptee.    │
│  │  specific_   │
│  │  request()   │

</pre>

## 机制

### 类适配器：多重继承的接口桥接

类适配器通过多重继承同时拥有 Target 接口和 Adaptee 的实现。可以**直接覆盖** Adaptee 的方法（通过 `super()`），但不支持同时适配多个 Adaptee。

```python
class Adapter(Target, Adaptee):
    def request(self):
        # 调用 Adaptee 的特殊方法
        return self.specific_request()[::-1]
```

**约束**：多重继承在 Python 中通过 MRO（方法解析顺序）处理，复杂继承层级可能导致方法解析不直观。类适配器要求 Adapter 同时继承 Target 和 Adaptee，这在 Adaptee 是类（非接口）时改变对象的类型层次。

### 对象适配器：组合持有的委托转发

对象适配器持有 Adaptee 实例（组合），将调用转发。可适配 Adaptee 的所有子类（多态适配）。

```python
class Adapter(Target):
    def __init__(self, adaptee: Adaptee):
        self._adaptee = adaptee

    def request(self):
        return self._adaptee.specific_request()[::-1]
```

**约束**：对象适配器不能直接调用 Adaptee 的 protected 方法（需要通过 public 接口）。但可以适配多个 Adaptee（通过组合多个 Adaptee 实例）。

**适配器选择策略**：
- 需要调用 Adaptee 的内部方法 → 类适配器
- 需要适配 Adaptee 的所有子类 → 对象适配器
- 需要同时适配多个 Adaptee → 对象适配器

### 双向适配器：双向翻译

双向适配器同时实现两个接口，使两个本不兼容的系统可以互相调用。需要同时了解两个接口的语义，职责较重，易成为维护热点。

```python
class BidirectionalAdapter(Target, Adaptee):
    def __init__(self):
        self._target = TargetImpl()
        self._adaptee = AdapteeImpl()

    def request(self):
        return self._adaptee.specific_request(self._target.request())

    def specific_request(self):
        return self._target.request(self._adaptee.request())
```

**职责过重的警示**：双向适配器同时知道两个接口的语义，违反单一职责原则。当任一接口变化时，双向适配器都需要修改。

### 适配器 vs 门面模式

| | 适配器 | 门面（Facade） |
|--|-------|--------------|
| 目的 | 使不兼容接口可交互 | 简化复杂子系统接口 |
| 转换方向 | 双向翻译 | 单向简化 |
| 接口暴露 | 暴露 Adaptee 的完整接口 | 只暴露必要接口，隐藏细节 |
| 转换逻辑 | 参数/返回值映射 | 封装多个调用为一个 |
| 设计视角 | 适配已有接口 | 简化新设计的接口 |

**门面模式是适配器的对偶**：适配器将不兼容的接口变得兼容，门面将复杂的接口变得简单。两者都在接口层做转换，但方向和目的不同。

### 适配器的使用时机

适配器适用于以下场景：
1. **遗留代码集成**：已有类库的接口不符合新系统要求
2. **第三方库集成**：不同第三方库的接口风格不一致
3. **接口标准化**：将不同实现统一到同一接口下

**不适用场景**：若 Adaptee 的行为本身不符合需求，适配器无法修复——此时应考虑**装饰器**（改变行为）或**策略模式**（替换算法）。
