# 工厂模式

## 定义

工厂模式是一类**对象创建解耦机制**的核心抽象：通过引入中间层（工厂），将"对象创建"这一操作从调用方的词法作用域中分离，使创建逻辑可配置、可替换、运行时可变。工厂本质是一个**偏函数**：

$$f: \text{TypeId} \rightharpoonup \text{Object}$$

其中 $\text{TypeId}$ 是类型标识符集合，$\text{Object}$ 是实例集合，$f$ 对未注册的标识符无定义（抛出异常）。

## 数学模型

**工厂函数性质**：设产品类型集合 $P = \{p_1, p_2, \dots, p_n\}$，工厂函数 $F: \text{TypeId} \rightarrow P$ 满足：

$$\forall tid,\ F(tid) = p \iff p \in P \land \text{constructor}(p) \text{ 被调用}$$

**唯一性**：同一 `tid` 两次调用返回的两个实例满足引用相等（若产品类自身非单例）或状态相等（若需要独立实例）：

$$F(tid)_1 \sim F(tid)_2 \quad \text{或} \quad F(tid)_1 =_s F(tid)_2$$

**开闭原则的数学表达**：令 $\mathcal{F}$ 为工厂函数空间，$\mathcal{P}$ 为产品类型空间。扩展产品集 $P' = P \cup \{p_{n+1}\}$ 只需扩展 $F$ 的定义域，无需修改 $F$ 的代码实现——这在范畴论中对应**自然变换**的延拓。形式化地：

$$\text{extend}(F, p_{n+1}) = F' \quad \text{s.t.} \quad F'|_{\text{dom}(F)} = F \land F'(tid_{n+1}) = p_{n+1}$$

**注册表工厂**：运行时映射 $R: \text{Name} \rightarrow \text{Class}$ 满足 $R[name] = cls$ 当且仅当 `register(name, cls)` 已被调用。`create(name)` 求值结果为 $R[name]()$。

**工厂方法的参数化多态**：设工厂方法签名 $m: \text{Context} \rightarrow \text{Product}$，在子类 $C_1, C_2$ 中有不同实现：

$$m_{C_1}(ctx) = p_1,\quad m_{C_2}(ctx) = p_2$$

同一调用表达式在不同子类的实例上有不同求值结果，这正是参数化多态的核心特征。

**抽象工厂的产品族约束**：设产品族 $F_i = \{p_{i1}, p_{i2}, \dots, p_{im}\}$，同一工厂创建的产品必须来自同一族：

$$\forall i, j:\ \text{Factory}_i.create(k) \in F_i,\quad \text{Factory}_j.create(k) \in F_j$$

且 $F_i \cap F_j = \emptyset$（不同族产品不混用）。

**归约终点**：工厂方法可归约为**依赖倒置**——高层模块（调用方）不依赖低层模块（具体产品），两者都依赖抽象（工厂接口）。在 SOLID 原则中，这是 DIP（Dependency Inversion Principle）的具体实现。

## 数据流

<pre>
调用方 ──→ Factory.create("dog") ──→ 映射查找 ──→ Dog() ──→ Animal 实例
                │
                │ "dog" 是类型标识符，非具体类
                │ 工厂封装了 new Dog() 的细节
                ▼
         ┌──────────────────┐
         │  映射字典          │
         │  "dog" → Dog     │
         │  "cat" → Cat     │
         └──────────────────┘
</pre>

**调用方与产品类型的解耦**：
- 调用方持有 Factory 引用，不持有具体产品类的直接引用
- 产品类型标识符（字符串）是调用方与工厂之间的唯一契约
- 运行时可动态改变映射关系，实现热更新（需重启）

**工厂方法模式的数据流**：

<pre>
调用方 ──→ creator.factory_method() ──→ 子类实现 ──→ Product
                │                          │
                │  延迟绑定                 │ 运行时多态
                ▼                          ▼
         ┌─────────────────┐        ┌─────────────────┐
         │ Creator (抽象) │───────→│ ConcreteCreator │
         │ factory_method │        │ factory_method  │
         └─────────────────┘        └─────────────────┘
</pre>

**抽象工厂的数据流**：

<pre>
Client ──→ Factory.create_button() ──→ 产品族内查找 ──→ WinButton
                │                              │
                │ "产品族"约束                  │
                ▼                              ▼
         ┌─────────────────┐          ┌─────────────────┐
         │ AbstractFactory │          │ ConcreteFactory │
         │ (Win 或 Mac)    │          │ (创建同族产品)  │
         └─────────────────┘          └─────────────────┘
</pre>

## 机制

### 简单工厂：集中映射分发

简单工厂将类型标识符到类的映射维护在一个字典或 `if/elif` 链中。

**约束**：映射表是静态的——新增产品必须修改工厂代码，违反开闭原则。适用场景：产品类型相对稳定，创建逻辑简单的场景。

**静态映射的实现**：

```python
class SimpleFactory:
    _mapping = {
        "dog": Dog,
        "cat": Cat,
    }

    @classmethod
    def create(cls, name: str):
        cls_ = cls._mapping.get(name)
        if cls_ is None:
            raise ValueError(f"Unknown product: {name}")
        return cls_()
```

**工厂的返回类型协变**：若 `Dog extends Animal`，则工厂方法返回类型可协变为 `Animal`。调用方不应依赖具体子类的类型信息。

### 注册表工厂：运行时插件架构

注册表工厂将注册行为运行时化：通过 `register(name, cls)` 动态添加映射，工厂本身无需改动。这本质上是**插件架构**的雏形，新增产品无需重新编译工厂代码。

**注册机制的核心性质**：
- 注册与使用分离：插件可在工厂创建后注册
- 延迟加载：直到首次 `create()` 才触发类的导入
- 反射能力：`register` 内部使用 `__init_subclass__` 或元类自动注册

**约束**：注册表是非线程安全的——同时注册可能破坏映射一致性。若需线程安全，需要锁保护或使用线程安全的数据结构。

### 工厂方法模式：创建职责下放到子类

父类定义创建接口但不实现，具体创建逻辑由子类决定。

**数学含义**：工厂方法是一种**参数化多态**的实现——同一创建调用 `factory.create()` 在不同子类中有不同解释：

$$f_{\text{CreatorA}} \rightarrow p_A,\quad f_{\text{CreatorB}} \rightarrow p_B$$

**约束**：每新增一种产品就需要新增一个 Creator 子类，如果产品种类极多可能导致类爆炸。解决方案：使用注册表工厂替代类爆炸。

### 抽象工厂模式：产品族的统一分发

抽象工厂保证**产品族**内各产品间的兼容性——同一个工厂创建的所有产品属于同一主题（Windows 主题 vs Mac 主题）。

**数学本质**：抽象工厂定义了一个**笛卡尔积的分区**：

$$\text{Factory}_{\text{Windows}} \rightarrow \{\text{WinButton}, \text{WinTextField}\}$$
$$\text{Factory}_{\text{Mac}} \rightarrow \{\text{MacButton}, \text{MacTextField}\}$$

**约束**：如果要在已有工厂中新增产品（比如 WinComboBox），必须修改抽象工厂接口及其所有子类——这是抽象工厂的最大弱点。解决方案：使用**抽象工厂的注册表扩展**。

### 工厂 vs 建造者

| | 工厂 | 建造者 |
|--|------|--------|
| 创建结果 | 单一完整对象 | 多部件组合对象 |
| 创建过程 | 一次分发，无中间状态 | 分步构建，有中间态 |
| 关注点分离 | 创建逻辑 vs 使用逻辑 | 构建步骤 vs 表示 |
| 扩展方式 | 新增工厂/注册 | 新增 Builder 方法 |
| 参数化 | 类型标识符 | 链式方法调用 |

## 参考存根

```python
class AnimalFactory:
    _registry: dict[str, type] = {}

    @classmethod
    def register(cls, name: str, animal_cls: type):
        cls._registry[name] = animal_cls

    @classmethod
    def create(cls, name: str):
        cls_ = cls._registry.get(name)
        if cls_ is None:
            raise ValueError(name)
        return cls_()

# 使用
AnimalFactory.register("dog", Dog)
AnimalFactory.register("cat", Cat)
animal = AnimalFactory.create("dog")
```
