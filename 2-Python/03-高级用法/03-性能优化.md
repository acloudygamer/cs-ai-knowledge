# 性能优化

## 定义

性能优化是通过定位计算热点、理解约束边界、实施针对性改进来降低程序资源消耗的过程。优化的核心原则：**先测量，后优化；先正确，后快速**。直觉判断的热点往往与实际不符——profiling 才是定位热点的唯一可靠方法。

## 数学模型

### 算法复杂度理论（大O归约）

所有性能问题最终可归约为算法复杂度问题。设程序的时间开销为 $T(n)$、空间开销为 $M(n)$，其中 $n$ 是输入规模。性能优化的目标是：

$$\min T(n) \quad \text{或} \quad \min M(n)$$

在大O表示法下，我们关心的是**增长阶**而非精确值：

- $T(n) = O(f(n))$ 意味着 $\exists c, n_0: T(n) \leq c \cdot f(n), \forall n > n_0$
- 优化效果体现在将增长阶从 $O(n^2)$ 降至 $O(n \log n)$，或从 $O(n)$ 降至 $O(1)$

**归约终点**：性能优化可归约为**算法复杂度的最优化问题**——在给定的计算资源约束下，通过改进算法或数据结构，将问题的渐近复杂度降至最低。

### Amdahl 定律的完整推导

并行化加速比 $S(n)$ 受串行部分比例 $f$ 限制：

$$S(n) = \frac{1}{f + \frac{1-f}{n}} \leq \frac{1}{f}$$

**Amdahl 定律的物理含义**：设程序运行时间为 $T$。其中串行部分耗时 $fT$，可并行部分耗时 $(1-f)T$。并行化后，可并行部分在 $n$ 个核心上运行，耗时 $\frac{(1-f)T}{n}$。总时间：

$$T'(n) = fT + \frac{(1-f)T}{n}$$

加速比 $S(n) = T/T' = \frac{1}{f + \frac{1-f}{n}}$

**数值示例**：若 $f = 0.05$（5% 串行），则最大加速比 $S(\infty) = 20\times$；若 $f = 0.10$，则最大 $10\times$。即使可并行部分在无限核心上趋近 0 时间，串行部分仍决定上限。

**Gustafson 定律**（弱扩展场景）：当问题规模随核心数增长时，加速比可以超过 Amdahl 上限。设每次核心都完成等量工作：

$$S_{Gustafson}(n) = n - f(n-1)$$

其中 $f$ 是串行部分比例随规模的变化。当问题规模可扩展时，Amdahl 的悲观预测可以被突破。

### 列表与生成器的内存复杂度

设构建包含 $N$ 个元素的序列：

**列表（立即求值）**：

$$M_{list}(N) = N \cdot (\text{PyObject}_\text{header} + \text{引用指针}) + \text{列表容器本身}$$

$$= N \cdot (56 + 8) + O(N) = O(N)$$

其中每个 Python 对象（整数、字符串等）本身也占用独立堆内存，列表仅存储引用指针。

**生成器（惰性求值）**：

$$M_{gen}(N) = \text{生成器对象} + \text{当前元素缓存} + \text{迭代状态}$$

$$= O(1)$$

生成器不预分配 $N$ 个引用的数组，仅在迭代时按需计算并覆盖当前元素。

当 $N \to \infty$ 时，列表的 $O(N)$ 空间成为瓶颈，生成器的 $O(1)$ 优势趋于主导。

### cProfile 的调用图成本模型

将程序执行建模为有向调用图 $G = (V, E)$，每条边 $(u, v)$ 表示 $u$ 调用 $v$。对每个顶点 $v$ 定义：

- $\text{self}(v)$：$v$ 自身的执行时间（不含子调用）
- $\text{cost}(v)$：$v$ 的总执行时间（后序遍历的和）

$$\text{cost}(v) = \text{self}(v) + \sum_{(v, w) \in E} \text{cost}(w)$$

这正是 `cumtime` 的定义。cProfile 的 `cumulative` 排序本质是对**调用树的后序遍历**——对每个节点，先计算子节点的时间和，再加自身时间。

**优化决策规则**：
- $\text{self}(v) \gg \sum \text{cost}(w)$ → $v$ 自身是热点，优化 $v$ 的实现
- $\text{self}(v) \ll \sum \text{cost}(w)$ → 子调用是热点，优化调用结构

### 复杂度降级的量化示例

| 原始复杂度 | 优化后复杂度 | $N=10^6$ 时的比值 |
|-----------|-------------|-----------------|
| $O(n^2)$ | $O(n \log n)$ | $\frac{n^2}{n \log n} \approx 50,000$ |
| $O(n^2)$ | $O(n)$ | $n = 1,000,000$ |
| $O(n)$ | $O(1)$ | 比值为 $n$，优化收益恒定 |
| $O(n \log n)$ | $O(n)$ | $\log n \approx 20$ |

## 数据流

<pre>
代码执行路径
    │
    ▼
cProfile 插桩记录 ──> (函数名, ncalls, tottime, cumtime)
    │
    ▼
调用图构建 ──> 顶点: self(v) ─> 边: 调用关系
    │
    ▼

    │
    ▼

    │
    ├── self(v) >> Σchildren ──> 函数自身是热点
    ├── self(v) << Σchildren ──> 子调用是热点
    └── I/O 等待占比高 ──> 并发/异步化
</pre>

## 机制

### cProfile 的侵入性

cProfile 基于 `settrace` 注入回调，本质是**每次函数调用/返回事件的全量记录**（插桩），而非采样。这意味着 profiling 期间程序以 $1/n$ 的速度运行（n 为平均每行字节码数，约 10-20）。

**关键约束**：profiling 是**侵入式的观测**，对极短程序（毫秒级）的测量结果可能严重失真——overhead 可能比实际执行时间还长。

**侵入性的量化**：设程序原始运行时间 $T$，profiling overhead 为 $k$（通常 $k \in [5, 20]$）。则：

$$T_{profiled} = k \cdot T$$

对于 $T = 10ms$ 的程序，profiling 后可能运行 $50ms$–$200ms$，热点定位仍然有效。但对于 $T = 1ms$ 的程序，profiling 后可能运行 $5ms$–$20ms$，测量结果已经失真。

**采样 profiling 的替代**：对于生产环境或长运行程序，`py-spy` 的采样模式（每隔 ~1ms 中断采样）侵入性更低，适合对运行中的进程 profiling。

### 列表 vs 生成器的内存模型

列表在构造时即在堆上分配 $N$ 个元素的连续数组，每个元素是指向 Python 对象的指针。Python 对象本身（整数、字符串等）也占用独立堆内存——**列表存储的是引用，不是对象本身**。

```python
# 列表：构造时即分配全部内存
squares = [x**2 for x in range(10**7)]
# 内存占用: 列表本身(80MB) + 10^7个整数对象(28MB each) ≈ 280MB+

# 生成器：只保存迭代状态
squares_gen = (x**2 for x in range(10**7))
# 内存占用: 生成器对象 + 当前整数对象 ≈ 几十字节
# 每次迭代: 计算新值 → 覆盖旧值引用
```

**约束**：生成器只能迭代一次；生成器无法随机访问（下标访问需先完成所有计算）；生成器持有迭代器状态，无法并发访问。

### `__slots__` 的实现原理

普通类实例的 `__dict__` 是一个散列表，每个属性作为键值对存储。散列表的内存开销包括：键的哈希值、冲突链指针、负载因子导致的空槽。

`__slots__` 将属性存储为**紧凑数组**——每个 slot 对应固定的内存偏移量，属性值直接存储在该偏移位置。这消除了 `__dict__` 的哈希表开销，同时**禁止动态添加新属性**（因为 slots 数量固定）。

**`__slots__` 的空间节省**：

| 实现 | 每个实例开销 |
|------|------------|
| `__dict__` | ~56 bytes（哈希表）+ 键值对 |
| `__slots__` | 8 bytes × 属性数 |

对于大量小对象的场景（如游戏引擎的粒子系统），`__slots__` 可将内存占用降低数倍。

### Faster CPython（Python 3.11+）

Python 3.11 引入了"零成本异常"和"自适应解释器"等优化。Python 3.14 继续在此基础上改进。

**自适应解释器**：Python 字节码解释器在运行时收集类型信息，对同质类型序列进行专门化，将通用 `BINARY_ADD` 字节码替换为针对 `int+int` 或 `str+str` 的快速路径。

**Tier 2 编译**：热点字节码序列被二次编译为更高效的机器码，进一步提升执行效率。

**Tier 2 加速的数学模型**：设热点代码片段执行 $k$ 次。每次解释执行开销为 $c_1$（类型检查 + dispatch）；二次编译后开销为 $c_2$（直接机器码执行，$c_2 \ll c_1$）。总代价：

$$T_{tiered} = k \cdot c_1 + c_{compile} + k \cdot c_2$$

当 $k \cdot (c_1 - c_2) > c_{compile}$ 时，二次编译产生净收益。

**优化的本质**：减少 dispatch overhead（每次字节码执行前的类型检查开销），通过 specialization 将类型检查从运行时移到编译时。

### 性能优化的决策树

```
热点定位（cProfile）
    │
    ├── self(v) >> Σchildren（函数自身是热点）
    │       │
    │       ├── 算法复杂度是否最优？ → 重新设计算法
    │       ├── 数据结构是否合理？ → 改用更合适的数据结构
    │       └── 代码实现是否低效？ → 微优化（__slots__、缓存等）
    │
    ├── self(v) << Σchildren（子调用是热点）
    │       │
    │       ├── 调用次数是否过多？ → 减少调用（内联、缓存）
    │       └── 子调用自身是否可优化？ → 递归到热点定位
    │
    └── I/O 等待占比高
            │
            └── 并发/异步化（见并发与异步章节）
```

## 参考存根

```python
import cProfile
import pstats
import sys

# cProfile：定位热点
profiler = cProfile.Profile()
profiler.enable()
# ... 被测代码 ...
profiler.disable()
stats = pstats.Stats(profiler)
stats.strip_dirs()
stats.sort_stats('cumulative')
stats.print_stats(20)

# Amdahl 示例
def amdahl_speedup(f, n):
    return 1 / (f + (1 - f) / n)

# 列表 vs 生成器
def compare_memory():
    N = 10**7
    t0 = time.perf_counter()
    squares_list = [x**2 for x in range(N)]
    t1 = time.perf_counter()
    print(f"列表: {t1-t0:.2f}s, 内存: {sys.getsizeof(squares_list)/1e6:.1f}MB")
    t0 = time.perf_counter()
    squares_gen = (x**2 for x in range(N))
    total = sum(squares_gen)
    t1 = time.perf_counter()
    print(f"生成器: {t1-t0:.2f}s, 内存: ~0MB")

# __slots__ 内存对比
class Point: pass
class PointSlotted:
    __slots__ = ('x', 'y')
    def __init__(self, x, y):
        self.x, self.y = x, y

p1 = Point(); p1.x = 1; p1.y = 2
p2 = PointSlotted(1, 2)
print(f"无 slots: {sys.getsizeof(p1.__dict__)}B")
print(f"有 slots: {sys.getsizeof(p2)}B")
```
