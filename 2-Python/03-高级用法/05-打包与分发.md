# 打包与分发

## 定义

Python 打包系统将代码产物（源码、字节码、元数据）封装为可分发单元，通过标准化构建后端（setuptools、poetry、hatch）和分发格式（sdist、wheel）实现跨环境部署。`pyproject.toml` 是现代 Python 包的事实标准配置格式，取代了传统的 `setup.py`、`setup.cfg`。

## 数学模型

### 版本约束求解（约束满足问题）

依赖解析本质上是**约束满足问题（CSP）**。令 $P$ 为包集合， $V(p)$ 为包 $p$ 的可用版本集合，$R$ 为依赖关系集合（格式：`package >=ver`）。求解器寻找版本组合：

$\{v_p \in V(p) | \forall (a, b) \in R,\ \text{satisfies}(v_a, b)\}$

**约束冲突**：当不存在满足所有约束的版本组合时，打包工具报告 `ResolutionImpossible`。当存在多个解时，按版本排序策略选择（通常是最高满足版本）。

**CSP 求解的复杂度**：最坏情况下为指数时间（ $O(2^n)$ ，$n$ 为包数量）。实践中使用回溯剪枝和启发式搜索（如 MRV 规则）加速。

### wheel 分发格式

wheel（`.whl`）是预编译分发格式：

$\text{wheel filename} = \text{name}-\text{version}-\text{pyver}-\text{abi}-\text{platform}.whl$

- `pyver`：Python 版本标签（如 `py3-none`、`cp312-cp312`）
- `abi`：ABI 标签（如 `abi3` 表示稳定 ABI，`none` 表示纯 Python）
- `platform`：目标平台（如 `linux_x86_64`、`win_amd64`）

纯 Python wheel 使用 `py3-none-any`，无平台限制。

**wheel 的安装数学**：wheel 安装本质是文件复制操作。设 wheel 包含 $n$ 个文件，总安装时间：

$T_{install} = \sum_{i=1}^{n} T_{copy}(file_i) + T_{metadata}$

其中 $T_{copy}$ 与文件大小成正比。相对于 sdist 的编译时间，wheel 的安装时间是 $O(n)$ 的文件操作。

### 构建后端等价性

主流构建后端（setuptools、poetry、hatch）均读取 `pyproject.toml` 的 `[project]` 元数据，输出兼容的分发格式。构建过程等价：

$\text{Source} \xrightarrow{\text{build-backend}} \text{sdist} \lor \text{wheel}$

### 依赖传递约束传播

设 $A \to B$ 表示 $A$ 依赖 $B$ ，依赖约束为下界约束。设传递依赖链 $A \to B \to C$ ：

- 若 $A$ 要求 $C \geq 1.0$ ， $B$ 要求 $C \geq 2.0$，则最终约束为 $C \geq \max(1.0, 2.0) = 2.0$
- 约束取所有依赖要求的**最大值**（最严格下界）

$c_C = \max_{(p, C) \in R} \text{lower\_bound}(p, C)$

## 机制

### pyproject.toml 的三层架构

```toml
[build-system]       # 第一层：声明构建工具（不含构建指令）
requires = ["setuptools>=61"]
build-backend = "setuptools.build_meta"

[project]            # 第二层：包元数据 + 运行时依赖
name = "mypackage"
version = "0.1.0"
dependencies = ["requests>=2.28"]

[project.optional-dependencies]  # 可选依赖组
dev = ["pytest", "ruff"]

[tool.setuptools]   # 第三层：后端特定配置
packages = { find = { where = ["src"] } }
```

**关键约束**：`[build-system]` 只声明工具，不含构建指令。这使得不同后端可替换，同时产出兼容格式。

**[build-system] 的语义**：`requires` 声明构建时依赖，但不执行构建脚本。`build-backend` 指定入口点（如 `setuptools.build_meta`）。这实现了构建系统的可插拔性。

### sdist vs wheel

| 属性 | sdist | wheel |
|------|-------|-------|
| 内容 | 源码 + 原始元数据 | 预编译字节码（.pyc）+ 纯元数据 |
| 安装速度 | 慢（需编译） | 快（直接复制） |
| 可移植性 | 高（跨平台源码） | 受限于 pyver-abi-platform 标签 |
| 包含扩展 | 是 | 否（扩展需 platform tag） |

**wheel 的平台标签约束**：wheel 必须在目标平台上构建。`cp312-cp312-linux_x86_64` 只能在 CPython 3.12 + Linux x86_64 上安装。若在不同平台安装，需要相应的 platform tag。

### 依赖解析策略

pip/poetry 在安装时执行依赖解析。当约束为 `requests>=2.28` 时：

- 解析器从 PyPI 获取 `requests` 的所有版本
- 选择满足约束的**最高**版本（`>=2.28` 的最新发布版）
- 递归解析 `requests` 的传递依赖

**版本锁定**：`poetry.lock` / `requirements.txt` 将解析结果固定，避免不同环境的版本差异。

**传递依赖的约束传播**：设 $A \to B \to C$ 表示 $A$ 依赖 $B$ ， $B$ 依赖 $C$。若 $A$ 要求 $C \geq 1.0$，$B$ 要求 $C \geq 2.0$，则最终约束为 $C \geq 2.0$。约束取所有依赖要求的最大值。

### entry_points 与可执行脚本

```toml
[project.scripts]
myapp = "mypackage.cli:main"
```

构建后端在安装时生成平台特定的脚本包装器（Windows `.exe` 或 POSIX 可执行文件），调用指定模块的入口函数。这实现了"安装即成命令"——用户无需知道 Python 路径或模块路径。

**entry_points 的安装语义**：安装时，打包工具在 `bin/` 或 `Scripts/` 目录创建可执行脚本，其内容是调用 `pkg_resources` 或 `importlib.metadata` 加载指定入口点。

### 约束与违反后果

- **Python 版本不兼容**：`requires-python = ">=3.8"` 限制安装环境；旧版 Python 无法安装，但不会报告具体原因
- **ABI 不兼容**：C 扩展 wheel 的 ABI 标签必须与目标 Python 匹配；`cp312-cp312` wheel 只能在 CPython 3.12 中安装
- **Namespace package 冲突**：同一命名空间下的多个包必须都声明 `namespace_packages`；冲突导致导入失败
- **构建后端不一致**：不同后端可能对同一配置产生略有差异的元数据
- **循环依赖**：两个包相互依赖导致解析死锁

## 参考存根

```toml
# pyproject.toml
[build-system]
requires = ["setuptools>=61", "wheel"]
build-backend = "setuptools.build_meta"

[project]
name = "mypackage"
version = "0.1.0"
description = "A sample package"
readme = "README.md"
requires-python = ">=3.12"
license = {text = "MIT"}
authors = [{name = "Alice", email = "alice@example.com"}]

dependencies = [
    "requests>=2.28",
]

[project.optional-dependencies]
dev = ["pytest>=7", "ruff>=0.1", "mypy>=1.0"]

[project.scripts]
myapp = "mypackage.cli:main"

[tool.setuptools.packages.find]
where = ["src"]

[tool.ruff]
line-length = 88
```

```bash
# 构建
python -m build                    # sdist + wheel
python -m build --wheel           # 仅 wheel
python -m build --sdist           # 仅 sdist

# 上传
twine upload dist/*               # 正式 PyPI
twine upload --repository testpypi dist/*  # TestPyPI

# 本地安装
pip install -e ".[dev]"          # 可编辑模式 + dev 依赖
pip install dist/*.whl --force-reinstall
```
