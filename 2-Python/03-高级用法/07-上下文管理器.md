# 上下文管理器深入

## 定义

上下文管理器是 Python 资源管理协议，通过 `with` 语句实现**获取→持有→释放**的三段式资源控制，保证资源在所有代码路径下（正常返回、异常退出、早期 return）均被正确清理。`__enter__` 和 `__exit__` 构成该协议的两个钩子，由解释器在 `with` 块入口和出口自动调用。

## 数学模型

### 资源状态机

上下文管理器的资源生命周期可建模为状态机：

$$
S = \{\text{未获取}, \text{已获取（正常）}, \text{已获取（异常）}, \text{已释放}\}
$$

$$
\delta: S \times \{\text{enter}, \text{exit（无异常）}, \text{exit（异常）}\} \rightarrow S
$$

$$
\delta(\text{未获取}, \text{enter}) = \text{已获取（正常）} \\
\delta(\text{已获取（正常）}, \text{exit（无异常）}) = \text{已释放} \\
\delta(\text{已获取（异常）}, \text{exit（异常）}) = \text{已释放}
$$

**关键约束**：状态转移是**幂等的**——无论 `__enter__` 是否成功，`__exit__` 都必须被调用（由解释器保证），但转移结果必须在语义上保持一致。

### @contextmanager 的生成器语义

`@contextmanager` 将生成器函数 $G$ 转换为上下文管理器类。令 $G$ 中 `yield` 前为前段（setup），`yield` 后为后段（cleanup）：

$$
\text{instantiate}(G) \rightsquigarrow \text{ContextManagerClass}
$$

$$
\text{__enter__} \triangleq \text{执行前段至 } \text{yield} \\
\text{__exit__} \triangleq \text{从 } \text{yield} \text{ 恢复执行后段（被 finally 包装）}
$$

生成器 $G$ 的状态在 `yield` 处挂起，由 pytest 的 fixture 机制（而非解释器）负责恢复。这意味着 `yield` 后的代码在 `__exit__` 调用时才会执行。

### 异常传播模型

`__exit__` 的返回值控制异常传播，其语义是**集合差运算**：

令 $E$ 为当前活跃异常集合（通常至多一个），$S \subseteq E$ 为 `__exit__` 返回 `True` 时压制的异常集合：

$$
\text{exit\_result}(r, E) = E \setminus S \quad \text{其中 } S = \begin{cases}
\{e\} & r = \text{True} \\
\varnothing & r = \text{False} \lor r = \text{None}
\end{cases}
$$

若 $E = \varnothing$（无活跃异常），则 `__exit__` 的返回值对异常传播无影响——返回值仅在有异常时才决定是否将其从活跃集合中移除。

**行为矩阵**：

| 上下文状态 | `__exit__` 返回值 | 结果 |
|-----------|------------------|------|
| body 正常返回 | `False`/`None`/`True` | 无异常，压制语义不适用 |
| body 抛出异常 $e$ | `False`/`None` | $e$ 传播至 `with` 外 |
| body 抛出异常 $e$ | `True` | $e$ 被压制，`with` 语句正常返回 |

**压制异常的后果**：`True` 返回值将异常从活跃集合中移除，但异常对象本身仍通过 `sys.exc_info()` 可访问（由解释器保存）。压制异常意味着调用者无法感知错误发生，导致静默失败——调试极为困难。事务管理中压制异常尤其危险：ROLLBACK 被跳过，数据处于部分提交的中间状态。

## 机制

### 资源获取的三种模式

| 模式 | 获取时机 | 适用场景 |
|------|----------|----------|
| `__init__` | `with` 表达式创建对象时 | 简单资源（文件句柄） |
| `__enter__` | 进入 `with` 块时 | 延迟获取（数据库连接池） |
| `yield` 值 | 生成器恢复时 | `@contextmanager` 装饰器 |

**关键约束**：`__init__` 中获取资源意味着对象创建时就持有资源，即使从未进入 `with` 块也会泄漏。而 `__enter__` 获取则在 `with` 块入口才真正分配。

### @contextmanager 的生成器陷阱

`yield` 前的代码在 `try` 块**之外**执行，如果这些代码抛出异常，`finally` 块不会执行：

```python
@contextmanager
def bad_context():
    result = setup_that_might_raise()  # 异常 → cleanup 不执行
    try:
        yield result
    finally:
        cleanup()

# 正确做法：
@contextmanager
def good_context():
    try:  # 整个 setup 都在 try 内
        result = setup_that_might_raise()
        yield result
    finally:
        cleanup()
```

### 嵌套上下文管理器的退出顺序

嵌套 `with` 块的退出顺序是**栈式的**（LIFO）——最内层先退出：

```python
with outer():
    with inner():
        pass
# 执行顺序：inner.__exit__() → outer.__exit__()
```

### ExitStack 的动态组合

`ExitStack` 允许运行时动态添加上下文管理器，而非编译时静态嵌套：

```python
with ExitStack() as stack:
    file1 = stack.enter_context(open("file1.txt", "w"))
    file2 = stack.enter_context(open("file2.txt", "w"))
    # 退出时全部自动清理，无论添加顺序
```

`ExitStack` 内部维护一个上下文管理器栈，退出时逆序弹出并调用 `__exit__`。

### 事务管理的原子性

上下文管理器可保证事务的原子性：

```python
with Transaction(conn):
    conn.execute(sql1)
    conn.execute(sql2)
# 正常退出 → COMMIT
# 异常退出 → ROLLBACK（__exit__ 检测到异常参数）
```

**约束**：`__exit__` 收到异常参数时，ROLLBACK 是正确的响应；压制异常（返回 `True`）会导致部分提交，破坏原子性。

### 连接池的资源限制

上下文管理器可实现连接池的令牌分发：

```python
@contextmanager
def acquire(self):
    with self.lock:
        if self.available <= 0:
            raise RuntimeError("No connections available")
        self.available -= 1
    try:
        yield connection
    finally:
        with self.lock:
            self.available += 1
```

**关键约束**：计数器递减在锁外进行，避免长时间持锁；递增在 `finally` 中保证即使获取后抛异常也能归还。

### 违反约束的后果

- **在 `yield` 前获取资源且未在 try 内**：`yield` 抛出异常时 cleanup 不执行，资源泄漏
- **返回 `True` 压制异常**：异常被静默丢弃，调用方无法感知错误，调试困难
- **在 `__exit__` 中抛出异常**：原异常被新异常替代，原始错误信息丢失
- **在多线程环境中共享上下文管理器对象**：多个线程同时进入同一 `with` 块，导致资源竞争

## 参考存根

```python
from contextlib import contextmanager, asynccontextmanager, suppress, closing

@contextmanager
def managed_resource(name):
    print(f"Acquiring {name}")
    resource = f"Resource-{name}"
    try:
        yield resource
    finally:
        print(f"Releasing {name}")

@asynccontextmanager
async def async_managed_resource(name):
    print(f"Acquiring {name}")
    resource = f"AsyncResource-{name}"
    try:
        yield resource
    finally:
        print(f"Releasing {name}")

# 事务管理
class Transaction:
    def __enter__(self):
        print("BEGIN")
        return self
    def __exit__(self, *args):
        if args[0] is None:
            print("COMMIT")
        else:
            print(f"ROLLBACK: {args[1]}")
        return False

# 连接池
class ConnectionPool:
    def __init__(self, max_connections):
        self.available = max_connections
        self.lock = __import__('threading').Lock()

    @contextmanager
    def acquire(self):
        with self.lock:
            if self.available <= 0:
                raise RuntimeError("No connections")
            self.available -= 1
        try:
            yield f"Conn-{id(self)}"
        finally:
            with self.lock:
                self.available += 1
```
