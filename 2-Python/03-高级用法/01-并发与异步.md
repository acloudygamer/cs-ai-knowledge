# 并发与异步

## 定义

并发是在单一 CPU 时间片内通过交错执行多个 I/O 等待片段来最大化吞吐量的编程模型；异步是协作式调度的具体实现形式，通过在 I/O 点主动让出控制权避免线程阻塞。Python 的并发受制于 GIL（全局解释器锁）的约束：同一时刻仅允许一个线程持有解释器执行字节码。

## 数学模型

### GIL 约束下的并行度

设线程集合 $T = \{t_1, \dots, t_n\}$，每个线程的 CPU 时间片为 $\Delta t_i$。在 GIL 约束下，最大并行度为：

$$P_{\max} = 1 \quad \text{(CPython, standard build)}$$

即同一时刻仅一个线程在解释器中执行，其余线程在 I/O 等待或 C 扩展调用期间并行。

对于 I/O 密集型任务，并发加速比近似为：

$$S \approx \frac{T_{serial}}{T_{serial} \times (1 - f) + T_{serial} \times \frac{f}{n}} = \frac{1}{1 - f(1 - \frac{1}{n})}$$

其中 $f$ 是 I/O 等待时间占比，$n$ 是线程数。当 $f \to 1$（纯 I/O 等待）时，$S \to n$——I/O 密集型任务几乎能实现完美线程扩展。

### 事件循环：有限状态自动机

asyncio 事件循环调度的核心是**有限状态自动机（FSA）**。令 $\Sigma$ 为事件集合（I/O 就绪、定时器到期、Future 完成），$\delta: Q \times \Sigma \to Q$ 为状态转移函数：

$$Q = \{\text{READY}, \text{WAITING}, \text{SUSPENDED}\}$$

协程对象是状态机的当前状态，`await` 触发状态转移至 `SUSPENDED`，事件循环通过回调恢复执行。

**归约终点**：
- 线程 → OS 调度的时间片轮转 + GIL 串行化
- 协程 → 用户态 FSA + 事件循环轮转调度
- 进程 → 独立地址空间 + OS 调度（无 GIL）

## 数据流

<pre>

**所有权流转**：
- 线程模型：每个线程持有独立的栈帧和寄存器副本，堆内存共享
- asyncio 模型：协程共享同一线程栈帧，协程切换仅保存/恢复寄存器状态（无栈帧拷贝）

## 机制

### GIL 的精确语义与实现

GIL 保护的是**Python 对象访问**而非字节码执行本身。CPython 的 GIL 机制：

1. 线程在解释器主循环中每执行 5ms（可配置 `sys.setswitchinterval`）检查是否需要让出
2. I/O 系统调用（`read`、`socket.recv`）在等待期间**释放 GIL**——这是 I/O 密集型多线程有效的物理基础
3. C 扩展调用若在内部显式释放 GIL（`Py_BEGIN_ALLOW_THREADS`），其余线程可并行执行

**GIL 的本质**：GIL 是 CPython 的**解释器级互斥锁**，而非语言级语义保证。它是实现决策而非语言规范——其他 Python 实现（如 PyPy、 GraalPython）可以无 GIL。

**约束条件**：
- 纯 Python 代码的 CPU 密集型任务无论多少线程，**每秒执行的字节码指令数相同**（受 GIL 限制）
- 多进程是 CPU 密集型的唯一有效并行方案（绕过 GIL）
- GIL 的切换间隔（5ms）是吞吐量和响应性的折中：间隔过短导致线程切换开销增大，过长导致其他线程等待时间增加

**违反约束的后果**：
- 在 CPU 密集型代码中使用线程 → 性能反而下降（线程创建和上下文切换开销）
- 在没有显式释放 GIL 的 C 扩展中期待并行 → 实际串行执行

### asyncio 事件循环的调度语义

事件循环是一个**基于回调的有限状态机**，其核心数据结构是优先级队列（通常为堆）管理的定时器和 I/O 就绪事件。

**READY 队列的调度策略**：FIFO 公平调度，不考虑优先级。这导致：
- 所有就绪协程轮流执行
- 长计算会阻塞其他协程（协程不是抢占式的）
- 需手动 `await asyncio.sleep(0)` 让出控制权

**WAITING 状态的精确语义**：协程在 `await fut` 时进入 WAITING，fut 完成时协程被重新放入 READY 队列。这实现了 O(1) 的协程唤醒——无需遍历所有协程。

```python
# asyncio.sleep 的精确语义
async def sleep(delay):
    loop = get_running_loop()
    h = loop.call_later(delay, lambda: future.set_result(None))
    try:
        await future  # SUSPENDED，事件循环继续调度其他协程
    finally:
        h.cancel()    # 清理定时器句柄
```

### TaskGroup vs asyncio.gather 的异常语义

`asyncio.gather` 的异常策略：**第一个异常立即传播，其余任务继续执行**。gather 返回的异常列表包含所有捕获的异常（`return_exceptions=True` 模式）。

`TaskGroup`（Python 3.11+）的异常策略：**所有任务在同一个 scope 内，任一取消导致组内所有任务取消**，最终抛出 `ExceptionGroup`。这实现了结构化并发的不变量：子任务的生命周期被父任务 scope 严格包含。

**结构化并发的约束保证**：
- 父任务 scope 退出前，所有子任务必须完成（或被取消）
- 消除了"孤儿任务"问题——协程泄漏
- `TaskGroup` 内部使用 `try/finally` 确保取消信号传播

```python
# gather：任一异常后，其余任务继续（可能产出结果或异常）
results = await asyncio.gather(t1, t2, return_exceptions=True)
# results[0] = Exception(...)  # t1 异常
# results[1] = "success"       # t2 继续完成

# TaskGroup：取消信号在组内传播
async with asyncio.TaskGroup() as tg:
    t1 = tg.create_task(unsafe_op())
    t2 = tg.create_task(safe_op())
# 若 t1 抛出异常：t2 会被 TaskGroup 立即取消
# 最终抛出 ExceptionGroup([exc_t1, CancelledError(t2)])
```

### 超时处理的精确语义

`asyncio.wait_for(fut, timeout)` 的实现：
```python
async def wait_for(fut, timeout):
    shield = asyncio.ensure_future(_shield(fut))  # 保护任务不被立即取消
    try:
        return await asyncio.wait_for(shield, timeout)
    except asyncio.TimeoutError:
        shield.cancel()   # 向 shield（即 fut）发送取消信号
        raise
```

取消信号触发 `fut` 的协程栈向上弹出 `CancelledError`，协程的 `finally` 块会被执行——取消是**协作式的**，不是线程的强制 kill。

**超时的数学约束**：
- 等待时间 $T_{wait} \leq timeout$（精确上界）
- 若 fut 在 timeout 前完成，立即返回（不等满 timeout）
- `asyncio.timeout`（3.11+）是更简洁的等效实现

## 对比参照

| 属性 | threading | multiprocessing | asyncio |
|------|-----------|-----------------|---------|
| **并行度上限** | 1（受 GIL 限制） | N（进程数） | 1（单线程） |
| **GIL 影响** | 阻塞 CPU 代码 | 无 | 无 |
| **切换代价** | ~0.5μs（系统调用） | ~10μs（进程创建+页表） | ~50ns（寄存器） |
| **内存模型** | 共享（需锁） | 独立（需 IPC） | 共享（协程） |
| **调度权** | OS 抢占式 | OS 抢占式 | 用户态协作式 |
| **异常传播** | 线程局部 | 进程局部 | TaskGroup 聚合 |
