# 内存管理

## 定义

Python 内存管理的核心是**引用计数**（reference counting）——每个堆对象维护一个整数计数器，记录指向该对象的引用数量，当计数归零时对象被立即回收。引用计数使 Python 拥有确定性的内存回收延迟：对象死亡的确切时刻就是引用计数归零的时刻，无需等待 GC 扫描。

## 数学模型

### 引用计数的操作语义

设对象 $o$ 的引用计数为 $rc(o) \in \mathbb{N}$ 。引用计数的操作语义：

| 操作 | $rc$ 变化 | 触发者 |
|------|-----------|--------|
| `o = expr`（创建引用） | $rc(o) \leftarrow rc(o) + 1$ | 赋值语句 |
| `del o`（删除引用） | $rc(o) \leftarrow rc(o) - 1$ | `del` 语句 |
| 变量超出作用域 | $rc(o) \leftarrow rc(o) - 1$ | 控制流 |
| 函数参数传入 | 调用方 $rc$ 不变；被调用方 $rc + 1$ | 调用约定 |

当 $rc(o) = 0$ 时，对象立即进入析构序列（调用 `__del__`，若存在）并释放内存。

**引用计数是 O(1) 的**：每次引用操作（创建/销毁）只涉及一次原子递增/递减，无需遍历全局对象集合。这是其相对于 tracing GC 的优势。

**原子引用的必要性**：在多线程环境下，两个线程同时对同一对象执行 `del` 时，可能发生：

$rc(o) = 1 \quad \text{（线程A和B各持有一个引用）}$

若 `DECREF` 非原子，可能出现竞态：线程A读取 rc=1 后，线程B也读取 rc=1，两者各自执行递减，写回 0，对象被释放两次——**下溢错误**。因此多线程 CPython（Python 3.13+ 自由线程模式）中引用计数操作必须原子化。

### 循环引用检测的图论约束

设对象图 $G = (V, E)$ ，其中 $V$ 是对象集合、 $E$ 是引用边（有向）。引用计数无法检测的子图满足：

$\forall v \in S \subseteq V,\ \text{in-degree}_S(v) \geq 1 \quad \text{且} \quad \text{in-degree}_{V\setminus S}(v) = 0$

即子图 $S$ 内所有顶点入度 $\geq 1$ ，但 $S$ 整体无外部入边。所有局部计数 $> 0$ ，全局却应被回收。

GC 的标记-清除算法对此进行补充，时间复杂度 $O(|V| + |E|)$ ：

- **标记阶段**：从根集合（全局变量、栈帧）出发，DFS 标记所有可达对象
- **清除阶段**：扫描整个堆，未被标记的对象判定为死亡

**标记-清除的数学性质**：令 $R$ 为根集合， $reach(v)$ 为从 $R$ 可达的所有对象。则死亡对象集合  $D = V \setminus reach(R)$。标记-清除的正确性由 $v \in reach(R) \iff v$ 被标记 给出。

### 分代假说的概率模型

分代假说（Generational Hypothesis）的量化表述：

$P(\text{对象存活} \mid \text{已存活} > g) \ll P(\text{对象存活} \mid \text{刚创建})$

即对象存活的条件概率随年龄增长单调递减。Python GC 的代际配置将这一假说落地：

- Generation 0：新建对象放入此代（阈值通常 700）
- Generation 1：经历一次 GC 仍存活的对象移至此代（阈值通常 10）
- Generation 2：经历两次 GC 仍存活的对象移至此代（阈值通常 10）

**分代扫描的代价模型**：设第 $i$ 代的对象数为 $|V_i|$ ，GC 触发阈值为 $T_i$ 。第 $i$ 代 GC 的时间复杂度为 $O(|V_i| + |E_i|)$ 。由于大多数对象在 Gen 0 被回收，GC 代价集中在 $|V_0|$ ，而非全堆 $|V|$ 。

**归约终点**：Python 内存分配器可归约为**分层的 arena 分配器**——小块（ $\leq 256$ 字节）由内存池（pool）管理，大块直接调用系统 `malloc`。

## 数据流

<pre>
对象创建                         引用计数更新
  │                                 │
  ▼                                 ▼
  PyObject_Malloc                rc(o) = rc(o) ± 1
  │                                 │
  ├── 小对象 (<=256B) ──→  pool: 预先分配的内存块
  │                                 │  (管理 4KB 页面)
  └── 大对象 (>256B) ──→  malloc: 系统堆直接分配
                                  │
                                  ▼
                            rc(o) == 0 ?
                             /          \
                          是            否
                           │              │
                           ▼              ▼
                       立即释放       保留在堆
                       (无 GC)           │
                                          ▼
                                      分代 GC 扫描
                                      (循环引用检测)
</pre>

**所有权流转**：
1. 对象创建：分配器分配内存，`rc = 1`
2. 引用传递：发送方 $rc + 1$ ，接收方接收引用
3. 引用销毁： $rc - 1$
4. $rc = 0$ ：析构函数调用（若存在），内存返还分配器
5. 分配器：小块返还 pool（不归还系统），大块归还系统

## 机制

### 引用计数的根本局限

引用计数无法处理循环引用的根本原因：**引用计数是有向图的局部属性，入度为 0 是回收的必要条件，但非充分条件**。循环引用子图内每个对象入度 $\geq 1$ ，但子图整体无外部引用——所有局部计数 $> 0$ ，全局却应被回收。

**代价分析**：
- 引用计数操作需要原子递增/递减（多线程环境下），有同步开销
- 原子操作在多核系统上触发缓存行 bounce，影响性能
- Python 3.13 自由线程模式下（PEP 703），引用计数操作必须原子化，引入额外同步开销

### obmalloc 的三层架构

CPython 的 `obmalloc` 分配器分为三层，各层有不同的分配策略和内存来源：

| 层 | 对象大小 | 策略 | 内存来源 |
|---|---------|------|---------|
| `pool` | 8–256 字节 | 固定大小池（每 pool 4KB） | 预分配 arena |
| `arena` | 多个 pool | 64 pool / arena = 256KB | `mmap` (Linux) / `VirtualAlloc` (Windows) |
| `malloc` | > 256 字节 | 直接系统分配 | 系统堆 |

**设计意图**：避免频繁系统调用——小对象复用预先分配的 pool，只有 pool 耗尽才向系统申请新 arena。

**Arena 的空间效率**：arena 包含 64 个 pool，当某个 pool 的所有对象都被释放后，该 pool 的内存不归还 arena，只归还系统（通过 mmap/VirtualAlloc）。这意味着极端情况下（大量分配后立即释放）内存可能不归还系统。

**约束违反后果**：
- 若程序大量分配 >256 字节的对象（fragmentation 导致实际无法复用 pool），会导致内存向系统持续增长
- 若程序频繁创建和销毁大量小对象，arena 会被持续申请但不释放

### 弱引用的机制

弱引用不增加引用计数：`<obj>` 的引用不计入 `rc(<obj>)`。实现原理：

```python
class weakref:
    def __init__(self, obj):
        self._obj_id = id(obj)   # 存储对象 ID，而非引用
        # 对象注册到全局 __weakrefs__ 字典
    def __call__(self):
        # 通过 ID 查找对象是否仍存在
        # 若不存在（已被回收），返回 None
```

**弱引用的图论语义**：设 $W$ 为弱引用集合， $o \xrightarrow{w} w$ 表示 $o$ 的弱引用。 $w$ 不影响  $rc(o)$，因此 $o$ 的存活完全由强引用决定。

**使用场景**：缓存（允许被缓存对象被回收）、观察者模式（不延长对象生命周期）、跨引用结构（避免循环引用）。

### 自由线程模式下的内存管理（Python 3.13+）

Python 3.13 实现 PEP 703 的自由线程模式，移除 GIL 后内存管理面临根本性挑战：

**原子引用计数的数学约束**：
- `Py_DECREF` 在减至 0 时必须释放对象并调用析构函数
- 多线程同时 `DECREF` 同一对象时，必须保证 `rc$ 不会下溢
- 需要 CAS（compare-and-swap）原语确保线程安全

**自由线程模式的引用计数操作**：

```python
# 原子递增（伪代码）
def Py_INCREF(obj):
    atomic_fetch_add(&obj.rc, 1)

# 原子递减 + 条件释放（需确保线程安全）
def Py_DECREF(obj):
    if atomic_fetch_sub(&obj.rc, 1) == 1:
        # rc 从 1 减到 0，仅一个线程执行析构
        destructor(obj)
```

**关键问题：析构函数的并发安全**。当 `DECREF` 发现 `rc=0` 时，对象进入析构序列。若两个线程同时对相互引用的对象执行 `DECREF`，可能触发：
1. 线程A析构对象 $o_1$ ，触发 `__del__`，该方法可能访问 $o_2$
2. 线程B可能同时析构 $o_2$ ，导致 $o_2$ 的 `__del__` 在 $o_2$ 部分析构时访问已析构状态

**GC 的角色变化**：自由线程模式下，循环引用问题更加严重（多线程可能同时创建相互引用的对象图），GC 的稳定性成为关键约束。标记-清除算法需要 Stop-the-world 暂停，可能影响实时性。

**自由线程模式的性能权衡**：移除 GIL 后，约 20-30% 的同步开销来自原子引用计数操作。但对于 CPU 密集型工作负载，多线程并行收益远超同步开销。

## 参考存根

```python
import gc
import weakref
import sys

# 引用计数观察
obj = [1, 2, 3]           # rc = 1
ref = obj                 # rc = 2
del obj                   # rc = 1（ref 仍存活）
del ref                   # rc = 0 → 立即回收

# 循环引用（引用计数无法处理）
class Node:
    def __init__(self):
        self.next = None

a, b = Node(), Node()
a.next = b                # b.rc += 1
b.next = a                # a.rc += 1
del a; del b              # a.rc = 1, b.rc = 1（循环！）
# 此时引用计数均为 1，但无外部引用
# 需等待 GC 标记-清除才能回收

# GC 手动触发
gc.collect()              # 强制全代扫描

# 弱引用缓存
cache = {}

def get_cached(key, factory):
    ref = cache.get(key)
    obj = ref() if ref else None
    if obj is None:
        obj = factory(key)
        cache[key] = weakref.ref(obj)
    return obj

# __slots__ 内存优化
class Point:
    __slots__ = ('x', 'y')   # 消除 __dict__，每个实例减少 ~56 字节
    def __init__(self, x, y):
        self.x = x
        self.y = y
```
