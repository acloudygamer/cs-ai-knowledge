# 06-数据库操作

> 前置：[08-错误与异常](../01-语言核心/08-错误与异常.md)（事务回滚与异常）、[09-上下文管理器](../01-语言核心/09-上下文管理器.md)（事务语义）、[03-序列化与配置格式](03-序列化与配置格式.md)（连接配置来源） · 后续：[03-并发与异步](../03-运行时与性能/03-并发与异步.md)（连接池与并发）、[05-数据分析与机器学习](../06-应用领域/05-数据分析与机器学习.md)（分析型负载）

Python 的数据库栈分两层：DB-API（PEP 249，各家驱动共有的手柄）与其上的选择——raw SQL、查询构造器、ORM。本篇以标准库 `sqlite3` 讲透协议层（参数化、事务、游标），再给"raw 还是 ORM"一个工程判据。SQLite 本身值得认真对待：零部署的单文件数据库，从原型到中小生产都够用。

## 本质

- DB-API 三件套：**connection**（会话与事务边界）、**cursor**（语句执行与结果游标——名字即模型：迭代器语义，见 [06-迭代器与生成器](../01-语言核心/06-迭代器与生成器.md)）、**参数化查询**（`?` / `%(name)s` 占位）。
- 事务边界由连接管理：默认第一条 DML 隐式开启，`commit()` 落盘 / `rollback()` 撤销——**异常即回滚**的组合靠上下文管理器表达（见 [09-上下文管理器](../01-语言核心/09-上下文管理器.md)）。

## 机制

### 参数化：不是风格，是安全边界

```python
cur.execute("SELECT id, name FROM users WHERE id = ?", (uid,))          # 正确
cur.execute(f"SELECT ... WHERE id = {uid}")                              # 注入漏洞
cur.executemany("INSERT INTO events(user_id, kind) VALUES (?, ?)",
                [(u, k) for u, k in events])                             # 批量
```

字符串拼接进 SQL = 把调用者输入当代码执行（SQL 注入），与 `eval` 同罪；`?` 占位让驱动负责转义（类型化传参）。名字占位 `:name` 配 dict 用于多参数可读场景。表名/列名**不能**参数化——动态标识符必须走白名单校验，不是拼接。

### sqlite3 的事务上下文管理器：一个著名的不对称

```python
with sqlite3.connect("app.db") as conn:      # 提交/回滚：有（异常即 rollback）
    conn.execute("UPDATE ...")               # 离开 with：成功 commit / 异常 rollback
# 注意：连接本身【不会关闭】——with 块管理的是事务，不是连接生命周期。
# 需要两者都管时包一层（见 09-上下文管理器 的 @contextmanager 示例）。
```

`autocommit` 语义：（Python 3.12 增量）`autocommit=False|True|LEGACY_TRANSACTION_CONTROL` 把隐式行为显式化——新代码写明意图，别吃历史默认。

### 结果处理

- `cur.fetchone()` / `fetchall()` / 迭代 cursor（惰性）；行默认是 tuple——`conn.row_factory = sqlite3.Row` 后按名访问 `row["name"]`。
- 拿到即类型化的路线：`cur.execute(...)` 后直接 `map(Job, cur)`（dataclass 构造）或 SQLAlchemy 的 `Typed` 结果——把"数据库行 → 有类型对象"的边界显式化（见 [11-类型提示](../01-语言核心/11-类型提示.md)）。
- 时刻的存取纪律：aware UTC 进库（[04-日期与时间](04-日期与时间.md)），SQLite 无原生时区类型，ISO 字符串或 unix 秒皆可，但必须全库统一。

### 其他数据库：协议不变，特性各异

| 库 | 驱动 | 差异点 |
|---|---|---|
| PostgreSQL | `psycopg`（3.x） | 服务端参数 `%s`、`RETURNING`、`COPY` 批量导入、`SELECT ... FOR UPDATE` |
| MySQL/MariaDB | `pymysql` / `mysqlclient` | 隔离级别与服务端配置耦合深 |
| SQL Server/Oracle | `pyodbc` 系 | ODBC 层配置先于代码 |

连接池：Web 服务的标配（每请求新连接吃不起握手成本）——`psycopg_pool` / 框架内置（FastAPI 依赖注入，见 [02-FastAPI](../06-应用领域/02-FastAPI.md)）；并发下"一连接一事务"的边界讨论见 [03-并发与异步](../03-运行时与性能/03-并发与异步.md)。

### raw SQL vs 查询构造器 vs ORM

| 路线 | 代表 | 适用 | 代价 |
|---|---|---|---|
| raw SQL | sqlite3 / psycopg 直接写 | 报表、批处理、DBA 审查的语句 | 手写结果映射 |
| 查询构造器 | SQLAlchemy Core | 组合动态查询（过滤条件运行时拼） | 学习一层抽象 |
| ORM | SQLAlchemy ORM / Django ORM | CRUD 密集的业务模型 | N+1 查询、懒加载的隐性 IO、性能悬崖 |

判据：**OLTP 业务模型选 ORM（享受映射与迁移），分析与批量走 raw**；两者可以共存于同一工程（同一连接池上各走各的）。ORM 的 N+1（循环里逐条懒加载）是必须现场盯防的经典陷阱——ORM 的日志/echo 打开即可看见 SQL 放大。

## 示例

```python
import sqlite3
from contextlib import contextmanager
from dataclasses import dataclass

@dataclass(frozen=True)
class Event:
    user_id: int
    kind: str

@contextmanager
def db(path: str):                            # 补齐 sqlite3 不对称的另一半：关闭
    conn = sqlite3.connect(path, autocommit=False)
    conn.row_factory = sqlite3.Row
    try:
        yield conn
        conn.commit()                         # 成功路径：提交
    except Exception:
        conn.rollback()                       # 异常路径：整体撤销
        raise
    finally:
        conn.close()

with db("app.db") as conn:
    conn.executemany("INSERT INTO events(user_id, kind) VALUES (?, ?)",
                     [(e.user_id, e.kind) for e in (Event(1, "login"), Event(2, "pay"))])
    top = conn.execute(
        "SELECT user_id, COUNT(*) n FROM events GROUP BY user_id ORDER BY n DESC LIMIT 3"
    ).fetchall()
    print([dict(r) for r in top])
```
