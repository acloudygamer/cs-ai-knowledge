# 02-开发环境与工具链

> 前置：[01-语言定位与执行模型](01-语言定位与执行模型.md)（环境 = 解释器 + 包两要素的来源） · 后续：[10-模块与导入系统](../01-语言核心/10-模块与导入系统.md)、[04-打包与分发](../03-运行时与性能/04-打包与分发.md)、[06-代码质量工具](../04-测试与质量/06-代码质量工具.md)

承接执行模型：跑 Python 代码需要一个具体解释器加一组可导入的第三方包，"环境"就是这两者的组合。本篇讲清隔离的维度与工具谱系，为模块导入（包如何被找到）、打包分发（包如何被构建发布）、质量工具（工具如何挂进流程）奠基。

## 本质

环境管理的本质是二维隔离：**解释器版本** × **依赖包集合**。venv 只隔离后者（共享宿主解释器二进制），conda 两者都管，容器在操作系统层再包一层。工具谱系近年的主线变化是 pip+venv 的地位被 uv（Rust 实现，快一个数量级、原生锁文件）快速取代，但概念模型不变——先懂 pip/venv，任何新工具都只是同一张图的换皮。

## 机制

### 解释器：实现与版本是两个正交问题

- **实现**：CPython（本库基准）、PyPy（JIT 追踪编译）、MicroPython（嵌入式）。生态兼容性以 CPython 为准。
- **版本**：本库基准 3.12 stable / 3.14 latest（见 [versions.json](../versions.json)）。多版本共存：Linux/macOS 用 pyenv 或 `uv python install`；Windows 自带 `py` 启动器（`py -3.12` 选版本）。

### 虚拟环境：隔离什么、不隔离什么

`python -m venv .venv` 生成的目录只有三样东西：指向宿主解释器的入口脚本（`python`/`pip`）、空的 `site-packages`、声明归属的 `pyvenv.cfg`。

- 隔离：包安装目录、console scripts 入口、`pip` 自身。
- 不隔离：解释器二进制与标准库（升级宿主 Python 意味着环境重建）；系统层 C 库（`libxml2`、CUDA——conda 的存在理由）。
- 边界：`--system-site-packages` 可打通宿主包（HPC 集群常见）；venv 是路径隔离，不是安全边界。

约束与后果："装了包却 `ModuleNotFoundError`"九成是解释器对不上——命令行的 `python` 必须指向 `.venv` 内（`which python` 验证），IDE 与 CI 必须显式指定解释器路径。导入时包如何被定位的完整机制见 [10-模块与导入系统](../01-语言核心/10-模块与导入系统.md)。

### 依赖声明与锁：三个层次

| 层次 | 文件 | 语义 |
|---|---|---|
| 直接依赖 + 版本约束 | `pyproject.toml` 的 `[project].dependencies`（PEP 621 声明 + PEP 508 语法） | "我要什么"，如 `httpx>=0.27,<1` |
| 锁（传递依赖全量解析） | `uv.lock` / `poetry.lock` | "全世界精确装什么"，跨机器可复现 |
| 一次性环境 | `requirements.txt` | 简单直接；注意 `pip freeze` 导出的是锁、不是声明 |

工程铁律：声明与锁都进版本库，`.venv` 永不进。`pip install -e .` / `uv sync`（可编辑安装，PEP 660）让改代码立即生效，是库开发日常——机制与版本约束语义（SemVer、`~=`）见 [04-打包与分发](../03-运行时与性能/04-打包与分发.md)。

## 连接

**隔离方案对比——何时用谁**：

| 方案 | 隔离维度 | 适用 | 代价 |
|---|---|---|---|
| venv / uv venv | 包集合 | 一切 Python 项目的默认答案 | 不隔离解释器版本与系统库 |
| pyenv / uv python | 解释器版本 | 多版本开发、CI 版本矩阵 | 只管解释器，仍需 venv |
| conda / miniforge | 解释器 + 包 + 系统 C 库 | 科学计算、CUDA 等二进制依赖 | 生态小于 PyPI，与 pip 混装易碎 |
| Docker | 整个 OS 用户态 | 部署一致性、CI、推理服务 | 重，迭代反馈慢 |

判据：先问"有没有非 Python 二进制依赖"，再问"要不要跨机器复现"——前者决定 conda 与否，后者决定容器与否，其余一律 venv。

**延伸**：CI 里如何拼装这套环境见 [07-CI-CD集成](../04-测试与质量/07-CI-CD集成.md)；Web 服务运行时环境（ASGI 进程模型）见 [01-Web开发总览](../06-应用领域/01-Web开发总览.md)。

## 示例

```bash
# uv 路线（当前事实标准方向）：一个工具管解释器 + 环境 + 锁
uv init myproj && cd myproj      # 生成 pyproject.toml 并初始化 .venv 与锁
uv add httpx                     # 加依赖：更新声明 + uv.lock + 装入 .venv
uv run python -c "import httpx"  # 免激活：uv run 自动选对环境
uv python install 3.12           # 解释器版本本身也归它管
```

```bash
# 传统路线（理解概念、无 uv 环境的兜底）
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -e ".[dev]"          # 可编辑安装 + extras（dev 附加依赖组）
pip freeze > requirements.lock.txt
```

```toml
# pyproject.toml 最小骨架（声明层；完整构建配置见 打包与分发）
[project]
name = "myproj"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = [
    "httpx>=0.27,<1",   # PEP 508：直接依赖 + 约束
]

[project.optional-dependencies]
dev = ["pytest>=8", "ruff>=0.6"]
```
