# 测试覆盖率

## 定义

覆盖率是测试执行过程中代码路径被执行程度的量化指标。覆盖率是**测试完整性的代理信号**，而非正确性的保证——高覆盖率不等于高质量测试，但低覆盖率明确表示存在未测试的代码路径。

## 数学模型

### 覆盖率指标体系

| 指标 | 定义 | 公式 |
|------|------|------|
| 语句覆盖 | 每条可执行语句至少执行一次 | $\frac{\text{exec\_stmts}}{\text{total\_stmts}}$ |
| 分支覆盖 | 每个条件分支的每个方向至少执行一次 | $\frac{\text{branches\_taken}}{\text{total\_branches}}$ |
| 函数覆盖 | 每个函数/方法至少被调用一次 | $\frac{\text{called\_funcs}}{\text{total\_funcs}}$ |
| 行覆盖 | 等价于语句覆盖 | 同上 |
| MC/DC | 修正条件/判定覆盖（航空电子标准） | $\frac{\text{mcdc\_pairs\_covered}}{\text{total\_mcdc\_pairs}}$ |

### 分支覆盖的不对称性

分支覆盖要求测试覆盖条件的两个方向：

```python
if condition:
    return a
return b
```

语句覆盖 $100\%$ 仅需一次调用（任意 condition 值）；分支覆盖 $100\%$ 需两次调用（分别取 True/False）。

$$
\text{branch\_coverage} = \frac{\text{branches\_taken}}{\text{total\_branches}}
$$

**分支复杂度的数学表达**：

$$
\text{branches} = \sum_{i} 2^{\text{condition\_complexity}_i}
$$

每个 `if/else` 产生 2 个分支；每个 `and/or` 表达式产生多个隐式分支。分支覆盖的路径数指数级增长。

### MC/DC 覆盖

修正条件/判定覆盖（Modified Condition/Decision Coverage）是航空电子 DO-178C 标准中的高级覆盖指标。

**判定（Decision）**：布尔表达式的最终值（True/False）

**条件（Condition）**：布尔表达式的原子子表达式

**MC/DC 约束**：每个条件必须独立影响判定的最终值——即，改变该条件的值（其他条件保持不变）必须导致判定结果改变。

$$
\text{MC/DC} = \frac{\text{独立影响判定的条件数}}{\text{总条件数}}
$$

**示例**：对于 `A and B`：
- 条件 A 独立影响判定：A=True→False 或 A=False→True（要求 B=True）
- 条件 B 独立影响判定：B=True→False 或 B=False→True（要求 A=True）

达到 100% MC/DC 需要 4 个测试用例，而非简单的 2 个（分支覆盖）。

### 增量覆盖率

CI 中的增量覆盖率衡量 PR 新增/修改代码的测试充分性。设 $L_{new}$ 为 PR 中新增或修改的行集合，$C_{new} \subseteq L_{new}$ 为测试执行期间实际覆盖的行集合：

$$
\text{coverage}_{delta} = \frac{|C_{new}|}{|L_{new}|}
$$

**关键约束**：百分比不能线性相减（$\%$ 是比值，非可加减的量）。正确做法是比较两次 coverage 报告中的行级覆盖位图（bitmask），计算新增行集合中有多少行被标记为已执行。

`coverage diff` 命令正是基于此原理工作：取 main 分支和 PR 分支的两份 coverage JSON，比较 `L_new` 中每个文件每行的覆盖状态差异。

### 覆盖率的组合谬误

$$
\text{aggregate\_coverage} = \frac{\text{covered\_lines}}{\text{total\_lines}}
$$

aggregate coverage 可能掩盖新增未测试代码：若新 PR 增加 100 行测试代码且新功能 100 行无测试，覆盖率可能因稀释而变化不大。

### 100% 覆盖率的理论不可能性

对于非平凡程序，达到 100% 覆盖率在理论上是不可能的（停机问题的不可判定性）：

**路径爆炸**：包含 $n$ 个分支的程序，其路径数为 $2^n$。测试所有路径的复杂度是指数级的，无法在有限时间内完成。

$$
\text{paths} = \sum_{i=0}^{n} \binom{n}{i} = 2^n
$$

**停机问题的归约**：给定一个程序 $P$ 和输入 $x$，构造一个分支使得 $P(x)$ 停机对应一个分支（return），$P(x)$ 不停机对应另一个分支（while True）。测试所有路径要求判定 $P(x)$ 是否停机——这是停机问题的变体，已知不可判定。

因此，100% 覆盖率仅在理论上有意义，实际测试策略应聚焦于**高价值路径覆盖**（关键路径、边界条件、错误处理）。

## 数据流

<pre>
测试执行
    │
    ├── coverage.py / pytest-cov 启动
    │      │
    │      ├── AST 解析源码
    │      ├── 插桩：每条可执行语句前插入追踪计数
    │      └── 执行测试
    │
    ├── 追踪模块
    │      │
    │      ├── 行追踪：__lines__[line_number]++
    │      ├── 分支追踪：__branch__[branch_id]++
    │      └── 函数追踪：__call__[func_id]++
    │
    └── 覆盖率报告生成
           │
           ├── 覆盖行标记（term-missing）
           ├── 分支覆盖可视化
           └── XML/JSON 输出（供 CI 解析）
</pre>

**插桩的数据形态**：
1. **源码 AST** → 解析得到可执行语句列表
2. **追踪位图** → 每行/分支对应一个计数位，执行时原子递增
3. **覆盖报告** → 位图与源码映射，标记已执行/未执行行

## 机制

### 覆盖率工具的插桩原理

coverage.py 在测试收集阶段通过 AST 重写或字节码插桩，在每条可执行语句前插入计数指令：

```python
# 原始代码
def foo(x):
    if x > 0:
        return x
    return -x

# 插桩后（概念等价）
def foo(x):
    __trace__.count(4)  # if x > 0:
    if x > 0:
        __trace__.count(5)  # return x
        return x
    __trace__.count(6)  # return -x
    return -x
```

**AST 重写 vs 字节码插桩**：
- AST 重写：在源码解析阶段修改 AST，插入追踪调用
- 字节码插桩：在编译后字节码中插入追踪指令，性能开销更小但调试困难

### 覆盖率的盲区

覆盖率无法区分：
- 测试**断言正确行为** vs 测试**仅执行代码**
- 测试**验证错误处理** vs 测试**通过异常捕获避免错误**
- 测试**边界条件** vs 测试**典型路径**

高覆盖 + 弱断言 = 虚假安全感。

**典型盲区示例**：

```python
def divide(a, b):
    if b == 0:
        raise ValueError("div by zero")
    return a / b

# 测试
def test_divide():
    assert divide(6, 2) == 3  # 只测试典型路径，b==0 分支未覆盖
```

### 覆盖率的互补方法：突变测试

覆盖率衡量代码是否被执行，**不衡量测试是否有效**。突变测试（Mutation Testing）通过故意注入代码缺陷来验证测试质量：

$$
\text{mutation\_score} = \frac{\text{killed\_mutants}}{\text{total\_mutants}}
$$

**变异算子**：
- `AOR`（算术运算符替换）：`+` → `-`，`*` → `/`
- `LCR`（逻辑运算符替换）：`and` → `or`
- `NEG`（条件取反）：`if x` → `if not x`
- `ROR`（关系运算符替换）：`<` → `>=`

**强/弱杀灭**：
- 强杀灭：测试在变异体上失败，且失败原因与原始断言不同
- 弱杀灭：测试在变异体上失败（任何原因）

**覆盖率 vs 突变分数的差异**：

$$
\text{coverage} \in [0, 1] \quad \text{是执行频率} \\
\text{mutation\_score} \in [0, 1] \quad \text{是测试有效性}
$$

高覆盖率可以由"执行但不验证"的测试达到；高突变分数必须由真正验证行为的测试达到。

### 分支覆盖 vs 路径覆盖

分支覆盖仅要求每个分支方向至少执行一次；路径覆盖要求每个可行的执行路径至少执行一次。对于嵌套条件：

```python
if a:
    if b:
        return 1
    return 2
return 3
```

分支覆盖 $100\%$ 需要：
- a=True, b=True（覆盖第一个 if 的 True 和第二个 if 的 True）
- a=True, b=False（覆盖第一个 if 的 True 和第二个 if 的 False）
- a=False（覆盖第一个 if 的 False）

路径覆盖 $100\%$ 还需要：
- a=True, b=True（已在分支覆盖中）

对于无分支的程序，分支覆盖 = 路径覆盖 = 语句覆盖。但嵌套分支导致路径数指数增长：

$$
\text{paths} = 2^{\text{nested\_branches}}
$$

### 排除规则与语义

```toml
[tool.coverage.run]
omit = ["*/tests/*", "*/migrations/*", "*/__pycache__/*"]

[tool.coverage.report]
exclude_lines = [
    "pragma: no cover",           # 故意不覆盖
    "raise NotImplementedError",  # 未实现
    "if TYPE_CHECKING:",          # 仅类型检查时运行
]
```

**语义约束**：`# pragma: no cover` 标记意图性未覆盖路径；但过度使用表明代码可能在逃避测试。

### 覆盖率门禁的阈值设定

`--cov-fail-under=X` 设定覆盖率红线。合理阈值取决于：
- 新项目：70-80%
- 成熟项目：80-90%
- 关键系统（安全、金融）：95%+

**关键约束**：阈值应针对增量覆盖率，而非总覆盖率，防止老代码拉低整体百分比导致 PR 被错误拒绝。

### 增量覆盖率的工作原理

增量覆盖率的核心是**行级位图比较**：

1. 在 main 分支运行 coverage，生成 `base.json`（每行是否被覆盖的位图）
2. 在 PR 分支运行 coverage，生成 `pr.json`
3. 取 diff = `L_new`（PR 中新增/修改的行）
4. 对 diff 中每行，比较 `base.json` 和 `pr.json` 中对应行的覆盖状态
5. 增量覆盖率 = diff 中被覆盖的行数 / diff 总行数

**正确公式**：

$$
\text{delta\_coverage} = \frac{\sum_{l \in L_{new}} \mathbb{1}_{\text{covered}_{pr}(l) \land \neg \text{covered}_{base}(l)}}{|L_{new}|}
$$

即：PR 新增覆盖的行数 / PR 新增/修改的总行数。

## 约束与违反后果

| 约束 | 违反后果 |
|------|---------|
| 覆盖率门禁设置过低 | 总覆盖率 80% 但新增代码 0% 覆盖仍通过 CI |
| 排除规则过于宽泛 | `omit = ["*/migrations/*"]` 排除了 migration 中的业务逻辑测试 |
| 依赖覆盖率而非断言 | 测试仅调用代码无断言，覆盖率高但功能错误无法发现 |
| 覆盖率的路径敏感性 | 只测试 if True 分支，分支覆盖 50% 误认为足够 |
| 覆盖报告不含增量数据 | 100% 覆盖的老代码 + 0% 覆盖的新代码仍显示高覆盖 |
| MC/DC 混淆为分支覆盖 | 复杂布尔表达式用分支覆盖标准认为足够，实际未达到 MC/DC 标准 |
| 100% 语句覆盖 = 充分测试 | 语句覆盖 100% 但未测试错误路径，高风险缺陷仍潜伏 |

pytest --cov=mypackage --cov-fail-under=80 tests/

# XML 输出（CI 集成）
pytest --cov=mypackage --cov-report=xml tests/

# 增量对比
coverage xml -o coverage.xml
coverage diff -m --compare-mode=incremental
```

    # 私有辅助函数由更高层测试覆盖
    pass
```

    "*/__pycache__/*",
