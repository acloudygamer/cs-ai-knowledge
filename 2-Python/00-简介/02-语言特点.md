# 语言特点

## 定义

Python 的核心语言特点源于其**引用语义 + 动态类型 + 解释执行**三位一体的设计：

- **引用语义**：变量是命名绑定而非内存槽位
- **动态类型**：对象携带类型信息而非变量携带
- **解释执行**：字节码由虚拟机逐条调度而非机器码直接硬件执行

## 数学模型

### 动态类型的形式化

Python 的类型系统可建模为**变量名到对象的偏函数**：

$$v: Name \hookrightarrow Object$$

其中 $Name$ 是标识符集合，$Object$ 是对象集合。每个对象是一个四元组：

$$o = (value, \tau, rc, storage)$$

- $value$：对象的实际值
- $\tau$：类型（$\tau \in Type$）
- $rc$：引用计数（$rc \in \mathbb{N}$）
- $storage$：存储位置

类型注解是**断言约束**，不参与运行时检查：

$$\text{typeof}(o) = \tau \implies \text{check}_\tau(o) \text{ 仅在显式调用时发生}$$

### 引用计数的形式化

CPython 的引用计数是**确定性资源管理**：

$$\text{bind}(v, o): rc(o) \leftarrow rc(o) + 1$$
$$\text{unbind}(v, o): rc(o) \leftarrow rc(o) - 1$$
$$\text{destruct}(o): \text{当 } rc(o) = 0 \text{ 时立即析构}$$

这与** tracing GC**（如 Java 的分代收集）不同——后者是非确定性的，对象在 GC 运行时才被回收。

引用计数不能处理循环引用：

$$\exists o_1, o_2: o_1 \rightarrow o_2 \land o_2 \rightarrow o_1 \land rc(o_1) > 0 \land rc(o_2) > 0 \land \text{无法从根集到达}$$

此时需要 tracing GC 作为补充（标记-清除或分代收集）。

### 一切皆对象的对象层次

Python 的对象层次可建模为格（lattice）结构：

$$
\mathcal{O} = (Object, \preceq, \top, \bot)
$$

- $\top = object$（所有类的最终基类）
- $\bot$：无公共下界（基本类型之间无继承关系）
- 子类型关系 $\preceq$ 满足自反性和传递性

### CPython 分代 GC 的形式化

CPython 的循环垃圾回收器基于**分代假设**（weak generational hypothesis）：

$$P(\text{对象存活时长} > t) = e^{-\lambda t} \quad \text{（指数分布假设）}$$

大部分对象是"朝生夕灭"的——函数局部变量在函数返回后即成为垃圾。分代 GC 优先扫描年轻代，将成熟对象晋升，减少扫描量。

GC 代的数学描述：

| 代 | 扫描频率 | 对象存活阈值 |
|----|----------|--------------|
| Generation 0 | 最高 | 0 次晋升 |
| Generation 1 | 中等 | 经历 1 次扫描 |
| Generation 2 | 最低 | 经历 2 次扫描 |

回收代价的数学期望：

$$E[\text{扫描时间}] = \sum_{g=0}^{2} |O_g| \cdot P_g(\text{存活})$$

其中 $|O_g|$ 为第 $g$ 代对象数，$P_g(\text{存活})$ 为存活概率。分代假设使 $P_0(\text{存活}) \ll P_2(\text{存活})$，从而减少总体扫描量。

## 数据流

### 动态类型赋值的数据流

<pre>
x = 10                    int 对象 (Heap)          namespace (dict)
+------------------+       +------------------+      +------------------+
| 1. eval(10)     | ----> | value: 10       |      | "x" → int_obj   |
| 2. 创建 int_obj |       | type: int       |      +------------------+
| 3. rc(int)=1   |       | rc: 1           |
| 4. ns["x"]=ref  |       +------------------+
+------------------+

x = "hello"              int 对象              str 对象 (Heap)
+------------------+       +--------+           +------------------+
| 1. eval("hello")| ----> | rc: 0  | (析构)  | value: "hello"   |
| 2. rc(str)=1   |       +--------+           | type: str        |
| 3. rc(int)→0   |                             | rc: 1            |
| 4. ns["x"]=str |                             +------------------+
+------------------+
</pre>

**所有权转移**：namespace 持有对象的引用，对象持有其值和类型。重新赋值导致旧对象 rc 减 1，新对象 rc 加 1。

### 一切皆对象的数据流

<pre>
def func(): pass         class MyClass: pass    module = __import__("os")
+------------------+       +------------------+   +------------------+
| function 对象     |       | type 对象        |   | module 对象      |
| - codeobject     |       | - __dict__       |   | - __dict__      |
| - globals 引用   |       | - metaclass=type |   | - __name__      |
+------------------+       +------------------+   +------------------+
         │                         │                        │
         └──────────────┬─────────┴────────────────────────┘
                        ▼
                 都是 first-class object
                 可赋值、可传参、可返回值
</pre>

### 循环引用与 GC 的数据流

<pre>
a = []                   b = []
a.append(a)              b.append(a)
# a = [a]                # b = [a]
# rc(a) = 2             # rc(b) = 1
# 形成循环: a -> [a] -> a

可达性分析（GC root = 全局namespace）：
GC 无法从 root 到达 a 和 b（循环引用）
但 rc(a) > 0, rc(b) > 0
→ 引用计数无法回收
→ 需要 tracing GC（分代标记-清除）介入
</pre>

### CPython 循环 GC 的完整数据流

<pre>
触发条件: GC 计数器超过阈值
        │
        ▼
 Generation 0 扫描
        │
        ├── 标记阶段: 从 root (frame, global) 出发，递归标记可达对象
        │    使用 dark hash table 记录已标记对象
        │
        ├── 清除阶段: 遍历非标记对象，收集到 free list
        │    循环引用对象相互引用但无法从 root 到达
        │    此时 rc > 0 但无法从 root 触发 unbind
        │
        └── 晋升阶段: 存活对象晋升到下一代
             │
             ▼
        晋升计数器清零，重新累计
</pre>

**关键洞察**：循环引用的本质是"引用计数局部性"——对象之间的引用关系形成了强连通分量，外部无法介入打破。tracing GC 从外部根集出发，绕过了引用计数的局部性限制。

## 机制

### 动态类型的本质代价

Python 对象头包含 `PyObject_HEAD`：

```c
typedef struct _object {
    PyObject_HEAD       // type pointer + refcount
} PyObject;
```

属性访问的代价：

$$\text{attr\_lookup}(obj, name) = \underbrace{O(1)}_{\text{解引用}} + \underbrace{O(1)}_{\text{类型查找}} + \underbrace{O(1)}_{\text{属性表查找}}$$

相比之下，C 的结构体访问是 $O(1)$ 直接偏移计算（类型在编译时确定）。Python 的灵活性以间接性为代价。

### 解释型语言的两层执行

<pre>
编译阶段 (离线)               运行时阶段
+------------------+           +------------------+
| .py → Token     |           | Frame 创建       |
| Token → AST      |           | Bytecode 解释     |
| AST → CodeObject| --------> | 对象分配/GC      |
+------------------+  .pyc     +------------------+
</pre>

**字节码指令的调度循环**（PVM）：

```c
// 伪代码
while (frame->f_i < len(code)) {
    instr = code[frame->f_i++];
    dispatch[instr]();  // 查表跳转
}
```

每次 dispatch 是一次函数指针调用，是 Python 执行慢于机器码的根本原因。

### 缩进语法的设计约束

Python 使用缩进划分代码块，因为**没有显式的 `end` 关键字或花括号**。这强制了视觉格式与语义的绑定：

$$\text{IndentationError} \iff \text{同一逻辑块的语句缩进不一致}$$

设计约束：缩进必须是**一致的空白字符序列**（空格或 Tab，不能混合）。违反则解析失败。

### "Batteries Included" 的依赖管理含义

Python 标准库提供的能力可形式化为：

$$\text{stdlib} = \bigcup_{i=1}^{n} \text{module}_i$$

其中每个 module 是自包含的，无需外部依赖。这导致：
- **优点**：零配置即可使用文件系统、网络、数据库、并发等能力
- **缺点**：标准库实现未必最优（如 `json` vs `orjson`，`sqlite3` vs 专用数据库）

### 引用语义下的对象同一性与相等性

| 比较操作 | Python 语义 | 数学形式 |
|----------|------------|----------|
| `x is y` | 同一对象（`id(x) == id(y)`） | $x \equiv y$（对象同一） |
| `x == y` | 值相等（`__eq__` 定义） | $x = y$（值相等） |
| `x is None` | 同一性检查 | $x \equiv \bot$ |

`is` 操作是 $O(1)$ 直接指针比较；`==` 操作可能调用 `__eq__`，复杂度由对象决定。

### 分代 GC 的触发条件与收集代价

CPython 的 GC 触发条件由**代际计数器**控制：

$$trigger_gc(g) \iff count_g \geq threshold_g$$

| 代 | 默认阈值 |
|----|----------|
| Generation 0 | 700 |
| Generation 1 | 10 次 Generation 0 扫描后触发 |
| Generation 2 | 10 次 Generation 1 扫描后触发 |

**收集代价的不对称性**：
- Generation 0 扫描最频繁，但对象数量最少
- Generation 2 扫描代价最高，但触发频率最低
- 当循环引用对象的"年龄"（经历扫描次数）达到晋升阈值时，会被晋升到下一代，减少在年轻代的扫描开销

**违反约束的后果**：
- 若对象创建速度远超 GC 扫描速度，内存会持续增长（内存泄漏的表现之一）
- 显式调用 `gc.collect()` 会暂停所有线程（通过 GIL），对实时性要求高的场景需谨慎

### 引用计数与循环 GC 的协同

CPython 的内存管理是**引用计数 + 分代 GC** 的混合系统：

| 机制 | 触发时机 | 回收确定性 | 能处理的循环引用 |
|------|----------|------------|-----------------|
| 引用计数 | 每次 rc 归零 | 即时（确定） | 否 |
| 分代 GC | 计数器超阈值 | 延迟（非确定） | 是 |

**为什么两者必须共存**：引用计数保证了大多数对象的即时回收，维持内存使用的确定性；循环 GC 解决了引用计数的盲区（循环引用）。两者分工明确，互相补充。
