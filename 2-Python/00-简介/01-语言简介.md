# 语言简介

## 定义

Python 是一门由 Guido van Rossum 于 1991 年创立的**解释型、动态类型通用编程语言**。它以**引用语义**为核心——变量是对象的命名绑定而非内存地址的别名——通过自动内存管理（引用计数 + 垃圾回收）将程序员从手动释放中解放出来。Python 的设计哲学是"人的时间比机器的时间更宝贵"，以执行速度的牺牲换取开发效率的大幅提升。

## 数学模型

### 解释器执行模型的形式化

Python 代码的执行可建模为一个**管道函数**：

$$Exec: SourceCode \rightarrow Bytecode \rightarrow Objects$$

各阶段定义为：

$$T_{lex}(n) = O(n) \quad \text{（词法分析）}$$
$$T_{parse}(n) = O(n) \quad \text{（语法分析）}$$
$$T_{compile}(n) = O(n) \quad \text{（编译为字节码）}$$
$$T_{exec}(m) = O(m) \quad \text{（虚拟机执行）}$$

总代价：

$$T_{total}(n, m) = O(n) + O(m)$$

关键约束：**每次运行都重复前三个阶段**，这与编译型语言（C/C++）的代价模型形成对比——后者只需编译一次：

$$T_{compiled}(n) = O(n)_{compile} + O(m)_{machine\_code}$$

解释执行的均摊优势在于无需编译步骤即可运行，适合快速迭代。

### GIL 的并发约束模型

CPython 使用**全局解释器锁**（GIL），其存在性由以下不变量约束：

$$\forall t_1, t_2 \in Threads, t_1 \neq t_2: \neg hold(GIL, t_1) \lor \neg hold(GIL, t_2)$$

即**同一时刻最多一个线程持有 GIL 并执行 Python 字节码**。这意味着：

- **CPU 密集型任务的并行度上界为 1**（单核）
- **I/O 密集型任务可通过阻塞释放 GIL** 实现并发

GIL 的持有周期约 5ms（可配置），在此窗口内多个 CPU 指令交织执行。GIL 释放点包括：
- I/O 系统调用（`read`, `write`, `select`, `poll` 等）
- 特定字节码指令（`LOAD_NAME`, `CALL_FUNCTION` 等）
- 显式 `time.sleep()`

### CPython 内存分配器层次

CPython 的内存分配并非直接调用系统 `malloc`，而是维护一个**多层级分配器**：

<pre>
应用程序 (PyObject* 分配请求)
        │
        ▼
pymalloc arena (256KB chunk, mmap 获取)
        │
        ├── pool (4KB page, 管理同一尺寸对象)
        │     ├── used pagemap: 记录已分配页
        │     └── free block list: 可用块链表
        │
        └── 超出 arena 大小 → 直接 mmap/sbrk

系统分配阈值: > 256KB → 绕过 pymalloc，直接 malloc
</pre>

**关键约束**：pymalloc 的设计针对**小对象**（≤ 256KB）做了优化，对大对象反而有额外开销。频繁分配大对象（如 `list` 快速增长）会退化为系统 `malloc`，触发系统调用和 TLB 失效。

## 数据流

<pre>
源码 (.py)                    字节码 (.pyc)              执行帧 (Frame)
+------------------+          +------------------+         +------------------+
| 文本字符流       | 编译     | CodeObject       | 实例化   | 本地变量表        |
| length = n       | --------> | locals + constants| ----> | bytecode 计数器   |
|                  |          | co_code: m 条    |         | 动态栈           |
+------------------+          +------------------+         +------------------+
                                                                 │
                                                                 ▼
                                                          +------------------+
                                                          | 对象 (Heap)      |
                                                          | refcount + type  |
                                                          +------------------+
</pre>

**阶段间数据形态变换**：

1. **源码**（文本字符串）→ **Token 流**（词法分析产物）
2. **Token 流** → **AST**（语法分析产物）
3. **AST** → **CodeObject**（编译产物，包含字节码 + 常量池）
4. **CodeObject** → **Frame**（运行时实例，每函数调用创建一个 frame）
5. **Frame** → **Heap 对象**（执行字节码时在堆上分配的对象）

     │                             │
     ▼                             ▼
 PyObject* ──────────────────> deref ──> value
</pre>

## 机制

### 为什么 Python 选择解释执行

Python 选择解释执行而非编译执行，基于以下设计约束：

1. **启动延迟最小化**：无需编译即可运行，适合交互式开发和脚本场景
2. **平台无关字节码**：`.pyc` 文件可在任何安装 CPython 的平台上运行
3. **动态代码修改**：无需重新编译即可运行修改后的代码

**违反约束的后果**：
- CPU 密集型程序性能受限——Python 3.12 中每条字节码指令需经过 PVM 的 fetch-decode-execute 循环
- 解决方案：使用 `multiprocessing`（进程级并行）或调用 C 扩展（绕过 PVM）

### GIL 的深层存在理由

CPython 的引用计数是原子操作（通过 `Py_INCREF`/`Py_DEC_REF` 宏），但**复杂对象（如容器）的 GC 需要遍历所有对象图**，这必须在持有 GIL 的情况下进行，否则可能出现数据竞争。

**为什么不能轻易移除 GIL**：
- 移除后需重写整个内存管理子系统为线程安全
- 会破坏与 C 扩展的兼容性（大量 C 扩展假设 GIL 存在）
- 替代方案：`multiprocessing`（进程隔离，无共享状态）、`asyncio`（单线程协作式）、`threading`（I/O 密集型任务）

**PEP 703（无 GIL CPython）** 正在探索中，通过细粒度锁替代 GIL。其核心机制：
- 每个对象拥有独立的**细粒度锁**（per-object lock）替代全局 GIL
- 引用计数的增减需获取对象锁，保证原子性
- 代价：单线程性能下降约 10-15%（锁竞争开销），但多线程 CPU 密集型任务可获得近线性加速

**GIL 与 pymalloc 的交互**：pymalloc 本身是线程安全的（通过内部锁），但多线程同时分配小对象时仍会竞争该锁。GIL 保证同一时刻只有一个线程执行字节码，间接序列化了 pymalloc 的调用，避免了更复杂的锁设计。

### PVM 的 fetch-decode-execute 循环

<pre>
while frame->f_i < len(code):
    instr = code[frame->f_i++]    # Fetch: 取指
    dispatch[instr]()              # Decode + Execute: 译码并执行
</pre>

**函数指针 dispatch 的性能代价**：

每次 dispatch 是通过 `switch` 或函数指针表跳转至目标处理函数。这个间接寻址导致：

- **分支预测失败**：CPU 无法准确预测下一条指令的位置（目标地址从表中读取），流水线停顿
- **I-Cache 失效**：频繁跳转到不同处理函数导致指令缓存命中率下降
- **间接寻址延迟**：从内存加载函数指针的额外访存

对比编译型语言：机器码指令的跳转目标在编译时确定（或使用相对跳转），CPU 分支预测器能有效工作。这是 Python 执行速度比 C 慢一到两个数量级的微观原因。

**约束边界**：使用 `__slots__` 可减少属性查找开销；使用 C 扩展可将关键路径上的 dispatch 循环展开，消除函数指针跳转。

### 设计权衡的深层原因

Python 的核心权衡：**开发效率 vs 执行效率**

$$\text{Python 设计} = \arg\max_{e,d} \text{开发体验}(e) \cdot \text{执行性能}(d)^{-1}$$

约束边界：
- 人的时间（开发）比机器时间（执行）更宝贵
- 快速原型迭代优先于性能优化
- 类型错误延迟到运行时发现（通过 mypy 等静态检查工具可部分解决）
