# 开发环境

## 定义

Python 开发环境是**字节码执行 + 包解析 + 符号表管理**的运行时基础。安装 Python 本质是将 CPython 解释器（`python.exe`）及其标准库部署到本地文件系统，并通过 `PATH` 环境变量使解释器可被发现。虚拟环境通过目录隔离 + `sys.path` 调整实现依赖隔离。

## 数学模型

### 路径解析的形式化

当执行 `python script.py` 时，shell 查找 `python` 可执行文件的过程是**首个匹配原则**：

$$\text{python\_path} = \min \{ p_i \in PATH \mid \exists \text{python.exe} \in p_i \}$$

其中 $\min$ 按 $PATH$ 中的顺序定义（返回第一个匹配）。若有多个 Python 安装，后加入 PATH 的目录优先级更高（因为从左到右扫描）。

### 虚拟环境隔离的数学描述

虚拟环境的隔离效果可形式化为：

$$\forall \text{package } pkg \in \text{venv}_A.\text{site-packages}: \text{import }(pkg) \Rightarrow \text{venv}_A.\text{namespace}$$
$$\forall \text{package } pkg \in \text{venv}_B.\text{site-packages}: \text{import }(pkg) \Rightarrow \text{venv}_B.\text{namespace}$$

且 $\text{venv}_A.\text{site-packages} \cap \text{venv}_B.\text{site-packages} = \emptyset$（若使用 `--copies` 选项则例外）。

隔离的本质是 **sys.path 的有序优先**：

$$\text{import}(pkg) \iff \exists p \in \text{sys.path}: p = \text{venv\_A}/Lib/site-packages \land pkg \in p$$

### pip 依赖解析的约束

pip 使用**贪婪版本匹配 + 回溯求解**策略：

$$\text{selected\_version}(pkg) = \max \{ v \in \text{available\_versions}(pkg) \mid v \succeq \text{constraint} \}$$

其中 $\succeq$ 是满足约束的偏序关系。贪婪策略可能导致依赖冲突：

$$\exists pkg_A, pkg_B: \text{constraint}(pkg_A) \cap \text{constraint}(pkg_B) = \emptyset$$

当冲突发生时，pip 尝试回溯求解：

<pre>
依赖图遍历:
1. 选择一个未满足约束的包
2. 贪心地选择最高版本（满足约束）
3. 若约束冲突，回溯到上一个决策点
4. 尝试次高版本
5. 若所有分支失败，报告冲突

时间复杂度: 最坏情况指数级
实际中受版本数量限制，通常可解
</pre>

### site-packages 的物理布局

<pre>
venv/
├── Lib/
│   └── site-packages/          # 第三方包
│       ├── mypackage-1.2.3.dist-info/
│       │     ├── METADATA         # 包元数据（依赖声明）
│       │     ├── RECORD           # 安装文件清单 + hash
│       │     └── WHEEL            # wheel 元信息
│       └── otherpkg-0.1.0.dist-info/
└── Scripts/                    # Windows 可执行文件
    ├── python.exe              # 入口点（指向 venv 的 python）
    └── pip.exe                 # 包管理（指向 venv 的 pip）
</pre>

## 数据流

### Python 安装的数据流

<pre>
安装包 (.exe/.pkg)           文件系统                环境变量
+------------------+          +------------------+    +------------------+
| 解压标准库       | --------> | {prefix}/Lib/    |    | PATH += {prefix}|
| 复制 python.exe | --------> | {prefix}/Scripts/|    +------------------+
| 写入 pyvenv.cfg | --------> | pyvenv.cfg       |
+------------------+          +------------------+

pip 安装:
+------------------+          site-packages/      pip 缓存
| pip install pkg  | --------> | pkg/             | --------> ~/.cache/pip/
| (PyPI 查询)     |          | pkg-x.x.x.dist-info/
+------------------+          +------------------+
</pre>

### 虚拟环境隔离的数据流

<pre>
激活虚拟环境 (myenv)
1. PATH 修改: PATH = myenv/Scripts:原始 PATH
2. VIRTUAL_ENV = myenv
3. sys.path 被调整（插入 myenv/Lib/site-packages）

sys.path 调整逻辑:
+------------------+          +------------------+
| sys.path[0]     | = 脚本目录（保持不变）       |
| sys.path[1:]    | = myenv 的 site-packages 优先搜索
+------------------+

隔离效果:
- import mypackage 时，优先从 myenv/site-packages 加载
- 不同虚拟环境的同名包可共存（版本可能不同）
</pre>

### venv 创建的数据流（symlink vs copy）

<pre>
python -m venv myenv --symlinks    python -m venv myenv --copies
         │                                │
         ▼                                ▼
   myenv/Scripts/python.exe          myenv/Scripts/python.exe
   (symlink → 原始 python.exe)       (copy → 原始 python.exe 的副本)

Lib/ 目录:
   ├── site-packages/               行为相同
   └── stdlib/                      (不复制，整个目录)
                                       实际通过 pyvenv.cfg 的 home 指向原始 stdlib
</pre>

**关键差异**：
- `--symlinks`：python.exe 是符号链接，系统 Python 升级后 venv 自动使用新版
- `--copies`：python.exe 是完整副本，系统 Python 升级后 venv 保持原版本

### pip 安装的完整数据流

<pre>
pip install requests==2.28.0

Step 1: PyPI 查询
  → 发送 HTTP GET 到 https://pypi.org/pypi/requests/2.28.0/json
  → 获取 JSON 元数据（依赖、文件列表、hash）

Step 2: 依赖解析
  → 构建依赖图: requests → urllib3, charset-normalizer, ...
  → 贪心选择最高兼容版本
  → 若冲突，回溯重试

Step 3: 下载 wheel
  → 下载到 ~/.cache/pip/wheels/
  → 验证 hash (SHA256)

Step 4: 解压到 site-packages
  → 解压 .whl 文件（zip 格式）
  → 创建 .dist-info/ 目录
  → 写入 RECORD 文件（含 hash）

Step 5: 缓存校验
  → pip-selfcheck.json 记录已验证版本
</pre>

## 机制

### 虚拟环境的三层隔离

虚拟环境通过**三层隔离**实现：

1. **解释器副本**：通过 symlink 或 copy 指向原始 Python
2. **site-packages 隔离**：独立的第三方包目录
3. **sys.path 调整**：优先搜索虚拟环境的包

关键约束：`pyvenv.cfg` 中的 `home` 指向原始 Python 安装路径，解释器本身的 stdlib 来自原始安装，仅 site-packages 来自虚拟环境。

### symlink 与 copy 的设计权衡

| 模式 | 优点 | 缺点 |
|------|------|------|
| `--symlinks` | 磁盘占用小，系统 Python 升级自动生效 | Windows 上需开发者模式，跨卷符号链接复杂 |
| `--copies` | 隔离性强，不受系统 Python 影响 | 磁盘占用大，升级需重建 venv |

**Windows 默认行为**：在 Windows 10/11 上，默认使用 symlinks（若权限允许），否则回退到 copies。Linux/Mac 默认 symlinks。

**pyvenv.cfg 中 home 的作用**：即使使用 `--copies`，解释器的标准库仍通过 `home` 路径加载，不复制整个 Lib 目录——这保证 venv 体积可控。

### pip 的包解析机制

pip 从 PyPI（默认）或镜像源下载包。三种分发格式：

| 格式 | 特点 | 安装速度 |
|------|------|----------|
| sdist (.tar.gz) | 源码，需编译 | 慢 |
| wheel (.whl) | 预编译，直接安装 | 快 |
| binary wheel | 平台特定（如 .cp312-cp312-win_amd64.whl） | 最快 |

pip 的版本解析使用**语义版本**（Semantic Versioning）：
- `>=1.0,<2.0`：兼容版本约束
- `~=1.4`：至少 1.4，向上兼容（`>=1.4,<2.0`）
- `==1.4.2`：精确版本

**回溯算法的具体行为**：
1. 构建所有包的依赖图
2. 对每个包，从最高版本向下贪心选择第一个满足约束的版本
3. 若最终方案有冲突（如 A 需要 C>=2.0，B 需要 C<2.0），pip 从冲突点回溯
4. 回溯时尝试次优选择，直到找到兼容组合或确认无解

**约束冲突的典型场景**：
```
package-a requires requests>=2.28.0
package-b requires requests<2.0.0
```
此时 pip 报告冲突，无法同时满足。

### pyvenv.cfg 的配置约束

```ini
home = /usr/local/python3.12
include-system-site-packages = false
version = 3.12.0
```

- `home`：指向原始 Python 安装，解释器从此处加载 stdlib
- `include-system-site-packages`：是否包含系统 site-packages（默认 false）
- `version`：Python 版本号

**include-system-site-packages 的影响**：设为 true 时，虚拟环境的 sys.path 会包含系统 site-packages，此时系统安装的包对虚拟环境可见。但依赖冲突风险增加，不推荐在生产环境使用。

### 版本约束（Python 3.12 stable / Python 3.14 latest）
