# 08-错误与异常

> 前置：[04-控制流程与表达式](04-控制流程与表达式.md)（控制流底座）、[07-面向对象](07-面向对象.md)（异常类是类） · 后续：[09-上下文管理器](09-上下文管理器.md)（with 接管 finally）、[07-日志与调试](../02-IO与工程实践/07-日志与调试.md)（异常的归宿）、[01-pytest基础](../04-测试与质量/01-pytest基础.md)（断言异常）

在 Python 里异常不是耻辱，是控制流的一等形态——EAFP 哲学（宽恕比许可容易）是语言设计选择（见 [01-语言定位与执行模型](../00-概览/01-语言定位与执行模型.md)）。本篇讲清四件事：层次结构（接什么、不接什么）、五个子句的精确语义、异常链与重抛、以及自定义异常的设计规范。

## 本质

- `raise` 是非局部跳转：正常执行流立即中断，沿调用栈上溯找最近的匹配 `except`；找不到则冒到顶层（REPL 打印、进程退出码非零）。
- 异常是对象（`BaseException` 的子类实例），携带三样证据：类型（匹配与语义）、`args`（载荷）、`__traceback__`（完整调用现场）。
- 性能模型：`try` 块在**不抛异常时近乎零成本**（CPython 3.11 起异常表机制，无异常路径基本免费）；`raise` 本身很贵。结论：异常路径用于异常，不要在热循环里拿 raise 当 goto。

## 机制

### 层次结构与"接什么"

```text
BaseException
├── SystemExit        # sys.exit() —— 不是"错误"
├── KeyboardInterrupt # Ctrl-C —— 不是"错误"
├── GeneratorExit     # 生成器关闭协议（见 06-迭代器与生成器）
└── Exception         # 一切"错误"的总基线
    ├── ValueError / TypeError / KeyError / ...   # 内建具体错误
    └── ArithmeticError / LookupError / ...       # 内建分组基类
```

- 裸 `except:` 连 `SystemExit`/`KeyboardInterrupt` 一起吞——程序无法退出、Ctrl-C 失效。**永远写 `except Exception`（或更具体）**。
- 接分组基类是兼容性写法：`except LookupError` 同时接住 `KeyError` 与 `IndexError`——文档化"这类失败"，而非枚举具体类型。

### 五个子句的精确语义

```python
try:
    risky()            # 只放"可能抛"的调用
except ValueError as e:
    handle(e)          # 按类型匹配，第一个命中即止
except (KeyError, IndexError):
    ...
else:
    success()          # 未发生异常才执行——把"正常路径"移出 try 体，
                       # 防止 handle()/success() 自己的异常被误接
finally:
    cleanup()          # 无论如何执行（含 break/return/raise 穿越）
```

陷阱两条：`finally` 里的 `return` / `raise` 会**吞掉**try 体里正在传播的异常（两个都丢）；`except ... as e` 的 `e` 在子句结束即被删除（防止引用循环），要留存须另起名字 `err = e`。

### 异常链与重抛

- 隐式链：except 块内再抛新异常，旧异常自动挂到 `__context__`（"处理时发生了另一个"）。
- 显式链：`raise NewError("...") from e` 挂到 `__cause__`——转换异常边界（把 `KeyError` 转成库自己的 `ConfigError`）时**必须**用，否则丢因。`from None` 是有意的抑制（向调用者隐藏实现细节）。
- 重抛：except 块内裸 `raise` 保留原 traceback（`raise e` 会重建 traceback 栈，多一层当前帧）。惯用法：`except Exception: log...; raise`——记录后原样上抛，见 [07-日志与调试](../02-IO与工程实践/07-日志与调试.md)。

### EAFP vs LBYL

| | EAFP（先做再说） | LBYL（先查再做） |
|---|---|---|
| 形态 | `try: v = d[k] except KeyError:` | `if k in d: v = d[k]` |
| 竞态 | 天然安全 | check-then-act 之间状态可能变（TOCTOU） |
| 性能 | 失败昂贵、成功路径近零成本 | 每次都付检查成本 |
| 适用 | 失败罕见、或检查本身有竞态 | 失败常见、检查廉价且无竞态 |

### 自定义异常的设计规范

```python
class AppError(Exception):
    """库的对外错误基线——调用方except AppError 即接住全部本库错误。"""

class ConfigError(AppError):
    def __init__(self, key: str, reason: str):
        super().__init__(f"config {key!r}: {reason}")   # args 决定 str(e)
        self.key, self.reason = key, reason             # 字段化：调用方可编程处理
```

三条纪律：库顶层必须有自己的异常基线（调用方不必枚举你的内建异常）；载荷放字段而非只塞进消息（字符串是给人看的，字段是给代码用的）；不要在异常类里做复杂逻辑。

### 异常组与 except*（Python 3.11 增量）

`ExceptionGroup` 打包**多个同时发生**的异常，`except* ValueError:` 按成员类型匹配（可多次命中）。存在理由是结构化并发：一组并行任务可能集体失败——`asyncio.TaskGroup` 收集全部异常后整组抛出（见 [03-并发与异步](../03-运行时与性能/03-并发与异步.md)）。单线程顺序代码里几乎不需要手造 ExceptionGroup。

### warning 不是异常

`DeprecationWarning` 等走 warning 通道（不中断执行）；`-W error::DeprecationWarning` 可升格为异常，用在不允许踩废弃 API 的 CI 里（见 [07-CI-CD集成](../04-测试与质量/07-CI-CD集成.md)）。运行时过滤 `warnings.filterwarnings`。

## 示例

```python
import json

def load_config(raw: str) -> dict:
    try:
        cfg = json.loads(raw)
    except json.JSONDecodeError as e:
        # 转换异常边界：显式链保留根因，字段化保留可编程信息
        raise ConfigError("root", "invalid JSON") from e
    if "workers" not in cfg:
        raise ConfigError("workers", "missing required key")
    return cfg

try:
    load_config("{oops")
except ConfigError as e:
    print(f"{e.key}: {e.reason}; cause={e.__cause__!r}")
```

```python
# finally 与 return 的吞噬陷阱：bar 的 ValueError 消失了
def bar():
    try:
        raise ValueError("boom")
    finally:
        return "cleanup"      # 反模式：吞异常
print(bar())                   # cleanup —— 异常去哪了？
```
