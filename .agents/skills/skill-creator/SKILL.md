# 造技能

技能是给以后的自己写的操作手册：一段在特定情境下必须照做的流程，不是一段可以随手取用的知识。

分界只有一条：**这段内容会不会在同类任务里第二次被用到。** 会，进技能；不会，留在当次对话里。

## 一、先问三个问题

1. 什么时候该用它？（触发场景，最终要写进 description）
2. 它产出什么？（一个文件、一段结论、一次操作）
3. 不用它会怎样？（如果答案是"我本来也会"，那就别写）

三个都答不上来就先别动笔。写下来的技能如果每次都要被违反，它就不再是规范，只是噪音——而且违反是不留痕的，没人会检查跳得对不对。

## 二、放哪、叫什么

| 项 | 约定 |
| --- | --- |
| 位置 | 本仓库：`.agents/skills/<name>/SKILL.md`；全局：`~/.dsh/skills/<name>/` |
| 名字 | 小写连字符，与目录同名，frontmatter 的 `name` 与之一致 |
| 生效 | 不用注册，写完下一次会话就出现在技能目录里 |
| 写文件 | 用 fs 工具（write / edit）。**bash、pwsh 这类子进程写不进 `.agents`**，那条路只读 |
| 依赖 | 脚本只用标准库。`.agents` 里装不了 node_modules，需要第三方库就换个思路，别硬装 |

## 三、description 是唯一决定触发的东西

正文写得再好，触发之前也看不见。所以 description 必须同时给出两样：**做什么**，以及**用户在什么话术下需要它**。两条都要具体。

- 写"用户说『看一眼渲染效果』『这张表是不是散了』时用"，别写"用于 Markdown 视觉检查"。
- 宁可稍微主动：模型通常倾向于不用技能，而不是滥用。
- 和已有技能的边界要写出来（"修预览器自身的显示问题走 preview-format-fix"），否则两个都会被拉进来，或者都不被拉进来。
- 用户的特殊要求只有写在这里才生效。比如"默认不主动调用""被点名就直接跑完别追问"。

## 四、正文怎么写

- **先为什么，再做什么。** 讲清意图后模型不需要满篇 MUST；MUST 太多往往说明作者没想清哪条真重要。
- **一条规则带一个来源。** 一次实测、一处代码、一个日期。没有来源的规则，下次没人敢改。
- **给能直接执行的东西**：命令、路径、表格。少写形容，多写"跑这个，看这个"。
- **正文控制在 100 行上下。** 超了就把最长的分支挪进 `references/`，正文留一行指针。加载是分级的——description 常驻、正文触发时读、`references/` 与 `scripts/` 只在被点名时才读——所以正文写"什么时候读哪个文件"，比把内容塞进正文划算。
- **写边界。** "这个技能不做什么"比"它做什么"更能防误用。

## 五、交付前拿一个真任务跑一遍

不是造 eval 集，是**用一次**：挑一个真实输入，照文档走一遍，看结果对不对。

跑完回填三件事：哪一步文档没说清、哪条规则其实没用上、哪句被自己跳过了。被跳过的那句多半该删——技能最贵的不是长度，是"每次都要私下筛一遍"。

## 六、什么时候读附录

| 文件 | 什么时候读 |
| --- | --- |
| `references/eval-harness.md` | 要给别人的技能打分，或触发率明显不对时。双批子代理、grading、benchmark、盲比、description 优化全流程 |
| `references/schemas.md` | 要写 `evals.json` / `grading.json` / `benchmark.json` 时查字段 |

评测机器的零件都在 `references/eval/`（三个子代理说明书、评审页、模板），评测脚本在 `scripts/experimental/`，两处都不在默认路径上；跑 `claude -p` 的那几个测的是别的模型的触发率，当相对参考用。

## 七、脚本

```bash
python scripts/quick_validate.py "<技能目录>"     # frontmatter 与结构自检，一句话结论
```

Windows 上先设 `$env:PYTHONUTF8="1"`：脚本按 UTF-8 读文件，但解释器默认用 GBK 打开，含中文的 SKILL.md 会直接抛 `UnicodeDecodeError`。
