# 容器化基础

## 一、容器 = namespace（视图切分）+ cgroups（资源配额）

容器不是一台机器，而是一个进程。02-操作系统 已经确立这条底座：内核把每个执行流表示为一个 task 结构（task_struct，进程在内核中的唯一身份记录），一进程一棵页表树，地址空间私有由页表项的用户/内核位与读写位保证，全局挂载表由虚拟文件系统（VFS，Virtual File System）逐条维护。容器没有给这台机器添加任何新硬件或新内核，它只把上述既有机制挪用为隔离手段：namespace（命名空间）在进程组访问内核查找表的路径上加视图过滤，cgroups（control groups，控制组）给进程组加资源记账与限额。内核里至今没有"容器"这个对象——所谓容器，只是一组 task 结构、几枚 namespace 指针与一条 cgroup 归属关系的总称。

由此立起全篇的核心断言：**隔离是内核视图的投影，不是虚拟出第二台机器。** 容器内进程发出的每一条系统调用都直达宿主机唯一内核，由内核按该进程所属的 namespace 过滤结果再返回；硬件没有多出一份指令副本、一个页表副本或一块网卡副本。这条断言把容器与虚拟机划在两个物种里，第三节的对照图是它的完整展开。

### 1.1 排除法立账：chroot 的一维隔离与六个漏口

容器隔离不是一步设计出来的，而是被漏洞逼出来的。1979 年进入 Unix 的 chroot（change root，更换根目录）是最早的尝试：把进程的文件系统根目录重定向到指定子目录，进程从此"看不到"根目录之外的世界。但文件系统只是六个共享视图中的一个——用排除法清点 chroot 之后仍然全机共享的东西，每一个都是一个漏口：

| 漏口（chroot 之后仍全机共享） | 不设防的后果 | 对应 namespace | 切分后各进程组独立拥有 |
| --- | --- | --- | --- |
| 进程号全表 | 能看到并 `kill` 宿主机任意进程 | PID | 以自己为根的 PID 树，自己是 1 号 |
| 网络设备与协议栈 | 端口冲突、可旁听宿主机流量 | NET | 独立网卡、路由表、防火墙规则与 0~65535 端口空间 |
| 全局挂载表 | 能看到宿主机全部挂载点与设备 | MNT | 独立挂载表与独立根文件系统 |
| 主机名 | 一组改名、全机跟着改 | UTS | 独立主机名与域名 |
| 进程间通信对象池 | 跨组可读写共享内存、收发信号 | IPC | 独立的信号量、共享内存与消息队列池 |
| 用户与组 ID 表 | 容器内 uid 0 就是宿主机真 root | USER | uid 映射：容器内 0 号映射到宿主机非特权 uid |

表中 UTS 是 UNIX 分时系统标识（UNIX Time-Sharing System）的缩写，IPC 是进程间通信（Inter-Process Communication）的缩写，uid 是用户 ID（user ID）的缩写。六个漏口对应六个维度，每个 namespace 恰好堵住一个口——这不是巧合，namespace 的维表就是按"内核里哪些查找表被全机共享"逐项列出来的。

### 1.2 namespace 六维切分：同一内核的两份投影

namespace 的本质是内核查找表加了一维过滤。创建容器进程时，`clone()` 系统调用带上 `CLONE_NEWPID | CLONE_NEWNET | CLONE_NEWNS | CLONE_NEWUTS | CLONE_NEWIPC | CLONE_NEWUSER` 六个标志位，内核在六个查找表上各登记一个新表项，把这个进程"罩"进去；此后视图在进程创建那一刻定死，`execve` 换程序也不换视图。宿主机与两个容器在六个维度上各自看到的值如下：

```text
namespace 六维视图切分（同一物理机，内核持有唯一真值，各进程组各领一份投影）：

  内核持有的唯一真值                容器 A 的投影           容器 B 的投影
  ───────────────────             ───────────────        ───────────────
  全局 PID 树（4211、4288…）──切──► 自为根：自己是 1 号 ──切──► 自为根：自己是 1 号
  │                                （外层查得到 4211）      （外层查得到 4288）
  网络设备 eth0 + 协议栈    ──切──► vethA + lo，独立       ──切──► vethB + lo，独立
  │                                端口空间可再听 80        端口空间也可听 80
  全局挂载表 + 各根文件系统 ──切──► / = A 的镜像 rootfs ──切──► / = B 的镜像 rootfs
  内核主机名（全局一处）    ──切──► hostname = web-01  ──切──► hostname = db-01
  SysV/POSIX IPC 对象池    ──切──► 只见 A 的共享内存   ──切──► 只见 B 的共享内存
  全局 uid/gid 表          ──切──► 容器内 0 → 宿主机    ──切──► 容器内 0 → 宿主机
  │                                非特权 uid 100000       非特权 uid 100100

  方向性：外层 namespace 永远看得见内层（宿主机 ps 列出 4211），
          内层看不见外层（容器内 ps 只剩自己那棵树）
```

逐维遍历这张图，四个维度值得展开，两个维度一句话带过：

- **PID 维：一棵树两套编号。** 容器内进程在自家 namespace 里是 1 号，在宿主机全局树里仍是普通 task（如 4211）。1 号在 Unix 里承担收养孤儿进程与接收信号的职责，所以容器内 1 号必须正确转发终止信号（SIGTERM），否则 `docker stop` 会等到超时后改发强杀（SIGKILL）——这是视图投影直接改变进程行为的实例。方向性在这里最直观：内层看不见外层，外层始终看得见内层，调试（宿主机上排查容器进程）与安全（容器内进程摸不到宿主机进程表）都由这一条单向性同时给出。
- **NET 维：一条虚拟网线通到宿主机。** 每个网络 namespace 开局只有一块回环网卡 lo，宿主机用一对虚拟以太网线对（veth pair）把它接进来：一头插在容器内改名 eth0，一头留在宿主机桥接设备上。容器组各有一套独立的路由表、防火墙规则与端口空间，所以 A 与 B 能同时监听 80 端口——它们监听的是两块不同虚拟网卡上的 80。
- **MNT 维：挂载表指向镜像。** 挂载 namespace 复制时继承父进程的整张挂载表，容器创建随即用 `pivot_root` 把根目录切到镜像展开出来的根文件系统（rootfs）上——"镜像是什么、如何长出这棵根目录树"是第二节的主题，此处只确立挂载点在哪个维度被隔离。
- **USER 维：把 uid 0 关进笼子。** 用户 namespace 建立一张映射表，容器内的 root（uid 0）落到宿主机上是一个非特权 uid。没有它，容器内拿到 root 等于宿主机拿到 root，前五个维度切得再干净也挡不住"根即全权"这条 Unix 老规则。
- UTS 维与 IPC 维各切一张小表：前者让每组进程有自己的主机名（日志与集群注册按名字区分），后者让共享内存与信号量不出组——防止一组进程伪造 IPC 键值读取另一组的共享内存。

可核验：Linux 下 `lsns` 列出当前机器可见的 namespace（列 `NS` 为内核对象号、`TYPE` 为维度、`NPROCS` 为组内进程数）；对运行中的容器执行 `docker exec <容器> lsns`，会看到与宿主机输出完全不同的 NS 号——两份投影各自成表，就是六维切分的直接物证。

### 1.3 cgroups：视图之外的资源记账与限额

namespace 切的是"看见什么"，不切"能用多少"——这是排除法的第二段。即使六个维度全部罩上，一台容器里的 fork 炸弹仍能吃光整机进程表额度，一个内存黑洞仍能把宿主机物理内存耗尽：因为调度器与内存管理只认 task，而所有 task 在资源竞争里一律平等。cgroups 补上这一层：把一组 task 挂到 /sys/fs/cgroup 树上的一个节点，节点里的控制文件就是该组的资源边界。Linux 5.x 之后的 cgroups v2 统一层级把三类核心限额收进同一棵树：

| 控制器 | 限额文件 | 语义 | 超限动作（机制归因） |
| --- | --- | --- | --- |
| memory | `memory.max` | 组内内存用量上限（记账单位是页） | 内核 OOM（out-of-memory，内存耗尽）杀手在组内选中占用最大的进程发 SIGKILL——动作是"杀"，不可恢复 |
| cpu | `cpu.max` | 两个数：`quota period`，每 period 微秒内最多用 quota 微秒 | 该组被暂停调度到下一周期（限流）——动作是"等"，可恢复 |
| io | `io.max` | 按设备限每秒读写次数与字节带宽 | 超标请求被内核延迟下发——动作是"缓"，可恢复 |

三类超限动作的方向必须写死：内存超限是终止（进程被杀、容器按策略退出），CPU 与 IO 超限只是减速。这也是"配额不是性能保证而是边界保证"的具体含义——配额封顶不封底，空闲资源仍允许组内用满。

可核验：`docker run --memory=512m --cpus=1.5 <镜像>` 启动后，到 cgroups v2 的容器组目录执行 `cat memory.max`，预期读到 536870912（即 512 MiB 的字节数）；执行 `cat cpu.max`，预期读到 `150000 100000`——每 100000 微秒周期最多使用 150000 微秒，折合 1.5 核。写在容器目录里的这两个文件，就是 1.3 节控制器的直接物证。

至此隔离的两半各就各位：namespace 给视图、cgroups 给配额。还剩最后一问——容器进程的根目录下那套文件从哪来，这是下一节的主题。

## 二、镜像分层与联合文件系统：构建即缓存

namespace 的 MNT 维给容器进程切出了独立的挂载表，但挂载表是空的，还需要一个根文件系统挂进去。容器对 rootfs 的要求是反常的：单机几百个容器要共享同一套基础文件（否则每容器一份 GB 级拷贝，密度优势全毁），同时每个容器又要能独立改写自己的文件（否则应用无法运行）。镜像分层加联合文件系统是这对矛盾的解，而解法的关键落点在"谁真正被写"。

### 2.1 镜像 = 只读层栈：OCI 清单与层哈希

镜像按 OCI（Open Container Initiative，开放容器倡议）镜像规范组织：一份清单（manifest）列出配置对象与各层的哈希，每一层是一组文件变更的 tar 包，附 sha256 内容摘要。构建文件（Dockerfile）的每条指令产出一层：`FROM` 展开基础发行版是第 1 层，`RUN` 装依赖是第 2 层，`COPY` 放进源码是第 3 层——层与层之间只记增量，下层的文件在上层可见，整栈叠加就是完整 rootfs。

层哈希是内容哈希：层内容不变则哈希不变，这个性质让"层哈希即缓存键"。04-CI-CD 的缓存键结论——缓存键（输入内容的哈希）决定命中与否，键失配即全量重建——在镜像层上原样成立，且粒度细到单层：改一行源码只让 `COPY` 及其后的层失效，前面的依赖层照常命中。

可核验：`docker image inspect <镜像>` 输出的 `RootFS.Layers` 是一列 sha256 摘要，长度即层数；`docker history <镜像>` 逐行列出每层由哪条指令产生（`CREATED BY`）与体积（`SIZE`）——层栈结构与 2.3 节的优化规则都能在这两条命令的输出里逐层对上。

### 2.2 overlayfs 联合挂载：写时复制与删除标记

层栈在磁盘上是几摞目录，容器进程需要一个统一视图。overlayfs 按代号处理，它用一次联合挂载把多摞目录叠成一棵树：lowerdir 声明只读层栈（自下而上按镜像层顺序），upperdir 声明本容器独占的可写层，merged 是挂载点，进程在 merged 里看到的 `/` 即整栈合并的结果。

```text
镜像分层与 overlayfs 联合挂载（挂载视角，自上而下）：

        容器进程看到的 /（merged，统一合并视图）
                       ▲ 挂载点
  ┌────────────────────┴─────────────────────┐
  │ upperdir（可写层，每容器一份，容器删除即弃）  │
  │   · 新建文件 → 直接落本层                   │
  │   · 改下层文件 → 先整文件复制上来再改（copy-up）│
  │   · 删下层文件 → 本层落 whiteout 删除标记     │
  ├──────────────────────────────────────────┤
  │ lowerdir 第 3 层：COPY . /app    只读 L3   │
  ├──────────────────────────────────────────┤
  │ lowerdir 第 2 层：RUN 安装依赖    只读 L2   │
  ├──────────────────────────────────────────┤
  │ lowerdir 第 1 层：FROM 基础镜像   只读 L1   │
  └──────────────────────────────────────────┘
        读：自 upper 起向下逐层找，命中即返回
        写：永不触及 lower，改动全部留在 upper
```

对图的逐条路径遍历：

- **读路径**：merged 里的查找自 upper 开始向下逐层比对，任何一层命中即返回——因此上层文件遮蔽下层同名文件，遮蔽的优先级就是层序。
- **写路径（写时复制，Copy-on-Write，COW）**：首次修改 lower 层的文件时，内核先把整个文件复制到 upper，之后所有写都落在副本上；lower 层的字节一个不动。代价账本很直白：copy-up 的成本与文件体积成正比，首次写一个百 MB 级文件就付一次百 MB 级复制，后续写零额外。
- **删除路径**：删除 lower 层文件时不能真删（下层只读），内核在 upper 里落一个 whiteout（删除标记），merged 视图里该文件从此消失；重建同名文件则撤掉标记。
- **新建路径**：全新文件直接落 upper，不触发复制。

| 容器内操作 | overlayfs 实际动作 | 首次代价 | lower 层是否被改 |
| --- | --- | --- | --- |
| 读下层文件 | 逐层查找命中 | 零 | 否 |
| 改下层文件 | copy-up 整文件到 upper 再改 | 与文件体积成正比 | 否 |
| 删下层文件 | upper 落 whiteout 标记 | 常数级 | 否 |
| 新建文件 | 直接写 upper | 零 | 否 |

这张表的反向读法是设计意图：四种操作没有一个会碰 lower 层，于是单机 N 个容器共享同一份镜像层栈，各自的差异全部收敛进每容器一份的 upperdir——GB 级的镜像只占磁盘一份，MB 档的可写层按容器计费。密度优势由"永不改下层"这一条保证，而它同时带来一个副作用：可写层随运行时间增长（日志、临时文件都落在 upper），所以生产容器要求日志外送、数据外挂——可写层被约定为"薄"的。

### 2.3 层序即缓存：构建顺序优化

层缓存按自上而下的顺序判定：逐条指令与上次构建比对，第一条失配指令之后的层全部重建，之前的层直接复用。这条规则把 Dockerfile 的书写顺序变成性能参数——变动频率越低的指令越靠前：

| 指令序（同一份 Dockerfile 两种写法） | 改一行源码后重算的层 | 重算代价方向 |
| --- | --- | --- |
| ① COPY 源码 → ② RUN 安装依赖 | ①② 两层全重算，依赖重新下载安装 | 分钟级档 |
| ① RUN 安装依赖 → ② COPY 源码 | 只有 ② 及其后重算，依赖层命中 | 秒级档 |

第一种写法里源码每次变动都触发依赖重装——依赖并没有变，却因为排在易变层之前而被连带重建；第二种写法把易变的 `COPY` 压到栈底，变动的传播被截断在最窄处。这与 04-CI-CD 流水线按变动频率切分缓存段的 DAG 切分同构：把稳定的构建步骤与易变的构建步骤切开，缓存键的失配范围就等于真实变化的范围。

至此三个部件齐备：只读层栈定义 rootfs 的内容，overlayfs 把它挂成容器进程看到的 `/`，层哈希把构建变成可缓存的过程。下一节把"镜像文件 → 运行中的进程"整条生命周期连成环，并回答单机撑不住之后的问题。

## 三、Docker 运行时与编排：从单机到集群

### 3.1 一次 docker run 的生命周期环

第一节给出隔离的两个内核机制，第二节给出 rootfs 的来源，`docker run` 把它们按固定次序装配起来。这条链共七步，每步只消费上一步的产物：

```text
docker run 的生命周期环（起点：一条命令；终点：进程退出、现场拆除）

 ① 拉镜像 ──► ② 建可写层 ──► ③ 建 namespace ──► ④ 挂 cgroups ──► ⑤ 启进程 ──► ⑥ 运行 ──► ⑦ 死亡即弃
 │校验清单│   │upperdir 落盘│  │clone 带六个     │  │task 挂入   │  │1 号进程   │   │健康检查  │   │可写层删除│
 │哈希   │   │（每容器一份）│  │NEW* 标志位      │  │cgroup 组   │  │执行入口   │   │日志输出  │   │镜像不动  │
 ▼                                                                                          │
 └────────────── 重建容器 = 从 ① 重走一遍（同一镜像哈希，得到全新可写层）◄────────────────────┘
```

逐环核对职责：①按清单哈希校验镜像各层，缺哪层补哪层（层哈希在此第二次充当缓存键——这次是跨机器的分发缓存）；②在宿主机文件系统上落一份空 upperdir；③用带 `CLONE_NEW*` 标志的 `clone()` 创建进程组，六个视图一步罩齐；④把组内 task 挂进 cgroup 树的新节点，限额文件写入；⑤入口命令作为组内 1 号启动；⑥进程运行，stdout/stderr 由运行时收走；⑦进程退出后可写层整体删除，宿主机上不留运行痕迹。②③④⑤是装配阶段（毫秒级），⑥是生命周期主体，⑦回到与①相同的镜像起点——环闭合。

第⑦环的"死亡即弃"是刻意设计而非实现偷懒：镜像只读层永不改、可写层随容器生灭，意味着**容器的正确修复方式是重建而不是修补**。这与 04-CI-CD 的制品不可变性同构——同一哈希制品沿环境晋级、回滚即切回上一制品，制品若可变则"回滚"不回到已知状态；容器若允许运行中手工改文件，可写层就成了不可复现的状态，重建不再等于回到已知起点。所以运行时故障的标准处置是删容器、按同一镜像哈希重走 ①~⑤，而不是进容器改文件——重建在毫秒级装配成本下恰恰是最便宜的选项。

### 3.2 容器 vs 虚拟机：共享内核的分水岭

第一节的核心断言——隔离是视图投影而非第二台机器——决定了容器与虚拟机在栈结构上的分岔：虚拟机靠虚拟机监视器（hypervisor）给每个客户机配一套真内核，容器让所有租户共用宿主机那一个内核，差别只剩视图与配额。

```text
容器栈（共享内核）                        虚拟机栈（各带内核）

 ┌───────┐ ┌───────┐ ┌───────┐         ┌─────────────┐  ┌─────────────┐
 │ 容器 A │ │ 容器 B │ │ 容器 C │         │    VM A     │  │    VM B     │
 │ 进程组 │ │ 进程组 │ │ 进程组 │         │ 应用 + 库    │  │ 应用 + 库    │
 │六维视图 │ │六维视图 │ │六维视图 │        │ 客户内核     │  │ 客户内核     │
 │cgroup  │ │cgroup  │ │cgroup  │        │ 完整 OS 栈   │  │ 完整 OS 栈   │
 │ 限额   │ │ 限额   │ │ 限额   │         └──────┬──────┘  └──────┬──────┘
 └───┬───┘ └───┬───┘ └───┬───┘                └───────┬────────┘
     └─────────┴────┬────┘                            ▼
                    ▼                        虚拟机监视器（hypervisor）
         宿主机 OS（唯一内核）                 硬件虚拟化：CPU/内存/设备
         全部系统调用直达此内核               按客户机逐一模拟
                    ▼                                ▼
                 物理硬件 ◄────────────────────── 物理硬件

 启动 = execve + 建视图 + 挂限额           启动 = 固件 → 引导 → 内核 init
       毫秒级                                   十秒级
 隔离边界 = 一个共享内核的系统调用面         隔离边界 = hypervisor 的缺陷面
```

图中每个箭头对应一条真实流：容器侧只有"系统调用直达宿主机内核"这一条边；虚拟机侧每个客户机的系统调用先被自己的内核处理，内核再经 hypervisor 的 CPU/内存/设备虚拟化落到物理硬件——多出一整层，也多出一整套内核。逐项对照代价与收益：

| 维度 | 容器 | 虚拟机 | 方向不等式 |
| --- | --- | --- | --- |
| 启动 | `execve` 加建视图加挂限额，毫秒级 | 固件、引导、内核 init 全流程，十秒级 | 容器快 1~2 个数量级 |
| 单机密度 | 每容器开销 MB 档（可写层加内核对象），数百个同机 | 每 VM 开销 GB 档（客户内核加完整 OS），数十个同机 | 容器高一个数量级 |
| 隔离强度 | 逃逸面 = 共享内核的系统调用面 | 逃逸面 = hypervisor 的虚拟设备与指令模拟路径 | 虚拟机强 |
| 故障域 | 内核 panic 则全机容器同死 | 单 VM 崩溃不波及邻居 | 虚拟机更窄 |

隔离强度一行的账要算清：攻破容器隔离只需利用一个宿主机内核漏洞——攻击面是整套内核代码路径（数百个系统调用及其下游）；攻破虚拟机隔离需要 hypervisor 虚拟化路径上的漏洞，hypervisor 的代码面比整个内核小一个数量级以上，且没有容器内那条"以 root 身份发系统调用"的直通道。两个逃逸面的差距就是隔离强度的差距，方向恒定：**启动速度容器远快于虚拟机，隔离强度容器低于虚拟机**——共享内核换来毫秒级启动与高密度，代价是所有容器共用同一个内核逃逸面。工程上的缓解是收窄这个面而非否认它：seccomp 按容器削减可用系统调用集合（Docker 默认规则禁掉约四成系统调用），用户 namespace 再把容器内 root 降级为宿主机非特权 uid（1.2 节 USER 维的动作在这里兑现为安全收益）。

### 3.3 单机失败模式逼出编排：期望状态与调谐循环

单机 `docker run` 有三个无解的失败模式：宿主机宕机，其上容器全部消失；容器进程崩溃，没有任何机制把它拉起；负载增长，一台机器装不下。这些失败共享同一个结构缺陷——启动容器是一次性动作，动作完成之后没有任何东西在"记住容器应该存在"。编排器补上的正是这个缺失的部件：把"应该有几个什么样的容器"写成期望状态，交给一个永不停歇的循环去逼近。

调谐循环（reconcile loop）的形态是一个三步闭环，没有出口：

```text
调谐循环（每个受管容器组一个，永续运行）

      ┌────────────────────────────────────────────┐
      │                                            │
      ▼                                            │
 ① 读实际状态 ──► ② 与期望状态求差 ──► ③ 执行收敛动作 ──┘
  （现存容器数、   （期望 replicas = 3，   （差 -1 → 按镜像哈希
    健康检查结果）   实际存活 2 个）           重建一个容器；
                                            差 +1 → 删多余）
```

Kubernetes 只作机制概述到这一层就够：期望状态与实际状态存进控制面的存储，每个节点的代理对"本节点应有哪些容器"各跑一个本地调谐循环——全局的编排被拆成大量局部的收敛。健康检查（health check）是循环的状态输入之一：探针连续失败即判定容器不健康，处置动作不是"进容器修"，而是杀掉它——3.1 节的死亡即弃让重建成为最便宜的动作，于是"崩溃 → 杀死 → 调谐循环发现副本缺一 → 按同一镜像哈希重建"成为标准恢复路径，恢复时间与 3.2 表中的毫秒级启动同档。

三条线在此收拢：namespace 与 cgroups 回答"如何在同一内核上隔离"，镜像分层回答"rootfs 从哪来、如何缓存"，调谐循环回答"容器消失后谁来重建"。容器至此解决了"应用如何装、如何以进程级密度运行"——但一个系统该切出哪几个服务、容器边界与业务边界如何对齐，是软件结构问题而非装配问题，交给 06-架构分层与前后端；"每个服务一个容器"的部署形态由 08-微服务消费。
