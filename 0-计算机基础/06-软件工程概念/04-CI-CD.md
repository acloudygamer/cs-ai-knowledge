# CI/CD

## 一、流水线 = 构建依赖的有向图：切分与缓存

持续集成（Continuous Integration，CI）指每次提交自动触发构建与验证；持续交付（Continuous Delivery，CD）指通过验证的制品自动沿环境晋级到可发布状态。承载这两件事的执行载体是流水线（Pipeline）：一条从提交事件出发、经构建与测试、终于可部署制品的自动化链路。它向上消费 01-Git 的提交与合并事件——Git 的提交是把目录快照按内容哈希链入有向无环图、分支只是指向提交的可移动引用，推送与合并本质都是"引用前进"这一事件；向下产出可部署制品，其标准形态由 05-容器化基础回答。本篇的拓扑主干是时序因果链：流水线严格单向推进，每个阶段以上一阶段的产物为输入，任一阶段失败即停，下游永不启动；辅以一条空间事务环——一次提交到生产环境、验证失败后沿回滚通道回到上一已验证状态的闭环。

流水线不是一串顺序命令，而是一张图。各验证步骤之间存在真实的依赖：集成测试需要构建产物，构建需要依赖安装完成，lint 只需要源码本身。把"步骤"建成节点、把"产物依赖"建成边，得到的是一张有向无环图（Directed Acyclic Graph，DAG）——与 01-Git 的提交 DAG 一脉相承：两个 DAG 都用"无环"保证存在一个合法的推进顺序，只是提交 DAG 记录历史，任务 DAG 调度执行。

```text
一次流水线运行的任务图（节点 = 作业，实线边 = 产物依赖，虚线边 = 缓存命中边）

                    push / merge 事件（引用前进）
                            │
                            ▼
                     ┌────────────┐
                     │  checkout  │ 拉取提交快照与依赖清单
                     └─────┬──────┘
          并行切分点 ① ─────┼────────────────────────┐
          ┌────────────────┘                        ▼
          ▼                                ┌────────────────┐
    ┌──────────┐                           │    依赖安装     │◄╌╌ 缓存键 = 依赖清单哈希
    │   lint   │                           └───┬────────┬───┘
    └────┬─────┘              并行切分点 ② ────┼────────┼──────┐
         │                        ┌───────────┘        │      │
         │                        ▼                    ▼      │
         │                  ┌───────────┐       ┌──────────┐  │
         │                  │  单元测试  │       │   构建    │◄╌┤ 缓存键 = 源码哈希+工具链版本
         │                  └─────┬─────┘       └────┬─────┘  │
         │                        │  汇合             │        │
         │                        ▼                  │        │
         │                  ┌────────────┐           │        │
         └─────────────────►│  集成测试   │◄──────────┘        │
                            └─────┬──────┘────────────────────┘
                                  ▼
                            ┌────────────┐
                            │ 打包与归档  │  产出制品 artifact:SHA
                            └────────────┘
```

### 1. 执行器：拓扑序调度与退出码门

对这张 DAG，执行器（Runner）按拓扑序调度：先算每个节点的入度，把入度为零的节点（checkout）投到空闲执行机上；某节点退出后，把它的所有下游节点入度减一，减到零的节点继续投递。图中的两条并行切分点由此产生：切分点 ① 处 lint 与依赖安装互不依赖，各自占一台执行机同时开跑；切分点 ② 处单元测试与构建只共享依赖安装的产物，也并行推进。并行不改变语义——图的边仍是全序依赖，并行的只是无依赖关系的支路。

每个节点是一个或多个进程步骤，成败判定依据是退出码：03-终端与Shell 的结论是，进程退出状态里有一个 0~255 的 8 位退出码档，0 表示成功、非 0 表示失败，命令链上第一个非零退出码即可中断整条链。流水线把这条规则当作唯一的门：lint 退出码非 0，切分点 ① 之后与它同批启动的支路照常跑完或被取消（执行器策略），但集成测试节点的三条入边少了一条满足条件，该节点永不启动。这就是"失败即停"的图语义——不需要额外的标志位传递，入度本身就是门。

门上还挂着一个重试判定，它区分两类失败：环境性失败与代码性失败。checkout 拉不到依赖仓库、执行机磁盘满、网络抖动，这些失败的输入没有变，重试是有意义的动作，执行器对它们做有限次自动重试并标记为"基础设施原因"；而编译错误、断言失败这类代码性失败，重试读到的是同一份源码、算出的是同一个非零退出码，重试只是把分钟账重复支付一遍——对它们的唯一合法动作是改码重推。把两类失败混在一起自动重试，会把真实的红灯淹没在重试噪声里；混在一起禁止重试，又会让流水线被基础设施抖动反复误杀。判定依据仍然只有退出码与失败类别标记，不引入新的通道。

### 2. 缓存：键决定命中，命中决定分钟账

DAG 决定了"做什么"，缓存决定"每一步花多久"。流水线中三类中间结果可以跨运行复用，每一类的键都取自"决定其内容的输入集合"的哈希：

| 缓存层 | 缓存键的输入集 | 命中后的动作 | 命中与失配的时长档 |
| --- | --- | --- | --- |
| 依赖下载层 | 依赖清单文件（如 lockfile）内容的哈希 | 从缓存直接还原依赖目录 | 命中：秒级；失配：全量下载，分钟级档 |
| 编译中间产物层 | 源码哈希 + 工具链版本 | 只重编变动的编译单元 | 命中：秒到十秒级；失配：全量重编，分钟级档 |
| 容器镜像层 | 每层构建指令与上下文的哈希（05 展开） | 未变动层直接复用 | 命中：跳过该层；失配：该层起全部重建 |

键命中与否就是一次哈希比对，但后果差出一个数量级档位：冷构建（依赖下载 + 全量编译）落在分钟级到十分钟级档，缓存命中后降到秒级档——方向不等式恒为冷时间远大于热时间，且差的是"分钟对秒"的档位差，不是百分比。

键的构造规则因此有两条硬边界。键过粗——把与产物无关的文件混进哈希输入——则一次无关提交就打翻缓存，全量重建的分钟账按次重复支付；键过细或漏算真实输入——比如键里漏了工具链版本——则会命中陈旧缓存，把"编译环境已变"这个事实瞒过构建节点，错误推迟到测试甚至生产才暴露。正确的键恰好吃满"决定产物的全部输入、且仅这些输入"：内容不变则键不变，键不变则产物不变，这条"寻址即校验"的性质与 01-Git 的内容寻址同构。

读侧之外，写侧还有一条纪律：缓存内容本身不可信，谁验证它。一个曾被污染的缓存条目（键相同、内容损坏或被掺入构建产物之外的文件）会在后续所有运行中反复命中，把同一个错误复制给每一次构建——这就是缓存投毒，它是"键不变则产物不变"这条性质的攻击面。工程上的封堵动作有两个方向：其一是写入方收敛，只允许主链（合并后、测试全绿）的运行写入共享缓存，PR 运行只读不写，把污染源挡在门禁之外；其二是产物自证，对缓存条目连同其哈希一起存取，命中后校验一致性，不一致即按失配处理。两个动作都是把"缓存命中"从无条件的信任降级为可校验的复用——复用是收益，校验是代价，与"键失配全量重建"共同构成缓存的完整代价账。

### 3. 快慢分离：两级流水线与反馈环长度

把全部验证串成一条链，反馈环就是全链总时长；把验证按速度分层、分挂在不同的门上，反馈环就被切短。快级（lint + 单元测试，秒级档）挂在 PR 门禁上，慢级（集成，分钟级档；E2E，秒到分钟级档）挂在合并后的主链上——这个分层的依据是 02-测试策略 的金字塔结论在门禁上的落地，第二节展开。方向不等式锚定：反馈环越短，提交者等待结果时保持在同一上下文中的概率越高，修复越快；反馈环一旦超过十分钟档，开发者在等待期切走上下文、回来重建心理状态的成本开始超过修复本身的成本，行为随之退化为攒大批量提交——大批量又进一步拉长单次反馈与加大失败定位半径，形成正反馈恶化。快慢分离正是切断这个正反馈的机制动作：把占验证总量大头的快级验证压到秒级档，让每一次推送都能立即得到裁决，慢级验证的分钟账由主链承担、不挡在个人反馈环上。

## 二、构建、测试与部署阶段：每道门的判定

第一节给出了流水线的骨架——DAG、调度与缓存；本节进入链路的主体段：构建把源码变成制品，测试把验证金字塔落成一道道门，部署把制品投进环境。三个阶段共用同一条纪律：每道门只认上一阶段的产物与一个二值判定，判定不过，流转即停。

### 1. 构建：源码到带版本号的不可变制品

构建节点的输入是三样：提交快照（源码）、依赖清单解析出的依赖闭包、工具链。三者中只有源码随提交变化，另外两个都必须被钉死：工具链版本写进构建镜像或环境声明；依赖闭包由锁文件（lockfile）钉死——依赖清单只声明"要哪些包及其版本范围"，每次解析可能落在不同的具体版本上，而锁文件把解析结果固化成一份精确的版本快照，后续构建不再重新解析、只按快照取包。没有锁文件的构建，两个相隔一周的运行可能拿到两份不同的依赖闭包，构建产物在源码未变的情况下发生漂移——这正是"输入决定产物"性质的缺口。锁文件把依赖从"每次重新掷骰"变成"给定常数"，随源码一起进版本库，是构建可复现的最小前提。输出是一个带版本号的制品（Artifact）——编译产物、打包归档或镜像，版本号取自提交哈希或由它派生的单调序号。制品一经产出即为不可变制品（Immutable Artifact）：字节不再改变，任何环境要使用它都是拉取同一份字节，而不是重新构建一份。

"一次构建，处处部署"不是口号，而是一条消除漂移的因果链。反面路径是每个环境各自重新构建：不同环境的工具链版本、依赖解析发生的时间点、构建参数都可能不同，产出的字节就不同——测试环境验证过的字节与生产环境实际运行的字节不是同一份，中间的差异无人验证过。这个"同一逻辑版本在不同环境的实际字节发生无人看管的分叉"就是环境漂移（Environment Drift）。构建一次并把同一哈希投向所有环境，把"测过的字节 = 跑的字节"变成恒等式，从机制上消除了每次重建引入的工具链与依赖解析差异；代价是构建节点成为单点——它失败，整条链没有制品可用，所以它的缓存与可重试性按第一节的标准配置。

### 2. 测试门：金字塔落到三道门

02-测试策略 的金字塔把验证分成三层并给出方向不等式：单元测试隔离一切外部依赖、毫秒级且数量最多；集成测试验证模块间连接处、单条几十毫秒到秒级；端到端（End-to-End，E2E）测试走真实用户路径、秒到分钟级且数量最少。流水线不重推这套分层，只把它装配到三个位置上，形成"层级挡流量"的门禁矩阵：

| 门 | 位置 | 挂载的验证层 | 时长档 | 挡住的流转 |
| --- | --- | --- | --- | --- |
| PR 门禁 | 推送后、合并进主干前 | lint + 单元测试（快级） | 秒级档 | 不合格提交进不了主干分支 |
| 合并门 | 合并后的主链 | 集成测试（慢级） | 分钟级档 | 主链失败阻断制品产出 |
| 发布门 | 晋级生产环境前 | E2E 测试 + 人工审批 | 分钟级档 | 未过发布门的制品进不了生产 |

三道门与第一节的快慢分离互相咬合：PR 门禁只挂秒级档的快级，是因为它处在个人反馈环上；集成与 E2E 的分钟账由主链与发布门承担。每一层验证失败都遵循同一状态转移：门不开，制品停在原地，下游节点不启动。

### 3. 阶段失败处置：谁的动作、回滚到哪

"失败即停"在图上是入度归不上一，在组织上是责任与动作的分配。各阶段失败的判定依据、处置主体与回滚范围逐行列出：

| 失败阶段 | 成败判定依据 | 谁的动作 | 回滚范围 | 流水线终态 |
| --- | --- | --- | --- | --- |
| checkout | 引用不存在或网络失败 | 检查引用、执行器自动重试 | 无（未产生任何状态） | 终止，无产物 |
| lint | 退出码非 0 | 提交者改码重新推送 | 无需回滚（无制品产生） | 终止 |
| 单元测试 | 退出码非 0 | 提交者改码重新推送 | 无需回滚 | 终止 |
| 依赖安装与构建 | 依赖不可解析或编译错误 | 提交者改码或锁定依赖版本 | 丢弃半成品，不写入本次缓存 | 终止 |
| 集成测试 | 退出码非 0 | 提交者修复（缺陷多在连接处，02 结论） | 无需回滚，制品不产出 | 终止 |
| E2E（发布门） | 退出码非 0 | 提交者确认预期行为后修复 | 晋级中止，制品留在原环境 | 终止发布 |
| 部署后验证 | 健康检查与错误率基线越限 | 值班工程师执行回滚 | 生产流量反向切回上一已验证制品（三.2） | 生产回到旧版本，事件转入复盘 |

前六行的共同点是"无生产状态可回滚"——失败发生在制品投产之前，止损动作就是不让它投产。只有最后一行不同：错误流量已经到达用户，止损动作从"拦截"变成"回退"，这正是第三节回滚机制的消费场景。

### 4. 部署策略：蓝绿与金丝雀的流量切换

制品通过发布门后进入部署。把新版本直接替换旧版本，失败时要付出"重新部署旧版本"的分钟级代价，且错误暴露面是全部用户。两种降低暴露面的策略由此而来，它们的差别在于流量切换的粒度。

蓝绿部署（Blue-Green Deployment）维护两套等价环境，切换是路由表上的一条记录：

```text
蓝绿部署：一条路由记录的两个状态（视角：流量面）

     切换前                                切换后
     用户流量                              用户流量
        │                                    │
        ▼                                    ▼
  ┌───────────┐ 100%                  ┌───────────┐ 0%（保温待命）
  │  蓝  v_n  │◄──┐                   │  蓝  v_n  │◄──┐
  └───────────┘   │  路由表            └───────────┘   │  路由表
  ┌───────────┐ 0%   同一条        ┌───────────┐ 100%  同一条记录
  │ 绿 v_n+1  │◄──┘   记录         │ 绿 v_n+1  │◄──┘   改指绿
  └───────────┘                    └───────────┘
        ▲
        └─ 绿先通过内部验证（部署脚本退出码 0 + 冒烟测试通过）
           才取得切换资格

  回滚 = 同一条记录改回蓝：秒级，因为蓝从未销毁
```

图的遍历：切换前，全部流量走蓝（旧版本 v_n），绿（新版本 v_n+1）流量为零，但必须先在绿上完成部署验证——部署动作本身退出码为 0，且冒烟测试（Smoke Test，对最核心路径的极小验证集）通过——才取得切换资格；切换动作是把路由表的同一条记录从蓝改指绿，秒级完成；切换后蓝不销毁而是保温，回滚就是把这条记录改回去，同样秒级。代价明码标价：两套环境全程同时在线，资源翻倍；且切换瞬间是全量暴露——若缺陷在绿上，全部用户同时承受。

金丝雀发布（Canary Release）把一次性切换拆成随观察窗推进的逐级放量：

```text
金丝雀放量：比例随观察窗推进（视角：流量面 + 指标面）

  流量 5% ──观察窗 T1──► 25% ──观察窗 T2──► 50% ──► 100%
   │       错误率/延迟      │          │          │
   │       与旧版基线对照    │          │          ▼
   │                       │          │      金丝雀群体并入主流，v_n 退役
   ▼ 任一观察窗指标越限
  停止放量 ──► 金丝雀比例归零，100% 回到 v_n（回滚 = 不再前进）
```

图的遍历：新版本先承接一个小比例流量（典型从个位数百分比起步），每个观察窗（分钟级起步）内把金丝雀群体的错误率与延迟同旧版本基线逐版本对照；指标正常则推进到下一档比例，任一窗口越限则停止放量、比例归零——回滚动作是"不再前进"，因为旧版本始终承接其余全部流量，从未离开。代价与蓝绿互换：资源只多出小比例实例，远低于双份环境；但暴露面靠时间换——放量全程要维持可按版本分组对照的指标基线，观察窗的总时长计入发布周期。

两种策略逐维对照：

| 维度 | 蓝绿 | 金丝雀 |
| --- | --- | --- |
| 切换粒度 | 一次性 100% 切换 | 5% → 25% → 50% → 100% 逐级放量 |
| 资源代价 | 双份环境全程在线 | 仅多一份小比例实例 |
| 回滚动作 | 路由记录切回旧环境，秒级 | 停止放量，比例归零 |
| 错误暴露面 | 切换瞬间全量用户 | 仅金丝雀群体，随窗口扩大 |
| 观察方式 | 切换前后整体对照 | 每个窗口与基线逐版本对照 |
| 前提条件 | 环境可整份复制，新旧版本接口与数据模式兼容 | 指标可按版本分组，新旧版本可按比例共存 |

两行的"前提条件"是硬约束：版本间数据模式不兼容时，蓝绿的秒级切回会踩到新版本已写入的数据，金丝雀的共存会读到彼此的格式——部署策略解决不了数据迁移问题，它只在应用层互斥。

## 三、制品与环境晋级：不可变性与回滚

部署策略回答了"怎么切流量"，本节回答"制品沿着什么路径走到生产、以及走错了怎么退回来"。这条路径是环境晋级链，它与第一节的流水线衔接：流水线终点的制品 artifact:SHA，正是晋级链在每个环境投递的唯一对象。

### 1. 晋级链：同一哈希逐门推进

环境晋级（Promotion）指同一个制品沿 dev → test → staging → prod 的顺序逐环境推进，每道门通过才进入下一环境：

```text
环境晋级链（制品不可变：每个环境投递的都是同一哈希的字节，差异全部外置为配置）

  构建产物 artifact:SHA = e3f1…（只此一份，字节只读，任何环境不得重新构建替换）
        │
        ▼  投递 = 拉取同一哈希 + 注入该环境的配置
  ┌───────┐  门 1 判定：部署脚本退出码 0 且冒烟测试通过
  │ dev   │──────────────► 开发环境自证"装得上、起得来"
  └───────┘
  ┌───────┐  门 2 判定：自动化回归测试全绿
  │ test  │──────────────► 验证层挡下功能缺陷
  └───────┘
  ┌─────────┐ 门 3 判定：E2E 全绿 + 人工审批（变更单）
  │ staging │──────────────► 生产等价环境中的最终彩排
  └─────────┘
  ┌───────┐  门 4 判定：审批 + 发布窗口 + 部署后验证
  │ prod  │                （健康检查通过、错误率回到基线档）
  └───────┘

  每道门只认判定结果：任一门不过，制品停在当前环境，下游不得拉取
```

逐节点遍历：dev 门是自动化判定（部署退出码与冒烟测试），挡"根本装不起来"的制品；test 门挂回归测试，挡功能缺陷——这一步就是第二节合并门的验证层在环境维度的延续；staging 门是发布门（E2E + 人工审批）的落点，staging 环境的配置与拓扑向生产对齐，使 E2E 结论对生产有效；prod 门在审批与发布窗口之外，还要求部署后验证——健康检查通过且错误率回到基线档，才算晋级完成。链上所有门判定都是前两节机制的复用：退出码判定来自第一节，测试分层来自第二节，本节只增加一样东西——人工审批作为门的一种判定类型。

环境之间的全部差异被外置为配置：数据库地址、密钥、副本数、日志级别放在环境变量或配置中心里，投递时注入；制品内不含任何环境特定值。这正是第一节"一次构建，处处部署"在环境维度的兑现：若把配置烘焙进制品，四个环境就需要四份字节不同的制品，哈希各不相同，test 上验证的那份与 prod 上运行的那份再次分叉——环境漂移从门缝里回来。外置配置把漂移源从制品中拆除，代价是配置本身成为一类需要版本化与审计的状态：错误配置能通过全部门禁放倒生产，因为门禁验证的是制品，而配置在制品之外——所以配置变更同样要走流水线与审批，而不是绕过它。

### 2. 回滚 = 反向状态转移，前提是字节不变

部署后验证失败（第二节处置表最后一行）时，止损动作是把生产状态反向转移到上一版本：不是"重新构建旧版本"，而是拉取上一个已通过全链验证的制品哈希，重新投递或切回其环境（蓝绿切回、金丝雀归零都是这条反向边的具体形态）。至此，"一次提交到生产、失败后回到上一已验证状态"的空间事务环闭合。

这条反向边可信的前提，是制品不可变。因果链正向写是：制品不可变 → 历史 SHA 指向的字节今天与发布当时完全一致 → 部署上一 SHA 就是精确回到当时验证过的状态。反面排除：若制品可变（同名覆盖、原地重建），上一版本的字节可能已被后续构建改写，"回滚"部署到的是一份无人验证过的未知字节——回滚动作本身成为新的故障源。这条依赖链与 01-Git 的"对象只增不改、回退靠移动引用而非改写历史"同构：引用可以指回去，是因为被指的对象从未变过。可实操核验：发布记录中存下每个环境的制品 SHA256 摘要，回滚前用 `sha256sum <制品文件>` 与记录比对，字节一致才执行反向切换——把"回滚可信"从纪律变成一次哈希比对。

反向切换完成后，事务环还剩最后一段：状态回到旧版本，但触发回滚的原因还悬着。回滚不是终点而是状态回退——缺陷仍在 v_n+1 的字节里，它要以一个新的提交进入流水线，重新走完全部门禁，才能再次请求晋级；同时本次生产事件进入复盘，把"哪道门没有拦住它"的结论回写进门禁本身——缺一类测试就补挂一层，缺一项指标基线就补进部署后验证。没有这最后一段，同样的缺陷会在下一次发布重新走到用户面前；有了它，晋级链的门禁集合随每一次事故单调收紧，这是闭环留给系统的唯一增量。

### 3. 制品的标准形态：镜像

晋级链在每个环境搬运的制品，最通用的标准形态是镜像：把应用连同其运行时与依赖闭包封成一个带层结构的不可变包，环境差异同样由投递时注入的配置承担——容器不可变、重建优于修复，与本节的制品不可变是同一条纪律在运行载体的投影；而镜像的分 layer 缓存（每层以指令与上下文哈希为键、未变层直接复用）正是第一节缓存键结论在构建工具里的落地。制品解决"带什么走完晋级链"之后，下一个问题是这份封装在操作系统层面如何隔离运行——namespace 视图切分与 cgroups 资源配额的机制，交给 05-容器化基础。
