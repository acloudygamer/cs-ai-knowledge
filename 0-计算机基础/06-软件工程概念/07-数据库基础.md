# 数据库基础

06-架构分层篇的一次用户操作沿「前端 → 网关 → 应用层 → 数据层」的分层链路下行，终点停在应用向数据层发出的持久化调用——本篇从这一跳接手，还原数据层内部机制。数据层内部有三个战场：数据在磁盘上怎么摆（存储引擎与索引）、并发读写各事务看到什么（隔离与 MVCC）、掉电后已提交的数据凭什么还在（预写日志与恢复）。全部机制共享同一条物理前提：磁盘比内存慢两到三个数量级——介质延迟档位见 01-计算机体系 02 的存储层次表（DRAM 百纳秒档、NVMe SSD 百微秒档），数据库的一切组织手段都在围绕这条鸿沟支付或摊薄代价。

## 一、存储引擎与索引：B+ 树与 LSM 的对偶

### 1. 页：磁盘 IO 与缓存的最小单位

数据库不按行读写磁盘，而按**页**搬运：页是磁盘 IO 与缓存的最小单位，大小是锚定常数——PostgreSQL 为 8 KB，MySQL InnoDB 为 16 KB。一行数据小到几十字节，永远只作为页的一部分被整体搬进搬出；一次整页 IO 的代价由页内全部行摊薄，这与 01-计算机体系 02 中 64 字节缓存行摊薄单字节访存的逻辑同构，只是粒度从缓存行放大到页。

数据库在进程内存里自建**缓冲池（Buffer Pool）**，把热页常驻其中。一次行读的链路如下：

```text
SELECT 一行数据的取页链路：
  ① 查缓冲池：目标页在内存 ──► 直接拼出行返回（百纳秒档内存访问）
  ② 未命中 ──► 落到操作系统页缓存：页已在 OS 内存 ──► 一次拷贝入缓冲池（微秒档，差 1~2 个数量级）
  ③ 页缓存也没有 ──► 发起 SSD 随机读，整页读入（十~百微秒档，差 2~3 个数量级）
  ④ 页进入缓冲池，后续同页访问回到 ①
```

命中与未命中的代价差一到两个数量级起步，冷缓冲池下可拉开到三个——这就是缓冲池值得占掉数据库大半内存的量化依据。页缓存与 fsync 的结论由 02-操作系统 篇就地复述一句：操作系统把磁盘块缓存在内存、`write` 返回不代表落盘，`fsync` 才把脏页刷穿设备缓存。

页内行布局采用**槽页结构**：页头存槽数与空闲空间起点，行指针槽数组从页头向下生长，行数据从页尾向上生长，两者在页中间相向逼近；定位一行靠「页号 + 槽号」的偏移而非绝对地址。这与 01-计算机体系 05 的结构体布局结论同构——成员位置由偏移标尺决定、访问粒度由对齐保证——页内行的排布只是把同一套偏移思想搬进一页。行布局到此为止，本篇主线在页与页之间如何组织。

### 2. B+ 树：键对树层的逐级投影

B+ 树是排序数据的投影：把一亿条键值按键序分装到叶节点里，再给叶节点建一层「分段目录」（内节点），再给目录建目录（根节点）。查询键从根进入后，每一层用区间比较排除掉大部分分支，搜索空间被逐层吞噬——与 01-计算机体系 02 中虚拟地址被位段逐级切分的投影流同构：地址靠位段切分定位字节，键靠区间切分定位行。

```text
B+ 树三层结构（扇出取 3 作示意，真实引擎为数百；键为示意值）

            【根节点（第 1 层，1 个页）】
   ┌─────────────────────────────────────────┐
   │   子指针 P1        P2        P3          │
   │   分隔键  10         40                  │
   └─────┬─────────────┬─────────────┬───────┘
         │ k < 10      │ 10 ≤ k < 40 │ k ≥ 40
         ▼             ▼             ▼
  ┌────────────┐ ┌────────────┐ ┌────────────┐
  │ 内节点 A    │ │ 内节点 B    │ │ 内节点 C    │   （第 2 层）
  │ 分隔键 3│7  │ │ 分隔键 15│30│ │ 分隔键 55│68│
  └───┬───┬────┘ └───┬───┬────┘ └───┬───┬────┘
      ▼   ▼          ▼   ▼          ▼   ▼
【叶节点（第 3 层）：有序键 + 行指针，页间双向链表】
 … ⇄ [1 2 3] ⇄ [4 7 9] ⇄ [12 15 20] ⇄ [25 30 35] ⇄ [55 60 68] ⇄ …

点查 k = 15（3 次页读）：
  ① 根节点：15 ∈ [10, 40) → 取 P2 下探          （页读 1）
  ② 内节点 B：15 ∈ [15, 30) → 取对应分支下探     （页读 2）
  ③ 叶 [12 15 20]：定位 15 的行指针 → 回表取行   （页读 3）

范围查 k ∈ [12, 35]（1 次下探 + 叶层顺序扫描）：
  前半 = 点查 k = 12 的路径，落到叶 [12 15 20]
  之后沿叶层双向链表向右：[12 15 20] → [25 30 35]，读到键 > 35 停止
  全程不再触碰第 1、2 层
```

树高决定页读次数，树高由扇出与行数唯一确定。**算例前提**：一张千万行（ $10^{7}$ 行）的表，16 KB 叶页按每条目几十字节计可容纳约 500 个条目，即扇出 $f = 500$。设树高为 $h$（根为第 1 层，叶为第 $h$ 层），全树可容纳的索引条目数约为 $f^{h}$，逐层代入：

$$500^{1} = 5 \times 10^{2}, \qquad 500^{2} = 2.5 \times 10^{5}, \qquad 500^{3} = 1.25 \times 10^{8} \ge 10^{7}$$

即千万行三级就够。一般化求解：

$$h \ge \frac{\ln 10^{7}}{\ln 500} = \frac{16.12}{6.21} \approx 2.59 \quad\Rightarrow\quad h = \lceil 2.59 \rceil = 3$$

推导终点落回量化断言：**千万行级的点查 = 3 次页读**（根、内节点、叶），再加一次回表取行；行数涨到十亿级， $h$ 也只从 3 升到 4——页读次数与数据量呈对数关系，缓冲池再把根与内节点这些薄层常驻内存后，热路径往往只剩最后一级叶页可能未命中。

范围查询的效率来自叶层双向链表：范围起点走一次点查路径定位到叶，之后整段数据在叶层物理上按键序连续排布，沿链表右移就是顺序扫描。顺序读的带宽比随机页读高约两个数量级（方向不等式，同一介质），所以「索引即排序数据的投影」不是修辞——B+ 树把随机定位与顺序扫描两种访问模式同时压到了介质物理极限的形态上。

### 3. LSM：写优化的对偶结构与选型矩阵

B+ 树的写路径要在树的固定位置就地改页，随机 IO 躲不开。LSM（Log-Structured Merge-tree，日志结构合并树）把姿态反过来：先记账、后誊清——写操作先追加进内存表，攒满一批后按键序一次性刷成磁盘上的有序文件，全程顺序写。链路如下：

```text
LSM 写路径（一条追加流水线）：
  写 (k, v) ──► 追加 WAL ──► 内存表（有序结构）攒批
        │ 内存表写满，冻结
        ▼
  刷盘：按键序整体写成 SSTable（Sorted String Table，有序字符串表），顺序追加
        │ 旧层文件越积越多
        ▼
  压实（Compaction）：后台把多层 SSTable 归并排序、去重、丢旧版本，逐层下推

读路径：内存表 → 各层 SSTable 逐层查找；
  无关键的 SSTable 先被布隆过滤器（Bloom Filter）一层层挡掉，避免无效页读
```

代价在此换手。写放大 $W$ 定义为磁盘实际写入量与应用逻辑写入量之比：

$$W = \frac{\text{压实重写的 SSTable 数据量}}{\text{应用逻辑写入量}} \ge 1$$

分层压实下 $W$ 典型落在 5~20 档——同一批数据在逐层下推时被反复重写；换来的读路径代价是：一个点查可能要查内存表加多层 SSTable，层越多读放大越大，压实越激进读放大越小、写放大越大。这与 01-计算机体系 02 中 SSD 的写放大（WAF）同源：LSM 是在软件层主动顺应了闪存「不能就地覆盖写、只能块级擦除」的物理约束，把硬件被迫做的垃圾回收变成了自己可控的批量压实。两种引擎的账本对照如下：

| 维度 | B+ 树 | LSM |
| --- | --- | --- |
| 写路径 | 就地改页：先写 WAL，再改缓冲池脏页，后台刷盘 | 追加进内存表，冻结后按键序刷成 SSTable，顺序写 |
| 读路径（点查） | 树高次页读（3~4 次），路径唯一 | 内存表 + 多层 SSTable 多路查找，布隆过滤器先挡无关键 |
| 读放大 | 低：单路径固定代价 | 中~高：随层数增长，压实缓解 |
| 写放大 | 低~中：就地更新，一份 WAL | 高：压实反复重写，典型 5~20 档 |
| 空间放大 | 低：碎片困在页内 | 中：旧版本待压实回收，存在瞬时双份 |
| 适用负载 | 读多写少、点查与范围查密集 | 写吞吐密集、追加型负载（日志、时序、消息存储） |
| 代表引擎 | PostgreSQL 全部索引、InnoDB 主键索引 | RocksDB、LevelDB、Cassandra、TiKV |

选型方向由这张表锁死：读多写少选 B+ 树（PostgreSQL、InnoDB 皆为此姿态），写吞吐密集且读可容忍多路查找时选 LSM。两者没有优劣，只有负载画像匹配——下一节看读路径上的 B+ 树投影为什么有时不生效。

## 二、索引使用与代价：投影为什么有时不生效

### 1. 聚簇索引与回表：随机读的乘法

索引叶节点存的不是整行，需要区分两种摆放。**聚簇索引（Clustered Index）**：行数据本身随主键序存放在叶页中，InnoDB 的表就是主键聚簇索引——按主键定位即同时拿到整行，无需第二步。**二级索引（Secondary Index）**：叶节点存「索引键 + 主键值」（InnoDB）或「索引键 + 物理地址」（PostgreSQL，堆表上一切索引皆二级，堆表指行按写入序摆放、无主键序的表结构）。用二级索引查非键列时的链路：

```text
二级索引点查（查的列不在索引键中）：
  ① 在二级索引树上定位目标键 → 得到主键值（1 次索引树下降，3~4 次页读）
  ② 拿主键值回聚簇索引树再下降一次取整行 —— 回表（又是 3~4 次页读，且叶页随机分布）

覆盖索引消掉回表：
  查询所需的所有列都在索引键里 → ① 之后就返回，② 整段不存在
```

因果链在此收口：**回表次数 = 命中行数**，每次回表是一次随机页读；回表把「索引命中」乘上一个随机读系数。据此推出两个方向：

- 命中行数少（点查、小范围）：回表系数小，索引完胜全表扫描。
- 命中行数多（占比达到百分之几到百分之十以上的档位）：回表随机读总量逼近甚至超过一次顺序扫的代价，优化器弃索引改全表顺序扫描——顺序读带宽比随机 IOPS 高约两个数量级，这是同一介质的物理方向，不是优化器的偏好。

覆盖索引是消除回表的唯一手段：把查询要取的列并进索引键（InnoDB 靠联合索引把列排进键尾，PostgreSQL 用 `INCLUDE` 子句挂在键外），回表次数直接归零。代价是每行索引条目变宽、叶页容量下降、写路径多一份维护——用空间与写放大换读路径的一次树下降。

### 2. 最左前缀：联合索引的逐段吞噬

联合索引 `(a, b, c)` 的叶层排序规则是：先按 `a` 排，`a` 相同的段内按 `b` 排，`b` 相同的段内按 `c` 排。查询条件从左向右逐段匹配，每匹配一段就吞噬一层搜索空间——这与 01-计算机网络 02 的路由最长前缀匹配同构：路由表按目的地址的前缀逐段定位下一跳，联合索引按条件列的前缀逐段定位数据段。前缀一旦断裂，后面的列在排序中散布于所有前段取值里，无法定位。

| 查询条件（索引为 `(a, b, c)`） | 索引可用段 | 投影行为 |
| --- | --- | --- |
| `a = ?` | a | 定位到 a 的一个取值段 |
| `a = ? AND b = ?` | a, b | 两段吞噬后定位到叶页内窄区间 |
| `a = ? AND b = ? AND c = ?` | a, b, c | 全键定位，等价点查 |
| `b = ?` | 无 | 前缀断裂 → 全表扫描 |
| `a = ? AND c = ?` | a | c 散布在 a 段内，只能定位 a 后逐行过滤 c |
| `a = ? AND b > ?` | a, b（到 b 为止） | b 取范围后其内的 c 失序，c 条件退化为过滤 |

表内每行都是同一条因果链：索引能用的段数 = 条件列从左起连续命中的段数；`c` 只有在 `a`、`b` 都被等值固定后才有序可用。联合索引的列序设计因此就是查询画像的编码——等值列在前、范围列在后，范围列之后不再放需精确定位的列。

### 3. 失效场景与 EXPLAIN 预期形态

前缀匹配之外，还有一类失效：查询写法把键变成了键序之外的东西。对索引列做函数运算、隐式类型转换或前导通配符匹配，都会让「键的排序序」与「查询要比较的值」脱钩，投影退化。每条失效的 EXPLAIN（PostgreSQL）预期形态如下：

| 写法（示例，`name`/`phone` 建有 btree 索引） | 失效机理 | EXPLAIN 预期形态 |
| --- | --- | --- |
| `WHERE upper(name) = 'A'` | 函数改写了比较值，叶层键序对新值无效 | `Seq Scan on t   Filter: (upper(name) = 'A'::text)` |
| `WHERE phone = 13800000000`（`phone` 为 text） | 数字字面量迫使列被 casting，text 序失效 | `Seq Scan on t   Filter: ((phone)::numeric = 13800000000)` |
| `WHERE name LIKE '%abc'` | 前缀未知，无法定位叶层起点 | `Seq Scan on t   Filter: ((name ~~ '%abc'::text))` |
| `WHERE name LIKE 'abc%'` | 前缀可定位——投影生效 | `Bitmap Index Scan` / `Index Scan using idx_name` |
| `WHERE a = 1 OR b = 2`（`b` 无索引） | OR 需两条路径合一，缺一条即全扫 | `Seq Scan on t   Filter: ((a = 1) OR (b = 2))` |
| `WHERE b = 1`（联合索引 `(a, b)`） | 最左前缀断裂 | `Seq Scan on t   Filter: (b = 1)` |

两种典型形态的判读：`Seq Scan`（顺序扫，Filter 逐行判定）意味着投影已失效；`Index Scan`（按索引取行指针后回表）与 `Bitmap Index Scan`（先在索引上收齐行指针位图、再统一回表，把随机读合并成近顺序读）意味着投影生效。恢复失效的正解不是绕过写法，而是让索引匹配查询：函数调用场景建表达式索引 `CREATE INDEX ON t (upper(name))`，类型转换场景统一列类型与字面量类型。

### 4. 可实操核验

以上断言在 PostgreSQL 上可逐条读回。准备一张百万行表 `t(id int 主键, name text, phone text)`：

| 核验点 | 命令 | 预期观察点 |
| --- | --- | --- |
| 点查走索引 | `EXPLAIN ANALYZE SELECT * FROM t WHERE id = 42;` | `Index Scan using t_pkey`，`actual time` 亚毫秒档，`rows=1` |
| 失效走全扫 | `EXPLAIN ANALYZE SELECT * FROM t WHERE upper(name) = 'X';` | `Seq Scan`，`actual time` 毫秒到数十毫秒档，`rows` 接近表行数 |
| 索引清单 | `\d+ t` | `Indexes:` 段列出 `t_pkey btree (id)` 及各二级索引的键列 |
| 扫描计数 | `SELECT seq_scan, idx_scan FROM pg_stat_user_tables WHERE relname = 't';` | 跑一次全表扫后 `seq_scan` 计数加一，点查只增 `idx_scan` |

两种执行形态的 `actual time` 差两到三个数量级（缓冲池冷时更甚），`pg_stat_user_tables` 的累计计数则把「优化器这次选了哪条路」变成可查的状态——扫描计数漂移是生产环境索引失效的第一现场。

## 三、事务与 ACID：并发与崩溃两个战场

### 1. ACID 四性的机制归因

事务的四条性质不是四个模块，而是三个机制加一个结果属性。动作归因如下：

| 性质 | 承载机制 | 具体动作与代价去向 |
| --- | --- | --- |
| 原子性（Atomicity） | WAL 的 undo 侧（InnoDB）/ 版本可见性（PostgreSQL） | 未提交事务的改动在崩溃重放后按不可见处理或被回滚，全部动作或全部生效、或全部不生效 |
| 一致性（Consistency） | 前三者 + 应用约束 | 唯一键、外键、CHECK 在写路径上强制校验；一致性本身没有独立机制，是其他三性收口后的结果 |
| 隔离性（Isolation） | 锁 + MVCC | 并发事务按快照挑可见版本、按锁仲裁写冲突，各自战场见 3、4 小节 |
| 持久性（Durability） | WAL 日志先行 + 提交时 fsync | commit 返回前日志必须已落盘，崩溃后凭日志重放重建 |

持久性的一半是 WAL（Write-Ahead Logging，预写日志）：**改页之前先把改动记入日志**。归因很直接——若先改页后记日志，崩溃时页是新页而日志里没有对应记录，改动无从追溯也无法撤销；日志先行把改动先固化到顺序追加的日志文件里，随机页写变成顺序日志写加异步脏页刷盘，顺序写带宽高出随机写约两个数量级（方向不等式），崩溃恢复则凭日志重放补齐未刷盘的页。

### 2. WAL 与崩溃恢复时序

```text
WAL 崩溃恢复时序（单事务 T 的生命周期 × 两个崩溃点）

 正常运行                                      崩溃与结局
 ───────────────────────────────────          ───────────────────────────────────
 ① BEGIN
 ② 改缓冲池中的页（脏页，不落盘）
 ③ 追加 WAL 记录，LSN 递增                     ✘ 崩溃点 c1：③ 后、④ 前
 ④ 追加 COMMIT 记录                               → 日志中无 COMMIT 记录
 ⑤ 日志缓冲 fsync 落盘（毫秒档）                   → 重放时 T 被判未提交，改动不可见
    │ 此刻起 T 视为已提交                            （原子性成立）
 ⑥ 返回应用：COMMIT 成功
 ⑦ 脏页由检查点/后台异步刷盘                    ✘ 崩溃点 c2：④⑤ 后、⑦ 前
                                                  → 日志有 COMMIT 记录
                                                  → 重放 redo 重建改动，已提交不丢
                                                    （持久性成立）

 重启恢复（日志先行 → 崩溃 → 重放 → 断点续写）：
   定位最近检查点 LSN → 从该 LSN 顺序重放 redo，已提交改动重建进页
   → 未提交事务标记为中止 → 恢复完毕，对外开放连接，新事务从日志尾断点续写
```

时序图的全部保证收在一条铁律上：**COMMIT 返回之前，日志必须先于数据落盘**。commit 的等待本质上是一次 fsync——02-操作系统 篇的结论就地复用：页缓存使 `write` 返回不代表落盘，`fsync` 要过「数据块落地、设备缓存刷穿、提交记录 FUA 落盘」三道屏障，机械盘毫秒到十毫秒档、SSD 毫秒以下、NVMe 数十微秒档。每事务一次 fsync 是持久性的固定税，高并发靠组提交摊薄：多个并发事务的日志在同一窗口合并成一次屏障，每事务均摊成本随并发数下降。LSN（Log Sequence Number，日志序列号）给日志全局定序；检查点（Checkpoint）把脏页刷盘并推进 LSN，恢复只需从检查点起重放，日志不必从头回放。

### 3. MVCC：写不阻塞读

隔离性的第一根支柱是 MVCC（Multi-Version Concurrency Control，多版本并发控制）：写操作不就地覆盖旧值，而是生成新版本，读者按自己拿到的快照挑选可见版本。归因：就地改写必然要求读写互斥（读者会看到改到一半的行），多版本把「改」与「读」拆到不同副本上，读写互不阻塞。一条最小链路（PostgreSQL 口径，每行版本带创建事务号 xmin 与删除事务号 xmax）：

```text
一次 UPDATE 的版本链与可见性判定：

  事务 101 执行：UPDATE account SET balance = 90 WHERE id = 1;
    旧版本：balance=100, xmin=100, xmax=101   ← 被事务 101 标记删除
    新版本：balance=90,  xmin=101, xmax=空    ← 由事务 101 创建，链到旧版本

  读者 R 在事务 101 提交前开始，快照定格在「100 已提交、101 未提交」：
    旧版本：xmin=100 已提交且先于快照 → 存在；xmax=101 未提交 → 未被删
            → R 看到 balance=100
    新版本：xmin=101 未提交 → 不可见

  事务 101 提交后，R 后续查询（读已提交级别）刷新快照：
    旧版本 xmax=101 已提交 → 已删；新版本 xmin=101 已提交且先于新快照
    → R 看到 balance=90
```

可见性判定只有一条规则：版本的 xmin 已提交且先于快照、且其 xmax 未提交或不先于快照，则该版本可见。快照何时刷新决定了隔离级别的高低——快照每条语句一刷，读到的就是最新已提交态；整个事务一刷，重复读得到保证（下一节矩阵展开）。InnoDB 同一思想的不同实现：版本链藏进 undo 日志，行头记录事务 ID 与回滚指针，读时沿 undo 链向旧版本回溯，判定规则同上。多版本的代价是旧版本累积：PostgreSQL 靠 VACUUM 回收死元组，InnoDB 靠 purge 线程清理 undo——不清理则表膨胀、索引变厚、扫描变慢，这是写不阻塞读明码标价的维护税。

### 4. 隔离级别 × 并发异常矩阵

三类并发异常的机理都落在 MVCC 的判定规则上：脏读 = 快照不排除未提交版本；不可重复读 = 事务内快照被刷新，同一行两次读到不同已提交值；幻读 = 快照刷新叠加范围谓词，同一范围条件两次查出行集不同。隔离级别即「快照刷新粒度 + 锁策略」的分档：

| 并发异常 | 读未提交（RU） | 读已提交（RC） | 可重复读（RR） | 串行化（SER） |
| --- | --- | --- | --- | --- |
| 脏读 | 出现（InnoDB 支持该档；PostgreSQL 无此档，最低即读已提交） | 不出现（快照只含已提交版本） | 不出现（同 RC 判定） | 不出现 |
| 不可重复读 | 出现 | 出现（每条语句刷新快照） | 不出现（事务首查定格快照） | 不出现 |
| 幻读 | 出现 | 出现（每条语句刷新快照） | PostgreSQL：不出现（快照隔离，但并发写冲突以「无法串行化」错误退出）；InnoDB：普通快照读不出现，当前读（加锁读/写）靠 Next-Key 锁锁住间隙补齐 | 不出现（谓词锁/串行化检测） |

默认级别按引擎锚定：**PostgreSQL 默认读已提交**，**InnoDB 默认可重复读**。级别每升一档，机制代价随之上涨：RC 靠快照即可，RR 需要固定快照加（InnoDB）间隙锁，SER 需要谓词级检测（PostgreSQL 用可串行化快照隔离 SSI），并发吞吐逐档下降——隔离级别是「异常容忍度换并发度」的定价表，默认档位是引擎对大多数负载的权衡结论。

## 四、关系模型与 SQL：声明式即优化器代劳

### 1. 关系模型与算子树

关系模型（Codd，1970，历史路径依赖锚定）把表定义为集合上的谓词运算：行是使谓词为真的元素，查询是选择、投影、连接、聚合的代数组合。SQL 声明「要什么」——谓词与聚合；「怎么遍历」的控制流由优化器生成：扫描（第一节的全扫/索引扫）→ 连接 → 聚合构成一棵算子树，执行引擎按树自底向上流水。声明式省掉的正是遍历控制流——应用不写循环、不管先查哪张表，代价是优化器基于统计信息（行数、直方图、不同值数）估算各算子代价后择优，估算失真即选错路径；第二节失效场景表里的 `Seq Scan` 就是「代价模型判定索引更贵」的极端输出。

### 2. 连接的两种物理实现

同一句 `JOIN` 有两条物理路径，选择依据是内外表规模的方向不等式：

$$C_{\text{嵌套}} = N_{\text{外}} \times c_{\text{点查}}, \qquad C_{\text{哈希}} = \left( N_{\text{外}} + N_{\text{内}} \right) \times c_{\text{顺序}}$$

其中 $N_{\text{外}}$、 $N_{\text{内}}$ 为驱动表与被探表的行数， $c_{\text{点查}}$ 是一次索引点查代价（消费第一节的 3 次页读断言）， $c_{\text{顺序}}$ 是一次顺序行读取代价。两式相比得方向：外表行数少且被探表连接列有索引时， $N_{\text{外}}$ 小使嵌套循环的乘法不膨胀，嵌套胜；两表行数同为大数量级时，两次顺序扫加一次内存建哈希的加法胜过海量乘法，哈希胜。

| 实现路径 | 动作链 | 适用方向 | EXPLAIN 形态（PostgreSQL） |
| --- | --- | --- | --- |
| 嵌套循环（Nested Loop） | 外表每行 → 按连接列在内表索引点查一次 | 外表行数少 + 内表连接列有索引 | `Nested Loop (cost=...)`，内层为 `Index Scan` |
| 哈希连接（Hash Join） | 小表全扫建内存哈希表 → 大表全扫逐行探测 | 两表都大、等值连接、连接列无可用的窄索引 | `Hash Join  Hash Cond: (... = ...)`，两侧 `Seq Scan` |

`EXPLAIN` 打印的算子树即本节与第一、二节的总装现场：看到 `Nested Loop + Index Scan` 说明优化器判定外表足够小、点查路径值得走；看到 `Hash Join + Seq Scan` 说明两表规模已把乘法路径判出局。执行计划由此成为可审计对象——慢查询的第一步诊断永远是读树，而不是猜。

### 3. 单库机制的边界：数据层拆分给谁

至此单库闭环：页与缓冲池定下存取代价的底座，B+ 树/LSM 在其上组织索引，WAL 收口崩溃战场，MVCC 与锁收口并发战场，SQL 与算子树把前三者的能力封装成声明式接口。下一跳在数据层的边界上：当数据按服务边界拆开（每服务私有存储、跨库无联合事务），本篇依赖的全部机制——跨表联合事务、同库 MVCC 隔离、单机 WAL 持久——在库与库的缝隙处同时失效，一致性从引擎内置降级为应用侧的补偿与对账，这笔分布式税由 08-微服务架构 核算。
