# 微服务架构

单体把一个系统装进一个进程：模块之间的连接是进程内的函数调用，数据的一致性由单库事务保证——07-数据库基础 篇的 ACID 机制就在这个前提下成立，跨表操作被同一个引擎的同一份预写日志与多版本机制收口。微服务（Microservices）把这条边界推开：按业务域把系统切成一组独立部署的服务，每个服务一个进程、一份私有存储，服务之间的连接从函数调用变成跨网络的请求。06-架构分层篇埋过这条线——横向按业务域切层（用户域/订单域）让各域独立演进，本篇把这层切到服务粒度，并核算这次切分引入的全部代价。服务间通信的物理底座是 05-计算机网络 篇的 TCP/HTTP/TLS——每条服务间请求都是一次毫秒级的跨机往返；部署单元的落点由 05-容器化基础 篇给出——"每个服务一个容器"正是编排器调谐循环所管理的对象。

由此立起全篇的核心断言：**拆分是一场交易——用运维复杂度换组织扩展性。** 收益端是独立发布、独立扩容与团队边界对齐，支出端是三笔新税与一整套补偿机制。本篇按三条拓扑流展开：第一节核算税单（为什么付、付多少）；第二节走两条通信环——同步请求-等待环与异步发布-订阅环，这是本篇的空间事务环主体；第三节挂载数学推演（可用性串联相乘、扇出尾延迟放大），推导终点落回"串联服务越多可用性越低"的量化断言，并以分布式追踪收口部分失败的定位链。

## 一、拆分的约束：为什么付分布式税

### 1.1 单体的三个失效点

单体不是起点错误——规模小时它把本篇要核算的分布式税全部免掉，第二节的两条通信环在进程内都是一次函数调用。失效点在三个维度上随规模逼近，每一个都锁死一个方向：

- **发布耦合。** 所有变更共享同一个发布周期：一次两行的缺陷修复与一个新模块走同一条编译-测试-发布流水线，任何一处编译错误拦停整站发布，任何一次发布都要全站重部署。发布粒度被进程边界焊死为全站。
- **资源画像冲突。** 订单模块 CPU 密集、推荐模块内存密集，而扩容的单位是整个进程——只能整体复制，按最贵的那个维度为所有模块付费，其余维度的余量全部闲置。
- **团队耦合。** 康威定律（Conway's Law，1968，锚定来源）断言模块边界会复刻沟通结构——06-架构分层篇以此为分层依据；反过来看，多个团队挤在同一个代码库里时，模块边界不再是沟通边界：合并冲突、发布排队、一处改坏全站回滚，沟通成本直接沉淀为工程成本。

三个失效点共享同一个结构成因：**进程边界 = 发布边界 = 扩容边界 = 团队边界**，四条边界被焊在同一处，任何一条需要独立移动时都要拖着其余三条。拆分就是把这条焊缝切开，让四个边界各自独立移动。

对图中的每条边与每个 ★ 逐一核算：

- **★① 序列化税。** 单体里模块间传递的是对象引用，零拷贝、零转换；跨进程后对象必须编码成字节流（JSON 之类的文本格式或二进制协议）发出去，接收方再解码还原。编码与解码是纯 CPU 开销，每一跳各付一次，随调用频次线性累积。
- **★② 网络税。** 进程内函数调用是纳秒到亚微秒级，跨机 HTTP 请求是毫秒级——05-计算机网络 03 篇的 RTT 档位（同城毫秒级、跨洲几十至百毫秒级）在此原样生效。方向不等式锁死：**进程内调用 < 跨机请求，量级差三到六个数量级**，且每次跨机往返还要叠加 TCP 连接管理、TLS 握手（05-计算机网络 06 篇：完整握手本身就要一到两个 RTT）的既有结论。
- **★③ 部分失败税。** 这是三笔税里唯一改变失败语义的一笔。单体里失败沿调用栈确定性回退——要么异常抛出、要么返回码返回，调用方永远知道结果。部分失败（Partial Failure）指跨网络调用后调用方可能拿到第三种结果：**未知**——请求超时，而被调方可能已经成功（事务已提交，只是响应没赶回来）。失败从两态变成三态（成功/失败/未知），未知态是分布式的独有产物，第二节失败四件套与第三节分布式追踪都在为它买单。

序列化税与网络税是把同一个动作做慢了，部分失败税是把同一个动作变得结果不确定——前者可以用缓存与就近部署摊薄，后者只能靠机制消化，这是它单独成税的原因。

### 1.3 交易账本与拆分依据

三笔税汇总成账本，与收益逐笔对照：

| 维度 | 单体 | 微服务 | 交易方向 |
| --- | --- | --- | --- |
| 发布 | 全站一个发布周期，一处错误全站重部署 | 各服务独立发布，互不拦停 | 发布排队 → 发布编排 |
| 故障域 | 一个模块崩溃，全进程退出 | 单服务故障可被隔离与降级 | 异常传播 → 部分失败 |
| 扩容 | 整体复制，按最贵维度付费 | 按服务资源画像独立扩容 | 粗粒度浪费 → 细粒度运维 |
| 数据一致性 | 单库 ACID，跨表联合事务 | 跨库最终一致，靠补偿与对账 | 强一致 → 应用侧补偿 |
| 调试 | 一个调用栈走到底 | 跨服务链路，栈回溯失效 | 栈回溯 → 分布式追踪 |
| 运维面 | 1 个进程、1 份存储 | N 个进程、N 份存储，各带监控/发布/容量管理 | 组织扩展性 ← 运维复杂度 |

账本的读法与 01-Git 版本控制篇 merge/rebase 账本同构：每一行的左右两格由同一个动作推出——切开进程边界，所以发布解耦、故障隔离、扩容独立，也所以多出网络税、部分失败与 N 倍运维面。没有全局最优，只有"这些问题是否已经大到值得付这笔税"的判断。

拆分依据是**业务域边界**，不是技术分层：康威定律的正用——让服务边界与团队边界重合，沟通结构被直接编码进系统拓扑；按技术层切（全部服务共享一个"数据层服务"）则每个业务变更都要横穿多个团队，沟通税原样回流。拆细的下限是**数据自治**：每个服务私有存储，跨库无联合事务。这一条不是偏好而是 1.2 部分失败税在数据层的必然结果——联合事务要求一个协调者能同时看到全部参与者并锁住它们直至全局提交，而私有存储在物理上切断了这条路径；跨库一致性如何补救，第三节展开。

税单至此核算完毕：序列化与网络税在每一跳上定量可测，部分失败税则贯穿余下全篇。下节进入服务间通信——拆开的边界靠什么连起来。

## 二、服务间通信：同步与异步的两条环

切分后的服务之间只剩两种连接形态：同步环——调用方发出请求后停在原地等待结果；异步环——发布方发出消息后立即离开，消费者按自身节奏处理。同一个业务动作走哪条环，决定了失败如何传导、容量如何匹配，本节逐环走完再给决策矩阵。

### 2.1 同步环：请求-等待与失败传导

同步环的协议形态是 REST（Representational State Transfer，表述性状态转移）或 RPC（Remote Procedure Call，远程过程调用）跑在 HTTP 之上——05-计算机网络 篇的方法语义、状态码与连接管理在此原样消费。调用方序列化请求（★①）、跨网络等待（★②），被调方处理后原路返回。下图为同一笔"订单完成"的两种连接形态对照，左环即同步链：

```text
同步环与异步支线对照（视角：同一笔"订单完成"的两种连接形态。
│为阻塞等待边，⇄为跨网络请求，║为队列隔离）

—— 同步环：请求-等待（调用方停在原地直到被调方返回）—————————
  客户端
   │ ① 请求下单
   ▼
 订单服务 ⇄② 调库存：阻塞等待……（毫秒级 RTT）⇄ 库存服务
   │ ◄──────────────库存结果──────────────
   │ ③ 再调支付：阻塞等待……
   │ ◄──────────────支付结果──────────────⇄ 支付服务
   ▼
 ④ 响应客户端：总延迟 = 各跳 RTT 串联相加
 失败沿链向上传导：任一跳失败或超时，上游收到失败或"未知"

—— 异步支线：发布-订阅（发布方发完即走，消费者按自身节奏拉取）—
 订单服务               消息队列                    消费者（邮件/积分…）
   │ ① 发布 OrderPaid     ║                             │
   ├─────持久化落盘───────►║                             │
   │ ◄──毫秒级确认─────────║                             │
   ▼ ② 已返回客户端       ║（双方不必同时在线）            │

                          ║◄────④ 消费完成确认───────────┤
 环闭合：发布方与消费者被队列解耦，消费失败不沿链向上传导
```

同步环的逐边遍历：①→④ 的每条 ⇄ 边都是一次 ★①+★② 的全额支付，总延迟是各跳 RTT 的串联相加——链越长响应越慢，这是 3.1 节尾延迟公式的延迟版。失败传导是更重的一笔：②③ 的任一跳失败，异常或"未知"沿链向上涌，上游每接一次都要消耗自己的等待预算；整条链的可用性也因此变成串联相乘的形态（3.1 节公式）。同步环本身没有任何机制处理这些传导——消化部分失败的机制是四件套，下小节展开。

### 2.2 失败四件套与熔断器状态机

四件套挂在同步环的调用方一侧，每个机制各自阻断一种具体的失败级联，动作与代价如下：

| 机制 | 动作 | 阻断的级联 | 代价 |
| --- | --- | --- | --- |
| 超时（Timeout） | 给每次等待设上界，超界判失败返回 | 无界等待拖垮调用方的线程与内存 | 放大"未知"结果——被调方可能仍在执行 |
| 重试 | 失败或超时后重发请求 | 瞬时故障（网络抖动、下游重启窗口）被误判为永久失败 | 要求被调操作可安全重复（幂等，2.3 节展开）；重试流量放大下游压力 |
| 熔断器（Circuit Breaker） | 失败率越阈值后直接快速失败，不再发请求 | 对已死下游持续重试的流量放大，以及下游故障向上游蔓延 | 正常请求被一并拒绝——可用性主动受损换下游喘息 |
| 舱壁（Bulkhead） | 每个下游独立分配连接池/并发配额 | 一个慢下游占光全部并发额度，拖垮对其他健康下游的调用 | 资源利用率下降——配额可能闲置 |

四个动作的归因各占一级级联：超时防"等待无界"，重试防"瞬时故障被当永久失败"，熔断防"重试打已死下游"，舱壁防"故障跨下游共享资源"——顺序正好是失败从一个下游向外扩散的路径。其中熔断器是一个完整的三个状态的状态机：

```text
熔断器状态机（三状态；转换条件标在边上）

      正常放行，滚动窗口统计失败率        失败率 ≥ 阈值
  ┌──────────────────┐  ──────────────►  ┌──────────────────┐
  │  闭合（CLOSED）    │                   │  打开（OPEN）      │
  │  请求照常发往下游   │  ◄──────────────  │  一律快速失败      │
  └─────────▲────────┘   探测成功，复位计数  │  不触碰下游        │
            │                            └────────┬─────────┘
            │                                     │ 冷却计时到期
            │ 探测失败，重回打开                    ▼
            │ （并重新冷却计时）            ┌──────────────────┐
            └──────────────────────────── │  半开（HALF-OPEN） │
                                           │  只放行少量探测请求 │
                                           └──────────────────┘
```

逐状态遍历。**闭合态**是常态：请求全部放行，同时在一个滚动时间窗口里统计失败率——熔断器的判断依据是"失败的比例"而不是"失败的事实"，零星失败不触发，这是它区别于简单失败计数的核心。**打开态**在失败率越阈值后进入：请求不再发往下游、原地快速失败——动作归因是把"必然失败的等待"替换成"立刻返回的失败"，同时给下游留出恢复窗口。**半开态**在冷却计时到期后进入：放行少量探测请求试探下游是否恢复，成功则复位计数回到闭合，失败则重回打开并重新冷却。三状态的方向只有一条循环，没有跨态转移——恢复必须经过半开的探测验证，不能直接从打开跳回闭合，这防止下游抖动时熔断器反复开关。

四件套守住同步环之后，还有一类需求是同步环结构性解决不了的：调用方根本不需要结果，或者下游消费不了峰值流量——这要求把"发出"与"处理"在时间上切开，异步环的结构正落在这里。

### 2.3 异步环：发布-订阅的两重解耦

异步环的形态是消息队列（Message Queue）加发布-订阅（Publish-Subscribe）：发布方把消息写进队列、拿到毫秒级确认后立即离开；消费者按自身节奏从队列拉取处理。上图下半的 ①→④ 闭环给出全部边：发布边只付一次队列写入的代价，消费边由消费者主动发起——连接的方向与同步环相反。两重解耦由队列这个中介提供：

- **时间解耦。** 双方不必同时在线：消费者下线或重启期间，消息在队列里持久化排队（落盘机制与 07 篇 WAL 同源——先日志后确认），上线后续读。同步环里被调方不在线即调用失败，这里失败被排队吸收。
- **容量解耦（削峰填谷）。** 峰值流量进队列排队，消费速率等于消费者稳态处理能力，突发被摊平到时间轴上。同步环里峰值直接砸到下游，只能靠限流拒绝多出来的部分。

代价在一致性一侧。发布时刻与消费完成时刻之间存在时间窗口，系统在这段时间里处于不一致状态——最终一致性（Eventual Consistency）：不承诺任意时刻各副本一致，只承诺停止更新后副本终将收敛。多数业务可以接受窗口（订单已创建、积分几秒后到账），不能接受的操作留在同步环。第二个代价在投递语义上，队列保证到哪一档决定了消费端要做什么：

| 投递语义 | 队列的动作 | 谁承担后果 |
| --- | --- | --- |
| 至多一次（At-Most-Once） | 发完即忘，失败不重投 | 可能丢消息，消费端最省事 |
| 至少一次（At-Least-Once） | 未收到消费确认即重投，不丢但可能重复 | 消费端必须幂等 |
| 恰好一次（Exactly-Once） | 投递端与消费端两端去重/事务协同 | 协同复杂度最高，吞吐代价最大 |

主流消息队列的默认语义是至少一次——不丢消息与不重复消息之间，队列选择保前者，把重复交给消费端处理。这就是幂等（Idempotency）：**同一操作执行一次与执行多次，结果相同。** 消费端的落地是业务键去重：给每条消息带唯一消息 ID 或业务单号，消费前先查去重表——记录已存在就跳过，不存在就执行业务并把去重记录与业务写入放进**同一个本地事务**提交，保证"执行过"与"记过账"同时成立。幂等同时被 2.2 的重试所需要：重试重发的正是同一条请求，被调方不幂等则重试就把一次成功变成两次扣减——四件套与异步环在这一条上交汇。

至此两条环各自闭合：同步环用四件套消化部分失败，异步环用队列消化时间与容量、用幂等消化重复。选环本身是一个多变量判定，下小节给出完整决策矩阵。

### 2.4 同步 vs 异步决策真值矩阵

三个变量完全决定选环：本次响应是否依赖下游结果（时延要求）、下游是单一被调方还是广播给不确定的多个消费方（依赖方向）、业务能否容忍最终一致的窗口（一致性需求）。三变量八种组合的真值矩阵如下，单元格全部补齐：

| 时延要求（响应即需结果） | 依赖方向 | 一致性需求 | 决策 | 理由与典型场景 |
| --- | --- | --- | --- | --- |
| 强 | 单一被调方 | 强一致（读己之写） | 同步环 | 结果依赖无法靠排队消除——下单扣库存，响应必须携带扣减结果 |
| 强 | 单一被调方 | 弱（可容忍旧值） | 同步环 + 缓存 | 结果仍须当场返回，缓存把可容忍旧值的读挡在下游之外 |
| 强 | 广播（多被调方） | 强一致 | 同步环串行扇出 | 全部被调方都成功才能返回——延迟与失败率按扇出放大（3.1 节公式），业务上应极力避免 |
| 强 | 广播 | 弱 | 同步主干 + 异步支线 | 响应只依赖主干（扣库存），其余下沉为消费方（通知、积分） |
| 弱（可排队） | 单一被调方 | 强一致 | 异步环 + 消费端本地事务强一致写 | 结果晚到不违反一致——消费端在自己的库里强一致落账 |
| 弱 | 单一被调方 | 弱 | 异步环 | 削峰填谷的标准形态——订单完成写积分流水 |
| 弱 | 广播 | 强一致 | 异步环 + 分区有序消费 | 队列按业务键分区保序，各消费方按同一顺序重放 |
| 弱 | 广播 | 弱 | 异步环（发布-订阅） | 事件广播的标准形态——订单完成事件通知任意多个订阅方 |

矩阵的行间读法：时延要求是第一判决变量——它单独决定主干必须同步；依赖方向与一致性需求决定剩余部分能否下沉到异步支线。第一行与第五行的对照最有信息量：同为强一致，结果依赖压向同步、结果延迟放行异步——一致性从来不是单独的选环依据，它总是与时延要求共同判决。

两条环至此都走完：同步环的失败在链上串联传导，异步环的代价是最终一致与重复消息。两环的账在第三节合并核算——一致性如何补救、失败如何定位。

## 三、分布式的代价：一致性与可观测性

### 3.1 可用性串联与尾延迟放大

CAP 定理一句话立骨：一致性（Consistency）、可用性（Availability）、分区容忍性（Partition tolerance）三者不可兼得，而网络分区在多机系统里必然发生——P 必选，剩下是在 C 与 A 之间按请求取舍。多数业务系统据此选择最终一致性（2.3 节的窗口），只在少数强一致读的路径上动用共识算法（Paxos、Raft 一族，机制概述到"多数派写入才提交"为止，本篇不展开证明）。

选择最终一致之后，可用性成为量化核算的对象。一条业务请求串联经过 $n$ 个服务，整体可用性是各节可用性的连乘：

$$A_{\text{总}} = \prod_{i=1}^{n} A_{i}$$

**算例前提**：假设各服务故障相互独立，链路串联 4 个可用性 99.9% 的服务，代入：

$$A_{\text{总}} = 0.999^{4} \approx 0.996$$

即整体可用性从 99.9% 跌到 99.6%：按全年 525600 分钟计，不可用时长从约 8.8 小时档涨到约 35 小时档。推导终点落回量化断言：**串联服务越多可用性越低**——每串一节就乘上一个小于 1 的因子，整体恒低于链条中最弱的一节；串联 8 个 99.9% 则跌到 99.2%，每翻一倍掉约 0.8 个百分点。抬升的动作归因也在这条公式里：串联降、并联升——给单节配 $m$ 个冗余副本，该节可用性变为 $1 - \left(1 - A\right)^{m}$，代入 2 副本 99.9% 得 $1 - 0.001^{2} = 0.999999$，从"三个九"抬到"六个九"。容错的方向因此是加并联副本而不是祈祷串联的每一节都完美。

延迟侧有对称的账。前端一次请求扇出（fan-out） $k$ 个下游调用，各下游独立地以概率 $p$ 落在慢档，则整请求变慢（任一调用落在慢档）的概率为：

$$P_{\text{慢}} = 1 - \left(1 - p\right)^{k}$$

**算例**： $p = 1\\%$、 $k = 10$，代入得 $1 - 0.99^{10} \approx 0.096$——单个下游慢的概率只有 1%，扇出 10 个之后整请求变慢的概率涨到约 9.6%，放大近十倍。两条公式合起来是同一个结构事实的两侧：**串联相乘，扇出相并——链条越长、扇出越宽，整体越向最弱一节与最慢一节看齐。** 这正是 2.4 矩阵把"强时延 + 广播 + 强一致"判为"业务上应极力避免"的量化依据：那一格同时踩中两条放大曲线。

### 3.2 幂等与 Saga：跨服务事务的落地

1.3 节的数据自治下限（跨库无联合事务）留下一个缺口：一笔业务跨多个服务、多个库，单库 ACID 管不到库缝之外。补这个缺口的方案里，两阶段提交（Two-Phase Commit，2PC）是最直觉的一条：由一个协调者先询问全部参与者"能否提交"、再统一下令提交——但协调者必须锁住全部参与者的资源直到全局决议，任一参与者失联即全链阻塞，阻塞时长跨网络进一步放大；这既与私有存储的自治前提冲突，又把 3.1 节的可用性串联再乘一层。工程上的主流落地因此是 Saga：**把全局事务拆成本地事务序列 $T_{1} \dots T_{n}$，每一步配一个补偿动作 $C_{1} \dots C_{n}$；序列走到底即全局提交，中途某步失败则逆序执行已完成步骤的补偿**——每个 $T_{i}$ 都是本服务库内的普通本地事务（07 篇的 ACID 在库内照常成立），跨库的原子性由补偿序列拼接出来。

算例沿用 1.2 的下单链：T1 订单库创建订单 → T2 库存库锁定库存 → T3 支付库扣款。T3 失败时逆序补偿：C2 解锁库存 → C1 撤销订单，三份本地账各自落定、最终对齐。两笔代价明码标价：其一，补偿窗口内的中间态对外可见——库存已锁、订单未付的间隙里，其他事务看到的是"锁着却没买"的状态，07 篇的单库隔离性在此降级为应用侧的业务规则容忍；其二，补偿动作本身要幂等——补偿可能因超时重试被执行多次（2.3 节的去重机制在此复用），解锁与撤销执行多次必须与一次等效。至此幂等消费了三次：异步去重、重试安全、补偿安全——同一机制服务三条链路。

一致性一侧收口完毕：窗口靠最终一致容忍、原子性靠补偿拼接、重复靠幂等去重。剩下的问题是观测——补偿窗口、重试、熔断打开，这些都让"此刻系统处于什么状态"变成跨服务的问题。

### 3.3 可观测性三支柱：trace 是事务环的投影

可观测性（Observability）的三根支柱各持一种数据形态，分工与局限如下：

| 支柱 | 数据形态 | 回答的问题 | 单独使用的局限 |
| --- | --- | --- | --- |
| 日志 | 离散事件记录，各服务各写各的 | 单个服务里发生了什么 | 时间戳对不齐、服务名拼不全，跨服务拼不出因果 |
| 指标 | 聚合时序（QPS、延迟分位、错误率） | 系统整体健康与趋势 | 看得见异常的形状，看不见任何一个具体请求 |
| 追踪 | 单次请求的跨服务 span 树 | 这次请求经过了谁、慢或死在哪一跳 | 只覆盖被埋点的路径，覆盖率靠采样权衡 |

前两根支柱在单体里几乎够用——一个进程、一份日志、一个调用栈。微服务里三笔税里的部分失败税把定位问题变成跨服务问题：2.2 节的四件套把失败隔离在某一跳，但"哪一跳"没有跨服务的数据就无法回答。分布式追踪补上这一根：入口服务给请求分配全局唯一的 trace ID，每一跳把自己的处理过程记为一个 span（一段带起止时间戳与父子关系的区间），父子关系即调用关系——span 树就是 2.1 节同步调用链的投影：

```text
一次入口请求的追踪 span 树（视角：追踪面 = 2.1 同步链的投影。
缩进即父子调用关系，横条长度示意耗时占比，✘ 为失败/超时 span）

trace: 提交订单（入口，总耗时 182 ms）
├─ 网关 span                       ██ 3 ms
├─ 订单服务 span                 ██████ 170 ms
│  ├─ 查订单库 span                █ 8 ms
│  ├─ 库存服务 span            ████ 95 ms
│  │  ├─ 查库存库 span             █ 6 ms
│  │  └─ 锁定库存 span          ██ 80 ms   ← 慢点在自身逻辑
│  └─ 支付服务 span    ✘ 超时
│     └─ （被调方仍在执行，结果为"未知"——1.2 的三态在此现形）
└─ （异步支线：OrderPaid 的消费在消费者侧另起 trace，
    经消息头透传关联，不在本树——发布方不等待，树在队列处断开）
```

逐行遍历：树的形状与 2.1 图的同步链逐一对应——订单服务 span 的三个子 span 正是 ②查库、③调库存、③调支付三条边；每个 span 的起止时间戳把 182 ms 拆解到每一跳，"锁定库存 80 ms"这类慢点直接读出。✘ 行是部分失败税的物证：超时的支付 span 在树上悬空，但 trace ID 已随请求带过去，被调方落盘的 span 稍后可按同一 ID 关联——"未知"态由此从三态里的黑洞变成两条可拼接的记录。异步支线对应 2.3 图的发布-订阅环：消息头里透传关联标识，消费者侧另起 trace 树，两条树靠业务键关联而非嵌套——树在队列处断开正是时间解耦在追踪面的投影。

因果链在此收口：1.2 的部分失败税产生"未知"，2.2 的四件套把失败隔离在某一跳，3.3 的追踪把"哪一跳"变成一次树查询——没有追踪，前两节的全部机制都缺少最后的定位环节，部分失败只能靠逐个服务翻日志碰运气。

至此微服务的账目全部收口：第一节的三笔税划定了代价的结构，第二节的两条环给出了连接与失败传导的全部形态，第三节的公式把串联与扇出的代价算成数、把一致性与定位补成机制。系统交付之后还要对抗主动的恶意方——信任边界的划定、注入与越权的阻断，是另一个视角对同一条请求环的攻击性遍历，交给 09-安全基础。
