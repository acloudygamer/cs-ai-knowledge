# Git 版本控制

## 一、内容寻址对象模型：版本库 = 键值存储

Git 把"记录版本"降维成一条机制：把每个时刻的目录快照切成四类对象，按内容摘要编址，存进一个只增不改的键值存储——对象库只认内容不认名字，像一台凭票取货的寄存柜；其余一切概念——分支、标签、历史、合并——都是这个存储之上的引用与图遍历。本章是 06 章的底座，上游消费两处既有机制：02-操作系统 的文件系统篇确立过一条结构事实——inode（索引节点）存放文件的大小、时间戳与块索引，但文件名不进 inode，名字到 inode 号的绑定由目录项（dentry）承担；03-终端与Shell 确立 Shell 只是普通用户态进程、外部命令经 fork 加 execve 生成子进程、以退出码报告成败——本篇核验小节里的每条 git 命令都是这样一个单功能进程，可按管道方式组合。下游产出唯一一份资产：**版本 = 内容寻址的有向无环图（Directed Acyclic Graph，DAG）**。04-CI-CD 的流水线以提交事件为唯一触发源，消费的正是本篇的提交与引用前移。

本篇的第一表达是信息投影流，与 05-计算机网络 01 篇的报文封装同构：那里，载荷自上而下逐级包上协议头（以太网帧头包住 IP 头、IP 头包住 TCP 头），每级头部只新增本级的控制字段；这里，内容字节自内向外逐级组装成对象——blob（二进制大对象，Binary Large OBject）只装内容，tree（树对象）用目录条目包住一批 blob 与子 tree，commit（提交对象）用一个树摘要加历史字段包住整棵树，tag（标签对象）再给任意对象署名包裹。每包一级，新增的只是该级的字段；文件名这类结构信息，恰好在 tree 这一级才第一次出现。

### 1.1 四对象字段切分：逐级组装的投影瀑布

```text

每框列出该对象的全部字段——字段没列出的属性就不在这一级对象上）

  ┌──────────────────────┐   ┌────────────────────────────────────────────────┐

  │ parent = [C1]        │  │ 只有内容字节，    │        └──────────┬───────────┘

  │   tags/v1.0          │   tag 对象的字段：object = C2、type = commit、

  └──────────────────────┘
                             分叉：另一条支路 C4、C5 的 parent 链同样回到 C2

```

对这张图逐边逐字段遍历：

- **blob：字段只有内容字节。** 对象字节 = 一行对象头 `blob <字节数>` 加原始内容，落盘前经 zlib 压缩。文件名、权限、修改时间都不在 blob 上——改一个字节就是全新的 blob；同一内容出现两个名字，是两个 tree 条目指向同一个 blob（去重是寻址的副产品，1.2 展开）。这与 dentry/inode 的分工完全同构：名字是目录项的事，内容本体不携带名字。
- **tree：字段是（模式， 类型， 名字， 摘要）四元组的清单。** 类型只有两种——blob 或 tree，后者使目录嵌套递归终止于 blob；模式是固定档位：`100644` 普通文件、`100755` 可执行、`120000` 符号链接、`040000` 子 tree。**文件名只存在于 tree 条目**：从根 tree 出发按名字逐级下钻（README.md → src/ → main.py），到 blob 才取到内容字节；树里任何条目变了个摘要，其所在 tree 的清单就变，整条路径上每个 tree 随之全部重写——树结构是自下而上逐级冻结的。
- **commit：字段恰好一组。** 一个 tree 摘要（本次快照的根）、零或多个 parent 摘要、author 与 committer（各带姓名、邮箱、时间戳、时区）、提交信息。**历史不在任何单个对象里，而在 parent 边上**：根提交 parent 为空；普通提交 parent 一个；合流提交 parent 两个（第三节）。
- **tag：包裹任意对象的署名层。** 字段为 object（被包裹对象的摘要）、type（被包裹对象的类型）、标签名、打标人与标签信息。附注标签自身是对象、可被再引用；轻量标签不是对象，只是一个引用文件（2.1）。

四对象逐级投影的分工表：

| 对象 | 存储的字段 | 明确不存什么 | 投影职能 |
| --- | --- | --- | --- |
| blob | 内容字节（zlib 压缩） | 文件名、模式、时间戳 | 内容的唯一真身 |
| tree | （模式， 类型， 名字， 摘要）清单 | 内容字节、时间戳 | 目录结构，文件名的唯一持有层 |
| commit | tree 摘要、parent 摘要、作者/提交者、提交信息 | 文件内容、目录清单 | 快照的时序与归属 |
| tag | object 摘要、type、标签名、打标人、信息 | —— | 指向其余任意对象的署名包裹 |

可核验：在任意仓库执行 `git cat-file -t <摘要前缀>` 报对象类型、`git cat-file -p <摘要前缀>` 打印对象原始内容——对 commit 打出 tree/parent/作者/信息各字段，对 tree 打出逐条 `模式 类型 摘要\t名字`，对 blob 打出原文；字段清单与上表逐项对得上。

### 1.2 寻址即校验：SHA-1 的双重身份

对象的键是 SHA-1（Secure Hash Algorithm 1，安全散列算法 1）摘要：160 bit，即 20 B，惯例写成 40 个十六进制字符。现行对象格式锚定 SHA-1；SHA-256 过渡格式已在协议层定义（`git init --object-format=sha256` 可启用），但生态与托管平台主流仍是 SHA-1，本篇按现行格式陈述。摘要覆盖对象头加全部内容，地址空间为 $2^{160}$ 档，生日界意义下的无偏碰撞在 $2^{80}$ 次运算档——工程上按"摘要即身份"使用。

SHA-1 在这里承担双重身份：**既是地址，又是校验**。读对象 = 按摘要前两级定位目录、按其余位定位文件，取出后重算摘要比对——字节有任何损坏，比对必然失败，不需要额外的校验和字段。更强的推论是**内容不变则地址不变**：同一内容在同一个库里永远只存一份，两份"应该一样"的内容可以直接比摘要判等。

这条性质顺手排除了反面设计：若按名字或存储位置编址，内容一改所有指向它的引用都得跟着重写；内容寻址把"修改"降解为"新增对象 + 移动引用"，旧对象原地不动。这是 1.3 的存储纪律与第二章"引用是唯一可变层"的全部前提。

可核验：`echo "# demo" | git hash-object --stdin` 连跑两次输出同一摘要；`echo "# demo " | git hash-object --stdin`（多一个空格）输出完全不同的摘要——"内容不变则地址不变"与"一字之差即新对象"在一次实验里同时成立。

### 1.3 对象只增不改：append-only 的三条后果

对象库的写路径只有一种动作：**新增**。一次提交产生一批新对象，旧对象的字节从此不再被改写。删除文件 = 下一个 tree 的清单里少一个条目（旧 tree 与旧 blob 原样保留）；修改文件 = 新 blob 连带逐级新 tree。整库因此是 append-only 的。

三条后果沿因果链排开。其一，**引用可逆**：任何历史地址永远有效，把引用指回去就回到那个状态——第二章 reset 与恢复的物理前提。其二，**被甩出引用链的提交仍可寻址**：reset 或变基把某些提交移出引用可达集后，它们的对象还在库里，"几乎不会真丢提交"的结论由此成立，恢复手段见 2.3。其三，**库只增不减**：空间回收交给打包与垃圾回收——按可达性清理长期不可达的对象，默认给不可达对象留以周计的宽限期；本文不展开，只需知道清理判据就是"从引用出发的图遍历是否可达"。

不可变层至此建完。但版本控制还需要"当前在哪个版本""下一个版本叫什么"这样的可变状态——Git 把全部可变性收敛到一个极薄的层：引用。这是第二章的全部内容。

## 二、分支 = 指针与三区流转

第一章的结论是对象库只进不出、字节不改；本节补上可变层。分支、标签、HEAD、远程追踪引用全是引用（reference），本质都是"一个名字对应一个对象摘要"，差别只在谁移动它、何时移动。

### 2.1 引用家族：41 字节的分支

分支的物理实体是一个文本文件：`.git/refs/heads/main`，内容 41 字节——40 位十六进制摘要加一个换行符。**创建分支 = 写这样一个文件**，O(1) 的常数动作：不复制任何对象、不复制任何工作区文件，库中所有对象原样共享。方向不等式要分开记账：创建分支 O(1) 写 41 B；切换分支（checkout/switch）要按目标提交重写工作区里的文件，代价随差异文件数走——"建分支零成本、切换才搬文件"，两个动词的代价差一个数据规模量级。

HEAD 是指向引用的引用：`.git/HEAD` 的内容是 `ref: refs/heads/main`。提交动作 = 在 HEAD 所指分支的提交链上新增 commit 对象，并把该分支文件原地改写为新摘要——"分支随提交前进"的全部机制就是这 41 B 的原地改写。当 HEAD 直接写着某个摘要（分离 HEAD）时，提交不前移任何分支，新提交悬空、只入 reflog。

标签与分支同为引用文件，唯一差别是移动策略：分支随 commit 自动前移，tag 一次写就不再动。附注标签的引用指向一个 tag 对象；轻量标签的引用直接指向 commit。

引用家族的完整清单：

| 引用 | 物理位置 | 文件内容 | 谁移动它 |
| --- | --- | --- | --- |
| 本地分支 | `.git/refs/heads/<名>` | 41 B：40 位十六进制 + 换行 | commit 自动前移；reset/merge/rebase 手动 |
| HEAD | `.git/HEAD` | `ref: <分支路径>` 或 40 位摘要 | checkout/switch |
| 附注标签 | `.git/refs/tags/<名>` | 40 位摘要（指向 tag 对象） | 一次写入，永不前移 |
| 轻量标签 | `.git/refs/tags/<名>` | 40 位摘要（直接指向 commit） | 同上 |
| 远程追踪引用 | `.git/refs/remotes/origin/<名>` | 40 位摘要 | 仅 fetch/push（第四章） |

可核验——`.git` 目录实地走查（`git init` 后的骨架，行尾注释为该路径存放的内容）：

```text
.git/
├── HEAD                   → 文本 "ref: refs/heads/main"：指向引用的引用
├── config                 → 远程地址与本地配置
├── index                  → 暂存区：路径 → blob 摘要 的二进制清单（2.2）
├── refs/
│   ├── heads/main         → 41 B 的分支文件
│   ├── tags/              → 标签引用
│   └── remotes/origin/    → 远程追踪引用（clone/fetch 时写入）
└── objects/
    ├── e8/3c5167…         → 松散对象：摘要前 2 位作目录名，其余 38 位作文件名
    ├── pack/              → 打包对象（多对象压缩归档，存储与传输优化）
    └── info/
```

在仓库里执行 `git branch dev`，随后 `wc -c .git/refs/heads/dev` 读到 41——"O(1) 写一个 41 字节文件"从断言变成一次读数。

### 2.2 三区流转：一次改动的入库生命周期

引用解决了"版本叫什么"，还剩"改动怎么进库"。Git 把一次改动的旅程分成三个区：**工作区**（working tree，直接编辑的文件副本）、**暂存区**（staging area，物理实体是 `.git/index`，内容是"路径 → blob 摘要"的清单——即下一个 tree 的清单）、**对象库**（第一章的键值存储）。三个区由两条命令串联：

```text
三区流转环（视角：一次改动的搬运路径；边上标注该命令搬运什么）

   工作区                     暂存区 index                  对象库 + 引用
   working tree              （.git/index）                （.git/objects + refs/）
   ─────────────             ──────────────                ─────────────────────
   直接编辑的文件副本          下一个 tree 的清单：
                             路径 → blob 摘要
        │
        │ git add <路径>
        │ ① 对改动文件算摘要，blob 对象写入对象库
        │ ② 把（路径, 摘要）记入 index
        ▼
                              [README.md → e83c…]
                              [src/main.py → 6f8a…]
        │
        │ git commit
        │ ① 把 index 清单冻结成 tree（逐条变条目，逐级挂子 tree）
        │ ② 写 commit 对象（tree 摘要 + parent + 作者/信息）
        │ ③ 分支引用前移：main 文件从 C2 的摘要原地改写为 C3 的
        ▼
                                                         main: C2 ──► C3
   工作区文件不变，改动已永久入库（对象只增不改）
```

逐边遍历。**add 边搬运的是内容与清单**：为每个改动文件写 blob（摘要寻址，重复内容零成本）、更新 index 条目；工作区里未 add 的改动留在原地，commit 看不见它们。**commit 边搬运的是整张清单**：把 index 冻结成 tree、包上 commit 壳、移动分支引用——三个动作一次完成，此后这批内容永久可寻址。对照 1.1 的投影方向：add 是"内容字节入投影"的第一级（blob），commit 一次补齐结构级（tree）与时序级（commit）。

暂存区的存在理由是一条解耦：**把"选哪些改动入库"与"何时入库"拆成两个独立时刻**。同一批工作区改动可以 add 一半、提交一半，再 add 剩余、提交第二次——没有暂存区，提交粒度就只能等于编辑器的保存粒度，要么整盘入库要么寸步难行。动作归因：add 把入库内容的挑选从 commit 时刻提前到 add 时刻，commit 时刻只做冻结与引用前移，两者各管一件事。

至此每个提交都已入库、可寻址、随分支前进。但引用会动错——reset 打算退一格却退了三格、变基中途想反悔——下一段给出这类操作的回退依据。

### 2.3 reflog：引用变更的本地流水账

HEAD 与各分支的每一次移动——commit、reset、merge、rebase、checkout——都会向本地的引用日志追加一条记录：动作类型、旧摘要、新摘要、一句描述。这就是 reflog（reference log，引用日志），它是引用变更的流水账，`HEAD@{n}` 表示"HEAD 在第 n 次移动之前指向的地址"。

reflog 是 reset 与误操作恢复的依据，恢复闭环只有两步：`git reset --hard HEAD@{2}` 之类的操作把提交甩出分支后，`git reflog` 里仍留着它的旧地址；再把分支指回去（`git reset --hard <旧摘要>`），提交重新回到可达集。整条恢复链没有一个动作触碰对象字节——能恢复，靠的正是 1.3 的"对象只增不改"：引用指回去时，对象原样还在。reflog 只存于本地、从不随 push 传输，默认保留期可达提交 90 天、不可达提交 30 天，过期由垃圾回收清理。

可核验：任意仓库连续做 commit 与 reset，`git reflog` 逐行读出每次移动；`git log --graph --oneline` 只画引用可达的提交链，两者对照即可看到"reflog 记住的比分支显示的多"。

引用是唯一的可变层，历史整形因此也是成批移动引用的动作。同一张 DAG 有两种整形路径——合并与变基，它们对"分叉"这件事给出了相反的答案。

## 三、合并与变基：两条 DAG 整形路径

本节消费 1.1 的 parent 边与 2.1 的引用移动：merge 与 rebase 都是把两条提交链整形成一张新 DAG，前者新增一个节点保留分叉，后者重放整条支路拉直历史。

### 3.1 三方合并：base 与两份 diff 的合成

三方合并（three-way merge）从两条链的**共同祖先**入手，这个祖先提交称为 base。有了 base，双方各自的改动集就是两份可计算的 diff：diff(base → 本方链) 与 diff(base → 对方链)。合成规则：只被一方触碰的区域自动采纳该方的版本；**双方对同一段落的不同改写构成冲突**——Git 无法替人决定保留谁，就把两版并列写进文件、标记冲突区，由人裁决出最终内容，`git add` 把裁决结果写入暂存区，最后产出合流提交。

为什么必须过 base 一步？排除法可见：没有共同参照，两方直接互 diff，对方的新增行会被当成"我删了它"的改写，整篇文件全是冲突；有了 base，"谁改的"变成一次三方比对就能回答的判定，冲突范围收缩到双方真实相撞的那几段。base 把合并成本从"与文件总量成正比"压到"与双方真实改动量成正比"。

```text
两条 DAG 整形路径（视角：历史整形面。C1–C3 为主链，C4–C5 为 feature 支路；
时间自上而下，竖线为 parent 边——每个提交指向其下方的更早提交）

整形前（main 与 feature 从 C2 分叉）：

  C1
   │
  C2 ◄──────┐
   │        │
  C3        C4
   │        │
  main      │
            C5
            │
          feature

merge 之后（新增 1 个合流提交 M；既有对象一个不改）：

  C1
   │
  C2
   ├──────────┐
  C3          C4
   │          │
   │         C5
   │          │
   └──► M ◄───┘       M.parent = [C3, C5]
        │
      main（前移到 M）        feature 仍指 C5：分叉拓扑永久入史

rebase 之后（C4、C5 逐个重放到 C3 之上，产出全新对象）：

  C1
   │
  C2
   │
  C3
   │
  C4'        C4'、C5' 是重放产出的全新提交：parent 分别指向 C3 与 C4'
   │         旧 C4、C5 失去引用，成为不可达对象（仍在库中，见 1.3）
  C5'
   │
  main（前移到 C5'，此后是单链到底）
```

merge 面板逐边遍历：C3 与 C5 各自持有从 C2 出发的 parent 链；合流提交 M 的 parent 字段恰好两个——`[C3, C5]`，这是 1.1 说的"parent 多于一个"的唯一来源；main 引用前移到 M，feature 仍指 C5。分叉的拓扑被永久写进历史：此后任何 `git log --graph` 都会画出这枚菱形。

可核验：在两个分支各提交一次后执行 `git merge`，`git log --graph --oneline` 输出自下而上先分叉、顶部汇于一个提交的图形，M 的双 parent 可用 `git cat-file -p` 读出。

### 3.2 变基：重放成新链，地址全变

rebase（变基）走另一条路：把 feature 支路上 base 之后的提交逐个摘下来，依次重放到目标链（main）的末端。重放不是移动而是重做——每个提交在新基底上重新生成 tree 与 commit 对象：内容基底变了，tree 的摘要变；parent 变了，commit 的摘要变。于是 C4 变成 C4'、C5 变成 C5'，**地址全部改变**；main 前移到 C5'，旧 C4、C5 失去引用、成为不可达对象（仍留在库里，等垃圾回收，见 1.3）。

收益与代价来自同一个动作。收益：历史拉成单链，`git log` 与 `git bisect` 的遍历不再经过合流节点，二分定位每一步都是单链前进一步。代价明码标价：**已推送的历史被重写**——若 C4、C5 已被别人拉取，协作方手里持有旧链，远端与本地从此各自持有"内容相同但地址不同"的两条历史，后续同步会反复撞车。由此有黄金法则：**只变基未共享的提交**——没有推送过的本地提交，重写只影响自己。

可核验：rebase 前后各执行 `git log --oneline feature`，提交信息逐条相同、40 位摘要逐条全变——"重放 = 新对象"直接读出来。

### 3.3 两条路径的取舍账本

| 维度 | merge | rebase |
| --- | --- | --- |
| DAG 动作 | 新增 1 个合流提交，parent = 双方 | 逐个重放，产出全新提交对象 |
| 既有提交的地址 | 全部不变 | 支路提交地址全变 |
| 历史形态 | 保留真实分叉拓扑（菱形） | 线性单链 |
| 已推送/共享提交 | 安全，不改写任何历史 | 撕裂协作方，黄金法则禁止 |
| 冲突处置 | 一次性解决全部相撞段落 | 逐个提交解决，可能反复撞同一段 |
| log/bisect 遍历 | 需穿越合流节点 | 单链直达 |
| 适用边界 | 共享分支的整合 | 未推送的本地提交整理 |

账本的行间读法：两列的每一行都由同一根因推出——rebase 重写地址，所以线性、整洁，也所以不能碰已共享的历史；merge 不动地址，所以历史真实，也所以拓扑分叉。没有全局最优，只有按"这些提交是否已离开本机"划分的适用边界。两条路径的产物最终都要发布出去——下一节处理发布这一跳。

## 四、远程协作流：分布式引用同步

前两章建成了单机模型：全量对象库加一组引用。Git 的"分布式"含义由此直接得出：每个克隆都是全量对象库与全量历史，远端只是另一台机器上的同名引用空间，不存在中央权威数据结构——跨机器同步的对象自始至终只有两类：对象本体与引用。

### 4.1 远程追踪引用：本地对远端的缓存视图

克隆时，本地会建一组远程追踪引用（remote-tracking reference）：`refs/remotes/origin/main` 等。它们是**上次同步时远端各分支的快照**——本地对远端的缓存视图，不随远端的实际变动自动更新。本节三个动作各搬运不同的东西：

| 动作 | 更新的引用 | 搬运的对象 | 触碰工作区？ |
| --- | --- | --- | --- |
| fetch | `refs/remotes/origin/*` | 远端有而本地缺的对象 | 否 |
| push | 远端的 `refs/heads/*` | 本地有而远端缺的对象 | 否 |
| pull | fetch + 一步整合（merge 或 rebase） | 同 fetch | 整合落地时是 |

fetch 只做两件事：补齐缺失对象、把 `origin/*` 引用改指远端最新摘要——本地分支与工作区一个不动。动作归因：fetch 把"知道远端变了"与"整合进本地"拆成两个独立决策，先看（`git log origin/main`）再合，不必一上来就动工作区。

push 则是一次**快进请求**（fast-forward）：请求远端分支从当前值前移到本地链的末端。远端只在接受"现值在待推送链的 parent 链上"时放行——此时远端只是把引用文件前移，与本地 commit 前移分支是同一个动作。请求被拒即非快进：**远端有你没有的提交**，远端若接受就会凭空丢掉那些提交，这是对象只增不改在远端的执行方式。

### 4.2 多人协作即 DAG 分叉与整合

把上述部件装进一个双人文档场景，协作的全程就是 DAG 的分叉与再整合：A 与 B 都从 C2 出发提交；A 先 push，远端 main 前移到 A 的提交；B 的 push 被拒（非快进）；B 执行 fetch，`origin/main` 缓存更新，`git log --graph --oneline --all` 画出本地链与远端链从 C2 分叉的真实拓扑；B 在本地整合——已推送过就 merge 出合流提交，未推送就 rebase 拉直（第三章账本的适用边界在此兑现）——再 push，这次是快进，放行。"先 fetch 加整合、再 push"的纪律由此而来：把分叉的合流做在本地，让远端永远只处理快进请求。

可核验：在两个克隆间互相 push 模拟上述场景，`git log --graph --oneline --all` 的输出先后出现分叉、合流提交（或拉直后的新链）与快进——三个阶段逐一对上图。

至此闭环走完：一次改动经三区入库成提交，提交链成 DAG，分支与标签是 DAG 上的引用，reflog 记下引用的全部行踪，远端同步只是对象与引用两类东西的搬运——提交丢了可以从 reflog 指回，历史分叉了可以按账本整形。但这一整套机制只回答了"提交是否被完整记录、能否找回"，从不回答"提交的内容是否正确"——正确性要靠测试回答，那是 02-测试策略 的领地。
