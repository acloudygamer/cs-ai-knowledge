# 架构分层与前后端

单进程的机制——对象模型、测试边界、流水线——到本篇抬升到系统级：一个服务由哪几层组成、层与层的边界画在哪、一次用户操作如何跨越浏览器与服务端完成端到端闭环。上游消费三处既有结论：05-计算机网络 的请求生命周期——01 篇的封装瀑布、03 篇的往返时延（Round-Trip Time，RTT）档位、04 篇的域名系统（Domain Name System，DNS）缓存阶梯、05 篇的超文本传输协议（HyperText Transfer Protocol，HTTP）语义（方法真值矩阵、状态码五档、无状态与凭据回传）、06 篇的传输层安全（Transport Layer Security，TLS）握手——本篇把它们当作已知节点单句引用，不重标数、不重画协议图；02-测试策略 立过的判据——缺陷密集在模块连接处——本篇画的正是这些连接处的系统级形态；03-设计模式与设计原则 的依赖倒置原则将在第三节被搬到进程边界之外。产出是一套系统级分层边界：07-数据库基础 在数据层节点内部下钻（索引、事务、存储引擎），08-微服务架构 把本篇的横向域边界放大为部署边界。

本篇的拓扑主干是空间事务环：一次用户操作从前端组件状态出发，经序列化、加密、负载均衡（Load Balancing）、网关、业务规则与持久化，再原路返回更新状态——端到端生命周期闭环，逐节点标注「参与处理」还是「纯转发」；辅以一条时序因果链：一个服务副本从启动到可接客的依赖顺序。三节按因果排开：先立分层的约束（变化速率与团队边界，第一节），再遍历请求事务环（第二节），最后处理边界上的承诺——应用程序编程接口（Application Programming Interface，API）契约（第三节）。

## 一、分层的约束：变化速率与团队边界

### 1. 变化速率谱：层界画在档位跳变处

系统里的代码不是匀速变化的。三档典型节奏把变更按快慢排开：

- **表现层——界面、交互、文案：周级档。** 产品迭代与视觉改版以周计，一周多次发布是常态；变更只动界面代码，不触碰任何规则与数据。
- **业务层——业务规则与流程：月级档（周到月）。** 优惠叠加规则、风控阈值、审批流跟着经营节奏调整，频率低于界面、高于表结构。
- **数据层——表结构与历史数据：年级档。** 一次列变更牵出迁移脚本、存量数据回填与全部读旧数据的代码回归，代价按年级资产计算，节奏因此最慢。

三档速率不同的代码若绑进同一个部署单元、以函数直调互通，会发生什么：改一处周级的界面文案，整个单元重新构建、全量回归——年级档的数据层代码被迫陪跑一遍验证；发布节奏被最慢的验证面锁死；任何一层的缺陷，半径都是全站。快层每改一次都要碰慢层，这是速率错配的直接代价。分层的切线因此画在档位跳变处：层与层只经接口对话，周级变更被接口挡在表现层内，年级档的表结构资产不被快层节奏拖着走。代价明码标价：每跨一层多一次进程内间接调用（纳秒到亚微秒级档），外加一份接口定义的维护——对照一次跨网络请求（毫秒级档，05-计算机网络 03 篇的 RTT 档位），进程内分层税低两三个数量级，这笔税买回的是变更局部化。

这条切线与 05-计算机网络 01 篇的分层判据形成对照：网络按抽象层级切（每层只解决一种距离、只读写自己的头），架构按变化速率切（每层只容纳一种变更节奏）——切线依据不同，形式同构。

把两条切线（纵向按层、横向按域）合到一张网格上，每个格子的变更节奏就位：

### 2. 团队边界与前后端分离：康威定律的两次落地

横轴的依据是康威定律（Conway's Law，Melvin Conway，1968）：系统的结构会复刻设计它的组织的沟通结构——锚定为历史观察结论而非物理定律。分层因此不只是代码切分，同时是团队分工：纵向三层天然映射三支队伍（前端、后端、数据），层间接口即团队之间的交付界面；横向按业务域切格（图① 的列），每列由一条产品线独立演进，域间只经契约对话。这条横向切分的埋线由 08-微服务架构 兑现：当域边界直接升格为部署边界，每个域成为独立服务，本篇层内按域分格的结构就放大成了服务间拓扑。

前后端分离是同一条定律在消费端逼出的第二次落地。消费端形态多样——桌面浏览器、移动 App、小程序、第三方系统。排除法看反面：若坚持服务端拼 HTML（服务端把界面组装成最终页面再下发），每种端要各养一套模板，交互体验绑死在整页刷新上，第三方连页面都拿不到数据。唯一出路是统一 HTTP API 加各端独立渲染：服务端交付数据、不交付表现，浏览器与 App 各自持有表现层、消费同一份 API。结构后果正落在图① 上：表现层一行要按客户端形态横向复制（Web 端、App 端各一份），业务层与数据层各域全端共享单份——「前后端分离」在结构上就是表现层与业务/数据层之间那条界线的正式化。下一节遍历的请求事务环，走的正是这条界线两侧的完整链路。

逐节点遍历。**①②（参与处理）**：用户事件先把前端组件状态改到「提交中」，再触发请求装配——业务对象被序列化（把内存对象压平成可传输文本的动作）为 JSON（JavaScript Object Notation，键值对构成的文本格式）文本，装入 HTTP 报文。方法语义按 05-计算机网络 05 篇的方法真值矩阵取既定前提：查询用 GET、提交用 POST，幂等列留作第三节的重试开关。

**③ DNS（参与解析）**：浏览器把 URL 主机段换成 IP，延迟结论单句引用 05-计算机网络 04 篇——本地缓存命中微秒档、递归缓存命中毫秒档、未命中全链路几十至上百毫秒档；命中与未命中只决定这一跳的档位，不改变链路形态。

**④ TLS 握手（参与处理）**：加密通道在此建立，结论单句引用 05-计算机网络 06 篇——TLS 1.3 全握手一个 RTT、1.2 两个；RTT 档位锚定 05-计算机网络 03 篇（同城毫秒级、跨洲几十至上百毫秒级）。握手只付一次：后续请求在同一条连接上复用（05-计算机网络 05 篇的 keep-alive 结论），形态切换也发生在这里——HTTP 报文进记录层切块加密为 TLS 记录。

**⑤ 逐跳路由（纯转发）**：互联网上的每一台路由器查表转发、把帧头逐跳重写（05-计算机网络 02 篇的受力现场），不解读应用字节。形态沿 05-计算机网络 01 篇的封装瀑布逐级就位：TLS 记录装进 TCP 段、段装进 IP 分组、分组装进帧——本篇复用该瀑布，不重画。

**⑥ 负载均衡（参与处理）**：请求抵达服务端的第一站。它终止 TLS——加密在此卸掉，明文报文首次可见——再按各副本的负载与健康状态选中一台应用实例。参与处理与纯转发在这里分型：七层形态解读报文内容做选择（参与处理），四层形态只按地址与端口分发、不解密（纯转发特例）。它选谁，以图③ 的可用副本表为输入。

**⑦ API 网关（API Gateway，服务的统一入口；参与处理）**：三职能依次执行——路由匹配（按路径决定请求归哪个服务）、鉴权（核验调用者身份与权限；认证与授权的机制谱系归 09-安全基础）、限流（Rate Limiting，超阈值的请求按策略拒收，保护下游）。三职能任一不过，请求当场以 4xx 档拒绝，到不了应用层——网关因此是环上第一道可整批拦截的闸门。

**⑧ 应用层（参与处理）**：JSON 文本在此反序列化为业务对象——环上对象第一次「复活」；随后参数校验、业务规则执行（订单域的优惠计算、库存扣减规则），最后发起数据访问调用。表现层与业务层的界线（第一节立的那条线）就在 ⑦ 与 ⑧ 之间：网关看到的只是路径与凭据，业务对象只活在界线以内。

**⑨ 数据层（参与处理）**：SQL 执行、事务落库、返回行集。本篇只走到这格黑盒的门口，内部机制在收尾交接。

**⑩ 响应原路返回**：行集上交 ⑧，装配为响应体——状态码在此定档（05-计算机网络 05 篇的五档分档为既定前提）；⑦ 已做过裁决、原样上交，⑥ 重新加密进 TLS 记录，⑤ 照旧纯转发。**⑪ 状态落地（参与处理）**：同一条连接解密，JSON 文本反序列化为业务对象，组件状态更新、界面重渲染——回到 ① 的事件源：这次渲染可能触发下一次用户事件，事务环闭合。

环走完了，但两次过界的代价还没记账：每次过界，数据都要换一次形态、延迟都要加一档——下一小节算这笔账。

### 2. 形态瀑布与延迟账：与封装瀑布同构

把环上全部形态切换按节点排开，得到一张换装谱系：② 内存对象 → JSON 文本；④ HTTP 报文 → TLS 记录；⑤ 记录 → TCP 段 → IP 分组 → 帧（帧头逐跳重写）；⑧ JSON 文本 → 业务对象；⑨ 业务对象 → SQL 语句 → 行集。这张谱系与 05-计算机网络 01 篇的封装瀑布同构——载荷逐级换装、每级只换成下一跳需要的形态——本篇复用其结论，不重画瀑布。差异只有一处：中间各级的形态由协议钉死（帧、分组、段、记录全是固定格式），两端的形态由应用自定义——前端对象与后端对象各长各样，靠什么对齐，是第三节契约的任务。

延迟账逐段归位（各档数字以 05-计算机网络 结论为准，本篇不另立数）：一次点击到界面更新的等待，由四段拼成——DNS 档（05-04：命中微秒/毫秒档、未命中几十至上百毫秒档）+ 握手档（05-06：TLS 1.3 一个 RTT、1.2 两个；RTT 档位 05-03：同城毫秒级、跨洲几十至上百毫秒级）+ 请求-响应往返（一次 RTT 档起；连接复用后握手不重付）+ 服务端处理（本篇不展开，数据层部分由 07-数据库基础 核算）。本篇从这笔账里只取结构结论：跨网络每多一跳，延迟就多加一个 RTT 档的倍数——这正是第一节「进程内分层税远低于跨网络一跳」的另一半依据。

可实操核验：`curl` 的分段计时把环的前段各档一次读出来——

```console
$ curl -o /dev/null -s -w 'DNS %{time_namelookup}s | TCP %{time_connect}s | TLS %{time_appconnect}s | 首字节 %{time_starttransfer}s\n' https://example.com
DNS 0.012s | TCP 0.198s | TLS 0.316s | 首字节 0.401s
```

四个时刻的差值正好对应环的前段节点：DNS 档、TCP 握手一个 RTT、TLS 握手再加若干 RTT、服务端处理加返程首字节。对同城与跨洲目标各跑一次，两次读数的差就是 RTT 档位差的直接读数（以上为一次跨洲目标的示例读数）。

形态与延迟都有了去处，还剩环上最后一个结构性问题：凭什么负载均衡可以把任意请求发给任意副本——这个前提的成立与否决定整条环能否横向放大，下一小节收口。

### 3. 无状态与水平扩展：一条因果链的收口

前提来自 05-计算机网络 05 篇的结论：HTTP 协议本身无状态（Stateless）——服务器不保留请求间的上下文，会话状态由 Cookie 或 Token 携带、每请求凭据回传、服务端验证。应用层把这个前提落成部署形态：会话状态外置——要么随签名令牌自带（服务端只验签、不存会话），要么放集中存储（所有副本共享同一份会话库），任何副本都读得到同一份上下文。

水平扩展（Horizontal Scaling，加机器而非换更大的机器）由此收口成一条因果链：请求自带全部上下文 → 任一副本对任一请求的处理完全等价 → 负载均衡按当前负载任意分发，不需要记住「这个用户归哪台」→ 扩容就是把下面的启动链再跑一遍、把新副本挂入可用副本表，缩容就是摘副本，全程不迁移会话。方向不等式固定：无状态用「每请求携带凭据 + 每次验证」换「零会话内存 + 自由扩缩」，换出去的每一笔去向明确（05-计算机网络 05 篇算过同一笔账，此处只取部署结论）。

新副本可接客之前要走完一条启动依赖链——这是本篇的时序因果链，严格单向推进，任一步未过、健康检查不放行、副本不进分发言：

```text
图③ 应用副本的启动依赖链（视角：时序因果面。每步以上一步的就绪为输入；
任一步未过，健康检查不放行，副本不进负载均衡的可用副本表）

 步1 数据层就位：schema 迁移先落库
     （年级档资产先就绪——周级代码启动时依赖的表结构必须已在）
        ▼
 步2 实例启动：读配置 → 建数据层连接池（Connection Pool，
     复用与数据库的 TCP 连接、免每请求重建握手）→ 装载业务对象
        ▼
 步3 健康检查（Health Check）探活：实例自证「起得来、连得上」
        ▼
 步4 负载均衡把副本挂入可用副本表（图② ⑥ 的选副本动作以这张表为输入）
        ▼
 步5 网关路由表已含本服务的匹配项——任意请求可经图② ⑦ 抵达该副本
```

对图遍历：步1 先行，因为应用启动的第一件事就是连库，表结构未迁移则连接后第一个查询即失败；步2 的连接池把建连的握手税摊到多个请求上（05-计算机网络 03 篇的握手成本结论在此复用）；步3 通过才允许步4——带病的副本挂入分发言，等于让负载均衡向它持续投递必然失败的请求；步5 补上最后一环，网关的路由与副本的就绪在此会合。图② 的扩容动作，物理上就是把这条链完整重跑一遍。

反面一句钉死：会话粘滞（sticky session）——负载均衡记住用户与副本的绑定——把刚卸掉的服务端状态加了回来：副本故障即其上会话全丢，扩缩容即全量重分布，是补丁而非设计。

> **事实澄清：无状态 ≠ 无数据。**
>
> - 无状态说的是请求之间不在应用实例内存里保留「这次对话」的上下文；业务数据本身仍是系统的状态重心，全部沉淀在数据层。
> - 无状态化转移的只是会话上下文（登录态、未提交的草稿这类短期状态），不是业务数据——把两者混为一谈，会得出「服务端什么都不存」的误读。

至此环上每个节点、每笔形态税与延迟税、扩缩容的因果链都已收口；唯一还没立约的东西是过界时的数据形态本身——JSON 的字段、类型与错误结构。它是两侧各自独立开发的前提，第三节展开。

## 三、API 契约：边界上的承诺

### 1. schema 即接口：契约内容与错误契约

第二节环上，前后端两次交换 JSON 文本（② 与 ⑪）；本节回答这份 JSON 长什么样由谁说了算。答案是契约（Contract）：双方共同依赖的接口约定，内容最小集是 schema（数据结构的字段级描述）——字段名、类型、必选性、枚举取值，外加错误码表。契约是边界上的一张公共图纸，两侧各自施工、按同一张图验收——类比到此为止。

这个动作的原理层来自 03-设计模式与设计原则 的依赖倒置原则（Dependency Inversion Principle）：调用方与实现双方都改依赖同一个抽象接口，具体实现只在装配点绑定一次。契约把同一动作搬到进程边界之外：前端不引入后端代码、后端不知道前端组件树，双方唯一共同依赖就是这份 schema——对彼此具体实现的依赖，被「双方各自依赖契约」取代。动作归因：契约先行让两侧并行开发（前端按契约自造假数据先行界面，后端按契约暴露尚未实现的桩），也让变更影响可以被静态判定——下一小节的兼容矩阵，正是把「改了哪个字段」代入契约做出的分类。

契约的另一半是错误契约。状态码承担粗归因（05-计算机网络 05 篇的五档分档为既定前提：4xx 请求方错、5xx 服务端错），统一错误体承担细归因。结构固定三件：机器可分支的业务错误号 `code`、人读的 `message`、字段级的 `details` 数组：

```json
{
  "code": "ORDER.STOCK_INSUFFICIENT",
  "message": "库存不足",
  "details": [ { "field": "skuId", "reason": "剩余 0 件" } ]
}
```

前端据契约做分支：4xx 改请求或提示（补凭据、提示无权、退避重发），5xx 按方法的幂等列决定能否原样重试（05-计算机网络 05 篇的「幂等列 × 状态码档」二维判定，单句引用），`details` 驱动表单的字段级红标。错误结构同样受契约管辖：改一个错误码枚举值，就是一次破坏性变更——它进下面矩阵的同一行受审。

契约一旦发布就不是单方面可改的私有物——哪些变更能直接上线、哪些必须走版本，下一小节补齐矩阵。

### 2. 兼容矩阵与版本化：破坏性变更的分类处置

把字段级的变更逐类过审，判定线只有一条——旧客户端在不知情时的行为是否改变：

| 变更类型 | 旧客户端行为 | 新客户端行为 | 兼容性判定 | 处置动作 |
| --- | --- | --- | --- | --- |
| 加可选字段 | 不认识即忽略（JSON 解析器的默认动作），其余功能不受影响 | 可消费新字段 | 兼容 | 直接上线 |
| 加必选字段（服务端收严校验） | 未携带该字段即被拒——存量请求批量失败 | 携带该字段，正常 | 破坏性 | 先按可选字段灰度，确认存量迁移完成后再收严 |
| 删字段 | 仍在读取该字段，拿到缺失值或默认值，行为破坏 | 已改读新来源 | 破坏性 | 版本号隔离新旧契约；或先停写（返回空值并公告）再物理删除 |
| 改字段类型 | 解析失败或按错误类型解读 | 已适配新类型 | 破坏性 | 新增字段并行上线，旧字段标记废弃、双写过渡 |
| 改字段语义（类型不变、含义变） | 解析照常通过，行为悄悄漂移 | 已按新语义适配 | 隐性破坏（最危险） | 视同破坏性：新字段加文档，旧字段冻结不再动 |
| 改错误码枚举 | 前端分支匹配不到，落进未知分支 | 已适配新枚举 | 破坏性 | 新错误码新增，旧码保留并映射到新码 |

矩阵的行间读法：加可选字段之所以兼容，是因为旧客户端的解析器遇到不认识的键一律忽略——兼容性不是双方协商出来的，是解析器默认动作送的；删与改之所以破坏，是因为旧客户端的代码还按旧契约在读。最危险的一行是改语义：类型不变、解析照过、没有任何报错可供定位，行为却已漂移——它必须按破坏性对待，用新字段加文档把新旧语义分开。

破坏性变更不能原地生效，机制是版本并存：新旧两份契约各占一个版本号（典型形态是路径前缀 `/v1/`、`/v2/`），网关按版本分流（图② ⑦ 的路由职能多一条分流维度），存量客户端在并存窗口内迁移，窗口推进的节奏即灰度（按比例逐步放量）——04-CI-CD 的金丝雀放量是同一动作在部署维度的形态，单句引用。版本不是越多越好：每个并存版本都是一份要持续维护的旧契约，窗口的终点是旧版本下线。

至此事务环上每个节点都已立约：层界由变化速率画出（第一节），环上的形态税与延迟税各归其档（第二节），过界的数据形态由契约钉死（本节）。环的终点是图② 的 ⑨ 数据层节点——它在本篇只是「SQL 执行、事务落库、返回行集」的一格黑盒：数据如何组织、SQL 靠什么结构加速、并发与崩溃时一致性如何保证，是数据层内部的一整篇机制，交给 07-数据库基础；而本篇横向按域切分的网格，当域边界升格为部署边界时，就是 08-微服务架构 的出发点。
