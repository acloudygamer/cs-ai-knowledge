# 测试策略

> **版本基准**: universal

## 骨架要点（正文按此展开，完成后删除本骨架块）

- **定位**：消费 01-Git 的提交流（测试挂在提交之后）、04-编程运行环境 的编译/运行时（测试即特殊进程）；产出"质量验证的分层结构"，供 04-CI-CD（流水线的核心阶段即测试）消费。
- **核心拓扑流**：时序因果链（一次失败从发现到定位的传导链：测试失败 → 失败层定位 → 修复 → 回归）+ 表格化决策（各层测试的边界判定）。本篇量化单位换轨：测试数量比例、运行时长档位、缺陷发现成本档位（复杂数学推导不强制）。
- **必备图**：①测试金字塔 ASCII 图（数量/速度/成本三轴：单元多而快在底、E2E 少而慢在顶，方向不等式写死）；②"一段代码变更从单元到 E2E 的验证覆盖区"示意（每层照到代码的哪一段）；③测试 doubles（stub/mock/fake）对照表。
- **量化锚点**：单元测试毫秒级、集成测试几十毫秒到秒级、E2E 秒到分钟级（量级档位，不承诺精确值）；测试套件总时长与提交反馈环的关系（CI 门禁要求分钟级）。

### 一、测试金字塔：数量、速度、成本的三轴反比

- 结构成因：越靠近端到端，牵连组件越多 → 运行越慢、失败定位半径越大、维护越贵——所以数量越少；逐层放大/缩小的因果链为骨架，比例数字（如 7:2:1）只作典型参考不硬性承诺。
- 方向不等式锚定：单元 < 集成 < E2E（运行时长、单条维护成本、失败定位精度）；反转金字塔（E2E 为主）的失败模式：套件脆弱、红绿灯噪声、团队放弃信任。

### 二、单元、集成与端到端的边界：按依赖真实程度切分

- 边界判据 = 是否触碰真实外部依赖（真实数据库/网络/文件系统为集成以上）：单元测试隔离一切外部依赖、验证单模块契约；集成验证模块间连接线（恰好是 02-操作系统 与网络等章讲的连接点）；E2E 验证用户可见行为闭环。
- 决策表：什么变更用哪层测（纯函数逻辑 / 数据库交互 / 跨服务请求 / 用户路径）——真值矩阵补齐单元格。
- 集成测试的第一公民地位：多数缺陷出在连接处而非模块内部——金字塔中段不能空心。

### 三、可测试性设计与测试替身

- 可测试性 = 把依赖连接点显式化：依赖注入即"把硬编码的 new 换成可替换的构造参数"——消费 03-设计模式 的多态解耦机制（单句引用，本篇不展开模式谱系）。
- 测试替身谱系表：stub（按剧本回值）/ mock（验证交互）/ fake（轻量真实现）——各自适用场景与过度使用的代价（mock 泄漏实现细节 → 重构即碎）。
- 适度原则：替身隔离了慢依赖也隔离了真实回归——集成层用 fake、边界层用真依赖。

### 四、覆盖率与缺陷经济：度量的边界

- 覆盖率只回答"没被测到的必未验证"，不回答"被测到的已充分验证"——方向写死；把覆盖率当目标会逼出无断言测试（动作归因）。
- 缺陷修复成本随发现阶段后移而上涨（设计期 < 单元 < 集成 < 上线后，档位方向锚定）——测试前移的经济账。
- 收尾落在下一跳：测试是质量的度量面，代码结构本身的质量由设计决定——交给 03-设计模式与设计原则。
