# 测试策略

## 一、测试金字塔：数量、速度、成本的三轴反比

测试回答的问题只有一句：这段代码在给定输入下产生的行为，是否与它声明的契约一致。验证发生在提交流之后——01-Git 版本控制的提交流把一次改动经工作区、暂存区、对象库三区流转冻结成 commit 对象并前移分支引用，push 则是一次快进请求，请求远端引用前移；测试正是横在"引用前移"与"放行"之间的验证面，绿灯放行这次提交、红灯拦截它。验证的执行载体不是静态分析器，而是一个真实进程：04-编程运行环境 的结论是源码经编译或解释装载为可执行形态、由运行时接管栈与调度，测试进程走的正是同一条装载路径——它只是一个喂了验证性输入与断言的特殊进程，同样要经过装载、同样要分配内存、同样以退出码报告成败。本篇的任务是把"验证"组织成一个分层结构：为什么分层、层与层的边界画在哪、依赖用什么顶替、度量到哪为止。下游消费方是 04-CI-CD 的流水线——其 PR 门禁、合并门、发布门三道门，正是本篇三层测试在门禁位置上的装配。

### 1. 三轴金字塔：塔形由因果链逼出

```text
测试金字塔（视角：三轴投影面。塔的宽度 = 该层用例数量；左右两列是另外两轴
——三条轴不是三个独立事实，是同一条因果链的三次投影，方向自下而上单调）

   单条维护成本高 · 失败定位半径大
        ▲
        │            ╱￣￣￣￣￣￣╲
        │           ╱   E2E      ╲      数量：个位数到几十条
        │          ╱  （端到端）   ╲     时长：秒到分钟级/条
        │         ╱───────────────╲
        │        ╱                 ╲
        │       ╱     集成测试      ╲    数量：几十到几百条
        │      ╱                    ╲   时长：几十毫秒到秒级/条
        │     ╱─────────────────────╲
        │    ╱                       ╲
        │   ╱       单元测试          ╲  数量：数百到数千条
        │  ╱                          ╲ 时长：毫秒级/条
        │ ╱───────────────────────────╲
        │                                ▲ 用例数量多 · 单条运行快

  三轴方向不等式（自下而上逐层单调，写死）：
    数量：        单元 > 集成 > E2E
    单条运行时长：单元（毫秒级） < 集成（几十毫秒到秒级） < E2E（秒到分钟级）
    单条维护成本与失败定位半径：单元 < 集成 < E2E
```

塔顶是 E2E（End-to-End，端到端）测试：把整个系统连同真实数据库、真实网络、真实部署环境一并拉起，从用户入口发起一次真实请求，验证到最终响应为止的完整行为闭环。塔的中段是集成测试：验证两个及以上模块之间的连接线——调用参数、接口契约、数据落库、跨进程消息。塔基是单元测试：把一切外部依赖替换掉，单独驱动一个模块，验证它的输入到输出映射。

塔形不是审美偏好，而是一条因果链的必然投影。**越靠近塔顶，一条用例牵连的组件越多**：一条单元测试只装载一个模块（毫秒级启动，测试进程几乎感知不到）；一条集成测试要多拉起数据库、消息队列等真实进程（每次校验先付环境启动的几十毫秒到秒级）；一条 E2E 要部署完整系统并清准备数据（秒到分钟级起）。牵连组件多，运行就慢；运行慢，单位时间能跑的用例就少；失败时怀疑面覆盖所有牵连组件，定位半径就大；环境搭建与数据准备是持续性负担，维护就贵。三条轴由此同向：**数量与单条成本成反比，不是规范要求，是把昂贵验证用在刀刃上的资源分配结果**。

经典的数量比例 7:2:1（单元 : 集成 : E2E）出自 Mike Cohn 2009 年《Succeeding with Agile》提出的分层建议，属历史惯例而非物理必然——本篇只锚定方向不等式，比例数字按项目类型浮动，作典型参考使用。

三层逐维对照（数量、速度、成本、定位四维的真值矩阵）：

| 维度 | 单元测试 | 集成测试 | E2E 测试 |
| --- | --- | --- | --- |
| 验证对象 | 单模块的输入 → 输出契约 | 模块间连接线与真实外部依赖 | 用户可见行为的全链路闭环 |
| 触碰真实外部依赖 | 否，全部替换 | 是，至少一个（数据库/网络/文件系统） | 是，全部 |
| 用例数量档位 | 数百到数千条 | 几十到几百条 | 个位数到几十条 |
| 单条运行时长档位 | 毫秒级 | 几十毫秒到秒级 | 秒到分钟级 |
| 失败定位半径 | 被测单模块内部 | 参与连接的模块对 | 整条用户路径，需向下逐层排查 |
| 单条维护成本档位 | 最低 | 中等 | 最高（环境 + 数据 + 时序） |
| 套件总时长档位 | 秒级档 | 分钟级档 | 分钟到十分钟级档 |

可核验：在一个真实项目里分别给两层套件计时——以 pytest 为例，`time pytest tests/unit/` 与 `time pytest tests/integration/` 各跑一次读墙上时钟：单元套件即便数百条也常压在秒级档（摊到每条毫秒级），集成套件几十条即进入十秒级档——"单元 < 集成"的方向不等式一次读数可验，且差的是档位差，不是百分比。

### 2. 反转金字塔的失败模式：三条退化链逐条归因

把塔倒过来——以 E2E 为主要验证层、单元层稀薄——不是激进，是自毁。退化沿三条机制链展开，每条都归因到具体动作：

- **套件脆弱，红灯噪声化。** E2E 触碰全部真实依赖：数据库里一条被别的用例改过的记录、网络的一次抖动、第三方服务的一次限流，都会把红灯点亮——失败原因三分叉为"代码缺陷 / 环境抖动 / 用例自身坏"，且红绿灯不区分三者。每次红灯都需要人工甄别一次，甄别成本按次重复支付；数据准备若有共享状态，用例之间还会互相踩踏，失败进一步随机化。
- **反馈环拉长，提交粒度被迫变大。** E2E 单条秒到分钟级、动辄全量重跑，一次提交的验证反馈落到分钟到十分钟级档——04-CI-CD 的结论在此反向兑现：反馈环超过十分钟档，开发者切走上下文、回来重建心理状态的成本超过修复本身，行为退化为攒大批量提交；大批量又拉长单次反馈与失败定位半径，正反馈恶化。
- **验证信任瓦解，团队绕过验证面。** 红灯常态化后，成员的动作依次退化为：重跑直到变绿、给失败用例加注释跳过、最后整层禁用——E2E 层一旦失信，整层验证面失效，而底下又没有单元层兜底，回归缺陷从此无拦截直入主干。这就是"团队放弃信任套件"的机制终点：不是态度问题，是红灯噪声把验证信号的信噪比压到了不可用。

三条链的共性归因：反转金字塔把"昂贵且信号模糊"的验证层推到最大占比，把"便宜且信号精确"的层推到最小占比——同样的验证预算，买回的定位信息最少、噪声最多。金字塔正向堆叠是排除法的结论：全 E2E 在时间预算上跑不完（数量需求与单条时长的乘积爆档），全单元则连接处无验证（缺陷最密集的区域裸奔）——两个极端都失效，只剩金字塔形态成立。

### 3. 一次失败的传导链：从红灯到回归绿

金字塔不仅是数量分配，还是失败的定位导航图。一次测试失败从发现到闭环的传导链是一条严格的单向因果链：

```text
一次失败的传导链（视角：状态流转面。绿 = 该层通过，缺陷被"透传"到上一层；
边标注该状态转移携带的定位信息）

  代码变更入库（01-Git：commit 前移分支引用，push 发起快进请求）
        │ 触发验证
        ▼
  ┌─────────────┐   通过    ┌─────────────┐   通过    ┌─────────────┐
  │  单元测试    │ ────────► │  集成测试    │ ────────► │   E2E       │
  │  毫秒级/条   │           │ 几十ms~秒级  │           │ 秒~分钟级    │
  └──────┬──────┘           └──────┬──────┘           └──────┬──────┘
         │ 失败                    │ 失败                     │ 失败
         ▼                         ▼                         ▼
  定位信息：缺陷在被测        定位信息：缺陷在连接处        定位信息：仅知"用户路径断"
  单模块内部                 （契约/数据格式/时序）        断点可在任何一层，
         │                         │                      需向下逐层重放
         │                         │                         │
         └────────────► 修 复 ◄────┴─────────────────────────┘
                              │
                              ▼
                 回归（Regression Test）：
                 ① 失败用例重跑，转绿；
                 ② 在缺陷所在层新增一条用例，把这次缺陷永久钉死
```

逐边遍历。**失败层即定位层**：单元测试红灯，定位半径被图收窄到被测单模块内部——读失败输入与期望输出的差值即可动手；集成测试红灯，缺陷在两侧模块各自成立、合起来不成立的那条连接线上——参数顺序、空值语义、时间戳时区、字符编码是高发区；E2E 红灯只报告"用户路径走不通"，断点可能在任何一层，必须向下逐层重放（先跑相关集成、再跑相关单元）把定位半径收窄——这正是单条维护成本不等式 E2E 最贵在定位维度的来源：**同一次失败，越在上层发现，人要付出的排查动作越多**。

**修复后的回归是两步而非一步**：失败用例重跑转绿只证明"这次改好了"；在缺陷所在层新增一条用例才把缺陷钉死——否则下一次有人改坏同一处，验证面仍然失明。这套"失败即补用例"的滚动积累就是回归测试（Regression Test）：它不追求一次写全，而是让每一次失败都转化为一条永久守卫。传导链至此闭环，但闭环依赖一个前提——每层的红灯都发生在正确的层。层与层的边界画在哪，是下一节的问题。

## 二、单元、集成与端到端的边界：按依赖真实程度切分

上一节给了三层的数量与速度账，本节回答分界判据。判据只有一条且可以机械执行：**这条用例是否触碰真实外部依赖**——真实数据库、真实网络、真实文件系统只要有一个参与，用例就归集成以上；全部替换掉，才是单元测试。

### 1. 判据的机制根据：替身替换的是行为，替换不掉的是语义

这条判据不是随意的分类学。替身（下一节的机制）能顶替一个依赖的**调用行为**——"调用后返回这个值"；顶替不掉它的**语义**——SQL 在真实数据库上的事务隔离行为、网络栈的超时与重试时序、文件系统在磁盘满时的失败模式。单元测试隔离一切外部依赖，验证的是单模块契约在"依赖行为完全可控"前提下的正确性；一旦被验证的行为本身依赖外部语义（SQL 语义、序列化格式、并发时序），替身就把它从测试对象里删掉了——这条用例对这类缺陷永久失明。所以分界线画在"行为是否依赖真实语义"上：不依赖 → 单元；依赖本地或远端进程的真实语义 → 集成；依赖整个系统的组合语义 → E2E。这些连接点正是 02-操作系统（进程与系统调用边界）与 05-计算机网络（协议两侧）各章讨论的对象：两侧各自成立、合起来出错，是缺陷的密集产地。

### 2. 验证覆盖区：每层照到变更的哪一段

把一次代码变更切成按依赖真实程度排列的三个区段，三层的覆盖区间互补、拼满整个变更面：

```text
一次代码变更的验证覆盖区（视角：依赖真实程度轴。左列 = 变更触及的代码段切片，
下方 = 承担验证的测试层；三层覆盖区间互补，不重叠地拼满变更面）

  变更触及的代码段（自左向右，依赖越来越真实）
  ┌──────────────────────┬──────────────────────────┬──────────────────────┐
  │  模块内部             │  连接处                   │  用户路径             │
  │  单模块的计算与        │  模块↔模块、模块↔外部依赖  │  入口请求 → 多模块 →  │
  │  状态转换             │  的调用与数据交换          │  持久化 → 最终响应    │
  │                      │                          │                      │
  │  依赖：全部替身        │  依赖：被测侧真实，        │  依赖：全部真实        │
  │                      │  其余可控                 │                      │
  └──────────▲───────────┴────────────▲─────────────┴──────────▲───────────┘
             │                        │                        │
         单元测试                  集成测试                  E2E 测试
        （毫秒级/条）           （几十 ms~秒级/条）         （秒~分钟级/条）

  读法：一段变更入库后，三层各自照亮自己的区段；
        哪个区段没有对应层的用例，那段变更就没被验证
```

逐列遍历。**左列（模块内部）**由单元测试独占照亮：依赖全部替换后，单模块的分支、边界值、异常路径可以以毫秒级单条成本穷举——这是唯一能负担"每个分支一条用例"密度的区段。**中列（连接处）**由集成测试承担：调用参数与返回契约、SQL 语句落到真实库的语义、跨进程消息的序列化格式——这些行为的正确性依赖真实语义，替身插足即失明（1 的结论）；同时被测侧保持真实、其余依赖保持可控，把定位半径压在"这一对模块"上。**右列（用户路径）**由 E2E 承担：权限串联、多服务协作的最终行为、配置在真实环境下的组合效果——验证对象是全链路组合行为，任何一层替换都会截断闭环。三列的分工与金字塔的数量分布咬合：左列用例密度最高（最便宜）、右列最低（最贵），覆盖区互补但用例密度递减。

### 3. 变更类型 × 测试层决策矩阵

覆盖区给出空间划分，决策表把它落成"拿到一段变更，先写哪层用例"的执行规则。真值矩阵逐格补齐（"能" = 该层可对这类变更给出有效验证；"不能" = 该层对此类缺陷失明或代价失衡）：

| 变更类型 | 单元测试 | 集成测试 | E2E 测试 | 首选层 | 归因（机制动作） |
| --- | --- | --- | --- | --- | --- |
| 纯函数逻辑（计算规则、格式转换、边界值） | 能：替掉依赖后直接驱动 | 能，但多付环境启动时长，不新增定位信息 | 能，但定位半径最大、单条最贵 | 单元 | 缺陷落点在单模块内部，毫秒级回归即可钉死 |
| 模块内部状态机与异常分支 | 能：分支逐条枚举 | 能，但不必要 | 能，但不必要 | 单元 | 分支穷举在隔离环境成本最低，环境参与只会稀释信号 |
| 数据库交互（SQL 语义、事务、迁移） | 不能：替身丢失 SQL 语义，对此失明 | 能：真实库 + 小数据集 | 能，但过重 | 集成 | 事务隔离与约束行为只在真实库上成立 |
| 跨进程/跨服务调用（序列化、超时、重试） | 不能：替身截断时序与格式语义 | 能：对端用受控 fake 或真实桩服务 | 能 | 集成为主，少量 E2E | 契约两侧各自成立、合起来出错，须在连接处验证 |
| 用户可见行为闭环（登录、下单、权限串联） | 不能 | 部分：能验连接、验不了组合 | 能 | E2E（少量） | 验证对象是全链路组合行为，任何替身都截断闭环 |

矩阵的列间读法：一个变更类型从上往下看，"能"的层逐格递减——**每往右一层，验证换来的真实性上升、可负担的密度下降**；首选层恒为"仍能给出有效验证的最左层"，即用最便宜的层覆盖缺陷落点。这个选层规则与金字塔的数量分配互为因果：正因为多数变更的首选层在左，左层用例才天然最多。

### 4. 中段不能空心：缺陷分布压在连接处

矩阵逐格归因后，一条经验规律浮出：**多数缺陷出在连接处而非模块内部**。机制归因有二：其一，模块内部逻辑已被调用方与被调方的类型系统压实，明显的错误在编译期或本地单测即被拦截，能存活到集成阶段的内部缺陷所剩无几；其二，连接处的缺陷本质是"两侧各自对契约的理解不一致"——一侧按毫秒计时、另一侧按秒计时，一侧发 `null` 另一侧按空串处理——这类错误任何一侧的单元测试都测不出来，因为各自的单元测试各自建模了对方的假设。这正是集成测试在金字塔中占稳一层的理由：**塔基验证"每块砖合格"，塔顶验证"房子能住"，而"砖与砖之间的灰缝"只有中段照得到**。中段空心（只有海量单元 + 几条 E2E）的套件，缺陷检出会集中漏掉连接处，红灯只能由最贵的 E2E 层报出——定位半径立即放大。层与层边界划清之后，剩下的问题是：单元测试凭什么能"隔离一切外部依赖"？这要求代码结构允许替换——下一节的可测试性设计。

## 三、可测试性设计与测试替身

上一节的所有结论都建立在"依赖可以被替换"这个前提上。这个前提不是测试框架给的，是代码结构给的：依赖写死在模块内部的结构，任何框架都替换不了它。

### 1. 可测试性 = 依赖连接点显式化

可测试性的机制定义只有一句：**把"模块用到谁"从写死的内部构造，改成外部可替换的连接点**。依赖注入（Dependency Injection，DI）就是这个动作的名字——把硬编码的 `new` 换成可替换的构造参数：

```text
替换前：连接点焊死在模块内部

  class 报表服务 {
      private 数据库 = new 生产数据库()      // 构造发生在类内部，
      ...                                   // 测试拿不到替换的机会
  }

替换后：连接点外移为构造参数

  class 报表服务 {
      constructor(数据库) { ... }           // "用哪个数据库"由组装处决定
  }

  生产组装：new 报表服务(new 生产数据库())
  测试组装：new 报表服务(new 内存数据库())   // ← 单元/集成测试的入口
```

这个动作的运行时底座是多态，就地引用 03-设计模式与设计原则的结论：接口把调用方可见的方法集与具体实现分离，实现藏在虚表之后、经动态绑定替换，调用方只依赖抽象——依赖注入不新增任何模式，它只是把"注入哪个实现"这个决定从类内部移动到组装处，使测试进程获得与生产进程不同的组装权。没有这个连接点，单元测试对"隔离一切外部依赖"的要求（二.1）无从落地；有了它，替换才成为一次普通的传参。反向推论同样成立：一段连替身都插不进去的代码（依赖散布在函数体内、构造焊死、静态单例持有全局状态），其可测试性缺陷本身就是结构缺陷的信号——这条线索在第四节收尾处交还给设计。

### 2. 替身谱系：stub、mock、fake 各自验证什么

连接点打通后，往连接点里注入什么？测试替身（Test Double）——测试里顶替真实依赖的对象——按验证目标分三个谱系，一词借自电影特技替身：真演员做不了的动作由接口相同的替身完成。三者的机制动作、验证对象与代价逐列对照：

| 替身 | 机制动作 | 验证对象 | 适用位置 | 过度使用的代价 |
| --- | --- | --- | --- | --- |
| stub（桩） | 预设剧本："收到某调用即返回某值"，被动应答，不做任何校验 | 只看被测模块自身的输出 | 单元层隔离慢依赖、随机源、外部服务 | 代价最低；剧本过厚时会悄悄固化对依赖行为的假设 |
| mock（模拟对象） | 预设期望并记录全部调用，测试末校验"是否以预期参数调用了预期方法" | 交互本身：调用是否发生、参数是否正确、次序是否正确 | 需验证调用契约的边界（如"必须恰好发出一次通知"） | 断言写死实现细节 → 重构即碎（见下） |
| fake（伪实现） | 提供一个能真正运行的简化实现（内存数据库、内存消息队列） | 被测模块与依赖的联合行为 | 集成层替掉外部服务与进程边界 | 实现漂移：fake 与真实现的语义分叉后，绿灯变假阳性 |

谱系的分野在"验证的是值还是交互"。stub 与 fake 服务于**状态验证**——执行完毕后检查返回值或落库状态，不关心中间怎么调用；mock 服务于**交互验证**——检查被测模块与依赖之间的对话本身。三者沿金字塔自上而下各有其位，但代价曲线陡峭程度不同，其中 mock 的过度使用有一条明确的退化机制，单独展开：

**mock 泄漏实现细节 → 重构即碎。** 一条 mock 断言写的是"调用了 `getUser(id)` 两次、第二次参数为 `null`"——这断言的不是模块的外部契约（输入 → 输出），而是模块的内部实现路径（怎么调用依赖）。重构的定义恰是"不改变外部行为的内部调整"：把两次查询合并为一次缓存读取，外部行为完全不变，mock 断言却红了。于是每一次重构都要同步修改一批与行为无关的 mock 断言——维护成本按 mock 数量线性上涨，团队的理性反应是减少重构，结构质量随之冻结。动作归因：mock 把"验证实现细节"这个本不属于测试的职责拉进了断言，让测试从行为的守卫变成了实现的镜像。

### 3. 适度原则：隔离了慢依赖也隔离了真实回归

替身的收益与代价来自同一个动作：**把依赖挡在进程外，同时也把"依赖的行为变了"这个回归信号挡在了外面**。真实依赖升级后语义变化（数据库引擎更改索引行为、消息队列更改投递时序），全替身的单元层对此永久绿灯——它验证的契约建立在旧语义上。所以替身的使用密度必须沿金字塔递减，形成一条与依赖真实程度同构的分配规则：

- **单元层用替身换速度**：毫秒级单条成本依赖隔离，全部替换，代价由集成层兜底；
- **集成层用 fake 换可控**：需要真实语义（二.1）但不需要真实部署，fake 提供语义的可控近似——代价是 fake 与真实现的语义偏差要靠少量真依赖用例校准；
- **进程与系统边界用真依赖换真实**：跨服务、跨系统的契约两侧无法互相建模，用真实对端 + 少量 E2E 兜住组合语义。

三条分配规则与二节的覆盖区逐列咬合：覆盖区回答"验证哪段"，分配规则回答"注入什么"。至此三层各自的验证对象、边界判据与替换机制全部就位；最后一节处理度量本身——测了多少怎么算、缺陷晚发现贵多少。

## 四、覆盖率与缺陷经济：度量的边界

前三节建立了"怎么分层验证"，本节处理两个度量问题：覆盖率能证明什么、晚发现的缺陷贵在哪。两者共同给"测试做到什么程度"划出边界。

### 1. 覆盖率的方向：只保证下界，不保证上界

代码覆盖率（Code Coverage）度量测试执行时被走过的代码元素（行/分支/路径）占可执行元素总数的比例。它的逻辑方向必须写死：**覆盖率只回答"没被测到的必未验证"——低覆盖率是存在未验证代码的证明；不回答"被测到的已充分验证"——高覆盖率不构成验证充分的证明**。前半句是有效推理（没执行过的代码，其行为从未被任何断言检查过），后半句是无效推理（执行过 ≠ 断言过，更 ≠ 断言对过）。

把覆盖率当考核目标，会通过一条明确的机制链逼出无断言测试：考核指标是"元素被执行的比例"，指标既不检查断言是否存在、也不检查断言是否有效；于是一条只调用函数、不带任何断言的测试用例——执行了元素、抬升了覆盖率、且永远不会失败——成为成本最低的达标路径。指标惩罚"没跑到"、不惩罚"没验证"，最省力的优化方向必然是"跑到但不验"。结果是覆盖率数字上涨而缺陷检出能力不变甚至下降，度量面与目标脱钩。反面同样成立：100% 覆盖率的套件，若断言缺席或断言写的是实现细节（三.2 的 mock 病），对缺陷的拦截力仍然为零。

覆盖率的正确用法是**只当下限报警，不当下限承诺**：新代码覆盖率低于阈值时挡下合并（未验证区被拦截），已达标后不再追求更高数字（验证充分性由断言质量决定，不由数字决定）。可核验：`coverage run -m pytest && coverage report -m` 读出逐文件行覆盖率与未覆盖行号；再手写一条只调用被测函数、不加任何断言的测试，重跑 coverage——覆盖率上升而它对任何缺陷都不报警，"覆盖 ≠ 验证"在一次实验里同时成立。

### 2. 缺陷经济：修复成本随发现阶段后移上涨

第二个度量轴是时间：同一个缺陷，在不同的阶段被发现，付出的总代价差出档位。方向不等式写死：**设计期 < 单元 < 集成 < E2E/预发布 < 上线后**。逐档的定位信息与止损动作对照：

| 发现阶段 | 定位信息 | 止损与修复动作 | 附加成本项 | 成本档位 |
| --- | --- | --- | --- | --- |
| 设计期（评审/静态检查） | 缺陷在尚未实现的逻辑里 | 改一段还没写的代码 | 一次评审意见 | 最低档 |
| 单元层 | 缺陷在被测单模块内部 | 改码 + 毫秒级回归确认 | 无 | 低档 |
| 集成层 | 缺陷在连接处，跨模块排查 | 改码 + 秒到分钟级回归 | 需真实环境复现 | 中档 |
| E2E/预发布层 | 用户路径断，断点未知 | 向下逐层重放定位后改码 | 排查动作 + 晋级延迟 | 高档 |
| 上线后 | 缺陷输出已到达用户 | 回滚止损 + 数据修复 + 事件复盘 | 错误数据清理、信任损耗、复盘工时 | 最高档 |

逐档归因上涨的机制动作：越往后移，**定位半径越大**（单元层一眼定位，上线后要先从用户报障反推断点）、**止损动作越重**（从改一行代码到回滚生产）、**波及面越宽**（从一个人的本地状态到用户手里的错误输出）。最高档与最低档的差不是百分比而是档位：设计期发现是一次会议上的修改意见；上线后发现是数据修复加事件复盘加用户信任的折损——两者的工时差出数量级，且后者含无法收回的信誉成本。

测试前移的经济账由此成立：**把验证从右档搬到左档，同一个缺陷的发现、定位、修复三个动作全部降价**。04-CI-CD 的门禁设计正是这笔账的落地：快级验证（lint + 单元，秒级档）挂在个人反馈环的 PR 门禁上，让缺陷在最低档被拦下；集成与 E2E 的分钟账由合并门与发布门承担；部署后验证与回滚则是最后一档的止损机制——门禁层数越多、越靠左，到达最高档的缺陷越少。这也是本篇对下游的唯一交付：金字塔不是审美，是成本函数的形状。

### 3. 度量面止于测试：结构质量交给设计

四节的结论收拢：测试是质量的**度量面**——它报告"哪里断了、哪段没验证、发现晚了贵多少"，但它从不改善"断的原因"。断的原因在代码结构里：依赖焊死的结构连替身都插不进去（三.1），可测试性缺陷本身就是结构缺陷的信号；而降低断的概率——让模块各自合格、连接处契约清晰、变更波及面收窄——靠的不是加用例，是接口投影与模式化解耦这些代码结构级的机制。测试能度量的边界，正是设计开始接管的地方：代码结构本身的质量由设计决定，其机制交给 03-设计模式与设计原则。
