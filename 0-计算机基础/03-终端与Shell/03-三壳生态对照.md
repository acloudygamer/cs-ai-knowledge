# 三壳生态对照

## 一、第一次分叉：进程边界上的数据单位

### 1. 三种执行体的边界

三个 Shell 的区别不在语法，而在**执行体是什么**：PowerShell 的命令通常是运行在同一个 .NET 进程里的类，bash 的命令几乎总是另一个进程。这条差别决定了后文全部的数据单位、进程账本与翻译断层。

```text
   用户输入
      │
      ├──► PowerShell 7.6.7 ──► 解析为命令 AST ──► 绑定到 Cmdlet（.NET 类）
      │                                              │ 同一进程内调用
      │                                              ▼
      │                                          对象（.NET 实例）
      │                                              │ 逐对象直接传引用
      │                                              ▼
      │                                          下游 Cmdlet / 格式化器 / 原生命令
      │
      ├──► Git Bash 5.3.15 ──► 解析为 argv ──► MSYS2 运行时翻译 ──► Win32 进程
      │                                           │ 跨进程边界
      │                                           ▼
      │                                       字节流（命名管道/匿名管道）
      │
      └──► WSL GNU Bash 5.2.21 ──► 解析为 argv ──► fork + execve ──► Linux 进程
                                                  │ 跨进程边界
                                                  ▼
                                              字节流（匿名 pipe）
```

三条边的分岔点各不相同。**第一条边**在"命令名 → 执行体"处就分开了：PowerShell 先查命令表，命中 Cmdlet 则同进程调用，未命中才降级为外部程序；因此 `Get-ChildItem` 与 `ls` 在 PowerShell 里是同一条路径（后者是前者的别名），而 `git` 一定是外部进程。**第二条边**的翻译发生在 MSYS2 运行时内部：bash 以为自己在调 `fork`/`execve`，实际落到 `CreateProcess`——这一跳的存在使"bash 脚本在 Windows 上能跑"成立，也使它的进程开销高一个档位。**第三条边**没有翻译层：`fork` 就是内核的 `clone`，`execve` 就是装载 ELF。

| 维度 | PowerShell 7.6.7 | Git Bash 5.3.15 | WSL GNU Bash 5.2.21 |
| --- | --- | --- | --- |
| 内建命令 | Cmdlet（.NET 类，同进程） | bash 内建（同进程） | bash 内建（同进程） |
| 外部命令 | Win32 进程（`CreateProcess`） | Win32 进程（MSYS2 翻译） | Linux 进程（`fork`+`execve`） |
| 管道载荷 | .NET 对象引用 | 字节流 | 字节流 |
| 管道载体 | 进程内队列 / 原生命令间的 OS 管道 | 命名管道 | 匿名 pipe |
| 进程创建开销档 | 毫秒档 | 毫秒档（更高） | 百微秒~毫秒档 |

### 2. 数据单位与可寻址单元

同一次"列目录"在三种壳里产出不同粒度的东西，这不是实现差异，而是**可寻址单元**的定义差异：

```text
   PowerShell：100 个 FileInfo 对象
     ┌────────┬────────┬────────┬─────┐
     │ Name   │ Length │ Mode   │ …   │  ← 每个对象自带 N 个属性
     └────────┴────────┴────────┴─────┘
        │ 下游可直接取 $_.Length（0 次解析、0 次系统调用）
        ▼
   bash：100 行文本，每行约 40 字节
     "rw-r--r-- 1 u u 4096 Oct 25 16:00 a.txt\n"  ← 字段靠空白分隔，无类型
        │ 下游要取大小：awk '{print $5}'（1 个进程 + 1 次字段切分）
        ▼
   字节流：约 4 KB 连续字节，行边界是唯一的内部结构
```

三条边的成本差异是可数的。PowerShell 的每个对象携带全部属性，取任一属性是**内存解引用**（微秒级以下、0 次系统调用）；bash 的每行只携带格式化后的文本，取任一字段必须重新切分（1 个进程，毫秒档）。反过来，字节流的优势是**边界无关**：4 KB 文本可以原样写进文件、经网络发出、被任何语言解析，而 100 个 .NET 对象一旦离开进程就失去意义。

这也解释了"为什么 PowerShell 的输出重定向到文件后会变成文本"：格式化器在管道末端把对象渲染为字符串，可寻址单元从对象退化为行——降级点不在重定向，而在"最后一个消费者是文本设备"这一事实。

### 3. 边界降级点

对象与字节之间只有一个降级点，但它出现的位置决定了整条链的语义：

```text
   对象 ──► 格式化器 ──► 字符串 ──► 编码器 ──► 字节
     │         │            │           │         │
     │         │            │           │         └─ 写入管道/文件/子进程 stdin
     │         │            │           └─ $OutputEncoding 决定每字符字节数
     │         │            └─ 属性被摊平为列，类型信息丢失
     │         └─ 只有被"显示"或"交给原生命令"时才运行
     └─ 在纯 Cmdlet 管道中永不降级
```

三个节点各自丢失一类信息：格式化器丢**类型**（`int` 变 `"42"`），编码器丢**字符集**（不能表示的字符变替换符），管道本身丢**边界**（接收方只能按换行猜结构）。因此"跨壳协作"的可靠性上限由这条链上最弱的一环决定，而这条链只在**离开 PowerShell 进程**时才启动。

一条判据可以提前判断是否会降级：管道中下一个消费者是不是 Cmdlet。是，则保持对象；否（原生命令、文件、控制台），则在边界处一次性降级，且降级不可逆——`Get-Process | ConvertTo-Json` 这类写法之所以存在，就是因为降级一旦发生，唯一的结构恢复手段是让生产者自己先序列化成文本。

## 二、PowerShell 7.6.7 对象管道

### 1. 管道处理器与 `begin`/`process`/`end` 三段

PowerShell 的管道不是"把数据交给下一个程序"，而是"把每个对象依次喂给下一个命令的处理函数"。每个 Cmdlet 被编译成带三个方法的类：

```text
   上游 Cmdlet                     下游 Cmdlet（管道处理器）
   ┌──────────────┐               ┌──────────────────────────────┐
   │ WriteObject  │               │ ① BeginProcessing()   1 次    │
   │   对象 1 ────┼──────────────►│ ② ProcessRecord()     N 次    │
   │   对象 2 ────┼──────────────►│ ③ EndProcessing()     1 次    │
   │   对象 N ────┼──────────────►│                               │
   └──────────────┘               └──────────────────────────────┘
         │                                      │
         └─ 逐对象、流式、无缓冲 ◄───────────────┘ 下游处理完 1 个才返回取下一个
```

三条边的时序是严格交替的，不是批量传递：`WriteObject(对象 1)` 之后控制权立刻转到下游的 `ProcessRecord`，下游处理完才回来取对象 2。这条"拉取式"设计带来两个可观测性质——**内存占用与对象总数无关**（`Get-ChildItem -Recurse` 在百万文件目录上不会先攒齐再输出），以及**上游可以被下游提前终止**（`Select-Object -First 3` 之后上游停止枚举）。

`BeginProcessing` 与 `EndProcessing` 各执行 1 次，负责打开与关闭资源；把资源获取写进 `ProcessRecord` 是 PowerShell 脚本最常见的性能缺陷：N 个对象会打开 N 次连接。

### 2. `ValueFromPipeline` 的两种绑定

参数如何从管道取到值，由两个特性决定，它们的绑定源完全不同：

| 绑定方式 | 绑定源 | 每对象调用次数 | 属性缺失时 | 典型声明 |
| --- | --- | --- | --- | --- |
| `ValueFromPipeline` | 整个对象 | 1 | 仍绑定（对象本身非空） | `[Parameter(ValueFromPipeline)]$InputObject` |
| `ValueFromPipelineByPropertyName` | 同名属性 | 1（该属性存在时） | 不绑定，可能报"参数为空" | `[Parameter(ValueFromPipelineByPropertyName)]$Name` |
| 两者同时声明 | 先按属性、后按整对象 | 1 | 整对象兜底 | 常见于重命名类命令 |
| 无管道特性 | 只能命令行传参 | 0（不参与管道） | — | 普通参数 |

第二行是最容易出错的一格：绑定按**参数名与属性名相同**匹配，属性名不同就静默不绑定，表现为"`Get-Process | Stop-Process -Name xxx` 行为与预期不符"。第四行说明并非所有参数都参与管道，位置参数与管道绑定是两套独立机制——`1..3 | ForEach-Object { $_ }` 中的 `$_` 是自动变量，不属于任何参数绑定。

### 3. 逐对象流的量化账本

以 1000 个整数经过两级 Cmdlet 为例，账本完全确定：

```text
   1..1000 | ForEach-Object { $_ * 2 } | Measure-Object -Sum
     │              │                        │
     │              │                        └─ Begin 1 次、Process 1000 次、End 1 次
     │              └─ Begin 1 次、Process 1000 次、End 1 次（每对象 1 次乘法）
     └─ 生成 1000 个 Int32（值类型装箱为 PSObject 引用）
```

| 计量项 | 数值 | 说明 |
| --- | --- | --- |
| `fork` / `CreateProcess` 次数 | 0 | 全在同一 .NET 进程内 |
| 管道系统调用 | 0 | 进程内队列，不经过内核 |
| 序列化次数 | 0 | 对象按引用传递 |
| `ProcessRecord` 调用 | 1000 | 每对象 1 次 |
| 对象分配 | 1000 个包装对象 | 值类型需装箱为 `PSObject` |
| GC 标记 | 每对象 1 次 | 引用归零后由 GC 回收 |

第一行的 0 是与 bash 最本质的差别：等价操作在 bash 里要 1000 次外部进程（秒档），在此处是纯内存循环（毫秒档）。第四行的 1000 次说明成本与对象数线性相关，且每次调用都有托管调用开销——因此"管道段数少、每段多做事"在 PowerShell 里同样成立，只是代价从进程创建变成了方法调用。

### 4. 版本字段与运行时身份

PowerShell 的版本不是单一数字，而是四个字段的投影，每个字段对应一条不同的行为分叉：

| 字段 | 本仓库取值 | 决定什么 |
| --- | --- | --- |
| `$PSVersionTable.PSVersion` | 7.6.7 | 语言特性与 Cmdlet 参数集合 |
| `$PSVersionTable.PSEdition` | `Core` | 跨平台运行时（.NET）还是 Windows 专属（.NET Framework） |
| `$PSVersionTable.Platform` | `Win32NT` | 路径分隔符与默认编码 |
| `$PSVersionTable.PSCompatibleVersions` | 含 5.1 等 | 脚本可用的降级语法范围 |

四个字段里 `PSEdition` 的权重最高：`Core` 与 `Desktop` 的默认编码、Cmdlet 集合、`$OutputEncoding` 默认值都不同。因此任何"版本相关"的脚本断言都必须至少检查 `PSEdition` 与 `Major` 两项，只比 `PSVersion` 的数字会漏掉 5.1 与 7.x 的真实断层。

## 三、POSIX 字节流与编解码投影

### 1. `|` 只是 fd：行边界与块读写

bash 的管道没有类型系统，`|` 在机制上只做一件事：把左侧进程的 fd 1 与右侧进程的 fd 0 指向同一个内核管道。此后两侧各自按自己的块大小读写，行边界是双方**约定的**，不是内核保证的：

```text
   生产者（写 1 行 40 字节）              消费者（按 8 KiB 块读）
        │                                      │
        │ write(1, "…40B…\n", 40)               │ read(0, buf, 8192)
        ▼                                      ▼
   ┌──────────────────────────────────────────────────────┐
   │ 内核 pipe 缓冲（64 KiB 档，环形）                       │
   │  [40B][40B][40B][40B] …                              │
   │   ▲ 写指针                         读指针 ▲           │
   └──────────────────────────────────────────────────────┘
        │                                      │
        └─ 写入不保证原子（> 4096 字节时）      └─ 一次 read 可能拿到 N 行、
                                                   也可能只拿到半行
```

三条边的语义必须分开记。**写入边**：小于 `PIPE_BUF`（4096 字节）的写是原子的，多个写者不会交错；超过则可能被切开，因此"每行一次 `write`"是安全的，"攒 1 MB 一次写"不是。**缓冲边**：容量固定，写满即阻塞，这把生产者的速度钳制在消费者速度上——`yes | head` 不会无限吃内存，只会让 `yes` 阻塞。**读取边**：`read` 返回的是"当前可用的至多 8192 字节"，与行边界无关；消费者必须自己维护一个残留缓冲区，把最后半行留到下一次拼接。

第三条边是所有文本工具正确性的来源，也是所有"最后一行没有换行"故障的来源：文件末尾若无 `\n`，最后一行仍会被 `read` 返回，但按行处理的工具可能丢弃它——`while read line` 在最后一行无换行时循环不执行最后一次，是这一机制的直接后果。

### 2. 部分写与流控的两个方向

`write` 的返回值可能小于请求长度，这是管道唯一的流控信号，且它在两个方向上对称存在：

```text
   A. 写端被钳制                      B. 读端被拖慢
   消费者慢 → 缓冲满 → write 部分写    消费者停止读 → 缓冲满 → 写端阻塞
   → 生产者循环重试剩余字节            → 生产者睡在写等待队列
   → 无数据丢失，吞吐 = 消费者速度      → 上游整条链被反压
```

两个方向的共同结论是：**管道的吞吐由最慢一段决定，且压力向上游传播**。这解释了 `producer | slow_filter | consumer` 中为什么 `producer` 也会变慢——不是它自己慢，而是它的 `write` 在缓冲满时睡住了。

一个必须区分的边界：`write` 部分写**不等于**错误。返回 `n > 0 && n < len` 是正常流控，调用者必须从 `buf+n` 继续；只有返回 `-1` 且 `errno == EPIPE`（同时收到 `SIGPIPE`）才是读端消失。把部分写当错误处理的程序会表现为"大输出时随机截断"，而把 `EPIPE` 当正常退出的程序会掩盖真实故障。

### 3. 去程：对象 → 文本 → 编码

对象离开 PowerShell 进程时，先被格式化器摊平为文本，再被编码器转成字节。两步各有确定的丢失项：

```text
   FileInfo 对象
     │  ① 格式化器（Format-Table / Out-String / ToString）
     ▼
   "a.txt   4096"      ← 属性变列，类型、嵌套结构、空值语义全部丢失
     │  ② $OutputEncoding（PowerShell 7 默认 UTF-8 无 BOM）
     ▼
   61 2e 74 78 74 20 20 20 34 30 39 36 0a    ← 每个 ASCII 字符 1 字节
     │  ③ 写入子进程 stdin / 文件 / 控制台
     ▼
   原生命令按自己的编码假设解码
```

三条边各有可观测的失败模式。**边①**的丢失是不可逆的：一旦摊平，接收方无法区分"空字符串"与"属性不存在"。**边②**的字节数由编码决定：同一段中文在 UTF-8 下每字符 3 字节、在 GBK 下 2 字节、在 UTF-16LE 下 2 字节且带 BOM——同一份输出在两种编码下的长度差可达 50%。**边③**的失败表现为乱码或替换符：接收方用错误编码解码时，UTF-8 的三字节序列被当成三个 GBK 字节，产生 1~3 个错误字符（每字节一个替换符，最多 3 个）。

### 4. 回程：字节 → 解码 → 行 → 显式对象

反方向的降级更彻底：字节流没有任何机制能自动恢复为对象，必须由脚本显式声明结构：

```text
   子进程 stdout 字节
     │  ① [Console]::OutputEncoding 解码（随宿主代码页，非 $OutputEncoding）
     ▼
   字符串（含换行）
     │  ② 按行切分（PowerShell 把每行作为一个字符串对象送进管道）
     ▼
   1 行 = 1 个 String 对象（不是 1 个结构化对象）
     │  ③ 显式转换：ConvertFrom-Json / ConvertFrom-Csv / -split / 正则
     ▼
   结构化对象（此时才恢复可寻址性）
```

三条边的责任划分决定了排查顺序。**边①**用错编码是乱码的唯一来源，且它用的变量与去程**不是同一个**（`$OutputEncoding` 管写出，`[Console]::OutputEncoding` 管读入），这是最容易配错的一对。**边②**把"一个进程的 N 字节"变成"N 个字符串对象"，行的切分依赖换行字节，因此 Windows 程序输出的 `\r\n` 会在每行末尾留下一个 `\r`——它不是显示问题，而是字符串长度多 1 字节，影响比较与哈希。**边③**是唯一能恢复结构的一步，且必须知道格式（JSON、CSV、固定列宽）；不知道格式时只能靠正则，而正则一旦依赖列位置就与生产者的格式化宽度绑定。

| 编码参数 | 作用方向 | 本仓库默认取值 | 失配症状 |
| --- | --- | --- | --- |
| `$OutputEncoding` | PowerShell → 原生命令 stdin | UTF-8 无 BOM（7.x） | 子进程收到的中文变问号或乱码 |
| `[Console]::OutputEncoding` | 原生命令 stdout → PowerShell | 随宿主代码页 | 中文输出在管道里变替换符 |
| `-Encoding`（文件类 Cmdlet） | 文件读写 | 7.x 为 UTF-8 无 BOM | 用 5.1 打开时中文全乱 |
| 控制台代码页（`chcp`） | 控制台宿主 | 随系统区域设置 | 同一命令在两种终端里输出不同 |

### 5. 版本断崖：5.1 与 7.x 的默认编码差

同一个脚本在 Windows PowerShell 5.1 与 PowerShell 7.6.7 上输出中文，字节序列完全不同，这是三壳对照里最确定的一处断崖：

| 项 | Windows PowerShell 5.1 | PowerShell 7.6.7 |
| --- | --- | --- |
| `$OutputEncoding` 默认 | ASCII 编码器 | UTF-8 无 BOM |
| 非 ASCII 字符去向 | 每个替换为 1 字节 `?` | 原样 3 字节 UTF-8 |
| `-Encoding` 默认（文件） | ANSI 代码页 / UTF-16LE（部分 Cmdlet） | UTF-8 无 BOM |
| 结论 | 中文在管道里被**销毁**（不可逆） | 中文可完整往返 |

第一行的"ASCII 编码器"是关键：它不是"默认用系统代码页"，而是明确的 7 位编码，因此任何非 ASCII 字符在写入子进程 stdin 时被替换为 `?`，接收方再无法恢复——这与"乱码"不同，乱码至少保留了字节，替换是不可逆的信息销毁。跨版本脚本必须在开头显式设置 `$OutputEncoding` 与 `[Console]::OutputEncoding`，不能依赖默认值。

## 四、Git Bash 5.3.15 的 MSYS2 仿真层

### 1. 翻译层的位置与两侧原语

Git Bash 是 bash 5.3.15 编译到 MSYS2 运行时上的产物。bash 本身不做平台适配，所有 POSIX 语义都由中间那层运行时提供：

```text
   ┌───────────────────────────────────────────────────────────┐
   │ bash 5.3.15（未修改的 GNU 源码）                            │
   │   fork() / execve() / pipe() / kill() / open() / chmod()  │
   └──────────────────────────┬────────────────────────────────┘
                              │ 链接到
   ┌──────────────────────────▼────────────────────────────────┐
   │ MSYS2 运行时（msys-2.0.dll）                                │  唯一翻译节点
   │   fork   → CreateProcess + 地址空间复制                     │
   │   execve → CreateProcess（或对 .exe 直接转交）              │
   │   pipe   → 命名管道（CreateNamedPipe）                      │
   │   kill   → 控制台事件 / TerminateProcess                    │
   │   open   → CreateFile（路径与共享模式改写）                  │
   │   chmod  → ACL 附加项或合成 mode                            │
   └──────────────────────────┬────────────────────────────────┘
                              │ Win32 API
   ┌──────────────────────────▼────────────────────────────────┐
   │ Windows 内核（NT 对象管理器、NTFS、控制台子系统）            │
   └───────────────────────────────────────────────────────────┘
```

三层之间的两条边性质不同。**下边**是 Win32 调用，语义由 Windows 定义，MSYS2 只能适配不能改变；**上边**是 POSIX 调用，语义由 MSYS2 用 Win32 原语**模拟**，因此存在"能调通但语义不等价"的灰区。整个 Git Bash 的所有怪现象都落在这个灰区里：脚本不报错，结果与 Linux 不同。

判断一个症状是否来自这一层，有一条硬判据：`strace` 看到的是 POSIX 调用序列，`Process Monitor` 看到的是 Win32 调用序列，两者对不上就是翻译层在改写。

### 2. `fork` 模拟：`CreateProcess` 加地址空间复制

Linux 的 `fork` 靠写时复制，成本与页表规模成正比；MSYS2 没有这个机制，只能"起一个新进程，把父进程的内存搬过去"：

```text
   ① bash 调 fork()
        │
        ▼
   ② 运行时 CreateProcess(同一个 msys-2.0.dll 宿主程序)   ← 1 次进程创建，毫秒档
        │
        ▼
   ③ 父进程把数据段/堆/栈的内容复制给子进程（无写时复制）  ← 与地址空间大小成正比
        │
        ▼
   ④ 子进程从 fork() 的返回点继续执行，返回 0
```

账本与 Linux 的对比是一组档位差：Linux 上 `fork` 复制页表（几十到几百微秒档，与 RSS 弱相关），MSYS2 上复制**全部可写内存**（毫秒档到数十毫秒档，与 RSS 强相关）。因此在 Git Bash 里跑"1000 次外部命令"的循环，墙钟时间比 WSL 里同脚本高一个数量级档，且这个差距随 bash 自身内存占用增长——装了很多函数的 `.bashrc` 会让每次 `fork` 都更贵。

第 ③ 步还带来一个语义后果：`fork` 期间父进程的内存必须保持一致，因此运行时会在复制窗口内暂停其他线程。这让"多线程 + fork"在 MSYS2 上比 Linux 更危险，也解释了为什么 `git` 在 Git Bash 里做并行操作时表现不同于 Linux。

### 3. 路径转换与 argv 改写

路径是跨壳的第一条断层，它发生在**参数传递**而非文件访问处，因此症状常表现为"命令找不到文件"而不是"路径错误"：

```text
   bash 侧看到的路径                  传给 Win32 程序时
   /c/Users/u/a.txt        ──►        C:\Users\u\a.txt
   /tmp/x                  ──►        C:\Users\u\AppData\Local\Temp\x（映射目录）
   /usr/bin/git            ──►        C:\Program Files\Git\usr\bin\git.exe
   //server/share/f        ──►        \\server\share\f（UNC，需保留双斜杠）
```

转换由运行时在 `CreateProcess` 之前扫描 argv 完成，规则是"看起来像 POSIX 绝对路径的字符串"才转换。这条启发式带来三类误伤：以 `/` 开头的**非路径参数**（如 `git log --format=/…`）被误转；正斜杠与反斜杠混用的字符串只转前段；含空格的路径在转换后需要重新加引号，而 argv 已经切分完毕，无法恢复原始边界。逃逸手段是环境变量 `MSYS2_ARG_CONV_EXCL`，它按参数前缀把匹配项排除在转换之外——这是"路径转换"这一层的唯一开关，不是一个可选优化。

一个可核验的判据：同一参数分别传给 `echo`（bash 内建，不转换）与 `cmd /c echo`（Win32 程序，转换），输出不同即证明转换发生在进程边界上，而非 bash 的解析阶段。

### 4. 权限合成与符号链接降级

POSIX 权限模型在 NTFS 上没有对应物，MSYS2 用两种方式合成：

| 操作 | Linux（WSL bash） | Git Bash（MSYS2） | 观测差异 |
| --- | --- | --- | --- |
| `chmod 755 f` | 改写 inode 的 mode 位（1 次系统调用） | 写 1 条附加 ACL 项或仅改运行时视图 | `ls -l` 显示变化，Windows 资源管理器不变 |
| `chmod +x` 后执行 | 内核按 mode 位判定 | 由文件扩展名与运行时规则判定 | 无扩展名的脚本可能仍不可执行 |
| `ln -s a b` | 创建符号链接 inode | 需开发者模式/特权，否则**复制文件** | 改 `a` 不影响 `b` |
| `umask` | 影响新建文件 mode | 影响合成 mode，不影响 ACL 继承 | 新建文件实际权限取决于父目录 ACL |
| `stat -c %a` | 返回真实 mode | 返回合成值 | 与 `icacls` 输出不一致 |

这张表的读法是：前两行是"权限位被降级为视图"，第三行是"链接被降级为复制"。`ln -s` 的降级最危险——脚本里 `ln -s` 成功返回 0，但产物是独立副本，后续对源文件的修改不会反映到链接上，而脚本对此毫无感知。判据是 `readlink` 是否返回非空：真链接返回目标路径，副本返回空。

`git` 对这两种降级的处理值得单独记一句：仓库里记录的 `100644` 与 `100755` 只有 1 位之差，而 Windows 上这一位来自合成 mode，因此"同一仓库在 Git Bash 与 WSL 里 `git status` 结果不同"是权限断层与换行断层的叠加，不是仓库损坏。

## 五、版本三元组与 5.3.15 / 5.2.21 差异对照

### 1. 四组版本字段的投影

三壳的版本不是一个数字，而是四组字段。每组字段对应一条独立的实现分支，必须分别取：

| 壳/平台 | 探测表达式 | 本仓库预期值 | 该字段决定什么 |
| --- | --- | --- | --- |
| PowerShell | `$PSVersionTable.PSVersion` | 7.6.7 | Cmdlet 参数与语言特性 |
| PowerShell | `$PSVersionTable.PSEdition` | `Core` | 默认编码与跨平台 API 集合 |
| Git Bash | `$BASH_VERSION` | `5.3.15(1)-release` | bash 语言级行为 |
| Git Bash | `$BASH_VERSINFO[0]` `[1]` | 5 与 3 | 特性开关的可用上限 |
| WSL bash | `$BASH_VERSION` | `5.2.21(1)-release` | bash 语言级行为 |
| WSL bash | `$BASH_VERSINFO[0]` `[1]` | 5 与 2 | 特性开关的可用上限 |
| WSL 平台 | `uname -r` | `6.18.54.1-microsoft-standard-WSL2` | 内核行为与 `/proc` 内容 |
| WSL 平台 | `wsl.exe --version` | 3.0.3 | 9P 与 interop 的实现版本 |

八行里最容易混淆的是 `$BASH_VERSION` 与 `$BASH_VERSINFO` 的关系：前者是给人看的字符串，后者是给脚本判定的数组，且两者的第 1、2 段必须一致。判定的正确写法是读数组而不是解析字符串——字符串包含打包信息（`(1)-release`），解析它会引入与语言版本无关的噪声。

### 2. 差异集的三分结构

两个 bash 之间的差异不是"全部不同"，而是三层包含关系，只有最外层才是不兼容项：

```text
   ┌─────────────────────────────────────────────────────────┐
   │ 层 3：5.3 相对 5.2 的新增与变更（仅 Git Bash 有）          │  ← 唯一的不兼容源
   ├─────────────────────────────────────────────────────────┤
   │ 层 2：5.2 引入的特性（两版都有，WSL 5.2.21 也支持）        │  ← 不必判定
   ├─────────────────────────────────────────────────────────┤
   │ 层 1：5.0/4.x 以来的稳定语义（两版一致）                   │  ← 不必判定
   └─────────────────────────────────────────────────────────┘
   ┌─────────────────────────────────────────────────────────┐
   │ 层 4：与版本无关的运行时差异（MSYS2 仿真 vs Linux 内核）    │  ← 由第四章承担
   └─────────────────────────────────────────────────────────┘
```

三层包含关系决定了判定策略：脚本的兼容性下限由**层 3** 决定，而层 4 的差异与版本号无关——把 MSYS2 的行为差异误记为"版本差异"是最常见的归因错误，因为升级 bash 并不能消除它。

| 探测项 | 5.3.15 预期 | 5.2.21 预期 | 不满足时的结论 |
| --- | --- | --- | --- |
| `BASH_VERSINFO[0]` | 5 | 5 | 不是 bash 5.x，脚本应立即退出 |
| `BASH_VERSINFO[1]` | 3 | 2 | 版本主次号与预期不符，停止使用层 3 特性 |
| 5.2 引入的选项（如 `globskipdots`） | 存在 | 存在 | 两版都应通过；失败说明是更老的 bash |
| 5.3 引入的选项与内建 | 存在 | 不存在 | 在 WSL 上必须走降级分支 |
| 5.3 的行为变更项 | 新行为 | 旧行为 | 同一脚本两侧结果不同，需显式分叉 |
| `${var@op}` 支持的操作符集合 | 超集 | 子集 | 使用前必须探测单个操作符 |
| `printf` 的格式扩展 | 超集 | 子集 | 用 `printf '%s'` 兜底 |
| 数组/关联数组语义 | 一致 | 一致 | 差异不来自版本，查层 4 |
| 模式匹配与 `shopt` 默认值 | 可能不同 | 可能不同 | 每条断言都显式设置，不依赖默认 |
| `fork` 单次成本档 | 毫秒档以上 | 百微秒档 | 差异来自层 4（MSYS2），非版本 |
| 路径分隔符与 `/` 语义 | 转换 | 原生 | 差异来自层 4，非版本 |
| 信号可捕获性 | 部分不可捕获 | 全部可捕获 | 差异来自层 4，非版本 |

十二行的读法是"前七行判版本，后五行判平台"。把它们混在一张表里而不是分成两张，是因为排查时看到的就是一个失败现象，必须先判断它属于版本还是平台——两者的修复动作完全不同：版本问题降级语法，平台问题改调用方式。

### 3. 判定协议：脚本入口的三行判定

把上表压缩成脚本入口处的三条判定，代价是 3 次内建调用、0 次进程创建：

```text
   ① 取 $BASH_VERSINFO[0] 与 [1]  → 低于下限则退出（退出码非 0）
   ② 探测单个 5.3 特性（shopt -q 或 [[ -o ]]）→ 决定是否走降级分支
   ③ 探测平台特征（路径分隔符 / fork 成本）→ 决定路径与进程策略
```

三条判定的顺序不可交换：①决定"能不能跑"，②决定"走哪条实现"，③决定"用哪种写法"。把 ③ 放在 ① 之前，会在不支持的 bash 上先因语法错误崩溃，拿不到可读的失败原因。

一条实测判据：在 Git Bash 与 WSL 里各执行一次 `echo "${BASH_VERSINFO[*]}"`，输出首两项分别应为 `5 3` 与 `5 2`——这是本仓库所有"版本相关"断言的锚点，也是唯一不需要外部工具的判定。

## 六、五条翻译断层的总账

### 1. 断层表：产生点、吸收者与残余代价

跨壳调用的失真只发生在五个通道上，每个通道都有确定的产生点与残余代价。这张表是本篇的收敛点，前五章的机制在此各出现一次：

| 通道 | 产生于哪一跳 | 由谁吸收 | 残余代价（可量化） |
| --- | --- | --- | --- |
| 路径 | argv 交给 Win32 程序前 | MSYS2 运行时的启发式转换 | 每条命令行 ≥1 次转换；含空格路径多 2 个引号字节；`/` 开头的非路径参数被误转 1 处 |
| 换行 | 文本写入文件或管道时 | 文本模式转换 / 工具自身 | 每个 `\n` 多 1 字节（10 万行 +100 KB）；解释器遇 `\r` 报 1 处语法错误 |
| 权限 | `chmod`/`stat` 与 NTFS 之间 | 合成 mode 或附加 ACL | `100644` 与 `100755` 的 1 位信息丢失；`ln -s` 退化为 1 次文件复制 |
| 编码 | 跨进程边界读写字节时 | `$OutputEncoding` 与 `[Console]::OutputEncoding` | 1 个中文字符 3 字节对 2 字节；5.1 下每字符替换为 1 字节 `?`（不可逆） |
| 信号 | POSIX 信号落到 Win32 进程时 | 控制台事件或 `TerminateProcess` | 1 次 `SIGTERM` 退化为不可捕获的终止；`SIGUSR1` 无对应物（0 次投递） |

五行的共同结构是"一侧有信息、另一侧无对应物"。路径与换行是**表示差异**（同一语义两种字节形态），权限与信号是**能力差异**（对侧根本没有该概念），编码是**表示与能力叠加**。因此修复手段分两类：表示差异靠转换（`wslpath`、`dos2unix`），能力差异只能靠**放弃该语义**或**换一条通道**（用文件代替信号、用 ACL 代替 mode）。

### 2. 叠加规则与排查顺序

断层不独立，它们按固定顺序叠加，排查时必须按同一顺序剥离：

```text
   症状：git status 显示所有文件被修改
        │
        ├─ ① 先查换行：文件是否被写成 CRLF（每个 \n 多 1 字节）
        │       └─ 是 → 设置 autocrlf 或 .gitattributes，症状消失
        ├─ ② 再查权限：mode 是否从 100644 变 100755（1 位差异）
        │       └─ 是 → 设置 core.fileMode=false
        └─ ③ 最后查编码：文件名是否以不同编码存储（3 字节 vs 2 字节）
                └─ 是 → 统一 UTF-8，重建索引
```

顺序不可颠倒，因为三者都会表现为"内容变了"，但只有 ① 影响字节数、② 只影响 1 个属性位、③ 影响文件名的字节序列。先查 ③ 会得到"文件名看起来一样"的假阴性。

一条收敛断言：**跨壳协作的可靠性 = 1 − 未吸收断层数 / 5**，而每吸收一条断层的成本是确定的——路径 1 次转换、换行 1 字节/行、权限 1 位、编码 1 字节/字符、信号 1 次不可捕获。把这五个数写进脚本的入口注释，比写"注意跨平台兼容"有用得多。
