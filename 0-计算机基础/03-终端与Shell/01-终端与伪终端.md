# 终端与伪终端

## 一、从电传打字机到设备节点：TTY 三层栈

### 1. 速率常数与字符集：110 bit/s 留下的 termios 形状

电传打字机 ASR-33 的线路速率是 110 bit/s，每字符按 1 起始位 + 7 数据位 + 1 校验位 + 1 停止位共 10 位传输，折算 11 字符/秒。这条速率把三个结构决定钉进了今天的终端子系统：字符必须**成行缓存**后再交付（每秒 11 个字符的到达率下，逐字符唤醒读者的调度开销与打字速度同量级）；控制字符必须与数据字符**共用同一条 7 位通道**，因而只能在字节层分流，无法占用独立信号线；速率本身必须作为可枚举常量写进设备属性，即使物理线早已不存在。

| 形态 | 线路速率 | 单字符位数 | 内核交付单元 | 控制字符通道 |
| --- | --- | --- | --- | --- |
| ASR-33 电传机 | 110 bit/s（11 字符/秒） | 10 | 1 个字符（无缓冲） | 独立机械键（无软件语义） |
| 串口终端（VT100） | 300 ~ 38400 bit/s | 10 | 1 行（canonical） | 行规程按 `c_cc[]` 匹配 |
| 伪终端（PTY） | 无物理上限，`c_cflag` 速率位被忽略 | 8（纯字节） | 1 行（canonical）或 1 字节（raw） | 同上，仍是 `c_cc[]` 匹配 |

`termios` 结构里 `c_cflag` 仍保留 `B9600`、`B38400` 这类以波特为单位的常量，PTY 驱动对它们的处理是**存下但不使用**：Linux 的 pty 在 `TCGETS` 时回报固定值，与真实吞吐无关。这条"字段存在但语义为空"的残留，是后文所有"配置看起来生效、实际由别的机制决定"现象的源头。

### 2. 三层栈的节点职能：驱动层、行规程、核心

终端子系统不是一个字符设备，而是三层可替换结构叠起来的一条流水线。三层的分工必须严格区分，否则后面所有字节计数都会算错：

```text
        用户进程（bash / powershell / 任意读终端的程序）
          │  fd 0 / fd 1 / fd 2
          ▼
 ┌──────────────────────────────────────────────────────────┐
 │  tty 核心（tty_struct）                                    │  纯转发
 │    · 持有 ldisc 指针、读队列 read_buf、等待队列 read_wait   │
 │    · 持有前台进程组 pgrp、会话 session、窗口尺寸 winsize    │
 ├──────────────────────────────────────────────────────────┤
 │  行规程（line discipline，n_tty）                           │  唯一参与解析
 │    · receive_buf()：逐字节状态机（编辑、回显、信号、流控）    │
 │    · write()：把用户写出的字节交给驱动                       │
 │    · ioctl()：termios 读写、TIOCSPGRP、TIOCGWINSZ           │
 ├──────────────────────────────────────────────────────────┤
 │  驱动层（tty_driver：pty / serial / virtual console）       │  纯转发
 │    · 把字节塞进对端 flip buffer，或从硬件 FIFO 取字节        │
 └──────────────────────────────────────────────────────────┘
          │
          ▼  硬件 FIFO（串口）／对端 master fd（PTY）
```

三条边逐一对应真实动作。**最下一条边**是驱动层的 `ops->write()`：串口场景把字节写进 UART 发送 FIFO 并等待移位寄存器空，PTY 场景把字节直接压入对端（master 侧）的 flip buffer，不经过任何硬件。**中间一条边**是 `tty_ldisc_receive_buf()`：驱动把收到的字节整块交给行规程，行规程是整条链上唯一会**改变字节数量与顺序**的节点——它可能吞掉一个字节（`VINTR`）、可能回写一个字节（`ECHO`）、可能把一个字节改写成另一个（`ICRNL` 把 `\r` 改写成 `\n`）。**最上一条边**是读队列与 `read_wait`：行规程把处理完的字节放进 `read_buf`，满足交付条件后唤醒等待队列，`read()` 从 `read_buf` 拷贝到用户缓冲区。

三层之间的边界是"谁有权改字节"的边界：核心与驱动只搬运与计数，行规程才解析。这条边界决定了两件事——作业控制只能通过核心的 `ioctl` 完成（行规程无权改 `pgrp`），信号只能由行规程产生（核心不知道哪个字节是 `Ctrl-C`）。

### 3. 一个字节的五跳：从设备中断到 `read()` 返回

以串口终端上敲一个字母 `a` 为例，追踪它在内核内的完整路径与每一次字节拷贝：

```text
 ① UART 收到 1 字节，置中断
        │
        ▼
 ② 串口驱动 ISR → tty_flip_buffer_push()        ← 拷贝 1：硬件 FIFO → flip buffer
        │
        ▼
 ③ tty_ldisc_receive_buf() → n_tty_receive_buf() ← 逐字节状态机（本字节为普通字符）
        │                                           · ICANON：追加进 read_buf
        │                                           · ECHO：反向写回 1 字节
        ▼
 ④ read_buf 达到交付条件（遇到 \n）→ wake_up_interruptible(read_wait)
        │
        ▼
 ⑤ 进程 read() 从 read_buf 拷到用户缓冲区        ← 拷贝 2：read_buf → 用户空间
```

五跳中真正消耗时间的只有两处：第 ③ 跳的逐字节状态机（每字节一次分支判定，按字节线性累加），第 ④ 跳的唤醒（进程从睡眠转为可运行，微秒到数十微秒档，取决于调度器是否正好在该 CPU 上）。第 ② 跳与第 ⑤ 跳各一次字节拷贝，因此**一个字节从设备到用户空间恰好两次拷贝**；若 `ECHO` 置位，回程再走一次 `ops->write()`，总拷贝数变为三次。

交付条件由行规程模式决定，这是后文所有"为什么 `read()` 没有立刻返回"问题的根：canonical 模式下 `read_buf` 必须出现换行字节（或达到 4096 字节上限、或收到 `VEOF`），`read()` 才被唤醒；raw 模式下唤醒条件是"至少 `VMIN` 个字节到达"或"`VTIME` 计时到期"。

## 二、PTY 对偶：master/slave 与两跳字节复制

### 1. 对偶拓扑与一次 `openpty()` 的系统调用账本

伪终端不是一台设备，而是**一对**互相咬合的端点：master 端由终端模拟器持有，slave 端表现得像一台真实终端，交给 Shell 及其子进程。两端之间没有硬件，只有内核里的一段字节搬运代码，但两端语义完全不对称——master 是"控制者接口"，slave 是"被控制者接口"。

```text
   终端模拟器 / sshd / tmux                      Shell 及其子进程
        │  fd_master                                   │  fd_slave (0,1,2)
        ▼                                              ▼
 ┌───────────────┐   ① write(master)  ┌───────────────────────────┐
 │  pty master   │───────────────────►│  行规程 n_tty（slave 侧）  │
 │  （对端 flip   │                    │  · 编辑 / 回显 / 信号分流  │
 │   buffer 的    │◄───────────────────│  · read_buf 攒行           │
 │   另一端）     │   ④ 回显 / 输出     └─────────────┬─────────────┘
 └───────────────┘                                  │ ② 满足交付条件
        ▲                                           ▼
        │                                  ③ read(slave) 取走 1 行
        └──── ⑤ slave 写出的数据经同一条行规程反向到达 master 读队列
```

一次 `openpty()` 在 Linux 上展开为固定的一串系统调用，账本可数：`open("/dev/ptmx")` 取 master fd（1 次）；`ioctl(TIOCGPTN)` 取从端编号 $N$（1 次）；`ioctl(TIOCSPTLCK)` 写入 0 解锁从端（1 次，此前从端不可打开）；`open("/dev/pts/N")` 取 slave fd（1 次）。合计 **4 次系统调用、2 个 inode、1 对主次设备号**。少了 `TIOCSPTLCK` 那一步，`open("/dev/pts/N")` 返回 `EIO`——这是"从端存在但拒绝服务"的唯一原因。

`TIOCGPTN` 与 `TIOCSPTLCK` 是安全边界的载体：编号可猜，但未解锁的从端不响应任何打开请求，因此一个进程无法凭编号劫持别人的终端会话。

### 2. 一次按键的字节账本

canonical 模式 + `ECHO` 置位是交互式 Shell 的默认配置。此时敲一个 `a` 再敲回车，内核侧账本如下：

| 阶段 | 系统调用 | 字节数 | 唤醒次数 | 数据落点 |
| --- | --- | --- | --- | --- |
| 终端把 `a` 写进 master | `write(fd_master)` 1 次 | 1 | 0 | master 对端 flip buffer |
| 行规程处理 `a` | 无（内核内调用） | +1 入队 | 0（未遇换行） | slave 侧 `read_buf` |
| 行规程回显 `a` | 无（内核内调用） | 1 回写 | 0 | master 读队列 |
| 终端读回显 | `read(fd_master)` 1 次 | 1 | 0 | 终端渲染 |
| 敲回车 `\n` | `write(fd_master)` 1 次 | 1 | 0 | 追加进 `read_buf` |
| 达到交付条件 | 无 | 0 | 1 次 `read_wait` | 可被 `read()` 取走 |
| Shell 读一行 | `read(fd_slave)` 1 次 | 2（`a` + `\n`） | — | 用户缓冲区 |

结论是一句可排序的断言：**canonical + echo 下，一次两字符输入产生 3 次用户态系统调用、2 次内核字节拷贝、2 次回显字节搬运、1 次唤醒**。同样输入在 raw 模式下，`read()` 在第一个字节到达时立即返回，系统调用次数变成 2（两次 `read`）、唤醒次数变成 2，而回显责任整体移交给用户态程序（终端模拟器自己画字符）。系统调用次数与唤醒次数的这次翻倍，正是 raw 模式（编辑器、TUI、`ssh` 交互）必须自己实现行编辑的原因。

### 3. 关闭语义：EOF、挂断信号与孤儿从端

对偶结构的生命周期由两端谁先关闭决定，两个方向的后果不对称：

```text
  A. master 先关（终端窗口被关掉）
     close(fd_master)
        ├─► slave 侧：read() 返回 -1/EIO（Linux 实测；POSIX 允许退化为 0 字节 EOF）
        ├─► 前台进程组：收到 1 次 SIGHUP（默认动作 = 终止）
        └─► 组内每个进程各 1 次投递，非 1 次广播合并

  B. slave 全部关闭（Shell 退出，无子进程持有 fd）
     close(fd_slave) × N
        └─► master 侧：read() 返回 -1/EIO，终端模拟器据此销毁窗口
```

A 路径的关键是 `SIGHUP` 的投递对象为**前台进程组**而非单个进程：一个 `bash` 加它当前的 `vim` 各收一次，共 2 次投递，且除"忽略"外无法拦截——`nohup` 的全部作用就是把该信号的处理动作改为忽略并把输出改道到文件。B 路径说明 master 端读到 `EIO` 不是错误而是**会话终止的显式信令**，终端模拟器靠它区分"程序崩溃"与"会话正常结束"。

从端数量决定挂断时机：只要有一个子进程还持着 slave fd（例如 `sleep 100 &` 未重定向），Shell 退出也不会触发 B 路径，master 端继续可读——这是"关闭窗口后后台进程仍在跑、输出无处可去"的结构原因。

## 三、行规程：`termios` 标志位的分流投影

### 1. `c_lflag` 位段与四条分流通道

行规程的全部行为由 `struct termios` 的四个字段决定：`c_iflag`（输入转换）、`c_oflag`（输出转换）、`c_cflag`（线路参数）、`c_lflag`（本地模式）。真正决定"字节走哪条路"的是 `c_lflag` 位段，每一位对应一条确定的分流通道：

| 位 | 置位后的动作 | 清位后的行为 | 影响的字节数 |
| --- | --- | --- | --- |
| `ICANON`（规范模式标志） | 攒满一行才交付；启用 `VERASE`/`VKILL`/`VEOF` 编辑键 | 按 `VMIN`（最小接收字节数）/`VTIME`（字符间超时，单位 0.1 s）交付，编辑键退化为普通字节 | 每次 `read` 从 1 到 4095 |
| `ECHO` | 每个输入字节反向写回 1 字节 | 不回写（密码输入靠清此位） | 等于输入字节数 |
| `ISIG`（信号产生标志） | 匹配 `VINTR`/`VQUIT`/`VSUSP` 时产生信号，**字节不入队** | 控制字符当普通数据入队 | 该字节 0 入队 |
| `IEXTEN` | 启用 `VLNEXT`（`Ctrl-V`）转义下一个字符 | 无字面量转义通道 | 被转义的 1 字节 |
| `ECHOE` | `VERASE` 回显为 `\b \b` 三字节 | 只删缓冲不回显 | 3 字节/次退格 |
| `ECHOK` | `VKILL` 回显为换行 | 静默清行 | 1 字节/次清行 |

这张表的读法是"置位位决定一条边是否存在"。`ICANON` 最重：它同时开启行缓冲、编辑键与"最多返回一行"的交付契约。`ISIG` 决定控制字符是否被**消耗**——置位时 `Ctrl-C` 一个字节都不进 `read_buf`，清位时它作为 `0x03` 原样进入数据流，这正是 `vim` 里 `Ctrl-V Ctrl-C` 能插入字面量的原因。

### 2. canonical 与 raw 的交付契约：返回字节数的真值矩阵

`read()` 返回多少字节，由 `ICANON` 与 `VMIN`/`VTIME` 两个变量组合决定。三种典型配置列全：

| `ICANON` | `VMIN` / `VTIME` | `read()` 返回条件 | 单次返回字节数 | 典型使用者 |
| --- | --- | --- | --- | --- |
| 置位 | 被忽略 | 遇 `\n`，或 `read_buf` 达 4096，或 `VEOF` | 1 ~ 4095 加换行 | bash、`cat`、`read` |
| 清位 | `VMIN=1`，`VTIME=0` | 至少 1 字节到达 | 恰好 1（每按键一次系统调用） | `vi`、`tmux`、`ssh` |
| 清位 | `VMIN=0`，`VTIME=n` | 计时 $n \times 0.1$ 秒到期或字节到达 | 0 ~ 请求长度（可返回 0） | 超时轮询型程序 |

第三行是唯一允许 `read()` 返回 0 的配置，也是唯一让"返回 0"不代表 EOF 的配置——终端编程里最容易被误判为文件结束的一处：`read()==0` 在 `VMIN=0` 下只是"超时无数据"，而 canonical 模式下 `VEOF`（`Ctrl-D`）产生的 0 才是真正的流结束语义。两种 0 在系统调用返回值上完全同形，只能靠 `termios` 配置区分。

canonical 模式的 4095 字节上限来自 `read_buf` 的 4096 字节容量：一行超过 4095 字节时，行规程在缓冲填满时提前交付一个**不含换行**的片段，超长行被拆成多次 `read` 返回——这是"粘贴超长单行导致命令被截断执行"的结构原因。

### 3. `ISIG` 与 `IXON`：不进入数据队列的两条旁路

行规程对每个输入字节先做一次"是否属于旁路"的判定，判定失败才进入数据队列。三条旁路的走向完全不同：

```text
                   1 字节进入 n_tty_receive_buf()
                              │
                    ┌─────────┴──────────┐
                    ▼                    ▼
        ① 命中 c_cc[] 中某个控制字符？    ② 否 → 普通数据路径
                    │                    │
        ┌───────────┼──────────┐         ├─ ICRNL 置位且为 \r → 改写为 \n
        ▼           ▼          ▼         ├─ IUCLC 置位且为大写 → 改写为小写
   命中 VINTR   命中 VSUSP  命中 VSTOP    └─ 追加进 read_buf（ECHO 则回写 1 字节）
        │           │          │
        ▼           ▼          ▼
   SIGINT 投递  SIGTSTP 投递  IXON 流控：
   字节丢弃     字节丢弃      挂起输出，字节丢弃
```

三条旁路的共同点是**字节数归零**：`Ctrl-C` 在 `ISIG` 置位下进入内核后不产生任何可读数据，只产生一次 `kill_pgrp(前台进程组, SIGINT)`。因此"程序为什么收不到 `Ctrl-C` 这个字符"的答案永远是 `ISIG` 把它吃掉了，而不是程序读得不够快。

`IXON` 是唯一一条**影响输出方向**的输入旁路：`Ctrl-S` 不产生信号，而是让行规程把后续输出挂起在 `ops->write()` 之前，`Ctrl-Q` 再恢复。它必须放在行规程而不是应用层，理由是它要在应用已经写满管道、卡在 `write()` 里时仍然生效——此时应用没有机会执行任何代码，只有内核里的行规程能拦住输出。

`IEXTEN` 提供的 `VLNEXT`（`Ctrl-V`）是三条旁路的**逃生口**：它让下一个字节绕过所有旁路判定直接入队，`Ctrl-V Ctrl-C` 因此得到 1 个 `0x03` 数据字节而非信号。这条边的存在，使"控制字符不可输入"成为一个可被局部推翻的约定。

## 四、作业控制：会话、进程组与 `TIOCSPGRP`

### 1. 三个句柄：控制终端、会话、前台进程组

作业控制不是 Shell 的功能，而是内核在 tty 核心上维护的三个句柄之间的对应关系。Shell 只是这三个句柄的操作者：

```text
   ┌───────────────────────────────────────────────────────────────┐
   │ 会话（session）                                                │
   │   首进程 = 会话首进程（session leader），持有 sid               │
   │   ┌─────────────────────────────────────────────────────────┐ │
   │   │ 控制终端（controlling terminal）：1 个 tty_struct          │ │
   │   │   tty->ctrl.session ──► 本会话                            │ │
   │   │   tty->ctrl.pgrp    ──► 前台进程组（唯一可变的那一格）      │ │
   │   └─────────────────────────────────────────────────────────┘ │
   │        ▲ 归属由 ioctl(TIOCSCTTY) 建立，或首次 open 时自动认领    │
   │   ┌────┴──────────┬──────────────────┬──────────────────────┐  │
   │   ▼               ▼                  ▼                      │  │
   │ 进程组 A        进程组 B           进程组 C                  │  │
   │ (前台)          (后台)             (后台)                    │  │
   │ pgid = pgrp     pgid ≠ pgrp        pgid ≠ pgrp               │  │
   └───────────────────────────────────────────────────────────────┘
```

三条边各有一个可观测的建立方式。**会话 → 控制终端**由 `ioctl(TIOCSCTTY)` 建立（`open` 时未带 `O_NOCTTY` 且会话尚无控制终端则自动认领）；这是"一个会话只能有一个控制终端"的强制点，第二次调用返回 `EPERM`。**控制终端 → 前台进程组**那一格是整张图里唯一被 `TIOCSPGRP` 改写的字段，也是作业控制的全部状态所在——`ps` 输出里的 `TPGID` 列就是这一格。**会话 → 各进程组**由 `setpgid` 建立，同一会话内的进程组共享该会话的控制终端，但没有前台身份，因而它们的终端读写会被行规程拦下（见下节）。

一个进程能否改写这一格，由内核做两条检查：调用者所在会话必须拥有该 tty（否则 `ENOTTY`），目标进程组必须属于同一会话（否则 `EPERM`）。因此"把别人的终端抢过来做前台"在结构上不可行，`sudo` 也无法绕开——它只能新开会话并另认控制终端。

### 2. 状态机：`SIGTTIN`、`SIGTTOU` 与 `SIGCONT` 三条边

后台进程组对控制终端的每一次访问，都要经过一次"我是不是前台"的判定。判定失败时不返回错误码，而是投递信号——这是理解"后台任务为什么卡住"的唯一入口：

```text
                    后台进程组访问控制终端
                              │
              ┌───────────────┴────────────────┐
              ▼                                ▼
        ① 读操作 read()                  ② 写操作 write()
              │                                │
              ▼                                ▼
     pgrp ≠ 前台进程组？              TOSTOP 置位 且 pgrp ≠ 前台？
              │ 是                             │ 是
              ▼                                ▼
     投递 SIGTTIN（默认停止）          投递 SIGTTOU（默认停止）
              │                                │
              ▼                                ▼
     进程进入 TASK_STOPPED ──────────► Shell 的 waitpid 收到 WIFSTOPPED
              │                                │
              └────────────┬───────────────────┘
                           ▼
              Shell 执行 tcsetpgrp(0, shell_pgid) 取回前台
                           ▼
              fg：tcsetpgrp(0, job_pgid) + kill(-job_pgid, SIGCONT)
```

图中三条边的语义必须分清。**`SIGTTIN` 边**：读被拦，字节一个都不交付，进程停止。**`SIGTTOU` 边**：写只在 `TOSTOP` 置位时被拦（默认关闭，所以后台 `echo > /dev/tty` 通常能成功——这是最常见的"以为会被拦住却没有"）；但 `tcsetattr` 这类改终端属性的调用**无条件**触发 `SIGTTOU`，因为它会破坏前台程序的显示状态。**`SIGCONT` 边**：恢复不是自动的，必须由 Shell 显式投递，且投递前要先把前台权属改回该进程组，否则被恢复的进程立刻又踩到自己不是前台的判定上。

一个例外必须记下：若进程组是**孤儿组**（组内所有进程的父进程要么已退出、要么在别的会话里），内核对后台读不再投 `SIGTTIN` 而是直接返回 `EIO`——给一个永远不会被 `SIGCONT` 唤醒的组发停止信号等于让它永久挂死，所以内核选择让调用失败而不是挂起。

### 3. `Ctrl-Z` → `fg` 的完整往返：系统调用与终端状态账本

把一次挂起与恢复的全过程按系统调用展开，可以看清 Shell 在作业控制上真正的开销不在信号，而在终端状态的保存与恢复：

```text
 $ sleep 100          ← 按下 Ctrl-Z
 [1]+  Stopped   sleep 100
 $ ps -o pid,pgid,tpgid,stat -p $$
```

`ps` 的 `TPGID` 列显示当前前台进程组：`Ctrl-Z` 之后该值回到 Shell 自己的 `pgid`，`STAT` 列里的 `T` 出现在被停止的作业上。这条命令在内核侧发生了什么：`ps` 只读 `/proc/<pid>/stat` 的第 5、6、8 三个字段，不触碰控制终端，因此它自己无论在前台后台都能成功——它是观察那一格而不改变它的最小工具。

一次 `Ctrl-Z` 到 `fg` 的完整账本：

| 步骤 | 动作 | 系统调用/事件 | 次数 |
| --- | --- | --- | --- |
| 1 | 行规程匹配 `VSUSP`，投递停止信号 | `kill_pgrp(pgrp, SIGTSTP)` | 1 |
| 2 | `sleep` 进入 `TASK_STOPPED`，`waitpid` 返回 | 调度器状态迁移 | 1 |
| 3 | Shell 保存该作业的 `termios`（防 `vim` 留在 raw 模式） | `tcgetattr` | 1 |
| 4 | Shell 取回前台权属 | `tcsetpgrp`（内部 `TIOCSPGRP`） | 1 |
| 5 | Shell 打印作业号，回到提示符 | `write` | 1 |
| 6 | 用户 `fg`：恢复该作业的 `termios` | `tcsetattr` | 1 |
| 7 | 交前台 | `tcsetpgrp` | 1 |
| 8 | 恢复执行 | `kill(-pgid, SIGCONT)` | 1 |

合计 **4 次终端 `ioctl`、2 次信号投递、1 次作业状态查询**。第 3 与第 6 步是容易被忽略的一半：没有这一对保存/恢复，一个在 raw 模式下被挂起的 `vim` 会让 Shell 提示符也处于 raw 模式（回车不回显、`Ctrl-C` 不产生信号），表现为"退出编辑器后终端坏掉"。作业控制的完整职责因此是"前台权属 + 终端模式"两份状态，而不是一份。

## 五、转义序列与终端能力协商

### 1. ECMA-48 的字节投影：`ESC [ 参数 中间 终止`

终端不是"显示字符的屏幕"，而是"解释字节流的解析器"。屏幕上的颜色、光标位置、清屏，全部由夹在数据流里的控制序列驱动；这些序列的语法由 ECMA-48 固定，逐字节可切分：

```text
 字节位置:   第 1 字节   第 2 字节    第 3..n 字节      第 n+1 字节
           ┌──────────┬──────────┬──────────────────┬────────────┐
 控制序列:  │  0x1B    │ 0x5B '[' │  参数字节 0x30-3F │ 终止 0x40-7E│
           │  ESC     │  CSI     │  中间字节 0x20-2F │            │
           └──────────┴──────────┴──────────────────┴────────────┘
                │           │              │                │
                ▼           ▼              ▼                ▼
            引导符      进入 CSI      "多少/哪个"         "做什么"
            (1 字节)    (1 字节)      (0~n 字节)         (1 字节)

 实例:  ESC [ 3 1 m          → SGR，前景红        共 5 字节
        ESC [ 3 8 ; 5 ; 1 9 6 m → 256 色索引 196  共 11 字节
        ESC [ 3 8 ; 2 ; 2 5 5 ; 0 ; 0 m → 真彩   共 15 字节
        ESC [ ? 1 0 4 9 h     → 切备用屏           共 8 字节
```

四条边的职能区分清楚：引导符 `0x1B` 只负责"下一个字节不是数据"，`0x5B` 把序列归入 CSI 族（光标、编辑、模式设置都在这一族），参数字节是十进制数字与 `;`（子参数分隔）与 `?`（私有模式前缀），终止字节决定动作类别（`m` 属性、`H` 定位、`h`/`l` 模式开关、`J` 擦除）。

这条投影的直接后果是**功能密度与字节成本的换算**：一个 80×24 屏幕整屏重绘，若每个单元格用一条独立 SGR 序列着色，最坏情况 1920 条 × 5 字节 ≈ 9.6 KB，而有状态的颜色（只在色变处发序列）通常只需数百条。终端程序的所有"性能优化"实际上都是在减少这条字节通道上的序列条数——这就是为什么 TUI 库要维护"当前已设置的颜色"这一小份状态。

### 2. 从 `$TERM` 到 terminfo：能力查询而非全表载入

`$TERM` 不携带序列本身，它只是一个**数据库主键**。程序拿到 `xterm-256color` 后，去 terminfo 数据库取该条目的能力表，再按需取用：

```text
   环境变量 $TERM = "xterm-256color"
        │
        ▼
   terminfo 数据库条目（二进制编译格式，头部约 20 字节 + 能力表 + 字符串表）
        │  · 布尔能力：am（自动换行）、hs（状态行）…
        │  · 数值能力：cols、lines、colors…
        │  · 字符串能力：cup（光标定位）、sgr0（复位）、smcup（进备用屏）…
        ▼
   程序按能力名查询 ──► 拿到具体字节序列 ──► 写入 stdout
        │
        └─ 未命中该能力 → 退化为硬编码默认值或放弃该特性（不报错）
```

逐步遍历：`$TERM` 为空或为 `dumb` 时，所有非必需能力查询全部落空，程序退化到"只用换行与回车"的输出模式（1 个变量决定整条能力链是否存在）；查询命中 `cup` 则拿到类似 `ESC[%i%d;%dH` 的模板，参数按行列填入；查询 `smcup` 命中才切备用屏，退出时用 `rmcup` 恢复——两个能力必须成对使用，否则退出后原屏内容被覆盖（备用屏被销毁而不是恢复）。未命中任何能力时程序不会得到错误码，而是得到"无此能力"的空结果，这正是"同一个程序在不同终端里少几个功能"的机制。

能力查询的成本是每进程一次条目装载（数 KB 级读取），而非每次输出一次查询——能力表在进程启动时解析进内存，此后是纯内存查表，微秒级以下。

### 3. 窗口尺寸与 `SIGWINCH`：`TIOCGWINSZ` 的 8 字节

窗口尺寸不属于行规程，而属于 tty 核心的 `winsize` 字段。它的更新通路是"终端算出来、内核只存、程序被通知"：

```text
   用户拖拽窗口
        │
        ▼
   终端模拟器算出新行列 → ioctl(TIOCSWINSZ) 写入 tty 核心的 winsize
        │                                   （struct winsize = 4 × unsigned short = 8 字节）
        ▼
   内核向该 tty 的前台进程组投递 SIGWINCH
        │
        ▼
   程序信号处理器 → ioctl(TIOCGWINSZ) 读回 8 字节 → 重排界面
```

这条链上没有任何"尺寸变化本身"的数据随信号传递：`SIGWINCH` 是纯通知，尺寸必须由程序自己再 `ioctl` 取回。这解释了三个常见现象：信号处理器里不能直接安全地调 `ioctl`（异步信号安全限制），所以通行做法是置一个标志位、回到主循环再查；窗口连续拖拽会产生多次 `SIGWINCH`（每帧一次，数十次），程序必须做去抖；`winsize` 的像素字段 `ws_xpixel`/`ws_ypixel` 常被填 0，依赖它做图像缩放的程序在多数终端上得不到有效值。

8 字节的尺寸结构还解释了另一件事：行列上限各 65535，超出即回绕。把终端调到极端宽（例如 `resize` 到 100000 列）在结构上不可表达，程序只会看到回绕后的值。

## 六、ConPTY（Console Pseudo Terminal，控制台伪终端）：Windows 的第三跳

### 1. 屏幕缓冲区传统与 ConPTY 的字节化改造

Windows 的控制台从来不是字节流设备。传统模型里 `conhost.exe` 维护一块**屏幕缓冲区**（`CHAR_INFO` 单元格数组，每格一个字符加一组属性位），程序通过 `WriteConsoleOutput` 之类的 API 直接写单元格，光标位置、颜色、清屏都是对这块缓冲区的结构化操作。这条路径上没有"字节流"这个概念，因此 ANSI 序列在原生控制台里长期无效。

ConPTY（Windows 10 1809 起）做的事是在这块屏幕缓冲区外面**套一层字节化外壳**：

```text
   终端宿主（Windows Terminal / VS Code / 任意 GUI）
        │  ① write 字节（VT 序列 + 文本）
        ▼
   ┌──────────────────────────────────────────────┐
   │ 伪控制台（HPCON，由 CreatePseudoConsole 创建） │
   │   ├─ 输入方向：字节 → VT 解析 → 输入记录       │
   │   └─ 输出方向：单元格变更 → 序列化为 VT 字节   │
   ├──────────────────────────────────────────────┤
   │ conhost.exe（1 个独立进程，屏幕缓冲区持有者）   │
   └──────────────────────────────────────────────┘
        │  ② 单元格（CHAR_INFO，非字节）
        ▼
   目标进程（powershell.exe / cmd.exe / 任意控制台程序）
        │  ③ WriteConsole 系列 API
        └─ 输出方向反向：单元格 → 序列化 → 字节 → 宿主
```

三条边与 Linux PTY 的对应关系是本节的判据。**边①**等价于 Linux 的 `write(master)`，但字节必须先被 conhost 的 VT 解析器翻译成输入记录（按键、鼠标、粘贴事件），再由控制台 API 分发给目标进程——目标进程拿到的是**事件**，不是字节。**边②**是 Linux PTY 里不存在的一跳：目标进程的输出进入 conhost 的屏幕缓冲区，成为单元格；只有"脏"单元格才在边③被重新序列化为 VT 字节发给宿主，因此整屏重绘的实际字节数取决于变更行数而非屏幕面积。**边③**等价于 Linux 的 `read(master)`，但宿主读到的是 conhost 重新生成的序列，而不是目标进程原样写出的字节。

这条结构决定了 ConPTY 下"程序写什么"与"终端看到什么"之间必然存在一次**解析再生成**，任何在解析器里不被支持的能力（自定义序列、私有扩展）都会在这一跳丢失，而在 Linux PTY 上它们只是原样透传的字节。

### 2. 双向翻译的拷贝账本与延迟档位

把同一次输出在两条路径上的拷贝次数对齐，差异就成了一组可数的量：

| 计量项 | Linux PTY | ConPTY |
| --- | --- | --- |
| 额外进程数 | 0（纯内核结构） | 1（conhost.exe） |
| 用户态/内核态边界跳数 | 2（`write` 进、`read` 出） | ≥4（宿主→conhost→目标→conhost→宿主） |
| 每次输出的字节拷贝 | 2 | ≥4（其中 2 次跨进程） |
| 首字节可见延迟档 | 百微秒档 | 毫秒档 |
| 大块输出吞吐 | 基准 | 低 1 个数量级档 |
| 控制字符 `Ctrl-C` 的落点 | 行规程 `ISIG` → `kill_pgrp(SIGINT)` | 目标进程组收到 `CTRL_C_EVENT`（`GenerateConsoleCtrlEvent`） |
| 窗口尺寸通知 | `SIGWINCH` + `TIOCGWINSZ` 8 字节 | `ResizePseudoConsole` + 控制台尺寸事件 |
| 会话终止 | master 关闭 → slave `EIO` + `SIGHUP` | `ClosePseudoConsole` → 目标进程收到控制台关闭事件 |

拷贝账本的读法是：Linux 的两次拷贝都在内核态内完成（flip buffer → `read_buf`，`read_buf` → 用户缓冲区），没有一次跨地址空间切换；ConPTY 的 ≥4 次里有 2 次是**跨进程**的（宿主 ↔ conhost），每次都要经过一次管道读写与一次上下文切换，这是"毫秒档 vs 百微秒档"的全部来源。

最后一行的差异最容易被误读为"功能相同"：`Ctrl-C` 在两条路径上都表现为"程序被打断"，但机制完全不同。Linux 上那个 `0x03` 字节由行规程消费、转成信号，程序永远读不到它；ConPTY 上字节被解析成输入记录后由 conhost 调用 `GenerateConsoleCtrlEvent`，目标进程收到的是控制台控制事件，只有在其未注册处理器时才退化为终止。因此把 `Ctrl-C` 的字节写进一个不读输入的 Windows 控制台程序，行为与 Linux 不同——前者仍可能被终止，后者若 `ISIG` 被关则完全无事发生。

### 3. 失效模式：第三跳带来的两类故障

多一跳进程带来两类 Linux PTY 上不存在的失效，必须能被识别，否则会被误判为程序缺陷。

```text
  故障 A：conhost 崩溃
     宿主 ── 管道 EOF ──► 读到 0 字节，会话立即结束
     目标进程 ──► 收到控制台关闭事件，通常直接终止（无机会清理）

  故障 B：宿主退出但 conhost 存活
     宿主进程消失 → conhost 侧管道写失败 → 目标进程仍持有"控制台"
     → 子进程继续运行但输出无处可去，形成孤儿控制台
```

A 路径的特征是"整屏输出突然截断且退出码异常"，B 路径的特征是"窗口关了但进程还在，`tasklist` 里能看到"。两者的共同根因是控制台的所有权被拆给了**两个**进程（宿主与 conhost），任何一方消失都留下半条通道；而 Linux PTY 的所有权在内核的 `tty_struct` 上，只有关闭 fd 才能终止，不存在"半个终端"的中间态。

这也解释了为什么在 ConPTY 下做"终端复用"（`tmux` 类工具）必须由宿主侧实现：复用所需的是"多个视图共享一个控制台"，而控制台在 Windows 上是一个进程持有的对象，不是内核里一个可被任意 fd 指向的结构。
