# WSL与跨平台环境

## 一、WSL 3.0.3 的架构定位：真内核轻量 VM 与 9P 文件桥

### 1.1 宿主与 VM 两侧：一条边界、三条通道

```text
宿主 Windows（NT 内核）                          轻量 VM（真实 Linux 内核）
┌──────────────────────────────┐            ┌────────────────────────────────┐
│ wsl.exe ──► wslservice       │            │ /sbin/init（PID 1）             │
│              │               │            │   └─ 发行版用户态：bash、gcc    │
│              ├─ 9P 服务 ◄────┼─ 通道 A ───┼──► 9P 客户端 → VFS → /mnt/c    │
│              │   └─ NTFS     │ (hvsocket) │                                │
│              ├─ virtio 后端 ◄┼─ 通道 B ───┼──► virtio-blk → /dev/sdX       │
│              │               │ (共享环)    │    virtio-net → eth0           │
│              └─ interop 代理 ◄┼─ 通道 C ───┼──◄ binfmt_misc：WSLInterop     │
│                  └─ CreateProcess          │                                │
└──────────────────────────────┘            └────────────────────────────────┘
```

图被一条虚拟化边界切成两栏：左栏是 NT 内核上的入口 `wsl.exe` 与常驻服务 `wslservice`，右栏是一个 Hyper-V 托管的轻量 VM，其中运行未经改写的上游 Linux 内核，1 号进程为 `/sbin/init`，其下才是发行版用户态。边界上的连接被收敛为三条通道，本篇此后每一次"跨平台开销"都可归因到其中一条。

通道 A（9P 文件桥）是唯一承载路径语义的通道。VM 内 9P 客户端把 VFS 请求编码为 9P 报文，经 Hyper-V socket（`AF_VSOCK`）送达宿主 9P 服务，再由后者落到 NTFS；一次请求-应答即一次往返，往返次数是 `/mnt/c` 全部性能断崖的唯一自变量。该挂载点由 `/init` 在引导期写入 `mount` 表，`mount` 输出中呈现为 `C:\ on /mnt/c type 9p`。

通道 B（virtio 设备）是纯数据面：块设备呈现为 `/dev/sdX`，网卡呈现为 `eth0`，另有一只气球设备向宿主归还空闲页。它不解析路径、不理解文件语义，只搬运按页对齐的字节，因此不产生元数据往返。

通道 C（interop）是进程创建通道：`binfmt_misc` 中的 `WSLInterop` 条目承接 ELF 解释器不匹配而 PE 头匹配的可执行文件，请求被转交宿主 `CreateProcess`，标准输入输出经字节管道回传；一次调用只落成 1 个宿主进程，与 9P 无关。

### 1.2 翻译层与真内核：两个维度定分野

| 维度 | WSL1（系统调用翻译层） | WSL2 起（真内核轻量 VM） |
| --- | --- | --- |
| `getpid()` 的跨界次数 | 0 次 VM 退出，1 次翻译 | 0 次，纯本地系统调用 |
| `open("/mnt/c/…")` 的路径 | pico 提供者内改写为 NT 调用 | VFS → 9P 客户端 → 1 次往返 |
| `/proc` 真实性 | 翻译层合成，字段不全 | 内核原生 procfs，与上游一致 |
| 可加载模块 / eBPF | 0 个模块，eBPF 不可用 | 模块可加载，eBPF、netfilter 可用 |
| 内存占用档 | 与宿主进程同档，数十 MB | VM 常驻底噪数百 MB |
| 文件语义 | 单一命名空间，无 9P 税 | `/mnt/c` 有 9P 税，VM 内 ext4 无 |

分野不是版本号，而是系统调用要不要跨过那条边界。第一个维度看路径长度：WSL1 下 `getpid()` 由 pico 提供者在同一 NT 内核内翻译，1 次翻译、0 次 VM 退出；WSL2 下它退化为本内核中的一次函数调用，0 次翻译、0 次退出，百纳秒档。第二个维度看 `/proc` 真实性：翻译层只能合成字段，真内核直接输出 procfs，`/proc/self/maps` 与宿主进程地址空间 0 重叠。

两个维度各自派生一个量级断言：可加载模块由 0 变正数，eBPF 从不可用变为可用；内存占用则从与宿主进程同档抬到 VM 常驻数百 MB 档——这是为"真内核"支付的固定物理税，也是容器共享内核路线不必付的一笔。`wsl.exe --version` 报 3.0.3，`uname -r` 报 `6.18.54.1-microsoft-standard-WSL2`，后缀即上表右列的判据。

### 1.3 边界定价：0 次、1 次与数万次

| 操作 | 跨边界次数 | 典型耗时档 | 页缓存可否吸收 |
| --- | --- | --- | --- |
| `getpid()`，VM 内 | 0 | 数百纳秒 | — |
| `stat`，VM 内 ext4 | 0 | 数十微秒 | 命中时更低 |
| `stat`，`/mnt/c` | 1 次 9P 往返 | 数百微秒 | 否，元数据不缓存 |
| `open` + 4 KB `read`，`/mnt/c` | 2 次往返 | 数百微秒 ~ 毫秒 | 后续读可吸收 |
| `git status`，万级文件 | 数万次往返 | 秒级 | 否 |
| `wslpath -u` | 0 | 数十微秒 | — |

0 次档是 VM 内的一切本地系统调用，成本由内核自身决定，与边界无关。1 次档是 `/mnt/c` 的单个元数据操作：往返一次数百微秒，同操作在 ext4 上数十微秒，两者相差正好一个数量级档，比值即 9P 的固定协议税。

数万次档是放大器的落点。元数据密集型负载把每个文件的 `stat`、`open`、`readdir` 逐个变成往返，累计墙钟 $T$ 由 $T \approx N \cdot t_{9p}$ 给出，其中 $N$ 为元数据往返次数、 $t_{9p}$ 取数百微秒档；同一负载在 VM 内 ext4 上只有 $N$ 次本地系统调用。万级文件的 `git status` 因此从数十毫秒档抬到秒级，慢 1~2 个数量级。此外 `inotify` 在 9P 上投递 0 个事件，文件监视退化为轮询，又给墙钟加一层与轮询周期成正比的固定开销。

路径转换开销另成一档：`wslpath -w` 与 `-u` 是纯用户态字符串变换，0 次文件系统访问、数十微秒、随路径长度线性，两个方向的改写次数对称故成本同档。它不查盘，因此不受 9P 影响——这正好解释了"转换一条路径"便宜而"访问转换后的路径"昂贵的分工：前者改写字节，后者跨边界取元数据。三条通道、三个档位由此闭合：通道 A 定价元数据，通道 B 定价字节吞吐，通道 C 定价进程创建。

## 二、启动链：`wsl.exe` → 轻量 VM → init → 登录 Shell

### 2.1 冷热两条路径与一个汇合点

```text
wsl.exe -d Ubuntu
  │
  ├─[VM 不存在 · 冷]──────────────────────────────────────────┐
  │   wslservice → HCS 申请 utility VM              数百毫秒档 │
  │     └─ 引导内核（/proc/version 带 microsoft-standard-WSL2）│
  │        └─ /init：挂 9P、设 hostname、起 interop 监听       │
  │           └─ exec /sbin/init → PID 1                      │
  │                                                           │
  ├─[VM 已存在 · 热]──────────────────────────────────────────┤
  │   复用保活 VM                                    十毫秒档 │
  │                                                           │
  └──────────────────────┬────────────────────────────────────┘
                         ▼ 汇合：一次进程创建请求
                宿主 CreateProcess（1 次）
                         │
                         ▼
                VM 内 fork + exec（1 次）→ 登录 Shell
                         │
                  ┌──────┴───────┐
                  ▼              ▼
            登录形态          -e 形态
        /etc/profile     直接 exec argv
        → ~/.profile     （0 次读取 profile）
        （1 次读取）
```

图的左半是两条互斥入口：VM 不存在时，`wslservice` 先向 Hyper-V 的主机计算服务申请一个 utility VM，再让内核引导，最后由 `/init` 完成挂载 9P、设置 hostname、建立 interop 监听三件事，然后把 1 号进程位置让给 `/sbin/init`。VM 已存在时整段跳过，只剩右半的进程创建。

右半的汇合点是一次进程创建请求，被拆成宿主侧 `CreateProcess` 与 VM 内 `fork + exec` 各 1 次独立的进程创建。此后分叉：登录形态按 `/etc/profile` → `~/.profile` 顺序读一遍，`-e` 形态直接以 argv 执行，profile 读取 0 次。

### 2.2 三形态的进程创建账本

| 形态 | VM 创建 | 宿主进程创建 | VM 内进程创建 | 典型耗时档 | `/etc/profile` 读取 | pty 分配 |
| --- | --- | --- | --- | --- | --- | --- |
| 冷启动登录 | 1 | 1 | 1 | 数百毫秒 | 1 | 1 |
| 热启动登录 | 0 | 1 | 1 | 十毫秒 | 1 | 1 |
| 热启动 `-e` | 0 | 1 | 1 | 十毫秒 | 0 | stdin 为 TTY 时 1 |
| 冷启动 `-e` | 1 | 1 | 1 | 数百毫秒 | 0 | stdin 为 TTY 时 1 |

四行里有三列恒为 1：进程创建次数不随形态变化，变的只有 VM 创建与 profile 读取两项。这决定了比较只能落在两个量级上——冷与热差 1~2 个数量级档，登录与 `-e` 差的是 profile 那一次读取及随之而来的一整份环境变量拷贝，属毫秒与数十微秒的差。

于是"第一次慢、之后快"不是缓存预热，而是 §2.1 冷路径那几百毫秒被保活窗口摊掉了。`vmIdleTimeout` 默认 60 秒，到期回收 VM；`wsl.exe --shutdown` 立即回收，下一次调用回到冷档。判据因此可写死：两次调用间隔小于保活窗口则落在十毫秒档，跨过窗口或执行过 `--shutdown` 则回数百毫秒档。

表外还有一种形态会把冷档再抬一级：`/etc/wsl.conf` 的 `[boot] systemd=true` 令 `/sbin/init` 变成 systemd，冷路径在 1 号进程之后多出一串 unit 拉起（默认目标串行启动十余个 unit），数百毫秒因此抬到秒档。它只改冷档：unit 仅在 VM 首次引导时启动，热路径仍是十毫秒档，账本里那三列恒为 1 的进程创建计数也不变——单位置换了，模型没换。

### 2.3 三个档位的来源

数百毫秒档由三段构成：utility VM 创建占大头，内核引导次之，`/init` 挂载 9P 与建立 interop 监听再占一小段。这一段与命令本身无关，`wsl.exe -e true` 与 `wsl.exe -e make -j8` 的冷启动开销同档。

十毫秒档只有三项：两次进程创建、一次 hvsocket 握手（数十微秒）、`WSLENV` 列出的变量按字节 marshal 过界（每个变量一次字符串拷贝，未列出的 0 字节过界）。命令本身若只做一次 `getpid()`，其成本被淹没在这十毫秒里。

毫秒档属于 profile 读取：`/etc/profile` 加 `/etc/profile.d/` 下数十个片段，逐个 `stat` 加 `read`，在 VM 内 ext4 上每次数十微秒，累计到数毫秒。这一段正是登录形态与 `-e` 形态的分界，也把"脚本入口环境假设"落到具体字节——登录形态的 `PATH` 含 profile 追加项，`-e` 形态不含。

## 三、`/mnt/c` 的 9P 文件桥：一次 `open` 的跨 VM 往返

### 3.1 一次冷 open 的七个 Stop

```text
open("/mnt/c/proj/a.txt")
   │
   ▼ Stop 1  VFS：按 "/" 切段，dentry 未命中
   ├─ Twalk  proj        ─┐  报文头 = size[4] type[1] tag[2]
   ├─ Twalk  a.txt        │  消息体 = fid / offset / count
   ├─ Tlopen O_RDONLY     │  每个路径段 1 次 walk
   ├─ Tread  4 KB        ─┘
   ▼ Stop 2  9P 客户端：marshal → 发送队列（1 次 kick）
   ▼ Stop 3  hvsocket：整包拷入宿主共享环
   ▼ Stop 4  宿主 wslservice：unmarshal → NTFS CreateFile / ReadFile
   ▼ Stop 5  回包分支：Tread 数据 ｜ Rerror（ENOENT、EPERM）
   ▼ Stop 6  hvsocket 接收队列（1 次唤醒）→ 数据入页缓存
   ▼ Stop 7  VFS 交回用户态：read() 返回 4096
```

Stop 1 决定报文数：路径有 $d$ 段且缓存全冷，则 walk 报文 $d$ 条，加 `Tlopen` 与 `Tread`，共 $d + 2$ 条报文，每条报文各自构成一次往返。`proj/a.txt` 的 $d$ 为 2，故一次冷 `open` 加 `read` 是 4 次往返。

Stop 3 与 Stop 6 是两次独立的队列操作，中间隔着一次宿主唤醒：这正是单次往返落在数百微秒而非数十微秒的直接原因——本地系统调用不换地址空间，这里要换两次。Stop 4 是全程唯一真正触碰存储的点，其余 Stop 都是编解码与搬运。Stop 5 的失败分支把宿主 NT 错误码映射为 1 个负 errno，路径不存在时用户态看到 `ENOENT`，权限拒绝时看到 `EPERM`，两者都消耗了完整的往返。

### 3.2 往返次数账本

| 操作 | 报文数 | 往返次数 | 延迟档 | 页缓存可否吸收 |
| --- | --- | --- | --- | --- |
| `stat`（`Tgetattr`） | 1 | 1 | 数百微秒 | 否 |
| `open`，深度 3，全冷 | 5 | 5 | 1~2 毫秒 | — |
| `open`，dentry 命中 | 1 | 1 | 数百微秒 | — |
| `read` 4 KB，首读 | 1 | 1 | 数百微秒 | 是，后续 0 往返 |
| `read` 4 KB，再读 | 0 | 0 | 数十微秒 | 是 |
| `readdir`，1 万条目 | $\lceil N / B \rceil$ | 同左 | 数十毫秒 | 否 |
| `write` 4 KB + `fsync` | 2 | 2 | 毫秒档 | 写可吸收，`fsync` 不可 |

表的读法是一条乘法：单次元数据往返数百微秒，`stat` 一万次即数秒，`open` 一万次（深度 3）即十秒档。`readdir` 的批量 $B$ 是单条 `Tread` 能装下的目录项数，条目数 $N$ 越过 $B$ 后每多一批就多一次往返，故大目录的墙钟与 $N$ 成正比而与字节数无关——目录越大越慢，慢在往返次数上。

有一条不改往返次数的外生抬升：宿主实时扫描在 `CreateFile` 处插入一次文件检查，把单次往返从数百微秒抬到毫秒档，倍数随扫描策略变化，但账本里的往返次数一格不动。诊断时这两类开销必须分开记，否则会把杀软误判为 9P 退化。

账本还漏了一项与文件数而非字节数绑定的固定成本：每个被打开的文件在 `close` 时补一条 `Tclunk`，又是 1 次往返。于是单文件生命周期的最少往返是 2（`Tlopen` 与 `Tclunk`），与读写多少字节无关——遍历十万个空文件因此比读一个 10 MB 文件更慢，慢在十万次 Tclunk 上。

大块读也不是零成本：单条 `Tread` 受 msize 上限约束，顺序读 $N$ 字节需 $\lceil N / M \rceil$ 条报文， $M$ 取 msize。msize 在兆字节档时读 1 GB 是千次量级往返，相对 ext4 的 0 次仍是一个量级的税，但每往返搬运的字节数大，摊到每 GB 的墙钟只差 1~2 倍——这正是 §1.3 中大块顺序读写只放大 1~2 倍的结构原因，与元数据负载的 5~20 倍分属两条曲线。

### 3.3 语义折价三项

| 语义项 | NTFS 原生形态 | `/mnt/c` 上的 9P 呈现 | 退化后果 |
| --- | --- | --- | --- |
| 权限位 | ACL + 属性 | 无 metadata 时 mode 恒 0777，uid/gid 全为挂载属主 | 可执行位恒真，`chmod` 0 生效 |
| 变更通知 | USN 日志 / `ReadDirectoryChangesW` | 9P 无事件通道，`inotify` 投递 0 个事件 | 监视退化为轮询，检出延迟 0 至 1 个周期 |
| 共享映射 | 页缓存一致 | `MAP_SHARED` 写回不参与 9P 缓存协议 | 跨进程可见要等 `msync` 或 `close` |
| 符号链接 | reparse point | 按 `symlinkroot` 前缀做字符串映射 | 相对链接跨域后指向漂移 |

第一项可在 `/etc/wsl.conf` 的 `[automount]` 段开 `options = "metadata"` 修正：开启后 9P 把 uid/gid/mode 存进 NTFS 扩展属性，权限位恢复可写，代价是每次元数据操作多读一段扩展属性——往返次数不变，单次载荷变大，属低频代价。

第二项是结构缺口而非配置项：9P 协议没有 event 通道，`inotify` 在内核侧注册成功、在 9P 侧 0 个事件投递，于是所有依赖 `inotify` 的工具（文件同步、热重载、测试 watcher）退化为按固定周期 `stat` 全树，把一个 0 事件通道换成每秒数百次往返。

三项折价合起来给 `/mnt/c` 定了性：它是交换区语义——可读、可写、权限与通知不可信，因此构建缓存、版本库工作树、依赖安装目录都不该落在其上；VM 内 ext4 付出 0 次跨界往返，只付出一次磁盘 I/O。

## 四、转换税核算：元数据密集操作的放大倍数

### 4.1 三个量：单次往返、调用数、本地基线

```text
             ┌──────────── 同一份负载 ────────────┐
             ▼                                    ▼
   /mnt/c 路径                                  ext4 路径
   N 次系统调用                                N 次系统调用
        │                                            │
        ├─ 每次 1 次 9P 往返（数百微秒档）            ├─ 每次本地系统调用（数十微秒档）
        │                                            │
        └─► T_9p = N·t_9p + T_loc                    └─► T_loc_total = N·t_loc + T_loc
                        │                                        │
                        └──────────► M = T_9p / T_loc_total ◄────┘
```

图里只有三个自变量：单次往返 $t_{9p}$、单次本地调用 $t_{loc}$、负载的系统调用数 $N$。 $T_{loc}$ 是与路径无关的固定开销（解释器启动、进程创建、纯计算），两条路径都要付，因此它在分子分母里同时出现，只稀释倍数、不改变方向。

### 4.2 联立式与单调性

```math
\begin{aligned}
T_{9p} &= N \cdot t_{9p} + T_{loc} \\
T_{ext4} &= N \cdot t_{loc} + T_{loc} \\
M &= \frac{T_{9p}}{T_{ext4}} = \frac{N \cdot t_{9p} + T_{loc}}{N \cdot t_{loc} + T_{loc}} \\
r &= \frac{t_{9p}}{t_{loc}}, \quad M \approx r \ \ (N \cdot t_{loc} \gg T_{loc}) \\
\frac{\partial M}{\partial N} &> 0, \quad \frac{\partial M}{\partial r} > 0
\end{aligned}
```

前两式是两条路径的墙钟，第三式是放大倍数，第四式给出上界：当固定开销被系统调用数淹没时， $M$ 收敛到往返比 $r$。按 §1.3 的档位取 $t_{9p}$ 数百微秒、 $t_{loc}$ 数十微秒， $r$ 落在 10 附近，即一个数量级档。第五式是两个偏导的符号： $M$ 随 $N$ 与 $r$ 同向上升，故"慢多少倍"不是常数，而是负载形状的函数。

### 4.3 三类负载的落点

| 负载 | 系统调用数 $N$ | 9P 往返次数 | 往返累计 | 放大倍数档 |
| --- | --- | --- | --- | --- |
| `git status`，1 万文件 | 3 万次量级 | 3 万次量级 | 10 秒档 | 5~20 倍 |
| 依赖安装，2 万文件创建 | 10 万次量级 | 10 万次量级 | 30 秒档 | 10~20 倍 |
| `dd` 顺序 1 GB | 千次量级 | 千次量级 | 秒档 | 1~2 倍 |

表与式对得上：`git status` 的 $N$ 大而单次载荷小， $M$ 逼近 $r$ 的上界；`dd` 的 $N$ 被 msize 摊薄，每往返搬运兆字节档， $N \cdot t_{loc}$ 与 $T_{loc}$ 同档， $M$ 被压到 1~2 倍。两端之间是连续的，中间档由"每次系统调用携带的字节数"决定。

把 $M$ 的变量换成人手可估的量更实用：记负载的元数据强度为每次系统调用携带的字节数 $v$，则 $M$ 随 $v$ 单调下降。 $v$ 在数十字节档（源码树的目录遍历、版本库索引比对）落在高倍区， $v$ 在兆字节档（镜像、归档）落在低倍区。这就是一条判据而非形容词——先估 $v$，再决定目录放哪边。

## 五、`wslpath` 与路径三域投影：Windows / Linux / WSL UNC

### 5.1 三域与两条投影边

```text
        ┌────────────── 宿主 Windows 命名空间 ──────────────┐
        │  C:\proj\a.txt          \\wsl.localhost\Ubuntu\…  │
        └────┬──────────────────────────────────┬───────────┘
   -u 投影   │                                  │   -u 投影
             ▼                                  ▼
        ┌────────────── VM 内 Linux 命名空间 ───────────────┐
        │  /mnt/c/proj/a.txt            /home/u/a.txt       │
        └───────────────────────────────────────────────────┘
   -w 投影：反向逐段拼回，盘符前缀 或 UNC 前缀 二选一
```

三个命名空间之间只有两条边，且两条边都是纯字符串变换：`-u` 把盘符降为小写并前置 `/mnt/`，`-w` 反向拼回 `C:` 加反斜杠；UNC 域则把 `\\wsl.localhost\<发行版>\` 前缀整体替换为 `/`。图中两侧的斜线不是数据流而是同一个 inode 的两种写法，故转换过程 0 次文件系统访问。

关键的同价事实在图外：`/mnt/c/...` 与 `\\wsl.localhost\Ubuntu\...` 各自落到两个不同的 9P 挂载点，一次 `stat` 都要跨一次 VM 边界，往返次数与延迟同档。于是"从 Windows 侧访问 Linux 文件"并不比反向便宜，方向不构成成本差异。

### 5.2 五种输入形态的投影结果

| 输入形态 | `wslpath -w` 输出 | `wslpath -u` 输出 | 转换规则 |
| --- | --- | --- | --- |
| `C:\proj\a.txt` | 原样 | `/mnt/c/proj/a.txt` | 盘符降小写、`\` 换 `/`、前置 `/mnt/` |
| `C:/proj/a.txt` | `C:\proj\a.txt` | `/mnt/c/proj/a.txt` | 正斜杠先归一为反斜杠 |
| `/mnt/c/proj/a.txt` | `C:\proj\a.txt` | 原样 | 识别 `/mnt/<单字母>` 前缀 |
| `/home/u/a.txt` | `\\wsl.localhost\Ubuntu\home\u\a.txt` | 原样 | 非 `/mnt/` 前缀走 UNC 形态 |
| `\\wsl.localhost\Ubuntu\home\u\a.txt` | 原样 | `/home/u/a.txt` | 剥 UNC 前缀与发行版名 |

五种输入的耗时同档：都是 1 次进程启动加 1 次字符串改写，数十微秒量级，其中进程启动占大头，改写本身在微秒以下。差异只在规则分支数：上表第三、四行要判别前缀归属，分支数 1；第五行要剥离三段前缀（`\\`、主机名、发行版名），分支数 3，仍在同一档内。

### 5.3 转换的边界条件

含空格路径是唯一会改字节数的情形：`C:\Program Files\x` 转成 `/mnt/c/Program Files/x` 后，若被拼进未加引号的命令行，会被下游再切一次词，于是多 1 处引号或转义差异，与路径转换本身无关。同理，尾随反斜杠在 `-u` 时被归一为单个 `/`，`C:\` 转成 `/mnt/c` 而非 `/mnt/c/`。

大小写不归一是另一条边界：`-u` 只把盘符字母降为小写，路径其余部分原样保留，因此 `C:\Proj` 与 `c:\proj` 转出两个不同字符串却指向同一目录——NTFS 在宿主侧大小写不敏感，Linux 侧按字节比较。判据因此是：转换负责形态，不负责等价类；需要比较路径时先归一大小写，不能指望 `wslpath` 代劳。

相对路径是第三条边界：`wslpath` 收到不带前缀的字符串时按当前工作目录解析，`-a` 才强制输出绝对形态。这一步仍然 0 次文件系统访问——它拼接的是 `getcwd` 已知的字节，而不是去查盘。于是"转换便宜"的前提被钉死在这里：转换器只做字符串代数，任何需要判存在性的判断（软链指向、挂载点归属）都不在它的职责内，得由调用方另做一次 `stat`，而那一次就回到 9P 的账本上了。

## 六、interop：`WSLInterop` 与 PE 进程的跨边界启动

### 6.1 Linux 侧 execve 一个 `.exe` 的五个 Stop

```text
execve("/mnt/c/Windows/System32/cmd.exe")
   │
   ▼ Stop 1  binfmt_misc：ELF 解释器不匹配 → 回落 WSLInterop 条目
   ├─ 读前 2 字节 = "MZ" ── 否 ──► 返回 ENOEXEC（1 个负 errno，边界 0 次穿越）
   ▼ Stop 2  内核 interop：argv、cwd、环境变量序列化，经 hvsocket 送宿主
   ▼ Stop 3  宿主 wslservice → CreateProcess（1 个 NT 进程，十毫秒档）
   ▼ Stop 4  管道：stdout/stderr 以 64 KB 缓冲回灌 VM，每 64 KB 一轮
   ▼ Stop 5  退出码：NT 32 位状态 & 0xFF → Linux 8 位状态
```

Stop 1 是唯一在 VM 内完成的判定，代价是一次读文件头 2 字节；不匹配时整个调用在边界前终止，用户态收到 `ENOEXEC`，跨界次数为 0。Stop 2 把参数与环境变量压成一段字节流，这一步与 `WSLENV` 白名单同时发生：未列名的变量在此被丢弃，过界字节数为 0。

Stop 3 是这条链上唯一一次宿主进程创建，落在十毫秒档，与一次热启动同档——两者都是"1 次跨边界进程创建加 1 次通道握手"。Stop 4 的管道按 64 KB 分轮，1 MB 输出即 16 轮读写；因为写端在宿主、读端在 VM，每轮都带一次唤醒，大输出程序的墙钟因此与输出字节数成正比而与小段延迟无关。

参数在这一跳上有一个硬上限：整条命令行压成一段字符串交给宿主 `CreateProcess`，上限 32 KB 档，超出部分在边界处被截断而无错误返回。于是批量传参（`xargs` 展开的上千个文件名）必须分批，单批控制在数十 KB 以内，否则截断发生在最后一个参数中间，表现为目标程序报"文件不存在"而非参数错误。

### 6.2 两个方向的对照

| 方向 | 启动方式 | 跨边界进程创建 | 交互式 tty | 环境变量过界 | 退出码映射 |
| --- | --- | --- | --- | --- | --- |
| Linux → Windows | `cmd.exe /c dir` | 宿主 1 次 | 0 个 Linux pty，需另建 ConPTY | 仅 `WSLENV` 列名 | 32 位截断为 8 位 |
| Windows → Linux | `wsl.exe -e ls` | VM 内 1 次 | 分配 ConPTY 并桥接为 pty | 仅 `WSLENV` 列名，`PATH` 双侧独立 | 8 位直接透传 |

两行的对称处只有"1 次进程创建"与"白名单过滤"两项，不对称处集中在 tty：Windows 进程拿到的是管道而非 pty，交互式程序（编辑器、分页器、`ssh` 的密码提示）在 interop 下必须由调用方另建 ConPTY 通道，否则 `isatty` 判假、行编辑与信号语义整体缺失；反向则天然分配 ConPTY 并在 VM 内映射为 pty。

退出码的截断是可观测的：宿主进程返回 300 时 Linux 侧看到 44（ $300 \bmod 256$），返回 0 与 256 不可区分。脚本跨边界串联时，判定必须落在 0 与 非 0 上，不能依赖具体数值。

### 6.3 三条可判定的边界规则

第一条，`.exe` 调用只买到一个进程，买不到 tty 与信号：凡是需要 `SIGWINCH`、行缓冲、Ctrl-C 中断语义的程序，都必须显式建 ConPTY，否则中断信号在边界上丢失，只能等目标进程自行退出。

第二条，参数传递是字节流而非词表：Linux 侧用单引号包住的整串在过界后由 Windows 侧重新分词，含空格与引号的参数要在调用点就按目标侧规则拼好，转换层不做转义。

第三条，环境变量默认不过界：宿主设的变量在 VM 内不可见，除非在 `WSLENV` 中列名；反之亦然。因此同一份脚本在两个方向上都依赖 `PATH` 查找时，必须假设两侧的 `PATH` 是两套互不包含的值，而非一个共享列表。

## 七、`WSLENV` 与变量过界：后缀位投影

### 7.1 一项 `WSLENV` 的位切分

```text
WSLENV 中的一项：      NODE_PATH/p:l
                       └───┬───┘││
                         变量名 │└─ /l：值是列表，逐元素转换
                                └── /p：值是路径，做 1 次形态转换

四项标志，可叠加，顺序无关：

 /p  路径     每方向各 1 次改写：C:\x  ⇄  /mnt/c/x
 /l  列表     先按源侧分隔符切分，逐元素做 /p，再按目标侧分隔符拼接
 /u  仅 W→L   方向门控：反向启动时整项丢弃，0 字节过界
 /w  仅 L→W   同上，方向相反
 无  透传     原字节搬运，0 次改写
```

一项 `WSLENV` 被两个分隔符切成两段：冒号切项，斜杠切"变量名 / 标志串"。判定顺序固定为方向门控先于改写——先看 `/u`、`/w` 与本次启动方向是否匹配，不匹配则整项作废，连字符串改写都不发生；匹配后再看 `/l` 与 `/p`，先切列表再逐元素转换。

### 7.2 三跳投影：宿主环境块 → interop → VM 环境块

```text
 跳 1  宿主环境块              跳 2  interop 启动              跳 3  VM 环境块
 ───────────────             ─────────────────             ──────────────
 KEY=VALUE;K2=V2  ─白名单─►  逐项：门控 → 切分 → 改写  ─写入─►  KEY=VALUE:K2=V2
 分隔符 ';'                   /p 每值 1 次                  分隔符 ':'
 未列名项 ──► 丢弃（0 字节）   含空格值：原样字节，无引号层
```

跳 1 只做一件事：按 `WSLENV` 的项名做白名单过滤，未列名变量的过界字节数为 0，且无提示。跳 2 是全部转换发生的地方：`/p` 每个值改写 1 次，`/l` 对 $k$ 个元素改写 $k$ 次，无后缀 0 次；改写是纯字符串操作，单次数十微秒以下，一百个变量各带三个元素的列表也只累计到毫秒档以下，相对一次进程创建十毫秒的底噪可以忽略。跳 3 把结果写进目标环境块，同名的既有项被覆盖，不合并。

三跳的成本因此不在 CPU，而在语义：跳 1 的静默丢弃与跳 3 的静默覆盖都不返回错误码，变量在边界上"消失"或"被顶掉"都不产生任何输出。

### 7.3 每跳的转换次数与失败形态

| 变量 | 后缀 | 跳 1 白名单 | 跳 2 改写次数 | 跳 3 落地 | 失败形态 |
| --- | --- | --- | --- | --- | --- |
| `JAVA_HOME` | `/p` | 通过 | 1 | `/mnt/c/Program Files/Java` | 含空格，被下游重新分词后断成两段 |
| `NODE_PATH` | `/l` | 通过 | $k$（元素数） | `/mnt/c/a:/mnt/c/b` | 元素本身含 `:` 时反向切分歧义 |
| `HTTPS_PROXY` | `/p:u` | 仅 W→L | 1 | 反向启动时为 0 | 反方向调用时变量缺失，静默 |
| `TOKEN` | 未列名 | 丢弃 | 0 | 不存在 | 0 字节过界，无提示 |
| `PATH` | 未列名 | 丢弃 | 0 | 由 VM 自行生成 | 两侧两套值，互不包含 |

表里两处失败源自分隔符冲突，与路径无关而与"哪个字符算分隔符"有关。第一处是 `;` 与 `:` 的错位：宿主侧列表用 `;` 切，目标侧列表用 `:` 拼，`/l` 负责这对映射；若只给 `/p` 而不给 `/l`，整条 `C:\a;C:\b` 被当成一个路径去转换，得到一条含分号的假路径 `/mnt/c/a;C:\b`。第二处是 Linux 文件名的自由度：`:` 在 Linux 侧是合法文件名字符，故反向 `/l` 遇到 `a:b` 无法判定它是两个元素还是一个名字，切分结果只能按协议猜。

含空格的路径是第三种失败形态，但它不改字节数：`C:\Program Files\X` 转成 `/mnt/c/Program Files/X` 后仍是同一串字符，只是过界后没有引号层，任何把变量值拼进命令行的下游都会在空格处断词，表现为"文件不存在"。这三种失败都不报错，只能靠调用点自己加固。

### 7.4 过界判定规则

| 类别 | 判据 | 处理 | 例 |
| --- | --- | --- | --- |
| 必须显式过界 | 目标侧进程要按路径打开，且路径在另一侧 | 列名加 `/p` | `JAVA_HOME`、`CARGO_HOME`、`HTTPS_PROXY` |
| 必须显式过界 | 值是多条路径，任一侧工具会自行遍历 | 列名加 `/l` | 自建的 `*_PATH` 列表 |
| 条件过界 | 两侧语义不同但同名 | 单方向加 `/u` 或 `/w` | 只在宿主侧有意义的工具目录 |
| 永不过界 | 值是凭据、会话态或与平台绑定的二进制路径 | 不列名 | `TOKEN`、`LD_LIBRARY_PATH`、`PWD` |
| 永不过界 | 目标侧应自行生成 | 不列名 | `PATH`、`TERM` |

判据只有一条：过界后的字符串是否仍能被目标侧当作"同一个东西"使用。路径能，因为 `/p` 给了双射；列表在元素不含目标侧分隔符时能，否则不能；凭据不能，因为它一旦过界就多了一份副本，而副本的可见范围由接收侧进程树决定，不由设置者决定。

`PATH` 属于最后一类的典型：它默认两侧独立取值，一个变量名、两套值，故 VM 内 `PATH` 与宿主 `PATH` 不存在包含关系。给它加 `/p` 反而会把它压成单套值，覆盖掉 VM 侧原本正确的条目——这是"过界并非越多越好"的最短反例。同理，`LD_LIBRARY_PATH` 过界只会把宿主侧的目录塞进动态链接器的搜索路径，而那里的 `.so` 与 VM 内 ABI 不匹配，失败发生在加载期而非解析期。
