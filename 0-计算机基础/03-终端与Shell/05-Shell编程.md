# Shell 编程

## 一、脚本执行入口：shebang 的单参数重组与退出码低 8 位

```text
  调用方 execve("/opt/s.sh", ["s.sh", "a"], envp)
        │
        ▼
  ┌───────────────────────────────────────────────────────────────┐
  │ binfmt_script：读前 BINPRM_BUF_SIZE 字节（老内核 128，5.1 起 256）│
  │   · 前 2 字节 ≠ 0x23 0x21 → 不接管，返回 ENOEXEC                │
  └──────────────────────────────┬────────────────────────────────┘
                                 ▼
  重组 argv（内核内字符串拼接：0 次 fork、0 次用户态调用）
     argv' = [ 解释器路径, 行内余下部分（至多 1 项）, 脚本路径, 原 argv[1..] ]
                                 │
                                 ▼
  execve(解释器, argv', envp)              ← 第 2 次 execve（仅 env 形态）
                                 │
                                 ▼
  解释器 open(脚本路径) → 逐行解释 → exit(n)
                                 │
                                 ▼
  父进程 wait4() → WIFEXITED → WEXITSTATUS =（status >> 8）& 0xFF
```

| 形态 | `execve` 次数 | 新进程 `argv` 项数 | 解释器路径来源 | 退出码来源 |
| --- | --- | --- | --- | --- |
| `#!/bin/bash` | 1 | 原项数 + 1（仅追加脚本路径） | shebang 字面量，必须是绝对路径 | bash 的 `exit` 或最后一条命令 |
| `#!/usr/bin/env bash` | 1 + `PATH` 命中前失败的次数 | 原项数 + 2（`bash`、脚本路径） | `env` 按 `PATH` 逐项试 `execve` | bash；`env` 只转发，自身不产生业务状态 |
| 无 shebang，`bash s.sh` | 1（由调用方壳发起） | 原项数 + 1 | 调用方壳的 `PATH` 查找 | bash，`$0` 仍为脚本路径 |

表的读法是：三种形态的差别不在"能不能跑"，而在**多几次 `execve`、多几项 argv**。`env` 形态把"解释器在哪"从编译期常量降级为运行期 `PATH` 查找，代价是每项 miss 一次 `execve` 系统调用。

### 1. 内核重组：2 字节判定与 1 项字符串拼接

判定只读文件前 2 个字节：命中 `0x23 0x21`（`#!`）则 `binfmt_script` 接管，否则连同 `binfmt_elf` 一起失败并返回 `ENOEXEC`，调用方壳据此决定是否退回"自己按脚本解释"。接管后的解析规则是纯字节操作：跳过 `#!` 之后的空白，取到下一个空白为止作为解释器路径；**整行余下部分（去掉尾部空白）作为单个参数**，不再按空白切分；随后追加脚本路径，再原样接上调用方的 `argv[1..]`。因此 argv 项数恒为 原项数 + 2，无额外参数时为 原项数 + 1。

字节账在这里有一处硬上限：整条 shebang 行必须落在 `BINPRM_BUF_SIZE` 内，超长部分被截断在缓冲区边界。若截断落在解释器路径中间，拼出的路径不存在，`execve` 返回 `ENOENT`——表现为"脚本有可执行位却报找不到解释器"，而脚本正文一个字节都没被读过。长串选项写不进 shebang，原因不是语法限制，而是内核读取缓冲区的固定长度。

### 2. 单参数边界：`env` 形态的三处代价

```bash
#!/usr/bin/env bash -e
printf '%s\n' "$0" "$@"
```

在解释器/内核侧发生了什么：`env` 收到的 `argv[1]` 是**单个字符串** `bash -e`（内核不按空白再切一次），它拿这个名字沿 `PATH` 每项各试一次 `execve`，全部 `ENOENT` 后以 127 退出，脚本正文一行未执行。

这条边的正确用法与错误用法只差一个空格的位置。`#!/bin/bash -eu` 合法，因为 bash 自己会把 `-eu` 当短选项簇拆成两个开关；`#!/bin/bash --rcfile /etc/x` 不合法，bash 收到的是字面量 `--rcfile /etc/x` 这一个参数，无法识别为两个。`env` 形态额外付三笔：多 1 次 `execve`（`env` 自身）、多 N 次失败的 `execve`（N 等于 `PATH` 中 `bash` 之前的目录数）、多一个运行期依赖——精简镜像里 `/usr/bin/env` 常在而 `bash` 已被换成 `/bin/sh`。

### 3. 退出码：`wait4` 的 16 位状态字与 256 档有效值

退出码不是一个整数，而是 `wait4` 返回的 16 位状态字里的三个位段：低 7 位放信号号，bit 7 放 core dump 标志，高 8 位放退出码。这个布局直接决定了后面所有"错误传播"的算术：

```bash
( exit 256 ); printf 'exit=%d\n' "$?"
bash -c 'kill -TERM $$'; printf 'sig=%d\n' "$?"
```

在解释器/内核侧发生了什么：第一条让子壳以 256 退出，`exit_group` 只保留低 8 位，父壳读到 0，即"失败被读成成功"；第二条让 bash 自杀于 `SIGTERM`，`WIFSIGNALED` 置位而 `WEXITSTATUS` 无意义，壳按惯例合成 $128+15=143$。

两个档位因此必须分开读：正常退出只有 256 档（0~255），信号退出落在 129~255 这一段并与正常退出码共享数值空间，`137` 既可能是 `exit 137` 也可能是被 `SIGKILL` 杀掉。`set -e` 只看高 8 位是否为零，故它对"被信号杀死"与"返回 137"给出同一个反应；CI 与 `systemd` 额外查 `WIFSIGNALED`，正是为了把这两类分开——`137` 在容器里被读作 OOM kill，依据就是信号位段而非退出码。

一次 `fork+execve` 的端到端开销在毫秒档（数百微秒到 1 毫秒，含页表复制与 ELF 装载），退出码的截断本身是 0 次系统调用、1 次位与运算；入口成本几乎全在进程创建，这一环的问题不是慢，而是**只有 256 个可区分状态**，任何结构化的错误都必须另开通道（stderr 或临时文件）。

## 二、变量三档与作用域投影：属性位决定过界资格

```text
  Shell 变量表：hash bucket → variable 记录
   ┌──────────────────────────────────────────────────────────────┐
   │ name        字节串，首次赋值时插入桶链                        │
   │ value       堆块（可含除 \0 外的任意字节，长度另存）           │
   │ attributes  位图：export / readonly / array / integer /       │
   │             nameref / local，各占 1 位                        │
   └──────┬────────────────────────┬──────────────────────────────┘
          │ 展开 $v / ${v}          │ 过 execve 边界
          ▼                         ▼
   ┌────────────────────┐   ┌─────────────────────────────────────┐
   │ 展开器按属性分流：  │   │ export 位 = 1 → 拼 "name=value\0"    │
   │ 标量原样 / 整数求值 │   │   追加进 environ[] 副本，字节数 =     │
   │ 数组下标定位 /      │   │   Σ(len(name)+len(value)+2)          │
   │ nameref 逐层解引用  │   │ export 位 = 0 → 0 字节通过            │
   └────────────────────┘   └─────────────────────────────────────┘
          │
          ▼  fork（子壳 / 命令替换 / 管道段）
   页表复制、物理页共享（COW）：写前 0 字节拷贝，首次写入复制 1 页 4 KiB
```

| 属性 | 过 `execve` 边界 | 可再赋值 | 展开规则 | 失效时的观测 |
| --- | --- | --- | --- | --- |
| 普通（无属性） | 否，0 字节 | 是 | 字符串原样，0 次求值 | 子进程 `env` 中不可见 |
| `export` | 是，`name=value\0` | 是 | 同普通 | 子进程 `environ` 可见 |
| `readonly` | 仅当同时 `export` | 否，返回 1、0 字节变更 | 同普通 | `R=2` 报 readonly |
| `integer`（`-i`） | 随 `export` 位 | 是 | 赋值与展开各 1 次算术求值（`$(( ))` 语义） | `08` 求值失败、返回 1 |
| `array` | 否（bash 不导出数组） | 是 | 下标求值 + 1 次元素定位 | 子进程看不到 |
| `nameref`（`-n`） | 否 | 是（写到目标） | 每层 1 次查表、0 次值拷贝 | 循环引用报错 |

表把三档并成一列看：真正决定"能不能过界"的只有 `export` 那一位，其余属性只影响**赋值与展开时的解释路径**。三档因此不是三种变量，而是同一记录上三个独立开关的组合——`readonly` 加 `export` 得到"只读且可继承"，`integer` 加 `export` 得到"子进程看到的是十进制字符串而非原始输入"。

### 1. 记录布局：值在堆上，资格在位图上

一条变量记录由三项构成：名字字节串、值堆块、属性位图。名字入表时算一次哈希（每字符 1 次移位与加法，长度线性），值每次赋值走 1 次 `realloc` 加 1 次 `memcpy`（字节数等于新值长度），属性位则在记录头里就地置位，0 次内存分配。`declare -p v` 打印出来的 `declare -x v="..."` 前缀就是位图的文本投影：`-x` 是 export，`-r` 是 readonly，`-i` 是 integer，`-a`/`-A` 是索引/关联数组，`-n` 是 nameref。

位图与值分离有一个直接后果：加属性是 0 字节拷贝的元数据操作（微秒以下），改变值必然是一次堆写入。所以 `export v` 之后再改 `v`，新值自动带出到后续子进程——导出的是**名字**，不是当时的值快照。

### 2. `execve` 边界：一次 `environ` 重建的字节账

导出变量的过界方式是重建一块 `char *[]`：每项形如 `name=value\0`，总字节数为 $\sum(\text{len}(name)+\text{len}(value)+2)$（`=` 与结尾 NUL 各 1 字节）。典型交互式壳的导出集合在 1~4 KiB 量级，这段字节在每次 `execve` 时被复制进新进程的栈区，属于"每启动一个外部命令付一次"的固定税，与命令本身做什么无关。

未导出变量在这条边上通过的字节数是 0，且不产生任何错误或警告——这是"子脚本读不到父壳变量"的唯一原因，与作用域、与是否 `source` 都无关。反过来的观测点同样干净：`env` 的输出就是本次 `execve` 实际搬运的字节集。上限侧有两个常数：单个字符串受 `MAX_ARG_STRLEN` 限制（32 页 = 128 KiB），整个 `argv+envp` 受 `ARG_MAX` 限制（通常 2 MiB）；超限时 `execve` 返回 `E2BIG`，1 次失败、0 字节落地。

### 3. `fork` 边界：COW 页共享与"子壳改了却看不见"

子壳（`( )`、`$( )`、管道段）由 `fork` 产生，变量表整体被**页表复制而非字节复制**：父子共享同一批物理页，只有任一方写入才复制该页（4 KiB）。这条边因此有两个可测数字：`fork` 后立刻读，拷贝 0 字节；子壳内首次写某变量，拷贝 1 页 4 KiB（与该变量实际长度无关）。所以"子壳里改了父壳看不见"不是设计上的隔离，而是 COW 的必然结果——子壳写的是自己那份页。

正因如此，管道与命令替换的赋值丢失无法用 `export` 修补：导出的方向是"向下传"，这里需要的是"向上回传"，通道根本不存在。唯一的零 `fork` 回写方式是 nameref 或全局数组（见 §4），`shopt -s lastpipe` 则把管道最后一段挪回主壳执行，用"少 1 个进程"换回变量存活。

### 4. 三个属性的失效模式：readonly 的返回码、integer 的八进制、nameref 的查表次数

```bash
declare -i n=010                 # 前导 0 → 八进制 → 8
declare -r R=1; R=2; echo "R=$R rc=$?"
declare -n ref=n; ref=7
printf 'n=%s\n' "$n"
```

在解释器/内核侧发生了什么：`-i` 使赋值走算术求值而非字节拷贝，`010` 按八进制解析得 8；`-r` 使第二次写入在触碰堆块之前就被拒，返回 1 且值 0 字节变化；`-n` 使 `ref=7` 沿目标指针直接写进 `n` 的堆块，不产生第二份值。

三处失效各有形态。`readonly` 的拒绝发生在赋值路径入口，代价是 1 次失败返回、0 次 `realloc`，且该位被 `fork` 继承——子壳里 `unset` 同样返回 1，无法绕过。`integer` 的坑在进制：前导 `0` 触发八进制解释，`08` 含非法数字而在求值阶段失败，赋值不落地，变量保持 0 并返回 1；两个字符的输入得到一个"合法但不预期"的值或一次静默失败。`nameref` 的成本按层数线性叠加：每层多 1 次哈希查表、0 次值拷贝，两层即 2 次查表，故它适合做输出参数而不适合热路径别名；循环引用（`a→b→a`）由解析器在固定深度内检出并报错。

`array` 属性另有一条独立约束：bash 不把数组放进 `environ`，所以 `arr=(1 2 3)` 无论是否 `declare -a` 都不会出现在子进程里，跨进程传数组只能序列化（`printf '%s\0'` 配合 `IFS=` 读取）——这一条把变量三档与 §3 的字节保真接在同一条边界上。

## 三、数组与 `IFS`：分词器是唯一的字节保真断点

```text
  arr=( "a b" "" "c" )     3 个元素，数据 4 字节（"a b" 占 3 + "c" 占 1），空元素 0 字节
        │
        ▼
  槽表：64 位下 8 字节/槽，空槽为 NULL
   [0]──► "a b\0"     [1]──► "\0"     [2]──► "c\0"
        │
        │ 展开器按引用形态分流（全在用户态，0 次系统调用）
        ├─ "${arr[@]}"  ──► 3 项，元素与 argv 1:1：[a b] [] [c]     0 次分词、0 次通配
        ├─  ${arr[@]}   ──► 逐元素过 IFS 分词 + 路径名展开：
        │                      "a b" → 2 词 a、b
        │                      ""    → 0 词（整项消失）
        │                      "c"   → 1 词 c          合计仍 3 项，边界已重组
        ├─ "${arr[*]}"  ──► 1 项：a b<IFS首字节>c       段间插 n-1 = 2 字节
        └─  ${arr[*]}   ──► 先拼成 1 项，再整体切一刀    词数由 IFS 决定
        │
        ▼ execve（只有外部命令才走这一步）
  argv[]：8·n 字节指针槽 + Σ(len+1) 字节字符串，受 ARG_MAX = 2 MiB 约束
```

| 引用形态（`arr=( "a b" "" "c" )`） | argv 项数 | 空元素 | 含空格元素 | 每元素额外代价 |
| --- | --- | --- | --- | --- |
| `"${arr[@]}"` | 3 | 保留为 1 项空串 | 1 项，空格留在项内 | 0 次扫描 |
| `${arr[@]}` | 3（巧合相同） | 消失，0 词 | 拆成 2 项 | 1 次 IFS 扫描 |
| `"${arr[*]}"` | 1 | 保留为空段 | 保留 | 插 n-1 个分隔字节 |
| `${arr[*]}` | 由 IFS 切分决定 | 连续分隔符折叠 | 再拆一次 | 1 次拼接 + 1 次扫描 |
| `$arr`（等价 `arr[0]`） | 1 | — | 若凸出则再拆 | 只读 1 个槽 |
| `arr=()` 时 `"${arr[@]}"` | 0 | — | — | 唯一能表达"空参数表" |

表的读法是：**项数相同不代表字节相同**。第二行的 3 项与第一行的 3 项在 `$#`、`${#arr[@]}`、`wc -l` 三处检查里全都通过，只有逐项打印才能看出边界已被重组；判据因此只能是引用形态本身，不能是任何计数。

### 1. 两种容器：8 字节指针槽与哈希桶

下标数组在壳内是一块 `char *` 槽表加若干堆块：每个存在元素占 1 个 8 字节槽与 1 个 `len+1` 字节堆块，空槽是 NULL。稀疏性因此完全可测——`a[999]=x` 只把槽表扩到 1000 槽即 8000 字节，中间 999 个槽为 NULL，而 `"${a[@]}"` 遍历槽表时跳过 NULL，故传出去的 argv 恒为 1 项：0 个空项落到 `execve` 边界，8000 字节留在壳堆里。这条规则解释了"稀疏数组不产生空参数"，也解释了为什么用数组收集可选参数比用 `$@` 拼字符串安全。

关联数组是另一套容器：每键 1 次哈希（代价随键长线性）+ 1 次桶链查找，`declare -A` 的遍历序是桶序而非插入序。`"${m[@]}"` 传给子进程时，参数顺序在同一 bash 版本内稳定、跨版本不保证，所以依赖顺序的处理必须显式排序——`printf '%s\n' "${!m[@]}" | sort` 多 1 个 `sort` 进程，即 1 次 fork + 1 次 execve 的毫秒档开销。`${#m[@]}` 读的是 O(1) 计数器，不做遍历。

### 2. `"${arr[@]}"`：引号内 `@` 唯一的 n 词特例

七级展开瀑布的所有规则都收敛到"引号内只出 1 个词"，只有 `"$@"` 与 `"${arr[@]}"` 例外：n 个元素各出一词，元素与 argv 1:1，且整条路径绕过 IFS 分词与路径名展开两道工序——这两道在任何其他形态下至少跑一遍。所谓"保真"的全部机制含义就在这里：不是转义写对了，而是**根本没进分词器**。

空集是这条规则的边界值：`arr=()` 时 `"${arr[@]}"` 产出 0 项，`"${arr[*]}"` 产出 1 个空串项，`${arr[@]}` 也是 0 项。0 与 1 的差在 `rm`、`set --`、`cmd "$@"` 上直接表现为"什么都不做"与"处理一个空文件名"。

```bash
arr=( "a b" "" "c" )
printf '[%s]\n' "${arr[@]}"      # [a b] [] [c]
printf '[%s]\n' ${arr[@]}        # [a] [b] [c]，3 行，边界已毁
set -- "${arr[@]}"; printf 'argc=%d\n' "$#"
```

在解释器/内核侧发生了什么：`printf` 与 `set` 都是内建，0 次 fork、0 次 execve；第二行在展开器里对 4 字节数据各做 1 次 IFS 扫描，把 `a b` 切成两词并把空元素整个丢弃；第一行 0 次扫描，3 个元素原样成为 3 个 argv 项。

### 3. `IFS` 的三笔字节账：扫描、折叠、首字节拼接

`IFS` 的默认值是 3 个字节 `$' \t\n'`。分词器对整串做一次线性扫描，每字节做 1 次成员比较，代价 O(字节数)、无额外堆分配。三笔账必须分开记：

1. **折叠**：连续 IFS 空白字符折叠为 1 次分隔，串首尾空白直接丢弃，故 `a   b` 与 `a b` 都切出 2 词。非空白 IFS 字符不折叠，`a,,b` 在 `IFS=,` 下切出 3 词，中间那个是 0 字节空字段——"空字段保留"与"空串消失"是两组不同规则，触发条件只在于分隔符是否为空白。
2. **关闭**：`IFS=` 使扫描 0 次切分，整串恒为 1 词。要区分"未设 `IFS`"（取默认三字节）与"设为空串"（0 切分），这两者在 `read`、`for`、`$*` 三处行为完全不同。
3. **拼接**：`"${arr[*]}"` 与 `"$*"` 只用 IFS 的**首字节**做段间分隔，插 n-1 个字节，与 IFS 长度无关——`IFS=abc` 拼出来的仍是以 `a` 分隔。

```bash
IFS=: read -r -a f <<< "root:x:0"
printf '%s %s\n' "${#f[@]}" "${f[2]}"
IFS=,; printf '%s\n' "${arr[*]}"
```

在解释器/内核侧发生了什么：`read` 是内建，0 次 fork；`<<<` 由 bash 在用户态落成 1 个一次性读端交给 `read` 的 stdin，`IFS=:` 让切分只认 `:`，3 个字段一次读完并写进数组槽；第三行开始的 `IFS=,` 是持久赋值（少了命令前缀那层临时环境），此后所有拼接都改用它。

第三笔账是 `IFS` 与文本协议之间的死结：既然拼接用 IFS 首字节、切分又按 IFS 全集识别，任何"用 `$*` 拼好再切开"的往返都会在元素自身含分隔符时改变元素数。元素内容含 `,` 而 `IFS=,`，往返一次 3 个元素变 4 个，且没有任何校验能发现。

### 4. 为什么只有 NUL 能做保真分隔符

保真分隔符必须是一个**永远不可能出现在数据里**的字节。文件名与 argv 字符串在系统调用边界上都以 NUL 结尾，内核因此不允许其内容含 NUL——这不是编码约定，而是 `execve`/`open` 的入参表示法决定的硬约束。可打印分隔符则全部失守：`\n`、`,`、`:`、`\t` 都是合法文件名与合法参数内容，故 `find | while read` 遇到含换行的文件名就断成 2 条错路径，而这在 Linux 上完全合法。

保真写法因此固定为两条：生产者用 `printf '%s\0'` 或 `find -print0`，消费者用 `mapfile -d ''` 或 `read -d ''`，中间 0 个文本处理进程。字节账是：n 个元素平均 L 字节，管道里搬 n(L+1) 字节，按 4 KiB 缓冲块折成 n(L+1)/4096 次 `write`。

反方向的通道更能说明问题：若改用 `$( )` 收集，尾部**所有**连续换行被剥、NUL 被丢弃（bash 4.4 起在 stderr 报 ignored null byte），可区分的元素数从 n 直接掉到 1。命令替换的返回通道只认文本，不认字节，这与 §2 的 `export` 边界正好互为镜像：环境变量走"名字+值"的文本编码，数组与 NUL 走"文本编码不了就换通道"。

## 四、函数的退出码返回通道：0 fork 调用与四条回传路径

```text
  f() { ...; return 7; }          定义：仅在壳内哈希表插 1 条记录，0 次系统调用
        │
        │  f a b                     调用：0 次 clone、0 次 execve
        ▼
  ┌────────────────────────────────────────────────────────────────┐
  │ 当前壳进程内压入函数帧                                          │
  │   · $1..$n 整体替换（每参数 1 次指针入栈，字符串 0 字节拷贝）    │
  │   · local 变量压栈（动态作用域：被调者可见调用者的 local）       │
  │   · $? 入口不清零，退出时被 return 或最后一条命令覆写            │
  └────────────────────────────┬───────────────────────────────────┘
                               ▼
   四条回传通道，容量与存活范围各不相同
    ① return n / $?     → 8 位，256 档，经 wait4 高 8 位跨进程存活
    ② stdout            → 字节流，容量不限，被 $( ) 与管道改写
    ③ 全局变量 / nameref → 0 字节拷贝，仅同进程内有效
    ④ 临时文件 / fd 3   → 任意字节，2 次 open + 1 次 unlink 的固定税
                               │
                               ▼
   调用方读 ①：1 个槽，任何命令（含内建）写 1 次即覆写
```

| 通道 | 容量 | 数据单位 | 跨子壳/管道是否存活 | 典型失效 |
| --- | --- | --- | --- | --- |
| `return` / `$?` | 8 位，256 档 | 整数 | 存活 | 只能编码 1 个状态，下一条命令即覆写 |
| stdout | 受 pipe 缓冲 64 KiB 与读端限制 | 字节 | 存活 | `$( )` 剥尾换行、丢 NUL、1 次 fork |
| 全局变量 / nameref | 受内存 | 任意壳值 | 管道段不存活 | 子壳写不回父壳 |
| 临时文件 / fd 3 | 受磁盘与缓冲 | 任意字节 | 存活 | 2 次 open + unlink，微秒到毫秒 |

表的读法是：四条通道不是"哪种更优雅"，而是在**容量、数据单位、跨进程存活**三个维度上互不重叠的取舍。函数本身 0 fork，所以通道③最便宜（0 字节拷贝）、通道②最通用（任意字节但被劫持）、通道①最贵在只有 8 位、通道④最贵在两次路径解析。

### 1. 调用即查表：0 次 fork、两个数量级的差价

函数定义只在壳的哈希表里插一条记录：名字、函数体字符串、属性位，0 次系统调用。调用 `f a b` 的动作是：查表 1 次、压函数帧、把 `$1..$n` 整体换成 `a b`（每参数 1 次指针入栈，字符串本身 0 字节拷贝）、执行体、弹帧恢复旧的位置参数。全程 0 次 `clone`、0 次 `execve`，耗时在微秒档偏下。

对照外部脚本 `./f.sh`：至少 1 次 `fork`（页表复制，写时复制才付 1 页 4 KiB）+ 1 次 `execve`（ELF 装载与动态链接，数百微秒到毫秒档），再加 §1 的 shebang 解析与 argv 重组。同一段逻辑写成函数还是写成独立脚本，差价是 2 个数量级——这是"脚本内多用函数、少起子进程"唯一的量化依据。

帧里的作用域是动态的：`local` 把变量推进函数帧栈，被调函数沿调用栈向下查找同名变量，因此能看到调用者的 `local`（不是词法位置决定），同名 `local` 会遮蔽同名全局，查找深度等于嵌套层数。

### 2. `return` 的 8 位截断： $2^{8} = 256$ 档

`return n` 与 `exit n` 走同一条截断路径 `n & 0xFF`：`return -1` 得 255，`return 256` 得 0，`return 0x41` 得 65。一个字节 8 位，可区分状态数为 $2^{8} = 256$，其中 129~255 已被信号约定占用，真正留给业务的只有 0~125 与 126/127 两个壳级约定。

约定层是外加的，不是内核语义：0 成功、1 一般失败、2 用法错误、126 找到但不可执行、127 未找到、128+n 被信号 n 终止。要同时回传"数据"与"状态"，至少需要 2 条通道（如 stdout 走数据、`return` 走状态），因为 $2^{8}$ 的分辨率在"数据"这一侧连一个 ASCII 字节都放不下。

```bash
f() { local n=$(false); printf 'A:%s\n' "$?"; }
g() { local n; n=$(false); printf 'B:%s\n' "$?"; }
f; g
```

在解释器/内核侧发生了什么：`local` 是内建，`local n=$(...)` 形态下它自身的返回码 0 在赋值完成后写入 `$?`，把命令替换那个 1 挤掉；`g` 里赋值是独立一条命令，`$?` 保留 1。整个过程 0 次 fork，`$?` 只有一个槽，被写一次就换值。

### 3. 三处静默覆盖：子壳、管道段、`set -e` 的判定位置

三处都不报错，只在读数上偏移一格：

1. **子壳形态的函数** `f() ( ... )`：多 1 次 fork，体内变量写留在子壳的 COW 页上，`return` 只决定子壳的退出状态。通道①经 `wait4` 存活，通道③全部失效——这与 §2 的 `fork` 边界是同一件事，只是入口从 `( )` 换成了函数体。
2. **管道** `f | cat`：默认每段 1 个 fork，`$?` 只反映最后一段。`${PIPESTATUS[@]}` 给出逐段状态，元素个数等于管道段数，且必须在下一命令前读走（1 条命令 = 1 次覆写）。
3. **`set -e` 的判定位置**：命令位于 `if`/`while` 条件、`&&`/`||` 的操作数、或 `!` 之后时，非 0 只被当作条件值而不触发退出。于是同一函数在 `f` 与 `if f; then` 两种调用下行为不同：后者让体内所有失败都免疫 `-e`。这是"本地测试通过、CI 中途退出"最常见的来源，与函数写错无关。

`trap ... ERR` 还有一处边界：默认不继承进函数（需 `set -E` 才继承），且函数整体只算 1 条命令——体内 3 条命令失败，ERR 处理器只在函数最终返回非 0 时触发 1 次，不是 3 次。

### 4. 用 stdout 搬结构化结果：`$( )` 的 2n 字节与 `printf -v` 的 0 字节

`$( )` 的执行账是：1 次 fork + 1 对 pipe fd + 父进程 `read` 到 EOF。n 字节输出意味着 2n 字节拷贝（壳内缓冲 → 内核 pipe 缓冲 → 父缓冲），且尾部**所有**连续换行被剥（不是 1 个），NUL 被丢弃并告警。它适合搬文本行，不适合搬任意字节。

0 fork 的替代是 `printf -v var`：格式化结果直接写进壳内变量，拷贝 n 字节、0 次系统调用。把"解析"也留在壳内则用 `read -r a b <<< "$s"`。多行结果用 `mapfile -t arr < <(f)`：进程替换给 1 个读端（1 次 fork），`mapfile -t` 按行落进数组，每行 1 个元素，尾部换行不进入元素内容，比 `$( )` 少 1 次换行剥离与 1 次再分词。

把两条边界并起来读：函数调用 0 次系统调用、退出码 1 个字节、`$( )` 搬运 2n 字节；脚本能省的成本几乎全在"不起进程"，能丢的状态几乎全在"跨界"。同一条 fork 账在管道段与 `trap` 覆盖范围里会再出现一次——管道每段 1 个 fork，而 `trap` 的处理器只在注册它的那个进程里有效，子壳里注册的处理器随子壳一起消失。

## 五、引号与展开：七级瀑布的固定次序与 0 次系统调用

```text
  键入  "${d}"/f*      一个词 → 7 级瀑布，次序由 POSIX 钉死，不可重排
    │
    ├─① 花括号 {a,b}       bash 扩展，排在瀑布最前：纯字节切分，产出 2^k 个词
    ├─② 波浪号 ~ / ~user   前者 1 次 getenv（0 次系统调用）；后者 1 次 getpwnam（读 /etc/passwd）
    ├─③ 参数 ${d} / $d     1 次哈希查表；值按指针引用，0 字节拷贝
    ├─④ 命令替换 $( )      全瀑布唯一带 fork 的一级：1 fork + 1 pipe2 + 2n 字节拷贝
    ├─⑤ 算术 $(( ))        1 次解析 + 1 次求值 + 1 次十进制转换（≤ 20 字节）
    ├─⑥ 分词（IFS）        每字节 1 次成员比较；双引号内整级跳过
    ├─⑦ 路径名展开 glob    无元字符 → 0 次系统调用；有 → 1 openat + N 条 dirent + N log N 次比较
    └─⑧ 引号剥离           不是独立 pass：融在 ③④ 的拷贝里，引号字节从不进 argv
```

| 级 | 触发条件 | 系统调用次数 | 字节操作 | `"…"` 内是否执行 |
| --- | --- | --- | --- | --- |
| ① 花括号 | 含未引用的 `{` 与 `,` 或 `..` | 0 | 每层 1 次切分 + 1 次拼接，产出 $2^{k}$ 词 | 执行（引号只挡 `,`） |
| ② 波浪号 | 词首 `~` | 0；`~user` 为 3（open/read/close passwd） | 前缀替换，长度差 Δ 字节 | 不执行（`"~"` 是字面量） |
| ③ 参数 | `$` | 0 | 0 字节拷贝，仅指针引用 | 执行 |
| ④ 命令替换 | `$(` 或反引号 | 1 fork + 1 pipe2 + 读端 2 次往返 | 2n 字节（子 → 内核 → 父） | 执行 |
| ⑤ 算术 | `$(( ))` | 0 | 解析输入 + ≤ 20 字节十进制输出 | 执行 |
| ⑥ 分词 | 未引用且 IFS 非空 | 0 | n 次字节比较 | 跳过 |
| ⑦ glob | 未引用且含 `*?[` | 0；命中则 1 openat + ⌈32N/4096⌉ getdents64 | N 条名字 + O(N log N) 次比较 | 跳过 |
| ⑧ 剥离 | 恒有 | 0 | 每对引号 -2 字节 | — |

表的读法是：八行里只有第 ④ 行带 `fork`，只有第 ⑥⑦ 行被双引号关闭——**引号的全部作用就是关掉这两级**，它不做转义，也不改 ③④⑤ 的结果。

### 1. 引号是两级开关的标记，不是转义

双引号在词法阶段只置两个标志位：不可分词、不可通配。解析器把引号字符留在词串里（否则无法区分 `"$x"` 与 `$x`），到 ③④ 拷贝值时逐字节跳过——引号剥离因此不是第 8 次扫描，而是搭在已有那次拷贝上：0 次系统调用、0 次额外堆分配。`printf '%s' "a b"` 交给内建的是 3 字节，源码 5 字节中的 2 字节被丢弃。

单引号把 ③④⑤ 一起停掉：`'$x'` 是 2 字节字面量，0 次查表、0 次 fork。`$'…'` 在解析期就把 `\n`、`\x41` 转成真实字节，1 次转换、0 次运行期展开。反斜杠是单字节转义：未引用与双引号内 2 字节进、1 字节出，单引号内 `'\n'` 仍是 2 字节。三者都不改变耗时量级（n 次字节比较，微秒以下），只改变词数：加双引号恒为 1 词，不加则 1 到 n 词、每词再各跑 1 次 glob 检测。

### 2. 通配的两段式：先查元字符，再开目录

bash 调 `glob()` 前先 `strchr` 扫描找 `*?[`；无元字符就原样返回，0 次系统调用。于是 `ls /nope/*` 与 `ls /nope/x` 的系统调用数完全相同——通配开销不是"每次展开都付"，而是"含元字符才付"。

命中元字符后，`glob()` 对每个路径分量做 1 次 `openat(O_DIRECTORY)` 加若干次 `getdents64`：每次取回 4 KiB 目录块、每条约 24~40 字节，故 N 项约需 ⌈32N/4096⌉ 次；结果再做一次 `strcoll` 排序（O(N log N) 次比较，`LC_ALL=C` 时退化为 `strcmp`，单次快 3~10 倍），需要判定类型时每项多 1 次 `lstat`。

N = $10^{4}$ 的目录里展开 `*`：1 次 openat + 约 80 次 getdents64 + 约 $1.3 \times 10^{5}$ 次比较，整体在毫秒档；`LC_ALL=C` 下落到数百微秒档。空匹配是另一条分支：默认把字面量 `*` 原样传给命令（1 项），`nullglob` 变 0 项，`failglob` 直接不执行——三种行为在 argv 项数上是 1 / 0 / 不执行。

### 3. 二次瀑布：`eval` 的 1 次重解析与 `printf %q` 的往返

```bash
s='a b'
printf -v q '%q' "$s"        # 3 字节 → 4 字节：a\ b
set -- $q; printf 'set=%d\n' "$#"
eval "x=( $s )"; printf 'eval=%d\n' "${#x[@]}"
```

在解释器/内核侧发生了什么：`printf -v` 把 4 字节写进壳内变量，0 次系统调用；`set -- $q` 拿到的反斜杠来自**展开结果**，不再当引号解释，故仍切 2 词；`eval` 把字符串重新送进词法分析器，等于整条瀑布再跑一轮，4 字节被拷贝 2 次，串里含 `$( )` 则再付 1 次 fork。

`eval` 的成本是"1 次 parse + 1 轮完整瀑布"：毫秒以下免费，却把词数、通配、命令替换重新打开一遍，这正是注入入口。`printf %q` 是其逆运算，每个需转义字节 +1 字节，且输出**只能进 `eval`**，再过一次未引用展开即散架。

## 六、`trap` 与作业控制：信号按进程组投递，处理器只在安全点执行

```text
  终端驱动 n_tty 收到 1 字节 0x03（VINTR）
        │  不写入读缓冲、不当 EOF，直接走信号路径
        ▼
  kill_pgrp(前台组 pgid, SIGINT)            1 次系统调用，n 次投递
        │
        ├─► sleep（段 1）   ┐  n = 2：2 次信号、2 次唤醒（微秒档）
        └─► cat（段 2）     ┘  壳不在前台组内，故不被杀；它靠 wait4 返回得知子进程死因
        │
        ▼
  bash 的处理器只置 1 个 pending 位（1 条 trap 表项）后立即返回
        │
        ▼
  run_pending_traps()：安全点 = 每条命令之后 / wait4 返回之后
        │
        ▼
  作业控制三件套：setpgid(0,0) 建组 → tcsetpgrp ×2（交给子、收回）→ wait4(…, WUNTRACED)
```

| 动作 | `fork` 次数 | 关键系统调用 | 壳是否阻塞 | 退出状态去处 |
| --- | --- | --- | --- | --- |
| `cmd`（前台） | 1 | `setpgid` + `tcsetpgrp` ×2（交给子、收回） | 是，`wait4` 挂起 | `$?` |
| `cmd &` | 1 | `setpgid` 1 次 | 否 | 作业表；`wait` 前是僵尸 |
| `fg` / `bg` | 0 | `tcsetpgrp`（仅 fg）+ `kill(-pgid, SIGCONT)` | fg 阻塞、bg 不阻塞 | `$?` / 作业表 |
| `wait` / `wait -n` | 0 | `wait4` 1 次/已结束子 | 是 | 该子退出码 |
| `disown -h` | 0 | 0，只改壳内作业表 | 否 | 壳退出时不再收到 `SIGHUP` |

表的读法是：`fork` 只出现在"产生新进程"的两行，其余四行都是对既有进程的簿记与信号投递——作业控制的成本不在创建，而在切换的 2 次 `ioctl` 与回收的 1 次 `wait4`。

### 1. 一次按键的投递账：1 次系统调用、n 次投递

终端驱动把 0x03 当控制字符处理（`stty -a` 的 `intr = ^C`），不写入读缓冲，而向**前台进程组**发 `SIGINT`。投递次数等于该组成员数，与"用户以为只打断了当前命令"无关：`a | b` 里两个段各得 1 次；每次投递的固定成本是 1 次唤醒（微秒档），目标若在 `sleep` 中则多走一次 `EINTR` 返回。前台组只含作业进程、不含壳，故前台命令跑着时 Ctrl-C 杀不掉壳；反过来，`cmd &` 之后壳在 `wait` 里等时，终端的前台组正是壳自己的组，信号直达壳——§6.2 的例子即此。

被忽略的信号照样投递：`trap '' INT` 置 `SIG_IGN` 后内核仍走完整投递路径，接收端返回用户态前查表即丢弃——省的是用户态动作，不是内核动作。不可捕获的只有 `SIGKILL`(9) 与 `SIGSTOP`(19)，它们在 `sigaction` 层就被拒（`EINVAL`）。

终端还有两条与作业控制绑定的信号：后台组读 tty → `SIGTTIN`（默认停），后台组写 tty 且 `tostop` 置位 → `SIGTTOU`——这就是"`cmd &` 之后 `cat` 卡住不动"的全部机制。

### 2. `trap` 的时机：处理器不是异步的

```bash
trap 'printf "INT@%s\n" "$SECONDS"' INT
trap -p INT                    # 回读注册表
sleep 5 & wait $!              # 此处按 Ctrl-C
trap '' TERM                   # SIG_IGN：投递照旧，动作留空
```

在解释器/内核侧发生了什么：每次 `trap` 只写 1 条壳内表项并调 1 次 `sigaction`；Ctrl-C 到达时 bash 的处理器只置 pending 位就返回，真正的 `printf` 要等 `wait4` 返回（子进程被同一信号杀死，或 `EINTR`）之后才在 `run_pending_traps()` 里执行，故处理器时刻 = 信号时刻 + 剩余前台命令时长。

延迟执行可测：长命令不会被"打断到半条"，处理器永远落在两条命令之间，故 `trap` 里可安全改全局变量、写临时文件。`trap -p` 回读 0 次系统调用；`EXIT` 处理器能改退出码仅当体内显式 `exit n`，且 `set -e` 在其内部不生效。

继承规则是三条：`SIG_IGN` 被 `fork` 与 `execve` 继承（POSIX 规定被忽略的信号跨 `exec` 仍忽略）；被**捕获**的信号在子壳里复位为默认——这正是 §4 那句"处理器随子壳消失"的机制，`exec` 后更必然复位（处理器地址在新映像里不存在）；`set -E` 只让 `ERR` 处理器进函数与命令替换。

### 3. 作业控制：`setpgid`、`tcsetpgrp` 与僵尸回收

`&` 只做三件事：`fork`、子进程 `setpgid(0,0)` 自立一组、父进程在作业表里插 1 条记录后立刻返回。后台命令的 stdout 仍接终端，与前台输出交错——交错不是缺陷，是两个进程各自 `write` 到同一 tty 的结果；单次 `write` 不超过 `PIPE_BUF`（4096 字节）时行内不乱，超过则按 4 KiB 块交错。

前台命令要 `tcsetpgrp` 两次：执行前切成子组（子进程才收得到 Ctrl-C），结束后切回（否则壳读不到键盘）——这 2 次 `ioctl` 就是"前台"二字的全部实现，微秒档。

回收侧：子进程退出后到 `wait4` 之前是僵尸，占 1 个进程表项（内核侧数百字节）、不占内存页；交互壳在每条提示符前隐式回收，故僵尸只出现在长脚本里。`wait -n` 回收最先结束的 1 个并返回其退出码。壳退出时向所有作业发 `SIGHUP`：`disown -h` 把作业从表里摘掉不再发，`nohup` 则把 `SIGHUP` 置 `SIG_IGN` 并把 stdout 改写到文件。

## 七、here-doc 与 `IFS` 的边界：正文不过分词器，`read` 才过

```text
  cat <<'EOF' > out
    line
  EOF
        │  解析器先"预读"正文，与命令本身分离；正文长度决定落地形态
        ├─ n ≤ 管道缓冲（Linux 默认 64 KiB）
        │    1 pipe2 + ⌈n/4096⌉ write + 1 dup2      → 子进程 fd 0 接读端
        └─ n > 64 KiB
             1 openat(/tmp/sh-thd-XXXXXX) + ⌈n/4096⌉ write + 1 lseek + 1 unlink + 1 dup2
        │
        ▼  正文的展开级别：与普通词不同
  参数 / 命令替换 / 算术：执行（定界符未引用时）
  分词（IFS） / 通配：整级不执行   ← 正文是 1 条字节流，从不进分词器
```

| 形态 | 落地（n ≤ 64 KiB） | 系统调用 | 展开级 | 边界 |
| --- | --- | --- | --- | --- |
| `<<EOF` | 管道 | 1 pipe2 + ⌈n/4096⌉ write | 3 | 正文含空格、`*`、`;` 均不解释 |
| `<<'EOF'` | 管道 | 同上 | 0 | 逐字节透传，`$` 与 `\` 全部保留 |
| `<<-EOF` | 管道 | 同上 | 3 | 只剥行首 TAB，空格不剥 |
| `<<< "$s"` | 管道 | 同上 + 1 字节换行 | 3 | 自动补 1 个 `\n` |
| 大正文 | 临时文件 | 1 openat + ⌈n/4096⌉ write + lseek + unlink | 3 | 目录项已 unlink，进程崩溃也不留文件 |

表的读法是：五行里只有"展开级"在变，落地形态只由长度决定——`<<` 与 `<<<` 差 1 个换行字节，`<<` 与 `<<-` 差行首 TAB，定界符带不带引号决定正文要不要进展开器。

### 1. 两种落地：4 次路径系统调用 vs 1 次 `pipe2`

bash 5.1 起按正文长度分流：不超过管道缓冲时用 `pipe2` 一次写入，读端直接 `dup2` 到 fd 0；超过则退回临时文件（`mkstemp` 建 `/tmp/sh-thd-XXXXXX`，写完 `lseek` 回 0，立刻 `unlink`，再把 fd 交给子进程）。阈值就是管道容量本身（Linux 默认 65536 字节），因为写入必须不阻塞——超过容量而读端未读时写方会挂起，壳死锁在自己身上。

两条路径的系统调用数差 4 次（openat、lseek、unlink、`fstat`），落在微秒档；差别在数据通路：临时文件多一次路径解析与 inode 分配，`/tmp` 是 tmpfs 只付内存页，是磁盘则正文落盘再读回，比管道多 1 倍拷贝。

为什么必须落地成内核对象：fd 0 得是真实 fd，壳内变量在 `execve` 之后不可见（与 §2 的 `environ` 边界同构）。`<<<` 是 `<<` 的 1 行特例，多补 1 个 `\n`。

### 2. 正文只跑 3 级：分词与通配在 fd 0 上不存在

定界符带引号与否决定展开级数：`<<'EOF'` 逐字节透传（0 级，`$x`、`$( )`、`\` 全部原样），`<<EOF` 跑参数、命令替换、算术三级，但**永远不跑分词与通配**。因此正文里写 `a  b` 与 `*` 都保持字面量，哪怕它们是从 `$x` 展开来的。

这条规则与 §3 的 argv 边界互为镜像：同一串字节，走 `cmd $x` 会被 IFS 拆成 n 词、再被 glob 展开；走 `cmd <<< "$x"` 则是 1 条字节流，fd 0 上没有"词"这个概念。保真的两条路径也在此分岔：§3 的 NUL 分隔符靠"选一个不可能出现的字节"，here-doc 靠"根本不过分词器"——后者更彻底，代价是接收方只能按行读。

陷阱在 3 级那一侧：未引用定界符时正文里的 `$( )` 会执行（每个 1 次 fork），`\` 吃掉 1 字节（`\$` → `$`），行尾 `\` 还会吞掉换行把两行并成一行；要原样又想保留插值，只能逐个 `\$` 转义，每处多 1 字节。

### 3. `read` 的逐字节与 `mapfile` 的块读

```bash
while IFS= read -r l; do n=$((n+1)); done < <(cat big.txt)
mapfile -t a < <(cat big.txt)
printf 'lines=%d %d\n' "$n" "${#a[@]}"
```

在解释器/内核侧发生了什么：`read` 内建在不可 seek 的 fd（管道、FIFO、终端）上每次 `read(2)` 只取 1 字节，因为取多了无法退回；`mapfile` 按内部缓冲块取数，系统调用数为块数。普通重定向 `< big.txt` 是普通文件，可 `lseek` 回退，bash 会读一块再退回，故逐字节只发生在管道一侧——这一条决定了同一份数据走重定向还是走进程替换，系统调用数相差 3 个数量级。

```math
\begin{aligned}
S_{\mathrm{read}} &= n = 1\,048\,576 \\
S_{\mathrm{mapfile}} &= \left\lceil \frac{n}{B} \right\rceil \approx 10^{3}\quad (B \sim 1\ \mathrm{KiB})
\end{aligned}
```

按每次系统调用 0.5~1 µs 计，前者落在 0.5~1 s 档，后者在毫秒档以下；差价与内容无关，只与"fd 能否回退"有关——字节拷贝量相同（各 n 字节），系统调用数却是 n 与 ⌈n/B⌉ 之比。

`IFS= read -r` 里的 `IFS=` 只作用于 `read` 自己的切分，不改重定向内容的任何字节：行首行尾 IFS 空白被剥、内部连续空白折叠、最后一个变量收下剩余全部（含内部分隔符）；非空白分隔符（`IFS=:`）不折叠，空字段保留——与 §3 的三笔账同源，区别只在入口是 fd 0 而非 argv。`-r` 关掉反斜杠转义，不加时 `\` 吃 1 字节并续行，行数与字节数同时变化。管道形态的 `while read` 还要多 1 次 fork、循环体在子壳里跑而变量丢；进程替换把循环留在当前壳，代价是多 1 个 `cat` 进程（1 fork + 1 execve，毫秒档）。
