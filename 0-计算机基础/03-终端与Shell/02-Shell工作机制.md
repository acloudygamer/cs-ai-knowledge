# Shell 工作机制

## 一、Shell 只是一个用户态进程

### 1. REPL 的循环状态与 fd 0/1/2 的独占

Shell 没有任何特权：它不解释命令的语义（那是子进程的事），不碰硬件，也不拥有终端——终端在 02 章 06 已建立为内核里的 tty 结构，Shell 只是在启动时被 `getty`/登录程序把 fd 0、1、2 指向同一个 tty 的一个普通用户态进程。它做的全部事情是一个五态的循环：

```text
   ┌──────────────────────────────────────────────────────────────┐
   │  ① 读：read(0) 或 readline 取一行（canonical 模式下等换行）    │
   │        │                                                      │
   │        ▼                                                      │
   │  ② 解析：字节行 → token → 语法树（纯内存，无系统调用）          │
   │        │                                                      │
   │        ▼                                                      │
   │  ③ 展开：变量/命令替换/通配 → argv（可能触发 fork：$( )）       │
   │        │                                                      │
   │        ▼                                                      │
   │  ④ 执行：内建（本进程内）或外部（fork + execve + waitpid）      │
   │        │                                                      │
   │        ▼                                                      │
   │  ⑤ 收尾：记录 $?、执行 trap、回到 ①                            │
   └──────────────────────────────────────────────────────────────┘
```

五条边逐一对应可观测的动作。**边①**是唯一的读入点：交互模式下由行编辑库接管，脚本模式下直接 `read(2)`。**边②**是纯用户态计算，字节不离开进程地址空间，因此"解析慢"不会出现在任何系统调用统计里。**边③**是第一个可能越界的点——只有命令替换与算术里的子表达式会产生新进程，普通变量展开不产生。**边④**是进程创建的唯一出口，也是后文所有 fork 计数的归属地。**边⑤**决定下一条命令的输入：`$?`、`set -e`、`trap` 都在这一格读写。

fd 0/1/2 的独占是这条循环的存在前提。Shell 自己不读 stdin 时就把它交给子进程（`cat` 直接读终端），自己读时才用 readline——所以"Shell 与子进程争抢同一个 fd"必然导致输入被吞掉。经典表现是在 `while read` 循环里调用会读 stdin 的命令（`ssh` 不加 `-n`），子进程把本属于循环的后续行全部吃掉，循环提前结束。

### 2. 三种启动形态：交互、脚本与 `-c`

同一份 Shell 二进制在三种启动形态下的行为差异，全部来自"输入从哪来"与"是否连接终端"两个变量：

| 形态 | 输入源 | `isatty(0)` | 读入方式 | 读 profile | 提示符 |
| --- | --- | --- | --- | --- | --- |
| 交互登录 | tty | 真 | 行编辑库逐行 | 是（登录文件 + 交互文件） | 是 |
| 交互非登录 | tty | 真 | 行编辑库逐行 | 仅交互文件 | 是 |
| 脚本文件 | 普通文件 fd | 假 | 按块 `read` + 逐命令解析 | 否（除非 `--login`） | 否 |
| `-c '字符串'` | 内存字符串 | 取决于父进程 | 直接从内存解析 | 否 | 否 |

第三行的"按块 `read` + 逐命令解析"是一个容易误解的点：Shell **不把整个脚本读进内存**，而是按 8 KiB 档的块向前读，解析出一条完整命令就执行一条；遇到 `if`/`for`/`case` 这类跨行构造时，它必须记住文件偏移并在语法未闭合时回退继续读。这带来两个可观测后果——脚本执行期间 `lseek` 会因跨行构造而回退（多次），以及"脚本正在被写入"时后半个文件的行可能读到已被覆盖的内容。

### 3. 提示符、行编辑与两次终端往返

交互形态下每次回车都包含两次方向相反的终端往返，它们不属于 Shell 的解析逻辑，却占了交互延迟的绝大部分：

```text
   Shell                          tty 行规程                   终端模拟器
     │                               │                            │
     │── ① write 提示符 + 控制序列 ─────►│── 转义序列 ──────────────►│ 渲染
     │                               │                            │
     │                               │◄── ② 用户按键（1 字节/键）──│
     │◄── ③ read 返回一行 ────────────│                            │
     │                               │                            │
     │── ④ 命令输出与回显交错的写 ─────►│──────────────────────────►│
```

**边①**把提示符与颜色序列写进 tty，这本身是 1 次 `write`，字节数取决于提示符里嵌了多少条 SGR 序列。**边②**是行规程在 canonical 模式下的攒行，每个按键 1 字节、退格 3 字节（`ECHOE`）。**边③**是唯一的唤醒点。**边④**是输出方向，与输入共享同一个 tty 但走独立的写路径，两者在终端屏幕上交错——这就是"输出的同时打字会把提示符冲掉"的结构原因。

行编辑库在边②之前插入了一层：它把 tty 临时切到 raw 模式（`tcsetattr` 2 次：进入与退出），逐字节读入并自己画字符、自己处理方向键。因此一次交互命令的终端系统调用账本是 **2 次 `tcsetattr` + 1 次 `read` 行 + 若干次 `write`**，而纯脚本模式为 **0 次 `tcsetattr` + N 次 `read`**。

## 二、解析与展开：从字节到 argv 的七级瀑布

### 1. 词法与语法：token 与语法树的两次切分

Shell 的解析分两步，中间隔着一棵语法树。第一步把字节切成 token（词），第二步按文法把 token 组合成命令节点。两次切分的判据完全不同：词法只看引号与元字符，语法只看保留字与运算符。

```text
  字节行  echo "a b"  >  out  ;  ls
     │
     ▼  ① 词法：识别引号、元字符、单词边界
  [WORD echo] [WORD "a b"] [OP >] [WORD out] [OP ;] [WORD ls]
     │
     ▼  ② 语法：按文法归约为节点
  ┌──────────────────────────────────────────┐
  │ LIST                                      │
  │  ├─ SIMPLE_CMD(words=[echo, "a b"],       │
  │  │              redirects=[> out])         │
  │  └─ SIMPLE_CMD(words=[ls], redirects=[])   │
  └──────────────────────────────────────────┘
     │
     ▼  ③ 展开（下一小节）：只有 WORD 节点会被改写，运算符与结构不变
```

三条边的职能必须分清。**边①**把 `"a b"` 归为**一个** WORD——引号在词法阶段就完成配对，空格因此在引号内不构成分隔符；这一步不展开任何变量，`$x` 仍是一个含 2 个字符的 WORD。**边②**决定命令的拓扑（谁与谁串联、谁重定向到哪），此时 `>` 已经成为结构而不是单词。**边③**只作用于 WORD 节点的内容，且可能改变节点数量（一个 WORD 展开成 100 个 argv 项）。把这三步混在一起，就会得出"引号防止通配符展开"这类错误因果——引号的作用是让词法阶段不切分，通配符是否展开由第 ③ 步的引号状态位决定。

### 2. 七级展开的顺序与字段数变化

展开是一条严格定序的流水线，每一步的输入是上一步的字段集合。顺序由 POSIX 固定，不能交换：

```text
 输入: 1 个 WORD（可能含 $、`、*、~）
   │
   ├─ ① 波浪号展开       ~/x        → /home/u/x           字段数不变，字节数变
   ├─ ② 参数与变量展开    $a ${b:-c} → 值的字节            字段数不变，字节数变（可为 0）
   ├─ ③ 命令替换          $(cmd)     → 子进程 stdout        1 次 fork + 1 个 pipe
   ├─ ④ 算术展开          $((1+2))   → 十进制字符串          字段数不变
   ├─ ⑤ 词分割（IFS）     "a b" 去引号后 → 2 个字段          字段数可增
   ├─ ⑥ 路径名展开（glob）*.c        → N 个文件名            字段数可增（可增至 0）
   └─ ⑦ 引号移除          去除所有引号字符                   字节数减少
   ▼
 输出: argv 数组（字段数 = 上一步结果，逐项 1 个 argv 项）
```

七步的次序决定了一批"反直觉"行为的归属。**第 ⑤ 步在 ⑥ 之前**：因此变量展开出的 `*` 会被第 ⑥ 步当通配符处理（"变量里的星号也会展开"），而引号阻止第 ⑤ 步切分、从而让整个值成为 1 个字段、再让第 ⑥ 步看到一个含空格的完整模式（通常匹配不到，于是原样保留）。**第 ③ 步在 ⑤ 之前**：命令替换的输出同样要经过词分割，所以 `$(printf 'a b')` 不加引号会变成 2 个字段。**第 ⑦ 步在最后**：它只减小字节数，不改变字段数，因此"引号是否保留"对 argv 内容无影响，只影响匹配到的路径字符串。

| 展开级 | 触发语法 | 是否可产生 0 个字段 | 是否 fork | 观测点 |
| --- | --- | --- | --- | --- |
| ① 波浪号 | 词首 `~` | 否 | 否 | `echo ~` 的字节数 = 家目录长度 |
| ② 参数 | `$name`、`${…}` | 是（空值 + 未加引号） | 否 | `set -x` 打印的 argv |
| ③ 命令替换 | `$(…)`、反引号 | 是 | 是（1 次） | `strace -f -e clone` 计数 |
| ④ 算术 | `$((…))` | 否（总是一个数字） | 否 | 结果为十进制字符串 |
| ⑤ 词分割 | 未加引号的展开结果 | 是 | 否 | `printf '<%s>'` 的尖括号数 |
| ⑥ 路径展开 | `*`、`?`、`[…]` | 是（无匹配时按 `nullglob` 或原样） | 否（`glob()` 只读目录） | `shopt -s nullglob` 前后 argv 长度 |
| ⑦ 引号移除 | 任意引号 | 否 | 否 | 最终 argv 字节 |

### 3. 命令替换的 fork 账本与两处优化

第 ③ 步是七级瀑布里唯一会产生进程的一级。它的实现是一个固定的小型事务：

```text
   Shell                                  子进程
     │  pipe(fds) ── 1 次系统调用 ──────────►│
     │  fork() ───── 1 次系统调用 ──────────►│（写时复制页表）
     │                                       │  dup2(fds[1], 1)  ── 1 次
     │  close(fds[1])                        │  execve(cmd)      ── 1 次
     │  read(fds[0]) 直到 EOF ◄──────────────│  写到 stdout 的全部字节
     │  waitpid() ── 1 次 ──────────────────►│  退出
     ▼                                       ▼
   剥离尾部全部换行 → 结果作为一个字符串进入第 ④ 步
```

账本：**每次命令替换 = 1 次 `pipe` + 1 次 `fork` + 1 次 `dup2` + 1 次 `execve` + 1 次 `waitpid`**，读端把子进程全部输出缓冲在内存里之后才继续。三个可直接观测的后果：输出越大、内存峰值越高（无法流式处理）；尾部换行**全部**被剥离（不是只剥 1 个），因此无法用 `$(…)` 保留结尾空行；子进程继承父进程的 stdin，若循环里调用会读 stdin 的命令，输入被吞。

两处优化改变了这个账本。`$(<file)` 是 Shell 内建的特殊形式，直接 `open` + `read` 文件，**0 次 fork**——它把"读文件"从一条通用路径降级为一条专用路径。另一处是 `exec` 内建：它不创建进程，而是把**当前 Shell 进程**的镜像换成目标程序（`execve` 1 次、`fork` 0 次），因此"脚本最后一行用 `exec`"能让解释器进程直接消失，省掉 1 个常驻进程。

## 三、重定向：fd 表的 `dup2` 改写

### 1. fd 表的三个继承槽位

每个进程有一张 fd 表，下标就是 fd 编号。Shell 关心的只有前三个槽位，因为只有它们会被 fork 继承并被 exec 保留：

```text
   父 Shell 的 fd 表                       fork 后的子进程
   ┌────┬──────────────┐                  ┌────┬──────────────┐
   │ 0  │ tty slave    │ ──── 复制 ─────► │ 0  │ tty slave    │
   │ 1  │ tty slave    │ ──── 复制 ─────► │ 1  │ tty slave    │
   │ 2  │ tty slave    │ ──── 复制 ─────► │ 2  │ tty slave    │
   │ 3  │ 脚本文件      │                  │ 3  │ （CLOEXEC，不继承）│
   └────┴──────────────┘                  └────┴──────────────┘
                                                │
                                       dup2(newfd, 1) → 槽位 1 被替换
```

三条边对应三个事实：fd 表在 `fork` 时**逐项复制**（指向同一批打开文件描述），所以父子共享文件偏移；`execve` **保留**未置 `CLOEXEC` 的 fd（这就是重定向能跨越 exec 生效的原因）；`dup2` 是**替换**而非新增，槽位 1 原来的打开文件描述被关闭、引用计数减 1。因此"重定向"在机制上只是"在 fork 之后、exec 之前，把某个槽位改指到另一个打开文件描述"——它不需要任何特殊的系统调用，只需要 `open` 与 `dup2` 两个原语。

### 2. 操作符到 `open` 标志的投影

每种重定向写法都对应一组确定的 `open` 标志与一次 `dup2`：

| 写法 | `open` 标志 | 目标 fd | 系统调用次数 | 是否创建文件 |
| --- | --- | --- | --- | --- |
| `> f` | `O_WRONLY｜O_CREAT｜O_TRUNC` | 1 | 1 `open` + 1 `dup2` | 是（存在则截断为 0 字节） |
| `>> f` | `O_WRONLY｜O_CREAT｜O_APPEND` | 1 | 1 `open` + 1 `dup2` | 是（不截断） |
| `< f` | `O_RDONLY` | 0 | 1 `open` + 1 `dup2` | 否（不存在则失败） |
| `2> f` | 同 `>` | 2 | 1 `open` + 1 `dup2` | 是 |
| `2>&1` | 无 | 2 | 1 `dup2`（复制槽位 1 的当前指向） | 否 |
| `&> f` | 同 `>` | 1 和 2 | 1 `open` + 2 `dup2` | 是 |
| `n<> f` | `O_RDWR｜O_CREAT` | n | 1 `open` + 1 `dup2` | 是（可读写同一 fd） |
| `> /dev/null` | `O_WRONLY` | 1 | 1 `open` + 1 `dup2` | 否（设备节点，写即丢弃） |

`2>&1` 那一行是整张表的枢纽：它**没有 `open`**，只把槽位 2 指向槽位 1 当前所指的那个打开文件描述。因此它的语义完全依赖于"执行到这一条时槽位 1 指向哪里"，而重定向按**从左到右**顺序执行：

```text
  写法 A:  cmd > f 2>&1          写法 B:  cmd 2>&1 > f
          ┌────┬──────────┐              ┌────┬──────────┐
   初始   │ 1  │ tty      │              │ 1  │ tty      │
          │ 2  │ tty      │              │ 2  │ tty      │
          ├────┼──────────┤              ├────┼──────────┤
   > f    │ 1  │ f        │              │ 1  │ tty      │
          │ 2  │ tty      │              │ 2  │ tty      │
          ├────┼──────────┤              ├────┼──────────┤
   2>&1   │ 1  │ f        │              │ 1  │ f        │
          │ 2  │ f  ← 跟随 │              │ 2  │ tty ← 已定 │
          └────┴──────────┘              └────┴──────────┘
   结果: stdout 与 stderr 都进 f        结果: stderr 仍在 tty，只有 stdout 进 f
```

A 路径正确，是因为 `2>&1` 在槽位 1 已改指文件之后执行，复制到的是文件的打开文件描述。B 路径的结果是 stderr 留在 tty——这不是 bug，而是"复制当前指向"这一语义的必然结果：`2>&1` 复制的是**当时**的槽位 1，之后槽位 1 再变也与槽位 2 无关。两行的差异恰好是 1 个 fd 指向，却决定了错误信息是否落进日志文件。

### 3. 重定向的作用域：单个命令、复合命令与 `exec`

重定向的作用域由它挂在哪个语法节点上决定，三种挂法对应三种生命周期：

```text
  A. 挂在简单命令上           B. 挂在复合命令上           C. 挂在 exec 上
     cmd > f                    { …; } > f                 exec > f
       │                          │                          │
       ▼                          ▼                          ▼
     fork 的子进程改自己的 fd     fork 的子进程改 fd        **当前 Shell** 改自己的 fd
     父 Shell 的 fd 不变          块内所有命令共享          此后所有输出都进 f
     作用域 = 1 个进程           作用域 = 1 个块            作用域 = 整个 Shell 余生
```

A 与 B 的共同点是改动发生在子进程里，父 Shell 的 fd 表不受影响；C 是唯一改父进程的写法，因此它是"整脚本日志重定向"的唯一手段，代价是此后所有输出（包括错误提示）都离开终端。若要恢复，必须显式保存与还原（`exec 3>&1` 保存槽位 1，`exec 1>f`，稍后 `exec 1>&3`）——这里 `3>&1` 只在 fd 表里新增一个槽位，`>&3` 再把槽位 1 指回去，两次操作都不产生新文件。

重定向的失败也发生在 fork 之后：`> /root/x` 在普通用户下 `open` 返回 `EACCES`，Shell 打印错误并**不执行**该命令，退出码 1。因为 open 在子进程里，父 Shell 只能通过退出码得知失败——这就是"重定向失败不终止脚本（除非 `set -e`）"的原因。

## 四、管道：`pipe()` 两端与 N 子进程

### 1. 匿名 pipe 的环形缓冲与三个阻塞点

管道在机制上是一对 fd 指向内核里的一个缓冲区，加上两个等待队列。它的行为由容量与原子性两个常数决定：

```text
   写端 fd[1]                                    读端 fd[0]
       │                                              │
       ▼                                              ▼
  ┌─────────────────────────────────────────────────────────┐
  │  内核 pipe_inode_info：环形缓冲（默认 16 页 = 64 KiB 档） │
  │   ┌────┬────┬────┬────┬────┬────┬────┬────┐             │
  │   │ 已用 │空 │    │    │    │    │    │    │             │
  │   └────┴────┴────┴────┴────┴────┴────┴────┘             │
  │   写指针 ──►                        ◄── 读指针            │
  ├─────────────────────────────────────────────────────────┤
  │  写等待队列（缓冲满时睡）    读等待队列（缓冲空时睡）        │
  └─────────────────────────────────────────────────────────┘
```

三条阻塞边是理解所有管道行为的钥匙。**写满即阻塞**：缓冲剩余空间不足以容纳本次写入时，`write` 要么部分写并返回已写字节数，要么（在阻塞模式下）睡在写等待队列直到读者腾出空间——因此"生产快于消费"不会丢数据，只会把压力反推到写进程。**读空即阻塞**：缓冲为空且写端仍开着时，`read` 睡在读等待队列；**写端全关**时 `read` 立即返回 0（EOF），这是管道唯一的流结束信号。**原子写边界**：单次 `write` 不超过 `PIPE_BUF`（4096 字节）时不会被其他写者插入分割，超过则可能交错——这是多进程写同一管道时必须按行小块写的原因。

容量不是固定的：`F_SETPIPE_SZ` 可把缓冲调到 1 MiB 档，也就把"写满阻塞"的阈值提高 16 倍。这个可调项解释了一个常见误判：同一段生产/消费代码在不同环境里表现不同，往往不是调度差异，而是管道容量不同导致阻塞时机不同。

### 2. N 段管道的 fd 拓扑与计数

`a | b | c` 在 Shell 里展开为一组固定数量的系统调用。以 3 段管道为例，Shell 先建 2 个管道（4 个 fd），再 fork 3 个子进程，每个子进程把自己那两端接到 0/1 上：

```text
  父 Shell：pipe(p1) → pipe(p2)
     fd: 3=p1[0] 4=p1[1] 5=p2[0] 6=p2[1]
        │
        ├── fork ──► 子 A：dup2(3,0)? 否；dup2(4,1)  → close 3,4,5,6
        │              （A 只写 p1：1 ← p1[1]=4）
        ├── fork ──► 子 B：dup2(3,0)、dup2(6,1)     → close 3,4,5,6
        │              （B 读 p1、写 p2）
        └── fork ──► 子 C：dup2(5,0)                → close 3,4,5,6
                       （C 只读 p2：0 ← p2[0]=5）
  父：close 3,4,5,6（4 次）→ waitpid × 3
```

| 管段数 $k$ | `pipe()` 次数 | `fork()` 次数 | `dup2()` 次数 | `close()` 次数 | 在途 fd 峰值 |
| --- | --- | --- | --- | --- | --- |
| 1 | 1 | 2 | 2 | 6 | 4 |
| 2 | 2 | 3 | 4 | 12 | 6 |
| 3 | 2 | 3 | 6 | 16 | 8 |
| $k$ | $k-1$ | $k$ | $2(k-1)$ | $2(k-1)+4+4k$ 化简为 $6k-2$ | $2(k-1)+2$ |

表的读法是：进程数随段数线性增长，系统调用数也随之线性增长，而每组管道增加 2 个在途 fd。这意味着"把命令拆成更多段"的代价是**确定且可预算的**：每加一段，多 1 个进程、2 次 `dup2`、约 6 次 `close`、2 个 fd。

### 3. 关闭顺序与 `SIGPIPE`

管道的正确性依赖一个容易被忽略的动作：**父 Shell 必须关闭自己持有的全部管道 fd**。若父进程保留写端不关，读端永远等不到"写端全关"，EOF 不会到来：

```text
   A. 正确：父关闭两端          B. 漏关写端                C. 读端提前退出
   子写 → 子关写端 → 父关       子写 → 子关写端 → 父仍持写端   读端 close
   → 读端 read 返回 0（EOF）    → 读端永久阻塞（可数：不返回）  → 写端 write 收到 SIGPIPE
```

A 路径是正常终止：EOF 由"写端引用计数归零"触发，而不是由某个特殊字节触发——这解释了为什么二进制数据可以安全地流经管道（不存在保留的 EOF 字节）。B 路径是 `cat f | ssh host cmd` 类挂起的根因：`ssh` 退出后若某个进程还持着写端，下游 `cat` 永远等不到 EOF。C 路径是 `yes | head -1` 的机制：`head` 读够 1 行即关闭读端，`yes` 的下一次 `write` 触发内核投递 `SIGPIPE`，默认动作是终止——因此 `yes` 不是被 `head` "通知"退出的，而是被信号杀死的。

要区分 B 与 C，只需看是"卡住"还是"被杀"：卡住说明某个写端没关（引用计数不为零），被杀说明读端已消失。两者都不涉及数据丢失，只涉及引用计数的两个方向。

## 五、fork-exec 与进程创建开销

### 1. `fork()` 的写时复制与页表账本

`fork` 不复制数据，它复制**页表**并把所有可写页标记为只读、父子共享。这条设计把"创建一个进程"的成本从"复制整个地址空间"降到"复制页表 + 设置写保护"：

```text
   父进程地址空间                     子进程地址空间
   ┌──────────────┐                  ┌──────────────┐
   │ 虚拟页 → 物理页 │  ── 复制页表 ──►  │ 虚拟页 → 同一物理页 │
   │ 权限 RW        │                  │ 权限 R（写保护）    │
   └──────┬───────┘                  └──────┬───────┘
          │ 任一方写入                      │
          ▼                                 ▼
   触发写保护缺页 ──► 内核复制该页 ──► 双方各得 1 个私有副本（1 页 COW）
```

这条图上只有一条"付费边"：首次写入。因此 `fork` 的固定成本与**页表规模**成正比，而不是与数据量成正比：一个 1 GiB 常驻内存的进程约有 26 万个 4 KiB 页，多级页表条目合计数百 KB 到 1 MB 档，`fork` 要为这些条目分配并复制——几十到数百微秒档；而一个几 MB 的小进程在数十微秒档内完成。这就是"fork 大进程很贵、fork 小进程很便宜"的量化来源。

子进程若立刻 `execve`，刚刚复制的页表会被整体丢弃，写时复制的收益归零。因此现代 C 库与运行时提供 `posix_spawn`（内部用 `CLONE_VM` 共享地址空间的变体），把"复制页表"这一步直接省掉——`posix_spawn` 的进程创建成本比 `fork` + `execve` 低一个档位，但它放弃了"在 fork 与 exec 之间修改子进程状态"的能力。

### 2. `execve()` 的镜像替换与动态链接器

`execve` 把当前进程的地址空间整体换成新程序的镜像，pid 不变。它的成本由三段构成，且第三段最容易被忽略：

```text
   execve("/bin/ls", argv, envp)
        │
        ├─ ① 内核：读 ELF 头，校验，卸载旧地址空间        数十微秒档
        ├─ ② 内核：按 PT_LOAD 段 mmap 代码/数据，设栈      数十微秒档
        └─ ③ 回到用户态：动态链接器 ld.so 解析依赖并重定位  百微秒~毫秒档
              · 读 /etc/ld.so.cache 找 .so 路径
              · mmap 每个依赖库，符号绑定（lazy 或 now）
              · 运行库的初始化函数（.init_array）
```

三段成本的排序是固定的：①、② 与二进制大小弱相关，③ 与**动态库数量**强相关。一个只依赖 libc 的程序在第三段花百微秒档；一个依赖几十个库的 GUI 程序可以到毫秒档。这解释了两件事——静态链接程序启动快（跳过 ③ 或大幅缩短），以及"容器里首次启动慢、之后快"主要是页缓存与 `ld.so.cache` 已就绪。

`execve` 只保留三样东西跨越边界：pid、未置 `CLOEXEC` 的 fd 表、以及调用者提供的 `argv`/`envp`。信号处理函数被重置为默认动作（被忽略的信号仍保持忽略），地址空间、堆、栈内容全部丢弃。这三条"保留/丢弃"清单是后面所有"为什么子进程看不到父进程的变量/为什么 `trap` 在 `exec` 后失效"的答案。

### 3. 内建、函数与外部命令的账本

同一个动作用不同形态执行，进程账本差一个数量级：

| 形态 | 例 | `fork` | `execve` | 典型完成时间档 | 能否改变父 Shell 状态 |
| --- | --- | --- | --- | --- | --- |
| 内建命令 | `cd`、`export`、`read` | 0 | 0 | 数十微秒档 | 能（同进程） |
| 函数 | 自定义 `f()` | 0 | 0 | 数十微秒档 | 能（同进程，`local` 除外） |
| 外部命令 | `/bin/ls` | 1 | 1 | 毫秒档 | 不能 |
| 带 shebang 的脚本 | `./x.sh` | 1 | 2 | 毫秒档 + 解释器启动 | 不能 |

第四行的 2 次 `execve` 来自 shebang：内核先 exec 解释器，解释器再读脚本（若 shebang 写的是 `env`，则中间还有第 3 次）。这也解释了为什么"脚本里 100 次外部命令"的墙钟时间主要由 100 次 fork+exec 决定，而不是由脚本本身的语法复杂度决定——**控制流的开销可以忽略，进程创建的开销不能**。

一条可核验的对照：在同一台机器上循环执行 `cd /` 与 `/bin/true` 各 1000 次，前者总耗时在毫秒档（纯用户态），后者在秒档（1000 次 fork + exec）。两者的差就是进程创建开销的实测下界。

### 4. 优化路径：`exec`、隐式 exec 与进程复用

Shell 有三条把进程创建成本压回去的路径，机制各不相同：

```text
  A. exec cmd          → 当前进程被替换：fork 0 次，Shell 自身消失
  B. 脚本最后一条命令    → 解释器可隐式 exec：省 1 个常驻进程
  C. 内建/函数替代外部   → 0 次创建（如 printf 替代 echo 外部版）
```

A 与 B 的共同点是**消除一个本可避免的进程**：`exec` 之后 Shell 不再存在，因此"退出码"直接由目标程序提供；`bash -c 'cmd'` 在无 trap、无后续命令时会做同样的隐式替换。C 的收益最大但适用范围最窄：能用内建完成的操作（字符串处理、算术、文件测试）完全没有进程开销，一旦需要真正的程序（`grep`、`sed`、`awk`）就必须付一次创建成本。

三条路径都不能改变一个事实：**每一次外部命令执行都是一次完整的进程生命周期**（创建、装载、运行、回收），因此"用 100 个管道段处理 100 行"在任何优化下都比"1 个进程处理 100 行"贵两个数量级档。

## 六、环境变量与作业控制的继承

### 1. 从 `environ` 到 `envp`：两次拷贝与一次过滤

环境不是"继承的一块内存"，而是一个字符串数组在两次边界上的复制：

```text
   父进程 environ（char *[]，仅含已导出项）
        │
        ▼  ① fork：地址空间写时复制，environ 指针随页表共享（0 次额外拷贝）
        │
        ▼  ② execve(..., envp)：内核把字符串数组逐项复制到新进程栈顶
        │     · 拷贝字节数 = Σ(名 + '=' + 值 + '\0')
        │     · 未导出变量根本不在 environ 里，故 0 字节过界
        ▼
   子进程 environ（栈上的新副本，与父进程的修改完全隔离）
```

两条边对应两个可观测事实。**边①**不产生拷贝，因此 `fork` 之后、`exec` 之前子进程看到的变量与父进程一致（同一批字符串）。**边②**是唯一的数据搬运点，搬运量等于导出变量总字节数——这解释了为什么把大块数据塞进环境变量（如几 MB 的证书内容）会让每次外部命令启动都变慢：不是"环境变量慢"，而是每次 exec 都要拷贝那几 MB。

环境还有一个不可见的边界：**子进程无法把变量传回父进程**。任何 `export` 都只影响本进程及其后续子进程，因此 `cd`/`export` 必须是内建——外部程序改不了父进程的 cwd 与环境，这正是"`cd` 写成外部命令就无效"的机制原因。

### 2. 三档赋值的作用域

赋值有三种写法，作用域依次扩大：

| 写法 | 生效范围 | `fork` 后可见 | `execve` 后可见 | 父 Shell 是否受影响 |
| --- | --- | --- | --- | --- |
| `a=1` | 当前 Shell 的变量表 | 是（同一批字符串） | 否（未导出） | 是 |
| `a=1 cmd` | 仅 `cmd` 这一个进程 | 是 | 是（临时 envp） | 否（命令结束即撤销） |
| `export a=1` | 当前 Shell 且标记导出 | 是 | 是 | 是（后续子进程都可见） |

第二行是一次**临时环境块**的构造：Shell 在 fork 之后、exec 之前把 `a=1` 追加进 envp 数组，`execve` 用它，命令结束后该数组丢弃——父 Shell 的 `environ` 一个字节都没变。这条机制是"`PATH=/tmp ./x` 只影响这一次执行"的全部原因，也是"`a=1 sleep 1` 之后 `$a` 仍为空"的解释。

`set -a` 是第四种形态：它把后续所有赋值自动打上导出标记（等价于每条赋值都加 `export`），因此子进程能看到全部变量。反过来 `set +a` 关闭。这条开关常被用于"整份配置一次性传给子进程"，代价是每个子进程的 envp 都变长。

### 3. 进程组与前台权的继承

进程组与终端前台权已经在 01 篇建立（`TIOCSPGRP` 与 `SIGTTIN` 三条边），这里只补它在 Shell 侧的一次初始化：交互式 Shell 启动时必须把自己设为独立进程组并取得前台权，否则它自己就是后台进程，读终端会被停止。

```text
   登录 shell 启动
        │
        ├─ ① setpgid(0, 0)          自建进程组，pgid = 自己的 pid
        ├─ ② tcsetpgrp(0, pgid)     把自己的组设为前台（内部 TIOCSPGRP）
        └─ ③ signal(SIGTTOU, SIG_IGN) 忽略"后台写"信号，否则 ② 会把自己停掉
```

三步的顺序不可交换：先建组、再交前台、并在此过程中忽略 `SIGTTOU`——因为 ② 本身是"后台进程组修改终端属性"，若未忽略就会被自己的操作停止，形成启动即挂死的死锁。这条自指的边界说明作业控制不是"Shell 管理子进程"的单向关系，而是 Shell 必须先把自己纳入同一套规则。

之后每条外部命令都由 Shell `fork` 出子进程并 `setpgid` 进新组，前台权在"Shell 组"与"作业组"之间来回转移。非交互 Shell 完全跳过这三步：它没有控制终端前台权，也没有作业可管，因此 `set -m` 关闭时所有命令都在 Shell 自己的进程组里跑——这也意味着脚本里 `Ctrl-C` 会同时打到脚本与子进程（同组），而不是只打前台作业。
