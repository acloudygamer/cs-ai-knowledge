# 进程与线程

## 一、双实体：资源容器与调度实体的切分面

### 1. 一个容器装什么：共享项与独占项的清单

「进程」这个词在两种场合被当成两件不同的事使用：它既是资源的持有者（地址空间、打开的文件、凭据），又是被调度运行的单位。两个角色一旦绑死，同一时刻就只能有一个执行流，于是「一个进程内并发」只能靠多进程实现，每次切换都要换地址空间。把两个角色拆开，得到的是进程（资源容器）与线程（调度实体）——容器负责「有什么」，实体负责「谁在跑」。

拆分的判据不是「概念上属于谁」，而是「换掉它是否需要付出复制成本」。凡是复制一次就要跨页表、跨文件表、跨安全令牌的东西，留在容器里共享；凡是复制一次只是几十字节到几 KiB 连续内存的东西，下沉到实体里独占。

```text
 ┌───────────────────── 进程（资源容器）─────────────────────┐
 │  地址空间：CR3/页表树 · 映射区表 · 驻留集                 │
 │  打开文件表：fd 表（Linux）/ 句柄表（NT）                 │
 │  凭据：uid/gid 与能力集（Linux）/ 访问令牌（NT）          │
 │  信号处置表 · 文件系统根与当前目录 · 资源限制 · 会话/进程组│
 │                                                            │
 │   ┌──────── 线程 A（调度实体）────────┐  ┌──── 线程 B ────┐│
 │   │ 用户栈 + 内核栈（各 16~24 KiB 档）│  │ 同构，各自独立 ││
 │   │ 寄存器现场（16 GPR + RIP/RFLAGS） │  │                ││
 │   │ TLS 基址（FS/GS）· 浮点与向量状态 │  │                ││
 │   │ 调度参数（优先级/亲和）· 信号掩码 │  │                ││
 │   └───────────────────────────────────┘  └────────────────┘│
 └────────────────────────────────────────────────────────────┘
```

清单里有两项容易被误归类。其一是「信号掩码」：信号处置表（哪个信号走哪个处理函数）属于容器，而「当前阻塞了哪些信号」属于实体——因为掩码是每线程独立的，`pthread_sigmask` 改的是调用线程。其二是「错误码」：`errno` 在 Linux 上是每线程一份的（TLS 里的一个整数），因为两个线程同时失败时不能互相覆盖返回值；这条设计把「返回值」与「错误码」的存储位置分到了两个层级。

| 资源项 | 容器级共享 | 实体级独占 | NT 承载结构 | Linux 承载结构 |
| --- | --- | --- | --- | --- |
| 地址空间 | 是（线程切换不换 `CR3`） | 否 | `EPROCESS`（Executive Process，进程执行体）内嵌的 `KPROCESS` | `mm_struct`（`task_struct.mm`） |
| 打开文件表 | 是（`dup` 与线程共享同一表） | 否 | 进程句柄表 | `files_struct`（`task_struct.files`） |
| 凭据 | 是 | 否 | `EPROCESS.Token` | `cred`（`task_struct.cred`） |
| 信号处置 | 是（进程级安装） | 掩码独占 | 无直接对应（APC 与异常端口代偿） | `sighand_struct` + 每线程 `blocked` |
| 栈与寄存器现场 | 否 | 是 | `ETHREAD` + 内核栈 | `task_struct.stack` + `thread_struct` |
| TLS 基址 | 否 | 是 | `TEB`（Thread Environment Block，线程环境块；`ETHREAD.Teb`） | `task_struct.thread.fsbase` |
| 调度参数 | 否 | 是 | `KTHREAD.Priority` | `task_struct.prio` / `se` |
| 错误码 | 否 | 是 | `TEB.LastErrorValue` | TLS 中的 `errno` |

最后一行值得单独确认：`TEB`（线程环境块）挂在 `ETHREAD` 上而不是 `EPROCESS` 上，因此 `GetLastError()` 读的是本线程的 `TEB.LastErrorValue`，一个线程失败不会污染另一个线程的错误码。这和 Linux 把 `errno` 放进 TLS 是同一个决定，只是 NT 把整个 `TEB` 都做成了「线程私有的一页用户态结构」。

### 2. 一个结构对两个结构：`task_struct` 与 `EPROCESS`/`ETHREAD`

两侧对「容器与实体」的建模方式不同，这个差异决定了后续所有创建、销毁、遍历代码的形状。

Linux 用**一个** `task_struct` 表示两种角色。进程与线程的区别不在结构类型，而在**哪些字段是指针、哪些字段是副本**：`clone` 时若置 `CLONE_VM`，新 `task_struct.mm` 直接指向父的 `mm_struct` 并把引用计数加 1；若不置，则调用 `dup_mm` 复制一份。fd 表（`CLONE_FILES`）、文件系统上下文（`CLONE_FS`）、信号处置（`CLONE_SIGHAND`）同理。于是「创建线程」与「创建进程」是同一条代码路径，差别只是一组比特位。

NT 用**两个**结构。`EPROCESS` 持有地址空间、句柄表、令牌、配额，`ETHREAD` 持有栈、上下文、优先级、`TEB`，`ETHREAD.ThreadsProcess` 回指所属 `EPROCESS`。结构类型在编译期就固定了角色，不存在「一个结构有时当进程用」的情形：NT 没有「跨进程线程」，任何线程必须挂在某个进程下，进程退出时其下所有线程被终止。

```text
 ── Linux：一个结构 + 标志位 ────────────────────────────────
   fork()  ──► clone(SIGCHLD, 0)          mm 复制（dup_mm）
   pthread_create() ──► clone(CLONE_VM|CLONE_FS|CLONE_FILES|CLONE_SIGHAND|CLONE_THREAD|...)
                                          mm / files / sighand 全部共享（指针 + 引用计数）
   ── 两者都是 1 次 clone 系统调用，差别只在标志位

 ── NT：两个结构，角色编译期固定 ─────────────────────────────
   CreateProcess() ──► 1 次 NtCreateUserProcess ──► EPROCESS + 首个 ETHREAD
   CreateThread()  ──► 1 次 NtCreateThreadEx    ──► 仅 ETHREAD，挂到既有 EPROCESS
   ── 线程创建不碰地址空间：新线程直接沿用 EPROCESS 的页表树
```

标志位之间存在强制蕴含关系，这一点是 `clone` 语义的核心：`CLONE_THREAD` 要求 `CLONE_SIGHAND`，而 `CLONE_SIGHAND` 要求 `CLONE_VM`。原因是线程组共享信号处置表，而处置函数运行在某个线程的栈上、操作同一批地址，若两个「线程」各自有独立地址空间，信号处理函数就无法在两者间通用。内核在 `clone` 入口处显式校验这三者的组合，不合法的组合直接返回 `EINVAL`——这条例行检查把「线程」定义成了一个不可拆的共享三元组：地址空间、信号处置、文件表。

### 3. 切分之后得到的三个可观测后果

第一个后果在切换成本上。线程切换只需保存实体级现场（6 个 callee-saved 通用寄存器加 `RSP`/`RIP`/`RFLAGS`，见 02 篇的保存集），不需要写 `CR3`；进程切换要额外换页表树根。02 篇已经量过：空载切换 1~3 µs 档，而真正拉开差距的是换树根引发的 TLB 行为——`CR3` 写入会按 PCID 标签保留旧条目，但新进程的工作集仍需重新预热，代价在毫秒档的可观测抖动上。

第二个后果在通信成本上。同一容器的两个线程共享地址空间，交换数据只需传指针（0 次拷贝、0 次陷门）；两个进程交换数据必须经内核对象（管道 2 次拷贝，见后文）或显式共享映射。这条差异是「线程比进程轻」的真实来源——不是创建更便宜，而是**数据交换不跨容器**。

第三个后果在故障域上。线程崩溃会带走整个容器（同一地址空间，一个线程写坏页表链，其余线程一起遭殃），进程崩溃只影响自己。所以「用多进程还是多线程」的判据不是性能，而是「故障是否必须被隔离」：浏览器把每个标签页放进独立进程，正是为了让渲染引擎的崩溃不带走其余标签页。

## 二、创建与销毁：`fork` 加 `exec` 两跳与 `CreateProcess` 一跳

### 1. 两跳路径：`fork` 复制了哪些表、没复制哪些页

`fork` 的语义常被概括成「复制进程」，实际复制的东西可以逐项列清：复制页表（不是页框）、复制 fd 表（并把每个打开文件的引用计数加 1）、复制信号处置表、复制文件系统上下文（根目录与当前目录的引用计数加 1）、分配新 pid 与新 `task_struct`。物理页框一个都不复制，全部标成写时复制。

```text
 fork()  ── 1 次 clone 系统调用
   │
   ├─① 分配 task_struct + 内核栈（16 KiB 档，4 页）
   ├─② dup_mm：复制页表页，所有 PTE 清可写位、标 COW；页框引用计数 +1
   ├─③ copy_files：复制 fd 表，每个 struct file 的 f_count +1（0 次数据拷贝）
   ├─④ copy_sighand / copy_fs：处置表与目录上下文引用计数 +1
   ├─⑤ 分配 pid，插入调度队列，返回两次
   ▼
 父进程拿到子 pid，子进程拿到 0 —— 一次系统调用，两条返回路径

 execve() ── 1 次系统调用
   ├─① 校验并读取镜像头（ELF/PE），决定装载布局
   ├─② 拆掉旧地址空间：mmput 释放旧页表树与驻留页（写时复制的页此刻才真正结算）
   ├─③ 新建 mm，按段建立映射：代码段私有可执行、数据段私有可写、共享库文件映射
   ├─④ 布置栈与辅助向量（argv/envp/auxv），设置入口点
   └─⑤ 返回用户态，从新入口的第一条指令开始执行
```

第 ②步的成本需要单独量化：复制的不是数据而是页表页，每个页表页 4 KiB、覆盖 512 个页表项，因此复制成本线性于**已映射的虚拟地址范围**而非驻留页数。一个映射了 1 GiB 的进程调用 `fork`，需要复制约 512 个页表页（约 2 MiB 内存），哪怕其中只有几十 MiB 真正驻留。这也解释了「大内存进程 `fork` 变慢」的现象：慢在页表遍历与标 COW，不在拷数据。

第 ②步与 `execve` 的第 ②步是一对账：`fork` 标的 COW 在子进程 `exec` 时被整体丢弃（旧地址空间整个卸载），因此「`fork` 后立刻 `exec`」的场景下，COW 缺页一次都不会发生，复制的页表页随即被释放。这条「标了但不用」的路径是 `fork` 加 `exec` 在服务器程序里仍能接受的根本原因；`vfork` 与 `posix_spawn` 则进一步把页表复制本身也省掉，做法是让父子共享同一份地址空间（`CLONE_VM`）并挂起父进程直到子进程 `exec` 或退出（`CLONE_VFORK`），把「复制页表」压到 0 次。

销毁侧与创建侧对称。`exit` 释放地址空间（页表树与驻留页）、关闭 fd 表（每个 `struct file` 的 `f_count` 减 1）、释放凭据与信号处置表，但保留 `task_struct` 与退出码，等待父进程 `wait` 收尸。这里有一个必须点明的顺序约束：fd 表必须在地址空间之后关闭，因为某些文件的关闭路径（如 `mmap` 过的文件在最后一页被释放时）需要访问已映射的地址；调换顺序会在关闭阶段触发对已卸载映射的访问。

### 2. 一跳路径：`CreateProcess` 的装配顺序

NT 没有 `fork`。`CreateProcess` 从零装配一个新容器，装配过程由内核在一次系统调用内完成，用户态负责的是「把参数打包」而不是「逐步构造」。

```text
 CreateProcess("app.exe")  ── 用户态：kernel32 组装参数
   ├─① 解析 STARTUPINFOEX：属性列表携带句柄白名单、父进程、作业对象、桌面
   ├─② 1 次 NtCreateUserProcess，参数含镜像路径、属性列表、继承标志
   ▼
 NtCreateUserProcess ── 内核态：一次装配
   ├─③ 打开镜像文件 → 建节对象（Section），映射为镜像视图
   ├─④ 新建地址空间：新 PML4，内核半区表项共享，用户半区装 ntdll 与镜像
   ├─⑤ 建 EPROCESS：句柄表（按白名单复制父进程可继承句柄）、令牌、配额
   ├─⑥ 建首个 ETHREAD：分配内核栈（x64 上 12~24 KiB 档）、设入口点、插入就绪队列
   └─⑦ 失败回滚：任一步失败即按逆序释放已建对象，不留半成品进程
```

第 ③步的「节对象」是 NT 特有的中间层：镜像不是被读进内存再拷贝，而是先变成一个可映射的节对象，再由地址空间把节映射进来。这层多出来的对象带来一个可观测的好处：同一镜像被多次启动时，代码段在物理内存里只有一份，各进程各自映射——共享粒度由节对象统一管理，不需要每个进程各扫一遍文件。

第 ⑥步的数量级差异值得记住：线程创建不复制地址空间，只分配一枚内核栈（12~24 KiB 档）与一个 `ETHREAD`（1 KiB 量级），因此 NT 上「多线程」比「多进程」便宜得多，与 Linux 的结论同向。

### 3. 两跳与一跳的账本对照

| 阶段 | Linux `fork` + `execve` | NT `CreateProcess` | 差异方向 |
| --- | --- | --- | --- |
| 系统调用次数 | 2 次 | 1 次 | NT 少 1 次陷门 |
| 页表复制 | 1 次，线性于已映射范围 | 1 次，线性于镜像与 `ntdll` 大小 | 同阶；`fork` 侧可能复制无用区域 |
| 页框复制 | 0 次（全标 COW） | 0 次（按需缺页） | 相同 |
| fd/句柄继承 | 默认全继承，除 `FD_CLOEXEC` | 默认不继承，除置了可继承位 | 默认方向相反 |
| 失败回滚 | 父进程检查返回值即可，无半成品 | 内核逆序释放，不留半成品 | 语义等价 |
| 中间态可观测 | 有：`fork` 后 `exec` 前可改 fd、改优先级、设 `rlimit` | 无：一步到位，只能在属性列表里预设 | `fork` 更灵活，代价是多一跳 |

「默认方向相反」这一行是移植时最容易出错的地方。Linux 的 fd 默认被 `exec` 继承，所以程序必须在打开时主动打 `FD_CLOEXEC`（或用 `O_CLOEXEC`），否则子进程会意外持有不该持有的文件；NT 的句柄默认不继承，必须在创建时置可继承位，且还要在 `CreateProcess` 的属性列表里显式列入白名单才会真正传过去。两侧都在往「显式优于隐式」的方向演进：Linux 的新接口普遍默认带 `CLOEXEC`，NT 则用属性列表取代了早期的「继承标志一把梭」。

## 三、调度：选体判据、时间片量级与抢占点

### 1. Linux 侧：虚拟运行时间与合格集合

Linux 6.8 的默认调度器是 EEVDF（Earliest Eligible Virtual Deadline First，最早合格虚拟截止期优先），它在 6.6 中取代了 CFS。判据由三个量构成：`vruntime`（按权重折算后的累计运行时间）、`lag`（应得份额与实得份额之差）、以及由 `vruntime` 加基准时间片得到的虚拟截止期。

`vruntime` 的推进速度与权重成反比，因此高权重（低 nice 值）的实体每跑一个 tick 只累积很少的虚拟时间，从而在红黑树里更靠前。`lag` 度量「欠账」还是「透支」：长时间没被调度的实体 `lag` 为正，说明它应得而未得；刚被调度过的实体 `lag` 为负。EEVDF 把这些实体分成两堆——`lag` 不为负的是「合格」集合，只有合格集合里的实体才有资格被选中，选中的是其中虚拟截止期最早的那一个。

```text
 EEVDF 选体（每个 CPU 一棵红黑树，按虚拟截止期排序）
   ├─① 新唤醒实体的 lag = 应得份额 − 实得份额（长时间睡眠者 lag 显著为正）
   ├─② 合格判定：lag ≥ 0 者进入候选；透支者即使截止期更早也不选
   ├─③ 选体：候选集中虚拟截止期最小者（红黑树最左节点），复杂度对数级
   ├─④ 让出：时间片耗尽或主动 schedule()，vruntime 按权重折算后前进
   └─⑤ 抢占点：返回用户态、中断返回、显式调度点；内核态默认不抢占（可配置）
```

这套判据解决的是 CFS 的一个具体毛病：CFS 只按最小 `vruntime` 选体，一个刚被唤醒的短任务因为睡了很久而 `vruntime` 极小，会立刻抢走 CPU，导致交互延迟不可控。EEVDF 用 `lag` 把「欠账」与「截止期」分开，短任务仍能被及时响应，但不会无限透支——`lag` 被限制在基准时间片的正负一档内，超出部分不再累积。这条截断是防止「睡眠越久优先级越高」被滥用的关键。

时间片的量级由两个参数共同决定：目标延迟 `sysctl_sched_latency`（默认 6 ms）给出「一轮内所有就绪实体都被服务一次」的时窗上界，基准时间片参数给出单个实体一次最多能跑多久，权重越高的实体分到的片越长。就绪实体数增加时，每人的片按比例缩短，短到低于最小粒度时不再缩短，改为「一轮装不下所有人」——此时高权重实体的份额优势才真正体现为「跑得更频繁」而不是「跑得更久」。

### 2. Windows 侧：32 级优先级与就绪位图

NT 的调度器用一个固定的 32 级优先级空间：0~31，数值越大越优先。0 级留给零页线程，31 级是实时级；普通进程的默认级为 8，`IDLE`、`BELOW_NORMAL`、`ABOVE_NORMAL`、`HIGH`、`REALTIME` 各自映射到固定档位。每个处理器维护 32 条就绪队列，外加一个 32 位掩码记录哪些队列非空——选体就是在这个掩码里找最高置位，一条位扫描指令即可完成，与就绪实体数无关。

```text
 NT 选体（每处理器一张 32 位就绪掩码 + 32 条队列）
   ├─① 线程就绪时按优先级挂入对应队列，置位掩码第 n 位
   ├─② 选体：掩码最高置位 → 该优先级队列的队首（常数级，与线程数无关）
   ├─③ 同级轮转：队列内按 quantum 计数，耗尽后移到队尾
   ├─④ 优先级提升：等待同步对象返回、IO 完成、前台窗口等场景临时 +1~+2 档
   └─⑤ 抢占：更高优先级就绪时发软件中断，在 IRQL < DISPATCH_LEVEL 处立即切换
```

`quantum` 以时钟 tick 的整数倍计，典型落在十余毫秒档，比 Linux 的 6 ms 目标延迟更粗。方向上的后果是：Windows 的切换次数更少、单次等待更长，交互响应更依赖「优先级提升」这条补偿路径而不是缩短时间片。前台窗口线程会获得 quantum 加权（可配档位），这是 NT 用「加长时间片」而非「提高优先级」来照顾交互的选择——加长时间片不改选体顺序，只让前台线程在被选中后跑得更久。

两侧的复杂度方向也相反。Linux 用红黑树，选体是对数级但对就绪实体数不敏感地平滑；NT 用位图加队列，选体是常数级但对优先级的粒度敏感（只有 32 档，档内无法再区分）。这条差异决定了调优手段的不同：Linux 上调 nice 值是在连续权重空间里挪位置，NT 上调优先级是在 32 个离散档位里跳格，且跳格会影响抢占判定（高优先级一旦就绪立即抢占，不留时间片余量）。

### 3. 两条路径的量化对照

| 维度 | Linux 6.8（EEVDF） | Windows 11（32 级） | 方向 |
| --- | --- | --- | --- |
| 选体判据 | 合格集合内最早虚拟截止期 | 最高非空优先级队列队首 | 前者连续、后者离散 |
| 选体复杂度 | 红黑树，对数级 | 32 位掩码位扫描，常数级 | NT 更快，但档位更粗 |
| 权重表达 | nice 值映射到权重，权重比即份额比 | 32 个离散优先级档 | Linux 连续可调 |
| 时间片量级 | 目标延迟 6 ms 上界，按权重缩放 | quantum 十余毫秒档 | 同数量级档，NT 更粗 |
| 交互补偿 | `lag` 让欠账者优先，无需提权 | 优先级临时提升 + 前台 quantum 加权 | 机制不同，目标相同 |
| 抢占时机 | 返回用户态、中断返回、显式调度点 | 更高优先级就绪即在可抢占点切换 | NT 抢占更即时 |
| 观测入口 | `/proc/<pid>/sched`、`schedstat` | `GetThreadPriority`、性能计数器 | 均可读 |

两条路径的共同下界是 02 篇量过的切换成本：一次 1~3 µs。因此任何调度策略都无法把时隙压到切换成本以下，能优化的只有「选谁」与「选多久」。表格最后一行给出的观测入口值得实际读一次：在 Linux 上读 `/proc/<pid>/sched` 能看到 `se.sum_exec_runtime` 与 `nr_switches`，两者相除即得平均时隙；在 Windows 上用性能计数器读「上下文切换/秒」与「处理器时间占比」，可反推同一量级。两个读数落在同一档内，就是「调度策略不同但物理下界相同」这句话的可核验形式。

## 四、同步与通信：跨实体边界的数据搬运账

### 1. 同一容器：0 次拷贝的数据路径，同步是唯一税项

两个线程共享同一 `mm_struct`，交换数据的物理路径只有一条：双方 PTE 指向同一物理页，一方的写经缓存一致性协议可见于另一方。这条路径上没有内核参与、没有数据拷贝、没有陷门——「线程比进程轻」的绝大部分来自这里，而不是创建开销。代价整体转移到同步面：没有所有参与者都承认的顺序点，两个写者就会互相覆盖。

```text
 ── 数据面：0 次拷贝 ─────────────────────────────────────────
   线程 A                        线程 B
   写 x = 1 ──► 同一物理页 / cache line ◄── 读 x
                 （MESI 状态迁移，数十拍档）
 ── 控制面：按争用程度分三档 ─────────────────────────────────
   ① 未争用：用户态原子指令（lock cmpxchg / LL-SC），$O(1)$ 拍
   ② 短暂争用：自旋 + 退避，仍在用户态，百拍档
   ③ 需睡眠：1 次陷门，挂入内核等待队列，1~3 µs 档
```

第 ③档的分界线由两侧各自的机制划定，形状几乎相同：Linux 的 `futex`（Fast Userspace muTEX，快速用户态互斥量）在内核里维护一张以用户态地址为键的等待队列哈希表，`pthread_mutex_lock` 的快路径只做一次 CAS，失败才以 `FUTEX_WAIT` 挂起；NT 的键控事件（Keyed Event）由 `SRWLock` 在 `lock cmpxchg` 失败后按「(地址, 进程)」为键向内核取一枚事件对象。两侧都把内核降格为「睡眠停车场」，判定留在用户态，只有真要让出 CPU 的实体才付费。

量化的方向比绝对值重要：未争用临界区在 20 ns 档，跨争用一次往返在 1~3 µs 档，相差两个数量级。因此锁优化的方向是降低争用率（缩临界区、分片计数、每线程缓冲），而非压缩慢路径——慢路径已贴着陷门成本的下限。

### 2. 跨容器：拷贝次数是硬账，选通道即选拷贝次数

两个进程不共享页表，任何数据都必须经过一次「双方都能访问的中转站」。中转站只有两类：内核缓冲区（拷贝两次）或共享映射（拷贝零次）。所有 IPC 机制都是这两类的组合。

| 通道 | 写侧拷贝 | 读侧拷贝 | 每消息陷门 | 单向带宽档 | NT 对应物 |
| --- | --- | --- | --- | --- | --- |
| 匿名管道 `pipe()` | 1（用户→内核缓冲） | 1（内核→用户） | 2 | 数 GB/s，单核上限 | 匿名管道 |
| UNIX 域流套接字 | 1 | 1 | 2 | 略低于管道（多一层 socket 层） | ALPC |
| 共享映射 `mmap(MAP_SHARED)` | 0 | 0 | 0（建映射后） | 内存带宽档，数十 GB/s | 节对象 + `MapViewOfFile` |
| `splice` 零拷贝转发 | 0（页引用移交） | 0 | 2 | 管道档 | 无直接对应 |
| 回环 TCP | 1 | 1 | 2 + 协议栈 | 数 GB/s，CPU 税最高 | 回环 TCP |

管道的两次拷贝是这套账的基准。以内存拷贝 10 GB/s 量级估算，1 KiB 消息的两次拷贝约 200 ns，与两次陷门（2~6 µs 档）相比反而是小头——这正是「小消息走管道、大消息走共享映射」这条经验规则的算术来源：消息越大，拷贝项越主导；消息越小，陷门项越主导。共享映射把拷贝项归零，代价换成一次建映射的固定开销与同步责任。

NT 侧有一个值得单独点出的折中：ALPC 对数百字节以内的小消息只做一次拷贝（拷进内核消息缓冲再映射到目标地址空间），超过阈值退化为节对象共享——按消息大小自动切换通道，而 Linux 侧要应用自己分流。

### 3. 事件模型：就绪通知与完成通知是两种因果方向

跨实体通信的第二个决策不是「怎么搬」，而是「谁来发起搬」。就绪模型把发起权留给应用，完成模型把发起权交给内核。

```text
 就绪模型（epoll / kqueue / select）
   应用：注册 fd 关注的事件 ──► 内核：事件发生时就绪链表追加一项
   应用：epoll_wait 取回就绪集合 ──► 应用自己 read（第 2 次陷门）
   因果：内核只回答「现在可读」，读多少、读几次由应用决定

 完成模型（IOCP）
   应用：投递 OVERLAPPED 请求 ──► 内核/驱动直接执行 IO
   完成：数据已在应用缓冲区，完成包入队 ──► GetQueuedCompletionStatus 取结果
   因果：内核回答「已经读完，结果在这里」，应用不再为取数据陷门
```

两种模型的差别落在每次事件的陷门次数上：就绪模型 2 次（等待加读取），完成模型 1 次投递加 1 次取完成，且读取不再陷门、完成包可成批取走；在每秒十万级事件的负载下，这个差额就是数万次陷门。

与事件模型同层的是「打断目标实体」的机制：Linux 的信号与 NT 的 APC（Asynchronous Procedure Call，异步过程调用）。两者都在目标线程的上下文里插一段代码，但生效条件不同——信号在任意指令边界生效（内核在返回用户态前检查待处理信号），用户态 APC 只在目标线程进入可警告等待（alertable wait）时投递。后果是：信号能打断一段纯计算，APC 不能；反过来，APC 的投递点确定，不必处理「在任意位置被中断」的重入问题。

## 五、亲和性与拓扑：实体钉在哪一层

### 1. 三层编号：掩码位宽决定可表达的范围

亲和性设置的表面语义是「让这个实体只在某些逻辑处理器上运行」，但三层编号空间决定了这句话能表达多远：用户态掩码 → 内核 `cpumask` → 物理 APIC ID。NT 在这条链上多插了一层「处理器组」，于是同一句语义在两侧的表达能力不同。

```text
 Linux：单一编号空间
   cpu_set_t（CPU_SETSIZE 默认 1024 位）──► 内核 cpumask ──► APIC ID
   一个实体的掩码可同时覆盖跨 socket 的任意核，无需额外 API

 NT：组是第一等公民
   GROUP_AFFINITY{ Group, Mask(64 位) } ──► 处理器组 ──► 物理包
   单次设置最多覆盖 64 个逻辑处理器；> 64 时线程默认只属于一个组
   跨组必须显式：SetThreadGroupAffinity / SetThreadIdealProcessorEx
```

| 维度 | Linux `sched_setaffinity` | NT 掩码与组 API | 方向 |
| --- | --- | --- | --- |
| 掩码位宽 | 1024 位（编译期可调） | 每组 64 位 | Linux 单掩码覆盖更宽 |
| 默认继承 | 子进程继承父掩码 | 线程继承进程默认组 | 同向 |
| 跨组/跨节点 | 同一 API 内完成 | 需切换 `GROUP_AFFINITY` | NT 多一次显式动作 |
| 查询接口 | `sched_getaffinity` | `GetThreadGroupAffinity` | 对称 |
| 与 NUMA 的关系 | 掩码隐含节点，`mbind`/`set_mempolicy` 分离控制 | 组与节点近似对齐 | 控制粒度不同 |

处理器组的成因是历史包袱：早期 NT 用 32 位掩码表示处理器集合，超过 32 个逻辑处理器就必须分组，这条边界固化进了 API；Linux 则把 `cpu_set_t` 做成定长位图，一次接口变更就换掉了上限。后果很具体：在 128 核机器上，Linux 一次 `sched_setaffinity` 就能表达「用 0~127 号核」，NT 必须逐组循环，并额外决定实体偏好哪一组。

### 2. 物理邻近：共享什么，决定迁移后还剩什么

亲和性的真实价值不在「绑定」这个动作，而在绑定位置的物理属性：同一 socket 内的核共享 L3，同一物理核的两个 SMT 兄弟共享 L1/L2 与执行单元，跨 socket 只能走互连。

```text
 Socket 0
  ├─ Core 0 ── L1i/L1d 32~48 KiB 私有 · L2 1~2 MiB 私有
  │    ├─ SMT 线程 0 ─┐ 共享 L1/L2 与执行单元，各自独立寄存器组
  │    └─ SMT 线程 1 ─┘
  ├─ Core 1 ── 同上
  └─ L3 切片（全片核共享，按物理地址散列到各切片）
        ▲
        │ UPI / Infinity Fabric，60~80 ns 协议税
 Socket 1（远端 DRAM 访问 130~150 ns 档）
```

| 访问层级 | 典型延迟档 | 迁移之后的状态 |
| --- | --- | --- |
| L1 命中 | 4~5 拍 | 迁走即全部失效 |
| L2 命中 | 十余拍 | 迁到 SMT 兄弟仍命中（共享） |
| L3 命中 | 数十拍 | 迁到同 socket 任意核仍可能命中 |
| 本地 DRAM | 80 ns 档 | 与核无关，但 TLB 项随核失效 |
| 远端 DRAM | 130~150 ns 档 | 跨 socket，NUMA 惩罚的主要来源 |

由此得到一个反直觉结论：迁到 SMT 兄弟最便宜——两个逻辑处理器共享 L1/L2 与执行单元，TLB 通常也是核内共享结构，缓存不冷、地址翻译不重做，代价只剩流水线与分支预测器的重建；迁到同 socket 的另一物理核要重建 L1/L2，迁到另一 socket 还要再缴远程访存的固定税。

### 3. 迁移的判据：收益是排队时间，成本是缓存重建

负载均衡器每秒要回答数千次「要不要把这个实体搬到那个核」。判据可以写成一个不等式：迁移的收益是省下的排队等待，成本是迁走后的缓存重建，只有前者大于后者才值得搬。

$$T_{queue}^{local} - T_{queue}^{remote} > T_{rebuild}$$

$T_{rebuild}$ 由热工作集 $W$ 与内存带宽 $B_{mem}$ 决定，量级为 $W / B_{mem}$ ：1 MiB 的热工作集在 10 GB/s 档带宽下约需 100 µs 重建，而一次队列等待通常只有数十 µs 档——所以均衡器对「热」实体天然保守，只在队列长度差超过阈值时才动手。

```text
 两个迁移方向
   拉（idle balance）：空闲核扫描忙核的运行队列，把可迁移实体取走，针对持续空闲
   推（work stealing）：空闲核从忙核队列尾部窃取，减少争用，针对瞬时不均
   共同约束：只能搬就绪态实体，且不得违反亲和掩码
```

两个方向针对不同的失衡：拉对持续空闲有效，推对瞬时不均有效。两者受同一条物理约束——迁移只能发生在实体不在 CPU 上执行的时刻，因此正在跑的热循环不会被搬走，热实体的迁移总是滞后于负载变化。

核验入口：Linux 上 `numactl --hardware` 读节点与距离矩阵，`lstopo-no-graphics` 读缓存与 SMT 拓扑；NT 上 `GetLogicalProcessorInformationEx` 返回 `RelationCache`、`RelationNumaNode`、`RelationProcessorCore` 三类记录，可还原同一棵树。两侧读到的层级应与上图一致，不一致说明虚拟化层屏蔽了拓扑。

## 六、生命周期收束：退出、回收与围栏

### 1. 退出之后：谁来持有那具尸体

两侧在「实体停止执行」这一点上一致，在「结构何时释放」上分道。Linux 让退出者留下一具尸体等父进程收尸；NT 用引用计数，最后一个持有者放手即销毁。

```text
 Linux：退出 ≠ 释放
   RUNNING ──exit()──► ZOMBIE（task_struct 与退出码保留，地址空间已释放）
                          │
              父 wait() ──┴──► 释放 task_struct
              父先死 ──► 过继给 init/systemd，由它收尸

 NT：终止 ≠ 删除
   RUNNING ──ExitProcess──► 已终止，EPROCESS 对象仍存活（可查询退出码）
                               │
          所有句柄关闭且无其他引用 ──┴──► 对象删除
```

| 维度 | Linux | NT | 后果 |
| --- | --- | --- | --- |
| 尸体持有者 | 父进程（`task_struct` 留存） | 对象管理器（引用计数） | Linux 可能积累僵尸 |
| 取退出码 | `waitpid` 返回状态字 | `GetExitCodeProcess` 读对象 | NT 可反复读 |
| 等待终止 | `waitpid` | `WaitForSingleObject(进程句柄)` | 对称 |
| 父进程缺失 | 过继给 `init` 或 `subreaper` | 无过继概念，句柄即生命线 | 生命周期归属不同 |
| 进程组/树 | `setpgid`、`kill(-pgid)` | 作业对象 | NT 围栏更强 |

「僵尸」在 Linux 上不是缺陷而是设计：退出码必须有个地方存到父进程来取，`task_struct` 就是那个地方；父进程若不 `wait`，僵尸便一直占着一个 pid 与一枚 `task_struct`。NT 把退出码存进内核对象，任何持有句柄的实体都能读，因此不需要「等待被收尸」这个状态——代价是句柄泄漏会让对象永不删除，泄漏形态从「僵尸进程」变成「句柄计数不归零」。

### 2. 围栏：作业对象与 cgroup 是同一诉求的两种形态

「把一组进程当成一个整体来限制和杀灭」这个诉求，两侧的实现形态差异很大：NT 用内核对象加句柄，Linux 用层级文件系统。

| 维度 | NT 作业对象 | Linux cgroup v2 | 方向 |
| --- | --- | --- | --- |
| 加入方式 | `AssignProcessToJobObject`（显式） | 写 `cgroup.procs`（显式）或 fork 继承 | 都需显式，前者要句柄 |
| 默认继承 | 子进程默认加入父的作业（可设 breakaway） | 子进程自动继承所在 cgroup | 同向 |
| 内存限制 | `JOB_OBJECT_LIMIT_PROCESS_MEMORY` 等 | `memory.max` 加 `memory.high` 软限 | cgroup 更细 |
| CPU 限制 | 亲和掩码、CPU 速率控制 | `cpu.max`（配额/周期）、`cpu.weight` | cgroup 更细 |
| 整体杀灭 | 关闭最后一个作业句柄加 `KILL_ON_JOB_CLOSE` | 写 `cgroup.kill` | 语义等价 |
| 观测 | `QueryInformationJobObject` | `memory.current`、`cpu.stat` 等文件 | 形态不同 |

作业对象的关键性质是「生命周期绑定在句柄上」：最后一个作业句柄关闭时，若置了 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`，作业内所有进程被终止。这让「父进程崩溃后子进程成为孤儿」在 NT 上有干净的解法；Linux 侧要达到同样效果，需要 `PR_SET_PDEATHSIG`（每进程单独设置、只对直接父进程生效）或把整组放进 cgroup 再 `cgroup.kill`。

### 3. 崩溃收束：异常端口与核心转储都按容器打包

实体崩溃时的现场是「容器 + 全部实体」的快照：地址空间、打开的文件、各线程的栈与寄存器。两侧的收集路径不同，但打包边界相同。

```text
 NT：用户态异常 ──► 内核查 EPROCESS 注册的异常端口（ALPC）
     ├─ 有调试器：投递给调试器，可读改上下文后继续
     └─ 无调试器：默认处理器 → WER → 生成 minidump（可按类型裁剪）

 Linux：do_coredump ──► core_pattern 决定去向
     ├─ 落盘：按 ELF core 格式写地址空间（可配 core 大小上限）
     └─ 管道：`|/usr/lib/systemd/systemd-coredump` 交给用户态收集器
     仅默认动作为 core 的信号（SIGSEGV / SIGABRT 等）触发
```

这张图的收束点正是第一节的切分面：转储以容器为单位打包，因为地址空间、fd 表、凭据都挂在容器上；而恢复与重放只能以实体为单位，因为调度实体没有跨进程身份——线程 ID 在进程退出后即失效，`ETHREAD` 与 `task_struct` 都不提供可跨容器引用的稳定标识。于是「进程是可打包的单位，线程是可执行的单位」这句话在崩溃路径上得到它最实际的一次确认，本篇的拓扑遍历到此为止。
