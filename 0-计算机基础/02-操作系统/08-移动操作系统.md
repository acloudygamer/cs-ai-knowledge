# 移动操作系统

## 一、三处裁剪：移动端不是新内核，是同一套机制的减法

| 裁剪面 | 桌面默认形态 | Android 的削法 | iOS 的削法 | 直接代价 |
| --- | --- | --- | --- | --- |
| 内核 | 可 `insmod`、多用户登录 | 单体内核 + 厂商 LSM + 模块签名白名单 | XNU 混合内核，`kext` 需签名与公证 | 驱动缺陷只能随整包 OTA 修 |
| 应用模型 | 任意 ELF/PE，运行期可生成代码、可热更新 | `dex` + ART 的 AOT（Ahead-Of-Time，提前编译）/JIT（Just-In-Time，即时编译）混合 | `Mach-O` 构建期 AOT + 强签名，第三方禁 JIT | 安装期多一次编译，热更新受限 |
| 生命周期 | 后台常驻，用户可配置保活 | 冻结 + `lmkd` 按水位杀 | 挂起 + `Jetsam` 按 band 杀 | 回前台冷启动，百毫秒档 |
| 权限 | 用户/组 + 文件位，管理员可提权 | 权限组 + SELinux 域 | entitlement + 沙箱 profile | 换签名即换权限，没有临时提权 |
| 内存压力 | 磁盘 swap 换出匿名页 | `zram` 压缩后驻留，无盘 swap | 压缩内存（compressor），无盘 swap | 常驻集受物理内存硬约束 |

每一行都是本章前文某条机制换了参数，而不是新增一段代码。判据只有一条：凡是「给不受信主体留的余地」，先削。

### 1. 三条约束各压出一个数量级

电量的直接度量是待机功率：整机黑屏待机落在 5~20 mW 档，而一颗 3.5 GHz 大核空转一个循环就要 数百 mW，两者相差 2 个数量级。于是「后台偶尔跑一下」在桌面上是噪声，在手机上就是吃掉半个预算：一次 5 ms 的唤醒落在 1.28 s 的寻呼周期里，占空比 $\eta = 5\ \text{ms} / 1.28\ \text{s} \approx 0.4\\%$ ，按 400 mW 的工作功率摊销，均值约 1.6 mW。

热约束把持续功耗钉在 3~6 W 档：手机无风扇，热量只经机身表面散出，SoC 结温上限 90 °C 附近，持续超过 5 W 即降频；桌面 65~125 W 有风冷兜底，可长时间满频。降频又直接拉长前台响应时间，这是「后台线程池常驻」不可移植的物理原因。

来源约束是唯一非物理的一条：桌面把用户当管理员，可自行安装二进制、加载内核模块；移动端的应用来自商店，安装期核对签名，运行期再校验代码完整性。它把「应用可能恶意」从例外变成前提，权限模型因此改成「默认拒绝、逐项声明」。

### 2. 毫瓦档预算怎么花：三项固定，一项可削

```text
 待机预算 5~20 mW
   ├── SoC 深睡（电源域关断，仅留唤醒源）             1~3 mW    固定
   ├── DRAM 自刷新（LPDDR5，按容量计）                1~5 mW    固定
   ├── modem 寻呼监听（DRX 周期 1.28 s，醒 3~5 ms）   1~2 mW    固定
   └── 应用侧唤醒（定时器、推送、后台任务）           0~无上限   可削 ← 冻结的对象
```

前三项随硬件配置走，软件压不到零；第四项完全由「还有多少进程被允许运行」决定。一个每秒醒一次的后台进程均值约 0.5~1.6 mW，十个就是 5~16 mW，把整机待机从 10 mW 推到 20 mW 以上。冻结就是把这一项从「按进程数线性增长」压成 0，代价写在 §4。

### 3. 减法之后没有新增机制

内核这一刀削掉模块热插拔与多用户，保留 06 篇那套「中断 → 驱动 → 块/字符设备」的模型，只把驱动来源收窄成签名白名单；应用模型这一刀把 04 章 02 篇的装载校验从每次 `execve` 提前到每次安装，运行期因此少一道全量校验；生命周期这一刀让 03 篇的调度器与 04 篇的回收水位共用同一份进程状态表。三刀方向一致：把不确定性推给安装期、商店与用户，运行期只留确定性最高的路径。

## 二、内核裁剪：Linux 加 `binder`，XNU 的 Mach/BSD 双层

```text
 Android（Linux 单体内核）
   应用（每应用一个 Linux UID）
     └─ Binder ioctl → binder 驱动：1 次 ioctl、1 次拷贝（发方 → 收方 mmap 区）
          └─ 调度器 + lmkd 阈值；无盘 swap（zram）；驱动模块签名

 iOS（XNU 混合内核）
   应用（每应用一个容器目录）
     └─ syscall / mach trap → 入口桩按编号区间分派
          ├─ Mach 层：task/VM、mach_msg 端口（send/receive right 决定收发资格）
          └─ BSD 层：proc/VFS/socket/权限位；IOKit 的 kext 需签名；无盘 swap（compressor）
```

两条栈的差别不在谁更先进，而在一次跨进程调用要经过几层、拷几次。

### 1. `binder`：一次事务 1 次 `ioctl`、1 次拷贝

`binder` 是字符设备，节点在 `/dev/binder`（厂商另开 `/dev/hwbinder`、`/dev/vndbinder` 分域）。一次跨进程调用在用户态是一次 `ioctl(fd, BINDER_WRITE_READ, &bwr)`，待发事务与待读回复合并进同一次系统调用。内核侧 `binder_transaction` 把发送方缓冲区 `copy_from_user` 一次，落到接收进程预先 `mmap` 好的内核页上；接收方在用户态直接读这块映射，不再有第二次拷贝。

| 指标 | `binder` 一次事务 | Unix domain socket 一次往返 |
| --- | --- | --- |
| 进入内核次数 | 1 次 `ioctl`（可批量携带 N 个事务） | 2 次（`sendmsg` + `recvmsg`） |
| 数据拷贝次数 | 1 次（发方用户态 → 收方映射页） | 2 次（发方 → skb，skb → 收方） |
| 收方如何得知有数据 | 线程池阻塞在 `ioctl`，由驱动唤醒 | `epoll` 就绪后自行 `recvmsg` |
| 单次开销档位 | 几十微秒档（含唤醒与调度） | 同尺寸高半档到一档 |
| 批量摊销 | 一次 `ioctl` 打包多事务， $1/N$ | 靠 `sendmmsg` 部分弥补 |

「1 次拷贝」的代价也明确：接收方须常驻一块绑定自身地址空间的缓冲区，不能按需回收；socket 不占这笔内存，但每次多拷一遍。

### 2. XNU：同一条 `syscall` 指令，两张分派表

XNU 把 Mach 与 BSD 两套接口叠在同一个内核里。用户态发的仍是同一条 `syscall` 指令，入口桩按编号区间分派：一段进 Mach trap 表（`mach_msg`、`mach_vm_allocate`），一段进 BSD 的 `sysent` 表（`open`、`read`、`fork`）。两条路径共享同一个 `task`/`proc` 结构，语义却不同：Mach 侧资源以端口权限表达，持 send right 才能发、持 receive right 才能收；BSD 侧以文件描述符表达，检查走 POSIX 权限位。

同一份数据因此可能走两条路。小消息内联在 `mach_msg` 消息体里，一次系统调用完成；超过内联上限的数据改走 out-of-line 描述符，内核把发送方的页映射进接收方地址空间，拷贝次数为 0，代价是双方对这批页的生存期达成约定。

### 3. 无盘 swap：压力下的动作是压缩或杀，不是写闪存

两端都没有磁盘 swap 文件，原因不是装不下，而是闪存写入特性：TLC 颗粒每单元只有 1~3 千次擦写寿命，随机写延迟在 数十微秒到毫秒档，还带 2~4 倍写放大。桌面换出一页再换入不过是 数十微秒档的盘访问；手机做同一动作按天消耗写寿命，并在前台掉帧时被看见。约束由此逼出唯一解：匿名页要么就地压缩，要么连同进程一起消失。

Android 用 `zram` 把匿名页压缩后留在内存，压缩比典型 2~3:1，压缩与解压单页在 微秒档，等价于用 CPU 换内存，不产生任何闪存写；iOS 用 compressor 把冷匿名页压进内存池。真正兜不住时才杀进程：`lmkd` 读 `MemAvailable` 与 PSI 压力，按 `oom_score_adj` 档位从高到低杀；`Jetsam` 按 `memorystatus` 的 band 从低到高杀。水位按设备内存分档，低端机阈值在 数十 MB 档，高端机在 数百 MB 档，跌破即触发，先杀最不重要的一档。

## 三、应用模型：ART 的混合编译与 iOS 的强签名 AOT

```text
 Android：.apk ──安装──▶ dex2oat ──▶ .oat（机器码）/.vdex（已校验 dex）/.art（类元数据）
                              │                    │
                              │                    └─▶ 运行：AOT 代码 + JIT 热点 + profile 采样
                              └─ 空闲且充电时按 profile 重编译（只编热方法）

 iOS：源码 ──构建──▶ Mach-O（AOT 完成）──▶ 签名（CodeDirectory 逐页哈希）──▶ 安装期只校验
                                                              │
                                                              └─▶ 运行：页首次换入即验哈希，禁 JIT
```

两条链的时序差一格：Android 把编译摊在安装期与运行期之间来回摆动，iOS 把它全部压在构建期，安装期只剩校验。

### 1. 四段：打包、安装期编译、首次运行、稳态执行

Android 的 `.apk` 里装 `dex` 字节码。安装时 `dex2oat` 编译成机器码，同时产出三份副产物：`odex`（早期 DALVIK/ART 的产物名）或现代等价物 `oat`（机器码，以 ELF 段 `oatdata` 承载）、`vdex`（已校验的 `dex` 副本与校验结果）、`art`（类元数据与堆镜像）。首次运行仍有类初始化与资源解析，冷启动在 数百毫秒档；稳态下未编译方法由 JIT 接手，热点采样进 profile，空闲且充电时才按 profile 重编译，把编译成本摊进看不见的窗口。

iOS 的 `.ipa` 里装已编译的 `Mach-O`，构建期由 LLVM 完成 AOT，安装期只做两件事：核对签名与描述文件，把每页代码的哈希登记进 `CodeDirectory`。运行期 `dyld` 完成符号绑定（系统库经共享缓存预绑定，绑定成本移出进程启动路径），此后不再有编译动作。

### 2. `dex` → `odex`/`vdex`：一份代码的多种产物

| 产物 | 内容 | 生成时机 | 校验方式 | 可写性 |
| --- | --- | --- | --- | --- |
| `.dex` | Dalvik 字节码、字符串表、类与方法索引 | 构建期，随 APK（Android Package，安卓安装包） | APK v2/v3 整体签名，覆盖全部 zip 字节 | 只读，随 APK |
| `.odex`/`.oat` | 机器码与方法级映射表 | 安装期 `dex2oat`，或空闲期重编译 | 与源 `dex` 校验和绑定，不匹配即废弃 | 系统生成，OTA 后重建 |
| `.vdex` | 已校验 `dex` 副本 + 校验结果 | 安装期，紧随编译 | 命中即跳过全量校验 | 系统生成 |
| `.art` | 类元数据、堆镜像 | 安装期与首次启动 | 无独立校验，随 `vdex` 版本失效 | 系统生成 |

`vdex` 的理由可量化：全量校验要做类结构、方法引用、字节码边界逐项检查，成本在 每 MB 十毫秒档；数十 MB `dex` 的应用光校验就是 数百毫秒，与一次冷启动同量级。`vdex` 把「已校验」结论缓存下来，命中后只剩头部与 CRC 核对，降到 毫秒档以下。

### 3. 可执行页：`mmap(PROT_EXEC)` 的分水岭

iOS 把代码页锁在 `__TEXT` 段，权限 `r-x`，页哈希写进签名。页首次换入时内核逐页校验哈希，单页成本 微秒档；校验失败直接 `SIGKILL`，错误码指向代码签名，应用无法捕获。匿名可执行映射需要 `MAP_JIT` 加 `com.apple.security.cs.allow-jit` 这条 entitlement，只有系统自带 WebKit 进程持有；第三方应用的 JS 要么走解释器，要么把页面交给 `WKWebView` 的独立进程——JIT 权限归属进程，不归属应用。

Android 没有这道闸：匿名 `mmap(PROT_EXEC)` 可用，ART 的 JIT 代码写在名为 `jit-code-cache` 的匿名映射里，容量有上限（数十 MB 档），写满即停 JIT 并回退解释执行，不杀进程。

分岔点因此不是「谁允许动态代码」，而是「完整性校验发生在什么时刻」：iOS 在页换入，Android 在安装期 `dex` 校验与运行期类验证。两者都把校验放在装载之前而非执行每条指令时，与 04 章 02 篇的 ASLR 同层——地址与代码的合法性在映射建立时就已确定。

## 四、生命周期：后台冻结是调度器与回收器的联合干预

```text
  前台 top            后台可见 visible        后台冻结 frozen           被杀 dead
  oom_score_adj 0  →  100~200            →   700~900               →   —
  CPU：可运行       →  受 CPU 配额限制     →   0（不排入运行队列）    →   0
  内存：正常记账     →  正常记账           →   匿名页仍在，不可回收    →   全部释放
       │  Home 键 / 切走        │ 数十秒窗口耗尽        │ 可用内存跌破水位
       └───────────────────────┴───────────────────────┘
                    ▲                                    │
                    │  解冻：温启动，十毫秒档              │  冷启动：百毫秒档
                    └────────────────────────────────────┘
```

### 1. 三态与两条回边

前台态占满调度配额，内存记账正常。切到后台先进「可见」态：仍可运行，但被压在较低 CPU 配额里，窗口典型数十秒（iOS 后台任务窗口、Android 前台服务与 `JobScheduler` 宽限期都在这一档）。耗尽即冻结：Android 用 cgroup 的 freezer 把进程组从运行队列摘下，iOS 用 `task_suspend`——任务状态与页表还在，CPU 时间归零，但没有指令被退休。

两条回边对应两种成本。冻结态回前台是温启动：任务重新入队、页表已热、类已初始化，恢复在 十毫秒档。被杀后回前台是冷启动：进程重建、类重新加载、资源重新解析，落在 百毫秒档。两档差一个数量级，这就是「别随便杀我」的全部技术依据。

### 2. 冻结的账：CPU 归零，代价是恢复延迟

按 §1 的式子算收益：一个每秒醒一次、每次工作 5 ms、跑在 100 mW 档小核上的后台进程，均值 0.5 mW；十个是 5 mW，占 5~20 mW 预算的 25%~100%。冻结把它们整项归零。

代价有三笔：恢复延迟十毫秒档，可感知为「切回时一瞬间白屏」；冻结期定时器不投递，「每秒同步」必须自行补偿，否则时间窗被吞；匿名页仍计入常驻集、不可回收，只能压缩，冻结越多压缩池越满。三笔代价决定冻结粒度：按进程组整体冻结，不按线程冻结，否则留下的锁持有者会让整个进程组在解冻时死锁。

### 3. 杀的次序：LRU 加水位，不是重要性声明

| 状态 | Android `oom_score_adj` | iOS `memorystatus` band | 是否参与杀 |
| --- | --- | --- | --- |
| 前台 | 0 | 最高 band | 否（最后才动） |
| 可见 / 前台服务 | 100~200 | 次高 band | 极端压力下才动 |
| 后台缓存（冻结） | 700~900 | 低 band | 是，按 LRU 从旧到新 |
| 空进程 / 无 Activity | 900~1000 | 最低 band | 是，最先动 |

`adj` 只决定「先杀谁」，不决定「杀不杀」。触发条件是水位：`lmkd` 把 `MemAvailable` 与按设备内存分档的阈值比较，跌破即从最高 `adj` 开始回收，杀到水位回升为止；`Jetsam` 同理，只把阈值换成分 band 的内存上限。应用声明的优先级只能把自己挪进更靠后的一档，挪不出这张表。

冷启动成本按段拆开：进程创建与 `zygote` fork 在 毫秒档，类加载与静态初始化在 数十毫秒档（数千个类，每类 数十微秒），资源解析与布局在 数十毫秒档，首帧绘制再叠上 GPU 上传。四段相加落在 300~800 ms；温启动省掉前两段，落在 100~200 ms；仅重建 Activity 的热启动在 数十毫秒档。这条不等式解释了厂商为何用常驻进程做预加载，也解释了为何冻结优于杀死。

## 五、权限与沙箱：应用来源不可信前提下的两条路线

```text
 Android
   声明：AndroidManifest.xml 的 <uses-permission>（安装前可读）
     └─ 安装期：权限组归并后弹窗授予（normal 级安装期自动授予）
          └─ 运行期检查点：框架 API + SELinux 域；判定者 PackageManager / SELinux

 iOS
   声明：entitlements（嵌在二进制内，被签名覆盖）
     └─ 安装期：签名核对 + 描述文件匹配（不匹配即拒装）
          └─ 运行期检查点：框架 API + 沙箱 profile + TCC；判定者内核沙箱（越界即 SIGKILL）
```

### 1. 检查点必须落在框架入口与系统调用

判据与 01 篇的竖井同源：应用进程内任意代码都能跳到检查逻辑之后，所以检查不能与被检查者同处一个特权级。Android 把检查放在框架 API（`checkPermission`）与 SELinux 域两处，前者拦「应用主动调用」，后者拦「应用直接发起的系统调用」——即便绕过框架直接对 `binder` 发事务，SELinux 仍会在 `binder_transaction` 里比对源域与目标域。iOS 把检查放在框架与内核沙箱两处，profile 在 `open`、`mach_msg` 这些入口逐次比对路径与服务名。

成本由此固定：每次跨进程调用 1 次 SELinux 检查（数十纳秒到微秒档），每次打开文件 1 次 `inode_permission`。检查次数与系统调用次数同阶，这就解释了权限粒度为何只能做到「每次打开检查」而做不到「每次读写检查」——后者会把检查次数乘上 IO 次数，直接压垮前台。

### 2. 权限组 vs entitlement：一个管弹窗次数，一个管二进制身份

| 维度 | Android 权限组 | iOS entitlement |
| --- | --- | --- |
| 声明载体 | `AndroidManifest.xml` 的 `<uses-permission>`，安装前可读 | 二进制内 `__TEXT,__entitlements`，被签名覆盖 |
| 授予时机 | `normal` 级安装期自动授予；`dangerous` 级首次使用弹窗，按组归并 | 构建/签名时确定，安装期核对描述文件，运行期不再询问 |
| 检查点 | 框架 API + SELinux 域 | 框架 API + 内核沙箱 profile + TCC 数据库 |
| 越权后果 | `SecurityException`，应用可捕获并降级 | 进程被 `SIGKILL`，不可捕获 |
| 换签名的影响 | 签名变更即失去原有授权，升级须同签名 | entitlement 随签名整体变化，描述文件不匹配即拒装 |
| 可授予的粒度 | 权限组是弹窗单位，组内权限仍可单独判定 | entitlement 是二进制级布尔量，无「组」概念 |

权限组解决弹窗疲劳：把 N 条细粒度权限归并成 $g$ 个组，弹窗次数从 $N$ 降到 $g$ 的量级，代价是用户对组内权限的认知被合并，授予「存储组」等于同时给了读写两向。entitlement 解决权限归属：权限不再是运行时可以商量的东西，而是编译进二进制的一段数据，同一份源码换一套签名就是另一个权限集合，越权的前提因此是先攻破签名，而不是先骗过弹窗。

### 3. 沙箱边界是「可见集合」，不是地址空间

两端都不靠进程地址空间隔离做沙箱——地址空间隔离在 01 篇已由页表完成，移动端要隔离的是另外三样：文件路径、IPC 端点、系统服务名。

Android 给每个应用独立 Linux UID（形如 `u0_a123`），文件权限按 UID 位裁决，跨应用读写只能经 `ContentProvider` 或共享 UID；binder 端点的可见性由 `binder` 上下文与 SELinux 域共同决定，拿不到句柄就发不出事务。iOS 给每个应用一个容器目录，沙箱 profile 以白名单列出可访问的路径前缀与可连接的 `mach` 服务名，越界 `open` 返回 `EPERM` 并留审计记录；跨应用共享走扩展进程，不直接读对方容器。

这条思路与 06 章 05 篇的 namespace 同源：都把全局命名空间切成按主体划分的视图，主体只看见被投影进来的对象。差别在于 namespace 切的是内核对象视图，移动端沙箱切的是路径与端点的可见性，后者更粗，但足以让「应用来源不可信」这条前提成立。
