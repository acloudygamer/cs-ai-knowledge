# 文件系统

## 一、三级绑定：名字 → 记录 → 字节

```text
      ①名字                 ②记录（内核元数据，只读）                    ③字节
 ┌────────────┐   ┌────────────────────────────────────────────┐   ┌────────────┐
 │ "/a/b/c"   │   │ VFS:  superblock ─ inode ─ dentry ─ file    │   │ 数据块      │
 │ 路径串      │──▶│ NT :  VOLUME     ─ FCB   ─ FILE_OBJECT      │──▶│ 4 KiB/簇   │
 └────────────┘   └────────────────────────────────────────────┘   └────────────┘
       │                     │                  │                        │
       │ 逐分量解析           │ 按编号取记录      │ 装进 fd 表/句柄表        │ 首次 read
       ▼                     ▼                  ▼                        ▼
   k 个分量              i_ino / 文件引用号     fd 或 HANDLE           物理块号
                   └──────── open 全程止于此线 ────────┘        └── 数据块读 0 次 ──┘
```

| VFS 对象 | 职责（承载什么） | NT 对应物 | 生命周期判据 |
| --- | --- | --- | --- |
| `super_block` | 一个已挂载卷的布局参数：块大小、inode 总数、空闲位图位置 | `VOLUME`（`VPB` 挂接） | 卷挂载到卸载，全卷 1 个 |
| `inode` | 单文件的元数据本体：大小、时间戳、块索引、链接计数 | `MFT` 记录（`$STANDARD_INFORMATION` + `$DATA`） | 内存副本随缓存回收，磁盘实体随文件存亡 |
| `dentry` | 名字到 `inode` 的绑定，带 parent 指针构成目录树 | 索引项（`$I30` 中的文件名项） | 纯内存对象，引用计数归零即可丢弃，无磁盘实体 |
| `file` | 一次打开实例：读写偏移、打开标志、权限快照 | `FILE_OBJECT` | 每次 `open`/`NtCreateFile` 各 1 个，随句柄关闭销毁 |

这张表的分界只有一条：**前两行在磁盘上有实体，后两行只活在内存里**。`dentry` 与 `FILE_OBJECT` 的字段全部可由「名字 + 记录 + 打开参数」重建，故掉电不损失一致性；`inode` 与 `MFT` 记录一旦写坏，文件即失去块索引。所谓「元数据损坏比数据损坏更难修」，指的正是前两行。

### 1.1 一次 open 的端到端：k 个分量，k+1 次元数据读

`open("/a/b/c")` 在内核里被切成固定的三段，每段都只搬元数据：

1. **名字段**：路径串按 `/` 切成 `a`、`b`、`c` 三个分量，从根 `dentry` 或当前工作目录起逐段比对。
2. **记录段**：每个分量在父目录里命中一项后，按项里的编号（ext4 的 `i_ino`、NTFS 的 64 位文件引用号）读该文件的 `inode`/`MFT` 记录，取权限位、属主与块索引。
3. **装表段**：分配 `struct file` 或 `FILE_OBJECT`，把「打开时的权限判定结果」与读写偏移固化进去，返回 fd 或 `HANDLE`。整条路径只过 1 次系统调用陷门，`open` 内部的分量遍历不增加陷门次数。

冷缓存下的元数据读次数下限是分量数加目录自身，即 $N_{\text{meta}} = k + 1$：`/a/b/c` 为 4 次——1 次读根目录块找到 `a`，3 次分别读 `a`、`b`、`c` 所在目录块与 `c` 的记录。这个式子里**没有文件大小这一项**，所以打开 10 GiB 文件与打开 1 KiB 文件是同价的：两者都只读记录本体，数据块读 0 次。

### 1.2 记录本体：256 B 与 1 KiB 的定长账

两侧都把小记录做成定长槽位，代价是槽内留白，收益是编号可直接换算成偏移：

- ext4 的 `inode` 默认 **256 B**（`s_inode_size`；早期为 128 B，扩到 256 B 是为了塞下纳秒时间戳与 extent 树头）。inode 表是连续数组，故「inode 号 × 256 B」即得字节偏移，取一条记录 = 1 次 4 KiB 块读里顺带取出 16 条。
- NTFS 的 `MFT` 记录固定 **1 KiB**，一个 4 KiB 簇装 4 条。记录号 48 位、序列号 16 位，拼成 64 位文件引用号；序列号在槽位复用时递增，使「删后复用」不会让旧引用号指向新文件。

定长的第二个后果是**容量上限由编号宽度钉死**：ext4 的 `i_ino` 为 32 位，单卷 inode 数上限约 $2^{32}$，按 256 B 计 inode 表本身即达 1 TiB 量级——这是「小文件多」的卷必须调 `-N` 指定 inode 数的原因，inode 用尽时即使还有空闲数据块也无法建新文件。

### 1.3 成本档位：由命中率而非分量数主导

| 情形 | 元数据 IO 次数 | 耗时档位 | 主导因素 |
| --- | --- | --- | --- |
| 全路径 `dentry` 命中、记录在页缓存 | 0 | 百纳秒档（百 ns 量级） | 哈希查找 + 引用计数加 1 |
| 仅记录缺页、目录项命中 | 1 | 微秒~百微秒档（SSD）/ 5~10 毫秒档（HDD） | 一次块层读 |
| 全冷、k = 3 | 4 | 上档 × 4，且串行不可重叠 | 分量数 × 单次读延迟 |

热路径的成本由命中率决定：同一目录下重复打开百万次，第 2 次起落在百纳秒档，与分量数几乎无关；而冷启动扫目录时，串行的 4 次读在 HDD 上就是 20~40 毫秒。这也解释了为何 `dentry` 缓存（Linux）与索引缓存（Windows）的回收策略要按「目录热度」而非「文件大小」加权。

## 二、路径逐分量走查：缓存、上溯与链接重试

```text
 取下一个分量
      │
      ▼
 ┌──────────────┐  命中   ┌────────────────────┐
 │ 查 dentry /   │────────▶│ 取记录 → 权限判定    │──┐
 │ 索引缓存      │         └────────────────────┘  │
 └──────┬───────┘                                  │
        │ 未命中                                    │
        ▼                                          │
 ┌──────────────┐  有挂载点  ┌──────────────────┐   │
 │ 下发 lookup   │──────────▶│ 换 vfsmount/卷    │──┤
 │ 读目录块       │           └──────────────────┘   │
 └──────┬───────┘                                   │
        │ 命中项是符号链接 / 重解析点                  │

 ┌──────────────┐  计数 +1   ┌──────────────────┐   │

```

| 分量类型 | Linux 动作 | Windows 动作 | 额外 IO | 次数上限 |
| --- | --- | --- | --- | --- |
| 普通名 | `dentry` 比对全名 | `$I30` 索引二分 | 未命中 +1 | 无 |
| `.` | 直接取当前 `dentry` | 直接取当前 `FILE_OBJECT` | 0 | 无 |
| `..` | 取 `dentry->d_parent` | 取路径串回退一级 | 0 | 无 |
| 挂载点 | 切 `vfsmount` 后继续 | 切卷设备对象后继续 | 0 | 无 |
| 符号链接 | 回填目标串重走 | 读重解析点、回填重走 | +1 | 40 / 32 |
| 卷前缀 | 无此层（单根树） | 展开 `\??\C:` 符号链接 | +1 | 32 |

### 2.1 命中分支：一次全名比对，0 次 IO

`dentry` 缓存与 NTFS 的索引缓存都以「父目录 + 名字」为键。命中时内核只做两件事：比对名字长度与字节串、把 `dentry` 的引用计数加 1；随后从 `dentry` 直接取到 `inode` 指针，不读任何磁盘块。`..` 更便宜——它不查任何表，直接读 `dentry` 里保存的 parent 指针，故「上溯 100 层」与「上溯 1 层」同为 0 次 IO、同一档耗时。这是 `getcwd` 与相对路径解析能在微秒内完成的原因。

### 2.2 未命中分支：目录项字节决定一次读能筛掉多少

未命中的代价是一次目录块读，而一次读能覆盖多少分量，取决于目录项的编码密度：

- ext4 的 `ext4_dir_entry_2` 是变长项：8 B 定长头（inode 号 4 B、项长 2 B、名字长 1 B、文件类型 1 B）加名字，按 4 B 对齐。名字 1~3 B 时项占 12 B，名字 200 B 时占 208 B；一个 4 KiB 目录块因此装 19~340 项不等。目录小于 4 KiB 时是线性表，逐项比对全名，查找为 $O(n)$。
- NTFS 的索引项头 16 B 起（文件引用号 8 B、项长 2 B、名字长 2 B、标志 2 B 等），名字按 UTF-16 存、每字符 2 B，故同样名字占用的字节约为 ext4 的 2 倍，单块可容纳项数约为一半。

目录项字节数的直接后果是**目录分裂阈值**：ext4 目录超过 1 个块后转为 `htree` 两级哈希（`dx_root` 存哈希种子，`dx_node` 存哈希区间到块号的映射），查找从 $O(n)$ 降到 $O(1)$；NTFS 目录自建即为 `$I30` B+ 树，按文件名 UTF-16 序排列，查找 $O(\log n)$、单次索引块读覆盖数百项。

### 2.3 重试分支：链接与卷前缀的两道闸门

两类分量不产生新文件、只改写待解析的路径串，故必须设上限，否则一个自指链接即可让内核无限循环：

1. **符号链接**：读到目标串后整体回填、从头重走。Linux 以 `MAXSYMLINKS` = 40 为限，超限返回 `ELOOP`；Windows 重解析点链上限 32，超限返回 `STATUS_IO_REPARSE_TAG_INVALID`。每跳固定 +1 次 IO，故 40 跳的最坏路径比 4 分量普通路径贵一个数量级。
2. **卷前缀**：Windows 的对象管理器必须先展开 `\??\C:` 这条符号链接才能到 `\Device\HarddiskVolumeN`，即任何盘符路径都自带 1 次符号链接解析；Linux 无此层，卷在挂载时已并入单根树，解析时只切 `vfsmount`、0 次 IO。

宽度上限同样分两档：单个分量 Linux 255 B、Windows 255 个 UTF-16 字符；全路径 Linux `PATH_MAX` 4096 B、Win32 `MAX_PATH` 260 字符（NT 命名空间前缀 `\\?\` 下放宽到 32767）。「深目录在 Windows 上更早撞墙」不来自分量数，而来自这 260 字符的定性上限。

## 三、从记录到块：一条记录如何指认磁盘上的区间

```text
 两条块索引路线（左：VFS inode 内的 60 B 槽位；右：NTFS MFT 记录内的 $DATA 属性）

  ext4 inode（256 B）                               NTFS MFT 记录（1 KiB）
 ┌──────────────────────────────┐                ┌────────────────────────────────┐
 │ i_size / i_blocks / 时间戳     │                │ $STANDARD_INFORMATION           │
 │ i_block[15] = 60 B           │                │ $FILE_NAME（与 $I30 索引项同源） │
 │  ┌──────────────────────────┐│                │ $DATA                           │
 │  │ extent_header：12 B      ││                │  ├ 常驻：数据内嵌（≤ 约 700 B）  │
 │  │  entries=4，depth=0      ││                │  └ 非常驻：run list             │
 │  ├──────────────────────────┤│                │     (长度, LCN 增量) × n        │
 │  │ extent0：lblk / len / pblk││                └───────────────┬────────────────┘
 │  │ extent1 …                ││                                │
 │  │ extent2 …                ││                     变长字节流，顺序解码
 │  │ extent3 …                ││                     一次读整条映射表
 │  └───────────┬──────────────┘│
 │   entries > 4 │               │
 └───────────────┼───────────────┘
                 ▼
      4 KiB 索引块（340 项），按 lblk 二分；depth 每加 1 多一层块读
```

第一节的两个槽位在这里兑现：`inode` 的 `i_block[15]` 共 60 B，`MFT` 记录的 `$DATA` 属性另有配额。两者回答同一个问题——第 n 个逻辑块落在哪个物理块——却走了相反路线：ext4 把区间描述做成定长项再堆成树，NTFS 把同一描述压成变长增量流顺序解码。本节走完「记录 → 区间表 → 物理块」，页缓存与回写留到第四节。

### 3.1 编码账：12 B 定长项对 1~17 B 变长增量

| 维度 | ext4 extent | NTFS run list（mapping pairs） |
| --- | --- | --- |
| 落点 | `inode` 的 `i_block[15]`（60 B）；4 项装不下时溢出到 4 KiB 索引块 | `$DATA` 属性值；常驻时数据内嵌，非常驻时属性值即 run list，溢出 1 KiB 记录后由 `$ATTRIBUTE_LIST` 拆到扩展记录 |
| 项结构 | 12 B 定长：`lblk` 4 B、`len` 2 B、`pblk` 6 B | 1~17 B 变长：1 B 头（长度字节数 4 位 + 偏移字节数 4 位）+ 长度 + 相对前一区间的有符号 LCN 增量 |
| 单区间上限 | 32768 块 = 128 MiB（`ee_len` 15 位，最高位另作「未初始化」标记） | 长度最多 8 B；偏移 8 B 有符号、相对前项累加，首项为绝对 LCN |
| 定位方式 | B+ 树按 `lblk` 二分，`depth` 从 0 起逐级加 1 | 线性表，从头顺序解码；命中区间被缓存，后续按偏移复用 |
| 冷查找 IO | `depth` 次块读（根在 inode 内，`depth=0` 时 0 次） | 1 次读整条属性值（碎片重时可能跨多个扩展记录） |
| 规模上限 | `lblk` 32 位 → 4 KiB 块下单文件 16 TiB | 块号 64 位 → 单文件 16 EiB，卷上限 256 TiB 档 |

表里每一行都在把成本推给对方。ext4 的定长项带 6 B 物理块号，碎片轻时也省不掉，换来索引块按 12 B 步长二分；NTFS 的变长项碎片轻时一项只占 2~4 B，代价是没有下标、定位第 n 项必须从首项解到第 n 项。这个取舍由记录宽度逼出：NTFS 常驻数据上限约 700 B，run list 也活在 1 KiB 记录里，多占 8 B 就少一段；ext4 的 60 B 槽位同样有限，但溢出方向是树——4 项装不下开索引块，索引块再放 340 项，于是槽位小只影响深度，不影响单区间长度。

### 3.2 覆盖上限与深度：4 项内联管到 512 MiB

```math
\begin{aligned}
L_{\max} &= 2^{15} \times 4\ \text{KiB} = 128\ \text{MiB}, \\
N_{\text{ext}} &= \left\lceil \frac{S}{L_{\max}} \right\rceil, \\
C_{\text{inode}} &= 4 \times 128\ \text{MiB} = 512\ \text{MiB}, \\
C_{\text{leaf}} &= 340 \times 128\ \text{MiB} \approx 42.5\ \text{GiB}
\end{aligned}
```

四个量依次把上限抬到 128 MiB、512 MiB、42.5 GiB、14 TiB：单区间最多 128 MiB；inode 内联 4 项最多覆盖 512 MiB（按每项取满长算，实际更小）；一个索引块装 340 项、管到 42.5 GiB；第二层再乘 340，约 14 TiB。于是 extent 树深度在真实文件上几乎只有 0 和 1 两档：512 MiB 以下不读索引块，42 GiB 以下只多读 1 次。

深度是元数据账，碎片是 IO 账。1 GiB 文件打散成 4 KiB 一段就是 262144 个 extent：树 3 MiB、叶子块 772 个，只占文件体积 0.3%。比例不致命，读路径致命——顺序读退化成 262144 次不连续访问，HDD 上按每次 5 ms 档算落在 20 分钟档，而单段 1 GiB 只有十秒档。`mballoc` 与延迟分配压的是段数，不是单次读速。

### 3.3 分配与空洞：先脏页后落位，未覆盖区间不占块

| 机制 | ext4 | NTFS | 方向 |
| --- | --- | --- | --- |
| 落位时机 | 延迟分配：`write` 只置脏，回写时 `mballoc` 才分配 | 缓存页置脏；回写时由文件系统分配簇 | 把多次小写合并成一次连续分配 |
| 空闲图 | 每块组 1 张位图 + buddy 空闲链表，`goal` 提示贴近上一 extent | `$Bitmap` 每簇 1 位，从分配提示起找连续 0 位；MFT 区预留 12.5% | 有连续空闲段才可能一段装下 |
| 预分配 | `fallocate` 写未初始化 extent，只改树不改数据 | `SetEndOfFile` 扩大小但不扩 VDL（Valid Data Length，有效数据长度）；`FSCTL_SET_ZERO_DATA` 显式置零 | 预分配 0 次数据 IO |
| 空洞 | 无 extent 覆盖的 lblk 读返回 0；`st_blocks` 可远小于 `st_size/512` | 稀疏属性 + 有效数据长度 VDL；VDL 之后读 0 且不分配 | 占用按写入量而非 `i_size` 计 |

四行的方向一致：把分配从 `write` 路径推到回写路径，因为只有回写时才看得见一批连续的写。Linux 的延迟分配把窗口开到 30 s 档（第四节），窗口内相邻的写合并进同一 extent 再落位；NTFS 没有这个名字，但缓存管理器同样攒脏页，分配器从提示簇起找连续空闲段。MFT 区预留 12.5% 是同一逻辑的自我保护——让 MFT 增长时拿到连续簇，而不是被用户数据切碎后再去扩展记录。

空洞判据分两层。ext4 只看 extent 是否覆盖该 lblk，未覆盖即返回零、不读盘，`st_blocks` 可远小于 `st_size/512`；NTFS 多一层有效数据长度 VDL，`SetEndOfFile` 只扩大小、VDL 之后的读返回零且不分配。预分配语义因此分岔：ext4 的 `fallocate` 写未初始化 extent，块已占、读为零；NTFS 要走 `SetFileValidData`（需 `SeManageVolumePrivilege`）才能跳过清零、直接推高 VDL，代价是残留内容可被读到——「新文件读出旧数据」类问题正出在这里。

## 四、页缓存与回写：write 返回时字节还在内存里

```text
 一次 write(fd, buf, 4 KiB) 的两段：返回前只动内存，返回后才碰设备

   用户 buf ──① copy_from_user ──► 页缓存页（4 KiB，按文件偏移索引）
                                    │ 置脏位
                                    │ write 此刻返回：设备写 0 次
                                    ▼
                     ┌────────────────────────────────┐
                     │ 四路触发，任一满足即入回写队列     │
                     ├─ 周期：5 s 扫一遍                 │
                     ├─ 年龄：脏页超过 30 s             │
                     ├─ 水位：脏页占比越线              │
                     └─ 显式：fsync / 卸载              │
                     └───────────────┬────────────────┘
                                     ▼
               ② 按 inode → 页 → LBA 排序，相邻页合并成 bio / IRP
                                     ▼
               ③ 设备 DMA ──完成中断──► 清脏位；失败则重脏并记账
                                     ▼
               ④ fsync 额外等一次 FLUSH / FUA：设备缓存也落盘
```

第三节接通「记录 → 物理块」，但 `read`/`write` 先经过一层以页为单位的缓存。这是两侧最同构的部件：都是按文件偏移索引的 4 KiB 页数组，差别只在索引对象的名字与内核看见它们的方式。同构带来同一个语义断点——`write` 返回只代表字节进了内存。

### 4.1 三件套：页、索引与内核视图

| 层 | Linux | NT | 粒度与判据 |
| --- | --- | --- | --- |
| 缓存页 | `struct page`，挂 `address_space` 的 xarray，索引 = 偏移 >> 12 | 缓存管理器页，挂共享缓存映射 `SHARED_CACHE_MAP` | 4 KiB/页 |
| 索引对象 | `address_space`，每个 inode 1 个 | 共享缓存映射 + 段对象 | 同一文件的多个句柄共享同一份页 |
| 内核视图 | 直接映射区的线性地址，无需额外映射 | VACB（Virtual Address Control Block）：256 KiB 系统地址视图，把缓存页临时映射进内核 VA | 视图可重建，按需建立 |
| 脏标记 | `PG_dirty` / `PG_writeback` | 页头脏位 + 脏页链表 | 每页 1 位 |

命中路径两侧同形：按偏移算出页号，在索引里查到页，`copy_to_user`/`copy_from_user` 搬 4 KiB，全程不进块层，百纳秒档；未命中则分配页、发读请求，NVMe 上百微秒档，两档差两个数量级。缓存命中率因此比任何单次优化都重要——同一文件读百万次，第一次之后全落在前一档。

Windows 多出的 VACB 是可重建窗口：缓存页会被回收或移动，内核不能长期持有其物理地址，缓存管理器便把 256 KiB 页簇临时映射进系统 VA，用完即弃。Linux 没有这层，全部物理内存常驻直接映射区（04 篇第一节），缺的只是「页在不在 xarray 里」这次查找。语义等价，失败模式不同：VACB 视图耗尽会阻塞 IO，Linux 靠内存回收腾地方。

### 4.2 回写：四路触发与水位算术

| 触发 | Linux | NT | 方向 |
| --- | --- | --- | --- |
| 周期 | `dirty_writeback_centisecs` = 500，每 5 s 唤醒回写线程 | 惰性写线程按秒级节拍扫描 | 固定节拍，不随负载伸缩 |
| 年龄 | `dirty_expire_centisecs` = 3000，超过 30 s 的脏页优先 | 页年龄 + 引用位，最旧优先 | 丢数据窗口上限 30 s 档 |
| 水位 | `dirty_background_ratio` 10% 起后台回写，`dirty_ratio` 20% 令写者同步等 | 脏页阈值按物理内存比例算，可经 `CcSetDirtyPageThreshold` 调整 | 越线即从异步转同步 |
| 显式 | `fsync` / `fdatasync` / `syncfs` | `FlushFileBuffers` / `FlushViewOfFile` | 调用者承担全部等待 |

前三路是「无主等待」，第四路是「调用者等待」。前三路只保证脏页最终会走，不保证何时走；第四路把「何时」交给调用者，代价是调用者承担整条链的延迟。水位算术决定写者会不会被拖住：

```math
\begin{aligned}
D_{\max} &= r \cdot M_{\text{avail}} = 0.2 \times 16\ \text{GiB} = 3.2\ \text{GiB}, \\
B_{\text{wb}} &\ge \frac{D_{\max}}{T_{\text{age}}} = \frac{3.2\ \text{GiB}}{30\ \text{s}} \approx 109\ \text{MiB/s}
\end{aligned}
```

16 GiB 可用内存、20% 上限即 3.2 GiB 脏页；30 s 内清空要求后台带宽至少 109 MiB/s。设备写带宽低于此值，脏页在 3.2 GiB 处填满、`dirty_ratio` 触发，写者从微秒档返回变成等一次回写，抖动落在秒档。回写侧靠合并压请求数：按 inode 与 LBA（Logical Block Address，逻辑块地址）排序，相邻页并进 128 KiB 请求，1 MiB 连续脏区只发 8 个；字节数不变，页级放大仍在——512 B 写弄脏 4 KiB 页，落到设备就是 8 倍。

### 4.3 持久化边界：fsync 的三道屏障

```text
 ext4 data=ordered 下一次 fsync 的屏障顺序（NTFS 的 $LogFile 同构）

  ① 数据块 bio 提交 ────────────────┐
                                   │ 数据先落地
  ② 日志提交记录（commit block）◄───┘ 才允许写
        │
        ├─ REQ_PREFLUSH：命令设备把写缓存刷到介质
        ▼
  ③ 提交记录 + FUA 写：绕过设备缓存直接落盘
        │
        ▼
  ④ fsync 返回 —— 此后掉电，重放日志仍得到完整文件
     （数据未 fsync 的部分可能丢，元数据不会指向旧块）
```

`write` 返回后的崩溃窗口上限由年龄触发决定，30 s 档；`fsync` 返回才把窗口关到零。关窗要过三道屏障：数据块先落地、设备缓存刷穿、提交记录带 FUA 落盘。ext4 的 `data=ordered` 强制第一道先于第三道，故崩溃后不会出现「元数据指向新块、块内还是旧数据」；`data=writeback` 放弃该序，用更少的依赖等待换更短的提交延迟。NTFS 的 `$LogFile` 用 redo/undo 记录做同样的事，检查点推进前日志必须先落盘。

| 落盘动作 | NVMe | SATA SSD | HDD | 主导项 |
| --- | --- | --- | --- | --- |
| `fsync` 空文件（只有屏障） | 20~100 µs | 0.2~1 ms | 5~15 ms | 设备缓存刷穿 + 一次寻道 |
| 4 KiB 写 + `fsync` | 数十微秒档 | 毫秒档 | 10 ms 档 | 屏障占九成 |
| 1 MiB 顺序写（不 `fsync`） | 百微秒档返回 | 百微秒档返回 | 百微秒档返回 | 只做一次拷贝 |

两侧日志都只保证元数据一致，不保证数据不丢：`fsync` 之前写入的字节崩溃后可能整段消失，但结构不会坏。`fsync` 的代价几乎全在设备缓存刷穿这一道，故档位由介质而非字节数决定；并发调用被日志合并成一次屏障，高事务率系统因此按批 `fsync` 而非按记录。

核验路径：Linux 侧用 `filefrag -v` 看 extent 段数、`strace -T -e trace=fsync` 看屏障耗时；Windows 侧用 `fsutil fsinfo ntfsinfo C:` 看簇大小与 MFT 有效数据长度、`fsutil file queryextents` 看 run list 段数。数字对得上，本节三条账（页、回写、屏障）就闭合。

## 五、一次写的账本：数据块写一次，元数据写几遍

```text
 同一个 4 KiB 载荷的三条路径（ext4，4 KiB 块、元数据日志、data=ordered）

   ① 覆盖已分配块          ② 追加（要分配新块）        ③ 新建文件再写
   ───────────────        ───────────────────        ───────────────────
   data block     1        data block        1         inode bitmap   2
   inode（mtime）  2        block bitmap      2         block bitmap   2
                           inode（extent）    2         inode table    2
                                                      dir block      2
                                                      data block     1
                                                      commit block   1
   ───────────────        ───────────────────        ───────────────────
   合计 3 块写             合计 5 块写                合计 10 块写
   A ≈ 3                  A ≈ 5                     A ≈ 10
```

第四节停在「脏页交给块层」，本节算清这笔交付在设备侧变成几次写。图中的数字是设备块写次数，标 2 的项表示写两遍：一遍进日志区，一遍在检查点写回原位。同一个 4 KiB 载荷，覆盖、追加、新建三条路径分别是 3、5、10 次块写——差别全在元数据，数据块永远只写一次。

### 5.1 三条路径的块账

| 写入形态 | 设备块写 | 放大 A | 主导项 |
| --- | --- | --- | --- |
| 4 KiB 覆盖已分配块 | 3 | 3 倍 | inode 的 mtime 日志 |
| 4 KiB 追加（分配 1 块） | 5 | 5 倍 | 块位图 + extent 更新 |
| 4 KiB 新建文件 | 10 | 10 倍 | 两级位图 + 目录项 + 提交块 |
| 1 MiB 覆盖 | 259 | 1.01 倍 | 数据本身 |
| 1 MiB 新建 | 265 | 1.04 倍 | 数据本身 |

①只改 inode 的 mtime，代价仍是 2 次写：日志 1 次加原位 1 次。②多出块位图与 extent 两项：位图必须先标记后分配，否则崩溃后同一块可能被两个文件认领。③把 inode 位图、块位图、inode 表、目录块四件事凑齐，再加 1 个事务提交块。NTFS 的账结构相同，名字换成 `$Bitmap`、MFT 记录、`$I30` 索引块与 `$LogFile` 记录；差别在常驻数据——小于约 700 B 的文件，数据直接内嵌在 1 KiB 的 MFT 记录里，新建时省掉独立数据块与块位图两项，故小文件密集的负载在 NTFS 上的块写次数比 ext4 少 2~3 次。

### 5.2 日志的复写税：每个脏元数据块写两遍

日志不是可选开销，而是 4.3 那三道屏障的价格：元数据必须先写进日志区（顺序追加、可批量），提交记录落盘后才允许检查点把同一块写回原位（随机落点）。一次事务因此由描述块、若干元数据块、提交块三段组成，检查点推进后日志空间才可复用。NTFS 的 `$LogFile` 用 redo/undo 记录做同一件事，检查点推进前日志必须先落盘，否则重放时找不到依据。

把账写成式子，放大倍数只由数据块数决定：

```math
\begin{aligned}
B_{\text{dev}} &= 2M + C + D, \\
A &= \frac{2M + C + D}{D} = 1 + \frac{2M + C}{D}
\end{aligned}
```

新建 4 KiB 文件时 M 取 4（两级位图、inode 表、目录块）、C 取 1，故 A = 10；1 MiB 覆盖时 M 取 1、C 取 1、D 取 256，故 A 约为 1.01。两个极端之间没有平台期：A 随 D 单调下降，M 与 C 是每次操作的固定税。日志的收益也在此显形——崩溃后只需重放最近的日志事务，代价是正常路径上元数据写两遍。

### 5.3 摊销方向：把 D 做大，把 M 与 C 摊薄

五条杠杆都指向同一个方向，即抬高单次操作的 D：

- **合并**：延迟分配把 30 s 窗口内的多次小写并成一段，D 从 4 KiB 变成数百 KiB，A 从 10 降到 2 以下。
- **预分配**：`fallocate` 一次把 M 付清（位图、extent、日志各一遍），后续写只付 D；NTFS 侧对应 `SetEndOfFile` 先扩大小、再由写回填。
- **批处理**：`commit=5` 让 C 按事务摊薄，事务越大 C 占比越低；`fsync` 合并同理（4.3）。
- **小文件形态**：1 万个小文件各付 10 块写，合计 400 MiB 设备写换 40 MiB 数据，A 恒为 10；打包成一个大文件后 A 趋近 1，这正是归档格式在冷数据场景仍占优的算术原因。
- **介质层**：以上都是逻辑块写；SSD 的 FTL 还要按擦除块做垃圾回收，小文件随机写在逻辑 A 之上再乘 2~3 倍物理写，故「逻辑账好看」不等于「闪存寿命好看」。

## 六、挂载与卷栈：块设备如何变成路径上的一段

```text
 块设备到路径的两段接线（左：Linux 单根树；右：NT 对象命名空间）

   /dev/nvme0n1p2                          \Device\HarddiskVolume3
        │ ① 读超级块（ext4_fill_super）           │ ① MountMgr 分配卷 GUID
        ▼                                        ▼
   super_block（布局参数）                   VOLUME 设备对象 + VPB
        │ ② vfsmount 挂到挂载点 dentry           │ ② 文件系统驱动 Attach 到卷
        ▼                                        ▼
   mount namespace 里的树                    NTFS 卷设备（FCB 树根）
        │ ③ 遍历跨过挂载点                        │ ③ \??\C: → 卷设备（符号链接）
        ▼                                        ▼
   /home 下的目录项                          C:\ 下的目录项
```

前五节的对象都活在「已挂载的文件系统」里，本节补上这个前提：卷怎么被识别、超级块怎么建立、命名空间怎么接上。第二节已从路径侧看过「跨挂载点」这一跳，这里从设备侧看同一跳的另一半。

### 6.1 挂载四步：识别、读表、建对象、接树

| 步骤 | Linux | NT | 产物 |
| --- | --- | --- | --- |
| 识别 | 分区表或 `mount` 参数给出设备号，`blkid` 校验 | MountMgr 枚举卷、分配 `\??\Volume{GUID}` | 设备对象 |
| 读表 | `ext4_fill_super` 读超级块、校验、必要时重放日志 | NTFS 读引导扇区与 `$LogFile`，校验卷状态 | 布局参数 |
| 建对象 | `super_block` 加根 `dentry`/`inode` | `VOLUME` 设备对象加 `VPB` 加根 FCB | 内存中的文件系统实例 |
| 接树 | `vfsmount` 挂到挂载点，计入 mount namespace | 盘符符号链接或卷挂载点重解析 | 路径可达 |

四步里只有前两步碰设备，后两步只建内存对象。干净卷的挂载落在毫秒档（一次超级块读加若干元数据块）；非干净卷要先重放日志，耗时按日志量与事务数走秒档，这正是非正常关机后首次挂载明显变慢的原因。`VPB` 是 NT 的绑定点：它把卷设备对象与文件系统设备对象互指，卷栈向下走时据此找到「这个卷挂的是哪个文件系统」；Linux 的对应绑定分成两级——`super_block` 记文件系统实例，`vfsmount` 记「该实例挂在树的哪个位置」，一个 `super_block` 可以被多个 `vfsmount` 引用。

### 6.2 路径拼接：挂载点标记对盘符符号链接

VFS 的挂载点标记在 `dentry` 上（`DCACHE_MOUNTED`）：遍历到该项时 `follow_mount` 换一个 `vfsmount` 继续，0 次 IO、不产生新的路径串。同一 `super_block` 被多个 `vfsmount` 引用即 bind mount，所以「同一文件系统出现在树里多处」在 VFS 里是一等能力，不需要复制目录项。NT 没有这个中间层：盘符是对象命名空间里的符号链接（第二节量过，1 次解析），卷挂载点是 NTFS 重解析点（`IO_REPARSE_TAG_MOUNT_POINT`），解析时由重解析器改写路径再走一遍。文件系统驱动只看得到「卷 + 剩余路径」，看不见全局树，故 NT 的挂载关系分散在符号链接与重解析点两处，而 Linux 的挂载关系集中在 `vfsmount` 一张表里。

### 6.3 命名空间归属与卸载

归属方式决定隔离粒度。Linux 的 mount namespace 每进程一份，`CLONE_NEWNS` 复制后各自增删挂载，容器因此能有自己的根；NT 的对象命名空间全局一份，`\Device` 下的卷是同一批，盘符符号链接则按登录会话各一份（`\Sessions\<id>\DosDevices`），故同一台机器两个会话可以有不同盘符映射，但看到的是同一批卷。

卸载两侧都要求「先 flush 再摘」。Linux 的 `umount` 先把该文件系统的脏页写完（4.3），仍有打开文件或子挂载时返回 `EBUSY`，`umount -l` 把摘除延后到引用归零；Windows 要依次 `FSCTL_LOCK_VOLUME` 独占、`FSCTL_DISMOUNT_VOLUME` 摘除、`DeleteVolumeMountPoint` 删挂载点，卷忙时第一步就失败。顺序不能反：摘除后页缓存里的脏页失去回写目标，只能丢——这正是卸载路径必须接在回写路径之后的原因。
