# 操作系统概述

## 核心定义：夹在硬件与应用之间的管理者

操作系统（Operating System，OS）是运行在 CPU 最高特权级上的一层软件，夹在硬件与应用程序之间，做两件事：

1. **管理**：把硬件资源——CPU 时间、内存容量、磁盘空间、外设——分配给同时运行的多个程序，并裁决它们之间的冲突。
2. **抽象**：给程序提供比硬件简单得多的接口。程序面对的是"进程、地址空间、文件、socket"，而不是"寄存器、扇区、中断线"。

**为什么必须有这层软件（约束）**：没有 OS 的裸机上，一次只能跑一个程序，这个程序直接操作全部硬件。这带来三个无法接受的问题：

- **无隔离**：程序的一次越界写可以改坏任意内存，包括引导代码本身——一个 bug 毁掉整台机器。
- **无共享**：两个程序想同时用 CPU 和内存，结果不是分工而是互相踩踏。
- **太复杂**：每个程序都要自带全部硬件的控制代码——同一块网卡，每个软件各写一遍驱动逻辑。

OS 把这三个问题一次性收编：隔离由特权级和虚拟内存保证（下文与 04-内存管理），共享由调度与分配保证（03-进程与线程），复杂性由统一接口和驱动模型吸收（05-文件系统、06-IO与设备管理）。

## 内核态与用户态：特权级隔离

隔离的物理根基不在 OS，而在 CPU：x86 提供 4 个特权级（Ring 0~3），当前特权级记录在代码段寄存器（CS）的低两位，每条指令执行时都带着它。特权级决定指令的资格：装载页表基址（CR3）、开关中断、直接访问设备端口这类**特权指令**，在低特权级下执行会立刻触发异常，由内核接管。

实践中只用两级：

| 特权级 | 名称 | 谁运行在这 | 能做什么 |
|--------|------|-----------|---------|
| Ring 0 | 内核态（Kernel Mode） | OS 内核 | 一切：全部特权指令、全部物理内存、全部设备 |
| Ring 3 | 用户态（User Mode） | 应用程序 | 只能算数和访问自己的虚拟地址空间；碰特权指令即异常 |

这个划分的理由（约束）是**故障隔离**：应用代码不可信——有 bug，甚至恶意——它绝不能直接碰硬件和别人的内存。但应用又确实需要硬件服务：读文件、发网络包、申请内存。解决办法是把所有危险操作收进内核，只留几条受控入口。这就是下一篇的主题：**系统调用、异常、中断是进出内核仅有的三扇门**。

## 内核的四大职能

内核（Kernel）是 OS 的主体：开机后常驻内存、运行在 Ring 0 的那份代码。它的职能对应本部分后续四篇：

| 职能 | 管理的对象 | 提供给应用的抽象 | 对应篇目 |
|------|-----------|-----------------|---------|
| 进程管理 | CPU 时间 | 进程、线程 | 03-进程与线程 |
| 内存管理 | 物理内存 | 私有地址空间 | 04-内存管理 |
| 文件系统 | 磁盘块 | 文件与目录 | 05-文件系统 |
| 设备管理 | 外设 | 设备文件、I/O 接口 | 06-IO与设备管理 |

四大职能不是四个孤岛，它们咬在同一条数据流上：进程（03）要跑起来需要地址空间（04），地址空间的内容往往来自文件（05），文件的读写最终落在设备上（06）。02 的系统调用则是应用访问这四个职能的统一入口。

## 内核之外：系统库、工具与发行版

内核再大也只是 OS 的一部分。一个能开机干活的系统，还住着两类用户态设施：

- **系统调用库（如 glibc）**：应用几乎从不直接执行 `syscall` 指令——代码里的 `read()`、`fork()` 都是普通函数调用，由库完成参数搬运与指令触发（02 篇的包装函数）。库还兼任入口胶水：程序的起点是 `_start` 而非 `main`（03-编程运行环境 的链接与装载一篇）。
- **系统工具与服务**：shell、`ls`/`cp` 这类 coreutils、以及开机后的第一个进程 init（07 篇）。它们没有任何特权，全是普通用户态程序——04-终端与Shell 正是从"shell 是个普通进程"讲起的。

**"Linux 是内核，不是操作系统"**的说法由此而来：内核只有一份（Linus 维护的那棵树），而 Ubuntu、Fedora、Debian 这些**发行版（Distribution）** = Linux 内核 + 一套选定版本的库和工具 + 包管理器。同一份内核配上不同的用户态组件，就拼出不同的发行版。

应用能跨发行版运行，靠的是**接口的稳定性承诺**：Linux 内核的系统调用 ABI 长期承诺不破坏（"不破坏用户空间"是内核社区的第一戒律），POSIX（Portable Operating System Interface，可移植操作系统接口）约定了 Unix 系系统共同的函数与语义。02 篇讲的系统调用门，正是这层承诺的物理载体。

## 内核形态：宏内核、微内核与混合内核

四大职能装在哪，有三种结构方案。分歧点只有一个：**多少代码放在 Ring 0**。

- **宏内核（Monolithic Kernel，Linux、传统 UNIX）**：四大职能全部在 Ring 0，内部交互就是普通函数调用，零切换开销。代价是爆炸半径大：任何驱动的 bug 都以内核权限执行，一处崩溃拖垮整机。Linux 的补救是模块化——驱动做成可动态装卸的内核模块（.ko 文件）——但模块仍跑在 Ring 0，权责不变。
- **微内核（Microkernel，MINIX、seL4）**：Ring 0 只留最小集合（调度、进程间通信、内存映射），文件系统和驱动挪到用户态，当普通服务进程跑。驱动崩溃只损失一个进程，重启即可。代价在性能：一次读文件要跨多次进程边界，每次跨界都是特权级切换的开销。
- **混合内核（Hybrid Kernel，Windows NT、XNU）**：承认纯微内核的通信开销不可接受，把性能敏感的服务拉回 Ring 0，但保留微内核的分层骨架。macOS/iOS 使用的 XNU 是最典型的实例，其内部结构在 08-移动OS架构 展开。

形态之争的本质是同一笔账的两端：Ring 0 里的代码越多，交互越便宜，爆炸半径越大。三种形态是对"性能 vs 故障半径"这束约束给出的三个不同答案。

## 虚拟化：内核之下再垫一层

虚拟化把"一台物理机器"本身也变成可切片分配的抽象：虚拟机监视器（Hypervisor）运行在比内核更高的特权级（Intel VT-x 为此新增 VMX root 模式），把硬件切片分给多个虚拟机（VM），每个 VM 里跑一个完整的、对此不知情的 OS。

- **Type 1（裸金属型）**：hypervisor 直接跑在硬件上（ESXi、Hyper-V、Xen），是机房与云平台的标准形态。
- **Type 2（托管型）**：hypervisor 是宿主 OS 上的一个进程（VMware Workstation、VirtualBox），虚拟机相当于宿主里的一个应用。

早期 x86 虚拟化的难点在于部分敏感指令在低特权级下不触发异常而是静默失效，hypervisor 抓不到它们，只能靠二进制翻译在运行时改写客户机代码。2005 年起 Intel VT-x 与 AMD-V 用硬件新增特权级直接消除这个问题，虚拟化开销从"慢数倍"降到百分之几的量级。云时代的全部弹性——按秒创建、随时销毁、超卖复用——都建立在这一层之上。
