# 内核与系统调用

> **版本基准**: universal

## 定义

内核是操作系统中**唯一运行在特权模式（Ring 0）的软件组件**，持有全部硬件资源的所有权。系统调用是用户态进程进入内核态的唯一入口，通过专用指令（syscall/sysenter）实现特权级跨越。内核的设计目标是在有限硬件上支持多个并发进程，并保证故障隔离——一个进程的崩溃不能导致另一个进程或内核本身崩溃。

**归约视角：** 系统调用的本质是将用户态的**受限资源请求**归约为内核态的**特权操作序列**。从数学上讲，这是从用户空间函数集合到内核空间函数集合的一个偏序映射，约束条件由硬件特权级机制 enforce。

## 数学模型

**系统调用的本质是受控函数查找：**

$$
\text{内核函数指针} = \text{sys\_call\_table}[\text{syscall\_number}]
$$

sys_call_table 是内核中的一张函数指针数组，系统调用号是数组索引。查找过程在 O(1) 时间内完成。

**参数传递约定（x86_64 System V ABI）：**

| 寄存器 | 参数1 | 参数2 | 参数3 | 参数4 | 参数5 | 参数6 |
|--------|-------|-------|-------|-------|-------|-------|
| x86_64 | RDI | RSI | RDX | R10 | R8 | R9 |

返回值写入 RAX：非负值表示成功，负值（-errno）表示错误。

**快速系统调用的性能差异：**

| 机制 | 指令 | 上下文保存量 | 典型延迟 |
|------|------|-------------|---------|
| 传统中断 | `int 0x80` | 完整中断帧（压栈 CS/IP/FLAGS/SP 等 10+ 寄存器） | ~300-500 周期 |
| 快速系统调用 | `syscall` | 仅保存 RIP/RFLAGS/CR3/SP（4 寄存器） | ~100-150 周期 |

syscall 之所以快，是因为它避免了解码中断向量表和压栈中断帧的通用逻辑，专用硬件（MSR）直接跳转到内核指定入口。

**MSR（Model Specific Register）机制深层解析：**

x86_64 快速系统调用依赖三个 MSR 寄存器：
- `IA32_STAR` (0xC0000081)：高 32 位存内核 CS/SS（Ring 0），低 32 位存用户 CS/SS（Ring 3）
- `IA32_LSTAR` (0xC0000082)：64 位，存 syscall 入口函数地址
- `IA32_CSTAR` (0xC0000083)：64 位，存 32 位兼容模式入口
- `IA32_SYSCALL_FLAG_MASK` (0xC0000084)：syscall 行为控制标志

执行 `syscall` 时，CPU 自动完成：
1. RIP ← IA32_LSTAR（内核入口）
2. RFLAGS ← RFLAGS AND NOT IA32_SYSCALL_FLAG_MASK
3. CS ← IA32_STAR[47:32]
4. SS ← CS + 8（Ring 0 栈段）
5. CPL ← 0

返回时 `sysret` 使用 IA32_STAR 低 32 位设置 CS/SS。

**IA32_LSTAR 写入的约束：**
- 只有 Ring 0 可写（WRMSR 指令在 CPL > 0 时触发 #GP）
- 内核启动时写入，从此 syscall 入口固定
- 这意味着攻击者无法劫持 syscall 入口（除非通过内核漏洞）

**特权级检查的数学形式：**

$$
\text{有效特权级} = \max(\text{CPL}, \text{RPL}), \quad \text{访问许可} = (\text{CPL} \leq \text{DPL}) \land (\max(\text{CPL}, \text{RPL}) \leq \text{DPL})
$$

数据段访问要求 $\max(\text{CPL}, \text{RPL}) \leq \text{DPL}$ ；代码段（门描述符）访问要求 $\text{CPL} \leq \text{DPL}$ 。 ；代码段（门描述符）访问要求 $\text{CPL} \leq \text{DPL}$ 。 。

**数据所有权变换路径：**

| 阶段 | 数据位置 | 所有权归属 | 变换操作 |
|------|----------|------------|----------|
| 用户调用 | 用户栈 (RDI/RSI/RDX) | 用户进程 | - |
| 进入内核 | 内核栈（副本） | 内核（临时） | copy_from_user() |
| 文件系统 | VFS inode cache | 内核 | 查找 fd → inode |
| 设备驱动 | DMA 缓冲区 | 设备 | 写入磁盘控制器 |
| 返回用户 | RAX 寄存器 | 用户进程 | 返回值传递 |

参数验证是安全关键步骤：用户态传入的指针必须经过 `access_ok()` 检查，确认指向用户地址空间。若跳过此检查，恶意程序可利用内核函数读写任意物理地址——这是特权升级漏洞的常见根因。

**access_ok() 的精确语义：**

```c
static inline bool access_ok(const void __user *ptr, size_t size) {
    unsigned long addr = (unsigned long)ptr;
    return addr < TASK_SIZE_MAX && (addr + size) <= TASK_SIZE_MAX;
}
```

`TASK_SIZE_MAX` 在 x86_64 上为 `0x00007FFFFFFFFFFF`（用户空间上界）。检查确保：
- `ptr` 在用户空间范围内
- `ptr + size` 不溢出（无 wrapping）
- 指针指向的页面在物理内存中（P=1 的用户页）

**未验证 access_ok() 的攻击向量：**

```
场景：某内核函数接受用户指针但未调用 access_ok()
攻击者构造：
1. fd = open("/proc/kernel_symbol", O_RDWR)
2. write(fd, kernel_address, sizeof(kernel_address))
   → 内核直接解引用用户传入的 "kernel_address"
   → 若该地址在内核空间，写操作修改内核数据结构
   → 若该地址是内核符号表 → 控制流劫持

利用前提：
- 内核函数使用用户指针直接解引用
- 内核函数不使用 copy_from_user() / get_user()
- 这样的 bug 历史上出现过多次（如早期的 procfs 读写）
```

**copy_from_user() 的安全语义：**

```c
unsigned long copy_from_user(void *to, const void __user *from, unsigned long n) {
    if (access_ok(from, n)) {
        // 执行拷贝
    }
    // 若 access_ok 失败，清零目标缓冲区并返回 n
    memset(to, 0, n);
    return n;
}
```

注意：copy_from_user() 在 access_ok 失败时**不清空数据**（只清零），这是设计选择——内核不能假设用户提供了有效缓冲区，因此不能复制不可知的数据。返回 n 表示"还有 n 字节未拷贝"。

**违反约束的后果：** 若跳过 access_ok()，恶意程序可通过构造指向内核地址的指针，触发内核对任意物理地址的读写。这是特权升级漏洞（local privilege escalation）的常见根因。

## 机制

### 特权级与保护

CPU 通过 CS 寄存器的 RPL（请求特权级）和 CPL（当前特权级）字段，以及段描述符的 DPL（描述符特权级）字段实现三维保护。这是硬件 enforce 的访问控制矩阵，不是软件约定。

**约束条件：**
- 用户态执行 `cli`（清除中断标志）→ CPU 查 CPL=3 > 0，触发 #GP
- 用户态访问内核线性地址（如直接映射区 0xFFFF880000000000 以上）→ 页表权限位检查失败，触发 #PF

**违反约束的后果：** #GP 异常递达内核，内核可选择发送 SIGSEGV 杀死进程，或在内核 Bug 情况下 panic。#PF 发生在内核态本身时，内核无法恢复（double fault → panic）。

### 中断/异常向量

| 向量 | 类型 | 触发条件 | 用途 |
|------|------|----------|------|
| 0x00 | 异常 | 除零 | CPU 内部错误 |
| 0x0D (#GP) | 异常 | 权限检查失败 | 越权访问 |
| 0x0E (#PF) | 异常 | 页表 P=0 或权限不足 | 缺页/越页访问 |
| 0x80 | 中断 | `int 0x80` | Linux 32-bit syscalls（旧） |
| syscall | 中断 | `syscall` 指令 | Linux 64-bit syscalls |

页面错误（#PF）的二次分发决定进程命运：

| 条件 | 内核决策 | 结果 |
|------|----------|------|
| P=0，VA 在进程合法区间内 | demand paging / COW | 分配物理页 |
| P=0，VA 在 guard page（栈与堆/数据之间） | 栈扩展 | 分配新页 |
| P=0，VA 在 mmap 区域（匿名） | 分配匿名页（swap backup） | 进入 swap 流程 |
| P=0，VA 在 mmap 区域（文件） | 从文件读取 | 页缓存填充 |
| P=0，VA 超出版界线（mmap_base~user_space_end） | SIGSEGV | 进程终止 |
| P=1，权限不足（R=0 且写入，或 X=1 且 NX） | SIGSEGV | 进程终止 |
| P=1，设备映射（/dev/mem 等） | I/O 操作 | 设备访问 |

**#PF 发生时的精确地址检查流程：**

```
do_page_fault():
  1. 获取错误码 (CR2 register = 触发地址)
  2. 判断在用户态还是内核态触发
  3. 若内核态：
     a. vmalloc_fault()：检查是在 vmalloc 区域（fixmap/ioremap）
     b. 若不在合法内核区域 → bad_page_fault() → oops
  4. 若用户态：
     a. find_vma()：查找包含 fault_addr 的 VMA
     b. find_vma() 返回 NULL → SIGSEGV (区间外)
     c. find_vma() 返回 VMA：
        - 检查权限位（VM_READ/VM_WRITE/VM_EXEC）
        - 权限不足 → SIGSEGV
        - 权限足够 → handle_mm_fault() 分配页
```

**write、保护错误与 CoW 的区分：**

当 P=1 但 R=0（只读页）触发写操作时：
- 若页由 `vm_flags = VM_SHARED` 映射 → SIGSEGV（共享文件/设备不可写）
- 若页由 `vm_flags = VM_PRIVATE` 映射 → COW（私有映射，写时复制）
  - 内核分配新物理页
  - 复制原页内容到新页
  - 更新页表指向新页（现在可写）

**违反约束的后果：** #PF 发生在内核态且无法恢复时（如 fixmap 区域外的内核地址），触发 `panic()` 或 `oops`。用户态 #PF 若处理不当（如递归 page fault），触发 double fault → triple fault → 系统复位。

### 系统调用号与表查找

Linux 系统调用号定义在 `arch/x86/entry/syscalls/syscall_64.tbl`，每个架构有独立编号表。查找路径：

$$
\text{用户 RAX (syscall 号)} \xrightarrow{\text{aligned\_array}} \text{函数指针} \xrightarrow{\text{call}} \text{内核函数}
$$

**约束条件：**
- syscall 号必须有效（< NR_syscalls），否则返回 -ENOSYS
- 指针参数必须通过 access_ok()，未验证指针导致内核读取任意用户态地址

**违反约束的后果：**
- 无效 syscall 号 → `-ENOSYS` 返回用户态（进程不会崩溃，但不执行任何操作）
- 未验证指针 → 内核信息泄露（读取用户态内存作为内核数据返回）或死机（如果内核尝试解引用无效指针）

### 内核地址空间布局（x86_64）

```
[0x0000000000000000, 0x00007FFFFFFFFFFF]  用户空间（128TB）
[0xFFFF800000000000, ...]                  内核直接映射区（物理页直接映射）
[0xFFFF880000000000, ...]                  内核 vmalloc/模块区域
[0xFFFFFFFF80000000, ...]                  内核 text 段（恒等映射）
```

用户态地址和内核态地址在 x86-64 上从不重叠，这是有意设计，防止内核数据泄露到用户态（KAISER/KPTI 缓解 Meltdown 的基础）。

**内核直接映射区（direct map）的精确结构：**

| 区域 | VA 范围 | PA 映射 | 大小 |
|------|---------|---------|------|
| compat过年 mapping | 0xFFFF800000000000 - 0xFFFF87FFFFFFFFFF | PA = VA - 0xFFFF880000000000 | ~128TB |
| vmalloc | 0xFFFF880000000000 - 0xFFFFC8FFFFFFFFFF | 非线性（页表查找） | ~128TB |
| modules | 0xFFFFC90000000000 - 0xFFFFC9FFFFFFFFFF | 相对 vmalloc 连续 | 2GB |
| physmem | 0xFFFFEA0000000000 - 0xFFFFED0000000000 | PA / 2^12 | 64TB |

早期 Linux（2.6以前）使用线性映射：VA = PA + PAGE_OFFSET（0xC0000000），只支持 1GB 物理内存。4GB 以上需要高端内存（highmem）。现代 x86_64 使用 direct map + vmalloc 分离：

- **direct map**：连续 VA 空间，直接 PA=VA-offset 换算，O(1) 访问任意物理页
- **vmalloc**：非线性映射，通过页表动态建立映射，支持远大于 direct map 的物理内存

**归约视角**：内核直接映射区的物理地址和虚拟地址存在线性关系 $\text{VA} = \text{PA} + \text{DIRECTMAP\_OFFSET}$ ，使内核可以 O(1) 访问任意物理页而不需要页表查找。这是空间换时间的经典 trade-off。 ，使内核可以 O(1) 访问任意物理页而不需要页表查找。这是空间换时间的经典 trade-off。

### 常见系统调用解析

**openat 系统调用流程：**

```c
// 用户态
fd = openat(dirfd, "/path/to/file", O_RDONLY);

// 内核态 (sys_openat)
1. copy_from_user(pathname, user_path);
2. struct path path;
3. path_lookupat(dirfd, pathname, LOOKUP_FOLLOW, &path);
4. struct inode *inode = path.dentry->d_inode;
5. check permissions(inode, MAY_READ);
6. alloc file descriptor (fd);
7. allocate file* and link;
8. return fd;
```

**read 系统调用流程：**

```c
// 用户态
ssize_t n = read(fd, buf, count);

// 内核态 (sys_read)
1. struct fd f = fdget(fd);
2. struct file *file = f.file;
3. check file->f_mode & FMODE_READ;
4. loff_t *pos = &file->f_pos;
5. ssize_t ret = file->f_op->read(file, buf, count, pos);
6. fdput(f);
7. return ret;
```
