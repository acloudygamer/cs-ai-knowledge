# 移动 OS 架构

## 核心定义：同一主线，不同约束

Android 的内核是 Linux，iOS 的内核 XNU 里住着完整的 BSD 层——移动 OS 没有重新发明操作系统。前七篇讲的每一条机制（进程、虚拟内存、文件、驱动）在手机里原样存在。变的是**约束**，而约束变了，形状就跟着变：

| 约束 | 桌面/服务器 | 手机 |
|------|------------|------|
| 能源 | 插座管够 | 电池是硬约束：每一毫瓦都记账 |
| 信任模型 | 用户装的少数软件，基本可信 | 应用商店模型：百万个互不信任的应用同机运行 |
| 响应要求 | 批处理可容忍延迟 | 触控：掉帧直接可感 |
| 存储 | swap 随便用 | 闪存有写入寿命（《硬件组成》的 DWPD），不能当 swap 随便磨 |

本篇沿前七篇的主线，看这四条约束在两大系统上各自塑出什么形状。

## Android：Linux 内核上的重定制

### Binder：为什么 IPC 要另造一套

Android 把所有系统服务（窗口、定位、通知、传感器……）拆成独立进程，应用的一切能力请求都要跨进程调用——IPC 在手机上是**最高频操作**，且每次调用都必须回答"谁在调我"（权限检查的锚点）。Linux 现成的管道/socket 两头都够不着这个约束：身份靠不住（对端自称是谁就是谁），数据还要进出两次内核缓冲区。

Binder 是为此专门造的 IPC 机制（驱动挂在 `/dev/binder`）：**内核亲自携带调用者的 UID/PID**——身份由内核背书，接收方拿到的不是声明而是事实；数据从发送方地址空间**一次拷贝**直达接收方映射区，比 socket 的两次少一半；还能跨进程传递文件描述符（把"访问权"连同消息一起递过去）。03 的进程隔离在此反转成协作接口：容器依然分开，但容器之间开了一条带安检的高速通道。

### Zygote：预热的进程模板

应用启动慢的根源在于每次都要从零初始化运行时和框架类。Android 的解法是 **Zygote**：开机时启动一个模板进程，预先把框架类和运行时环境加载好；启动新应用 = 从 Zygote `fork()` 出来。03 的 fork/COW 机制在这里兑现双重红利：启动时间只剩一次 fork（毫秒级），且所有应用共享 Zygote 那份只读框架页——几十个应用进程共用同一份物理内存，COW 保证谁改写谁才单复制一份。内存紧张和启动速度两条约束，被同一个机制同时回应。

### ART：把 JIT 挪到安装时

Dalvik（早期 Android 运行时）是纯 JIT：每次运行都把字节码边翻译边执行，CPU 在运行期反复做编译的功——在电池上这就是浪费。ART（Android 5.0，2014 年取代 Dalvik）改为**安装时预编译（AOT）**：应用安装那一刻就把字节码编译成本机码，运行时零编译开销。后来（7.0 起）演进为混合策略：先 AOT 快速安装，运行时收集热点画像，空闲时再按画像优化重编译。整条演进线的主轴始终没变：编译这笔 CPU 账，能挪出运行期就挪出去。

### 低内存管理：OOM killer 的前移版

手机没有 swap（闪存寿命约束），内存紧张时 04 的"换出"退路不存在，剩下的唯一手段是杀进程。但桌面 OOM killer 的逻辑是"耗尽时的最后裁决"——手机上等到耗尽就晚了：可能恰好杀掉你正在看的前台应用。

Android 把同样的思想前移为**按优先级主动清理**：每个进程按状态分级（前台应用 > 可见 > 服务 > 后台 > 缓存），低内存杀手（早期是内核里的 LMK 驱动，后来挪到用户态的 lmkd）按级别从低到高提前收割。缓存进程被杀不是事故而是设计：它存在的意义就是"内存富裕时的加速器，紧张时的储备粮"。

### 功耗与实时：电池和 16 毫秒的账

约束表里的"能源"与"触控"两行，在系统里落成两套纪律。

**功耗纪律的中心是"唤醒要收税"**：无线电和 CPU 从睡眠中醒来有一笔不小的固定代价，零散频繁的唤醒比一次长忙更耗电。对策成体系：

- **调度器感知能耗**：按负载升降 CPU 频率（DVFS）；ARM 大小核（big.LITTLE）把轻活推给小核，重活才惊动大核；
- **休眠批处理**：Doze 模式（Android 6.0 起）在灭屏后把网络访问、定时器、同步任务全部推迟到周期性的维护窗口——零散唤醒被对齐成批量唤醒；
- **统一推送**（FCM / APNs）：不让每个应用各自保活长连接——几百条长连接意味着无线电永不睡眠。系统级单通道代收所有推送，应用被消息唤醒才起身。缺少统一通道的生态里，各家应用自建保活链，功耗与内存双输——这是生态级的反例。

**实时纪律的中心是 16.6ms**：60Hz 刷新意味着每帧预算只有 16.6 毫秒，UI 线程一卡就掉帧。所以"主线程不做耗时操作"是移动开发的铁律——与《编程运行环境》04 事件循环的纪律完全同构：唯一的执行流只做调度，重活一律外包。

### 应用沙盒：最小新机制原则

商店模型要求每个应用都被当作潜在恶意对待。Android 的答案极简：**安装时给每个应用分配一个独立 UID**——直接复用 Linux 多用户隔离这套四十年的老机制，进程、文件、权限检查全部自动就位，一行新机制都不用发明。之上再叠加 SELinux 强制访问控制（4.3 引入、5.0 全面强制）收紧边界。这是 01 那句"抽象提供"的逆向用法：隔离机制不变，只是分配粒度从"一个用户"细化到"一个应用"。敏感能力（相机、通讯录、定位）再叠一层**运行时权限**（Android 6.0 起）：安装时只声明、使用时才弹窗——授权决策从安装一刻推迟到使用一刻，用户带着上下文才好判断。

## iOS：XNU——混合内核的教科书实例

iOS/macOS 的内核 XNU 是 01 讲的混合内核最完整的实例，三个部件各占一层：

| 部件 | 血统 | 管什么 |
|------|------|--------|
| Mach | 微内核思想 | 任务/线程抽象、IPC（端口消息）、虚拟内存 |
| BSD | 宏内核血统 | POSIX 系统调用（02 的门）、网络栈、文件系统 |
| IOKit | 自研 | 驱动模型（C++ 子集编写） |

Mach 提供微内核的骨架（一切资源经由端口消息访问），BSD 把性能敏感的 POSIX/网络/文件服务拉回内核态——01 那笔"性能 vs 故障半径"的账，XNU 选择两边各取一段。

iOS 的安全模型把 07 的信任链延伸到每个字节：Secure Boot 从固件验签 bootloader、内核开始，**代码签名一直签到每个应用的每一页**——没有有效签名的代码页根本无法执行（内核拒绝映射）。配合每应用强制沙盒（Seatbelt 策略：白名单式声明你能碰什么），商店模型的信任问题被压进密码学：不是"检测恶意"，而是"未授权的根本运行不了"。

内存管理上 iOS 同样无 swap（早期）并以 **Jetsam** 按优先级杀进程——与 Android lmkd 同构：同一条闪存寿命约束，长出同一个形状的机制。近年 iOS 对后台地址空间启用了压缩换出，思路与 zram 一致：宁可烧 CPU 压缩，不磨闪存。

后台纪律上 iOS 更激进：应用退到后台几秒内即被挂起，只有音乐、导航、VoIP 等白名单模式可以续命，其余任务必须交给系统统一调度——与 Doze 同一套"唤醒收税"逻辑，只是执行得更早更绝。

## 收束：约束塑形

把本篇折回主线：Binder 是 03 进程隔离上的安检通道，Zygote 是 03/04 fork 与 COW 的工程化榨取，ART 是"编译开销何时支付"的时序挪移，lmkd/Jetsam 是 04 OOM killer 在无 swap 约束下的前移，UID 沙盒是 01 隔离机制的粒度细化，Doze 与统一推送是把唤醒次数当成能耗来记账。**没有一条是移动端独有的新原理**——它们全是同一条主线在不同约束下长出的不同形状。这也回应了本部分的组织逻辑：先讲清约束与机制（01-07），变体（08）就只是机制在新约束下的重新推导，而不是另一堆要死记的新知识。
