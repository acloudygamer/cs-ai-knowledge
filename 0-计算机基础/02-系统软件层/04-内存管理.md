# 内存管理

## 核心定义：私有地址空间这个"谎言"

《硬件组成》讲过地址翻译的硬件：MMU 查页表、TLB 缓存翻译、缺页触发异常。本篇讲同一个机制的软件一侧：**页表由谁建、物理页从哪来、不够用时谁被赶走**。

内存管理的核心产品是第二条抽象：**每个进程都以为自己独占一整片连续地址空间**——从 0 到 $2^{48}$（x86-64 当前实现的 48 位虚拟地址），地址在编译链接时就写死进代码，运行时不用关心物理内存在哪、够不够、和谁共享。这个"以为"由三方合谋维持：

- **CPU（MMU）** 提供翻译硬件：每条访存指令把虚拟地址过一遍页表；
- **内核** 建造和维护页表：决定每个虚拟页映射到哪个物理页、什么权限；
- **缺页异常**（02 的门）提供补救通道：翻译失败时让内核现场修路，程序毫无知觉。

为什么需要这个谎言（约束）：物理内存只有一份而进程有几十个，直接暴露物理地址意味着链接器不知道程序会装在哪儿、任何进程都能摸到别人的数据。虚拟地址空间把"在哪"和"是否够"两个问题都从程序手里收走，交给内核按需兑现。

## 地址空间的布局与 VMA

一个进程的地址空间不是一整块，而是若干段**虚拟内存区域（Virtual Memory Area，VMA）**的拼接，每段有自己的权限和后备来源：

```text
高地址  ┌─────────────────────┐
        │ 栈（Stack）          │ 向低地址生长；函数帧、局部变量
        ├─────────────────────┤
        │ mmap 区              │ 动态库、malloc 大额分配、文件映射
        ├─────────────────────┤
        │ 堆（Heap）           │ brk 管理，malloc 小额分配
        ├─────────────────────┤
        │ BSS / Data           │ 未初始化 / 已初始化全局变量
        ├─────────────────────┤
        │ 代码段（Text）        │ 可执行指令，只读+可执行
低地址  └─────────────────────┘
```

内核用 `vm_area_struct` 记录每一段的起止地址、权限（读/写/执行）、后备（匿名页还是某个文件的映射），并把所有段组织成一棵树（Linux 6.1 起由红黑树换成 maple tree，2022 年）——02 缺页链里"查 X 属于哪段"查的就是它。权限位与页表项联动：代码段标了只读，你写它，MMU 触发异常，内核判决 SIGSEGV。

栈那段还有一个守卫：栈向低地址生长，长过头就撞上未映射的守卫区域——同样走缺页链、同样判决 SIGSEGV。这就是栈溢出（Stack Overflow）的物理形态：递归失控不是在"栈"这个抽象里溢出，而是真有一条地址撞出了 VMA 边界。

各段的位置每次启动随机偏移（ASLR，Address Space Layout Randomization，地址空间布局随机化），让攻击者无法预知栈和库的地址——这是用内存布局做的安全机制。

## 按需分页：页表是懒出来的

地址空间开得豪迈，物理页却给得吝啬。原则是：**能不分配就不分配，直到有人真的碰**。

- `malloc` 成功返回时，内核只是把堆的 VMA 边界向前推了一格——**一个物理页都没分配**。
- 第一次写这块内存：MMU 发现页表项 Present=0 → 缺页异常（02）→ 内核 `do_page_fault()` 确认该地址落在合法 VMA 内 → 分配物理页、清零（防止读到上一个主人的残留——安全约束）、填入页表 → 返回重执指令。程序只感觉到这次写慢了一点。
- `fork()`（03）复制地址空间时同样不复制物理页：父子页表指向同一批页、全部降级为只读；任何一方写入触发异常，内核现场复制该页给写入方——写时复制（COW）。

这条"VMA 先记账、缺页再兑现"的链条，是 02 的异常机制最大的客户：一次 `fork` 一次 `malloc` 都只是改账本，真正的物理分配全部推迟到异常里按需发生。

**缺页的代价分两级**：minor fault（页其实已在内存、只差填表——COW 复制、页缓存命中都属此类）在微秒以内，可以忽略；major fault（真的要读盘——可执行文件首次装入、swap 换入）等于一次磁盘 I/O，百微秒起。同样叫"缺页"，一个无所谓，一个是灾难——/proc 里的 `minflt`/`majflt` 两个计数器就是这个分级，排查内存型卡顿先看 majflt。

## 物理页分配器：伙伴系统与 slab

缺页异常里那句"分配物理页"，背后是两级分配器。

**伙伴系统（Buddy Allocator）管整页。** 空闲物理页按 $2^k$ 个连续页组织成各阶空闲链表（order 0 = 1 页，order 10 = 1024 页 = 4MB，上限即 4MB）。申请 $2^k$ 页时：对应阶无空闲就从更高阶劈一半下来（两半互为"伙伴"），释放时伙伴若也空闲就合并回高阶。它解决的是**外碎片**：长期运行后空闲内存变成一堆不连续的小洞，大页申请无处可放；伙伴结构保证任意时刻都能尽量拼出大块连续内存。

**slab 分配器管小对象。** 内核自己高频创建销毁的小结构体——`task_struct`、`inode`、`dentry`——若每次都按整页申请，浪费惊人（一页 4KB 装一个几百字节的结构体）。slab 的做法：向伙伴系统批发整页，预切成等长小格做成"缓存"，内核对象从中零售取用。当代 Linux 默认实现是 SLUB。`kmalloc` 走的就是这条路。

用户态的 `malloc` 是这套机制的下游：小额申请增长堆（`brk` 扩张 VMA），大额申请（glibc 默认阈值 128KB）直接走 `mmap` 单独映射——两条路最终都汇到缺页异常和伙伴系统。

顺记一笔连接：伙伴系统的 order 9（512 个连续页）恰好是 2MB 大页的尺寸。《硬件组成》TLB 一节讲过大页把 TLB 覆盖率放大 512 倍；OS 侧的透明大页（THP）机制负责在后台扫描，把零散的 4KB 页搬迁合并成这种 order 9 大块——分配器的一阶，正好接住硬件层的一招。

## 页面回收：谁被赶走

物理页耗尽时的退路，取决于页的来历：

| 页类型 | 后备 | 回收方式 |
|--------|------|---------|
| 文件页（File-backed） | 磁盘上的文件 | 干净的直接丢（要用再读回）；脏的先写回文件再丢 |
| 匿名页（Anonymous） | 没有文件（堆、栈） | 只能写入交换区（Swap）后才能丢 |

内核维护 active/inactive 两条 LRU 链表（按匿名/文件再分）做候选排序：内存压力低于水位线时，后台内核线程 **kswapd** 悄悄扫描回收；压力大到来不及时，申请内存的进程自己被拖去做**直接回收（direct reclaim）**——这就是内存紧张时所有进程一起变卡的机制。

**Swap 的代价账**写在硬件层：DRAM ~100ns，NVMe SSD ~100µs（《硬件组成》存储层次一节，千倍差距）。被换出到 swap 的匿名页下次被碰时，要等一次磁盘读——一次"内存访问"突然变成百微秒级，这就是 swap 命中时服务延迟毛刺的来源。折中方案 zswap/zram：不换到磁盘，而是压缩后留在内存里，用 CPU 换容量。

## OOM killer：最后的裁决

回收也救不回来时（内存耗尽且 swap 已满），内核必须选一个进程杀掉，否则全系统卡死。OOM killer 给每个进程算 `oom_score`（大致按占用内存比例计分），挑分最高的下手。`oom_score_adj`（-1000~1000）是留给管理员的旋钮：调低保护关键服务，调高让边缘服务先死。

OOM killer 的存在本身是一个设计声明：**Linux 默认允许内存超卖**——`malloc` 承诺的地址空间可以超过物理内存总量（懒分配使超卖通常兑现不了也就无需兑现），OOM killer 是这个乐观策略破产时的兜底。移动端不允许这种兜底逻辑（不能随便杀掉前台应用），于是把同样的思想前移成按优先级主动清理——那是 08-移动OS架构 里 LMK 的故事。

容器化之后 OOM 的账本多了一层：cgroup 给每个容器独立的内存限额与计分，容器内超限触发的是它**自己的** OOM killer——只杀容器内的进程，与整机互不相干（《软件工程概念》05 的 cgroup 限额）。Kubernetes 里"容器莫名重启、日志只有 OOMKilled"的出处就是这一层。
