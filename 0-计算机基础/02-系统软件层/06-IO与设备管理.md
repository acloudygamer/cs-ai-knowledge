# IO 与设备管理

## 核心定义：内核与硬件之间的翻译官

设备管理是内核的第四职能。一件设备在硬件眼里是三样东西的组合：**一组寄存器**（读它拿状态、写它下命令）、**一条中断线**（活干完了通知 CPU，见 02）、**一条 DMA 通道**（数据搬运卸载，见下文）。**驱动（Driver）**就是知道这组寄存器语义的代码：网卡驱动知道哪个寄存器装着收到的包长，磁盘驱动知道怎么把"读第 N 块"翻译成设备命令。设备之间的千差万别全部封在驱动内部，对上只暴露统一接口。

驱动以**内核模块**（.ko）形式存在，可动态装卸——01 说过这不改变宏内核的权责：模块跑在 Ring 0，一个驱动 bug 照样能拖垮整机。设备接入时由 udev 在 `/dev` 下创建设备文件，用主设备号（找哪个驱动）和次设备号（驱动管的几号设备）定位。设备因此也被纳入文件抽象：打开 `/dev/sda` 就能像读文件一样读磁盘——这是"一切皆文件"的真实含义与边界（它统一了命名和打开方式，但设备各有 `ioctl` 这样的后门接口，抽象是漏的，漏得恰到好处）。

设备分两类：**字符设备**（键盘、串口——字节流，没有"第几块"的概念）和**块设备**（磁盘、SSD——定长块的数组，可随机寻址）。05 的文件系统建在块设备之上。

**网络接口是这个分类的例外**：`ls /dev` 里找不到网卡。它不是"按名字读写"的对象，而是协议栈的端点——管理它走 `ioctl`（`ip addr`、`ifconfig` 背后就是这个调用），用它传数据走 socket（《计算机网络》07）。这划出了"一切皆文件"的真实边界：它统一了存储与字节流设备，网络栈天生是 API 形态。

字符设备里最著名的其实是两个假设备：`/dev/null`（写入即丢弃，读即 EOF——输出黑洞）和 `/dev/zero`（读即无限个零字节——04 篇清零页的数据来源之一就有它）。

## DMA：CPU 不当搬运工

**约束**：一次磁盘读要搬 4KB，一次网卡收包要搬几 KB——若由 CPU 逐字从设备寄存器搬进内存，一颗 5 GHz 的核就成了全职搬运工，且搬运本身白烧内存带宽（数据从设备到 CPU 再到内存，走两遍）。DMA（Direct Memory Access，直接内存访问）把搬运卸载给专用控制器（《硬件组成》给了它的定义），本篇看 OS 一侧的协作协议：

```text
驱动申请一块物理连续的 DMA 缓冲区（物理地址必须真实且连续——
  DMA 控制器不过 MMU，不认虚拟地址，这是 04 的页表够不到的地方）
  → 把缓冲区的物理地址 + 长度写进设备寄存器，下达"开始"
  → CPU 脱身去干别的（调度器切走，03）
  → 设备自己把数据搬进内存，完成后拉中断（02 的门）
  → 中断处理函数里驱动验收：数据已在内存，无需一次 CPU 拷贝
```

整条链上 CPU 只做了开头写几个寄存器和结尾收一次中断，中间的搬运一个字节没沾手。

## 块层：请求排队的地方

文件系统（05）回写脏页、应用直接读块设备，最终都变成块层（Block Layer）里的 **I/O 请求**。块层的职责是把零散的请求流整理成设备爱吃的形状，手段有两样：

- **合并**：相邻扇区的两个请求并成一个——设备按"一段连续区间"干活效率最高。
- **排序**：按扇区号排序（电梯算法思想）。这条源自 HDD 的机械约束：磁头寻道要 5~10ms，请求按柱面顺序服务能少走回头路。

SSD 普及后约束改写：没有磁头，排序失去意义，排序本身的开销反倒成了负担。NVMe 设备自己就有数万条硬件队列（《硬件组成》存储层次一节给过这个数字），Linux 块层相应换为**多队列 blk-mq**——每个 CPU 核一条软件队列直接对到硬件队列，请求全程无锁。对足够快的设备，调度器直接选 `none`：什么整理都不做，原样下发。HDD 时代的调度智慧，在约束消失后果断退役——这是"约束变了，形状跟着变"的标准案例。

## I/O 模型：一个线程能等多少个连接

I/O 模型问题不是设备问题，而是**等待的组织问题**：网络服务器守着上万个连接，数据什么时候来不可知，怎么等？

**阻塞 I/O 的极限**。最朴素的写法：`read()` 读 socket，没数据就睡眠（03 的状态机），数据到了被中断底半部唤醒（02 的收包链）。一个连接占一个线程。一万个连接（C10K 问题）就是一万个线程：内存被栈吃光，调度器在就绪队列里空转——瓶颈不是 CPU 不够快，是"一个等待者配一个执行流"这个组织方式本身。

**epoll：把中断的思想搬进软件**。02 里硬件不等 CPU 轮询、有事发中断；epoll 对连接做同样的事——不再挨个问"你有数据吗"，而是登记兴趣、睡眠等待、有事被叫醒：

```text
epoll_create()  → 内核建一个事件表
epoll_ctl(ADD)  → 登记关心的 fd：内核在它的等待队列上挂好回调
                 （数据到达时，唤醒回调顺手把这个 fd 挂进就绪链表）
epoll_wait()    → 进程睡眠；被唤醒时直接拿到"就绪链表"——
                 回来的全是有数据的 fd，一次都不用空问
```

关键差异在就绪链表：轮询（select/poll）每次调用都要把全部 fd 扫一遍，O(N) 且每次重新登记；epoll 登记一次、内核用回调维护"谁就绪了"，`epoll_wait` 返回的只有就绪者。万级连接里活跃的可能只有几十个——epoll 的开销跟着活跃数走，不跟总数走。

通知语义还有两档之分：**水平触发（LT，默认）**——只要 fd 里还有数据没读完，下次 `epoll_wait` 还会叫它，稳妥；**边沿触发（ET）**——只在"从空到有"的瞬间叫一次，之后必须循环 `read` 到 EAGAIN 把数据读空，否则剩余数据再也不会触发通知。ET 换来的是更少的唤醒次数，代价是"必须读空"这条纪律——选它是性能与纪律的交易，多数应用用默认的 LT 就够了。

**io_uring（2019 年 Linux 5.1）再进一步**。epoll 优化了"等"，io_uring 连"叫"都优化掉：用户态和内核态共享两个环形缓冲区——提交队列（SQ）与完成队列（CQ）。提交 I/O 请求 = 往 SQ 里放一个条目，收割结果 = 从 CQ 里取，**批量操作全程不需要系统调用**（02 的门票直接免了）；开启 SQPOLL 模式后内核线程主动轮询 SQ，连提交时的那次 `io_uring_enter` 也省掉。这把 02 的账算到了极致：I/O 密集的代理、数据库因此把 syscall 开销压近归零。

至此四个常被混用的术语可以钉死：**阻塞**——没数据就睡在调用现场等；**非阻塞**——没数据立刻返回 EAGAIN，自己待会再来问；**多路复用**（epoll）——登记一批，问一次，回一批就绪的；**异步**（io_uring 的形状）——提交后立即返回，完成时内核把结果放进 CQ 送上门。前三种都要你自己去"取"，异步是结果自己来"敲门"。

## 零拷贝：数据不过用户态

"把磁盘文件发给 socket"这个最常见的任务，传统写法（`read` + `write`）的完整路径是：

```text
磁盘 ──DMA──► 页面缓存 ──CPU拷贝──► 用户缓冲区
                                      │
socket ◄──DMA── socket 缓冲区 ◄──CPU拷贝──┘
```

数据被 CPU 亲手搬了两次（进出用户态各一次），外加两次系统调用往返。但数据在用户态根本没被看一眼——这次旅行纯属礼节性拜访。**零拷贝**就是把礼节砍掉：`sendfile(out_fd, in_fd, ...)` 一个调用，数据从页面缓存直送 socket 缓冲区；网卡支持分散-聚集（Scatter-Gather）DMA 时，连 socket 缓冲区这一步都省去——DMA 直接从页面缓存取数据送网卡。四次拷贝两次往返，压到两次 DMA 一次调用，CPU 全程旁观。

同一思想在内存方向的亲戚是 `splice`（管道内搬运不过用户态）和 `mmap`（05：连"复制给调用者"都省掉，直接映射页面缓存）。
