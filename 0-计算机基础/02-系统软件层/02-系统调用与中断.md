# 系统调用与中断

## 核心定义：进出内核的三扇门

01-操作系统概述 把危险操作全部收进了 Ring 0，但收编之后必须回答一个问题：控制流怎么合法地跨过去？x86 留给 Ring 0 的入口只有三种，按"谁发起、何时发起"区分：

| 门 | 触发者 | 时机 | 例子 |
|----|--------|------|------|
| 系统调用（System Call） | 当前程序**主动** | 同步：执行到这条指令才发生 | `read()`、`fork()`、`mmap()` |
| 异常（Exception） | 当前程序**被动**：指令自己闯祸 | 同步：由正在执行的这条指令引发 | 缺页、除零、非法指令 |
| 中断（Interrupt） | **外部硬件** | 异步：可以落在任意两条指令之间 | 键盘按键、网卡收包、磁盘 DMA 完成、定时器 |

三扇门共用同一副骨架：CPU 切换到 Ring 0、保存被打断的现场、跳到内核预设的处理函数、处理完恢复现场返回。区别只在入口那一下。本篇沿三条路径各走一遍，最后把骨架抽出来。

## 系统调用：程序主动敲门

### 一次系统调用的完整路径

以 x86-64 上的一次 `read(fd, buf, n)` 为例，从用户态到内核态再返回，链路是：

```text
用户程序调用 read()                       ← 这只是 glibc 里的一个普通函数
    │
    ▼  glibc 包装函数：把参数搬进约定寄存器
       rdi=fd, rsi=buf, rdx=n，rax=系统调用号（read 是 0）
    │
    ▼  执行 syscall 指令 ──────────────── 特权级在此切换
       CPU 硬件完成三件事：
         ① 从 MSR 寄存器（LSTAR）读出内核入口地址，装入 RIP
         ② 切换到该线程的内核栈（栈指针来自 TSS）
         ③ 把用户态的 RIP 和 RFLAGS 压栈保存
    │
    ▼  内核入口汇编（entry_SYSCALL_64）：
       把所有通用寄存器存进栈上的 pt_regs 结构 —— 完整现场
    │
    ▼  查表分发：以 rax 为下标查 sys_call_table[]，调到 sys_read()
    │
    ▼  内核干活（VFS → 文件系统 → 块层，见 05/06）
    │
    ▼  返回路径：恢复 pt_regs 里的寄存器，sysret 指令回到 Ring 3
    │
    ▼  glibc 包装函数检查返回值：
       rax 落在 -4095~-1 区间 → 说明内核返回了错误码，
       取其相反数写入 errno 变量，read() 返回 -1
```

几个关键设计点：

- **参数走寄存器不走栈**：`rdi/rsi/rdx/r10/r8/r9` 依次装前 6 个参数——用户栈在内核眼里是不可信的，参数必须先复制进寄存器或内核空间再校验。这套"编号放哪个寄存器、参数按什么顺序放"的约定就是系统调用 ABI。
- **入口地址由 MSR 预先写好**：`syscall` 指令本身不带目标地址，跳去哪完全由内核开机时写进 MSR（Model Specific Register）的值决定——用户程序无法把入口指到自己的代码。这保证了"门"是收窄的：进内核只能落在内核指定的少数几个入口函数上。
- **`int 0x80` 是旧门**：32 位时代用软件中断进内核，要走完整的中断描述符表查向量，比专用指令慢；x86-64 的 `syscall/sysret` 是为这条路专门开的快速通道。旧机制至今可用，只是没人再用。

### 开销的账与 vDSO 优化

一次普通系统调用的往返（不含内核实际干活的时间）在 2020 年代的 x86 服务器上是 **100 ns 量级**——模式切换、现场保存、查表分发各占一份。对比：一次函数调用约 1 ns。这 100 倍就是"进一次内核"的门票价，也是后文反复出现的优化动机：futex 无竞争时不进内核（03）、页面缓存命中不出内核（05）、epoll/io_uring 批量收割事件（06），本质上都是在省这张门票。

还有两笔账值得知道：

- **vDSO（virtual Dynamic Shared Object）**：对 `gettimeofday`、`clock_gettime` 这类只读内核数据、不碰硬件的调用，内核干脆把数据页映射到每个进程的地址空间里，配一份用户态的读取代码——"系统调用"变成了纯用户态的内存读，开销压到几十 ns 以内。
- **KPTI 的加价**：2018 年 Meltdown 漏洞曝光后，内核引入页表隔离（KPTI，Linux 4.15 合入）：用户态运行时页表里几乎不留内核映射，进出内核要多换一次页表基址。换页表的代价靠 PCID（进程上下文标识符，允许 TLB 同时缓存多套页表的翻译，不必每次清空）来对冲——这两个机制都已在《硬件组成》的 TLB 一节展开，这里只是它们出现在系统调用路径上的位置。

## 异常：被动的同步陷入

异常是当前指令自己引发的门：CPU 执行到某条指令时发现无法继续，转入内核。按能否恢复分三类：

| 类型 | 含义 | 返回后 | 例子 |
|------|------|--------|------|
| Fault（故障） | 可修复 | 重新执行这条指令 | 缺页（#PF，向量 14） |
| Trap（陷阱） | 故意触发 | 从下一条继续 | 断点（int3）、单步调试 |
| Abort（中止） | 不可恢复 | 不返回 | 双重故障（#DF）、机器检查 |

### 缺页异常：最忙的良性异常

缺页（Page Fault）是唯一能"修好自己"的异常，也是 OS 内存管理的发动机。它的完整处理链在 04-内存管理 展开，这里只看它在异常机制上的位置：

```text
指令访问地址 X
  → MMU 查页表：该页 Present = 0（或权限不够）
  → 触发 #PF 异常，CR2 寄存器自动装入肇事地址 X
  → 内核 do_page_fault()：在进程的 VMA 链表/红黑树里查 X 属于哪段
      ├── 合法但未分配（malloc 过还没碰、fork 后该写时复制）
      │     → 分配物理页、填页表、iret 返回重执该指令 —— 程序毫无知觉
      └── 非法（不在任何 VMA，或权限不符）
            → 给进程投递 SIGSEGV 信号 —— 这就是"段错误"的全部来历
```

所以"段错误"不是编译器的诊断，也不是运行时的检查——它是一条从 MMU 硬件出发、穿过异常门、经内核判决后由信号送达的完整因果链。

### 除零与断点

除零（#DE，向量 0）无法修复，内核向进程投递 SIGFPE。断点（int3，一字节指令 `0xCC`）是调试器的全部根基：gdb 在你的函数入口把第一个字节临时改成 `0xCC`，CPU 执行到它陷入内核、调试器进程通过 ptrace 收到通知——trap 类异常执行完从下一条继续，正是为了"停一下还能接着走"。

## 中断：硬件随时敲门

### 中断路径：从引脚到处理函数

先回答中断为什么存在（约束）：设备又慢又不可预测——磁盘完成一次读要几十微秒起，两次按键之间隔着百毫秒级。没有中断，CPU 只能轮询设备的状态寄存器：反复读一个几乎从不变的值，把执行时间烧在空转上。中断把等待的方向反转过来——CPU 照常干活，设备有事时主动敲门。

中断因此是异步的：它不等任何指令，可以落在任意两条指令之间。一块 NVMe SSD 完成了一次 DMA 读，之后发生的事是：

```text
设备完成操作，发出中断信号（现代设备用 MSI：直接写一段约定内存，
  由芯片组转成中断，免去专用引脚）
  → 中断控制器（IOAPIC）按路由表把它投递给某个 CPU 核的本地 APIC
  → 该核在当前指令结束后响应：压栈保存 SS/RSP/RFLAGS/CS/RIP
  → 以中断向量号查中断描述符表（IDT），跳到对应处理函数
  → 处理函数保存它要用的寄存器，开始干活
  → iretq 指令弹出保存的现场，被打断的代码继续执行
```

被打断的代码毫不知情——它可能是一个正在算加法的用户程序，也可能是内核自己正在执行的另一段代码（中断嵌套由优先级控制）。

### 顶半部与底半部

中断处理函数里有一条铁律（约束）：**处理某个中断期间，同一路中断被屏蔽**。处理函数跑多久，这类事件就丢多久。所以处理被劈成两半：

- **顶半部（Top Half，硬中断上下文）**：只做秒级内必须做的事——应答设备、把数据从设备寄存器搬到内存、登记"还有活没干完"。几微秒内必须返回。它不能睡眠（没有进程上下文，无从挂起）。
- **底半部（Bottom Half）**：真正的重活——协议栈处理收包、块层合并请求——推迟到之后执行。Linux 提供三档机制：**softirq**（编译期静态登记，网络/块层在用）、**tasklet**（基于 softirq 的动态版）、**workqueue**（运行在真正的内核线程里，可以睡眠）。

收一个网络包的完整旅程因此是：网卡 DMA 数据进内存 → 中断 → 顶半部应答网卡、挂起 softirq → 底半部 softirq 里跑 IP/TCP 协议栈 → 数据放进 socket 接收队列 → 唤醒在 `read()` 里睡眠的进程（03 的状态机在此衔接）。

### 定时器中断：调度的心跳

有一路中断不为任何外设服务，只按固定频率敲打内核：**定时器中断**（tick）。典型频率 100~1000 Hz（内核编译选项 `CONFIG_HZ`；服务器常见 250 或 1000）。每敲一次，内核更新系统时间、给当前进程记账 CPU 消耗、检查是否该把它换下去——03 的调度器全靠这颗心跳驱动。空闲核上连续 tick 纯属浪费电，于是有了 NO_HZ：无事可做时停掉心跳，睡到下一个真实事件。

## 信号：反方向的门——内核如何通知进程

三扇门都是控制流**进入**内核；信号（Signal）是反方向的通道：内核（或另一个进程）异步通知一个进程"出事了、该停了、有人找你"。本篇前两节已经见过它的两个来源：异常判决的送达（缺页非法访问 → SIGSEGV，除零 → SIGFPE）、终端驱动的转发（Ctrl-C → SIGINT，见 04-终端与Shell）。第三个来源是软件主动发送：`kill` 系统调用——名字有误导性，它能发任意信号，`kill -9 pid` 里的 9 只是 SIGKILL 的编号。

接收方对每种信号有三种处置：

- **默认动作**：终止、忽略、暂停——内核预置，什么都不注册就按它办；
- **捕获**：用 `sigaction` 注册处理函数（handler），信号到来时内核打断进程的正常流程、在用户态执行 handler，然后回到断点继续；
- **屏蔽**：暂时不递送，积攒到解除屏蔽时补投。

两个例外没有商量余地：**SIGKILL 和 SIGSTOP 不可捕获、不可屏蔽、不可忽略**——它们是管理员与内核的最后手段，保证任何进程总能被杀掉或停住。这就是"杀不死就用 -9"的机制含义。

handler 里能做的事极少：信号可能打断在任何指令点，主程序此刻也许正持着锁、改着半截数据结构。能安全调用的函数只有一份"异步信号安全"白名单（连 `printf` 都不在其列）。标准做法是 handler 里只置一个标志位，真正的处理留给主循环自己读到标志后做。

## 三扇门共用同一副骨架

把三条路径叠在一起，不变的部分浮出来：

1. **入口受控**：目标地址不出自触发者——syscall 的入口在 MSR 里，异常/中断的入口在 IDT 里，两者都由内核开机时独占写就。IDT 的向量空间是分工的：0~31 由 CPU 保留给异常（前面见到的 #DE=0、#PF=14 就在此列），32 起才分配给外部中断。
2. **特权级切换**：Ring 3 → Ring 0，CPU 换到内核栈。
3. **现场保存**：被打断位置的 RIP/RFLAGS 等由硬件压栈，通用寄存器由内核入口代码存入 pt_regs。
4. **对称返回**：恢复现场，特权级切回，从断点继续（fault 类异常是"重新执行"，其余是"从下一条继续"）。

后续篇目里，三扇门各挑大梁：03 的调度由定时器中断驱动、进程阻塞与唤醒由各类中断和 syscall 交替推动；04 的按需分页整个挂在缺页异常上；05/06 的 `open/read/write/epoll` 全是系统调用。本篇是全层最基础的机制——它不生产任何抽象，只负责让控制流安全地进出那个生产抽象的地方。
