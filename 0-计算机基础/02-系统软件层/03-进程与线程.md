# 进程与线程

## 核心定义：资源容器与执行流

进程（Process）是 OS 提供的第一个抽象：**一个正在运行的程序实例**。它由两半构成：

- **资源容器**：一份私有虚拟地址空间（04）、一张打开文件表（05）、一组信号处理器和凭据（UID/权限）。
- **执行流**：至少一个可以被调度上 CPU 的执行上下文——寄存器组、栈、指令指针。

线程（Thread）是把这两半拆开后的产物：**共享同一个资源容器、各自独立的执行流**。一个进程内的多个线程共用地址空间和文件表，各自持有自己的寄存器、栈和调度实体。

为什么要把容器和执行流拆成两级（约束）？因为两类并发需求的开销完全不同：不同程序之间需要隔离（容器必须分开），而同一程序内部的并发（浏览器一个标签页里的渲染+网络+JS）需要高频共享数据——若每次切换都要换容器（地址空间），TLB 里的翻译缓存全部作废、缓存大面积变冷（《硬件组成》的 TLB 一节），代价不可接受。线程让"共享"成为默认、"隔离"成为可选项。

Linux 的实现把这一点做到了极致：**内核里没有独立的线程对象**。`fork()` 和 `pthread_create()` 底部都是同一个 `clone()` 系统调用，差别只在标志位——线程就是勾选了一组共享标志（`CLONE_VM | CLONE_FILES | CLONE_FS | CLONE_SIGHAND | ...`）的 `task_struct`。"Linux 的线程是轻量级进程"说的就是这个：容器和执行流本来就是一个结构体上的两组指针，共享与否全看指针是否复制。

## task_struct：一个进程的全部档案

Linux 内核中，每个执行流对应一个 `task_struct`（进程控制块，PCB），它是对上述定义的直接落地：

| 成员 | 装什么 | 连接到 |
|------|--------|--------|
| `mm_struct *mm` | 地址空间：VMA 树、页表基址 | 04-内存管理 |
| `files_struct *files` | 文件描述符表 | 05-文件系统 |
| `thread_info` / 内核栈 | 执行现场、syscall 时的栈 | 02-系统调用与中断 |
| `sched_entity` | 调度记账（vruntime 等） | 下文调度一节 |
| `state` | 运行/睡眠/僵尸…… | 下文状态机 |
| `signal` 相关 | 信号处理器、掩码 | 02 的 SIGSEGV 链 |

`fork()` 复制的、`execve()` 替换的、调度器翻找的、OOM killer 打分的，都是这一个结构体。

## 进程的诞生与死亡：fork、execve、wait

**fork()：复制一个自己。** 子进程得到父进程 `task_struct` 的副本，但资源容器并不真复制：地址空间逐页共享、全部标记为只读——这就是写时复制（Copy-On-Write，COW）。此后任何一方写某页，触发缺页异常（02 的门），内核这才复制那一页给写入方。fork 的开销因此与内存大小无关，只与页表条目数有关。COW 的完整异常链在 04 展开。

**execve()：换一副脑子。** 扔掉旧地址空间，装入新程序的可执行文件（ELF），重建栈和堆，从入口点开始执行。shell 里每敲一条命令，都是 fork + execve 的组合：fork 出容器，execve 装进程序。

**exit() 与 wait()：死亡要有人收尸。** 进程退出后，`task_struct` 不立即销毁——它停留在**僵尸（Zombie）**状态，直到父进程用 `wait()` 读走退出码。父进程先死怎么办？孤儿进程被过继给 PID 1（init/systemd），由它统一收割。PID 1 因此是整棵进程树的根和最终收尸人（它的诞生见 07-系统引导）。

## 进程状态机

调度器只能看到状态机上的一个状态。Linux 的主要状态与迁移驱动者：

```text
                    调度器选中
   就绪/运行 (TASK_RUNNING) ◄────────────┐
        │                                │
        │ 主动睡眠：read() 等 I/O、        │ 事件完成：数据到达、
        │ sleep()、等锁                   │ 定时器到点、锁被释放
        ▼                                │ （中断底半部负责唤醒，
   睡眠 (TASK_INTERRUPTIBLE /            │  见 02 的收包链）
        TASK_UNINTERRUPTIBLE) ───────────┘
        │
        │ exit()
        ▼
   僵尸 (EXIT_ZOMBIE) ──父进程 wait()──► 销毁
```

- **INTERRUPTIBLE vs UNINTERRUPTIBLE**：前者可被信号打断（`sleep` 能被 Ctrl-C 杀掉）；后者不可打断，专为"正在等磁盘 I/O、此刻被打断会损坏内核数据结构"的窗口设计——`ps` 里 D 状态的进程就是它，杀不掉只能等。
- 状态迁移的驱动者只有三类：**自己**（执行 syscall 主动睡眠）、**调度器**（抢占与选中）、**外部事件**（中断底半部把事件送到后唤醒）。02 的三扇门在这里显形为状态机的全部输入。

## 调度：谁在跑

**约束**：可运行的任务有 N 个，核只有 M 个，N > M。调度器要同时满足三个互相矛盾的目标——公平（每个任务都分到时间）、响应（交互任务按键即应）、吞吐（别把时间浪费在切换上）。

**CFS（Completely Fair Scheduler，完全公平调度器，2007 年 Linux 2.6.23 引入）**的答案是把 CPU 时间当成可记账的货币：

- 每个任务维护 `vruntime`（虚拟运行时间）——实际运行时间按权重折算后的账；跑得多，vruntime 涨得快。
- 所有可运行任务按 vruntime 挂在红黑树上，最左节点就是账最少、最"吃亏"的任务——调度器每次直接摘下最左节点上 CPU。
- `nice` 值（-20~19）不直接给优先级，而是换算成**权重**（每级约 1.25 倍差）：权重大的任务 vruntime 涨得慢，同样的实际时间买到的虚拟时间少，于是更常出现在最左端。公平因此不是"大家跑一样久"，而是"按权重分账，谁也不欠谁"。

2023 年 Linux 6.6 合入 **EEVDF（Earliest Eligible Virtual Deadline First）** 替换 CFS 的核心启发式：思路同样是记账，但改按"虚拟截止时间"排序——应得时间还没跑够（eligible）且 deadline 最早的任务先上，把 CFS 里一组打补丁式的延迟参数收敛成一个干净的数学模型。账本换了算法，记账的思想没变。

调度的时机由 02 的机制提供：定时器中断每 tick 检查一次当前任务是否该换（抢占点），加上任务主动睡眠时的让出。

## 上下文切换的账

切换一个执行流要做的事：保存当前任务的寄存器现场 → 调度器选出下一个 → 恢复其现场；若跨进程，还要换页表基址（CR3）。直接成本在微秒以内，真正的账在间接成本：

- **TLB**：换地址空间意味着旧翻译缓存大面积失效。《硬件组成》讲过 PCID 允许给 TLB 条目打进程标签，切换后旧标签条目作废即可，不必清空——这正是为进程切换准备的硬件。
- **缓存**：新任务的代码和数据不在 L1/L2 里，开头几百次访存全部降级为未命中——《硬件组成》AMAT 一章的每一项在这里集体兑现一次。

所以"进程切换比线程切换贵"的准确表述是：贵的不是保存恢复，而是**换容器带来的缓存与 TLB 冷启动**。同进程线程间切换不碰 CR3，绕开了这笔账的大头。

## 协程：不进内核的执行流

上下文切换的账摆出一个方向：切换能不能连内核都不进？**协程（Coroutine）/用户态线程**就是这个答案：执行流的切换完全发生在用户态——保存一组寄存器、换一个栈指针，没有系统调用、没有特权级切换。成本从线程切换的微秒级降到几十纳秒（一次函数调用的量级）；单机百万协程不是修辞而是常态——Go 的 goroutine 默认栈仅 8KB 起步且按需增长，与线程动辄 MB 级的栈形成两个世界。

实现形状是 **M:N 模型**：语言运行时里住着一个用户态调度器，把 M 个协程复用到 N 个内核线程上（Go 的 goroutine、Python asyncio 的协程、Java 21 引入的虚拟线程）。内核只看见那 N 个线程，协程的生死调度它一概不知。

代价直接来自这个形状：**内核看不见协程，阻塞就穿透下来**。一个协程发起阻塞式系统调用，被拖住的是它所在的整个内核线程——同线程上的其他协程一起挨饿。各家补救：Go 的调度器感知协程进入阻塞调用，把其余协程迁往别的线程；Python asyncio 干脆禁止隐式让出——只有 `await` 处才是调度点，I/O 必须走非阻塞。

协程与《编程运行环境》04 的事件循环是同一约束的两条写法：回调把"等待"摊成事件，`await` 把同一个等待写成同步的样子——底下都是让出执行流，去等一个还没到的数据。

## 同步原语：并发不是免费的

多执行流共享数据，必然出现竞态（Race Condition）：两个线程同时给同一变量 +1，结果只加了一次——底层的缓存行争夺由 MESI 协议裁决（《硬件组成》），但"谁有资格改"是 OS 必须提供的语义。同步原语按"竞争时去哪排队"分两类：

**用户态骨架：futex（Fast Userspace muTEX）。** Linux 上绝大多数锁（glibc 的 `pthread_mutex`、Go 的 `sync.Mutex`、Rust 的 `Mutex`）都建在 futex 上，设计动机就是 02 那张 100 ns 的门票：

- **无竞争（绝大多数情况）**：加锁只是用户态的一条原子指令（`lock cmpxchg`），不进内核，纳秒级完成。
- **有竞争**：才执行 `futex(FUTEX_WAIT)` 系统调用进内核，按锁地址哈希进等待队列睡眠；持锁者释放时用 `FUTEX_WAKE` 唤醒。

"快"字专指无竞争路径；竞争路径付出的正是 02 的 syscall + 03 的睡眠/唤醒状态机。一把用户态锁 = 一条原子指令 + 一条只在需要时踩下的内核逃生通道。

**内核态锁**：内核代码自己也要同步，但处境不同——中断上下文不能睡眠（02 的铁律）。于是：

- **自旋锁（spinlock）**：关抢占、原地空转等锁。只用于极短临界区和不能睡眠的场合——等锁期间 CPU 在烧电空转，锁被持有多久就浪费多久。
- **互斥锁（mutex）**：内核进程上下文里用，等不到就睡眠让出 CPU，把竞态的代价交给调度器消化。

信号量、条件变量、读写锁都是这两条基本路线（原地等 / 睡了等）上的变体，选型问题归结为一句话：**预计等多久、此刻能不能睡**。等得短选自旋，等得长选睡眠；不能睡（中断里）只能自旋。

## 进程间通信：隔离之后如何协作

进程的全部价值是隔离，但隔离必须有出口——工作要协作。进程间通信（Inter-Process Communication，IPC）的全部机制按三个轴定位：**数据形状、同步需求、是否跨机**。

| 机制 | 数据形状 | 同步 | 定位 |
|------|---------|------|------|
| 管道（pipe / FIFO） | 字节流 | 自带：写满阻塞、读空阻塞 | 亲缘进程用 pipe（04-终端与Shell 的管道手术就是它）；本机任意进程用 FIFO |
| 消息队列 | 有边界的消息 | 内核暂存 | 要消息边界不要流——边界的另一端见《计算机网络》07 的粘包 |
| 共享内存（shm） | 一整块内存 | **不自带** | 最快：同批物理页映射进两个地址空间（04 的机制），数据零拷贝；代价是并发纪律自理——上面的锁与信号量在此复用 |
| socket | 字节流/数据报 | 自带 | 唯一能跨机器；本机另有 unix domain socket（走内核但不过网卡协议栈） |
| 信号 | 只有一个编号 | 异步打断 | 只够说"出事了"，不带数据（02 的门） |

选型按轴走：本机大量数据 → 共享内存；流式小数据 → 管道；要跨机 → socket 别无选择；只需通知 → 信号。分布式系统的"服务间通信"在机制层就站在这张表的 socket 一行上——《软件工程概念》08 的微服务代价清单，根源是同一行。
