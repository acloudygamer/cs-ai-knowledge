# 进程与线程

> **版本基准**: universal

## 定义

进程是**资源分配的基本单位**（独立的地址空间、文件描述符、信号处理），线程是**CPU 调度的基本单位**（共享进程资源的执行流）。线程的出现是为了解决同一进程内并发执行的需求，避免进程间通信的高昂开销——同一进程的线程共享地址空间，线程间通信只需读写共享内存，无需系统调用。

进程与线程的根本区别在于**资源隔离边界**：进程边界由独立页表 enforce，线程边界由栈寄存器和 TLS（Thread Local Storage）寄存器 enforce。

**归约视角**：线程本质上是共享地址空间的轻量进程。如果把进程看作"隔离+调度"单元，则线程是"调度单元，隔离部分共享"。从数学上讲，线程是进程约束放松后的一个等价类。

## 数学模型

**进程虚拟地址空间布局（x86_64 Linux）：**

$$
\text{用户空间} = [0, 0x400000)_{\text{代码}} \cup [0x400000, \text{brk})_{\text{数据/堆}} \cup [\text{mmap\_base}, \text{RSP})_{\text{匿名映射}} \cup [\text{RSPAligned}, 0x00007FFFFFFFFFFF)_{\text{栈}}
$$

$$
\text{内核空间} = [0xFFFF800000000000, 0xFFFFFFFFFFFFFFFF] \quad \text{（对用户态不可直接寻址）}
$$

内核空间占高 128TB，通过 KPTI（内核页表隔离）防止用户态通过推测执行读取内核内存。

**CFS 调度权重（nice 值映射）：**

$$
\text{weight}_i = \frac{1024}{1.25^{\text{nice}_i}}, \quad \text{vruntime}_i += \frac{\delta\_\text{real}}{\text{weight}_i} \times 1024
$$

nice 值每增加 1，weight 降低约 20%。这意味着 nice=0 的进程 vruntime 增长速度是 nice=20 的 1/10，优先获得 CPU 时间。

**写时复制（Copy-on-Write）的物理页共享：**

fork() 后父子进程共享所有物理页，但页表项标记为只读。任一进程写入时触发 #PF（写保护），内核分配新物理页，复制内容，并更新页表。写时复制将 fork 的成本从 O(物理页数) 降低到 O(实际写入页数)。

**归约视角**：CoW 将内存复制归约为"页错误处理+物理页分配"，将 O(N) 的内存复制成本转换为 O(实际写入页数) 的按需分配成本。

**线程创建成本的数学分析：**

| 操作 | 时间复杂度 | 空间复杂度 |
|------|------------|------------|
| fork() | O(进程描述符) | O(页表项数) |
| vfork() | O(进程描述符) | O(共享页表) |
| clone(CLONE_VM) | O(线程栈 + TLS) | O(线程栈) |
| pthread_create() | O(线程栈) | O(线程栈) |

                      ▼

  min(vruntime) ←───── 最左节点（下一个调度目标）──────→ max(vruntime)
  [T1@100ms] [T3@150ms] [T2@200ms] [T1@300ms] ...

           当前执行

**数据形态变换：**

| 操作 | 资源复制 | 时间复杂度 |
|------|----------|------------|
| fork() | 复制页表（CoW）、文件描述符、信号处理 | O(页表项数) |
| vfork() | 不复制页表，共享地址空间（危险，已废弃） | O(进程描述符) |
| clone(CLONE_VM) | 共享页表，分配新栈和 TLS | O(线程栈) |
| pthread_create() | 底层调用 clone(CLONE_VM\|CLONE_THREAD\|...) | O(线程栈) |

- **fork()** → 复制 task_struct + 复制页表（CoW）+ 父子均指向同一物理页
- **exec()** → 保留 task_struct，替换页表为新程序，释放旧地址空间（不再 CoW）
- **exit()** → 关闭文件描述符，释放页表，task_struct 保留变为 zombie，等待父进程 wait()

## 机制

### 进程状态机

进程状态机是有限状态自动机（FSA），状态转移由内核调度器和系统事件驱动：

$$
S = \{\text{new}, \text{ready}, \text{running}, \text{blocked}, \text{zombie}\}
$$

$$
\delta: S \times E \rightarrow S \quad \text{（状态转移函数）}
$$

| 当前状态 | 事件 $E$ | 下一状态 | 触发条件 |
|----------|----------|----------|----------|
| new | fork() 成功 | ready | PID 分配完成，页表建立 |
| ready | 调度器选中 | running | 该进程的 vruntime 最小 |
| running | 时间片耗尽 | ready | CFS 重新调度 |
| running | I/O 阻塞 | blocked | 等待磁盘/网络/锁 |
| running | exit() | zombie | 主动终止或信号终止 |
| blocked | I/O 完成/锁释放 | ready | 等待队列 → CFS 红黑树 |
| zombie | wait() 被调用 | — | 资源回收，进程消亡 |

```
                    ┌────────────────────────────────────────┐
                    │       init/systemd (PID 1)             │
                    │       循环等待子进程退出                │
                    └────────────────────────────────────────┘
                                       ▲ wait()
                                       │
        ┌──────────────────────────────┴──────────────────────────────┐
        │                                                             │
    fork()                                                        wait()
        │                                                             │
        ▼                                                             ▼
  ┌───────────────┐                              ┌───────────────────────────────┐
  │   new         │                              │         zombie              │
  │ (分配 PID + 页表 + 内核栈)                    │ (task_struct 保留,等待回收)   │
  └───────┬───────┘                              └───────────────┬───────────────┘
          │                                                    │
          │ schedule() 激活                                      │ 父进程调用 wait()
          ▼                                                    ▼
  ┌───────────────┐                              ┌───────────────────────────────┐
  │   ready       │ ────────────────────────────► │        running               │
  │ (红黑树排队)  │      时间片耗尽 / I/O 阻塞     │  (CPU 上执行)                │
  └───────┬───────┘                              └───────────────┬───────────────┘
          │                                                    │

          ▼                                                    ▼
    (返回 running)                                      ┌───────────────┐
                                                          │    blocked    │
                                                          │ I/O 等待 / 锁睡眠 /
                                                          │ 信号暂停      │
                                                          └───────┬───────┘
                                                                  │
                                                                  │ I/O 完成 / 锁释放 / 唤醒信号
                                                                  ▼
                                                            (返回 ready)
```

**约束条件：**
- 进程退出时父进程必须调用 wait() 回收，否则僵尸进程占用 PID 和内核栈
- 同一进程的多个线程不可同时进入同一临界区（需同步原语）

**违反约束的后果：**
- 僵尸进程积累 → PID 耗尽（Linux PID 上限 2^22 ≈ 400 万），新进程无法创建
- 父进程不调用 wait() → 子进程成为僵尸直到系统重启

**PID exhaustion 的精确数学：**

Linux PID 上限定义：
$$
\text{PID\_MAX} = 2^{22} = 4194304 \quad (\text{可通过 /proc/sys/kernel/pid\_max 配置到 } 2^{15})
$$

分配算法：从 last_pid + 1 开始扫描，绕过已分配 PID，找到第一个空闲 PID。当 PID 耗尽时：
$$
\exists \text{PID } p: p \notin \text{allocated\_pids} \implies p = \text{NONE} \Rightarrow \text{ fork() 返回 -EAGAIN}
$$

**进程创建的闭包不变量：**

令 $P(t)$ 为时刻 $t$ 的活跃进程集合， $|P(t)| \leq \text{PID\_MAX}$ 。fork() 操作必须满足：
$$
\text{fork()} = \begin{cases}
\text{成功（返回子 PID）} & \text{若 } |P(t)| < \text{PID\_MAX} \\
\text{失败（返回 -EAGAIN）} & \text{若 } |P(t)| = \text{PID\_MAX}
\end{cases}
$$

这个约束保证 PID 永远不会冲突。

**wait() 的精确语义（POSIX）：**

```c
pid_t wait(int *status);
pid_t waitpid(pid_t pid, int *status, int options);
```

wait() 阻塞直到任一子进程退出，返回退出子进程的 PID。status 存储退出信息（WIFEXITED/WEXITSTATUS/WIFSIGNALED）。若已有僵尸子进程，立即返回。

wait4() 是 Linux 扩展，可获取资源使用统计（utime/stime/maxrss）。

### 线程同步原语

| 原语 | 底层机制 | 适用场景 | 代价 |
|------|----------|----------|------|
| mutex | futex + CAS 原子指令 | 短期临界区 | 上下文切换（自旋失败后） |
| semaphore | futex + 计数器 | 资源计数 | 同上 |
| rwlock | 两阶段：写排他，读共享 | 读多写少 | 写饥饿风险 |
| spinlock | 原子指令忙等待 | 极短期临界区（中断上下文） | CPU 空转 |
| condition variable | futex + 等待队列 | 事件等待 | 需配合 mutex |

**futex 的设计思想：** 大多数锁 contention 发生在用户空间——线程在用户空间忙等待 CAS（compare-and-swap），仅在真正需要阻塞时调用 futex_wait() 进入内核。这避免了每次加锁都触发系统调用。

**futex 两层锁机制的精确工作流程：**

```
用户空间（线程 A 尝试获取锁）：
1. atomic_load(&mutex) → 0（锁空闲）
2. CAS(&mutex, 0, 1) → 成功，线程获得锁（用户空间，无系统调用）

用户空间（线程 B 尝试获取锁，发现 mutex=1）：
3. atomic_load(&mutex) → 1（已被持有）
4. futex_wait(&mutex, 1) → 内核将线程加入等待队列（阻塞）

用户空间（线程 A 释放锁）：
5. atomic_store(&mutex, 0)
6. futex_wake(&mutex, 1) → 内核唤醒一个等待线程
7. 线程 B 被唤醒，从 futex_wait() 返回用户空间
8. CAS(&mutex, 0, 1) → 成功，获得锁
```

**futex hash 表的数学约束：**

futex 底层维护一个 hash 表，key 是用户空间地址：
$$
h(\text{addr}) = (\text{addr} \oplus (\text{addr} \gg 12)) \mod \text{futex\_hashsize}
$$

hashsize 通常为 4096。每个 hash bucket 是一个链表，存储等待该地址的线程信息（PID/TID、内核等待队列节点）。

**futex hash 碰撞概率分析：**

令 $N$ 为同时等待的 futex 地址数， $M = 4096$ 为 hash bucket 数。设 hash 函数均匀分布，则每个地址落入特定 bucket 的概率为 $1/M$。碰撞次数 $C$ 服从二项分布 $B(N, 1/M)$：

$$
E[C] = N \cdot \frac{1}{M}, \quad \text{Var}(C) = N \cdot \frac{1}{M} \cdot \left(1 - \frac{1}{M}\right)
$$

当 $N \gg M$ 时（如大量线程竞争同一锁），碰撞严重，链表遍历成为性能瓶颈。此时应考虑将锁拆分为多个 futex（锁分段），将竞争分散到不同 hash bucket。

**futex 公平性问题：**

futex_wake 唤醒顺序是 FIFO（按加入等待队列的顺序）。但由于 hash 碰撞，同一 bucket 内的多个等待线程可能产生竞争：先被唤醒的线程若 CAS 失败（锁被其他线程抢先获取），会再次进入等待，产生"惊群"效应。

设线程唤醒后 CAS 成功的概率为 $p$ ，则期望唤醒次数：
$$
E[\text{唤醒次数}] = \frac{1}{p}
$$

当 $p$ 很小时（高竞争），大量唤醒是无效的，浪费调度资源。

**futex 的 PI（Priority Inheritance）机制：**

标准 futex 不支持优先级继承，可能导致优先级反转（高优先级线程等待低优先级持锁线程）。PI futex 通过 rt_mutex 机制解决：

1. 持锁线程继承等待者的优先级（提升）
2. 持锁线程释放锁时恢复原优先级
3. 需要更多内核资源（PI futex 贵 3-5 倍）

**归约视角**：futex → futex_hash → 红黑树/链表 → 内核调度器。每一层抽象都将问题归约为更底层的资源管理问题。

**约束条件：**
- 自旋锁在持有锁期间必须禁用中断（否则死锁）
- mutex 的 futex_wait() 可能引入调度延迟，不适合极短期临界区

**违反约束的后果：**
- 自旋锁 + 中断 → 死锁（中断处理程序也试图获取同一锁）
- spinlock 持有时间过长 → 其他 CPU 核心空转，浪费电力

### 进程/线程创建成本对比

| 操作 | 资源复制 | 时间复杂度 |
|------|----------|------------|
| fork() | 复制页表（CoW）、文件描述符、信号处理 | O(页表项数) |
| vfork() | 不复制页表，共享地址空间（危险，已废弃） | O(进程描述符) |
| clone(CLONE_VM) | 共享页表，分配新栈和 TLS | O(线程栈) |
| pthread_create() | 底层调用 clone(CLONE_VM\|CLONE_THREAD\|...) | O(线程栈) |

**CLONE_* 标志的精确语义：**

| 标志 | 共享内容 | 独立内容 |
|------|----------|----------|
| CLONE_VM | 整个地址空间（页表） | 无 |
| CLONE_FS | 根目录、当前目录、umask | 无 |
| CLONE_FILES | 文件描述符表（fd 数组） | 无 |
| CLONE_SIGHAND | 信号处理函数、信号掩码 | 无 |
| CLONE_THREAD | 线程组（TGID = 创建者 TGID） | 无（但共享 CLONE_VM 等） |
| CLONE_VFORK | vfork() 语义：父进程等待子进程 exec/exit | 无 |
| CLONE_PARENT | 子进程的 parent = 创建者的 parent（init 取养父） | 无 |
| CLONE_NEWPID | 新 PID namespace | 进程级隔离 |
| CLONE_NEWUTS | 新 UTS namespace（hostname/domainname） |UTS 隔离 |
| CLONE_NEWIPC | 新 IPC namespace（SysV shm/msg/sem） | IPC 隔离 |
| CLONE_NEWNET | 新 network namespace | 网络隔离 |
| CLONE_NEWUSER | 新 user namespace | UID/GID 映射隔离 |
| CLONE_NEWCGROUP | 新 cgroup namespace | cgroup 层次隔离 |

**pthread_create() 底层调用的完整标志：**
```c
clone(CLONE_VM | CLONE_FS | CLONE_FILES | CLONE_SIGHAND | CLONE_THREAD | CLONE_SYSVSEM | CLONE_SETTLS | CLONE_PARENT_SETTID | CLONE_CHILD_CLEARTID, ...)
```

**约束条件：**
- clone() 的 CLONE_VM 标志使子进程共享父进程页表，此时必须确保不会同时执行（vfork 的语义要求）
- 线程栈大小固定（通常 8MB），溢出时触发栈溢出错误（SIGSEGV）

**违反约束的后果：**
- vfork() 后子进程执行与父进程冲突的代码 → 未定义行为（vfork 保证子进程先运行，但无法防止子进程调用其他函数）
- 线程栈溢出 → SIGSEGV，进程崩溃

### 调度策略与优先级

**实时调度策略（SCHED_FIFO / SCHED_RR）：**
- 实时进程比普通进程优先级更高
- SCHED_FIFO：无时间片，一直运行直到阻塞或让出
- SCHED_RR：有时间片，RR 轮转

**普通调度策略（CFS）：**
- 基于 vruntime 的红黑树
- nice 值决定权重比例

```bash
# 设置进程调度策略
chrt -f 10 command  # SCHED_FIFO, 优先级 10
chrt -r 10 command  # SCHED_RR, 优先级 10
chrt -o 0 command   # SCHED_OTHER (CFS)
```

## 参考存根

```c
// POSIX 线程创建：分配栈 + 设置线程局部存储 + 加入调度
pthread_create(&tid, NULL, start_routine, arg);

// Linux clone：灵活控制共享范围
// CLONE_VM: 共享地址空间 → 线程
// CLONE_FS/CLONE_FILES/CLONE_SIGHAND: 共享特定资源
clone(CLONE_VM | CLONE_FS | CLONE_FILES | CLONE_THREAD,
      child_stack, SIGCHLD, NULL);

// futex_wait 简化实现（用户态→内核态的边界）
// 大多数情况下线程在用户态自旋 CAS，只有真正需要阻塞时才进入内核
int futex_wait(int *uaddr, int val) {
    if (atomic_load(uaddr) != val)
        return EAGAIN;  // 值已变化，无需等待
    return syscall(SYS_futex, uaddr, FUTEX_WAIT, val, NULL, NULL, 0);
}
```
