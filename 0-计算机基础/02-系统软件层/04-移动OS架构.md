# 移动 OS 架构

> **版本基准**: universal

## 定义

移动操作系统是在传统宏内核（Linux/XNU）基础上，针对功耗管理、触控交互、移动安全进行深度定制的操作系统。Android 和 iOS 代表了两种不同的架构哲学：Android 继承 Linux 的开放生态，通过 HAL 解耦硬件；iOS 通过 XNU 混合内核强化功耗控制和安全沙盒。

两者的根本差异在于**设计优先级**：Android 以开放性和可定制性为优先（Linux 遗产），iOS 以功耗控制和内容安全为优先（Apple 生态锁定）。

**归约视角**：移动 OS 的核心挑战是将桌面 OS 的计算模型压缩到严格的功耗约束下。从数学上讲，这是多目标优化问题： $P = \max(\text{性能}) - \lambda \cdot (\text{功耗})$ ，其中 $\lambda$ 在移动端远大于桌面端。 ，其中 $\lambda$ 在移动端远大于桌面端。 在移动端远大于桌面端。

## 数学模型

**Android ART 编译器管线（JIT/AOT/解释混合）：**

$$
\text{安装时} \xrightarrow{\text{dalvik2oat AOT}} \text{oat 文件（机器码）}
$$

$$
\text{运行时} \xrightarrow{\text{JIT 热点检测}} \text{热点方法编译} \xrightarrow{\text{追加到 profile}} \text{后台 AOT 优化}
$$

冷启动路径：解释执行 → JIT 编译热点 → profile 积累 → 预编译优化。最终达到接近 AOT 的性能，同时保持 APK 体积可控。

**iOS 内存压缩（ASM）模型：**

$$
\text{物理页} \xrightarrow{\text{被回收}} \text{压缩存储于内存区} \xrightarrow{\text{再次访问}} \text{解压缩恢复}
$$

iOS 内存压缩器（compressor）将不活跃页面压缩到 LZBM 算法存储，释放物理页。当应用再次访问时，解压缩恢复，无需磁盘换出（闪存写入寿命有限）。

**ASM（Apple Software Memory Compressor）的精确机制：**

ASM 是 iOS（Darwin/XNU）特有的内存压缩器，位于 `vm_compressor.c` 中：

1. **压缩触发条件**：当 memory pressure 达到 `THROTTLE_LEVEL`（内存压力阈值）
2. **压缩对象**：inactive pages（最近未访问但未脏的页）
3. **压缩算法**：改良的 LZBM（基于 LZ4 的压缩块）：
   - 16KB 页压缩为约 4-6KB（压缩比 2.5-4:1）
   - 压缩块存储于 `compressor_pager`（内核内存区域，非磁盘）
4. **解压缩触发**：页面再次被访问时（page fault）
5. **解压缩延迟**：约 10-20μs（vs 磁盘 I/O 的 5-10ms）

**ASM vs swap 的设计权衡：**

| 特性 | ASM（内存压缩） | swap（磁盘换出） |
|------|-----------------|------------------|
| 延迟 | 10-50μs | 5-10ms |
| 写入寿命 | 无（内存内操作） | 闪存寿命消耗 |
| 容量限制 | 受物理内存限制 | 可用磁盘空间 |
| 功耗 | 低（CPU 压缩） | 高（磁盘 I/O） |

iOS 选择 ASM 而非 swap 的原因：移动设备闪存写入寿命有限，频繁 swap 会快速消耗闪存寿命。

**功耗模型：**

$$
P_{total} = P_{CPU} + P_{GPU} + P_{radio} + P_{display} + P_{ambient}
$$

移动设备功耗主要来自四个硬件部件。触控屏（display）和基带 radio（radio）占 60-70%，CPU/GPU 占 20-30%。移动 OS 的核心任务是将无用功耗降到零：屏幕暗时关闭 GPU，无网络请求时关闭 radio，无前台应用时冻结后台。

**功耗管理的约束优化模型：**

移动 OS 的功耗管理可建模为约束优化问题：
$$
\min P_{total} \quad \text{s.t.} \quad \text{性能} \geq P_{\min}, \text{响应时间} \leq T_{\max}
$$

Android Doze 引入占空比（duty cycle）控制空闲时间比例：
$$
\text{占空比} = \frac{T_{\text{active}}}{T_{\text{active}} + T_{\text{idle}}}
$$

Doze 的维护窗口（maintenance window）确保关键任务定期执行：
- 第一个窗口：15 分钟
- 后续窗口指数增长：30、60、120 分钟...
- 白名单应用不受限制

iOS Low Power Mode 降低 CPU 频率上限：
$$
f_{\max}^{\text{LPM}} = \alpha \cdot f_{\max}^{\text{normal}}, \quad \alpha \approx 0.5-0.7
$$

频率降低直接减少动态功耗： $P_{\text{dynamic}} \propto f \cdot V^2$ 。同时降低电压 $V$ 可获得平方收益。 。同时降低电压 $V$ 可获得平方收益。 可获得平方收益。

**App Lifecycle 状态机（iOS/Android 共用模型）：**

$$
\text{Active} \xleftarrow{\text{用户切换}} \text{Background} \xrightarrow{\text{内存压力}} \text{Suspended} \xrightarrow{\text{系统终止}} \text{Terminated}
$$

| 状态 | CPU | 内存 | 网络 | 功耗影响 |
|------|-----|------|------|----------|
| Active | 全速 | 可用 | 可用 | 最高 |
| Background | 受限 | 受限（部分被压缩） | 受限 | 中等 |
| Suspended | 冻结 | 部分压缩 | 不可用 | 极低 |
| Terminated | 不运行 | 不占用 | 不运行 | 零 |

**数据形态变换：**

| 平台 | 应用层数据 | IPC 传递 | 内核事件 |
|------|------------|----------|----------|
| Android | Java bytecode (DEX) | Binder 引用（mappped buffer） | ioctl 到 binder 驱动 |
| iOS | Objective-C/Swift 对象 | Mach Port 消息（copy_send） | mach_msg_trap → 内核 |

- **Android**: Java bytecode (DEX) → oat 文件（AOT） → 机器码（应用运行时）
- **iOS**: Objective-C/Swift → Mach Port 消息 → 内核事件 → 应用回调

## 机制

### Android Binder IPC

Binder 是 Android 专有的进程间通信机制，设计目标是**零拷贝**。

传统 Linux IPC (pipe/socket) 数据拷贝路径：
```
进程A ──► 内核缓冲区 A ──► 内核缓冲区 B ──► 进程B
          (第 1 次拷贝)     (第 2 次拷贝)
```

Binder 数据拷贝路径：
```
进程A ──► mmap 映射区 ──► 进程B
          (仅 1 次拷贝，通过地址传递引用)
```

Binder 通过 mmap 将接收方 buffer 直接映射到发送方地址空间，实现零拷贝。这在频繁 IPC 场景（如 AMS 进程间通信）中有显著性能优势。

**Binder mmap 的精确机制：**

Binder 零拷贝的核心在于共享内存映射，无需 CPU 复制：

```
发送方（进程 A）：
1. 构造 flat_binder_object，type = BINDER_TYPE_FDA（文件描述符）或 BINDER_TYPE_PTR（数据）
2. 通过 BC_TRANSACTION 发送给 Binder 驱动
3. Binder 驱动分配 buffer 和目标进程的 mmap 区域
4. 数据写入 mmap 区域（一次拷贝）
5. 接收方（进程 B）通过 mmap 直接访问该区域
```

Binder 驱动的 buffer 管理：
- 每个进程有 `proc->buffers`，记录 buffer 位置和大小
- `binder_buffer->user_buffer` 指向接收方 mmap 区域
- 引用计数管理：强引用（±1）和弱引用（±1）分离，弱引用归零时释放对象，强引用归零时销毁对象

**Binder vs Mach Port 的延迟对比：**

| 指标 | Binder (Android) | Mach Ports (iOS) |
|------|-----------------|------------------|
| 单次 IPC 延迟 | ~1-5 μs | ~5-15 μs |
| 数据拷贝次数 | 1 次（mmap） | 2 次（msg + copy_send） |
| 引用传递 | 支持（通过 flat_binder_object） | 支持（端口 rights） |
| 死亡通知 | BR_DEAD_BINDER | MACH_RCV_NOTIFY |

Binder 的 mmap 机制使接收方直接访问发送方的缓冲区物理页，实现真正的零拷贝。而 Mach 的 `copy_send` 将数据拷贝到内核缓冲区，再拷贝到接收方。

**Binder 引用计数的数学模型：**

Binder 实体引用计数遵循以下不变量：
$$
\text{对象存在} \iff \text{强引用计数} > 0
$$
$$
\text{对象可查询} \iff \text{弱引用计数} > 0
$$

强引用归零时对象被销毁；弱引用归零时对象结构被释放但内存保留（等待强引用归零）。这避免了循环引用导致的内存泄漏：两个对象可以互相持有弱引用。

**Binder 的核心设计：**
- **Binder 实体**（Server 端）以 BpBinder（代理）形式暴露给 Client
- **flat_binder_object** 是跨进程传递的数据结构，包含句柄或数据指针
- Binder 驱动维护**引用计数**，仅当引用计数归零时才释放资源
- ServiceManager 作为"白页"服务，通过字符串名查找 Binder 引用（而非像 DNS 那样分布式查找）

**Binder 协议命令（BC_*/BR_*）：**

| 命令 | 方向 | 说明 |
|------|------|------|
| BC_TRANSACTION | 用户→驱动 | 发起事务 |
| BC_REPLY | 用户→驱动 | 事务响应 |
| BR_TRANSACTION | 驱动→Server | 分发请求 |
| BR_REPLY | 驱动→Client | 返回结果 |

**约束条件：**
- 调用者必须持有正确 UID/PID，Binder 驱动验证
- Server 必须注册到 ServiceManager，否则 Client 无法查找
- 事务数据大小受限（默认 1MB）
- 传递文件描述符时，fd 在目标进程重新编号（不是同一个 fd 值）

**违反约束的后果：** SecurityException（权限不足），TransactionTooLargeException（数据超限导致事务失败）

### iOS 沙盒机制

iOS 沙盒（Seatbelt）是基于 MAC（Mandatory Access Control，强制访问控制）的运行时限制：

$$
\text{进程权限} = f(\text{进程代码签名}, \text{沙盒配置文件})
$$

代码签名确保可执行文件未被篡改，沙盒配置文件（sandbox.sb）定义进程可访问的资源集。两者共同决定了进程的权限边界——即使攻击者实现了代码注入，也无法突破沙盒限制访问其他应用数据。

沙盒配置文件（sandbox.sb）示例：
```
(allow file-read* (regex "^/private/var/mobile/Containers/"))
(deny file-write* (regex "^/System/"))
```

**约束条件：**
- 应用无法访问其他应用的容器目录
- 系统调用受限（不可调用 fork/exec/spawn）
- 动态代码加载受限（JIT 必须申请特殊 entitlement）

**违反约束的后果：**
- 越狱检测失效（沙盒被突破）
- App Store 审核拒绝
- 运行时被 SIGKILL

### 功耗管理机制

Android Doze 和 iOS Low Power Mode 对比：

| 特性 | Android Doze | iOS Low Power Mode |
|------|--------------|---------------------|
| 触发条件 | 屏幕关闭 + 静止检测（加速度计） | 电量 < 20%（用户手动或自动） |
| 后台 Jobs | 暂停所有 JobScheduler 任务 | 暂停全部后台刷新 |
| 网络 | 批量延迟（允许白名单） | 推迟非关键网络请求 |
| GPS | 降低定位精度 | 同上 |
| 恢复 | 白名单应用例外 | 即时恢复（充电时） |

**设计权衡：** Doze 对功耗优化更精细（app-by-app 白名单），但兼容性更复杂；Low Power Mode 是全局开关，实现简单但更激进。

**约束条件（功耗管理）：**
- 后台应用在 Doze 深度休眠时无法访问网络（除非加入白名单）
- iOS Low Power Mode 会限制后台应用的刷新频率

**违反约束的后果：**
- 应用未适配 Doze → 深度休眠时无法及时收到推送通知
- 应用在 Low Power Mode 下未推迟网络请求 → 用户体验降级

### Android Low Memory Killer

Android 的 Low Memory Killer（LMK）机制在内存压力时按进程优先级杀死进程：

```
oom_score_adj 范围: -1000 (最不重要) ~ +1000 (最重要)
oom_score 越小，进程越优先被杀死

优先级顺序（从低到高）：
1. 空进程（已退出但未清理）
2. 受保护应用（persistent 或前台服务）
3. 内容提供器（Content Provider）
4. 可见进程（Visible process）
5. 可感知进程（Perceptible process）
6. 前台进程（Foreground process）
```

**约束条件：**
- LMK 触发阈值可配置（通过 `/sys/module/lowmemorykiller/parameters/`）
- 杀死进程会调用其 onTerminate() 回调

**违反约束的后果：**
- 内存泄漏 → LMK 频繁触发 → 用户体验下降
- 重要后台服务被杀死 → 推送通知延迟
