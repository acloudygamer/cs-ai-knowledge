# 文件系统

> **版本基准**: universal

## 定义

文件系统是将块设备上的物理存储组织为**命名文件层次结构**的逻辑抽象，提供按名访问、持久化存储和权限控制。核心约束：**文件名到数据块的映射关系必须在系统崩溃后仍可恢复**。

**归约视角**：文件系统的本质是将"名字"（字符串路径）映射到"数据块"（物理存储位置）的持久化数据结构。这个映射必须满足 ACID 中的耐久性（durability）——系统崩溃后映射关系不能丢失或损坏。

## 数学模型

**inode 直接/间接块寻址（ext4，块大小 4KB）：**

$$
\text{inode 可寻址块数} = 12 + 256 + 65536 + 16777216 = 16843020
$$

每个块 4KB，inode 通过传统间接块指针可寻址的总空间：

$$
16843020 \times 4\text{KB} \approx 64\text{GB}
$$

**注意区分两个独立约束：**

| 约束来源 | 寻址能力 | 说明 |
|----------|----------|------|
| inode 间接块指针（传统方案） | 16843020 块 ≈ 64GB | 块指针数组的上限 |
| ext4 文件大小硬限制 | 2^32 × 4KB = 16TB | inode 的 i_size 字段为 32-bit，以字节为单位 |

ext4 的 16TB 限制并非来自 inode 间接块指针的寻址能力（64GB 远小于 16TB），而是由 **inode 的 i_size 字段（32-bit 无符号整数，上限 2^32 字节）** 强制的文件大小硬上限。无论采用何种块寻址机制（传统间接块或 extent 树），ext4 文件大小均受此 32-bit i_size 约束。

**VFS 抽象接口代数：**

$$
\text{file\_operations} = \{open, read, write, mmap, fsync, lock, \ldots\}
$$

所有文件系统（ext4/xfs/btrfs）必须实现同一组函数指针，内核通过函数指针调用，屏蔽实现差异。

**目录项缓存（dentry cache）加速路径查找：**

$$
T_{\text{路径解析}}^{\text{无缓存}} = O(\text{路径深度}) \quad \xrightarrow{\text{dcache缓存}} \quad T_{\text{路径解析}}^{\text{缓存命中}} = O(1)
$$

dentry 维护父目录指针和孩子链表，查找时先查缓存，缓存命中则跳过 VFS 层直接获取 inode。

**归约视角**：dentry cache 将路径解析从树遍历问题归约为哈希查找问题。路径字符串经哈希函数映射到 dentry 结构，缓存命中时直接返回，避免递归遍历。

**dentry hash 冲突的数学约束：**

Linux dentry 哈希函数：
$$
h(\text{name}) = \text{hash\_len}(\text{name}) \mod \text{dhash\_size}
$$

dentry 哈希表大小通常为 $2^{\text{order}}$ ，可通过 `sysctl fs.dentry-nr` 监控。哈希冲突导致同一 bucket 内链表遍历，最坏情况 $O(n)$ ，但实际命中时 $O(1)$ 。

dentry 还维护 LRU（最近最少使用）链表，用于内存压力时回收：
$$
\text{dentry\_evict} \implies \text{移出 LRU 末尾} \xrightarrow{\text{引用计数=0}} \text{释放内存}
$$

未使用的 dentry 最终被 prune 线程回收，释放内存。

**日志文件系统的事务模型：**

ext4 使用 JBD2（Journaling Block Device 2）作为日志层：

$$
\text{write} \xrightarrow{\text{JBD2}} \begin{cases}
\text{TXN\_BEGIN} \rightarrow \text{metadata blocks} \rightarrow \text{TXN\_COMMIT} \rightarrow \text{数据块写入} \\
\text{或} \\
\text{数据块写入} \rightarrow \text{TXN\_BEGIN} \rightarrow \text{metadata blocks} \rightarrow \text{TXN\_COMMIT}
\end{cases}
$$

**JBD2 日志的物理结构：**

```
日志区域（默认 128MB）：
┌─────────────────────────────────────────────────────────────┐
│ Journal Superblock │ Journal Header │ Commit Block          │
│ (固定位置 LBA 8)   │ (事务起始)    │ (事务提交)           │
└─────────────────────────────────────────────────────────────┘
     ▼
┌─────────────────────────────────────────────────────────────┐
│ Transaction N:                                              │
│   [T吕 BEGIN] → [descriptor block] → [data blocks] → ... │
│   → [commit block]                                          │
└─────────────────────────────────────────────────────────────┘
```

**三种日志模式对比：**

| 模式 | metadata | data | 崩溃恢复 | 性能 |
|------|----------|------|----------|------|
| journal | 写日志 | 写日志 | 完整恢复 | 最慢 |
| ordered（默认） | 写日志 | 无日志 | 丢失最后事务 data | 中等 |
| writeback | 无日志 | 无日志 | 可能丢失多个事务 | 最快 |

ordered 模式：data block 在 metadata TXN_COMMIT 之后写入，保证文件系统一致性（不会 data 与 metadata 不一致），但 data 可能丢失。

## 机制

### inode 结构与硬链接

inode（index node）是文件元数据的容器，不包含文件名：

| 字段 | 说明 | 约束 |
|------|------|------|
| mode | 文件类型 + 权限位 | 权限检查依据 |
| uid/gid | 所有者 | 访问控制 |
| size | 文件大小（字节） | - |
| atime/mtime/ctime | 访问/修改/变更时间 | 文件系统一致性 |
| block[15] | 直接/间接块指针 | extents 替代方案 |
| i_links_count | 硬链接计数 | 归零时释放 inode |

**硬链接本质**：多个目录项指向同一 inode，共享 i_links_count。删除文件（unlink）时递减计数，仅当归零时释放数据块和 inode。

**约束条件：**
- 硬链接不能跨文件系统（inode 编号仅在本分区唯一）
- 硬链接不能指向目录（防止循环引用）

**违反后果：**
- 删除正在打开的文件 → 目录项立即移除，数据块保留（文件描述符仍有效）直至最后引用关闭
- 硬链接跨分区 → 指向错误的 inode，数据损坏

### 日志文件系统（ext4）

ext4 journal 保证一致性，崩溃后通过重放或回滚恢复：

**ext4 journal 模式：**
- **journal 模式**：所有数据+元数据都写日志（最安全，最慢）
- **ordered 模式**（默认）：元数据写日志，数据写入在 commit 之前（平衡安全与性能）
- **writeback 模式**：仅元数据日志，不保证数据顺序（最快，可能丢失数据）

崩溃恢复流程：
1. 文件系统 mount 时检测 journal 是否有未完成事务
2. 有 → 读取 journal，重复所有 TXN_COMMIT（重放）或撤销 TXN_BEGIN（回滚）
3. 恢复完成，正常挂载

**约束条件：**
- journal 本身需日志一致性保护（日志块环形写入）
- journal 空间有限，需定期 checkpoint 回收

**违反后果：**
- 日志损坏 → mount 失败，需 fsck 完整扫描
- 未正常 unmount → journal 重放，可能丢失最后几秒数据

### 页面缓存与回写

Linux 页面缓存机制：

$$
\text{物理页框} \xrightarrow{\text{address_space}} \text{文件偏移} \xrightarrow{\text{radix树}} \text{缓存页}
$$

读文件时，数据先进入页面缓存；写文件时，数据写入缓存页并标记 dirty，延迟回写到磁盘（一般 30 秒或内存压力时）。

**约束条件：**
- dirty 页过多会触发内存回收（回收算法决定哪些页被换出）
- 强制回写：sync()/fsync() 确保数据落盘

**违反后果：**
- 程序异常退出且未 fsync → 最近写入的数据可能丢失
- 电源故障 → ext4 ordered 模式最多丢失一个事务的数据

### ext4 Extent 树

ext4 用 extent 替代传统的间接块指针，提高大文件操作效率：

```c
struct ext4_extent {
    __le32  ee_block;   // 逻辑块号
    __le16  ee_len;    // 连续块数（最大 128）
    __le16  ee_start_hi; // 物理块号高16位
    __le32  ee_start_lo; // 物理块号低32位
};
// extent 树：内部节点最多 4 层，支持更大文件
```

**ext4 extent 树的精确结构：**

extent 树存储在 inode 的 `i_data` 数组中（若 < 4 个 extent）或外部 `ext4_extent_header` + `ext4_extent` 节点：

```
ext4_extent_header（12 字节）：
- eh_magic: 0xF30A（魔数）
- eh_entries: 当前节点中的 extent 数量
- eh_max: 最大 extent 数
- eh_depth: 树深度（0=叶子，>0=内部节点）

ext4_extent_idx（内部节点，12 字节）：
- ei_block: 子节点覆盖的起始逻辑块
- ei_leaf_lo: 子节点物理块号（低 32 位）
- ei_leaf_hi: 子节点物理块号（高 16 位）
- ei_unused: 未使用

extent 查找复杂度：O(depth)，深度最多 4

**extent 树深度与地址空间的关系：**

extent 树采用 48-bit 物理块号（ee_start_hi:ee_start_lo），理论寻址能力为 2^48 × 4KB ≈ 256PB。然而 ext4 额外约束 inode 的 i_size 字段为 32-bit（字节为单位），因此**无论 extent 树深度如何，ext4 最大文件大小始终被限制在 2^32 字节 = 16TB**。extent 树深度（≤4）决定了元数据查找效率，而非最大文件大小上限。

**extent 树查找复杂度的精确分析：**

extent 树是 B+ 树的变种，查找从根到叶子的路径长度即为查询复杂度：

$$
T_{\text{extent lookup}} = O(\text{tree depth}) = O(4) \quad \text{（最多 4 层）}
$$

相比之下，间接块方案的查找复杂度：
$$
T_{\text{indirect lookup}} = O(\text{间接层级数}) = O(1) + O(1) + O(1) = O(1)
$$

但间接块方案的问题是：对于大文件，需要跟踪多个间接块指针，每个指针块包含 $4\text{KB} / 4\text{B} = 1024$ 个块指针。当文件跨越多个间接块时，I/O 次数增加：

- 间接块方案读取逻辑块 $L$ ：首先读取一级间接块（1次 I/O），再读取数据块（1次 I/O），共 2 次 I/O
- extent 方案：extent 树最多 4 层查找，然后 1 次 I/O 读取数据

extent 的优势在于**元数据局部性**：一个 extent 描述最多 128 个连续块，减少了元数据开销和数据块的 I/O 次数。
```

**extent 合并与分裂策略：**

extent 节点饱和时（eh_entries = eh_max），新分配触发分裂：
- 若新块与现有 extent 相邻且物理连续 → **合并**
- 若不相邻 → **分裂为两个 extent**，可能需要向上递归分裂父节点

**extent 优势：**
- 大文件顺序读：一次 extent 查询（O(depth) ≤ O(4)）代替多个间接块查找（O(间接块数)）
- 碎片化减少：extent 尽量合并连续块
- 元数据开销降低：减少块指针数量（一个 extent 可覆盖 128 × 4KB = 512KB，而间接块方案需要 128 个块指针）
