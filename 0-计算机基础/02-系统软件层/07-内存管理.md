# 内存管理

> **版本基准**: universal

## 定义

内存管理通过**虚拟地址空间**实现进程间隔离，并通过**页表**实现虚拟地址到物理地址的翻译。核心目标：在有限物理内存上为每个进程提供看似无限的地址空间，同时通过页面置换在内存与磁盘之间迁移数据。

**归约视角**：虚拟内存将"地址空间大小 > 物理内存大小"的矛盾归约为"缺页率 vs 磁盘 I/O 延迟"的权衡。页面置换算法研究的是如何最小化缺页率，数学上可建模为最优化问题。

## 数学模型

**x86_64 四级页表翻译（48 位虚拟地址）：**

$$
\text{VA[47:0]} = \underbrace{[\text{PGD}_9][\text{PUD}_9][\text{PMD}_9][\text{PTE}_9][\text{Offset}_{12}]}_{\text{5级索引}}
$$

$$
\text{PA} = \underbrace{\text{PTE}[\text{PFN}]}_{\text{物理页框号}} \times 2^{12} + \text{VA}[11:0]
$$

页表项结构（PTE，64位）：

| 位 | 内容 | 说明 |
|----|------|------|
| [0] | P (Present) | 页是否存在物理内存 |
| [1] | R/W | 读/写权限 |
| [2] | U/S | 用户/超级用户权限 |
| [5] | A (Accessed) | 访问过（被 CPU 或软件设置） |
| [6] | D (Dirty) | 脏页（被写） |
| [12:51] | PFN | 物理页框号 |

虚拟地址高 16 位为符号扩展位，必须与第 47 位相同，否则触发 #GP（Canonical Address Check 失败）。

**页面置换的数学约束（Belady 异常）：**

Belady 证明：FIFO 置换算法在增加页框数时可能增加缺页率，LRU 则不会。这说明**置换算法的选择直接影响缺页率**。

$$
\text{缺页率}} = f(|\text{working set}|, \text{内存总量})
$$

当 $|\text{working set}| > \text{内存总量}$ 时，系统进入抖动（thrashing）。

**归约视角**：抖动是 working set 大小超过可用物理页框数时的必然结果。数学上，thrashing 等价于 $P_{\text{页面置换}} \gg P_{\text{计算}}$，导致系统时间被磁盘 I/O 主导。

**伙伴系统分配数学：**

物理页框分配以 2^k 页为单位：
$$
\text{buddy}[k] = \text{大小为}2^k\text{页的空闲块链表}, \quad k \in [0, 10]
$$

分配算法时间复杂度：O(1)（查找）+ O(分裂次数)（递归查找）。

**数据形态变换序列：**

| 阶段 | 地址形态 | 查找代价 | 备注 |
|------|----------|----------|------|
| TLB 命中 | VA → PA | O(1) | 硬件并行查找 |
| TLB 未命中 | VA → 中间物理地址 | O(4) × 4级 | 每级需内存访问 |
| P=1, 权限足 | PA 直接返回 | - | 正常翻译 |
| P=0（合法） | 触发缺页异常 | 磁盘 I/O | 换入或分配 |
| P=0（非法） | 触发 SIGSEGV | - | 进程终止 |

## 机制

### 页面置换算法

| 算法 | 决策函数 | 缺页率特征 | 实现开销 |
|------|----------|------------|----------|
| OPT | 最远未来访问 | 理论最低（下界） | 需预知未来（不可实现） |
| FIFO | 最早进入内存 | 简单，但可能有 Belady 异常 | O(1) |
| LRU | 最近最少使用 | 近似 OPT | O(n) 或 O(log n)（堆实现） |
| CLOCK | R=1 清除，R=0 置换 | LRU 近似 | O(n) 环形链表 |
| Working Set | 时间内访问过的页面 | 自适应 | 需跟踪每个进程历史 |

CLOCK 算法（第二次机会）的精确行为：
```
扫描环形缓冲区：
  - R=1 → 清除R，下一格
  - R=0 → 置换该页，下一格
  - 循环直到找到置换页
```

**约束条件**：
- 页面置换代价高（磁盘 I/O 毫秒级 vs 内存访问纳秒级，差距约 10^5-10^6 倍）
- 抖动：换页比计算更快时，系统退化

**违反约束的后果**：
- 内存泄漏（未释放 malloc） → 可用内存减少 → OOM Killer 触发
- OOM Killer 按 score 杀死最"坏"进程

**OOM Killer 的精确评分算法：**

Linux OOM Killer 计算每个进程的 oom_score：

$$
\text{score} = \text{pages\_owned} + \text{oom\_score\_adj} + \text{age\_factor} + \text{numa\_factor}
$$

- `pages_owned`：进程拥有的物理页数（从 /proc/[pid]/stat 的 vm_rss 字段获取）
- `oom_score_adj`：用户可调的分数调整（范围 -1000 到 +1000）
- `age_factor`：进程运行时间越长，score 越低（避免杀死长期进程）
- `numa_factor`：NUMA 内存亲和性，优先杀死使用本地内存少的进程

**oom_score_adj 的调节策略：**

| oom_score_adj | 效果 |
|---------------|------|
| -1000 | 完全免疫（不会被杀死） |
| -800 ~ -200 | 降低被杀概率 |
| 0 | 默认 |
| +200 ~ +800 | 提高被杀概率 |
| +1000 | 优先杀死 |

典型使用场景：
- `oom_score_adj = -1000`：数据库等关键进程
- `oom_score_adj = +500`：日志进程等可重启服务

**OOM 触发的精确条件：**

```c
// 在 alloc_pages() 失败时触发
if (gfp_mask & __GFP_NOFAIL) {
    // NOFAIL 分配不允许失败，会触发 OOM killer
}
// 或当 watermark[LOW] 持续低于 min 且无法回收时
```

OOM killer 被调用时，选择 score 最高的进程发送 SIGKILL。

### 伙伴系统（内核内存分配）

物理页框分配（以 2^k 页为单位）：

$$
\text{buddy}[k] = \text{大小为}2^k\text{页的空闲块链表}, \quad k \in [0, 10]
$$

分配算法（阶 k=5 为例）：
1. 在 buddy[5] 查找
2. 找到 → 分配
3. 未找到 → 在 buddy[6] 分裂为两个 buddy[5]
4. 一个分配，另一个加入 buddy[5]
5. 若 buddy[6] 也无，递归向 buddy[7] 查找

释放算法：
1. 释放 buddy[5]
2. 检查其伙伴（物理地址连续、大小相同）是否也空闲
3. 空闲 → 合并为 buddy[6]
4. 递归向上合并直到最大阶或遇到非空闲伙伴

**约束条件**：
- 只能分配 2 的幂次方页数（内部碎片）
- 碎片化可能导致大块请求失败（外部碎片）

**违反约束的后果**：
- 内存碎片化 → 明明总空闲量够但分配失败（外部碎片）
- 解决方案：slab 分配器（基于伙伴系统的对象缓存，减少碎片）

### NUMA 感知内存管理

在 NUMA（Non-Uniform Memory Access）系统中，内存访问延迟与 CPU-内存距离相关：

$$
T_{\text{access}} = T_{\text{local}} + \text{distance}(cpu, memory) \times \text{latency\_per\_hop}
$$

| 节点配置 | 本地访问 | 远程访问 |
|----------|----------|----------|
| 2节点NUMA | ~60-80ns | ~150-200ns |
| 4节点NUMA | ~60-80ns | ~200-300ns |

**Linux NUMA 内存分配策略：**

| 策略 | 行为 | 适用场景 |
|------|------|----------|
| MPOL_DEFAULT | 使用当前 CPU 所在节点的内存 | 默认 |
| MPOL_BIND | 仅使用指定节点 | 关键应用固定 |
| MPOL_INTERLEAVE | 跨节点交错分配 | 大型数据库 |
| MPOL_PREFERRED | 优先本地，失败时远程 | 通用 |

**Linux NUMA 内存重平衡：**

当进程从一个节点迁移到另一个时，其内存可能仍保留在原节点：
1. 新节点访问远程内存 → 延迟增加
2. 内核定期检测 NUMA 失衡
3. 若失衡超过阈值（`numa_balancing_scan_period_ms`），触发页面迁移
4. 页面迁移使用 migrate_pages()，将内存复制到新节点

**migrate_pages() 的约束：**
- 迁移需要：分配新节点页 → 复制内容 → 更新页表 → 释放旧页
- 迁移代价：约 10-20μs/页
- 无法迁移：共享页、locked 页、kernel 栈

### Slab 分配器

slab 分配器在伙伴系统之上构建对象缓存：

```
slab 分配器层次:
┌─────────────────────────────────────┐
│  对象缓存 (kmalloc/kfree)          │
│  ├─ cache_cache (slab 元数据)       │
│  ├─ size-32, size-64, ...          │
│  └─ 专用缓存 (inode, dentry, etc.) │
├─────────────────────────────────────┤
│  slab 层 (物理页组合)               │
│  ├─ slabs_full (已分配完)           │
│  ├─ slabs_partial (部分使用)        │
│  └─ slabs_free (完全空闲)           │
├─────────────────────────────────────┤
│  伙伴系统 (页框分配)                │
└─────────────────────────────────────┘
```

**优势**：
- 减少内部碎片（对象大小精确匹配）
- 减少分配延迟（常用对象缓存预热）
- 着色技术优化 CPU cache 利用率

### 内存映射（mmap）

mmap 将文件或匿名区域映射到进程地址空间：

$$
\text{文件映射} = \underbrace{\text{页缓存}}_{\text{磁盘 ↔ 内存}} \xleftarrow{\text{read/write}} \text{用户虚拟地址}
$$

映射类型：
- **文件映射**：页缓存关联文件，支持持久化
- **匿名映射**（MAP_ANONYMOUS）：无后端文件，swap 空间作为备份
- **私有映射**（MAP_PRIVATE）：写时复制（CoW）
- **共享映射**（MAP_SHARED）：修改直接落磁盘（对文件）或跨进程共享（对匿名）

**归约视角**：mmap 将文件 I/O 归约为内存读写。磁盘块到虚拟页的映射由页面置换子系统管理，对用户程序透明。

**约束条件**：
- MAP_FIXED 会覆盖已有映射，可能导致原有映射丢失
- 匿名映射需要 swap 空间备份，swap 耗尽时分配失败

**违反约束的后果：**
- MAP_FIXED 覆盖 → 原映射中的数据若未同步会丢失
- swap 耗尽 → 分配失败（返回 MAP_FAILED），程序可能崩溃

### TLB 与缓存协同

TLB（Translation Lookaside Buffer）是页表的硬件缓存：

```
VA → TLB 查询 → TLB Miss → 4级页表查找 → TLB 填充 → PA
            │                              │
            │ 命中 (O(1))                   │ 未命中 (~30-100 周期)
            ▼                              ▼
         直接返回 PA                   继续翻译
```

**TLB 刷新策略**：
- **TLB shootdown**：多核系统中一个核修改页表后，需要广播通知其他核刷新 TLB
- **CR3 写入**：上下文切换时自动 flush（Linux 使用的方法）

**TLB shootdown 的精确机制（多核环境）：**

当一个 CPU 核修改了共享页表（如 munmap），其他 CPU 核的 TLB entry 可能指向过期映射：

```
核 A 执行 munmap(addr):
1. 更新页表（PTE 标记为无效）
2. 调用 flush_tlb_mm(mm) 刷新本地 TLB
3. 发送 IPI（Inter-Processor Interrupt）到其他持有 mm 相关 TLB entry 的 CPU 核
4. 其他核收到 IPI → 执行 INVLPG 或 CR3 写入刷新 TLB

TLB shootdown 的成本：
- IPI 延迟：约 1-5μs（取决于架构）
- 广播范围：只有持有相关 TLB entry 的核需要刷新
- 优化：Linux 使用 "lazy TLB" 优化，避免不相关的核参与 shootdown
```

**TLB shootdown 的 NUMA 影响：**

在 NUMA 系统中，页表修改的影响范围更复杂：
- 本地节点修改 → 可能影响远程节点的 TLB
- Linux 使用 "flush TLB by range" 而非 "flush entire mm" 减少开销

**性能影响**：
- TLB 未命中率每上升 1%，内存密集型应用性能下降约 2-5%
- 大页（HugePages）减少 TLB miss 率（2MB vs 4KB）

## 参考存根

```c
// 页面分配（Linux 内核）
struct page* alloc_pages(gfp_t gfp_mask, unsigned int order);
// order=0: 4KB, order=2: 16KB, order=10: 4MB

// 用户空间 mmap
void* mmap(void* addr, size_t length, int prot, int flags, int fd, off_t offset);
// prot: PROT_READ|PROT_WRITE|PROT_EXEC
// flags: MAP_PRIVATE|MAP_ANONYMOUS|MAP_FIXED

// 伙伴系统分配（简化）
void* buddy_alloc(int order) {
    for (int o = order; o <= MAX_ORDER; o++) {
        if (!list_empty(&free_area[o])) {
            struct page* page = list_pop(&free_area[o]);
            split_page(page, o, order);
            return page_to_virt(page);
        }
    }
    return NULL;  // 分配失败
}
```
