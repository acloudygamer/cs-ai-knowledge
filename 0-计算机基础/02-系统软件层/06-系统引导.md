# 系统引导

> **版本基准**: universal

## 定义

系统引导是从上电到操作系统内核完全加载并执行第一个用户进程的**确定性状态迁移序列**。每一阶段都有明确的入口函数和退出条件，引导失败将导致系统无法启动，因此引导代码必须极度保守且高度调试。

**归约视角**：引导过程的本质是从"固化硬件状态"到"通用操作系统状态"的**状态机初始化序列**。每个阶段都是前一个阶段的**后置条件**和下一个阶段的**前置条件**。

## 数学模型

**BIOS/UEFI 跳转向量：**

$$
\text{CS:IP} = 0xFFFF0 \quad \text{(BIOS)} \xrightarrow{\text{JMP}} \text{POST} \xrightarrow{\text{检查}} \text{启动设备选择}
$$

$$
\text{UEFI} \xrightarrow{\text{PE/COFF加载}} \text{EFI入口} \xrightarrow{\text{BS.Call}} \text{BootServices}
$$

GPT 分区表 CRC 校验：

$$
\text{gpt\_header.crc32} = \text{CRC32}(\text{gpt\_header} - \text{CRC32字段}, 92\text{字节})
$$

$$
\text{分区表 CRC} = \text{CRC32}(\text{分区表}, \text{Header.partition\_entry\_count} \times 128\text{字节})
$$

UEFI 启动时验证 GPT 头部和分区表 CRC，任一失败拒绝启动。

**Secure Boot 签名链：**

$$
\text{固件 DB（签名数据库）} \xrightarrow{\text{验证}} \text{Bootloader (签名)} \xrightarrow{\text{验证}} \text{内核/efi (签名)}
$$

$$
\text{DBX（撤销列表）} \xrightarrow{\text{检查}} \text{签名在 DBX 中 → 拒绝执行}
$$

**Secure Boot 的 X.509 证书体系：**

| 密钥存储区 | 用途 | 可修改性 |
|------------|------|----------|
| PK (Platform Key) | 验证 KEK 的根证书 | OEM 锁定后不可改 |
| KEK (Key Exchange Key) | 验证 DB/DBX 的签名 | 可通过 PK 更新 |
| DB (Signature Database) | 允许签名的启动组件 | 可通过 KEK 更新 |
| DBX (Forbidden Signature Database) | 撤销的签名（已知漏洞/恶意） | 可通过 KEK 更新 |

签名验证流程：
1. UEFI 固件用 PK 验证 KEK 签名
2. 用 KEK 验证 DB/DBX 的签名
3. Bootloader 的签名必须在 DB 中且不在 DBX 中
4. 内核/efi 的签名同样必须在 DB 中且不在 DBX 中

**Secure Boot 的形式化验证约束：**

签名验证必须满足以下数学约束才能允许执行：
$$
\text{允许执行} \iff (\text{signature} \in \text{DB}) \land (\text{signature} \notin \text{DBX}) \land (\text{验证者} \in \text{KEK})
$$

这个约束是**不可变的**：若任一条件不满足，引导链中断。此外，DBX 的优先级高于 DB——即使签名在 DB 中，若同时出现在 DBX，仍会被拒绝。这用于快速撤销被泄露的证书。

**约束条件**：签名验证必须覆盖引导链的每个阶段，任何一个阶段的验证失败都会阻止引导。

**第三方 OS 的签名困境：**

Linux 发行版的 GRUB/内核要支持 Secure Boot，通常需要：
1. 找 CA 签名（如微软签名给 Shim bootloader）
2. 或用户手动将发行版的公钥添加到固件 DB

微软签名要求：内核必须链接到 Microsoft验证过 PE 签名，这增加了复杂性。

## 机制

### MBR vs GPT 分区格式

| 特性 | MBR | GPT |
|------|-----|-----|
| 磁盘容量限制 | 2TB（512B 扇区 × 2^32） | 8ZB（16EB 使用 64 位 LBA） |
| 分区表位置 | LBA 0（与 MBR 共用扇区） | LBA 1（主），LBA 2-33（备份） |
| 最大分区数 | 4 主分区（或 3 主 + 1 扩展） | 128（按 EFI 标准） |
| 校验方式 | 0x55AA（仅 MBR 扇区） | CRC32（头部 + 分区表） |
| 唯一标识 | 无 | UUID（磁盘 + 每个分区） |

MBR 的根本限制：使用 32 位 LBA，只支持 2^32 × 512 = 2TB 磁盘。

**约束条件：**
- BIOS 只能从 MBR 启动，无法识别 GPT
- UEFI 可以从 GPT 启动（推荐），也可配置为 BIOS 兼容模式（CSM）

**违反后果：**
- MBR 损坏 → 系统无法找到可启动介质，停在 "No bootable device"
- GPT 损坏且备份未同步 → 分区信息丢失，数据不可恢复

### UEFI Secure Boot

Secure Boot 防止在引导阶段加载未签名或恶意签名的引导程序：

$$
\text{固件 DB} \xrightarrow{\text{签名验证}} \text{第一阶段引导程序} \xrightarrow{\text{签名验证}} \text{后续引导程序/内核}
$$

签名验证使用 X.509 证书 + RSA/ECDSA 签名。PK（Platform Key）由 OEM 写入，KEK（Key Exchange Key）存储可接受的签名证书。

**约束条件：**
- 密钥必须写入固件 NVRAM
- 第三方 OS 需要微软签名或用户手动添加签名到 DB

**违反后果：**
- 签名验证失败 → UEFI 拒绝执行，返回 "Secure Boot violation"
- 关闭 Secure Boot → 固件设置中可禁用，但可能触发某些 OEM 锁定

### initramfs 与根文件系统切换

initramfs 是压缩的 cpio 归档，在真正根文件系统挂载前作为临时根：

**pivot_root vs switch_root 的区别：**

| 操作 | pivot_root | switch_root |
|------|------------|-------------|
| 适用场景 | initramfs 内切换根 | initramfs 结束，exec 新 init |
| 调用者 | initramfs 内 /init 脚本 | initramfs 内 /init 脚本最后一步 |
| 语义 | 改变当前进程的根目录视图 | 删除旧根，exec 新程序 |

**pivot_root 精确流程：**
```
# 假设当前根 = initramfs 的 rootfs
1. mkdir /new_root              # 在 initramfs 中创建挂载点
2. mount --move /dev/sda2 /new_root   # 将真正根挂载到 /new_root
3. pivot_root("/new_root", "/old_root")  # 切换根目录
4. # 现在进程的根 = /new_root，/old_root 仍挂载（但不可见）
5. exec /sbin/init              # 执行真正 init（通过 chroot）

# 新 init 执行后：
6. umount /old_root            # 清理 initramfs
```

**switch_root 精确流程：**
```
# switch_root 会删除 initramfs 的 rootfs（更彻底）
1. mount --move /dev/sda2 /new_root
2. delete /old_root/*          # 删除 initramfs 内容
3. chroot /new_root
4. exec /sbin/init
```

**initramfs 的 cpio 格式：**

initramfs 是链接到内核的 cpio 归档（gzip 压缩）：
- 内核编译时：`CONFIG_INITRAMFS_SOURCE="path/to/dir"` 或 `CONFIG_INITRAMFS_SOURCE="path/to.cpio.gz"`
- 格式：ASCII cpio（SVR4/archive）或 Gnu cpio 2.x 格式
- 内核解压后直接作为 rootfs（不是 tmpfs），使用 `populate_rootfs()` 函数

**initramfs 的典型内容：**
- /bin/bash（shell）
- /sbin/mount, /sbin/umount, /sbin/switch_root
- /lib/modules/*.ko（根文件系统驱动：ext4/xfs/btrfs, LVM, LUKS, RAID）
- /lib64/ld-linux-x86-64.so.2（动态链接器）
- /init（通常是 shell 脚本或指向 systemd 的链接）

**归约视角**：initramfs 将"内核需要支持所有可能的根文件系统"的问题归约为"initramfs 只需包含加载根文件系统的最小驱动集"。内核模块化设计的具体体现。

**约束条件：**
- initramfs 里的驱动必须包含根文件系统的驱动，否则无法 mount root
- pivot_root 需要 root 用户权限
- initramfs 空间有限（约 10-50MB），内容需精简

**违反后果：**
- 根文件系统驱动缺失 → kernel panic ("VFS: Unable to mount root fs")
- pivot_root 失败 → 无法切换根文件系统，引导终止
- initramfs 过大 → 内核镜像膨胀，影响加载时间

### 内核引导参数

引导参数通过命令行传递给内核：

```
"root=/dev/sda2 ro quiet splash"
```

常用参数：
- `root=`：根文件系统设备
- `ro/rw`：根文件系统挂载为只读/可写
- `init=`：第一个用户进程（默认 /sbin/init）
- `quiet`：抑制内核启动信息
- `nosmp/maxcpus=`：禁用或多核限制
