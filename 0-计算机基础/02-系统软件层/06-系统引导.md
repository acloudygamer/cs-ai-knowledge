# 系统引导

## 定义

系统引导是从上电到操作系统内核完全加载并执行第一个用户进程的**确定性状态迁移序列**。每一阶段都有明确的入口函数和退出条件，引导失败将导致系统无法启动，因此引导代码必须极度保守且高度调试。

**归约视角**：引导过程的本质是从"固化硬件状态"到"通用操作系统状态"的**状态机初始化序列**。每个阶段都是前一个阶段的**后置条件**和下一个阶段的**前置条件**。

## 数学模型

**BIOS/UEFI 跳转向量：**

$$
\text{CS:IP} = 0xFFFF0 \quad \text{(BIOS)} \xrightarrow{\text{JMP}} \text{POST} \xrightarrow{\text{检查}} \text{启动设备选择}
$$

$$
\text{UEFI} \xrightarrow{\text{PE/COFF加载}} \text{EFI入口} \xrightarrow{\text{BS.Call}} \text{BootServices}
$$

GPT 分区表 CRC 校验：

$$
\text{gpt\_header.crc32} = \text{CRC32}(\text{gpt\_header} - \text{CRC32字段}, 92\text{字节})
$$

$$
\text{分区表 CRC} = \text{CRC32}(\text{分区表}, \text{Header.partition\_entry\_count} \times 128\text{字节})
$$

UEFI 启动时验证 GPT 头部和分区表 CRC，任一失败拒绝启动。

**Secure Boot 签名链：**

$$
\text{固件 DB（签名数据库）} \xrightarrow{\text{验证}} \text{Bootloader (签名)} \xrightarrow{\text{验证}} \text{内核/efi (签名)}
$$

$$
\text{DBX（撤销列表）} \xrightarrow{\text{检查}} \text{签名在 DBX 中 → 拒绝执行}
$$

**约束条件**：签名验证必须覆盖引导链的每个阶段，任何一个阶段的验证失败都会阻止引导。

数据形态变换：
- BIOS ROM → 内存映射执行（CPU 读取指令）
- MBR 扇区（512 字节）→ 加载到内存 0x7C00 → 跳转执行
- 内核镜像（bzImage 压缩）→ 解压缩到 1MB 以上内存区域
- initramfs（cpio）→ 解压到 tmpfs → pivot_root 切换根文件系统

## 机制

### MBR vs GPT 分区格式

| 特性 | MBR | GPT |
|------|-----|-----|
| 磁盘容量限制 | 2TB（512B 扇区 × 2^32） | 8ZB（16EB 使用 64 位 LBA） |
| 分区表位置 | LBA 0（与 MBR 共用扇区） | LBA 1（主），LBA 2-33（备份） |
| 最大分区数 | 4 主分区（或 3 主 + 1 扩展） | 128（按 EFI 标准） |
| 校验方式 | 0x55AA（仅 MBR 扇区） | CRC32（头部 + 分区表） |
| 唯一标识 | 无 | UUID（磁盘 + 每个分区） |

MBR 的根本限制：使用 32 位 LBA，只支持 2^32 × 512 = 2TB 磁盘。

**约束条件：**
- BIOS 只能从 MBR 启动，无法识别 GPT
- UEFI 可以从 GPT 启动（推荐），也可配置为 BIOS 兼容模式（CSM）

**违反约束的后果：**
- MBR 损坏 → 系统无法找到可启动介质，停在 "No bootable device"
- GPT 损坏且备份未同步 → 分区信息丢失，数据不可恢复

### UEFI Secure Boot

Secure Boot 防止在引导阶段加载未签名或恶意签名的引导程序：

$$
\text{固件 DB} \xrightarrow{\text{签名验证}} \text{第一阶段引导程序} \xrightarrow{\text{签名验证}} \text{后续引导程序/内核}
$$

签名验证使用 X.509 证书 + RSA/ECDSA 签名。PK（Platform Key）由 OEM 写入，KEK（Key Exchange Key）存储可接受的签名证书。

**约束条件：**
- 密钥必须写入固件 NVRAM
- 第三方 OS 需要微软签名或用户手动添加签名到 DB

**违反约束的后果：**
- 签名验证失败 → UEFI 拒绝执行，返回 "Secure Boot violation"
- 关闭 Secure Boot → 固件设置中可禁用，但可能触发某些 OEM 锁定

### initramfs 与根文件系统切换

initramfs 是压缩的 cpio 归档，在真正根文件系统挂载前作为临时根：

pivot_root 流程：
```
1. mount --move /dev/sda1 /new_root   // 将真正根挂载到 /new_root
2. pivot_root("new_root", "old_root") // 切换根目录
3. exec /sbin/init                     // 执行真正 init
```

关键约束：旧根（old_root）在 pivot_root 后仍需保持挂载，直至 init 进程用 umount 解除。

initramfs 的典型内容：
- /bin/bash（shell）
- /sbin/mount, /sbin/umount
- /lib/modules/*.ko（根文件系统驱动：ext4/xfs/btrfs, LVM, LUKS, RAID）
- /lib64/ld-linux-x86-64.so.2（动态链接器）

**归约视角**：initramfs 将"内核需要支持所有可能的根文件系统"的问题归约为"initramfs 只需包含加载根文件系统的最小驱动集"。内核模块化设计的具体体现。

**约束条件：**
- initramfs 里的驱动必须包含根文件系统的驱动，否则无法 mount root
- pivot_root 需要 root 用户权限

**违反约束的后果：**
- 根文件系统驱动缺失 → kernel panic ("VFS: Unable to mount root fs")
- pivot_root 失败 → 无法切换根文件系统，引导终止

## 参考存根

```bash
# UEFI 启动项管理
efibootmgr -v                        # 显示当前启动项
efibootmgr --create \
    --disk /dev/sda \
    --part 1 \
    --label "Arch Linux" \
    --loader "\\EFI\\arch\\grubx64.efi"

# GRUB 配置片段（/boot/grub/grub.cfg）
menuentry 'Arch Linux' {
    load_video
    set gfxpayload=keep
    linux   /boot/vmlinuz-linux root=/dev/sda2 ro
    initrd  /boot/initramfs-linux.img
}

# initramfs 内容检查
lsinitcpio /boot/initramfs-linux.img  # 显示 cpio 内容
```
