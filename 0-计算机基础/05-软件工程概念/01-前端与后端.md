# 前端与后端

> **版本基准**: universal

## 定义

前后端分离是一种架构范式，将用户界面（前端）与业务逻辑及数据管理（后端）解耦为独立服务，通过标准化协议通信。其本质是**关注点分离（Separation of Concerns）在进程边界的具象化**：前端运行于浏览器沙箱（受限于同源策略），后端运行于服务器进程（受限于系统资源），两者通过网络协议通信——每一次前后端交互都是一次跨越机器边界的进程间通信（IPC）。

**归约内核**：前后端分离的核心约束是**进程边界的显式化**。前端代码运行在浏览器沙箱中，后端代码运行在服务器进程中，两者通过网络协议进行通信。这意味着前端无法直接访问后端的内存空间，后端也无法直接调用前端的函数——所有交互必须通过序列化/反序列化的网络消息完成。

## 数学模型

### 端到端延迟分解

$$
T_{total} = \underbrace{T_{network}}_{RTT \times (1 + 2p)^{-1}} + \underbrace{T_{server}}_{T_{cpu} + T_{io}} + \underbrace{T_{render}}_{T_{layout} + T_{paint}}
$$

其中 $p$ 是丢包率（丢包触发重传，使有效 RTT 放大）。后端处理时间可进一步分解为：

$$
T_{server} = T_{route} + T_{auth} + T_{biz} + T_{db} + T_{ser}
$$

| 阶段 | 复杂度 | 说明 |
|------|--------|------|
| $T_{route}$ | $O(1)$ | 哈希表查找 |
| $T_{auth}$ | $O(1)$ 或 $O(\log n)$ | JWT 验证 vs Session 查询 |
| $T_{biz}$ | 算法相关 | 业务逻辑复杂度 |
| $T_{db}$ | $O(\log_f N)$ 或 $O(N)$ | B+树查找 vs 全表扫描 |
| $T_{ser}$ | $O(n)$ | JSON 序列化 |

**利特尔法则（Little's Law）**：设后端并发处理能力为 $C$（线程/进程数），请求到达率为 $\lambda$，稳态延迟：

$$
T_{total} = \frac{1}{\mu - \lambda} + T_{think}
$$

当 $\lambda \to \mu$ 时，延迟趋于无穷——这是后端容量规划的核心理论依据。

### 接口兼容性约束

接口兼容性可建模为版本空间的包含关系。设接口版本 $v$ 的有效操作集合为 $O(v)$，向后兼容要求：

$$
\forall v_{old} < v_{new}: O(v_{old}) \subseteq O(v_{new}) \cup O_{deprecated}(v_{new})
$$

即新版本必须包含旧版本的全部操作，或旧操作仅被标记为废弃（仍可使用）。

## 数据流

<pre>
用户浏览器                      前端服务                      后端服务                      数据库
    │                             │                             │                             │
    │─── HTTP Request ──────────►│                             │                             │
    │      (JSON/HTML/CSS/JS)    │                             │                             │
    │                             │─── REST/gRPC Request ─────►│                             │
    │                             │      (JSON/二进制)         │                             │
    │                             │                             │─── SQL Query ──────────────►│
    │                             │                             │      (结构化查询)           │
    │                             │                             │◄─── Result Set ───────────│
    │                             │◄─── JSON Response ─────────│                             │
    │◄─── HTML/JSON ────────────│                             │                             │
    │      (渲染指令)             │                             │                             │
</pre>

**数据形态变换链路**：

1. `用户操作` → `DOM 事件` → `状态更新`
2. `状态更新` → `HTTP 请求（JSON）` → `TCP 连接复用（Keep-Alive）`
3. `HTTP 请求` → `路由中间件` → `认证中间件` → `业务处理器`
4. `业务处理器` → `SQL 查询` → `B+树查找` → `结果集`
5. `结果集` → `ORM 映射` → `JSON 序列化` → `HTTP 响应`
6. `HTTP 响应` → `前端状态更新` → `虚拟 DOM diff` → `真实 DOM 更新`

**所有权变换**：
- 浏览器持有 DOM 所有权，前端框架持有虚拟 DOM 描述权
- HTTP 请求的所有权在浏览器和网络层之间转移
- 后端进程中，请求从网络缓冲区转移到应用内存，最后返回
- 数据库返回的结果集所有权属于数据库连接会话

## 机制

### 接口契约的约束本质

前后端通过 API 协议通信，接口是跨越进程边界的隐式契约。契约的约束来自两个方向：

**向后兼容约束**：新增可选字段不破坏旧客户端；删除字段需经折旧周期；修改类型导致兼容断裂。违反此约束的结果是**级联式故障**：API 消费者无法预期响应格式，解析失败产生 500 或 400 错误。

**版本正交性**：URL 版本（如 `/api/v1/`）与语义版本（header `API-Version`）是两种流派。前者直观但导致 URL 污染；后者整洁但需要消费者主动指定。

### 无状态设计的真正含义

"后端不应依赖前端状态" 的真正含义是：**后端每次请求都必须能够从请求本身重建完整上下文**。

- 用户身份：从 JWT token 或 Cookie 中解析，而非从内存中的会话对象
- 业务上下文：从请求参数/Body 中获取，而非从上一次请求的副作用中获取

违反此约束的结果是**状态耦合导致的水平扩展障碍**：有状态服务无法通过简单增加副本数来扩容。

**数学约束**：无状态服务的水平扩展性。设服务实例数为 $N$，有状态服务中，若请求 $i$ 只能由实例 $f(i)$ 处理，则有效并发能力被限制为 $\max_i |\{j : f(j) = f(i)\}|$。

### 跨域限制的根因

浏览器 CORS 策略是同源政策（Same-Origin Policy）的延展。同源政策的根因是**浏览器是攻击面**：恶意脚本可读写同源资源。若无同源限制，恶意页面可借助用户 cookie 向银行 API 发起 CSRF 攻击。

CORS 是服务器显式授权跨域访问的机制。本质是服务器通过特定 HTTP header 声明"此资源允许特定来源的脚本访问"。

**CORS 预检请求的状态机**：
1. 浏览器发送 OPTIONS 请求，包含 `Access-Control-Request-Method` 和 `Access-Control-Request-Headers`
2. 服务器响应允许的方法和头部
3. 浏览器缓存预检结果（依据 `Access-Control-Max-Age`）

### REST vs GraphQL vs gRPC 的本质差异

| 维度 | REST | GraphQL | gRPC |
|------|------|---------|------|
| 数据获取 | 资源粒度，多次请求 | 按需字段，单次请求 | 接口定义，多次请求 |
| 缓存 | HTTP 层缓存天然支持 | 需自行实现缓存层 | 无 HTTP 缓存 |
| 类型安全 | 无，运行时才发现错误 | Schema 声明，编译时验证 | Protobuf 编译时验证 |
| 传输 | JSON（文本） | JSON（文本） | Protocol Buffers（二进制） |

**性能权衡**：gRPC 的二进制协议使序列化/反序列化开销接近零，但浏览器无法直接使用；GraphQL 减少网络往返但查询复杂度可能失控；REST 缓存友好但接口粒度设计依赖经验。

**GraphQL 查询复杂度约束**：设查询深度为 $d$，每层字段数为 $f_i$，总复杂度 $C = \sum_{i=1}^{d} \prod_{j=1}^{i} f_j$。无限制的查询可能导致服务器资源耗尽。

## 参考存根

```javascript
// 前端请求后端 API（Fetch API + async/await）
const getUser = async (id) => {
    const res = await fetch(`/api/users/${id}`, {
        headers: { 'Authorization': `Bearer ${token}` }
    });
    if (!res.ok) throw new Error(`HTTP ${res.status}`);
    return res.json();
};

// JWT 解析（仅解码，不验证签名）
const parseJWT = (token) => {
    const base64 = token.split('.')[1].replace(/-/g, '+').replace(/_/g, '/');
    return JSON.parse(atob(base64));
};
```
