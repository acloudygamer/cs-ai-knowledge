# 前端与后端

## 定义

前后端分离是一种架构范式，将用户界面（前端）与业务逻辑及数据管理（后端）解耦为独立服务，通过标准化协议通信。其本质是关注点分离（Separation of Concerns）在系统边界的具象化：前端负责渲染与交互，后端负责业务与数据，两者通过契约式接口交互，互不感知内部实现。

## 数学模型

端到端延迟构成：

$$
T_{total} = \underbrace{T_{network}}_{RTT \times (1 + 2p)^{-1}} + \underbrace{T_{server}}_{T_{cpu} + T_{io}} + \underbrace{T_{render}}_{T_{layout} + T_{paint}}
$$

其中 $p$ 是丢包率（丢包触发重传，使有效 RTT 放大）。后端处理时间可进一步分解为：

$$
T_{server} = T_{route} + T_{auth} + T_{biz} + T_{db} + T_{ser}
$$

- $T_{route}$：路由查找，通常 $O(1)$（哈希表）
- $T_{auth}$：身份验证，如 JWT 验证 $O(1)$，Session 查询 $O(\log n)$
- $T_{biz}$：业务逻辑，与算法复杂度直接相关
- $T_{db}$：数据库查询，B+树查找 $O(\log_f N)$，复杂查询涉及全表扫描 $O(N)$
- $T_{ser}$：序列化/反序列化，JSON 解析 $O(n)$

**吞吐量模型**：设后端并发处理能力为 $C$（线程/进程数），前端并发请求率为 $\lambda$，则利特尔法则（Little's Law）给出稳态延迟：

$$
T_{total} = \frac{1}{\mu - \lambda} + T_{think}
$$

当 $\lambda \to \mu$ 时，延迟趋于无穷——这是后端容量规划的核心理论依据。

<pre>
用户浏览器                      前端服务                      后端服务                      数据库
    │                             │                             │                             │
    │─── HTTP Request ───────────►│                             │                             │
    │      (JSON/HTML/CSS/JS)     │                             │                             │
    │                             │─── REST/gRPC Request ─────►│                             │
    │                             │      (JSON/二进制)          │                             │
    │                             │                             │─── SQL Query ──────────────►│
    │                             │                             │      (结构化查询)            │
    │                             │                             │◄─── Result Set ───────────│
    │                             │◄─── JSON Response ─────────│                             │
    │◄─── HTML/JSON ─────────────│                             │                             │
    │      (渲染指令)              │                             │                             │
                                 状态管理                     业务逻辑                      数据持久化
</pre>

数据形态变换链路：

1. `用户操作` → `DOM 事件` → `状态更新`
2. `状态更新` → `HTTP 请求（JSON）` → `TCP 连接复用（Keep-Alive）`
3. `HTTP 请求` → `路由中间件` → `认证中间件` → `业务处理器`
4. `业务处理器` → `SQL 查询` → `B+树查找` → `结果集`
5. `结果集` → `ORM 映射` → `JSON 序列化` → `HTTP 响应`
6. `HTTP 响应` → `前端状态更新` → `虚拟 DOM diff` → `真实 DOM 更新`

## 机制

### 接口契约的约束本质

前后端通过 API 协议通信，接口是跨越进程边界的隐式契约。契约的约束来自两个方向：

**向后兼容约束**：新增可选字段不破坏旧客户端；删除字段需经折旧周期；修改类型导致兼容断裂。违反此约束的结果是**级联式故障**：API 消费者无法预期响应格式，解析失败产生 500 或 400 错误。

**版本正交性**：URL 版本（如 `/api/v1/`）与语义版本（header `API-Version`）是两种流派。前者直观但导致 URL 污染；后者整洁但需要消费者主动指定。REST 社区倾向前者，GraphQL 社区倾向后者。

### 无状态设计的真正含义

"后端不应依赖前端状态" 的真正含义是：**后端每次请求都必须能够从请求本身重建完整上下文**。这意味着：

- 用户身份：从 JWT token 或 Cookie 中解析，而非从内存中的会话对象
- 业务上下文：从请求参数/Body 中获取，而非从上一次请求的副作用中获取

违反此约束的结果是**状态耦合导致的水平扩展障碍**：有状态服务无法通过简单增加副本数来扩容，因为请求必须路由到特定实例。

### 跨域限制的根因

浏览器 CORS 策略是同源政策（Same-Origin Policy）的延展。同源政策的根因是**浏览器是攻击面**：恶意脚本可读写同源资源。若无同源限制，恶意页面可借助用户 cookie 向银行 API 发起 CSRF 攻击。

CORS 是服务器显式授权跨域访问的机制。本质是服务器通过特定 HTTP header（`Access-Control-Allow-Origin`）声明"此资源允许特定来源的脚本访问"。Preflight 请求（OPTIONS）是浏览器主动探测机制，用于判断是否可安全发送实际请求。

### REST vs GraphQL vs gRPC 的本质差异

| 维度 | REST | GraphQL | gRPC |
|------|------|---------|------|
| 数据获取 | 资源粒度，多次请求 | 按需字段，单次请求 | 接口定义，多次请求 |
| 缓存 | HTTP 层缓存天然支持 | 需自行实现缓存层 | 无 HTTP 缓存 |
| 类型安全 | 无，运行时才发现错误 | Schema 声明，编译时验证 | Protobuf 编译时验证 |
| 传输 | JSON（文本） | JSON（文本） | Protocol Buffers（二进制） |
| 浏览器支持 | 原生 | 需中间层转换 | 需 grpc-web |

**性能权衡**：gRPC 的二进制协议使序列化/反序列化开销接近零，但浏览器无法直接使用；GraphQL 减少网络往返但查询复杂度可能失控（嵌套查询）；REST 缓存友好但接口粒度设计依赖经验。

## 参考存根

```javascript
// 前端请求后端 API（Fetch API + async/await）
const getUser = async (id) => {
    const res = await fetch(`/api/users/${id}`, {
        headers: { 'Authorization': `Bearer ${token}` }
    });
    if (!res.ok) throw new Error(`HTTP ${res.status}`);
    return res.json();
};
```
