# 前后端与架构分层

## 核心定义：切分由变化频率与部署单元决定

"前端/后端"不是两种技术口味，而是对**约束差异**的回应：一套系统里，有的部分贴着用户设备（浏览器、手机——设备多样、网络不可控、发版受制于应用商店审核），有的部分贴着数据和算力（服务器——集中、可控、随时可改）。两部分的**变化频率、部署单元、所需专长**都不同，于是切分：

- **前端**：运行在用户设备上，负责呈现与交互——HTML/CSS/JS（浏览器）或原生应用；
- **后端**：运行在服务器上，负责数据、规则与协调——业务逻辑、数据库、鉴权。

切分的接口是 **API**（通常是 HTTP + JSON，见《计算机网络》05）：一份明确的契约让两侧独立演化。契约因此是全系统最需要稳定性的地方——前端发版慢、后端迭代快，**API 的向后兼容**就是两条变化曲线之间的缓冲带。

契约演化的纪律是**只加不删、不改语义**：新字段可以加，旧字段的含义不能变；必须破坏性变更时走版本化（`/v2/...`），新旧并存一段时间给客户端迁移期。契约破坏没有编译期告警，只有线上事故。

## 分层：每侧内部再按职责切

无论前端后端，内部组织的主线都是**按职责分层，依赖单向向下**。后端经典三层：接入层（HTTP 接口、参数校验）→ 业务逻辑层（规则与流程，不感知 HTTP）→ 数据访问层（ORM/SQL，不感知业务）。分层的回报是可替换与可测：换掉 Web 框架，业务层一行不动（依赖倒置，01 篇）；测业务逻辑不需要起服务器（02 篇的可测性）。

前端对应的形态是 MVC 一族的演化。MVC 把应用分成模型（数据与状态）、视图（呈现）、控制器（协调），其现代后代的关键一跃是**声明式 UI**：旧写法是命令式地一步步操作界面元素（"找到这个节点、改它的文字"），界面一复杂，状态与视图的一致性全靠人肉维护；声明式把视图写成**状态的函数**（`视图 = f(状态)`，React/Vue 的核心思想），状态一变框架负责重算差异并打补丁——开发者只维护状态，视图永远与其一致。这是用一条不变式（视图是状态的纯函数）消灭了一整类 bug。

## 全链路的形状

一个请求穿过全栈的路径，把前篇内容串成一条线：

```text
浏览器渲染（声明式 UI，状态 → 视图）
  → 用户操作触发状态变化 → 发起 HTTP 请求（API 契约）
  → 后端接入层（校验、鉴权——09 篇的信任边界）
  → 业务逻辑层（规则计算）
  → 数据访问层 → 数据库（07 篇）
  → 响应沿原路返回 → 前端按新状态重渲染
```

每个箭头都是一个可以独立替换的接缝，每层只与相邻层对话——分层架构的本质不是"分"，而是**接缝处契约的稳定性**。

## 微服务的预告

当后端这一个部署单元内部的变化频率也开始撕裂（订单团队和支付团队互相等发版窗口），切分就会继续向内部推进——按业务边界把后端拆成独立部署的服务。那是 08 篇的主题；07 篇先解决切分后最硬的问题：数据放哪。
