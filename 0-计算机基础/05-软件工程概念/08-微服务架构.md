# 微服务架构

## 核心定义：把部署单元切到业务边界上

微服务不是"把程序写小"，而是**把独立部署的单元对齐到独立变化的业务边界**：订单、支付、库存各自是一个服务，各有代码库、数据库、发版节奏。它回应的约束来自组织和规模，而非技术优雅——单体应用里，几十个团队共享一个代码库和一个发版窗口，合并冲突与互相等待随人数超线性增长（康威定律：系统的结构终将长成组织的沟通结构；反过来用，想让系统怎么切，就先怎么摆团队）。

**换来的能力**是三件：独立部署（支付改版不用等订单）、独立伸缩（大促时只扩容订单）、独立选型（各服务用各自合适的技术栈）。

## 账本：分布式的全部代价

单体里一次函数调用变成跨网络调用，06-计算机网络 的每个约束都进来收税：

- **延迟与故障面**：进程内调用 ~100ns，网络调用 ~1ms 起跳且会失败——一次用户请求扇出到十个服务，任何一个慢/挂都会传导。"分布式系统就是多了一万种失败方式的系统"。
- **分布式事务**：单体里数据库事务（07 的 ACID）包办一致性；跨服务后没有共享事务，只有 Saga（每步本地事务 + 失败时逐个补偿）和**最终一致性**——中间态会短暂不一致，业务必须容忍。
- **数据所有权**：每个服务私有数据库（共享库意味着隐式耦合，等于没拆）；跨服务查询要 API 聚合或事件同步，Join 没了。
- **可观测性**：一次请求穿过十个服务，没有分布式追踪（trace id 串联）就无法定位慢在哪——微服务把"运维"从配角变成一等公民。
- **测试与契约**：服务间靠 API 契约协作，契约测试（Consumer-Driven Contract）替代了编译器的类型检查。

拆开的系统还需要一组支撑组件，各管一件分布式下才存在的事：**服务注册与发现**（实例动态上下线，地址不固定——Consul、Nacos）、**配置中心**（几十份实例的配置集中改）、**API 网关**（统一入口：鉴权、限流、路由）、**熔断器**（下游挂了快速失败，而不是无限等待拖死自己）。它们不是微服务的一部分，但没有它们微服务转不起来。

还有一条理论边界值得知道：**CAP**——分布式系统在网络**分区**发生时，只能在**一致性**与**可用性**之间二选一（分区时继续服务就得接受副本暂时不一致；保持一致就得拒绝服务）。它不是"三选二随时选"，而是"分区必然发生，选哪边必须事先想清楚"——07 篇的最终一致性就是选可用性的那一派。

## 切分的依据与时机

服务边界画在哪，答错比不拆更糟。依据是**业务限界上下文**（领域驱动设计 DDD 的概念）：数据和行为内聚在同一个业务概念内（"订单"自己的生命周期全归订单服务），跨上下文的交互走明确接口。错误的切法是按技术层切（"所有查询一个服务、所有写入一个服务"）——那只会把每个业务需求都变成跨服务变更。

时机的共识：**先单体，后拆分**。新项目业务边界根本没人知道，过早拆分等于把猜测冻进架构。单体先跑、边界在代码里自然显形（模块间耦合最少的缝），等到部署冲突与团队等待真实发生时，沿缝切开。微服务是止痛药，不是保健品——没有单体的痛，吃它只剩副作用。

## 与前后篇的连接

08 是 06 的切分逻辑的极限推演：前后端分离是切一刀，微服务是把后端继续切碎；每个微服务仍是 06 的三层结构、仍交付为 05 的镜像、仍由 04 的流水线独立发布——本篇的全部新成本，本质上是为"独立部署"四个字支付的分布式税。评估一个微服务方案，先数它新增了多少条跨服务调用链，再问每条链的延迟、失败与一致性怎么处理——答不上来的边界，就是画错的边界。
