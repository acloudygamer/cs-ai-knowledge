# 测试策略

> **版本基准**: universal

## 定义

测试是通过执行代码并验证输出来证明程序正确性的系统性方法。其本质是**对程序行为的空间进行采样**：穷举所有输入在计算上不可能，测试通过有策略的采样推断整体质量。测试覆盖率是采样密度的度量，而非正确性的保证——100% 覆盖率不意味着无缺陷。

**归约内核**：测试的本质是**验证程序的输入-输出关系**。对于函数 $f: I \to O$ ，测试验证 $\forall i \in I_{test}, f(i) = expected(i)$ 。由于 $I$ 通常是无限集或巨集，测试只能验证 $I_{test} \subset I$ 的子集。

## 数学模型

### 缺陷发现率模型

设缺陷总数为 $D_{total}$ ，各层测试对特定缺陷的发现概率为 $p_i$ （第 $i$ 层测试）。则该缺陷被发现的概率为：

$$
P_{detected} = 1 - \prod_{i=1}^{n}(1 - p_i)
$$

此公式揭示了**测试金字塔的经济学**：各层测试的 $p_i$ 是互补的。

**各层测试的缺陷发现概率矩阵**：

| 测试层 | 单元内缺陷 $p$ | 集成缺陷 $p$ | 跨系统缺陷 $p$ |
|--------|---------------|-------------|---------------|
| 单元测试 | 0.7-0.9 | 0.1-0.2 | 0.0 |
| 集成测试 | 0.3-0.5 | 0.5-0.7 | 0.1 |
| E2E 测试 | 0.1-0.2 | 0.3-0.5 | 0.6-0.8 |

### 缺陷密度与测试充分性

代码复杂度与缺陷密度正相关：

$$
\rho_{defect} = \frac{D_{found}}{LOC}
$$

McCall 度量表明缺陷密度在 0.1-2 defects/KLOC 区间为正常范围。

**圈复杂度与缺陷率的关系**：

$$
P_{defect} \propto e^{\alpha \cdot V(G)}
$$

其中 $V(G)$ 是圈复杂度， $\alpha$ 是与语言相关的常数。圈复杂度越高，缺陷率指数增长。

### 随机测试的覆盖率收敛

设输入空间为 $S$ ，随机采样 $n$ 次，覆盖率期望为：

$$
E[coverage] = 1 - \left(1 - \frac{|S_{covered}|}{|S|}\right)^n
$$

**MC/DC 的数学定义**：对于复合条件 $C = A \land B$ ，MC/DC 要求：
- $A$ 独立影响 $C$ 的结果
- $B$ 独立影响 $C$ 的结果

## 机制

### 测试独立性的约束本质

测试独立性的约束来自**因果关系的可追溯性**：若测试 A 的执行影响测试 B 的结果，则 B 的失败可能由 A 引入，而非被测代码本身。

约束表述：任意测试的执行顺序不应影响任何测试的结果。这要求：
- 每个测试使用独立的测试数据（fixture 隔离）
- 不共享可变全局状态
- 不依赖执行顺序或时间因素

违反此约束的后果是**不稳定的测试（Flaky Tests）**：同样的代码、同样的输入，测试结果不确定。

**隔离性的形式化**：设测试 $T_i$ 的输入为 $I_i$ ，输出为 $O_i$ 。独立性要求：

$$
\forall i \neq j: O_i = f(I_i) \quad \text{且} \quad O_j = f(I_j)
$$

其中 $f$ 是被测函数， $I_i$ 不包含 $T_j$ 的副作用。

### 确定性的执行语义

确定性的约束是**纯函数式的**：给定相同的输入，程序必须产生相同的输出。

约束表述：测试必须能够控制所有输入的来源。随机数必须 seedable，时间必须可 mock，文件系统必须使用内存文件系统或临时目录。

违反此约束的后果是**不可复现的失败**：CI 失败但本地通过，或相反。

### 测试金字塔的物理直觉

| 层级 | 单个测试成本 | 缺陷发现概率（单元级） | 缺陷发现概率（集成级） |
|------|-------------|----------------------|---------------------|
| 单元测试 | $10^{-3}$ - $10^{-2}$s | 高 | 低 |
| 集成测试 | $10^{-1}$ - $10^{0}$s | 中 | 中 |
| E2E 测试 | $10^{1}$ - $10^{2}$s | 低 | 高 |

**测试金字塔的平衡点**由团队规模和发布频率共同决定：小团队/快发布应偏重单元测试，大团队/慢发布应增加集成层。

### 边界条件测试的必要性

许多缺陷发生在**边界条件**而非典型输入：
- 整数溢出：MAX_INT + 1
- 空集合：处理空数组的第一个/最后一个元素
- 竞态条件：多线程同时访问共享状态

**等价类划分的数学表述**：设输入空间 $I$ 被划分为 $k$ 个等价类 $E_1, E_2, ..., E_k$ ，满足：

$$
\bigcup_{i=1}^{k} E_i = I, \quad E_i \cap E_j = \emptyset \ (i \neq j)
$$

每个 $E_i$ 只需一个代表值即可推断该类所有输入的行为。

### 契约式测试与代数性质

某些函数具有可验证的代数性质：
- **幂等性**： $f(f(x)) = f(x)$
- **对合性**： $f^{-1}(f(x)) = x$
- **单调性**： $x < y \Rightarrow f(x) \leq f(y)$

契约测试（Property-Based Testing）通过随机生成输入验证这些性质。

## 参考存根

```python
# pytest 示例：参数化边界测试
@pytest.mark.parametrize("input,expected", [
    (0, 0), (1, 1), (-1, 1), (10, 100),
])
def test_square(input, expected):
    assert square(input) == expected

# Hypothesis 示例：属性测试
from hypothesis import given, strategies as st

@given(st.lists(st.integers()))
def test_sort_idempotent(xs):
    sorted_once = sorted(xs)
    sorted_twice = sorted(sorted_once)
    assert sorted_once == sorted_twice
```

```javascript
// Jest Mock 示例：时间控制
beforeEach(() => { jest.useFakeTimers(); });

test('debounce waits correctly', () => {
    const fn = jest.fn();
    debounce(fn, 1000);
    jest.advanceTimersByTime(500);
    expect(fn).not.toHaveBeenCalled();
    jest.advanceTimersByTime(600);
    expect(fn).toHaveBeenCalledTimes(1);
});
```
