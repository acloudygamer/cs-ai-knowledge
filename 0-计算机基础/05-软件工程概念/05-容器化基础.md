# 容器化基础

## 核心定义：不是轻量虚拟机，是被隔离的进程

容器最常见的误解是"轻量级 VM"。错——虚拟机在硬件层切分（hypervisor 虚拟出整台机器，各跑完整内核，《系统软件层》01）；容器里**没有任何虚拟化**：容器就是宿主机上的一个普通进程，只是内核给它做了三样手术：

- **namespace（命名空间）——隔离视图**：进程看到的 PID、网络栈、挂载点、主机名都是自己的一份。容器里的 PID 1 是宿主机上的一个普通进程；容器有自己独立的网卡、路由表、`/` 目录。
- **cgroup（控制组）——限额用量**：CPU 配额、内存上限、I/O 带宽按组记账，超限就限流或 OOM 杀掉。
- **分层镜像——供给文件系统**：容器看到的根文件系统来自镜像，用 overlayfs 把多个只读层叠起来，顶层加一层可写薄层；删容器即扔可写层，镜像本身不变。

所以容器便宜：没有第二个内核、没有虚拟化开销，启动就是 fork 一个进程（毫秒级），密度可以高 VM 一个量级。代价同样直接：**所有容器共享宿主机内核**——隔离强度弱于 VM（内核漏洞即逃逸通道），且容器只能跑与宿主内核兼容的系统（Linux 机上跑 Windows 容器，底下其实垫了个 VM）。

## 镜像：分层与内容寻址

镜像（Image）是静态的交付物：一个分层的文件系统快照 + 启动元数据（入口命令、环境变量、端口声明）。两条机制让它高效：

- **分层复用**：每层是只读的增量 diff。`ubuntu` 基础层被一千个镜像共享，磁盘和传输都只存一份；Dockerfile 每条指令产出一层，**层可缓存**——构建时从上往下，某层输入没变就直接复用缓存（这就是把依赖安装写在拷贝源码之前的原因：源码天天变，依赖不常变）。
- **内容寻址**：层以内容哈希命名——与 03 篇 Git 的对象库同构，同样的不可变、可复用、可校验。

`docker build` 造镜像，`docker run` = 从镜像建可写层 + 配 namespace/cgroup + 启动入口进程。镜像与容器的关系，就是 03 篇里"类与实例"、进程与程序关系的又一次重演。

## 从 Dockerfile 到运行：一个最小实例

```dockerfile
FROM python:3.12-slim      # 基础层：复用别人发布的镜像
WORKDIR /app
COPY requirements.txt .    # 先拷依赖清单——它很少变
RUN pip install -r requirements.txt   # 依赖安装：被缓存的关键层
COPY . .                   # 源码最后拷——天天变，只重建这层
CMD ["python", "main.py"]  # 启动元数据，不产生层
```

层缓存的实操含义就在顺序里：**变化频率低的指令写前面**。改一行代码重新构建，前四层全部命中缓存、秒级完成；若把 `COPY . .` 写在依赖安装之前，每次改代码都连带重装依赖。Dockerfile 的写法就是对变化频率的排序。

运行时还有一块要单独安排：**数据**。容器删了，可写层就没了——数据库文件、用户上传必须放进**卷（Volume，宿主机目录挂进容器，生命周期与容器解耦）**。这是有状态服务容器化要掂量的第二件事（第一件是 IO 性能，见本篇末的边界）。

## 这套形状回应的约束

容器解决了工程交付的三个老问题：

1. **环境漂移**："我机器上能跑"——镜像把依赖、系统库、配置全部钉进交付物，开发机与生产跑同一个哈希。这正是 04 篇"不可变产物"要求的载体。
2. **交付物标准化**：不管什么语言、什么框架，交付物统一是镜像，启动统一是 `run`——CI/CD 流水线和编排系统只需懂一种形状。
3. **密度与弹性**：进程级启动速度让"按负载秒级伸缩"成为可能，这是云原生弹性的地基。

## 边界：编排与编外

容器只解决单机的打包与隔离。成百上千个容器跨机器调度、故障自愈、服务发现，是**编排**层的事——Kubernetes 的标准做法是给集群一个"期望状态"声明（要几个副本、什么镜像），控制器持续把现实收敛到声明。编排的逻辑母体仍然是本篇：副本重建依赖镜像不可变，资源调度依赖 cgroup 记账。

也有编外不适用的场景：强状态、强 IO 性能的负载（数据库）放进容器要掂量——可写层文件系统有开销、容器漂移与数据持久存在张力；安全强隔离场景（多租户不可信负载）往往需要 VM 级别的边界。容器是默认答案，不是万能答案。
