# Git 版本控制

## 核心定义：内容寻址的对象库 + 三个指针游戏

Git 的本质常被教程埋掉：它不是一个"记录文件差异"的工具，而是一个**内容寻址的对象数据库**，版本历史是建在库上的指针结构。理解了这个，所有命令都是推论。

对象库里只有四种对象，全部以内容的 SHA-1 哈希作为键：

- **blob**：一个文件的内容（不含文件名）；
- **tree**：一个目录——一组"名字 → blob/tree 哈希"的条目；
- **commit**：指向一个根 tree + 零到多个父 commit + 作者/时间/说明；
- **tag**：给某个 commit 贴的标签。

内容寻址带来两个直接推论：相同内容只存一份（两个目录里的同内容文件共享 blob）；**任何对象不可变**——改一个字节就换哈希换身份，历史因此天然防篡改。commit 沿父指针连成一条**有向无环图（DAG）**，这就是"历史"的全部。

```text
commit C3 ──parent──► commit C2 ──parent──► commit C1
   │                     │
   ▼                     ▼
 tree T3                tree T2 ──► blob（文件内容）
   │
   └──► tree（子目录）──► blob
```

## 分支、HEAD、暂存区：全是指针

- **分支** = 一个指向 commit 的可移动指针，存成文件只有 41 字节。建分支零成本——这是 Git 工作流自由的根基。
- **HEAD** = 指向"当前分支"的指针（指针的指针）。`git checkout dev` 只是把 HEAD 挪到 dev。
- **提交** = 建一个新 commit（父指针指向旧 HEAD 所指），然后把当前分支指针挪到新 commit。分支"前进"就是指针搬家。
- **暂存区（index）** = 下一个 tree 的装配台：`git add` 把工作区文件做成 blob 入库、登记进暂存区；`git commit` 把暂存区快照成 tree、挂进 commit。它让你把一团改动拆成几个语义独立的提交。

## merge 与 rebase：合并的两种历史观

两条分支要合拢，Git 给两种机制，区别不在结果代码（通常一样），在**留下的历史形状**：

- **merge**：新建一个有两个父 commit 的合并节点，两条分支的历史原样保留——历史是"真实发生过什么"的档案。
- **rebase**：把本分支的提交逐个**复制**成新提交、嫁接到目标分支最新点之后——历史变成一条直线，假装你一直在最新基础上开发。代价：rebase 产生的是新对象（新哈希），**已经推送出去的提交绝不能再 rebase**——别人手里的旧哈希会和你改写后的历史分裂。这就是"rebase 不碰公共历史"铁律的机制根源。

**冲突的机制**：合并时两边改了同一文件的同一区域，Git 无法自动裁决——在文件里留下 `<<<<<<<`、`=======`、`>>>>>>>` 标记，把裁决权交还给人。冲突不是故障，是"机器不替你判断语义"的诚实；解决 = 手工选定内容 → add → 完成合并。

**reset 与 revert 的分工**也由历史观推出：撤销已推送的提交用 `revert`——新建一个"反向操作"的提交，历史只增不改，安全；`reset` 是把分支指针移回旧提交——改写历史，与 rebase 同受公共历史铁律约束。

## 分布式：每个克隆都是全量档案

Git 的分布式不是"功能"而是结构：克隆即完整复制对象库与全部历史，本地可以提交、建分支、查日志，全程离线；`push`/`pull` 只是两个库之间按哈希对账、互传缺的对象。没有一个"中心服务器"在概念上必需——GitHub 只是大家约定的那台。对照集中式（SVN）：历史只在服务器，本地是某个版本的裸拷贝——断网即停工，单点即风险。

## 回到工程问题

版本控制回应的约束是 01/02 篇的延续：多人同时改同一份代码 + 需要随时回答"上周这行为什么这样"。Git 的解法是**不可变对象 + 移动指针**：任何时刻的状态可精确重建（检出任意 commit），协作冲突被限制在合并节点上显式处理。日常命令（add/commit/branch/merge）都是这个模型的外壳；遇到困惑时回到对象图想一遍，答案几乎总在那里。
