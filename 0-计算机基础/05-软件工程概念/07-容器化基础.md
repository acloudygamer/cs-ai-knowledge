# 容器化基础

## 定义

容器化是将应用及其全部依赖打包为轻量级、可移植的运行时单元的技术，通过操作系统级虚拟化实现进程级隔离。容器与虚拟机的本质区别是：虚拟机虚拟化硬件（提供"机器"），容器虚拟化操作系统（提供"进程"）。

**归约内核**：容器的本质是**进程 + 文件系统隔离**。Linux namespace 隔离进程视图，cgroups 限制资源使用，overlayfs 提供分层文件系统。三者组合使容器成为轻量级的"虚拟机"。

## 数学模型

### 容器启动时间模型

容器启动时间由以下因素决定：

$$
T_{start} = T_{pull} + T_{create} + T_{run}
$$

其中：
- $T_{pull}$：镜像拉取时间，取决于镜像大小和网络带宽
- $T_{create}$：容器创建时间，约 100-500ms（cgroup/namespace 配置）
- $T_{run}$：应用启动时间，取决于应用本身

相较于虚拟机（需启动完整 Guest OS，数分钟级），容器启动快 100-1000 倍。

### 镜像层存储效率

镜像层共享使存储空间大幅节省。设 $n$ 个镜像，各自大小为 $S_i$，共享层大小为 $L$：

$$
Storage_{with\_share} \approx \max(S_i) + \sum layer_i
$$

实际中，10 个基于 alpine 的镜像可能只占用 ~5MB 而非 10 × ~5MB。

### cgroups 资源限制公式

cgroups 通过层级控制组限制资源使用：

| 资源 | 限制参数 | 计算公式 |
|------|----------|----------|
| CPU | cpu.cfs_quota_us / cfs_period_us | $\text{CPU share} = \frac{\text{quota}}{\text{period}}$ |

若 quota=50000, period=100000，则 CPU 上限为 0.5 核。

### namespace 隔离度量的数学表示

Linux 6 种 namespace 的隔离维度：

| Namespace | 隔离内容 | 形式化 |
|-----------|----------|--------|
| PID | 进程树 | $PID_{container} \neq PID_{host}$ |
| Network | 网络栈 | $\text{NetIfs} \subset \text{HostIfs}$ |
| Mount | 文件系统视图 | $M_{container} \neq M_{host}$ |
| User | 用户 ID 映射 | $UID_{container} \in U_{mapped}$ |
| UTS | 主机名/域名 | $hostname_{container} \neq hostname_{host}$ |
| IPC | 进程间通信 | $IPC_{container} \cap IPC_{host} = \emptyset$ |

## 数据流

<pre>
Dockerfile                          构建上下文                      Docker Daemon                     镜像存储                      容器实例
   │                                   │                               │                               │                              │
   │─── 指令序列 ────────────────────►│                               │                               │                              │
   │      (层定义)                     │                               │                               │                              │
   │                                   │─── 上下文发送 ─────────────►│                               │                              │
   │                                   │      (tar 归档)              │                               │                              │
   │                                   │                               │─── 逐层构建 ───────────────►│                              │
   │                                   │                               │◄─── 镜像 ID ───────────────│                              │
   │                                   │                               │                               │─── pull/checkout ─────────►│
   │                                   │                               │                               │◄─── 文件系统 ─────────────│                              │
   │                                   │                               │◄─── create+start ─────────│                              │
   │                                   │                               │                               │◄─── 容器进程 ────────────│
</pre>

**数据形态变换链路**：

1. `Dockerfile（文本）` → `指令解析` → `层构建计划`
2. `层构建计划` → `上下文打包（tar）` → `流传输`
3. `Dockerfile 指令` → `执行器（docker build）` → `只读镜像层`
4. `只读镜像层` → `镜像注册` → `可共享镜像`
5. `镜像 + 可写层` → `容器创建` → `容器层（Copy-on-Write）`
6. `容器层` → `进程启动` → `运行中的应用`

## 机制

### 单进程模型的设计约束

单进程模型（PID 1 是应用主进程）的约束来自**容器生命周期与进程生命周期绑定**：
- 容器设计哲学：容器 = 应用 + 运行环境
- PID 1 退出 → 容器退出（exit code 即容器 exit code）

违反此约束（多进程容器，如 systemd）会导致：
- 主进程无法监控子进程生命周期
- 信号传播问题：SIGTERM 只发给 PID 1
- 容器退出时子进程成为孤儿（orphan）

### 无状态容器的实现约束

无状态容器要求**容器内容不可变**，配置通过外部注入。实现方式：
1. **环境变量**：运行时注入配置
2. **挂载卷**：数据持久化到宿主机
3. **配置映射（ConfigMap/Secret）**：Kubernetes 模式

违反此约束的后果：**重建后状态丢失**。

### 最小镜像的工程价值

| 维度 | debian (活镜像) | alpine (最小) |
|------|----------------|--------------|
| 镜像大小 | ~120MB | ~5MB |
| 攻击面 | 数千包 | 数百包 |
| 拉取时间 | 10s+ | <1s |

### 容器 vs 虚拟机的隔离边界

容器通过 Linux namespace 实现隔离，虚拟机通过硬件虚拟化（Intel VT-x / AMD-V）实现更强隔离。容器的隔离边界是进程，虚拟机是硬件。

### Copy-on-Write 的写时复制语义

OverlayFS 的层结构：

```
Upper (可写层)     ← 容器修改写入此处
Middle (分界线)
Lower1 (镜像层1)   ← 共享只读
Lower2 (镜像层2)
```

写操作触发 **COW**：从 lower 层复制文件到 upper 层，然后修改。读操作直接读 lower 层（未被修改的文件）。

### 容器网络的命名空间隔离

容器的网络命名空间创建独立的：
- **网络接口**：veth pair 一端在容器，一端在 host
- **iptables 规则**：独立的 NAT 和 filter 规则
- **路由表**：独立的默认网关
- **端口空间**：独立的 0-65535 端口绑定

## 参考存根

```dockerfile
FROM alpine
COPY app /app
CMD ["app"]

# 多阶段构建示例
FROM golang:1.21 AS builder
WORKDIR /src
COPY . .
RUN go build -o app

FROM alpine
COPY --from=builder /src/app /app
CMD ["/app"]
```

```bash
# 容器资源限制
docker run --memory="256m" --cpus="0.5" app:latest

# 查看容器资源使用
docker stats
```

```yaml
# Kubernetes Pod 资源配额
apiVersion: v1
kind: Pod
metadata:
  name: app
spec:
  containers:
  - name: app
    image: app:v1
    resources:
      limits:
        memory: "256Mi"
        cpu: "500m"
```
