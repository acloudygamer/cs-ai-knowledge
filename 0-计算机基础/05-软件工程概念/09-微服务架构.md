# 微服务架构

> **版本基准**: universal

## 定义

微服务架构是将单体应用拆分为一组自治服务的风格，每个服务独立部署、拥有独立数据存储，通过轻量级协议通信。自治性（Autonomy）是核心：每个服务从开发到部署的生命周期完全独立，服务间通过接口交互而非共享内部状态。

**归约内核**：微服务的本质是**按业务边界划分的分布式系统**。每个服务是一个独立的进程，服务间通过网络通信而非函数调用。这将进程内调用转换为进程间通信（IPC），引入了网络的不确定性和分布式系统的复杂性。

## 数学模型

### 端到端延迟模型

服务间调用延迟累加：

$$
T_{e2e} = \sum_{i=1}^{n} T_i + \sum_{j=1}^{n-1} L_j
$$

其中 $T_i$ 是各服务处理时间， $L_j$ 是网络通信延迟（通常 1-10ms 同机房，10-100ms 跨地域）。

**尾延迟（Tail Latency）问题**：调用链深度增加导致尾延迟指数增长。对于 $n$ 个串联服务，每个服务的 p99 延迟为 $t_{p99}$ ：

$$
P(T_{e2e} > t_{p99}) \approx 1 - \prod_{i=1}^{n} P(T_i < t_{p99}) \approx n \times (1 - 0.99)
$$

对于 10 个服务，p99 尾延迟概率从 1% 上升到 ~10%。

### 可用性与调用链深度

设每个服务的可用性为 $A_i$ （如 99.9%），串联服务的整体可用性：

$$
A_{total} = \prod_{i=1}^{n} A_i
$$

对于 5 个 99.9% 可用性的服务， $A_{total} = 0.999^5 \approx 99.5\%$ 。

**可用性与宕机时间对应**：

| 可用性 | 年宕机时间 |
|--------|-----------|
| 99% | 3.65 天 |
| 99.9% | 8.76 小时 |
| 99.99% | 52.6 分钟 |
| 99.999% | 5.26 分钟 |

### 分布式事务的 CAP 约束

微服务架构下，跨服务的数据一致性受 CAP 定理约束：

$$
Consistency + Availability = 1 \quad \text{（在分区发生时）}
$$

服务自治要求每个服务拥有独立数据库，这使跨服务事务成为分布式事务，必须在以下之间 tradeoff：
- **一致性（CP）**：放弃可用性，分区时拒绝请求
- **可用性（AP）**：放弃强一致，接受最终一致

### 熔断器的状态机模型

熔断器（Circuit Breaker）实现有限状态机：

$$
M = (States, Events, Transitions)
$$

$$
States = \{CLOSED, OPEN, HALF\_OPEN\}
$$

$$
Transitions: \begin{cases}
CLOSED \xrightarrow{failures \geq threshold} OPEN \\
OPEN \xrightarrow{timeout} HALF\_OPEN \\
HALF\_OPEN \xrightarrow{success} CLOSED \\
HALF\_OPEN \xrightarrow{failure} OPEN
\end{cases}
$$

## 数据流

<pre>
API Gateway                          服务 A                          服务 B                          数据库 A                        数据库 B
    │                                 │                               │                               │                               │
    │─── 路由分发 ──────────────────►│                               │                               │                               │
    │      (请求拆分)                  │                               │                               │                               │
    │                                 │─── 同步调用 ───────────────►│                               │                               │
    │                                 │      (HTTP/gRPC)             │                               │                               │
    │                                 │                               │─── 查询 ─────────────────────►│                               │
    │                                 │                               │◄─── 结果 ────────────────────│                               │
    │                                 │◄─── 聚合结果 ──────────────│                               │                               │
    │◄─── 响应组装 ──────────────────│                               │                               │                               │
    │                                 │                               │                               │                               │
    │                                 │─── 异步事件 ────────────────────────────────────────────────────────────────────────────►│
    │                                 │      (消息队列)                                       │                               │
</pre>

**数据形态变换链路**：

1. `客户端请求` → `API Gateway`
2. `Gateway` → `路由 + 负载均衡`
3. `路由后请求` → `服务 A 调用（同步 HTTP/gRPC）`
4. `服务 A` → `服务 B 调用（同步）` + `查询数据库 A`
5. `服务 B` → `查询数据库 B`
6. `结果聚合` → `Gateway 响应组装`
7. `业务完成事件` → `消息队列（异步）`
8. `消息消费者` → `其他服务处理`

## 机制

### 服务自治的约束条件

服务自治要求每个服务在以下维度独立：
- **部署自治**：服务可独立部署，不依赖其他服务部署顺序
- **数据自治**：每个服务拥有独立数据库，跨服务不直接共享数据
- **技术栈自治**：服务可选择不同技术栈

违反数据自治的后果是**架构腐蚀**：服务间直接共享数据库导致耦合，丧失独立部署能力。

### API 优先设计的契约约束

API 优先（Contract-First）设计的约束是：
- API 契约在实现前定义
- 契约变更需要版本管理
- 向后兼容必须保证

违反此约束导致**消费者破碎（Consumer Drift）**：API 变更破坏已有消费者。

### 同步调用的级联失败风险

同步调用链过长的风险是**级联失败（Cascading Failure）**：下游服务故障导致上游服务阻塞，阻塞累积导致整个调用链崩溃。

解决方案：
- **超时（Timeout）**：设置调用超时，避免无限等待
- **熔断器（Circuit Breaker）**：快速失败，拒绝请求
- **限流（Rate Limiting）**：保护下游，防止过载

### 分布式事务模式的选择

| 模式 | 一致性 | 复杂度 | 补偿机制 | 适用场景 |
|------|--------|--------|----------|----------|
| 2PC | 强一致 | 高 | 自动回滚 | 跨库写（极少） |
| Saga | 最终一致 | 中 | 逆向操作 | 长流程业务 |
| TCC | 最终一致 | 高 | Try/Confirm/Cancel | 高性能要求 |
| 可靠消息 | 最终一致 | 中 | 消息幂等 | 异步解耦 |

### 服务发现的一致性约束

服务发现有两种模式：
- **客户端发现**：客户端查询服务注册表（如 Eureka），直接请求目标实例
- **服务端发现**：客户端请求负载均衡器（如 NGINX），由负载均衡器查询注册表

**一致性约束**：服务注册表必须保证**最终一致性**——服务实例变化时，所有消费者最终都能感知到变化。

### 追踪的上下文传播

分布式追踪通过 **Trace ID** 串联跨服务请求：

$$
\text{Trace} = \bigcup_{i=1}^{n} \text{Span}_i, \quad \text{Span}_i = (service_i, start_i, end_i, parent_{i-1})
$$

```go
type UserServer struct{}
func (s *UserServer) GetUser(ctx context.Context, req *pb.GetUserRequest) (*pb.User, error) {
    return &pb.User{Id: req.Id, Name: "example"}, nil
}

// 服务发现示例（客户端发现）
func discover(service string) ([]string, error) {
    instances, _ := consulClient.Catalog().Service(service, "")
    addrs := make([]string, len(instances))
    for i, inst := range instances {
        addrs[i] = fmt.Sprintf("%s:%d", inst.ServiceAddress, inst.ServicePort)
    }
    return addrs, nil
}
```
