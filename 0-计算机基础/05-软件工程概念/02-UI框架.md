# UI框架

## 定义

UI框架是构建用户界面的组件化工具集，通过声明式语法描述视图状态，由框架运行时将状态描述转换为实际像素。核心抽象是**状态到视图的单向数据流**：给定状态 S，框架总是渲染相同的视图 V，不存在状态同步混乱。

**归约内核**：UI 框架的本质是**状态机的可视化描述**。组件是状态转换函数 $V = f(S)$，框架负责当 $S$ 变化时调用 $f$ 并将结果同步到真实 DOM。这将 UI 开发从"命令式 DOM 操作"转变为"声明式状态描述"。

## 数学模型

### 帧率模型

UI 渲染性能由帧率决定，帧率上限由 VSync（垂直同步）决定，通常为 60Hz（16.67ms/帧）或 120Hz（8.33ms/帧）：

$$
FPS = \frac{1}{T_{frame}} \leq \frac{1}{T_{vsync}}
$$

单帧可用时间：

$$
T_{frame} = T_{layout} + T_{paint} + T_{composite}
$$

任何一阶段超时都会导致掉帧，用户感知为界面卡顿。

### 虚拟 DOM 复杂度

真实 DOM 操作代价高昂，因为每次属性修改都可能触发重排（reflow）和重绘（repaint）。虚拟 DOM 的核心洞察是：**将多次微小的 DOM 修改合并为一次批量更新**。

设组件树有 $N$ 个节点，直接比较两棵树的时间复杂度为 $O(N^3)$（每个节点与另一树的每个节点比较）。React 启发式优化基于两个假设：

1. 两个组件树之间的不同节点数量远小于总节点数
2. 组件的更新遵循结构性规则：相同类型的组件产生相似的结构

这将比较降至 $O(N)$——同层比较，避免跨层级比较。

**Diff 算法的精确复杂度**：设两棵树同层节点数为 $n$，同层比较的最坏情况是 $O(n)$。设树深度为 $d$，总复杂度为 $O(d \times n)$。实际应用中 $n$ 是单层节点数，$d$ 是树深度，总复杂度远低于 $O(N^3)$。

### 响应式追踪开销

响应式框架（Vue/Svelte/Solid）的追踪开销公式：

$$
T_{update} = O(\text{affected\_nodes}) = O(\text{dependencies} \times \text{observers})
$$

依赖追踪越细粒度，初始开销越大，但运行时精确通知开销越小。Vue 3 的 Proxy 方案将追踪从"访问时建立依赖"改为"设置时触发更新"，减少了不必要的依赖建立。

### 组件状态转移的有限状态自动机

组件生命周期可建模为有限状态自动机：

$$
M = (Q, \Sigma, \delta, q_0, F)
$$

其中：
- $Q = \{\text{UNMOUNTED}, \text{MOUNTING}, \text{MOUNTED}, \text{UPDATING}, \text{UNMOUNTING}\}$
- $\Sigma = \{\text{props change}, \text{state change}, \text{forceUpdate}, \text{parent unmount}\}$
- $\delta: Q \times \Sigma \to Q$ 是状态转移函数

组件状态机确保了 UI 更新的可预测性——任何状态变化都触发确定性的状态序列。

## 数据流

<pre>
组件声明                      框架运行时                      渲染引擎                      屏幕像素
    │                           │                            │                            │
    │─── JSX/Template ─────────►│                            │                            │
    │      (声明式描述)           │                            │                            │
    │                           │─── 虚拟DOM ──────────────►│                            │
    │                           │      (内存对象树)           │                            │
    │                           │                            │─── 绘制命令 ──────────────►│
    │                           │                            │      (光栅化指令)           │
    │                           │                            │                            │─── 像素更新
    │                           │◄─── Diff 结果 ────────────│                            │
    │                           │      (最小变更集)           │                            │
</pre>

数据形态变换链路：

1. `声明式语法（JSX/Template）` → `组件函数调用/渲染函数`
2. `组件函数` → `虚拟 DOM 节点（Plain Object）`
3. `新虚拟 DOM + 旧虚拟 DOM` → `Diff 算法` → `变更操作列表`
4. `变更操作列表` → `真实 DOM API 调用` → `浏览器重排/重绘`
5. `重排/重绘` → `GPU 合成` → `屏幕像素更新`

**关键不变式**：虚拟 DOM 的树结构在每次更新前后都必须满足 —— 父节点包含子节点引用，根节点是唯一的。

## 机制

### 组件封闭性的约束意义

组件状态私有的约束来自**可组合性需求**：若组件可被外部任意修改，则组件间的交互将形成难以推理的网状依赖。

约束表述：**组件是一个纯函数** $V = render(S)$，其中 $S$ 是组件的内部状态与 props 的并集，$V$ 是视图描述。对 $S$ 的修改只能通过框架提供的有限方式（setState/dispatch）进行。

违反此约束的后果是**外部状态耦合**：外部直接修改组件内部状态（如直接操作 ref），组件的自我描述性被破坏，框架无法追踪状态变化，导致视图与状态不一致。

**纯函数的数学保证**：设 $S_1, S_2$ 为相同的状态值，若 $render(S_1) = render(S_2)$，则组件是引用透明的，状态变化是 UI 更新的唯一来源。这保证了组件行为的可测试性和可预测性。

### 单向数据流的执行语义

单向数据流不是简单的"数据从父到子流动"，其执行语义是：

1. **状态变化触发**：状态变更（如用户点击）产生 Action
2. **Action 流转**：Action → Dispatcher → Store → Reducer → New State
3. **新状态触发渲染**：新状态触发组件重新计算，产生新视图

此环路的意义是**时间旅行调试的可能性**：因为状态变化是纯函数且可序列化，任何时刻的状态都可重建。Redux DevTools 正是基于此实现。

### 声明式优先的认知价值

声明式（描述"什么"而非"如何"）的认知价值在于**复杂度转移**：将"如何更新视图"的控制流复杂度转移给框架，开发者只需描述"给定状态，视图是什么样"。

约束表述：框架是视图更新的**唯一权威**。任何直接 DOM 操作都绕过框架的 diff 机制，可能导致框架维护的视图描述与真实 DOM 不一致。

### 渲染模式对比的机制差异

| 框架 | 渲染方式 | 更新粒度 | 框架开销 | 适用场景 |
|------|----------|----------|----------|----------|
| React | 虚拟 DOM diff | 组件级 | 中等（Fiber 架构） | 中大型应用 |
| Vue | 响应式追踪 | 响应式依赖级 | 较低（自动追踪） | 快速开发 |
| Svelte | 编译时代码生成 | 语句级 | 极低（无运行时） | 小型应用/嵌入式 |
| Solid | 编译时精确代码 | 语句级 | 零（无虚拟 DOM） | 高性能需求 |

**React Fiber 的机制**：Fiber 将渲染工作拆分为可中断的小单元（Fiber Node），每次处理一个 Fiber 的更新。优先级机制允许高优先级更新（如用户输入）打断低优先级更新（如网络数据到达）。这是 React 16+ 实现异步渲染的基础。

**Fiber 调度的时间片模型**：

$$
T_{slice} = 16.67ms \quad \text{（一帧的时间预算）}
$$

若工作未在时间片内完成，Fiber 会中断并让出主线程，允许浏览器处理用户输入等高优先级任务。

### 响应式与订阅发布模式的数学关联

Vue/Svelte 的响应式系统本质上是一个**发布-订阅系统**，其依赖追踪可形式化为：

$$
\text{Dep} = \{(d, \text{subscribers}) \mid d \in \text{DataProperties}\}
$$

当属性 $d$ 被读取时（getter），当前活跃的 watcher 被添加到 $\text{subscribers}(d)$。当 $d$ 被写入时（setter），所有 $\text{subscribers}(d)$ 被通知更新。

这保证了**最小更新原则**：只有真正依赖变化属性的组件才会重新渲染，而非全局刷新。

## 参考存根

```jsx
// React 函数组件（Hooks）- 状态管理与副作用
const Counter = ({ initialCount = 0 }) => {
    const [count, setCount] = useState(initialCount);

    useEffect(() => {
        document.title = `Count: ${count}`;
    }, [count]);

    return (
        <button onClick={() => setCount(c => c + 1)}>
            Count: {count}
        </button>
    );
};
```

```html
<!-- Vue 响应式声明 -->
<script setup>
import { ref, computed, watch } from 'vue'

const count = ref(0)
const doubled = computed(() => count.value * 2)

watch(count, (newVal) => {
    console.log(`count changed to ${newVal}`)
})
</script>
```
