# CI/CD

## 核心定义：把集成与交付从仪式变成流水线

CI（Continuous Integration，持续集成）：每次代码合入都自动构建并跑测试。CD（Continuous Delivery/Deployment，持续交付/部署）：构建产物自动走到可发布状态，甚至自动上线。

它们回应的约束是手工时代的两个老大难：

- **集成地狱**：各人在自己的分支上开发数周，合并那天发现接口全对不上——冲突随分支寿命指数增长。CI 的解法是频率：每天合入主干，冲突在只有几行时就暴露。
- **发布即仪式**：手工发布的步骤存在文档和人的脑子里，每次执行都是一次即兴操作——漏一步、顺序错一步就是事故。CD 的解法是**流水线即代码**：发布过程写成脚本存进仓库，每次执行完全相同。

## 流水线的阶段

一条典型流水线是阶段的串联，前一阶段失败，后一阶段不启动——**快失败（fail fast）**是省钱的形状：

```text
提交 push
  → 构建（编译、打包）           —— 分钟级，拦住"编译不过"
  → 快速测试（单元 + 静态检查）    —— 拦住逻辑与风格错误
  → 慢速测试（集成、E2E 冒烟）     —— 拦住接缝问题（见 02 的金字塔）
  → 产出不可变产物（jar、镜像）    —— 只构建一次
  → 部署到预发环境 → 验收         —— 与生产同构的环境
  → 生产发布                     —— 交付（手动闸门）或部署（自动）
```

**不可变产物**是流水线的地基：同一个产物（同一个镜像、同一个包，哈希一致）依次流过预发和生产。反面教材是"每个环境各自从源码构建"——源码相同不等于产物相同（依赖漂移、编译器版本差异），你在预发验证的东西和上线的东西不是同一个，验证就失效了。这条原则直接解释了下一篇容器的价值：镜像是不可变产物的最彻底形态。

## 部署策略：让发布不再是悬崖

即使流水线全自动，"切换"这一下仍有风险。工程上的缓释手段：

- **滚动更新**：分批替换实例，任何时刻都有旧版本在服务；
- **蓝绿部署**：新旧两套完整环境并存，切流量即切换，回滚=切回去；
- **金丝雀（灰度）**：先放 1% 流量到新版本，指标正常再逐步放大——把"全有或全无"变成"按比例的实验"。

三者共同的机制思想：**把一次离散的切换摊成一段可观察、可中止的过程**。配合前滚修复（fix forward）与快速回滚的预案，发布从高危仪式退化为日常操作。

流水线的物理形态是仓库里的配置文件（`.github/workflows/`、`.gitlab-ci.yml`）——"流水线即代码"的字面含义：构建过程与代码同源、同评审、同版本。注意一个边界：**密钥不进仓库**——部署凭证放 CI 系统的 secrets 存储，构建时注入为环境变量；写进配置文件的密码等于公开（09 篇的最小权限在此落地）。

## 与前后篇的连接

CI/CD 站在前三篇的肩膀上：02 的测试金字塔是流水线的核心关卡（没有可靠测试，自动化只会自动发布 bug）；03 的 Git 模型是流水线的触发器和原料（push 触发、tag 标记发布点）；下一篇 05-容器化基础 的产物（镜像）正是流水线上流淌的那个不可变对象。GitOps 把闭环再推一步：环境的期望状态也存进 Git，部署系统持续把现实收敛到仓库里的声明——变更历史的终点也是运维的起点。
