# 缓存与存储层次

## 一、层级的必然性：速度-容量-成本三角与局部性赌注

### 1. 不可约约束：三种物理量不可兼得

没有一种存储介质能同时满足快、大、便宜。静态随机存取存储器（SRAM）每比特由 6 个晶体管构成双稳态触发器，翻转极快但面积昂贵、静态漏电高；动态随机存取存储器（DRAM）每比特仅 1 个晶体管加 1 个电容，密度高出数个量级，但电容充放电、破坏性读出后的写回刷新与行列译码，把访问延迟钉死在百拍量级。

| 层级 | 介质 | 典型容量 | 访问延迟 | 延迟折算（@2.6 GHz） |
| --- | --- | --- | --- | --- |
| L1d | SRAM | 32 ~ 48 KB / 核 | 4 ~ 5 周期 | ≈ 1.5 ns |
| L2 | SRAM | 512 KB ~ 2 MB / 核 | 12 ~ 14 周期 | ≈ 5 ns |
| L3 (LLC) | SRAM | 16 ~ 64 MB / 共享域 | 40 ~ 50 周期 | ≈ 15 ~ 20 ns |
| 主存 | DRAM | 数十至数百 GB | 约 260 周期 | ≈ 100 ns |
| NVMe SSD | NAND Flash | 数百 GB 至 TB | 约 260,000 周期 | ≈ 100 µs |
| HDD | 磁介质 | TB 级 | — | ≈ 10 ms |

相邻两级的延迟差约一个数量级（DRAM 到 SSD 则跳变三个数量级）。当任何单一介质都无法兼顾容量与延迟，唯一出路是**多级漏斗过滤**：每一层挡下绝大多数访问，只让极少数未命中（Miss）请求向下穿透。

### 2. 局部性：层级成立的统计赌注

漏斗过滤生效的前提是程序的访存地址分布高度倾斜，即具备**局部性（Locality）**：

* **时间局部性（Temporal Locality）**：刚访问过的数据大概率很快再次被访问，因此值得驻留在高层级 SRAM。一旦崩溃（如链表指针追逐、图随机游走、大型哈希表探测），每次访存都将穿透至 DRAM，CPU 停顿百纳秒。
* **空间局部性（Spatial Locality）**：相邻地址大概率随后被访问，因此缓存以 **64 字节缓存行（Cache Line）** 为最小搬运粒度，一次未命中顺带取回邻接数据。一旦崩溃（如结构体中冷热字段混排、大跨步跳跃访问），64 字节中仅有几个字节被消费，既污染缓存容量又浪费总线带宽。

### 3. AMAT：层级过滤的递推账本

把 L1 → L2 → L3 → 主存看作级联漏斗，记 $\ell_i$ 为到达第 $i$ 层必定支付的硬件增量延迟， $M_i$ 为第 $i$ 层的局部未命中率（进入该层的请求中未能命中的比例）。平均内存访问时间（AMAT）按请求下穿的概率层层累加：

$$\text{AMAT} = \underbrace{\ell_1}_{\text{必达 L1}} + \underbrace{M_1 \ell_2}_{\text{穿透至 L2}} + \underbrace{M_1 M_2 \ell_3}_{\text{穿透至 L3}} + \underbrace{M_1 M_2 M_3 \ell_{\text{mem}}}_{\text{穿透至主存}}$$

**算例**（以 $\ell_1 = 4, \ell_2 = 12, \ell_3 = 40, \ell_{\text{mem}} = 260$ 周期； $M_1 = 5\\%, M_2 = 10\\%, M_3 = 20\\%$ 计）：

$$\text{AMAT} = 4 + (0.05 \times 12) + (0.005 \times 40) + (0.001 \times 260) = 4 + 0.6 + 0.2 + 0.26 = \mathbf{5.06 \text{ 周期}}$$

只要三级漏斗将穿透至 DRAM 的全局概率压在 $0.1\\%$（ $M_1 M_2 M_3 = 0.001$），260 周期的 DRAM 鸿沟就会被稀释为平均每次访存不到 0.3 周期的尾项。注意：AMAT 仅度量**空载下的平均延迟**；当 $M_1 M_2 M_3$ 升高导致并发未命中请求越过内存控制器带宽上限时，排队效应会使实际 $\ell_{\text{mem}}$ 呈指数级膨胀（详见「延伸」）。

## 二、信息投影流：地址切分、VIPT 与 SRAM 物理阵列

### 1. 页内偏移恒等区与 VIPT 并行

CPU 核发出的访存指令携带 48 位虚拟地址（VA），而缓存最终必须用物理地址（PA）校验数据归属。在 4 KB 标准页（ $2^{12} = 4096$ 字节）下，MMU/TLB 只改写高 36 位页号，**低 12 位页内偏移（Page Offset）在翻译前后原封不动**：

$$\text{VA}[47:0] = \text{VPN} \\;\Vert\\; \text{Page Offset}[11:0] \quad\xrightarrow{\text{TLB}}\quad \text{PA}[47:0] = \text{PPN} \\;\Vert\\; \text{Page Offset}[11:0]$$

L1 缓存利用这 12 位恒等区实现 **VIPT（Virtually Indexed, Physically Tagged，虚拟索引、物理标签）**：用无需翻译的 `VA[11:0]` 直接去 SRAM 阵列中定位组（Set）与字节偏移，与此同时将 `VA[47:12]` 送入 TLB 翻译出物理页号 PPN（Physical Page Number）；两条硬件路径并行推进，最终在比较器（Comparator）处汇合比对 Tag。L2 与 L3 位于 L1 之后，接收的已是翻译完备的 PA，故直接采用 **PIPT（物理索引、物理标签）**。

### 2. L1 / L2 / L3 跨层位标尺与组相联演进

缓存行大小固定为 64 字节，吃掉最低 6 位 `Bit[5:0]` 作为块内偏移（Block Offset）。在 L1 中，为保证 Set Index 不越过 `Bit 11` 的页边界（否则选组必须等待 TLB 翻译，VIPT 并行破产），留给 Set Index 的位数被死死锁在 `Bit[11:6]`（6 bits），即 **L1 最多只能有 $2^6 = 64$ 个组（Sets）**。

因此，现代 x86 处理器要扩大 L1 容量，**不能增加组数，只能增加每组的路数（Ways）**：

* **32 KB L1d**（Skylake / Zen 1~3）：64 Sets × **8 Ways** × 64B
* **48 KB L1d**（Sunny Cove ~ Golden Cove / Zen 5）：64 Sets × **12 Ways** × 64B

当请求在 L1 未命中、携物理地址下穿至容量更大的 L2 和 L3 时，组数成倍扩张，**原本在 L1 中充当 Tag 的低位地址，在 L2 和 L3 中被逐级吞噬为 Set Index**（L3 还会先用全地址哈希选定切片 Slice，再取高位索引组）：

```text
48-bit 地址在三级缓存中的位段切分标尺（以 32KB L1 / 512KB L2 / 16MB L3 为例）：

       47                         20 19          15 14      12 11       6 5        0
      ┌─────────────────────────────┴──────────────┴──────────┼──────────┴──────────┐
  VA  │              虚拟页号 VPN [47:12] (送 TLB 翻译)        │   页内偏移 [11:0]   │
      └─────────────────────────────┬──────────────┬──────────┼──────────┬──────────┘
                                    ║ TLB 1拍译出 PPN [47:12]  │ (恒等直通)│
                                    ▼                         ▼          ▼
      ┌───────────────────────────────────────────────────────┬──────────┬──────────┐
  L1  │                  L1 Tag [47:12] (36 bits)             │Set [11:6]│Off [5:0] │ VIPT: 64 Sets × 8/12 Ways
      ├────────────────────────────────────────────┬──────────┴──────────┼──────────┤
  L2  │             L2 Tag [47:15] (33 bits)       │  L2 Set [14:6] (9b) │Off [5:0] │ PIPT: 512 Sets × 16 Ways
      ├─────────────────────────────┬──────────────┴─────────────────────┼──────────┤
  L3  │       L3 Tag [47:20] (28b)  │  Slice Hash + L3 Set [19:6] (14b)  │Off [5:0] │ PIPT: 多核切片哈希 + 组索引
      └─────────────────────────────┴────────────────────────────────────┴──────────┘

```

### 3. SRAM 阵列的物理形态：Tag Array 与 Data Array 分离

在硬件硅片上，缓存并非一张混装的大表，而是拆分为左右两块独立的 SRAM 宏单元：**Tag Array（标签阵列）** 与 **Data Array（数据阵列）**。以 8 路组相联 L1 为例，一次寻址的内部电路动作如下：

```text
                        VA [47:0]
                            │
        ┌───────────────────┼───────────────────────────────┐
        ▼ VPN [47:12]       ▼ Set Index [11:6]              ▼ Block Offset [5:0]
   ┌─────────┐        ┌───────────┐                         │
   │ dTLB 查表│        │6-to-64 译码│                         │
   └────┬────┘        └─────┬─────┘                         │
        │ PPN [47:12]       │ 字线 (Wordline) 激活第 k 组    │
        │                   ▼                               │
        │        【Tag Array: 64 Sets × 8 Ways】             │  【Data Array: 64 Sets × 8 Ways】
        │      Way 0           Way 1              Way 7     │     Way 0      Way 1         Way 7
        │   ┌────┬─────┐    ┌────┬─────┐       ┌────┬─────┐ │  ┌────────┐ ┌────────┐    ┌────────┐
      Set k │MESI│ Tag │    │MESI│ Tag │  ...  │MESI│ Tag │ │  │64B Line│ │64B Line│... │64B Line│
        │   │ 2b │ 36b │    │ 2b │ 36b │       │ 2b │ 36b │ │  └───┬────┘ └───┬────┘    └───┬────┘
        │   └─┬──┴──┬──┘    └─┬──┴──┬──┘       └─┬──┴──┬──┘ │      │          │             │
        │     │V≠I  │         │V≠I  │            │V≠I  │    │      ▼          ▼             ▼
        ├─────┼────►⊕         ├────►⊕            ├────►⊕    │   ┌──────────────────────────────┐
        │           ║               ║                  ║    │   │      8-to-1 路选通器         │
        │       (8 个 36-bit 硬件比较器并行比对)       ║    │   └──────────────┬───────────────┘
        │           ╚═══════════════╬══════════════════╝    │                  │ 命中路的 64B
        │                           ▼                       │                  ▼
        │                   ┌───────────────┐               │           ┌─────────────┐
```

* **水平选组，8 路齐出**：`Set Index[11:6]` 经译码器拉高第 $k$ 行的字线（Wordline），该组全部 8 个 Way 的 `[MESI 状态位 (2 bits) | Tag (36 bits)]` 在同一拍被同时读出。
* **8 路并行比对**：8 个独立的硬件比较器将读出的 8 个 Tag 与 TLB 刚刚译出的 `PPN[47:12]` 同时异或比对，并检查 MESI 状态不为 Invalid（I）。
* **路选通与字节裁剪**：唯一命中的那个比较器产生 Hit 信号，控制右侧 Data Array 的 8 选 1 路选通器导出对应 Way 的 64 字节缓存行，最后由 `Block Offset[5:0]` 控制 Byte MUX 夹出指令所需的 4 或 8 字节送入寄存器。

## 三、空间事务环：一次访存的硬件生命周期

以 Core 0 执行 `arr[0]++`（一次 Load 加一次 Store，目标行初始不在任何缓存中）为例，追踪请求在核心流水线、缓存缓冲器与主存之间的完整硬件闭环：

```text
  Core 0 执行单元 (AGU/ALU)
    │
    ├── Load arr[0] ──► ① L1d VIPT 查询 ──(Miss)──► 登记 MSHR (合并且限流)
    │                                                  │
    │   ┌──────────────────────────────────────────────┘ (携 PA 下穿)
    │   ▼
    │  ② L2 PIPT 查询 (Miss) ──► ③ L3 + 目录查询 (Miss，确认他核无副本)
    │                                                  │
    │   ┌──────────────────────────────────────────────┘
    │   ▼
    │  ④ 内存控制器向 DRAM 发 Burst 读 (8×64-bit 拍回 64B 缓存行)
    │   │
    │   ▼
    │  ⑤ 缓存行回填 L3/L2/L1，唤醒 MSHR ──► Byte MUX 夹出 4B 送入 ALU 完成 +1
    │
    └── Store 新值 ──► ⑥ 先入 Store Buffer (缓冲写) ──► ⑦ 指令退休且持 M 权限后刷入 L1d

```

1. **L1 Miss 与 MSHR 登记**：地址生成单元（AGU）算出 `arr[0]` 的 VA，L1d 并行查 TLB 与 Tag Array 后判定未命中。此时流水线不会原地锁死，而是将该缺失请求登记到 **MSHR（Miss Status Holding Register，缺失状态保持寄存器）**。
* **并发封顶與合并**：每个核心的 L1 MSHR 条目数有限（通常 10~16 个），决定了单核最多能同时在途挂起多少个缓存未命中（即内存级并行度 MLP 上限）。若后续指令紧接着访问 `arr[1]`（落在同一 64B 缓存行），MSHR 会直接将其合并（Coalesce）到同一个在途条目上，不会向下层发出第二次冗余请求。


2. **L2 与 L3 目录接力**：MSHR 携翻译好的物理地址向下请求 L2（PIPT 查询）；若再 Miss，则经片上网络（Ring 或 Mesh）发往共享 L3 切片。L3 在查找数据的同时，查询**一致性目录**以确认其他核心是否持有该行的脏副本。
3. **DRAM 突发取数与行回填**：确认全网无副本后，内存控制器向 DRAM 发起读取，通过一次突发传输（Burst，DDR4 BL8 或 DDR5 BL16）取回完整的 64 字节缓存行，沿途回填并解除 MSHR 挂起，目标 4 字节送入 ALU 完成加一。
4. **Store Buffer 异步提交**：ALU 算出的新值**绝不会当场直接写进 L1 Data Array**（因为此时指令尚未退休，若遭遇分支预测失败需要回滚）。新值与地址会先写入核内的 **Store Buffer（写缓冲器）**。直到该 Store 指令正式退休（Retire），且核心已通过一致性协议拿到该缓存行的独占写权限（Modified 状态），Store Buffer 才在后台将新值排空（Drain）写入 L1d 并将该行置脏（M）。

## 四、缓存包含策略与嗅探过滤器的演进

多核系统中每个核心拥有私有 L1/L2，共享 L3。这带来两个紧密绑定的架构问题：**其一，L1/L2 里的数据需不需要在 L3 里留底稿（包含策略）？其二，当某核请求一行数据时，如何免于向全网所有核心广播探针（嗅探过滤）？**

```text
  【包容式 Inclusive】               【非包容/排他 + 独立过滤器 (现代主流)】
   (如 Intel Skylake 桌面端)          (如 Intel Skylake-SP+ / AMD Zen 全系)

    ┌────────┐    ┌────────┐           ┌────────┐    ┌────────┐
    │Core0 L2│    │Core1 L2│           │Core0 L2│    │Core1 L2│  (L2 扩至 1~2MB)
    │ [LineA]│    │ [LineB]│           │ [LineA]│    │ [LineB]│
    └───┬────┘    └───┬────┘           └────────┘    └────────┘
        │ (必须留底稿)│                    ▲             ▲
        ▼             ▼                    │ (点对点探针) │
  ┌──────────────────────────┐       ┌─────┴─────────────┴────┐
  │       Shared L3          │       │ 独立 Snoop Filter /    │ (仅存 Tag+状态，
  │ [LineA] [LineB] [LineC]  │       │ Shadow Tags (占5~10%面积)│  精确记录行在何核)
  │ (L3 Tag 天然兼任过滤器)  │       ├────────────────────────┤
  └──────────────────────────┘       │   Shared L3 (Victim)   │
  代价: L3 约 30% 容量被副本吃掉     │  [LineC] [LineD] ...   │ (专存被 L2 踢出的行)
        且 L3 驱逐会反向作废 L1/L2   └────────────────────────┘

```

### 1. 包容式（Inclusive）：用容量税换取天然过滤器

经典 Intel 客户端架构（如 Skylake 桌面端）采用严格包容式：L1/L2 中的任何缓存行，必须在共享 L3 中留有一份副本。

* **收益（天然的嗅探过滤器）**：L3 的 Tag Array 就是全局目录。当某核发生 Miss 去查 L3 时，若 L3 未命中，硬件瞬间确知**没有任何核心的 L1/L2 持有该行**，直接去 DRAM 取数，零跨核广播。
* **代价（容量税与反向无效化）**：首先是容量浪费——若 8 核每核私有 L1+L2 共 576 KB，上层总计 4.6 MB 的数据必须在 16 MB 的 L3 中占坑，L3 凭空损失近 30% 的有效容量。更致命的是**反向无效化（Back-invalidation）**：一旦某行在 L3 中因为组冲突被踢出，为了维护「L3 没有则上层绝不能有」的铁律，L3 必须向持有该行的核心发指令，强行作废其 L1/L2 中正在热用的副本。

### 2. 非包容式（Non-Inclusive）与排他式（Exclusive）：外挂过滤器解放 L3

随着核数膨胀与单核 L2 扩容（现代服务器单核 L2 已达 1~2 MB），包容式会把 L3 彻底吃空。因此，现代架构全面转向将**数据存储**与**一致性追踪**解耦：

* **AMD Zen（L2/L3 排他式 Victim Cache + Shadow Tags）**：从 DRAM 取回的数据直入 L1/L2，**完全不进 L3**；只有当缓存行从 L2 被淘汰（Evict）时，才作为受害者（Victim）坠入 L3。为了弥补 L3 看不见 L2 数据的视野盲区，Zen 在 L3 旁外挂了 **Shadow Tags（影子标签）**——只存地址 Tag 与核心归属位、不存 64B 数据，仅用 5%~10% 的硅片面积就实现了完备的全局点对点追踪。
* **Intel Skylake-SP 及后续服务器（Non-Inclusive + Snoop Filter）**：Intel 自 2017 年启用 Mesh 互连与 1 MB 大 L2 起，同样废弃了 Inclusive L3，改为非包容式（回填时可选择不写 L3，L3 驱逐时也不再反向作废 L1/L2），并专门辟出独立的 **Snoop Filter（嗅探过滤器）** 阵列来追踪各核私有缓存状态。

| 维度 | 包容式（经典 Intel 桌面） | 非包容 / 排他式（Intel Server / AMD Zen） |
| --- | --- | --- |
| **L1/L2 与 L3 关系** | L3 必须包含 L1/L2 全部副本 | L2 满后淘汰入 L3（Victim Cache 语义） |
| **全局嗅探机制** | 复用 L3 Tag Array | 独立 Snoop Filter 或 Shadow Tags（只存 Tag 不存数据） |
| **L3 有效容量** | 缩水（需扣除全核 L1+L2 总和） | 接近 L1+L2+L3 物理容量之和 |
| **L3 驱逐副作用** | 触发 Back-invalidation 强拆上层热数据 | 无反向作废，核心私有热数据不受干扰 |

## 五、MESI 及其工业演进：多核一致性的状态机

当多个核心的私有缓存同时盯上同一块物理内存，缓存一致性协议负责保证「写操作全局有序可见、读操作绝不拿到过期脏数据」。其工程精髓只有八个字：**读零开销，写须夺权**。

### 1. 基础 MESI 四状态与本地权限

每个缓存行在 Tag Array 中携带状态位（见第二节物理形态图），状态决定了核心能否在本地静默完成读写：

| 状态 | 含义 | 与下层一致性 | 本地 Load | 本地 Store |
| --- | --- | --- | --- | --- |
| **M (Modified)** | 唯一副本，已修改（脏） | 下层数据已过期 | 直接读（零总线信号） | 直接写（零总线信号） |
| **E (Exclusive)** | 唯一副本，未修改（净） | 与下层一致 | 直接读（零总线信号） | 直接写，状态**静默升为 M**（零总线信号） |
| **S (Shared)** | 多核共享副本之一（净） | 与下层一致 | 直接读（零总线信号） | **禁止直接写**，须先发 `BusUpgr` 作废他核副本 |
| **I (Invalid)** | 缓存行无效（空或被作废） | — | 须发 `BusRd` 索取数据 | 须发 `BusRdX` (RFO) 索取数据并夺取独占权 |

* **读命中的绝对静默**：只要行处于 M/E/S 任一有效状态，Load 指令在核内 4 周期直接闭环，片上网络没有任何事务。
* **E 状态的工程价值**：若线程独占操作某块内存，首次读入即给 `E` 状态；随后的写操作直接由 `E` 静默翻转为 `M`，省去了一次向全网广播夺权的总线事务。

### 2. 状态流转与工业修正：MOESI (AMD) 与 MESIF (Intel)

在教科书级的基础 MESI 中，有一个极其低效的痛点：当 Core A 持有脏行（`M`），Core B 发起读请求（`BusRd`）时，Core A 必须**先把 64B 脏数据写回（Flush）L3/DRAM 洗白**，然后 A 和 B 才能一起降为干净的 `S` 状态。为了消灭这种无意义的写回并明确谁来负责核间转发（C2C Transfer），工业界对 MESI 做了关键扩展：

* **AMD 的 MOESI 协议——引入 `O (Owned)` 状态**：
当 Core A（持 `M`）收到 Core B 的读请求时，A 通过片上网络把 64B 脏数据直接塞给 B（B 标为 `S`），同时 **A 将自己的状态从 `M` 降为 `O`（Owned，共享但持有脏数据主权），完全不写回 L3/DRAM**。只要数据还在核间热传，脏数据就在片上 SRAM 内部闭环流转；只有当持有 `O` 的核心最终淘汰该行时，才由它负责写回下层。
* **Intel 的 MESIF 协议——引入 `F (Forward)` 状态**：
当一行数据被 8 个核心同时以 `S` 状态共享时，若第 9 个核心发起读请求，究竟由谁来响应？MESIF 规定：最新拿到该共享行的核心标记为 `F`（Forward，唯一转发人），其余 7 个核心标为 `S`。新来的读请求直接由 `F` 核通过核间直达（Cache-to-Cache Transfer）就近供给，避免了多核同时响应的冲突，也省去了去慢速 DRAM 取数的开销。

```text
一个缓存行在两核间的实战流转（结合 MOESI / C2C 直达）：

  T1 [独占读] Core A 读 x ──► L1 Miss，发 BusRd ──► 目录确认全网无副本
                              └──► 取回 64B，Core A 标【E】

  T2 [静默写] Core A 写 x ──► 已持 E，核内直接改写，零信号静默升为【M】（数据变脏）

  T3 [跨核读] Core B 读 x ──► L1 Miss，发 BusRd ──► 目录/过滤器定位到 Core A 持 M
                              └──► Core A 触发 C2C 转发，将脏行直接通过片上网络送给 Core B
                              └──► Core A 转为【O】(MOESI) 或更新 L3 后转【S】；Core B 标【S】

  T4 [夺权写] Core B 写 x ──► 持 S 无写权，发 BusUpgr (失效信号，无需传数据)
                              └──► 目录点对点通知 Core A 作废为【I】；Core B 独占升为【M】

```

### 3. 核间迁移账单与伪共享（False Sharing）

哪怕有目录/嗅探过滤器将广播降为点对点消息，一次跨核夺权（C2C 迁移）的物理延迟依然高昂：

$$L_{\text{migrate}} = \underbrace{L_{\text{snoop}}}_{\text{目录/过滤器查询 (≈15~20 ns)}} + \underbrace{L_{\text{transfer}}}_{\text{片上网络多跳搬运 (≈30~50 ns)}} + \underbrace{L_{\text{protocol}}}_{\text{状态机翻转 (≈10 ns)}} \approx \mathbf{60 \sim 80\text{ ns}}$$

（若跨 CPU 插槽走 UPI / Infinity Fabric 互连，延迟更会飙升至 **120~150 ns**，比直接读本地 DRAM 还慢。）

**伪共享（False Sharing）** 是触发这张高昂账单的头号杀手：两个线程分别在不同核心上高频修改两个逻辑上完全独立的变量（如 `struct { long a; long b; }`），但由于 `a` 和 `b` 相距仅 8 字节，被打包在**同一个 64 字节缓存行**内。Core 0 改 `a` 会发 `BusRdX` 把整行抢过来并把 Core 1 的副本作废为 `I`；紧接着 Core 1 改 `b` 又发 `BusRdX` 把整行抢回去——同一个缓存行在两核 L1 之间像乒乓球一样来回弹射（Cache Line Ping-Pong），每次写入都退化为 70 ns 级的跨核迁移。工程上必须使用 `alignas(64)`（C++）或填充字节（Padding）将高频并发写的变量强制隔离到不同的 64B 缓存行。

## 六、TLB 的性能面：覆盖率墙与跨核击落

```text
【机制速览：x86-64 两级 TLB 与硬件页表遍历】
 • L1 dTLB（通常 64 项，4KB 页下仅覆盖 256 KB）：与 L1d VIPT 同步查询，命中零额外延迟
 • L2 sTLB（通常 1536~2048 项，覆盖 6~8 MB）：L1 TLB 未命中后查询，耗时约 7~10 周期
 • Page Miss Handler（PMH，页未命中处理器）：两级 TLB 全 Miss 时启动硬件页表遍历；先查页结构缓存（PML4E/PDPTE/PDE Cache），按命中情况跳级进入，需读 1~4 个表项——多数命中 L2/L3（DRAM 访问常为 0），耗时数十周期；表项行全冷时四级串行 ≥ 260 ns

```

地址翻译在微架构上是访存的「前置买路钱」，对软件性能构成两道硬约束：

### 1. 覆盖率墙（Reach）与大页（Huge Pages）

一条 TLB 条目只映射一个页。当程序的工作集（如大型图结构、数据库缓冲池、百 GB 级 JVM 堆）远超 L2 sTLB 的 **8 MB 覆盖窗口**，且访问呈现随机跳跃时，TLB 会发生剧烈颠簸（Thrashing）：每次访存不仅数据本身在缓存中 Miss，连翻译都要先读 1~4 个表项；页表行仍有缓存局部性时这些表读多数命中 L2/L3（DRAM 为 0），一旦页表行也被挤出，最坏叠加 4 次 DRAM 表读 + 1 次数据读（合计 5 次访存）。

破局手段是启用 **2 MB 或 1 GB 大页（Huge Pages）**：

* **覆盖率暴增 512 倍**：同样 64 项 L1 dTLB，在 2 MB 大页下可直接覆盖 **128 MB** 热数据；L2 sTLB 更是可扩展至 **数 GB**，彻底消灭 TLB Miss。
* **缩短页表树高度**：2 MB 页直接省掉最后一级页表（PTE），将 4 级遍历减为 3 级；1 GB 页进一步减为 2 级。
* **工程权衡**：Linux 透明大页（THP）在后台动态扫描拼凑连续物理内存，但在内存碎片化严重时，后台整理线程（`khugepaged`）的锁争用与同步内存规整反而会引发毫秒级延迟毛刺。低延迟系统（如高频交易、核心数据库）通常禁用 THP，改为在系统启动时通过 `hugepages=` 静态预留 2 MB / 1 GB 物理大页。

### 2. TLB Shootdown（跨核 TLB 击落）

缓存有 MESI 协议由硬件自动维护跨核一致性，但 **TLB 没有硬件一致性协议**。当多线程进程在 Core 0 上调用 `munmap()` 或 `mprotect()` 修改了页表映射，Core 0 只刷新了自己的本地 TLB；此时正在 Core 1~63 上跑的同进程线程，其私有 TLB 中依然残留着指向旧物理页的过期映射。

为此，操作系统内核必须执行 **TLB Shootdown**：

1. Core 0 修改页表后，通过 APIC 向所有可能持有该映射的核心广播 **处理器间中断（IPI，Inter-Processor Interrupt）**，并原地自旋等待。
2. 收到 IPI 的核心被迫打断当前用户态流水线，陷入内核态执行 `INVLPG` 指令冲刷本地 TLB，随后向 Core 0 回复确认（ACK）。
3. Core 0 收齐所有核心的 ACK 后，才能安全释放该物理页并返回用户态。

一次跨核 TLB Shootdown 耗时高达 **数千周期（微秒级）**，且随核数增加呈木桶效应（受制于最慢响应的那个核）。这也是为何高并发服务严禁在热路径中频繁调用 `mmap/munmap`（或触发 glibc `malloc` 向内核归还内存的阈值），而必须使用内存池（如 `jemalloc`/`tcmalloc`）在用户态复用虚拟地址空间。

## 七、DRAM 以下：SSD 闪存物理约束与写放大

当数据规模突破 DRAM 容量下沉至 NVMe SSD，延迟从 100 ns 跳变至 100 µs（相差 1000 倍）。但比延迟跳变更深刻的变化在于：从 SRAM、DRAM 到 SSD，底层物理介质彻底丧失了「原地覆盖写（In-place Update）」的能力。

### 1. NAND Flash 的非对称物理铁律

DRAM 改写一个字节只需给电容重新充放电，读写对称；而 SSD 内部的 NAND 闪存受浮栅/电荷阱晶体管物理特性限制，遵循三条严苛铁律：

1. **读写按页（Page），擦除按块（Block），且块内严格顺序写**：
   * 操作系统页通常为 4 KB，但 NAND 闪存的最小读写单位 Page 高达 **16 KB**（一条字线 Wordline 需配备一套感测放大器与锁存电路，做成 16 KB 才能分摊外围电路占用的硅片面积、保住存储密度）。
   * 最小擦除单位是 **Block**（由 256~512 个 Page 组成，容量高达 4~8 MB）。且同一个 Block 内的 Page 必须严格按 `Page 0 -> Page N` 的物理顺序依次追加编程，严禁跳跃或回退写入（防止相邻单元电压干扰 Program Disturb）。
2. **异地更新（Out-of-place Update）**：已写入数据的 Page 绝不能直接覆盖写（电子只能单向注入将比特从 1 编程为 0，必须靠约 20V 高电压整块擦除才能把整个 Block 重置回全 1）。
3. **读写擦耗时极度悬殊**：读一个 Page 仅需约 50 µs，写（编程）一个 Page 需约 500 µs，而擦除一个 Block 高达 2~5 ms。

### 2. FTL（Flash Translation Layer，闪存转换层）映射、两路写入管线与垃圾回收（GC）

为了向操作系统伪装出「可以按 4 KB 逻辑扇区（LBA）随时原地覆盖写」的假象，SSD 控制器内部运行着一层微型操作系统——**FTL（Flash Translation Layer，闪存转换层）**，并在板载 DRAM 中维护着数 GB 的 **L2P（逻辑到物理地址）映射表**与写缓冲区。

由于不能原地改写，向空闲新 Block 写入的数据实际上由**两条异步管线（两路数据源）**共同构成：

```text
【第一路：前台主机写入管线（实时发生，接收主机内存刷下的新数据）】
  主机修改 LBA #100 (4KB) ──► 板载 DRAM 写缓存攒批 (凑满 16KB 物理页)
                                      │
         ┌────────────────────────────┴────────────────────────────┐
         ▼ 1. 仅在位图中标为失效(不擦除)                            ▼ 2. 顺序追加写入空闲页，并更新 L2P 表
    Block A (历史旧块，逐渐变成半死不活状态)                  Block B (前台活动块 Active Open Block)
  ┌──────────┬──────────┬──────────┬──────────┐          ┌──────────┬──────────┬──────────┐
  │ Page 0   │ Page 1   │ Page 2   │ Page 3   │          │ Page 0   │ Page 1   │ Page 2   │
  │ [Valid]  │ [Stale✗] │ [Valid]  │ [Stale✗] │          │[LBA#100']│  [Free]  │  [Free]  │
  └────┬─────┴──────────┴────┬─────┴──────────┘          └──────────┴──────────┴──────────┘
       │                     │
       │  【第二路：后台 GC 搬迁管线（当空闲块不足时异步唤醒，抢救存量旧数据）】
       └─────────────────────┼──────► ① 将 Block A 残存的 Valid 页读回控制器内部 RAM
                             │        ② 顺序追加写入专用的新目标块 (Block C)，同步更新 L2P
                             │        ③ 此时 Block A 全员失效，施以 4MB 高压整块擦除 (Erase) 回收
                             ▼
                        Block C (GC 目标块 GC Target Block，实现冷热数据隔离)
                      ┌──────────┬──────────┬──────────┬──────────┐
                      │ Page 0   │ Page 1   │ Page 2   │ Page 3   │
                      │ [搬迁页0]│ [搬迁页2]│  [Free]  │  [Free]  │
                      └──────────┴──────────┴──────────┴──────────┘

```

* **第一路：前台写时重定向（Host Write Path）**
当主机修改逻辑地址 `LBA #100` 时，数据先进入 SSD 板载 DRAM 缓冲区，与其他写入攒批凑满 16 KB 后，直接顺序追加写入当前正打开的前台活动块（Block B）的下一个空页；随后 FTL 修改 L2P 映射表指向新物理页，并将旧块（Block A）中的原物理页标记为失效（Stale）。**注意：此时绝不擦除旧块，也不搬运任何旧数据，前台写入立刻返回。**
* **第二路：后台垃圾回收与存量搬迁（GC Relocation Path）**
随着随机覆盖写持续进行，SSD 内布满了像 Block A 这样「半死不活」的块（既有失效页 `Stale`，又夹杂着长期未修改的有效页 `Valid`）。当空闲块（Free Blocks）耗尽触及警戒线时，SSD 必须在后台启动 GC：
1. **挑出牺牲块（Victim Block）**：选取有效页最少的旧块（如 Block A）。
2. **搬移存量有效页**：将 Block A 中残存的 `Valid` 页读出，顺序追加写入到新的GC 目标块（Block C）中，并更新 L2P 映射。（工程上通常将前台热数据与 GC 冷数据分流到不同新块，防止刚搬完的冷数据又被频繁修改的热数据拖累）。
3. **整块擦除回收**：确认 Block A 内已无任何有效数据后，对其执行 4~8 MB 整块擦除（Erase），重置为空闲块以备后用。



### 3. 写放大系数（WAF）及其工程后果

由于后台 GC 被迫不断把旧块里残存的有效页“读出来再写进新块”，导致 SSD 实际写入闪存颗粒的物理数据量，远大于主机请求写入的逻辑数据量。两者的比值即为**写放大系数（Write Amplification Factor, WAF）**：

$$\text{WAF} = \frac{\text{主机写入量} + \text{GC 内部搬运写入量}}{\text{主机请求写入量}} \ge 1$$

* **工程后果**：在纯顺序追加写且整块删除的理想场景下， $\text{WAF} \approx 1$；但在小粒度（4 KB）随机覆盖写且盘空间使用率超过 80% 时，每一个旧块里都残留着大量有效页，FTL 每擦除回收一个块都要额外搬运大半个块的数据，导致 WAF 飙升至 5~20 以上。这不仅吞噬数倍的内部闪存通道带宽（导致前台正常读写被 GC 阻塞，出现数十毫秒的长尾延迟尖峰），更以成倍的速度消耗闪存颗粒极其有限的物理擦写寿命（P/E Cycles）。
* **软件层面的架构顺应**：现代底层存储引擎（如 RocksDB 的 LSM-Tree）的核心设计哲学，就是在主机内存（MemTable）中先将随机写缓冲并按键排序，转化为面向 SSD 的大块顺序追加写（SSTable 文件），并通过后台 Compaction 整批淘汰旧文件，从软件源头顺应闪存的异地顺序写特性，将硬件层面的 WAF 压至最低。
