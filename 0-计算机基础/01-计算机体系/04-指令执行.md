# 指令执行

## 一、顺序契约与乱序实现

同章《指令集架构与 SIMD》§一说明 ISA 规定软件可见的状态变化，这里看微架构如何兑现它。软件可以按程序顺序推理指令结果，硬件却希望独立指令重叠执行。两段要求由重排序缓冲区连接：执行可以乱序，架构状态必须按序提交。

以三条指令为例：

```asm
load r1, [a]
add  r2, r3, r4
mul  r5, r1, r6
```

`add` 不依赖慢速 `load`，可以先算完；`mul` 必须等 `r1`。硬件让 `add` 先完成，却不能让它越过尚未退休的旧指令随意改变异常边界。临时结果先留在物理寄存器和 ROB 中，再按程序顺序退休。

```text
预测 PC → 取指 → 译码为微操作
                      │
                      ▼
             按程序顺序分配 ROB 与重命名
                      │
          ┌───────────┴───────────┐
          ▼                       ▼
    操作数就绪后乱序发射      Load / Store 进入访存队列
          │                       │
          └───────────┬───────────┘
                      ▼
             写临时结果并标记完成
                      │
                      ▼
             ROB 头部按程序顺序退休
```

“完成”表示结果已经算出，“退休”表示结果成为不可撤销的架构状态。区分这两个时刻，才能解释乱序执行为何仍能给出精确异常。

### 1. 顺序流水线提供基准

经典五级流水线把指令分成取指、译码、执行、访存、写回。理想情况下，每个周期流入一条新指令；结构冲突、数据等待和控制不确定会让流水线停顿。

| 冒险 | 阻塞原因 | 典型缓解手段 | 无法消除的部分 |
| --- | --- | --- | --- |
| 结构冒险 | 两条操作争用同一硬件资源 | 增加端口、缓存或功能单元 | 峰值需求仍可能超过资源 |
| 数据冒险 | 源操作数尚未产生 | 旁路转发、乱序调度 | 真依赖链仍要按因果等待 |
| 控制冒险 | 后续 PC 取决于未完成分支 | 分支预测 | 猜错必须撤销错误路径 |

顺序发射遇到长延迟 Load 时，后面的独立指令也可能无法继续前进。乱序窗口的作用就是扩大可搜索的独立指令范围，而不是缩短 DRAM 本身的访问时间。

### 2. 资源账比单一流水线更完整

实际吞吐同时受前端供给、后端容量、依赖和错误投机影响。Intel 的顶层微架构分析法（Top-down Microarchitecture Analysis，TMA）把分配槽位分为退休、错误投机、前端受限和后端受限四类，用来先定位大方向。

$$\text{总槽位}=\text{退休}+\text{错误投机}+\text{前端受限}+\text{后端受限}$$

这个分类面向具体性能计数器与流水线模型。它能说明槽位耗在哪里，不能单独证明哪条指令或哪个物理部件就是根因。

## 二、前端供给：先确定 PC，再形成微操作

后端每个周期需要若干条微操作。前端要先预测下一段代码的位置，再取回字节并译码。分支预测错误会让供给作废，缓存或译码不足则会让后端等输入。

### 1. 分支预测把控制等待变成可撤销的投机

条件分支的方向和间接跳转的目标可能要到执行阶段才确定。若前端始终等待，分支后的流水线会空出来。预测器先给出候选 PC，错误路径上的结果再由退休与冲刷机制撤销。

```text
当前 PC
   │
   ▼
目标预测：下一取指块在哪里？
   │
   ▼
方向预测：条件分支是否采用该目标？
   │
   ├─预测正确：后续微操作继续供给
   │
   └─执行时发现错误：作废年轻微操作，从正确 PC 重新取指
```

分支目标缓冲器（Branch Target Buffer，BTB）记录分支目标与类型。返回地址栈（Return Stack Buffer，RSB）针对调用与返回配对预测返回地址。方向预测器利用局部与全局历史估计条件分支是否跳转；TAGE 等设计用不同长度的历史表互补。

预测的代价可写成

$$\Delta\mathrm{CPI}=f\times r\times P$$

其中 $f$ 是分支占比， $r$ 是误预测率， $P$ 是每次误预测暴露的平均周期。三个量必须来自同一程序与处理器口径。短流水线和长流水线不能用同一个固定惩罚值。

返回栈容量有限只意味着过深调用可能降低预测质量，不代表之后每次返回都必然失败。方向预测也不能保证把任意程序的错误率压到某个固定阈值。

### 2. 译码缓存复用已经完成的切分

同章《指令集架构与 SIMD》§二说明 x86 变长编码需要识别指令边界，这里看它如何影响供给。传统译码路径取回 L1I 字节，识别边界，再生成一个或多个微操作。微操作缓存保存译码结果，使命中路径跳过重复的字节切分与译码。

```text
L1I 字节 → 传统译码 ───────────────► 微操作队列 → 分配
                 │                         ▲
                 └────► 微操作缓存 ────────┘
                       命中时复用译码结果
```

小型循环还可由循环流机制重复供给，具体容量和启用条件随微架构变化。复杂指令可能拆成多个微操作，微码指令还会进入专门序列，因此“每条机器指令对应一个内部动作”并不成立。

宏融合把符合条件的相邻架构指令作为一个前端单位，微融合让若干内部动作在部分管线中共同占用条目。它们减少的是特定阶段的供给压力，执行时仍可能分开，不能据此把两条指令的所有成本都算作一次。

## 三、重命名与分配：保留真依赖，解除寄存器重名

前端形成微操作后，分配器按程序顺序为其预留 ROB、调度和访存资源。重命名再把架构寄存器映射到物理寄存器。ROB 记住先后次序，物理寄存器堆（Physical Register File，PRF）保存不同写版本。

### 1. 三类相关中只有 RAW 传递值

若指令 $i$ 先于 $j$，可用读写集合区分三类寄存器相关：

| 相关 | 条件 | 本质 | 处理方式 |
| --- | --- | --- | --- |
| RAW | $i$ 写入 $j$ 读取的对象 | 后序需要前序结果 | 等待结果并转发 |
| WAR | $j$ 覆写 $i$ 要读取的对象 | 架构寄存器重名 | 给 $j$ 分配新物理寄存器 |
| WAW | 两者写同一对象 | 两个写版本争用一个名字 | 分开保存，按程序顺序提交 |

RAW 是数据因果，重命名不能消除。WAR 与 WAW 只是存储名字不足造成的约束，可通过版本化解除。

### 2. RAT 建立新版本，ROB 保存旧版本

寄存器别名表（Register Alias Table，RAT）记录每个架构寄存器当前对应的物理寄存器。遇到写 `RAX` 的微操作时，硬件从空闲表分配新项，把 RAT 更新为新项，并在 ROB 中记录旧映射。

```asm
add  rax, 1       # RAX: P0 → P10，ROB 记录旧值 P0
load rax, [x]     # RAX: P10 → P20，ROB 记录旧值 P10
mov  rax, 2       # RAX: P20 → P30，ROB 记录旧值 P20
```

后续读取总是使用当时 RAT 给出的版本。因此，`load` 尚未完成时，`mov` 仍能把 2 写入 P30，更后面的指令也可读取 P30，不必误等 P20。

### 3. 旧物理寄存器在退休时释放

P10 不能因 P20 已经分配就立即回收。发生错误投机时，RAT 可能还要恢复旧映射；已退休状态也不能被投机写覆盖。常见方案让每条写操作在退休时释放自己取代的旧物理寄存器。

| 时刻 | P10 | P20 | P30 |
| --- | --- | --- | --- |
| 三条都已分配 | 当前值的前身，仍受保护 | 等待 Load | 可提前写入 2 |
| `add` 退休 | P0 可释放，P10 成为已提交映射 | 仍等待 | 仍属未退休结果 |
| `load` 退休 | P10 可释放 | 成为已提交映射 | 仍属未退休结果 |
| `mov` 退休 | 已不在当前链上 | P20 可释放 | 成为已提交映射 |

若 `load` 后的分支预测失败，分支之后的年轻条目被撤销，RAT 恢复到分支时的映射。被撤销指令分配的新物理寄存器可以回收，分支之前的旧指令与未决 Load 则继续保留。

物理寄存器、ROB 或调度队列任一耗尽，都可能让分配停顿。窗口越大可搜索的独立指令越多，但面积、查找与恢复成本也随之增加。

## 四、乱序执行：就绪判断与端口供给

完成重命名后，微操作进入相应调度结构。保留站（Reservation Station，RS）或发射队列等待源操作数就绪，再选择可执行的条目送往端口。程序顺序仍保存在 ROB 中，执行顺序则由依赖和资源决定。

### 1. 唤醒与选择分开

某执行单元产生结果时，会公布目标物理寄存器。等待该值的条目标记对应源操作数就绪；全部源就绪后，条目才参与发射选择。

```text
生产者完成 → 公布目标 Tag → 等待者标记源就绪
                                  │
                                  ▼
                       全部源就绪的候选集合
                                  │
                                  ▼
                 按年龄、端口和资源选择本拍发射项
```

仲裁不一定在所有队列中采用同一种“最老优先”规则。选择策略还要避免端口冲突和唤醒冲突，不能把一种常见策略写成硬件定律。

旁路网络把刚产生的值直接送给相关消费者，省去等待 PRF 写回再读出的完整路径。它缩短真依赖的传递延迟，却不能让依赖指令与生产者同时得到结果。

### 2. 端口把吞吐限制落到具体功能单元

后端有多个执行端口，不同端口可挂载整数、分支、向量、地址生成或存储数据单元。一个周期能发射多少微操作，既取决于调度宽度，也取决于所需端口是否可用。

| 代码形态 | 主要供给要求 | 常见限制 |
| --- | --- | --- |
| 独立整数运算 | 多个可用 ALU 与足够发射宽度 | 真依赖较少时受端口和前端限制 |
| 单累加器求和 | 每轮等待上一轮结果 | 跨迭代 RAW 链 |
| 密集向量运算 | 对应向量单元、寄存器与数据供给 | 特定向量端口和访存带宽 |
| 大量加载与存储 | AGU、Load/Store 队列、缓存端口 | 队列容量与内存级并行 |

同一段向量指令在不同核心上的吞吐可以不同。ISA 只规定结果，端口数量与执行宽度属于微架构。

### 3. 错误假设只需重放相关路径

Load 延迟取决于命中层级。部分调度器会按预期的缓存命中时间提前唤醒消费者；若数据未按时返回，相关微操作必须重放。它不同于分支误预测：前者是执行时序假设错误，后者是控制路径错误。

重放会浪费发射槽和端口，却不必撤销整条程序路径。性能分析应区分局部重放、访存序清管与全流水线冲刷，它们的范围并不相同。

## 五、访存子系统：地址消歧与写可见性

访存除了计算地址，还要维护 Load 与 Store 的顺序。Load 队列和 Store Buffer 共同形成访存队列（Load-Store Queue，LSQ）。它允许独立访问并行，又在发现冲突时恢复原语义。

### 1. 年轻 Load 何时能越过老 Store

若老 Store 地址已知且与 Load 不重叠，年轻 Load 可提前访问缓存。若老 Store 地址尚未算出，处理器可保守等待，也可依据历史预测二者无关。若后来证明地址冲突，Load 及其依赖者必须重新执行。

同章《缓存与存储层次》§三说明 MSHR 会合并在途行，这里用它说明多个独立 Load 的收益：只要队列、MSHR 和缓存端口允许，多次未命中可以重叠。内存级并行受整条资源链限制，不由 ROB 容量单独决定。

### 2. Store Buffer 隔离投机写与全局可见写

```text
Store 拆出地址与数据
          │
          ▼
进入 Store Buffer，供后续同地址 Load 查询
          │
          ▼
指令退休，写操作不再属于可撤销的投机路径
          │
          ▼
按顺序取得缓存行写权限并更新缓存
```

未退休的 Store 不能让其他核心看到。退休后的写也可暂留缓冲区，等待缓存端口与一致性权限。年轻 Load 查询同地址时，可以从最新的匹配 Store 转发，而不必读取旧缓存值。

这解释了 Store→Load 重排的一种来源：Core 0 的写仍在本核缓冲区中，后续对不同地址的读却已经取得结果。其他核心可以先观察到读的效果，再观察到写。它不代表 Load 在机器内部物理上一定先执行，而是全局可见顺序允许如此。

### 3. 内存模型约束允许发生的重排

对普通可回写内存，x86-64 的常见程序顺序模型保留 Load→Load、Load→Store 与 Store→Store，允许 Store→Load 的可见性窗口。非临时写、强不可缓存内存和特殊指令另有规则，不能把它们一并套用普通写缓冲模型。

AArch64 与 RISC-V 的普通内存序允许更多重排，软件用获取、释放或屏障表达必要顺序。弱序不是“每次执行都会乱序”，而是软件不能依赖未被契约保证的顺序。

| 软件需要的关系 | 典型机制 | 约束对象 |
| --- | --- | --- |
| 阻止编译器移动访问 | 编译器屏障或语言内存序 | 代码生成与优化 |
| 保持写后读的全局顺序 | 相应全屏障或更强原子操作 | 硬件可见顺序 |
| 保持指令取指与系统状态同步 | 指令同步屏障，如 AArch64 `ISB` | 后续取指与上下文，不等于数据屏障 |

x86 的普通 acquire 读和 release 写通常可映射为普通装载、存储加编译器约束；需要 Store→Load 的顺序一致写则要用更强序列。ARMv8 可用带获取或释放语义的访存指令。具体映射还受语言操作和编译器影响。

## 六、退休与恢复：异常必须落在正确指令上

ROB 头部按程序顺序检查已完成条目。寄存器写成为已提交状态，旧物理寄存器被回收，Store 转为可提交写。只有头部连续可退休，后面的年轻结果才能依次提交。

### 1. 三类恢复范围不同

| 事件 | 发现位置 | 要撤销的对象 | 恢复动作 |
| --- | --- | --- | --- |
| 分支误预测 | 分支执行或目标校验 | 该分支之后的年轻微操作 | 恢复 RAT，改从正确 PC 取指 |
| 访存序违例 | LSQ 或一致性观察 | 违规 Load 及其依赖路径，范围随实现而变 | 重放或清管后重新执行 |
| 精确异常 | 故障信息先到 ROB，到头部才交付 | 故障指令之后的年轻状态 | 保存架构现场并进入处理入口 |

分支误预测不必等它到达 ROB 头部才冲刷，因为分支之前的状态仍然有效。缺页等故障若在错误投机路径上，则必须随该路径一起消失，不能提前报告给操作系统。

### 2. 精确异常保护软件可恢复点

假设一条错误预测路径上的 Load 访问无效地址。硬件可以先记录故障，却不能立即让进程收到异常；等真实分支方向揭晓后，这条 Load 可能根本不应存在。

只有故障指令成为 ROB 头部、之前指令都已提交时，处理器才按 ISA 交付异常。此时已提交状态对应明确的指令边界，操作系统才能修改页表并重试，或报告错误。

异步中断没有某条故障指令的因果关系，它在架构允许的指令边界接管。故障、陷阱和中断的返回地址规则由 ISA 分别规定，不能统一写成“总是返回到下一条”。

### 3. 沿链定位瓶颈

程序变慢时，各节点留下不同证据：误预测看分支事件，译码不足看前端供给，依赖与端口看执行利用率，长延迟访存看缓存与队列，退休阻塞再看 ROB 头部原因。

同一段代码可能同时受多个因素限制。优化应改变对应节点，再检查瓶颈是否转移：增加累加器可打断依赖链，却增加寄存器压力；减少分支可降低误预测，却可能增加数据依赖；扩大向量宽度可减少指令数，却不能解除缓存与主存的供给上限。
