# 并行与并发

## 一、并行与并发的界定：三条并行列与加速比账本

并行与并发常被当成程度不同的同一件事，实际是两个判据：并行说的是"同一时刻真有多个执行流在推进"，并发说的是"结构上允许交错，单核时分复用也能成立"。一个单核上的事件循环是并发而非并行；四颗核心各跑一个独立进程是并行；一个 warp 的 32 条 lane 锁步执行同一指令，是并行里最窄的一种。判据不同，优化手段就不同：并行的上限由硬件并行度与串行段比例决定，并发的上限由切换成本与临界区长度决定。

| 串行段比例 p | 2 核 | 4 核 | 8 核 | 16 核 | 64 核 | 核数趋于无穷 |
| --- | --- | --- | --- | --- | --- | --- |
| 0.50 | 1.33 | 1.60 | 1.78 | 1.88 | 1.97 | 2.00 |
| 0.90 | 1.82 | 3.08 | 4.71 | 6.40 | 8.77 | 10.0 |
| 0.95 | 1.90 | 3.48 | 5.93 | 9.14 | 15.4 | 20.0 |
| 0.99 | 1.98 | 3.88 | 7.48 | 13.9 | 39.3 | 100 |

### 1. 三条并行列与并行度的上限

一台机器能提供的并行度是三条列相乘：指令级并行（一个核心每拍发射多少条不相关指令）、线程级并行（多少颗核心、每核多少个 SMT 线程）、数据级并行（每条向量指令覆盖多少 lane）。03 的乱序窗口把第一条列撑到数百条在飞指令，04 的 AVX-512 把第三条列撑到 16 个 FP32 lane，剩下的第二条列由本篇第二节的拓扑决定。三条列不是简单相加：指令级并行被依赖链封顶，线程级并行被串行段封顶，数据级并行被分支发散与访存合并封顶。

对软件而言，可达到的并行度取"算法可并行比例"与"硬件并行度"的较小者。把一段 95% 可并行的代码放到 16 核上，理论上限是 9.14 倍而不是 16 倍；放到 64 核上是 15.4 倍而不是 64 倍。这不是实现缺陷，而是串行段的算术后果。

### 2. 强扩展：Amdahl 上限与边际收益递减

固定问题规模、增加核数，叫强扩展。设串行段占单线程执行时间的比例为 p 的补，强扩展加速比为

$$S_{\text{strong}}(N) = \frac{1}{(1-p) + p/N}$$

核数趋于无穷时，加速比收敛到串行段倒数的上限：

$$S_{\infty} = \frac{1}{1-p}$$

表中每一行都在这条曲线上：p = 0.95 时，2 核得 1.90 倍、16 核得 9.14 倍、64 核得 15.4 倍，核数翻四倍只多出六成。边际收益递减的斜率由串行段决定，与核数无关；想继续提速，只能压缩串行段本身（把初始化、归并、I/O 也并行化），而不是继续加核。这条结论对多线程程序、GPU kernel、分布式任务同样成立，区别只在"核"的定义。

### 3. 弱扩展、并行效率与拐点

固定每核工作量、让问题规模随核数增长，叫弱扩展。此时加速比换成

$$S_{\text{weak}}(N) = (1-p) + pN$$

p = 0.95、16 核时弱扩展上限是 15.25 倍，接近线性——因为串行段的绝对时间不变，而并行段随规模一起长大。工程上报告加速比必须先声明是强扩展还是弱扩展，否则两个数字不可比。

把强扩展加速比除以核数，得到并行效率：

$$\eta(N) = \frac{S_{\text{strong}}(N)}{N}$$

效率永远小于 1，且随核数单调下降；真实系统还会在某个核数之后加速下降，因为除串行段之外又出现了第二类开销：跨核缓存行迁移（02 §五.3 的 60 ~ 80 ns 账单）、一致性目录查询、TLB 击落（02 §六 的微秒级停顿）、共享 LLC 与内存控制器的排队。这些开销随核数超线性增长，把效率曲线从"缓慢下降"推成"掉头向下"。定位拐点的办法不是继续加核，而是按第二节的拓扑把线程放到正确的域里。

## 二、多核硬件底座：SMT、L3 共享域与软件可见拓扑

并行度的第二条列由封装内的拓扑决定：一颗插槽里有几个 L3 域、每个域挂几颗核心、每颗核心有几条 SMT 线程、内存控制器挂在哪一侧。操作系统通过 CPUID 与 ACPI 表枚举这棵树，调度器按树放置线程；放错一层，同一段代码的访存延迟就差一到两个档位。

```text
双路服务器的软件可见拓扑（边标注访存延迟档）：

        ┌──────────── Socket 0 ────────────┐    ┌──────── Socket 1 ─────────┐
        │  L3 域（数十 MB，多切片共享）      │    │  L3 域                     │
        │   ┌────────┐    ┌────────┐       │    │   ┌────────┐   ┌────────┐  │
        │   │ Core 0 │    │ Core 1 │  ...  │    │   │ Core N │   │Core N+1│  │
        │   │ T0  T1 │    │ T0  T1 │       │    │   │ T0  T1 │   │ T0  T1 │  │
        │   └───┬────┘    └───┬────┘       │    │   └───┬────┘   └───┬────┘  │
        │       └──────┬──────┘            │    │       └──────┬─────┘       │
        │              ▼                   │    │              ▼             │
        │        本地 DRAM ~80 ns          │    │        本地 DRAM ~80 ns     │
        └──────────────┬───────────────────┘    └──────────────┬─────────────┘
                       │      UPI / xGMI 互连（数十 GB/s 档）   │
                       └──────────────────┬───────────────────┘
                                          ▼
                                  跨槽 DRAM ~150 ns
```

### 1. 拓扑枚举与三层共享

固件在启动时把拓扑写进 ACPI 的 SRAT 与 SLIT 表：SRAT 声明哪些核心与内存属于哪个亲和域，SLIT 给出域间距离矩阵。内核读表建立调度域，`lscpu -e` 打印每个逻辑 CPU 的 socket、core、NUMA 节点归属，`numactl --hardware` 打印节点距离矩阵。CPU 侧另有 CPUID 的拓扑叶（`0x1F` / `0xB`）给出 SMT 位移与核心位移，用于把逻辑处理器号还原成"第几核第几线程"。

三层共享的粒度依次放大：SMT 兄弟共享执行端口与 L1/L2；同 L3 域的核心共享 LLC 与环/网格互连；跨插槽共享 UPI 或 xGMI 链路。每上一层，带宽降一档、延迟升一档。02 §二 已经给出 L1/L2/L3 的延迟标尺，01 §四 给出了 L3 共享域与封装的对应关系，本节只把这两组结论接到"线程该放哪"的问题上。

### 2. SMT：共享端口换来的吞吐

SMT 让两条线程共享一颗物理核心的取指、译码、执行端口与 L1/L2，只复制寄存器与架构状态。它的收益完全取决于两条线程的端口占用是否互补：一条在等访存、另一条在算，填充率上升，吞吐增益典型在 1.2 ~ 1.3 倍；两条都在打满向量乘加端口，增益趋近 1.0，只剩上下文切换的开销。因此 SMT 对分支密集、访存密集的负载友好，对已经端口饱和的 SIMD 负载几乎无效。

SMT 还放大了一致性成本：两条兄弟线程共享 L1，若它们写同一缓存行，冲突发生在核内而非核间，检测更快但同样退化为串行。把两条高频写的线程放到同一核心的两个 SMT 线程上，并不会比放到两颗核心更好——争用点从缓存行迁移到了执行端口。

### 3. L3 域、跨域迁移与绑核

同一 L3 域内的两颗核心交换缓存行，走的是片上互连与目录/嗅探过滤器，一次迁移约 60 ~ 80 ns；跨插槽要走 UPI，涨到 120 ~ 150 ns，比本地 DRAM 的 80 ns 还慢。这不是"内存更远"，而是"协议税更高"：跨槽事务要经过两层路由、两次协议转换，还要与穿槽的 DMA 流量抢同一条链路。跨槽带宽只有数十 GB/s 档，不到本地 DRAM 的五分之一，穿槽并发拷贝会把链路打满，反过来拖慢所有远端访问。

绑核是把这层拓扑暴露给软件的最直接手段：把同一进程的线程约束在同一个 L3 域内，跨域迁移就退化为域内命中；把内存分配约束在本地节点，远端访问就只发生在显式共享的数据上。这两步不需要改算法，只改放置策略，通常能拿回效率曲线上拐点损失的一半以上。代价是灵活性：绑死之后，负载突增无法借用其他域的空闲核心，需要在上层再做一层弹性调度。

## 三、内存序语义阶梯：从 MESI 到 acquire/release 的契约面

02 的 MESI 解决的是"单个地址的写最终对所有核心可见"，不解决"两个地址的写谁先谁后"。后者由内存一致性模型规定：硬件可以把年轻访存提前、把年老 Store 延后，只要不违反契约。契约以"允许哪些重排"的形式暴露给软件，软件再用屏障或带语义的原子操作把不允许的重排封住。

| 相邻访存对 | relaxed | acquire | release | acq_rel | seq_cst |
| --- | --- | --- | --- | --- | --- |
| Load → Load | 允许 | 禁止 | 允许 | 禁止 | 禁止 |
| Load → Store | 允许 | 禁止 | 允许 | 禁止 | 禁止 |
| Store → Load | 允许 | 允许 | 禁止 | 禁止 | 禁止 |
| Store → Store | 允许 | 允许 | 禁止 | 禁止 | 禁止 |

### 1. 单地址一致性与多地址顺序的分界

缓存一致性协议只保证同一缓存行的写有一个全局顺序，不保证不同缓存行之间的顺序。核心 A 先写 `flag`、再写 `data`，核心 B 可能先看到 `data` 的新值、后看到 `flag` 的新值——因为两次写走的是不同的缓存行、不同的目录查询路径，到达顺序不受协议约束。Store Buffer 进一步放大了这个窗口：写先落在本地缓冲里，对别的核心完全不可见，直到它被排空。

因此"无锁编程"的第一课不是原子性，而是"哪些顺序硬件不保证"。原子性只保证单条读改写不可分割，顺序性要另外购买；把两者混为一谈，就会写出"计数器正确、发布顺序错误"的代码。

### 2. 五档语义与重排矩阵

C++11 把契约压缩成五档，与硬件语义一一对应。`relaxed` 只保证原子性，四种重排全部允许，适合统计计数这类不需要顺序的场合；`acquire` 加在读上，禁止其后的访存上移到该读之前，用于"拿到锁或标志后再读数据"；`release` 加在写上，禁止其前的访存下移到该写之后，用于"写完数据再发布标志"；`acq_rel` 是读改写的双向约束；`seq_cst` 在全部操作上再叠一个全局总序，代价最高。

矩阵的读法是"该档位下，这一对相邻访存是否允许换序"。`acquire` 只封住它后面的操作，`release` 只封住它前面的操作，所以二者在矩阵里恰好互补；`seq_cst` 全封，`relaxed` 全开。把 `seq_cst` 无差别降成 `relaxed` 是并发缺陷的第一来源：单核测试永远通过，多核压测偶发失败，且失败点与症状相距很远。

### 3. 屏障在两种 ISA 上的落地

x86-TSO 的硬件契约已经封住了三种重排，只留 Store → Load 一个口子（03 §五.4 给出了 Store Buffer 的物理成因，此处只引用结论）。因此在 x86 上，`acquire` 读与 `release` 写编译后没有额外指令，只有 `seq_cst` 写需要一条 `xchg` 或 `mfence` 把 Store Buffer 排空；读屏障 `smp_rmb()` 与写屏障 `smp_wmb()` 退化为编译器屏障，运行时零拍。

ARMv8 是弱序：四种重排全部允许，必须显式发射带语义的指令。`ldar` 一条即 acquire 读，`stlr` 一条即 release 写，二者配对可替代大部分全屏障；`dmb ish` 才是全屏障，代价在数十拍档。`isb` 是流水线冲刷屏障，只管取指流，不管数据序——把 `isb` 当内存屏障用，是移植 ARM 代码时最常见的错误。

| 档位 | x86-64 落地 | ARMv8 落地 | 无争用代价 |
| --- | --- | --- | --- |
| relaxed | 普通 `MOV` | 普通 `LDR` / `STR` | 零额外 |
| acquire | 读本身零额外（TSO 已保证） | `LDAR` | 一条指令 |
| release | 写本身零额外（TSO 已保证） | `STLR` | 一条指令 |
| acq_rel | `lock` 前缀的读改写 | `LDAXR` / `STLXR` 对 | 数拍档 |
| seq_cst | 写用 `XCHG` 或 `MFENCE` | `STLR` 加 `DMB ISH` 组合 | 数十拍档 |

这套阶梯是下一节的地基：CAS 是带 `acq_rel` 或 `seq_cst` 语义的读改写，锁是用 CAS 拼出来的等待队列，RCU 则是把 release/acquire 用在指针发布上的特化。

## 四、原子性与 CAS：缓存行所有权上的重试环

原子操作的物理本质是"在持有缓存行独占权期间完成读改写"。`lock` 前缀告诉硬件：把目标行锁在 M 态，期间不允许其他核心读写，完成后按语义决定是否立即写回。比较并交换（Compare-and-Swap，CAS）在这条基础上加一个条件：只有当前值等于期望值才写入，否则原样返回。无锁算法的重试循环就建在这个条件上。

```text
CAS 重试环（两核争用同一 64B 行）：

  线程 A                              线程 B
    │                                   │
    ▼                                   ▼
 读 x=0（取快照）                    读 x=0（取快照）
    │                                   │
    ├─ lock cmpxchg(x, 0, 1) ──┐        │
    │   成功：行升 M，写入 1    │        │
    │                          ▼        │
    │                   行所有权迁移（60 ~ 80 ns 档）
    │                                   │
    │                          cmpxchg(x, 0, 1) 失败（x 已是 1）
    │                                   │
    │                                   └─► 回到「读 x」重试（回滚边）

  节点职责：快照读只做本地缓存访问；比较交换是解析网关；
            行所有权迁移参与一致性解析；失败分支是回滚边
```

### 1. lock 前缀与行所有权

`lock` 前缀把目标行锁在 M 态直至写回完成。无争用时，目标行本来就在本地 L1 且已是 E/M，原子操作在二十拍档完成；有争用时，目标行在别的核心手里，先要发一次夺权事务把行迁过来，退化为一次 60 ~ 80 ns 的行迁移（02 §五.3 的账单）。因此"原子操作很便宜"只在无争用前提下成立，争用下的价格与一次跨核缓存行传递同价。

两条硬件边界必须记住：原子变量必须自然对齐，且不得跨 64B 行；跨行或非对齐时，硬件无法用缓存锁完成，退化为锁总线，整条内存总线在此期间停摆。这也是 05 §4 的对齐规则在并发层的直接后果——结构体打包把两个原子变量压进同一行，不会报错，只会让每次原子操作都变成跨行。

### 2. CAS 循环与 fetch_add 的分工

CAS 循环的形态是"读—算—比较交换—失败重试"。争用线程数为 N 时，每轮只有一个线程成功，其余 N - 1 个线程重试，重试次数随争用度上升，整体吞吐随核数增加反而下降。对"只做加法"的计数器，硬件提供 `fetch_add` 单指令完成读改写，不需要循环，也不会出现活锁；因此计数器、序列号、引用计数应当优先用 `fetch_add`/`fetch_sub`，而不是 CAS 循环。

CAS 真正不可替代的场合是"条件更新"：只有当值仍等于快照时才写入新值，例如无锁栈的栈顶替换、无锁队列的尾指针推进。这类算法的正确性依赖于"比较与交换不可分割"，用 `fetch_add` 无法表达。工程上把 CAS 循环写成"先读、再算、再 CAS"，并在失败时重新读，而不是盲目重试同一个旧值。

### 3. ABA、tagged pointer 与多地址不变式

CAS 只比较值，不比较历史。若一个值从 A 变成 B 又变回 A，CAS 会误认为"没变过"并成功写入，这就是 ABA 问题。无锁栈的经典故障是：线程 1 读栈顶 A，线程 2 弹出 A、压入 B、再压回 A，线程 1 的 CAS 成功，但栈的结构已经变了。解法是给指针附加版本号，把"指针 + 计数"打包进一个 128 位原子，或借用 05 §5 的低位标记把版本藏在地址低位（前提是地址对齐留出了空闲位）。

最后一条边界是范围：原子操作只提供单地址的线性化点，不提供多地址的不变式。两个原子变量之间的"和恒定"这类约束，CAS 无法维护，必须用锁或事务内存。把多个原子变量当成一个整体来更新，等于在没有事务的硬件上自己实现两阶段提交——可行，但复杂度远超收益。

下一节把 CAS 从"单次操作"扩展成"等待与唤醒"：当临界区不是一条指令而是一段代码时，自旋与睡眠的选择决定了一致性税的总额。

## 五、锁的一致性税：futex 快路径、排队与惊群

临界区一旦超过几条指令，忙等就不划算了：等待者占着执行端口反复发原子事务，把争用放大成 N 倍一致性流量。锁的工程解法是两级结构——无争用时只付一次 CAS，有争用时把等待者交给内核睡眠、由解锁方唤醒。两级之间的切换点，就是锁的大部分性能差异所在。

| 机制 | 无争用代价 | 有争用行为 | 适用读写比 |
| --- | --- | --- | --- |
| 自旋锁 | 一次 CAS，二十拍档 | 等待者持续发 `lock` 事务，N 倍流量 | 临界区短于一次上下文切换 |
| futex 互斥量 | 一次 CAS，二十拍档 | 陷入内核入队睡眠，微秒档 | 通用，临界区长度中等 |
| 读写锁 | 一次 CAS 改计数 | 写者与读者互相排斥，写者可能饥饿 | 读远多于写 |
| 序列锁 | 读侧零原子，写侧两次自增 | 读侧重试，写者从不等待 | 读极多、写极少、数据可重读 |
| RCU | 读侧零原子零写内存 | 写者等待宽限期，数十微秒至毫秒档 | 读极多、写极少、可延迟释放 |

### 1. futex 快慢路径

futex（Fast Userspace Mutex）把"锁变量"留在用户态：加锁先做一次 CAS，成功即进入临界区，全程不陷内核；失败才调用 `FUTEX_WAIT` 把自己挂到内核等待队列，解锁方在释放时调用 `FUTEX_WAKE` 唤醒一个等待者。无争用时成本就是一次 CAS（二十拍档），有争用时多出两次系统调用（微秒档），两者差两个数量级。

这条设计的隐含前提是"争用是少数情况"。若临界区很短而争用很频繁，线程会在快慢路径之间反复横跳，每次都要陷内核、排队、唤醒，开销比自旋还大。工程上要么把临界区缩到 CAS 能覆盖的长度，要么改用分片（每核一个计数器、最后汇总）把争用从源头上拆掉。

### 2. 自旋、队列锁与惊群

自旋锁在争用时让所有等待者在原地反复执行 `lock cmpxchg`，每次失败都是一次缓存行夺权事务。N 个等待者意味着目标行的所有权在 N 颗核心之间来回弹跳，一致性流量按 N 倍放大，而真正做事的只有一个线程。因此自旋只适合"临界区短于一次上下文切换"的场合；长临界区应当立刻睡眠。

队列锁把等待者排成一列：每个等待者只在自己的本地节点上自旋，解锁方直接把锁移交给队首，只有队首节点被写一次。这把每次解锁的 O(N) 失效风暴降为 O(1)，代价是多一次链表操作与更高的常数。MCS 锁与 CLH 锁是这一族的代表，Linux 的 qspinlock 也采用排队结构。

广播唤醒是另一种浪费：解锁时唤醒全部等待者，N 个线程同时被调度、同时抢锁，只有一个成功，其余重新睡眠。这在唤醒成本低时看似无害，在核数多时会把调度器打满。正确的做法是只唤醒一个，或按队列顺序移交。

### 3. 读写锁、序列锁与争用域

读写锁把"读者共享、写者独占"编码进计数：读者只做一次原子加，写者要等所有读者退出。读多写少时它确实提升吞吐，但读者原子加本身仍会争用同一缓存行，核数一多，读侧也退化为串行。序列锁更进一步：读侧完全不加原子，只在读前读后各取一次版本号，版本不一致就重读；写侧把版本号加一、改数据、再加一。代价是读侧可能重试，收益是读侧零原子、零等待。

锁的争用范围由第二节的拓扑决定：同一 L3 域内的锁争用走片上互连，跨槽争用要走 UPI，后者一次交接就是 120 ~ 150 ns。把一把全局锁换成每 NUMA 节点一把，再在必要时合并，是把争用限制在域内的标准手法；代价是跨域合并时要再拿一次锁，锁的层级必须单向，否则死锁。

## 六、无锁读路径与安全回收：RCU 与 hazard pointer 的宽限期

锁的极端形态是"读侧完全不加锁"。读-复制-更新（Read-Copy-Update，RCU）让读者在无锁状态下遍历链表，写者复制节点、原子替换指针、延后释放旧节点。读者看到的要么是旧版本、要么是新版本，绝不会看到半更新的中间态。代价从读侧整体转移到写侧的"宽限期"。

```text
宽限期时间轴（三个读者与一个回收者）：

  读者 R0   ├──临界区──┤
  读者 R1          ├──────────临界区──────────┤
  读者 R2                        ├────┤
  回收者           │◄──────── 宽限期 ────────►│
                  摘链                      释放旧对象
                                  ▲
                          最后一个读者（R1）退出

  宽限期 = 从摘链到所有"可能持有旧指针的读者"退出的时间
```

### 1. 读侧零税的结构

RCU 读侧只做两件事：进入临界区（在非抢占内核里是一条编译器屏障）、按指针遍历。没有原子指令、没有写内存、没有缓存行夺权，因此在读极多的场景下几乎线性扩展。这条性质依赖一个前提：读者不会睡眠、不会阻塞，否则宽限期无法在有限时间内结束。用户态 RCU 因此要显式标记静止态，或依赖上下文切换作为静止点。

### 2. 宽限期与静止态

宽限期从写者摘链开始，到"所有在摘链前进入临界区的读者都退出"为止。内核通过静止态（quiescent state）判定：一个 CPU 经过一次上下文切换、一次用户态返回或一次空闲，就说明它不可能还持有旧指针。宽限期的长度因此与调度节奏同档，典型在数十微秒至毫秒级。

这段延迟就是 RCU 的税率：写者不能立即释放内存，必须等；读者拿到的收益是零开销。若写很频繁，宽限期会不断积压，内存回收跟不上分配，最终退化为内存暴涨。RCU 只适合"读极多、写极少、旧对象可延迟释放"的结构，误用到写密集场景会比锁更慢。

### 3. hazard pointer 与引用计数

hazard pointer 是用户态的替代方案：读者在遍历前把自己的 hazard 指针发布出去，回收者扫描所有线程的 hazard，确认没有线程持有该对象后才释放。读侧代价是一次 store-load 序——x86 上退化为编译器屏障，ARM 上是一条 `dmb ish` 档开销；收益是对象可以立即回收，不需要等宽限期。

引用计数是最直观的方案：每次取指针原子加一、放回原子减一，归零即释放。它的读侧税是两次原子操作，且所有线程争用同一个计数行；16 核以上时，计数行本身就是热点，扩展性比 RCU 差一个档位。三者的权衡轴是"读侧税、写侧税、内存税"：RCU 把税压在写侧与内存，hazard pointer 压在读侧的一条屏障，引用计数压在读侧的原子行。没有零成本方案，只有与读写比匹配的方案。

## 七、并发模型光谱：共享内存、消息传递与协程的载体映射

前六节都在讲共享内存模型：线程直接读写同一地址空间，用原子与屏障约束顺序。另有两类模型把同步点从缓存行移走——消息传递把同步点放进队列，协程把阻塞点放进调度器。选择哪一种，取决于问题结构里"共享状态"与"消息"哪个是本质。

| 模型 | 通信载体 | 同步点 | 典型失败模式 |
| --- | --- | --- | --- |
| 共享内存 | 同一地址空间的读写 | 缓存行、屏障、锁 | 数据竞争、伪共享、死锁 |
| actor | 每 actor 一个邮箱 | 消息入队与出队 | 邮箱积压、死信、顺序假设 |
| CSP channel | 有界或无界通道 | 发送与接收的握手 | 无缓冲通道互相等待、通道关闭竞态 |
| 协程 + 事件循环 | 单线程内的挂起队列 | `await` 点 | 阻塞调用堵死循环、丢失并行 |
| 数据并行 | 向量 lane 或 grid | kernel 边界 | 发散、合并失效、尾波 |

### 1. 同步点的位置决定扩展性

共享内存的同步点落在缓存行上，扩展性受一致性协议约束：核数越多，同一行的争用越贵。消息传递把同步点移到队列，队列本身仍要原子操作，但临界区从"一整段数据"缩成"一个头尾指针"，争用面小得多。CSP 的通道容量决定背压：无缓冲通道是 rendezvous，发送方必须等到接收方取走，两侧节奏被强制对齐；有缓冲通道把节奏解耦，代价是缓冲区本身成为共享状态。

actor 模型把状态封进单个 actor，消息串行处理，天然没有数据竞争；代价是邮箱可能积压，且"消息到达顺序"只在同一对 actor 之间成立。把 actor 当成"自带锁的对象"会低估邮箱与调度成本；把它当成"分布式节点"又会高估序列化成本。正确的定位是"以消息为同步点的单机并发单元"。

### 2. 协程与线程的切换成本

协程切换在用户态完成，只保存少量寄存器与栈指针，开销在百纳秒档；内核线程切换要陷入内核、保存完整上下文、跑调度器，开销在微秒档。两者差一个数量级，因此 I/O 密集型负载用协程可以把"等待"的成本压到可忽略；CPU 密集型负载用协程没有收益，因为计算本身就要占满核心，切换成本不是瓶颈。

协程不提供并行：单线程事件循环里，所有协程共享一个执行流，一个 CPU 密集任务就会堵死整个循环。要并行必须把协程调度到多个线程上（work-stealing 运行时），此时协程负责"等待的复用"，线程负责"计算的并行"，二者是分工而非替代。

### 3. 事件循环与 GMP 的载体分层

单线程事件循环把"就绪队列 + 回调"作为唯一调度结构：所有 I/O 完成都变成队列里的一个回调，循环按序执行。它的并发度高、切换成本低，但没有并行，且任何同步阻塞调用都会冻结整个循环。工程上的铁律是"回调里不做阻塞操作"，代价是业务代码被迫拆成状态机或协程。

Go 的 GMP 把两层叠起来：G 是协程，M 是内核线程，P 是调度上下文。运行时就绪队列把 G 多路复用到 M 上，阻塞系统调用会让 M 与 P 解绑、由其他 M 接管 P，从而不让一个阻塞调用拖住整个调度器。这属于"协程 + 线程"的混合载体，既保留了协程的切换成本，又保留了线程的并行度。

三条路线最终指向同一个判据：同步点放在哪里，成本就记在哪里。放在缓存行上，付一致性税；放在队列上，付排队与拷贝税；放在调度器上，付切换与不并行的税。选型的实质，是把税率压到与负载读写比、并行度需求相匹配的那一档。
