# 硬件组成

> **版本基准**: universal

## 定义

计算机是存储程序式电子计算机，其本质是通过指令序列对二进制数据进行变换的机器。冯·诺依曼架构将指令与数据统一存储在同一个读写存储器中，CPU 通过显式的取指-执行周期驱动所有计算。这一设计的深远影响在于：程序本身成为可以被读写、修改、甚至自生成的数据——图灵完备性的物理载体。

**归约终点**：从数学上讲，任何图灵机可归约为"一个无限状态寄存器 + 一个有限状态控制器"。冯·诺依曼机的物理实现将这个抽象具体化：寄存器文件是状态寄存器，ALU + 控制单元是有限状态控制器，内存是外部存储带。

## 数学模型

### 冯·诺依曼瓶颈的定量描述

CPU 与内存之间的带宽失衡是贯穿整个计算机体系结构的核心矛盾。设总线宽度为 $W_{\text{总线}}$ （比特/周期），内存带宽为 $B_{\text{内存}}$ （字节/秒），CPU 时钟周期为 $T_{\text{周期}}$ （秒/周期），核数为 $N_{\text{CPU}}$ 。

将所有项转换到同一单位：**每周期字节数**。

**供给侧（物理上限，不随核数变化）**：

| 来源 | 计算式 | 单位 |
|------|--------|------|
| 总线每周期可传输字节数 | $B_{\text{bus}} = W_{\text{总线}} / 8$ | 字节/周期 |
| 内存每周期可交付字节数 | $B_{\text{mem}} = B_{\text{内存}} \times T_{\text{周期}}$ | 字节/秒 × 秒/周期 = 字节/周期 |
| **端到端可用带宽** | $B_{\text{supply}} = \min(B_{\text{bus}}, B_{\text{mem}})$ | 字节/周期 |

> 注：数据从内存到达 CPU 须经总线和内存两段串联，实际端到端可用带宽取两者较小值。

**需求侧（随核数线性增长）**：

| 来源 | 计算式 | 单位 |
|------|--------|------|
| 每核每周期平均需要从内存访问的字节数 | $R_{\text{core}}$ | 字节/周期 |
| 所有核的总需求带宽 | $B_{\text{demand}} = N_{\text{CPU}} \times R_{\text{core}}$ | 字节/周期 |

**瓶颈条件**——当需求远大于供给时，CPU 大量周期被迫等待数据：

$$
B_{\text{supply}} \ll B_{\text{demand}} \quad \Longleftrightarrow \quad \min(B_{\text{bus}}, B_{\text{mem}}) \ll N_{\text{CPU}} \times R_{\text{core}}
$$

**拐点条件**：令供需相等，解得临界核数：

$$
\min(B_{\text{bus}}, B_{\text{mem}}) = N_{\text{CPU}} \times R_{\text{core}}
$$

$$
\boxed{N_{\text{critical}} = \frac{B_{\text{supply}}}{R_{\text{core}}} = \frac{\min(W_{\text{总线}}/8,\ B_{\text{内存}} \times T_{\text{周期}})}{R_{\text{core}}}}
$$

代入展开后，存在两种情形：

| 情形 | 条件 | 临界核数 | 瓶颈来源 |
|------|------|----------|----------|
| **总线受限** | $W_{\text{总线}}/8 < B_{\text{内存}} \times T_{\text{周期}}$ | $N_{\text{critical}} = \dfrac{W_{\text{总线}}/8}{R_{\text{core}}}$ | 总线带宽 |
| **内存受限** | $W_{\text{总线}}/8 > B_{\text{内存}} \times T_{\text{周期}}$ | $N_{\text{critical}} = \dfrac{B_{\text{内存}} \times T_{\text{周期}}}{R_{\text{core}}}$ | 内存带宽 |

> $N_{\text{critical}}$ 的量纲检验： $\dfrac{\text{字节/周期}}{\text{字节/周期}} = 1$ ，即临界核数无量纲，正确。

**工程估算形式**：

$$
N_{\text{critical}} \approx \frac{B_{\text{supply}}}{R_{\text{core}}}
$$

给定具体架构参数后可直接代入估算。例如：总线带宽 64 字节/周期、内存带宽折算 32 字节/周期、每核需求 4 字节/周期，则 $B_{\text{supply}} = 32$ （内存受限）， $N_{\text{critical}} = 32/4 = 8$ 核。

**自然语言解释**：

- **为什么核数只影响需求侧**： $B_{\text{supply}} = \min(W_{\text{总线}}/8,\ B_{\text{内存}} \times T_{\text{周期}})$ 中的两项——总线宽度、内存带宽、周期时间——均由硬件物理特性决定，与核数无关。核数增加只是让更多核同时向同一个供给侧发起请求，因此只改变需求侧。

- **为什么超过 $N_{\text{critical}}$ 后增加核数无效**：此时 $B_{\text{demand}} > B_{\text{supply}}$ ，所有核的总需求超过了物理上能交付的带宽。增加的核无法获得更多带宽，反而因总线争用导致所有核的等待时间变长，整体吞吐率不再提升甚至下降。

- **为什么供给侧增速远落后于核数增速**：总线宽度受芯片引脚数和 PCB 走线限制（物理约束），内存带宽受 DRAM 本身制程和菊花链拓扑限制（电气约束），而 CPU 核数依赖工艺进步可以翻倍增长。三者增速的不匹配导致 $N_{\text{critical}}$ 在历史上不断增大，但终究会被再次突破。

### 局部性原理的缓存命中率模型（AMAT）

程序的时间局部性（Temporal Locality）和空间局部性（Spatial Locality）决定了缓存效率。本节采用平均内存访问时间(Average Memory Access Time，AMAT)模型，用"敲门与开门"的比喻来清晰区分两种本质不同的量。

---

#### 一、核心概念：增量延迟（Incremental Latency）与"敲门成本"

访问某一层 Cache 时，无论最终是否命中，访问动作本身就要消耗时间。在体系结构中，**敲门成本**的真实物理含义是：**访问该层 Cache 必须完成的所有硬件前置与读取动作。** 无论是 Hit 还是 Miss，这扇门你都必须先敲，成本必定发生。

以 L1 为例，一次访问的完整"敲门"动作包含：

```
地址解码（Address Decode）
    ├── 虚拟地址 → 物理地址（TLB 并发查询；若 TLB 未命中，还需查页表）
    ├── Index 位提取（来自虚拟地址，VIPT 方式）→ 选中目标 Set
    └── Tag 位提取（来自物理地址）→ 与 Tag Array 比对
数据读取（Data Array Access）
    └── 命中后，根据 Offset 取出目标字节 → 返回 CPU
```

**敲门成本的"层级递减"特性：**

进入 L2 甚至更深层级时，不需要再像 L1 那样做繁重的虚拟地址翻译（TLB）。因为在 L1 阶段，物理地址已经获取完毕。L2 拿到物理地址后，直接提取物理 Index 和 Tag 进行比对。

> 结论：每一层的敲门成本 $\ell_i$ 都是该层**独有的、纯粹的硬件动作耗时**。

| 符号 | 含义 | 物理图像 |
|------|------|----------|
| $T_i$ | 从第 $i$ 层出发的 AMAT | CPU 感受到的平均访存时间；递归定义： $T_i = \ell_i + M_i \cdot T_{i+1}$ |
| $\ell_i$ | 第 $i$ 层增量延迟（敲门成本） | 只要你向第 $i$ 层发起了访问，就**必定付出**的过路费 |
| $L_i$ | 第 $i$ 层总命中时间 | 从 CPU 出发，一路过关斩将直到在第 $i$ 层拿到数据，**累计付出的总时间**（ $\ell_1 + \ell_2 + \cdots + \ell_i$ ） |
| $M_i$ | 第 $i$ 层局部未命中率 | 到了第 $i$ 层却吃闭门羹，被迫继续向下的概率 |
| $H_i$ | 第 $i$ 层局部命中率 | $1 - M_i$ ，在第 $i$ 层成功拿到数据并终止旅程的概率 |

---

#### 二、计算 AMAT 的两种等效视角：算的是同一笔账

把整个存储层级（L1 → L2 → L3 → 主存）看作一个整体时，如何计算平均访存时间？这里存在两种在物理和数学上**完全等价**的建模视角，它们的区别仅仅是**"记账方式"不同**。

> **核心比喻**：递推式是"按经过的收费站（动作）记账"，概率加权式是"按最终到达的目的地（位置）记账"。两者算的是同一笔物理账单，所以必然等价。

##### 视角一：按"动作"记账（增量延迟/递推式）

**核心逻辑：既然每次向下访问都必定付出当前层的敲门成本，那就把必然发生的时间提取出来。**

- 敲 L1 的门是 100% 发生的，直接记账  $\ell_1$。
- 只有在 L1 Miss 时（概率  $M_1$），才会去敲 L2 的门，记账  $M_1 \ell_2$。
- 只有在 L1 和 L2 都 Miss 时（概率  $M_1 M_2$），才会去敲 L3 的门，记账  $M_1 M_2 \ell_3$。

$$
T_1 = \underbrace{\ell_1}_{\text{必然敲L1}} + \underbrace{M_1 \ell_2}_{\text{可能敲L2}} + \underbrace{M_1 M_2 \ell_3}_{\text{可能敲L3}} + \underbrace{M_1 M_2 M_3 \ell_{\text{mem}}}_{\text{可能敲主存}}
$$

> **关键点**：敲门成本 $\ell_i$ 前面乘的不是命中率，而是**到达这一层的概率**。只要到达，就必须付钱。

##### 视角二：按"终点"记账（全局命中/概率加权式）

**核心逻辑：追问数据最终到底在哪一层被找到（互斥事件），然后乘以到达该终点所付出的"累计总时间"。**

要在第 $i$ 层命中，必须先敲过前面所有的门。因此"总命中时间"是敲门到该层为止的**累计时间**：

$$
L_1 = \ell_1, \quad L_2 = \ell_1 + \ell_2, \quad L_3 = \ell_1 + \ell_2 + \ell_3, \quad L_{\text{mem}} = \ell_1 + \ell_2 + \ell_3 + \ell_{\text{mem}}
$$

在第 $i$ 层命中 = 敲过所有前面的门，被第 $i$ 层开门：

$$
T_1 = \underbrace{H_1 L_1}_{\text{终点是L1}} + \underbrace{M_1 H_2 L_2}_{\text{终点是L2}} + \underbrace{M_1 M_2 H_3 L_3}_{\text{终点是L3}} + \underbrace{M_1 M_2 M_3 L_{\text{mem}}}_{\text{终点是主存}}
$$

展开含义（按概率从高到低）：

- $H_1 L_1$ ：数据在 L1 被找到（概率 $H_1$ ，耗时 $L_1 = \ell_1$ ）
- $M_1 H_2 L_2$ ：数据在 L2 被找到（概率 $M_1 H_2$ ，耗时 $L_2 = \ell_1 + \ell_2$ ）
- $M_1 M_2 H_3 L_3$ ：数据在 L3 被找到（概率 $M_1 M_2 H_3$ ，耗时 $L_3$ ）
- $M_1 M_2 M_3 L_{\text{mem}}$ ：数据在主存被找到（概率 $M_1 M_2 M_3$ ，耗时 $L_{\text{mem}}$ ）

---

#### 三、为什么它们完全等价？（代数证明）

很多初学者误以为"把内存看作整体时，只能用概率加权式"。这是思维误区。我们将"视角二（概率加权）"彻底展开，按 $\ell_i$ 重新合并同类项，看看每一笔"过路费"到底向谁收了：

$$
\text{对于 } \ell_1: \underbrace{H_1}_{1-M_1} + \underbrace{M_1 H_2}_{M_1(1-M_2)} + \underbrace{M_1 M_2 H_3}_{M_1 M_2(1-M_3)} + \underbrace{M_1 M_2 M_3}_{\text{去主存的人}} = 1
$$

*含义：不管你在哪层找到数据，所有人都得付 L1 的敲门费，系数为 1*

$$
\text{对于 } \ell_2: \underbrace{M_1 H_2}_{M_1(1-M_2)} + \underbrace{M_1 M_2 H_3}_{M_1 M_2(1-M_3)} + \underbrace{M_1 M_2 M_3}_{\text{去主存的人}} = M_1
$$

*含义：只有经过 L1 未命中的那部分人，才需要付 L2 的敲门费，系数为 $M_1$ *

$$
\text{对于 } \ell_3: \underbrace{M_1 M_2 H_3}_{M_1 M_2(1-M_3)} + \underbrace{M_1 M_2 M_3}_{\text{去主存的人}} = M_1 M_2
$$

*含义：只有经过 L1/L2 未命中的那部分人，才需要付 L3 的敲门费，系数为 $M_1 M_2$ *

数学上完美闭环：

$$
\boxed{\text{概率加权式的展开结果} \equiv \ell_1 + M_1 \ell_2 + M_1 M_2 \ell_3 + M_1 M_2 M_3 \ell_{\text{mem}} \equiv \text{递推式}}
$$

#### 四、直观的数据实例验证

设典型 x86-64（如 AMD Zen 3）架构参数：

- 敲门费（增量延迟）： $\ell_1 = 4$ 周期， $\ell_2 = 12$ 周期， $\ell_3 = 40$ 周期， $\ell_{\text{mem}} = 220$ 周期。
- 累计耗时（总时间）：  $L_1 = 4$，  $L_2 = 16$，  $L_3 = 56$，  $L_{\text{mem}} = 276$。
- 未命中率：  $M_1 = 5\%$，  $M_2 = 10\%$，  $M_3 = 20\%$。

**用递推式计算（极速版）**：

$$
T_1 = 4 + (0.05 \times 12) + (0.005 \times 40) + (0.001 \times 220) = \mathbf{5.02 \text{ 周期}}
$$

**用概率式计算（追踪终点版）**：

- L1 命中（终点 L1）：概率  $95\%$，耗时 4 → $0.95 \times 4 = 3.80$
- L2 命中（终点 L2）：概率  $0.05 \times 0.90 = 4.5\%$，耗时 16 → $0.045 \times 16 = 0.72$
- L3 命中（终点 L3）：概率  $0.05 \times 0.10 \times 0.80 = 0.4\%$，耗时 56 → $0.004 \times 56 = 0.224$
- 去往主存（终点 Mem）：概率  $0.05 \times 0.10 \times 0.20 = 0.1\%$，耗时 276 → $0.001 \times 276 = 0.276$
- **合计**： $3.80 + 0.72 + 0.224 + 0.276 = \mathbf{5.02 \text{ 周期}}$

**缓存层级访问流程（视角一）**：

```
L1 --> ℓ_1 = 4       (100% 到达)
  \ miss (5%)
   L2 --> ℓ_2 = 12    (5% 到达)
     \ miss (10%)
      L3 --> ℓ_3 = 40 (0.5% 到达)
        \ miss (20%)
         DRAM --> ℓ_mem = 220 (0.1% 到达)
```

#### 五、两种等效视角的比较与工程指导

不存在"把内存看作整体时不能用递推式"的说法，它们是同一条物理真理的一体两面。在实际工程中，两者的应用场景各有侧重：

| 视角 | 物理思维 | 数学特征 | 工程用途 |
|------|----------|----------|----------|
| **递推式**（增量延迟） | 流水线思维（看路径）：关注每一次跨越层级的动作成本 | 提取公因式，极其精简 | **硬件架构师最爱。** 方便快速心算，用来评估某条互连总线或某级缓存设计的延迟红利 |
| **概率加权式**（全局命中） | 分布思维（看位置）：关注数据最终驻留在哪里 | 全概率公式，互斥展开 | **软件/性能调优工程师最爱。** 直观展示各个层级对访存时间的"贡献占比"，一眼看出性能瓶颈究竟在哪一层 |

> **直击本质的一句话**：递推式是"按经过的收费站（动作）记账"，概率加权式是"按最终到达的目的地（位置）记账"——同一笔账单，两种数法。

等价性的代数证明见**第三节**。

#### 六、寻址机制：地址是如何被"肢解"的？

程序发出虚拟地址(Virtual Address，VA)，MMU 将其翻译为物理地址(Physical Address，PA)，缓存控制器再将 PA 精确地切分为三段。

**打工人比喻体系**（配合 AMAT 敲门模型理解）：

| 硬件单元 | 比喻角色 | 说明 |
|----------|----------|------|
| 算术逻辑单元(Arithmetic Logic Unit，ALU) | 超级打工人 | 手速极快，但被焊在工位上，只处理手里的数据 |
| 寄存器（Registers） | 打工人的双手 | 真正发生计算的地方，容量极小（64 位 × 几个寄存器） |
| L1 缓存 | 办公桌面 | 极快（3-4 周期），CPU 核私有；分 L1i（指令）和 L1d（数据） |
| L2 缓存 | 办公桌下抽屉 | 较快（12 周期左右），CPU 核私有 |
| L3 缓存 | 部门公共档案室 | 较慢（40 周期），同 CCX 多核共享；也是 L2 淘汰文件的"受害者缓存" |
| 主存（DRAM） | 公司总部大仓库 | 慢（200+ 周期），海量（16GB+） |
| SSD / HDD | 外部物流中转站 | 极慢，数据永久保存地 |
| 操作系统 & MMU | 安保部与物流调度 | VA→PA 翻译，页面置换调度 |

**关键物流单位**：

| 单位 | 大小 | 说明（物流隐喻与物理实质） |
|------|------|------|
| 字 / 字节 (Word/Byte) | 1~8 字节（现代 64 位 CPU 通常为 8 字节） | "打工人手里的'单件物品'。这是 ALU (算术逻辑单元) 和寄存器真正能够吞吐、计算的精确颗粒度。无论 Cache 搬来多大的货箱，数据通过 MUX (多路复用器) 从货箱中精准'夹取'这 4 字节（int）或 8 字节（long），放入寄存器（双手），ALU (超级打工人) 再从寄存器中取出数据进行计算。" |
| 缓存行 (Cache Line) | 固定 64 字节 | "标准化集装箱"。硬件层面的最小搬运单位。出于空间局部性（买一送多），哪怕程序只声明读取 1 个字节的 char，内存控制器也会雷打不动地打包相邻的 64 字节，装进集装箱送往 L1 Cache。 |
| 内存页 (Page) | 通常 4KB | "重型货柜"。操作系统 (OS) 管理内存的最小基本盘。当发生缺页中断时，DMA 自动搬运车会一次性将整个 4KB 的货柜从硬盘 Swap 区拉入物理内存 (DRAM)。 |

**VIPT 机制：L1 缓存的"跨时空并行"奇迹**

通常，必须等 MMU/TLB 把 VA 翻译成 PA 后才能查缓存（即 PIPT，用于 L2/L3）。但这太慢了。为了追求极致的 $\ell_1$ 敲门速度，L1 Cache 采用了 VIPT (Virtually Indexed, Physically Tagged) 技术：用虚拟地址找组（快），用物理地址比对标签（准）。

在 4KB 分页（低 12 位为页内偏移）和 64 字节 Cache Line 的标准系统中，地址切分如下：

```
虚拟地址(VA)
 ┌──────────────────────┬──────────────────────┐
 │     VPN (虚拟页号)   │   Page Offset (12位) │
 └───────────┬──────────┴──────────┬───────────┘
             │ TLB 翻译            │ 物理透传 (不被翻译改变)
             ▼                     ▼
 ┌──────────────────────┬──────────────────────┐
 │     PPN (物理页号)   │   Page Offset (12位) │
 └───────────┬──────────┴────────┬─┴─────────┬─┘
             │                   │           │
       【Tag 比对】        【Index 寻址】 【Offset 提取】
```

- **块内偏移 (Block Offset)**：锁定 64 字节集装箱内的具体字节，需 6 位（  $2^6 = 64$）。

- **组索引 (Set Index)**：因为页内偏移（低 12 位）在 VA 和 PA 中是绝对相同的，硬件直接截取 VA 的  $Bit\ 6 \sim 11$（共 6 位）去定位 L1 的 Set。此时 TLB 还在旁边苦苦翻译高位地址。（零延迟并行！）

**查询流程（从大到小）**：

```
第一层：L1 整体定位
└── VA 的 Bit 6~11 → Index → 立即定位到 64 个 Set 中的某一个（零延迟并行！）

第二层：Set 内部定位 Way
└── TLB 翻译完成，得到 PA 高位
└── 用 PA 高位与 Set 内 8 个 Way 的 Tag 同时比对
└── Tag 匹配 → 命中某个 Way；Tag 不匹配 → L1 Miss → 继续查 L2/L3/DRAM

第三层：Way 内部的 Cache Line 夹取
└── 命中后，数据从 L1 Data Array 输出 64 字节缓存行
└── VA 的 Bit 0~5 (Offset) → 定位缓存行内目标字节起始位置
└── MUX 根据指令类型（int 4字节 / long 8字节）夹取连续数据
└── 夹取的数据放入寄存器 → ALU 计算
```

整个流程的关键在于：**Index 寻址（快）和 Tag 比对（准）并行执行**，而传统 PIPT 必须等 TLB 完成才能开始寻址。

**Cache Line 的内部结构：数据是如何被夹取的**

Cache Line 是 64 字节的"集装箱"，命中后数据从 L1 Data Array 送出：

```
L1 Data Array 输出的 64 字节缓存行：
┌────────┬────────┬────────┬─────────┬────────┬────────┬─────────┬────────┐
│ Byte 0 │ Byte 1 │ Byte 2 │ ...     │ Byte 6 │ Byte 7 │ ...     │Byte 63 │
└────────┴────────┴────────┴─────────┴────────┴────────┴─────────┴────────┘
          ↑ Offset (Bit 0~5) 精确定位     ↑ MUX 夹取
                                           │
                              ┌────────────┴────────────┐
                              │  若程序读 int (4字节)：  │
                              │  MUX 从偏移位置夹取连续4字节 │
                              │  若程序读 long (8字节)：  │
                              │  MUX 从偏移位置夹取连续8字节 │
                              └────────────┬────────────┘
                                           ▼
                                    放入寄存器（双手）
                                           ▼
                                    ALU (超级打工人) 计算
```

- **Offset（6 位）**：从 VA/PA 低位提取，精准定位 64 字节集装箱内的目标字节起始位置。
- **MUX（多路复用器）**：根据程序指令类型（int/long），从缓存行中夹取连续 4 字节或 8 字节，送入寄存器。
- **寄存器 → ALU**：数据就位后，ALU 才能真正开始计算。

> **为什么不全部用 VA**：L2 及以下层级必须用 PA 才能保证跨核一致性；L1 用 VIPT 是利用页内偏移不改变这一特性，在 TLB 查询同时并行做 Index 寻址。

**硬核推导：为什么 L1 Cache 不能无限做大？**

为了不产生严重的"缓存别名（Aliasing）"问题，Index 的位数必须被限制在未经翻译的页内偏移中：

$$
Index 位数 + Offset 位数 \le 12 \text{ 位（4KB 页的偏移）}
$$

即 Index 最多只能有 6 位（  $12 - 6 = 6$），对应 $2^6 = 64$ 个 Set。

假设是 8 路组相联 (8-Way)，L1 的物理极限大小为：

$$
64 \text{ (Set)} \times 8 \text{ (Way)} \times 64B = 32KB
$$

这就是为什么市面上大量 CPU 的 L1 数据缓存都被精准定格在 32KB 的数学根本原因！

#### 七、arr[0]++ 的微观全景工作流

以 Core 0 执行 `arr[0]++` 为例，完整追踪数据在层级间的流转与淘汰过程。

**步骤 1：发号施令与 L1 的组内微观淘汰**

CPU 发出 arr[0] 的虚拟地址(Virtual Address，VA)，L1 缓存控制器用 VA 截取组索引(Set Index，Index)，径直走向 L1 的 Set 5（假设 arr[0] 映射到此）。同时翻译后备缓冲区(Translation Lookaside Buffer，TLB) 将 VA 翻译为物理地址(Physical Address，PA)。标签(Tag，Tag) 比对 PA 高位与 Set 5 内 8 个 Way 的标签——全不匹配，**L1 未命中(L1 Miss)**。

此时 L1 发现 8 个槽位全满，必须淘汰一个。硬件检查每条缓存行(Cache Line，Cache Line)的"活跃度计数器"（年龄位），无情地选出最老的那条，准备踢出。这就是**微观最近最少使用淘汰(Micro LRU Eviction)**——每次数据被访问，年龄归零（返老还童）；长期不被访问则年龄不断增长，直到被踢。

**步骤 2 & 3：跨越层级的接力索求（L2 → L3）**

请求传给 L2（抽屉），按 L2 的组索引(Set Index，Index)/标签(Tag，Tag) 结构再次查找——**L2 未命中(L2 Miss)**。

请求通过总线传给 L3 公共档案室，同时顺带总线监听/嗅探(Snoop，Snoop)其他核的 L2 有无此数据——**L3 未命中(L3 Miss)**。

**步骤 4：宏观物流介入（大仓库与缺页中断）**

内存控制器向 DRAM 大仓库要货。假设极度倒霉，包含 arr[0] 的那一页（4KB）根本不在 DRAM 里，还在硬盘上！触发**缺页中断（Page Fault）**，CPU 暂停。

OS 调度直接内存访问(Direct Memory Access，DMA，自动搬运车)去硬盘读取这 4KB 数据放入 DRAM。若 DRAM 已满，OS 把最老的一页（4KB）打包扔回硬盘 Swap 区——这就是**宏观页面置换淘汰**。

数据从 DRAM 发出，打包为 64 字节的 Cache Line 货箱，顺总线杀回 CPU。

**步骤 5：回填穿透与驱逐（Zen 架构的精妙之处）**

64 字节货箱回到 CPU。AMD Zen 架构下，为节省 L3 公共空间，货箱直接**无视/穿透 L3**，填入 Core 0 的 L2，并进一步送到 L1 桌面。

与此同时，步骤 1 中选中的"最老货箱"被一脚踢出 L1。依据 Exclusive 策略（AMD Zen 采用），老货箱若在 L2 中有副本则上移 L2，否则继续下探——最终**落入 L3 作为受害者缓存**。这正是 L3 作为"淘汰文件收容站"的核心价值。

**步骤 6：多路复用器与算术逻辑单元提取计算（真正的"工作"）**

64 字节货箱稳稳停在 L1 Set 5 某 Way 中，标签(Tag，Tag) 已标记，年龄已归零。

多路复用器(Multiplexer，MUX) 登场：根据地址中的块内偏移(Block Offset，Offset) = 0，精准地从 64 字节中夹出前 4 个字节（arr[0]），送入 CPU 通用寄存器（如 EAX）。

算术逻辑单元(Arithmetic Logic Unit，ALU) 拿起这 4 字节，在 **1 个时钟周期**内完成 +1 操作。

> **补充：L1 命中时的块内偏移(Block Offset) 工作流程**
>
> 若 arr[0] 已在 L1 中（**L1 命中(L1 Hit)**），则 Tag 比对成功后同样需要 Offset 来选取特定字节：
> 1. 标签(Tag，Tag) 比对成功 → 选中了 Set X 中某个 Way 的缓存行（64 字节）
> 2. 块内偏移(Block Offset，Offset) = 0 → 从该缓存行的首字节取出 4 字节（arr[0]）
> 3. 多路复用器(Multiplexer，MUX) 根据 Offset 将数据送入寄存器，算术逻辑单元(Arithmetic Logic Unit，ALU) 执行运算
>
> 命中与未命中的区别仅在于是否需要跨层级索取数据，Offset 的作用完全相同。

**步骤 7：写回与脏标记（Store & Dirty Bit）**

计算完成后，CPU 发出 Store 指令，把新值写回 L1 中该货箱的对应位置。此时 L1 货箱与 DRAM 里的数据不一致了。

硬件给这个货箱贴上**"脏(Dirty)"标签**。当该货箱未来某次被淘汰（回到步骤 1）时，脏数据会一路写回 L3，最终回写到 DRAM，完成数据一致性闭环。

### 存储层次容量-延迟积（Area-Latency Product）

每一层缓存都面临容量与延迟的根本取舍。SRAM 每个 bit 需要 6 个晶体管，DRAM 每个 bit 只需 1 个电容 + 1 个晶体管，但 DRAM 需要周期性刷新且访问更慢。第 $i$ 层的面积-延迟积定义为：

$$
AP_i = S_i \times L_i
$$

其中 $S_i$ 为容量， $L_i$ 为命中延迟。这个乘积的几何意义是：单位面积上能"保持在场"的数据量与访问速度的折中。L1 的 AP 最小（32KB × 4周期），L3 的 AP 最大（64MB × 40周期）。

### NUMA 架构的内存访问延迟模型

在多路服务器中，每个 CPU 核心有本地 DRAM，访问远程 DRAM 需要通过 CPU 互连（QPI/UPI/ Infinity Fabric）。访问延迟建模为：

$$
T_{内存访问} = \begin{cases}
L_{本地} & \text{访问本地节点} \\
L_{本地} + L_{互连} + L_{远程} & \text{访问远程节点}
\end{cases}
$$

其中 $L_{互连}$ 通常比 $L_{本地}$ 高 1.5-2 倍。在 4 路系统中，跨节点访问延迟可达本地访问的 2-3 倍。

### 修改/独占/共享/无效(Modified Exclusive Shared Invalid，MESI) 协议状态转移矩阵

缓存一致性协议确保多个核的缓存行视图一致。MESI 是最基础的协议，四个状态：

| 当前状态 \ 请求 | BusRd | BusRdX | BusUpgr | Flush |
|-----------------|-------|--------|---------|-------|
| **M**（Modified） | → I（响应数据后失效） | → M（自身已是所有者） | → I（升级为独占写） | → M（刷新自身脏行） |
| **E**（Exclusive） | → S（总线共享） | → I（总线独占写） | → I | → E |
| **S**（Shared） | → S（已有共享副本） | → I（invalidate 自身） | → I | → S |
| **I**（Invalid） | → S/E（从提供者接收数据） | → I（总线独占写） | → I | → I |

**BusRd**（总线读）：其他核发起读请求，所有监听核将共享行置为 S，或独占地提供数据（若状态为 M/E 则提供数据后置为 S）。**BusRdX**（总线读-独占）：其他核发起写请求（读-改-写原子操作），所有监听核 invalidate 自身副本。**BusUpgr**（总线升级）：写请求但数据未变化（仅需 invalidate），可合并为 BusRdX 以节省总线事务。**Flush**：持有脏数据的核将数据写回主存。

### 核间缓存行迁移延迟量化模型

核间缓存行迁移延迟 $L_{migrate}$ 是理解多核性能的关键：

$$
L_{migrate} = L_{snoop} + L_{transfer} + L_{protocol}
$$

- $L_{snoop}$ ：总线嗅探延迟（~20ns），核检测到总线请求并决定响应的时间
- $L_{transfer}$ ：数据在互联网络上传输的延迟（~40ns/跳），Mesh 拓扑每增加一跳额外 ~5ns
- $L_{protocol}$ ：协议状态机转换开销（~10ns）

典型跨插槽迁移延迟：~100ns，远超 L1 命中的 4 周期（约 1-2ns）。

### 缓存一致性协议广播 vs 目录

广播协议（如 MESI 的总线嗅探）在核数增加时成为瓶颈——每次请求都广播到所有核。目录协议为每个内存行维护一个目录节点，记录哪些核持有副本：

$$
\text{目录访问延迟} = \begin{cases}
O(1) & \text{本地节点} \\
O(\log_2 N) & \text{跨节点，N 为节点数}
\end{cases}
$$

这在 4+ 插槽系统中比广播协议高效得多。

## 机制

### 冯·诺依曼架构

程序与数据共存于同一内存，CPU 通过共享总线访问。这一设计在 1945 年是天才之举，但它创造了一个根本矛盾：CPU 与内存之间的语义不对等——CPU 以 GHz 运行，内存带宽以 GB/s 计量，两者相差 2-3 个数量级。

**本质问题**：CPU 计算速度增长（摩尔定律）远超内存带宽增长，导致算力无法被充分利用。缓解手段是缓存层次结构。

**约束条件**：
- 内存访问带宽决定整机性能上限，CPU 算力无法完全发挥
- 总线争用导致 CPU 与 I/O 设备竞争访问权
- 指令流和数据流共享同一物理通道

**违反后果**：
- 当缓存命中率低于 95% 时，CPU 大部分时间在等待数据
- DMA 设备与 CPU 并发访问内存时，若无一致性协议协调，会导致缓存脏数据问题
- 多核时代缓存一致性协议（MESI/MESIF）成为性能瓶颈——核间通信延迟可达 100+ 周期

### 内存层级

**包容型缓存 vs 独占型缓存(Inclusive vs Exclusive Cache)**：

包容型缓存(Inclusive Cache，Inclusive，Intel 常用)策略：L1d ∩ L2 = L1d，L3 包含所有上行数据。优点是 L1d/L2 未命中时可直接检查 L3，无需下探主存。缺点是存储冗余——同一行可同时存在于 L1/L2/L3。

独占型缓存(Exclusive Cache，Exclusive，AMD Zen 常用)策略：L1d ∪ L2 ∪ L3 = 全部数据，无重复。优点是总容量最大化。缺点是查询路径更长——L1d 驱逐时必须查找 L2（若 L2 有副本则上移，否则下探 L3 或主存）。

**包容型缓存的一致性代价**：

若 L3（共享）中的某行被修改，L3 的 snoop filter 需向所有核广播 invalidation，即使 L1d/L2 中没有该行。这在某些 workloads 下造成不必要的广播流量。AMD Zen 的 M (Modified) 状态设计回避了这个问题。

**嗅探过滤器(Snoop Filter，Snoop Filter)**：

现代多核系统的 L3 包含 snoop filter，记录每个缓存行在哪些核的 L1/L2 中有副本。有了 snoop filter，跨插槽请求可以精确地只向持有副本的核发送，而非广播到所有核。这在 4+ 核系统中显著降低总线流量。

**缓存行大小与未命中的权衡**：

Cache line 通常为 64 字节。这是空间局部性与带宽浪费的折中：
- 更大的行有利于顺序访问（空间局部性好）
- 更大的行导致更多伪共享（两个核修改同一行的不同字节）
- 更大的行意味着未命中时传输更多数据（但带宽利用率取决于访问模式）

**违反后果**：
- 数据局部性差导致缓存未命中——每次未命中需从下级存储加载整个 cache line
- 伪共享（False Sharing）：两个核修改同一 cache line 的不同字节，导致 MESI 协议下的写穿透，性能骤降数倍
- Snoop filter miss 导致广播而非精确失效，增加延迟

### 翻译后备缓冲区层级(Translation Lookaside Buffer Hierarchy)

翻译后备缓冲区(Translation Lookaside Buffer，TLB)是页表查找的硬件缓存，将虚拟地址到物理地址的转换结果缓存起来。

**TLB 的结构**：

| 层级 | 条目数 | 命中延迟 | 备注 |
|------|--------|----------|------|
| L1 ITLB / DTLB | 32-64 项/核 | 1 周期 | 分离的指令/数据 TLB |
| L2 STLB | 512-1024 项/核 | 7-10 周期 | 共享 TLB |

**地址空间标识符(Address Space Identifier，ASID)**：

软件（操作系统）用 ASID 区分不同进程的页表条目，实现 TLB 的进程间共享而无需在每次上下文切换时 flush TLB。x86-64 使用进程上下文标识符(Process Context Identifier，PCID)，ARM 使用 ASID。TLB 条目结构：`(VPN, PFN, ASID, valid, protection)`。

**击落TLB(TLB Shootdown，TLB Shootdown)**：

当操作系统修改页表（如 munmap、页面换出）时，必须使受影响进程的 TLB 条目失效。跨核的 TLB shootdown 需要处理器间中断(Inter-Processor Interrupt，IPI)广播到所有核，代价高昂（数百周期）。大页(Huge Page，HugePage)减少 TLB 条目数，降低 shootdown 频率。

**约束条件**：
- TLB miss 代价：L1 TLB miss → L2 STLB → 页表遍历（Memory） → 4-30 额外内存访问
- TLB shootdown 阻塞所有受影响核上的当前线程，造成调度抖动

**违反后果**：
- TLB miss 代价：L1 TLB miss → L2 STLB → 页表遍历 → 4-30 额外内存访问
- TLB shootdown 阻塞所有受影响核上的当前线程，造成调度抖动

### 存储层次

速度/容量/成本构成不可能三角：SSD 的延迟是 DRAM 的 1000 倍，HDD 的延迟是 SSD 的 1000 倍，但每 GB 成本也相应降低 1000 倍。

**NVMe 消除协议栈开销**：

传统 SATA SSD 需经过 南桥 → SAS/SATA 控制器 → AHCI 协议层，路径漫长。NVMe 直接挂在 PCIe 总线上，协议专为 NAND Flash 特性优化（多队列、并行化），延迟降低 50%+。

**NAND Flash 的物理特性与 SSD 内部机制**：

NAND Flash 以 page（通常 16KB）为读写单元，以 block（通常 256-512 page）为擦除单元。写操作只能将 bit 从 1 改 0；若需将 bit 改回 1，必须擦除整个 block（耗时 1-3ms）。SSD 控制器通过 FTL（Flash Translation Layer）将逻辑页映射到物理页，并维护一个写放大因子（Write Amplification Factor）：

$$
WAF = \frac{\text{实际写入 Flash 的数据量}}{\text{主机写入量}}
$$

WAF 通常为 1.5-10，取决于碎片化程度。GC（Garbage Collection）运行时会产生额外的写入放大。

**约束条件**：
- HDD 机械寻道限制吞吐量（~100MB/s 顺序读，~1MB/s 随机读）
- SSD 无机械部件但写入寿命有限（TBW：500 TBW/1TB 典型）
- NVMe PCIe 直连消除协议开销（5-7 GB/s vs SATA SSD 的 550 MB/s）
- SSD 的 GC 导致写入时出现突发延迟

**违反后果**：
- 数据库等随机访问场景用 HDD 导致性能灾难——1 次查询需要 10+ ms 寻道
- 写入密集型应用（日志、缓存淘汰）忽略 TBW 导致固态衰减到只读
- SSD 碎片化导致 WAF 上升，写入性能随使用时间下降

### NUMA 架构

多路服务器中，每个 CPU 核心有本地 DRAM，访问远程 DRAM 需要通过 CPU 互连。

**NUMA 距离感知编程**：

- 线程应优先在本地节点分配内存
- 关键数据结构的内存布局应匹配访问模式
- libnuma / hwloc 工具可用于查询 NUMA 拓扑

**Linux NUMA 平衡策略**：

Linux 默认使用 first-touch 策略（内存在哪里被首次触碰就属于哪个节点），以及 numa_balancing 机制（定期将进程迁移到更近的节点，或将内存迁移到活跃线程所在节点）。后者开销较大，在高性能场景通常禁用。

**内存一致性在 NUMA 中的代价**：

跨节点缓存行传输不仅增加内存访问延迟，还需要更复杂的一致性协议（目录协议 vs 广播协议）。目录协议在 4+ 插槽系统中比广播协议更高效——每个内存行有一个目录节点记录哪些核持有副本，避免广播风暴。

**约束条件**：
- 跨节点内存访问延迟比本地访问高 1.5-2 倍
- 跨节点 cache line 传输需要更复杂的一致性协议
- 内存分配策略（first-touch vs numa_balancing）影响性能

**违反后果**：
- 不感知 NUMA 的程序在 4 路服务器上可能有 2-3 倍性能差距
- 关键路径跨节点访问成为瓶颈
- 跨节点内存分配导致跨插槽的缓存行 bounce，加剧一致性协议开销
