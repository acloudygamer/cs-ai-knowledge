# GPU 与异构计算

## 一、资源预算的分野：两条指令供给路径

一条 `Load` 未命中缓存时，依赖它的指令必须等待。CPU 与图形处理器（Graphics Processing Unit，GPU）都要利用这段等待期。差别主要在于，它们从哪里取得下一条可执行指令。在 NVIDIA GPU 中，这项调度由流式多处理器（Streaming Multiprocessor，SM）完成。

```text
一次缓存未命中后的指令供给（等待期的下一条指令从哪里来）：

                         Load 未命中
                              │
                              ▼
                    依赖指令等待数据返回
                              │
          ┌───────────────────┴───────────────────┐
          ▼                                       ▼
  乱序 CPU 大核：检查同一硬件线程的窗口     GPU SM：检查驻留 warp
          │                                       │
          ▼                                       ▼
  发射其中已经就绪的独立指令               选择有就绪指令的 warp
          │                                       │
          ▼                                       ▼
  没有可发射的独立指令时停顿               没有就绪 warp 时停顿
          └───────────────────┬───────────────────┘
                              ▼
                    数据返回，原依赖链继续
```

### 1. 硬件状态决定指令候选

典型乱序 CPU 大核用重命名映射、调度窗口与 ROB 跟踪同一硬件线程的在飞指令。调度器检查后续指令的数据依赖与操作数，已经就绪的独立指令可以先执行。这些指令最后仍按程序顺序退休。分支预测负责维持取指供给，不负责重排数据依赖。

SM 主要用多组线程提供候选。warp 是 SM 的线程调度单位。每个驻留 warp 的上下文都保存在片上，选择另一个驻留 warp 时不必换出上下文。调度器在发射时选择有就绪指令的 warp。

CPU 侧的状态扩大单个硬件线程内的搜索范围，GPU 侧的状态扩大可切换的 warp 集合。前者优先改善单个硬件线程的吞吐，后者优先维持多线程聚合吞吐。

| 比较项 | 典型乱序 CPU 大核 | NVIDIA GPU SM |
| --- | --- | --- |
| 候选指令的主要来源 | 同一硬件线程的后续指令 | 驻留 warp 的就绪指令 |
| 主要状态成本 | 重命名映射、调度窗口、ROB | 各驻留 warp 的寄存器与调度状态 |
| 直接收益 | 单个硬件线程在等待期仍能推进独立工作 | 多线程在等待期仍能填充发射槽 |
| 发射停顿条件 | 窗口内没有可发射的独立指令 | 没有任何 warp 提供就绪指令 |

这些结构都要占面积并消耗功耗。乱序 CPU 大核与 SM 又不是等面积、等功能的标准单元，因此不能据此推出固定面积配比或通用能效倍数。CPU 也可用硬件多线程补充候选。GPU 也可利用同一 warp 的独立指令。两条路径是设计倾向，不是互斥的功能清单。

### 2. 隐藏的是等待期，不是访存延迟

缓存、分支预测与乱序执行作用于不同节点。缓存命中缩短本次访问。分支预测减少控制流造成的前端空档。乱序执行在等待期发射独立指令。三者不能合并成一种“压低访存延迟”的机制。

一次已经发出的高带宽显存（High Bandwidth Memory，HBM）访问，其数据返回时间不因多 warp 调度本身而提前。调度器只是让等待与就绪 warp 的计算重叠，减少单个 warp 暴露的停顿。若所有 warp 都在等待内存或同步，发射槽仍会空闲。

驻留 warp 数表示当前可参与调度的 warp 数，不等于其中有多少就绪。延迟隐藏能力因此不与驻留数成正比。新增 warp 能否提高吞吐，还取决于执行端口、内存带宽和每个 warp 的指令级并行。并发请求过多时，排队与带宽争用还可能延长等待。

### 3. 负载决定两条路径的收益

GPU 的聚合吞吐来自许多 warp 同时推进，不是单个 warp 的依赖链更短。并行任务不足时，执行阵列缺少工作。warp 内控制流频繁分裂时，发散路径上的一次发射只覆盖其中一部分线程。

不规则访存通常会增加内存事务，降低带回字节的利用率。它会削弱 GPU 的有效带宽，却不能单独推出 GPU 一定慢于 CPU。比较两种平台必须固定任务、数据规模与精度要求，再分别计量计算、搬运、启动与同步成本。

因此，串行依赖与复杂控制流通常更适合留在 CPU。并行规模足够、发射与访存损失可控的段，才值得考虑交给 GPU。只有加速收益覆盖跨设备搬运、启动与同步成本，卸载才有端到端收益。

## 二、SIMT 执行模型：warp 发射、发散与驻留上限

在 NVIDIA GPU 中，单指令多线程（Single Instruction, Multiple Threads，SIMT）让程序员按独立线程写控制流，硬件则按 warp 组织发射。每个线程保有自己的寄存器状态。线程可以走不同路径；发射到某条路径时，其他路径的 lane 会被活跃掩码屏蔽。

```text
一个 warp 的 if/else 发射抽象（按 then → else 分组示意，只画该 warp）：

  阶段             lane 0-15          lane 16-31        活跃掩码
  ────────────────────────────────────────────────────────────────
  比较 A[i]>0      执行比较            执行比较           0xFFFFFFFF
  then 段发射      C[i]=A[i]+B[i]     屏蔽               0x0000FFFF
  else 段发射      屏蔽               C[i]=B[i]          0xFFFF0000
  可重汇聚时       后续共同指令        后续共同指令        0xFFFFFFFF

  两条路径都执行时，各自的路径内发射指令数可累加；公共指令、控制开销与停顿另计。
  墙钟时间不能一般写成 then + else：路径可交错，其他 warp 还会共享资源。
```

### 1. warp 打包与活跃掩码

SM 把线程块（block）内连续编号的每 32 个线程组成一个 warp。线程数不足 32 的末尾 warp 会留下无效 lane。warp 是调度与发射单位，lane 是线程在 warp 内的位置；32 个 lane 不代表 32 条独立指令。

无发散时，全部有效 lane 可以共享当前指令的取指与译码。发散时，不同路径需要分别发射，活跃掩码决定哪些 lane 参与。分支发散只发生在 warp 内；不同 warp 在分支意义上可独立推进，同步与数据依赖仍会约束其进度。

### 2. 分支从编译选择到硬件发散

短分支可以先在编译期消失。编译器可使用谓词指令或选择指令消除实际分支；在谓词形式下，谓词为假的线程不写结果，也不计算地址或读取操作数。同章《指令集架构与 SIMD》§四.3 给出谓词掩码按位选择写回的契约语义，这里把同一语义对应到 warp 的活跃掩码上：掩码只决定哪些 lane 提交结果，不改变控制流。是否这样变换取决于路径长度、副作用、目标架构与编译器启发式，不存在通用的固定指令数阈值。

保留下来的分支若让 lane 走向不同路径，就形成 warp 发散。硬件按路径发射指令，并用活跃掩码屏蔽不在当前路径的线程。若 32 个 lane 各走一条路径，每次发射可能只剩一个活跃 lane；1/32 只是该极端指令或区域的活跃比例，不是整个设备程序的吞吐或能效下界。

Volta 起的独立线程调度（Independent Thread Scheduling）为每个线程维护程序计数器与调用栈。warp 调度器仍选择含就绪线程的 warp，但不同进度的线程可以独立等待，并在子 warp 粒度重新组合活跃线程；不是每个线程各有一个调度器。自然重汇聚不再保证发生在固定点。需要依赖同 warp 线程的执行顺序或交换数据时，应使用 `__syncwarp()` 等显式同步，不能沿用隐式锁步假设。

### 3. 占用率的 block 资源账本

占用率是驻留 warp 数与 SM 最大驻留 warp 数之比，不是就绪率或执行单元利用率。由资源需求算出的通常是理论占用率；实际驻留还受剩余 block 数与并发任务影响。计算理论值要先按 block 分配资源，再换算成 warp。

设每个 block 有 $T$ 个线程，则每 block 的 warp 数为 $W_b = \lceil T / 32 \rceil$ 个。三类资源分别给出可容纳的 block 数，资源允许的驻留量为

$$B = \min(B_{\text{reg}}, B_{\text{smem}}, B_{\text{slot}}), \qquad W = B \times W_b, \qquad O = W / W_{\max}$$

其中 $B$ 是资源允许的驻留 block 数， $W$ 是对应的驻留 warp 数， $O$ 是理论占用率。 $W_{\max}$ 是 SM 的最大驻留 warp 数。寄存器上限由每线程用量与 block 线程数共同决定，共享内存上限由每 block 申请量决定，槽位上限同时受最大驻留 block 数与 warp 数限制。实际计算还要遵守架构的分配粒度；取最小的是 block 数，不是把寄存器数、字节数与 warp 数直接取最小。

假设待调度 block 充足，某 SM 可用于驻留 block 的共享内存总量为 64 KB，最大驻留 warp 数为 64，寄存器与 block 槽位均不构成限制。每个 block 有 256 个线程并申请 48 KB 共享内存，则每 block 有 8 个 warp。共享内存只允许 1 个 block 驻留，因此驻留 8 个 warp，理论占用率为 12.5%。这只是说明计算顺序的假设算例，不是某代产品的固定参数。

| 调整 | 主要收益 | 必须同时核对的代价 |
| --- | --- | --- |
| 缩小数据块（tile）或复用共享内存 | 降低每 block 共享内存，允许更多 block 驻留 | 是否增加全局访存、同步或重复计算 |
| 调整 block 线程数 | 改变 warp 打包与槽位取整 | 每线程工作量、末尾 warp 和 block 同步范围 |
| 限制寄存器用量 | 提高寄存器允许的 block 数 | 寄存器溢出是否引入额外访存 |
| 增加每线程指令级并行 | 较低驻留数也可能维持指令供给 | 寄存器压力、代码尺寸与额外指令 |

优化目标不是把占用率拉满，而是让足够的就绪指令持续进入发射槽，同时不引入更大的访存与同步损失。占用率用于定位资源约束，最终仍以设备程序的实测耗时与瓶颈指标判定。

## 三、数值格式与张量核：输入精度、累加与供给

第二节的 32 lane 提供线程级并行。以 warp 级矩阵乘加指令为例，张量核让一条 warp 矩阵指令完成一小块矩阵乘加。输入格式在这条链上同时改变每元素字节数、可表示范围与精度，以及阵列可执行的指令类型。位宽变窄会减少存储与搬运压力，但不会让同宽寄存器自动增加 lane，也不保证吞吐按位宽反比增长。

同章《数据表示与字节序》§二给出了 IEEE 754 的字段与隐含位规则，这里用同一把标尺比较输入格式，不再重推次正规数规则。

FP32 与 FP16 分别指 32 位和 16 位浮点格式，TF32 是 TensorFloat-32。

```text
三种可存储格式的字段（最高位在左）：

  FP32   s(1) | e(8) | f(23)     32 bit，有效精度 24 bit
  BF16   s(1) | e(8) | f(7)      16 bit，有效精度 8 bit
  FP16   s(1) | e(5) | f(10)     16 bit，有效精度 11 bit

  TF32 不画固定字段：按并行线程执行（Parallel Thread Execution，PTX）口径，
  它使用 32 bit 容器，内部布局由实现定义。
  这里只比较张量核输入时的有效精度。
```

| 格式 | 容器位宽 | 指数与有效精度口径 | 主要收益 | 主要代价 |
| --- | --- | --- | --- | --- |
| FP32 | 32 bit | 8 位指数，24 位有效精度 | 表内有效精度最高 | 每元素 4 B |
| TF32 | 32 bit | 指数范围同 FP32；常见实现按 11 位有效精度描述 | 保持 FP32 指数范围，支持特定张量核路径 | 内部布局由实现定义，不能当通用存储格式 |
| BF16 | 16 bit | 8 位指数，8 位有效精度 | 每元素 2 B，指数范围同 FP32 | 尾数明显缩短 |
| FP16 | 16 bit | 5 位指数，11 位有效精度 | 每元素 2 B，尾数多于 BF16 | 最大有限值 65504，范围较窄 |

### 1. 范围与精度的交换

BF16 与 TF32 保留 FP32 的指数范围，用更低的有效精度换取特定计算路径。BF16 的 8 位有效精度约合 2.4 位十进制，长累加中的低位损失不能当作偶发事件。FP16 保留更多尾数位，却把最大有限值压到 65504；在普通、非饱和的舍入路径中，足够大的结果会溢出为 Inf，饱和转换则可钳到最大有限值。过小的值则进入次正规并逐步失去精度。

FP16 混合精度训练常用损失缩放（loss scaling）放大梯度，更新前再缩回，降低小梯度下溢为零的概率。缩放因子及其调整策略取决于模型与框架；它不是消除所有溢出的通用开关，也不保证收敛。

### 2. 输入格式与累加格式分开

典型的张量核路径把输入格式与累加格式分开：在 $D = A \times B + C$ 中，A、B 可按 FP16、BF16 或 TF32 的输入口径提供，C、D 可使用 FP32 累加器。实际支持的组合随架构与指令而变，不能由格式名称直接推断。

同章《数据表示与字节序》§二说明浮点加法不满足结合律，这里用 FP32 累加降低连续累加的舍入损失，而不是恢复结合律或消除抵消。常见混合精度实现还会让部分权重或主副本保留 FP32，前向与反向使用较低精度输入；哪些张量必须保留高精度，仍由数值误差与框架共同决定。

### 3. 分块乘加与供给上限

这里以 warp 级矩阵乘加为例：一个 warp 协同提供寄存器片段，完成一次矩阵乘加后，再沿归约维推进下一块。片段形状与线程到寄存器的映射随架构而变，不能固定写成某一种 tile 尺寸。warp 组（warpgroup）级路径可由更大的线程集合协作，并允许部分操作数直接由共享内存提供，不能套用下面的寄存器路径。

```text
warp 级矩阵乘加的分块供给路径（示例）：

  A / B tile ──► 共享内存或缓存 ──► 寄存器片段 ──► 张量核乘加 ──► 累加寄存器
                                                        ▲                    │
                                                        │                    ▼
                                     下一块 A/B 与已有 C/D 继续乘加     归约完成后写出 D tile
```

对一个 $M \times N \times K$ 的分块乘加，一次乘加按两次浮点运算计。设从所考察存储层实际读取 $Q$ 字节，该层供给带宽为 $B_{\text{feed}}$，实际吞吐为 $P$，则

$$F = 2MNK, \qquad I = F / Q, \qquad P \le \min(P_{\text{peak}}, B_{\text{feed}} \times I)$$

其中 $F$ 是浮点运算数， $I$ 是算术强度， $P_{\text{peak}}$ 是该格式与架构对应的阵列峰值。 $Q$ 与 $B_{\text{feed}}$ 必须属于同一存储层和同一工作区间， $P_{\text{peak}}$ 还要与具体型号及稠密、稀疏口径一致。 $Q$ 要计入实际复用，不能只取矩阵的逻辑字节数。这里只计算读供给上限，完整流量账还要另计写回。窄格式既能减少 A、B 的搬运字节，也可能在支持的架构上提高阵列峰值；若 $B_{\text{feed}} \times I$ 已低于峰值，继续提高阵列规格也无法消除供给瓶颈。

## 四、存储层级与合并访存：sector 事务与有效载荷

一条 warp Load 产生 32 个地址，硬件先按它们落入的 32B 扇区（sector）归并，再向缓存与显存发起事务。以下以 32B sector、128B 缓存行的典型 NVIDIA 实现为例；不同代际的缓存组织可能变化，不能把这两个尺寸当成所有 GPU 的永久常数。

合并访存既会改变 sector 传输数量，也会改变有效载荷率。sector 数用于核算流量，不等于 L1 request 数；后者还受指令级归并与架构影响。有效载荷率则回答带回的字节有多少真正被 lane 使用。

```text
一次 warp Load 的归并路径（32 lane 各取连续 4B，起始地址按 32B 对齐）：

  lane 0-7      lane 8-15     lane 16-23    lane 24-31
     │             │             │             │
     ▼             ▼             ▼             ▼
  sector 0      sector 1       sector 2       sector 3
  32B           32B            32B            32B
     └────────────┴──────┬──────┴─────────────┘
                         ▼
                       L1 查询
                         │ 仅未命中的 sector 继续下穿
                         ▼
                      L2 / HBM
                         │
                         ▼
             4 个独立 32B 事务的数据返回
                         ▼
               32 个 4B 值写入寄存器
```

### 1. sector 归并与有效载荷

把有效载荷率记作 $U$，则 $U = 有效请求字节数 / 实际传输字节数$。以下假设起始地址按 32B 对齐，所考察 sector 都从下层取回，且带回的数据没有后续复用。每个 lane 都请求 4B，因此有效请求始终是 128B。

| 访问模式 | 覆盖的 sector 数 | 实际传输字节数 | 有效请求字节数 | $U$ |
| --- | --- | --- | --- | --- |
| 32 个连续 4B 地址 | 4 | 4 × 32B = 128B | 128B | 100% |
| 相邻地址间隔 16B | 16 | 16 × 32B = 512B | 128B | 25% |
| 相邻地址间隔至少 32B | 32 | 32 × 32B = 1024B | 128B | 12.5% |

跨步 32B 时，每个 32B 事务只使用其中的 4B，所以有效载荷率是 1/8，而不是 1/32。sector 掩码记录一条 warp 指令实际需要哪些 sector；在分扇区缓存中，未命中的 sector 才继续向下层请求，不能因为缓存行是 128B 就默认每次都取回整行。

### 2. 共享内存的复用与 bank 冲突

共享内存是 SM 内由软件管理的片上存储。程序可以先把一个 tile 搬入共享内存，再让多个线程重复读取，用一次全局搬运换取后续复用。它是否划算取决于复用次数、同步成本和占用容量，而不是只看共享内存本身的延迟。

在典型的 32 bank 模型中，每个 bank 每拍可提供一个 4B 字。不同 bank 的地址可以并行服务；同一 bank 的不同 32-bit 字需要拆成多拍，形成 bank 冲突，同字内的不同字节不因此冲突。多个 lane 读取同一个 32-bit 字时可广播，写入场景不能直接套用读广播语义。padding 与 swizzle 通过改变地址到 bank 的映射来减少冲突，代价分别是额外容量或更复杂的索引。

| 层级 | 管理者 | 主要职责 | 应观察的量化口径 |
| --- | --- | --- | --- |
| 寄存器 | 编译器 | 保存线程状态、矩阵片段与累加器 | 每线程寄存器数及其对驻留的影响 |
| 共享内存 | 软件显式管理 | 在 block 内暂存并复用数据 | bank 冲突、每 block 字节数、复用次数 |
| L1 / L2 | 硬件自动管理 | 过滤 sector 请求并保留热点数据 | 命中率、在途请求数与排队 |
| HBM | 硬件自动管理 | 保存设备侧工作集 | 整卡带宽；典型离片访问为数百拍档，实际随型号与排队变化 |

### 3. 与 CPU 缓存账本的差异

同章《缓存与存储层次》§三说明 CPU 的 MSHR 会合并同一缓存行的未命中，这里用它区分两类归并：MSHR 跟踪并合并多个在途请求，sector 归并则先整理一条 warp Load 内 32 个 lane 的地址。GPU 也有缓存未命中跟踪结构，不能反过来说它只有 warp 合并器。

CPU 示例使用 64B 缓存行，这里的 NVIDIA 示例使用 32B sector 与 128B 缓存行。尺寸不同首先改变搬运与掩码的账本，不能直接推出哪种引擎更快。有效载荷率、缓存命中情况与在途并发必须一起比较。

## 五、CPU↔GPU 数据通路：BAR 控制面与 DMA 数据面

主机与离散 GPU 之间的数据通常要跨过 PCIe。控制面由 CPU 通过 MMIO 访问设备寄存器，数据面则由 DMA 引擎在主机内存与 HBM 之间搬运。两条路径都经过 PCIe，但发起者与地址窗口不同，不能把 DMA 数据写成经过 BAR 窗口落入 HBM。

```text
一次主机到设备的 DMA 搬运（典型实现）：

  驱动把源址、目标址、长度写入主机描述符
                    │
                    ▼
  CPU 对 BAR 寄存器做 MMIO doorbell 写 ──PCIe──► GPU 命令处理器
                    │                              │
                    │                              ▼
                    │                     DMA 引擎读取描述符
                    │                              │
                    ▼                              ▼
          主机页锁定缓冲区 ──PCIe 读返回──► GPU DMA 引擎 ──► HBM 写入
          │
                                                             ▼
                                               完成记录或中断（可选）


```

### 1. BAR 与页锁定缓冲区

枚举时，系统读取基地址寄存器（Base Address Register，BAR）声明的窗口需求，并为窗口分配主机物理地址范围。CPU 再把这些范围映射进自身地址空间，用 MMIO 访问设备寄存器或部分设备内存。BAR 窗口不必覆盖整块 HBM，也不承担所有设备数据的搬运。

MMIO 读通常需要完成响应，内存写通常是 posted，不要求对端返回完成包。访问宽度与是否适合批量搬运取决于设备接口，不能统一写成每次只能搬 4～8 B 或每次都必须往返。控制面适合寄存器与门铃，批量数据通常交给 DMA。

设备 DMA 不经过 CPU 的虚拟内存机制。驱动必须保证搬运期间相关页不会失效或被随意迁移，并建立 DMA 映射。页锁定（pinned）用于稳定这些页，但不要求它们在物理上连续。设备使用映射得到的总线地址；启用输入输出内存管理单元（Input-Output Memory Management Unit，IOMMU）时，由它完成设备地址到物理页的翻译。

普通可分页缓冲区可由运行时先转入页锁定的暂存区，再由 DMA 搬运，不能一概要求用户预先锁页。页锁定本身也有系统内存代价，是否预分配缓冲池应由拷贝频率与测量结果决定。

### 2. 描述符环与 doorbell 的握手

一种典型的命令路径是生产者—消费者环：驱动写入源地址、目标地址、长度与操作类型，设备读取并消费。驱动发布新描述符后，再写 doorbell 通知设备。描述符写入与 doorbell 之间还要满足设备要求的发布顺序，避免设备读到尚未完成的条目。

doorbell 是对设备寄存器的 MMIO 写，宽度由设备定义，不是固定的 4B。DMA 引擎取描述符并发起读写，主机到设备的数据最终进入 HBM，设备到主机的数据则写入主机 DMA 映射。完成状态可以由驱动轮询，也可以经中断上报；数据面不需要 CPU 逐字节参与。

环深限制在途命令数量。环太浅可能无法维持流水线，环太深则会增加排队与尾延迟。若描述符处理与数据搬运能够重叠，可用“链路带宽 × 往返时间”估算维持流水线所需的在途字节，再折算描述符数量；这只是容量估算，不是吞吐保证。

### 3. 固定开销与批量边界

对一次串行、以固定同步方式完成的搬运，把传输字节数记作 $S$，链路带宽记作 $B_{\text{link}}$，提交与同步的固定开销记作 $T_{\text{fixed}}$，则

$$B_{\text{eff}} = \frac{S}{S / B_{\text{link}} + T_{\text{fixed}}}$$

其中 $B_{\text{eff}}$ 是按总完成时间计算的有效带宽。 $T_{\text{fixed}}$ 必须按实际接口与同步口径测量，不能直接等同于固定的 PCIe 往返延迟。小批量由固定开销主导，大批量才逐渐接近链路带宽。异步流水线可以重叠提交、传输与计算，因此不能把这条串行公式当成所有拷贝的统一性能模型。

以每向理论有效带宽估算，PCIe 4.0 x16 约为 32 GB/s，PCIe 5.0 x16 约为 64 GB/s；实际端到端吞吐还受协议开销、实现与访问模式影响。批量化的作用是摊薄固定开销，而不是让链路规格变成必然可达的收益。

## 六、异构执行时序：提交、波次与流依赖

数据到位之后，计算以 kernel（提交到 GPU 执行的设备函数）为单位进入命令队列。CPU 的提交与设备完成是两个事件：提交只把命令排入流，完成由设备进度与依赖决定。小 kernel 的固定提交开销和尾部调度空隙，往往比算术时间更先成为瓶颈。

```text
三条流的依赖时间轴（K1 与 K2 可重叠，K3 等待 K1）：

 stream A: [主机→设备]──[kernel K1]──[事件 e]
 stream B:              [kernel K2]──[设备→主机]
 stream C:              [等待 e]────[kernel K3]

  同一流内按顺序建立依赖；跨流等待由事件显式给出。
```

### 1. 提交开销与计算图

一次 kernel 提交的固定开销通常在微秒档，包含运行时处理、命令编码与设备调度等环节，具体数值随驱动、设备和测量方式变化。CPU 提交后可以继续执行，不必等待 kernel 完成。设备侧错误可能在启动时暴露，也可能到后续调用或同步点才返回。

统一计算设备架构（Compute Unified Device Architecture，CUDA）的计算图（CUDA Graph）先把 kernel、拷贝及依赖实例化，之后重复回放。它主要减少重复的主机提交与依赖设置开销，不会把多个设备节点融合成一个节点，也不消除每个 kernel 的设备执行与调度成本。把多个小 kernel 手工融合则可能减少提交次数，但会改变寄存器压力、并行粒度与调度方式，收益必须实测。

### 2. 波次是调度模型，不是全局屏障

一个 kernel 的网格（grid）包含若干 block。设备调度器在 SM 有空闲资源时补入新 block，不等待整卡上一波全部完成。所谓波次，是用驻留容量估算调度量化的分析模型，不是硬件在所有 SM 之间设置的同步阶段。

在等长 block 的简化模型中，假设有 $S$ 个 SM，每个 SM 固定驻留 $B$ 个 block，共有 $N$ 个等长 block，每块耗时为 $T$，则整卡容量与模型时间为

$$C = S \times B, \qquad T_{\text{model}} = \left\lceil \frac{N}{C} \right\rceil T, \qquad U_{\text{wave}} = \frac{N}{C\lceil N/C\rceil}$$

其中 $C$ 是整卡可同时驻留的 block 数， $U_{\text{wave}}$ 是该模型的槽位时间利用率。它不等于实际吞吐，也不包含启动、访存或指令效率。真实 block 的时长不同，调度器又会持续补位，因此尾部损失还取决于长块、依赖与补位顺序，不能用“最后一波空槽数除以总槽数”直接计算。更细的 block 通常能改善负载量化，但也会增加调度、同步与重复搬运成本。

### 3. 流、事件与数据可见性

流是命令的有序队列：同一流内的命令按提交顺序建立依赖，不同流之间可以乱序或并发。事件记录某条流中的位置，其他流可以等待它，用来表达跨流依赖。不能把不同流上的执行顺序当作天然确定，需要顺序时必须显式建立。

默认流有传统默认流与每线程默认流两种语义，不能一概写成“隐式同步流”。同步拷贝接口会阻塞调用线程；异步拷贝若要同计算重叠，需要满足页锁定主机内存、设备能力与流依赖等条件。显式流与事件的作用，是把可以并行和必须等待的边界写清楚。

流同步保证其前序命令已经完成。若主机与设备或多个设备线程在这些命令之外直接共享数据，还要按 CUDA 内存模型处理访问范围、内存序与数据竞争。提交顺序、完成顺序和数据可见顺序相关，但不是可以互相替代的三个概念。

## 七、统一内存与迁移边界：驻留、缺页与预取

统一虚拟地址空间（Unified Virtual Address Space，UVA）只统一指针的地址范围，统一内存（Unified Memory，UM）则让托管分配可被 CPU 与 GPU 访问，并由驱动管理驻留与一致性。地址可路由不代表数据已在本地，也不代表平台支持按需缺页。

| 平台能力 | 迁移与访问方式 | 显存超订 | 关键边界 |
| --- | --- | --- | --- |
| 完整 UM 支持 | 可按需迁移；软件一致性可按页处理，硬件一致性可按缓存行处理 | 支持 | 迁移粒度与一致性机制随平台而变 |
| 受限 UM 支持 | 主要在 kernel 启动与同步边界迁移，不支持 GPU 按需缺页 | 不支持 | GPU 活跃时 CPU 不能随意访问托管数据 |

完整支持还可按系统分配器、页表与互连方式继续细分，不能把某一种缺页路径当成所有 UM 实现的统一行为。下面先用软件一致性路径解释按需迁移的成本；受限平台应改按启动与同步边界核算。

```text
支持按需缺页时的迁移闭环（软件一致性路径）：

  GPU lane 访存 ──► GPU MMU 查页表 ──(未驻留)──► 缺页异常
                                                   │
                                                   ▼
                                       UM 驱动选择迁入本地或建立远程映射
                                       ┌───────────┴───────────┐
                                       ▼                       ▼
                                 迁入本地内存        建立远程映射（若支持）
                                       │                       │
                                       └───────────┬───────────┘
                                                   ▼
                                        重放触发指令（可能再次缺页）
```

### 1. 缺页与驻留成本

在支持按需缺页的路径上，GPU MMU 发现映射未驻留后触发异常，由 UM 驱动处理迁移或远程映射，再更新映射并重放访问。迁移粒度、缺页处理时间与是否回迁都随平台、驱动和访问模式变化，不能固定写成某几种页大小或统一的微秒、毫秒档位。

一次缺页的成本包含异常处理、数据传输、映射更新和被暴露的停顿，通常远高于一次本地 HBM 访问。迁入后若能重复命中，后续访问才可利用本地显存带宽；若每页只访问一次，迁移成本难以摊薄。若平台选择远程映射而非迁入，则省去整块搬运，但后续访问仍要承担主机—设备互连的延迟与带宽约束。

### 2. 超订与抖动

只有完整 UM 支持的平台才允许显存超订。工作集大于本地显存时，驱动可以迁出部分页面，为当前访问腾出空间。若循环复用的工作集始终超过驻留容量，页面会反复往返，形成抖动；损失不仅是互连传输，还包括缺页处理与计算停顿。

处理抖动要先改变驻留与复用关系，而不是只调迁移参数。可以缩小分块、压缩数据或降低存储位宽，也可以调整遍历顺序与预取策略。同章《数据表示与字节序》§六说明窄化转换会改变宽度与转换语义，这里用它减少工作集字节数，不把缩窄当成无损压缩。

### 3. 预取与总成本判据

`cudaMemPrefetchAsync` 是流序的预取提示，可能把数据迁到指定处理器附近。预取任务等待同流前序操作完成后才开始，后续同流操作则等待它完成；数据在预取期间仍可被访问。它不能把后续驻留或“绝不再缺页”当成保证，是否值得仍要看迁移量与访问局部性。

| 方案 | 主要成本入口 | 适用条件 | 主要风险 |
| --- | --- | --- | --- |
| 显式批量拷贝 | 提交开销与批量传输 | 布局稳定、工作集明确且能放入目标内存 | 额外拷贝与暂存需求 |
| 页锁定 + 异步拷贝 | 固定开销、传输与可重叠计算 | 有稳定流水线和独立计算任务 | 没有足够并行工作时难以掩盖传输 |
| zero-copy 映射 | 每次远程访问的互连延迟与带宽 | 小量、低频或必须由主机持有的数据 | 重复访问无法利用本地显存带宽 |
| UM 按需迁移 | 缺页处理、迁移与驻留命中 | 平台支持，且访问稀疏或布局难以显式管理 | 抖动、过量迁移与不可预测的停顿 |
| UM 预取 | 流序迁移与可能的过量读取 | 已预知下一阶段工作集 | 多搬未使用数据，仍可能发生后续缺页 |

对第 $i$ 次迁移或缺页，把固定处理开销记作 $F_i$，迁移字节数记作 $S_i$，可被有用计算覆盖的时间记作 $O_i$，则暴露给总耗时的时间可估为

$$T_{\text{exposed}} = \sum_i \max\left(0, F_i + \frac{S_i}{B_{\text{link}}} - O_i\right)$$

这里 $B_{\text{link}}$ 是实际传输路径的有效带宽， $O_i$ 不能超过本次处理与传输时间。总迁移字节数是 $\sum_i S_i$，它与暴露时间必须分开记账。预取可以减少随机缺页的暴露，却可能增加第二项；因此不存在通用的命中率阈值，只能比较同一任务在两种方案下的总时间。

UM 是否划算，取决于驻留命中率、迁移字节数、固定缺页成本和可重叠计算。地址统一只是接口便利，不能代替这四项测量。
