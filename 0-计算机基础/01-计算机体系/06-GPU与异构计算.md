# GPU 与异构计算

## 一、约束分野：面积预算下的控制逻辑与 ALU 配比

同一块硅片面积可以换两种东西：更聪明的控制逻辑，或更多的算术单元。CPU 与 GPU 的分野不是"通用"与"专用"的标签，而是把面积押在延迟还是押在吞吐——押延迟就要为单条指令准备预测、重命名、乱序窗口与多级缓存；押吞吐就要把这些面积全部让给阵列，再用海量线程把延迟填满。

```text
同一面积预算的两种押注（按大核 / SM 的相对比例示意）：

  CPU 大核                                 GPU SM
 ┌──────────────────────────────┐       ┌──────────────────────────────┐
 │ 乱序窗口 / ROB      ~20%     │       │ 寄存器堆          ~20%       │
 │ 分支预测 + 取指译码  ~10%     │       │ 共享内存 / L1     ~15%       │
 │ L1 / L2 缓存        ~40%     │       │ ALU / FP 阵列     ~60%       │
 │ 执行单元与端口      ~30%     │       │ 控制与调度        ~5%        │
 └───────────────┬──────────────┘       └───────────────┬──────────────┘
                 │ 押延迟                                │ 押吞吐
                 ▼                                       ▼
      单线程 CPI ≈ 1，访存延迟纳秒档            单线程停顿数百拍，
      靠 OoO 窗口 + 预测隐藏                    靠每 SM 数十 warp 隐藏
```

### 1. 面积预算的分配

CPU 的乱序窗口以数百条指令为量级（03 §二 的 ROB 与保留站结构），分支预测器要为一个取指块准备多套历史表，L1/L2 要覆盖工作集——这三项加起来吃掉大核的多数面积，换来的是"单线程跑一段分支密集的代码也不停"。GPU 的流式多处理器（Streaming Multiprocessor，SM）把同样的面积换成宽发射的 ALU 阵列与巨大的寄存器堆：一个 SM 每拍可发射数条 warp 指令，每条指令覆盖 32 个 lane，控制逻辑只负责从就绪 warp 中挑一条，不做重命名、不做乱序、不做深度预测。

| 维度 | CPU 大核 | GPU SM |
| --- | --- | --- |
| 面积主项 | 乱序窗口、预测器、多级缓存 | 寄存器堆、ALU 阵列、共享内存 |
| 在飞指令 | 数百条（受 ROB 封顶） | 数十个 warp，每 warp 32 lane |
| 单线程访存延迟 | 纳秒档，靠缓存与预测压住 | 数百拍，与 CPU 同档甚至更高 |
| 延迟隐藏手段 | 乱序执行 + 分支预测 | 线程级并行（多 warp 轮转） |
| 每 FLOP（Floating-point Operation，浮点运算）面积效率 | 低（控制开销摊在少量数据上） | 高一个数量级以上 |
| 擅长负载 | 分支密集、指针追逐、串行依赖 | 同指令作用于万级数据、规则访存 |

### 2. 两条延迟隐藏路径

两条路径的代价结构完全不同。CPU 用乱序窗口把"后面不相关的指令"提前执行，窗口深度就是它能跨越的延迟上限；一旦某条 Load 未命中且后续指令全部依赖它，窗口填满，流水线只能停顿。GPU 放弃跨指令重排，改用"换一个 warp 执行"：当前 warp 等 HBM（High Bandwidth Memory，高带宽显存）时，调度器在同一拍改发另一个就绪 warp 的指令，停顿被别的线程的算力填掉。因此 GPU 的延迟隐藏能力正比于驻留 warp 数，而驻留 warp 数受寄存器、共享内存与 block 大小三重封顶——这是第二节占用率讨论的起点。

这条分野也解释了为什么 GPU 的频率通常低于 CPU：吞吐优先的阵列在低电压下更容易堆面积，而延迟优先的乱序逻辑必须靠高频率把串行链缩短。频率低而并行度高，单线程响应更慢，聚合吞吐更高，两者是同一面积预算下的两个解。

### 3. 能效曲线与工作负载反转

每 FLOP 的面积效率优势只在"控制开销可摊薄"时成立。当一段代码的分支发散率很高（每个 warp 的 32 条 lane 走不同路径），阵列的实际利用率按发散度倒数下降，最坏退到 1/32，此时 GPU 的每 FLOP 成本反超 CPU；指针追逐类的访存模式让每次访问都落在不同缓存行，合并器失效，GPU 的带宽优势同样被拆散。反过来，矩阵乘、卷积、逐元素变换这类"同一指令、规则地址、万级数据"的负载，控制开销被摊到可以忽略，阵列效率接近峰值。

于是异构分工可以被算出来而不是被规定：先把负载拆成"规则并行段"与"串行/分支段"，前者交给阵列、后者留给大核，中间用 PCIe 通路连接。这条判据会在第七节以迁移成本的形式再次出现。

## 二、SIMT 执行模型：warp、发散掩码与重汇聚

单指令多线程（Single Instruction, Multiple Threads，SIMT）把 SIMD 的 lane 从"指令内的数据通道"提升为"线程"：每个线程有自己的寄存器和程序计数器，硬件把 32 个线程打包成一个 warp，让它们共享同一条指令的取指与译码。寄存器是每线程私有的，指令流在无发散时是共享的——这使 SIMT 既保留了 SIMD 的前端摊销，又允许线程各自持有不同的数据与地址。

```text
一个 warp 遇 if/else 的执行时间线（32 lane，活跃掩码逐拍变化）：

  阶段             lane 0-15          lane 16-31        活跃掩码
  ────────────────────────────────────────────────────────────────
  比较 A[i]>0      执行比较            执行比较           0xFFFFFFFF
  分支             走 then 路径        走 else 路径       分成两组
  then 段          C[i]=A[i]+B[i]     屏蔽（空转）       0x0000FFFF
  else 段          屏蔽（空转）        C[i]=B[i]          0xFFFF0000
  重汇聚点         合流                合流               0xFFFFFFFF

  两段路径串行执行 → 该分支段耗时 = then 段 + else 段（不是二者最大值）
```

### 1. warp 打包与锁步执行

warp 的宽度 32 是 NVIDIA 的固定常数（AMD 的 wavefront 为 64），一条指令在一个 warp 上覆盖 32 个 lane。打包发生在 block 分配到 SM 时：连续 32 个线程号编成一个 warp，此后同 warp 的线程共享取指、译码与指令发射，只有寄存器和活跃掩码是每线程的。这条规则带来一个硬性约束：warp 内线程的地址越分散，合并器要拆的事务越多；warp 内线程的控制流越不一致，串行执行的路径越多。

### 2. 发散的两条处置：谓词化与重汇聚

分支发散时硬件有两条路。谓词化让两条路径都执行、只按掩码屏蔽写回，适合两条路径都很短的场合——总耗时是两段之和，但省掉了分支与重汇聚开销。真发散则按路径分组串行执行，每组只激活对应 lane，执行完在重汇聚点合流；最坏情形是 32 条 lane 各走一条路径，该段吞吐降到 1/32。编译器通常对短 if 生成谓词化，对长分支生成真发散，阈值由指令数与寄存器压力共同决定。

重汇聚的实现随架构演进：早期 GPU 用重汇聚栈（SIMT Stack）记录每条路径的掩码与返回点，发散与合流都是栈操作；Volta 之后每线程拥有独立 PC 与调度器，发散的 lane 可以直接重汇聚，不再强制走栈。后者让"线程间细粒度同步"成为可能，也让发散的开销从"栈深度"变成"实际路径数"。

### 3. 占用率的三重封顶

SM 能驻留多少 warp 由三项资源共同决定：每线程寄存器数、每 block 共享内存字节数、每 SM 的 block 与 warp 上限。三者取最小，任何一项先耗尽，其余资源就闲置。典型的假性低占用是"寄存器够、共享内存不够"：一个 block 声明了 48 KB 共享内存，而 SM 只有 64 KB，于是只能驻留一个 block，warp 数被迫压到 block 内线程数除以 32。工程上要么缩小 tile、要么改用动态共享内存分段复用，要么提高每线程工作量（增加 ILP）来补偿低占用——这三条都直接改变第三节的数值格式选择与第四节的合并访存模式。

## 三、数值格式与张量核：FP16/BF16/TF32 的字段重用

第二节的 32 lane 是空间上的并行；张量核在同一空间上再叠一层"每拍完成一个小矩阵乘加"。要让阵列在同样面积下吞吐更高，最直接的办法是把每个数变窄：字段位宽减半，同样宽度的寄存器就能装下两倍 lane，乘加阵列的吞吐随之翻倍。05 §2 的 IEEE 字段标尺在这里被整体削短，语义（偏置、隐含位、特殊值）保持不变。

```text
FP32 字段削短为三种计算格式（保指数 → 保范围；保尾数 → 保精度）：

  FP32   s(1) | e(8)  | f(23)     范围 2^-126 ~ 2^127，有效精度 24 bit
  TF32   s(1) | e(8)  | f(10)     范围同 FP32，有效精度 11 bit
  BF16   s(1) | e(8)  | f(7)      范围同 FP32，有效精度 8 bit
  FP16   s(1) | e(5)  | f(10)     范围 ±65504，有效精度 11 bit

  被砍掉的尾数位 → 同宽寄存器容纳更多 lane → 阵列吞吐按位宽反比放大
  被砍掉的指数位 → 动态范围收窄 → 需要 loss scaling 把梯度拉回可表示区间
```

| 格式 | 指数位 | 尾数位 | 有效精度 | 动态范围 | 相对 FP32 峰值吞吐 |
| --- | --- | --- | --- | --- | --- |
| FP64 | 11 | 52 | 53 bit | 极大 | 1/2 ~ 1/4 |
| FP32 | 8 | 23 | 24 bit | $2^{-126}$ ~ $2^{127}$ | 1 |
| TF32 | 8 | 10 | 11 bit | 同 FP32 | 数倍 |
| BF16 | 8 | 7 | 8 bit | 同 FP32 | 数倍到十倍档 |
| FP16 | 5 | 10 | 11 bit | ±65504 | 数倍到十倍档 |
| FP8 | 4 或 5 | 2 或 3 | 3 ~ 4 bit | 很窄 | 十倍档以上 |

### 1. 字段裁剪的两种取向

保留指数、砍尾数（BF16、TF32）保住动态范围，代价是相对精度下降：BF16 的 8 位有效精度约合 2.4 位十进制，累加几千项就会明显丢低位，因此必须用 FP32 累加器。保留尾数、砍指数（FP16）保住相对精度，代价是范围窄：超过 65504 直接溢出为 Inf，训练时梯度稍大就会炸掉，必须用 loss scaling 把梯度乘一个常数拉回可表示区间、更新前再除回去。两种取向对应两类负载：推理的激活值范围稳定、精度要求高，偏 FP16；训练的梯度动态范围大，偏 BF16。

### 2. 累加器宽度与混合精度

张量核的乘加阵列通常以窄格式接收输入、以 FP32 累加： $D = A \times B + C$ 中 A、B 是 FP16/BF16，C 与 D 是 FP32。这样乘法的位宽减半、吞吐翻倍，而累加不在窄格式里进行，避免了几千项累加后的灾难性抵消（05 §2 的结合律失效在这里是工程红线）。所谓混合精度训练，本质是"主权重存 FP32、前向反向用窄格式、累加用 FP32"的三层分工，不是把所有数都换成 FP16。

### 3. 分块乘加与吞吐换算

一个 SM 的张量核按 4×4、8×8 或更大的 tile 组织乘加：每个周期读入一小块 A 与 B，在阵列内完成 tile 内的乘加，再把结果写回累加寄存器。吞吐换算很直接：每拍完成的乘加数 = tile 面积 × 阵列并行度，位宽减半则同样寄存器堆能容纳的 tile 数翻倍。这条换算的瓶颈通常不在阵列，而在喂数：共享内存带宽、寄存器读写端口、以及 05 §6 的格式转换单元，任一项跟不上，阵列就空转。因此实际吞吐要按"阵列峰值 × min(1, 供给带宽/需求带宽)"估算，而不是直接读规格表。

## 四、存储层级与合并访存：32B sector 与 128B 事务

warp 的 32 个 lane 在同一拍发出 32 个地址，硬件必须把它们压成尽量少的内存事务。这一层叫合并器（Coalescer）：它按地址落在哪个 32B sector 分组，同一 sector 内的多个 lane 请求合并成一次访问，跨 sector 的请求拆成多条。GPU 的最小事务粒度是 32B sector，而非 CPU 的 64B 缓存行——这条差异决定了同样的访问模式在两种引擎上的带宽账完全不同。

```text
一次 warp Load 的合并路径（32 lane 各取 4B，地址连续）：

  lane 0-7      lane 8-15     lane 16-23    lane 24-31
     │             │             │             │
     ▼             ▼             ▼             ▼
  ┌───────┐    ┌───────┐     ┌───────┐     ┌───────┐
  │ 32B   │    │ 32B   │     │ 32B   │     │ 32B   │   4 个 sector
  │sector │    │sector │     │sector │     │sector │
  └───┬───┘    └───┬───┘     └───┬───┘     └───┬───┘
      └────────────┴─────────────┴─────────────┘
                          │ 合并为 1 条 128B 事务
                          ▼
                  L2 切片 / HBM 通道 ──► 回填 4 个 sector ──► 32 个寄存器
```

### 1. 合并器与 sector 掩码

合并器不关心 lane 的语义，只关心地址落在哪些 sector 里：32 个连续 4B 地址覆盖 128B，恰好 4 个 sector，合并成一条事务；若每个 lane 的地址间隔 32B（跨步访问），32 个 lane 落在 32 个不同 sector，就拆成 32 条事务，有效带宽降到 1/32。sector 掩码是合并器的输出：它告诉 L1 哪几个 32B 块被需要，L1 按掩码回填，未命中的 sector 才继续下穿。L1 命中率因此按 sector 而非按行统计——一条 128B 行里只碰了 4B，也只算命中一个 sector。

### 2. 共享内存与 bank conflict

共享内存是 SM 内的一块软件管理的 SRAM，延迟约 20 ~ 30 周期，比 HBM 的 400 ~ 800 周期低一个数量级以上，因此 tiling 的标准动作是"先把块搬进共享内存，再反复复用"。共享内存被切成 32 个 bank，同一 warp 的 32 个 lane 若访问同一 bank 的不同地址，就发生 bank conflict，访问被串行化成多拍；若 32 个 lane 访问同一地址，则广播、不冲突。工程上用 padding 把列数错开、或用 swizzle 重排索引，都是为了把"同 bank 不同地址"改成"不同 bank"。

| 层级 | 管理方式 | 事务粒度 | 延迟档位 | 典型带宽 |
| --- | --- | --- | --- | --- |
| 寄存器 | 编译器分配 | 每线程 4B 起 | 零拍（操作数直读） | 由阵列端口决定 |
| 共享内存 | 软件显式 | 32 bank × 4B | 二十拍档 | 每 SM 每拍数十 B |
| L1 / L2 | 硬件自动 | 32B sector / 128B 行 | 数十至百拍档 | 每 SM 数百 GB/s 档 |
| HBM | 硬件自动 | 32B sector | 数百拍档（百 ns 级） | 数百 GB/s 至 TB/s 档 |

### 3. 与 CPU 缓存层级的差异

CPU 侧的行填充粒度是 64B、事务以行为单位，且 MSHR 把同一行的多个未命中合并（02 §三）；GPU 侧以 32B sector 为单位，合并发生在 warp 内部的地址归并，二者不是同一层机制，不能互相套用。相同的是"未命中的代价随并发度放大"：GPU 一个 SM 可同时挂起数十个 warp 的未命中，靠线程级并行把 HBM 的百纳秒延迟藏起来；CPU 靠 MSHR 与乱序窗口把十几个未命中重叠。带宽锚点仍取 01 §三 的单服务台上限 25.6 GB/s：HBM 单堆比它高 1 ~ 2 个数量级，这正是 GPU 敢用低命中率缓存换面积的原因。

## 五、CPU↔GPU 数据通路：PCIe 事务层与 DMA 描述符环

前四节讨论的层级都在 GPU 封装内部；数据要从主机内存进来，必须跨过 PCIe。这条通路是整机最贵的一段：带宽比 HBM 低一个数量级，往返延迟高 1 ~ 2 个数量级。因此它不是"另一条内存总线"，而是一条需要显式打包、显式排队、显式摊薄启动税的窄链路。

```text
一次批量拷贝的端到端路径：

 ┌─ 主机域 ─────────────────┐         ┌─ 设备域 ───────────────────┐
 │ 应用缓冲区（页锁定）      │         │ 命令处理器 / DMA 引擎       │
 │        │                 │         │        │                   │
 │        ▼                 │         │        ▼                   │
 │ 描述符环（host 内存）     │         │ 读描述符 → 发起读写请求     │
 └────────┬─────────────────┘         └────────┬───────────────────┘
          │ doorbell（4B PIO 写）              │
          ▼                                    ▼
    ┌──────────────────── PCIe 链路 ─────────────────────┐
    │ 事务层包：Src / Dst / Opcode / Address 四大件封装   │
    │ 数据链路层加 CRC ──► 物理层 SerDes 串行化           │
    └───────────────────────┬────────────────────────────┘
                            ▼
                 目标 BAR 窗口 → HBM 写回

  节点职责：根复合体参与地址路由（解析）；交换机纯转发（不解析载荷）；
            GPU 端点的 BAR 参与地址解析，HBM 控制器只做落盘
```

### 1. 枚举、BAR 与页锁定内存

上电枚举时，配置空间把 GPU 的显存地址窗口映射进系统物理地址空间，这段窗口就是基地址寄存器（Base Address Register，BAR）。CPU 通过 BAR 读写显存，但每次只能搬 4 ~ 8 B，且要跨链路往返——它只适合写 doorbell 与读寄存器，不适合搬数据。数据面由设备 DMA 引擎主导：驱动在主机内存里建描述符环，把"源地址、目标地址、长度、操作码"逐条写入，再写一次 doorbell 通知设备取环。

DMA 的前提是页锁定（pinned）内存。普通匿名页可能被换出或被内核迁移，设备按物理地址搬运就会读到错误内容，于是驱动必须先做一次"锁页 + 建 DMA 映射"；未锁页的缓冲区要走 bounce buffer，多一次主机内拷贝。工程上应在初始化时预分配页锁定缓冲池，把锁页成本移出热路径——这与 02 §三 的"先把页表买路钱付掉"是同一类摊销思路。

### 2. 描述符环与 doorbell 的握手

描述符环是生产者-消费者队列：驱动是生产者，推进写指针；设备是消费者，推进读指针。doorbell 是唯一需要 CPU 主动写设备的动作，一次 4 B 的 PIO，通知"写到第几个描述符了"。设备取到描述符后发起读请求，数据经 PCIe 写入 BAR 窗口背后的 HBM；搬完一个描述符就更新完成计数，必要时发中断。整条链路里，只有 doorbell 与完成中断需要 CPU 参与，中间的搬运全由 DMA 引擎完成——这是"设备自治"与"CPU 不参与数据面"的分界。

环的深度决定流水线能挂多少在途请求：环太浅，CPU 来不及补描述符，链路空转；环太深，一次提交的批量变大，尾延迟变差。典型的工程折中是按"链路带宽乘以往返延迟"估算在途字节数，再除以单个描述符的搬运量，得到环深下限。

### 3. 带宽与往返税：为什么必须批量

把链路带宽记作 $B_{\text{link}}$、往返延迟记作 $L_{\text{rt}}$，一次搬运 $S$ 字节的有效带宽为

$$B_{\text{eff}} = \frac{S}{S / B_{\text{link}} + L_{\text{rt}}}$$

搬运量很小时，往返延迟主导分母，有效带宽趋近于零；搬运量足够大时，有效带宽趋近链路带宽。PCIe 4.0 x16 的单向带宽约 32 GB/s、5.0 x16 约 64 GB/s，往返延迟在微秒档；HBM 的带宽是数百 GB/s 至 TB/s 档、延迟百纳秒档。用 1 KB 的小拷贝去填这条链路，有效带宽只有规格值的零头；把拷贝合并到 MB 级，才能把往返税摊薄到可忽略。NVLink 把单向带宽提到数百 GB/s、往返压到亚微秒档，缓解但不消除同一条公式的约束——它仍然跨封装，不能与 HBM 同档。

## 六、异构执行时序：kernel 启动、波次调度与流

数据到位之后，计算以 kernel 为单位提交。一次 kernel 启动不是"CPU 调用一个函数"，而是"把一条命令写进队列、由设备端调度器分派到 SM"。这条命令路径上有两处固定开销：启动税与波次量化。两者都与 kernel 的计算量无关，因此小 kernel 密集的负载会被它们主导。

```text
时间轴（两条流并发，第三条被事件挡住）：

 stream A: [H2D 拷贝]──[kernel K1]────────────────[事件 e]──[kernel K3]
 stream B:              [kernel K2]──[D2H 拷贝]
 默认流  :  ─────────────────────────────────────────────────[同步点]

  每个 kernel 前支付启动税 t_launch（微秒档）
  K1 与 K2 在不同流上可重叠；K3 必须等 e 触发
```

### 1. 启动税与命令队列

一次 kernel 启动的固定开销在微秒档：写命令、更新队列、doorbell、设备端取命令、建立网格描述。计算只花几百纳秒的 kernel，启动税就是主体成本。把多个小 kernel 合并成一个大 kernel、或把整张计算图预先录制成 CUDA Graph 一次提交，都是把 N 次启动税压成 1 次——图执行把逐次提交变成一次回放，启动开销降一个数量级。这条优化不改变计算，只改变提交路径，属于纯粹的时序结构优化。

命令队列是主机与设备之间的异步边界：CPU 提交后立即返回，不等待 kernel 完成；只有显式同步（设备同步、流同步、事件等待）才阻塞。这把"提交"与"完成"解耦，也让错误处理变复杂——kernel 内的非法访存不会立刻返回给调用方，而是在下一次同步点以错误码形式出现。

### 2. 波次、尾波与占用率

grid 的 block 数通常远大于 SM 容量，调度器按波次推进：一波填满所有 SM 的驻留槽位，跑完再填下一波。若 grid 的 block 数不是"波次乘以每波容量"的整数倍，最后一波只填了一部分 SM，其余 SM 空转，这段空转叫尾波。尾波损失的比例等于"最后一波的空槽数除以总槽数"，block 粒度越细、grid 越大，尾波占比越小；反之一个大 block 的 grid 可能只有两三波，尾波损失可达三成。

波次与占用率共同决定实际并行度：每 SM 驻留的 block 数受寄存器、共享内存、block 上限三重封顶（第二节），驻留数乘以每 block 的 warp 数就是可切换 warp 总数。调度器每拍从就绪 warp 中挑一条发射，可切换 warp 数不足时，HBM 的数百拍延迟就无处可藏。

### 3. 流与事件的同步语义

流是命令的串行队列：同一流内的拷贝与 kernel 严格按提交顺序执行，不同流之间可并发。事件是流内的一个标记，可被其他流等待，用来表达"K3 必须等 K1 完成"这类跨流依赖。默认流是隐式同步流，多数拷贝接口默认在默认流上同步阻塞；要让拷贝与计算重叠，必须使用页锁定内存加非默认流，否则拷贝会把整条流串行化。

这套语义与 CPU 侧的内存序不是同一层：流同步保证的是命令完成顺序，不保证设备写回的数据对主机可见的缓存一致性——跨设备可见性还要靠显式的同步接口与内存栅栏。工程上把"提交顺序、完成顺序、可见顺序"三件事分开检查，是异构程序最常见的错误来源。

## 七、统一内存与迁移边界：缺页回填的收敛点

前两节假设数据先拷到显存再算。统一内存（Unified Memory，UM）把这步隐式化：主机与设备共享一个虚拟地址空间，GPU 访问未驻留页时触发缺页，驱动把页迁到显存再重放指令。地址空间统一了，物理搬运没有消失——它只是从"显式拷贝"变成"按需缺页"，成本从可预测的批量传输变成不可预测的随机停顿。

```text
缺页迁移闭环：

  GPU lane 访存 ──► GPU MMU 查页表 ──(未驻留)──► 缺页异常
                                                   │
                                                   ▼
                                       驱动选择迁移方向（分流阀）
                                       ┌───────────┴───────────┐
                                       ▼                       ▼
                                 显存有余量：迁入        显存不足：回迁/直通
                                       │                       │
                                       └───────────┬───────────┘
                                                   ▼
                                        重放触发指令（可能再次缺页）
```

### 1. 缺页迁移闭环

缺页路径上的每一步都在毫秒与微秒的交界处：GPU MMU 发现页表项无效，向驱动发缺页；驱动决定迁移方向，向拷贝引擎提交页级搬运；搬运完成后更新页表、重放指令。以页为粒度（64 KB ~ 2 MB 档），一次缺页的端到端延迟在微秒至毫秒档，比 HBM 的百纳秒档高 3 ~ 4 个数量级。若访问模式是"每个页只碰一次"，缺页成本无法摊薄，UM 反而比显式拷贝更贵。

### 2. 超订与抖动

显存容量小于工作集时，UM 允许超订：页在主机与显存之间来回迁移。若访问模式呈"两个页交替访问"的抖动形态，每次访问都触发一次迁移，有效带宽跌到 PCIe 档甚至更低，吞吐可掉一个数量级。这类抖动无法靠调参消除，只能改数据布局（分块、压缩、降低精度）把工作集压进显存；05 §6 的窄化转换在这里第一次成为容量手段，而不只是吞吐手段。

### 3. 预取与收敛判据

把按需缺页改成显式预取，是把不可预测的停顿移出热路径的标准做法：在 kernel 启动前把下一段要用的页预取到显存，计算期间不再缺页。预取的代价是可能多搬了用不到的页，收益是把随机毫秒级停顿换成批量微秒级传输——只要命中率高于某个阈值就划算。

| 方案 | 有效带宽 | 首次访问延迟 | 适用规模 |
| --- | --- | --- | --- |
| 显式拷贝 | 接近链路带宽 | 批量传输，可预算 | 工作集小于显存 |
| 页锁定 + 异步拷贝 | 接近链路带宽，可与计算重叠 | 批量传输，可预算 | 稳定流水线 |
| zero-copy 映射 | 钉在 PCIe 带宽档 | 每次访问都付链路延迟 | 一次性流式读 |
| 统一内存按需迁移 | 命中时 HBM 档，缺页时链路档 | 微秒至毫秒档，不可预测 | 工作集略大于显存 |

四条路径的收敛判据是同一条乘积：迁移次数乘以迁移粒度。地址空间是否统一只是编程接口的便利，物理搬运的总量才决定性能。这条判据把本篇与前六节连起来：数值格式决定每页装多少有效数据，合并访存决定每次迁移的利用率，PCIe 通路决定搬运单价，三者相乘就是异构程序的性能上限。
