# 并行与并发

## 定义

并行是同一时刻物理上同时执行多个执行流，要求多个物理计算单元；并发是同一时间间隔内交替执行多个执行流，单核 CPU 通过时间片轮转实现逻辑并行。并行是并发的一个子集——所有并行都是并发，但并非所有并发都是并行。

并行的本质是**同时性**（Simultaneity），解决的硬件问题是单个处理单元的算力不足；并发的本质是**交替性**（Alternation），解决的软件问题是程序 IO 等待时的资源利用率。

两者的核心差异在于资源争用模式：并行中各执行单元拥有独立资源（独立寄存器集、独立栈），天然无数据竞争；并发中各执行单元共享资源，必须通过同步机制协调访问。

**归约终点**：并行是"同时性"的物理实现，并发是"交替性"的逻辑抽象。两者可统一描述为：多执行单元对有限资源的竞争与协调问题。

## 数学模型

**阿姆达尔定律（加速比上界）：**

$$
S_{max} = \frac{T_{串行}}{T_{并行}} = \frac{1}{(1-P) + \frac{P}{N}}
$$

其中 $P$ 为可并行化比例，$N$ 为并行 worker 数。当 $N \to \infty$ 时：
$$
\lim_{N \to \infty} S_{max} = \frac{1}{1-P}
$$

这意味着即使无限增加核心数，加速比也被串行部分 $1-P$ 锁死。例如 $P=0.9$（90% 可并行），最大加速比仅为 10 倍。

**Gustafson 定律（弱加速比，规模可扩展性）：**

$$
S_{weak} = \alpha + N(1-\alpha)
$$

其中 $\alpha$ 为串行部分在新问题规模中的比例。当问题规模随 $N$ 线性增长时，串行比例趋向常数，加速比可随 $N$ 线性增长。

阿姆达尔定律和 Gustafson 定律并不矛盾：前者固定问题规模，后者固定时间/资源——随核心数增加问题的规模也在增大。

**同步开销模型：**

$$
T_{同步} = T_{锁获取} + N \times T_{迁移} + T_{缓存一致性}
$$

其中各部分的物理含义与权衡关系：

| 组件 | 物理来源 | 随 N 的变化 | 典型量级 |
|------|----------|-------------|----------|
| $T_{锁获取}$ | 总线原子操作（CAS/Test-and-Set） | $O(1)$，不随 N 增长 | ~10–100 ns |
| $N \times T_{迁移}$ | 缓存行迁移（cache line bounce） | $O(N)$，与 worker 数成正比 | ~10 ns/次 × N |
| $T_{缓存一致性}$ | MESI 协议广播开销 | $O(\log N)$（总线带宽竞争加剧） | ~100 ns（固定），高竞争时非线性增长 |

**关键权衡：**

- **锁粒度 vs 并发度**：粗粒度锁（单一全局锁）使 $T_{锁获取}$ 占比低，但 $N \times T_{迁移}$ 因所有线程竞争同一缓存行而急剧增长；细粒度锁（多个分区锁）降低 $N \times T_{迁移}$，但增加 $T_{锁获取}$（更多原子操作）和 $T_{缓存一致性}$（更多锁变量）。
- **扩展临界区 vs 缩短临界区**：临界区内部操作越多，$T_{迁移}$ 被摊销，但锁持有时间 $T_{持有}$ 增长，导致 $\rho = N \lambda / \mu$ 趋向 1（利用率饱和），等待时间急剧膨胀。
- **NUMA 效应**：跨节点内存访问使 $T_{迁移}$ 成为主导因素，此时细粒度锁反而因跨节点缓存行竞争而更差，应优先考虑数据局部性（thread-local + 消息传递）。

**性能拐点判定：** 当 $T_{同步} > T_{并行收益} = T_{串行} \times (1-P)/N$ 时，增加 worker 反而降低性能。此时应检查：$T_{缓存一致性}$ 是否因总线饱和而非线性增长（$\rho \to 1$ 的队列效应），以及锁竞争是否使临界区成为新的串行瓶颈。

**临界区争用模型（M/M/1 队列近似）：**

线程竞争锁的等待时间服从以下分布。设锁持有时间为 $T_{持有}$，线程数为 $N$：
$$
\lambda = \frac{1}{T_{持有}} \quad (\text{服务率})
$$
$$
\rho = \frac{N \lambda}{\mu} \quad (\text{利用率})
$$

当 $\rho \to 1$ 时，等待时间趋向无穷——这就是锁竞争的尾部延迟问题。

**死锁充分条件（咖啡馆定理的工程表述）：**

死锁当且仅当资源分配图出现循环等待且每个节点仅有一条出边。四个必要条件（互斥持有、占有等待、不可抢占、循环等待）同时满足时死锁必然发生。

打破任一条件即可防止死锁：
- 互斥持有：改用无锁数据结构
- 占有等待：一次性申请所有资源
- 不可抢占：优先级继承协议
- 循环等待：按固定顺序获取锁

## 机制

### 同步原语

**Mutex（互斥锁）：**

互斥锁将临界区访问串行化，保证同一时刻仅一线程进入。

```cpp
// 自旋锁实现（简化）：基于 CAS 的用户态互斥
struct SpinLock {
    std::atomic<bool> locked = {false};  // 锁状态，true=已锁定
    void acquire() {
        // exchange 返回旧值；若为 false（未被锁定）则原子地置为 true，获得锁
        while (locked.exchange(true, std::memory_order_acquire)) {
            // busy-wait：锁已被其他线程持有，空转等待
        }
    }
    void release() {
        // 释放锁：写 false + release 语义确保之前所有写操作对其他线程可见
        locked.store(false, std::memory_order_release);
    }
};
```

**约束：**
- 同一时刻仅一线程持有
- 持有者必须释放（Lock/Unlock 配对）
- 锁的粒度决定并发度（粗粒度简单但低效，细粒度高效但易死锁）

**违规后果：**
- 死锁（重复加锁、不平衡释放、锁顺序不一致）
- 活锁（两个线程都谦让但持续重试，解决方案：随机退避）
- 优先级反转（低优先级持有锁，高优先级忙等，解决方案：优先级继承）

**读写锁（RWLock）：**

读者可并行，写者排他。适用于读多写少场景。

```cpp
// 读写锁：读者可并行，写者排他（reader preference）
struct RWLock {
    std::atomic<int> readers = {0};  // 当前读者数，atomic 保证跨线程可见性
    std::mutex mtx;                  // 保护写者侧的互斥锁
    void read_lock() {
        // 原子递增读者计数；acquire 语义确保后续读操作看到临界区的最新数据
        readers.fetch_add(1, std::memory_order_acquire);
    }
    void read_unlock() {
        // 原子递减读者计数；release 语义确保当前读操作在递减前完成
        readers.fetch_sub(1, std::memory_order_release);
    }
    void write_lock() { mtx.lock(); }   // 写者获取互斥锁，阻塞所有新读者
    void write_unlock() { mtx.unlock(); }
};
```

**约束：**
- 写者排他，读者可并行（reader preference）
- 读者数由 atomic 变量追踪
- 写者等待时，新读者会被阻塞（写者优先 RWLock 可避免此问题）

**违规后果：**
- 写饥饿（大量读者持续到达导致写者永久等待）
- 读写锁死锁（写者持有锁并等待读者完成，但读者在等待写者释放锁）

**信号量（Semaphore）：**

计数器表示可用资源数。P()（wait/acquire）递减，V()（signal/release）递增。

```cpp
// 信号量：P()（wait/acquire）递减计数，V()（signal/release）递增计数
struct Semaphore {
    std::atomic<int> count;                       // 可用资源数
    std::queue<std::thread::id> waiters;          // 阻塞线程的 FIFO 等待队列
    std::mutex mtx;                               // 保护等待队列的互斥锁
    void P() {
        // 原子递减计数；若原值 <= 0，说明资源耗尽，当前线程必须阻塞
        int old = count.fetch_sub(1, std::memory_order_acquire);
        if (old <= 0) {
            std::unique_lock<std::mutex> lock(mtx);  // 加锁后入队，保证队列操作原子性
            waiters.push(std::this_thread::get_id());  // 当前线程加入等待队列
            // park current thread...（线程睡眠，由 V() 的 unpark 唤醒）
        }
    }
    void V() {
        // 原子递增计数；若原值 < 0，说明有线程在阻塞，应唤醒一个
        int old = count.fetch_add(1, std::memory_order_release);
        if (old < 0) {
            std::unique_lock<std::mutex> lock(mtx);  // 保护等待队列的出队操作
            waiters.pop();                            // 取出最早等待的线程
            // unpark a waiter...（唤醒该线程）
        }
    }
};
```

**约束：**
- 计数上限初始化后固定
- PV 操作必须成对（若 V 不足，资源泄漏；若 P 超过资源数，线程阻塞）

**违规后果：**
- 资源泄漏（V 不足 → 所有线程永久阻塞）
- 计数为负时线程阻塞在 P()

**屏障（Barrier）：**

所有线程到达后同时继续，用于批量同步。

```cpp
// 屏障（Barrier）：所有线程到达后同时继续，用于批量同步
struct Barrier {
    std::atomic<int> arrived = {0};    // 已到达线程计数器
    int total;                         // 参与线程总数（初始化时确定）
    std::mutex mtx;                    // 保护条件变量的互斥锁
    std::condition_variable cv;         // 阻塞未到达线程的条件变量
    void wait() {
        // 原子递增并返回旧值；若达到 total，则自己是最后一个到达的线程
        int prev = arrived.fetch_add(1, std::memory_order_acq_rel);
        if (prev + 1 == total) {
            // 最后一个到达：重置计数器（为下一轮屏障做准备）并唤醒所有等待线程
            arrived.store(0, std::memory_order_release);
            cv.notify_all();
        } else {
            // 非最后线程：阻塞在条件变量上，等待最后一个线程调用 notify_all
            std::unique_lock<std::mutex> lock(mtx);
            cv.wait(lock);
        }
    }
};
```

**约束：**
- 参与线程数必须在初始化时确定
- 所有线程必须到达同一屏障点

**违规后果：**
- 某线程永远不调用 wait() → 其他线程永久等待
- 线程数动态变化 → 计数不匹配

### 死锁条件与预防

死锁的四个必要条件（1971 年 Coffman 证明）：

1. **互斥持有（Mutual Exclusion）**：资源被一个线程独占持有
2. **占有等待（Hold and Wait）**：持有资源的同时请求其他资源
3. **不可抢占（No Preemption）**：资源不能被强制夺走
4. **循环等待（Circular Wait）**：形成线程→资源→线程的环

**资源分配图检测法：**

若资源分配图和进程等待图合二为一后存在环，则死锁必然发生。

**工程实践中的死锁预防：**
- **锁顺序**：所有线程按固定顺序获取锁（避免循环等待）
- **一次性获取**：pthread_mutex_lock_all() 一次性申请多个锁（避免占有等待）
- **无锁设计**：使用 lock-free 数据结构（避免互斥持有）
- **优先级继承**：低优先级线程持有高优先级线程想要的锁时，临时提升低优先级（避免优先级反转）

### 无锁数据结构

**CAS（Compare-And-Swap）原语：**

```cpp
// 伪代码：无锁栈 push
void push(Node* new_node) {
    Node* old_head;
    do {
        old_head = head.load();
        new_node->next = old_head;
    } while (!head.compare_exchange_weak(old_head, new_node));
    // 若 head 已变为 old_head（其他线程修改），重新尝试
}
```

**无锁 vs 有锁：**
- 无锁保证至少有一个线程在有限步骤内完成（wait-free）
- 有锁在锁竞争激烈时可能导致线程饥饿
- 无锁代码更复杂，但避免了锁的上下文切换开销

### Python GIL

CPython 的 GIL（Global Interpreter Lock）将 Python 字节码执行限制在单线程，同一时刻仅一线程执行 Python 字节码。

**为什么需要 GIL：**
CPython 的内存管理不是线程安全的。引用计数是主要内存管理手段，若无 GIL，两个线程同时引用计数更新会导致内存泄漏或提前释放。GIL 保证了引用计数的原子性。

**约束：**
- IO 等待时线程让出 GIL（`threading` 库对 IO 密集型有效）
- CPU 密集型操作无法并行（多线程竞争 GIL，实质是串行）
- 扩展库（numpy/Cython/PyPy）释放 GIL 做 native 计算

**GIL 的调度策略：**
- 每 5ms（`CHECK_INTERVAL`），当前线程检查 `eval_breaker` 标志
- 若有挂起信号或当前线程用完时间片，设置 `eval_breaker`，强制释放 GIL
- 下一线程通过 `PyThreadState_New()` 竞争 GIL

**违规后果：**
- CPU 密集型多线程反而更慢（GIL 争用开销 + 线程切换开销）
- 解决方案：multiprocessing（进程池）或 asyncio（协作式并发）
