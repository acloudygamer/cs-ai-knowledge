# 指令执行

> **版本基准**: universal

## 定义

指令执行是 CPU 按照指令周期（取指→译码→执行→访存→写回）对存储在内存中的指令序列进行解码并完成数据变换的过程。每一指令是 CPU 硬件能完成的最原子操作——它要么完成一次数据移动，要么完成一次算术逻辑运算，要么完成一次控制流跳转。CPU 的全部功能都是这三类指令的组合。

指令执行的核心矛盾在于：指令流是串行的（PC 顺序递增），而计算资源（流水线、ALU、寄存器文件）可以并行。CPU 架构设计者的任务就是最大化指令级并行（ILP），同时保持程序员的指令执行模型（顺序语义）的可见性。

**归约终点**：从数学上讲，指令执行是一个有限状态自动机（FSA）：状态是寄存器/内存的内容，输入是下一条指令，转移函数是 ALU/控制单元定义的运算。流水线将这个 FSA 的执行重叠在时间维度上，但状态转移的逻辑顺序不变。

## 数学模型

### 流水线吞吐率与加速比

理想五级流水线每个周期完成一条指令，CPI = 1。吞吐率定义为：

$$
TP = \frac{指令数}{周期数} = \frac{N}{T_{周期} \times CPI}
$$

实际 CPI 受冒险损失影响：

$$
CPI_{实际} = CPI_{理想} + \sum Hazards
$$

流水线的理论加速比（相对于单周期非流水线）为流水线级数 $N_{stage}$ ：

$$
S_{流水线} = \frac{T_{非流水}}{T_{流水}} = N_{stage} \quad (\text{忽略冒险})
$$

但由于流水线寄存器延迟（Setup + Hold time）和时钟 skew，实际加速比略低。

### 分支预测错误惩罚模型

分支预测错误时，流水线必须清空（flush），浪费的周期数为流水线深度。吞吐率损失建模为：

$$
P_{错误} = f_{分支} \times r_{错误} \times \delta_{惩罚}
$$

其中 $f_{分支}$ 为分支指令频率（~15-20%）， $r_{错误}$ 为预测错误率（~5-10%），$\delta_{惩罚}$ 为流水线清空代价（10-20 周期，取决于流水线深度）。

### TAGE 分支预测器错误率

TAGE（TAken GEometry）使用多组历史长度不同的分支历史表（256b 到 4Kb 全局历史），选择匹配历史最长的表项进行预测。错误率近似：

$$
r_{错误} \approx \frac{1}{\sqrt{H_{matched}}}
$$

其中 $H_{matched}$ 是命中的最长历史长度。对于高度可预测的分支（如循环退出）， $r_{错误} < 1\%$ ；对于不可预测的分支（如间接跳转表），$r_{错误} \sim 10-20\%$。

### 数据冒险检测（WAR/WAW/RAW）

两条相邻指令 $i$ （先执行）和 $j$ （后执行）存在数据冒险当且仅当：

$$
RAW: \quad \text{Write}(i) \cap \text{Read}(j) \neq \emptyset \quad \text{（先写后读）}
$$

$$
WAW: \quad \text{Write}(i) \cap \text{Write}(j) \neq \emptyset \quad \text{（先写后写）}
$$

$$
WAR: \quad \text{Read}(i) \cap \text{Write}(j) \neq \emptyset \quad \text{（先读后写）}
$$

RAW 是真实依赖（True Dependency），必须通过转发或停顿解决。WAR 和 WAW 是名称依赖（Name Dependency），在顺序执行流水线中不可能发生（因为顺序发射→顺序完成），但乱序执行流水线中需要寄存器重命名来消除。

### 寄存器重命名消除 WAR/WAW

物理寄存器数 $N_{phys}$ 远大于架构寄存器数 $N_{arch}$ （如 x86-64：16 通用寄存器 vs 128-256 物理寄存器）。每条指令发射时从空闲列表分配一个新物理寄存器，结果写入该物理寄存器。WAR/WAW 通过让后序指令写入不同的物理寄存器来消除：

$$
\text{reg}_{dest}(j) = \text{alloc()} \neq \text{reg}_{dest}(i) \quad \text{（若相同旧名）}
$$

### x86 内存模型的形式化描述

x86 使用 Processor Consistency + Store Order（PSO/TSO）。每个 CPU 的 stores 按程序顺序出现在总线上，但其他 CPU 看到 stores 的顺序可能不同（由于 store buffer 的存在）。形式化约束：

$$
\text{Program Order} \xrightarrow{} \text{Store Buffer} \xrightarrow{} \text{L1d}
$$

`MFENCE` 强制 store buffer 中的所有 store 按序刷入 cache。

## 数据流

<pre>
指令 i       指令 i+1      指令 i+2      指令 i+3
   │             │             │             │
IF ──────► ID ──────► EX ──────► MEM ──────► WB    (指令 i)
   │        IF ──────► ID ──────► EX ──────► MEM ──► WB   (指令 i+1)
   │        │        IF ──────► ID ──────► EX ──────► MEM  (i+2)
   │        │        │        IF ──────► ID ──────► EX    (i+3)
   │        │        │        │              ↑
   │        │        │        │         分支预测错误时
   │        │        │        │         这里开始清空流水线
   └────────┴────────┴────────┘

转发路径（Data Forwarding）：
   EX/MEM 流水线寄存器 ──→ EX 阶段输入 （解决 RAW 冒险）
   MEM/WB 流水线寄存器 ──→ EX 阶段输入
</pre>

**完整五级流水线数据流**：

<pre>
PC（程序计数器）
    │
    ├──→ 指令缓存（I-cache）读取 32/64bit 指令字
    │        ↓
    │    IF/ID 流水线寄存器（保存 PC, IR）
    │        ↓
    │    译码阶段（ID）
    │    ├──→ 操作码 → 控制单元 → 控制信号
    │    ├──→ 寄存器文件读取（2-3 个源操作数）
    │    └──→ 立即数符号扩展
    │        ↓
    │    ID/EX 流水线寄存器（保存操作数、控制信号）
    │        ↓
    │    执行阶段（EX）
    │    ├──→ ALU 执行（算术/逻辑）
    │    ├──→ 有效地址计算（load/store）
    │    └──→ 分支条件判断 + 目标计算
    │        ↓
    │    EX/MEM 流水线寄存器（保存结果、分支决策）
    │        ↓
    │    访存阶段（MEM）
    │    ├──→ 数据缓存（D-cache）访问
    │    │    ├──→ Load：cache → 寄存器
    │    │    └──→ Store：寄存器 → cache
    │    └──→ 分支目标 PC 更新（若分支决策在 EX 做出）
    │        ↓
    │    MEM/WB 流水线寄存器
    │        ↓
    │    写回阶段（WB）
    │    └──→ 结果写回寄存器文件
</pre>

**乱序执行（Out-of-Order）数据流**：

<pre>
顺序发射队列（Issue Queue）
    │
    ├──→ 指令1 (ready) ──► EX (ALU)
    ├──→ 指令2 (waiting for operand) ──► 等待
    ├──→ 指令3 (ready) ──► EX (ALU)
    └──→ 指令4 (waiting for mem) ──► 等待

寄存器重命名：
    架构寄存器 (x0-x31) ──→ 物理寄存器 (物理寄存器堆 128 项)
    │
    ├──→ 每条指令发射时分配新物理寄存器
    ├──→ 重排缓冲区（ROB）维持顺序提交
    └──→ 指令完成后标记 ROB 项为完成
    │
    └──→ 按顺序提交（Commit），释放旧物理寄存器

Store Buffer（Store Queue）：
    所有 Store 指令经 ROB 顺序发射到 Store Buffer
    Store Buffer 与 L1d 之间：乱序写入
    Store-to-Load Forwarding：同地址 Load 可直接从 Store Buffer 读取未提交数据
</pre>

**数据所有权在流水线中的变换**：

<pre>
指令 i:    [源寄存器读取] → [ALU计算] → [结果写回寄存器]
               ↓
          寄存器文件（架构寄存器 → 物理寄存器映射）
               ↓
指令 j:    [从转发路径获取i的结果] → [使用新物理寄存器]
               ↓
          ROB 中按顺序提交时，旧物理寄存器释放回空闲列表
</pre>

## 机制

### 五级流水线

流水线通过重叠执行多条指令提升吞吐。理想情况下，每个周期完成一条指令，CPI = 1。但三条冒险会导致流水线暂停或清空。

**流水线各级功能**：
- **IF（Instruction Fetch）**：从 I-cache 取指令，更新 PC
- **ID（Instruction Decode）**：译码 + 读取寄存器
- **EX（Execute）**：ALU 运算或地址计算
- **MEM（Memory Access）**：数据 cache 访问（仅 load/store）
- **WB（Write Back）**：结果写回寄存器文件

**约束条件**：
- 各阶段延迟需大致均衡（否则最慢阶段成为瓶颈）
- 指令间无数据依赖才能并行执行
- 条件分支在译码阶段无法确定目标（需等待 EX 阶段条件码）

**违规后果**：
- **数据冒险（Data Hazard）**：RAW 导致数据相关指令不能并行
- **结构冒险（Structural Hazard）**：硬件资源不足（如单端口 register file 同时读写）
- **控制冒险（Control Hazard）**：分支指令在取下一条指令前无法确定 PC

### 微操作缓存（Micro-op Cache / OP Cache）

现代 x86 CPU 在 IF 阶段之后增加微操作缓存（op cache），将已译码的微操作缓存起来。对于循环体，op cache 可以避免重复译码开销，直接从缓存中发射微操作到后端流水线。

**op cache 的数据结构**：

Op cache 是一个由 PC 索引的查找表，每条目包含 1-4 条微操作（对应一条 x86 指令）。命中时，流水线跳过 IF/ID 阶段，直接从 op cache 发射到后端乱序调度器。这对于 I-cache miss 率高的 workloads 尤其有效（可降低 10-15% 的前端气泡）。

**约束条件**：
- op cache 条目有限（通常 1-2K 条目）
- 间接分支（jmp rax）需要查表，无法从 op cache 受益
- op cache 与 I-cache 的替换策略需要协同设计

### 指令类型（RISC-V 格式）

| 类型 | 格式 | 操作 | 访存 |
|------|------|------|------|
| R 型 | `opcode rd, rs1, rs2` | ALU 寄存器-寄存器运算 | 否 |
| I 型 | `opcode rd, rs1, imm12` | ALU 立即数运算、load | load |
| S 型 | `opcode rs2, rs1, imm12` | store | store |
| B 型 | `opcode rs1, rs2, imm13` | 条件分支 | 否 |
| U 型 | `opcode rd, imm20` | lui, auipc | 否 |
| J 型 | `opcode rd, imm21` | jal（直接跳转） | 否 |

### 分支预测

分支预测降低控制冒险影响。现代 CPU 采用多层级混合分支预测器（TAGE 或 neural branch predictor）。

**分支目标缓冲器（BTB）**：

- 记录已知分支指令的跳转目标地址
- 取指时用 PC 查询 BTB，预测本次是否跳转及目标地址
- 未在 BTB 中的地址默认为非分支（fall-through）

BTB 是组相联 cache（如 16-way，8K 条目），用 PC 的高位做索引。BTB 条目包含：分支目标地址、分支类型（直接/间接/返回）、预测方向。为减少延迟，现代 BTB 采用流水线设计（First-line BTB 在 IF 阶段完成查找）。

**分支历史表（BHT）/模式历史表（PHT）**：

- 记录分支指令的历史跳转情况
- 2 位饱和计数器：Strongly Taken → Weakly Taken → Weakly Not Taken → Strongly Not Taken
- 混合预测器使用多组计数器，根据历史长度选择最优计数器组

**TAGE 预测器（Intel Skylake+ 采用）**：

TAGE 使用多组历史长度递增的分支历史表（Base table + 多个 Tagged tables）。每组表用全局分支历史（Global History Register，GHR）做索引。预测时，选择历史最长且标签匹配（tag match）的表项。若均不匹配，使用基表（2-bit 饱和计数器，无历史）。

**返回地址栈（Return Stack Buffer，RSB）**：

CALL 指令将返回地址压栈，RET 指令从栈中弹出。RSB 是硬件实现的浅栈（8-32 项），用于预测 RET 的目标地址。当 CALL 嵌套深度超过 RSB 容量时，RSB 底部填充预测值（通常为 fall-through 地址）。

**约束条件**：
- 动态预测需历史信息（PHT/BHT/GHR），短期历史 0-12 位
- 分支方向和目标分别预测
- 错误预测后需回滚寄存器状态（ROB）

**违规后果**：
- 错误预测导致流水线清空（flush），浪费 10-20 周期
- 错误率每上升 1%，CPI 增加约 0.2-0.3
- Spectre 变种可通过恶意分支模式操纵预测器（边界检查绕过、ROP 攻击）

### 乱序执行（Out-of-Order Execution）

超标量 CPU 在流水线内部实现乱序执行，通过寄存器重命名消除 WAR/WAW 冒险。

**寄存器重命名机制**：

- 程序员可见的架构寄存器（如 x86 的 16 个通用寄存器）映射到物理寄存器
- 每条指令发射时分配新的物理寄存器
- 重排缓冲区（ROB）维持指令顺序提交，保证精确中断

**物理寄存器文件（Physical Register File）**：

如 Intel Haswell 有 168 个物理整数寄存器 + 168 个物理浮点寄存器，远超 16 个架构整数寄存器 + 8 个 XMM 寄存器。物理寄存器在指令发射时分配，在指令 retirement（提交）时释放回空闲列表。

**空闲列表管理（Free List）**：

物理寄存器释放后加入空闲列表（Free List）。分配时从列表尾部 pop。 retire 时，旧物理寄存器（被新映射替代的那个）被标记为可重用，加入空闲列表。

**发射队列（Issue Queue/IQ）**：

- 指令译码后进入 IQ，等待操作数就绪
- 操作数就绪后发射到功能单元
- IQ 仲裁器选择可发射指令（通常选择最老的 Ready 指令——oldest-ready-first）
- 发射宽度：每周期可发射 4-6 条指令（Skylake：4 INT + 2 FP）

**重排缓冲区（ReOrder Buffer，ROB）**：

ROB 按程序顺序存储所有 in-flight 指令。条目包含：目标架构寄存器、目标物理寄存器、完成位、异常标志。指令完成后标记完成位，但只有当所有更早的指令也完成后，才能按顺序 retire。

**乱序执行的内存 ordering 问题**：

- 加载和存储指令的顺序可能被打乱（Store-to-Load 转发除外）
- 内存 ordering 由 Load Store Queue（LSQ）维护
- x86 使用强内存模型（程序顺序 + store_forward），ARM/RISC-V 使用弱内存模型

**Store-to-Load 转发（Store Forwarding）**：

当一条 Load 指令在 LSQ 中等待执行时，如果在其之前有一条 Store 指令写入相同地址，则 Load 可以直接从 Store Buffer 中读取未写入 cache 的数据，无需等待 Store retire。这避免了在 Store 未提交时 Load 被阻塞的问题。

**约束条件**：
- 物理寄存器数量有限，满时指令必须在 IQ 中等待
- ROB 满时流水线必须停顿（无法接收新指令）
- 乱序执行必须保证精确异常（Precise Exception）

**违规后果**：
- 乱序执行的内存访问需严格按序提交
- 推测执行（Speculative Execution）可能导致 Meltdown/Spectre 侧信道攻击
- 乱序执行增加了验证复杂度（内存 ordering violations）

### 内存 ordering 与屏障

**Store Buffer 与 Load Forwarding**：

Store 指令的结果先写入 Store Buffer，后续同地址的 Load 可直接从 Buffer 转发，绕过 cache。

**内存屏障（Memory Barrier/Fence）**：

- **写屏障（Store Barrier）**：确保在屏障前的所有 store 在屏障后的 store 之前完成
- **读屏障（Load Barrier）**：确保在屏障前的所有 load 在屏障后的 load 之前完成
- **全屏障（Full Barrier）**：同时包含读写屏障

**ARMv8/POWER 弱内存模型的问题**：

弱内存模型下，编译器和 CPU 都可以重排内存访问顺序。Store Buffer 深度更大（比 x86），允许更多写重排。Barrier 指令（ISB/DMB in ARM）强制刷新流水线/store buffer。

**违规后果**：
- 弱内存模型不正确的同步导致死锁或数据损坏
- 编译器优化可能重排弱内存模型下的内存访问
