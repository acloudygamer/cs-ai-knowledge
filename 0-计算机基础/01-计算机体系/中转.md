### 微架构补篇：一条指令从取指到退休的物理漂流

ROB、MSHR 这些部件在系统健康时如何协同工作？本节回到“和平时期”，完整展开一条指令在现代乱序执行（Out-of-Order）微架构中的生命周期——代码在物理层面的执行早已脱离表面的线性逻辑，而是经历一场高度并发的“物理漂流”。

一条指令的完整生命周期，会严格穿过以下五个核心组件，每种 $\mu$ op 类型在其中各有独特的漂流轨迹：

**1. 粮草先行：L1I 与前端（Front-End）的“碎肉机”与“豪赌”**

一切的起点在前端。前端从 L1I（L1 指令缓存）中抓取宏观的机器码（比如汇编里的 MOV 或 ADD）。随后，解码器（Decoder）像碎肉机一样，将这些复杂的宏观指令切碎成 CPU 执行引擎能看懂的原子物理动作——微操作（ $\mu$ ops）。正是从这里开始，ALU $\mu$ ops、Load/Store $\mu$ ops、Branch $\mu$ ops 正式分道扬镳。

在切碎指令的同时，前端还有一个关键组件在同步工作——**RAT（寄存器别名表，Register Alias Table）**。硅片上根本不存在名叫 RAX、RBX 的物理存储盒子；真实存在的是一组编号 P1、P2……P300 的**物理寄存器堆（PRF）**。RAT 就是前端手里的一张翻译表，将程序员写的架构寄存器名实时映射到 PRF 里的物理编号。每当解码器切出一条会修改寄存器的 $\mu$ op，RAT 立刻做两件事：从 PRF 空闲池里抓一个新 P 盒子作为**目标**，并记下该架构寄存器当前指向的旧 P 盒子作为**前任**——这张“前任指针”正是第 2 段要展开的核心。

遇到条件跳转指令（if-else）时，前端的分支预测器（Branch Predictor）不会停下来等——它基于历史记录“猜”一个方向，立刻顺着猜测路径把后续代码疯狂切碎成 $\mu$ ops 塞进后端，RAT 照常为它们分配 P 盒子。这就是**投机执行（Speculative Execution）**：整个 CPU 都在为一个未经证实的猜测打白工。等 Branch $\mu$ op 在 Branch 执行单元算出真实跳转方向后，与前端猜测对比：赌赢了，皆大欢喜；**赌输了（Misprediction），触发 Pipeline Flush（流水线冲刷）**——ROB 无情抹杀排在 Branch 后面的所有 $\mu$ ops，它们占用的 P 盒子全部释放回空闲池。前端调转车头去正确地址重新抓取、重新解码、重新排队。这就是“投机废请求”的物理根因。

**2. RAT、ROB 与寄存器重命名：前任指针的暴力美学**

所有被解码出的 $\mu$ ops 必须先去 ROB 挂号登记。ROB 是容量物理焊死的环形队列，遵循铁律：严格按代码顺序分配坑位，也必须按挂号顺序出院（顺序退休，In-Order Retire）。挂完号后各 $\mu$ op 分赴车间——ALU 去 RS、Load/Store 去 LSQ、Branch 去 Branch 执行单元。

**RAT 与“前任指针”——死亡通知单的签发**

退休的物理真相：硅片上不存在名叫 RAX 的存储盒子——真实存在的是**物理寄存器堆（PRF，Physical Register File）**，大约 200 到 300 个一模一样的 64 位物理盒子，只有冰冷的编号 P1、P2……P300。RAX 只是前端 RAT（寄存器别名表，Register Alias Table）手里捏着的一张便利贴。

当一条修改 RAX 的指令进入 ROB 时，前端 RAT 为它做两件事：

1. 从 PRF 空闲池里抓一个新 P 盒子作为**目标**（比如 P20）。
2. 记录当前 RAT 中 RAX 指向的旧 P 盒子作为**前任**（比如 P10）。

于是这条 $\mu$ op 在 ROB 里的档案写成：`[坑位 N] [目标: P20] [前任: P10]`。这张“前任指针”就是一张死亡通知单——只有等这条 $\mu$ op 自己平安退休，P10 才会被处决释放。在此之前，无论 P20 里的新值算得多快，**P10 都必须活着**——万一这条 $\mu$ op 被 Branch 误判掀了桌子，系统还指望 P10 恢复旧状态。

下面用一个极端剧本展示这套机制的暴力美学。四行代码，三次修改 RAX，中间插一条分支：

```
ADD RAX, 1              ; 造物主（极快，1周期）
LOAD RAX, [极慢内存]     ; 老慢牛兼刺客1（极慢，300周期）
CMP RAX, 0; JEQ label   ; 分支赌徒（快）
MOV RAX, 2              ; 刺客2（极快，1周期）
```

——先假设分支赌徒**赌赢了**（预测正确），只看寄存器重命名的连锁反应。

**第一幕：RAT 发牌——签发死亡通知单**

前端 RAT 为四条指令签发档案：

| ROB | 指令 | 目标 | 前任 | 状态 |
|-----|------|------|------|------|
| #1 | ADD | P10 | P0 | 造物主 |
| #2 | LOAD | P20 | P10 | 老慢牛，手持 P10 死亡通知单 |
| #3 | CMP | — | — | 分支赌徒，不写 GPR（FLAGS 同理可重命名，例中略） |
| #4 | MOV | P30 | P20 | 刺客2，手持 P20 死亡通知单 |

关键：刺客2 领到的前任是 P20（老慢牛的目标），不是 P10。寄存器的“刺客链”按指令顺序传递——每一任新写入者只刺杀自己的直接前任。

**第二幕：乱序大塞车**

- #1（造物主）：瞬间算完，P10 装着 `1`，Done。
- #3（分支赌徒）：瞬间算完，与前端猜测一致，Done。
- #4（刺客2）：瞬间算完，P30 装着 `2`，Done——但只能当“地下情人”，#2 还没走。
- #2（老慢牛）：Load 指令，Cache Miss，P20 空壳，300 周期后才拿回数据。

ROB 1~4 号坑全满，前端停工。核心表面 IPC 极低，但 P10（旧值 1）和 P30（新值 2）都在 PRF 里活着，只等排队号依次清关。

**第三幕：连环退休与斩杀**

- **T=1**：#1（造物主）熬到头部，退休。RAT 正式宣布 P10 为官方 RAX（值 1）。P0 被斩杀。老慢牛 #2 升为头部——未 Done，卡死。
- **T=2~301**：长达 300 周期的死寂。#2 不死，#3 和 #4 谁也退不了休。
- **T=302**：#2（老慢牛）终于拿回数据填进 P20，Done。退休！P20 成为官方 RAX。老慢牛触发手中死亡通知单——**P10 被当场斩杀**。
- **T=303**：#3（分支赌徒）退休，不碰寄存器，默默消失。
- **T=304**：#4（刺客2）退休！P30 成为官方 RAX（值 2）。触发死亡通知单——**P20 被斩杀**。P20 作为官方 RAX 仅活了 2 个周期就遭处决。

物理寄存器的生死，完全不看你算得有多快或等得有多慢，只看你手里的前任指针以及你在 ROB 里的排队号。老慢牛就算慢到令人发指，只要它背负着斩杀前任的使命，在退休那一刻它依然完美履行职责，绝不会让旧盒子泄漏。

**第四幕：如果分支赌徒赌输了——流水线冲刷与前任指针的韧性**

回放第二幕，假设 #3（CMP）算完后发现前端猜错了方向（Misprediction）。

Branch 执行单元立刻拉响警报：ROB 查找 #3 的排队号，把**排在它后面的所有条目**——包括 #4（刺客2）——全部抹杀。P30 虽然算好了数据，永远失去退休资格，直接释放回空闲池。前端调转车头去正确地址重新抓取。

但关键来了：**#2（老慢牛）排在 #3 前面，不受冲刷影响。** 老慢牛依然卡在 ROB 里等它的数据，手中那张“斩杀 P10”的死亡通知单依然有效——退休瞬间照样处决 P10。P20 也不会因 #4 被抹杀而泄漏：它的斩杀者只是从 #4 换成了分支之后新流入的写 RAX 指令（新指令重命名时领到的前任正是 P20）——先由 #2 退休时处决 P10，再由新来者退休时处决 P20。

这正是前任指针的暴力美学精髓：**分支冲刷只摧毁排队号大于 Branch 的条目，已被签发但未退休的前任关系，只要刺杀者本身存活在外，就永不失效。** 跑得再快的 ALU 也得陪最慢的 Load 排队；而 Branch 是这套精密机制中唯一的“暴力拆迁”——只要在执行单元算出真实方向时发现赌错（无需等它爬到 ROB 头部），排在它后面的所有条目立即全部作废，横扫千军。

**3. 乱序的狂欢者：LSQ（访存队列）与 MLP 的“翻找”**

Load 和 Store $\mu$ ops 挂完号后，会被塞进 LSQ（Load/Store Queue）。与 ROB 极其死板的“按序排队”截然不同，LSQ 是一个极度疯狂的竞技场——CPU 调度器会利用内存级并行（MLP，Memory-Level Parallelism），在 LSQ 中向后疯狂“翻找”，只要确认后面的 Load 指令与前面的指令没有地址依赖冲突，它就会越过还在苦等老慢牛的旧指令，把后续的 Load 提前发射（Issue）出去。这种疯狂的翻找让多个 Cache Miss 请求能同时在 MSHR 和物理总线上飞驰，这正是“乱序执行”的精髓。

Store $\mu$ op 在 LSQ 中有着特殊的物理身份。它被解码为 STA（Store Address，算目标地址）和 STD（Store Data，准备数据）两个 $\mu$ ops，存入 LSQ 中的 Store Buffer（写缓存队列）特区。

Store 并没有绕过 PRF——执行 MOV [0x8000], RAX 时，RAX 的值仍然通过 RAT 从 PRF 中读取。但 Store 与 ALU 的根本区别在于**目标**：ALU 的结果写入寄存器，需要从 PRF 申请一个新的目标 P 盒子并建立 RAT 映射——这个新映射就是旧值的“刺客”，退休时正式夺权；Store 的目标是内存地址，而**内存不做寄存器重命名**——没有 P 盒子可供抢占，也不产生需要 GC 的 RAT 条目。代价则是：一旦写错就无法撤销，因此 Store 在退休前**绝对不允许**触碰 L1D。

往寄存器里写错数据可以丢弃临时物理寄存器撤销，但往 L1D 里写错数据会污染整个系统的物理状态。乱序执行是投机的，排在它前面的指令随时可能触发异常或分支预测失败，这条 Store 随时可能被作废。算完的 Store 只能把数据紧紧憋在 Store Buffer 里，苦熬到 ROB 最头部、确信绝不会被作废时，才在退休瞬间将数据正式烙印进 L1D（或扔给 L2/主存）。

LSQ 还有一个精妙的内部消化机制——**Store-to-Load Forwarding（存储到加载转发）**：如果 Store 正憋着数据不写进 L1D，排在后面恰好要读同一地址的 Load 去 L1D 读就会读到旧数据。LSQ 让后面的 Load 先扫描前面的 Store Buffer，如果发现里面正好有自己需要的数据，直接从 Store Buffer 里“偷”过来，省去了敲 L1D 门的巨大延迟。

**4. 物理触水与包裹打包：L1D 与 Cache Line**

被提前发射的 Load $\mu$ op 终于抵达了它的第一目的地：L1D（L1 数据缓存）。CPU 内部的数据搬运绝不是“要几个字节就给几个字节”——为了利用空间局部性，L1D 与外部内存的数据交换是以 Cache Line（通常为 64 字节）为最小单位的整体打包搬运。

- **命中（Cache Hit）**：如果 L1D 里有这个数据， $\mu$ op 在几个周期内就能拿到结果，随后立刻向 ROB 报告“我算完了”，安静等待退休。
- **缺失（Cache Miss）**：如果 L1D 中没有需要的数据，LSQ 的疯狂就会遇到物理边界。

**5. 兜底催单本：MSHR（缺失状态保持寄存器）**

当 L1D Miss 发生时，缓存控制器必须向更慢的 L2/L3 或主存发起物理请求。在等待这 64B 数据跨越漫长总线返回的几百个周期里，控制器必须把这笔“未决请求（Pending Request）”登记在 MSHR 中。MSHR 记录了“正在向外要哪个 Cache Line”以及“回来后喂给哪个等待中的 $\mu$ op”，一个核心通常只有 10 到 16 个物理条目——它是限制 MLP 无限度向外索取带宽的终极硬件闸门。

当 MSHR 条目耗尽、ROB 被最老的慢 Load 锁死时，上述有序的物理漂流就会全面崩解，滑入撞墙过程。
