# 数据表示与字节序

## 一、定宽模环：补码、符号扩展与溢出判据

寄存器里没有"负数"这个对象，只有 n 个触发器承载的比特串。减法、比较、取负共用同一套加法器，差别只在于事后按哪条规则解释符号位。把 n 位比特串的全部取值首尾相接，就得到一个模 $2^n$ 的加法环；所谓补码，只是给环上每个位置配一个带符号读法的约定。

```text
8 位模 256 环的展开（上排无符号读法，下排补码读法）：

  状态     0x00  0x01  0x02  ...  0x7E  0x7F  0x80  0x81  ...  0xFE  0xFF
  无符号     0     1     2        126   127   128   129        254   255
  补码       0     1     2        126   127  -128  -127         -2    -1
                                             ▲
                                    符号位 bit7 在此由 0 翻 1：
                                    同一比特串的读法跳变 256 = 2^8

  加 1：0xFF ──► 0x00   回绕，进位标志 CF=1
  减 1：0x00 ──► 0xFF   借位，CF=1
  加 1：0x7F ──► 0x80   有符号越界，溢出标志 OF=1，CF=0
```

### 1. 环上的加与减：CF 与 OF 的分工

加法器的物理输出只有 n 位和与一条进位链，硬件不区分有符号与无符号。无符号解释下越过 0xFF 的回绕被记录为进位标志 CF；有符号解释下越过 +127 或 -128 的跳变被记录为溢出标志 OF。两者的判据不同源：CF 看最高位是否向外进位，OF 看最高位进位与次高位进位是否不一致——符号位被低位进位推翻了，才叫有符号溢出。写成式子即

$$\text{OF} = C_{n} \oplus C_{n-1}$$

其中 $C_{n}$ 是最高位向外的进位， $C_{n-1}$ 是次高位向符号位的进位。减法不另设电路，而是把减数取补后相加，借位同样落在 CF 上。于是"无符号溢出"与"有符号溢出"是两个正交的事实：0x7F 加 1 时 OF=1 而 CF=0，0xFF 加 1 时 CF=1 而 OF=0。编译器对无符号类型只看 CF，对有符号类型只看 OF，这条分工决定了下文所有比较与断言的生成方式。

环上每个状态都同时挂着两个值，二者的差恒为 $2^n$ 的整数倍：低半环（符号位为 0）两种读法相同，高半环（符号位为 1）补码读法比无符号读法小 $2^n$。这条恒等式是后面所有符号扩展、宽度转换与端序讨论的算术底座——改变位宽就是改变环的周长，改变解释只改变读数，不改变比特。

### 2. 宽度扩展：movsx 与 movzx 的分岔

把 8 位值搬进 64 位寄存器时，高 56 位填什么由指令而非数据决定。`movzx`（零扩展）补 0，把 0xFF 读成 255；`movsx`（符号扩展）复制 bit7，把 0xFF 读成 -1。两条指令在寄存器里留下不同的 64 位串，后续所有比较、除法、地址计算都继承这个差异。

```text
0xFF 装入 64 位寄存器的两条路径（bit63 在左）：

  RAX = 0000 0000 0000 0000 ... 0000 0000 1111 1111   movzx → 255
  RAX = 1111 1111 1111 1111 ... 1111 1111 1111 1111   movsx → -1

  与 64 位常量 -1 比较：
    movzx 路径：255 ≠ 0xFFFF_FFFF_FFFF_FFFF，比较为假
    movsx 路径：两边同为全 1，比较为真
```

C 语言的整型提升规则正是这条硬件分岔的投影：`char`、`short` 参与运算前先提升到 `int`，有符号类型走 `movsx`，无符号类型走 `movzx`。若把一个负数按无符号读法提升，它会变成 $2^{64}-|x|$ 量级的大正数，比较方向整体翻转——这是"同一份二进制、两种读法"在软件层最常触发的错误。反之，把无符号值窄化再符号扩展，则会把高位为 1 的合法值变成负数。宽度转换的每一条路径都必须在"保号"与"补零"之间明确选边，没有默认正确项。

| 位宽 | 无符号值域 | 补码值域 | 加 1 回绕点 | 典型宿主 |
| --- | --- | --- | --- | --- |
| 8 | 0 ~ 255 | -128 ~ 127 | 0xFF 回到 0x00 | 字节、`char`、协议字段 |
| 16 | 0 ~ 65535 | -32768 ~ 32767 | 0xFFFF 回到 0x0000 | 短整型、UTF-16 码元 |
| 32 | 0 ~ 4294967295 | -2147483648 ~ 2147483647 | 全 1 回到 0 | `int`、FP32 的位容器 |
| 64 | 0 ~ $2^{64}-1$ | $-2^{63}$ ~ $2^{63}-1$ | 全 1 回到 0 | 指针、`long`、通用寄存器 |

### 3. 取负、除法与未定义行为

取负在环上是"按位取反再加 1"，即 $-x = \sim x + 1$，不需要独立的减法器。环上唯一没有对称点的是最负值：8 位的 -128 取负仍是 -128（0x80 取反得 0x7F，加 1 回到 0x80），64 位的 `INT64_MIN` 同理。这不是硬件缺陷，而是环上状态数为偶数、零点只有一个的必然结果。软件层因此把 `-INT_MIN` 与 `abs(INT_MIN)` 划入未定义行为；除法更直接——`INT_MIN / -1` 的商无法在 n 位内表示，x86 的 `idiv` 触发除零异常（#DE），而不是回绕。

有符号溢出的未定义性给了编译器优化空间：既然溢出"不会发生"，`x + 1 > x` 可以被折叠为恒真，循环归纳变量可以假设单调。工程上要安全地做回绕运算，必须显式转成无符号类型计算再转回，或使用编译器的溢出内建函数读取 CF/OF。位宽在这里第一次成为可审计的约束：每一个算术表达式都隐含一个环的周长，跨周长的运算要么被证明不会发生，要么必须显式换环。

下一节把同一套位段读法搬到浮点：指数域是一段带偏置的整数，尾数域是一段定长小数，二者拼成的值不再是环上的等距刻度，而是按指数倍增的对数刻度。

## 二、IEEE 754 字段切分：偏置指数、隐含位与次正规数

浮点格式没有独立的"小数点位置"字段，小数点由指数域隐式给出。IEEE 754 把 n 位容器切成三段：1 位符号、w 位偏置指数、t 位尾数。读出值时先做一次偏置减法，再把隐含的最高位 1 拼回尾数——这一步"补 1"是浮点与定点在硬件上唯一的结构性差别。

```text
FP32（32 位）字段标尺：

  31 30              23 22                                    0
 ┌──┬──────────────────┬──────────────────────────────────────┐
 │s │   指数 e (8 位)   │           尾数 f (23 位)              │
 └──┴────────┬─────────┴──────────────────┬───────────────────┘
             │ e - 127（偏置）             │ 隐含位：1.f
             ▼                            ▼
      值 = (-1)^s × 1.f × 2^(e-127)

FP64（64 位）：s(1) | e(11) | f(52)，偏置 1023，有效精度 53 位
```

### 1. 指数偏置与值域分段

偏置的作用是把全 0 与全 1 两个端点空出来做特殊值，同时让指数域的比较可以用无符号比较器完成。8 位指数域的取值被切成三段：全 0 表示次正规数与零，1 ~ 254 表示正规数，全 1 表示无穷与 NaN。因此 FP32 的指数实际范围是 $2^{-126}$ 到 $2^{127}$，而不是直觉上的 $2^{-127}$ 到 $2^{128}$。

| 指数域 e | 尾数域 f | 类别 | 数值 |
| --- | --- | --- | --- |
| 0 | 0 | 有符号零 | ±0，`1/-0` 得 -Inf |
| 0 | ≠0 | 次正规数 | $(-1)^s \times 0.f \times 2^{-126}$ |
| 1 ~ 254 | 任意 | 正规数 | $(-1)^s \times 1.f \times 2^{e-127}$ |
| 255 | 0 | 无穷 | ±Inf，溢出与除零的终点 |
| 255 | ≠0 | NaN | 静默 NaN 与信号 NaN，载荷位可自定义 |

次正规数的存在是为了让"最小正规数与零之间"平滑过渡：尾数不再补隐含的 1，而是按 $0.f$ 解释，间距固定为 $2^{-149}$，比最小正规间距 $2^{-126}$ 细 $2^{23}$ 倍。代价是硬件必须为这一段单独准备一条慢路径——部分 x86 微架构对次正规操作触发微码辅助，单条指令从数拍膨胀到上百拍；工程上常以"把次正规数刷成零"（flush-to-zero）换取稳定吞吐，代价是丢失极小值附近的精度。

### 2. 有效精度、间距与结合律的失效

FP32 的 24 位有效精度（隐含位加 23 位尾数）约合 7.22 位十进制，FP64 的 53 位约合 15.95 位。这个"有效位数"不是小数位数，而是相对精度：相邻两个可表示数的间距与数值本身成正比，指数每加 1，间距翻倍。于是浮点加法不满足结合律，减法在量级接近时发生灾难性抵消。

用 FP32 计算 `1e16f + 1.0f - 1e16f`：1e16 附近的可表示间距约为 $2^{53-23}$ 量级，1.0 落在间距之内，加 1 被舍入掉，结果为 0 而非 1。把顺序换成先算 $(1.0f - 1e16f) + 1e16f$ 同样得不到 1，因为第一次减法已经丢失了 1。累加 $10^7$ 个量级悬殊的项时，这种丢失会系统性偏向大数，必须用成对求和（两两归并）或 Kahan 补偿把误差从随项数线性的量级压到对数与常数档。

舍入模式是这条误差链上的可配置阀门。默认的"就近舍入、偶数优先"让 0.5 的舍入方向由最低位奇偶决定，避免统计偏置；向零、向正无穷、向负无穷三种模式服务于区间算术与饱和转换。IEEE 754 要求加、减、乘、除、开方各自只舍入一次；融合乘加（FMA）把 $a \times b + c$ 合成一条指令、中间乘积不舍入，因此比"先乘后加"少一次误差，也更快——这是 04 中 SIMD 专属操作码在浮点层的精度红利。

### 3. 特殊值、零的符号与转换边界

±0 在比较时相等，但符号位在除法与对数中决定结果方向；NaN 与任何值比较都为假（包括与自身），因此判断 NaN 必须用"不等于自身"或位模式检查，而不能用等号。静默 NaN 会沿运算链传播，信号 NaN 则在被消费时触发异常——编译器默认不生成信号 NaN，故它只出现在手工构造的位模式中。

浮点与整数的边界是双向陷阱。整数转浮点时，超过 24 位的整数在 FP32 中不再精确，`16777217` 会舍入为 `16777216`；浮点转整数时，超出目标范围的值在 C 层是未定义行为，x86 的 `cvttss2si` 返回 `0x80000000` 作为"整数不定值"哨兵。这两条边界在后续还会出现：字节序决定这些位串怎样落进内存，宽度转换决定它们怎样换容器。06 的张量核正是把本节的字段标尺整体削短——保留指数、砍掉尾数——来换取阵列吞吐。

## 三、字节车道与端序：主机序、网络序与位序的正交性

一个多字节标量在内存中占连续若干字节，端序回答的是"哪一端落在低地址"。硬件不需要统一答案：x86 与 ARM64 默认把小端作为数据面的约定，网络协议栈则统一按大端编码，二者在 socket 边界上交换。端序是字节车道到地址的映射约定，与位序（一个字节内哪一位是 MSB）互不影响。

```text
把 32 位值 0x11223344 存入地址 0x1000（字节车道映射）：

  地址        0x1000  0x1001  0x1002  0x1003
  小端         44      33      22      11    低有效字节 → 低地址
  大端         11      22      33      44    高有效字节 → 低地址

  按 8 位读 0x1000：小端得 0x44，大端得 0x11
  按 32 位读 0x1000：两种布局都还原出 0x11223344
  ——宽度一致时布局自洽，只有跨宽度或跨机器读取才暴露差异
```

### 1. 车道映射与跨宽度读取

小端的定义是"最低有效字节放在最低地址"，大端相反。对同宽度的读回，两种布局都自洽；差异只在两种场合暴露：按更窄宽度分段读取（如上图按字节读首地址），或把内存内容直接搬到另一台端序相反的机器。前者是协议解析与哈希计算的日常，后者是网络传输与文件格式的日常。

```text
主机序 → 网络序的网关位置：

  应用缓冲区（小端） ──► htonl/htons ──► 报文字段（大端） ──► 网卡 DMA ──► 链路
                            │
                            └─ 纯字节重排：不改宽度、不改位序、不改变数值

  反向：recv 缓冲区（大端字节） ──► ntohl/ntohs ──► 主机整数（小端）
```

图中 `htonl` 是唯一的解析网关：它把 4 个字节的顺序倒过来，数值语义保持不变；链路层与网卡只做纯转发，不参与端序解释。因此"网络序"不是另一种整数表示，而是同一整数在传输约定下的字节排布。任何绕过该网关、直接把主机整数结构体 `memcpy` 进报文的代码，都会在端序相反的机器上得到字段错位。

### 2. 端序的适用边界：标量有、字节流无

端序只对"由多个字节拼成的标量"有意义。`char`、`uint8_t` 数组、UTF-8 字节流没有端序，因为每个元素只有一个字节；对它们做字节交换是纯粹的错误。序列化格式必须先声明宽度，再声明端序：声明了 32 位大端，接收方才敢按 4 字节重组；只声明"一个整数"而不声明宽度，端序讨论无从落地。

文本层把这件事显式化：UTF-16 与 UTF-32 的字节序标记（BOM）就是文件开头的一个端序声明，读取方据此决定后续码元的拼接方向；UTF-8 没有 BOM 需求，因为它按字节流定义。ARM64 支持在异常级别间切换端序（BE8 模式），同一颗芯片上指令流保持小端、数据面可切大端，这进一步说明端序是"每个访问域各自的约定"，而不是处理器全局属性。

| 边界 | 约定端序 | 转换点 | 若省略转换 |
| --- | --- | --- | --- |
| x86-64 与 ARM64 数据面 | 小端 | 无 | — |
| TCP/IP 头部字段 | 大端 | `htonl` 与 `ntohl` | 端口号、长度字段整体错位 |
| PCIe 配置空间与 BAR | 小端 | 驱动按小端读写 | 寄存器值高低字节颠倒 |
| UTF-16 与 UTF-32 文本 | 由 BOM 声明 | 解码器读取 BOM | 码元拼接方向错误，出现乱码 |
| ELF 与 PE 目标文件 | 由文件头标识 | 链接器与装载器解析 | 跨架构加载失败 |

### 3. 位序与字节序的正交

协议文档常写"第 0 位是最高位"，这是位序约定，与端序无关。一个字节内部的 8 个比特没有地址，只有编号习惯：TCP 头部按 MSB-first 编号，以太网前导码按线序发送，二者都可能在字节序之外单独规定。把位序当成端序的推论，会在位图协议、CRC 计算与硬件寄存器定义上出错。

判断一个字段是否受端序影响，只需问两个问题：它由几个字节组成？它是按数值整体读取，还是按位段逐位解析？前者受端序约束，后者只受位序约束。本节给出的车道映射将在下一节继续使用：结构体的成员偏移决定了每个字段落在哪几个字节车道上，端序决定这些车道内部的排布；两者叠加，才得到"一个结构体在内存中的完整布局"。再往上一层的报文解析、目标文件装载与 GPU 端缓冲区约定，都只是这两条规则的组合。

## 四、结构体布局：偏移标尺、对齐填充与 64B 行边界

端序决定了字节车道内部的排布，对齐规则决定了每个成员占用哪几条车道。编译器在成员之间插入填充字节，使每个成员的起始偏移是其对齐值的整数倍；结构体总大小再向上取整到最大成员对齐的整数倍，保证数组中的每个元素都对齐。填充不是浪费，而是硬件访问粒度的强制税：一次 8 字节读若跨了缓存行或跨了页，就要拆成两次总线事务。

```text
LP64 下 struct { char c; long l; int i; short s; } 的偏移标尺：

  偏移    0    1  2  3  4  5  6  7    8 ... 15   16 17 18 19   20 21   22 23
        ┌────┬───────────────────────┬────────────┬───────────┬───────┬───────┐
        │ c  │      填充（7 B）       │     l      │     i     │   s   │ 填充  │
        └────┴───────────────────────┴────────────┴───────────┴───────┴───────┘
         1 B           无成员              8 B          4 B       2 B     2 B

  成员对齐 = min(自然对齐, 编译器上限)；结构体大小取整到最大对齐 8 的倍数 → 24 B
  若按对齐降序重排为 { long; int; short; char; }：8 + 4 + 2 + 1 + 1(尾部) = 16 B
```

### 1. 对齐规则与填充洞

对齐的物理来源是总线的突发粒度与 SRAM 的行选通：一次访问只对齐到自然边界，硬件就不必做跨拍拼接。C 的对齐值取成员自然对齐与编译器上限的较小者；LP64 下 `long` 与指针为 8，`int` 为 4，`short` 为 2，`char` 为 1。成员按声明顺序累加偏移，若当前偏移不是下一成员对齐值的倍数，就插入填充洞；结构体末尾再补一次，使总大小为最大对齐值的整数倍。

本次布局中，`char c` 占偏移 0，`long l` 需要 8 对齐，于是 1 ~ 7 成为填充洞；`int i` 落在 16，`short s` 落在 20，末尾 22 ~ 23 补齐到 24。填充洞没有任何成员，`memcmp` 比较两个逻辑相等的结构体会因洞内残留字节而失败，`write` 直接把结构体落盘会把洞内垃圾写进文件——这是序列化必须逐字段编码、不能整体 `memcpy` 的第二个理由（第一个是端序）。

| 成员 | 类型 | 偏移 | 大小 | 对齐 | 前置填充 |
| --- | --- | --- | --- | --- | --- |
| `c` | `char` | 0 | 1 | 1 | 0 |
| `l` | `long` | 8 | 8 | 8 | 7 |
| `i` | `int` | 16 | 4 | 4 | 0 |
| `s` | `short` | 20 | 2 | 2 | 0 |
| 尾部 | — | 22 | 2 | 8 | 2 |

### 2. 重排、数组布局与 64B 行

按对齐值降序声明成员，可以把填充洞压到最小：`long`、`int`、`short`、`char` 依次排列得 16 B，比原顺序省 8 B，一个百万元素的数组就省下 8 MB。这条规则在跨模块 ABI 中不可随意使用——结构体一旦作为库接口暴露，成员顺序即二进制契约，重排会破坏兼容性；只应在模块内部的热数据结构上做。

数组布局的选择比成员重排影响更大。结构体数组（AoS）把每个元素的全部字段连续放置，遍历某一字段时会把无关字段一并拉进缓存行；结构体拆分数组（SoA）把同名字段各自成数组，一次缓存行搬运的全部是该字段的有效数据。对 64B 行而言，若一个元素 64 B 而热字段只占 8 B，AoS 的有效带宽只有 1/8；改 SoA 后有效带宽回到接近 1。这一换算与 02 §二 的 64B 行切分直接对应，不需要重新推导行结构。

最后一个边界是并发：两个高频写变量若落在同一 64B 行，会触发 02 §五.3 的跨核迁移账单，本节只给出布局侧的处置——按 64B 边界对齐并填充，让每个变量独占一行，代价是内存占用按行放大。

### 3. packed、位域与非对齐访问

`#pragma pack(1)` 或 `__attribute__((packed))` 取消填充，把结构体压到成员大小之和，代价是成员可能落在非自然对齐的偏移上。x86 允许非对齐访问，但跨 64B 行时拆成两次事务、吞吐减半；ARMv8 默认允许非对齐的普通内存访问，但跨页边界会陷入异常由内核修补；对设备寄存器或原子变量做非对齐访问则直接非法。压缩布局只应在"线协议解析"这类一次性读取场景使用，读完立即拷进对齐的结构体。

位域把多个小字段塞进同一个存储单元，但 C 标准只规定语义、不规定布局：位域的分配方向（从低位还是高位开始）、跨存储单元时是否续接、`int` 位域的符号性，全部由编译器实现定义。同一份位域声明在 GCC 与 MSVC 下可能得到不同的位序，再叠加端序差异，跨机器解析必然错位。因此位域只能用于进程内压紧内存，不能用于报文与文件格式；线协议必须用手工移位与掩码，把位序写死在代码里。

## 五、位运算到指令选择：掩码、位扫描与布尔函数压缩

源级的一行位运算，落到硬件上可能是立即数逻辑、可能是专用位操作指令、也可能是一串移位拼接。编译器按操作数是否常量、位段是否连续、目标寄存器宽度做模式匹配；同一语义在不同微架构上甚至选中延迟差一个数量级的指令。下表把常用位操作、其标量指令、向量对应物与延迟档位并置，后文按行遍历。

| 操作 | x86 标量 | x86 向量（AVX-512） | ARM64 | 延迟档位 |
| --- | --- | --- | --- | --- |
| 掩码与/或/异或 | `AND`/`OR`/`XOR` | `vpandd`/`vpord`/`vpxord` | `AND`/`ORR`/`EOR` | 一拍档 |
| 三输入布尔函数 | 需 2~3 条 | `vpternlogd` 一条 | 需 2~3 条 | 一拍档 |
| 逻辑左/右移 | `SHL`/`SHR` | `vpsllvd`/`vpsrlvd`（可变） | `LSL`/`LSR` | 一拍档 |
| 算术右移 | `SAR` | `vpsravd` | `ASR` | 一拍档 |
| 循环移位 | `ROL`/`ROR` | `vprold` | `ROR` | 一拍档 |
| 位段提取 | `BEXTR`（BMI1） | `vpshufbitqmb` 组合 | `UBFX`/`SBFX` | 数拍档 |
| 位压缩/展开 | `PEXT`/`PDEP`（BMI2） | 无直接对应 | 无直接对应 | 数拍档或十几拍档 |
| 统计置位数 | `POPCNT` | `vpopcntd` | `CNT` | 数拍档 |
| 前导/尾随零 | `LZCNT`/`TZCNT` | `vplzcntd` | `CLZ`/`CTZ` | 数拍档 |

### 1. 移位量的取模与未定义边界

x86 的移位指令只取移位量的低若干位：64 位操作数取低 6 位、32 位取低 5 位。因此 `x << 64` 在硬件层等价于 `x << 0`，结果仍是 x，而不是 0。C 标准把"移位量不小于操作数宽度"划为未定义行为，编译器可以据此假设不会发生并做常量折叠，于是同一行代码在 `-O0` 与 `-O2` 下可能给出不同结果。安全的写法是先对移位量取模，或改写成乘法/查表；对位图与哈希代码，这条边界是最常见的移植故障点。

算术右移与逻辑右移的分岔同样落在符号位上：`SAR` 复制符号位，把负数右移保持为负数（等价于向负无穷取整），`SHR` 补零。C 对有符号负数的右移是实现定义，对无符号是逻辑右移。把负数当无符号右移再转回，是手工实现"向下取整除法"的常用手法，但前提是显式转换，不能依赖编译器默认。

### 2. 专用指令：POPCNT、PEXT/PDEP 与位图分配

`POPCNT` 一条指令完成 64 位置位统计，替代 SWAR 位技巧的十余条；`LZCNT`/`TZCNT` 给出前导/尾随零个数，是哈希表探测与位图分配器的基本动作。`BEXTR` 把"右移加掩码"两条压成一条，`PEXT`/`PDEP` 按掩码把位压缩到连续位置或反向展开。后两条的代价高度依赖微架构：Zen 1/2 上微码化为十几拍，Zen 3 之后与 Intel 上降到数拍，同一条指令跨代差一个数量级——这正 04 §4.1 所说 ISA 契约与微架构实现解耦的直接实例：指令语义不变，执行代价随硅片变。

编译器认得一批惯用式：`x & -x` 取最低置位，`x & (x-1)` 清最低置位，二者分别映射到 `BLSI` 与 `BLSR`；`x | (x-1)` 把最低置位以下全部填 1。位图分配器正是靠这两条在 64 位字上找空闲位：先取反求最低置位，再用 `TZCNT` 换算成下标，最后用 `BLSR` 清除。页表项的标志位解析、伙伴系统的阶位查找、布隆过滤器的置位，走的都是同一组动作。

### 3. 向量侧的位操作：掩码寄存器与布尔函数压缩

SIMD 把上述操作按 lane 并行化：`vpternlogd` 用一张 8 项真值表把任意三输入布尔函数压成一条指令，等价于在 32 个 lane 上各做一次任意组合逻辑；`vpsllvd` 支持每 lane 不同的移位量，替代标量循环。谓词掩码寄存器 `k0 ~ k7`（04 §4.4 扩展三）本身就是位图：比较指令把 32 个 lane 的结果写成一个 32 位掩码，`kmov` 再把它搬到通用寄存器做标量处理，`vpmovmskb` 则是字节 lane 到比特掩码的压缩器。

掩码与位图之间只差一次重解释：`k` 寄存器的第 i 位对应第 i 个 lane 的谓词，`vpmovmskb` 输出的第 i 位对应第 i 个字节的最高位。这条映射让"向量比较 → 标量位扫描 → 跳转"成为分支消除的标准套路：先用向量比较生成掩码，再用 `TZCNT` 找第一个不满足条件的 lane，最后只在真正需要的位置做标量处理。下一节把位段从"逻辑操作"推进到"容器宽度"，讨论同一比特串换容器时哪些位被丢弃、哪些被复制。

## 六、宽度转换：截断、符号/零扩展、饱和与 lane 重排

宽度转换有四条语义不同的路径：保号扩展、补零扩展、模截断、饱和钳位。前两条加宽容器，后两条缩窄容器或在同一容器内改变解释。四条路径都只动位、不改数值语义之外的任何东西；混淆它们，就会得到"数值看起来对、边界全部错"的代码。

```text
同一比特串的四条转换路径（以 8 位源、32 位目标为例）：

  源：        1011 0110            (0xB6)

  ① 符号扩展  1111...1111 1011 0110   → -74     movsx / SBFX
  ② 零扩展    0000...0000 1011 0110   → 182     movzx / UBFX
  ③ 模截断    32 位源取低 8 位         → 0xB6    mov / vpmovdb（丢高位）
  ④ 饱和钳位  32 位源 > 127 则钳到 127 → 0x7F    vpmovsdb / vpmovusdb
               源 < -128 则钳到 -128
```

### 1. 保号、补零与模截断

保号扩展复制源的最高位，补零扩展填 0；两者的选择由源类型的符号性决定，而不是由目标类型决定。模截断直接丢弃高位，等价于对 $2^n$ 取模，C 的无符号窄化保证这一语义，有符号窄化则是实现定义（主流编译器按补码回绕处理，但标准不保证）。浮点到整数的转换是第四条路径的反面：目标范围装不下时，模截断会得到完全错误的符号，饱和钳位才保持"接近真值"。

### 2. 饱和与打包：AVX-512 的窄化指令族

向量窄化把多个宽 lane 压进一个窄寄存器，天然需要"丢高位"或"钳位"二选一。传统做法是 `vpackssdw` 一类打包指令加交错的 `vperm` 重排，一条窄化要三四条指令；AVX-512 的 `vpmovdb`/`vpmovsdb`/`vpmovusdb` 把"取低 8 位 / 有符号饱和 / 无符号饱和"各做成一条，直接写进连续的目标 lane，省掉重排。对图像、量化推理这类"宽累加、窄输出"的流水，窄化指令的条数会与乘加指令数持平，成为吞吐的旁路瓶颈；若转换单元每拍只能处理一个 lane 组，主阵列再宽也喂不饱。

### 3. 重解释与数值转换的边界

`memcpy` 式重解释（C++ 的 `bit_cast`、C 的联合体）保持位不变、只换类型标签，用于浮点位模式检查、哈希与序列化；数值转换改变位，用于算术。二者不可混用：把 `float` 的位模式直接当 `int` 读，得到的是 IEEE 字段拼成的整数，不是截断后的数值；把 `int` 用 `bit_cast` 转 `float`，得到的是极小或 NaN 量级的异常值。位宽转换的每一次调用都应能回答"我要的是同一个值的另一种容器，还是同一串位的另一种解释"。

这三条边界最终在 06 汇合：张量核把 FP32 字段削成 FP16/BF16 是重解释加窄化，主机与显存之间的格式转换是数值转换，二者都由本节与 §2 的字段标尺定义。字节序、布局、位操作、宽度转换四条线索到此收束为一个判据：任何跨边界的二进制数据，都必须同时声明宽度、端序、对齐与转换语义，缺一项就会在某一层被静默改写。
