# 并行与并发

## 定义

并行是同一时刻物理上同时执行多个执行流，要求多个物理计算单元；并发是同一时间间隔内交替执行多个执行流，单核 CPU 通过时间片轮转实现逻辑并行。并行是并发的一个子集——所有并行都是并发，但并非所有并发都是并行。

并行的本质是**同时性**（Simultaneity），解决的硬件问题是单个处理单元的算力不足；并发的本质是**交替性**（Alternation），解决的软件问题是程序IO等待时的资源利用率。

## 数学模型

**阿姆达尔定律（加速比上界）：**

$$
S_{max} = \frac{T_{串行}}{T_{并行}} = \frac{1}{(1-P) + \frac{P}{N}}
$$

其中 $P$ 为可并行化比例，$N$ 为并行 worker 数。当 $N \to \infty$ 时：
$$
\lim_{N \to \infty} S_{max} = \frac{1}{1-P}
$$

这意味着即使无限增加核心数，加速比也被串行部分 $1-P$ 锁死。例如 $P=0.9$（90% 可并行），最大加速比仅为 10 倍。

**Gustafson 定律（弱加速比，规模可扩展性）：**

$$
S_{weak} = \alpha + N(1-\alpha)
$$

其中 $\alpha$ 为串行部分在新问题规模中的比例。当问题规模随 $N$ 线性增长时，串行比例趋向常数，加速比可随 $N$ 线性增长。

**同步开销模型：**

$$
T_{同步} = T_{锁获取} + N \times T_{迁移} + T_{缓存一致性}
$$

当 $T_{同步} > T_{并行收益}$ 时，增加 worker反而降低性能。

**死锁充分条件（咖啡馆定理的工程表述）：**

死锁当且仅当资源分配图出现循环等待且每个节点仅有一条出边。四个必要条件（互斥持有、占有等待、不可抢占、循环等待）同时满足时死锁必然发生。

## 数据流

<pre>
并发（单核，协作式/抢占式调度）：
┌─────────────────────────────────────────────────┐
│ T1 执行 ──→ T1 yield ──→ T2 执行 ──→ T2 yield ──→ ...
│   ↑ 上下文切换（用户态或内核态）                    │
│   └────────── 共享地址空间（堆/全局变量）───────────┘
└─────────────────────────────────────────────────┘

并行（多核，SMP/UMA）：
核心0 ──→ Worker T1 ──→ L1 cache ──┐
                                   ├──→ 缓存一致性协议（MESI/MESIF）
核心1 ──→ Worker T2 ──→ L1 cache ──┤
                                   │
核心2 ──→ Worker T3 ──→ L1 cache ──┘
              ↑ 独立栈，共享堆/代码段/只读数据
</pre>

## 对比参照

| 维度 | 进程 | 线程 | 协程 |
|------|------|------|------|
| 调度权 | 内核 | 内核 | **用户态** |
| 切换代价 | $T_{ctx} \approx \mu s$ | $T_{ctx} \approx ns$ | $T_{ctx} \approx 10-100ns$ |
| 内存模型 | 独立虚拟地址空间 | 共享地址空间，私有栈 | 共享地址空间，共享/私有栈 |
| 数据交换 | 管道/共享内存/消息队列 | 直接读写（需同步） | 直接读写（单线程无竞争） |
| 并行性 | 多核 | 多核 | 单核 |

## 机制

### 同步原语

**Mutex（互斥锁）：**

```
acquire() {
    while (locked) sleep();
    locked = true;
}
release() {
    locked = false;
    wake_one();
}
```

**约束：**
- 同一时刻仅一线程持有
- 持有者必须释放（Lock/Unlock 配对）
- 锁的粒度决定并发度

**违规后果：**
- 死锁（重复加锁、不平衡释放）
- 活锁（两个线程都谦让但持续重试）
- 优先级反转（低优先级持有锁，高优先级忙等）

**读写锁（RWLock）：**

```
read_lock()  { atomic_inc(readers); if (readers == 1) acquire(mutex); read_unlock(); }
read_unlock(){ atomic_dec(readers); if (readers == 0) release(mutex); }
write_lock() { acquire(mutex); }
write_unlock(){ release(mutex); }
```

**约束：**
- 写者排他，读者可并行（reader preference）
- 读者数由 atomic 变量追踪

**违规后果：**
- 写饥饿（大量读者持续到达导致写者永久等待）
- 解决方案：写优先RWLock 或 公平队列

**信号量（Semaphore）：**

计数器表示可用资源数。P()（wait/acquire）递减，V()（signal/release）递增。

**约束：**
- 计数上限初始化后固定
- PV 操作必须成对

**违规后果：**
- 资源泄漏（V 不足）
- 计数为负时线程阻塞在 P()

**屏障（Barrier）：**

所有线程到达后才能继续：

```
counter = 0;
lock(counter_mutex);
if (++counter == n) { release(counter_mutex); broadcast(); }
else { release(counter_mutex); wait(); }
```

**约束：**
- 参与线程数必须在初始化时确定
- 所有线程必须到达同一屏障点

**违规后果：**
- 某线程永远不调用 wait() → 其他线程死等
- 线程数动态变化 → 计数不匹配

### 死锁必要条件（同时满足才死锁）

1. **互斥持有**：资源被一个线程独占持有
2. **占有等待**：持有资源的同时请求其他资源
3. **不可抢占**：资源不能被强制夺走
4. **循环等待**：形成线程→资源→线程的环

打破任一条件即可防止死锁。

### Python GIL

CPython 的 GIL（Global Interpreter Lock）将 Python 字节码执行限制在单线程，同一时刻仅一线程执行 Python 字节码。

**约束：**
- IO 等待时线程让出 GIL（`threading` 库有效）
- CPU 密集型操作无法并行（多线程竞争 GIL）
- 扩展库（numpy/Cython）释放 GIL 做 native 计算

**违规后果：**
- CPU 密集型多线程反而更慢（GIL 争用开销）
- 解决方案：multiprocessing（进程池）或 ProcessPoolExecutor
- 注意：IO 密集型 + threading 仍然有效

## 参考存根

```python
# 原子计数器
from threading import Lock
counter = 0
lock = Lock()
def inc(): global counter; with lock: counter += 1
```

```python
# multiprocessing 绕过 GIL
from multiprocessing import Process, Value
counter = Value('i', 0)
def inc(): with counter.get_lock(): counter.value += 1
```
