# HTTP 协议

## 核心定义：应用层的请求-应答语义

HTTP（HyperText Transfer Protocol）是应用层协议：在 TCP 的可靠字节流上，定义"请求一段资源、应答一个结果"的文本格式与语义。一个请求长这样：

```text
GET /index.html HTTP/1.1        ← 请求行：方法 + 路径 + 版本
Host: example.com               ← 头部：元信息（虚拟主机、缓存、内容协商…）
Accept: text/html
                                ← 空行分隔
（请求体，GET 通常为空）
```

应答对称：`HTTP/1.1 200 OK` 状态行 + 头部 + 空行 + 体。全部明文可读——这是 HTTP/1.x 的特征（也是它的调试红利：telnet 就能对话）。

## 方法与状态码：语义的分工

HTTP 的设计里，**方法表达操作意图，状态码表达结果类别**：

- 方法：`GET` 读取（安全+幂等：不产生副作用，重复执行结果相同）、`POST` 创建/提交、`PUT` 全量替换（幂等）、`DELETE` 删除（幂等）、`PATCH` 局部修改。幂等性不是学术洁癖——网络会重试（03 篇的超时重传在应用层的重演），幂等方法被重试是安全的，非幂等的 POST 重试可能下两个订单。
- 状态码按百位分类：`2xx` 成功、`3xx` 重定向/缓存有效、`4xx` 是**你**错了（404 没有、401 没认证、403 没权限）、`5xx` 是**我**错了（500 内部错误、502 上游挂了、503 过载）。排障第一眼就看百位：责任在哪一侧直接定了。

REST 是把这套语义用成架构风格：URL 指资源（名词），方法指操作（动词），状态码报告结果——URL 里不该出现动词（`/getUser` 是语义错位）。

## 无状态与 Cookie

HTTP 被设计为**无状态**：每个请求自足，服务器不记得你上一个请求。这是可伸缩性的地基（任何一台机器都能接任何请求，见《软件工程概念》08 的水平扩展），但应用需要会话——登录一次不能每页都登录。Cookie 就是补丁：服务器用 `Set-Cookie` 头发一小段数据，浏览器此后**每次请求自动带回**。会话 ID 放进 Cookie，状态存在服务器（session 或 Redis）——协议保持无状态，状态被挪到了数据层。

代价：自动带回意味着跨站也会带——CSRF 攻击的全部立足点（《软件工程概念》09 篇），`SameSite` 属性是对它的防线。

**头部的两个实战主角**：`Content-Length` / `Transfer-Encoding: chunked` 负责告知体的边界（连接复用的前提）；**缓存头**是 HTTP 性能优化的主战场——服务器用 `ETag` 给资源发指纹，客户端下次带 `If-None-Match` 询问，没变就回 `304 Not Modified`（只有头没有体）。`Cache-Control` 直接宣告可缓存时长。标配用法：静态资源文件名带内容哈希 + 长缓存，动态接口短缓存或不缓存。

## 演进线：1.1 → 2 → 3，全是传输层约束的反推

HTTP 的三代演进，每一步都是被下层逼的：

- **HTTP/1.1（1997）**：keep-alive 复用连接，但同一连接上请求**必须串行**——前一个不答完，后一个不能发。浏览器的对策是开 6 个连接并行（每域上限），绕过而不解决。
- **HTTP/2（2015）**：二进制分帧——消息切成帧、打上流 ID，同一连接上**多路复用**（多请求交织并发）。应用层的队头阻塞治好了，但 TCP 的队头阻塞浮出水面（03 篇：一个 TCP 包丢失，所有流一起等）——这病在 TCP 内部，HTTP/2 治不了。
- **HTTP/3（2022 标准化）**：换掉 TCP，跑在 QUIC（UDP 之上的自建可靠传输）上——多流独立、丢包不互相堵，握手还把 TLS 合并进来（1-RTT 建连）。HTTP/3 的语义层（方法、状态码、头部）与 HTTP/2 几乎相同，变的是运载——再次印证分层：应用语义与传输机制可以独立演化（01 篇）。

**WebSocket** 是另一种形状：HTTP/1.1 的 `Upgrade` 头握手后，连接从"请求-应答"切换为全双工帧流——为服务器主动推送而生（聊天室、行情推送）。它的起点仍是 HTTP，握手借道，随后各走各路。

---

**衔接**：HTTP 的一切语义都是明文，链路上任何人能看能改。给这套语义加上机密、完整、身份三件套，是下一篇 HTTPS 与 TLS 的事。
