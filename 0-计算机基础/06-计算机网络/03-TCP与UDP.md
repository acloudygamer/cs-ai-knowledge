# TCP 与 UDP

## 核心定义：在不可靠地基上造可靠，或直接暴露不可靠

02 篇的 IP 层四个"不保证"。传输层面对一个选择：把可靠性造出来，还是把不可靠原样交上去？

- **UDP**：原样上交。头部只有 8 字节（源/目的端口、长度、校验和），发完即忘。适用场景由约束决定：**实时性 > 完整性**时——语音通话、直播、游戏状态，丢一帧比等重传强；DNS 这类一问一答，丢了重问即可。QUIC（见 05 篇 HTTP/3）证明 UDP 还有一个用途：作为自建传输协议的底座。
- **TCP**：在端点上用软件机制把"可靠的、有序的字节流"造出来。本篇的主体就是它怎么造。

## TCP 的工具箱：四个机制各补一个"不保证"

| IP 的缺陷 | TCP 的机制 | 原理一句话 |
|-----------|-----------|-----------|
| 不保证送达 | 序号 + ACK + 重传 | 每字节编号；接收方累计确认"N 之前的都到了"；超时或收到 3 个重复 ACK 就重发 |
| 不保证顺序 | 序号重排 | 接收方按序号装配，乱序的先缓存 |
| 不保证一份 | 序号去重 | 重复序号直接丢弃 |
| 不保证速率匹配 | 滑动窗口（流量控制） | 接收方在 ACK 里通告"我还剩多少缓冲"（rwnd），发送方不超发 |

注意序号是**每字节一个号**——TCP 眼里没有"报文"，只有字节流。这个事实在 07 篇以"粘包"的名字再来收账。

## 连接：为什么三次握手、四次挥手

**三次握手**（SYN → SYN+ACK → ACK）的目的不是礼节，是**双方交换初始序号（ISN）并确认对方真的在**。为什么不能两次：两次只能让一方确认；且旧连接残留的重发 SYN 可能骗服务端建一条僵尸连接——三次握手让双方都用"你能对上我的序号"来验明正身（ISN 随机化，旧包对不上号）。

**四次挥手**比握手多一次，因为关闭是单向的：A 发 FIN 只说"我没数据要发了"，B 先 ACK，等 B 的数据发完再发自己的 FIN，A 最后 ACK。主动关闭方随后进入 **TIME_WAIT**（2 倍报文最大寿命，默认共 2 分钟级）：防最后一个 ACK 丢失时对方重发 FIN 无人应答，也防旧连接的字节游荡进同五元组的新连接。高并发短连接服务器上大量 TIME_WAIT 的含义：这台机器在主动关连接，且连接寿命太短。

## 拥塞控制：对网络容量的分布式探测

流量控制管的是**接收方**装不装得下；拥塞控制管的是**网络**扛不扛得住——路由器缓冲溢出就丢包，丢包是网络喊"满了"的唯一信号。TCP 的策略：

- **慢启动**：从很小的拥塞窗口（cwnd）起步，每收到 ACK 翻倍——指数探路；
- **拥塞避免**：越过阈值后改为线性增长——小心翼翼地继续探；
- **丢包即降速**：超时重传视为严重拥塞（窗口砍到底重慢启动），重复 ACK 视为轻度拥塞（窗口减半，快恢复）。

总体是 AIMD（加法增大、乘法减小）：所有 TCP 流各自独立地试探又退让，全网带宽被动态瓜分——没有中央调度，只有端点算法。这是端到端原则的第二次兑现：连"网络容量"这件事也没人告诉端点，端点用丢包当信号自己试出来。

## 半开连接与心跳：TCP 自己感知不到对端崩溃

连接只是一对状态，没有流量就没有证据——对端断电、进程被杀，本端的连接对象还好好地"活着"。两个对策：内核的 TCP keepalive（默认两小时才探一次，慢得帮不上忙）；应用层心跳（WebSocket 的 ping/pong、IM 的定时包）。心跳还有一个更常见的真实用途：02 篇的 NAT 映射表项会老化——空闲几分钟到几小时的连接被 NAT 静默丢弃，下次发包石沉大海。给 NAT 续命，往往比探活更要紧。

## TCP 的代价与 QUIC 的由来

TCP 的两笔账：**队头阻塞**——字节流必须按序交付，一个包丢了，后面已到的数据也只能等它重传（对实时应用是硬伤）；**握手延迟**——建连 1 个 RTT，加 TLS 还要更多（06 篇）。QUIC（HTTP/3 的基座）因此把可靠传输搬到 UDP 之上自己实现：多流独立（丢包只堵一条流）、传输与加密握手合一（1-RTT 甚至 0-RTT）、连接随客户端迁移（Wi-Fi 切 5G 不断线）。TCP 三十年的地位没变，但它的形状第一次被正面绕过——约束没变（IP 仍不担保），只是造的地点从内核挪到了用户态。
