# Socket 编程

## 核心定义：传输层在操作系统里的接口

前五篇讲的协议全部住在内核里（TCP/IP 协议栈是内核代码）。应用程序怎么用上它们？通过 **socket API**——OS 暴露的一组系统调用（《系统软件层》02 的门）。socket 的字面身份是一个文件描述符："一切皆文件"的接口延伸到了网络——`read`/`write` 一个 socket，就是收/发网络数据。

## 五元组：一条连接的唯一身份

内核如何区分成千上万个并发连接？**五元组**：`(协议, 源IP, 源端口, 目的IP, 目的端口)`。只要五元组不同，就是不同连接。两个直接推论：

- 服务器只用 80 端口监听，却能同时服务百万连接——连接的区分靠完整五元组，不靠端口独占；
- 客户端的源端口由内核从**临时端口**池分配（典型 49152~65535）——这就是"端口被占满"在客户端也会发生的原因（高并发短连接 + TIME_WAIT 占用，见 03 篇）。

## 两端的调用序列

TCP 服务端与客户端的调用序列不对称，各对应连接生命周期的一半：

```text
服务端                          客户端
socket()                        socket()
  │                               │
bind(80)  ← 钉住端口              │
  │                               │
listen()    ← 变被动，建全连接队列  │
  │                               │
  │            ── 三次握手（内核自动完成，03 篇）──
  │                               connect()
  ▼                               ▼
accept()    ← 从队列取一条已建好的  connect 返回
              连接，返回**新 fd**
  │                               │
read/write ◄────── 数据双向流动 ──► read/write
  │                               │
close()     ◄── 四次挥手 ──►      close()
```

关键点：

- **`listen` 的 fd 不传数据**——它只负责"接客"；`accept()` 每接到一条连接就返回一个**新的连接 fd**，之后读写全用新 fd。监听 fd 与连接 fd 的分工，是 socket 编程第一个要分清的结构。
- **握手由内核代办**：`connect()` 返回时三次握手已完成；服务端的 `accept()` 不参与握手，只是从"已就绪队列"里取成果。

UDP 的 socket 序列简单得多：不需要 `listen`/`accept`/`connect`——`socket()` 之后直接 `sendto()`/`recvfrom()`，每次调用自带目的地址。没有连接、没有握手、没有重传，socket 在这里退化成一个收发报文的信箱。

## 粘包：字节流没有消息边界

TCP 之上最经典的困惑："我 `send` 了两次各 100 字节，为什么对端一次 `recv` 收到 200？"——答案在 03 篇：TCP 是**字节流**，序号按字节编，合并、拆分、任意重组都是合法行为。"两次发送"这个概念在 TCP 里**根本不存在**，存在的只是你往流里写了 200 个字节。

所以"粘包"不是 bug 是特性，分包是**应用层自己的职责**。三种标准做法：

1. **定长**：每条消息固定 N 字节（简单场景）；
2. **分隔符**：按 `\n` 切（文本协议，如 Redis 的 RESP 行）；
3. **长度前缀**：消息头先写 4 字节长度，接收方先读头、再按长度读体（二进制协议主流，HTTP/2 帧即如此）。

读循环必须处理"半包"：`recv` 返回的字节数 ≤ 你要的，攒够了一条消息再交给上层解析。

## 高并发：socket 与 I/O 模型的衔接

一个线程读写一个 socket，一万个连接就卡死在 03 篇的线程账上。出路已在《系统软件层》06 篇：**epoll**——把所有 socket 设为**非阻塞**，登记进 epoll，内核将就绪的 socket 批量给你。`epoll_wait` 返回后按 fd 查读写，Node.js 的事件循环（《编程运行环境》04）就是这个结构的完整产品化。

到此，本部分的链条闭合：01 的分层 → 02 的寻路 → 03 的可靠流 → 04 的命名 → 05 的语义 → 06 的信任 → 07 的接口。一条 `curl` 命令背后，是这七层机制在一秒内的全部合奏。
