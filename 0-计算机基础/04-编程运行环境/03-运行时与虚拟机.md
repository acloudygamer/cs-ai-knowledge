# 运行时与虚拟机

## 一、运行时的接管边界：进程内再造的一层

```text
进程虚拟地址空间（高 → 低；02 篇装好的 PT_LOAD 只是最底五段）
┌──────────────────────────────────────────────┐
│ 栈  默认 8 MB（OS 给上限，运行时按帧向下切）    │
├──────────────────────────────────────────────┤
│ [运行时追加区]                                │
│  代码缓存  16~256 MB（仅 JIT；只映射、不放文件）│
│  托管堆    保留 4 GiB~10¹¹ B，提交按缺页发生   │
│  GC 元数据 卡表 1/512、位图 1~2 bit/8 B → 0.2%~3%│
│  TLS 块    每线程 1~2 页，%fs 基址直指块首     │
├──────────────────────────────────────────────┤
│ mmap 区：共享库、文件映射、线程栈              │
├──────────────────────────────────────────────┤
│ 堆 .data/.bss（brk 段；glibc <128 KB 的 malloc）│
├──────────────────────────────────────────────┤
│ .text / .rodata（r-x / r--，跨进程共享物理页）  │
└──────────────────────────────────────────────┘
```

- 接管在 `main` 之前完成：`_start` 只清零 `rbp`、取 `argc/argv`、跳 `__libc_start_main`；堆元数据、线程池、GC 根表、代码缓存由初始化填好，失败即"没进 `main` 就退出"。
- 启动税四档（x86-64 Linux，到首个用户语句）：Go 1.27 < 1 ms、CPython 3.12 20~40 ms、Node 24（V8 13.6）30~50 ms、OpenJDK 21 40~60 ms；排序 JVM > CPython ≈ Node > Go，差值来自要打开的模块文件数。
- 系统调用次数同序：Go 10¹~10²（`clone`/`mmap`）、CPython 10²~10³（`import site` 逐目录 `openat`）、Node 与 JVM 10³ 量级（每个 jar/`.so` 至少 1 次 `openat` 加数次 `mmap`）。

### 1.1 五口径主权对照：谁管栈、谁管堆、类型在哪

| 项 | 裸 C | CPython 3.12 | V8 13.6（Node 24） | Go 1.27 | Java 21 |
| --- | --- | --- | --- | --- | --- |
| 栈 | OS 8 MB，`rsp` 直推 | C 栈上切 `_PyInterpreterFrame` | C 栈上放寄存器文件 | 自管，2 KB 起 | C 栈上切解释器帧 |
| 堆 | `malloc`：brk / mmap | pymalloc：pool 4 KiB、arena 1 MiB | 分代页 + 压缩 cage | mspan/mcache + arena | G1 region，1~32 MB |
| 对象头 | 无 | 引用计数 8 B + 类型 8 B | Map 4 B + props 4 B + elems 4 B | 无 | mark word 8 B + klass 4 B |

- 对象头是摊销到每次分配的固定税：CPython 空对象至少 16 B、V8/Java 压缩下 12~16 B，8 B 整数装箱即膨胀 2~3 倍——逃逸分析的全部理由。

### 1.2 保留与提交：虚拟尺寸与 RSS（Resident Set Size，常驻集大小）的缺口

| 运行时 | 保留 | 初始提交 | 缺口来源 |
| --- | --- | --- | --- |
| V8 13.6 | 压缩 cage 4 GiB | MB 级 | cage 内仅少量页被触碰 |
| Java 21 | `-Xmx`（默认内存 1/4）整块 | 1/64 物理内存 | 堆按需扩，虚拟先占满 |
| Go 1.27 | arena 10¹¹ B 量级 | 数 MB | arena 大段不触碰 |
| CPython 3.12 | 按 1 MiB arena 增量 | 1 arena | 仅剩 arena 内碎片 |

- 方向恒为 虚拟尺寸 ≥ 提交 ≥ RSS：保留只建 VMA、页在缺页里给（首次触碰每页一次 minor fault，约 1 µs 量级），故 `-Xmx4g` 的进程只占 100 MB RSS 是常态。

## 二、调用约定：参数寄存器与栈帧位标尺

```text
单帧标尺（SysV AMD64；每格 8 B；示例 2 个局部量，帧体 64 B）
偏移        内容                 写入者
[rbp+24] ┌──────────────────┐  第 8 个及以后实参（溢出区）
[rbp+16] │ 溢出区 / 传参中转 │  调用者（call 之前写）
[rbp+8]  │ 返回地址 rip      │  call 指令    ← 环的接口面
[rbp+0]  │ 调用者的 rbp      │  prologue: push rbp
[rbp-8]  │ callee-saved rbx  │  prologue
[rbp-16] │ callee-saved r12  │  prologue
[rbp-24] │ 局部量 a（8 B）   │  函数体
[rbp-32] │ 局部量 b（8 B）   │  函数体
[rbp-40] │ 传参中转          │  函数体
[rbp-48] │ 填充              │  编译器
[rbp-56] │ 填充              │  编译器
[rbp-64] └──────────────────┘  ← rsp（sub rsp,64 之后）
         ↓ 再向下 128 B 为 red zone（叶子函数免调 rsp）
```

- 帧体 = `8（saved rbp）+ callee-saved + locals + 对齐填充`，向上取整到 16 B，含返回地址整帧 72 B；裸 C 典型帧 32~64 B，局部量超出寄存器余量后每 8 B 一档线性增长。
- `sub rsp,N` 的 N 必须是 16 的倍数（`push rbp` 后 `rbp` 已 16 B 对齐）：取非倍数即打歪 `rsp`，下一次 `movaps` 直接 `#GP`。
- 第 6 个整型参数以内零内存写；第 7 个起每多一个多 8 B 栈写，且该写落在调用者帧的 `[rsp+8k]`，不在被调者帧内。

### 2.1 三约定对照：寄存器参数、shadow space 与对齐

| 项 | SysV AMD64 | Windows x64 | AArch64 AAPCS64 |
| --- | --- | --- | --- |
| 整型参数寄存器 | `RDI RSI RDX RCX R8 R9`（6） | `RCX RDX R8 R9`（4） | `X0~X7`（8） |
| 浮点参数寄存器 | `XMM0~XMM7`（8） | `XMM0~XMM3`（4） | `V0~V7`（8） |
| 溢出起点 | 第 7 整型 / 第 9 浮点 | 第 5 整型 / 第 5 浮点 | 第 9 个 |
| shadow space | 无 | **每次调用固定 32 B** | 无 |
| 调用前对齐 | `rsp` 16 B | `rsp` 16 B | `SP` 16 B |
| red zone | 有，`rsp` 下 128 B | 无 | 无 |
| callee-saved | `RBX RBP R12~R15` | `RBX RBP RDI RSI R12~R15 XMM6~15` | `X19~X29` |

- 帧尺寸不可互换：1 参数的 Windows x64 调用也要写 4 个 8 B 槽（32 B shadow space），比 SysV 多 32 B 栈写，递归 10⁴ 层即多 320 KB。

### 2.2 对齐、red zone 与省略帧指针

- red zone 让叶子函数省 2 条指令与 2 次 `rsp` 依赖（约 0.5~1 ns/次）；代价是信号处理须跳过这 128 B（内核与 `sigaltstack` 侧按 `-mno-red-zone` 编译），否则信号帧覆写正在用的局部量。
- 省略帧指针（`-O2` 默认）再省 2 条指令，代价是回溯改走 `.eh_frame` 的 CFI（Call Frame Information，调用帧信息）表：段体积涨 5%~10%，`bt` 须先解析 CFI——这就是"优化过的代码里 `bt` 偶尔断链"的物理原因。

## 三、一次函数调用的空间事务环：从 `call` 到 `ret`

```text
[1] 实参落位 RDI..R9 / XMM0..7 / [rsp+8k]      改寄存器（w）
      ▼
[2] call rel32 ── push rip；rip ← target        改内存（-8 B）+ 改 rip
      ├──► [RSB 旁路] push 返回地址：只喂预测器，不改架构状态
      ▼
[3] prologue：push rbp；mov rbp,rsp；sub rsp,N  改内存（-8 B）+ 改 rsp/rbp
      ▼
[4] 函数体：读 [rbp+8] 取参、读写 [rbp-8..]、可能嵌套回 [1]
      ▼
[5] epilogue：mov rsp,rbp；pop rbp              改 rsp/rbp（内存不变）
      ▼
[6] ret ── pop rip                              改内存（+8 B）+ 改 rip
      └──► [RSB 旁路] pop 出预测目标
```

- 环上 6 节点、只有 2 个纯旁路：RSB 与架构状态完全解耦，故"`ret` 的语义只是弹栈、预测目标却取自 RSB 顶"。01 卷 03 已给出结论：RSB 深度 16~32 项，溢出点即递归返回的误预测起点。
- 逐节点记账：`call`/`ret` 各 1 条指令、各 1 次 8 B 栈写；`push rbp`/`pop rbp` 各 1 条 8 B 访存；`mov rbp,rsp` 与 `sub rsp,N` 纯寄存器、0 访存。

### 3.1 四种调用形态：栈增长与预测压力

| 形态 | 栈增长 | 指令数 | 预测压力 | 可回溯性 |
| --- | --- | --- | --- | --- |
| 普通调用 | +帧体（32~64 B） | 4~8 条 | BTB 单目标，命中 > 95% | 完整：`rbp` 链或 CFI |
| 尾调用 | 0（复用当前帧） | 2~5 条（重排参数 + `jmp`） | 同直接调用 | 中间帧消失，只见最终帧 |
| 内联展开 | 0（边界抹掉） | 0 条 | 无分支可预测 | 依赖 debug info 内联表 |
| 间接调用 | +帧体 | 2~3 条（`call r/m` + vtable load） | 单态可预测，多态误预测 20%~50% | 同普通调用 |

- 尾调用把栈深度从 $O(n)$ 压到 $O(1)$ ，即栈深与递归层数无关：这是"递归可等价循环"的机器级依据；代价是 `jmp` 不压 RSB，深层尾递归返回时 RSB 已空，需 shim 调整。

### 3.2 环的延迟账：一次调用花在哪

- 预测命中 2~5 ns：两次栈访存（`push rip`/`pop rip`）均落 L1 共约 1 ns，地址生成与 BTB 查表各约 1 周期，序言/尾声 4 条指令在乱序核上可与函数体前段重叠。
- 误预测 5~7 ns（15~20 周期）：RSB 空或目标不匹配即冲刷流水线，10⁴ 层递归按半数误判计约 25~35 µs 额外开销——"深递归比等价循环慢"在 $O(n)$ 之上的常数项。

## 四、解释器主循环：字节码分派的三代实现

```text
(a) switch 分派（单点回边）        (b) 直接线程化（N 点）
  loop:                            L_load_fast:
    op = code[pc]                    op = code[pc]; pc += 1
    switch (op) {                    goto *table[op];  ← 每 opcode 一处
      case LOAD_FAST:              L_store_fast:
        ...; break; ──┐               ...
      case STORE_FAST:│              goto *table[code[pc]];
        ...; break; ──┤
    }               │
    pc += 1; goto loop ◄┘          BTB 目标数 N，每 opcode 独立历史
  BTB 目标数 1，全 opcode 共用一份历史
```

- 直接线程化快 20%~30% 的机制不在指令数（两者都是 1 次间接跳转），而在**分支历史分裂**：switch 的全部 opcode 共用 1 个 BTB 项，`LOAD_FAST`/`STORE_FAST` 交替即交替误预测；直接线程化让每 opcode 有独立目标，命中率提高 10~30 个百分点。
- 单条字节码 5~20 ns（含分派）：CPython 3.12 的 `BINARY_OP` 约 10~20 ns、`LOAD_FAST` 约 5~8 ns；折算单线程每秒分派 5×10⁷~2×10⁸ 次，10⁹ 条字节码即 5~20 s。

### 4.1 三引擎对照：操作数模型、分派方式与开销

| 引擎 | 操作数模型 | 指令宽度 | 分派方式 | 单条开销 | 特化 |
| --- | --- | --- | --- | --- | --- |
| CPython 3.12 | 栈式 + `localsplus` 数组 | 定长 2 B（`EXTENDED_ARG` 扩宽） | computed goto | 5~20 ns | 有：预热 8 次换专用变体 |
| V8 13.6 Ignition | 寄存器 + 累加器 | 变长 1~5 B | switch | 3~10 ns | 有：反馈槽（IC） |
| OpenJDK 21 模板解释器 | 栈式 | 变长 1~5 B（`wide` 前缀） | 分派表 → 每字节码一段汇编入口 | 2~8 ns | 无：靠 C1/C2 分层 |

- 定长 2 B 让 CPython 的 `pc` 退化为一次数组下标；代价是 oparg 只有 8 bit，下标超过 255 必须前置 `EXTENDED_ARG`（每个前缀多 1 条字节码、多 1 次分派）。

### 4.2 自适应特化：把类型判断挪出热路径

- CPython 3.12 的机制是**原地改写指令**：同一 `LOAD_ATTR` 在预热计数（8 次）耗尽后按实际类型换成 `LOAD_ATTR_INSTANCE_VALUE` 等专用变体，快路径不再查字典；属性访问从 20~40 ns 降到 5~10 ns，热点路径整体提速 10%~60%。
- V8 走另一条路：字节码不变，反馈向量记录此处见过的 Map，IC 由单态退到 2~4 态线性比较、再退到 megamorphic 哈希查表（慢一个量级）。

## 五、JIT：IR 阶梯、内联缓存与去优化

```text
              热点计数（回边计数 / 调用计数 / 中断预算）
字节码流 ──► [0 解释] ──► [1 基线] ──► [2 中级 IR] ──► [3 优化 IR]
             Ignition    Sparkplug     Maglev         Turbofan
               │◄── deopt ──┴─────────────┴──────────────┘
               │    （按栈图重建解释器帧，必须落在指令边界）
               └◄── OSR（循环中途升级：整帧搬到新帧，不回解释器）
```

- 两条逆向回边是 JIT 与 AOT 的结构差别：deopt 在优化假设失效时退回解释器（保语义），OSR 在长循环中途升级（避免"循环跑完才升级"）。
- deopt 只允许落在指令边界，正是 01 卷 03 的精确异常语义的直接后果：帧必须能精确回滚到某条字节码开头。

### 5.1 三运行时对照：触发阈值、强度与可退性

| 运行时 | 层 | 触发阈值（典型） | 优化强度 | 可退性 |
| --- | --- | --- | --- | --- |
| V8 13.6 | Sparkplug | 首个中断预算（ms 级字节码执行） | 1:1 展开，无优化 | 可（无假设） |
| V8 13.6 | Maglev | 数百~数千次调用 | SSA + 类型反馈，轻量 | 可（deopt 点密集） |
| V8 13.6 | Turbofan | 数千~数万次调用且反馈稳定 | 内联、逃逸分析、向量化 | 可（按栈图重建） |
| OpenJDK 21 | C1 | 约 10²~10³ 次调用 | 快速编译，少量优化 | 可 |
| OpenJDK 21 | C2 | 约 10⁴ 次调用或 4×10⁴ 回边 | 激进内联、循环向量化 | 可（uncommon trap） |
| Go 1.27 | 无 JIT | 编译期一次成型 | 内联、逃逸分析、边界检查消除 | 不可退 |

- 代码缓存是分层编译的硬天花板：V8 13.6 的 code range 上限 128 MB（x64）、JVM 侧 `ReservedCodeCacheSize` 默认 240 MB（初始 2.5 MB）；写满后停编或清旧码，吞吐因此出现平台期而非无限上升。
- 单函数编译税 数十 µs~数 ms（Turbofan/C2 在毫秒端、Sparkplug/C1 在微秒端）：只跑 10 次的函数被优化就是净亏，"分层"存在的全部理由。

### 5.2 内联缓存状态机与 deopt 成本

```text
未初始化 ──首次执行──► 单态（1 个 Map）
                         │ 第 2 个类型
                         ▼
                      多态（2~4 个，线性比较）
                         │ 第 5 个类型
                         ▼
                      megamorphic（哈希查表，单向，不回升）
```

- 迁移单向：单态 1 次比较（~1 ns）→ 多态 2~4 次 → megamorphic 哈希查表（~10 ns）；回到单态需重新编译。
- 一次 deopt 在微秒量级（1~10 µs）：按栈图把寄存器映射回字节码槽位、重建解释器帧；热循环里反复 deopt 的成本按次数线性叠加，V8 用 deopt 计数与预算退避。

## 六、GC：分代假设、写屏障与三色不变式

```text
 [白：未访问，候选垃圾] ──被根/父标记──► [灰：已入队，子未扫]
       ▲                                      │ 扫描全部子指针
       │                                      ▼
       │                               [黑：子已扫完，出队]
       └──── 分配新对象即白（或直接黑，视分配器）──┘

唯一漏标边：黑 ──写指针──► 白（黑不再被扫，白被误回收）
  ① 增量更新（Dijkstra 插入屏障）：写"黑→白"时把白涂灰  ← Go 1.27 混合屏障之一
  ② 快照起始（Yuasa 删除屏障）：写前把旧值（白）涂灰     ← G1 SATB / Go 混合屏障之二
```

- 三色不变式只有一条：黑不得指向白；所有写屏障都为在"写"这一瞬间补上它，故屏障插入点是**每一次指针写**，不是每一次分配。
- 分代假设把"扫全堆"换成"扫新生代"：minor GC 成本正比于新生代容量（复制存活集），而非堆总容量——这是"堆变大不等于停顿变长"的唯一来源；major GC 才是与堆规模相关的那个。
- 屏障税明码标价：每次指针写多 1~2 ns（普通 store 的 2~5 倍），每秒 10⁸ 次指针写即 0.1~0.2 s/s；无屏障的 CPython 用引用计数替代，代价转移到每次赋值。

### 6.1 四口径对照：算法、屏障与停顿档位

| 运行时 | 回收算法 | 屏障 | 停顿档位 | 吞吐税 |
| --- | --- | --- | --- | --- |
| CPython 3.12 | 引用计数即时回收 + 3 代标记清除（仅容器） | 无写屏障（`gc_refs` 快照） | gen0 10~100 µs，gen2 1~10 ms | 10%~20% |
| V8 13.6 | Scavenger 半空间复制 + Mark-Compact/Sweep（增量 + 并发） | 存储缓冲 + 增量标记屏障 | minor 0.5~5 ms，major 10~100 ms | 5%~10% |
| Go 1.27 | 并发三色标记-清除，非移动 | 混合屏障（插入 + 删除） | 100~500 µs（停顿仅在起止） | 5%~10% |
| Java 21 G1 | 分代 + region 复制/整理，SATB 并发标记 | 写前屏障（SATB）+ 写后屏障（卡表） | 20~200 ms（默认目标 200 ms） | 5%~10% |
| Java 21 ZGC | 染色指针 + 并发整理（21 起分代，JEP 439） | 读屏障 | 0.1~1 ms | 10%~15% |

- 同一份堆的停顿跨 2~3 个数量级（ZGC 10⁻¹ ms ↔ G1 10² ms），差别不在"扫得多快"，而在是否把标记与整理搬到并发阶段：并发换停顿，代价是屏障与吞吐。
- CPython 3.12 引用计数即时回收但不处理环，故仍需分代 GC 兜底：gen0 阈值 700、gen1/gen2 各 10 次——几何级数，越老越少扫。
- Go 1.27 在 `GOGC=100` 下堆目标 = 存活集 × 2，配合 `GOMEMLIMIT`（Go 1.19 引入）做软上限；频率由分配速率而非堆大小驱动，故"加大 GOGC = 少 GC、多内存"是同一枚硬币的两面。

### 6.2 停顿、频率与摊销的算式

```math
\begin{aligned}
f_{\text{minor}} &= \frac{R_{\text{alloc}}}{S_{\text{young}}}, \\
\text{摊销税} &= f_{\text{minor}} \cdot t_{\text{pause}}
              = \frac{R_{\text{alloc}} \cdot t_{\text{pause}}}{S_{\text{young}}}, \\
H_{\text{goal}} &= L \cdot \left( 1 + \frac{\text{GOGC}}{100} \right).
\end{aligned}
```

代入典型值： $R_{\text{alloc}} = 1$ GB/s、 $S_{\text{young}} = 16$ MB、 $t_{\text{pause}} = 2$ ms，得 $f_{\text{minor}} = 62.5$ 次/s、摊销税 12.5%。

- 方向：加大 $S_{\text{young}}$ 使频率降、单次停顿升（复制存活集变大），摊销税先降后升，最优点由存活率决定——V8 半空间（1~16 MB）按存活率自适应伸缩即为此。
- 并发收集器改写的是 $t_{\text{pause}}$ 这一项：ZGC 停顿正比于根集而非堆大小，故停顿与 $S$ 解耦，摊销税退化为纯屏障税。

## 七、线程、栈与 TLS：运行时对 OS 线程的二次封装

```text
G（goroutine，2 KB 起，2× 增长，上限 1 GB）
G  G  G   G  G
 \ |  /    \ /
┌─▼──▼──────▼───┐        ┌──────────────────┐
│ P 本地运行队列 │◄──────►│ 全局队列（sched） │ 偷取：本地空则取全局/他 P
│ runq，256 项   │  偷取   └──────────────────┘
└───────┬────────┘
        │ 绑定：同一时刻 1 个 G 跑在 1 个 M 上
┌───────▼────────┐   ┌───────────────┐
│ M 内核线程      │   │ sysmon        │ 抢占：10 ms 级异步信号
└───────┬────────┘   └───────────────┘
        ▼  OS 调度实体（02 卷 03 的 task_struct）
```

- 三级映射把用户态调度插在内核调度之前：G 的数量（10⁵~10⁶）与 M 的数量（≈ 核数）解耦，P 是配额（`GOMAXPROCS` 默认 = 核数，Go 1.25 起容器感知），持有本地队列与内存缓存。
- 栈从 MB 级降到 KB 级是全部收益的来源：Linux 线程栈默认 8 MB（虚拟预留），goroutine 初始 2 KB 按 2× 增长——同一进程可容 10⁵ 量级 goroutine，只容 10³ 量级线程，差 2 个数量级。
- 切换代价差一个数量级：线程 1~2 µs（陷内核、换页表与 TLS），goroutine 20~50 ns（用户态存少量寄存器 + 换栈指针）；调度器把"上下文"从 `task_struct` 缩到几十字节。

### 7.1 四类执行体对照：栈、切换与调度者

| 执行体 | 初始栈 | 增长方式 | 切换代价 | 调度者 | 上限量级 |
| --- | --- | --- | --- | --- | --- |
| 平台线程 | 8 MB（虚拟预留） | 固定，可调 `pthread_attr` | 1~2 µs | OS 调度器 | 10³ |
| goroutine（Go 1.27） | 2 KB | 2× 复制增长，上限 1 GB | 20~50 ns | Go runtime（G-M-P） | 10⁵~10⁶ |
| 虚拟线程（Java 21） | 堆上 KB 级 chunk | 按 chunk 增长，挂起时帧拷到堆 | 100 ns~1 µs | ForkJoinPool 载体线程 | 10⁵~10⁶ |
| V8 isolate（Node 24） | 984 KB（V8 默认栈上限） | 不增长，超限抛 `RangeError` | 线程级（Worker） | OS + libuv | 10²（受内存约束） |

- 虚拟线程把"阻塞"下沉到调度器：遇 `park` 即卸载、帧复制成堆上 `StackChunk`，载体线程转去跑别的虚拟线程；故其切换代价介于线程与协程之间，且**栈不再是连续地址区间**——与 goroutine（自管连续栈、可原地增长）的结构性差别。

### 7.2 TLS 与栈增长：零成本假设的物理前提

- TLS 访问 1~2 条指令：x86-64 Linux 用 `%fs` 段基址（`mov %fs:0x0,%rax` 取 TCB，或 `mov %fs:offset,%rax` 直取字段），命中 ~1 ns；`errno`、线程本地缓存、`pthread_self` 全落在这条路径上。
- 栈增长是缺页驱动的：`rsp` 越过 VMA 下界触发缺页，内核按 `VM_GROWSDOWN` 自动扩栈——所以"栈溢出表现为 `SIGSEGV`"，越界发生在缺页处理里，不在分配器里。
- Go 走另一条路：每个函数序言插入栈空间检查（`morestack`），不足即分配 2× 新栈并**复制**旧帧、改写栈指针；故 Go 允许栈移动、C 不允许——Go 指针不要求栈地址稳定的根因。

## 八、同一函数的五种帧投影：可核验对照

| 运行时 | 帧表示 | 参数落位 | 返回地址 | 帧尺寸（典型） | 核验命令 |
| --- | --- | --- | --- | --- | --- |
| 裸 C（SysV） | `rsp/rbp` 划出的连续区 | 前 6 个寄存器，其后 `[rbp+16]` 起 | `[rbp+8]` | 32~64 B | `gdb -batch -ex bt -ex 'info frame'` |
| CPython 3.12 | `_PyInterpreterFrame`（C 栈上切片） | `localsplus[]` 数组 | C 栈上的 `rip` | 帧头 72 B + `co_stacksize`×8 | `dis` 的 `co_stacksize`、`sys._getframe()` |
| V8 13.6 | 解释器帧 + 寄存器文件 | 寄存器文件（累加器 + `r0..`） | C 栈上的 `rip`（`pc` 另存） | 40~80 B + 寄存器文件 | `--print-bytecode`、`--trace-deopt` |
| Go 1.27 | 自管栈上的连续区（args+locals） | ABIInternal 走寄存器，ABI0 走栈 | 自管栈上的 `pc` | 16~48 B（叶函数可为 0） | `go build -gcflags=-S`、`runtime.Stack` |
| Java 21 | 解释器帧（locals + 操作数栈 + 监视器） | 局部变量槽 0..n | C 栈上的 `rip` | 100~200 B（解释器帧） | `jstack`、`-XX:+PrintFrameConversion` |

- 尺寸差异的来源是"谁保存执行状态"：C 只存活跃变量；CPython 存整个 `localsplus` 槽位（含临时栈）；JVM 解释器帧还带监视器与 `bcp`；Go 帧最小是因为逃逸分析把大部分变量搬到了堆上。
- 五列共享同一底座：第 2 节的字节标尺；除 Go 外，其余四列的帧都落在 C 栈上，`gdb bt` 可逐帧遍历。

### 8.1 帧对象不是帧：CPython 的按需物化

- CPython 3.11 起解释器帧不再默认分配 `PyFrameObject`：`_PyInterpreterFrame` 直接铺在 C 栈上，只有 `sys._getframe()`、生成器暂停、`traceback` 需要时才把槽位复制成堆上的帧对象。
- 故"有帧"与"有帧对象"是两件事：普通调用零分配，`sys._getframe()` 才分配（一次小对象，~50 ns 级），且 `frame.f_locals` 是副本字典，写它不改写正跑着的帧。

### 8.2 三条可核验断言与预期落点

- `gdb` 的 `bt` 与 `info frame` 必须互相印证：前者走 CFI（`.eh_frame`）、后者读 `rbp` 链；省略帧指针时 `info frame` 报 `rbp` 不可用而 `bt` 仍出全栈，不一致即 CFI 与真实布局脱节（内联或尾调用）。
- GC 停顿落档核验：`GODEBUG=gctrace=1`（Go 1.27）每轮输出的停顿微秒数应落在 100~500 µs 档；`-Xlog:gc`（Java 21）与 `--trace-gc`（V8 13.6）分别给出毫秒与亚毫秒级条目，超出表格档位即说明堆/新生代参数被改动。
- 分派成本核验：同一段 10⁹ 次迭代的空循环，`perf stat -e instructions,cycles` 的每迭代指令数应落在"分派 1 次 + 执行体 1~3 条"量级；CPython 3.12 上该值约为 V8 13.6 的 2~4 倍——差值即第 4 节"单条开销"列的实测投影。
