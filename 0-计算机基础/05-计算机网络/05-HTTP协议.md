# HTTP 协议

03 篇已把传输控制协议（Transmission Control Protocol，TCP）定界为一条可靠有序的字节流：发送端切段编号、接收端按序号排序去重、丢失靠重传补齐——但它只承诺"字节按序完整到达"，字节流里既没有消息边界，也没有"这串字节想让对端做什么"的语义。04 篇补上最后一个寻址缺口：统一资源定位符（Uniform Resource Locator，URL）的主机段经递归解析换成 IP 地址，进程据此拿到一对可用的 IP 与端口建连。本篇在这条裸字节流之上回答三个问题：应用语义如何编码成报文并自画边界（第一节），请求动作与响应结果如何约定、状态如何随身携带（第二节），报文通道如何随代际演进逐层消除阻塞税、每步又引入什么新复杂度（第三节）。

承载这一切的是超文本传输协议（HyperText Transfer Protocol，HTTP）：1991 年的 HTTP/0.9 只有一行 GET，1996 年 HTTP/1.0（RFC 1945）补齐头部与体，1997 年 HTTP/1.1（RFC 2068；2014 年重订为 RFC 7230~7235，2022 年整理为现行规范 RFC 9110/9112）引入连接复用与 Host 头；2015 年 HTTP/2（RFC 7540，现 RFC 9113）把文本报文二进制化，2022 年 HTTP/3（RFC 9114）把传输底座从 TCP 换成 QUIC（RFC 9000，承载在 UDP 之上的多流可靠传输协议）。方法与状态码的语义按 RFC 9110 陈述为既定前提，本篇不为其辩护。产出的报文语义向下游交给本章 06-HTTPS与TLS（在其下加安全层），同时是 06-软件工程概念卷架构分层中 API 契约的底座。

## 一、报文切分：文本协议的行标尺

### 1. 请求与响应：行标尺逐行吞噬

TCP 交付的字节流无边无界，HTTP 报文的第一件事就是自己划边界。本章 01 篇《网络分层模型》用位标尺切协议头（IPv4 头按固定偏移切出源/目的地址），01-计算机体系《数据表示与字节序》把同一把标尺用在 FP32 的 32 位字段上——那两处的切分对象是定长二进制容器，切分线由字段宽度钉死；HTTP 的切分对象是不定长文本，标尺单位从位换成行，切分线由回车换行（Carriage Return + Line Feed，CRLF，字节 0x0D 0x0A）与空行给出。同构关系保持不变：一把全局标尺自上而下逐级吞噬，每一段有唯一职责。

```text
请求与响应报文的行标尺（每行以 CRLF 结尾；行标尺自上而下逐行吞噬）

        ◄─ 起始行(1 行) ─►◄──── 头部(n 行) ────►◄分隔►◄── 体(0 ~ n B) ──►

 请求报文
 行0   GET /index.html HTTP/1.1                请求行：方法、目标路径、版本，空格定界三段
 行1   Host: www.example.com                   头部：1.1 必备；同名多站按域名选站
 行2   User-Agent: curl/8.5.0                  头部：客户端标识
 行3   Accept: text/html                       头部：可接受的媒体类型
 行4   （空行，仅 CRLF）                       分隔：头部终结标志，缺它则头部永不闭合
 行5   title=hello&user=zhang                  体：应用数据，类型由 Content-Type 声明

 响应报文（同一把行标尺，仅首行换形）
 行0   HTTP/1.1 200 OK                         状态行：版本、状态码、短语
 行1   Content-Type: text/html; charset=utf-8  头部：体的媒体类型与字符集
 行2   Content-Length: 612                     头部：体长度定界（本节第 3 小节展开）
 行3   （空行，仅 CRLF）                       分隔：头部终结标志
 行4   <html>……（共 612 B）                    体
```

对图逐行走一遍。起始行是标尺的第一格，请求行与状态行共用一个位置而形状不同：请求行按"方法 目标路径 版本"以空格切三段，状态行按"版本 状态码 短语"切三段——两端各自宣告自己讲的方言版本，协商方言的任务在此完成，无需再握手一次。头部区每行一对 `Key: Value`，冒号分隔，键名大小写不敏感，一行一格职责。行 4 的空行是头部终结符：头部行数不定长，解析器只能靠"空行"这个显式标志判断头部到此为止——没有它，头与体的分界在字节流上不可裁决。体是任意字节序列，HTTP 对其内容不做任何解释，类型交给 Content-Type 声明。请求行与状态行还有一处不对称：请求行的第二段只有路径（绝对路径），完整站点身份拆成了两处——04 篇解析出的 IP 只负责建连，同名多站共享同一 IP 时，选哪个站由 Host 头在应用层补上，这是域名消费链路的最后一跳。响应行的三位状态码承载结果语义，短语（OK、Not Found）仅供人读，机器只认数字——状态码分档在第二节展开。

### 2. 文本的收益与代价：可读性换解析税

选文本不选二进制，收益与代价都钉在"可读"两个字上。收益有三条：全部语义在线上以明文呈现，一条命令就能手写合法请求，协议行为可人工核验；逐字节 ASCII 没有多字节标量，端序问题（01-计算机体系《数据表示与字节序》的车道映射）整体不出现；字段按 Key 取值而与顺序无关，加头部不改解析器骨架，版本演进便宜。代价同样明码标价：解析器必须容忍历史宽松（键名大小写不敏感、值前可有空白、多值头的合并规则），逐字符判界比二进制定长字段的一次切分贵一个量级；体积税——每请求重发十余个头部，且大部分在请求间根本不变。

```console
$ printf 'GET / HTTP/1.1\r\nHost: example.com\r\nConnection: close\r\n\r\n' | nc example.com 80
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Content-Length: 1256

<!doctype html>……
```

三行手写报文换来一次完整往返：文本协议的可手写性到此可验。这里 `Connection: close` 是故意加的——它让服务端发完体就关 TCP 连接，"连接关闭"本身就是体的终点，接收方不需要任何定界字段就能收完整条报文，这正是 HTTP/1.0 短连接的默认姿态。体积税这笔账先记着，它在第二节随 Cookie 重付一次，在第三节的 HTTP/2 由头部压缩一次结清。

### 3. 长度与边界：Content-Length 与 chunked 的因果链

HTTP/1.1 的主基调是复用：默认开启 keep-alive（连接复用），一次三次握手（03 篇：一个 RTT 换取连接建立）与慢启动爬坡的成本摊到多个请求-响应往返上。代价随之而来——连接不复用了，报文在字节流上背靠背，接收方读完上一条报文的头部之后，必须精确知道体的终点；差一个字节，"体的残余"与"下一条报文的起始行"就不可裁决，后续所有报文整体错位。定界问题由此从"可选项"变成"必需品"，两种定界器按"发送前是否已知总长"分流：

```text
keep-alive 连接上的定界问题（03 篇结论：TCP 只保证字节按序到达，不切分消息）

 同一条 TCP 字节流：
 ──响应1 [状态行|头部|空行|体]──响应2 [状态行|头部|空行|体]──►
                    ▲
        接收方读完响应1的体之后，下一个字节就是响应2的起始行：
        体终点差一字节，第二条报文整体错位。两种定界器的裁决规则：

 定界器一  Content-Length: 612
            从空行后起逐字节计数，读满 612 B 即体终止
            前提：发送前已知总长——整段数据已在内存或大小已知

 定界器二  Transfer-Encoding: chunked（分块传输编码）
            [块长(16进制) CRLF][块数据][块长][块数据]……[0 CRLF][尾部头部]
            每块自带长度，读到长度为 0 的终止块即体终止
            前提无关：边生成边发送，总长事前未知（流式生成、代理转发）
```

因果链沿图向下：Content-Length 路径要求总长先知，而"先知总长"要求整段数据先就位——静态文件与已缓冲的响应走这条，代价是把流式生成拉直成整段缓冲，首字节延迟凭空增加一个生成周期。chunked 的接收端解码是一个确定性小循环：读块长行 `1A`（十六进制，即 26 B），收满 26 字节回到块长行读 `0F`，再收 15 字节——块长为 0 时体终止，随后读尾部头部、回到"下一条报文的起始行"原点，字节流上永远不会有归属不明的字节。chunked 路径把定界信息拆散进每个块：块长自述，发送方边生成边上线，生成流水线保持流动，代价是解析器要多一层"读块长、收块、循环"的状态机，且尾部头部（trailer）只能后置——头部区已经用空行闭合了，迟到的小型元数据只能挂在终止块之后。两个定界器的错误模式也各有方向：Content-Length 声明小于实际体长，报文被截断，下一报文的起始行被吞进体里；声明大于实际体长，体被砍断后剩余字节被当成下一条报文解析，错位向下游扩散。两个字段同时出现则是 RFC 9112 明文规定的定界错误，接收方必须整条连接作废——这条铁律封死了请求走私（request smuggling）的口子：中间代理与源站若对同一条字节流采用不同定界器，攻击者就能让两边切出不同的报文边界；定界器必须唯一，歧义即漏洞。当两者并存时以 chunked 为准，因为代理改写体长时只有块序列是自洽的。

边界已定，报文里的动词与结果码如何约定，第二节展开。

## 二、方法、状态码与头部语义：无状态协议如何携带状态

### 1. 方法真值矩阵：安全性与幂等性是两个正交断言

请求行的第一段方法约定"这个请求想让对端做什么"。三条断言把方法分型：安全性（safe）——请求不改变服务器上应用可见的状态，只读动作；幂等性（idempotent）——同一请求独立执行一次与执行 N 次，服务器终态相同，注意它约束的是状态效果而非响应内容（同一 PUT 发两次，第二次可以回 204 而第一次回 200，终态一致即幂等）；可缓存（cacheable）——响应允许被中间缓存存储并复用于后续同目标请求。

| 方法 | 语义动作 | 安全性 | 幂等性 | 可缓存 | 典型用途 |
| --- | --- | --- | --- | --- | --- |
| GET | 读取目标资源的当前表示 | 是 | 是 | 是 | 拉取页面、API 查询 |
| HEAD | 同 GET 但只取头部、不取体 | 是 | 是 | 是 | 探测资源存在性、大小与有效期 |
| POST | 把数据交给目标资源处理 | 否 | 否 | 仅当响应自带新鲜度指令（如 `Cache-Control: max-age`） | 提交表单、创建实体 |
| PUT | 用请求体整体替换目标资源 | 否 | 是 | 否 | 上传文件、整写配置 |
| DELETE | 删除目标资源 | 否 | 是 | 否 | 删除实体（已不存在时终态不变，仍幂等） |
| PATCH | 对目标资源做部分修改 | 否 | 否 | 否 | 增量更新字段 |
| OPTIONS | 查询目标资源支持的通信选项 | 是 | 是 | 否 | 跨源预检（CORS）、探测方法表 |

矩阵里藏着两条结构性结论。其一，安全必幂等（只读动作重复执行当然不改状态），反向不成立——PUT 与 DELETE 幂等但不安全，安全列与幂等列是两个正交维度，不能合并成一列。其二，PATCH 两边都不占：补丁语义常含相对量（"把计数字段加 1"），重复执行状态漂移；POST 同理（重复提交创建出两个实体）。这两条不是修辞，是下游机制的裁决输入：缓存层看可缓存列决定哪些响应准许入库，重试逻辑看幂等列决定哪些失败准许原样重发——后者与状态码分档组成二维判定，下一小节展开。

### 2. 状态码分档：责任分界即重试裁决线

状态行中间的三位数字把结果切成五档，档位即归因方向：

| 档位 | 区间示例 | 归因方向 | 语义要点 |
| --- | --- | --- | --- |
| 1xx 信息 | 100 Continue、101 Switching Protocols | 中间应答 | 正式响应在后面，连接保持；101 用于协议切换（如升级 WebSocket） |
| 2xx 成功 | 200 OK、201 Created、204 No Content | 请求已处理 | 201 附新资源地址；204 成功但无体 |
| 3xx 重定向 | 301、302、304、307、308 | 答案在别处 | 不是错误，是导航；304 特殊——协商缓存命中，体为空，客户端用本地副本 |
| 4xx 客户端错 | 400、401、403、404、429 | 请求方责任 | 401 未认证（补凭据可救）、403 已认证但无权（补凭据也没用）、429 请求过频 |
| 5xx 服务端错 | 500、502、503、504 | 服务端责任 | 502/504 是网关档：上游无应答/超时 |

方向归因的第一落点是重试裁决：4xx 表示请求本身有问题，改请求之前原样重发没有意义；5xx 表示请求合法但服务端没接住，重试有意义。把方法的幂等列叠上来，重试裁决变成一张二维真值表——超时与断连单独占一列，因为响应缺失时无法归档进 4xx/5xx，请求可能已执行也可能没执行：

| 重试裁决 | 4xx（请求方错） | 5xx（服务端错） | 超时/断连（归因未知） |
| --- | --- | --- | --- |
| 幂等方法 | 修正请求后重试 | 原样重试有意义 | 原样重试安全（重复执行不改终态） |
| 非幂等方法 | 修正请求后重新发起 | 不应盲目重试：上一次可能已执行 | 不应盲目重试：请求可能已到达并执行 |

第三列是这张表的关键：非幂等方法在网络层失败后的盲目重试，可能造成双份扣款——"至少一次送达"的代价在应用层现形，幂等列由此成为重试开关。3xx 补一句方向纪律：301/308 表示永久移动可被缓存，302/307 表示临时移动不可缓存；301/302 历史上浏览器会把 POST 换成 GET，需要保持方法的临时跳转用 307/308。

责任与重试已定，还剩最后一个语义件：两个往返之间状态住在哪里——无状态的代价转移，下一小节算这笔账。

### 3. 无状态：把状态搬回客户端的代价转移

RFC 9110 的设计断言是：服务器在两个请求之间不保留任何请求上下文，每个请求自带被理解的全部信息——状态不留在柜台，写在顾客随身携带的票据上，类比到此为止。收益的动作归因具体到机制：服务器不为客户端维护会话内存，任一副本能处理任一请求，负载均衡器把请求任意分发即可，扩容只是加副本、不需要会话迁移，副本下线也不丢会话。反模式对照同样明确：负载均衡器上的会话粘滞（sticky session，把同一客户端固定打到同一副本）把无状态刚刚卸掉的服务端状态又加了回来——副本故障即会话丢失，扩容即重分布，这是补丁而非设计。

代价转移的账单逐笔列出。状态存储成本从服务器内存转移到客户端存储：Cookie 机制由响应头 `Set-Cookie` 下发键值对，浏览器按域存储，此后每个同域请求自动附上 Cookie 头回传；Token 路径由 `Authorization: Bearer` 头携带签名令牌，服务器无状态验签。传输成本每请求重付：Cookie 随头部反复上线，第一节的体积税在这里逐请求全额支付——这也解释了为什么会话数据应放 Token 载荷而非大块 Cookie。验证成本回到服务端每次请求：验一次签名，或查一次集中存储。无论 Cookie 还是 Token，机制同构：服务端下发凭据，客户端存储，每请求凭据回传，服务端验证。方向不等式固定：无状态协议用"每请求携带 + 每次验证"换"零会话内存 + 自由扩容"，换出去的每一笔都有明确去向。

语义层到此完备：方法、状态码、凭据回传都在 1.1 的文本报文上跑通。但通道本身欠着三层税——串行化、连接数、解析与头部冗余，第三节逐层清算。

## 三、HTTP/1.1 → 2 → 3：每一步在消除什么税

### 1. 1.1 的账本：串行队头与六连接补丁

队头阻塞（Head-of-Line Blocking）在 1.1 的第一层形态在报文层：一条连接同一时刻只承载一个未完成的请求-响应。机制成因是报文结构本身——按行切分的报文没有流编号，响应无法交错上线（谁先上线谁就得走完整条报文），pipelining（流水线式连发多个请求）试过，但响应必须按请求顺序返回，一个慢响应堵住其后全部，浏览器最终禁用它。第二层形态由此逼出：浏览器对同一主机并行开 6 条 TCP 连接。这是绕过串行化的补丁，账单三笔：每条连接独立三次握手与独立拥塞慢启动（03 篇：初始拥塞窗口 10 MSS，六条连接各自从零爬坡，单连接攒起的窗口优势被六等分）；服务端并发连接状态乘 6；并发封顶 6，第 7 个资源起排队。串行化的延迟账由此可算（口径：忽略服务器处理时间，每个往返按一次完整请求-响应计）：单连接串行送完 R 个资源需 $R \times RTT$ ，摊到 6 条各串行的连接上为 $t \approx \lceil R/6 \rceil \times RTT$ ，100 个资源、跨洲 50 ms RTT 即约 17 个往返档 850 ms 的纯串行地板——与带宽无关，加宽管道救不了串行等待。第三层税是第一、二节记下的体积账：文本头部逐请求全额重发。

三笔税都有明确的机制成因，也就能被明确的机制动作消除——HTTP/2 的动作清单如下。

### 2. HTTP/2：帧化与 HPACK 消除报文层队头

HTTP/2（RFC 9113）的动作有三个。其一，二进制帧化（framing）：报文切成带流编号的帧（frame），帧头定长前置，帧体是切开的头部或体片段。其二，多路复用（multiplexing）：流（stream）是一条逻辑上的请求-响应，多个流的帧在同一条连接上交错上线，接收端按流编号把帧重新归流组装。其三，HPACK（HTTP/2 头部压缩格式，RFC 7541）：静态表预置 61 个常见键值对（索引 8 即 `200` 这类高频项），动态表在连接生命周期内记住新出现的键值，键值串再过一遍 Huffman 编码——重复头部从"整串重发"变成"一个索引号"。消除的税与第 1 小节逐笔对账：流编号让响应可以交错，串行化队头消除；一条连接承载全部并发，六连接补丁连同三笔账单注销；HPACK 把逐请求头部重发压成"首次全量 + 后续索引"，体积税消除。HPACK 的实际走查以同连接的两个连续请求为例：首请求的 `:method: GET` 命中静态表索引 6，而 `user-agent` 这类未预置的头部全量上线并登记进动态表（索引 62 起）；次请求头部几乎全部收敛为索引号，逐请求原样重发的 Cookie 从数百字节缩到几个字节。新复杂度同步记账：二进制帧格式把文本的宽松容忍收走，解析器严格化；HPACK 动态表是全连接共享的按序状态，解压必须严格按字节序推进——压缩率与可并行度在此对冲；浏览器只在 TLS 之上启用 HTTP/2，加密事实上升为准入门槛，这笔账第三节与 06 篇接着算。

```text
三代通道承载同一组并发请求（帧标注所属流；X = 丢包段；═ = 因阻塞停摆）

【HTTP/1.1】一条连接一次一个请求-响应（报文层串行）
 连接  ─R1─►◄─响应1─►═R2─►◄─响应2─►═R3─►◄─响应3─►
        R2 在 R1 的完整往返结束前上不了线：队头由报文串行化产生
 补丁  浏览器对同一主机并行开 6 条连接，每条仍各自串行
        账单：6 份握手与慢启动、6 份服务端连接状态、并发封顶 6

【HTTP/2】单连接帧化多路复用（报文层队头消除，传输层队头残留）
 连接  ─[R1|R2|R3|R1|R2|R3|R1|R2|R3]─►（同流帧按序归流组装）
              X ← TCP 在此丢 1 段
        03 篇按序交付结论就地重述：接收端必须等丢失段重传补齐，
        其后已到达的字节才能上交应用——单连接把全部流的帧压进
        同一条字节流，一个丢包，R1/R2/R3 同停（═）
        伤害反而放大：1.1 时代一次丢包最多堵六分之一连接，2 时代堵全部

【HTTP/3】QUIC 多流独立恢复（传输层队头消除）
 UDP   ─[R1|R2|R3|R1|R2|R3|R1|R2|R3]─►
              X ← 任一流丢包
        仅丢包所在流触发流内重传；其余流的已到达数据照常上交应用
        R1 的丢包不再拖住 R2/R3：流间恢复路径相互独立
```

图分三段对照读。第一段：1.1 的连接线上一格只放得下一个请求-响应，R2 的起点被 R1 的终点钉死，队头在报文层；6 连接补丁是水平方向的复制而非修复。第二段：2 的连接线上三路帧交错，报文层队头已消——但 TCP 丢 1 段的位置一标，03 篇的按序交付立刻接管：丢失段之后所有已到达字节（含全部三路流的帧）一起停摆，传输层队头残留且被单连接集中化放大。第三段：3 的通道上同样的丢包只冻结其所属流，其余流的帧照常归流上交。三段的差即"队头阻塞"三个字的完整语义：同一句话在报文层与传输层各死一次，2 治报文层，3 治传输层。

传输层的队头 TCP 自己治不了——按序交付是 TCP 的语义本体，动它等于换协议。HTTP/3 换的就是协议。

### 3. HTTP/3：QUIC 流独立恢复与连接迁移

QUIC（RFC 9000）承载在 UDP 之上自建可靠传输：03 篇 TCP 的四件套（序号、确认、重传、流控）在用户态以流为单位重建，流是协议原生对象，恢复按流独立——流 1 丢包只触发流 1 的重传，流 2/3 的已到达数据即刻上交，传输层队头消除（上图第三段）。第二动作：TLS 1.3 内嵌进 QUIC 握手，加密握手与传输握手合并为一轮往返，明文模式在协议里不存在——上一节"事实加密"变成强制。第三动作：连接标识（Connection ID）取代四元组成为连接身份。02 篇的 NAT 映射表按五元组建项且空闲即老化，终端换网（Wi-Fi 切蜂窝）或 NAT 重绑定后 IP 与端口改变，TCP 的四元组身份作废、必须重新握手（一至两个 RTT 外加新慢启动）；QUIC 凭 Connection ID 在新地址上续接原连接，连接迁移把"换网即断"的税消除。

新复杂度三笔部署税。其一，UDP 443 在部分企业与运营商网络被限速或丢弃，HTTP/3 探测失败须回退 HTTP/2，部署面要求双栈并存。其二，用户态实现绕开了内核 TCP 数十年的成熟优化路径，每包处理成本更高。其三，加密强制使明文中间缓存与改写彻底退场——这不是缺陷而是设计意图：消除中间环节对语义的暗中干预，代价由依赖中间缓存的旧架构承担，方向明确。头部压缩在此换为 QPACK（HTTP/3 头部压缩格式，RFC 9204）：QUIC 多流不保证跨流字节序，HPACK"严格按序解压"的前提失效，QPACK 以小幅压缩率回退换流间独立解压——上一节"压缩率对并行度"的对冲在此再度定价。三代同台，账本收口。

### 4. 演进账本与交接

| 代际 | 消除的税（机制动作） | 引入的新复杂度 | 遗留税 |
| --- | --- | --- | --- |
| HTTP/1.1（相对 1.0） | 每请求一次握手：keep-alive 复用连接，握手与慢启动成本摊到多请求 | 体边界从"关连接"变为必须显式定界（Content-Length / chunked） | 报文层串行队头；6 连接补丁的三笔账单；文本解析与头部冗余 |
| HTTP/2 | 报文层队头（帧流编号 + 交错复用）；6 连接账单（单连接承载全部并发）；头部冗余（HPACK 静态/动态表） | 二进制帧解析器严格化；HPACK 按序解压状态；加密事实强制 | 传输层队头：单连接上全部流共担一次丢包重传 |
| HTTP/3 | 传输层队头（QUIC 流独立恢复）；换网断连（Connection ID 连接迁移）；握手轮次（TLS 内嵌合并） | UDP 443 部署税（限速/回退双栈）；用户态每包处理成本；QPACK 压缩率回退 | —— |

账本的规律一句话收拢：每步演进等于消除一层阻塞税、引入一层新复杂度，税不会消失只会转移——1.1 把短连接税换成串行税，2 把串行税换成 TCP 队头税（且被单连接集中放大），3 把队头税换成部署税。取舍是否值得由场景裁决，账目本身必须逐笔可查。

账本清点完毕，还剩一张最旧的账没有付：三代的报文语义始终跑在明文上。03 篇的 TCP 字节流只保证"完整按序"，不保证"途中无人看过、改过、换过人"——同网段任何主机、沿途任何一台路由器都握有 1.1 报文的完整视图，窃听、篡改、冒充三种攻击完全敞开。传输层安全（Transport Layer Security，TLS）把加密、完整性校验与身份认证垫在这条通道之下而报文语义几乎不变——怎么垫、垫的代价如何计价，交给本章 06-HTTPS与TLS。
