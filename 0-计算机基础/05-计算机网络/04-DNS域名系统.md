# DNS 域名系统

## 一、层次命名与逐级委托：为什么不用一张大表

03 篇的收尾留给本篇一个端口：UDP 只提供 8 B 头的进程间多路复用与可选校验，可靠性责任整体推给应用——DNS 正是接住这份责任的应用。02 篇的结论是路由器按最长前缀匹配做单跳本地决策，IP 前缀按网络拓扑聚合，全球路由表才能收敛在几十万条。本篇消费这两个结论：用 UDP 53 端口承载名字查询，用与层级路由同构的层次树组织名字空间，产出「名字 → 地址」的解析链路。这条链路向下游交给 05-HTTP（URL 的主机段必须先换成 IP 才能建连）与 07-Socket（`getaddrinfo` 是应用程序进入这套机制的编程入口）。

DNS（Domain Name System，域名系统）要回答的问题只有一句：`www.example.com` 这个名字对应哪个 IP 地址。1983 年 Paul Mockapetris 给出设计（RFC 882/883），1987 年固化为现行规范 RFC 1034/1035 谱系并沿用至今——它是互联网上部署面最广的分布式数据库，而它的结构选择本身就是一道排除法题。

### 1. 单张全局表的三个失效点

层次树不是审美选择，是被三个失效点逼出来的必然形态。DNS 之前的方案就是一张大表：SRI-NIC 机构维护的 `hosts.txt` 文件，全网主机各自下载同一份副本。主机数在数百量级时它已经撑不住，三个失效点按致命程度排列如下。

**失效点一：规模。** 单张表的查询与存储成本随记录数线性上升，而记录数随互联网增长冲到 $10^9$ 档（数亿注册域名、十亿级可解析主机名）。规模本身还不是要害——要害是它放大了后两条。

**失效点二：更新频率。** 域名注册、过户、解析记录修改全天候发生。单表意味着全部写入集中在一处，再靠分发副本同步全网；早期 `hosts.txt` 每周一至两次手工分发，连「一天一变」都跟不上。层次树把写入权随子树下放：每级只维护自己名下的委托关系与自持记录，写入在空间上彻底分散，任何一处的修改不再需要通知全网。

**失效点三：单点。** 唯一权威表是全球解析的单点故障与单点攻击面——它宕机，全网名字失效。层次树把权威分散到各级：任何一个区的权威失效，只影响该子树。

排除法到此收口：绕开层次树只有两条路——全网广播查询（问一个名字要打扰所有服务器，流量不可承受）与集中大表（上述三点全中）。逐级委托是剩下的唯一形态。这也是 02 篇层级路由的同一笔账：路由表按前缀聚合压缩查找范围，域名树按所有权威切分分散写入权——两棵树的分叉依据不同（网络拓扑对管理边界），收敛手法同构，都是把一个全局问题切成一层层局部问题，每跳只做一次本地决策。

### 2. 域名树与逐级委托：NS 记录把权威下放一级

命名空间是一棵从右向左生长的树：根是无名的一个点（写作 `.`），向下逐级分叉——根之下是 TLD（Top-Level Domain，顶级域），如 `com.`、`org.` 与各国国家码域；再向下是注册者持有的域（`example.com.`）；叶子是主机名（`www.example.com.`）。每个名字由路径上各标签倒序加点构成，末尾的点显式标出根——带末点的完整名字称 FQDN（Fully Qualified Domain Name，完全限定域名）；应用日常省略末尾的点，协议报文里它始终存在。

委托动作由 NS（Name Server，名称服务器）记录完成：父区写下一条 NS 记录，声明「这个子树以下的权威在某某服务器」，随后数据本身交给子区自持。父区从此只留指路的记录，不存子树内容——委托一旦完成，父区对子树里的具体记录不再知情。树的编码还立了两条格式边界：每个标签最长 63 B（「长度前缀 + 内容」的编码方式，前缀 2 bit 必须置零），完整名字最长 255 B——后者框死了一次查询里 QNAME 能携带的树深度。

```text
域名树与逐级委托（每条委托边 = 一个区边界；父区只留指路记录）

      .（根区：13 个根身份 a~m.root-servers.net，只答「下一级归谁管」）
      │
      │  NS 委托：com. 的权威在 gtld-servers.net 一族          ○ 转介边
      ▼
     com.（com 区：.com 注册局运营的权威服务器）
      │
      │  NS 委托：example.com. 的权威在 ns1/ns2.example.com.   ○ 转介边
      │  glue 随行：ns1/ns2 的 A 记录由 com 区代答（见 3 小节）
      ▼
example.com.（example.com 区：注册者自持或托管商代管）
      │
      │  A 应答：www.example.com. IN A 203.0.113.10            ◈ 权威边
      ▼
www.example.com.（叶子名：无下级委托，树到此为止）
```

对图逐边遍历：

- **根区 → com.（转介边）**：根区不持有任何 `com.` 之下的记录。有人问起，它只回答「com. 的权威服务器名单是什么」——名单本身是根区唯一自持的数据。
- **com. → example.com.（转介边）**：与上一条边同构。com 区只答「example.com. 的权威是谁」，外加随行的 glue 地址；`example.com.` 里有什么 A 记录，com 区一概不知。
- **example.com. → www.（权威边）**：这条边不是委托而是自持——`www.example.com.` 没有再往下委托，它的 A 记录就存在 example.com 区的权威服务器里，问到这里就是终点。

沿图的委托链逐级下放，每级只管自己的下一跳。各条边携带的数据由几种记录类型承载：

| 记录类型 | RDATA 内容 | 在解析链路中的职能 |
| --- | --- | --- |
| A | 32 位 IPv4 地址 | 叶子应答：名字 → IPv4 |
| AAAA | 128 位 IPv6 地址 | 叶子应答：名字 → IPv6 |
| NS | 子区权威服务器的域名 | 委托指路：只交名字，地址靠 glue 补齐 |
| CNAME | 规范域名 | 别名转发：把查询目标换成另一个名字，链路再走一遍 |
| SOA | 主权威、序列号与若干计时参数（含负缓存 TTL） | 区的元数据；负缓存与主从同步的依据 |
| MX | 优先级 + 邮件交换机域名 | 邮件路由，不在本篇主线展开 |

### 3. zone 与 domain：委托边界上的澄清

> **事实澄清：zone（区）与 domain（域）不是同一概念，业界混用极多。**
>
> - **domain（域）是树的子树**：`example.com.` 这个域指它名下全部名字的集合（含 `www.`、`api.`、再往下的所有后代）。它是纯树结构概念，与「谁存数据」无关。
> - **zone（区）是一个权威集自持的连续数据片**：以 NS 委托点为边界切出来的那一段。区的边界落在每条委托边上——被委托的子树整个划出，归新权威自持。
> - **域可以大于区**：若 `api.example.com.` 被委托给另一组服务器，它就在 `example.com.` 的域内、区外。只有当某域之下没有任何再委托时，域与区才重合。
> - **常见误读**：「zone file 就是这个域名的全部记录」。仅对叶子域成立；只要有委托，zone file 只含到委托点为止的自持记录加指路的 NS。

委托边还逼出一个必须处理的循环依赖。子区权威若叫 `ns1.example.com.`——名字落在被委托的子区内——查询它的地址得先问 example.com 区的权威，而那台权威恰恰就是 `ns1.example.com.`：先有鸡还是先有蛋。父区的解法是在转介时随附子区权威的 A/AAAA 记录，即 glue（粘合）记录——「父区代答地址、子区自持数据」，用一条冗余打破循环。glue 放在应答报文的 Additional 段，第二节随报文结构展开。

委托链是静态拓扑；一个名字如何沿这条链被逐级问出来，是第二节的事。

## 二、递归解析全链路：一次查询的生命周期

本节是一次查询的端到端生命周期闭环：报文从应用侧注入，跨过本机与网络的多级缓存与三级权威，答案沿原通道返回。全链路只有一种报文形态（查询/应答），靠角色与标志位区分问法。

### 1. 两种角色与两种查询方向

**stub resolver** 是解析的发起端，驻留在操作系统与应用侧（英文术语按惯例不译）：它自己不跑全程，把查询递给递归 resolver 后原地等答案。应用程序的入口是 `getaddrinfo("www.example.com", ...)`（07-Socket 的消费点）——库函数把名字交给 stub resolver，拿到 IP 或报错返回。

**递归 resolver（recursive resolver）** 替用户跑完全程：运营商默认 DNS、公共服务的 8.8.8.8 与 1.1.1.1 都属此类。它接收递归查询，逐级问根、TLD、权威，把最终答案交回。

两种角色之间隔着一个容易混淆的区分——递归查询与迭代查询，由报文头 1 bit 切换：

- **stub resolver → 递归 resolver 是递归查询**（RD=1）：「请替我跑完全程」，这是一项服务承诺，应答头里 RA=1 表示「我提供递归服务」。
- **递归 resolver → 根/TLD/权威是迭代查询**（RD=0）：每次只问一级，对方要么给答案、要么指路， resolver 拿到指路后自己走向下一级。这是协议义务——任何 DNS 服务器都只需会「答」或会「指路」其一即可入网，迭代查询把跑腿的义务从每台服务器身上卸下来，集中到递归 resolver 一处。

这个分工不是任意取舍，反证一眼可判：若连根都被要求替每个查询跑完全程，根就要为全球的每个查询承担「多级等待中的悬挂状态」，负载与信任都不成立；迭代把每台服务器的义务压到「看一级标签、交一组名单」，问询状态只存在于发起方 resolver 一台机器上。这正是第一节「每级只管自己的下一跳」在协议责任上的镜像——数据逐级下放，跑腿逐级上收。

### 2. 全链路逐边遍历

```text
递归解析全链路（视角：一次查询的报文生命周期）
图例：◈ 参与解析（权威应答，AA=1，答案可直接入缓存）
      ○ 纯指路（转介，只交付更近一级的 NS 名单与 glue）

 应用侧缓存阶梯              递归 resolver                        上游 DNS 服务器
 ─────────────              ────────────────                     ────────────────
 ① 浏览器缓存
    │ 命中 → 返回（0 次网络往返，微秒档）
    │ 未命中 ▼
 ② 系统 stub 缓存
    │ 命中 → 返回（0 次网络往返，微秒档）
    │ 未命中 ▼

    ▲                              │ 命中 → 返回（1 次往返，毫秒档）
    │                              │ 未命中 ▼ 改发迭代查询 RD=0，逐级下放
    │                              │ ④ 问「www.example.com 的 A 记录」──► 根服务器
    │                              │ ◄── ○ 转介：com. 的 NS 名单 + glue A ────
    │                              │     缓存 com. NS（TTL 以天计档）
    │                              │ ⑤ 同一问题 ─────────────────────► com. 权威（TLD）
    │                              │ ◄── ○ 转介：example.com. 的 NS + glue ───
    │                              │     缓存 example.com. NS（TTL 以天计档）
    │                              │ ⑥ 同一问题 ─────────────────────► example.com. 权威
    │                              │ ◄── ◈ 权威应答：A 记录（AA=1，TTL 数百秒档）──
    │                              │     缓存该 A 记录（TTL 逐秒递减）
    │ ◄── 最终应答（RA=1）──────────┘
 ⑦ 应用拿到 IP：未命中全程 = ④⑤⑥ 三次上游往返；命中 = 0~1 次
```

对图逐边遍历——每一跳问什么、答什么、缓存什么：

- **① 浏览器缓存**：浏览器进程内自持一份小缓存（上限数百秒档，防同页反复解析）。命中则一次网络往返都不发生；未命中把请求交给系统。
- **② 系统 stub 缓存**：操作系统的解析缓存（Windows 的 DNS Client 服务、Linux 的 systemd-resolved 等）。命中返回微秒档；未命中由 stub resolver 发出递归查询（RD=1）。
- **③ resolver 自身缓存**：递归 resolver 先查自己缓存过的记录。命中则只需 stub↔resolver 一次往返，毫秒档；未命中才进入下面的迭代三级。
- **④ → 根服务器（○ 纯指路）**：问的是完整问题「`www.example.com` 的 A 记录」，但根不看名字的叶子部分——它从右往左只认得第一级 `com.`，于是答「com. 的权威是这一组 NS，地址附在 glue 里」。这批数据放在应答的 Authority 与 Additional 段，根对最终答案零参与。resolver 缓存整组 com. NS（TTL 以天计档），下次任何 `.com` 查询都不必再回根。
- **⑤ → com. 权威（○ 纯指路）**：resolver 拿同一个问题问 com 区权威。对方同样只看两级标签，答「example.com. 的权威是 ns1/ns2，地址在 glue」。resolver 缓存这组 NS（TTL 以天计档）。
- **⑥ → example.com. 权威（◈ 参与解析）**：第三次问同一问题，这次问到了持有数据的人。权威服务器返回 A 记录，应答头置 AA=1（权威应答），TTL 随记录自带（数百秒档）。resolver 将其入缓存，TTL 开始倒计时。
- **⑦ 沿原通道返回**：应答装进同一个 UDP 五元组反向送回 stub resolver（RA=1），stub 再写入系统缓存，应用拿到 IP。返回通道与去程同一条、无连接、无握手——查询与应答各自是一个独立报文。

全链路的分色结论：**只有第 ⑥ 跳参与解析**（它持有答案），④⑤ 两跳是纯指路——转介不提供答案，只把问询者往权威推近一级；递归 resolver 本身既不指路也不权威，它只跑腿与记账（缓存）。两个细节补全闭环：若 `www.example.com.` 是 CNAME，权威会在应答里同时带回别名与目标记录，一次往返完成，链路形态不变；glue 记录在 ④⑤ 两跳的 Additional 段生效，正是第一节循环依赖的解法落地处。

### 3. 报文四段结构：封装 4 大件与逐段职能

一个 DNS 报文的封装 4 大件：**Src** 是源 IP + 随机源端口，**Dst** 是目的 IP + 53 端口，**Opcode** 是 0（标准查询），**Address** 是 QNAME + QTYPE——后两件装在 UDP 载荷的 12 B 头与 Question 段里。报文按职能分五段：

| 段 | 构成 | 出现场合 | 职能 |
| --- | --- | --- | --- |
| Header | 12 B 定长：事务 ID（16 bit）、标志位组（QR/OPCODE/AA/TC/RD/RA/RCODE）、QDCOUNT/ANCOUNT/NSCOUNT/ARCOUNT 四个计数器 | 所有报文 | 配对问答、表达应答性质、声明后四段各有多少条 |
| Question | QNAME + QTYPE + QCLASS（IN） | 所有报文 | 声明问题本体：问哪个名字的哪种记录 |
| Answer | 若干资源记录 | 应答报文 | 权威应答的直接答案（A/AAAA/CNAME 链） |
| Authority | 若干资源记录 | 应答报文 | 转介时放下一级 NS 名单；权威应答时放 SOA（负缓存取其计时参数） |
| Additional | 若干资源记录 | 应答报文 | 补充信息，主要是 glue A/AAAA |

每条资源记录统一编码为 NAME、TYPE、CLASS、TTL、RDLENGTH、RDATA 六个字段——TTL 占 32 bit、以秒计，RDLENGTH 占 16 bit 声明变长区 RDATA 的字节数。段落不设分隔符，Header 的四个计数器就是遍历后四段的步长依据。

标志位组在链路中各就各位：QR 区分查询（0）与应答（1）；RD 与 RA 承载第 1 小节的递归/迭代契约；AA 标记第 ⑥ 跳的权威应答；TC 报告响应被截断（下一小节的主角）；RCODE 携带结果码——0 无错，3 是 NXDOMAIN（名字不存在，第三节的负缓存主角）。

用图① 的两条跳把表格填实。第 ④ 跳（转介）的应答：QR=1、AA=0、RCODE=0，ANCOUNT=0（Answer 段为空——没有答案）、NSCOUNT 为 com. 的 NS 条数、ARCOUNT 为 glue A 的条数，四段里的有效载荷全在 Authority 与 Additional。第 ⑥ 跳（权威应答）：AA=1、ANCOUNT=1，Answer 段装一条 A 记录（NAME=`www.example.com.`、TYPE=A、TTL=300 档、RDATA=4 B 地址），Authority 段为空或放 SOA，四段各司其职——同一种报文格式，靠计数器与标志位在「指路」与「作答」两种形态之间切换，与图① 的 ○/◈ 分色一一对应。

### 4. 传输层落点：UDP 53 为主，TCP 53 兜底

03 篇的结论在此直接兑现：UDP 把连接建立、重传与排序的开销整体推给应用，省下的成本由「一次往返即可完成请求-响应」的协议独享——DNS 的查询与应答各是一个报文，丢了就整体重发一次，超时与重传由解析器自理，不需要传输层代劳。自理的具体形态：resolver 对每跳设秒级以下的超时，超时先重发同一服务器、再换同级下一台（根与 TLD 都成组部署，换一台是零成本的冗余），整体重传预算通常压在数秒档；stub 侧同样有超时兜底，resolver 全程无应答时向应用返回解析失败而非无限等待。无连接也意味着无握手税：一次查询就是一次往返，这是 DNS 选 UDP 的动作归因，而不是「UDP 更快」的空话。

TCP 53 在三个场合出场：

1. **TC 截断重试**：响应塞不进 UDP 载荷时，应答头置 TC=1、丢弃超限部分；解析器收到 TC 后改用 TCP 重发同一查询。经典 UDP 载荷上限 512 B，EDNS0（RFC 6891）把它扩展到 1232~4096 B 档，但 TC→TCP 的兜底路径保留。
2. **区域传送**：权威服务器主从同步整个 zone（AXFR/IXFR），是长流式传输，从设计上就走 TCP。
3. **大响应兜底**：带 DNSSEC 签名的应答动辄数 KB，超出 EDNS0 协商值时同样落回 TCP。

512 B 上限还倒逼出一个著名常数：根转介（13 组 NS + glue）恰好被压进单个经典 UDP 响应，根服务器因此定格为 **13 个身份**（a~m.root-servers.net）。13 是报文格式约束下的容量数字，不是机器台数——每个身份以 anycast 广播到全球上千个实例，解析者连的是拓扑上最近的一个。

报文生命周期到此闭环于权威应答。但每次未命中都跑 3 个上游往返太贵——缓存与 TTL 是这条链路的性能账本，第三节逐项结算。

## 三、缓存与 TTL：解析链路的性能账本

### 1. 逐级缓存与命中核算

图① 的缓存阶梯共三级，服务面逐级扩张：浏览器缓存服务单进程（上限数百秒档）；系统 stub 缓存服务整机（Windows DNS Client、systemd-resolved）；递归 resolver 缓存服务它的全部用户（千万级请求共享一套热点记录）。三级缓存的条目都带各自的剩余 TTL。

命中位置决定省下哪几跳：命中在浏览器或系统缓存，0 次网络往返；命中在 resolver，只剩 stub↔resolver 一次往返；未命中才是 ④⑤⑥ 三次上游往返加返回共 4 个报文来回。设递归 resolver 的缓存命中率为 $h$，平均上游往返次数为

$$R(h) = 3(1-h)$$

公网 resolver 聚合全网热点域名， $h$ 普遍在 $0.8 \sim 0.95$ 档——十次查询里至多两次真正打穿到权威。命中率高不是运气，是两个机制动作叠加的结果：一是查询分布高度倾斜（极少数热点域名承担绝大多数查询，少数长尾摊薄缓存），二是 NS 记录的 TTL 以天计档，委托链这种「变化极慢的骨架」几乎常驻缓存。命中率还是逐级可组合的——缓存了 com. NS 但未缓存 example.com. 的 NS 时，第 ④ 跳被省掉，全链路缩短为 2 次上游往返；三级缓存的每一级都可能砍掉链路的一段前缀。

各档延迟与方向不等式写死如下：

| 路径 | 往返次数 | 延迟档位 |
| --- | --- | --- |
| 浏览器/系统缓存命中 | 0 | 微秒档 |
| resolver 缓存命中 | 1（stub↔resolver） | 毫秒至十几毫秒档 |
| 未命中全链路 | 3 次上游往返 + 1 次返回 | 几十至上百毫秒档（跨洲逐跳递增） |

方向不等式：**本地命中（微秒档）< resolver 命中（毫秒档）< 未命中全链路（几十至上百毫秒档）**，相邻两档相差一至两个数量级；跨洲链路的每次上游往返还要在毫秒档上再抬升到几十毫秒档。缓存把「每次都付 3 个往返」压缩为「绝大多数次付 0~1 个往返」，代价是答案可能过期——给这个代价定价的就是 TTL。

### 2. TTL 的语义与变更传播的因果链

TTL（Time To Live，生存时间）是每条资源记录自带的 32 bit 秒数（上限 $2^{31}-1$，实际常见 60~86400 s 档），由权威服务器设定，含义是「此答案可以被缓存多久」。缓存方存「值 + 到期时刻」：每答一次给的是剩余 TTL 而非原始值，到期即删，不向权威确认。

变更传播的因果链由这条语义直接推出：权威修改记录 → 权威侧立即生效 → 但全网各级缓存里的旧值各自活到自己的到期时刻 → **变更传播延迟 ≤ 链路中最长的那个 TTL**。权威能立即给出新值，却无法主动撤销已经发出的旧值——TTL 的机制本质，是把「变更一致性」的责任从权威转移到缓存方。动作归因明确的运维手法由此而来：把 TTL 从 1 天调到 60 s（提前降温），等旧值按短 TTL 自然流出所有缓存，再改记录，变更窗口就从「天」压到「分钟」档；直接改一条高 TTL 记录，用户侧最长要等到旧值过期才看到新值。

### 3. 负缓存与失效模式

负缓存（negative caching，RFC 2308）把同一逻辑用到「不存在」上：NXDOMAIN（RCODE=3）与「名字存在但无此类型」（NODATA）同样入缓存，TTL 取权威 SOA（Start of Authority，权限起始）记录的计时参数，解析器普遍封顶在 10800 s（3 小时）档。动作归因：没有负缓存，拼错域名与端口扫描流量会把「确认不存在」的完整三级往返反复打在权威上；有了它，同一个不存在的名字每 3 小时最多穿透一次。代价与正缓存同一条因果链：刚注册的域名、刚补的记录，在负缓存存续期内仍被答「不存在」——缓存越省流量，变更越慢，没有两头便宜的档位。

失效模式还剩一条要记账：缓存投毒——攻击者抢在权威应答之前向 resolver 注入伪造记录。协议侧的对策是随机化事务 ID 与源端口，把伪造者的猜测空间抬到 16 bit ID × 16 bit 端口的组合档；彻底解法是 DNSSEC 的密码学签名验真，机制自成一篇，此处只留结论：投毒风险与端口随机化强度成反比，与是否部署签名验证成正比。

### 4. 可实操核验

前两节的每条断言都能亲手读回来：

| 观察点 | 命令 | 预期观察 |
| --- | --- | --- |
| 逐级委托全程 | `dig +trace www.example.com` | 输出按段打印：根 NS 名单 → com. 的 NS + glue → example.com. 的 NS + glue → 最终 A 记录；每一段就是图①的一条边，且 dig 自己执行迭代查询 |
| 指定递归 resolver | `dig @8.8.8.8 www.example.com` | 应答 flags 含 `rd ra`（递归服务），Query time 在毫秒至几十毫秒档；连续查两次，第二次明显更快——resolver 已入缓存 |
| 转介与权威应答分色 | `dig +norecurse @a.gtld-servers.net www.example.com` | 对 TLD 服务器发迭代查询，得到的是 Authority 段的 NS 名单（转介，无 `aa` 标志）；对 example.com. 权威发同样查询，得到 Answer 段 A 记录且 flags 含 `aa` |
| TTL 倒计时 | 间隔数秒连续两次 `dig @8.8.8.8 www.example.com` | 第二次应答的 TTL 比第一次减少约等于间隔秒数——缓存返回的是剩余寿命而非原始值 |
| 本机 stub 缓存 | Windows `ipconfig /displaydns`（`/flushdns` 清空后重查） | 可见刚解析过的记录与各自剩余 TTL；清空后首次解析的可感知延迟明显变长，即未命中与命中的档位差 |

偏差的读法：`dig +trace` 中途某级返回多组 NS 属正常（权威成组部署，resolver 取其一继续）；`@8.8.8.8` 的 TTL 一次性从原始值起步而不是递减，说明该查询恰好穿透了缓存（上游刚过期）；`/displaydns` 为空而解析正常，说明系统未启用本地缓存、请求直达 resolver。

至此名字已换成地址：解析链路的终点是应用侧拿到一对可用的 IP 与端口。地址之后，应用层报文如何组织请求语义、如何在连接上往返，交给 05-HTTP协议。
