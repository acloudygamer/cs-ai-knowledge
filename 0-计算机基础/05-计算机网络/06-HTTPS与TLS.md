# HTTPS 与 TLS

05 篇的 HTTP 报文语义建立在一条明文通道上：请求行、头部与体按行切分后原样上线；它脚下的 TCP——03 篇用序号、确认与重传把不可靠分组修补成可靠有序字节流的传输层协议——只保证字节完整且按序到达，不保证途中无人看过、改过、换过人。同网段的任何主机、沿途的每一台路由器、公共 Wi-Fi 热点，都握有这条字节流的完整视图。本篇回答一个问题：怎样把这条明文字节流升级为加密、防篡改且能证实对端身份的通道。答案分三段机制各管一段：先按威胁模型定出三种密码学动作（第一节），再用一次严格单向推进的握手把密钥与身份同时定下来（第二节），最后进入记录层把动作落到每一段应用数据上（第三节）。产出的结论向下游交给 07-Socket（TLS 库如何挂进编程接口）与 06-软件工程概念 09-安全基础（应用层安全在此之上继续）消费。

承载这一切的协议是传输层安全（Transport Layer Security，TLS）：前身安全套接字层（Secure Sockets Layer，SSL）由 Netscape 于 1990 年代中期提出，1999 年 TLS 1.0（RFC 2246）接棒，现行两代为 TLS 1.2（RFC 5246，2008）与 TLS 1.3（RFC 8446，2018）。HTTP over TLS 的组合即 HTTPS，约定走 443 端口（RFC 2818）——80 端口上的明文 HTTP 与它唯一的差别就在本篇要建立的这一层。握手的计价单位是往返时延（Round-Trip Time，RTT）：每多一个 RTT，首字节延迟就多加一档。

## 一、威胁模型与混合体制：排除法定密码学动作

### 1. 三种攻击对应三种动作

先给对手画像：他能读取线上每一字节（窃听），能改写任何在途报文再放行（篡改），还能在名字解析与路由都正常的前提下把自己插到目的地址后面、对客户端自称是服务器（冒充）。三种攻击不需要特殊能力——共享介质与逐跳转发天然给了他全部权限。对应地，密码学提供三种动作，每个动作恰好封住一种攻击，且任何一个动作单独都封不住另外两种：

| 攻击 \ 动作 | 加密（对称） | 完整性校验（MAC） | 认证（证书链 + 签名） |
| --- | --- | --- | --- |
| 窃听（读取内容） | **防住**：密文不可读 | 不防：内容照读不误 | 不防：内容照读不误 |
| 篡改（改写内容） | 不防：流密码逐位翻转可定向改明文 | **防住**：标签对不上即拒收 | 不防：拦不住在途改写 |
| 冒充（假装对端） | 不防：攻击者自带密钥加密即可 | 不防：攻击者为自己的密钥算标签 | **防住**：无私钥即签不出身份 |

对角线是这张表的全部结论：单一动作各守一格，任何一格空着，通道就在那个方向裸奔。完整性校验的载体是消息认证码（Message Authentication Code，MAC）：持有同一密钥的双方能为报文算出一个短标签，无密钥者既算不出正确标签、也无法把改动后的报文配上合法标签。认证动作还需要一层身份基础设施——CA（Certificate Authority，证书颁发机构）签发的证书链，第二节展开。现代 TLS 把加密与完整性校验合并为一次 AEAD（Authenticated Encryption with Associated Data，带关联数据的认证加密）运算，机制本体在第三节记录层展开；本节先解决三格动作成立的前提——密钥怎么到双方手里。

### 2. 密钥怎么递：排除法立分水岭

对称加密要求双方持有同一把密钥，而递密钥的通道本身就是被窃听对象——等于把保险柜密码写在寄保险柜的外箱上，类比到此为止。排除法第一格收口：纯对称体制在 bootstrap 处失效，密钥协商必须走一条"窃听者看见全部公开报文、却算不出结论"的路。这条路由迪菲-赫尔曼密钥交换（Diffie-Hellman，DH）给出：双方各发一个公开参数，各自用私有的随机数与对方公开参数运算，得出同一个共享秘密；窃听者持有双方全部公开报文，要还原共享秘密须解离散对数问题——其不可行性锚定在这一数学困难性上（现代部署用椭圆曲线版本，运算量再降档）。

但 DH 家族属于非对称运算，成本结构完全不同：单次非对称运算典型在微秒到毫秒档，对称加密单字节在纳秒档——若每条记录都过非对称，吞吐直接拉低三四个数量级（典型量级，方向性结论：非对称比对称慢若干个数量级）。排除法第二格收口：纯非对称承担数据面在算术上失效。两条路各自堵死后，剩下的唯一形态就是混合体制：**非对称只出现在握手、且只做一次密钥协商；对称承担全部应用数据**。成本转移方向明码标价——把"每字节的公钥运算税"换成"每连接一次的协商往返 + 每记录一次的对称运算"，公钥运算的账单从与数据量成正比压缩成与连接数成正比。

### 3. 前向保密：临时参数派生

混合体制还剩一个变量要定：密钥协商用的非对称参数，是长期的还是一次性的。这个选择决定私钥泄露的追溯半径。动作归因如下：让每次握手都用一对用完即焚的临时参数做密钥协商——临时椭圆曲线迪菲-赫尔曼（Elliptic Curve Diffie-Hellman Ephemeral，ECDHE）——会话密钥由这对临时参数派生，协商结束参数即焚；服务器长期私钥在握手中只出一份签名、不进入密钥派生。于是私钥日后泄露，攻击者只能冒充未来的服务器，不能回溯解密过去录下的流量——派生密钥的输入已经不存在了。

反例是 TLS 1.2 时代的静态 RSA 套件：客户端直接用服务器公钥加密预主密钥上传，握手全程不发生临时协商。录下流量、日后拿到私钥，历史会话全量可解——这与 ECDHE 套件在同一个密码套件清单里并存了十几年，直到 TLS 1.3 删除全部静态密钥传输套件、强制临时协商（或预共享密钥）才收口。前向保密由此不是选项而是架构决定：密钥协商参数必须 ephemeral，私钥的职责收敛为"签名证明身份"。

三格动作的前提到此齐备：对称加密、MAC/AEAD、证书链签名，加上一次性协商参数。把它们组装成一次严格单向推进的握手，是第二节的事。

## 二、TLS 握手：状态推进与证书链验证

握手是一次时序因果链：每条消息以上一条消息的产物为输入，状态严格单向推进，不设回退。本节按消息序列把两代握手各遍历一遍——TLS 1.2 走两个 RTT，TLS 1.3 压到一个 RTT——再单独拆出证书链的验证瀑布。

### 1. 消息序列对照：TLS 1.2 两 RTT 与 TLS 1.3 一 RTT

```text
图① TLS 握手消息序列对照（视角：时间推进的消息生命周期，每条消息标注内容与产物）
图例：►═► 明文上线    ►█► 用新派生的密钥加密上线    【产物】该消息落定后双方新增的状态

── TLS 1.2 全握手（ECDHE 套件，RFC 5246；2-RTT，10 条消息）────────────────

 客户端                                                          服务器
   │                                                               │
   │ ① ClientHello：客户端随机数 + 密码套件清单 + SNI            ►═►│
   │                                                               │
   │ ◄═► ② ServerHello：选定的密码套件 + 服务器随机数               │
   │ ◄═► ③ Certificate：证书链（叶子 + 中间 CA）                    │
   │ ◄═► ④ ServerKeyExchange：服务器临时公钥（私钥签名绑定）         │
   │ ◄═► ⑤ ServerHelloDone                                        │
   │                                                               │
   │         【产物】双方由两组临时公钥各算出同一共享秘密            │
   │                 → 派生主密钥 → 会话密钥块                      │
   │                                                               │
   │ ⑥ ClientKeyExchange：客户端临时公钥                         ►═►│
   │ ⑦ ChangeCipherSpec：换密钥旗语                              ►█►│
   │ ⑧ Finished：全部握手报文的哈希，新密钥加密                  ►█►│
   │                                                               │
   │ ◄█► ⑨ ChangeCipherSpec + ⑩ Finished：校验客户端 transcript     │
   │                                                               │
   ├── RTT 1 = ①→⑤；RTT 2 = ⑥→⑩；首个应用数据在 ⑩ 落定后 ────────────┤

── TLS 1.3 全握手（ECDHE 套件，RFC 8446；1-RTT，7 条消息）────────────────

 客户端                                                          服务器
   │                                                               │
   │ ① ClientHello：随机数 + 套件清单 + key_share                 ►═►│
   │    （客户端临时公钥直接随行）                                    │
   │                                                               │
   │         【产物】服务器收到 ① 即可算出共享秘密 → 握手密钥就位     │
   │                                                               │
   │ ◄═► ② ServerHello：选定套件 + 服务器 share（最后一条明文）      │
   │ ◄█► ③ EncryptedExtensions + Certificate + CertificateVerify   │
   │        （私钥对 transcript 哈希签名）+ Finished —— 整体加密     │
   │                                                               │
   │ ④ Finished（校验服务器 transcript）+ 首个应用数据            ►█►│
   │                                                               │
   ├── RTT 1 = ①→④；加密从 ③ 起全覆盖（证书链不再明文上网）──────────┤
```

**TLS 1.2 泳道逐消息遍历**：

- **① ClientHello**：客户端亮出三样输入——一个随机数、自己支持的全部密码套件清单、SNI（Server Name Indication，服务器名称指示，同一 IP 多站点时声明要访问哪个域名，与 04 篇解析出的名字对账）。随机数与套件清单是后续每一步的输入：前者进密钥派生，后者供服务器单向裁决。
- **②③④⑤ 服务器回合**：② 选定唯一套件并交出第二个随机数；③ 交付证书链（验证瀑布见第 3 小节），把"服务器公钥"与"域名"绑定；④ 交出服务器的 ECDHE 临时公钥，并用证书对应的私钥对"参数 + 双方随机数"签名——签名这一步是冒充防线的关键动作归因：中间人可以转发甚至替换临时参数，但没有私钥就签不出这份绑定，参数由此证明属于持证者；⑤ 声明回合结束。
- **【产物】行**：收到 ① 后服务器、收到 ④⑤ 后客户端，各自用对方临时公钥与自己的临时私钥算出同一个 ECDHE 共享秘密——它只存在于两端，从未上线。共享秘密过伪随机函数（Pseudo-Random Function，PRF），连同两个随机数一起派生主密钥，再展开成会话密钥块。两个随机数进派生输入的动作归因：每次握手的派生输入都不同，密钥与会话一一对应，跨会话复用与预计算全部失效。
- **⑥⑦⑧**：⑥ 交出客户端临时公钥——到此双方共享秘密已齐；⑦ ChangeCipherSpec 不加密也不签名，只是一面"以下改用新钥匙"的旗语；⑧ Finished 用新密钥装着 transcript（从 ClientHello 起全部握手消息的滚动哈希）——任何一条在途被改写的消息（删一个套件、降一次版本、换一次参数）都会让哈希对不上，握手当场终止。降级攻击与中间人改写在这道校验处被拦死。
- **⑨⑩**：服务器同样校验客户端的 transcript 后落定，握手结束，双方进入记录层（第三节）。

**RTT 记账**：第一个 RTT 消耗在协商与证书交付，第二个消耗在密钥确认——应用数据最早在第二个 RTT 结束后才上线。跨洲链路每次 RTT 几十至上百毫秒档（03 篇档位），两 RTT 的握手税直接叠在首字节延迟上。1.3 把它压掉一半的动作归因，就是下一泳道。

**TLS 1.3 泳道逐消息遍历**：

- **① key_share 先行**：动作归因——客户端不等服务器指定参数，直接把主流曲线（X25519、P-256 档）的临时公钥随 ClientHello 发出，赌绝大多数服务器接受；接受即省一个回合，猜错才回退多付一个 RTT。
- **【产物】行**：服务器收到 ① 即可算出共享秘密并派生握手密钥——密钥协商从"第二回合"提前到"第一个报文"，这是 2-RTT 压到 1-RTT 的唯一来源。
- **② ServerHello**：仅此一条明文，只回答"用哪组参数"。
- **③ 加密批次**：EncryptedExtensions、Certificate、CertificateVerify、Finished 整体加密上线。两个变化值得点名：其一，证书链自此不进明文网络，顺带消除按证书指纹区分站点的侧信道；其二，CertificateVerify 用服务器私钥对 transcript 哈希签名，把 1.2 中 ④（参数绑定）与 ⑧（transcript 校验）两处证明合并成一处——签名覆盖的输入更多，验证点更少。
- **④ 客户端 Finished + 应用数据**：校验完服务器 transcript，客户端把 Finished 与首个应用数据放进同一批发出——第二个 RTT 整体消失。

两代在同一视角下的对照收拢成一张表：

| 维度 | TLS 1.2 全握手 | TLS 1.3 全握手 |
| --- | --- | --- |
| RTT 数 | 2 | 1 |
| 消息数 | 10（含 2 条旗语） | 7（明文 2 + 加密 5） |
| 密钥协商起点 | 第二回合（⑥ 之后才齐） | 第一个报文（① 即齐） |
| 首个加密点 | ⑦ ChangeCipherSpec 之后 | ③ 起（ServerHello 之后） |
| 证书链是否明文可见 | 是 | 否 |
| 密码套件形态 | 密钥交换 + 签名 + 分组/流模式 + MAC 拼装 | 仅 AEAD 组合（AES-GCM、ChaCha20-Poly1305） |
| 静态 RSA 套件 | 在册（无前向保密） | 已删除，临时协商强制 |
| 身份证明位置 | ④ 签参数 + ⑧ 校 transcript 两处 | CertificateVerify 一处 |

### 2. 证书链验证瀑布：拿谁的公钥验谁的签名

①③ 泳道里交付的那份"证书链"如何兑现冒充防线，值得单独一张图。证书是 X.509 v3 格式（RFC 5280）：一张证书把"某个公钥属于某个主体"这段声明，用签发者的私钥签上名。验证的依赖方向与签发的方向相反——签名自上而下签发（根签中间、中间签叶子），验证自下而上递归（叶子用中间的公钥验，中间用根的公钥验）：

```text
图② 证书链验证瀑布（视角：签名验证的依赖方向）
信任锚：根证书预装在操作系统与浏览器的信任库中，不出网络、本身免验证

 ┌──────────────────────────────────────────────┐
 │ 根 CA 证书（自签名）                           │◄┄┄ 信任锚：权威性来自预装
 │ 公钥：Root-Pub                                │
 └───────────────────┬──────────────────────────┘
                     │ 边 1：用 Root-Pub 验中间证书上的签名
                     ▼
 ┌──────────────────────────────────────────────┐
 │ 中间 CA 证书（签发者 = 根 CA）                  │
 │ 公钥：Mid-Pub；用途位限定其只可再签发证书        │
 └───────────────────┬──────────────────────────┘
                     │ 边 2：用 Mid-Pub 验叶子证书上的签名
                     ▼
 ┌──────────────────────────────────────────────┐
 │ 叶子证书（签发者 = 中间 CA，服务器随握手交付）    │
 │ 行内三查：SAN 域名匹配 + 有效期 + 吊销状态       │
 │ 公钥：Server-Pub ◄—— 握手签名的验证密钥          │
 └──────────────────────────────────────────────┘
```

对图逐边遍历，每条边就是一次"拿谁的公钥验谁的签名"：

- **边 1（根 → 中间）**：拿本地信任库中根证书的公钥 Root-Pub，验中间证书上的签名。通过，则中间证书里的公钥 Mid-Pub 获得信任——信任从预装的锚点借出第一程。
- **边 2（中间 → 叶子）**：拿刚验过的 Mid-Pub，验叶子证书上的签名。通过，则叶子证书的公钥 Server-Pub 获得信任——信任续到第二程。服务器在图① 的 ③ Certificate 消息里交付叶子与中间两级；根不出网络，验证方自持。
- **叶子行内三查**：主体备用名称（Subject Alternative Name，SAN）字段与本次访问的域名精确匹配；当前时间落在有效期内；吊销状态通过证书吊销列表（Certificate Revocation List，CRL）或在线证书状态协议（Online Certificate Status Protocol，OCSP）核查。三查任一不过，等同验签失败。

任何一级失败——签名对不上、域名不匹配、过期、吊销——握手当场终止并回送 alert，不重试、不降级。为什么是瀑布而不是根直接签叶子：动作归因有两条——根私钥离线保管、日常签发下放给在线的中间级，签发税分摊；出事时只吊销中间级，信任锚不动，吊销粒度细化。全球信任库里的根只有几十个档，日常访问触到的链几乎都是"叶子 + 一两个中间"的短链。

> **事实澄清：证书证明的是"公钥属于该域名"，不证明"网站可信"。**
>
> - CA 签发前核验的命题是"申请者控制该域名"，签出的担保是"这个公钥是这个域名的"——仅此而已。它是域名与公钥之间的公证链。
> - 网站内容是否欺诈、服务是否滥用数据，不在签名覆盖范围内。CA 不是内容审核方，签名对页面行为零承诺。
> - 常见误读："浏览器显示锁标即可放心交易"。锁标只说明通道已加密、域名身份已被证实，与站点行为无关——"身份被证实的网站"与"可信的网站"是两个命题。

| 协商结果与证书链 | `openssl s_client -connect example.com:443 -tls1_3` | `New, TLSv1.3, Cipher is TLS_AES_256_GCM_SHA384` 一行锁定协商版本与 AEAD 套件；`Certificate chain` 段按 0（叶子）、1（中间）列出 `s:`（主体）与 `i:`（签发者），签发者链向上逐级对接；结尾 `Verify return code: 0 (ok)` 即瀑布验完 |

读输出时对准两个方向：`i:` 与上一级 `s:` 的逐级咬合就是图② 的两条边；`Verify return code: 0` 是三查加验签全部通过的收口。

握手结束时，密钥与身份同时就位：会话密钥块待命，transcript 校验通过，证书链验证通过。接下来全部应用数据都从这套密钥出发——记录层接管，第三节展开。

## 三、会话对称加密与会话恢复

### 1. 记录层：把字节流切成受保护的记录

03 篇的 TCP 字节流保证字节有序可靠到达，但字节内容对路径完全透明；TLS 在这条字节流之上再封一层记录层，把 05 篇的 HTTP 报文切成一段段受保护的记录。处理链是一条单向管线：

```text
图③ 记录层管线（视角：一段应用数据从明文到 TCP 字节流的处理链）

 应用数据字节流（05 篇的 HTTP 报文：请求行 / 头部 / 体）
    │
    ▼
 ① 分块：切成长度 ≤ 2^14 B（约 16 KB，协议常数）的明文块
    │
    ▼
 ② 挂记录头：类型 + 版本 + 长度（保持明文，供对端分帧）
    │
    ▼
 ③ AEAD 加密：明文块为待加密数据，记录头作关联数据一并进认证
    │            nonce 由静态 IV 与序号派生（每记录递增）
    ▼
 ④ 密文 + 认证标签下交 TCP 字节流（03 篇的可靠有序通道）
    │
    ▼
 接收端逆序还原；标签校验失败 → 立即终止连接（不重试、不降级）
```

管线四步逐段遍历：**① 分块**把连续字节流切成定长上限的块，一条大响应拆成多条记录；**② 记录头**保持明文，让接收端在解密前就知道这段密文的边界与类型；**③ AEAD**一次运算同时完成加密与认证——记录头虽不加密，却作为关联数据进了认证范围，改一个长度字节标签就对不上，第一节的"篡改"一格在此闭环；**④** 密文连同认证标签交给 TCP，接收端逆序执行，标签失败即整条连接作废。窃听一格由加密在 ③ 闭环，冒充一格早在握手证书验证处闭环——威胁模型三格至此全部找到机制落点。

防重放与防重排靠序号，且序号不单独上线：握手时随密钥一起派生一个静态写 IV（初始向量），每条记录递增一个序号，两者按位异或得到本次加密的 nonce：

$$\text{nonce} = \text{静态 IV} \oplus \text{序号}$$

式子即结论：序号藏在 nonce 里参与加密，窃听者看不见；重放旧记录或乱序注入新记录，nonce 与密钥的状态对不上，标签校验当场失败——篡改、重放、重排共享同一道闸门，这也是标签失败"直接终止连接"而不重试的归因：一旦序列状态可疑，继续通信只会扩大暴露面。

### 2. 会话恢复：省一次完整握手

每条新连接都走一遍完整握手，等于每次都重付协商往返与证书验证的非对称运算。会话恢复把上一条连接的结论带过来复用，机制按版本分两代：

- **TLS 1.2：session ID / session ticket**。完整握手时双方约定一个会话凭据——session ID 由服务器自持缓存，session ticket（RFC 5077）则由服务器把会话状态加密打包交给客户端保管。重连时客户端带凭据进门，双方直接从缓存的主密钥派生新会话密钥，跳过证书交付与密钥协商，两次 RTT 压成一次简略握手。
- **TLS 1.3：PSK（Pre-Shared Key，预共享密钥）**。上一条握手派生的恢复主密钥本身就是 PSK，凭据以 ticket 形式随行；还可再叠一层 ECDHE——恢复的同时产生新鲜的临时协商，兼得省往返与前向保密。纯 PSK 模式更进一步：首批应用数据（0-RTT early data）随 ClientHello 直接发出，整个 RTT 都省掉——代价是这批数据无防重放保护，只放幂等请求。

| 恢复机制 | 凭据存放 | 恢复往返 | 证书链重验 | 前向保密 |
| --- | --- | --- | --- | --- |
| 1.2 session ID | 服务器缓存 | 1（简略握手） | 否 | 无新协商，沿旧主密钥派生 |
| 1.2 session ticket | 客户端持加密票据 | 1（简略握手） | 否 | 同上 |
| 1.3 PSK + ECDHE | 客户端持 ticket | 1 | 否 | 有（新 ECDHE 混入派生） |
| 1.3 PSK + 0-RTT | 同上 | 0（首批数据提前） | 否 | 0-RTT 数据无防重放 |

省与花的账都明码标价：省下的是一次完整握手的往返税——跨洲链路几十至上百毫秒档，对高频短连接（API 调用、资源分片拉取）按连接数累积——外加一遍证书链验签的非对称运算；换来的是身份结论不刷新——恢复的连接不再重验证书链，站点证书被吊销后旧凭据仍在恢复期内有效，且恢复凭据本身成为新攻击面（票据加密密钥泄露，凭据即可伪造）。恢复是性能与新鲜度之间的定向交换，没有两头便宜的档位。

至此三条威胁全部闭环：窃听被记录层加密挡住，篡改与重放被 AEAD 标签挡住，冒充被证书链签名挡住；密钥靠一次性协商参数换来前向保密，会话靠恢复机制省掉重复协商的往返税。传输安全层到此闭合。剩下的最后一跳是编程接口：应用进程怎么拿到这些能力——TLS 库以用户态库的形式挂进 socket 调用流程，在 03 篇的字节流 fd 上、`connect` 之后与首个 `write` 之前插入握手，fd 与读写调用面保持不变；这套接口的展开交给 07-Socket 篇，应用层自身的安全（API 鉴权、内容安全）则站在传输安全之上，由 06-软件工程概念 09-安全基础继续。
