# Socket 编程

## 一、socket = 内核网络端点：fd 的网络延伸

前六篇的报文已经一路走进内核：01 篇的分层封装把物理比特组织成报文，02 篇的 IP 寻址决定逐跳去向，03 篇的 TCP/UDP 语义在两端建起可靠或尽力的字节通道，04 篇的 DNS 把名字落成地址。本篇回答最后一步——进程怎么拿到这些能力。答案是套接字（socket）：内核网络端点暴露给进程的句柄，全章六篇协议机制收拢成的唯一调用面。

### 1.1 fd 表里的网络条目：与普通文件共用一套系统调用面

02-操作系统 的 fd 结论就地复述：进程的打开文件表把小整数文件描述符（file descriptor，fd）映射到内核的 struct file，`read`/`write` 只认 fd，进入内核后按 struct file 挂载的操作表分发给具体对象——磁盘文件走页缓存，管道走环形缓冲区。socket 是这张表里的另一类条目：`socket()` 在内核分配网络端点结构并挂进 fd 表，返回的 fd 与普通 fd 共用同一套系统调用号，`read`/`write` 沿同一条 VFS 分发路径进入网络栈，最终落到 03 篇给出的 socket 收发缓冲区上。

共用调用面决定了语义也同构：写文件的 `write` 返回时数据只进了页缓存，设备回写由内核异步完成；写 socket 的 `write` 返回时字节只拷进了发送缓冲区，何时按 MSS 切段、何时发出、丢否重传，全部由 03 篇的可靠性四件套接管——`write` 成功返回不等于对端收到，两处的"成功"是同一种"进了内核队列"。协议栈整体住在内核态，socket 是用户态触碰它的唯一入口；本节先解决"端点是什么"，端点以什么坐标标识自己是下一节的问题。

### 1.2 sockaddr_in：族、端口与端序转换闸门

IPv4 下 socket 地址由 `sockaddr_in` 结构承载，16 B 三个字段：

```text
sockaddr_in（16 B，IPv4）
0x00  sin_family   2 B   地址族：AF_INET = 2（IPv4）、AF_INET6 = 10（IPv6）
0x02  sin_port     2 B   端口号，网络字节序
0x04  sin_addr     4 B   IPv4 地址，网络字节序
0x08  sin_zero     8 B   填零对齐，保证 sockaddr_in 可整体转成通用 sockaddr 传递
```

01-计算机体系 05 的端序结论在此收口：主机内存按小端摆放、网络报文字段按大端编码，两种约定在 socket 边界交接。`htons`/`htonl` 就是这道边界上的显式端序转换闸门——漏过闸的代价是坐标错位：端口 8080 = 0x1F90，小端主机不转换直接填入，报文里就成了 0x901F = 36895，对端连去另一个端口。规则只有一条：所有写入 `sockaddr_in` 的多字节字段必须过 `htons`/`htonl`，从内核取出的字段过 `ntohs`/`ntohl`。

bind 与 connect 用到的坐标更多时候不来自手写数字，而来自名字。04-DNS 的落名结论在此消费：getaddrinfo 把主机名与服务名翻译成一串现成的 `sockaddr`（04 篇递归解析链路的最终产物），`bind` 与 `connect` 直接拿这串坐标使用，名字到端口的最后一跳在本篇完成。端点与坐标齐备，接下来看两种协议各自怎么把它们用起来。

## 二、TCP 与 UDP 编程模型：两套生命周期

### 2.1 服务端五步环与客户端四步环

TCP 两侧的调用序列不对称：服务端多出 `bind`、`listen`、`accept` 三步，客户端只有 `connect` 一步进入通信。逐调用的分工如下表。

| 系统调用 | 服务端 | 客户端 | 内核动作 |
| --- | --- | --- | --- |
| `socket` | 建监听端点 | 建通信端点 | 分配 fd 与收发缓冲区 |
| `bind` | 绑定 (IP, 端口) | 通常省略，内核分配临时端口 | 登记地址占用，冲突报 EADDRINUSE |
| `listen` | 置状态 LISTEN、建连接队列 | 无此步 | 建半连接队列与全连接队列 |
| `connect` | 无此步 | 发起连接 | 组 SYN 发出，驱动三次握手 |
| `accept` | 从全连接队列摘取一条连接 | 无此步 | 返回新 fd，四元组定死 |
| `read`/`write` | 读写循环 | 读写循环 | 与收发缓冲区互拷，驱动协议栈 |
| `close` | 关闭连接 fd | 关闭连接 fd | 驱动四次挥手，回收 fd |

`bind` 的"谁都能绑吗"由两道闸回答。第一道是特权闸：1024 以下端口属特权端口，需要 root 或 CAP_NET_BIND_SERVICE 能力，普通进程绑 80 直接 EACCES——这是把"低端口 = 系统服务"的历史惯例固化成内核权限检查。第二道是占用闸：端口已被登记（包括停留在 TIME_WAIT 的旧连接占用）即 EADDRINUSE；SO_REUSEADDR 选项放行 TIME_WAIT 占用，服务重启不必等 60 s。

`listen` 只做两件事：把端点状态置为 LISTEN，并建出两个连接队列。它不参与握手、不阻塞、不产生任何网络报文——握手的实际执行者是内核，队列结构在 2.3 展开。

### 2.2 生命周期总图：双泳道系统调用时序

服务端与客户端的调用时序、三次握手与四次挥手的叠加位置如下图。中列是内核动作，两条泳道在每个时间点各自推进。

```text
TCP 连接生命周期：服务端与客户端系统调用时序（双泳道，中列为内核动作）

   服务端进程                  内核网络栈                            客户端进程
  ────────────────────────────────────────────────────────────────────────────
   socket() ────────────► 分配监听端点，返回 fd3
   bind(fd3, :8080) ────► 登记 (IP, 端口) 占用
   listen(fd3, 128) ────► 状态 → LISTEN，建半连接队列与全连接队列
   accept(fd3) ─────────► 全连接队列空，服务端睡在 accept 上
                                                                    socket() → fd4
                                                                    connect(fd4)，组 SYN 发出
                          ◄─── SYN［握手①］──────────────────────── 状态 → SYN_SENT
                          SYN 入半连接队列，状态 → SYN_RCVD
                          ──── SYN+ACK［握手②］───────────────────►
                          ◄─── ACK［握手③］──────────────────────── 状态 → ESTABLISHED
                          连接出半连接队列、入全连接队列
   ◄── accept 返回 fd5     从全连接队列摘取队首
   read(fd5) 阻塞         接收缓冲区空，服务端睡在 read 上
                                                                    write(fd4) 请求
                                                                    字节拷入发送缓冲区即返回
                          ──── 请求字节流（MSS 切段）──────────────►
   read 返回              数据入接收缓冲区，唤醒服务端
   write(fd5) 响应 ─────► 字节拷入发送缓冲区即返回
                          ──── 响应字节流 ─────────────────────────►  read(fd4) 返回
   ……（read/write 读写循环交替，这一段边可重复任意次）……
                                                                    close(fd4)，发 FIN
                          ◄─── FIN［挥手①］──────────────────────── 状态 → FIN_WAIT_1
   read 返回 0（EOF）      回 ACK［挥手②］────────────────────────►  状态 → FIN_WAIT_2
                          服务端状态 → CLOSE_WAIT
   （服务端发完剩余响应后）
   close(fd5) ──────────► 发 FIN
                          ──── FIN［挥手③］────────────────────────►  状态 → TIME_WAIT 等 2MSL
                          ◄─── ACK［挥手④］────────────────────────
   状态 → CLOSED（LAST_ACK → CLOSED）
```

对图逐段遍历。前四行是服务端的单向准备：`socket` 拿端点、`bind` 定坐标、`listen` 建队列，`accept` 在全连接队列上睡下——至此服务端没有任何报文发出。客户端 `connect` 触发第一条边：SYN 离开客户端进程后，握手的三个来回全部由两侧内核完成（03 篇的三次握手语义：SYN、SYN+ACK、ACK 让双方各确认一次收发能力），两条泳道上的进程在这段时间内一个睡在 `accept` 上、一个刚从 `connect` 返回。握手完成的连接先进全连接队列排队，直到服务端的 `accept` 把队首摘走、返回连接 fd5——监听 fd3 与连接 fd5 的分工从此固定：fd3 只管收排队，fd5 才承载四元组，一个监听 fd 对应 N 个连接 fd。

读写段的每条边都重复同一机制：`write` 把字节拷进发送缓冲区立即返回，发送节奏归协议栈；`read` 睡到接收缓冲区有数据被唤醒。关闭段从客户端先 `close` 开始：FIN 沿内核送达，服务端的 `read` 返回 0 作为对端关闭的信号（EOF 语义），服务端发完剩余响应后 `close`，四次挥手走完，客户端按 03 篇的结论停在 TIME_WAIT 等 2MSL。服务端与客户端状态机的每一步迁移都叠加在系统调用之间的内核时间里——这条时序可以直接在命令行核验：`strace -e trace=network ./server` 的预期序列是 `socket(AF_INET, SOCK_STREAM, ...) = 3`、`bind(3, {sa_family=AF_INET, sin_port=htons(8080), ...}, 16) = 0`、`listen(3, 128) = 0`、阻塞在 `accept(3, ...)`，连接到达后返回 4，随后 `read`/`write` 交替、`close(4)` 收尾；`htons` 出现在 strace 的参数里，正是 1.2 那道端序闸门在调用边界上的物证。

### 2.3 连接队列与 backlog：握手完成点与连接摘取点的分界

`listen` 建出的两个队列把"连接建立"切成两段：握手在内核里推进，摘取由用户进程执行，二者的分界就是全连接队列。

```text
listen 之后的两个队列：握手完成点与连接摘取点被分开

  客户端 SYN 抵达          内核协议栈                        用户进程
 ─────────────►  ┌───────────────────────────────┐
                 │ 半连接队列（SYN 队列）          │
                 │ 连接状态 SYN_RCVD，等第三个 ACK │
                 │ 容量锚 tcp_max_syn_backlog     │
                 │       │ 第三个 ACK 抵达，握手完成│
                 │       ▼                        │
                 │ 全连接队列（accept 队列）        │
                 │ 连接状态 ESTABLISHED            │
                 │ 容量 = min(backlog, somaxconn)  │ ◄── listen(fd, backlog) 圈定
                 └───────────────────────────────┘
                         │ accept() 摘取队首
                         ▼
                 返回连接 fd，进程从此读写
```

`backlog` 参数圈定的是全连接队列的容量上限，实际生效值为 $\min(\text{backlog}, \text{somaxconn})$ ：somaxconn 是内核全局上限，旧内核默认 128，Linux 5.4 起默认 4096；半连接队列容量另由 tcp_max_syn_backlog 锚定，典型 128~1024 档。溢出行为两队列各不相同：全连接队列满时，第三个 ACK 到达无处安放，内核默认丢弃该 ACK——客户端以为连接已建立、发出数据却石沉大海，直到重传超时；把 tcp_abort_on_overflow 置 1 可改为直接回 RST，把"静默拖延"换成"立刻失败"。半连接队列满时，新到的 SYN 直接丢弃，客户端按 03 篇的 RTO 结论从 1 s 起指数退避重发。

> **事实澄清：三次握手不依赖 accept 调用。** 握手在 `listen` 与 `accept` 之间由内核自动完成：客户端 SYN 一到，内核代为回 SYN+ACK、收 ACK、把建好的连接放进全连接队列，全程不需要服务端进程执行任何调用。`accept` 只负责从队列里摘取已经 ESTABLISHED 的连接，摘取动作可以发生在握手完成之后的任意时刻——延迟几秒才 accept，连接照样先建好再排队。推论是：accept 慢不阻止连接建立，只让全连接队列积压；队列满之后才开始拒绝服务。把"握手等待 accept"当成事实，是半连接洪水防护与队列调优场景里最常见的误判。

队列状态可以直接读回来：`ss -tlnp` 的 LISTEN 行里，Recv-Q 是全连接队列当前积压数，Send-Q 是队列容量（即生效 backlog）。预期观察点：服务进程不调用 accept 时，每来一条连接 Recv-Q 加一，涨到 Send-Q 后不再增长；`ss -tlnp sport = :8080` 中看到 `LISTEN 0 128 0.0.0.0:8080`，即积压 0、容量 128。队列模型清楚了，但 TCP 这套五步环的前提是"先建连接"，另一套协议连这个前提都不要。

### 2.4 UDP：无连接的报文环

UDP 编程模型把 TCP 的建连段整段删除：`socket` → `bind` → `sendto`/`recvfrom` → `close`，没有 `listen`、没有 `connect`、没有 `accept`，首个报文即业务数据。两套模型的分工对比如下。

| 维度 | TCP | UDP |
| --- | --- | --- |
| 系统调用序列 | socket→bind→listen→accept→read/write→close | socket→bind→sendto/recvfrom→close |
| 连接建立 | connect 驱动三次握手 | 无，报文直达 |
| 对端地址 | accept 时定死在连接 fd 上 | 每个报文自带：sendto 传入、recvfrom 返回 |
| 数据边界 | 字节流，无消息边界 | 报文整体，一次 recvfrom 取走一个完整报文 |
| 关闭 | 四次挥手 + TIME_WAIT | close 即止，无挥手 |

这里兑现 03 篇的"UDP 无连接状态"结论：UDP socket 在内核里只有一个接收缓冲区队列，报文按到达顺序整条入队，`recvfrom` 一次取走一条并顺带返回发送方地址——对端身份由每个报文自带，而不是像 TCP 那样在 accept 时定死在连接 fd 上。省下的连接状态、握手往返与挥手开销（03 篇的成本转移方向），换成了应用自己记账：报文丢了不知道、乱了不排序、对端死了不报错，DNS 与实时音视频正是拿这套责任转移换低延迟。两套模型在此分野完毕，但它们共享同一个尾部环节——连接怎么关、关闭的代价落在谁头上。

### 2.5 关闭与 TIME_WAIT：主动关闭方的账单

`close` 触发 03 篇的四次挥手语义：各关一个方向，主动关闭方最后停在 TIME_WAIT 等 2MSL——MSL（Maximum Segment Lifetime，报文最大生存时间）在 Linux 取 30 s，TIME_WAIT 时长即 60 s 档。等待的两个理由在 03 篇已给出：最后一个 ACK 丢失时主动方还能凭状态重发，以及让旧连接的残余报文在网络里自然消亡，避免污染四元组相同的新连接。

关键问题是账单落在谁头上：谁先 `close`，TIME_WAIT 就堆在谁那里。若服务端对每条短连接主动关闭，60 s 窗口内服务端堆起与关闭速率成正比的 TIME_WAIT——每条在内核里占数百字节档的记录并占住一个四元组，万级短连接的服务端就是万级内核记录的常驻税。反过来让客户端先关，账单转移到客户端：客户端用临时端口发起连接，端口空间大、连接数少，同样的记录堆在不敏感的一侧。这就是"服务端尽量让客户端先关"的机制本质——不是 TIME_WAIT 有害，而是它应该堆在端口与内存都宽裕的那一侧；服务端确实必须主动关时，HTTP 的 keep-alive 把关闭次数从"每请求一次"压到"每连接生命周期一次"，从源头减少 TIME_WAIT 供给。

TIME_WAIT 可直接观察：`netstat -an | grep TIME_WAIT` 的行数就是当前 60 s 窗口内由本机主动关闭的连接数，量级与关闭速率 × 60 s 相当；`ss -s` 的汇总里 TIMED 一行给出总数。预期观察点：压测一个短连接 HTTP 服务，服务端进程先关时服务机 TIME_WAIT 持续爬升、客户端侧接近零；把关闭顺序反转，两侧行数对调。到此 TCP 与 UDP 两套生命周期都已闭环，剩下一个所有模型共有的瓶颈：连接 fd 就绪之后，谁来读写它。

## 三、阻塞、非阻塞与 IO 多路复用：一个进程伺服万级连接的演进链

02-操作系统 的 IO 模型结论在此就位：阻塞 IO 的等待发生在 `read` 内部、一次只覆盖 1 个 fd，睡醒往返 1~5 µs 档；多路复用把"等"收拢到一个对象、一次覆盖全部 fd。本节把这条演进链落到网络连接上，每前进一步消除上一档的哪笔税，逐笔记账。

### 3.1 阻塞 IO：一连接一线程的线性账单

阻塞模型下，2.2 的双泳道图对每条连接原样复制一份：`accept` 没连接就睡、`read` 没数据就睡，睡的代价单条看是 1~5 µs 档，问题在连接数一多，进程必须给每条连接配一个独立线程，否则一条连接的等待会冻结所有连接。这笔配置的账单随连接数线性上涨：

$$10^4 \text{ 条连接} \times 8 \text{ MB 栈} = 80 \text{ GB}$$

8 MB 是 Linux 线程默认栈的虚拟上限，物理占用按实际触碰页计，真实业务每线程数十至数百 KB；叠加每线程 16 KB 档的内核栈，万级连接的常驻内存落在 GB 档。第二笔账在调度侧：万个可调度实体，每次事件到达都要唤醒对应线程，睡醒往返按万次计，且线程越多每次切换把缓存踩得越冷，单次切换成本随规模上升。两笔账都随连接数线性走，连接涨到万级（C10K 场景）时内存与调度同时破产——阻塞档的适用边界就是百级连接，排除法的第一刀由此落下。

### 3.2 非阻塞与轮询：把等待换成空转

把 fd 设为 O_NONBLOCK 后，`read` 无数据不再睡眠，立刻返回 -1 与 EAGAIN——EAGAIN 的语义是"此刻没有"而非错误（02 章的结论）。表面上看等待被删除了：单线程带一个 fd 列表，挨个试读，读到数据就处理。但这只是把睡眠税换成了空转税：N 条连接无事件也要每圈扫 N 次，单核被轮询打满 100%，事件到达的延迟等于整圈扫完的时间。事件越稀疏，空转占比越高——高并发服务器的常态恰恰是"万条连接、任意时刻只有几十条有数据"，空转税在正确的负载下最贵。这条路线在物理上不可行，排除法第二刀。要让单线程伺服万级连接，必须让"等"一次覆盖全部 fd、且只返回有事件的那些——这就是多路复用。

### 3.3 三档多路复用：select、poll 与 epoll 的逐笔税

select 是第一档：调用方把 fd 集合（fd_set 位图）交给内核，内核替进程盯着所有 fd，任一就绪即返回。它留下四笔税。第一笔，每次调用把整个集合全量拷入内核、返回时再全量拷出。第二笔，内核必须线性遍历全部 n 个 fd 才能找出就绪的几个，代价 $O(n)$ 。第三笔，返回的位图只标了"哪些就绪"，用户态还得再线性扫一遍把就绪位挑出来，又一遍 $O(n)$ 。第四笔，fd_set 位图定长 1024 位（FD_SETSIZE），超过 1024 条连接只能拆成多个线程各管一批——拷贝与遍历的税随之成倍放大。poll 修掉第四笔：pollfd 数组代替定长位图，每 fd 8 B、数量随连接数走，1024 上限消失；但每次调用仍要全量拷入（万级 fd 即 80 KB 档）加两遍 $O(n)$ 扫描，前三笔原样保留。

epoll（event poll，事件轮询）把消除的对象从"某一笔税"换成"查找本身"。三个调用分工：`epoll_create` 建一个 epoll 实例，内核用红黑树保存注册的 fd；`epoll_ctl` 增删改注册项，每个连接生命周期只做一次；`epoll_wait` 等事件、返回就绪列表。机制的关键动作在事件到达的那一瞬：网卡中断把数据收进协议栈，数据放入 socket 接收缓冲区的同一处理路径上，内核检查该 fd 是否注册在某个 epoll 实例里，是则把对应条目挂进就绪链表——就绪状态在事件到达时顺手维护，而不是在 wait 调用时全量查找。`epoll_wait` 因此只做一件事：把就绪链表整体交回，代价 $O(k)$ ，k 为就绪数，与总连接数 n 无关。三档的对照如下表，每行就是一笔税的去向。

| 维度 | select | poll | epoll |
| --- | --- | --- | --- |
| fd 规模上限 | 1024（FD_SETSIZE 位图位宽） | 无硬上限，数组随连接数增长 | 无硬上限，红黑树随注册增长 |
| fd 集传递 | 每次调用全量拷入、全量拷出 | 每次调用全量拷入（revents 拷出） | epoll_ctl 注册一次；wait 只携就绪项 |
| 内核找就绪 | 线性遍历全部 n 个 fd， $O(n)$ | 线性遍历全部 n 个 fd， $O(n)$ | 事件到达时回调挂就绪链表，wait 只取链表， $O(k)$ |
| 用户找就绪 | 重扫位图挑就绪位， $O(n)$ | 逐项查 revents， $O(n)$ | 返回值即就绪列表， $O(k)$ |
| 集合维护 | fd_set 被内核改写，每轮调用前重建 | 数组常驻，revents 每轮需复位 | 增删改显式走 epoll_ctl，一次注册终身有效 |
| 万级连接每次唤醒成本 | 两遍万级访存扫描 | 80 KB 档数组拷贝加两遍万级扫描 | 一次系统调用加几十项就绪拷贝 |
| 适用规模 | 百级连接 | 千级连接 | 万至十万级连接 |

按 1 万连接、每次唤醒几十个就绪的典型负载把三档摆在一起：select 每次唤醒付两遍万级访存，epoll 只碰就绪的几十项——单次唤醒差两到三个数量级，事件越稀疏差距越大。这不是内核实现优劣，而是"全量查找"与"事件到达时维护就绪"两种机制的算术差：查找成本转移到了注册时一次付清，wait 路径上的成本只与就绪数挂钩。epoll 至此把"单线程伺服万级连接"的最后一块税撤掉，下一步是把它装成一个循环。

### 3.4 事件循环：单线程闭环与全章收口

把 epoll 三件套与非阻塞读写串成一个循环，就是事件驱动服务的完整骨架：

```text
单线程事件循环（epoll 档）

  初始化：socket → bind → listen
              │ epoll_ctl 注册监听 fd
              ▼
        ┌──► epoll_wait（无事件则睡眠）
        │        │ 返回 k 个就绪 fd
        │        ▼
        │    监听 fd 就绪？──是──► accept 摘新连接 ──► 设 O_NONBLOCK
        │        │                                        │
        │        否                                       │ epoll_ctl 注册新连接 fd
        │        ▼                                        │
        │    连接 fd 就绪 ──► 非阻塞 read，读到 EAGAIN 为止
        │        │                                        │
        │        ▼                                        │
        │    处理请求 ──► 非阻塞 write，未写完挂回等下次就绪 │
        │                                                 │
        └──────────────── 回到 epoll_wait ◄───────────────┘
```

循环逐段遍历：初始化段复用 2.1 的服务端前三步，多出的唯一动作是用 `epoll_ctl` 把监听 fd 注册进 epoll 实例；`epoll_wait` 无事件时睡眠，整个进程只睡这一次，醒来拿到的是就绪列表而非"可能有事件"的位图；监听 fd 就绪走 accept 分支，新连接设为非阻塞后立即注册；连接 fd 就绪则非阻塞地读——读到 EAGAIN 才停，把接收缓冲区一次搬空——处理请求后非阻塞地写，写不完的挂回注册集等下一次就绪。读必须搬到 EAGAIN 的原因是触发模式：epoll 默认水平触发（Level-Triggered，LT），缓冲区仍有数据就每次 wait 都报；边缘触发（Edge-Triggered，ET）只在状态变化时报一次，不读到 EAGAIN 就会漏掉剩余数据——ET 把"读完"的责任从内核移交用户，本图按 LT 画，读到有数据即可。

这条闭环的运行纪律只有一条：循环体内禁止任何阻塞调用。归因在结构上：单线程里所有连接共享同一个执行流，一次慢磁盘读或一次锁等待就是全部连接的同步停摆——这正是 3.1 阻塞模型的老问题在单线程里的复刻，只是冻结面从"同线程的连接"扩大到"全实例"。代价是业务代码必须切成非阻塞状态机或协程，把"等待"交还给循环本身。

到此全章链路闭合：01 篇的物理比特经分层封装进入协议栈，02 篇的寻址把它逐跳送达，03 篇的 TCP/UDP 在两端建起字节通道或报文通道，04 篇把名字落成地址，05/06 篇的 HTTP 与 TLS 报文就是这条字节流上的内容——而这一切最终收进 socket 这个进程可调用的内核接口，读写的每一笔都经 fd 表、收发缓冲区与协议栈完成闭环。事件循环这一单线程骨架再向上托底：Python asyncio 的事件循环、Go 运行时的 netpoller、JavaScript 的事件循环，消费的都是同一份"注册 fd → 等就绪 → 逐个处理"的机制结论。
