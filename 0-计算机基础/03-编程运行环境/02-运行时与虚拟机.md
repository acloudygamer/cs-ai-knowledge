# 运行时与虚拟机

> **版本基准**: universal

## 定义

运行时是程序赖以生存的**抽象层**，位于硬件与程序之间，负责内存管理、线程调度、系统调用抽象和垃圾回收。虚拟机是以软件模拟硬件指令集（系统虚拟机）或完整计算机系统（语言虚拟机）的运行时形态。两者的本质区别在于：运行时是**程序执行所需的支撑环境**，虚拟机是**对该环境的软件模拟**。

$$
\text{程序} \xrightarrow{\text{加载}} \text{运行时} \xrightarrow{\text{系统调用}} \text{操作系统} \xrightarrow{\text{驱动}} \text{CPU/内存/外设}
$$

运行时损耗的量化分解：

$$
T_\text{运行时损耗} = \underbrace{T_\text{内存分配}}_{堆管理/GC} + \underbrace{T_\text{调度切换}}_{线程/协程} + \underbrace{T_\text{解释分发}}_{字节码解释器}
$$

**归约终点**：运行时最终归约为 **操作系统内核**（系统调用）和 **CPU 硬件指令**。虚拟化层越厚，归约路径越长，开销越大。

## 数学模型

### 内存分配策略的形式化

堆分配时间取决于分配策略：

$$
T_\text{alloc}(s) =
\begin{cases}
O(1) & \text{顺序分配（arena / bump-pointer）} \\
O(\log n) & \text{空闲链表有序查找（最佳适配）} \\
O(1) \sim O(k) & \text{多隔间空闲列表（碎片化程度影响查找范围）} \\
O(n) & \text{空闲链表无序查找（首次适配）}
\end{cases}
$$

**Bump-pointer 分配**是最简单的策略：维护一个指针 `free`，分配时直接返回 `free` 并递增。代价仅为 $O(1)$，但无法处理碎片化释放。

**空闲链表分配**中，最佳适配（best-fit）需要遍历所有空闲块找到最小满足大小的块：

$$
T_\text{best-fit}(n) = O(n)
$$

其中 $n$ 是空闲块数量。jemalloc 和 tcmalloc 采用多 arena + 空闲列表，将最坏情况降低到近似 $O(1)$。

**约束边界**：分配器的核心约束是**多线程无锁或低锁竞争**。线程局部分配缓存（thread-local cache）是关键：每个线程维护自己的分配池，线程内分配无需锁，只有池枯竭时才从全局池补充。

### 垃圾回收停顿时间分解

GC 停顿来自三个阶段：

$$
T_\text{GC} = \underbrace{T_\text{mark}}_{O(|可达对象|)} + \underbrace{T_\text{sweep}}_{O(|总对象|)} + \underbrace{T_\text{compact}}_{O(|存活对象| \times 平均移动距离)}
$$

**分代假设**的数学依据：研究表明大多数对象在创建后迅速成为不可达（weak generational hypothesis）。基于此假设：
- 年轻代回收代价：$O(|年轻代|)$，频率高但对象少
- 老年代回收代价：$O(|整个堆|)$，频率低但对象多

**停顿时间的实际约束**：
- STW（Stop-The-World）停顿必须小于 50ms 才能避免用户感知
- G1GC 的目标是软实时，通过设置 `MaxGCPauseMillis` 控制

### 栈 vs 堆分配

| 维度 | 栈分配 | 堆分配 |
|------|--------|--------|
| 时间复杂度 | $O(1)$ 指针移动（栈指针 +/-） | $O(1) \sim O(n)$ 取决于分配器 |
| 空间回收 | 函数返回自动释放（严格词法作用域） | 手动 free/delete 或 GC 自动回收 |
| 生命周期 | 严格词法作用域，退出即释放 | 动态，由所有者（owner）决定 |
| 容量限制 | 受栈大小约束（通常 1-8MB） | 受物理内存 + 交换区约束 |
| 缓存友好性 | 连续分配，缓存局部性高 | 可能产生碎片，缓存局部性差 |

**栈分配的数学约束**：栈空间 $S$ 有限，函数递归深度 $D$ 满足：

$$
D \times \text{栈帧大小} \leq S
$$

超出此约束会导致栈溢出（stack overflow）。

### 虚拟机性能分类

| 类型 | 代表 | 虚拟化开销 | 适用场景 |
|------|------|-----------|---------|
| 系统虚拟机 (Type 1 / 裸金属) | KVM, VMware ESXi, Hyper-V | 10-30% | 服务器虚拟化, 云计算 |
| 系统虚拟机 (Type 2 / 宿主) | VirtualBox, VMware Workstation | 15-50% | 桌面虚拟化, 开发测试 |
| 语言虚拟机 (JIT 型) | JVM, CLR, V8 | 0-50%（JIT 可弥补） | 托管代码执行 |
| 纯解释型虚拟机 | CPython, Ruby 1.8 | 50-100x | 跨平台脚本执行 |

### 协程调度模型（Go GMP）

<pre>
G (Goroutine) ←→ M (Machine/内核线程) ←→ P (Processor)
    │
    ├─ G 在 P 的本地队列中循环，阻塞时让出 P 而不阻塞 M
    ├─ M 阻塞 → G 窃取其他 P 的 G
    └─ 上下文切换代价: ~200-300ns（线程切换: ~2-5μs）
</pre>

吞吐量模型：

$$
\text{吞吐量} = \frac{\text{G 数}}{\text{M 数} + \text{阻塞时间} / \text{切换时间}}
$$

当 G 数远大于 M 数时，吞吐量主要受切换时间和阻塞时间影响。M 的阻塞时间（系统调用、GC、锁）越长，有效 G 数越少。

**Go GMP 的关键约束**：
- P 的数量默认等于 CPU 核心数，可在运行时修改
- G 阻塞于系统调用时，M 释放 P 供其他 G 使用
- G 阻塞于 mutex 时，P 被释放，但 M 不阻塞

### 引用计数法的形式化

每对象维护引用计数，计数归零立即回收：

$$
\text{refcount}(obj) = \sum_{ref \in \text{incoming references}} 1
$$

**循环引用的数学本质**：设对象集合 $C$ 为循环引用形成的连通分量。对于任意 $c \in C$：

$$
\text{refcount}(c) \geq 1 \quad (\text{因为 C 内至少有一个其他对象的引用})
$$

即使从外部根（GC Roots）无法到达 $C$，$\text{refcount}$ 仍大于 0，因为每个对象的引用都来自 $C$ 内部。

## 数据流

### 程序加载与运行时初始化

<pre>
可执行文件 (ELF/PE/Mach-O)
    │
    ▼ [内核加载器 — execve / CreateProcess]
映射段到虚拟地址空间:
├─ .text (代码段, r-x)
├─ .data (已初始化数据, rw-)
├─ .bss  (未初始化数据, rw-，零初始化)
├─ .rodata (只读数据, r--)
└─ heap/stack (运行时扩展)
    │
    ▼ [运行时初始化序列]
├─ CRT 初始化 (C/C++ 运行库构造函数)
├─ 堆管理器初始化 (malloc 池 / GC 数据结构)
├─ 线程系统初始化 (TLS, 线程-local storage)
├─ GC 初始化 (GC 根集, 读写屏障注册)
├─ 动态链接器解析 (符号重定位，PLT/GOT 延迟绑定)
└─ 入口点调用 (main / _start)
    │
    ▼
主线程启动 → 进入程序入口
</pre>

**ELF 加载的数学描述**：

ELF 文件的段映射是**虚拟地址空间上的区间划分**：

$$
\text{VA空间} = \bigcup_{i=1}^{n} [ \text{addr}_i, \text{addr}_i + \text{size}_i )
$$

各区间必须满足：互不相交、权限合法（r-x/rw-/r--）、对齐约束。

### 运行时内存布局模型

<pre>
┌────────────────────────────────────────────┐
│  代码区 (Code Segment)                      │
│    ├─ 可执行指令 (r-x)                      │
│    └─ 只读常量 (r--)                        │
├────────────────────────────────────────────┤
│  堆 (Heap) — 动态分配, GC 管理              │
│    ├─ 托管对象（Java 对象 / JS 对象）         │
│    └─ 编译器分配的临时对象                   │
├────────────────────────────────────────────┤
│  栈 (Stack) — 每线程独立                   │
│    └─ 栈帧: [返回地址][参数][局部变量][上下文]│
├────────────────────────────────────────────┤
│  全局数据区                                 │
│    ├─ .data: 已初始化全局变量               │
│    └─ .bss: 未初始化变量 (零初始化)        │
├────────────────────────────────────────────┤
│  元空间 (Metaspace / Code Cache)            │
│    └─ 类元数据, 方法表, JIT 编译缓存         │
└────────────────────────────────────────────┘
</pre>

> **JVM/CLR 差异**：JVM 将方法区和字符串常量池划为独立的"元空间"（JDK 8 前为永久代）；CLR 将其置于"托管堆"内。两者的逻辑分区一致，差异仅在物理布局。

**栈帧的结构约束**：

栈帧大小在编译时确定，包含：
- 返回地址（函数调用后继续执行的位置）
- 参数和局部变量
- 保存的寄存器上下文

递归调用的栈帧累积：$S_{\text{total}} = D \times S_{\text{frame}}$，其中 $D$ 是递归深度。

### 垃圾回收数据流

<pre>
标记阶段 (Mark):
GC Roots (栈引用, 静态字段, JNI 引用, 寄存器)
    │
    ▼ [三色标记算法]
白色 ← 未标记对象
灰色 ← 待处理 (已发现但未遍历子对象)
黑色 ← 已处理 (自身和子对象均已标记)
    │
    ▼ [可达性遍历 — BFS/DFS]
递归标记 → 所有可达对象变为黑色
时间复杂度: O(|可达对象|)

清除阶段 (Sweep):
扫描整个堆 → 回收白色对象 → 更新空闲列表
时间复杂度: O(|总对象|)

整理阶段 (Compact):
移动存活对象 → 消除内存碎片 → 更新所有引用
时间复杂度: O(|存活对象| × 平均移动距离)
</pre>

**三色标记的正确性条件**：赋值器（mutator）与 GC 并发执行时，必须保证「黑色对象不会指向白色对象」这一不变量。通过**写入屏障（write barrier）**在每次引用赋值时维护此不变量。

**SATB（Snapshot-At-The-Beginning）的形式化**：

$$
\forall obj \in \text{Reachable}(t_0): obj \notin \text{Garbage}(t_1)
$$

其中 $t_0$ 是 GC 开始时刻，$t_1$ 是 GC 结束时刻。SATB 保证所有在 $t_0$ 时可达的对象不会被回收，即使在 $t_1$ 时已变得不可达。

### 分代回收数据流

<pre>
新对象分配 → Eden 区
    │
    ▼ [Minor GC 后存活]
年龄 +1 → 复制到 Survivor 区 (S0 或 S1)
    │
    ▼ [年龄 ≥ 阈值（通常 15）或 Survivor 满]
Promote → 老年代
    │
    ▼ [老年代满 → Full GC]
标记-整理 → 回收 / 整理老年代
</pre>

**对象年龄的计算**：

$$
\text{age} = \text{经历的 Minor GC 次数}
$$

当 $\text{age} \geq \text{MaxTenuringThreshold}$ 时，对象晋升为老年代。

### 语言虚拟机执行流（JIT 型）

<pre>
字节码 / 源码加载 → 验证器检查合法性
    │
    ▼ [解释执行阶段 — Ignition / Interpreter]
解释器主循环: fetch → decode → dispatch → execute
    │
    ▼ [热点检测]
调用计数 ≥ CompileThreshold (JVM: 1500)
循环回边计数触发 OSR (On-Stack Replacement)
    │
    ▼ [JIT 编译 — Turbofan / HotSpot C2]
IR 生成 → 平台无关优化 → 平台相关优化
    │
    ▼ [投机优化]
├─ 类型特化 (Type Specialization)
├─ 内联 (Inlining)
├─ 逃逸分析 (Escape Analysis)
├─ 循环优化 (Loop Optimization)
└─ 向量化 (SIMD)
    │
    ▼ [假设验证]
类型稳定 → 继续执行优化码
类型变化 → 去优化 → 回退解释执行
</pre>

## 机制

### 运行时的核心职责

运行时位于程序与操作系统之间，提供**高级抽象**，将程序从硬件细节中解放出来。

**内存管理职责**：
- **分配**：程序请求内存 → 运行时调用系统 API（brk/mmap）→ 管理进程地址空间
- **回收**：手动（free/delete）或自动（GC）；自动回收解决了"忘记释放导致的泄漏"但引入了 GC 停顿问题
- **约束**：堆内存有限，分配失败必须处理（返回 null 或抛出异常）

**线程调度职责**：
- **内核线程**：OS 抢占式调度，时间片耗尽强制切换，切换代价 $T_{ctx} \approx 2\!-\!5\,\mu s$
- **用户线程（协程）**：运行时协作式调度，切换代价 $T_{ctx} \approx 200\!-\!300\,ns$，但必须显式 yield
- **Go GMP 模型**：协程（G）在处理器（P）上复用内核线程（M），G 阻塞时 M 可从其他 P 窃取 G 继续执行，实现「阻塞用户态协程但不阻塞内核线程」

**系统调用封装职责**：
- 程序通过运行时发起 I/O、进程管理等操作
- 运行时将系统调用封装为高级 API（read/write → fread/fwrite → iostream）
- 运行时处理信号和异常传播

**违规后果**：
- 内存泄漏：分配后未释放 → 堆耗尽 → OOM（Out-Of-Memory）杀死进程
- 悬空指针：释放后继续使用 → 未定义行为（可能 segfault 或读取已分配给其他对象的数据）
- 栈溢出：递归过深或大局部变量分配 → stack overflow（栈溢出异常或 SIGSEGV）
- 双重释放：同一块内存释放两次 → heap corruption → 随机崩溃

### 垃圾回收机制

#### 引用计数法

每对象维护引用计数，计数归零立即回收：

$$
\text{refcount}(obj) = \sum_{ref \in \text{incoming references}} 1
$$

**优点**：回收及时，无 STW（Stop-The-World）停顿；内存管理代价可预测。
**缺点**：无法处理循环引用；计数更新有原子操作开销（影响多线程性能）；计数为 0 时必须立即回收，若对象析构函数有副作用可能引发复杂依赖。

**循环引用泄漏**的数学本质：循环引用的对象集合的 refcount 永远大于 0，即使从外部已无法访问。

```python
a = Node()  # refcount(a) = 1
b = Node()  # refcount(b) = 1
a.ref = b   # refcount(b) += 1 → 2
b.ref = a   # refcount(a) += 1 → 2
del a; del b  # refcount 均降至 1（各自持有对方引用），永远无法归零
```

#### 标记-清除法

从 GC Roots 出发标记所有可达对象：

$$
\text{Reachable} = \text{DFS}(\text{GC Roots})
$$

未标记对象视为垃圾。GC Roots 包括：全局变量、栈帧中的变量、寄存器。

**约束**：需要 STW 停顿；全堆扫描代价高；清除后产生内存碎片。

**违规后果**：标记遗漏 → 存活对象被回收 → 悬空指针 → 程序崩溃或数据损坏。

#### 分代收集法

基于弱分代假设：大多数对象朝生夕死。不同代际使用不同回收算法：

| 分代 | 对象年龄 | 回收算法 | 回收频率 |
|------|---------|---------|---------|
| 年轻代 (Eden + S0 + S1) | 0-15 次回收 | 复制算法（Survivor 区 S0/S1 交换） | 高（90% 对象死亡） |
| 老年代 | ≥ 阈值 | 标记-整理 | 低 |

复制算法代价：$O(|存活对象|)$，无碎片，但浪费 50% 空间（一个 Survivor 区始终空闲）。

#### 并发标记与读写屏障

三色标记在并发场景下需要**读写屏障**维护正确性：

$$
\text{白色} \xrightarrow{\text{发现}} \text{灰色} \xrightarrow{\text{遍历}} \text{黑色}
$$

两种主流屏障策略：
- **SATB（Snapshot-At-The-Beginning）**：标记开始时对所有 GC Roots 做快照，保留快照时可达的所有对象，即使后续变为不可达也不回收。适合写多读少场景。
- **增量更新（Incremental Update）**：标记结束后，脏写（对象引用改变）将新引用的对象加入待处理队列。适合读多写少场景。

**约束**：屏障带来额外性能开销；标记必须最终完成（不能永远停在中间状态）。

**违规后果**：
- 标记遗漏 → 存活对象被回收 → 悬空指针
- 屏障性能开销过大 → GC 吞吐量下降（每秒回收的内存量减少）

### 虚拟机机制

#### 系统级虚拟机 (Hypervisor)

**Type 1（裸金属）**：hypervisor 直接运行在硬件上，自身是轻量级操作系统：
- KVM（Linux 内核模块）：依赖硬件辅助虚拟化（Intel VT-x / AMD-V），宿主机 Linux 承担部分管理职责
- VMware ESXi：裸金属 hypervisor，完全独立
- Hyper-V：Windows Server 虚拟化，Hypervisor 层在 Ring -1

**Type 2（宿主）**：hypervisor 运行在宿主机操作系统上：
- VirtualBox：依赖宿主 OS 的驱动程序栈
- VMware Workstation：用户态虚拟化，通过宿主机内核驱动实现

虚拟化开销的三个来源：
1. **CPU 模拟**：二进制翻译（BT）或硬件辅助虚拟化（VT-x）。硬件辅助将 Guest 的 Ring 0 置于 Host 的非特权模式，Guest 操作特权指令时触发 VM Exit，由 VMM 处理。
2. **内存虚拟化**：影子页表（软件模拟）或 EPT/NPT（硬件辅助）。Guest 的虚拟地址到物理地址再到宿主物理地址的两级映射由硬件自动完成。
3. **I/O 虚拟化**：半虚拟化（VirtIO，Guest 安装驱动直接与 Hypervisor 通信）或 VFIO（直通到宿主物理设备）。

#### 语言虚拟机

**JVM / CLR（JIT 型，基于线程共享地址空间）**：
- 类/程序集加载 → 字节码验证 → 解释或 JIT 执行
- JIT 编译热点代码 → 本地机器码
- GC 管理托管堆（分代 + 并发标记）
- 线程间共享堆，通过锁/原子操作处理数据竞争

**BEAM（Erlang/Elixir，基于 Actor 模型）**：
- 每个 Actor 是独立轻量级进程（BEAM process），拥有私有状态和 mailbox
- 基于 **reduction counting** 的抢占式调度（每执行一定数量指令被强制挂起）
- 进程间通过消息传递通信，无共享内存，从根本上避免数据竞争
- 进程创建代价极低（~微秒级），支持数万并发进程

> **关键对比**：JVM/CLR 是「共享地址空间的线程模型」，靠锁和原子操作处理数据竞争；BEAM 是「基于消息传递的 Actor 模型」，通过进程隔离从根本上避免竞争。前者在紧耦合共享数据场景效率更高，后者在高并发、独立进程隔离场景更具优势。

### JIT 编译器与运行时的关系

JIT 编译器是运行时的一部分，在运行时动态编译字节码：

$$
\text{字节码} \xrightarrow{\text{JIT}} \text{IR} \xrightarrow{\text{优化}} \text{机器码}
$$

**编译时决策 vs 运行时决策**：
- **编译时**：函数调用约定、栈帧布局、符号解析——这些在运行时不会改变
- **运行时**：热点识别（调用计数）、类型特化（基于历史反馈）、去优化触发——这些在运行时才可知

**约束**：JIT 编译时间计入程序运行时间，过度 JIT 导致程序停顿（ JVM 的「预热问题」：长时间运行的 Java 程序性能持续上升直到稳定）。

**违规后果**：
- JIT 编译错误：优化假设不成立（如类型变化）→ 去优化回退
- 编译时间过长：程序响应延迟，用户感知为「卡顿」
- 编译缓存溢出：JIT 编译代码存储在 Code Cache 中，若 Code Cache 满，新的 JIT 编译被抑制

### BEAM 调度器的 Reduction Counting

BEAM 使用 reduction counting 实现抢占式调度：

$$
\text{reduction} = \text{执行的指令数} + \text{函数调用次数} \times \text{权重}
$$

当 $\text{reduction} \geq \text{quantum}$ 时，进程被挂起，调度器选择下一个进程。

**优势**：不依赖定时器中断，不影响精确计时。
**约束**：计算密集型进程可能在 quantum 耗尽前长时间占用 CPU。

### 归约能力：运行时到硬件的映射

运行时本质上是将高级语言操作映射为硬件指令的翻译层：

| 运行时概念 | 归约到硬件/内核 | 归约路径 |
|-----------|---------------|---------|
| 内存分配 | brk/mmap 系统调用 | 运行时 → syscalls → 内核 → 物理内存 |
| 线程调度 | 内核线程 (pthread_create) | 运行时 → pthread库 → 内核 → CPU调度 |
| 文件 I/O | open/read/write | 运行时 → libc → 内核 → 驱动 |
| 网络 I/O | socket/connect/recv | 运行时 → libc → 内核 → 网卡驱动 |
| GC | 标记-整理算法 | 运行时自行管理，不涉及内核 |

**关键洞察**：运行时越薄（如 C 程序直接调用 libc），归约路径越短，开销越小。运行时越厚（如 JVM），提供的抽象越多，但运行时损耗也越大。现代语言选择厚运行时是为了**编程便利性**和**安全性**，以性能为代价。

### C 手动内存管理

```c
int *alloc_array(int n) {
    int *p = malloc(n * sizeof(int));  // 堆分配，可能失败（返回 NULL）
    if (!p) return NULL;
    for (int i = 0; i < n; i++)
        p[i] = i * i;
    return p;  // 调用者负责 free
}
// 使用: int *arr = alloc_array(100); ... free(arr);
```

### Go 协程与通道

```go
ch := make(chan int, 1)      // 有缓冲通道，容量 1
```

### Python 引用计数（CPython 实现）

```python
# CPython 的对象头包含 ob_refcnt 字段
class RefCounted:
    def __init__(self):
        self.refcount = 1   # 新建对象引用计数为 1

    def add_ref(self):
        self.refcount += 1   # 引用共享时

    def release(self):
        self.refcount -= 1
        if self.refcount == 0:
            self._free()     # 触发析构并释放内存
```

### BEAM Process 示例

```erlang
% Erlang/Elixir 的 Actor 模型示例
-module(echo).
-export([start/0]).

start() ->
    spawn(fun() -> loop() end).

loop() ->
    receive
        {Pid, Msg} ->
            Pid ! Msg,  % 回复发送者
            loop();
        stop -> ok
    end.

% 使用:
% Pid = echo:start(),
% Pid ! {self(), "hello"},  % 发送消息
% flush().  % 接收回复
```
