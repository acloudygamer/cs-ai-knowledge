# 运行时与虚拟机

## 定义

运行时是程序执行时赖以生存的环境，提供内存分配、线程调度和系统调用抽象；虚拟机是以软件模拟硬件指令集或完整计算机系统的运行时形态。

$$
\text{程序} \xrightarrow{\text{加载}} \text{运行时} \xrightarrow{\text{系统调用}} \text{操作系统} \xrightarrow{\text{硬件抽象}} \text{CPU/内存}
$$

$$
\text{性能损耗} = \underbrace{T_{解释分发}}_{解释器} + \underbrace{T_{内存分配}}_{GC/堆管理} + \underbrace{T_{调度}}_{线程/协程切换}
$$

## 数学模型

### 内存分配模型

<pre>
堆内存分配时间: T_alloc = O(1) ~ O(n)  取决于分配策略
  - 空闲链表: O(n) 查找
  - 堆栈式: O(1) 指针推进（顺序分配）
  - 空闲列表+隔间: O(1) ~ O(k)  取决于碎片化程度

垃圾回收停顿时间:
  T_gc = T_mark + T_sweep + T_compact
       = O(|可达对象|) + O(|总对象|) + O(|存活对象|×移动距离)
</pre>

### 栈 vs 堆分配

<pre>
栈分配: T = O(1)   — 只需移动栈指针
堆分配: T = O(n)~O(1)  — 取决于分配器实现
  分配子: jemalloc/tcmalloc → 多隔间空闲列表 → 近似O(1)
</pre>

### 虚拟机性能分类

| 类型 | 代表 | 开销 | 用途 |
|------|------|------|------|
| 系统虚拟机 (Hypervisor) | KVM, VMware ESXi, Hyper-V | 10-30% | 服务器虚拟化, 云计算 |
| 语言虚拟机 (JIT型) | JVM, CLR, BEAM | 0-50% | 托管代码执行, JIT可弥补开销 |
| 纯解释型虚拟机 | CPython, Ruby 1.8 | 50-100x | 跨平台字节码解释 |

### 协程调度模型 (Go GMP)

<pre>
G (Goroutine) ←→ M (Machine/线程) ←→ P (Processor)
  G队列在P上循环，分发到M执行
  M阻塞 → 窃取其他P的G
  上下文切换成本: ~200-300ns (vs 线程~2-5μs)
</pre>

## 数据流

### 程序加载与运行时初始化

<pre>
可执行文件 (ELF/PE)
    ↓ [内核加载器]
映射段到内存 (code, data, bss, stack)
    ↓
运行时初始化
    ├─ CRT初始化 (C/C++)
    ├─ 堆管理器初始化
    ├─ 线程系统初始化
    ├─ GC初始化 (若有)
    └─ 符号解析与动态链接
    ↓
入口点 (main/_start)
    ↓
程序主线程启动
</pre>

### 运行时数据区模型（通用视图）

<pre>
┌────────────────────────────────────────────┐
│  代码区 (Code Segment)                      │
│    ├─ 可执行指令                            │
│    └─ 只读常量                              │
├────────────────────────────────────────────┤
│  堆 (Heap)                                 │
│    ├─ 动态分配对象                          │
│    └─ GC管理的对象                          │
├────────────────────────────────────────────┤
│  栈 (Stack) — 每线程独立                   │
│    └─ 栈帧: 局部变量 + 返回地址 + 上下文    │
├────────────────────────────────────────────┤
│  全局数据区                                 │
│    ├─ 已初始化全局变量                      │
│    └─ 未初始化变量 (BSS)                    │
├────────────────────────────────────────────┤
│  PC Register — 每线程独立                  │
│    └─ 当前执行指令地址                       │
├────────────────────────────────────────────┤
│  本地方法区 / 原生调用区                    │
└────────────────────────────────────────────┘
</pre>

> **对比参照**：JVM 将方法区和字符串常量池单独划为"方法区"（元空间），CLR 将其置于"托管堆"；但基本布局一致——代码区、堆、栈、全局数据区是所有运行时共有的内存划分。

### 垃圾回收数据流

<pre>
标记阶段 (Mark):
  GC Roots遍历 → 可达对象标记 → 构建可达图
  时间复杂度: O(|可达对象|)

清除阶段 (Sweep):
  扫描整个堆 → 回收未标记对象 → 更新空闲列表
  时间复杂度: O(|总对象|)

整理阶段 (Compact):
  移动存活对象 → 消除碎片 → 更新引用
  时间复杂度: O(|存活对象|×移动距离)
</pre>

### 分代回收数据流

<pre>
新对象分配 → Eden区
    ↓ [Minor GC后存活]
→ Survivor 0 → 年龄+1
    ↓ [Minor GC后存活]
→ Survivor 1 → 年龄+1 (交换S0/S1角色)
    ↓ [年龄≥阈值 或 Survivor满]
→ 老年代
    ↓ [Full GC]
→ 回收 / 整理
</pre>

### 语言虚拟机执行流

<pre>
字节码 → 解释器循环 → 分发执行
              ↓
        热点检测(计数/回边)
              ↓
        JIT编译 → 本地机器码
              ↓
        直接执行(跳过解释)
              ↓
        假设失败 → 去优化 → 回退
</pre>

## 机制

### 运行时的核心职责

**内存管理**：
- 堆分配：malloc/new请求 → 分配器 → 寻找合适空闲块 → 返回指针
- 堆回收：手动free/delete 或 GC自动回收
- 栈管理：函数调用时压栈， 返回时弹栈（编译器生成）

**线程调度**：
- 内核线程：OS调度，抢占式，上下文切换成本高
- 用户线程：运行时管理，协程/纤程，切换成本低
- Go协程：GMP模型，协程在P上复用M，阻塞时让出P

**系统调用**：
- 程序通过运行时发起系统调用（read/write/socket等）
- 运行时封装系统调用为高级API
- 运行时拦截信号处理异常

**违规后果**：
- 内存泄漏：分配后未释放，堆耗尽
- 悬空指针：释放后使用，未定义行为
- 栈溢出：递归过深或大局部变量

### 垃圾回收机制

**引用计数法**：
- 每对象维护引用计数，计数为0立即回收
- 优点：回收及时，无STW停顿
- 缺点：无法处理循环引用，计数更新开销

**标记-清除法**：
- 从GC Roots出发标记可达对象
- 清除未标记对象
- 缺点：STW停顿，全堆扫描

**分代收集法**：
- 年轻代：对象朝生夕死，频繁Minor GC，复制算法
- 老年代：存活时间长，Full GC，标记-整理算法
- 核心假设：大多数对象朝生夕死

**三色标记法**：
- 白色：未标记
- 灰色：待处理（已发现但未遍历子对象）
- 黑色：已处理（自身和子对象均已标记）

**并发标记**：
- 增量标记：与Mutator交替执行
- 并发标记：Mutator与GC并发执行
- 需要读写屏障维护标记正确性

**违规后果**：
- 循环引用泄漏：引用计数无法回收互相引用但不可达的对象
- GC停顿过长：标记阶段STW导致程序卡顿
- 内存碎片：标记-清除产生碎片，大对象分配失败

### 虚拟机机制

**系统级虚拟机 (Hypervisor)**：

Type 1（裸金属）：
- 直接运行在硬件上
- 代表：VMware ESXi, KVM, Hyper-V
- 用途：服务器虚拟化，云计算

Type 2（宿主）：
- 运行在宿主机操作系统上
- 代表：VirtualBox, VMware Workstation
- 用途：桌面虚拟化，开发测试

**语言虚拟机**：

JVM执行模型（JIT型）：
- 类加载 → 字节码验证 → 解释/JIT执行
- JIT编译热点代码 → 本地机器码
- GC管理堆内存

CLR执行模型（JIT型）：
- 托管代码（IL）→ JIT编译 → 本地执行
- 类似JVM，但JIT在首次调用时编译

BEAM执行模型（Actor型）：
- Actor模型，每个进程独立
- 基于reduction counting抢占式调度
- 进程间消息传递

> **对比参照**：JVM/CLR是"基于线程的JIT型虚拟机"，BEAM是"基于Actor的虚拟机"——前者共享地址空间靠线程+锁并发，后者每个Actor是独立进程靠消息传递并发。

**违规后果**：
- 虚拟机逃逸：利用漏洞突破虚拟化隔离
- 字节码验证失败：加载非法字节码被拒绝
- JIT编译错误：优化假设失败触发去优化

### 运行时与编译器的关系

**编译时决策**：
- 生成何种运行时调用（libc vs libstdc++）
- 静态还是动态链接
- 堆分配策略（逃逸分析决定栈/堆分配）

**运行时依赖**：
- 编译器生成调用运行时的代码
- 运行时提供内存分配、线程管理、GC等服务
- JIT编译器是运行时的组成部分

## 参考存根

### C语言手动内存管理（≤20行）

```c
#include <stdlib.h>
int *alloc_array(int n) {
    int *p = malloc(n * sizeof(int));
    for (int i = 0; i < n; i++) p[i] = i;
    return p;
}
```

### Go协程示例（≤20行）

```go
func main() {
    ch := make(chan int)
    go func() { ch <- 42 }()
    <-ch
}
```

### Python引用计数（≤20行）

```python
import sys
class RefCounted:
    def __init__(self): self.refcount = 1
    def add_ref(self): self.refcount += 1
    def release(self):
        self.refcount -= 1
        if self.refcount == 0: self._free()
```
