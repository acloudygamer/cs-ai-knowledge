# 链接与装载

## 核心定义：把悬而未决的地址填上

01 篇的编译器后端吐出的目标文件（`.o`）里，地址全是空白：调用 `printf` 的那条指令不知道该跳去哪——符号悬而未决。两个收尾步骤把它变成运行中的进程：

- **链接（Link）**：编译期之后、运行之前，把多个目标文件和库装订成一个可执行文件——每个符号找到唯一定义，每个引用点填上真实地址。
- **装载（Load）**：运行那一刻，内核把可执行文件搬进内存、建成进程（03-进程与线程 的 `execve` 在那里只讲了一半，本篇补另一半）。

## 静态链接：两步装订

链接器（`ld`）对一组 `.o` 做两件事：

1. **符号解析**：收集所有目标文件导出（定义）与引用（未定义）的符号表，给每个引用找到唯一定义。找不到 → 链接错误 `undefined reference`；找到两个 → `multiple definition`。库只是 `.o` 的归档包（`.a` 文件就是 `ar` 打包），链接器按需从归档里挑出用得着的成员。
2. **重定位**：定义都找齐后，每个符号有了最终地址，链接器把地址回填到所有引用它的指令和数据处。

静态链接的产物是**自包含**的：所有代码进同一个文件，运行时不依赖任何外部库。什么时候要这个形状：容器镜像与嵌入式设备（目标环境里没有库可依赖）、以及"拷走就能跑"的分发——Go 默认静态链接正是这个取向，产出一个无依赖的单文件二进制。

## 动态链接：为什么把装订推迟到运行时

**约束**：libc 这样的库被系统里每个进程使用。静态链接意味着 100 个进程各背一份 libc 副本（内存浪费），库修一个安全漏洞要重编译所有程序（维护灾难）。动态链接把装订推迟：

- 可执行文件里只登记"我需要 `libc.so`"（ELF 的 `DT_NEEDED` 条目），不装内容；
- 共享库（`.so` / `.dll`）在内存里**只存一份物理页**，被所有进程映射进各自的地址空间（04-内存管理 的文件后备页机制：同一份文件页映射给多个 VMA）；
- 库升级只换一个 `.so` 文件，所有程序下次启动自动用新版。

**代价与对策**。动态链接引入一个位置问题：同一份 `.so` 被映射到不同进程的不同虚拟地址，库代码里不能写死任何绝对地址——这就是**位置无关代码（PIC）**：代码中所有对外引用都隔一层间接表。函数调用走 **PLT**（过程链接表，跳板），数据访问走 **GOT**（全局偏移表，存真实地址）。GOT 条目默认**惰性绑定**：第一次调用某函数时才由动态链接器解析回填——启动更快，但每个函数的第一次调用都要付一次解析费（安全加固场景可用 `BIND_NOW` 关掉惰性，启动时全解析）。

### 运行时，库从哪来

程序启动时，`ld.so` 按固定顺序搜索依赖的 `.so`：可执行文件里烤进去的 `rpath`/`runpath` → 环境变量 `LD_LIBRARY_PATH` → `ldconfig` 维护的系统缓存 → 默认系统目录。报错 `error while loading shared libraries: xxx.so: cannot open shared object file` 就是这条路全部落空。版本问题也在这一层：库文件名带主版本号（soname，如 `libfoo.so.2`），程序按 soname 登记依赖；两个库各自拖进不同大版本的同名库时，符号在进程的全局命名空间里互相踩踏——这就是 Linux 版的"依赖地狱"，容器化（《软件工程概念》05）正是它的隔离式解法。

### dlopen：装载还可以发生在运行中

启动时装载的前提是"链接时就知道要谁"。另一扇门是运行中主动装载：`dlopen("libx.so")` 打开库、`dlsym("func")` 取出函数指针——**插件机制的全部根基**。数据库驱动的动态加载、编辑器的插件、Python 的 C 扩展（`import numpy` 时，解释器就是在 dlopen 一个 `.so`）都是同一形状：主程序事先不知道、运行时按需装载。链接与装载的完整时间轴因此是：链接时装订（静态）→ 启动时装订（动态）→ 运行中装订（dlopen），越晚越灵活，越早越可校验。

## ELF：可执行文件的解剖

Linux 的可执行文件、目标文件、共享库共用同一格式 ELF（Executable and Linkable Format）。它有两副面孔，恰好对应本篇的两个主角：

```text
链接视角（Section）：          装载视角（Segment）：
.text   代码                   PT_LOAD 段①：R+X（.text+.rodata 合并）
.rodata 只读常量        ──►    PT_LOAD 段②：RW （.data+.bss 合并）
.data   已初始化数据           （段是节的打包：把权限相同的节合并，
.bss    未初始化数据            装载器按段 mmap，页表权限按段设置）
.symtab 符号表
```

`.bss` 值得单独看：未初始化全局变量在文件里**不占一个字节**，只记一个总大小；装载时内核把对应页映射到清零的匿名页——零值的物理供给推迟到缺页那一刻（04 的懒兑现，又一个客户）。

## 装载：execve 的完整链路

`execve("./a.out")` 之后，内核做的事（与 03-进程与线程 的"换一副脑子"衔接）：

```text
读 ELF 头，校验魔数与架构
  → 为每个 PT_LOAD 段建立 VMA（04 的机制），映射到可执行文件
    —— 注意只是记账：页还没读盘，首次触碰走缺页异常现读
  → 若带 PT_INTERP（动态链接程序）：先映射动态链接器 ld.so，
    入口让给 ld.so
  → 建立栈（压入 argv/envp），设置指令指针，返回用户态
  → 动态程序：ld.so 先跑——装载全部 DT_NEEDED 共享库、
    执行重定位，然后才跳到程序入口 _start → __libc_start_main → main
```

所以"程序启动"是一条两级接力链，与 07-系统引导 的加电链同构：每一级点亮下一级的能力，且处处懒兑现——段映射先记账后缺页，符号先登记后绑定，零页先承诺后供给。main 的第一行代码执行时，你的程序已经有地址空间、共享库就绪、参数在栈上，而这一切在你写下第一行代码前就被链接器和装载器安排妥了。
