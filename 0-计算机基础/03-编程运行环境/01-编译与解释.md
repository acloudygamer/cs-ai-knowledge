# 编译与解释

## 核心定义：同一件事，两种兑现时机

源码只是文本，CPU 只认机器码。把源码的语义兑现成 CPU 的行为，有两条路线：

- **编译（Compile，AOT）**：运行**之前**一次性翻译完，产出机器码文件，运行时零翻译开销。
- **解释（Interpret）**：运行**之中**边读边做，每执行一句现场翻译一句。

"编译型语言 / 解释型语言"这个说法本身是误导——**这是实现的属性，不是语言的属性**。Java 既能跑在 JIT 的 JVM 上，也能被 GraalVM native-image 提前编译成本机二进制；C 也有解释器。语言只规定语义，兑现时机的选择由实现按约束决定。约束是什么、各自付了哪笔账，是本篇的主线。

## 编译器的三段结构

一个现代编译器（GCC、Clang、rustc、swiftc）内部是同一条三段流水线：

```text
源码文本
  ▼ 前端（Frontend）：懂语言，不懂机器
     词法分析：字符流 → token 流（"int x" → [关键字int, 标识符x]）
     语法分析：token → 抽象语法树 AST（表达式套表达式，一棵树）
     语义分析：类型检查、名字解析——报错主要在这一步发出
  ▼ 产出中间表示（IR）：与源语言和目标机器都无关的通用指令集
  ▼ 中端（Middle-end）：IR 上的机器无关优化
     常量折叠、死代码消除、循环不变量外提、函数内联……
  ▼ 后端（Backend）：懂机器，不懂语言
     指令选择：IR 操作 → 目标 CPU 的具体指令
     寄存器分配：IR 里无限多的虚拟寄存器 → x86-64 仅有的 16 个通用寄存器
       （装不下的变量溢出到栈上——寄存器稀缺是这里的硬约束）
  ▼ 目标文件（.o / .obj）：机器码 + 悬而未决的符号（02 接手）
```

为什么劈成三段（约束）：M 种语言 × N 种 CPU 架构，若每种组合都单独写编译器，要 M×N 个；前后端以 IR 为界分开后，只需 M 个前端 + N 个后端。LLVM 就是把这个结构做成了公共基础设施——Clang、rustc、swiftc 共用同一个中端与后端，新语言只需写前端。

补一段 C 系特有的前奏：C/C++ 的编译在三段流水线之前还有**预处理**——`#include` 把头文件原文嵌入、`#define` 做纯文本替换。宏不认识语法、语法不认识宏，两层各自只做文本拼接——很多诡异编译错误（宏展开的优先级事故、重复包含）的来源就是这一层。它不属于三段中的任何一段，是 C 祖先传下来的独立一层。

## 解释器的形态谱系

解释不是只有一种做法。同一份源码语义，兑现速度按实现形态排成阶梯：

1. **树遍历解释器**：直接在 AST 上边走边执行。最慢——同一个循环体的语法树每轮都重新走一遍。教学实现和早期 Ruby（1.8 及以前）是这种。
2. **字节码虚拟机**：先把源码编译成一套紧凑的**字节码**（自定义的低级指令集），VM 主体就是一个循环：取一条字节码、译码、执行——与 CPU 的取指-执行循环同构，只是指令集是软件定义的。Python 的 `.pyc`、Java 的 `.class` 都是字节码。比树遍历快一个台阶：语法分析的功只付一次，执行循环紧凑且缓存友好。
3. **JIT（即时编译）**：VM 监视执行，把反复命中的热点字节码**在运行中编译成机器码**，之后热点路径不再经过解释循环。这是 03-运行时与虚拟机 的主题。

账本的对比（约束：翻译时机决定三件事）：

| | 编译（AOT） | 解释（字节码 VM） | JIT |
|---|---|---|---|
| 启动速度 | 即启即巅峰 | 快（VM 现成） | 慢热（热点要先攒） |
| 峰值性能 | 高 | 低——纯解释的 CPython 密集循环比 C 慢一到两个数量级（典型负载的量级估计） | 可逼近甚至追平 AOT（握有运行时真实信息） |
| 跨平台 | 二进制绑定目标架构 | 源码/字节码随处跑，只要有 VM | 同左 |

账本里"二进制绑定目标架构"的出口是**交叉编译**：在 x86 开发机上用 ARM 后端编出 ARM 二进制——嵌入式开发与发布的常态，三段结构里换的只是后端。

现实世界的收敛结果是：主流"解释型"语言的实现几乎全是**字节码 VM + JIT**（JVM、V8、LuaJIT、PyPy）。CPython 是主流中的例外——长期纯解释，直到 3.13（2024 年）才引入实验性 JIT。

## 另一根轴：类型检查的时机

"编译型=静态类型、解释型=动态类型"是同一系列的第二个错觉。两根轴其实正交：

- **编译 / 解释**：语义何时兑现成机器行为（本篇主线）；
- **静态 / 动态类型**：类型检查在编译期还是运行期做。静态（C、Java、Go）把类型错误拦在编译期，代价是写类型注解；动态（Python、JS）在运行期逐次检查，代价是错误推迟到撞上才爆。

四种组合都真实存在：C 是静态+编译，Java 是静态+JIT，Python 是动态+解释，TypeScript 是"静态检查 + 编译成动态语言"——类型注解在编译后全部擦除，运行期零成本也零保护，类型只是开发期的脚手架。两根轴回答的是两个不同问题：一根是性能账，一根是"错误多晚暴露"的账。

## 编译器与解释器之外：混合与边界

两条路线之间没有墙，只有光谱：

- **编译到字节码再解释**（Java、Python）：编译器的前端照用，只是后端的目标从机器码换成字节码——编译与解释在同一实现里接力。
- **AOT 与 JIT 混合**：Android 的 ART 把编译时机挪到安装时、再用运行时画像回炉优化（《系统软件层》08 篇展开过）；JVM 默认分层编译，解释器、快速编译器、深度优化编译器同时在岗。
- 甚至 C 也能"解释"：TinyCC 的 `tcc -run` 编译进内存直接执行，模糊了编译与运行的界限。

记住主线即可：**所有实现都在回答同一个问题——翻译的功，什么时候付、付几次**。时机越晚，信息越多（看到真实输入与热点）、重复付费越多；时机越早，一次付费终身受益、却丧失了运行时信息。下一篇看编译产物如何装订成进程；03 篇再看运行中的垫付服务。
