# 运行时与虚拟机

## 核心定义：进程之内，语言垫付的服务层

02 篇把程序装进了进程，但对 Java、Python、JavaScript、Go 这些语言，进程里不止有你的代码——还有一层语言实现垫付的**运行时（Runtime）**：程序运行期间持续提供服务的软件层，负责机器码不肯自己做的事。典型的垫付项目：

- **内存回收（GC）**：对象死了自动收尸（本篇重头）；
- **即时编译（JIT）**：运行中把热点代码升级为机器码（本篇重头）；
- 异常沿栈展开、反射、协程/线程调度（Go 的 goroutine 调度器就是运行时里的一台小型 OS 调度器）。

**虚拟机（Virtual Machine，VM）** 是运行时的重形态：不止垫付服务，还隔着一套字节码指令集模拟出一整台抽象机器——程序面对的"CPU"是软件。主要 VM 的谱系与定位：

| VM | 服务语言 | 特点 |
|----|---------|------|
| JVM | Java、Kotlin、Scala | 工业级 JIT 与 GC 的试验场，本篇多数机制的出处 |
| CLR | C# 等 .NET 语言 | 与 JVM 同代同构（微软系） |
| V8 | JavaScript | JIT 激进程度最高（ JS 类型太动态，不激进就慢） |
| CPython | Python | 主流中的异类：长期只有字节码解释，3.13 才引入实验性 JIT |
| BEAM | Erlang、Elixir | 为容错与软实时设计：每进程独立堆、抢占式调度 |

清单里其余垫付项各给一句位置注解：**异常**沿栈展开——抛出时运行时按调用栈逐帧查异常表找 handler，成本集中在抛出瞬间（"进 try 免费、抛一次很贵"）；**反射**——类与方法元数据随字节码常驻内存，运行期可查可调，代价是绕过编译期检查、并挡住 JIT 的部分优化；**协程调度**已在《系统软件层》03 的协程一节展开。

## JIT：运行中升级引擎

**约束**：纯解释慢（01 的账），全量 AOT 又有两个损失——拖慢启动（全部代码先编译才能跑）、丢失运行时信息（编译期不知道哪个分支真热、虚调用实际落在哪个实现）。JIT 的回答：**先解释着跑，用真实运行数据指导编译**。

以 JVM 的分层编译为例（V8 的 Ignition→TurboFan 同构）：

```text
字节码 → 解释器直接执行（启动零等待）
       → 方法/循环被计数器标记为热点（调用次数、回边次数越阈）
       → C1 编译器快速编译（轻优化，先解决"别解释"）
       → 继续变热 → C2 编译器深度优化（激进内联、逃逸分析、
         边界检查消除、循环展开）
```

清单里的**逃逸分析**值得单看：JIT 跟踪每个对象的作用范围，若一个对象从没逃出创建它的方法（没存进堆、没传给未知代码），就**不在堆上分配**——直接在栈上展开，甚至把字段拆成独立局部变量（标量替换）。栈上分配随方法返回自动消失，连 GC 都不惊动。"对象一定在堆上"是错觉，JIT 的第一刀就是消灭不必要的堆分配。

C2 的激进建立在**推测**上：比如把虚调用内联的前提是"到目前为止只见过来一种实现"。推测可能明天就失效（新加载的子类出现了），所以 JIT 必须配一条退路——**去优化（Deoptimization）**：假设失效时，把执行状态从优化后的机器码无缝搬回解释器，该次调用按保守路径重走。JIT 敢做 AOT 不敢做的优化，全靠这条退路兜底。

## GC：自动内存回收

**约束**：手动内存管理（C 的 `malloc/free`）有两类结构性灾难——悬垂指针（释放后使用，安全漏洞的头号来源）与内存泄漏（忘记释放，长跑服务缓慢失血）。自动回收用运行时开销一次性买断这两类错误。

**根基算法：可达性分析。** 从 GC Roots（栈上的局部变量、寄存器、静态/全局变量）出发沿引用遍历，走得到的对象是活的，走不到的回收。引用计数（Python 用它做主机制）解决不了循环引用，主流 VM 都以可达性为根。

**分代假说（Weak Generational Hypothesis）**：绝大多数对象朝生夕死——这是经验观察而非物理定律，但在绝大多数业务负载上成立。堆因此分代：

- **新生代**：新对象出生地，空间小、回收频繁（Minor GC）。用复制算法：活对象少，把活对象复制到幸存区、旧区整个抛弃——回收成本与活对象数成正比，而非堆大小。
- **老年代**：熬过若干轮 Minor GC 的对象晋升来此，回收稀少（Major GC）。用标记-清除-压缩：不挪窝会碎片化，压缩则要移动对象。

分代引入一个记账问题：Minor GC 时怎么知道老年代哪些对象引用了新生代？全局扫描就白费了分代。**写屏障（Write Barrier）**在每次写引用时顺手记一笔（卡表/记忆集），把这笔账摊到每次写操作里，回收时只查账本。所有现代 GC 的复杂度，一大半都花在写屏障这类"记账"上。

写屏障还有第二个记账用途。**并发标记**（CMS/G1/Go 都在用）的算法根基是**三色标记**：对象分白（未访问）、灰（已访问但引用未扫完）、黑（已扫完），不变式是"黑对象不指向白对象"。应用与标记并发运行时，引用改写可能打破这个不变式——写屏障把这类改写记下来，防止活对象被漏标成垃圾。记不全的代价是**浮动垃圾**（这轮漏收的死对象下轮再收，无害）；漏标的代价是事故（活对象被回收）——所以写屏障一条都不能少。

**停顿（STW，Stop-The-World）**是 GC 的主要代价：某些阶段必须暂停所有应用线程，否则标记着标记着引用关系又变了。收集器的演进史只有一个方向——压缩停顿：

```text
串行收集 → 并行收集（多线程一起 STW）
  → CMS：标记阶段与应用并发（STW 只剩首尾）
  → G1：堆切成数百个分区，按收益排序增量回收，停顿可设目标
  → ZGC / Shenandoah（JDK 15 起生产可用）：借助染色指针/读屏障
    把对象搬运也并发化，停顿压到亚毫秒级，且与堆大小解耦
```

Go 的运行时是同一方向的另一实例：并发三色标记 + 混合写屏障，STW 同样压到亚毫秒量级——GC 算法不同，约束相同。

最后破除一个误区："有 GC 就不会泄漏"不成立。可达性判活的语义是"你还拿着引用，它就活着"——无界增长的缓存、忘了注销的监听器、静态集合里越攒越多的对象，全都"活着"。GC 语言里的泄漏不是机制失效，而是引用的语义如此：释放的责任从"记得 free"变成了"记得放手"。

## 运行时的本质

把 JIT 与 GC 放在一起看，运行时的角色就清楚了：**它是程序与 OS 之间的一层"影子操作系统"**——OS 给进程发物理页（《系统软件层》04），运行时在进程内部再分配对象堆；OS 调度线程，Go 运行时再调度 goroutine；OS 给中断，运行时给异常。选语言时选的从来不只是语法，而是这一整套垫付服务的质量与账单。
