# 编译型与解释型语言

## 定义

**编译器将高级语言直译为机器码；解释器将高级语言逐句执行。前者空间换时间，后者时间换空间。**

$$
T_{编译} = T_{analysis} + T_{optimization} + T_{codegen} \quad \text{一次性代价}
$$

$$
T_{解释}(n) = n \cdot T_{per\_statement} \quad \text{随执行次数线性增长}
$$

## 数学模型

### 编译流程复杂度

<pre>
词法分析:    O(N)      — N为源码字符数
语法分析:    O(N)      — LL/LR_parser线性扫描
语义分析:    O(N)      — 符号表查找
中间优化:    O(N log N)— 数据流分析
代码生成:    O(N)      — 指令发射
─────────────────────────────
总计:        O(N log N)~O(N^2)  取决于优化强度
</pre>

### 解释执行开销模型

<pre>
解释开销 = 解析开销 + 分发开销 + 执行开销
         = O(1)每token × 解析 + 跳转表查找 × 执行
</pre>

### JIT编译阈值模型

<pre>
热点检测: 调用计数 + 循环回边计数 ≥ 阈值(默认1500)
       ↓
JIT编译触发 → 编译时间T_compile vs 解释时间T_interpret
       ↓
T_compile < k × T_interpret → 采用优化码
(k为JIT收益系数，通常k=100)
</pre>

## 数据流

### 编译型语言数据流

<pre>
source.c (文本)
    ↓ [词法分析] 字符流 → Token流
token stream
    ↓ [语法分析] Token → AST
AST (抽象语法树)
    ↓ [语义分析] + [类型检查]
修饰AST
    ↓ [生成中间表示 IR]
LLVM IR (平台无关SSA形式)
    ↓ [目标相关优化 Passes]
优化后IR
    ↓ [代码生成]
汇编文件 .s (文本)
    ↓ [汇编器]
目标文件 .o (二进制+符号表+重定位表)
    ↓ [链接器]
可执行文件 (ELF/PE/Mach-O)
    ↓ [加载器]
内存中执行 → CPU指令流
</pre>

### 解释型语言数据流

<pre>
source.py (文本)
    ↓ [Parser] 字符流 → Token流
Token流
    ↓ [Lexer/Parser] → AST
AST (抽象语法树)
    ↓ [Compiler] → Bytecode .pyc
字节码 (平台无关指令集)
    ↓ [VM解释器] 循环读取指令
执行循环: fetch → decode → execute → dispatch
    ↓
每条指令开销: 解释器分发 + 操作执行
</pre>

### 混合模型(字节码+ JIT)

<pre>
source.py → Parser → AST → Bytecode → VM解释执行
                                          ↓
                              热点检测(调用计数/回边计数)
                                          ↓
                              JIT编译器 → 本地机器码
                                          ↓
                              直接执行机器码(跳过解释)
</pre>

## 机制

### 为什么需要编译器

**约束条件**：
- CPU只懂二进制指令（机器码）
- 高级语言语法与机器指令存在语义鸿沟
- 不同CPU架构（x86/ARM/RISC-V）指令集不兼容

**违规后果**：
- 不编译：CPU无法理解源码，直接执行报错
- 跨平台编译错误：生成目标平台的机器码才能在其上运行

### 编译器前端（平台无关）

<pre>
源码 → 词法分析器 → Token序列
              ↓
        语法分析器 → AST
              ↓
        语义分析器 → 修饰AST
              ↓
        生成LLVM IR → 平台无关中间表示
</pre>

**设计原因**：前端负责语言语法和语义，与目标平台无关，复用于多后端

### 编译器后端（平台相关）

<pre>
LLVM IR
    ↓ [目标描述]
X86后端 / ARM后端 / RISC-V后端
    ↓ [指令选择 × 寄存器分配 × 指令调度]
机器码
</pre>

**设计原因**：同一IR可编译到不同平台，实现"一次前端，多平台输出"

### 链接机制

**静态链接**：
- 库代码在编译时合并进可执行文件
- 优点：部署简单，无外部依赖
- 缺点：可执行文件大，更新库需重编译

**动态链接**：
- 库代码在运行时加载
- 优点：可执行文件小，多进程共享同一库实例
- 缺点：运行时需存在目标库，存在DLL地狱问题

**违规后果**：
- 静态链接缺失库：链接器报错"undefined reference"
- 动态链接缺失库：运行时报错"cannot find library"

### 解释器设计

**REPL循环**：

<pre>
REPL:
    READ    → 读取一行源码
    EVAL    → 执行（解释）
    PRINT   → 输出结果
    LOOP    → 返回READ
</pre>

**字节码虚拟机**：

<pre>
指令格式: [opcode][operand1][operand2]...
解释执行循环:
    PC = 0
    while running:
        instr = bytecode[PC]
        switch opcode:
            case LOAD: push(arg)        ; PC++
            case ADD:   b=pop(); a=pop(); push(a+b); PC++
            case CALL:  push(PC+1); PC=arg ;跳转
            case RET:   PC=pop()         ;返回
</pre>

**违规后果**：
- 解释执行性能差：每条指令都有解释分发开销
- 纯解释无优化：无法利用运行时类型信息优化

### JIT编译机制

**触发条件**：
- 方法调用计数 ≥ CompileThreshold（默认1500）
- 循环回边计数触发OSR（On-Stack Replacement）

**优化决策**：

<pre>
热点代码片段
    ↓
猜测优化（Speculative Optimization）
    ↓
类型特化 / 内联 / 逃逸分析
    ↓
生成优化机器码
    ↓
假设检验：类型变化/分支跳出 → 去优化 → 回退字节码
</pre>

## 参考存根

### GCC四步编译（≤20行）

```bash
gcc -E source.c -o source.i  # 预处理
gcc -S source.i -o source.s   # 编译为汇编
gcc -c source.s -o source.o  # 汇编为目标文件
gcc source.o -o program      # 链接为可执行文件
```

### Python字节码解释器（≤20行）

```python
BYTECODES = {'LOAD': 1, 'ADD': 2, 'RETURN': 3}
def vm(bytecode):
    stack, pc = [], 0
    while pc < len(bytecode):
        op = bytecode[pc]
        if op == 1: stack.append(bytecode[pc+1]); pc += 2
        elif op == 2: b, a = stack.pop(), stack.pop(); stack.append(a+b); pc += 1
        elif op == 3: return stack.pop()
```
