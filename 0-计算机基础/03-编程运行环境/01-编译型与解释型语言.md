# 编译型与解释型语言

## 定义

编译型语言在**构建时（build time）**将源码完整地转换为目标机器码，后续执行无需再次转换；解释型语言在**运行时（runtime）**逐句读取源码或中间表示并立即执行。两者本质是**语义转换时机**的不同——前者将转换代价前置到构建阶段，后者将转换代价分散到每次执行中。

$$
T_\text{总}(N, m) =
\begin{cases}
T_\text{编译}(N) + m \cdot T_\text{执行}(N) & \text{编译型} \\
m \cdot T_\text{解释}(N) & \text{解释型}
\end{cases}
$$

其中 $N$ 为源码规模，$m$ 为执行次数。当 $m \to \infty$ 时，编译型语言的均摊执行成本趋近于纯执行成本 $O(1)$，而解释型始终保持 $O(n)$ 的解释开销。

**归约终点**：两者最终都归约为 **CPU 指令流**，区别仅在于转换发生在何时代价最小。

## 数学模型

### 编译前端复杂度

词法分析和语法分析均为对源码的单次线性扫描：

$$
T_\text{frontend}(N) = O(N)
$$

其中 $N$ 为源码字符数。主流编译器的词法分析器由确定性有限自动机（DFA）驱动，语法分析器由 LL(1) 或 LR(1) 表驱动，均可在线性时间内完成。

**DFA 的形式化定义**：

$$
\delta: Q \times \Sigma \rightarrow Q
$$

其中 $Q$ 是有限状态集，$\Sigma$ 是输入字母表（源码字符集）。词法分析器从初始状态 $q_0$ 开始，对每个输入字符应用转移函数，直到到达接收状态（Token 边界）。

**LR(1) 分析表的构造复杂度**为 $O(|G| \cdot |L|)$，其中 $|G|$ 是产生式数量，$|L|$ 是文法符号数量。实际实现中通过核（kernel）和 closure 操作构造项目集族。

### 语义分析与类型检查复杂度

语义分析阶段的时间复杂度：

$$
T_\text{semantic}(N) = O(N \cdot D)
$$

其中 $D$ 为最大嵌套作用域深度。符号表的查找（基于哈希或红黑树）平均为 $O(1)$ 或 $O(\log n)$，但嵌套作用域链的最坏查找为 $O(D)$。

**约束**：类型检查必须覆盖所有使用点，确保不存在类型不匹配。函数调用的类型检查需要逐参数比对，且涉及泛型特化时复杂度进一步提升。

### 优化与代码生成复杂度

中间优化的复杂度取决于优化级别和数据流分析的迭代轮数：

$$
T_\text{优化}(N) = O(N \cdot I \cdot |E|)
$$

其中 $I$ 为数据流分析的迭代次数，$|E|$ 为控制流图边数。数据流分析在每个基本块上迭代，直到达到不动点（fixpoint），收敛速度取决于格结构的高度。

**SSA（静态单赋值）形式的变换复杂度**：

$$
T_\text{SSA}(N) = O(N \cdot \phi)
$$

其中 $\phi$（phi 函数）插入数量与控制流图中的合并节点数成正比。$\phi$ 函数用于合并来自不同前驱的基本块的值，是 SSA 形式的核心构造。

总编译时间为：

$$
T_\text{编译}(N) = O(N) + O(N \cdot I \cdot |E|) + O(N) = O(N \cdot I \cdot |E|)
$$

### 寄存器分配的 NP 完全性

寄存器分配将无限虚拟寄存器映射到有限物理寄存器：

$$
\text{虚拟寄存器} \xrightarrow{\text{分配}} \text{物理寄存器} \cup \{\text{spill}\}
$$

图着色问题（判断是否可用 $k$ 种颜色为图着色且相邻节点颜色不同）是 NP 完全的。实际编译器使用 Chaitin-Briggs 启发式算法：

**Chaitin-Briggs 算法步骤**：
1. 构建干涉图（interference graph）：若两个虚拟寄存器同时活跃，则它们干涉
2. 迭代移除：度数 < $k$ 的节点可安全着色后移除
3. 着色：按逆序重新插入，贪心分配颜色
4. 如遇 spill，在内存中分配 slot

**约束边界**：实际实现中，当虚拟寄存器数远大于物理寄存器数（如 > 128），spill 代价显著增加。每次 spill 访问需要 load/store 指令对，额外增加 $O(1)$ 内存访问。

### 链接器的本质：符号解析与地址重定位

链接是**全局符号表合并 + 地址重定位**的过程：

$$
\text{符号定义} + \text{符号引用} \xrightarrow{\text{重定位算法}} \text{确定地址}
$$

**重定位条目（relocation entry）**的形式化定义：

$$
r = (offset, type, symbol, addend)
$$

其中：
- `offset`：需要重定位的字节在对象文件中的偏移
- `type`：重定位类型（如 `R_X86_64_PC32` 表示 PC 相对 32 位寻址）
- `symbol`：被引用的符号
- `addend`：加到符号值上的常量

静态链接时所有符号地址在链接时确定，可执行文件完全自包含。动态链接通过 PLT（Procedure Linkage Table）和 GOT（Global Offset Table）实现延迟绑定：

$$
\text{call} \xrightarrow{PLT} \xrightarrow{GOT} \text{实际函数地址}
$$

首次调用时 GOT 指向 PLT 的 resolver thunk，resolver 确定地址后将 GOT 更新为实际地址，后续调用直接跳转到实际地址。

### 解释执行开销

解释执行的每条指令都经历「解码 → 分发 → 执行」三阶段：

$$
T_\text{解释}(n) = \sum_{i=1}^{n} \bigl( T_\text{decode}(i) + T_\text{dispatch}(i) + T_\text{execute}(i) \bigr)
$$

其中 $n$ 为执行的语句数。关键约束：**解码开销与指令复杂度正相关**——越简单的指令，解码开销在总时间中的占比越高。

**dispatch 开销的量化**：在字节码解释器中，每次 dispatch 需要：
1. 读取 opcode（1 字节）
2. switch 分支查找（跳转表 $O(1)$ 或二分 $O(\log n)$）
3. 读取操作数
4. 执行

对于 `a = b + c` 这样的表达式，解释型语言需要多次 dispatch（LOAD, LOAD, ADD, STORE），而编译型语言一条 ADD 指令完成。

### JIT 阈值模型

HotSpot JVM 的 JIT 触发条件基于热度计数：

$$
\text{invocation\_count} + \text{backedge\_count} \times \beta \geq J \quad (J = 1500)
$$

其中 $\beta > 1$ 是循环回边的权重（循环比函数调用更易形成热点）。

**投机优化的收益判定**：

$$
\text{若 } T_\text{JIT} < k \cdot T_\text{interpreted} \quad (k \approx 100) \rightarrow \text{采用优化码}
$$

即 JIT 编译耗时若小于解释执行耗时的 $1/k$，则编译投资划算。当函数执行频率不够高时，JIT 编译的成本反而超过收益。

### 编译型 vs 解释型 均摊复杂度

| 指标 | 编译型 (C/Golang) | 解释型 (Python/JS) | 字节码+JIT (Java/Node) |
|------|-------------------|-------------------|----------------------|
| 构建开销 | $O(N \cdot I \cdot |E|)$ 一次性 | 零（无构建阶段） | $O(N)$ 类加载 + 可选 JIT |
| 单次执行 | $O(N_\text{机器码})$ | $O(n \cdot T_\text{decode})$ | $O(n \cdot T_\text{decode} + T_\text{JIT})$ |
| $m$ 次均摊 | $O(1)$ 热点路径 | $O(n \cdot T_\text{decode})$ | $O(1)$ 热点路径 |
| 启动延迟 | 链接/加载 $O(N)$ | 零 | 类加载 $O(N)$ |

## 数据流

### 编译型语言数据流

<pre>
source.c (文本字符流)
    │
    ▼ [词法分析器 — 确定性有限自动机 (DFA)]
Token 流 [type, lexeme, line, column]
    │
    ▼ [语法分析器 — LL(1)/LR(1) 递归下降或表驱动]
AST (抽象语法树)
    │
    ▼ [语义分析器 — 符号表 + 类型检查 + 作用域解析]
修饰 AST (类型标注, 作用域绑定)
    │
    ▼ [前端/后端解耦接口]
中间表示 (LLVM IR / SPIR-V / MLIR)
    │
    ▼ [目标无关优化 — SSA 形式, 循环优化, 死代码消除, 内联]
优化后 IR
    │
    ▼ [目标相关代码生成 — 指令选择 + 寄存器分配 + 指令调度]
汇编文件 .s (文本)
    │
    ▼ [汇编器]
目标文件 .o (二进制 + 符号表 + 重定位表)
    │
    ▼ [链接器 — 符号解析 + 地址重定向 + 库合并]
可执行文件 (ELF/PE/Mach-O)
    │
    ▼ [OS 加载器 — execve / CreateProcess]
进程内存布局 [代码段, 数据段, 堆, 栈]
    │
    ▼ [CPU 执行 — 取指/译码/执行流水线]
指令流水线
</pre>

**数据形态变换**：字符流 → Token 流 → 树结构 → 线性 IR → 二进制指令。每一步都丢失了源码级别的语义抽象（如作用域、类型），仅保留执行所需的最少信息。

**所有权流转**：
- 编译器持有源码文本（只读）
- Token 流由词法分析器生成，语法分析器消费
- AST 由语义分析器修饰，代码生成器消费
- 目标文件由链接器合并，操作系统加载器消费

### 解释型语言数据流

<pre>
source.py (文本字符流)
    │
    ▼ [词法分析]
Token 流
    │
    ▼ [语法分析]
AST (与编译型相同结构)
    │
    ▼ [解释器遍历 或 字节码编译]
字节码序列 [opcode, operand1, operand2, ...]
    │
    ▼ [VM 主循环 — fetch/decode/dispatch/execute]
while (PC < len(bytecode)):
    instr = bytecode[PC]
    switch (opcode):
        LOAD  → push(argument)
        ADD   → b=pop(); a=pop(); push(a+b)
        CALL  → push(PC+1); PC=arg
        RET   → PC=pop()
```

**关键差异**：每次执行都重复「字符 → Token → AST → 字节码 → dispatch」的全流程，无法被均摊。

**解释器与直接执行的区别**：

| 维度 | 直接执行 | 解释执行 |
|------|----------|----------|
| fetch | CPU 取指 | 从字节码数组读取 opcode |
| decode | CPU 译码单元 | switch 分支查找 |
| dispatch | CPU 控制单元 | 解释器主循环 |
| execute | ALU 执行 | 解释器函数调用 |

解释器实际上是在宿主语言的"CPU"上模拟目标语言，每条字节码指令都需要多次宿主语言函数调用。

### 混合模型（字节码 + JIT）

<pre>
source.py / source.java
    │
    ▼ [前端 — 平台无关]
AST
    │
    ▼ [字节码生成]
平台无关字节码 (.pyc / .class)
    │
    ├──────────────────────────────┐
    ▼                              ▼
解释器执行                    热点检测
(启动阶段)                  (调用计数 ≥ 阈值)
    │                              │
    │                         JIT 编译器
    │                              │
    │                         类型反馈收集
    │                              │
    │                         投机优化 (Speculative)
    │                              │
    │                         类型特化 / 内联 / 逃逸分析
    │                              │
    │                         生成优化机器码
    │                              │
    └──────────────────────────────┘
                │
                ▼
         执行引擎选择
    (字节码解释 或 优化机器码)
                │
                ▼
         类型反馈失败 → 去优化 → 回退字节码
</pre>

**去优化（Deoptimization）的触发条件**：
- 类型反馈变化：JIT 假设某处类型为 int，但实际出现 float
- 隐藏类变化：JavaScript 对象添加新属性导致形状改变
- 调用计数器溢出：热点函数被调用次数超出阈值

**去优化的代价分解**：
1. 丢弃优化机器码（~微秒级）
2. 恢复字节码解释执行（~微秒级）
3. 重置类型反馈（~微秒级）
4. 重新积累热点信息（~数十毫秒）

## 机制

### 为什么编译型语言是「以空间换时间」

**约束条件**：CPU 只执行二进制机器码，高级语言的抽象语义（函数调用、对象、闭包）在硬件层面不存在。

编译器必须在编译时将所有语义信息编码进机器码：

- **函数调用约定**：参数通过寄存器（rdi, rsi, rdx, ...）或栈传递，返回值通过 rax 返回。调用者将被调用者保存的寄存器压栈，被调用者负责恢复。调用约定（cdecl, stdcall, fastcall）的差异是 ABI 兼容性的核心。
- **闭包捕获**：堆上分配捕获变量，生成间接访问代码（指向堆对象的指针）。闭包的实质是「代码指针 + 环境指针」的对偶体。
- **虚函数表**：运行时多态通过 vtable 查表实现，每个对象隐含一个指向其类 vtable 的指针。虚调用需要：读取对象头 → 获取 vtable 指针 → 读取 vtable 中函数指针 → 间接跳转。

**违规后果**：
- 不编译：CPU 无法解释源码字节流。
- 跨平台：x86 机器码在 ARM 上触发 SIGILL（非法指令），或产生 SIGBUS/SIGSEGV。
- 语义丢失：编译器 bug 导致未定义行为（undefined behavior），如越过数组边界后编译器假设「不会发生」而删除边界检查。

### 前端与后端解耦的原理

编译器前端负责**语义完整转换**，后端负责**目标代码生成**：

$$
\text{Source} \xrightarrow{\text{前端}} \text{IR} \xrightarrow{\text{后端}} \text{MachineCode}_{target}
$$

这一分解使同一语言前端可连接多个后端（如 GCC 支持 x86、ARM、RISC-V 等）。

**前端的必须任务**：
- 歧义消除：C++ 的 `a*b` 可能是乘法或指针解引用，必须结合类型信息解决
- 作用域解析：同名变量在内外层作用域的区分
- 类型推导：泛型实例化、重载决策

**约束**：前端必须捕获语言的**全部语义**，任何遗漏都会导致生成的代码行为与源码不符。

**违规后果**：语义错误 → 编译错误（type error, undefined reference, ambiguous overload resolution）。

### 寄存器溢出的性能影响

寄存器溢出（spill）发生时：

$$
T_\text{执行} = T_\text{原操作}} + T_\text{load} + T_\text{store}
$$

当寄存器 $r$ 被 spill 时：
1. 使用 $r$ 前：load $r$ from memory（额外的内存读取）
2. 使用 $r$ 后：store $r$ to memory（额外的内存写入）

**约束**：溢出代价与溢出变量的访问频率成正比。热点循环中的寄存器溢出可能导致显著性能回退。

**启发式决策**：编译器在寄存器分配时计算每个虚拟寄存器的"spill cost"：

$$
\text{spill\_cost}(v) = \sum_{\text{基本块 } b \in \text{活跃区间}(v)} \text{frequency}(b)
$$

频率高的基本块中的活跃变量 spill cost 高，应优先分配物理寄存器。

### 链接的三大问题

**1. 符号解析的歧义**：

当多个编译单元定义同名符号时：
- 强符号（已初始化）：只能定义一次
- 弱符号（未初始化）：可被强符号覆盖

**违反后果**：多个强符号定义 → 链接错误 `multiple definition of 'symbol'`

**2. 地址重定位的时机**：

| 类型 | 重定位时机 | 例子 |
|------|------------|------|
| 绝对地址 | 链接时确定 | 全局变量地址 |
| PC 相对地址 | 链接时确定 | x86 的 `call rel32` |
| GOT 索引 | 加载时确定 | 动态库的函数引用 |

**3. 库依赖的循环**：

静态库（.a）中各目标文件之间的依赖关系可能形成环。链接器通过拓扑排序决定成员的包含顺序。

### 解释执行的本质约束

解释器在**每次执行**时重新完成编译型语言在**编译时**完成的工作：

$$
\text{源码} \xrightarrow{\text{运行时}} \text{Token} \xrightarrow{\text{运行时}} \text{AST} \xrightarrow{\text{运行时}} \text{执行}
$$

这意味着每条指令都有**分发开销**（decode + dispatch），且该开销无法被均摊——每次执行都完整经历整个流程。

**约束**：解释器无法在执行前获知运行时类型信息，所有类型检查必须推迟到执行时进行。这是 Python `TypeError` 在运行时而非编译时抛出的本质原因。

**违规后果**：
- 性能差距：解释执行通常比编译执行慢 10-100 倍（JavaScriptCore/V8 的 Ignition 解释器实测）。
- 类型错误延迟到运行时：运行时 `TypeError` 而非编译时报错，增加调试成本。
- 动态特性（`eval`）阻止静态优化：编译器无法假设 `eval` 不会修改代码或作用域。

### JIT 编译的投机优化机制

JIT 在运行时收集**类型反馈**（Type Feedback），基于历史信息做**投机优化**：

$$
\text{热点函数}(x_1, x_2, \ldots) \xrightarrow{\text{历史类型}} \text{假设 } \phi(x_1) = \text{int}, \phi(x_2) = \text{ptr}
$$

**投机优化的常见形式**：

| 优化 | 投机假设 | 验证条件 |
|------|----------|----------|
| 类型特化 | 参数类型固定 | 类型不变量检查 |
| 单态内联 | 调用目标是唯一实现 | 类层次不变 |
| 边界检查消除 | 数组访问索引在范围内 | index 变量不变量 |
| 锁粗化 | 锁的持有者不变化 | 锁对象的 identity 不变 |

若假设成立：优化代码以接近原生速度执行（类型特化消除了装箱/检查开销）。
若假设失败：**去优化**（Deoptimization）回退到解释执行，损失约 10-100ms（重新编译 + 重置优化状态）。

**约束**：JIT 优化是**概率性的**，基于历史数据。错误的假设（类型不稳定、隐藏类变化）导致性能回退。

**违规后果**：
- 频繁去优化：热点代码反复在 JIT 和 Deopt 间切换，性能反而不如纯解释执行。
- 类型不稳定：同一位置反复出现不同类型，JIT 放弃优化（sunspoint 触发），此后该函数始终以解释或轻量编译模式执行。

### 编译型与解释型的归约对照

| 层次 | 编译型 | 解释型 |
|------|--------|--------|
| 源码 | `a = b + c` | `a = b + c` |
| 词法/语法 | 构建时完成 | 运行时每次完成 |
| 语义表示 | 机器码（指令+操作数） | AST / 字节码 |
| 执行 | CPU 直接执行 | VM dispatch loop |
| 最终归约 | **硬件指令流** | **硬件指令流**（由 VM 发出） |

两者在 CPU 指令流层面完全等价，差异仅在于转换时机和是否可被均摊。

### GCC 四步手动编译

```bash
gcc -E source.c -o source.i  # 预处理: 宏展开, #include 头文件嵌入
gcc -S source.i -o source.s   # 编译: 源码 → 汇编 (生成 .s 文本文件)
gcc -c source.s -o source.o   # 汇编: 汇编 → 目标文件 (.o 二进制)
gcc source.o -o program       # 链接: 目标文件 + 库 → 可执行文件
```

### 简单字节码 VM

```python
OPS = {'LOAD': 1, 'ADD': 2, 'STORE': 3, 'RETURN': 4}

def vm(bytecode):
    stack, pc = [], 0
    while pc < len(bytecode):
        op = bytecode[pc]
        if op == 1:          # LOAD constant
            stack.append(bytecode[pc + 1])
            pc += 2
        elif op == 2:        # ADD
            b, a = stack.pop(), stack.pop()
            stack.append(a + b)
            pc += 1
        elif op == 3:        # STORE variable
            var_idx = bytecode[pc + 1]
            pc += 2
        elif op == 4:        # RETURN
            return stack[-1] if stack else None
```
