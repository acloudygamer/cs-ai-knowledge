# 编译型与解释型语言

## 定义

编译器将高级语言直译为机器码，在**编译时**完成全部语义转换；解释器在**运行时**逐句读取源码或字节码并立即执行。前者以空间换时间（提前完成转换），后者以时间换空间（延迟到每次执行）。

$$
T_{编译} = T_{lexical} + T_{parse} + T_{semantic} + T_{optimize} + T_{codegen}
$$

$$
T_{解释}(n) = n \cdot T_{per\_statement} + T_{startup}
$$

## 数学模型

### 编译复杂度

设源码字符数为 $N$，词法分析和语法分析均为线性扫描：

$$
T_{frontend} = O(N) \quad \text{(LL/LR 线性扫描)}
$$

中间优化的复杂度取决于优化级别：

$$
T_{optimize} = O(N \cdot \log N) \sim O(N^2) \quad \text{(数据流迭代)}
$$

总编译代价是一次性 $O(N \log N)$，单次执行被均摊：

$$
\bar{T}_{编译}(N, m) = \frac{O(N \log N) + m \cdot O(N)}{m} \xrightarrow{m \to \infty} O(1)
$$

其中 $m$ 为执行次数。

### 解释执行开销

解释执行的每条指令都有**分发开销**——CPU必须先理解"要执行什么"，再执行：

$$
T_{解释}(n) = \sum_{i=1}^{n} (T_{decode}(i) + T_{execute}(i))
$$

解码代价与指令复杂度正相关，简单指令的解码开销占比更高。

### JIT 阈值模型

HotSpot JVM 的 JIT 触发条件：

$$
\text{invocation\_count} + \text{backedge\_count} \times \beta \geq J \quad (J = 1500)
$$

其中 $\beta$ 是循环回边的权重（热点循环更易触发）。

JIT 收益判定：

$$
\text{若 } T_{JIT} < k \cdot T_{interpreted} \quad (k \approx 100) \rightarrow \text{采用优化码}
$$

### 编译型 vs 解释型复杂度对比

| 指标 | 编译型 (C/Golang) | 解释型 (Python/JS) | 字节码+JIT (Java/Node) |
|------|-------------------|-------------------|----------------------|
| 启动开销 | $O(N)$ 链接 | $O(N)$ 解析 | $O(N)$ 类加载 + JIT |
| 单次执行 | $O(N)$ 机器码 | $O(n \cdot T_{decode})$ | $O(n \cdot T_{decode} + T_{JIT})$ |
| 多次执行均摊 | $O(1)$ | $O(n \cdot T_{decode})$ | $O(1)$ 热点路径 |
| 内存布局 | 直接机器码 | 源码/字节码驻留 | 类对象 + JIT 缓存 |

## 数据流

### 编译型语言数据流

<pre>
source.c (文本字符流)
    │
    ▼ [词法分析器 — 状态机驱动]
Token 流 [type, lexeme, line, column]
    │
    ▼ [语法分析器 — LL(1)/LR(1) 递归下降或表驱动]
AST (抽象语法树 — 树结构, 每个节点为语法构造)
    │
    ▼ [语义分析器 — 符号表 + 类型检查]
修饰 AST (类型标注, 作用域解析)
    │
    ▼ [IR 生成器]
中间表示 (LLVM IR / SPIR-V / MLIR)
    │
    ▼ [目标无关优化 Passes — SSA 形式, 循环优化, 死代码消除]
优化后 IR
    │
    ▼ [目标相关代码生成器 — 指令选择 + 寄存器分配 + 指令调度]
汇编文件 .s (文本)
    │
    ▼ [汇编器 — 生成目标文件]
目标文件 .o (二进制 + 符号表 + 重定位表)
    │
    ▼ [链接器 — 符号解析 + 地址重定向 + 库合并]
可执行文件 (ELF/PE/Mach-O)
    │
    ▼ [OS 加载器]
进程内存布局 [代码段, 数据段, 堆, 栈]
    │
    ▼ [CPU 执行]
指令流水线
</pre>

### 解释型语言数据流

<pre>
source.py (文本字符流)
    │
    ▼ [词法分析]
Token 流
    │
    ▼ [语法分析]
AST (与编译型相同结构)
    │
    ▼ [解释器遍历 AST 或编译为字节码]
字节码序列 [opcode, operand1, operand2, ...]
    │
    ▼ [VM 主循环]
while (PC < len(bytecode)):
    instr = bytecode[PC]
    switch (opcode):
        LOAD  → push(argument)
        ADD   → b=pop(); a=pop(); push(a+b)
        CALL  → push(PC+1); PC=arg
        RET   → PC=pop()
```

### 混合模型 (字节码 + JIT)

<pre>
source.py / source.java
    │
    ▼ [前端 — 平台无关]
AST
    │
    ▼ [字节码生成]
平台无关字节码 (.pyc / .class)
    │
    ├──────────────────────────────┐
    ▼                              ▼
解释器执行                    热点检测
(启动阶段)                  (调用计数 ≥ 阈值)
    │                              │
    │                         JIT 编译器
    │                              │
    │                         优化机器码
    │                              │
    └──────────────────────────────┘
                │
                ▼
         执行引擎选择
    (字节码解释 或 优化机器码)
                │
                ▼
         类型反馈失败 → 去优化 → 回退字节码
</pre>

## 机制

### 编译型为什么需要"空间换时间"

**约束条件**：CPU 只执行二进制机器码；高级语言的抽象语义（函数、对象、闭包）在机器层面不存在。

编译器必须将**编译时**的语义信息全部编码到机器码中：
- 函数调用约定：参数通过寄存器/栈传递，返回值通过特定寄存器返回
- 闭包捕获：堆上分配捕获变量，生成间接访问代码
- 虚函数表：运行时多态通过 vtable 查表实现

**违规后果**：
- 不编译：CPU 无法解释源码字节流
- 跨平台：x86 机器码在 ARM 上触发 SIGILL（非法指令）

### 编译器前端的职责边界

前端与后端解耦，使同一语言可编译到多个目标平台：

$$
\text{Source} \xrightarrow{\text{前端}} \text{IR} \xrightarrow{\text{后端}} \text{MachineCode}_{target}
$$

前端负责：**词法分析**（字符→Token）、**语法分析**（Token→AST）、**语义分析**（类型检查、作用域解析）、**生成平台无关 IR**。

**约束**：前端必须捕获语言的**全部语义**，包括歧义消除（如 C++ 的歧义表达式）。语法分析器无法处理的语言特性必须在语义分析阶段解决。

**违规后果**：语义分析失败 → 编译错误（type error, undefined reference）。前端的错误消息质量直接影响开发者体验。

### 编译器后端的职责边界

后端负责：**目标相关优化**、**指令选择**、**寄存器分配**、**指令调度**。

$$
\text{IR} \xrightarrow{\text{指令选择}} \text{伪汇编} \xrightarrow{\text{寄存器分配}} \text{物理寄存器} \xrightarrow{\text{指令调度}} \text{最终机器码}
$$

寄存器分配的复杂度：图着色问题是 NP-complete，实际使用 Chaitin-Briggs 等启发式算法。

**违规后果**：
- 寄存器分配失败：溢出到栈（spill），增加内存访问
- 指令调度冲突：数据 hazard 导致流水线停顿

### 链接器的本质

链接是**符号解析 + 地址重定位**的过程。编译单元各自维护符号表，链接时合并：

$$
\text{符号定义} + \text{符号引用} \xrightarrow{\text{重定位}} \text{确定地址}
$$

**静态链接**：所有符号地址在链接时确定，可执行文件独立部署。

**动态链接**：部分符号延迟到运行时解析（PLT/GOT 机制），运行时多个进程共享同一库实例。

**违规后果**：
- 静态链接缺失：链接器报错 `undefined reference to 'func'`
- 动态链接缺失：加载器报错 `cannot find library.so`

### 解释器的本质约束

解释器必须在**每次执行**时重新完成编译型语言在**编译时**完成的工作：

$$
\text{源码} \xrightarrow{\text{运行时}} \text{Token} \xrightarrow{\text{运行时}} \text{AST} \xrightarrow{\text{运行时}} \text{执行}
$$

每条指令都有分发开销（decode + dispatch），无法被均摊。

**约束**：解释器无法提前获知运行时类型信息，所有类型检查必须在执行时进行。

**违规后果**：
- 性能差距：解释执行通常比编译执行慢 10-100 倍
- 类型错误延迟：运行时才报错，而非编译时

### JIT 编译的投机优化

JIT 在运行时收集**类型反馈**（Type Feedback），基于历史信息做**投机优化**：

$$
\text{热点函数}(x_1, x_2, \ldots) \xrightarrow{\text{历史类型}} \text{假设 } \phi(x_1) = \text{int}, \phi(x_2) = \text{ptr}
$$

若假设成立：优化代码高速执行。
若假设失败：**去优化**（Deoptimization）回退到解释执行，损失 ~10-100ms。

**约束**：JIT 优化是**概率性**的，基于历史数据，错误的假设导致性能回退。

**违规后果**：
- 频繁去优化：热点代码反复 JIT/Deopt 循环，性能反而下降
- 类型不稳定：同一位置反复出现不同类型，JIT 放弃优化

## 参考存根

### GCC 四步编译

```bash
gcc -E source.c -o source.i  # 预处理: 宏展开, 头文件嵌入
gcc -S source.i -o source.s  # 编译: 源码 → 汇编
gcc -c source.s -o source.o  # 汇编: 汇编 → 目标文件
gcc source.o -o program       # 链接: 目标文件 + 库 → 可执行文件
```

### 简单字节码 VM

```python
OPS = {'LOAD': 1, 'ADD': 2, 'RETURN': 3}
def vm(bytecode):
    stack, pc = [], 0
    while pc < len(bytecode):
        op = bytecode[pc]
        if op == 1: stack.append(bytecode[pc+1]); pc += 2
        elif op == 2: b, a = stack.pop(), stack.pop(); stack.append(a+b); pc += 1
        elif op == 3: return stack.pop()
```
