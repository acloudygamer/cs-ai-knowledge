# 终端高级操作

> **版本基准**: universal

## 定义

终端多路复用器（Terminal Multiplexer）在单个终端进程内管理多个相互独立的会话（Session），通过分离控制终端与实际终端实现**会话持久化**：用户可以断开会话（detach）后重新连接（attach），会话内的进程树、屏幕状态和工作目录完整保留。tmux 和 screen 是两个主流实现，它们通过将终端模拟器的职责从用户进程转移到服务端守护进程，实现了会话与终端的生命周期分离。

## 数学模型

### 三级层级结构的状态空间

tmux 维护严格的三级嵌套层次结构，状态空间定义为：

$$
S_{\text{tmux}} = \left\{ \bigl(s_i,\ w_{i,j},\ p_{i,j,k}\bigr) \ \middle| \ i \in [0, N_s),\ j \in [0, N_{w_i}),\ k \in [0, N_{p_{i,j}}) \right\}
$$

其中：
- $N_s$ ：会话（Session）数量 ：会话（Session）数量
- $N_{w_i}$ ：会话 $i$ 中的窗口（Window）数量 ：会话 $i$ 中的窗口（Window）数量 中的窗口（Window）数量
- $N_{p_{i,j}}$ ：窗口 $j$ 中的面板（Pane）数量 ：窗口 $j$ 中的面板（Pane）数量 中的面板（Pane）数量

每个会话 $s_i$ 关联一个控制终端（Control Terminal），会话内所有窗口共享该控制终端的生命周期。 关联一个控制终端（Control Terminal），会话内所有窗口共享该控制终端的生命周期。

**screen 的两级结构**（无 Pane 概念）：
$$
S_{\text{screen}} = \left\{ \bigl(s_i,\ w_{i,j}\bigr) \ \middle| \ i \in [0, N_s),\ j \in [0, N_{w_i}) \right\}
$$

screen 的 "Region" 仅为视觉分割，不对应独立的 tty 设备。

### 会话持久化的触发条件

tmux server 将所有 Pane 的状态写入持久化存储的条件为：

$$
\text{持久化触发} \iff \text{detach} \lor \text{socket 异常断开} \lor \text{tmux server 重启}
$$

**tmux 的实时持久化机制**：
tmux server 内存中的状态变更不会实时写入磁盘。只有在以下时机才触发持久化：
1. `detach` 命令执行时
2. tmux server 进程被 kill 信号终止时（无 graceful detach）
3. socket 连接异常断开（检测到 client 失联）

**持久化文件格式**：
- 路径：`/tmp/tmux-$(uid)/`
- 格式：msgpack 二进制序列化
- 内容：每个 session 的完整状态（含窗口、面板布局、历史缓冲区）

**screen 的持久化机制**（更简陋）：
- 路径：`/var/run/screen/S-$USER/`
- 仅在显式 `hardcopy` 命令或会话终止时写入
- 恢复时需要重建会话状态，无法真正从快照恢复

### 同步面板的广播延迟模型

开启同步面板（`synchronize-panes on`）后，所有 Pane 接收完全相同的键盘输入，广播延迟为：

$$
T_{\text{broadcast}} = \underbrace{T_{\text{网络}}}_{\text{本地 } \approx 0} + \underbrace{T_{\text{tmux 处理}}}_{\text{命令解析 + 路由}} + \underbrace{T_{\text{终端渲染}}}_{\text{ANSI 解析 + 帧缓冲写入}}
$$

在本地 Unix socket 场景下：
$$
T_{\text{broadcast}} \approx O(1)\quad (\text{亚毫秒级，人类无法感知})
$$

在远程 SSH 场景下，延迟主要由网络 $T_{\text{网络}}$ 决定。 决定。

### SIGHUP 的传播衰减模型

tmux/screen 关闭会话时，会向会话内所有进程传播 SIGHUP 信号。信号传播具有**层级衰减特性**：

$$
\text{信号强度}_p = \begin{cases}
1.0 & \text{若 } p \text{ 直接绑定到 pane} \\
0.8 & \text{若 } p \text{ 是 pane 内进程的子进程（部分实现会忽略）} \\
0.0 & \text{若 } p \text{ 已设置 nohup 或捕获 SIGHUP}
\end{cases}
$$

tmux 的默认行为是向 pane 内所有进程发送 SIGHUP，但 **nohup** 或显式信号处理器可以阻断这一传播。

**SIGHUP 传播的层级顺序**：
```
tmux kill-session
    │
    ▼
遍历 session 内所有 window
    │
    ▼
遍历 window 内所有 pane
    │
    ▼
向 pane 的 PTY 写入 SIGHUP
    │
    ▼
Pane 内所有进程收到 SIGHUP（除非忽略或 nohup）
```

### Pane 布局的数学约束

tmux 的 pane 分割必须满足以下约束：

$$
\sum_{k} \text{width}(p_{i,j,k}) = \text{window\_width}
$$
$$
\sum_{k} \text{height}(p_{i,j,k}) = \text{window\_height}
$$

对于网格布局（tiled）：
$$
\forall p_{i,j,k}: \text{width}(p_{i,j,k}) \in \{ \lfloor \frac{W}{n} \rfloor, \lceil \frac{W}{n} \rceil \}
$$

其中 $W$ 是窗口宽度， $n$ 是水平 pane 数量。tmux 通过均匀分配实现相邻 pane 宽度差不超过 1。 是窗口宽度， $n$ 是水平 pane 数量。tmux 通过均匀分配实现相邻 pane 宽度差不超过 1。 是水平 pane 数量。tmux 通过均匀分配实现相邻 pane 宽度差不超过 1。

**Pane 分割的递归约束**：
- 水平分割后，两个子区域的宽度和等于父区域宽度
- 垂直分割后，两个子区域的高度和等于父区域高度
- 分割后的子区域可以继续分割（递归）

### 多 Client 窗口尺寸协商模型

当多个 client attach 同一会话时，每个 client 可能有不同的终端尺寸。tmux 的协商策略：

$$
\text{effective\_winsize} = \max_{\text{all clients}} (\text{client\_winsize})
$$

Server 维护所有 attached client 的窗口尺寸集合，向每个 pane 进程发送 `SIGWINCH` 时使用**最大尺寸**，确保所有 client 都能看到完整内容，但某些 client 的终端可能被裁剪。

**协商算法的形式化**：
$$
\forall \text{pane}: \text{SIGWINCH\_size} = \max_{c \in \text{clients}} (\min(c.\text{width}, W_{\text{pane}}), \max(c.\text{height}, H_{\text{pane}}))
$$

**约束**：如果某个 client 终端极小（如 80x24），而另一个是 4K 显示器，pane 进程会收到 4K 尺寸的 SIGWINCH，但小终端 client 的视图会被缩放。

## 机制

### tmux server 的生命周期与资源语义

tmux server 进程启动时创建 Unix domain socket 监听客户端连接：

```
tmux new -s session_name
        │
        ▼
socket("~/.tmux.socket/$TMUX_SOCKET", AF_UNIX) 创建
        │
        ▼
fork() → exec("tmux", "new-session", "-s", "session_name")
        │
        ▼
server 进程持有 socket fd，监听来自 client 的连接
        │
        ▼
client 通过 socket 发送命令，server 解析并执行
```

**关键约束**：tmux server 是常驻进程，kill 命令默认只终止 client 端：

| 命令 | 效果 |
|------|------|
| `kill`（在 session 内） | 仅终止当前 client 的 attach 会话 |
| `tmux kill-server` | 强制终止 server，所有会话立即丢失 |
| `tmux kill-session -t name` | 仅终止指定会话 |

**server 进程的孤儿收养**：
- 当 tmux server 的父进程退出时，server 成为孤儿进程
- 孤儿进程被 init (pid=1) 收养，但继续正常运行
- server 的生命周期独立于创建它的 Shell

**违规后果**：
- 不 detach 直接断连（网络中断）：会话继续在 server 中运行，但 client 无法交互
- `kill-server` 无确认提示：所有会话进程收到 SIGHUP，已输入未提交的数据永久丢失

### 窗口与面板的进程边界

tmux 的三级层次在进程视角上有明确的边界语义：

| 操作 | 影响范围 | 进程行为 |
|------|----------|----------|
| 关闭 Pane | 仅该 Pane | 该 Pane 的进程收到 SIGHUP |
| 关闭 Window | Window 内所有 Pane | Window 内所有进程收到 SIGHUP |
| 关闭 Session | Session 内所有 Window | 所有会话进程收到 SIGHUP |

**Pane → Window 的层级约束**：Pane 关闭后，Window 仍存活（如果还有至少 1 个 Pane）；Window 关闭后，Session 仍存活（如果还有至少 1 个 Window）。

**进程终止的层级传播**：
$$
\text{Pane 关闭} \Rightarrow \text{该 pane 的 shell 进程收到 SIGHUP}
$$
$$
\text{Window 关闭} \Rightarrow \text{该 window 的所有 pane shell 收到 SIGHUP}
$$
$$
\text{Session 关闭} \Rightarrow \text{该 session 的所有 window 的所有 pane shell 收到 SIGHUP}
$$

**违规后果**：
- 在有多个 Pane 的 Window 中误关一个 Pane：该 Pane 进程收到 SIGHUP 而终止，已输入但未处理的数据丢失
- 在多窗口 Session 中误关 Session：该 Session 内所有进程全部收到 SIGHUP，Session 无法恢复

### 复制模式的缓冲区语义

tmux/scrollback buffer 是 tmux 维护的**循环缓冲区**，大小由 `history-limit` 控制（默认 2000 行/Pane）：

```
Pane 输出行
        │
        ▼
写入循环缓冲区（固定大小，FIFO）
        │
        ├── 缓冲区满时：最旧的行被覆盖（丢弃）
        │
        └── Ctrl+b [ 进入复制模式
                    │
                    ▼
                copy-mode：只读遍历缓冲区
                    │
                    └── q 或 Escape 退出，恢复正常输入
```

**约束**：
- 复制模式是只读状态，所有键盘输入不传递给 Pane 内的进程
- 缓冲区满后旧行被丢弃，无法恢复
- `history-limit` 是 per-pane 设置，每个 Pane 有独立的滚动缓冲区

**缓冲区大小约束**：
$$
\forall \text{pane}: |\text{history}| \leq \text{history-limit}
$$

**违规后果**：长会话的早期输出会被自动裁剪，无法通过 tmux 复制模式检索。

### 同步面板的广播语义与风险

`synchronize-panes on` 命令改变 tmux 的输入路由：

```
正常模式：
  按键 → 当前活动 Pane → 该 Pane 进程

同步模式：
  按键 → 当前 Window 内所有 Pane（同时接收相同输入）
```

**路由算法的形式化**：
$$
\text{同步开启} \Rightarrow \forall \text{pane}_{i,j,k} \in \text{window}_{i,j}: \text{input}(\text{pane}_{i,j,k}) = \text{user\_input}
$$

**约束边界**：
- 同步仅对**同一 Window 内**的 Pane 生效，不同 Window 的 Pane 不受影响
- 同步开启后，单次按键会在所有 Pane 的 bash 历史中留下相同命令
- 如果某个 Pane 正在运行交互式程序（如 vim、less、top），同步输入会导致该程序接收来自多个 Pane 的命令，可能导致状态混乱

**违规后果**：
- 在同步模式下对 vim 输入 `:wq`：所有 Pane 中的 vim 都收到 `:wq`，可能意外退出
- 多个 Pane 都在运行交互式程序时，同步输入会导致非预期行为
- 同步模式下 `Ctrl+C` 会在所有 Pane 中发送 SIGINT，可能同时终止多个进程

### 会话命名与唯一性约束

tmux 会话名称在同一 tmux server 内必须唯一：

```
tmux new -s dev        # 创建名为 dev 的会话
tmux new -s dev        # 错误：会话已存在
tmux new -s dev2       # 正确：不同名称
tmux attach -t dev     # 附加到已存在的 dev 会话
```

**约束**：
- 会话名称在**同一 tmux server** 内唯一
- 不同 server（不同用户、不同 socket 路径）可以有同名会话
- attach 已存在的会话会创建新 client，多 client 共享同一会话状态
- 新 client 和已存在的 client 按连接顺序依次接收会话输出（串行共享）

**会话名称的数学约束**：
$$
\forall s_i, s_j \in \text{sessions}: i \neq j \Rightarrow s_i.\text{name} \neq s_j.\text{name}
$$

### tmux -CCC 协议的远程多 client 语义

tmux 支持通过 `-CCC` 协议进行远程连接（通过 TCP socket 而非 Unix socket）：

```
远程机器：
  tmux -CCC attach -t session   # 通过 TCP 连接

本地机器：
  tmux (server)                 # 监听 TCP 端口
```

**约束**：
- 远程连接时，所有 client 共享同一会话状态
- 各 client 的终端尺寸可能不同，server 按各 client 最新的 `TIOCSWINSZ` 更新 `winsize`
- 若 client 网络中断，server 会在检测到后自动 detach 该 client

**TCP vs Unix socket 的差异**：
| 属性 | Unix socket | TCP socket |
|------|-------------|------------|
| 适用场景 | 本地多 client | 远程连接 |
| 认证 | 文件系统权限 | 无（需额外配置） |
| 延迟 | 极低（内核上下文切换） | 受网络影响 |
| 多 client | 原生支持 | 原生支持 |

### 多 client 的终端尺寸协商

当多个 client attach 同一会话时，每个 client 可能有不同的终端尺寸。tmux 的协商策略：

$$
\text{effective\_winsize} = \max_{\text{all clients}} (\text{client\_winsize})
$$

Server 维护所有 attached client 的窗口尺寸集合，向每个 pane 进程发送 `SIGWINCH` 时使用**最大尺寸**，确保所有 client 都能看到完整内容，但某些 client 的终端可能被裁剪。

**约束**：如果某个 client 终端极小（如 80x24），而另一个是 4K 显示器，pane 进程会收到 4K 尺寸的 SIGWINCH，但小终端 client 的视图会被缩放。

**多 client 场景的典型问题**：
1. Client A (4K) 和 Client B (800x600) 同时 attach
2. pane 进程收到 4K 的 SIGWINCH
3. Client B 的视图被裁剪，只能看到左上角
4. tmux 不会为不同 client 提供不同的视图（无 viewport 概念）

## 对比参照

| 维度 | tmux | screen |
|------|------|--------|
| **会话持久化** | detach 时写入磁盘；server 重启时从磁盘恢复 | detach 时写入 hardcopy 文件；恢复时重建 |
| **状态存储格式** | msgpack 二进制文件 | screen 目录下的 hardcopy 文件（明文） |
| **层级结构** | Session → Window → Pane（三级） | Session → Window（两级，无 Pane） |
| **Pane 分割** | 水平 + 垂直均可 | 仅水平分割（Regions），无垂直分割 |
| **复制模式快捷键** | `Ctrl+b [` | `Ctrl+a [` |
| **配置语法** | `set -g option value` | `set option value`（全局需 `set -g`） |
| **远程支持** | `-CCC` TCP 协议（多 client 天然支持） | 仅本地 Unix socket |
| **命名管道支持** | 支持（通过 `#(shell-cmd)` 语法） | 有限支持 |
| **客户端数量** | 多 client 同时 attach 同一 session | 单 client |
| **Socket 位置** | `/tmp/tmux- $(uid)/default` | `/var/run/screen/S-$ USER/` |USER/` |
| **状态恢复能力** | 完整恢复（msgpack 包含所有状态） | 仅文本内容恢复（进程树丢失） |
| **Pane 数量** | 每个 pane 独立 tty | 无 pane，所有在同一 tty |

**归约对比**：

两者本质上都是 **终端模拟器的服务端化**——将原本由用户终端直接控制的伪终端生命周期，转移到一个独立的守护进程中管理。tmux 通过三级结构（Session/Window/Pane）提供了更细粒度的组织能力，而 screen 的两级结构更简单但功能也更少。

tmux 的 Pane 概念可归约为"带有独立 PID 命名空间的 ptys"，而 screen 的 Region 仅是视觉分割，不对应独立的 tty。

**msgpack vs hardcopy 的本质差异**：
- msgpack：自描述二进制格式，包含类型信息，可完整反序列化恢复
- hardcopy：纯文本转储，丢失了所有元数据（进程树、终端状态、工作目录）

## 参考存根

```bash
# 会话管理
tmux new -s session_name           # 创建命名会话
tmux new-session -d -s name         # 后台创建会话
tmux attach -t session_name         # 附加到已存在会话
tmux detach (Ctrl+b d)             # detach 当前会话
tmux kill-session -t session_name   # 终止指定会话

# 窗口管理
tmux new-window                    # 创建新窗口
tmux select-window -t :0           # 选择窗口 0
tmux kill-window -t session:1      # 关闭窗口 1

# Pane 分割
tmux splitw -h -p 50              # 水平分割当前 Pane，50% 宽度
tmux splitw -v -p 30              # 垂直分割当前 Pane，30% 高度
tmux select-layout tiled           # 排列所有 Pane 为平铺模式
tmux kill-pane -t session:0.1      # 关闭指定 Pane

# 同步输入
tmux setw synchronize-panes on    # 开启同步输入（所有 Pane 接收相同命令）
tmux setw synchronize-panes off   # 关闭同步输入

# 在 Pane 中发送命令（不交互）
tmux send-keys -t session:0.1 "ls -la" C-m  # 发送命令到指定 Pane

# 复制模式
Ctrl+b [                              # 进入复制模式
Space                                 # 开始选择
Enter                                 # 复制选择内容
Ctrl+b ]                              # 粘贴

# 多 client 场景
tmux list-clients                     # 列出所有 attached client
tmux resize-window -t session:0 -x 80 -y 24  # 强制设置窗口尺寸
```

# 附录：tmux 状态机的归约分析

tmux 的会话管理可归约为一个 **层次状态机（Hierarchical State Machine）**：

$$
M_{\text{tmux}} = \bigl( S_{\text{tmux}},\ \Sigma_{\text{tmux}},\ \delta_{\text{tmux}} \bigr)
$$

其中状态空间 $S_{\text{tmux}}$ 如上定义的层级笛卡尔积，事件空间 $\Sigma_{\text{tmux}}$ 包含： 如上定义的层级笛卡尔积，事件空间 $\Sigma_{\text{tmux}}$ 包含： 包含：
- 客户端事件：`client\_connect`, `client\_disconnect`, `client\_resize`
- Pane 事件：`pane\_close`, `pane\_split`
- Window 事件：`window\_create`, `window\_close`
- Session 事件：`session\_attach`, `session\_detach`, `session\_destroy`

该模型的**可验证性质**：
- **可达性**：给定任意会话配置，可通过有限步骤到达
- **活性**：只要 server 存活，所有 attach 的 client 都能接收会话状态
- **公平性**：多个 client 的命令按先来先服务顺序执行

**状态机的物理归约**：
- tmux server 归约为**状态数据库**（存储会话/窗口/pane 的层级结构）
- client 连接归约为**状态订阅**（订阅 server 的状态变更）
- pane 归约为**带缓冲的 I/O 通道**（连接到 pane 内进程的 PTY）
- SIGWINCH 归约为**异步事件通知**（不中断正在执行的进程）
