# 终端与伪终端

## 核心定义：一个字节流通道的历史与现状

今天的"终端"是一个纯软件概念，但它的名字和骨架来自一件真实的硬件：**电传打字机（Teletype，缩写 TTY）**——一台通过串口线连到主机的打字机，键盘敲出的字节顺着线送进主机，主机回送的字节驱动打印头。TTY 这个缩写因此成为 Unix 终端设备的永久代号：`/dev/tty`、tty 驱动、`stty` 命令，全是这台 1960 年代机器留下的化石。

**这是本部分反复出现的历史遗物级约束**：物理终端早已消失，但它定下的接口——一个双向字节流通道，外加"行编辑"和"控制字符"两条内嵌规矩——被完整保留下来，现代所有终端软件都在模拟它。

设备随后进化：VT100（DEC，1978）把打印机换成屏幕，并引入**转义序列**——在字节流里夹带"以 ESC 开头的约定字节串"来表示光标移动、清屏、颜色。显示控制和数据混在同一字节流里，靠约定字节区分。这套协议（ANSI/VT100 转义序列）至今是所有终端的显示语言。

## 伪终端（pty）：软件时代的通道

物理终端消失后，通道两端都变成了程序。**伪终端（Pseudo-Terminal，pty）**是内核提供的一对相连设备，完整复刻串口线的行为：

```text
┌─────────────┐   写字节    ┌──────────┐   读字节   ┌────────┐
│  终端模拟器   │ ◄────────► │ pty 对    │ ◄────────► │  shell  │
│（GUI 程序）  │            │ master/  │            │（普通   │
│ 键盘 → 字节  │            │ slave    │            │ 进程）   │
└─────────────┘            └──────────┘            └────────┘
       你看到的窗口          内核里的通道            /dev/pts/N
```

- **终端模拟器**（Windows Terminal、iTerm2、VS Code 集成终端）是 GUI 程序：把键盘事件变成字节写进 pty master，把从 master 读到的字节（含转义序列）渲染成屏幕上的字符。
- **shell**（bash/zsh）把 pty slave（`/dev/pts/N`）当作自己的标准输入输出——它完全不知道、也不需要知道另一端是 GUI 窗口还是一根真正的串口线。

同一个抽象解释三件看似不同的事：**ssh** 会话里，sshd 为每个登录分配 pty，通道另一端是网络那头的终端模拟器；**tmux/screen** 是自己再插一层 pty——对 outer 终端它扮演渲染客户端，对 inner shell 它扮演终端模拟器（这就是 tmux 里滚动历史由 tmux 而非终端模拟器提供的原因）；**`ssh -t`** 强制分配 pty——默认非交互命令不分配，而 `top`、`vim` 这类全屏程序没有 pty 就无法工作。

## 行规：谁在做行编辑

tty 驱动里有一个中间层叫**行规（line discipline）**，默认工作在**规范模式（canonical mode）**：内核替你攒行——回显你敲的字符、处理退格删除，直到回车才把整行交给读的进程。`cat` 不加参数运行时能直接退格改字，靠的就是它，cat 自己一行编辑代码都没有。

shell 交互时行为不同：bash 用 readline 库，把终端切到**原始模式（raw mode）**——行规关闭攒行和回显，每个按键字节立刻送达 shell，由 readline 自己做回显、删除、历史翻找、Tab 补全。所以"行编辑在哪做"取决于谁在听：规范模式在内核，raw 模式在读的那个程序（vim、less、top 全部如此）。

## Ctrl-C 的真相：信号是 tty 驱动发的

一个广泛存在的误解是"Ctrl-C 是 shell 拦截的快捷键"。真实机制在 tty 驱动里（规范模式和 raw 模式都可能开启）：

- 键盘敲下 Ctrl-C，字节 `0x03` 进入 pty；
- tty 驱动认出这个控制字符，**不把它交给读的进程**，而是向前台进程组（foreground process group，见 02 的作业控制）的每个成员发送 `SIGINT` 信号；
- 进程按 03-进程与线程 的信号机制处理：默认动作是终止。

同理：Ctrl-Z → `SIGTSTP`（暂停），Ctrl-\ → `SIGQUIT`（终止+core dump）。**Ctrl-D 例外**：它不是信号，是让行规把当前缓冲立即交付——空缓冲时 `read()` 返回 0，程序读到 EOF 自行退出。所以"Ctrl-D 退出 shell"是间接效果：EOF 而已。

由此可推一个可验证的推论：往管道里写 `\x03` 不会中断任何程序——没有 tty 驱动参与，字节就是字节。

## 通道断开怎么办：SIGHUP 与会话持久化

tty 驱动的信号职责不止按键转发：**通道本身断开时**（终端窗口被关、ssh 掉线），内核向会话里的进程发送 SIGHUP——默认动作是终止。这就是"ssh 一断，跑了一夜的任务没了"的完整机制：不是网络断了杀死进程，是通道死亡触发了信号。

对策分两层。`nohup` 是进程级的盾牌：让进程忽略 SIGHUP，输出重定向到文件。**tmux/screen 是结构级的解法**——前面说过它在你和 shell 之间再插一层 pty：shell 和任务连的是 tmux 持有的 pty，不是你那头的终端。你的 ssh 断了，断的只是"你 ↔ tmux"这一截，tmux 与任务毫发无损，下次 `tmux attach` 重新接上。这就是"会话持久化"的机制实质：把任务的宿主从你的连接，换成一个常驻的终端服务器。

## 转义序列与 isatty：终端感知

终端显示控制的全部魔法就是往输出流里写约定字节：`\x1b[31m` 之后的文字变红，`\x1b[2K` 清当前行，`\x1b[H` 光标回家。进度条、彩色日志、全屏界面（vim 的每一帧）都是这套字节协议。历史上海量终端型号能力各异，靠 `TERM` 环境变量 + terminfo 数据库查询"你这个终端的清屏序列是哪串字节"；今天终端模拟器基本收敛到 VT100 兼容集。

程序判断自己是否连着终端，用 `isatty(fd)` 系统调用探测。这解释了一个常见困惑：`ls` 直接运行有颜色、`ls | cat` 没有——`ls` 发现 stdout 不是 tty 就自动关闭着色；同理 `grep` 的高亮、很多命令的分页行为。**stdout 是 tty 还是管道，程序是知道的，行为会分叉**。
