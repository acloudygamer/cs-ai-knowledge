# 前缀树

存一百万个英文单词，哈希表查一个词是 $O(1)$ 期望；但要"列出所有以 pre 开头的词"，哈希表只能把一百万个键全部算一遍哈希再比较。前缀树把"前缀"变成一条路径：走到 pre 那个节点，它底下的整棵子树就是答案。

前缀树不优化单点查找，它优化的是"一次查询对应一族键"。代价从时间挪到了空间：每存一个字符，都要占一个节点。

## 一、把键的字符拆成路径

### 1. 每个节点代表一个前缀

前缀树的每条边带一个字符，从根走到某个节点，路径上的字符拼起来就是一个前缀。同节点的出边字符不重复，所以一个字符串在树里的路径唯一。

```text
        (根)
       /  |  \
      c   d   g
      |   |   |
      a   o   o
     / \  |   |
    t   r g   l
    |   | |   |
   (t)(r)(g)(l)
   cat car dog gol

cat、car 共享 "ca"，dog、gol 只在根上分叉
```

### 2. 查一个词就是沿字符下降

查找从根开始，按字符逐个选边。字符走完且节点被标记为词尾，命中；中途没有对应的边，或者走完却没被标记，未命中。

```python
def search(root, word):
    node = root
    for ch in word:
        if ch not in node.children:
            return False          # 路径断了，前缀不存在
        node = node.children[ch]
    return node.is_end            # 走完还要确认是词尾
```

代价是 $O(L)$， $L$ 是词长，与词库里有几个词无关。这一点与哈希表看似相同——哈希也是 $O(L)$ 算哈希——但前缀树在下降过程中额外得到了路径上所有前缀的信息，哈希表只得到一个桶号。

## 二、公共前缀只存一份

### 1. 节点数由不同前缀数决定

$n$ 个词、平均长度 $L$ 时，节点数的上界是 $nL$，实际取决于共享程度。一百万个随机 8 字符小写单词，前两三个字符高度重复，节点数大约是词数的五到六倍；如果词都很短、前缀又分散，节点数接近 $nL$。

共享发生在分叉之前：`cat`、`car`、`cart` 三个词共用 `ca` 这一段，只需存一次。

### 2. 字符集决定每个节点的宽度

每个节点要为"下一个字符有几种可能"准备槽位。26 个小写字母、每槽一个 8 B 指针时，一个节点的指针表是 208 B，而它只代表一个字符。

| 实现 | 每节点开销 | 一百万个词的粗略占用 | 适用 |
| --- | --- | --- | --- |
| 定长数组 | 字符集大小 × 8 B | 最大，随字符集线性增长 | 字符集小且固定 |
| 哈希表 | 表头 + 实际出边 | 中等 | 字符集大或稀疏 |
| 压缩边（radix） | 一段字符串 + 少量指针 | 最小 | 长键、前缀稀疏 |
| 双数组 | 每状态两个整数 | 小且访问快 | 静态词典 |

前两行的差距就是"空间换时间"的具体汇率：定长数组用 208 B 换一次数组下标访问，哈希表用几十字节换一次哈希计算。字符集越大，这笔兑换越不划算。

## 三、前缀查询是树的前序遍历

### 1. 一次下降定位，再遍历子树

前缀查询分两步：先按字符下降到前缀对应的节点，代价 $O(|p|)$；再从那棵子树里收集所有被标记为词尾的节点，代价与子树大小成正比。

```text
查前缀 "ca"：
  1. 下降到 c → a，路径存在
  2. 以该节点为根做深度优先遍历，收集 is_end 节点
  3. 得到 cat、car、cart
```

输出本身有代价： $k$ 个结果、平均长度 $L$ 时，至少要写 $kL$ 个字符。前缀树节省的是"找到这批结果"的代价，不能省掉"把结果交出去"的代价。

### 2. isEnd 把前缀与完整的词分开

没有词尾标记时，树无法区分"`car` 是一个词"和"`car` 只是 `cart` 的前缀"。标记放在节点上，一个节点可以既是词尾又是中间节点。

这条标记也决定了删除：删一个词不能直接删路径，因为它的前缀可能被别的词共用。正确做法是清除词尾标记，再自底向上删除没有子节点且不再是词尾的节点。

## 四、与哈希表的取舍

| 需求 | 前缀树 | 哈希表 |
| --- | --- | --- |
| 等值查找 | $O(L)$，常数随字符集与实现变化 | $O(L)$ 期望，常数更小 |
| 前缀查询 | 定位代价与前缀长度成正比，再遍历子树 | 必须扫描全部键 |
| 按字典序遍历 | 前序遍历即有序 | 无序，需另行排序 |
| 空间 | 与节点数成正比，共享前缀时省 | 与键数成正比，与长度弱相关 |
| 最坏情况 | 稳定 $O(L)$ | 哈希碰撞时退化 |

前两行把两者的分工划清楚了：只做等值查找时，哈希表的常数更小，没有理由用前缀树；一旦需要"按前缀找一族键"或"按字典序输出"，哈希表做不到，只能全表扫描再排序。

第三行常被忽略。前缀树的中序遍历天然给出字典序，哈希表给不出。搜索引擎的自动补全、路由表的最长前缀匹配、拼写检查的编辑距离剪枝，都建立在这条有序性上。

## 五、工程口径

### 1. 压缩边把单字符节点合并

朴素前缀树为每个字符建一个节点，长键稀疏时节点数爆炸。压缩前缀树（radix tree）把"只有一个子节点的连续路径"压成一条边，边上存一段字符串。

压缩之后，节点数从"字符总数"降到"分叉点数"，通常与词数同阶。查询仍是从根下降，只是每步比较一段字符串而不是一个字符。IP 路由表的最长前缀匹配用的就是这种结构。

### 2. 静态词典用双数组换访问速度

词典在构建后不再变动时，可以把树压成两个整数数组：一个记录状态的基址，一个记录转移的检查值。一次转移是一次数组下标计算加一次校验，比指针追逐快，也不需要为每个节点分配对象。

代价是构建复杂、难以动态更新。这条取舍与前缀树本身的结构无关，是"树形逻辑 + 数组布局"的又一次置换：逻辑不变，物理布局换成连续内存。
