# 编译配置与严格模式

> 前置：[07-声明文件与互操作](./07-声明文件与互操作.md) · 后续：[09-项目组织与增量编译](./09-项目组织与增量编译.md)

> **版本基准**：TypeScript 7.0.2（`tsgo`，编译器由 Go 重写）。本篇示例实测环境：Node v24.13.1，`npx typescript@latest`，Windows x64。

## 本质

`tsconfig.json` 是 TypeScript 编译行为的**唯一来源**——命令行参数只是对它的临时覆盖。它决定四件事：**检查多严**（`strict` 一族）、**产出什么**（`target` / `module` / `outDir`）、**检查哪些文件**（`include` / `exclude` / `files`），以及**如何解析模块**（`moduleResolution`）。

其中最需要专门理解的是 `strict`：它**不是一个检查，而是一组开关**。关掉它不等于"类型检查变弱一点"，而是若干类错误**完全不再报**。

**TypeScript 7 把 `strict` 改成了默认开启**——这是升级到 7 时最主要的破坏性变更。实测确认：

```console
$ npx typescript@latest --strict false --noEmit strict.ts   # 显式关闭
（无输出，通过）

$ npx typescript@latest --noEmit strict.ts                  # 不传任何参数
strict.ts(1,41): error TS18047: 's' is possibly 'null'.
strict.ts(4,11): error TS2564: Property 'name' has no initializer and is not definitely assigned in the constructor.
```

**不传 `--strict` 也报同样的错**——默认值就是开启。

## 机制

### TypeScript 7 的默认值变更

官方发布说明列出的默认值变化（`strict` 只是其中之一）：

| 选项 | TypeScript 7 默认 | 旧行为 |
|---|---|---|
| `strict` | **`true`** | `false` |
| `module` | `esnext` | 随 `target` 推断 |
| `target` | 紧邻 `esnext` 之前的稳定 ES 版本 | `es5` |
| `noUncheckedSideEffectImports` | `true` | `false` |
| `libReplacement` | `false` | `true` |
| `stableTypeOrdering` | `true`（不可关闭） | — |
| `rootDir` | `./` | 从输入文件推断 |
| `types` | `[]`（不再自动加载 `@types`） | `["*"]` |

默认 `target` 提升的直接影响是**产物不再降级现代语法**：

```console
$ npx typescript@latest tgt2.ts --outDir outT2 && cat outT2/tgt2.js
class A {
    #x = 1;
    static s = 2;
    get v() { return this.#x; }
}
const arr = [1, 2, 3].at(-1);
const obj = { ...{ a: 1 } };
```

私有字段 `#x`、静态字段、`.at()`、对象展开全部原样保留。**编译器的职责从"降级到 ES5"转向"只做类型擦除"**——降级交给打包工具按目标浏览器处理（见 [5-JavaScript/09-工程化/03-打包与转译](../5-JavaScript/09-工程化/03-打包与转译.md)）。

### `strict` 包含什么

| 子开关 | 拦住什么 | 实测拦截 |
|---|---|---|
| `strictNullChecks` | `null` / `undefined` 与其它类型不可互赋 | 1 处 |
| `strictPropertyInitialization` | 类属性未在构造器初始化 | 1 处 |
| `noImplicitAny` | 参数/变量推断为 `any` 时不报错 | — |
| `strictFunctionTypes` | 函数参数的双变检查（更严格） | — |
| `strictBindCallApply` | `call` / `apply` / `bind` 的参数类型 | — |
| `useUnknownInCatchVariables` | `catch (e)` 的 `e` 是 `unknown` 而非 `any` | — |
| `strictBuiltinIteratorReturn` | 内建迭代器的返回类型 | — |

（"实测拦截"列是用只触发该开关的样例文件跑出来的；空白项表示该样例未覆盖到。）

**`strictNullChecks` 是其中影响最大的一项**：没有它，`null` 与 `undefined` 可以赋给任何类型，`s.length` 对可能为 `null` 的 `s` 也不报错——整个类型系统对"空值"这一最常见错误源失去防护。

### `strict` **不**包含的重要检查

有些高价值检查**不在 `strict` 里**，必须单独开启。最典型的是 `noUncheckedIndexedAccess`：

```console
$ npx typescript@latest --strict --noEmit idx.ts
（无输出，通过）

$ npx typescript@latest --strict --noUncheckedIndexedAccess --noEmit idx.ts
idx.ts(2,1): error TS2532: Object is possibly 'undefined'.
idx.ts(4,1): error TS2532: Object is possibly 'undefined'.
```

```typescript
const e = [1, 2, 3];
e[10].toFixed(2);                    // 默认不报——但运行时是 undefined
const m: Record<string, number> = {};
m["k"].toFixed(2);                   // 同上
```

**这是类型系统的一处已知不健全**：索引访问默认返回 `T` 而不是 `T | undefined`，尽管下标可能越界、键可能不存在。开启 `noUncheckedIndexedAccess` 后类型变准确，代价是每个索引访问都要处理 `undefined`——存量代码开启时改动量不小。

其它需要单独开启的：`noImplicitReturns`、`noFallthroughCasesInSwitch`、`noUnusedLocals`、`exactOptionalPropertyTypes`。

### 与打包工具的分工

现代工程里，`tsc` 常常**只做类型检查，不做转译**：

| 工具 | 职责 |
|---|---|
| `tsc --noEmit` | 类型检查（CI 与编辑器） |
| 打包工具（esbuild / SWC / Rolldown） | 语法降级、打包、压缩 |

这样做的原因是**速度**——打包工具的转译不做类型检查，快得多（见 [5-JavaScript/09-工程化/03-打包与转译](../5-JavaScript/09-工程化/03-打包与转译.md)）。代价是**转译器不理解类型**，某些写法会被它误处理。两个选项用来约束：

| 选项 | 作用 |
|---|---|
| `isolatedModules` | 保证每个文件可独立转译（禁止跨文件的类型推断依赖） |
| `verbatimModuleSyntax` | 要求类型导入必须写 `import type`，避免转译器无法判断该不该删除导入 |

`verbatimModuleSyntax` 解决的问题很具体：`import { Foo } from "./x"` 里的 `Foo` 如果只是个类型，转译器不知道该删掉这行还是保留——它没有类型信息。显式写 `import type { Foo }` 就消除了歧义。

### 常用配置

```json
{
  "compilerOptions": {
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "verbatimModuleSyntax": true,
    "moduleResolution": "bundler",
    "skipLibCheck": true,
    "noEmit": true
  }
}
```

| 选项 | 说明 |
|---|---|
| `skipLibCheck` | 跳过 `.d.ts` 之间的类型检查，显著提速；代价是依赖里的类型冲突不会被发现 |
| `moduleResolution` | `bundler` / `node16` / `nodenext`；影响能否省略扩展名（见 [5-JavaScript/01-语言核心/06-模块](../5-JavaScript/01-语言核心/06-模块.md)） |
| `paths` | 路径别名，需打包工具同步配置 |
| `incremental` | 增量编译，缓存上次结果 |

## 连接：检查强度与成本

| 选项 | 拦住的问题 | 迁移成本 |
|---|---|---|
| `strict` | 空值、隐式 `any`、未初始化属性 | 中（TS 7 起默认开） |
| `noUncheckedIndexedAccess` | 索引访问越界 | 高 |
| `exactOptionalPropertyTypes` | `undefined` 与"属性缺失"混淆 | 中 |
| `noImplicitReturns` | 分支漏返回 | 低 |
| `noUnusedLocals` | 死代码 | 低 |

**新项目全部开启**；存量项目按成本从低到高逐步加，每加一项单独提交以便定位新增的错误。

## 边界

- **`strict` 是一组开关**：只开它不等于开了全部检查，`noUncheckedIndexedAccess` 等仍要单独开。
- **TypeScript 7 起 `strict` 默认为 `true`**：从旧版本升级时会出现大量新错误，这是预期行为。
- **TypeScript 7 的 `types` 默认为 `[]`**：不再自动加载 `@types` 下的包，需要显式配置（见 [07-声明文件与互操作](./07-声明文件与互操作.md)）。
- **`skipLibCheck` 是速度换严格度**：它跳过的是依赖之间的检查，不跳过你自己代码的检查。
- **打包工具的转译不做类型检查**：CI 里必须单独跑 `tsc --noEmit`。
- **`noUncheckedIndexedAccess` 开启后改动量大**：存量项目需评估工作量。
