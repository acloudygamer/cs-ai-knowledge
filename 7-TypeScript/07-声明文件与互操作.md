# 声明文件与互操作

> 前置：[06-泛型与类型编程](./06-泛型与类型编程.md) · 后续：[08-编译配置与严格模式](./08-编译配置与严格模式.md)

> **版本基准**：TypeScript 7.0.2。本篇示例实测环境：Node v24.13.1，`npx typescript@latest`，Windows x64。

## 本质

TypeScript 的类型信息有两个来源：**从 TypeScript 源码推导**，或**从声明文件读取**。声明文件（`.d.ts`）是"类型的头文件"——它只描述形状，不含实现，编译后不产生任何代码。

它是 JavaScript 生态能渐进式采用 TypeScript 的关键：**已有的 JavaScript 代码不必改写**，只需补一份声明。声明文件分两类：

| 来源 | 谁写 |
|---|---|
| 包自带 | 库作者（`types` 字段指向的 `.d.ts`） |
| `@types/*` 包 | 社区（DefinitelyTyped 仓库） |

两者都没有时，自己写一份。

## 机制

### 生成声明文件

从 TypeScript 源码自动产出：

```console
$ npx typescript@latest lib.ts --declaration --emitDeclarationOnly --outDir types
```

```typescript
// types/lib.d.ts
export interface User {
    name: string;
    age: number;
}
export declare function greet(u: User): string;
export declare const VERSION: string;
export declare class Store<T> {
    private items;
    add(i: T): void;
    all(): T[];
}
```

函数体被换成 `declare`——**声明文件里没有实现**。私有字段 `items` 只留名字不留类型，因为外部本就访问不到。

### 三种声明写法，差别只在"文件是不是模块"

这是本节最容易踩的地方。`declare module "x" { … }` 在两种文件里含义**完全不同**：

| 所在文件 | 含义 | 前提 |
|---|---|---|
| **非模块**（脚本，无顶层 `import` / `export`） | **环境声明**：宣称"存在这样一个模块" | 无 |
| **模块**（有顶层 `import` / `export`） | **模块增强**：给**已存在**的模块补充声明 | 目标模块必须已存在 |

实测对比（两个文件内容几乎相同，只差结尾的 `export {};`）：

```console
$ npx typescript@latest --strict --noEmit ambient.d.ts use.ts   # 无 export {}
（退出码 0，声明生效）

$ npx typescript@latest --strict --noEmit legacy.d.ts use.ts    # 有 export {}
use.ts(1,32): error TS2307: Cannot find module 'legacy-lib' or its corresponding type declarations.
```

`legacy.d.ts` 结尾那行 `export {};` 把它变成了模块，于是 `declare module "legacy-lib"` 被当成**对 `legacy-lib` 的增强**——而这个模块根本不存在，增强无从谈起，报错是"找不到模块"。

**本篇编写过程中实际踩到了这个坑**：我最初想同时演示环境声明与 `declare global`，就在同一个文件里加了 `export {};`，结果环境声明整段失效。

**规则**：

- **给不存在的模块补声明** → 文件**不能**有顶层 `import` / `export`；
- **给已存在的模块补类型**（模块增强）→ 文件**必须**是模块（加 `export {}`）；
- **增强全局对象**（`Window` 等）→ 文件**必须**是模块，且用 `declare global` 包裹。

三种形态的完整写法：

```typescript
// 1. 环境声明：declare-modules.d.ts（非模块，无 import/export）
declare module "legacy-lib" {
  export function parse(input: string): { ok: boolean };
  export const version: string;
}

// 2. 通配符：让 import "./app.css" 有类型
declare module "*.css" {
  const content: string;
  export default content;
}
```

```typescript
// 3. 全局增强：global.d.ts（必须是模块）
export {};
declare global {
  interface Window { __APP_VERSION__: string }
}
```

通配符与全局增强都实测通过（退出码 0）。通配符声明是"导入非 JS 资源"（CSS、图片、`?raw` 后缀）的标准做法。

### 声明缺失时的报错

```console
$ npx typescript@latest --strict --noEmit missing.ts
missing.ts(1,23): error TS2307: Cannot find module 'legacy-lib' or its corresponding type declarations.
```

`TS2307` 是"找不到模块或其类型声明"。它的两类成因要分清：

- **模块真的不存在**（路径写错、没装依赖）；
- **模块存在但没有类型**（是纯 JavaScript 包，且没有 `@types`）。

第二种情况才需要自己写声明。判断方法：`node -e "require.resolve('包名')"` 能否成功。

### `@types` 包与查找顺序

类型声明的查找顺序：

1. 包自己的 `package.json` 的 `types` / `typings` 字段；
2. 包目录下的 `index.d.ts`；
3. `node_modules/@types/<包名>/`。

`@types` 包由社区维护（DefinitelyTyped 仓库），与运行时包分开安装：

```bash
npm install --save-dev @types/node @types/express
```

**版本要匹配**：`@types/foo` 的主版本通常跟随 `foo`，装了不匹配的版本会得到错误的类型。

TypeScript 7 的一个默认值变更与此相关：**`types` 现在默认为 `[]`**（旧行为是 `["*"]`，即自动加载 `node_modules/@types` 下的全部包）。需要自动加载时显式配置：

```json
{ "compilerOptions": { "types": ["node"] } }
```

### 让 JavaScript 也受检查

不必改写文件也能获得部分检查：

```console
$ npx typescript@latest --allowJs --checkJs --noEmit plain.js
plain.js(2,21): error TS7006: Parameter 'a' implicitly has an 'any' type.
plain.js(2,24): error TS7006: Parameter 'b' implicitly has an 'any' type.
```

| 选项 | 作用 |
|---|---|
| `allowJs` | 允许编译/检查 `.js` 文件 |
| `checkJs` | 对 `.js` 也做类型检查 |
| 文件头 `// @ts-check` | 只对单个文件开启检查（配合 `allowJs`） |

再配合 **JSDoc 注释**，JavaScript 里也能写类型：

```javascript
/** @param {number} a @param {number} b @returns {number} */
function add(a, b) { return a + b; }
```

这是"渐进式迁移"的中间态：不引入 `.ts` 文件，但获得参数检查与编辑器补全。

## 连接：三种声明写法对照

| 目的 | 文件类型 | 写法 |
|---|---|---|
| 为无类型的第三方包补声明 | 非模块 | `declare module "包名" { … }` |
| 为非 JS 资源补声明 | 非模块 | `declare module "*.css" { … }` |
| 给已有模块补类型 | 模块（`export {}`） | `declare module "包名" { … }` |
| 增强全局对象 | 模块（`export {}`） | `declare global { … }` |
| 只描述形状不产生代码 | 任意 | 只写 `declare`，不写实现 |

## 边界

- **`export {}` 会改变 `declare module` 的含义**：环境声明 ↔ 模块增强，最易踩的一处。
- **声明文件只描述形状**：它不生成任何运行时代码，写错了不会在运行时暴露，只在编译期体现。
- **声明是"承诺"不是"验证"**：手写的 `.d.ts` 与实际实现不符时，TypeScript 不会发现，运行时才出错。
- **`@types` 与运行时包版本要匹配**。
- **TypeScript 7 的 `types` 默认是 `[]`**：不再自动加载 `@types` 下的全部包。
- **通配符声明会掩盖真实错误**：`declare module "*.css"` 让所有 `.css` 导入都通过，拼错文件名也发现不了。
