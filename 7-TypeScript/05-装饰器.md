# 装饰器

> 前置：[04-类型收窄与控制流分析](./04-类型收窄与控制流分析.md) · 后续：[06-泛型与类型编程](./06-泛型与类型编程.md)

> **版本基准**：**TypeScript 7.0.2**（`tsgo`），Node v24.13.1，Windows x64。

## 本质

装饰器是**类声明期的元编程**：在类定义求值时拿到类或其成员，替换、包装、登记。它不是类型语法——`@log` 编译后生成**真实的运行时代码**（装饰器调用与包装函数），产物比源码重。这一点与类型标注完全相反，所以它从来不在"可擦除"之列（`erasableSyntaxOnly` 的精神由此而来，见 [02-枚举与字面量类型](./02-枚举与字面量类型.md)）。

TypeScript 里有**两代装饰器**，签名与产物都不同：

- **标准装饰器**（TC39 提案，TS 5.0 起支持，TS 7 默认）：`(value, context)` 两参。
- **实验装饰器**（`experimentalDecorators`，TS 早期的自有设计）：`(target, key, descriptor)` 三参。

## 机制

### 标准装饰器：默认开启

```console
$ npx typescript@latest deco.ts --target es2022 --outDir out && node out/deco.js
call greet
hi
```

```typescript
function log(value: any, context: ClassMethodDecoratorContext) {
  return function (this: any, ...args: any[]) {
    console.log(`call ${String(context.name)}`);
    return value.apply(this, args);
  };
}
class C {
  @log greet() { return "hi"; }
}
console.log(new C().greet());
```

第一参是**被装饰的值本身**（方法函数），第二参是 `context` 对象（`kind`、`name`、`addInitializer` 等元数据）。返回新函数即替换原方法。

看产物就知道代价——编译器为每个被装饰的类注入 `__esDecorate` / `__runInitializers` 辅助函数，逐个成员应用装饰器、管理初始化器队列。几十个装饰器的类会带一份不小的固定开销，这是"声明期元编程"的运行时账单。

### 实验装饰器：要开关的旧设计

```console
$ npx typescript@latest legacy.ts --target es2022 --outDir out
legacy.ts(9,3): error TS1241: Unable to resolve signature of method decorator when called as an expression.
  The runtime will invoke the decorator with 2 arguments, but the decorator expects 3.

$ npx typescript@latest legacy.ts --target es2022 --experimentalDecorators --outDir out && node out/legacy.js
legacy call greet
hi
```

```typescript
function log(target: any, key: string, desc: PropertyDescriptor) {
  const orig = desc.value;
  desc.value = function (...args: any[]) {
    console.log(`legacy call ${key}`);
    return orig.apply(this, args);
  };
}
```

三参旧签名在默认（标准）模式下直接报 TS1241——**两代装饰器的调用约定不兼容**，加 `--experimentalDecorators` 才切回旧行为。旧设计的产物用 `__decorate` 辅助函数，操作的是属性描述符。

### `emitDecoratorMetadata`：把类型信息留下来

类型在运行时本不存在（类型擦除，见 [01-类型系统基础](./01-类型系统基础.md)），但依赖注入框架需要知道"这个参数的声明类型是什么"。旧方案的回答是 `emitDecoratorMetadata`：编译器把设计期类型以 `Reflect.metadata` 调用的形式**写进产物**，运行时配合 `reflect-metadata` 库读回：

```console
$ npx typescript@latest meta.ts --target es2022 --module commonjs --experimentalDecorators --emitDecoratorMetadata --outDir out && node out/meta.js
[ 'Object' ]
```

```typescript
import "reflect-metadata";
function meta(...args: any[]) {}
class S {
  constructor(@meta dep: Object) {}
}
console.log(Reflect.getMetadata("design:paramtypes", S)?.map((t: any) => t.name));   // [ 'Object' ]
```

三个前提缺一不可：`experimentalDecorators` + `emitDecoratorMetadata` + 运行时的 `reflect-metadata` polyfill。读回的只是**构造函数引用**（接口、联合、泛型实参都没有运行时对应物，只能拿到 `Object`）——NestJS、Angular 的构造器注入能工作，靠的就是这条狭窄的通道。

## 连接：两代装饰器对照

| | 标准装饰器（TS 7 默认） | 实验装饰器（legacy） |
|---|---|---|
| 签名 | `(value, context)` | `(target, key, descriptor)` |
| 开关 | 无（默认） | `experimentalDecorators` |
| 产物辅助函数 | `__esDecorate` 系列 | `__decorate` |
| 元数据 | **无**（TC39 提案不含） | `emitDecoratorMetadata` + reflect-metadata |
| 主战场 | 新代码、TC39 对齐 | NestJS/Angular 等存量框架 |

## 边界

- **装饰器不改类型**：`@log` 包装了 `greet` 的运行时行为，但 `greet` 的类型签名不变——类型层看不到装饰器做的事。
- **两代不能混用**：一个文件走哪代由 `experimentalDecorators` 全局决定。
- **元数据只覆盖构造器引用**：接口、联合、泛型实参全部退化为 `Object`，注入更精细的契约要靠框架自己的 token 机制。
- **装饰器是运行时开销**：辅助函数与包装层进产物，热路径方法慎用。
- **Node strip-only 模式拒绝装饰器**：与 enum 同理，装饰器需要真正的语法转换（见 [02-枚举与字面量类型](./02-枚举与字面量类型.md)）。
