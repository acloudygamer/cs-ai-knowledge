# 类型收窄与控制流分析

> 前置：[03-类与接口](./03-类与接口.md) · 后续：[05-装饰器](./05-装饰器.md)

> **版本基准**：**TypeScript 7.0.2**（`tsgo`），Node v24.13.1，Windows x64。

## 本质

声明处的类型是**最宽的承诺**（`string | number`），使用处的具体操作需要精确类型（`toUpperCase` 只认 `string`）。连接两者的机制是**收窄**（narrowing）：编译器沿控制流逐句推演，在分支内把联合类型削成具体类型。这套推演叫**控制流分析**（control-flow analysis，CFA），纯编译期行为——产物与手写 JavaScript 一字不差。

## 机制

### 内建守卫：`typeof` / `instanceof` / `in` / 判别属性

```typescript
type Circle = { kind: "circle"; r: number };
type Rect = { kind: "rect"; w: number; h: number };

function area(s: Circle | Rect) {
  if ("r" in s) return Math.PI * s.r ** 2;   // in 守卫：此分支收窄为 Circle
  if (s.kind === "rect") return s.w * s.h;   // 判别属性：此分支为 Rect
  return s;                                   // 此处为 never——穷尽
}
```

四类内建守卫对应四条运行时判断：`typeof` 查原始类型标签、`instanceof` 走原型链（见 [5-JavaScript/02-对象模型与运行时/01-原型链与继承](../5-JavaScript/02-对象模型与运行时/01-原型链与继承.md)）、`in` 查键存在性、判别属性比较字面量。编译器把每条判断映射回类型层的削枝规则。判别属性是可辨识联合的入口（组合与穷尽检查见 [06-泛型与类型编程](./06-泛型与类型编程.md)）。

### 类型谓词：把自定义检查接进控制流

```console
$ npx typescript@latest pred.ts --target es2022 --outDir out && node out/pred.js
HI
```

```typescript
function isString(x: unknown): x is string {
  return typeof x === "string";
}
const u: unknown = "hi";
if (isString(u)) {
  console.log(u.toUpperCase());   // 分支内 u 收窄为 string
}
```

返回类型 `x is string` 是**类型谓词**：它告诉编译器"函数返回 `true` 时，参数就是 `string`"。没有它，`if (isString(u))` 只收窄不了任何东西——函数返回值对编译器只是 `boolean`。库的作者用谓词把运行时知识接进 CFA；`Array.isArray` 的内建声明就是这样写的。

### 断言函数：不通过就抛

```typescript
function assertString(x: unknown): asserts x is string {
  if (typeof x !== "string") throw new TypeError("not string");
}
const u: unknown = "hi";
assertString(u);
console.log(u.toUpperCase());    // 调用之后 u 收窄为 string
```

`asserts x is string` 把"返回后成立"编码进类型——不需要 `if` 包裹，调用本身就改变后续代码的推演起点。Node 的 `assert` 模块声明正是这套写法。与 [01-类型系统基础](./01-类型系统基础.md) 的原则一致：断言函数里**真的有运行时检查**（不满足就抛），类型变化有运行时的靠山。

### 赋值驱动的重收窄

```console
$ npx typescript@latest --noEmit reset.ts
reset.ts(5,17): error TS2339: Property 'toUpperCase' does not exist on type 'number'.
```

```typescript
let v: string | number = "s";
if (typeof v === "string") {
  console.log(v.toUpperCase());   // v 是 string
  v = 42;                          // 赋值发生
  console.log(v.toUpperCase());   // 报错：v 现在是 number
}
```

CFA 跟踪的不只是分支，还有**赋值流**：`v = 42` 之后，编译器知道 `v` 的实际内容变了，收窄跟着刷新为 `number`。编译器看到的是值的流动，不是声明的静止快照。

### 别名条件：判断可以先存起来

```typescript
declare const v: string | number;
const isStr = typeof v === "string";
if (isStr) { console.log(v.toUpperCase()); }   // 通过
```

判断提取成常量后仍然收窄（TS 4.4 起）——CFA 记住 `isStr` 与"`typeof v === "string"` 为真"的关联。但别名只在**引用不可变**时有效：`let isStr = ...` 中间若有重新赋值，关联即失效。

### 闭包边界：回调里收窄失效

```console
$ npx typescript@latest --noEmit closure.ts
closure.ts(3,35): error TS2339: Property 'toUpperCase' does not exist on type 'string | number'.
```

```typescript
let v: string | number = "s";
if (typeof v === "string") {
  [1].forEach(() => console.log(v.toUpperCase()));   // 报错：回调里 v 回到联合
}
```

把 `let` 换成 `const`，错误消失。约束来自执行时序：回调的执行时刻编译器无法排序——它可能发生在 `v` 被重新赋值之后（见 [5-JavaScript/04-异步与并发/01-事件循环与任务队列](../5-JavaScript/04-异步与并发/01-事件循环与任务队列.md)）。对 `let`，CFA 保守地在函数边界丢弃收窄；`const` 不可能再赋值，收窄可以安全地带进闭包。

## 连接：收窄在类型系统里的位置

| 机制 | 驱动者 | 收窄后的类型活在哪 |
|---|---|---|
| 内建守卫 | 语法模式（`typeof`、`in` 等） | 分支块内 |
| 类型谓词 `x is T` | 函数返回值 | 调用点的分支 |
| 断言函数 `asserts x is T` | 函数不返回（抛错） | 调用点之后的整个流 |
| 赋值重收窄 | 赋值语句 | 赋值点之后 |
| 闭包失效 | 函数边界的时序不可知 | —（收窄被丢弃） |

收窄的**主场在调用处**：类型在声明处写宽（表达能力），在使用处由 CFA 削窄（可用性）。泛型把"宽"参数化（见 [06-泛型与类型编程](./06-泛型与类型编程.md)），收窄把"宽"消解——两者共同支撑"写起来像 JavaScript"。

## 边界

- **收窄只改类型，不校验值**：`typeof` 检查是真实运行时判断，但 `as` 断言不是——`as` 绕过 CFA，错误推迟到运行时。
- **闭包内的 `let` 收窄失效**：时序不可排序，编译器保守丢弃。
- **谓词可以撒谎**：`x is string` 的实现若返回错误结果，编译器照单全收——谓词的正确性由作者担保。
- **`in` 守卫只削联合的成员**：对非联合类型，`"x" in obj` 不参与收窄。
- **别名条件要求不可变引用**：`let` 别名中断关联。
