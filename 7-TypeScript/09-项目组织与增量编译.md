# 项目组织与增量编译

> 前置：[08-编译配置与严格模式](./08-编译配置与严格模式.md) · 后续：[10-版本演进](./10-版本演进.md)

> **版本基准**：**TypeScript 7.0.2**（`tsgo`），Node v24.13.1，Windows x64。

## 本质

一份 `tsconfig.json` 定义**一个编译单元**（见 [08-编译配置与严格模式](./08-编译配置与严格模式.md)）。代码库长成 monorepo 后暴露两个问题：任何改动都触发**全量重编**，包与包之间**没有编译器可见的边界**。**项目引用**（project references）的回答是：把库切成有向无环图（DAG）上的多个编译单元，每个单元独立产出、独立缓存——这就是 `composite`、`references`、`.tsbuildinfo` 三件套的由来。

## 机制

### `references` + `composite`：把库切成编译单元

一个两包 monorepo（`core` 被 `app` 引用）：

```jsonc
// core/tsconfig.json
{ "compilerOptions": { "composite": true, "outDir": "dist", "declaration": true, "strict": true } }

// app/tsconfig.json
{ "compilerOptions": { "composite": true, "outDir": "dist", "strict": true },
  "references": [{ "path": "../core" }] }
```

- 被引用的项目必须开 `composite: true`——它同时强制 `declaration: true`（项目之间靠 `.d.ts` 对话，见 [07-声明文件与互操作](./07-声明文件与互操作.md)）与增量编译。
- `references` 声明依赖方向，构成 DAG——**循环引用直接报错**，包的层级由此被编译器钉死。

### `tsc -b`：按依赖序构建，能跳就跳

```console
$ npx typescript@latest -b app --verbose
12:12:50 PM - Projects in this build:
    * core/tsconfig.json
    * app/tsconfig.json
12:12:50 PM - Project 'core/tsconfig.json' is out of date because output file 'core/dist/tsconfig.tsbuildinfo' does not exist
12:12:50 PM - Building project 'core/tsconfig.json'...
12:12:50 PM - Project 'app/tsconfig.json' is out of date because output file 'app/dist/tsconfig.tsbuildinfo' does not exist
12:12:50 PM - Building project 'app/tsconfig.json'...

$ npx typescript@latest -b app --verbose
12:13:00 PM - Project 'core/tsconfig.json' is up to date because newest input 'core/src/index.ts' is older than output 'core/dist/tsconfig.tsbuildinfo'
12:13:00 PM - Project 'app/tsconfig.json' is up to date because newest input 'app/src/main.ts' is older than output 'app/dist/tsconfig.tsbuildinfo'
```

构建模式 `-b` 读 `references` 排出拓扑序，先建 `core` 再建 `app`。第二次运行时两个项目都跳过——判据是**输入文件不新于 `.tsbuildinfo`**。

`.tsbuildinfo` 是增量的状态文件：记录输入文件的版本指纹与上次的诊断结果，让编译器跳过未变部分的完整类型检查。`composite` 隐含 `incremental`；单项目也可以单独开 `incremental: true` 获得同样的缓存（不带跨项目边界）。

### `paths`：编译期映射，不动运行时

```jsonc
// app/tsconfig.json
{ "compilerOptions": { "paths": { "@lib/core": ["../core/src/index.ts"] } } }
```

```console
$ node app/dist/src/main.js
Error: Cannot find module '@lib/core'
```

`paths` 只影响**编译器的模块解析**：类型检查通过、正常出产物，但产物里的 `import "@lib/core"` 原样保留，Node 运行时解析不了它。编译期与运行时的解析是两条独立的链（见 [5-JavaScript/09-工程化/02-模块解析与产物格式](../5-JavaScript/09-工程化/02-模块解析与产物格式.md)）：`paths` 只接了编译期那条。运行时那条要么交给打包器重写（见 [5-JavaScript/09-工程化/03-打包与转译](../5-JavaScript/09-工程化/03-打包与转译.md)），要么用 `package.json` 的 `imports`/`exports` 让 Node 自己认识这个名字。monorepo 的正路是后者：每个包声明自己的 `exports`，`paths` 只做开发期指向源码的捷径。

## 连接：三件套的分工

| 机制 | 回答的问题 | 产物/状态 |
|---|---|---|
| `references` | 编译单元之间谁依赖谁 | 无（只声明 DAG） |
| `composite` | 这个单元能否被独立缓存 | 强制 `.d.ts` + 增量 |
| `.tsbuildinfo` | 上次编到哪了 | 状态文件（每个单元一份） |
| `paths` | 编译期这个名字去哪找 | **不改产物** |

与打包工具的分工不变：`tsc` 负责类型检查与声明产物，运行时产物由打包器或 Node 的解析规则接管（见 [08-编译配置与严格模式](./08-编译配置与严格模式.md)）。

## 边界

- **`references` 是 DAG**：循环依赖编译器直接拒绝，包的层级设计先于配置。
- **`composite` 强制 `declaration`**：被引用的包必须出 `.d.ts`，出不了就不能被引用。
- **`paths` 不影响运行时**：产物里的导入说明符原样保留，运行时必须另有解析方案。
- **`.tsbuildinfo` 是缓存不是源码**：随 `outDir` 一起进 `.gitignore`；删掉的代价只是一次全量重编。
- **增量不省首次**：冷启动仍是全量编译，缓存只对后续构建生效。
