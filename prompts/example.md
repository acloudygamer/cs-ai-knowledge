## 示例 1：std::vector 扩容机制

# std::vector 扩容机制

## 定义

`std::vector` 的扩容机制是在堆上分配一块新内存、将旧元素移动/复制到新内存、释放旧内存的 **确定性 O(N) 操作**。通过指数增长策略（通常增长因子为 2），将多次 push_back 的均摊时间压至 O(1)，同时避免频繁分配带来的系统调用开销。

## 数学模型

设容量序列 $\{c_0, c_1, c_2, \dots\}$，增长因子 $k > 1$（标准库实现通常 $k = 2$ 或 $1.5$）：
$$c_{i+1} = \max(c_i \times k,\ 1)$$

第 $i$ 次扩容发生时，已有元素数 $n_i = c_i$，移动代价与 $c_i$ 成正比。总移动次数 $T(N)$ 满足：
$$T(N) = \sum_{i=0}^{\lfloor \log_k N \rfloor} c_i = \sum_{i=0}^{\lfloor \log_k N \rfloor} k^i = \frac{k^{\lfloor \log_k N \rfloor + 1} - 1}{k - 1} \le \frac{kN - 1}{k - 1} = O(N)$$

均摊到每个插入操作的移动次数：
$$\frac{T(N)}{N} = O(1)$$

**归约终点**：扩容的代价归结为**内存分配 + 元素搬移 + 内存释放**，三者均受控于堆管理器和元素类型的移动开销。

## 数据流

<pre>
旧内存（堆）               新内存（堆）               旧内存（堆）
+------------------+       +--------------------+       +------------------+
| [A][B][C][空闲]  |  ---> | [A][B][C][空闲][空闲] |  ---> |       free       |
| size=3, cap=4    | 移动  | size=3, cap=8        | 释放  |  (所有权返还OS)   |
+------------------+       +--------------------+       +------------------+
         |                             |
         +--- 所有权：旧内存持有元素 ---+
                   移动后旧元素被析构，新内存接管
</pre>

**步骤**：
1. 判定 `size == capacity`，触发扩容。
2. 计算 `new_cap = cap_ ? cap_ * 2 : 1`。
3. 调用堆分配器申请 `new_cap * sizeof(T)` 字节的新内存块。
4. 对旧内存中每个元素，在新内存对应位置调用 placement new + std::move（或拷贝，取决于元素类型的移动保证）。
5. 析构并释放旧内存（将所有权交还堆管理器）。
6. 将 `data_` 指针指向新内存，`cap_` 更新。

## 机制

扩容采用指数增长而非固定步长增长的原因：
- 若每次 `push_back` 都按固定大小扩容（如 `cap += 1`），则 $T(N) = 1 + 2 + \dots + N = O(N^2)$，无法用于动态数组。
- 指数增长将分配次数从 $O(N)$ 降为 $O(\log N)$，总移动量线性。

**约束条件**：
- 扩容时旧内存中的元素必须满足**移动不抛出异常**（或至少是可移动的），否则回退到拷贝。
- 若元素移动构造函数抛出异常，从标准 C++11 起，`vector` 保证扩容失败时旧内存保持原状（强异常安全）。
- 增长因子过大会造成内存浪费（如 $k=2$ 可能使最终容量是实际需求的近一倍）；过小则引发频繁扩容。某些实现采用 $k=1.5$ 以允许之后的内存复用。

**违反约束**的后果：
- 若移动操作抛出异常且未提供拷贝后备，则 `vector` 进入未定义状态。
- 若使用自定义分配器但分配失败（`new_cap` 过大），`push_back` 抛出 `std::bad_alloc`，数据不变。

## 参考存根

```cpp
template<typename T>
void vector<T>::push_back(const T& val) {
    if (size_ == cap_) {
        size_t new_cap = cap_ ? cap_ * 2 : 1;
        T* new_data = alloc(new_cap);
        for (size_t i = 0; i < size_; ++i)
            new (new_data + i) T(std::move(data_[i]));
        dealloc(data_);
        data_ = new_data;
        cap_ = new_cap;
    }
    new (data_ + size_) T(val);
    ++size_;
}
```

## 示例 2：Scaled Dot-Product Attention

# Scaled Dot-Product Attention

## 定义

Scaled Dot-Product Attention 是一个可微的键值检索机制：查询向量（Query）与所有键向量（Key）计算点积相似度，经缩放和 Softmax 归一化后成为权重，对值向量（Value）加权求和。它在 Transformer 中作为核心算子，实现了输入序列的全局依赖建模。

## 数学模型

给定 Query 矩阵 $Q \in \mathbb{R}^{L \times d_k}$，Key 矩阵 $K \in \mathbb{R}^{L \times d_k}$，Value 矩阵 $V \in \mathbb{R}^{L \times d_v}$：

$$\text{Attention}(Q, K, V) = \text{softmax}\left(\frac{QK^T}{\sqrt{d_k}}\right)V$$

**缩放因子 $\frac{1}{\sqrt{d_k}}$ 的来源**：
假设 $Q$ 和 $K$ 的行向量各分量 $q_{it}$、$k_{jt}$ 独立同分布，均值为 0、方差为 1。则点积 $q_i \cdot k_j = \sum_{t=1}^{d_k} q_{it} k_{jt}$ 的方差为：
$$\mathrm{Var}\left( \sum_t q_{it}k_{jt} \right) = \sum_t \mathrm{Var}(q_{it}k_{jt}) = \sum_t \mathrm{Var}(q_{it})\mathrm{Var}(k_{jt}) = d_k \times 1 \times 1 = d_k$$

若不做缩放，Softmax 的输入方差 $\sigma^2 = d_k$。当 $d_k$ 较大（如 512）时，点积值取值于 $[- \sigma\sqrt{2\log L}, +\sigma\sqrt{2\log L}]$ 外，Softmax 输出接近独热分布，梯度几乎为零。除以 $\sqrt{d_k}$ 使方差降回 1，确保梯度正常流动。

## 数据流

<pre>
Q (L, d_k)                K^T (d_k, L)                 V (L, d_v)
    │                           │                           │
    └──────────────┬────────────┘                           │
                   │                                        │
                矩阵乘                                      │
                   │                                        │
                   ▼                                        │
          QK^T (L, L)                                       │
               │                                            │
               ├──> 除以 √d_k                               │
               │                                            │
               ▼                                            │
          (L, L) 未归一化 logits                            │
               │                                            │
               └──> softmax (沿行方向) ──> 注意力矩阵 A (L, L)
                                            │
                                            └──> 矩阵乘 ──> Output (L, d_v)
                                                 │
                                                 ▼
                                            O = A · V
</pre>

**所有权/变换**：
- $Q, K, V$ 均为输入张量（只读）。
- 中间 `QK^T` 由矩阵乘法产生，所有权归计算图，后续会被缩放和 Softmax 原地覆盖（或分配新张量，依实现而定）。
- 注意力矩阵 $A$ 作为权重，与 $V$ 行向量的线性组合生成输出，输出张量拥有新分配的内存。

## 机制

**三个矩阵的物理含义**：
- $Q$（Query）：当前 token "想寻找什么信息"。
- $K$（Key）：当前 token "能够提供的信息类型"。
- $V$（Value）：当前 token "实际携带的内容"。

`QK^T` 计算所有 query–key 对的内积，相当于在注意力空间中计算匹配分数。Softmax 将分数转为概率分布——对每个 query，它对整个序列的 key 有一个概率权重。最后用这个权重对 V 做加权和：$\text{Output}_i = \sum_j \text{softmax}_j(\frac{Q_i K^T}{\sqrt{d_k}}) V_j$。

**为什么要用点积 + Softmax 而非余弦相似度**：点积在矩阵乘法下高度并行，且可融入缩放因子直接控制方差。Softmax 保证权重非负且和为 1，等价于一种"软性键值检索"。

**设计约束与违反后果**：
- 若省略 $\sqrt{d_k}$ 缩放，当 $d_k$ 较大时梯度趋于 0，深层 Transformer 难以训练（梯度消失）。
- 若 Softmax 输入含有极大值（例如某些 token 间的点积远大于其他），输出几乎独热，模型丧失从多个位置融合信息的能力。
- 处理遮挡（masking）时，需将遮挡位置设为 $-\infty$ 而非 0，否则 Softmax 仍会分配非零权重。

## 参考存根

*本概念的核心价值在于数学形式而非短代码证明；但为展示可执行性，提供一个最小化 NumPy 实现：*

```python
import numpy as np
def attention(Q, K, V):
    d_k = Q.shape[-1]
    scores = Q @ K.T / np.sqrt(d_k)
    weights = np.exp(scores) / np.sum(np.exp(scores), axis=-1, keepdims=True)
    return weights @ V
```

## 示例 3：进程、线程、协程 对比

# 进程、线程、协程 对比

## 定义

进程、线程、协程是三种执行流的抽象层次。进程是操作系统资源分配的最小单位，拥有独立虚拟地址空间；线程是 CPU 调度（内核级抢占调度）的最小单位，共享进程地址空间；协程是用户态协作式调度的可挂起函数，完全由程序控制切换时机。

## 数学模型

令 $T_{ctx}$ 为单次上下文切换耗时的典型量级：

| 执行单元 | $T_{ctx}$ 典型值 | 内存模型 | 调度权 |
|----------|------------------|----------|--------|
| 进程     | $1\!-\!10\,\mu s$（含 TLB 刷新、页表切换） | 独立虚拟地址空间 | 内核抢占式 |
| 线程     | $0.2\!-\!1\,\mu s$（同进程内，需系统调用） | 共享地址空间，独立栈 | 内核抢占式 |
| 协程     | $10\!-\!50\,ns$（仅寄存器保存/恢复） | 共享地址空间，共享或独立栈 | **用户态协作式** |

**归约终点**：切换代价的本质差异来源于**特权级切换**（用户态↔内核态）和**地址空间切换**（CR3 寄存器重载导致 TLB 失效）。协程不触发任何特权级转换，因此逼近函数调用。

## 数据流

以下展示一个整数如何在不同执行单元间交换。

<pre>
进程 A (PID=100, 页表 PA)                    进程 B (PID=101, 页表 PB)
+------------------------+                   +------------------------+
| 堆变量 x = 42          |                   | 堆变量 y               |
| 内存地址 0x7f123456    |                   | 内存地址 0x7f654321    |
+------------------------+                   +------------------------+
         │                                                  │
         │  数据交换方式：管道 / 共享内存 + 互斥锁           │
         └──────────────────┬───────────────────────────────┘
                            ▼
                 内核拷贝数据（管道） 或 同一物理页帧映射到两个页表（共享内存）

线程 1 (同进程内)                        线程 2 (同进程内)
+------------------+                      +------------------+
| 栈变量 local = 42 |                      | 栈变量 other      |
| 直接读写堆        |  <-- 无锁交换 ---->  | 直接读写堆        |
+------------------+                      +------------------+
         │ 所有权：共享整个进程地址空间，任意指针可跨线程访问

协程 A (用户态)                          协程 B (用户态)
+------------------------+               +------------------------+
| 寄存器现场 (RSP, RIP等) |  <-- yield --> | 寄存器现场              |
| 共享栈 或 独立栈        |               | 共享栈                  |
+------------------------+               +------------------------+
         │ 数据直接放在相同线程的栈或堆上，切换时不经过内核
</pre>

**形态变换与所有权流转**：
- 进程间数据交换：数据从 A 的地址空间复制到内核缓冲区，再复制到 B 的空间（管道），或通过共享内存建立物理页的双向映射。
- 线程间：数据指针就是同一虚拟地址，无需变换形态，但所有权在逻辑层面需通过锁或原子操作转移。
- 协程间：在同一线程内顺序执行，数据始终驻留在内存同一位置；协程切换仅改变当前 CPU 寄存器状态，不改变数据所有权归属（仍属于整个线程）。

## 对比参照

| 属性 | 进程 | 线程 | 协程 |
|------|------|------|------|
| **内存模型** | 独立虚拟地址空间（页表、MMU 上下文） | 共享地址空间，独立栈 + 共享堆 | 共享地址空间，独立或共享栈 |
| **调度权** | 内核抢占式调度（时间片轮转） | 内核抢占式调度 | 用户态协作式调度（显式 yield/await） |
| **数据交换代价** | 高：需内核介入（拷贝或页映射） | 中：直接读写共享内存，但需同步原语 | 低：直接读写，无竞争（单线程） |
| **切换触发条件** | 系统调用、中断、时间片耗尽 | 系统调用、中断、时间片耗尽 | 程序主动挂起（I/O、定时、显式让步） |

## 机制

**进程与线程的本质差异**：
进程提供内存隔离与安全边界，但也导致 TLB 完全失效，切换代价高。线程保留进程的内存共享但移除隔离，代价降低。然而线程仍受内核调度，时间片耗尽时被强制挂起，保存/恢复通用寄存器、浮点寄存器、指令指针等，并可能进入内核态。

**协程为何更轻量**：
协程完全在用户态实现。它的上下文仅包含必要的 CPU 寄存器（栈指针、指令指针、少数通用寄存器），不涉及页表、内核栈、信号掩码等。**关键约束**：协程只在显式 `yield/await` 点出让执行权，否则不会被中断。这意味着同一线程内的多个协程从不存在真正的数据竞争（除非程序员故意在多个线程中调度协程）。

**违反约束会怎样**：
- 若协程内执行阻塞系统调用（如 `read`），将阻塞整个线程，所有协程都被卡住。因此协程必须配异步 I/O。
- 若滥用抢占（如试图从信号处理器中切换协程），会导致用户态栈状态不一致，崩溃不可恢复。
- 若在线程环境中直接复用普通的协程栈，可能出现栈溢出（协程栈通常较小，如 64KB），需要分段栈或动态增长。

## 参考存根

```cpp
// 基于 ucontext 的最简协程切换（仅展示原理，实际使用 boost::coroutine2 或 C++20）
#include <ucontext.h>
ucontext_t ctx_main, ctx_co;

void co_routine() {
    swapcontext(&ctx_co, &ctx_main);
}

int main() {
    char stack[8192];
    getcontext(&ctx_co);
    ctx_co.uc_stack.ss_sp = stack;
    ctx_co.uc_stack.ss_size = sizeof(stack);
    ctx_co.uc_link = &ctx_main;
    makecontext(&ctx_co, co_routine, 0);
    swapcontext(&ctx_main, &ctx_co);
    return 0;
}
```
