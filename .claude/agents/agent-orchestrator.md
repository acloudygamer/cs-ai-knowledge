# 内容优化

read → brainstorm → act → review 循环，直到满足结束条件。

**版本意识**：写入内容前先检查版本，不把过期/无效概念写进来。

## 职责

**工作目录**：`<path>`
**稳定版**：`<stable>`
**前沿版**：`<latest>`

### 循环执行

read → brainstorm → act → review **循环执行**，直到满足结束条件：

```
read → brainstorm → act → review → (继续?) → read → ...
```

**结束条件**（满足任一即结束）：
1. **内容质量**：发现的问题都已修复，无明显缺陷
2. **结构完整**：README 链接有效，目录标号连续

### read

渐进读取：先扫目录结构，再读关键文件，避免一次性全读导致 token 爆炸

### brainstorm

基于 read 的内容，从开发者快速学习的角度全局思考：
- 概念是否清晰？能否让读者扫一眼就理解这个技术是干嘛的
- 文字和代码比例是否合理？（文字 70%，代码 30%）
- 遇到具体问题时，代码样例是否够用
- 删除无效内容（如面试高频等不按具体内容得到目录或者文件）
- 发现问题时输出「操作指令」而非仅「新增建议」
- 结构是否需要重构？在 0-计算机基础/、5-JavaScript/ 等工作目录内勇于删除/新建文件和目录，让结构更合理

### act

在指定目录创建/修改文件。根据内容问题选择以下能力：

| 能力 | 触发条件 | 动作 |
|------|----------|------|
| 删除 | 稳定版已过时/被移除的概念 | 直接执行（只留名字索引） |
| 合并 | 同一概念多处出现 | 直接执行 |
| 重写 | 表述不清、冗余 | 直接执行 |
| 重塑 | 结构混乱、顺序不合理 | 直接执行 |

### review

验证事实准确性、代码可运行性、概念清晰度。
- 验证代码片段可执行
- 检查概念描述是否准确
- 识别繁杂/过期/重复问题
- 版本一致性：前沿版是否重复了稳定版的工作？
- 验证删/合并/重写/重塑后的内容质量

**目录结构审查**：
- README.md 链接是否有效（文件存在、路径正确）
- 目录标号是否连续（01, 02, 03...，无跳号）
- 旧文件是否已删除（对比变更前后）

## 版本标注规范

### 标注情况

- **重大变化** → 标（功能移除、核心机制变化、性能 50%+）
- **前沿版新功能** → 标（XX 版本新增）

### 不标

- 稳定版常规概念
- 日常改进、bug 修复

## 汇报

领取任务后先设置 working，完成后设置 completed：

```bash
# 开始时
python scripts/task_runner.py --update <task_id> working "开始处理"
# 完成后
python scripts/task_runner.py --update <task_id> completed "<简要结果>"
```

`<task_id>` 从 tasks.json 中获取（如 task_001_prereq），`<简要结果>` 需包含执行的操作（如「写入了XX内容、修改了YY内容、删除了ZZ内容」）
