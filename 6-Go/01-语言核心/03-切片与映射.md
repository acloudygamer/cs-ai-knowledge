# 切片与映射

> 前置：[02-类型与变量](./02-类型与变量.md) · 后续：[04-控制流程](./04-控制流程.md)

> **版本基准**：Go 1.27（stable = latest）。本篇示例实测环境：go1.27.1 windows/amd64。

## 本质

`slice` 与 `map` 是 Go 的两个**内置容器**——它们不是标准库类型，是语言内建，因此能享受 `append`、`range`、`len`、`make` 这些关键字级的语法支持。

两者的结构完全不同，但有一条共同的边界：**它们都是引用语义，且都是"描述符 + 背后数据"的两层结构**。

| | 描述符（变量里存的） | 背后的数据 | 谁管数据 |
|---|---|---|---|
| `slice` | 三个机器字：指针、长度、容量 | 一个连续数组 | 你（可以持有多份描述符指向同一数组） |
| `map` | 一个指针 | 哈希表（桶数组 + 溢出链） | 运行时（描述符指向它，你拿不到桶） |

**切片的描述符是值，map 的描述符是指针**——这条差异决定了两者最重要的行为分歧：

- 切片作为参数传递时，**描述符被复制**（三个字），因此函数内 `append` 出新切片不影响调用方，但**改元素会影响**（底层数组共享）。
- map 作为参数传递时，**指针被复制**，因此函数内增删元素**调用方可见**。

`slice` 与 `array` 的关系也由这张表定义：数组就是"背后的数据"本身，切片是它的一个窗口。`[3]int` 是值类型（赋值即拷贝整个数组），`[]int` 是引用语义。

## 机制

### 切片的扩容：实测的增长曲线

`append` 在容量不够时重新分配并拷贝。**增长策略是分段的**——容量小于 256 时翻倍，之后按约 1.25 倍增长：

```console
$ go run .
len  cap   扩容点
  1     4   ← -1→4
  5     8   ← 4→8
  9    16   ← 8→16
 17    32   ← 16→32
```

小容量阶段是干净的倍增：4 → 8 → 16 → 32。**首次扩容的容量是 4 而不是 1**，这是运行时的最小分配粒度：`[]int`（8 字节/元素）、`[]byte`（1 字节）、`[]string`（16 字节）三种类型首次 `append` 的容量分别是 4、32、2——**都恰好是 32 字节**。

跨过 256 之后，增长系数开始下降，收敛到 1.25：

```console
$ go run .
cap 256 → 512  (×2.0000)
cap 512 → 848  (×1.6562)
cap 848 → 1280 (×1.5094)
cap 1280 → 1792 (×1.4000)
cap 1792 → 2560 (×1.4286)
```

这组数字来自 `runtime/slice.go` 的 `nextslicecap`（go1.27.1 源码）：

```go
const threshold = 256
if oldCap < threshold {
    return doublecap            // 小于 256：翻倍
}
for {
    newcap += (newcap + 3*threshold) >> 2   // 大于等于 256：每次加 (newcap+768)/4
    if uint(newcap) >= uint(newLen) {
        break
    }
}
```

`(newcap + 768) >> 2` 就是 `newcap/4 + 192`——**固定项 192 让增长系数从 2 平滑滑向 1.25**，而不是在 256 处硬切。验算 512：`512 + (512+768)/4 = 512 + 320 = 832`，再经 `roundupsize` 按页对齐得到 848（实测值）。1792 同理：`1792 + (1792+768)/4 = 2432` 个元素 = 19456 字节，向上取整到 5 页 = 20480 字节 = 2560 个元素（实测值）。

**约束**：增长系数收敛到 1.25 而不是继续翻倍，是**空间换时间的反向权衡**——翻倍浪费空间（最坏情况一半容量闲置），1.25 倍浪费少但拷贝次数多。Go 选了后者，因为切片常驻内存的时间远长于扩容的瞬间。

**给使用者的结论**：能预估大小时用 `make([]T, 0, n)` 预分配。这不仅是省拷贝——它让底层数组只分配一次，避免中间态数组成为 GC 的负担（[03-运行时与内存/03](../03-运行时与内存/03-垃圾回收.md)）。

### 切片的共享：最容易出错的地方

```console
$ go run .
a = [1 99 3 4 5]  b = [99 3]  → 修改 b 影响 a
三索引后 append 不污染 a: [1 99 3 4 5]  c = [99 3 77]
copy 后 a = [1 99 3 4 5]  d = [-1 99 3 4 5]
```

`b := a[1:3]` 不拷贝数据，只新建一个描述符指向 `a` 的同一块数组。`b[0] = 99` 直接写进那块数组，`a[1]` 跟着变。

**三索引切片** `a[1:3:3]` 多给一个容量上界，把 `b` 的容量从"一直到 a 的末尾"压到 3。此后 `append(c, 77)` 发现容量不足，**必须重新分配**，于是不再污染 `a`。这是控制共享的主动手段：

| 写法 | len | cap | append 会污染 a 吗 |
|---|---|---|---|
| `a[1:3]` | 2 | 4 | 会（cap 够，原地写） |
| `a[1:3:3]` | 2 | 2 | 不会（cap 不够，重新分配） |

需要完全独立就 `copy`（或 `slices.Clone`）。

**约束**：切片不能比较（除与 `nil`），因为"相等"没有唯一含义——同一数组的两个窗口内容相同但描述符不同。`slices.Equal` 做逐元素比较，复杂度 $O(n)$。

### nil 切片与空切片等价

```console
$ go run .
nil 切片 len = 0 cap = 0 append 可用 = [1]
slices.Equal(nil切片, 空切片) = true
```

`var n []int` 是 nil 切片，`[]int{}` 是空切片——`len`、`cap` 都是 0，`append` 都能用，`slices.Equal` 判等。**唯一区别是 `n == nil`**，而这个区别只在序列化时暴露：`json.Marshal` 把 nil 切片输出成 `null`，空切片输出成 `[]`（[02-标准库/05](../02-标准库/05-序列化与编码.md)）。

### map 的迭代顺序不确定

```console
$ go run .
map 遍历顺序: [d a b c]
map 遍历顺序: [b c d a]
map 遍历顺序: [a b c d]
```

同一个 map，连续三次 `range` 给出三种顺序。**这是有意设计的**，不是实现缺陷：如果顺序固定，程序会不知不觉依赖它，而 map 的扩容会打乱顺序——那将是一个极难复现的 bug。运行时干脆在每次 `range` 开始时随机选一个起点，把这个依赖在开发阶段就暴露出来。

**约束**：需要有序遍历必须自己排。`maps.Keys`（Go 1.23 起返回迭代器）配合 `slices.Sorted`：

```go
for _, k := range slices.Sorted(maps.Keys(m)) { ... }
```

### map 的零值与 `comma ok`

```console
$ go run .
m["a"] = 1 true
m["zzz"] = 0 false （零值 + false）
```

`m["zzz"]` 对不存在的键返回**值类型的零值**——不 panic，也不报错。这就是为什么读取 map 几乎总该用两值形式：单值形式无法区分"键不存在"与"键存在但值是零值"。

```go
if v, ok := m[k]; ok { ... }   // 惯用形式
```

**约束**：map 的键必须**可比较**——`slice`、`map`、`func` 不能作键（编译期报错）。`struct` 作键要求所有字段可比较；含 `slice` 字段的 struct 不能作键。

**map 的零值是 nil**：`var m map[string]int` 可以读（返回零值），**不能写**——写入 nil map 直接 panic。用 `make` 或字面量初始化。

### 并发访问

**map 不是并发安全的**。多个 goroutine 同时读写同一个 map 会触发运行时的 `fatal error: concurrent map writes`——这是**不可恢复的**，`recover` 抓不住。切片同样，共享底层数组的并发写会丢数据且不报错。

需要并发访问时用 `sync.RWMutex` 保护，或用 `sync.Map`（[04-并发/03](../04-并发/03-sync与原子操作.md) 给了两者的实测对比）。

**与其它语言对照**：Go 的切片等价于"带容量的 `std::vector` 视图 + 显式共享语义"，而 Python 的 list、Java 的 `ArrayList` 都是独立对象、赋值即别名但不会共享底层数组的一部分。**切片能共享底层数组是 Go 独有的**，这也是三索引切片这个语法存在的唯一理由。
