# 错误处理

> 前置：[09-泛型](./09-泛型.md) · 后续：[11-包与可见性](./11-包与可见性.md)

> **版本基准**：Go 1.27（stable = latest）。本篇示例实测环境：go1.27.1 windows/amd64。

## 本质

**`error` 是一个接口，错误是一个值。**

```go
type error interface {
	Error() string
}
```

这行定义决定了 Go 错误处理的全部形状。没有异常、没有 `try`/`catch`、没有 `finally`——**错误是函数的普通返回值**，和其它返回值一样沿调用链向上传。

**约束的由来**：Go 的设计者把"错误"和"异常"当成两件事：

| | 错误（error） | 异常（exception） |
|---|---|---|
| 是什么 | 预期内的失败（文件不存在、网络超时、参数非法） | 预期外的失控（空指针、数组越界、断言失败） |
| 谁处理 | 调用方，作为正常控制流 | 最近的 catch，通常远离发生点 |
| 控制流 | 显式：`if err != nil` | 隐式：栈展开 |
| Go 里对应 | `error` 返回值 | `panic` |

**这条分野的代价是显式的重复**：`if err != nil { return err }` 会写很多遍。收益是**每一处失败的处理点都在源码里看得见**——读一个函数就能知道它在哪里会失败、失败后怎么办，不需要知道有哪些 catch 在栈上等着。

## 机制

### 三种创建方式

```go
errors.New("not found")                          // 无上下文的哨兵
fmt.Errorf("find: %w", ErrNotFound)              // 包装，保留原因
&QueryErr{Table: "users", Err: os.ErrPermission} // 自定义类型，带结构化字段
```

`%w` 与 `%v` 的差别是**是否保留因果链**：`%w` 让 `errors.Is`/`errors.As` 能穿透到被包装的错误，`%v` 只是把它变成字符串，链就断了。

### `errors.Is`：按值匹配整条链

```console
$ go run .
1) err            = find: not found
   errors.Is 哨兵  = true
   errors.Is 无关  = false
   errors.Unwrap   = not found
2) 两层包装       = service: find: not found
   仍能 Is 到哨兵  = true
```

`errors.Is(err, target)` 沿 `Unwrap()` 链**逐层比较**，直到找到相等的一层或链结束。上面的 `err` 是 `fmt.Errorf("find: %w", ErrNotFound)`，`Is` 穿透包装命中了 `ErrNotFound`。

**不要用 `==` 比较错误**（除非确认无包装）。`err == ErrNotFound` 在 `err` 被包装过时是 `false`。

### `errors.As`：取出链上的具体类型

```console
$ go run .
3) errors.As 成功 = true  Table = users
   包装链上都是啥  = true
4) 行为接口 As    = true
```

`errors.As(err, &target)` 沿链查找**第一个能赋值给 `target` 指向类型的错误**。目标必须是**指针的指针**（`*QueryErr` 的地址），因为它要写回结果。

注意第 3 行的第二个值：`errors.Is(e3, os.ErrPermission)` 也是 `true`——因为 `QueryErr` 实现了 `Unwrap()` 返回内层错误，链是打通的。**自定义错误类型要实现 `Unwrap() error` 才能参与 `Is`/`As` 的穿透**，否则链在它这里断掉。

第 4 行演示了更松的用法：目标是**行为接口**（`Temporary`）而不是具体类型。`errors.As` 不关心错误是什么类型，只关心它**能不能做某件事**。这是 Go 错误处理里最有表达力的一招——调用方不必知道错误的具体类型，只需知道"它能不能重试"。

### `errors.Join`：多错误聚合

```console
$ go run .
5) Join 的字符串  = not found
permission denied
   两个都 Is 到    = true true
```

`errors.Join`（Go 1.20）把多个错误合成一个，`Error()` 用换行连接，`Is`/`As` 对**每一个**都生效。适合"批量操作中多个失败"的场景——比如并发校验若干字段，把所有失败一次性返回（[04-并发/05](../04-并发/05-并发模式与竞态诊断.md) 的 `errgroup` 就常配合它用）。

### 哨兵错误 vs 自定义类型 vs 行为接口

| 方式 | 判据 | 例子 |
|---|---|---|
| **哨兵错误**（包级 `var ErrXxx`） | 调用方只需知道"是这一类失败" | `io.EOF`、`sql.ErrNoRows`、`os.ErrNotExist` |
| **自定义类型** | 调用方需要读取**结构化字段** | `*os.PathError` 带 `Op`/`Path`/`Err` |
| **行为接口** | 调用方需要问"能不能做某事" | `net.Error` 的 `Timeout()`、`Temporary()` |

**约束**：哨兵错误是**导出的包级变量**，因此调用方能用 `errors.Is` 引用它。这把它变成 API 的一部分——一旦发布就不能改语义（[11-包与可见性](./11-包与可见性.md)）。

### `panic` 与 `recover`：另一套机制

```console
$ go run .
6) safeDiv(1,0)   = 0 除零: runtime error: integer divide by zero
7) 非 defer 的 recover = <nil>
8) 子 goroutine 内部 recover 成功: 子 goroutine 崩溃
```

三条规则：

**一、`recover()` 只在 `defer` 中有效**。第 7 行的 `notInDefer` 直接调用 `recover()` 返回 `nil`——它不在延迟调用里，抓不到任何东西。这是语言层面的规定，不是运行时限制。

**二、`recover` 抓得住本 goroutine 的 panic**。第 6 行在 `defer` 里 recover 了除零 panic，并把它转成了 `error` 返回值。这是"把不可恢复的失败降级为可返回的错误"的标准写法。

**三、panic 不会跨 goroutine**。第 8 行在子 goroutine **内部** recover 成功了；但如果子 goroutine 不 recover，整个进程会崩溃——**父 goroutine 的 `defer`/`recover` 抓不住它**。这是 Go 程序最常见的线上崩溃来源：一个后台 goroutine 的 panic 会带走整个服务。

**判据**（Go 官方 FAQ 的立场）：`panic` 用于**程序无法继续**的情况——初始化失败、不变量被破坏、调用方违反了 API 契约（比如传了 nil 却要求非 nil）。**不要用 panic 做错误传递**，那等于把错误变成了隐式控制流，正是 Go 要避免的东西。

**边界**：`recover` 不能恢复所有 panic。并发 map 读写（`fatal error: concurrent map writes`）、栈溢出、`runtime.throw` 触发的致命错误**无法被 recover**——它们直接终止进程。

## 连接

**上游**：[08-接口](./08-接口.md)——`error` 就是一个单方法接口，`errors.As` 的行为接口用法是隐式满足的直接应用；[09-泛型](./09-泛型.md) 与反射（[03-运行时与内存/04](../03-运行时与内存/04-反射.md)）是另外两种绕过编译期检查的手段，错误处理则是**在编译期检查之内**传递失败信息。

**下游**：错误在所有 I/O 边界上出现——`os.Open`、`net.Dial`、`http.Client.Do`、`db.QueryContext` 都返回 `error`（[05-IO与外部世界](../05-IO与外部世界/)）；错误与日志的分工见 [05-IO与外部世界/05](../05-IO与外部世界/05-日志与可观测性.md)（**错误该包装后返回，日志该在边界处记一次**，不要层层都记）。

**与其它语言对照**：

| | Java | Rust | Go |
|---|---|---|---|
| 机制 | 受检异常 + 运行时异常 | `Result<T, E>` | `error` 返回值 |
| 编译器强制 | 受检异常强制处理 | 强制处理 | **不强制**（可以忽略返回值） |
| 传播成本 | 隐式栈展开 | `?` 运算符 | 显式 `if err != nil` |
| 能否忽略 | 运行时异常可以 | 需要显式 `unwrap` | **可以完全不管** |

Go 是四者中**唯一不强制处理错误**的。`go vet` 的 `errcheck` 类工具（[06-工程与工具链/03](../06-工程与工具链/03-代码质量工具.md)）就是用来补这个缺口的——把"忘了检查 err"从运行时问题变成静态检查问题。
