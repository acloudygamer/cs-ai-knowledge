# 接口

> 前置：[07-结构体与组合](./07-结构体与组合.md) · 后续：[09-泛型](./09-泛型.md)

> **版本基准**：Go 1.27（stable = latest）。本篇示例实测环境：go1.27.1 windows/amd64。

## 本质

**接口是一个方法集的约束**：任何拥有这些方法的类型都满足它，不需要声明。

```go
type Speaker interface{ Speak() string }
```

这一行说的不是"`Speaker` 是什么类型"，而是"**满足 `Speaker` 需要什么**"。类型与接口之间的关系是**满足**（satisfy），不是继承、不是实现——**并且是隐式的**：`Dog` 的定义里没有任何地方提到 `Speaker`。

**约束：为什么隐式？** 这是 Go 与 Java/C++ 最大的分野，值得交代清楚它换来了什么：

| | 显式 `implements`（Java） | 隐式满足（Go） |
|---|---|---|
| 谁决定连接 | 类型的作者 | **接口的作者** |
| 能否为已有类型补接口 | 不能（要改那个类型） | **能**（新接口自动被已有类型满足） |
| 编译期检查点 | 类型定义处 | **赋值给接口处** |
| 代价 | 类型必须预先知道所有接口 | **编译器要检查的点分散**，错误信息出现在使用处 |

隐式满足让"**接口属于使用方**"成为可能：调用方在自己的包里定义"我需要什么"，任何满足它的实现都能用——包括标准库的 `*os.File`、第三方的类型、你昨天写的类型。Java 里要这么做，得让 `*os.File` 的作者去 `implements` 你的接口。

**代价是错误后置**：`Dog` 少写一个方法，编译器不会在 `Dog` 定义处报错，而是在**你用 `Dog` 当 `Speaker` 的地方**报错。方法多、接口多时，排查链条会更长。

## 机制

### 小接口：标准库的设计倾向

Go 标准库的接口**几乎都是单方法或双方法**：

| 接口 | 方法 | 位置 |
|---|---|---|
| `io.Reader` | `Read(p []byte) (int, error)` | `io` |
| `io.Writer` | `Write(p []byte) (int, error)` | `io` |
| `error` | `Error() string` | 内建 |
| `fmt.Stringer` | `String() string` | `fmt` |
| `http.Handler` | `ServeHTTP(ResponseWriter, *Request)` | `net/http` |
| `sort.Interface` | `Len`/`Less`/`Swap` | `sort` |

**约束**：接口的方法数决定**满足它的类型有多少**。`io.Reader` 只有一个方法，所以文件、TCP 连接、HTTP body、压缩流、字符串、字节缓冲全都满足它——这才有了 [02-标准库/02](../02-标准库/02-io与bufio.md) 里"一切可以互相套接"的能力。一个十方法的接口，能满足它的类型必然寥寥。

**Rob Pike 的说法是"接口越大，抽象越弱"**：方法越多，约束越具体，能落进去的实现越少。

### 接口组合

接口可以嵌入接口，方法集取并集：

```go
type Both interface {
	Speaker
	KindNamer
}
```

```console
$ go run .
组合接口: 旺财 发出声音 / dog:柴犬
```

`io.ReadWriter` = `io.Reader` ∪ `io.Writer`，`io.ReadWriteCloser` = 三者并集。**组合的语义是纯集合运算**——没有优先级、没有覆盖，同名同签名的方法只算一个。因此不存在"接口冲突"这回事（不像嵌入 struct 会遇到方法歧义）。

### 接口的 nil 陷阱

**这是 Go 最著名的坑**：

```console
$ go run .
e == nil          : true
e 持有 (*MyErr)(nil): false  e = boom
```

`error` 是接口。接口值在运行时是**两个字段**：一个类型指针、一个数据指针。

```go
var me *MyErr        // me 是 nil 指针
var e error = me     // e 的类型字段是 *MyErr，数据字段是 nil
e == nil             // false —— 类型字段非空
```

**判据**：接口值为 nil，当且仅当**类型字段和数据字段都为空**。一个"装着 nil 指针的非 nil 接口"调用方法时，会进到方法体里，然后 `e` 的接收者是 nil——`(*MyErr).Error()` 因为不碰字段而正常返回 `"boom"`，但换成访问字段的方法就会 panic。

**约束**：返回接口的函数**不能返回具体的 nil 指针**。下面这段是经典 bug：

```go
func mayFail(ok bool) error {
	var p *MyErr
	if ok {
		p = &MyErr{}
	}
	return p          // ok=false 时返回的不是 nil error！
}
```

正确写法是 `return nil` 或显式声明 `var err error`。

### 类型断言与 type switch

```console
$ go run .
断言成功: 旺财 发出声音
断言 int 失败，ok = false
type switch → Dog, Breed = 柴犬
```

两值形式的断言 `v, ok := x.(T)` **永不 panic**——失败时 `v` 是零值、`ok` 是 false。单值形式 `v := x.(T)` 失败时 panic，只在**确定类型**时使用。

`switch v := x.(type)` 按**声明顺序**匹配第一个成功的 case，`default` 兜底。注意它**不是**按最具体类型匹配——`case Animal` 写在 `case Dog` 前面时，`Dog` 值会被 `Animal` 抢先匹配吗？不会：类型 switch 用的是**精确类型匹配**（不是接口满足），`Dog` 值在 `case Animal` 分支下不匹配，因为 `Dog` 与 `Animal` 是两个不同的类型（[07-结构体与组合](./07-结构体与组合.md)）。

**`any` 是空接口**（`interface{}` 的别名，Go 1.18 起）。所有类型都满足它，因此它不提供任何约束——**用 `any` 就等于放弃类型检查**。它该出现在真正的边界上（JSON 反序列化、反射入参），不该出现在内部 API 里。

### 接口的运行时表示

接口值在运行时有两种形态：

| 形态 | 用于 | 结构 |
|---|---|---|
| `iface` | 带方法的接口 | 两个指针：`itab`（类型 + 方法表）、数据指针 |
| `eface` | 空接口 `any` | 两个指针：类型描述符、数据指针 |

`itab` 是**缓存**——同一个（接口, 具体类型）组合只会生成一份 itab，之后调用只需查一次表。这是 [09-设计模式/01](../09-设计模式/01-设计模式总览.md) 里那个实测数据的来源：多态切片上的接口调用 8.924 ns/op vs 具体类型 3.803 ns/op，差价就是查 itab 与不能内联。

**下游**：[09-泛型](./09-泛型.md) 是接口约束的推广——类型约束就是"接口 + 类型集合运算"；[10-错误处理](./10-错误处理.md) 的核心 `error` 就是一个单方法接口。

**与其它语言对照**：

| | 抽象基类 | 接口 |
|---|---|---|
| C++ | 有（纯虚函数 + 多继承） | 无独立概念 |
| Java | 有（单继承） | 有，**显式 implements** |
| **Go** | **无** | **有，隐式满足** |

Go 没有抽象基类这个选项。所有"需要一个可替换的实现"的场景都必须走接口，而接口**不携带任何实现**——想要共享实现，用嵌入（[07-结构体与组合](./07-结构体与组合.md)），两者正交。这消除了 C++ 里"为了复用实现而被迫继承"的纠缠。
