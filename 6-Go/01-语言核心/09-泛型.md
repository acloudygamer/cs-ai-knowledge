# 泛型

> 前置：[08-接口](./08-接口.md) · 后续：[10-错误处理](./10-错误处理.md)

> **版本基准**：Go 1.27（stable = latest）。本篇示例实测环境：go1.27.1 windows/amd64。

## 本质

**类型参数**（type parameter）让一个函数或类型在**定义时**把某些类型留成变量，在**使用时**再填进去。

```go
func Sum[T Number](s []T) T { ... }
```

`[T Number]` 是类型参数列表：`T` 是类型变量，`Number` 是**约束**（constraint）——它规定了 `T` 能取哪些类型。约束是接口（[08-接口](./08-接口.md)）的推广：Go 1.18 起，接口可以出现在**类型集合**的位置（`~int | ~int64`），这在泛型之前是不合法的语法。

**约束的由来**：Go 1.18（2022-03-15）之前，同一段逻辑要为 `int`、`int64`、`float64` 各写一遍，或者退化成 `interface{}` + 类型断言——后者放弃编译期检查，还带来装箱开销。泛型的出现填的就是这个位置。

**边界**：泛型**不能**替代接口。判据是：

| 问题 | 用 |
|---|---|
| 不同类型上跑**同一段逻辑**，类型在编译期已知 | 泛型 |
| 运行时需要**替换实现**，类型在编译期未知 | 接口 |
| 只有一种类型参数化，且是"容器" | 泛型 |
| 需要调用方提供**行为**（方法） | 接口（约束可以嵌接口，但运行时多态仍是接口的活） |

## 机制

### 基本形态与类型推导

```go
func Map[T, U any](s []T, f func(T) U) []U {
	r := make([]U, len(s))
	for i, v := range s {
		r[i] = f(v)
	}
	return r
}
```

```console
$ go run .
Map: [10 20 30]
```

调用 `Map([]int{1,2,3}, func(i int) string {...})` 时**没有写类型参数**——编译器从实参推导出 `T=int`、`U=string`。推导的输入是实参类型，规则是"用实参类型去匹配形参类型"。

**约束**：推导失败时必须显式写，语法是 `Sum[int](s)`（不是 `Sum<int>(s)`，Go 没有尖括号）。推导失败常见于**只从返回值推导**的场景——`T` 不出现在任何实参里时，编译器无从下手。

### 约束：`~T` 与类型集合

```go
type Number interface {
	~int | ~int64 | ~float64
}
```

```console
$ go run .
Sum[int]: 6
Sum[float64]: 4
Sum[MyInt]: 6
```

三个要点：

**一、`|` 是类型并集。** `Number` 这个约束允许 `T` 是 `int`、`int64`、`float64` 三者之一。

**二、`~` 是"底层类型为"**。`~int` 匹配所有**底层类型是 `int`** 的类型——所以 `type MyInt int` 也满足，`Sum([]MyInt{1,2,3})` 编译通过。没有 `~` 的 `int` 只匹配 `int` 本身。这是 `~` 存在的唯一理由：**让用户定义的类型能享受为内建类型写的泛型代码**。

**三、`Number` 的语法形态是接口，但它是"带类型集合的接口"**，只在**约束位置**合法，不能用来声明变量类型：

```console
$ go build ./...
.\bad.go:4:8: cannot use type Number outside a type constraint: interface contains type constraints
```

（对照：不含类型集合的普通接口 `interface{ M() }` 可以照常当变量类型用。）

`~` 的作用可以用一条报错反过来确认——把 `PlainInt`（`interface{ int }`，无 `~`）用在 `MyInt` 上：

```console
$ go build ./...
.\main.go:14:23: MyInt does not satisfy PlainInt (possibly missing ~ for int in PlainInt)
```

编译器直接把"你是不是漏了 `~`"写进了错误信息。

**约束**：`comparable` 是语言内建的约束，匹配所有可用 `==` 比较的类型（`Contains[T comparable]` 就是这么写的）。它是唯一不能用类型集合表达的约束——因为"可比较"不是枚举出来的。

### Go 1.27：泛型方法

在 1.27 之前，**方法不能有自己的类型参数**——只有包级函数能泛型化。要在方法上做类型变换，只能把接收者写成接口或 `any`。

1.27 放开了这条：

```go
type Vec[T Number] struct{ xs []T }

func (v *Vec[T]) MapTo[U Number](f func(T) U) *Vec[U] {
	out := &Vec[U]{}
	for _, x := range v.xs {
		out.Push(f(x))
	}
	return out
}
```

```console
$ go run .
泛型方法 MapTo: [0.5 1 1.5]
```

`MapTo` 自己声明了 `[U Number]`，与接收者类型参数 `T` 相互独立。**这条限制的解除是有选择的**，官方 release notes 明确列出两条仍然禁止的：

- **接口的方法不能声明类型参数**——否则"某个类型是否满足这个接口"就无法在编译期判定。
- **泛型方法不能实现接口方法**——同理，接口要求的是固定签名。

`math/rand/v2` 的 `(*Rand).N` 是标准库里的第一个用例：它从 1.27 前的一个包级函数 `rand.N[Int]` 变成了方法 `r.N(10)`，类型参数从实参推导，调用处不必写类型。

### 泛型类型与标准库

```go
type Pair[K comparable, V any] struct {
	K K
	V V
}
```

泛型类型可以有多个类型参数，每个有自己的约束。标准库从 Go 1.21 起提供 `slices` 与 `maps` 两个泛型包：

```console
$ go run .
slices.Sort: [1 2 3]
```

`slices.Sort`、`slices.Contains`、`slices.Index`、`maps.Keys`、`maps.Values` 都是泛型的。**它们取代的是 `sort.Slice` + 反射的老写法**——后者要传 `less func(i, j int) bool`，在运行时用反射交换元素，而 `slices.Sort` 直接生成具体类型的比较代码。

### 实现方式：GC shape stenciling

Go 的泛型**不是** C++ 的模板（每个类型实参生成一份代码），**也不是** Java 的类型擦除（全部擦成 `Object`）。

Go 用的是 **GC shape stenciling**：把类型按"GC 形态"（大小与是否含指针）分组，同一组共用一个函数实例，组内的差异通过一个**字典**（dictionary）在运行时提供。

**约束与代价**：

- 同一 GC shape 的多个类型共享代码 → **二进制不会像 C++ 那样膨胀**。
- 但共享意味着**不能像 C++ 那样对每个类型做专门优化**——字典查表有开销。
- 这也是为什么 Go 的泛型约束不能像 C++ 模板那样"只要用到了就报错"（C++ 的 SFINAE 与 concepts 是编译期图灵完备的），Go 的约束是**类型集合**，能力刻意受限。

**判据**：如果一段代码的性能关键路径上大量使用泛型，值得实测对比一下泛型版本与具体类型版本的差距——共享代码实例意味着失去部分内联机会（[03-运行时与内存/07](../03-运行时与内存/07-性能剖析与调优.md)）。

**与其它语言对照**：

| | C++ 模板 | Java 泛型 | Go 泛型 |
|---|---|---|---|
| 实现 | 每类型实例化 | 类型擦除 | GC shape + 字典 |
| 约束能力 | 图灵完备（concepts） | 有界通配符 | 类型集合（刻意受限） |
| 二进制膨胀 | 显著 | 无 | 有限 |
| 何时检查 | 实例化时 | 编译期 | 编译期 |

Go 的选择是**用表达能力换可预测性**：约束只能是类型集合，不能表达"这个类型必须有 `+` 运算符且返回值可赋值给 `T`"这类关系。代价是有些 C++ 模板能写的抽象 Go 写不了；收益是编译速度不随泛型使用量爆炸。
