# 安装与第一个程序

> 前置：[00-概览/01-Go全景](../00-概览/01-Go全景.md) · 后续：[02-类型与变量](./02-类型与变量.md)

> **版本基准**：Go 1.27（stable = latest）。本篇示例实测环境：go1.27.1 windows/amd64。

## 本质

安装 Go 装的是**一个二进制目录**，不是一个虚拟机、不是一个包管理器。解压 `go1.27.1.windows-amd64.zip` 得到的 `go/` 目录里有 `bin/go.exe` 和 `pkg/`、`src/`：

```console
$ ls "$(go env GOROOT)"
api/  bin/  doc/  go.env  lib/  misc/  pkg/  src/  test/  VERSION
```

`GOROOT` 指向这个目录，它包含**工具链本身 + 标准库源码 + 标准库预编译归档**。没有安装向导、没有注册表项、没有系统级服务——把目录拷到另一台机器、设好 `PATH`，Go 就能用。这与 JVM 需要 `JAVA_HOME` + 独立 JDK 发行版、Python 需要区分解释器与 site-packages 的形态不同：Go 的"运行时"不是一个要单独装的组件，它已经在工具链里，最终被链接进你的产物（见 [00-概览/01](../00-概览/01-Go全景.md)）。

**第一个程序的全部构成**：

```go
package main

import "fmt"

func main() {
	fmt.Println("hello, 世界")
}
```

三行非空代码，三个规定性成分：`package main` 声明这是可执行包（[11-包与可见性](./11-包与可见性.md)），`import "fmt"` 引入标准库包（[02-标准库](../02-标准库/)），`func main()` 是入口（[05-函数](./05-函数.md)）。**没有分号，没有返回类型，没有类包装**——Go 的程序不要求你把 `main` 放进任何容器里。

## 机制

### 安装：两条路

**官方归档**（跨平台一致，不污染系统）：

```console
$ curl -O https://go.dev/dl/go1.27.1.windows-amd64.zip
$ unzip go1.27.1.windows-amd64.zip -d "$LOCALAPPDATA/Programs"
$ export PATH="$PATH:$LOCALAPPDATA/Programs/go/bin"     # Windows 上写进用户 PATH
$ go version
go version go1.27.1 windows/amd64
```

**包管理器**（Windows 上 `winget install GoLang.Go`、macOS 上 `brew install go`）会装到系统目录并自动配好 `PATH`。两者产出的 `GOROOT` 内容相同，区别只在安装位置与升级方式。下载后建议核对官方公布的 SHA-256——归档页的 `?mode=json` 接口同时给出哈希与文件名：

```console
$ curl -s 'https://go.dev/dl/?mode=json' | head -c 200
[{"version":"go1.27.1","stable":true,...
```

**版本选择**：Go 无 LTS，每 6 个月一个次版本，官方按"最近两个 major release"提供安全修复。写作时受支持的是 1.27 与 1.26，1.25 的支持已随 1.27 发布结束。生产环境跟最新版即可，不必等 LTS。

### 四个环境变量：Go 把什么放在哪里

`go env` 输出的键有几十个，但只有四个决定文件往哪写、从哪读：

```console
$ go env GOROOT GOPATH GOBIN GOMODCACHE GOCACHE
C:\Users\zyq\AppData\Local\Programs\go
C:\Users\zyq\go
C:\Users\zyq\go\bin
C:\Users\zyq\go\pkg\mod
C:\Users\zyq\AppData\Local\go-build
```

| 变量 | 是什么 | 谁写它 | 能否删 |
|---|---|---|---|
| `GOROOT` | 工具链 + 标准库的安装位置 | 安装时确定 | 否——删了 Go 就没了 |
| `GOPATH` | 工作区根，默认 `~/go` | 首次运行自动建 | 否——下面两个的父目录 |
| `GOBIN` | `go install` 装的可执行文件落点（默认 `GOPATH/bin`） | `go install` | 是——重装即可 |
| `GOMODCACHE` | 下载的第三方模块解压后的存放处 | `go get`/`go mod download` | 是——会重新下载 |
| `GOCACHE` | **构建缓存**：按内容哈希存放的编译中间产物 | 每次 `go build` | 是——只是下次变慢 |

后三个都是可删的缓存，判据是"删掉后能否从源码重建"。`GOROOT` 不能，它是源码本身。

`GOCACHE` 是 [00-概览/01](../00-概览/01-Go全景.md) 里那个 5.382s → 0.677s 差距的来源。它按"源码 + 编译标志 + 依赖的导出数据"的内容哈希索引，所以改一个包只重编它和它的下游。

**约束**：`GOROOT` 与 `GOPATH` 不能是同一个目录。前者是只读的（升级时整体替换），后者是可写的（放你的代码、缓存、第三方模块）。混在一起会让 `go` 命令分不清"这是标准库还是我的包"。

### go.mod：从"文件模式"到"模块模式"

新目录里写一个 `main.go` 之后，直接 `go run` 能跑，`go build` 却报错：

```console
$ go env GOMOD
NUL                                  # Windows 上表示"没有 go.mod"

$ go run main.go
hello, 世界

$ go build -o x.exe .
go: go.mod file not found in current directory or any parent directory; see 'go help modules'
```

**`go run` 收一个显式文件列表时走"文件模式"**：把列出的几个 `.go` 文件当一次性程序编译运行，不需要模块上下文。**`go build` 收的是包路径（`.` 表示当前目录的包）**，解析包必须先知道模块边界，因此必须有 `go.mod`。

```console
$ go mod init example/t
$ cat go.mod
module example/t

go 1.27.1
```

`go.mod` 两行：模块路径（这个模块对外叫什么名字，[06-工程与工具链/02](../06-工程与工具链/02-模块与依赖管理.md)）和 `go` 指令（语言版本口径）。Go 1.27 写的是**完整补丁号 `1.27.1`** 而非 `1.27`——`go` 指令自 Go 1.21 起允许带补丁号，用于在工具链层面锁定行为差异。

**约束**：`go` 指令只升不降。它不是一个"我用哪个版本编译"的开关，而是"这段代码依赖哪些版本相关行为"的声明——降级可能让代码用了新语义却声称兼容旧版。

### go run、go build、go install 的分工

| 命令 | 产物 | 产物在哪 | 什么时候用 |
|---|---|---|---|
| `go run .` | 临时可执行文件 | `GOCACHE` 里，运行后不管 | 开发时快速试 |
| `go build -o app.exe .` | 可执行文件 | 你指定的路径 | 要拿到产物 |
| `go build ./...` | 无（只校验） | — | 检查整个模块能否编译 |
| `go install example.com/cmd/x@latest` | 可执行文件 | `GOBIN` | 装工具 |

```console
$ go run .
hello, 世界
$ ls
main.go            # go run 不留下产物
```

`go run` 的"不留产物"是有代价的：每次调用都要走一遍构建缓存查找，缓存未命中就重编。所以**反复运行同一个程序时 `go build` 一次再直接跑二进制更快**。
