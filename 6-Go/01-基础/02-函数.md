# 函数

## 定义

Go 函数的核心价值在于**多返回值机制**——特别是 `(result, error)` 模式，使错误处理成为函数签名的显式组成部分，而非隐藏的异常机制。defer 关键字实现 LIFO 语义的资源清理，闭包允许函数捕获并持久化外部变量状态。Go 函数满足 lambda 演算规则：函数是值，可赋值、可传递、可返回。

## 数学模型

### 函数作为一等公民的 lambda 演算

Go 函数类型满足 **lambda 演算**的基本规则：

设函数类型为 $T \to U$（输入 T，输出 U），则 Go 的函数类型是**闭包**：

$$\text{Closure} = \lambda x. \text{body} + \text{captured\_variables}$$

Go 函数是 lambda 演算的实现：
- **函数是值**：可赋值给变量，作为参数传递，作为返回值
- **词法作用域**：闭包捕获定义时外部变量，而非调用时
- **引用透明**：无副作用的函数可安全求值

### defer 的栈帧模型

defer 调用存储在**调用者栈帧**中，按 LIFO 顺序执行：

$$\text{DeferStack} = \{ d_1, d_2, \ldots, d_n \} \text{ where } d_i \text{ added at position } i$$

执行顺序：$d_n, d_{n-1}, \ldots, d_1$

**defer 结构体的运行时表示**（src/runtime/runtime2.go）：

```go
type g struct {
    _defer *scade  // 指向 defer 链表的头部
}

type scade struct {
    fn       *funcval  // 延迟调用的函数
    sp       uintptr   // 注册时的栈指针（用于验证栈帧）
    pc       uintptr   // 注册时的程序计数器
    link     *scade    // 链表 next
}
```

**约束条件**：
- defer 注册：$O(1)$（仅追加到链表头）
- defer 执行：$O(n)$（函数返回时遍历执行）
- 空间复杂度：每个 defer 结构体占用固定大小（16-32 字节），n 个 defer 占用 $O(n)$ 空间

### 闭包捕获的代数语义

闭包捕获变量时，被捕获变量的**引用**被闭包持有：

$$\text{Closure}(f, \text{captured}) = \lambda x. f(x, \text{captured})$$

**生命周期约束**：
- 闭包内部修改被捕获变量 → 影响外部变量（共享状态）
- 被捕获变量的生命周期 ≥ 闭包的生命周期（否则悬空引用）
- 闭包阻止 GC 回收被捕获变量

**逃逸分析交互**：闭包是否导致变量逃逸，取决于闭包的生命周期：

```go
func adder() func(int) int {
    sum := 0  // adder 返回后闭包仍被引用 → sum 必须逃逸到堆
    return func(x int) int {
        sum += x
        return sum
    }
}

func demo() {
    f := adder()
    f(1)  // sum 在堆上
}
```

### 多返回值的错误传播模型

`(result, error)` 模式满足**结果与错误的正交组合**：

$$\text{Result} = \text{Ok} \oplus \text{Err}$$

其中 $\oplus$ 表示结果和错误的直和——正常值和错误不会互相覆盖。这不同于异常机制中异常会"穿透"调用栈。

## 机制

### 为什么 Go 选择多返回值

多返回值的设计满足**错误传播的组合律**：

相比异常机制的优势：
- **显式处理约束**：错误必须被显式处理，不能忽略（编译器可检测未使用的 error）
- **路径可见性**：错误路径和正常路径在代码中同等地位
- **局部性**：错误可以逐层传播或就地处理

**违反约束的代价**：若忽略 error，编译器不会报错（除非使用 `_`），但这会导致错误被静默忽略。

### 为什么 defer 执行顺序是 LIFO

defer 的 LIFO 执行顺序保证**资源释放的反向顺序**：

```go
defer file.Close()      // 后打开先关闭（file 依赖 fd）
defer mu.Unlock()        // 后加锁先解锁（锁保护临界区）
```

这符合资源管理的**嵌套语义**：内层资源依赖外层资源，内层先获取，外层后释放。LIFO 顺序保证先释放内层，再释放外层。

**违反约束的后果**：若顺序错误，可能导致 use-after-free（文件已关闭但仍被引用）或死锁（锁未释放但已等待）。

### defer 在 panic 时的行为约束

defer 在 panic 时仍然执行，这使得：
- 即使程序崩溃，也能保证资源释放（文件系统句柄、锁状态）
- 可以用 `recover()` 捕获 panic，实现类似异常的处理

**约束**：`recover()` 仅在 defer 中有效，且只在 panic 传播过程中有效。已恢复的 panic 不会继续传播。

**违反约束**：过度使用 panic/recover 破坏 Go 的显式错误处理哲学，使控制流难以追踪。

### recover 的形式化约束

`recover()` 的行为可形式化为：

$$\text{recover}() = \begin{cases} \text{panic\_arg} & \text{如果在 defer 中调用，且当前协程正在 panic} \\ \text{nil} & \text{其他情况} \end{cases}$$

**调用时机约束**：recover 只有在 panic 调用链的**当前函数**的 defer 中调用才有效。recover 不能跨协程捕获 panic。

### 闭包 vs 函数指针

| 维度 | 函数指针 | 闭包 |
|------|----------|------|
| 捕获环境 | 否（仅代码地址） | 是（代码+环境） |
| 状态持久化 | 否 | 是 |
| 内存分配 | 栈（编译时确定） | 堆（逃逸分析决定） |
| 适用场景 | C 回调、插件架构 | 迭代器、工厂函数、延迟求值 |

### 函数式选项模式的数学本质

Option 是函数复合 $f \circ g$ 的应用：

```go
type Option func(*Server)

func WithPort(port int) Option {
    return func(s *Server) { s.port = port }
}
```

多个选项组合时：

$$(\text{WithPort}(9090) \circ \text{WithTimeout}(30s) \circ \text{WithTLS})(\&s)$$

函数式组合替代了建造者模式的链式调用，且支持可选参数和默认值。
