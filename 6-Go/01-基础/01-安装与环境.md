# 安装与环境

## 本质断言

Go 是 Go 语言的开发环境核心——通过 GOPATH（废弃）与 Workspace（Go 1.18+）两种模式管理源代码布局，go mod 管理依赖版本，go workspace 支持多模块并行开发。

## 数学模型

### go.mod 依赖解析的图论模型

go mod 依赖管理可建模为**有向无环图（DAG）**：

$$G = (V, E), V = \text{模块集合}, E = \text{require 依赖关系}$$

版本选择算法采用**最小版本选择（Minimal Version Selection, MVS）**：

$$\text{Version}(m) = \min_{\text{满足所有约束}} \{ \text{版本列表}(m) \}$$

**MVS 约束证明（确定性构建的数学基础）**：

给定依赖图 $G = (V, E)$ 和版本约束函数 $C: V \to 2^{\text{Versions}}$，MVS 通过以下步骤保证确定性：

1. **单调性假设**：依赖包的版本集在其升级时只能增大，不能缩小。形式化：若 $v_1 \leq v_2$（语义版本），则 $C(v_2) \supseteq C(v_1)$。

2. **最小版本选择**：对每个模块 $m$，选择 $\min \{ v \in C(m) \mid \forall d \in \text{依赖}(m): v \geq \text{selected}(d) \}$。

3. **不动点存在性**：定义选择函数 $S: V \to \text{Versions}$，初始时每个模块选择其最小版本，迭代传播约束直到收敛。由于版本域是有限格（按语义版本排序），且约束单调，布劳威尔不动点定理保证收敛。

4. **唯一性证明**：设 $S_1, S_2$ 为两个不动点。对任意 $v \in V$，若 $S_1(v) \neq S_2(v)$，不妨设 $S_1(v) < S_2(v)$。由于 $S_2(v)$ 满足 $S_2$ 的约束，而 $S_1(v)$ 是满足约束的最小版本，矛盾。故不动点唯一。

这确保了**确定性构建**——给定相同的 go.mod，在任何机器上解析出相同的依赖图。

### 模块缓存的存储约束

模块缓存目录：`$GOPATH/pkg/mod/cache/download`

缓存大小无硬限制，但可配置 `GOMODCACHE` 改变位置。

### go build 的并行模型

编译并行度 $p = \min(GOMAXPROCS, \text{包依赖图的并行度})$

对于完全无依赖的包（如多个独立 package），编译速度提升接近 $p$ 倍。

## 机制

### 为什么废弃 GOPATH

GOPATH 模式的问题：
- 所有代码必须在 `$GOPATH/src` 下，限制了项目位置
- 无法同时开发多个版本的同一模块
- 依赖管理依赖第三方工具（dep、glide）

go mod 的改进：
- 任意位置创建项目
- 语义版本锁定（go.sum）
- 传递依赖自动解析

### 为什么需要 go mod tidy

go mod tidy 确保：
1. `go.mod` 中声明的依赖是**实际使用**的
2. `go.sum` 包含所有传递依赖的校验和
3. 清理不再使用的依赖

**幽灵依赖的安全漏洞路径**：

幽灵依赖指 `go.mod` 中声明了但代码实际未 import 的包。其危害路径：

```
间接依赖 A（已知） → 声明 A v1.0
                         ↓
                   代码直接 import A
                         ↓
                   go mod tidy 发现 A 未被使用
                         ↓
                   自动从 go.mod 移除 A
                         ↓
                   下一位开发者运行 go mod tidy
                         ↓
                   A 从 go.mod 消失，go.sum 移除 A 的校验和
```

若 A 是安全漏洞修复版本，开发者可能：
- 不知道代码传递依赖了 A
- 未主动更新到 A 的修复版本
- 幽灵依赖被移除后，攻击者可劫持 A 的旧版本发布含漏洞的 A v1.0.1

**防御机制**：go mod tidy 通过扫描所有 `.go` 文件的 import 语句，计算传递依赖的闭包，确保只有实际被引用的包进入依赖图。

### 为什么需要 go.sum

go.sum 防止**依赖篡改攻击**：
- go.sum 记录每个依赖的 SHA-256 校验和
- `go mod verify` 检查下载的模块是否与记录匹配
- 防止恶意修改的依赖被使用

### go workspace 的设计意图

go workspace 解决**多模块开发**问题：
- 多个相关的 go.mod 需要同时修改
- 不需要 `go mod edit -replace` 手动替换
- `go work sync` 同步所有模块的依赖

## Go Workspace 模式（Go 1.18+）

Workspace 模式是 Go 推荐的源代码组织方式，通过 go.work 文件在开发机器上同时管理多个模块。

### 核心命令

| 命令 | 作用 |
|------|------|
| `go work init` | 创建 workspace |
| `go work use ./module` | 添加模块 |
| `go work sync` | 同步依赖 |

### go.work 文件结构

```
go 1.24.0

use (
    ./module1
    ./module2
)
```

## 模块管理（go mod）

go.mod 是 Go 项目的依赖清单，go get 动态添加版本，go mod tidy 自动整理。

### 核心命令

```
go mod init module_name     # 初始化项目
go mod tidy                # 整理依赖
go get package@version     # 添加依赖
go mod download            # 下载依赖
go mod verify             # 验证完整性
```

### go.mod 文件结构

```
module github.com/user/project

go 1.24.0

require (
    github.com/gin-gonic/gin v1.9.1
)
```

### 替换依赖（本地调试用）

```
go mod edit -replace github.com/pkg/errors=../local/pkg/errors
```

### 私有模块配置

```
GOPRIVATE=github.com/company/*
GOPROXY=https://proxy.golang.org,direct
```

## 环境变量

| 变量 | 说明 | 默认值 |
|------|------|--------|
| GOROOT | Go 安装目录 | 自动检测 |
| GOPATH | 工作区目录 | $HOME/go |
| GOPROXY | 依赖代理 | proxy.golang.org |
| GO111MODULE | 模块模式 | auto |
| GOCACHE | 缓存目录 | $HOME/go-build |

## IDE 配置

### VS Code + Go 扩展

安装官方 Go 扩展后，在 `.vscode/settings.json` 配置：

```json
{
    "go.useLanguageServer": true,
    "go.lintTool": "golangci-lint",
    "go.formatTool": "gofmt",
    "go.testFlags": ["-v", "-race"]
}
```

### GoLand

- File → Settings → Go → Go Modules：启用 proxy
- File → Settings → Go → Testing：启用 race detector
- Ctrl+Shift+R：运行测试
- Ctrl+Shift+T：跳转测试/实现
