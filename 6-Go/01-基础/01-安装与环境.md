# 安装与环境

## 定义

Go 安装与环境是 Go 工具链的**物理布局与依赖解析机制**——通过 go mod 有向无环图（DAG）锁定依赖版本，通过 go workspace 协调多模块并行开发，通过 GOPROXY 代理网络获取模块。版本选择算法 MVS（最小版本选择）保证确定性构建：给定相同 go.mod，在任何机器上解析出相同的依赖图。

## 数学模型

### 依赖解析的 DAG 模型

go mod 依赖管理可建模为**有向无环图（DAG）**：

$$G = (V, E), \quad V = \text{模块集合}, \quad E = \text{require 依赖关系}$$

版本选择采用**最小版本选择（Minimal Version Selection, MVS）**：

$$\text{Version}(m) = \min_{\text{满足所有约束}} \{ \text{版本列表}(m) \}$$

**MVS 的数学证明（确定性构建的保证）**：

给定依赖图 $G = (V, E)$ 和版本约束函数 $C: V \to 2^{\text{Versions}}$，MVS 通过以下步骤保证确定性构建：

1. **单调性假设**：依赖包的版本集在其升级时只能增大，不能缩小。形式化：若 $v_1 \leq v_2$（语义版本序），则 $C(v_2) \supseteq C(v_1)$。

2. **最小版本选择**：对每个模块 $m$，选择 $\min \{ v \in C(m) \mid \forall d \in \text{deps}(m): v \geq \text{selected}(d) \}$。

3. **不动点存在性**：定义选择函数 $S: V \to \text{Versions}$，初始时每个模块选择其最小版本，迭代传播约束直到收敛。由于版本域是有限格（按语义版本排序），且约束单调，布劳威尔不动点定理保证收敛。

4. **唯一性证明**：设 $S_1, S_2$ 为两个不动点。对任意 $v \in V$，若 $S_1(v) \neq S_2(v)$，不妨设 $S_1(v) < S_2(v)$。由于 $S_2(v)$ 满足 $S_2$ 的约束，而 $S_1(v)$ 是满足约束的最小版本，矛盾。故不动点唯一。

### go build 并行编译模型

编译并行度 $p = \min(\text{GOMAXPROCS}, \text{包依赖图的并行度})$

对于完全无依赖的包（如多个独立 package），编译速度提升接近 $p$ 倍。对于有依赖关系的包，并行度受限于 DAG 的宽度。

## 机制

### 为什么废弃 GOPATH

GOPATH 模式的核心问题在于**目录结构的强制耦合**：

- 所有代码必须在 `$GOPATH/src` 下，项目位置受限
- 无法同时开发同一模块的不同版本（版本冲突）
- 依赖管理依赖第三方工具（dep、glide），无统一标准

go mod 的改进：
- **任意位置创建项目**：项目位置与代码布局解耦
- **语义版本锁定**：go.sum 记录精确校验和
- **传递依赖自动解析**：MVS 算法保证一致性

### 为什么需要 go mod tidy

go mod tidy 确保 `go.mod` 中声明的依赖是**实际被 import 的**，其安全价值在于防御**幽灵依赖攻击**：

```
攻击路径：
间接依赖 A（已知有漏洞，修复版本 v1.1） → 声明 A v1.0 在 go.mod
        │
        ▼
代码直接 import A → go mod tidy 发现 A 未被使用
        │
        ▼
自动从 go.mod 移除 A → go.sum 移除 A 的校验和
        │
        ▼
攻击者发布恶意 A v1.0.1（劫持旧版本）
        │
        ▼
下一位开发者运行 go mod tidy → 下载到恶意版本
```

**防御机制**：go mod tidy 扫描所有 `.go` 文件的 import 语句，计算传递依赖的闭包，仅保留实际被引用的包。

### 为什么需要 go.sum

go.sum 防止**依赖篡改攻击**：

- go.sum 记录每个依赖的 SHA-256 校验和
- `go mod verify` 检查下载的模块是否与记录匹配
- 防止中间人攻击替换为恶意模块

### go workspace 的设计意图

go workspace 解决**多模块同步修改**问题：

- 多个相关的 go.mod 需要同时修改（如微服务仓库）
- 不需要 `go mod edit -replace` 手动替换
- `go work sync` 同步所有模块的依赖视图

### 环境变量的约束

| 变量 | 约束/默认值 | 机制 |
|------|-------------|------|
| GOROOT | 自动检测 | Go 安装目录，go 命令行工具定位标准库 |
| GOPATH | `$HOME/go` | 旧模式工作区（已废弃，但仍影响模块缓存路径） |
| GOPROXY | `proxy.golang.org` | 模块下载代理，支持 direct 和 off |
| GO111MODULE | `auto` | auto 模式下，目录有 go.mod 时启用模块模式 |
| GOMODCACHE | `$GOPATH/pkg/mod` | 模块缓存位置 |

## 参考存根

```go
// go.mod 文件结构
module github.com/user/project

go 1.24

require (
    github.com/gin-gonic/gin v1.9.1
)

require github.com/pkg/errors v0.9.1 // indirect
```

```go
// go.work 文件结构
go 1.24

use (
    ./module1
    ./module2
)
```

```bash
# 核心命令
go mod init module_name      # 初始化
go mod tidy                  # 整理依赖（扫描 import 构建闭包）
go get package@version       # 添加依赖
go mod download              # 预下载到缓存
go mod verify               # 校验 go.sum 一致性
go work sync                # 同步 workspace 依赖

# 环境查看
go env GOROOT GOMODCACHE    # 查看关键环境变量
go version                  # 查看 Go 版本
```
