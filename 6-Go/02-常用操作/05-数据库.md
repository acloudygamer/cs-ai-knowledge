# 数据库操作

## 定义

数据库操作是通过 DB-API 2.0 接口（`database/sql`）执行 SQL 语句并获取结果的过程，连接池管理由驱动层负责，应用层只需关注 SQL 构建和结果映射。

数据库操作的本质是**客户端-服务端有状态会话**：客户端通过连接池维护与数据库的持久会话，复用连接避免重复建立 TCP/TLS 握手的开销。

## 数学模型

### 连接池资源模型

设连接池参数：
- $C_{max}$ = `MaxOpenConns`：最大打开连接数
- $C_{idle}$ = `MaxIdleConns`：最大空闲连接数
- $T_{conn}$ = 单次连接建立时间（TCP + 认证 + 初始化）

**连接复用收益**：
- 未复用：每个查询 $T_{conn} + T_{query}$
- 复用：首次 $T_{conn} + T_{query}$，后续仅 $T_{query}$

**资源约束**：
- $C_{idle} \leq C_{max}$（约束）
- 若并发请求 $> C_{max}$：请求排队等待
- 若 $C_{idle}$ 过小：高并发下连接重建频繁

**归约终点**：连接池的效率取决于 $(C_{max}, C_{idle}, T_{conn}, T_{query})$ 四元组的配置是否匹配 workload 特征。

### 连接泄漏检测

监控指标：
- `OpenConnections`：已打开的总连接数
- `InUse`：正在使用的连接数
- `Idle`：空闲连接数

**泄漏判定**：若 `OpenConnections ≈ MaxOpenConns` 且 `InUse ≈ OpenConnections`，说明连接被持有但未释放。

### SQL 注入的数学本质

SQL 注入是**字符串拼接破坏语法的结果**：

```sql
-- 正常查询
SELECT * FROM users WHERE id = 1

-- 注入后（用户输入 "1; DROP TABLE users; --"）
SELECT * FROM users WHERE id = 1; DROP TABLE users; --
```

使用 `?` 占位符时，驱动将参数作为**字面值**转义后嵌入，无法破坏 SQL 语法结构。

**注入的数学描述**：令用户输入为 $u$，查询构造为 $Q(u) = "SELECT * FROM users WHERE id = " + u$。当 $u$ 包含 SQL 元字符（`;`, `--`）时，$Q(u)$ 的语法结构被破坏。

## 机制

### database/sql 连接池的行为

`database/sql` 的连接池是**隐式管理**的：

1. 调用 `Query()`/`Exec()` 时自动获取连接
2. 读取完结果集后（`Rows.Close()`）连接自动归还池
3. 连接生命周期由 `SetConnMaxLifetime` 控制

**关键约束**：
- `Rows` 必须调用 `Close()`，否则连接泄漏
- `QueryRow()` 返回单行，若无数据返回 `ErrNoRows`
- 在事务中，`Begin()` 获取的连接必须通过 `Commit()`/`Rollback()` 释放

### SQL 注入防御

Go 的 `?` 占位符机制：

- 驱动负责转义（不同数据库驱动转义逻辑不同）
- `?` 仅作为**字面值占位符**，不能用于标识符（表名、列名）
- 动态表名/列名需要白名单验证

```go
// 安全：? 占位符
db.Query("SELECT * FROM users WHERE id = ?", userID)

// 不安全：字符串拼接
db.Query("SELECT * FROM users WHERE id = " + userID)
```

### GORM vs sqlx vs 原生 database/sql

| 维度 | database/sql | sqlx | GORM |
|------|-------------|------|------|
| SQL 可见性 | 完整 | 完整 | 隐藏 |
| 性能开销 | 零（直传） | 极低 | 低 |
| 类型安全 | 手动扫描 | 命名扫描 | 编译时检查 |
| 迁移 | 无 | 无 | 原生支持 |
| 关联查询 | 手动 | 手动 | 自动 |
| 适用场景 |极致性能 | 高性能+类型安全 | 快速开发 |

### Redis 分布式锁的正确实现

三要素缺一不可：

1. **原子性 SET**：防止锁被重复获取
2. **唯一值（UUID）**：防止误释放他人持有的锁
3. **Lua 脚本释放**：检查值后删除，保证原子性

```lua
-- 释放锁的 Lua 脚本
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end
```

**违反约束的后果**：
- 无唯一值：客户端 A 释放了客户端 B 的锁
- 无 Lua 脚本：GET 和 DEL 之间可能被其他客户端获取锁

### 批量操作的经济性

设批量大小为 $B$，单条插入时间为 $T_{single}$，批量插入时间为 $T_{batch}$：

- 理论加速比：$S = B \times T_{single} / T_{batch}$
- 实际收益：减少网络 RTT、减少事务开销
- 约束：$B$ 过大导致内存压力、锁竞争加剧

## 参考存根

```go
// database/sql 基本使用
db, _ := sql.Open("mysql", "user:password@tcp(localhost:3306)/dbname")
defer db.Close()

row := db.QueryRow("SELECT name FROM users WHERE id = ?", userID)
var name string
row.Scan(&name)

// sqlx 结构体扫描
var user User
db.Get(&user, "SELECT * FROM users WHERE id = ?", userID)

// GORM 模型定义
type User struct {
    ID   uint   `gorm:"primaryKey"`
    Name string `gorm:"size:255"`
}

// Redis 分布式锁
func acquireLock(ctx context.Context, client *redis.Client, key, value string, ttl time.Duration) (bool, error) {
    return client.SetNX(ctx, key, value, ttl).Result()
}

func releaseLock(ctx context.Context, client *redis.Client, key, value string) error {
    script := `
        if redis.call("GET", KEYS[1]) == ARGV[1] then
            return redis.call("DEL", KEYS[1])
        else
            return 0
        end
    `
    return client.Eval(ctx, script, []string{key}, value).Err()
}

// 批量插入
func batchInsert(db *sql.DB, users []User) error {
    if len(users) == 0 {
        return nil
    }
    tx, err := db.Begin()
    if err != nil {
        return err
    }
    defer tx.Rollback()

    stmt, err := tx.Prepare("INSERT INTO users (name, email) VALUES (?, ?)")
    if err != nil {
        return err
    }
    defer stmt.Close()

    for _, u := range users {
        if _, err := stmt.Exec(u.Name, u.Email); err != nil {
            return err
        }
    }
    return tx.Commit()
}
```

## 连接池调优参考

| 场景 | MaxOpenConns | MaxIdleConns | ConnMaxLifetime |
|------|-------------|--------------|-----------------|
| 低并发 API（< 100 QPS） | 25 | 5 | 5min |
| 高并发 API（> 500 QPS） | 100 | 20 | 5min |
| 批量任务（短生命周期） | CPU核数×2 | 0 | 1min |
| 数据库连接限制严格 | 与 DB max_connections 匹配 | 20% of max | 10min |
