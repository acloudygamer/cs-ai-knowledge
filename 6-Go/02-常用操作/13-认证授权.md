# 认证授权

## 定义

认证（Authentication）是证明"你是谁"的过程（`authn`），授权（Authorization）是决定"你能做什么"的过程（`authz`）。JWT 是认证结果的令牌格式，RBAC 是基于角色的授权模型，两者解决不同问题。

## JWT 签名验证流程

### 定义
JWT 的安全性基于**签名而非加密**——任何人都能解码 Header 和 Payload（Base64），但无法伪造有效签名。`HS256` 签名是 HMAC-SHA256，密钥泄漏等同于令牌伪造。

### 数学模型

**JWT 结构**：$JWT = Base64URL(Header) \cdot Base64URL(Payload) \cdot Base64URL(Signature)$

**签名计算**：
$$Signature = HMAC\_SHA256(Secret, Base64URL(Header) \cdot "." \cdot Base64URL(Payload))$$

**验证**：接收方重新计算签名，与收到的 Signature 比较：
$$\text{Verify} = \text{HMAC\_Equal}(ComputedSignature, ReceivedSignature)$$

**时间复杂度**：HMAC-SHA256 的验证是 O(1) 操作，与 payload 复杂度无关。这使 JWT 验证比传统会话查找快。

**归约终点**：JWT 验证可归结为**密钥对称加密的恒定时间比较**，安全性由密钥保密性保证。

### 数据流

<pre>
签发（Issuer 侧）：
  Payload（JSON）= {"sub":"user123","exp":1735689600}
                      │
                      ▼
  Base64URL(Header) = "eyJhbGciOiJIUzI1NiJ9"
  Base64URL(Payload) = "eyJzdWIiOiJ1c2VyMTIzIiwiZXhwIjoxNzM1Njg5NjAwfQ"
                      │
                      └──► Concat: "eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJ1c2VyMTIzIiwiZXhwIjoxNzM1Njg5NjAwfQ"
                                 │
                                 ▼
                         HMAC-SHA256(Secret, message)
                                 │
                                 ▼
  Signature = Base64URL(HMAC) = "SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c"
                                 │
                                 ▼
  JWT = Header.Payload.Signature

验证（Consumer 侧）：
  JWT 字符串
     │
     ├─→ Base64URL 解码 Header，验证 alg = "HS256"
     │
     ├─→ Base64URL 解码 Payload，检查 exp > now
     │
     └─→ 重新计算 HMAC-SHA256(Secret, Header.Payload)
              │
              ▼
         constant-time 比较 ←─ HMAC.Equal
              │
              ├─ 相等 → 解析 Payload（Claims）
              └─ 不等 → 401 Unauthorized
</pre>

### 机制

**为什么用 Base64URL 而非 Base64**：JWT 可能在 URL 中传递（如 `?token=xxx`），Base64 的 `+` 和 `/` 字符需要 URL 编码，增加长度。Base64URL 将 `+`→`-`，`/`→`_`，去掉 `=` 填充。

**恒定时间比较的原因**：若使用 `==` 比较签名，短路行为会导致比较时间与匹配字节数相关。攻击者通过测量响应时间可以逐位猜测签名（时序攻击）。`hmac.Equal` 保证比较时间与输入长度无关。

**Token 截持攻击**：JWT 存储在 localStorage 易受 XSS 攻击，存储在 HttpOnly Cookie 可防止 JavaScript 读取但仍可能被 CSRF 利用。最佳实践：短期 Access Token（15min）+ HttpOnly Refresh Token。

## Access Token vs Refresh Token

### 定义
Access Token 是短期令牌（15min），泄露后影响窗口有限；Refresh Token 是长期令牌（7天），用于 Access Token 过期后获取新令牌，应存放在 HttpOnly Cookie 中防止 XSS 窃取。

### 数学模型

**Access Token 生命周期**：
$$T_{access} = 15 \text{ minutes} = 900 \text{ seconds}$$

**Refresh Token 生命周期**：
$$T_{refresh} = 7 \text{ days} = 604800 \text{ seconds}$$

**泄露窗口分析**：
- Access Token 泄露：攻击窗口 ≤ 15 分钟
- Refresh Token 泄露：攻击窗口 ≤ 7 天（但需要 Refresh Token + 可能的社会工程）

### 机制

**Refresh Token 一次性使用（One-Time）的约束**：
1. 客户端用 Refresh Token 换取新 Access Token + 新 Refresh Token
2. 服务器检测到已使用的 Refresh Token，吊销整个 token family

```
攻击场景（无 One-Time）：
  攻击者截获 Refresh Token R
  → 用 R 换取 Access Token A1
  → 用 R 再次换取 Access Token A2  ← 成功，攻击持续

攻击场景（One-Time）：
  攻击者截获 Refresh Token R
  → 用 R 换取 Access Token A1 + Refresh Token R2
  → 服务器记录 R 已使用
  → 合法用户用原 Refresh Token → 被拒绝（R 已在黑名单）
  → 攻击窗口闭合
```

**Refresh Token 轮转**：每次刷新时颁发新的 Refresh Token，旧 Token 作废。这确保 Refresh Token 不会因长期有效而被暴力破解。

## RBAC vs ABAC

### 定义
RBAC（基于角色的访问控制）将权限归于角色，角色归于用户，适合权限层级相对固定的系统。ABAC（基于属性的访问控制）根据用户属性、资源属性、环境属性动态决策，适合细粒度、上下文相关的权限场景。

### 数学模型

**RBAC 权限检查**：
$$\text{HasPermission}(user, permission) = \exists role \in UserRoles(user): permission \in RolePermissions(role)$$

**ABAC 策略评估**：策略是一组规则，每个规则是属性三元组 $(subject, resource, environment)$ 的谓词：
$$\text{Evaluate}(request) = \bigvee_{i=1}^{n} Policy_i(request)$$

### 对比参照

| 属性 | RBAC | ABAC |
|------|------|------|
| 权限粒度 | 粗粒度（角色级别） | 细粒度（属性级别） |
| 权限变更 | 修改角色权限，所有成员自动继承 | 需为每个用户/资源单独调整 |
| 审计难度 | 较简单（角色数量有限） | 复杂（规则组合爆炸） |
| 适用场景 | 企业内部系统、权限层级固定 | 跨组织协作、动态权限 |

### 机制

**RBAC 的局限性**：当权限需求是"用户 A 可以编辑项目 B 的文档"这类细粒度需求时，RBAC 需要为每个用户-资源组合创建角色，导致角色爆炸。

**ABAC 的局限性**：动态策略评估的性能开销显著高于 RBAC 的查表操作。在高频访问路径上应谨慎使用。

### RBAC 参考存根

```go
type Role int
const (
    RoleAdmin Role = iota
    RoleEditor
    RoleViewer
)

type Permission int
const (
    PermRead Permission = iota
    PermWrite
    PermDelete
    PermAdmin
)

// 角色-权限映射
var rolePermissions = map[Role][]Permission{
    RoleAdmin:  {PermRead, PermWrite, PermDelete, PermAdmin},
    RoleEditor: {PermRead, PermWrite},
    RoleViewer: {PermRead},
}

func (a *Authorizer) HasPermission(role Role, perm Permission) bool {
    perms, ok := rolePermissions[role]
    if !ok {
        return false
    }
    for _, p := range perms {
        if p == perm {
            return true
        }
    }
    return false
}
```

## 密码存储

### 定义
密码必须使用 bcrypt（自适应哈希，Cost 参数控制计算时间，当前推荐 Cost=12）。MD5/SHA1/SHA256 不适合密码存储——它们设计为快速哈希，GPU 可在秒级完成数十亿次猜测。

### 数学模型

**bcrypt 计算时间**：
$$T_{bcrypt}(cost) = O(2^{cost} \cdot \text{Blowfish轮数})$$

- cost=10：约 100ms
- cost=12：约 300ms
- cost=14：约 1.2s

**Hash 计算公式**：
$$H(cost, salt, password) = \text{ExpensiveKeySetup}(password, salt, 2^{cost}) \rightarrow \text{BlowfishEncrypt}(64 rounds)$$

**暴力破解防御**：设攻击者 GPU 速度为 $10^9$ hashes/second：
- MD5：$2^{128}$ 搜索空间，平均 $2^{64}$ 次尝试，约 585 年
- bcrypt(cost=12)：$2^{128}$ 搜索空间，但每次 $2^{12} \approx 4000$ 倍慢，实际约 146,000 GPU-years

### 机制

**为什么 bcrypt 的 Cost 参数重要**：bcrypt 的设计目标是"故意慢"，使暴力破解成本不成比例地高。随着硬件提升，Cost 参数需要增加以维持安全性。

**bcrypt 的内置 salt**：bcrypt 的输出包含随机 salt，无需外部存储。相同密码每次哈希结果不同，防止彩虹表攻击。

**为什么不用 SHA-256**：SHA 系列是快速哈希，设计用于数据完整性校验。密码存储需要慢哈希 + 内置 salt，防止暴力破解和彩虹表攻击。

### 参考存根

```go
import "golang.org/x/crypto/bcrypt"

func hashPassword(password string) (string, error) {
    hash, err := bcrypt.GenerateFromPassword([]byte(password), 12)
    if err != nil {
        return "", err
    }
    return string(hash), nil
}

func checkPassword(password, hash string) bool {
    err := bcrypt.CompareHashAndPassword([]byte(hash), []byte(password))
    return err == nil
}
```
