# 错误处理

## 定义

Go 的错误处理范式是显式返回而非异常：函数通过多返回值将错误作为签名的显式部分，调用者必须处理或传播错误。这种设计使错误路径可见、可追踪，而非被隐藏于异常机制中。

错误处理的本质是**错误作为值**（errors as values）——错误是可以被检查、传播、包装的普通值，而非控制流异常。

## 数学模型

### 错误检查的逻辑结构

Go 的错误处理是**显式控制流**，而非异常机制的隐式传播：

```
function f():
    result, err := doSomething()
    if err != nil:
        return err  // 显式返回错误
    return result
```

这与异常的区别：

| 维度 | Go 错误返回 | 异常机制 |
|------|------------|----------|
| 传播方式 | 显式 `return err` | 隐式向上传播 |
| 检查时机 | 编译器强制检查 | 可捕获或不捕获 |
| 性能影响 | 无（普通返回值） | 栈展开有开销 |
| 可恢复性 | 必须显式处理 | 可通过 catch 恢复 |

### 错误包装的语义

`fmt.Errorf` 的 `%w` 动词创建**错误链**：

```go
err := fmt.Errorf("load config: %w", os.ErrNotExist)
errors.Is(err, os.ErrNotExist)  // true
```

数学上，错误链是**链表结构**：每个包装错误持有一个指向内部错误的指针，形成链表的链。

**归约终点**：错误链的查询（`errors.Is`）是沿着链表遍历，时间复杂度 $O(n)$ ，其中 $n$ 是包装深度。 ，其中 $n$ 是包装深度。 是包装深度。

### errors.AsType 的泛型保证

Go 1.23 引入 `errors.AsType[T]`，泛型版本避免类型断言的运行时开销：

```go
// 旧方式（运行时检查）
var perr *PathError
if errors.As(err, &perr) { ... }

// 新方式（编译时确定类型）
if pathError, ok := errors.AsType[*PathError](err); ok {
    // 处理错误
}
```

**编译时类型安全的数学意义**：`errors.AsType[T]` 将类型检查从运行时 $O(1)$ 查找转变为编译时的类型参数推导，消除动态派发开销。 查找转变为编译时的类型参数推导，消除动态派发开销。

### 错误处理的控制流复杂度

设函数调用深度为 $D$ ，每层错误检查率为 $p$ ： ，每层错误检查率为 $p$ ： ：

 $P_{错误被适当处理} = p^D$ 

当 $D=5, p=0.9$ 时： $P = 0.9^5 \approx 0.59$ 时： $P = 0.9^5 \approx 0.59$ 

这解释了为什么深度调用链中错误容易"漏报"——每层 90% 处理率，5 层后只有 59% 的错误被适当处理。

## 数据流

### 错误创建与传播

<pre>
os.ReadFile("config.json")
    │
    │ 返回 (data, error)
    ▼
if err != nil:
    │ 错误存在
    ▼
fmt.Errorf("load config: %w", err)
    │
    │ 创建包装错误，保留原错误链
    ▼
return err 向上传播
</pre>

### 错误检查路径

<pre>
errors.Is(err, target)
    │
    │ 遍历错误链（Unwrap()）
    ▼
┌──────────────────────────────────────────┐
│ err0 = fmt.Errorf("open file: %w", err1) │
│   │ Unwrap() → err1                     │
│   ▼                                     │
│ err1 = fmt.Errorf("read config: %w", err2)│
│   │ Unwrap() → err2                     │
│   ▼                                     │
│ err2 = os.ErrNotExist                   │
│   └───────────────►? = target           │
│                    是 → 返回 true        │
└──────────────────────────────────────────┘
若 err0.unwrap() → err1.unwrap() → err2 === target，返回 true
时间复杂度 O(n)（n = 包装深度）
</pre>

### errors.Join 的合并结构

<pre>
err1 ─┐
      ├─► errors.Join ──► err_joined
err2 ─┘           │
                  │ errors.Is(err_joined, err1)
                  │ errors.Is(err_joined, err2)
                  ▼
              两条错误链均可查询
</pre>

**Join 的数据结构**：Go 1.20+ 的 `errors.Join` 返回一个包含多个错误的单一 error，其内部结构是切片而非链表，支持多错误并行查询。

## 机制

### panic/recover 的使用边界

`panic` 用于**真正不可恢复的错误**：
- 数组越界（编程错误，发现后应修复代码）
- 断言失败（表明假设被破坏）
- 启动失败（如端口已被占用）

**约束**：panic 沿着调用栈向上传播，直到被 recover 捕获或程序终止。recover 只能在 defer 中调用。

**recover 只能在 defer 中调用的原因**：panic 触发时，Go runtime 会立即停止当前 goroutine 的正常执行，跳过所有后续代码，建立一个延迟调用栈。recover 之所以必须在 defer 中，是因为 panic 的传播本身就是通过延迟调用链实现的——当 panic 值被推入 goroutine 局部变量后，只有 defer 语句才能在栈展开过程中访问到这个值。若在非 defer 上下文中调用 recover，该函数对应的栈帧尚未被 panic 机制绑定，无法感知 panic 状态。

**违反约束的后果**：
- 在非 defer 中调用 recover 不起作用（返回 nil）
- 无限 panic（如 panic(nil)）会继续向上传播

### 错误包装的最佳实践

每层错误包装应添加**有意义的上下文**：

```go
// 好：每层添加上下文
return fmt.Errorf("load config %s: %w", path, err)

// 不好：丢失原始错误
return errors.New("config error")

// 不好：重复包装
return fmt.Errorf("load config: %w", fmt.Errorf("read file: %w", err))
```

**重复包装的问题**：双重包装导致 `errors.Is` 需要两次 Unwrap 才能到达原始错误，错误链深度增加但信息未增加。

### 哨兵错误的设计原则

哨兵错误（`var ErrNotFound = errors.New("not found")`）用于**公开的、可预测的错误检查**：

- 标准库：`os.ErrNotExist`、`io.EOF`
- 第三方库：公开错误常量供调用者检查

**约束**：哨兵错误是值而非类型，不能携带额外上下文。若需要携带上下文，使用自定义错误类型。

### 领域特定错误的设计

领域错误应实现 `Unwrap()` 方法以支持错误链检查：

```go
type DomainError struct {
    Err error  // 内部错误
    Domain, Operation, Entity, ID string
}

func (e *DomainError) Unwrap() error { return e.Err }
func (e *DomainError) Error() string {
    return fmt.Sprintf("%s.%s: %s [%s] - %v",
        e.Domain, e.Operation, e.Entity, e.ID, e.Err)
}
```

这样调用者可以：
- `errors.Is(err, os.ErrNotExist)` 检查根本原因
- `errors.As(err, &domainErr)` 获取领域上下文

### 重试与退避

网络操作等瞬时失败需要重试：

- **指数退避**：`delay = base * 2^attempt`，避免惊群效应
- **抖动（jitter）**： $\pm 20\%$ 随机化，分散重试时间 随机化，分散重试时间
- **最大尝试次数**：防止无限重试

**退避的收敛性**：设基础延迟 $b$ ，最大延迟 $M$ ，指数退避序列 $\{b, 2b, 4b, ..., M\}$ 的长度： ，最大延迟 $M$ ，指数退避序列 $\{b, 2b, 4b, ..., M\}$ 的长度： ，指数退避序列 $\{b, 2b, 4b, ..., M\}$ 的长度： 的长度：

 $n = \lfloor \log_2(M/b) \rfloor + 1$ 

这保证了最大重试次数的有界性。

## 参考存根

```go
// 基本错误检查
result, err := doSomething()
if err != nil {
    return fmt.Errorf("do something: %w", err)
}

// errors.Is / errors.As
if errors.Is(err, os.ErrNotExist) {
    // 文件不存在
}
var perr *PathError
if errors.As(err, &perr) {
    log.Printf("path: %s", perr.Path)
}

// errors.AsType（Go 1.23+）
if ve, ok := errors.AsType[ValidationError](err); ok {
    fmt.Println(ve.Field)
}

// panic/recover
func safeCall(fn func()) (err error) {
    defer func() {
        if r := recover(); r != nil {
            err = fmt.Errorf("panic: %v", r)
        }
    }()
    fn()
    return nil
}

// 指数退避重试
func withRetry[T any](fn func() (T, error), maxAttempts int) (T, error) {
    var zero T
    baseDelay := 100 * time.Millisecond

    for attempt := 0; attempt < maxAttempts; attempt++ {
        result, err := fn()
        if err == nil {
            return result, nil
        }
        if attempt == maxAttempts-1 {
            return zero, fmt.Errorf("after %d attempts: %w", maxAttempts, err)
        }
        delay := baseDelay * time.Duration(1<<attempt)
        time.Sleep(delay)
    }
    return zero, nil
}

// errors.Join（Go 1.20+）
err := errors.Join(err1, err2, err3)
if errors.Is(err, err1) { ... }
```

## 错误处理决策矩阵

| 场景 | 推荐做法 |
|------|---------|
| 标准库错误 | `errors.Is(err, os.ErrXXX)` |
| 公开 API | 定义哨兵错误 `var ErrXXX` |
| 内部错误 | 自定义错误类型 + `fmt.Errorf "%w"` |
| 批量错误 | `errors.Join` |
| 不可恢复错误 | `panic`，仅顶层 `recover` |
| 网络重试 | 指数退避 + 最大次数 |
| 降级处理 | fallback 模式 |
