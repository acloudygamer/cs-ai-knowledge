# 配置管理

## 定义

配置管理是将程序行为参数与代码分离的过程，核心问题是**加载优先级**（命令行 > 环境变量 > 代码默认值 > 配置文件）和**热重载**（变更时无需重启进程）。

## Viper 配置优先级

### 定义
Viper 的配置来源按优先级从高到低：命令行 flags > 环境变量 > 配置文件 > 代码默认值。`AutomaticEnv()` 和 `SetEnvKeyReplacer` 使环境变量渗透到嵌套配置键。

### 数学模型

**优先级权重**：设配置值来源集合 $S = \{默认值_0, 配置文件_1, 环境变量_2, 命令行flag_3\}$，最终值取 $\max_{s \in S} priority(s)$，其中 $priority(默认值_0) = 0$，其余依次递增。

**键路径映射**：配置键 $k$ 的环境变量形式 $E(k)$ 通过 `SetEnvKeyReplacer` 转换：
$$E(k) = \text{REPLACE}(k, '.', '_', \text{全局替换})$$
默认值行为：无 replacer 时，直接大写 $k$ 并加下划线前缀。

**归约终点**：配置查找是**有序集合的线性扫描**，时间复杂度 $O(|S|)$，其中 $|S|$ 是配置源数量。

### 数据流

<pre>
配置请求：viper.Get("database.host")

查找链（从高优先级到低）：
  ┌─────────────────────────────────────────────────────┐
  │ 1. 命令行 flag（最高优先级）                          │
  │    └─ viper.Set("database.host", "flag-host")       │
  │    若存在 → 返回 "flag-host"                         │
  └───────────────────────┬─────────────────────────────┘
                          ▼
  ┌─────────────────────────────────────────────────────┐
  │ 2. 环境变量                                          │
  │    └─ APP_DATABASE_HOST=env-host                    │
  │    若存在 → 返回 "env-host"                          │
  └───────────────────────┬─────────────────────────────┘
                          ▼
  ┌─────────────────────────────────────────────────────┐
  │ 3. 配置文件（config.yaml）                           │
  │    └─ database.host: file-host                      │
  │    若存在 → 返回 "file-host"                          │
  └───────────────────────┬─────────────────────────────┘
                          ▼
  ┌─────────────────────────────────────────────────────┐
  │ 4. 代码默认值（最低优先级）                           │
  │    └─ viper.SetDefault("database.host", "default")  │
  │    返回 "default"                                    │
  └─────────────────────────────────────────────────────┘
</pre>

### 机制

**为什么环境变量优先级高于配置文件**：环境变量通常用于容器化部署（Docker/Kubernetes），运行时修改无需重建镜像或重启进程。配置文件适合静态基础设施配置。这反映了"易变性：环境变量 > 配置文件"的工程原则。

**嵌套键的 `.` 问题**：许多 shell 不支持点号变量名（如 `APP.DATABASE.HOST`），因此 Viper 默认将 `.` 替换为 `_`。`SetEnvKeyReplacer` 允许自定义映射规则。

**性能约束**：每次 `Get` 都会遍历整个查找链，在高频访问场景下应缓存结果：

```go
// 高频访问前
viper.Unmarshal(&cfg) // 一次性加载到结构体
// 后续访问 cfg.Host 而非 viper.Get("database.host")
```

## 配置文件格式选择

| 格式 | 适用场景 | 优势 | 劣势 |
|------|---------|------|------|
| JSON | 跨语言配置 | 原生解析、无歧义 | 不支持注释 |
| YAML | 配置文件 | 支持注释、嵌套表达 | 空格缩进敏感、解析器差异 |
| TOML | 配置文件 | 语义清晰、无缩进陷阱 | 新格式、工具支持少 |
| ENV | 运行时覆盖 | docker/k8s 原生 | 不支持嵌套、复杂类型 |

### 机制

**YAML 的缩进陷阱**：YAML 依赖空格缩进，但不同解析器对 tab 和空格的处理不一致。同一 YAML 文件在不同工具下可能解析出不同结果。这使得 YAML 适合人工编写但不适合机器生成。

**TOML 的设计动机**：YAML 的嵌套容易产生歧义（如 `key: value` 和 `key:\n  value` 的嵌套差异），TOML 通过显式表（`[table]`）和键值对消除歧义。

## 热重载机制

### 定义
Viper 的 `WatchConfig()` 依赖 `fsnotify` 监听文件系统事件，变化时触发回调。但热重载的**可见性**需要程序主动查询——Viper 不自动更新内存中的值，需在回调中重新 `Unmarshal`。

### 数学模型

**文件系统事件驱动**：热重载本质是**观察者模式**，配置源作为被观察者，回调作为观察者。触发条件是 `fsnotify` 的 `WRITE` 或 `CHMOD` 事件。

**可见性延迟**：从文件变更到程序感知存在延迟 $\Delta t = t_{fsnotify} + t_{unmarshal}$，其中 $t_{fsnotify}$ 取决于操作系统轮询间隔（通常 10-100ms），$t_{unmarshal}$ 取决于配置结构复杂度。

### 数据流

<pre>
配置文件变更（disk）

fsnotify 监控
  │
  ├─ 事件类型：WRITE / CHMOD
  │
  └─ 回调触发
        │
        └─ viper.Unmarshal(&cfg)
              │
              ├─ 旧 cfg 对象的字段被新值覆盖
              │
              └─ 返回（同步更新内存）
</pre>

### 机制

**为什么 Viper 不自动更新原对象**：Go 的值语义使得 `Unmarshal` 到已存在的结构体时，会覆盖已有字段但保留旧对象身份。若直接替换指针，持有旧指针的代码会看到过期数据。显式 `Unmarshal` 强迫调用者控制更新时机。

**并发安全**：`WatchConfig` 的回调在单独的 goroutine 中执行，`Unmarshal` 本身不是并发安全的。热重载回调中若访问共享状态，需要加锁。

### 参考存根

```go
viper.WatchConfig()
viper.OnConfigChange(func(e fsnotify.Event) {
    // 重新 unmarshal 到同一个结构体
    if err := viper.Unmarshal(&cfg); err != nil {
        log.Printf("config reload failed: %v", err)
    }
    // 触发配置变更通知
    onConfigChange(&cfg)
})

// 并发安全版本
var cfgMu sync.RWMutex
viper.OnConfigChange(func(e fsnotify.Event) {
    cfgMu.Lock()
    defer cfgMu.Unlock()
    viper.Unmarshal(&cfg)
})
```

## 敏感配置

### 定义
密码、密钥等敏感配置**绝不**写入配置文件或日志。正确做法：运行时从环境变量或密钥管理服务（Vault/KMS）获取，内存中用后即清除。

### 机制

**为什么 `json:"-"` 是必要的**：`json:"-"` 标签使标准库 `json.Marshal` 跳过该字段，防止意外序列化到日志或错误响应。但这只是序列化层的保护，内存中的值仍可能被 core dump 或 profiling 工具暴露。

**内存安全的进一步措施**：
1. 使用后清零：`defer func() { zero.Bytes(password) }()`
2. 使用后即删除：从 map 或结构体中移除键
3. 专用密钥管理服务：AWS KMS、HashiCorp Vault、Azure Key Vault

### 参考存根

```go
// SafeConfig 防止敏感字段被序列化
type SafeConfig struct {
    Password string `json:"-"`
    APIKey   string `json:"-"`
}

// 运行时从环境变量加载
cfg := &SafeConfig{
    Password: os.Getenv("DB_PASSWORD"), // 容器注入
    APIKey:   os.Getenv("API_KEY"),
}

// 使用后清零
func clearSensitive(s *SafeConfig) {
    s.Password = ""
    s.APIKey = ""
}
```
