# Go 命令专题

## 定义

`go` 命令是 Go 工具链的统一入口，通过子命令区分功能域：环境查看(`env`)、代码编译(`build`)、测试运行(`test`)、静态分析(`vet`)、代码格式化(`fmt`)、模块管理(`mod`)。其本质是一个**自举的构建系统**——Go 本身用 Go 编写，工具链与语言版本严格绑定，意味着 `go version` 同时确定了编译器和标准库的版本契约。

## 数学模型

### go build 的编译管道

```
输入：.go 源文件集合 S = {f₁, f₂, ..., fₙ}
输出：可执行文件 / 共享库 / 插件

编译管道（数学形式）：

  ∀fᵢ ∈ S：
    ASTᵢ      = parse(fᵢ)                           // 词法+语法分析，O(|fᵢ|)
    AST'ᵢ    = typeCheck(ASTᵢ)                     // 类型检查，O(|ASTᵢ|)
    SSAᵢ     = compile(AST'ᵢ)                      // 生成 SSA（静态单赋值）
    objᵢ     = codegen(SSAᵢ)                       // 生成目标文件 .o

  binary    = link(obj₁ ⊕ obj₂ ⊕ ... ⊕ objₙ)     // 链接

其中 ⊕ 表示目标文件集合的合并
```

**SSA 形式的约束**：SSA 要求每条指令最多一次赋值，φ 函数的引入需满足支配边界条件。设 $d$ 为支配关系，则 $\phi$ 函数的放置位置 $p$ 满足：

$$\forall x \in Dom(p) \setminus \{p\} : x \text{ dominates } p \Rightarrow \phi_p \in Inst(p)$$

### go test 的覆盖率模型

```
覆盖率（Coverage） = 已执行的代码行数 / 总代码行数

分支覆盖率 = 已执行的分支数 / 总分支数

Coverage 计算（插桩法）：
  编译器在每行代码前插入计数器++：
    原始：x = a + b
    插桩后：__coverage[line_42]++; x = a + b

  运行测试后统计每个计数器的值
  输出：profile.out（line:execution_count 格式）
```

**覆盖率的形式化定义**：设 $P$ 为程序点集合，$E(p)$ 为执行期间经过 $p$ 的次数，则：

$$\text{coverage} = \frac{|\{p \in P \mid E(p) > 0\}|}{|P|}$$

### go mod 的版本解析约束

```
MVS（Minimal Version Selection）算法：

给定依赖图 G = (V, E)，V 为模块集合，E 为边集合
边 (u, v, constraint) 表示 u 依赖 v 的某个版本范围

MVS(root)：
  result = {}
  for each (root, dep, range) in root.requires：
    result[dep] = Minimal(dep, range, result)

  return result

Minimal(dep, range, result) 返回满足 range 的最小版本
若 result 中已有 dep 的更高版本，仍选择满足 range 的最小版本

约束：
  1. 单调性：选择的版本只增不减
  2. 可重现性：相同输入 → 相同输出
  3. DAG 约束：不允许循环依赖
```

**go.sum 的密码学约束**：每行 `module@version h1:treehash` 中 `treehash` 是 Go 团队维护的隐式依赖列表的哈希。若 `go.sum` 中存在 `h1:treehash`，则验证该模块内容的哈希确实等于 `treehash`。这构成 Go 的**可重现构建的信任根**。

## 机制

### go vet 为什么在 build 之后运行？

```
go build 成功后 → 意味着代码在语法和类型上是正确的

go vet 在此基础上做语义分析：
  - printf 的 format verb 与实参类型是否匹配
  - 是否有无效的类型转换
  - 是否有不可达的代码

这是二次检查的原因：
  1. 若 build 失败，不需要 vet（类型问题更基础）
  2. build 成功后，AST 已构建好，vet 可复用
  3. vet 结果不影响编译，继续输出二进制
```

**为什么是设计权衡而非缺陷**：将 vet 集成到 build 中会导致每次编译都执行完整静态分析，增加编译时间。分离设计允许开发者在提交前选择性运行 vet（`go vet ./...`），而 CI 中通过 `golangci-lint` 做更全面的检查。

### go test -race 的实现原理

```
race detector 使用 "shadow memory" 技术：

对每个字节的内存，用 shadow 字节追踪最后写入的 goroutine

内存访问插桩：
  每次 load：检查 shadow[addr] 是否属于当前 goroutine
  每次 store：更新 shadow[addr] = current_goroutine

若 load 发现 shadow 属于另一个 goroutine → race 报告

实现细节：
  - 编译器在每次内存访问前后插入 race 检测代码
  - 检测代码使用 TLS（Thread Local Storage）获取当前 goroutine ID
  - shadow memory 大小 = 1 shadow byte per heap byte × 5-10x 开销
```

**约束边界**：race detector 只能检测**已执行的并发访问路径**。未触发的 race 条件无法被发现，这是动态分析的固有局限。静态分析工具（如 go vet 的 -atomic 检查）可以发现潜在的 race，但存在假阳性。

### go fmt 的等幂性

```
gofmt 是等幂的（idempotent）：
  gofmt(gofmt(code)) = gofmt(code)

这意味着：
  1. 多次格式化结果相同
  2. 可安全用于 pre-commit hook
  3. 代码风格争议可以通过强制 gofmt 解决

gofmt 保留语义：
  gofmt 不改变程序行为，只是重新排列 token
  等价于：格式化后的代码与原代码在语义上完全相同
```

**等幂性的形式化证明思路**：设 `Format` 为格式化函数，若 `Format` 满足 `Format(x) = Format(Format(x))`，则等幂。gofmt 通过以下保证：
- 不改变 token 序列，只改变空白符和换行位置
- 确定性：相同输入 → 相同输出（无随机性）

### go build 的链接器行为

```
链接阶段解决的问题：

1. 符号解析（Symbol Resolution）
   - 每个目标文件包含导出符号和未定义符号
   - 链接器需将未定义符号与导出符号匹配
   - 未匹配 → "undefined: x" 错误

2. 符号重定位（Relocation）
   - 编译时生成的指令中使用相对地址/占位符
   - 链接器计算实际地址并更新所有引用

3. 库文件解析（Library Resolution）
   go build -i：安装前先安装依赖的库
   GOPATH/pkg/${GOOS}_${GOARCH}/xxx.a
```

**链接时的循环依赖检测**：Go 链接器在构建包依赖图时检测循环。若存在环，报告 "import cycle not allowed"。这是编译期检查，不是运行时错误。

### go get 与 go mod download 的差异

```
go get：
  - 旧版 GOPATH 时代的命令
  - 同时更新 go.mod 和下载模块
  - 会修改 go.mod 的 require 列表

go mod download：
  - 仅下载模块到缓存（GOMODCACHE）
  - 不修改 go.mod
  - 用于预热缓存或 CI 中的依赖安装

go mod download 的缓存位置：
  $(go env GOMODCACHE)/
  ├── github.com/user/repo@v1.2.3/
  │       ├── @v/
  │       │   ├── list
  │       │   ├── info
  │       │   ├── mod
  │       │   └── lock (go.sum 验证用)
  │       └── ...
  └── ...
```
