# 代码质量工具

## 定义

Go 代码质量工具按职责分为三层：**语法风格层**（`gofmt`/`goimports`）、**语义问题层**（`go vet`/`golangci-lint`）、**深度分析层**（`staticcheck`）。各层检查正交，串联形成完整质量门禁。每一层的**检查粒度**决定了其能发现的问题类型：token 流层面只能验证格式规范，AST 层面能验证结构正确性，SSA 层面能验证数据流和指针传递。

**三层检查的正交性**：每层检查都在独立的抽象层次上运行，不依赖其他层的检查结果。这保证了：
- gofmt 的修复不会影响 go vet 的检查
- go vet 的通过不意味着 staticcheck 也通过
- 三层串联使用能发现从风格到语义到安全的全谱问题

**检查粒度与问题发现能力的映射**：

| 检查层次 | 抽象表示 | 能发现的问题 | 误报率 |
|----------|----------|--------------|--------|
| Token 流 | 词法单元序列 | 缩进、空白、换行 | 零（确定性算法） |
| AST | 语法树结构 | 类型匹配、调用签名 | 极低 |
| SSA + 数据流 | 静态单赋值 + 控制流 | 未初始化变量、逃逸分析 | 低 |
| 调用图 | 函数调用图 | 错误处理覆盖、安全漏洞 | 中 |

## 数学模型

### golangci-lint 的并行检查模型

golangci-lint 执行 $N$ 个 linter（$N \geq 70$），每个 linter $L_i$ 对输入 $S$（源码）做独立分析：

$$
L_i(S) \rightarrow \{\text{issue}_{i,1}, \text{issue}_{i,2}, \ldots, \text{issue}_{i,k}\}
$$

golangci-lint 做结果归并：

$$
\text{Result} = \bigcup_{i=1}^{N} L_i(S)
$$

**去重操作的约束**：两个 issue 相等当且仅当其 $\text{RowCol}$（行号+列号）和 $\text{Message}$ 完全相同。golangci-lint 使用**笛卡尔积比较**而非哈希，以支持细粒度的去重策略配置。

**并行执行的时间复杂度**：

| 模式 | 时间公式 | 说明 |
|------|----------|------|
| 理论并行 | $T_{\text{parallel}} = \max(T_{L_1}, T_{L_2}, \ldots, T_{L_N})$ | $C$ 个 CPU 核心 |
| 串行 | $T_{\text{serial}} = \sum_{i=1}^{N} T_{L_i}$ | 无并行 |
| 实际 | $T_{\text{actual}} \approx \frac{\sum T_{L_i}}{C} + \underbrace{\kappa \times N}_{\text{调度开销}}$ | $\kappa$ 为每个 linter 启动成本 |

**实际并行效率约束**：由于 linters 共享 AST 和类型信息，AST 构建必须串行完成。因此并行优势主要来自 I/O-bound 的检查（如读文件）和 CPU-bound 检查的调度重叠。纯 CPU-bound 检查（如 SSA 数据流分析）几乎无法并行。

### staticcheck 的 SSA 数据流分析

**三大数据流分析框架**：

**1. 到达定义（Reaching Definitions）**

对于程序点 $p$，计算哪些定义（赋值）能到达 $p$：

$$
RD(p) = \bigcup_{s \in \text{pred}(p)} \left( \text{Gen}(s) \cup \left( RD(s) \setminus \text{Kill}(s) \right) \right)
$$

其中 $\text{Gen}(s)$ 是语句 $s$ 生成的新定义，$\text{Kill}(s)$ 是被 $s$ 无效化的定义。迭代求解直至不动点。

**不动点收敛性证明**：设程序中定义的数量为 $|D|$，初值 $\text{RD}^{(0)}[p] = \emptyset$。每次迭代，定义集合单调不减（仅可能增加），且上界为 $|D|$。由于 $|D|$ 有限，迭代必在 $|D|$ 步内收敛。

**2. 可用表达式（Available Expressions）**

对于程序点 $p$，计算哪些表达式已计算且操作数未改变：

$$
AE(p) = \bigcap_{s \in \text{pred}(p)} \left( \text{Avail}(s) \cup \left( AE(s) \setminus \text{Kill}(s) \right) \right)
$$

交集而非并集是因为表达式必须在**所有路径**上都可用才算可用。

**3. 活跃变量（Liveness Analysis）**

对于变量 $v$ 和程序点 $p$，计算在 $p$ 之后是否仍需：

$$
\text{LIVE}(p) = \bigcup_{s \in \text{succ}(p)} \left( \text{Use}(s) \cup \left( \text{LIVE}(s) \setminus \text{Def}(s) \right) \right)
$$

**不动点求解**：上述方程通过迭代求解。设初值 $\text{OUT}[n] = \emptyset$，反复应用转移函数直至收敛。Go 的 SSA 构建保证**终止性**，因为值域是有限集合（程序中的定义数有限），且每次迭代严格减小或增大（分别对应 Kill/Use 操作），所以必然在有限步内收敛。

### errcheck 的错误处理覆盖模型

errcheck 对每个函数调用 $f(\text{args}\ldots)$ 做检查：

设 $f$ 的返回类型为 $(T_1, T_2, \ldots, T_n, \text{error})$

对每个返回值 $T_i$：
- 若 $T_i \equiv \text{error}$：
  1. 检查是否被 `_, _ = f(...)` 丢弃 → 通过
  2. 检查是否被 `if err != nil` 处理 → 通过
  3. 否则 → 报告：未处理的错误返回值

**覆盖度公式**：

$$
\text{coverage} = \frac{|\{r \in \text{error returns} \mid \text{handled}(r)\}|}{|\{r \in \text{error returns}\}|}
$$

**静态分析的局限性**：errcheck 基于类型信息而非调用图。若错误通过接口传递或在闭包中捕获，静态分析无法追踪。

### go-critic 的复杂度约束

**appendVariable 检测的数学基础**：

设循环 $L$ 执行 $n$ 次，append 操作 amortized 复杂度为 $O(1)$：
- 总代价 $= n \times O(1) = O(n)$

但若切片在循环内声明，每次 append 可能触发扩容：
- 扩容代价：拷贝已有元素到新数组
- 设初始容量 $c_0$，每次扩容翻倍：

$$
c_0 \rightarrow c_0 \times 2 \rightarrow c_0 \times 4 \rightarrow \cdots \rightarrow c_k \geq n
$$

扩容次数 $k = \lceil \log_2(n/c_0) \rceil$

总拷贝代价：

$$
\sum_{i=0}^{k-1} c_0 \times 2^i = c_0(2^k - 1) < 2n
$$

**结论**：预分配将复杂度从 $O(n \log n)$ 的非均匀拷贝降至 $O(n)$。虽然 append 的均摊分析保证总代价是 $O(n)$，但预分配消除了每次扩容时的拷贝常数因子。

**cyclop（圈复杂度）的数学定义**：

$$
\text{CC} = E - N + 2P
$$

其中 $E$ 为控制流图的边数，$N$ 为节点数，$P$ 为连通分量数。对于顺序执行的代码块，$\text{CC} = 1$。每增加一个分支判断，$\text{CC}$ 至少增加 1。

### gosec 的安全漏洞模型

**漏洞模式的形式化表示**：

| 漏洞类型 | 模式描述 | 检测方法 |
|----------|----------|----------|
| SQL 注入 | `fmt.Sprintf("SELECT * FROM %s", userInput)` | AST 模式匹配 |
| XSS | `template.HTML(userInput)` 无转义 | 反射分析 |
| 硬编码凭证 | `password := "..."` | 字符串字面量检测 |
| 弱加密 | `md5.New()` 用于安全目的 | 调用图分析 |

**调用图分析的约束**：gosec 需要构建完整的调用图来追踪数据流。若存在函数指针或接口方法调用，调用图可能不完整，导致漏报。

## 数据流

### golangci-lint 的执行流

<pre>
源码 (*.go)
    │
    ▼
golangci-lint 进程（单进程多 goroutine）
    │
    ├── gofmt ──► 格式风格问题（token 流分析）
    ├── staticcheck ──► 深度语义问题（SSA + 数据流）
    ├── errcheck ──► 错误处理问题（类型 + 调用图）
    ├── ineffassign ──► 无效赋值（活跃变量分析）
    ├── gosec ──► 安全问题（AST 模式匹配）
    └── ... (70+ linters)
            │
            ▼
        归并去重（基于 RowCol + Message）
            │
            ▼
        统一报告
                │
                ├── 输出到终端（彩色）
                ├── --fix 模式：自动修复
                └── --json 模式：JSON 输出（CI）
</pre>

**共享资源约束**：linters 之间共享 AST 和类型信息，意味着：
- AST 只需构建一次
- 类型检查只需执行一次
- 并行优势主要来自 I/O-bound 的检查

**linters 的资源隔离约束**：虽然 linters 共享 AST，但分析结果相互独立。一个 linter 的误报不影响另一个 linter 的判断。去重在最终报告阶段进行，而非在各 linter 之间进行。

### go-critic 的独有检查维度

<pre>
go-critic 实现的独有检查：

appendVariable 检测：
  for range slice {
      result = append(result, item)  // result 在循环内声明
  }
  │
  ▼ 建议
  result := make([]T, 0, len(slice))
  for _, item := range slice {
      result = append(result, item)
  }
  │
  └── 时间复杂度从 O(n²) 降到 O(n)

unbalancedStructLiteral 检测：
  MyStruct{}  // 缺少字段
  │
  ▼ 警告
  MyStruct{Field1: val1}  // 显式字段名

cyclop 检测（圈复杂度）：
  cyclomatic complexity = E - N + 2P
  其中 E=边数, N=节点数, P=连通分量数
  │
  └── 约束：圈复杂度 > 10 通常认为需要重构
</pre>

### prealloc 的循环 append 检测

<pre>
代码模式：
  var result []int
  for _, v := range values {
      result = append(result, v)  // result 在循环内声明
  }

检测原理：
  1. 遍历 for-range 循环
  2. 检查 append 目标是否在循环外声明
  3. 若在循环内声明，报告

修复：
  result := make([]int, 0, len(values))  // 预分配
  for _, v := range values {
      result = append(result, v)
  }

优化效果：
  append 扩容代价：均摊 O(1)，但有常数因子
  预分配：完全消除扩容
  当 values 很大时，性能差异显著
</pre>

## 机制

### 为什么需要多层检查？

**检查深度与问题类型的对应关系**：

| 检查深度 | 可发现问题 | 代表工具 |
|----------|-----------|----------|
| Token 流 | 缩进、换行、import 排序 | gofmt, goimports |
| AST | 函数调用参数类型匹配、结构正确性 | go vet |
| SSA + 数据流 | 数据流分析、指针传递、未初始化变量 | staticcheck |
| 类型 + 调用图 | 错误处理覆盖、接口实现完整性 | errcheck |
| AST 模式匹配 | 安全漏洞、代码反模式 | gosec, go-critic |

**检查粒度决定问题类型的本质原因**：
- Token 流分析只能验证格式规范（空格、换行），因为此时尚未构建语法结构
- AST 分析能验证结构正确性（函数调用参数类型匹配），因为每个调用节点的类型信息已知
- SSA 分析能验证数据流（变量使用前是否初始化，指针是否逃逸），因为 SSA 形式下每个变量的定义点和使用点都明确追踪

**检查深度与误报率的关系**：检查越深，误报率通常越高，因为需要更多的启发式判断。gofmt 误报率为零（确定性算法），而 staticcheck 的某些检查可能有假阳性。

### golangci-lint 的 --fix 限制

**自动修复的能力边界**：

| 分类 | 可自动修复 | 代表问题 |
|------|-----------|----------|
| gofmt | 是 | 格式问题（缩进、空行） |
| goimports | 是 | import 排序和缺失导入 |
| staticcheck（部分） | 是 | 建议使用 time.Since |
| errcheck | 否 | 无法自动添加错误处理 |
| gosec | 否 | 安全问题需人工判断上下文 |
| go-critic | 部分 | 某些建议可能改变语义 |

**为什么某些问题无法自动修复**：errcheck 发现未处理的错误返回值，但添加错误处理需要修改业务逻辑（如重试、降级、传播）。这些决策需要人类判断，工具无法推断。类似地，gosec 发现的 SQL 注入需要理解业务语义才能修复，无法通过模板替换完成。

### errcheck 无法检测的错误类型

**已知局限性**：

```go
// 1. 无法检测通过变量传递的错误
err := os.Open("file")  // errcheck 会报告
defer os.Remove(name)   // 但 defer 中的错误无法检测

// 2. 无法检测通过接口传递的错误
var w io.Writer = os.Stdout
w.Write(data)           // errcheck 无法追踪

// 3. 无法检测自定义错误类型的不当处理
// 需要人工审核错误处理逻辑
```

**根本原因**：errcheck 是**局部分析**（per-call-site），不是**全局分析**（call-graph aware）。它只检查单个调用点的错误处理，不追踪错误通过变量、接口或闭包的传播。这是一种**可判定性权衡**：做全局分析需要构建完整的调用图，而 Go 的接口动态分派使得调用图精确构建在理论上不可判定。

### golangci-lint 的 linter 调度

```
golangci-lint 如何调度 70+ linters：

1. 初始加载：
   - 读取配置（.golangci.yml）
   - 实例化启用的 linter

2. 分析阶段：
   - 同一进程内通过 goroutine 并行调度
   - 每个 linter 运行在独立 goroutine
   - 共享 AST 和类型信息（避免重复分析）

3. 结果收集：
   - 使用 channel 收集各 linter 结果
   - 主 goroutine 等待并归并

调度约束：
   - linters 之间共享 AST 意味着按序构建
   - 并行优势来自于 I/O-bound 的检查（如读文件）
   - CPU-bound 的检查（如 data flow analysis）无法真正并行
```

**goroutine 调度 vs linter 并行**：golangci-lint 的并行是 Go runtime 的 goroutine 调度，而非操作系统的线程并行。goroutine 的切换代价远低于线程（仅涉及寄存器保存/恢复，无需内核态切换），但受 Go scheduler 的 `GOMAXPROCS` 限制。

### staticcheck 的检查分类

**检查分为四个严重程度级别**：

| 严重程度 | 含义 | 典型问题 |
|----------|------|----------|
| `error` | 必定是 bug | nil 指针解引用、越界访问 |
| `warning` | 可能是 bug 或反模式 | 冗余 if、硬编码数字 |
| `suggestion` | 风格优化 | 使用 strings.Builder |
| `performance` | 性能优化建议 | 避免字符串拼接 |

**严重程度与假阳性概率的关系**：级别越高（error > warning > suggestion > performance），假阳性概率越低。`error` 级别的检查通常有严密的数学证明或明确的语言规范依据；`suggestion` 和 `performance` 可能基于经验法则，存在例外情况。

**检查类别**：

```
1. 性能（performance）
   - 建议使用 strings.Builder 而非 string +
   - 建议使用 strconv.ParseInt 而非 fmt.Sscanf

2. 简化（simplification）
   - 冗余的 if (x) { return true } else { return false }
   - 可简化为 return x

3. 正确性（correctness）
   - nil 指针解引用
   - 越界访问
   - 竞态条件

4. 可维护性（maintainability）
   - 硬编码的数字（magic number）
   - 过于复杂的函数
```

**SA9003 检测的空分支**：空 if 分支通常表示逻辑错误或未完成的代码。staticcheck 会警告只有注释或空行的 if 分支。这基于一个假设：程序员有意让 if 分支为空，应该添加注释说明原因或删除该分支。

### golangci-lint 内部组件关系

golangci-lint 内部已包含 `go vet`、`staticcheck`、`errcheck`、`ineffassign` 等，无需单独调用。`go vet` 作为 golangci-lint 的一部分运行，单独运行 `go vet` 的场景仅在调试特定检查器时需要。

**工具串联工作流**：

```
源码
    │
    ▼
go fmt / goimports ──► 格式标准化（失败则阻止提交）
    │
    ▼
go vet ──► 编译后基础语义检查（CI 必需）
    │
    ▼
golangci-lint ──► 多 linter 并行检查（CI 必需）
    │
    ├── staticcheck 深度分析（SSA + 数据流）
    ├── errcheck 错误处理检查
    ├── gosec 安全问题检查
    └── go-critic 补充维度检查
    │
    ▼
质量门禁报告
```

## 检查器对比

| 检查器 | 检查深度 | 性能影响 | 误报率 | 自动修复 |
|--------|----------|----------|--------|----------|
| go vet | 基础 AST 遍历 | 低 | 低 | 部分 |
| golangci-lint | 多维度（可配置） | 中 | 中 | 部分 |
| staticcheck | SSA + 数据流 | 高 | 低 | 部分 |
| errcheck | 类型 + 调用图 | 低 | 低 | 否 |
| go-critic | AST 模式匹配 | 低 | 低 | 部分 |
| gosec | AST + 调用图 | 中 | 中 | 否 |

**性能影响对比**：golangci-lint 的 `-p=N` 参数控制并行 linter 数量，但真正的瓶颈是 SSA 构建的串行性。对于大型代码库，staticcheck 的分析时间可能达到其他 linters 的总和。
