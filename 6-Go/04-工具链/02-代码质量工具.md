# 代码质量工具

## Go 代码质量工具生态是多层级检查的串联管道

Go 代码质量工具按职责分为三层：语法风格层（`gofmt`/`goimports`）、语义问题层（`go vet`/`golangci-lint`）、深度分析层（`staticcheck`），各层检查正交，串联形成完整质量门禁。

---

## golangci-lint：多 linter 结果的归并与统一执行层

`golangci-lint` 是 Go 最流行的综合 lint 框架，通过单一进程加载并协调 70+ 种独立 linter，消除多次进程启动开销，并提供统一配置、缓存与报告接口。

```bash
golangci-lint run ./...
golangci-lint run --fix ./...      # 自动修复
golangci-lint run -v ./...         # 详细输出
golangci-lint run --timeout 5m .   # 超时控制
```

<pre>
源码
    │
    ▼
golangci-lint（单一进程）
    │
    ├─── gofmt ──▶ 格式风格
    ├─── staticcheck ──▶ 深度语义
    ├─── errcheck ──▶ 错误处理
    ├─── ineffassign ──▶ 无效赋值
    └─── ... (70+ linters)
    │
    ▼
归并去重 ──▶ 统一报告
</pre>

**机制**：golangci-lint 在首次运行时对每种 linter 启动子进程并将结果通过 RPC 传回，主进程归并去重后统一输出。其 `--fix` 模式仅对支持自动修复的 linter（如 `gofmt`、`goimports`）生效，其他仅报告。

---

## staticcheck：Go 深度静态分析的权威检查器

`staticcheck` 是 `honnef.co/go/tools` 提供的深度静态分析工具，检查范围超出 `go vet`，涵盖性能建议（`S1012` 使用 `time.Since`）、简化建议（`S1000` 消除冗余 if-else）、正确性建议（`S1031` 消除不必要的循环复制）。

```bash
staticcheck ./...
staticcheck -f text ./...    # 文本格式
staticcheck -f json ./...    # JSON 格式（CI 友好）
```

<pre>
源码
    │
    ▼
staticcheck
    │
    ├─── 类型检查（基于 go/types）
    ├─── 数据流分析（基于 SSA）
    └─── 模式匹配（S1000-S9999 规则集）
    │
    ▼
问题报告
</pre>

**机制**：staticcheck 在 `go/types` 类型检查结果上构建数据流分析（基于 SSA），能够发现跨函数的潜在问题（如未使用的错误返回值）。其规则命名空间 `Sxxxx` 与 `golint`/`revive` 正交，golangci-lint 中以 `staticcheck` linter 名称暴露。

---

## errcheck：未处理错误返回值的强制检查工具

`errcheck` 是专门检测 `if err != nil` 被忽略的检查器，通过对所有函数调用返回值逐个匹配，强制要求调用方必须显式处理错误或显式使用 `_` 丢弃。

```bash
errcheck ./...
errcheck -abspath ./...                   # 绝对路径
errcheck -ignore='os\.(Remove|Getenv)' . # 忽略特定函数
```

<pre>
函数调用
    │
    ▼
errcheck 分析
    │
    ├─── 提取所有多返回值调用
    │       │
    │       ▼
    │   错误类型返回值是否被处理
    │       │
    │       ├─── `_` 丢弃 ──▶ 通过
    │       ├─── `if err != nil` ──▶ 通过
    │       └─── 未处理 ──▶ 报告
    │
    ▼
未处理错误列表
</pre>

**机制**：errcheck 依赖 `go/types` 遍历所有函数调用签名，识别返回 error 类型的返回值，结合 `golang.org/x/tools/go/callgraph` 构建调用图。其 `-ignore` 参数使用正则表达式匹配函数全名，实现细粒度白名单。

---

## goimports：`gofmt` 的超集兼 import 语句的自动维护器

`goimports` 是 `gofmt` 的超集，在 `gofmt` 格式化能力基础上，额外自动添加缺失的 import、删除未使用的 import、按字母排序 import 分组。

```bash
goinstall golang.org/x/tools/cmd/goimports@latest
goimports -w .      # 格式化并写入
goimports -l .      # 仅列出
```

<pre>
未排序 / 缺失 import
    │
    ▼
goimports
    │
    ├─── gofmt 格式化
    ├─── 添加缺失 import（通过 go/types 解析）
    ├─── 删除未使用 import
    └─── 按字母排序 import
    │
    ▼
规范化源码
</pre>

**机制**：goimports 内部调用 `gofmt` 处理格式化，自己额外维护 import 块。其使用 `golang.org/x/tools/go/gcimporter` 解析包接口以判断需要添加哪个 import，相比纯文本替换更精确。

## go vet vs golangci-lint vs staticcheck：检查范围的梯度差异

```
go vet        ──▶ 编译器补充检查（必需）
golangci-lint ──▶ 多 linter 归并（日常 CI）
staticcheck   ──▶ 深度分析（可选深度质量门禁）
```

| 检查器 | 检查深度 | 性能影响 | 误报率 |
|--------|----------|----------|--------|
| go vet | 基础 AST 遍历 | 低 | 低 |
| golangci-lint | 多维度（可配置） | 中 | 中 |
| staticcheck | SSA + 数据流 | 高 | 低 |

**机制**：go vet 的检查器在 Go 编译成功后立即运行，利用编译已构建好的 AST；golangci-lint 需要分别调用各 linter 进程；staticcheck 因构建 SSA（静态单赋值）形式进行数据流分析，计算开销最大但检查最深。

---

## revive：Go 官方风格规则的严格执行器

`revive` 是 Go 官方推荐的 linter，提供比 `golint` 更严格的规则实现，支持规则级别 severity 配置，可将某些规则设为 error 级别以强制阻止构建。

```bash
revive ./...
revive -config revive.toml ./...
```

<pre>
源码
    │
    ▼
revive
    │
    ├─── exported ──▶ 导出函数必须有注释
    ├─── var-naming ──▶ 变量命名规范
    ├─── error-return ──▶ 函数必须返回 error
    └─── receiver-naming ──▶ receiver 命名一致性
    │
    ▼
规则匹配结果
</pre>

**机制**：revive 的规则以 TOML 配置文件声明，每条规则可单独设置 severity（warning/error/disabled）。golangci-lint 内部使用 revive 作为 `revive` linter，当配置 `issues.exclude-use-default: false` 时，revive 的 error 级别规则会导致 `golangci-lint` 以非零退出码退出。

---

## go-critic：包含独有检查维度的补充性 linter

`go-critic` 提供 `staticcheck` 和 `revive` 覆盖不到的检查维度，特别是性能相关（`appendVariable` 避免在循环中重复分配切片）和习惯用法（`unbalancedStructLiteral` 检测结构体字面量遗漏字段）。

```bash
go-critic check ./...
go-critic check -enable='diagnostic,performance' ./...
go-critic check -fix ./...
```

<pre>
源码
    │
    ▼
go-critic
    │
    ├─── diagnostic ──▶ 正确性隐患
    ├─── performance ──▶ 性能反模式
    └─── style ──▶ 惯用法建议
    │
    ▼
问题报告
</pre>

**机制**：go-critic 实现了若干独有检查规则（如 `appendVariable` 检测循环内切片追加是否外置以避免 O(n²) 复杂度），这些规则依赖对循环结构和 append 调用模式的特殊识别，不存在于其他 linter 中。

---

## prealloc：循环内 append 导致 O(n²) 的自动检测器

`prealloc` 专门检测在 for-range 循环内使用 `append` 扩容切片的情形，建议将 append 移到循环外预分配以将时间复杂度从 O(n²) 降至 O(n)。

```bash
prealloc ./...
prealloc -fix ./...    # 自动修复
```

<pre>
for range slice {
    slice = append(slice, item)  // O(n²)
}
    │
    ▼
prealloc 检测
    │
    ▼
建议改为:
result := make([]T, 0, len(slice))
for _, item := range slice {
    result = append(result, item)  // O(n)
}
</pre>

**机制**：prealloc 分析 for-range 循环内 append 调用模式，当 append 的目标是循环外声明的切片时给出警告。其 `-fix` 模式直接在循环前插入 `make([]T, 0, len(source))` 预分配并替换 append 目标。

---

## logrus-lint： logrus 日志调用规范的强制检查器

`logrus-lint` 检测 logrus 使用中的常见反模式，如使用 `info` 级别记录 error、使用字符串拼接而非结构化字段、`WithField` 链过长。

```bash
logrusr-lint ./...
```

**机制**：logrus-lint 通过 `golang.org/x/tools/go/ast` 遍历 logrus API 调用链，识别日志级别与字段类型的语义不匹配。其规则集中在 logrus 特有 API 的使用规范，不与其他通用 linter 重叠。

## 工具串联工作流

```
源码
    │
    ▼
go fmt / goimports ──▶ 格式标准化（失败则阻止提交）
    │
    ▼
go vet ──▶ 编译后基础语义检查（CI 必需）
    │
    ▼
golangci-lint ──▶ 多 linter 并行检查（CI 必需）
    │
    ├─── staticcheck 深度分析（可选）
    ├─── errcheck 错误处理检查
    └─── go-critic 补充维度检查
    │
    ▼
质量门禁报告
```

golangci-lint 内部已包含 `govet`、`staticcheck`、`errcheck`、`ineffassign` 等，无需单独调用。`go vet` 作为 golangci-lint 的一部分运行，单独运行 `go vet` 的场景仅在调试特定检查器时需要。
