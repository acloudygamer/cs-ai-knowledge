# 代码质量工具

## 定义

Go 代码质量工具按职责分为三层：**语法风格层**（`gofmt`/`goimports`）、**语义问题层**（`go vet`/`golangci-lint`）、**深度分析层**（`staticcheck`）。各层检查正交，串联形成完整质量门禁。每一层的**检查粒度**决定了其能发现的问题类型：token 流层面只能验证格式规范，AST 层面能验证结构正确性，SSA 层面能验证数据流和指针传递。

## 数学模型

### golangci-lint 的并行检查模型

```
golangci-lint 执行 N 个 linter（N ≥ 70）：
  每个 linter Lᵢ 对输入 S（源码）做独立分析：
    Lᵢ(S) → {issueᵢ₁, issueᵢ₂, ..., issueᵢₖ}

  golangci-lint 做结果归并：
    Result = merge(L₁(S), L₂(S), ..., Lₙ(S))

  去重逻辑：
    若 Lⱼ 和 Lₖ 都报告同一位置的同一问题 → 只输出一次

时间复杂度（并行执行）：
  T_total = max(T_L1, T_L2, ..., T_LN)  // 理论并行
  vs 串行：T_serial = Σᵢ T_Li

  实际实现（协程调度）：
    T_actual ≈ Σᵢ T_Li / C  // C 为可用 CPU 核心数
    存在调度开销：T_overhead = κ × N  // κ 为每个 linter 的启动成本
```

**归并操作的约束**：两个 issue 相等当且仅当其 `RowCol`（行号+列号）和 `Message` 完全相同。golangci-lint 使用**笛卡尔积比较**而非哈希，以支持细粒度的去重策略配置。

### staticcheck 的 SSA 数据流分析

```
staticcheck 在 go/types 类型检查后构建 SSA：

源码 → go/types 类型检查 → AST
                          │
                          ▼
                      SSA 构建（静态单赋值形式）
                          │
                          ├── 每条指令唯一赋值（SSA 约束）
                          ├── φ 函数处理分支合并
                          │     φ(p1, p2) 根据控制流选择值
                          │
                          ▼
                      数据流分析框架
                          │
                          ├── Reaching Definitions
                          │     对于程序点 p，计算哪些定义能到达 p
                          │     RD(p) = ⋃ U_gen(s) ∪ (RD(p') - KILL(s))
                          │
                          ├── Available Expressions
                          │     对于程序点 p，计算哪些表达式已计算且未失效
                          │     AE(p) = ⋂ U_avail(s) ∪ (AE(p') - KILL(s))
                          │
                          └── Liveness Analysis
                                对于变量 v，计算在程序点 p 是否仍需
                                LIVE(p) = ⋃ USE(s) ∪ (LIVE(p') - DEF(s))

                          ▼
                      问题报告（基于分析结果）
```

**数据流方程的不动点求解**：上述方程通过迭代求解。设初值 `OUT[n] = ∅`，反复应用转移函数直至收敛。Go 的 SSA 构建保证**终止性**，因为值域是有限集合（程序中的定义数有限）。

### errcheck 的错误处理覆盖模型

```
errcheck 对每个函数调用 f(args...) 做检查：

设 f 的返回类型为 (T₁, T₂, ..., Tₙ, error)

对每个返回值 Tᵢ：
  若 Tᵢ ≡ error：
    1. 检查是否被 `_, _ = f(...)` 丢弃 → 通过
    2. 检查是否被 `if err != nil` 处理 → 通过
    3. 否则 → 报告：未处理的错误返回值

覆盖度 = 已处理的错误返回值 / 总错误返回值
```

**静态分析的局限性**：errcheck 基于类型信息而非调用图。若错误通过接口传递或在闭包中捕获，静态分析无法追踪。

### go-critic 的复杂度约束

```
appendVariable 检测的数学基础：

设循环 L 执行 n 次，append 操作 amortized 复杂度为 O(1)：
  总代价 = n × O(1) = O(n)

但若切片在循环内声明，每次 append 可能触发扩容：
  扩容代价：拷贝已有元素到新数组
  设初始容量 c₀，每次扩容翻倍：
    c₀ → c₀×2 → c₀×4 → ... → cₖ ≥ n

  扩容次数 k = ⌈log₂(n/c₀)⌉
  总拷贝代价 = c₀ + c₀×2 + ... + c₀×2ᵏ⁻¹ = c₀(2ᵏ - 1) < 2n

优化后预分配：
  只需一次分配，O(n) 总代价

结论：预分配将复杂度从 O(n log n) 的非均匀拷贝降至 O(n)
```

## 数据流

### golangci-lint 的执行流

<pre>
源码
    │
    ▼
golangci-lint 进程
    │
    ├── gofmt ──► 格式风格问题
    ├── staticcheck ──► 深度语义问题
    ├── errcheck ──► 错误处理问题
    ├── ineffassign ──► 无效赋值
    ├── gosec ──► 安全问题（SQL 注入、XSS 等）
    └── ... (70+ linters)
            │
            ▼
        归并去重
            │
            ▼
        统一报告
            │
            ├── 输出到终端
            ├── --fix 模式：自动修复
            └── --json 模式：JSON 输出（CI）
</pre>

### go-critic 的独有检查维度

<pre>
go-critic 实现的独有检查：

appendVariable 检测：
  for range slice {
      result = append(result, item)  // result 在循环内声明
  }
  │
  ▼ 建议
  result := make([]T, 0, len(slice))
  for _, item := range slice {
      result = append(result, item)
  }
  │
  └── 时间复杂度从 O(n²) 降到 O(n)

unbalancedStructLiteral 检测：
  MyStruct{}  // 缺少字段
  │
  ▼ 警告
  MyStruct{Field1: val1}  // 显式字段名
</pre>

### prealloc 的循环 append 检测

<pre>
代码模式：
  var result []int
  for _, v := range values {
      result = append(result, v)  // result 在循环内声明
  }

检测原理：
  1. 遍历 for-range 循环
  2. 检查 append 目标是否在循环外声明
  3. 若在循环内声明，报告

修复：
  result := make([]int, 0, len(values))  // 预分配
  for _, v := range values {
      result = append(result, v)
  }

优化效果：
  append 扩容代价：均摊 O(1)，但有常数因子
  预分配：完全消除扩容
  当 values 很大时，性能差异显著
</pre>

## 机制

### 为什么需要多层检查？

```
各层检查的能力边界：

gofmt/goimports（语法层）：
  - 缩进、换行、import 排序
  - 检查深度：token 流
  - 可自动修复：是

go vet（语义问题层）：
  - printf verb 不匹配、nil 指针调用
  - 检查深度：AST + 类型信息
  - 可自动修复：否

golangci-lint（多 linter 归并）：
  - 在 go vet 基础上增加更多检查器
  - 检查深度：AST + SSA
  - 可自动修复：部分

staticcheck（深度静态分析）：
  - 性能建议、简化建议、正确性隐患
  - 检查深度：SSA + 数据流分析
  - 可自动修复：否
```

**为什么检查深度决定问题类型**：token 流分析只能验证格式规范（空格、换行）。AST 分析能验证结构正确性（函数调用参数类型匹配）。SSA 分析能验证数据流（变量使用前是否初始化，指针是否逃逸）。

### golangci-lint 的 --fix 限制

```
--fix 只修复支持自动修复的 linter：

支持自动修复的 linter：
  - gofmt：格式问题
  - goimports：import 排序和缺失导入
  - staticcheck（部分）：如建议使用 time.Since

不支持自动修复的 linter：
  - errcheck：无法自动添加错误处理（需要理解业务逻辑）
  - gosec：安全问题需要人工判断上下文
  - gocritic：某些建议可能改变语义

所以：--fix 是"尽力而为"，不是"完全自动化"
```

**为什么某些问题无法自动修复**：errcheck 发现未处理的错误返回值，但添加错误处理需要修改业务逻辑（如重试、降级、传播）。这些决策需要人类判断，工具无法推断。

### errcheck 无法检测的错误类型

```
errcheck 的已知局限性：

1. 无法检测通过变量传递的错误
   err := os.Open("file")  // errcheck 会报告
   defer os.Remove(name)    // 但 defer 中的错误无法检测

2. 无法检测通过接口传递的错误
   var w io.Writer = os.Stdout
   w.Write(data)           // errcheck 无法追踪

3. 无法检测自定义错误类型的不当处理
   // 需要人工审核错误处理逻辑

根本原因：errcheck 是**局部分析**（per-call-site），
不是**全局分析**（call-graph aware）
```

### golangci-lint 的 linter 调度

```
golangci-lint 如何调度 70+ linters：

1. 初始加载：
   - 读取配置（.golangci.yml）
   - 实例化启用的 linter

2. 分析阶段：
   - 同一进程内通过 goroutine 并行调度
   - 每个 linter 运行在独立 goroutine
   - 共享 AST 和类型信息（避免重复分析）

3. 结果收集：
   - 使用 channel 收集各 linter 结果
   - 主 goroutine 等待并归并

调度约束：
   - linters 之间共享 AST 意味着按序构建
   - 并行优势来自于 I/O-bound 的检查（如读文件）
   - CPU-bound 的检查（如 data flow analysis）无法并行
```

### staticcheck 的检查分类

```
staticcheck 的检查分为多个类别：

1. 性能（performance）
   - 建议使用 strings.Builder 而非 string +
   - 建议使用 strconv.ParseInt 而非 fmt.Sscanf

2. 简化（simplification）
   - 冗余的 if (x) { return true } else { return false }
   - 可简化为 return x

3. 正确性（correctness）
   - nil 指针解引用
   - 越界访问
   - 竞态条件

4. 可维护性（maintainability）
   - 硬编码的数字（magic number）
   - 过于复杂的函数

每个检查的严重程度：
   - error：必定是 bug
   - warning：可能是 bug 或反模式
   - suggestion：风格优化
```

## 工具串联工作流

```
源码
    │
    ▼
go fmt / goimports ──► 格式标准化（失败则阻止提交）
    │
    ▼
go vet ──► 编译后基础语义检查（CI 必需）
    │
    ▼
golangci-lint ──► 多 linter 并行检查（CI 必需）
    │
    ├── staticcheck 深度分析（可选）
    ├── errcheck 错误处理检查
    ├── gosec 安全问题检查
    └── go-critic 补充维度检查
    │
    ▼
质量门禁报告
```

## 检查器对比

| 检查器 | 检查深度 | 性能影响 | 误报率 |
|--------|----------|----------|--------|
| go vet | 基础 AST 遍历 | 低 | 低 |
| golangci-lint | 多维度（可配置） | 中 | 中 |
| staticcheck | SSA + 数据流 | 高 | 低 |
| errcheck | 类型 + 调用图 | 低 | 低 |
| go-critic | AST 模式匹配 | 低 | 低 |

golangci-lint 内部已包含 `go vet`、`staticcheck`、`errcheck`、`ineffassign` 等，无需单独调用。`go vet` 作为 golangci-lint 的一部分运行，单独运行 `go vet` 的场景仅在调试特定检查器时需要。
