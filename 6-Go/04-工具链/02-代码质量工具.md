# 代码质量工具

## 定义

Go 代码质量工具按职责分为三层：**语法风格层**（`gofmt`/`goimports`）、**语义问题层**（`go vet`/`golangci-lint`）、**深度分析层**（`staticcheck`）。各层检查正交，串联形成完整质量门禁。

## 数学模型

### golangci-lint 的并行检查模型

```
golangci-lint 执行 N 个 linter（N ≥ 70）：
  每个 linter Li 对输入 S（源码）做独立分析：
    Li(S) → {issue_i1, issue_i2, ..., issue_ik}

  golangci-lint 做结果归并：
    Result = merge(L1(S), L2(S), ..., LN(S))

  去重逻辑：
    若 L1 和 L2 都报告同一位置的同一问题 → 只输出一次

时间复杂度（并行执行）：
  T_total = max(T_L1, T_L2, ..., T_LN)  // 并行
  vs 串行：T_serial = sum(T_Li)

  实际：golangci-lint 用单一进程但协程调度各 linter
```

### staticcheck 的 SSA 数据流分析

```
staticcheck 在 go/types 类型检查后构建 SSA：

源码 → go/types 类型检查 → AST
                          │
                          ▼
                      SSA 构建（静态单赋值形式）
                          │
                          ├── 每条指令唯一赋值
                          ├── φ 函数处理分支合并
                          │
                          ▼
                      数据流分析
                          │
                          ├── Reaching definitions
                          ├── Available expressions
                          └── Liveness analysis
                          │
                          ▼
                      问题报告
```

### errcheck 的错误处理覆盖模型

```
errcheck 对每个函数调用 f(args...) 做检查：

设 f 的返回类型为 (T1, T2, ..., error)

对每个返回值 Ti：
  若 Ti ≡ error：
    1. 检查是否被 `_, _ = f(...)` 丢弃 → 通过
    2. 检查是否被 `if err != nil` 处理 → 通过
    3. 否则 → 报告：未处理的错误返回值

覆盖度 = 已处理的错误返回值 / 总错误返回值
```

## 数据流

### golangci-lint 的执行流

<pre>
源码
    │
    ▼
golangci-lint 进程
    │
    ├── gofmt ──► 格式风格问题
    ├── staticcheck ──► 深度语义问题
    ├── errcheck ──► 错误处理问题
    ├── ineffassign ──► 无效赋值
    └── ... (70+ linters)
            │
            ▼
        归并去重
            │
            ▼
        统一报告
            │
            ├── 输出到终端
            ├── --fix 模式：自动修复
            └── --json 模式：JSON 输出（CI）
</pre>

### go-critic 的独有检查维度

<pre>
go-critic 实现的独有检查：

appendVariable 检测：
  for range slice {
      result = append(result, item)  // result 在循环内声明
  }
  │
  ▼ 建议
  result := make([]T, 0, len(slice))
  for _, item := range slice {
      result = append(result, item)
  }
  │
  └── 时间复杂度从 O(n²) 降到 O(n)

unbalancedStructLiteral 检测：
  MyStruct{}  // 缺少字段
  │
  ▼ 警告
  MyStruct{Field1: val1}  // 显式字段名
</pre>

### prealloc 的循环 append 检测

<pre>
代码模式：
  var result []int
  for _, v := range values {
      result = append(result, v)  // result 在循环内声明
  }

检测原理：
  1. 遍历 for-range 循环
  2. 检查 append 目标是否在循环外声明
  3. 若在循环内声明，报告

修复：
  result := make([]int, 0, len(values))  // 预分配
  for _, v := range values {
      result = append(result, v)
  }

优化效果：
  append 扩容代价：均摊 O(1)，但有常数因子
  预分配：完全消除扩容
  当 values 很大时，性能差异显著
</pre>

## 机制

### 为什么需要多层检查？

```
各层检查的能力边界：

gofmt/goimports（语法层）：
  - 缩进、换行、import 排序
  - 检查深度：token 流
  - 可自动修复：是

go vet（语义问题层）：
  - printf verb 不匹配、nil 指针调用
  - 检查深度：AST + 类型信息
  - 可自动修复：否

golangci-lint（多 linter 归并）：
  - 在 go vet 基础上增加更多检查器
  - 检查深度：AST + SSA
  - 可自动修复：部分

staticcheck（深度静态分析）：
  - 性能建议、简化建议、正确性隐患
  - 检查深度：SSA + 数据流分析
  - 可自动修复：否
```

### golangci-lint 的 --fix 限制

```
--fix 只修复支持自动修复的 linter：

支持自动修复的 linter：
  - gofmt：格式问题
  - goimports：import 问题
  - staticcheck（部分）：如建议使用 time.Since

不支持自动修复的 linter：
  - errcheck：无法自动添加错误处理
  - gosec：安全问题需要人工判断
  - gocritic：某些建议可能改变语义

所以：--fix 是"尽力而为"，不是"完全自动化"
```

### errcheck 无法检测的错误类型

```
errcheck 的局限性：

已知限制：
  1. 无法检测通过变量传递的错误
     err := os.Open("file")  // errcheck 会报告
     defer os.Remove(name)    // 但 defer 中的错误无法检测

  2. 无法检测通过接口传递的错误
     var w io.Writer = os.Stdout
     w.Write(data)           // errcheck 无法追踪

  3. 无法检测自定义错误类型的不当处理
     // 需要人工审核错误处理逻辑
```

## 工具串联工作流

```
源码
    │
    ▼
go fmt / goimports ──► 格式标准化（失败则阻止提交）
    │
    ▼
go vet ──► 编译后基础语义检查（CI 必需）
    │
    ▼
golangci-lint ──► 多 linter 并行检查（CI 必需）
    │
    ├── staticcheck 深度分析（可选）
    ├── errcheck 错误处理检查
    ├── gosec 安全问题检查
    └── go-critic 补充维度检查
    │
    ▼
质量门禁报告
```

## 检查器对比

| 检查器 | 检查深度 | 性能影响 | 误报率 |
|--------|----------|----------|--------|
| go vet | 基础 AST 遍历 | 低 | 低 |
| golangci-lint | 多维度（可配置） | 中 | 中 |
| staticcheck | SSA + 数据流 | 高 | 低 |
| errcheck | 类型 + 调用图 | 低 | 低 |
| go-critic | AST 模式匹配 | 低 | 低 |

golangci-lint 内部已包含 `govet`、`staticcheck`、`errcheck`、`ineffassign` 等，无需单独调用。`go vet` 作为 golangci-lint 的一部分运行，单独运行 `go vet` 的场景仅在调试特定检查器时需要。
