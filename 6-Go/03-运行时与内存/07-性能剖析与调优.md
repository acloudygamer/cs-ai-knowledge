# 性能剖析与调优

> 前置：[06-CGO与跨语言调用](./06-CGO与跨语言调用.md) · 后续：[04-并发](../04-并发/)

> **版本基准**：Go 1.27（stable = latest）。本篇示例实测环境：go1.27.1 windows/amd64，Intel i7-10750H（6 核 12 线程）。

## 本质

**性能调优的顺序是"先测量、再定位、最后优化"——而 Go 把这三步都做进了工具链。**

| 步骤 | 工具 | 回答的问题 |
|---|---|---|
| 测量 | `go test -bench` | 到底有多快？改动有没有效果？ |
| 定位 | `go tool pprof` | 时间/内存花在哪里？ |
| 验证 | 再跑一次 benchmark | 优化真的有效吗？ |

**约束**：**没有测量就没有优化**。人的直觉在性能问题上极不可靠——Go 的编译器会内联、会做逃逸分析、会把小对象留在栈上，很多"看起来慢"的写法实际上零开销（[02](./02-内存分配与逃逸分析.md) 的 `-gcflags=-m` 实测就是证据：`escapeReturn` 返回指针必须上堆，`noEscape` 返回值留在栈上，两者的源码形状几乎一样）。

**边界**：基准测试测的是**微观性能**。它测不出架构问题（错误的并发模型、不必要的网络往返），也不代表真实负载——真实负载有 I/O 等待、有锁竞争、有 GC 压力。**benchmark 通过不等于程序快**。

## 机制

### 基准测试的正确写法

```go
func BenchmarkBuildSlow(b *testing.B) {
	for i := 0; i < b.N; i++ {
		_ = BuildSlow(200)
	}
}
```

四条规则：

**一、函数名必须是 `BenchmarkXxx(b *testing.B)`**，`b.N` 由框架调整（先小后大，直到测量时间足够长）。

**二、被测结果必须被使用**，否则编译器可能优化掉整段代码。用包级变量接收：

```go
var sink string
func BenchmarkX(b *testing.B) {
	for i := 0; i < b.N; i++ { sink = BuildSlow(200) }
}
```

**三、`b.ResetTimer()` 排除准备开销**。如果 setup 很贵（读文件、建连接），在循环前调用它。

**四、`-benchmem` 是必加项**：

```console
$ go test -bench=. -benchmem -run=^$
BenchmarkBuildSlow-12     	   60856	     20454 ns/op	   66888 B/op	     300 allocs/op
BenchmarkBuildFast-12     	  444376	      2758 ns/op	    1216 B/op	     101 allocs/op
BenchmarkSumSquares-12    	 4964563	       254.1 ns/op	       0 B/op	       0 allocs/op
```

| 列 | 含义 |
|---|---|
| `-12` | `GOMAXPROCS`（12 = 本机逻辑核数） |
| `ns/op` | 每次操作耗时 |
| `B/op` | **每次操作的堆分配字节数** |
| `allocs/op` | **每次操作的堆分配次数** |

**`allocs/op` 往往比 `ns/op` 更有指导意义**——分配次数直接决定 GC 压力（[03](./03-垃圾回收.md)）。`SumSquares` 的 `0 B/op, 0 allocs/op` 说明编译器把 `&struct{v int}{}` 留在了栈上（逃逸分析，见 [02](./02-内存分配与逃逸分析.md)）——**这段代码看起来在堆上分配，实际上没有**。

### CPU profile：定位热点

```console
$ go test -bench=BenchmarkBuildSlow -cpuprofile=cpu.out -o bench.test .
$ go tool pprof -top -nodecount=8 bench.test cpu.out
      flat  flat%   sum%        cum   cum%
     190ms  7.82%  7.82%      190ms  7.82%  runtime.sysUnusedOS
     180ms  7.41% 15.23%      940ms 38.68%  runtime.concatstrings
     160ms  6.58% 21.81%      190ms  7.82%  runtime.preemptM
     150ms  6.17% 27.98%      150ms  6.17%  runtime.memmove
     130ms  5.35% 33.33%      140ms  5.76%  runtime.typePointers.next
     120ms  4.94% 38.27%      120ms  4.94%  runtime.semasleep
     100ms  4.12% 42.39%      100ms  4.12%  runtime.procyieldAsm
      80ms  3.29% 45.68%      80ms  3.29%  runtime.scanObject
```

**`runtime.concatstrings` 的 `cum` 是 940ms，占 38.68%**——这一个函数就吃掉近四成的 CPU。它就是 `s += ...` 展开成的运行时调用（[02-标准库/01](../02-标准库/01-字符串与字节.md) 实测过 `+=` 比 `strings.Builder` 慢 60 倍）。

**两列的区别**：

- **`flat`**：这个函数**自身**消耗的时间（不含它调用的子函数）
- **`cum`**：这个函数**及其所有被调用者**的累计时间

**看 `flat` 找自身耗时，看 `cum` 找调用链**。`runtime.sysUnusedOS` 的 flat 最高（190ms）但 cum 也是 190ms——它没有子调用，纯粹是运行时在向 OS 归还内存（[02](./02-内存分配与逃逸分析.md) 的 `HeapIdle`）。

### heap profile：定位分配

```console
$ go test -bench=BenchmarkBuildSlow -memprofile=mem.out -o bench.test .
$ go tool pprof -top -sample_index=alloc_space -nodecount=6 bench.test mem.out
Showing nodes accounting for 4.78GB, 99.51% of 4.80GB total
      flat  flat%   sum%        cum   cum%
    4.78GB 99.51% 99.51%     4.80GB 99.94%  prof.BuildSlow
```

`-sample_index` 有四种口径，**必须选对**：

| 口径 | 含义 | 用途 |
|---|---|---|
| `alloc_space` | **累计分配字节数** | 找分配热点（默认） |
| `alloc_objects` | 累计分配对象数 | 找"次数多但都很小"的分配 |
| `inuse_space` | 当前存活字节数 | **找内存泄漏** |
| `inuse_objects` | 当前存活对象数 | 同上 |

**`alloc_space` 与 `inuse_space` 的差别是关键**：前者包含已被回收的，后者只有还活着的。**排查泄漏必须用 `inuse_space`**——用 `alloc_space` 会把大量正常回收的临时对象算进来。

### 优化的真实案例

上面那个程序，profile 指出热点是 `concatstrings`。改法就是 [02-标准库/01](../02-标准库/01-字符串与字节.md) 讲的 `strings.Builder`：

```go
func BuildFast(n int) string {
	var sb strings.Builder
	sb.Grow(n * 4)        // 预分配（见下）
	for i := 0; i < n; i++ {
		sb.WriteString(strconv.Itoa(i))
		sb.WriteByte(',')
	}
	return sb.String()
}
```

| | ns/op | B/op | allocs/op |
|---|---|---|---|
| `BuildSlow`（`+=`） | 20454 | 66888 | **300** |
| `BuildFast`（Builder） | **2758** | **1216** | **101** |
| 变化 | **快 7.4×** | **内存少 55×** | **少 3×** |

**7.4 倍的提升来自两处**：`strings.Builder` 避免了不可变字符串的重复分配，`sb.Grow(n*4)` 一次性预分配了缓冲区。这两条分别对应 [02-标准库/01](../02-标准库/01-字符串与字节.md) 与 [03-运行时与内存/02](./02-内存分配与逃逸分析.md) 的实测结论。

**注意还剩 101 次分配**——那来自 `strconv.Itoa` 每次返回新字符串。要再优化得换成 `strconv.AppendInt(sb.AvailableBuffer(), ...)` 这类零分配 API。**优化是迭代的**：profile → 改一处 → 再 profile。

### 其他剖析维度

| 类型 | 采集方式 | 查什么 |
|---|---|---|
| **block** | `runtime.SetBlockProfileRate(1)` | 阻塞在同步原语上的时间 |
| **mutex** | `runtime.SetMutexProfileFraction(1)` | 锁竞争 |
| **goroutine** | `pprof.Lookup("goroutine")` | goroutine 泄漏（[01](./01-运行时总览与调度器.md)） |
| **trace** | `go tool trace` | 调度延迟、GC 暂停、系统调用 |

**`net/http/pprof` 把上面这些挂到 HTTP 端点**（[05-IO与外部世界/03](../05-IO与外部世界/03-HTTP服务与客户端.md)），生产服务加上这一行就能远程取 profile：

```go
import _ "net/http/pprof"
```

**约束**：`pprof` 端点**没有任何认证**，会泄漏源码路径、函数名、内存内容片段。**必须挂在独立的内部端口上**，或加认证中间件。这是真实的安全事故来源。

**`go tool trace` 与本篇其他工具不同**——它看的是**时间轴**而非聚合统计，能回答"这次 GC 暂停发生在哪个请求上"这类问题。代价是数据量大、分析靠交互式界面。

### 编译器层面的观察

| 命令 | 看什么 |
|---|---|
| `go build -gcflags=-m` | 逃逸分析决策（[02](./02-内存分配与逃逸分析.md)） |
| `go build -gcflags=-S` | 生成的汇编 |
| `go build -gcflags='-N -l'` | **关闭优化与内联**，对照看优化效果 |
| `GODEBUG=gctrace=1` | GC 行为（[03](./03-垃圾回收.md)） |
| `go build -ldflags='-s -w'` | 去掉符号表与调试信息，减小二进制 |

**`-gcflags='-N -l'` 的用法**：如果关掉优化后性能**没有变化**，说明这段代码本来就不是瓶颈；如果**大幅变慢**，说明优化器帮了大忙，手写优化空间有限。

**与其它语言对照**：

| | 基准测试 | CPU profile | 堆 profile |
|---|---|---|---|
| Java | JMH（第三方，需专门配置） | JFR / async-profiler | JFR / MAT |
| Python | `timeit` / pytest-benchmark | cProfile | tracemalloc |
| C++ | Google Benchmark（第三方） | perf / VTune | valgrind |
| **Go** | **`go test -bench`（内置）** | **`go tool pprof`（内置）** | **`go tool pprof`（内置）** |

**Go 与其它语言的关键差别是"内置"**。Java 要用 JMH 得引依赖、写专门的 harness、处理 JIT 预热；Go 的 `go test -bench` 就在工具链里（[00-概览/01](../00-概览/01-Go全景.md) 说的"工具链是一个二进制"）。**这让"随手写个 benchmark 量一下"的成本降到几乎为零**——而正是这个低成本，让"先测量再优化"这条纪律在 Go 社区真正被执行。
