# 垃圾回收

> 前置：[02-内存分配与逃逸分析](./02-内存分配与逃逸分析.md) · 后续：[04-反射](./04-反射.md)

> **版本基准**：Go 1.27（stable = latest）。本篇示例实测环境：go1.27.1 windows/amd64，Intel i7-10750H（6 核 12 线程）。

## 本质

**Go 的 GC 是并发三色标记清扫（concurrent tri-color mark-sweep），不分代。**

两个定语各自是一条设计决策：

**一、标记清扫**（mark-sweep）：从根集合（栈、全局变量、寄存器）出发遍历对象图，标记可达对象，清扫未标记的。

**二、不分代**。Java、V8、.NET 的 GC 都是分代的——利用"大部分对象朝生夕死"这条经验规律，把新对象放新生代、用便宜的算法频繁回收。**Go 明确不做这件事**。

**约束的由来**：分代 GC 需要**写屏障记录跨代引用**，而且**移动对象**（压缩）会带来额外的复杂性。Go 的设计者认为分代带来的复杂度与延迟不确定性，对"服务端长驻进程"这个主要场景不划算——Go 的目标是**低延迟**而非最大吞吐。官方在 Go 1.5 引入并发 GC 时明确表态过这一点。

**代价**：不分代意味着**所有对象一视同仁**——一个存活 10 秒的对象和一个存活 10 毫秒的对象，在每次 GC 时都要被扫描。因此 Go 的 GC 吞吐低于 Java 的 G1/ZGC，换来的是**实现简单、暂停短且可预测**。

**边界**：GC 只管堆。栈上的对象随函数返回自动消失，不参与 GC——这正是 [02](./02-内存分配与逃逸分析.md) 里逃逸分析的价值所在。

## 机制

### 三色标记法

| 颜色 | 含义 |
|---|---|
| **白** | 尚未访问，可能不可达（**最终白的就是垃圾**） |
| **灰** | 已发现但子对象未扫描完 |
| **黑** | 自身与子对象都已扫描完 |

流程：根对象置灰 → 取灰对象、把它的子对象置灰、自己置黑 → 重复直到没有灰对象 → 剩下的白对象回收。

**约束**：三色标记有个致命问题——**并发标记期间，用户程序可能修改对象图**，让"已经扫描过的黑对象"指向"尚未扫描的白对象"，导致白对象被误判为垃圾。这就是**写屏障**（write barrier）要解决的。

### 写屏障

**写屏障是编译器在每次指针写入前插入的一小段代码**，它通知 GC"这里发生了变化"。Go 用的是**混合写屏障**（hybrid write barrier，Go 1.8 起），结合了 Dijkstra 插入屏障与 Yuasa 删除屏障，**消除了"重新扫描栈"这个 STW 步骤**。

**代价**：每次指针赋值多几条指令。这是"并发 GC"这笔账里最实在的一部分——**所有程序都要付，哪怕 GC 没在跑**（写屏障在 GC 活跃期才真正生效，但检查本身要执行）。

### STW 只发生两次

Go 的 GC 周期里，**只有两处短暂停顿**：

| 阶段 | 做什么 | 典型时长 |
|---|---|---|
| **mark setup** | 开启写屏障，准备标记 | 微秒级 |
| 并发标记 | 与用户程序同时跑 | **不 STW** |
| **mark termination** | 关闭写屏障，完成标记 | 微秒级 |
| 并发清扫 | 与用户程序同时跑 | **不 STW** |

**判据**：STW 的时间**与堆大小基本无关**——mark setup 的工作量是"启动所有 P 的标记协程"，mark termination 是"确认标记完成"。这与 Java 的分代 GC 形成鲜明对比，也是 Go 能宣称"亚毫秒暂停"的依据。

### 读 `gctrace` 输出

`GODEBUG=gctrace=1` 每次 GC 打一行。下面是实测输出（一个持续构建存活对象的程序）：

```console
$ GODEBUG=gctrace=1 ./gc3.exe
gc 5 @0.021s 7%: 0+8.3+0 ms clock, 0+0/13/9.6+0 ms cpu, 31->32->27 MB, 32 MB goal, 0 MB stacks, 0 MB globals, 12 P
gc 6 @0.036s 7%: 0+3.1+0 ms clock, 0+0/9.5/13+0 ms cpu, 49->49->42 MB, 54 MB goal, 0 MB stacks, 0 MB globals, 12 P (forced)
gc 8 @0.064s 7%: 0+5.0+0 ms clock, 0+0/13/37+0 ms cpu, 92->92->85 MB, 151 MB goal, 0 MB stacks, 0 MB globals, 12 P (forced)
gc 9 @0.091s 7%: 0+8.0+0 ms clock, 0+0/24/55+0 ms cpu, 149->149->128 MB, 170 MB goal, 0 MB stacks, 0 MB globals, 12 P (forced)
```

逐字段拆解：

| 字段 | 值 | 含义 |
|---|---|---|
| `gc 5` | 5 | 第几次 GC（程序生命周期内累计） |
| `@0.021s` | 0.021s | 距程序启动的时间 |
| `7%` | 7% | **GC 累计占用的 CPU 比例** |
| `0+8.3+0 ms clock` | 0 / 8.3 / 0 | **STW setup / 并发标记 / STW termination** 的墙钟耗时（毫秒） |
| `0+0/13/9.6+0 ms cpu` | | 同上，单位是 CPU 时间；中间的 `0/13/9.6` 是**辅助标记 / 后台标记 / 空闲标记**三段 |
| `31->32->27 MB` | | **GC 开始时的堆 → 标记结束时的堆 → 存活堆** |
| `32 MB goal` | 32 MB | **下次 GC 的触发阈值** |
| `0 MB stacks` | 0 MB | 扫描 goroutine 栈的耗时 |
| `0 MB globals` | 0 MB | 扫描全局变量的耗时 |
| `12 P` | 12 | 参与标记的 P 数量（= `GOMAXPROCS`） |
| `(forced)` | | 这次 GC 是 `runtime.GC()` 显式触发的 |

**关键读法**：中间那个 `8.3 ms` 是**并发标记**，它**不与用户程序竞争 STW**——用户程序在这期间照常运行。两端的 `0 ms` 才是真正的停顿。**判断 GC 有没有害，看的是两端而不是中间。**

`31->32->27 MB` 这组数的解读：GC 启动时堆 31 MB，标记完成时 32 MB，标记结束后存活 27 MB——**差出来的 5 MB 就是这一轮回收掉的**。

### 两个调优旋钮

**`GOGC`：堆增长比例**。默认 100，表示"当堆增长到上次存活量的 2 倍时触发 GC"。设成 `off` 完全关闭。

**`GOMEMLIMIT`：软内存上限**（Go 1.19 引入）。它告诉运行时"不要超过这个总量"，GC 会在接近上限时更积极地回收。

同一个程序（持续分配并保留 300 MiB）在四种设置下的实测：

```console
$ ./gc2.exe                      # 默认 GOGC=100
SUMMARY NumGC=6 HeapAlloc=300MiB HeapSys=307MiB

$ GOGC=off ./gc2.exe
SUMMARY NumGC=0 HeapAlloc=300MiB HeapSys=303MiB

$ GOGC=400 ./gc2.exe
SUMMARY NumGC=2 HeapAlloc=300MiB HeapSys=307MiB

$ GOMEMLIMIT=64MiB ./gc2.exe
SUMMARY NumGC=42 HeapAlloc=300MiB HeapSys=307MiB
```

| 设置 | GC 次数 | 说明 |
|---|---|---|
| 默认 `GOGC=100` | 6 | 基准 |
| `GOGC=off` | **0** | 完全不回收，**只适合短命进程**（如批处理脚本） |
| `GOGC=400` | 2 | 容忍更大堆，GC 更少 |
| `GOMEMLIMIT=64MiB` | **42** | **存活集 300 MiB 远超 64 MiB 上限 → GC 空转** |

**最后一行是关键教训**：`GOMEMLIMIT` 设得**低于存活集**时，GC 会陷入**抖动**（thrashing）——它拼命回收但回收不掉（对象都还活着），42 次 GC 全是白费。**`GOMEMLIMIT` 必须大于程序的稳态存活量**，否则只会浪费 CPU。

**约束**：`GOMEMLIMIT` 是**软限制**——它不阻止分配，只是提高 GC 频率。真正的内存上限仍要靠 `ulimit` 或容器配额。而且它**不能防止 OOM**，只能让 OOM 来得晚一点、让 GC 先努力一把。

### 手工干预

| 调用 | 作用 | 什么时候用 |
|---|---|---|
| `runtime.GC()` | 强制一次完整 GC（阻塞到完成） | 测试、内存敏感点前的主动释放 |
| `debug.FreeOSMemory()` | GC + **把空闲内存还给 OS** | 阶段性任务结束后收缩 RSS |
| `debug.SetGCPercent(n)` | 运行时改 `GOGC` | 按负载动态调整 |
| `debug.SetMemoryLimit(n)` | 运行时改 `GOMEMLIMIT` | 同上 |

**约束**：`runtime.GC()` 是**同步阻塞**的——它会等一次完整 GC 跑完。放在请求路径上会引入可观测的延迟尖峰。**生产代码里基本不该调用它**。

`FreeOSMemory` 的意义在于解释一个常见困惑："为什么我的程序释放了大量对象，RSS 却不降？"——因为 Go 保留空闲内存备用（[02](./02-内存分配与逃逸分析.md) 里 `HeapIdle` 那个字段），不主动还给 OS。

### Go 1.27：goroutine 泄漏 profile GA

`/debug/pprof/goroutineleak` 与 `runtime/pprof` 的 `goroutineleak` 类型在 1.27 正式可用。它**只报告真正泄漏的 goroutine**——被并发原语阻塞、且**从任何可运行 goroutine 都不可达**的那些。这比 `runtime.NumGoroutine()` 精确得多：后者把正常等待的 goroutine 也算进去。

**与其它语言对照**：

| | 算法 | 分代 | 典型暂停 |
|---|---|---|---|
| Java G1 | 分代 + 增量标记整理 | **是** | 几十毫秒（可调） |
| Java ZGC | 并发标记整理 + 染色指针 | **是** | < 1 ms |
| V8 | 分代 + 增量/并发标记清扫 | **是** | 几毫秒 |
| **Go** | **并发三色标记清扫** | **否** | **亚毫秒（与堆大小基本无关）** |

Go 与 ZGC 在"暂停极短"这个目标上一致，但**实现路径相反**：ZGC 用染色指针 + 读屏障 + 分代，Go 用写屏障 + 不分代。ZGC 的暂停更短更稳定（真正的 < 1 ms），但实现复杂度与内存开销都高得多（染色指针需要 42 位地址空间、需要多视图映射）。**Go 选了简单得多的方案，牺牲的是吞吐**——这是"Go 服务于工程效率"这条主线在 GC 上的体现。
