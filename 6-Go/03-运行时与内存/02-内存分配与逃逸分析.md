# 内存分配与逃逸分析

> 前置：[01-运行时总览与调度器](./01-运行时总览与调度器.md) · 后续：[03-垃圾回收](./03-垃圾回收.md)

> **版本基准**：Go 1.27（stable = latest）。本篇示例实测环境：go1.27.1 windows/amd64，Intel i7-10750H。

## 本质

**逃逸分析（escape analysis）是编译器在编译期判断"这个变量能否分配在栈上"的过程。**

判断规则只有一条：**如果变量的生命周期不超出它所在函数的栈帧，就分配在栈上；否则逃逸到堆**。

```console
$ go build -gcflags=-m .
./main.go:15:2: moved to heap: p          # 返回指针 → 逃逸
./main.go:22:9: p escapes to heap         # 存入 interface → 逃逸
./main.go:28:9: func literal escapes to heap  # 闭包 → 逃逸
./main.go:33:2: moved to heap: p          # 发到 channel → 逃逸
./main.go:39:11: make([]int, 4) does not escape   # 局部使用 → 不逃逸
./main.go:46:11: make([]int, 4) escapes to heap   # 返回 → 逃逸
```

**为什么值得区分**：栈分配的成本是**移动栈指针**（几条指令），释放是**函数返回时栈指针回退**——GC 完全不参与。堆分配要走分配器、要写 GC 元数据、最终要 GC 回收。

**约束的由来**：Go 的栈是**连续栈**，增长时会把整个栈拷贝到新地址（[01](./01-运行时总览与调度器.md)）。因此**栈上对象的地址不能长期有效**——一旦栈增长，旧地址失效。这就是"可能被函数外部引用的对象必须逃逸到堆"的物理原因。

**边界**：逃逸分析是**保守的**——编译器宁可多分配到堆上，也不能漏判导致悬垂指针。因此会出现"看起来不该逃逸但逃逸了"的情况（下面有例子）。

## 机制

### 用 `-gcflags=-m` 看逃逸决策

```go
func noEscape() int {          // 不逃逸
	p := Point{1, 2}
	return p.X + p.Y           // 只取字段值
}

func escapeReturn() *Point {   // 逃逸：moved to heap
	p := Point{3, 4}
	return &p                  // 指针逃出函数
}

func escapeIface() any {       // 逃逸：escapes to heap
	p := Point{5, 6}
	return p                   // 装箱进 interface{}
}

func escapeClosure() func() int {  // 逃逸：func literal escapes to heap
	p := Point{7, 8}
	return func() int { return p.X }
}

func escapeChan(ch chan *Point) {  // 逃逸：moved to heap
	p := Point{9, 10}
	ch <- &p
}
```

五条实测触发规则：

| 触发 | 报错原文 |
|---|---|
| 返回指针 | `moved to heap: p` |
| 存入 `interface{}` | `p escapes to heap` |
| 被返回的闭包捕获 | `func literal escapes to heap` |
| 地址发到 channel | `moved to heap: p` |
| 切片/映射大小未知 | `make([]int, 4) escapes to heap` |

**注意第 5 条的反例**：`make([]int, 4)` 在局部使用时是 `does not escape`，返回时才是 `escapes to heap`。**判据不是"用了 make"，而是"有没有逃出函数"**。

### 逃逸的常见隐藏来源

**一、`fmt.Println(x)` 让 `x` 逃逸**。`Println` 的参数是 `...any`，任何传进去的值都要装箱。实测输出里的 `main.go:51:22: ~r0 escapes to heap` 就是这个——调试打印会真实改变内存行为。

**二、接口方法调用**。把值存进接口变量（`var r io.Reader = &buf`）会让它逃逸，因为编译器不知道接口变量会被传给谁。

**三、切片扩容**。`append` 可能重新分配底层数组，编译器无法证明它不逃逸时，整个切片上堆。

**四、`for` 循环里取地址**。`&s[i]` 在循环中被收集进某个容器时会逃逸。

**判据**：**"这个值有没有可能在我返回后还被别人拿到？"**——是就逃逸。想验证就用 `-gcflags=-m` 实测，不要猜。

### 分配器：三级缓存

堆分配走的是 **mcache → mcentral → mheap** 三级结构，与 CPU 缓存层级同构：

| 层级 | 归属 | 粒度 | 锁 |
|---|---|---|---|
| **mcache** | 每个 P 一个 | **size class 级**（67 种规格） | **无锁**（P 独占） |
| **mcentral** | 全局，每 size class 一个 | span 级 | 有锁 |
| **mheap** | 全局 | 页级（8 KiB） | 有锁 |

**分配路径**：先查当前 P 的 mcache 对应 size class 的空闲链表；空则向 mcentral 要一个 span；mcentral 空则向 mheap 要页。

**约束**：**对象大小被归类到 67 个 size class 之一**（8、16、24、32、48…），因此"申请 20 字节"实际会拿到 24 字节的槽位。这解释了 [01-语言核心/03](../01-语言核心/03-切片与映射.md) 里"三种元素类型的首次 append 都落在 32 字节上"的实测结果——分配器只按 size class 出货。

**mcache 无锁是这套设计的关键**：绝大多数小对象分配**完全不碰全局锁**，这是 Go 能在高并发下保持分配性能的原因。

### `sync.Pool`：复用而非缓存

```console
$ go test -bench=. -benchmem -run=^$
BenchmarkNoPool-12        	25352130	        51.86 ns/op	     112 B/op	       2 allocs/op
BenchmarkWithPool-12      	33382758	        38.38 ns/op	      48 B/op	       1 allocs/op
```

**快 1.35 倍，内存少 57%**（48 B vs 112 B），分配次数 2 → 1。

**但 `sync.Pool` 不保证命中**：池里的对象**可能在任何一次 GC 时被清空**（[03](./03-垃圾回收.md)）。所以它只适合"可重新构造、构造成本高于复用收益"的临时缓冲，**不能当缓存**。

**约束**：`Get` 拿到的对象可能带着上一次使用者的数据。**必须在使用前重置**，`Put` 前也应清理——否则会把上一位用户的数据泄漏给下一位。

### 预分配：最有效的单点优化

```console
$ go test -bench=. -benchmem -run=^$
BenchmarkNoPrealloc-12    	 1000000	      1171 ns/op	    4088 B/op	       9 allocs/op
BenchmarkPrealloc-12      	 7981858	       157.3 ns/op	       0 B/op	       0 allocs/op
```

往切片里追加 256 个 `int`：**不预分配 1171 ns/op、9 次分配、4088 字节；预分配后 157.3 ns/op、0 次分配**。

**快 7.4 倍，且完全不产生堆分配**。原因在 [01-语言核心/03](../01-语言核心/03-切片与映射.md) 的扩容曲线：不预分配要经历 4→8→16→32→…→256 共 7 次重新分配与拷贝，每次都留下一个待回收的旧数组。

**判据**：**能预估大小时一律 `make([]T, 0, n)`**。这是 Go 里投入产出比最高的优化，没有之一。

### `runtime.MemStats`：看内存的真实现状

```console
$ go run .
HeapAlloc   = 244952 字节（0.24 MB）当前存活
HeapSys     = 8.29 MB（向 OS 要的总量）
HeapObjects = 252 个存活对象
HeapIdle    = 7.77 MB（已归还但未释放）
NumGC       = 0 次
GCSys       = 1.51 MB（GC 元数据）
StackInuse  = 0.10 MB（goroutine 栈）
Mallocs     = 256 累计分配次数
Frees       = 4 累计释放次数

分配 100MB 后：
HeapAlloc   = 105.13 MB
HeapObjects = 373
```

几个字段的判读：

| 字段 | 含义 | 什么时候看 |
|---|---|---|
| `HeapAlloc` | **当前存活对象的字节数** | 看内存占用 |
| `HeapSys` | 向 OS 要的总量 | 看 RSS 为什么下不去 |
| `HeapObjects` | 存活对象**个数** | 看有没有对象泄漏 |
| `HeapIdle` | 已归还但未释放给 OS | 解释 HeapSys 与 HeapAlloc 的差 |
| `NumGC` | GC 次数 | 判断 GC 压力 |
| `Mallocs` - `Frees` | 净分配次数 | 与 HeapObjects 对照 |

**注意 `HeapSys` 远大于 `HeapAlloc` 是正常的**（8.29 MB vs 0.24 MB）——Go 向 OS 要内存是**批量**的（按 arena，64 MB 对齐），不会一字节一字节要，也不会立刻还。`debug.FreeOSMemory()` 可以强制归还。

**约束**：`ReadMemStats` 会**短暂 STW**（stop the world）。高频调用会拖慢程序——监控采集间隔应在秒级，不要放在热路径。

**下游**：[03](./03-垃圾回收.md) 回收堆上的对象——**逃逸分析的成果直接决定 GC 的工作量**；[07-性能剖析与调优](./07-性能剖析与调优.md) 用 `-benchmem` 的 `allocs/op` 与 heap profile 定位分配热点。

**与其它语言对照**：

| | 栈/堆分配决策 | 谁决定 | 可观测 |
|---|---|---|---|
| C/C++ | 程序员显式（`malloc` vs 局部变量） | 人 | 靠工具 |
| Java | **全部对象在堆上**（逃逸分析只在 JIT 里做标量替换） | JIT | `-XX:+PrintEscapeAnalysis` |
| **Go** | **编译器逃逸分析** | 编译器 | **`-gcflags=-m`** |

Java 的逃逸分析发生在 **JIT 阶段**，只对热点代码生效，且主要用于"标量替换"（把对象拆成字段放寄存器）而非改分配位置——**Java 的对象仍然全部在堆上**。Go 的逃逸分析发生在**编译期**，直接决定分配位置，因此对**所有代码**生效，且**结果可查**（`-gcflags=-m` 是给开发者看的）。

这也是 Go 里"为什么 `var x T` 与 `x := new(T)` 性能可能差很多"的原因——而 Java 里两者没有区别。
