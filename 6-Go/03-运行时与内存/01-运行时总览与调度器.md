# 运行时总览与调度器

> 前置：[01-语言核心](../01-语言核心/) · 后续：[02-内存分配与逃逸分析](./02-内存分配与逃逸分析.md)

> **版本基准**：Go 1.27（stable = latest）。本篇示例实测环境：go1.27.1 windows/amd64，Intel i7-10750H（6 核 12 线程）。

## 本质

**Go 的运行时（runtime）不是外部进程，是链接进每个二进制的一个库。**

这句话是本目录与 Java 的 [03-JVM与运行时](../../4-Java/03-JVM与运行时/) 的切分点。Java 的程序跑在 JVM 上——JVM 是另一个进程，有启动参数、有版本、要单独安装；Go 的程序里，`runtime` 包和你的 `main` 包一起被编译进同一个可执行文件（[00-概览/01](../00-概览/01-Go全景.md)）。

运行时管五件事：

| 子系统 | 职责 | 主场节 |
|---|---|---|
| 调度器 | 把 goroutine 映射到 OS 线程 | 本篇 |
| 分配器 | 满足 `make`/`new`/逃逸对象的堆请求 | [02](./02-内存分配与逃逸分析.md) |
| 垃圾回收 | 回收不可达对象 | [03](./03-垃圾回收.md) |
| 栈管理 | goroutine 栈的分配、增长、收缩 | 本篇 |
| 系统调用桥接 | 阻塞式 syscall 时释放 P | [05-IO与外部世界/02](../05-IO与外部世界/02-网络编程.md) |

**边界**：`runtime` 包是**内部实现**，它的 API 只暴露了少量可控点（`GOMAXPROCS`、`GOGC`、`GOMEMLIMIT`、`runtime.Gosched`）。**不要依赖 `runtime` 的内部结构**——`g`/`m`/`p` 结构体的字段布局每个版本都可能变，`runtime` 也不承诺兼容性。

## 机制

### GMP：三个角色

```console
$ go run .
GOMAXPROCS = 12
NumCPU     = 12
NumGoroutine(起 goroutine 前) = 1
Go 版本     = go1.27.1
```

| 角色 | 是什么 | 数量 |
|---|---|---|
| **G**（goroutine） | 用户态执行单元 | 任意多 |
| **M**（machine） | OS 线程 | 按需创建，受 `GOMAXPROCS` 间接限制 |
| **P**（processor） | 调度上下文（本地队列 + 缓存） | **恰好 `GOMAXPROCS` 个** |

**`P` 的数量是 `GOMAXPROCS`，这是"同时能跑多少个 goroutine"的硬上界**。上面 12 是 i7-10750H 的 12 个逻辑核（6 物理核 × 超线程）。一个 M 要运行 G，必须先绑定一个 P。

**约束的由来**：为什么要 P 这一层，而不是直接把 G 挂到 M 上？

1. **本地队列**：每个 P 有自己的可运行 G 队列，取 G 不需要全局锁。全局队列只在本地队列空时访问。
2. **系统调用解耦**：M 陷入阻塞式 syscall 时，P 可以**被解绑交给另一个 M**——不浪费一个调度槽位。
3. **`GOMAXPROCS` 才有意义**：如果只有 G 和 M，限制并发度只能靠限制 M 的数量，而 M 会因为 syscall 阻塞被占用。

**Go 1.25 起 `GOMAXPROCS` 容器感知**：默认值会读取 cgroup 的 CPU 限额，而不是盲目取 `NumCPU`。这修掉了一个长期问题——在 CPU 限额 2 核的容器里，旧版 Go 会按宿主机核数起 P，导致大量无谓的上下文切换。

### 工作窃取

P 的本地队列空时，按以下顺序找活干：

1. **本地队列**（无锁）
2. **全局队列**（有锁）
3. **从其他 P 偷**——随机挑一个 P，偷走它队列的**一半**

偷一半而不是一个，是为了**摊薄窃取成本**：窃取本身要加锁，一次多拿些才划算。

```console
$ go run .
--- GOMAXPROCS(1) 下 6 个 goroutine 的执行顺序 ---
完成顺序: [5 0 1 2 3 4]
```

**顺序是 `5 0 1 2 3 4` 而不是 `0 1 2 3 4 5`**。原因是 Go 1.14 引入的 **`runnext` 槽位**：新创建的 G 会被放在当前 P 的 `runnext`（一个单元素槽），**优先于本地队列中的其他 G 运行**。循环里最后创建的那个（5）抢占了 `runnext`，于是它先跑。

**约束**：这个行为**不保证**——`runnext` 只是优化，调度顺序在任何版本、任何负载下都可能不同。**依赖 goroutine 启动顺序的代码是错的**，同步必须靠 channel 或 `sync` 包（[04-并发](../04-并发/)）。

### 抢占：从协作到异步

Go 的调度是**抢占式**的，但实现方式在 1.14 有过一次大改：

| | Go 1.13 及以前 | Go 1.14 起 |
|---|---|---|
| 机制 | 协作式：函数序言插入抢占检查点 | **基于信号的异步抢占** |
| 能否抢占死循环 | **不能**（`for {}` 会占死 P） | 能 |
| 实现 | 编译器插桩 | `SIGURG` 信号 + `mcall` |

**约束**：即使有了异步抢占，**抢占点也不在任意指令处**——运行时会等目标 G 到达一个**安全点**（safe point，此时寄存器与栈状态可被完整描述）才真正切换。因此抢占有延迟，但不会无限期。

**边界**：`cgo` 调用期间和 `runtime` 内部的临界区**不可被抢占**。长时间占用这些区域的代码仍会拖慢整个程序。

### 阻塞与唤醒：`sudog` 队列

**goroutine 阻塞时不占线程**——这是 Go 并发模型的另一半，也是 [04-并发/02](../04-并发/02-channel与select.md) 的 channel 阻塞与 [04-并发/03](../04-并发/03-sync与原子操作.md) 的 mutex 争抢共同的底层机制。

一次阻塞由三步构成：

| 步 | 做什么 | 源码位置 |
|---|---|---|
| 1 | 把当前 G 包成一个 **`sudog`** 节点，挂到被等待对象的等待队列上 | `runtime2.go` 的 `type sudog struct` |
| 2 | 调用 **`gopark`**，G 进入等待态，M 被释放去跑别的 G | `proc.go` 的 `func gopark(...)` |
| 3 | 条件满足时另一方调用 **`goready`**，G 回到运行队列 | `proc.go` 的 `func goparkunlock(...)` |

**`sudog` 里存的是什么**（结构体注释原文：*The following fields are protected by the hchan.lock of the channel this sudog is blocking on*）：

```go
type sudog struct {
	g    *g               // 被阻塞的 goroutine
	next *sudog           // 队列里的前后指针
	prev *sudog
	elem maybeTraceablePtr // 数据元素（可能指向栈上）
	...
}
```

**`elem` 是"可能指向栈上"的**——这正是阻塞能被安全支持的原因：**goroutine 的栈会增长并被拷贝**，所以等待队列里不能存栈地址。运行时的解法是让 `sudog` 记录的地址在栈收缩时被修正（`shrinkstack` 依赖这个字段）。

**等待队列挂在谁身上**：

| 等待对象 | 队列 | 源码 |
|---|---|---|
| channel | `recvq` / `sendq`（两个 `waitq` 链表） | `chan.go` 的 `type hchan struct` |
| mutex / `sync.WaitGroup` / `sync.Cond` | **信号量** `semaRoot` 的平衡树 | `sema.go` 的 `type semaRoot struct` |

**`semaRoot` 的注释说明了为什么是树而不是链表**：*A semaRoot holds a balanced tree of sudog with distinct addresses (s.elem).* 多个 goroutine 等同一个地址时，树结构让插入与删除保持 O(log n)。

**`sudog` 本身是复用对象**，否则每次阻塞都要分配：

```go
func acquireSudog() *sudog {
	pp := getg().m.p.ptr()
	if len(pp.sudogcache) == 0 {
		// 从全局 sched.sudogcache 借一半过来
		...
	}
}
```

**缓存是 P 级的，全局只作溢出**——这与 [02](./02-内存分配与逃逸分析.md) 的 `mcache`/`mcentral` 是同一套思路：高频分配的东西按 P 分片，避免全局锁。

**约束**：**"阻塞不占线程"的代价是每次阻塞要走一次 `gopark`，每次唤醒要走一次 `goready`**——这两步都要碰调度器的锁。所以**细粒度、高频的 channel 操作会放大调度开销**（[04-并发/03](../04-并发/03-sync与原子操作.md) 实测 `sync.Map` 在低竞争下反而比 `map+RWMutex` 慢，同一个道理）。**判据**：热点路径上能用无锁原子操作解决的，不要用 channel。

### goroutine 栈：按需伸缩

goroutine 的栈**从很小开始，按需增长**：

```console
$ go run .
--- 起 10 万个 goroutine ---
NumGoroutine 峰值 = 100001
堆增长 = 60.59 MB（635 字节/goroutine）
全部退出后 NumGoroutine = 1
```

**10 万个挂起的 goroutine 只占 60.59 MB，平均 635 字节**。对照 OS 线程：Linux 默认线程栈 8 MB（虚拟），实际驻留也在几十 KB 量级——10 万个线程根本起不来。

**约束**：goroutine 的初始栈是 **2 KiB**（`_StackMin`），比线程小三个数量级。栈不够时运行时**分配一块更大的栈并整体拷贝过去**（不是链表式栈段），因此**指向栈上变量的指针在增长后会失效**——这正是"栈上的对象一旦可能被外部引用就必须逃逸到堆"的根源（[02](./02-内存分配与逃逸分析.md)）。

**边界**：栈不能无限增长。默认上限是 1 GB（64 位平台），超过会 panic `goroutine stack exceeds 1000000000-byte limit`。**无限递归不会栈溢出崩溃，而是先耗尽内存**——这与 C 的栈溢出（段错误）表现不同。

栈也会**收缩**：GC 时如果发现栈只用了不到四分之一，会拷回小块。

### 可观测点

| API | 用途 |
|---|---|
| `runtime.GOMAXPROCS(n)` | 读/设 P 的数量（`n=0` 是只读） |
| `runtime.NumGoroutine()` | 当前 G 数量，**查泄漏的第一指标** |
| `runtime.Gosched()` | 主动让出 P，把当前 G 放回全局队列 |
| `runtime.GC()` | 强制一次 GC（[03](./03-垃圾回收.md)） |
| `runtime.ReadMemStats(&m)` | 读内存统计（[02](./02-内存分配与逃逸分析.md)） |
| `GODEBUG=schedtrace=1000` | 每秒打印调度器状态 |

`runtime.NumGoroutine()` 是排查 goroutine 泄漏最直接的手段——如果它随时间单调增长，说明有 G 卡在某个 channel 或锁上（[04-并发/01](../04-并发/01-goroutine与生命周期.md) 给了实测的泄漏例子）。

**Go 1.27 新增 goroutine 泄漏 profile**：`/debug/pprof/goroutineleak` 与 `runtime/pprof` 的 `goroutineleak` 类型正式 GA。它比 `NumGoroutine` 更精确——**能识别"被并发原语阻塞、且从任何可运行 goroutine 都不可达"的 goroutine**，也就是真正泄漏的那些，而不是正常等待的。

**与其它语言对照**：

| | 用户态执行单元 | 调度 | 栈 |
|---|---|---|---|
| Java | 虚拟线程（21+）/ 平台线程 | ForkJoinPool（虚拟线程用） | 虚拟线程按需分段 |
| Python | 无（GIL 限制） | — | — |
| C++ | `std::thread`（无用户态调度） | OS 调度 | 固定，溢出即崩溃 |
| **Go** | **goroutine** | **GMP + 工作窃取** | **2 KiB 起，拷贝式增长** |

Java 21 的虚拟线程与 goroutine 目标相同（M:N 调度、廉价创建），差别在**栈的实现**：虚拟线程用**分段栈**（stack chunk 链表，增长时不需要拷贝），goroutine 用**连续栈**（拷贝整个栈）。分段栈增长更便宜，但每次访问栈变量都要检查是否跨段；连续栈访问快，但增长时要拷贝。**Go 选择了访问性能优先**——因为栈访问的频率远高于栈增长。
