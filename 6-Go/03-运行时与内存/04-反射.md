# 反射

> 前置：[03-垃圾回收](./03-垃圾回收.md) · 后续：[05-unsafe与内存布局](./05-unsafe与内存布局.md)

> **版本基准**：Go 1.27（stable = latest）。本篇示例实测环境：go1.27.1 windows/amd64，Intel i7-10750H（6 核 12 线程）。

## 本质

**反射是"在运行时检查与操作值的类型"的能力**。它让程序能回答编译期无法回答的问题：这个 `any` 里装的是什么类型？它有几个字段？字段叫什么名字？

两个入口：

```go
reflect.TypeOf(x)    // 得到 reflect.Type：类型是什么
reflect.ValueOf(x)   // 得到 reflect.Value：值是什么
```

**约束的由来**：反射**绕过了 Go 的静态类型系统**——用 `reflect` 取字段、调方法，编译器完全无法检查。这带来三笔账：

1. **编译期检查失效**：字段名写错只在运行时 panic。
2. **性能开销**：动态派发无法内联，实测见下。
3. **可读性下降**：读代码时看不出实际调用了什么。

**判据**：反射该出现在**类型在编译期确实未知的边界上**——JSON 序列化、ORM 字段映射、模板渲染、通用校验器。**不该出现在内部 API 里**——那说明设计漏了接口或泛型（[01-语言核心/09](../01-语言核心/09-泛型.md)）。

## 机制

### `Type` 与 `Value`：Kind vs Type

```console
$ go run .
Type: main.User  Kind: struct  Name: User
MyString: Type = main.MyString  Kind = string
与 string 同 Kind: true
```

| | `Type` | `Kind` |
|---|---|---|
| 是什么 | **具体的类型** | **底层分类** |
| 例子 | `main.MyString`、`main.User` | `string`、`struct`、`ptr`、`slice` |
| 取值 | 任意多个 | **只有 26 种**（`reflect.Kind` 常量） |

**判据**：**几乎总是该用 `Kind` 判断**。`Type` 是精确的（`type MyString string` 与 `string` 是两个 `Type`），`Kind` 是分类的（两者 Kind 都是 `string`）。想写"处理所有字符串"的代码，用 `Kind`；想写"只处理 `string` 本身"，用 `Type` 相等比较。

```console
$ go run .
int Kind = int  struct Kind = struct  ptr Kind = ptr  slice Kind = slice
```

### 遍历字段与读取 tag

```console
$ go run .
NumField: 3
  字段 Name  类型 string json="name" validate="required" 值=张三
  字段 Age   类型 int    json="age" validate="min=0" 值=30
  字段 Bio   类型 string json="bio,omitempty" validate="" 值=
```

`t.Field(i)` 返回 `StructField`，带 `Name`/`Type`/`Tag`/`Index` 等字段。**`Tag.Get("key")` 是读取 struct tag 的唯一方式**——tag 本质是一个字符串，格式是 `key:"value" key2:"value2"`，`Get` 负责解析。

**约束**：tag 的格式**不会被编译器检查**。写 `json:"name` （少个引号）编译通过，`Get` 返回空串，字段被当成没有 tag。这是 Go 里少见的"字符串协议"。

**判据**：`encoding/json`（[02-标准库/05](../02-标准库/05-序列化与编码.md)）、`encoding/xml`、`database/sql`、各种校验库都靠 tag 驱动，**读它们的源码能直接看懂配置怎么生效**。

### 可设置性：`CanSet` 与 `CanAddr`

```console
$ go run .
ValueOf(u).CanSet() = false
ValueOf(&u).Elem().CanSet() = true
反射改 Age 后: 31
对不可设置的 Value 调 Set → reflect: reflect.Value.SetInt using unaddressable value
```

**这是反射最容易踩的坑**。`reflect.ValueOf(u)` 把 `u` **拷贝**了一份，这份拷贝没有地址，因此不能设置。要修改原值必须传指针再 `Elem()`：

```go
v := reflect.ValueOf(&u).Elem()   // 可设置
v.FieldByName("Age").SetInt(31)
```

**约束的由来**：`Value` 要能设置，底层必须是**可寻址的**（[01-语言核心/06](../01-语言核心/06-方法与接收者.md) 讲的同一套规则）。`ValueOf` 的入参是 `any`，装箱时值被拷贝到接口的数据字段里——那是一份只读的副本。

**错误信息本身很有用**：`using unaddressable value` 直接指出了病因。

### 动态调用方法

```console
$ go run .
MethodByName("Greet").Call() = hi 张三
```

`Call` 接收 `[]reflect.Value` 返回 `[]reflect.Value`。**参数与返回值都要装箱**，因此：

- 每次调用都分配
- 类型不匹配会 panic（不是编译错误）
- 无法内联

**判据**：动态方法调用在真实代码里很少见。需要"运行时选择行为"时，**接口（[01-语言核心/08](../01-语言核心/08-接口.md)）或函数值（[01-语言核心/05](../01-语言核心/05-函数.md)）几乎总是更好的选择**——它们有编译期检查，且快得多。

### 反射的代价：实测

```console
$ go test -bench=. -benchmem -run=^$
BenchmarkDirectField-12            	1000000000	         0.7157 ns/op	       0 B/op	       0 allocs/op
BenchmarkReflectField-12           	12530215	        95.31 ns/op	       0 B/op	       0 allocs/op
BenchmarkReflectFieldByIndex-12    	190465185	         5.984 ns/op	       0 B/op	       0 allocs/op
BenchmarkReflectTypeOf-12          	1000000000	         0.2462 ns/op	       0 B/op	       0 allocs/op
```

读两个字段（`Name` 与 `Age`）：

| 方式 | ns/op | 相对直接访问 |
|---|---|---|
| 直接字段访问 | **0.7157** | 1× |
| `FieldByName("Name")` | **95.31** | **133×** |
| `Field(i)`（按下标） | **5.984** | **8.4×** |
| `reflect.TypeOf(x)` | 0.2462 | 0.34×（**比直接访问还快**） |

三条结论：

**一、`FieldByName` 是 133 倍**。它要做**字符串比较**遍历所有字段名。这是反射里最贵的操作。

**二、改用下标 `Field(i)` 降到 8.4 倍**——**16 倍差距**。这是反射优化的核心手法：**把字段下标缓存起来，只算一次**。

```go
// ❌ 每次调用都按名字查
v.FieldByName("Name")

// ✅ 初始化时算一次，之后按下标
idx, _ := t.FieldByName("Name")   // 得到 StructField.Index
// 后续：v.FieldByIndex(idx.Index)
```

**三、`TypeOf` 几乎免费**（0.2462 ns）。它只是读接口值的类型指针，不涉及遍历。**缓存 `reflect.Type` 是廉价的**——`encoding/json` 就是这么做的（按类型缓存编解码器）。

**注意 `0 allocs/op`**：这里的 `Value` 都是栈上的临时值，逃逸分析把它们留在了栈上。真实场景里 `Call` 与 `Interface()` 会产生分配。

**约束**：反射的优化空间**在于减少反射调用次数**，不在于让单次调用更快。**能缓存的一律缓存**（字段下标、`Type`、`Method`），这是 `encoding/json` 与各种 ORM 性能的关键。

## 连接

**上游**：[01-语言核心/08](../01-语言核心/08-接口.md) 的接口运行时表示（`iface`/`eface`）是反射的数据来源；[01-语言核心/06](../01-语言核心/06-方法与接收者.md) 的可寻址性规则决定了 `CanSet`。

**下游**：[02-标准库/05](../02-标准库/05-序列化与编码.md) 的 `encoding/json` 是反射最大的用户（Go 1.27 的 v2 引入了代码生成路径来绕开反射）；[08-生态与框架](../08-生态与框架/) 的 ORM 与校验库都建立在反射上；[05-unsafe与内存布局](./05-unsafe与内存布局.md) 是**比反射更底层**的手段——反射仍受类型系统约束，unsafe 不受。

**与其它语言对照**：

| | 反射能力 | 代价 |
|---|---|---|
| Java | 完整（`Class`/`Method`/`Field`，可访问私有） | 慢，破坏封装 |
| Python | 不需要（一切都是动态的） | 无编译期检查 |
| C++ | **没有运行时反射**（RTTI 只有类型识别） | — |
| **Go** | **有，但只能访问导出成员** | **133× 的字段访问代价** |

**Go 的反射有一个 Java 没有的限制：只能读写导出字段**（[01-语言核心/11](../01-语言核心/11-包与可见性.md)）。`FieldByName` 对非导出字段返回的 `Value` 不能 `Set`——这正是 [02-标准库/05](../02-标准库/05-序列化与编码.md) 里"非导出字段被 JSON 静默忽略"的根源。Java 的反射可以 `setAccessible(true)` 强闯私有成员，Go 从设计上不允许。
