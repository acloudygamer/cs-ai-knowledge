# Go 1.18 至 1.27

> 前置：[02-Go 1.0 至 1.17](./02-Go1.0至1.17.md) · 后续：无（本目录终篇）

> **版本基准**：Go 1.27（stable = latest）。本篇示例实测环境：go1.27.1 windows/amd64。

## 本质

**2022-03-15 到 2026-08-19，四年半，十个版本。这十年只做了一件事：把 1.17 之前欠下的语言表达力补回来，同时不违反兼容承诺。**

补课的三条主线：

| 主线 | 轨迹 |
|---|---|
| **泛型的成熟** | 1.18 类型参数 → 1.21 推断改进 → 1.24 泛型别名 → 1.26 自引用约束 → 1.27 泛型方法 |
| **运行时** | 1.19 `GOMEMLIMIT` → 1.20/1.21 PGO → 1.24 Swiss map → 1.26 Green Tea GC → 1.27 小对象特化 |
| **工具链** | 1.18 workspace → 1.21 `go` 行转硬性 + `GOTOOLCHAIN` → 1.24 `tool` 指令 → 1.26 `go fix` 重写 |

**约束的由来**：**补课不能破坏承诺，所以每一处改动都要给出迁移路径**——循环变量语义（1.22）这种必然破坏现有代码的改动，靠 `go` 行的语言版本隔离；`net/url` 的收紧（1.26）靠 GODEBUG 隔离（[01-演进脉络与提案流程](./01-演进脉络与提案流程.md)）。**这是这十个版本的共同形态：新语义 + 版本门控**。

| 版本 | 发布日 | 标志性变化 |
|---|---|---|
| **1.18** | 2022-03-15 | **泛型**；**模糊测试**；**workspace** |
| 1.19 | 2022-08-02 | **`GOMEMLIMIT`**；`atomic.Int64` 等类型；文档注释格式化 |
| 1.20 | 2023-02-01 | `errors.Join`；`context.WithCancelCause`；**PGO 预览** |
| **1.21** | 2023-08-08 | **`min`/`max`/`clear`**；**`log/slog`**；**`slices`/`maps`/`cmp`**；**`go` 行转硬性最低版本 + `GOTOOLCHAIN`** |
| **1.22** | 2024-02-06 | **循环变量按迭代**；`range over int`；**`ServeMux` 方法 + 通配路由**；`math/rand/v2` |
| 1.23 | 2024-08-13 | **`iter` 与 range-over-func**；Timer/Ticker 可被 GC；`unique` |
| **1.24** | 2025-02-11 | **泛型类型别名**；`os.Root`；`weak`；**Swiss map**；`tool` 指令 |
| 1.25 | 2025-08-12 | **无语言变更**；`sync.WaitGroup.Go`；容器感知 `GOMAXPROCS`；`testing/synctest` 转正 |
| 1.26 | 2026-02-10 | `new(表达式)`；**Green Tea GC 默认**；`errors.AsType`；**`go fix` 重写为 modernizers** |
| **1.27** | 2026-08-19 | **泛型方法**；**`encoding/json/v2`**；`crypto/mldsa`；**goroutine 泄漏剖析转正** |

## 机制

### 泛型：从落地到补完（1.18 → 1.27）

**1.18 落地的泛型是不完整的**——release notes 明确列了五条限制：

| 1.18 的限制 | 解除于 |
|---|---|
| 泛型函数内不能声明类型 | 1.20（新前端） |
| 类型参数不能 `real`/`imag`/`complex` | — |
| 调用类型参数的方法必须由约束显式声明 | — |
| 不能通过类型参数访问结构体字段 | — |
| **类型别名不能带类型参数** | **1.24** |
| **方法不能有自己的类型参数** | **1.27** |

**最后两条是补课的重点**，因为它们决定了泛型能不能被库作者真正用起来。

实测：**从 1.18 到 1.27 的特性采样**（同一份源码，go1.27.1 编译）：

```console
$ go run .
1.18 泛型 Sum[int]      = 6
1.18 泛型 Sum[float64]  = 4
1.21 min/max            = 1 3
1.21 clear(map) 后 len  = 0
1.21 slices.Max         = 5
1.21 slices.Sort 后     = [1 1 3 4 5]
1.22 range over int 次数 = 5
1.23 range over func 和  = 14
1.25 WaitGroup.Go 和     = 10
1.26 new(表达式)        = 30
1.26 errors.AsType 命中  = true
1.27 泛型方法 Map        = box(42)
1.27 CutLast            = "a/b" "c" true
```

**1.21 是补课的转折点**——`slices`、`maps`、`cmp` 三个泛型标准库包 + `min`/`max`/`clear` 三个内建。**这之后泛型才真正"可用"**：在 1.21 之前，用泛型需要自己写 `Max[T constraints.Ordered]`，或者依赖 `golang.org/x/exp`（不受兼容承诺保护）。

**1.27 的泛型方法**是这个序列的终点，也是形态最特殊的一个：

```go
// 1.27：方法自己声明类型参数
func (b Box[T]) Map[U any](f func(T) U) Box[U] { return Box[U]{f(b.v)} }
```

**约束**：**接口方法不能声明类型参数，也不能被泛型方法实现**——所以泛型方法**不能用于满足接口**，它只服务于"对具体类型做一次变换"这类场景。官方给的标准例子是 `math/rand/v2` 的 `(*Rand).N[Int intType](n Int) Int`。

**边界**：**泛型的补课是"加能力"而不是"改语义"**——1.18 的类型参数语义到 1.27 一字未改，中间六版加的全是**能写出来的程序的范围**。这就是兼容承诺下的语言演进形态：**扩大合法程序集合，不改变已有程序的含义**。

### 运行时：GC 的第二次提速（1.19 → 1.27）

1.5 和 1.8 解决了"暂停时间"，这十年的主题是**"GC 的开销与可控性"**：

| 版本 | 改动 | 目标 |
|---|---|---|
| 1.19 | `GOMEMLIMIT`（设计 #48409） | 把 GC 从"按比例"改成"按绝对上限" |
| 1.20 | 内部结构重组 | CPU 开销降 2% |
| 1.21 | 显式透明大页管理 | 小堆内存省 50% |
| 1.24 | **Swiss table 版内建 map** | 平均 CPU 开销降 2–3% |
| 1.25 | Green Tea GC（`GOEXPERIMENT=greenteagc`） | GC 开销降 10–40% |
| 1.26 | **Green Tea GC 转默认** | 同上 + 新 CPU 上再约 10% |
| 1.27 | **小对象分配特化** | <80 字节分配最多快 30% |

**1.19 的 `GOMEMLIMIT` 是唯一一个"改变调优范式"的**——它让"内存上限"成为一等配置项（[03-运行时与内存/03](../03-运行时与内存/03-垃圾回收.md) 有完整实测，包括设得过低导致的 GC 抖动）。

**1.27 的小对象特化可以精确测出来**——同一份 benchmark，开关 `GOEXPERIMENT=nosizespecializedmalloc`：

```console
$ go test -bench=. -benchtime=500000x -count=5     # 默认
BenchmarkAlloc16-12     	  500000	        11.96 ns/op	      16 B/op	       1 allocs/op
BenchmarkAlloc24-12     	  500000	        13.19 ns/op	      24 B/op	       1 allocs/op
BenchmarkAlloc48-12     	  500000	        16.39 ns/op	      48 B/op	       1 allocs/op
BenchmarkAlloc80-12     	  500000	        21.06 ns/op	      80 B/op	       1 allocs/op
BenchmarkAlloc128-12    	  500000	        31.49 ns/op	     128 B/op	       1 allocs/op
```

（上表为 5 次的中位数；`GOEXPERIMENT=nosizespecializedmalloc` 的对照组见下表。）

| 对象大小 | 默认（ns/op） | 关闭特化（ns/op） | 变化 |
|---|---|---|---|
| 16 B | **11.96** | 17.49 | **−31.6%** |
| 24 B | **13.19** | 18.27 | **−27.8%** |
| 48 B | **16.39** | 21.54 | **−23.9%** |
| 80 B | **21.06** | 25.97 | −18.9% |
| 128 B | 31.49 | 32.05 | −1.7%（噪声内） |

**收益随对象变大而衰减，在 128 字节处消失**——官方说法是"cut small (<80 byte) allocation cost up to 30%"，**实测在 16 字节处正好 31.6%，到 80 字节只剩 19%**。这条曲线比"最多快 30%"这个数字更有用：**它告诉你在什么规模上值得期待收益**。

**代价是二进制变大**（官方说约 60 KB）：

```console
$ go build -o hello-default.exe . && GOEXPERIMENT=nosizespecializedmalloc go build -o hello-noexp.exe .
默认        : 2496512 字节
nosizespec : 2454016 字节
差值        : 42496 字节          # +1.7%
```

**判据**：**分配密集型服务值得这 42 KB**；分配很少的程序（CLI 工具）收益接近零。

### 可观测性：goroutine 泄漏剖析（1.26 试验 → 1.27 转正）

**goroutine 泄漏是 Go 里最常见也最难查的资源泄漏**——goroutine 卡在 channel 上，既不占 CPU 也不报错，只是内存慢慢涨。

1.26 引入试验性的 `goroutineleak` profile（设计文档 `design/74609-goroutine-leak-detection-gc.md`），1.27 转正。它的原理是**在 GC 之后做可达性分析**：一个阻塞的 goroutine，如果它等待的对象已经不可达，那它就永远不会被唤醒。

实测（3 个泄漏 + 100 个正常 goroutine）：

```console
$ go run .
goroutine     的 Count() = 4
goroutineleak 的 Count() = 0  <- 首次读取，扫描尚未触发
goroutineleak profile: total 3
3 @ 0x7ff7d36bc52a 0x7ff7d3651e8e 0x7ff7d36519d2 0x7ff7d3727e39 0x7ff7d36c2601
#	0x7ff7d3727e38	main.leakOne.func1+0x18	D:/cs-ai-knowledge/.gotmp/ver/leak/main.go:14

goroutineleak 的 Count() = 3  <- 扫描之后
```

**三件事同时被证实**：

| 观察 | 说明 |
|---|---|
| `goroutine` = 4 | 全量 profile 只看得到总数，**看不出哪些是泄漏** |
| `goroutineleak` = 3 | **精确识别出 3 个泄漏，100 个正常 goroutine 一个没误报** |
| 首次 `Count()` = 0 | **扫描是惰性的**——必须先 `WriteTo` 一次触发，`Count()` 才有值 |

**约束**：**这个 profile 依赖 GC**——如果程序长时间不触发 GC（内存压力小），泄漏检测也不会跑。**判据**：**在生产环境用 `/debug/pprof/goroutineleak` 之前，先确认 GC 在正常触发**（[03-运行时与内存/03](../03-运行时与内存/03-垃圾回收.md) 的 `GODEBUG=gctrace=1`）。

**边界**：**它只找"不可达的阻塞"**——goroutine 卡在一个仍然可达的 channel 上（比如全局队列满了）不会被报出来。**那是背压问题，不是泄漏**。

### 工具链：从"没有版本概念"到"工具链是依赖"

这十年工具链的改动比语言大得多：

| 版本 | 改动 | 效果 |
|---|---|---|
| 1.18 | `go work` workspace | 多模块本地联调不再需要 `replace` |
| 1.21 | `go` 行转为**硬性最低要求**；`toolchain` 行；`GOTOOLCHAIN` | **工具链版本成为可声明、可自动切换的依赖** |
| 1.23 | `go telemetry`（默认 `local`） | 遥测数据可查、可关 |
| 1.24 | `tool` 指令 + `go get -tool` | 取代 `tools.go` 空白导入的 workaround |
| 1.26 | **`go fix` 重写为 modernizers** | 老代码自动迁移到新 API |
| 1.27 | `go fix` 新增 `atomictypes`/`embedlit`/`slicesbackward`/`unsafefuncs` | 继续扩充 |

**1.21 是分界点**——在此之前，`go` 行只是建议，装了 1.21 的工具链能编译 `go 1.22` 的模块；之后**工具链会拒绝加载 `go` 行高于自身的模块**：

> The Go toolchain refuses to load a module or workspace that declares a minimum required Go version greater than the toolchain's own version.

配套的 `GOTOOLCHAIN=auto`（默认值）让工具链**自动下载并切换到需要的版本**：

```
go: module example.com/widget@v1.2.3 requires go >= 1.24rc1; switching to go 1.27.9
```

**判据**：**`go fix` 的 modernizers 是这套机制的另一半**——工具链能自动升级，代码里的旧写法也要能自动升级。**1.26 把 `go fix` 从"历史遗留修复器"重写成"现代化的统一入口"**，用的分析框架与 `go vet` 相同。

**边界**：**`go fix` 只做语义等价的替换**（`strings.Cut` 代替 `Index`+切片、`atomic.Int64` 代替裸 `int64`+`atomic` 函数），**不做重构**。它能省掉"新 API 出来了但没人改老代码"的这段摩擦，不能替你设计。

### 被低估的一条线：后量子密码

**这十年推进最快的其实是密码学**，而且全部是默认值级别的改动：

| 版本 | 改动 |
|---|---|
| 1.24 | `crypto/mlkem`（ML-KEM，FIPS 203）；`crypto/hkdf`、`crypto/pbkdf2`、`crypto/sha3` 入库；TLS 默认启用 `X25519MLKEM768` |
| 1.25 | SHA-1 签名在 TLS 1.2 中被禁用 |
| 1.26 | 混合密钥交换 `SecP256r1MLKEM768`/`SecP384r1MLKEM1024` **默认启用**；`crypto/hpke` 入库 |
| 1.27 | `crypto/mldsa`（ML-DSA，FIPS 204）；TLS 新增 `MLDSA44/65/87` 签名方案 |

**约束**：**这些都是"默认启用"**——不需要改代码，重新编译就获得了抗量子能力。**这是 Go 兼容承诺在安全领域的一次正面应用**：密码学升级是最需要"不改代码就能生效"的场景，因为改动密码学调用点的风险远高于重新编译。

**边界**：**默认启用意味着连接的对端也要支持**——混合密钥交换会先协商，对端不支持时回退到经典算法。所以**"我的服务支持后量子"不等于"我的流量受后量子保护"**（[05-IO与外部世界/02](../05-IO与外部世界/02-网络编程.md)）。

**与其它语言对照**：

| | 泛型落地 | 循环变量语义修复 | 工具链版本管理 |
|---|---|---|---|
| **Java** | 2004（1.5） | 一直按迭代 | 无（靠 LTS + 构建工具） |
| **C#** | 2005（2.0） | 一直按迭代 | 无 |
| **C++** | 模板（1998） | 一直按迭代 | 无 |
| **Rust** | 1.0（2015） | 一直按迭代 | `rustup` + `rust-toolchain.toml` |
| **Go** | **1.18（2022）** | **1.22（2024）** | **`go` 行 + `toolchain` 行 + `GOTOOLCHAIN`** |

**Go 的泛型比 Java 晚十八年，循环变量语义比所有人都晚**——这两件事都是兼容承诺的直接代价。**Java 在 2004 年加泛型时做了类型擦除，Go 在 2022 年加泛型时选了带字典的实现**，两者都不完美，但 Go 的方案不需要为了兼容而牺牲运行时类型信息。

**循环变量的修复更能说明问题**：这个语义在 C、Java、C# 里一直是"按迭代"，Go 因为 1.0 时的实现选择而不同。**修它的唯一办法是加版本门控**——1.22 起按迭代，但 `go 1.21` 及更早的模块保持原语义。**这是兼容承诺下"修正错误"的模板**，也是这十个版本里最能体现"Go 的演进是怎么做的"的例子。
