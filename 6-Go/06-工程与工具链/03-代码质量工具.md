# 代码质量工具

> 前置：[02-模块与依赖管理](./02-模块与依赖管理.md) · 后续：[04-项目布局](./04-项目布局.md)

> **版本基准**：Go 1.27（stable = latest）。本篇示例实测环境：go1.27.1 windows/amd64，staticcheck（`honnef.co/go/tools/cmd/staticcheck@latest`）。

## 本质

**Go 的质量工具分两层：标准库自带的一层（`gofmt`、`go vet`），与第三方的一层（`staticcheck`、`golangci-lint`）。**

| 层 | 工具 | 检查什么 |
|---|---|---|
| **标准库** | `gofmt` | 格式 |
| | `go vet` | **37 个分析器**（[01-go命令详解](./01-go命令详解.md)） |
| **第三方** | `staticcheck` | **约 150 条规则**，含风格与语义 |
| | `golangci-lint` | **聚合器**，把几十个 linter 打包成一个命令 |
| | `goimports` | `gofmt` + 导入的自动增删与分组 |

**约束的由来**：为什么标准库只做了 `gofmt` + `go vet` 这两样？因为 **`go vet` 的定位是"几乎肯定是 bug"**——它宁可漏报也不误报。风格建议、可疑但合法的写法、性能提示，全部留给第三方。

**判据**：**`go vet` 的失败必须修**（它报的都是真问题）；**staticcheck 的失败要看情况**（有误报，且有些是风格偏好）。

## 机制

### `gofmt`：不可配置的格式化

```console
$ gofmt -l .
ugly.go
```

`gofmt` **没有任何配置项**（[01-go命令详解](./01-go命令详解.md) 展开过这条约束的收益与代价）。CI 里的标准用法：

```bash
test -z "$(gofmt -l .)" || { gofmt -l .; exit 1; }
```

**注意 `gofmt -l` 的退出码永远是 0**——它只列出文件，不表示失败。必须用上面这个 shell 判断。

### `goimports`：`gofmt` 的超集

```console
$ go install golang.org/x/tools/cmd/goimports@latest
$ goimports -w .
```

`goimports` 在 `gofmt` 之上做了三件事：

1. **自动添加**缺失的 import（根据代码里用到的符号猜包）
2. **自动删除**未使用的 import
3. **自动分组**：标准库 / 第三方 / 本项目，三组之间空行分隔

**约束**：自动添加 import 依赖它能在**已下载的模块**里找到匹配的包——私有包或没在 `go.mod` 里的包不会被自动补上。

**判据**：**项目里用 `goimports` 而不是 `gofmt`**——多出来的三个能力全是刚需，且它是 `gofmt` 的严格超集（格式结果完全相同）。

### `staticcheck`：约 150 条规则

`staticcheck` 的规则按前缀分类：

| 前缀 | 类别 | 例子 |
|---|---|---|
| `SA` | **Staticcheck**：几乎肯定是 bug | `SA4006` 赋值后未使用、`SA6005` 应该用 `strings.EqualFold` |
| `S` | **Simple**：可以简化的写法 | `S1002` 冗余的布尔比较、`S1011` 循环 append |
| `ST` | **Stylecheck**：命名与风格 | `ST1003` 命名不规范 |
| `QF` | **Quickfix**：可自动修复 | 配合 `-fix` 使用 |

实测（故意写坏的代码）：

```console
$ staticcheck ./...
bad.go:11:2: should use 'return b == true' instead of 'if b == true { return true }; return false' (S1008)
bad.go:11:5: should omit comparison to bool constant, can be simplified to b (S1002)
bad.go:20:2: redundant return statement (S1023)
bad.go:25:2: should replace loop with a = append(a, b...) (S1011)
bad.go:41:2: should use a simple channel send/receive instead of select with a single case (S1000)
bad.go:49:2: this value of s is never used (SA4006)
bad.go:49:6: this result of append is never used, except maybe in other appends (SA4010)
bad.go:54:5: should omit nil check; len() for nil slices is defined as zero (S1009)
bad.go:62:9: should use strings.EqualFold instead (SA6005)
```

**每条都带规则编号**——可以用 `//lint:ignore SA4006 理由` 注释**逐条抑制**，理由必填：

```go
//lint:ignore SA4006 这里的赋值是为了触发 GC 的副作用
x = compute()
```

**约束**：`staticcheck` **不是 `go vet` 的超集**——两者有各自独有的检查。**应当都跑**。`staticcheck` 默认包含 `go vet` 的一部分检查（通过 `-checks=all` 可以打开更多），但不完全覆盖。

**判据**：`staticcheck` 的 `SA` 类必须修（真 bug）；`S` 类看团队偏好；`ST` 类在已有代码库上通常只对新增代码启用（全量启用会产生海量告警）。

### `golangci-lint`：聚合器

```console
$ golangci-lint run ./...
```

`golangci-lint` **本身不做检查**——它调用几十个 linter（含 `staticcheck`、`govet`、`errcheck`、`ineffassign`、`gosec` 等），合并输出，并提供统一配置。

| 优点 | 缺点 |
|---|---|
| **一个命令、一份配置** | 版本升级会一次性改变大量规则 |
| 并行执行，比逐个跑快 | 依赖树的体积大 |
| 支持缓存与增量 | 部分 linter 的版本与上游不同步 |

**配置**（`.golangci.yml`）的核心是 `enable`/`disable` 列表与 `exclude-rules`。**Go 生态的普遍做法是"只启用高置信度的 linter"**——全开会产生大量噪音，团队会习惯性忽略告警，工具就失效了。

**判据**：**`errcheck` 是最值得启用的一个**——它检查"错误返回值没有被处理"（[01-语言核心/10](../01-语言核心/10-错误处理.md) 讲过 Go 不强制处理错误，`errcheck` 补的就是这个缺口）。

**约束**：`errcheck` 在真实代码库里误报很多——`fmt.Fprintln`、`json.Marshal` 到 `bytes.Buffer` 这些"不可能失败"的调用也会被报。需要配 `exclude-functions` 列表。

### `go vet` 与 staticcheck 的分工

| | `go vet` | `staticcheck` |
|---|---|---|
| 归属 | **标准库** | 第三方 |
| 规则数 | 37 | 约 150 |
| 误报倾向 | 极低 | 低（S/ST 类有风格偏好） |
| 运行成本 | 快 | 较慢（需类型信息全量分析） |
| CI 地位 | **必跑** | 推荐 |

**实测对比**（同一份代码）：`go vet` 抓到 `copylocks`/`printf`/`stringintconv`/`timeformat`（[01-go命令详解](./01-go命令详解.md)），`staticcheck` 抓到 `S1002`/`S1023`/`S1011`/`S1000`/`SA4006`/`SA4010`/`S1009`/`SA6005`。**两者几乎不重叠**——`go vet` 管"写错了"，`staticcheck` 管"写歪了"。

### 安全扫描

| 工具 | 查什么 |
|---|---|
| `govulncheck`（**官方**） | 依赖里的**已知漏洞**，且**只报你实际调用到的** |
| `gosec` | 代码里的安全问题（弱随机数、SQL 拼接、文件权限） |
| `gitleaks` | 提交历史里的密钥泄漏 |

**`govulncheck` 的判据很关键**——它做**可达性分析**：如果一个有漏洞的函数你从没调用过，它不报。这大幅减少了噪音：

```console
$ go install golang.org/x/vuln/cmd/govulncheck@latest
$ govulncheck ./...
```

**约束**：`govulncheck` 需要网络访问漏洞数据库（`vuln.go.dev`），**离线环境需要自建镜像**。

### 代码覆盖率

```console
$ go test -cover ./...
$ go test -coverprofile=cover.out ./...
$ go tool cover -html=cover.out
```

| 粒度 | 标志 |
|---|---|
| 语句覆盖（默认） | `-cover` |
| **按包/函数统计** | `-coverpkg=./...`（跨包统计） |
| 原子模式（并发安全） | `-covermode=atomic` |

**约束**：**`-coverpkg` 不加的话，只统计被测试包自身的覆盖率**——如果一个测试调用了别的包的代码，那些代码不计入。做整体覆盖率统计必须加 `-coverpkg=./...`。

**边界**：**覆盖率是"有没有测到"，不是"测得对不对"**。100% 覆盖率的代码可以有严重 bug——覆盖率只保证每行代码被执行过，不保证断言充分。**不要把覆盖率当质量门禁的硬指标**（[07-测试与质量/04](../07-测试与质量/04-模糊测试与基准测试.md) 有更细的讨论）。

**与其它语言对照**：

| | 格式化 | Linter | 聚合器 |
|---|---|---|---|
| JavaScript | Prettier（**可配置**） | ESLint（**可配置**） | — |
| Python | Black（少量配置） | Ruff / flake8 | Ruff（**自己聚合**） |
| Java | google-java-format | SpotBugs / Error Prone | — |
| **Go** | **gofmt（零配置）** | **go vet + staticcheck** | **golangci-lint** |

**Go 的格式化工具零配置，这是全生态唯一的**。Python 的 Black 接近（只提供行宽等少数选项），JavaScript 的 Prettier 有几十个选项。**零配置的收益是"不需要在 PR 里讨论格式"**——而这恰好是代码评审里最没价值的一类讨论。

**代价是 `gofmt` 的某些选择有争议**：比如它坚持用 Tab 缩进、对齐 struct 字段的注释、把长的函数签名拆行。这些无法调整——**要么接受，要么不用**。
