# 模块与依赖管理

> 前置：[01-go命令详解](./01-go命令详解.md) · 后续：[03-代码质量工具](./03-代码质量工具.md)

> **版本基准**：Go 1.27（stable = latest）。本篇示例实测环境：go1.27.1 windows/amd64。

## 本质

**模块（module）是"一组一起发布、一起版本化的包"，由 `go.mod` 文件界定；`go.mod` 里记录的版本是"最低要求"，不是"锁定的版本"。**

后半句是 Go 依赖管理与 npm/pip 的根本差别：

| | 记录什么 | 选哪个版本 |
|---|---|---|
| **Go** | **最低要求**（`require` 行） | **所有要求里的最高者** |
| npm | `package.json` 范围 + `package-lock.json` 精确锁定 | 按 lock 文件 |
| pip | `requirements.txt` 精确或范围 | 按解析顺序 |
| Maven | 最近的声明（nearest-wins） | 依赖树深度优先 |

**约束的由来**：Go 的这套算法叫 **MVS（Minimal Version Selection，最小版本选择）**。它解决的问题是"**可复现的构建**"——给定同一组 `go.mod`，任何机器上都得到完全相同的依赖版本，不需要额外的 lock 文件。

**MVS 的核心洞察**：如果每个模块都声明"我至少需要 X 版本"，那么**取所有要求中的最大值**就是一个确定性的答案，且**不需要遍历所有可用版本**。

## 机制

### `go.mod` 的结构

```console
$ go mod tidy
$ cat go.mod
module mod1

go 1.27

require (
	github.com/google/uuid v1.6.0
	golang.org/x/text v0.42.0
)

require golang.org/x/tools v0.49.0 // indirect
```

四段内容：

| 行 | 含义 |
|---|---|
| `module mod1` | **模块路径**——这个模块对外的全局唯一名（[01-语言核心/11](../01-语言核心/11-包与可见性.md)） |
| `go 1.27` | **语言版本口径**（[01-语言核心/01](../01-语言核心/01-安装与第一个程序.md)） |
| `require (...)` | **直接依赖**及其最低版本 |
| `require ... // indirect` | **间接依赖**——不直接被 import，但为了可复现构建而记录 |

**`// indirect` 的意义**：Go 1.17 起引入**模块图剪枝**（module graph pruning）——`go.mod` 只记录"构建这个模块实际需要的"依赖版本，而不是整个传递闭包。带 `// indirect` 的是"我的直接依赖所需要的，但我自己不 import"的那些。

**约束**：**`// indirect` 标记由 `go mod tidy` 维护，不要手改**。手工删掉一行 `indirect` 会让 `go mod tidy` 在下次运行时加回来，或者导致构建失败。

### `go.sum`：校验而非锁定

```console
$ wc -l < go.sum
4
```

`go.sum` 里每行是一个 `模块 版本 hash`，**两行一组**（一个模块的 `.mod` 文件哈希 + `.zip` 文件哈希）。

**它不是 lock 文件**——它**不决定用哪个版本**（那是 `go.mod` 的 MVS 决定的），它只**校验下载到的内容与第一次构建时一致**。

**约束**：**`go.sum` 必须提交到版本库**。它保证的是"**同样的 `go.mod` 在任何时间、任何机器上得到同样的代码**"——即使模块作者事后修改了已发布的 tag（这是可能的，Go module proxy 不可变缓存能防一部分，但不能防全部）。

**`go mod verify`** 校验本地模块缓存的内容：

```console
$ go mod verify
all modules verified
```

### MVS：取所有要求中的最高版本

```console
$ go mod graph
mod1 github.com/google/uuid@v1.6.0
mod1 golang.org/x/text@v0.42.0
golang.org/x/text@v0.42.0 golang.org/x/tools@v0.49.0
golang.org/x/text@v0.42.0 golang.org/x/mod@v0.41.0
golang.org/x/text@v0.42.0 golang.org/x/sync@v0.23.0
```

`go mod graph` 每行是 `A@v B@v`，表示"A 的 v 版本要求 B 至少是 v"。MVS 的算法：

1. 从主模块出发，收集所有 `require` 边。
2. 对每个模块，**取所有要求中的最高版本**。
3. 用这个集合重新展开（因为高版本可能引入新的要求）。
4. 重复直到收敛。

**约束**：**MVS 只会选高不选低**。如果 A 要 `lib@v1.2`、B 要 `lib@v1.5`，结果是 `v1.5`——**哪怕 `v1.2` 也满足 A**。

**这条规则的后果是"升级传染"**：只要依赖树里任何一处要求了高版本，整个构建就用高版本。这保证了**同一个模块在整个构建里只有一个版本**（不像 npm 可能同时装 `lodash@3` 和 `lodash@4`）。

**但显式 `go get` 可以降级**——它是**改写 `go.mod` 里的最低要求**，而不是被 MVS 选择：

```console
$ go get github.com/google/uuid@v1.5.0
go: downgraded github.com/google/uuid v1.6.0 => v1.5.0

$ go get github.com/google/uuid@v1.3.0
go: downgraded github.com/google/uuid v1.5.0 => v1.3.0
```

**约束**：**降级可能失败**——如果别的依赖要求更高版本，`go mod tidy` 会把版本提回去。`go get` 的降级只有在"没有任何依赖要求更高"时才能保持。

### 常用 `go mod` 子命令

| 命令 | 作用 |
|---|---|
| `go mod init <path>` | 初始化模块 |
| `go mod tidy` | **增删 require 行，使之与实际 import 一致** |
| `go mod download` | 下载依赖到缓存 |
| `go mod graph` | 打印依赖图 |
| `go mod why <pkg>` | **解释为什么需要某个包** |
| `go mod vendor` | 把依赖复制到 `vendor/` |
| `go mod verify` | 校验缓存内容 |
| `go mod edit` | 用脚本编辑 `go.mod` |

```console
$ go mod why golang.org/x/text/language
# golang.org/x/text/language
mod1
golang.org/x/text/language
```

`go mod why` 输出**从主模块到该包的最短路径**——排查"这个依赖是谁引进来的"的标准手段。

**约束**：`go mod tidy` **应当作为提交前的固定动作**。它会：

- 删掉代码里不再 import 的依赖
- 补上代码里 import 但 `go.mod` 里没有的依赖
- 补齐 `// indirect` 标记
- **更新 `go.sum`**

**CI 里常见做法是跑 `go mod tidy` 然后检查 `git diff` 是否为空**——这保证提交的 `go.mod` 是最新的。

**Go 1.27 的变化**：`go mod tidy` 会把重复的 `require` 块合并成**最多两个**（直接依赖 + 间接依赖），并保留注释块。

### `vendor/`：把依赖复制进仓库

```console
$ go mod vendor
```

`vendor/` 目录会把所有依赖的源码复制进来。此后**构建不再需要网络或模块缓存**——`go build` 直接用 `vendor/`。

**判据**：

| | 用 `vendor/` | 不用 |
|---|---|---|
| 构建隔离 | **完全隔离**（不依赖 proxy 与缓存） | 需要能访问模块源 |
| 仓库体积 | 大（依赖全在仓库里） | 小 |
| 依赖审计 | **`git diff` 就能看到依赖变化** | 要看 `go.sum` |
| CI 速度 | 快（不用下载） | 首次慢 |

**约束**：**有 `vendor/` 目录时，`go build` 默认用它**，`go.mod` 里的版本仍会被校验。要强制用模块缓存加 `-mod=mod`。

**Go 生态的主流选择是"不用 vendor"**——依赖 proxy（`proxy.golang.org` 或私有 proxy）的可用性足够，且 `vendor/` 会让仓库变大、review 变吵。**少数场景需要 vendor**：完全离线的构建环境、对依赖做本地 patch、合规要求代码入库。

### 私有模块

```console
$ go env GOPRIVATE GONOSUMDB GONOSUMCHECK
```

| 环境变量 | 作用 |
|---|---|
| `GOPRIVATE` | **匹配的模块不走 proxy、不校验 sumdb**（通常设为 `*.corp.example.com`） |
| `GONOSUMDB` | 只跳过 sumdb 校验 |
| `GOPROXY` | proxy 地址（`off` 禁用、`direct` 直连、`\|` 分隔的回退链） |
| `GOFLAGS` | 默认标志（如 `-mod=vendor`） |
| `GONOSUMCHECK` | 已废弃 |
| `GOVCS` | 限制哪些模块可以用哪些 VCS 工具 |

**`GOPRIVATE` 是配私有仓库的关键**——它同时影响 proxy 与校验，是最常用的单个变量。

**约束**：`GOPRIVATE` 的值是**逗号分隔的 glob 模式**，匹配的是**模块路径**而不是 URL。设为 `github.com/mycorp/*` 会让该组织的模块直连 GitHub（用 SSH 凭据）。

### 工作区：`go.work`

**多个模块一起开发**时（比如主程序 + 本地库），传统做法是在主模块的 `go.mod` 里加 `replace` 指向本地路径。工作区是它的替代品：

```console
$ go work init ./lib ./app
$ cat go.work
go 1.27.1

use (
	./app
	./lib
)
```

有了 `go.work` 之后，**`app/go.mod` 里的 `replace` 可以删掉**——工作区自动把 `./lib` 解析成本地目录。

| | `replace` 写在 `go.mod` | `go.work` |
|---|---|---|
| 影响范围 | **提交后影响所有人** | **本地文件，通常不提交** |
| 需要改每个模块吗 | 是 | 否 |
| 适合 | 长期的 fork/替换 | **本地多模块开发** |

**约束**：**`go.work` 通常不提交**（要加到 `.gitignore`）——它是开发者本地的便利，提交后会让 CI 也去用本地路径。例外是 monorepo 里所有模块确实一起开发。

**`go work sync`** 把工作区的依赖版本回写到各模块的 `go.mod`。

**与其它语言对照**：

| | 版本选择 | lock 文件 | 多版本共存 |
|---|---|---|---|
| **Go** | **MVS（取最高）** | **不需要**（`go.mod` + `go.sum` 足够） | **不允许** |
| npm | 嵌套解析 | `package-lock.json` | **允许**（嵌套 node_modules） |
| pip | 回溯求解 | `requirements.txt` / `poetry.lock` | 允许（虚拟环境） |
| Maven | nearest-wins | 无（除非用 dependencyManagement） | 不允许 |

**Go 的"不需要 lock 文件"是 MVS 的直接结果**——因为版本选择是**确定性的纯函数**（输入是 `go.mod` 集合，输出是版本集合），不需要记录"上次解析的结果"。npm 需要 lock 是因为它的解析算法依赖"安装顺序"和"注册表的当前状态"。

**"不允许同一模块多版本共存"是另一条关键约束**。npm 的嵌套 `node_modules` 让 `lodash@3` 与 `lodash@4` 能同时存在——灵活，但会导致"同一个库的两个实例"这类诡异 bug（单例失效、instanceof 失败）。**Go 用 MVS 从设计上消除了这个问题**，代价是升级传染。
