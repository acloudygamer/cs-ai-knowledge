# 项目布局

> 前置：[03-代码质量工具](./03-代码质量工具.md) · 后续：[05-构建交叉编译与发布](./05-构建交叉编译与发布.md)

> **版本基准**：Go 1.27（stable = latest）。本篇示例实测环境：go1.27.1 windows/amd64。

## 本质

**Go 没有官方规定的项目布局。** 官方仓库 `golang/go` 里有一个 `golang-standards/project-layout` 社区仓库，但它**不是官方标准**——Go 团队多次澄清过这一点。

真正被**语言机制强制**的只有两样：

| 机制 | 强制什么 |
|---|---|
| **包是封装单位**（[01-语言核心/11](../01-语言核心/11-包与可见性.md)） | 目录 = 包，可见性靠大小写 |
| **`internal/` 是保留目录名** | `internal` 下的包只能被其父目录子树导入 |

**其余全部是约定**。`cmd/`、`pkg/`、`api/` 这些名字**没有任何特殊含义**——它们是社区习惯，改了不影响编译。

**约束的由来**：Go 的设计者刻意不规定布局，因为**布局应当由项目的问题域决定**，而不是由语言规定。一个库、一个 CLI 工具、一个微服务，它们的合理布局本就不同。

**边界**：正因为没有强制，**"什么算好布局"的判据只能是"它是否让依赖关系可见"**——好的布局让读者一眼看出"哪些包依赖哪些包""哪些是对外 API""哪些是内部实现"。

## 机制

### 一个完整布局的实测

```console
$ go list -f '{{.ImportPath}} -> package {{.Name}}' ./...
example/demo/app              -> package main
example/demo/internal/secret  -> package secret
example/demo/mathutil         -> package mathutil
```

`go list` 输出的是**导入路径**，而导入路径由**目录结构 + 模块路径**决定：

```
example/demo/          ← go.mod 里的 module 行
├── go.mod
├── main.go            → example/demo（如果是 package main，通常放 cmd/ 下）
├── mathutil/          → example/demo/mathutil
│   └── mathutil.go
├── internal/          ← 保留目录名
│   └── secret/        → example/demo/internal/secret
│       └── secret.go
└── cmd/
    └── app/           → example/demo/cmd/app（package main）
        └── main.go
```

### `internal/`：唯一有强制力的目录

```console
$ go build ./...        # 在另一个模块 example/outside 里
main.go:6:2: use of internal package example/demo/internal/secret not allowed
```

**规则**：路径中**最后一个 `internal` 之前的目录**是可见性根，只有该根目录下的代码能导入它。

| 导入路径 | 谁能导入 |
|---|---|
| `example/demo/internal/secret` | 只有 `example/demo/` 子树内 |
| `example/internal/x` | 只有 `example/` 子树内 |

**约束**：`internal` 是**唯一**给"包级隔离"提供编译期强制的机制。其余所有布局约定（`cmd`/`pkg`/`api`）都只是名字——**放错位置不会报错**。

**判据**：**任何"不想被外部导入"的包都该放进 `internal/`**。这是零成本的保护——不需要文档说明"这个包是内部的"，编译器替你保证。

### `cmd/`：多入口

```
cmd/
├── server/
│   └── main.go       → 可执行文件 server
├── cli/
│   └── main.go       → 可执行文件 cli
└── migrate/
    └── main.go       → 可执行文件 migrate
```

每个子目录一个 `package main`，`go build ./cmd/server` 产出 `server`。

**约束的由来**：`cmd/` 不是强制的，但它解决一个真实问题——**一个仓库产出多个二进制**。如果只有一个入口，`main.go` 放根目录就行。

**判据**：**`main.go` 应当只做装配**——解析配置、建依赖、启动服务，**不含业务逻辑**。业务逻辑放 `internal/`，这样它能被测试（`main` 包很难测）。上面的 `cmd/app/main.go` 如果写了业务逻辑，就没法写单元测试。

**边界**：`cmd/` 下的包名都叫 `main`，因此**不能互相导入**——它们之间的共享代码必须提到 `internal/` 或 `pkg/`。

### `pkg/`：有争议的约定

`pkg/` 的约定是"**可以被外部项目导入的包**"。

**这条约定在 Go 社区有明确争议**：

| 支持 | 反对 |
|---|---|
| 明确区分"公开 API"与"内部实现" | **Go 的导入路径已经表达了这一点**——外部项目导入的是 `example.com/demo/pkg/foo`，多一层 `pkg` 没有增加信息 |
| 与 `internal/` 对称 | 若模块路径本身是 `example.com/demo`，那 `demo/foo` 就已经是可导入的 |
| 从其它语言（Java 的 `src/main/java`）带来的习惯 | Go 官方仓库自己**不用 `pkg/`**（用的是 `src/`） |

**判据**：**默认不用 `pkg/`**。把可导入的包直接放模块根下（`example.com/demo/mathutil`）更短也更清晰。**需要区分时用 `internal/` 标记"不可导入的"**——那是编译器强制的，比 `pkg/` 的软约定可靠。

### `api/`、`web/`、`configs/` 等

| 目录 | 放什么 | 强制力 |
|---|---|---|
| `api/` | OpenAPI/protobuf 定义、API 契约 | 无 |
| `web/` | 静态资源、前端代码 | 无 |
| `configs/` | 配置模板、默认配置 | 无 |
| `scripts/` | 构建与运维脚本 | 无 |
| `testdata/` | **测试数据** | **Go 工具链会忽略它** |
| `docs/` | 文档 | 无 |

**`testdata/` 是第二个有特殊含义的目录名**——`go build`、`go test`、`go vet` 都会**跳过 `testdata/` 目录**。因此它是放测试固件的标准位置（[07-测试与质量/02](../07-测试与质量/02-单元测试与mock.md)）。

**约束**：除了 `internal/` 与 `testdata/`，**其余目录名对工具链毫无意义**。一个叫 `internal` 的目录会真的限制导入；一个叫 `pkg` 的目录不会做任何事。

### 布局与依赖方向

好的布局的核心是**让依赖方向可见**。一个典型的服务：

```
cmd/server/main.go           ← 装配（依赖所有层）
    ↓
internal/handler/            ← HTTP 层（依赖 service）
internal/service/            ← 业务逻辑（依赖 repository、domain）
internal/repository/         ← 数据访问（依赖 domain）
internal/domain/             ← 领域模型（不依赖任何内部包）
```

**约束**：**依赖方向必须单向**——`domain` 不导入 `service`，`service` 不导入 `handler`。这条约束由**编译器的循环导入禁令**（[01-语言核心/11](../01-语言核心/11-包与可见性.md)）部分保证，但**跨层的反向依赖不会报错**（`domain` 导入 `repository` 是合法的，只是设计错了）。

**判据**：**用接口把依赖方向倒过来**。`service` 需要 `repository` 时，在 `service` 包里**定义它需要的接口**（[01-语言核心/08](../01-语言核心/08-接口.md) 的隐式满足让这成为可能），`repository` 的实现去满足它。这样依赖方向是 `repository → service`（实现依赖接口），而不是反过来。

**这条是 Go 与 Java 在架构上的关键差别**：Java 的接口通常定义在"被调用方"的包里（`UserRepository` 接口在 repository 包），Go 的惯例是定义在"调用方"的包里。**结果是 Go 的依赖方向天然更容易做对**。

### 反模式

| 反模式 | 问题 |
|---|---|
| **所有代码放根包** | 无法用 `internal` 隔离；导入路径全变成 `example.com/demo/foo`，无法收紧可见性 |
| **过深嵌套**（5 层以上） | 导入路径冗长，且通常说明包的划分过细 |
| **`util/`、`common/`、`helpers/`** | **没有内聚性的包**——它们会成为所有东西的垃圾桶，最终导入图变成一团乱麻 |
| **一个目录塞几十个文件** | 通常是"该拆包了"的信号（[01-语言核心/11](../01-语言核心/11-包与可见性.md)：包是 Go 的封装单位） |
| **循环依赖靠 `interface{}` 绕过** | 掩盖了真实的耦合，运行时的类型断言会散落各处 |

**`util` 包是 Go 社区公认的反模式**。判据是：**一个包的名字应当说明它提供什么能力**——`mathutil` 比 `util` 好，`httpauth` 比 `helpers` 好。如果一个包实在找不出合适的名字，通常说明它该被拆开。

### 布局与编译缓存

包的划分**直接影响增量编译的粒度**（[00-概览/01](../00-概览/01-Go全景.md)）：

- **改一个包 → 重编它和它的下游**。
- 包越大，改动触发的重编范围越大。
- 包越小、依赖越少，缓存的命中率越高。

**约束**：这条给出了"包该多大"的一个量化判据——**高频改动的代码应当与低频改动的代码分在不同的包里**。把领域模型（稳定）与业务逻辑（频繁改）分开放，改业务逻辑时不需要重编领域模型的下游。

**边界**：不要为了编译速度过度拆包——包太小会让导入路径变长、包间跳转变多，可读性下降。**"按职责拆"仍然是第一判据**，编译缓存是附带收益。

**与其它语言对照**：

| | 布局规定 | 强制手段 |
|---|---|---|
| Java | Maven/Gradle **约定** `src/main/java/...` | 构建工具（不遵守会构建失败） |
| Python | 无（包 = 目录 + `__init__.py`） | 无 |
| Rust | Cargo 约定 `src/`、`tests/`、`benches/` | 构建工具 |
| **Go** | **无官方布局** | **只有 `internal/` 与 `testdata/` 被工具链识别** |

**Go 是四者中唯一"布局完全自由"的**——Java 的 Maven 布局不遵守就没法构建，Rust 的 `src/main.rs` 是 Cargo 的硬性要求。Go 只强制两个目录名，其余全靠社区约定。

**代价是"没有标准答案"**——新人会问"我的项目该长什么样"，而官方没有答案。**收益是"布局可以跟着问题域走"**——一个 CLI 工具不需要 `internal/handler/`，一个库不需要 `cmd/`，强制统一反而会引入无意义的目录。
