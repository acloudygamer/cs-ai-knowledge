# 构建、交叉编译与发布

> 前置：[04-项目布局](./04-项目布局.md) · 后续：[07-测试与质量](../07-测试与质量/)

> **版本基准**：Go 1.27（stable = latest）。本篇示例实测环境：go1.27.1 windows/amd64，Intel i7-10750H。

## 本质

**Go 的构建产物是一个自包含的静态可执行文件**——运行时、标准库、你的代码全在一个文件里（[00-概览/01](../00-概览/01-Go全景.md)）。

这条性质决定了发布流程的形态：**没有"部署运行时"这一步**。Java 要装 JRE、Python 要装解释器与依赖、Node 要装 node_modules，Go 只需要把文件拷过去。

**约束**：这条只在 **`CGO_ENABLED=0`** 时完全成立。用了 cgo 就依赖 C 运行时（[03-运行时与内存/06](../03-运行时与内存/06-CGO与跨语言调用.md)），静态链接与交叉编译都要打折。

## 机制

### 交叉编译：两个环境变量

```console
$ go tool dist list | wc -l
47
```

**Go 1.27 支持 47 个 `GOOS/GOARCH` 组合**。在 windows/amd64 上一条命令直接产出各平台产物：

```console
$ CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -o out_linux_amd64 .
$ CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build -o out_linux_arm64 .
```

| GOOS | GOARCH | 产物大小 |
|---|---|---|
| linux | amd64 | 2,350,681 |
| linux | arm64 | 2,342,261 |
| darwin | arm64 | 2,429,714 |
| windows | amd64 | 2,496,512 |
| freebsd | amd64 | 2,285,470 |
| **js** | **wasm** | **2,507,538** |

**同一个"打印 hello"程序，六个平台全部构建成功，体积在 2.28–2.51 MB 之间**。`GOOS=js GOARCH=wasm` 产出的是 WebAssembly 模块——Go 还能编译到浏览器里。

**约束**：`GOARCH=arm64` 时还可以用 **`GOARM64`** 指定微架构（默认 `v8.0`，可设为 `v8.1` 等，产物只能用对应或更新的 CPU 特性）：

```console
$ go version -m out_linux_arm64
	build	GOARCH=arm64
	build	GOOS=linux
	build	GOARM64=v8.0
```

**`CGO_ENABLED=1` 时交叉编译立刻失效**（[03-运行时与内存/06](../03-运行时与内存/06-CGO与跨语言调用.md) 实测报 `sys/mman.h: No such file or directory`）——那时需要目标平台的 C 交叉工具链并设 `CC`。

### 构建标志：体积与可复现

```console
$ CGO_ENABLED=0 go build -o a.exe .
$ CGO_ENABLED=0 go build -ldflags="-s -w" -o b.exe .
$ CGO_ENABLED=0 go build -trimpath -o c.exe .
$ CGO_ENABLED=0 go build -ldflags="-s -w" -trimpath -o d.exe .
```

| 标志 | 大小 | 变化 |
|---|---|---|
| 默认 | 2,496,512 | — |
| `-ldflags="-s -w"` | **1,660,416** | **−33.5%** |
| `-trimpath` | 2,486,272 | −0.4% |
| 两者都加 | **1,650,688** | **−33.9%** |

| 标志 | 作用 | 代价 |
|---|---|---|
| `-s` | 省略符号表 | 无法用 `gdb` 调试、`pprof` 的函数名可能不全 |
| `-w` | 省略 DWARF 调试信息 | **无法用 `dlv` 调试、panic 堆栈没有行号** |
| `-trimpath` | 去掉源码的绝对路径 | 无（**应当总是加**） |

**`-s -w` 省下三分之一体积**（约 840 KB）。**判据**：生产发布加，**本地开发与需要排查线上 panic 时不要加**——`-w` 会让 panic 堆栈丢失文件名与行号（[01-语言核心/10](../01-语言核心/10-错误处理.md)）。

**`-trimpath` 应当总是加**：它把编译时的绝对路径（`D:\cs-ai-knowledge\.gotmp\hello`）替换成模块相对路径。**收益是构建可复现**——同一份代码在不同机器上编译出**字节完全相同**的产物。不加的话，你的构建目录路径会泄漏进二进制，且不同机器上产物的哈希不同。

### 注入构建信息

```console
$ go build -ldflags "-X main.Version=1.2.3 -X main.Commit=abc123 -X main.BuildTime=2026-09-27" -o v.exe .
$ ./v.exe
version=1.2.3 commit=abc123 built=2026-09-27
```

`-X` 的格式是 **`-X importpath.varname=value`**，只能给**字符串类型的包级变量**赋值。

**约束**：`-X` 的目标变量**必须存在于代码里**（`var Version = "dev"`）——名字写错**不会报错**，只是静默不生效。这是发布流程里常见的坑：CI 的 `-X` 拼错了，二进制里还是 `dev`。

**判据**：**CI 里构建后必须验证版本号**——跑一次 `./app --version` 确认输出正确，而不是相信 `-X` 生效了。

### 自动嵌入的 VCS 信息

```console
$ go version -m out_linux_arm64
out_linux_arm64: go1.27.1
	path	example/hello
	mod	example/hello	(devel)
	build	-buildmode=exe
	build	-compiler=gc
	build	CGO_ENABLED=0
	build	GOARCH=arm64
	build	GOOS=linux
	build	GOARM64=v8.0
	build	vcs=git
	build	vcs.revision=1ad41a9720d66da3b411503dd109317f4944319b
	build	vcs.time=2026-09-27T10:03:25Z
```

**Go 1.18 起，构建时如果目录在 Git 仓库里，会自动把 commit hash 与提交时间嵌进二进制**。不需要 `-ldflags`，`go version -m <binary>` 就能读出来。

**这条对排查线上问题极其有用**——拿到一个二进制就能知道它是从哪个 commit 构建的。`runtime/debug.ReadBuildInfo()` 可以在程序里读到这些信息（[01-语言核心/01](../01-语言核心/01-安装与第一个程序.md)）。

**约束**：需要**有 `.git` 目录且 git 可用**。在 CI 里用浅克隆（`--depth=1`）时信息仍然可用；但**在没有 `.git` 的环境里构建**（比如从 tarball 解压的源码）会缺失。加 `-buildvcs=false` 可以显式关闭。

**边界**：`vcs.modified=true` 表示**构建时工作区有未提交的改动**——这是发布流程要检查的：**发布产物不该带这个标记**。

### `go install`：安装工具

```console
$ go install example.com/cmd/tool@latest
```

`go install pkg@version` 是**在模块外安装工具**的方式——它**不修改当前模块的 `go.mod`**，装到 `GOBIN`（默认 `$GOPATH/bin`）。

**约束**：**`go install pkg@version` 必须在模块外运行**（或在 `GOFLAGS=-mod=mod` 下）。在模块内运行不带 `@version` 的 `go install` 会安装当前模块里的包。

**工具依赖的管理**是 Go 生态的一个长期问题。两种方案：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| `go install` | CI 里显式装各工具 | 简单 | **版本不受 `go.mod` 管理**，不同机器可能装到不同版本 |
| **`tools.go`** | 建一个带 `//go:build tools` 的文件 import 所有工具 | **版本进 `go.mod`/`go.sum`**，可复现 | 需要多一个文件 |

`tools.go` 的写法：

```go
//go:build tools

package tools

import (
	_ "golang.org/x/tools/cmd/goimports"
	_ "honnef.co/go/tools/cmd/staticcheck"
)
```

**`//go:build tools` 让这个文件不参与正常构建**，但 `go mod tidy` 会把它 import 的工具记进 `go.mod`（[02-模块与依赖管理](./02-模块与依赖管理.md)）。

### 发布产物的形态

| 形态 | 做法 | 适合 |
|---|---|---|
| **裸二进制** | 直接分发文件 | CLI 工具、内部服务 |
| **容器镜像** | `FROM scratch` + 二进制 | 云原生部署 |
| **压缩包** | `tar.gz`/`zip` + 校验和 | 需要附带配置/文档 |

**`FROM scratch` 的容器镜像**：

```dockerfile
FROM golang:1.27 AS build
WORKDIR /src
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -trimpath -ldflags="-s -w" -o /app ./cmd/server

FROM scratch
COPY --from=build /app /app
COPY --from=build /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/
ENTRYPOINT ["/app"]
```

**注意 `ca-certificates.crt` 那一行**——`scratch` 镜像里**没有根证书**，HTTPS 客户端会失败。这是最常见的"本地能跑、容器里跑不了"问题之一。

**约束**：`scratch` 里也**没有时区数据库**——`time.LoadLocation` 会失败（[02-标准库/03](../02-标准库/03-日期与时间.md)）。解法是 `import _ "time/tzdata"`（约 +450 KB）。

**判据**：**容器镜像的价值在于体积**——一个 `scratch` 镜像可能只有 3 MB（二进制 2.5 MB + 证书 0.5 MB），而 `alpine` 基础镜像就有 5 MB、`debian-slim` 有 30 MB。**用 `scratch` 的代价是要显式处理证书、时区、`/tmp`、非 root 用户这些基础镜像本来自带的东西**。

### 发布流程的检查项

| 检查 | 命令 |
|---|---|
| 版本号正确 | `./app --version` |
| 无未提交改动 | `go version -m app \| grep vcs.modified` 应为空 |
| 可复现 | 两次构建产物哈希相同（需 `-trimpath`） |
| 漏洞扫描 | `govulncheck ./...`（[03-代码质量工具](./03-代码质量工具.md)） |
| 校验和 | `sha256sum app` 随产物一起发布 |

**约束**：**`vcs.modified` 是发布前的必查项**。它出现在 CI 构建的产物里，说明 CI 对源码做了修改（比如 `go mod tidy` 改了 `go.mod`）——那个产物不对应任何 commit。

**下游**：产物是 [07-测试与质量](../07-测试与质量/) 的测试对象；发布流程里跑的检查工具见 [03-代码质量工具](./03-代码质量工具.md)。

**与其它语言对照**：

| | 交叉编译 | 产物 | 部署依赖 |
|---|---|---|---|
| Java | 不需要（字节码跨平台） | `.jar` | **JRE** |
| Python | 不需要（源码跨平台） | `.py` | **解释器 + 依赖** |
| Node.js | 不需要（源码跨平台） | `.js` | **Node + node_modules** |
| C++ | **需要目标平台工具链** | 二进制 | 动态库 |
| **Go** | **两个环境变量** | **静态二进制** | **无** |

**Java 与 Go 是两种相反的解法**：Java 让**代码跨平台**（一次编译到处运行，靠 JVM 适配），Go 让**编译跨平台**（一个命令产出各平台原生代码）。**Java 的代价是运行时重、启动慢、内存占用高；Go 的代价是要为每个平台单独构建**。

**Go 选择了后者**，因为云原生的部署单元是容器——**构建一次产物的成本远低于每个容器都带一个 JVM**。这是"编译速度快"这条设计目标（[00-概览/01](../00-概览/01-Go全景.md)）在发布层面的回报：为 6 个平台各构建一次，总耗时仍然很短。
