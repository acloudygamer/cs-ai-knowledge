# 单元测试

## 定义

单元测试是通过隔离验证每个代码单元正确性的机制。Go 的 `testing` 包是标准库内置的测试框架，其核心约定是：以 `_test.go` 结尾的文件中，以 `Test` 开头的函数由 `go test` 自动发现并执行，失败时通过 `*testing.T` 报告。**单元测试的本质是验证 SUT（System Under Test）在给定输入下的输出是否符合预期**，其隔离性由 Mock 对象而非语言机制保证。

## 数学模型

### 表驱动测试的覆盖率

```
表驱动测试的代码结构：
  cases = [
      {name: "case₁", input: a, expected: b},
      {name: "case₂", input: c, expected: d},
      ...
  ]

对每个 case 执行测试：
  for _, tc := range cases {
      // 每个 case 是独立执行路径
  }

覆盖率形式化定义：
  设程序点集合 P = {p₁, p₂, ..., pₙ}
  执行路径 E = {e₁, e₂, ..., eₘ}
  coverage = |⋃ᵢ {p ∈ P | eᵢ 经过 p}| / |P|

若 cases 覆盖了所有分支，则测试覆盖率 = 100%
```

**表驱动测试的复杂度上界**：设 `|cases| = k`，时间复杂度为 `O(k × T)`，其中 `T` 是单个测试用例的执行时间。空间复杂度为 `O(k)` 用于存储测试用例。

### Mock 的接口隔离模型

```
依赖关系的形式化描述：
  SUT（被测系统） → Interface I → RealImpl / MockImpl

Mock 的数学定义：
  Mock: I → Σ*
  其中 Σ* 表示 Mock 可能产生的所有输出序列

Mock 注入的约束条件：
  1. Mock 必须实现与 RealImpl 相同的接口（结构型协变）
  2. Mock 的行为由测试控制，不应有副作用
  3. Mock 应验证调用参数（进入检查）和返回值（退出检查）

Mock 的验证能力：
  进入验证：given(mock.SomeMethod).With(params).WillReturn(value)
  调用次数验证：given(mock.SomeMethod).With(params).Times(n)
```

**Mock 的组合爆炸问题**：设 SUT 有 `n` 个依赖接口，每个接口有 `k` 种 Mock 行为，则可能的 Mock 组合数为 `kⁿ`。实践中通过选择关键路径测试而非全组合测试。

### go test 的测试函数执行语义

```
go test 内部执行模型：

TestXxx(t *testing.T) 的执行语义：

  1. 创建 *testing.T
  2. 执行测试函数体
  3. 若 t.Fail() 被调用 → 标记为 FAILED
  4. 若 t.Fatal() 被调用 → 立即终止并标记为 FAILED
  5. defer 执行（用于 cleanup）
  6. 返回测试结果

子测试 t.Run 的执行语义：
  创建子 *testing.T
  在独立 goroutine 中执行（由 go test 调度）
  父测试等待所有子测试完成

并行约束：
  t.Parallel() 标记后，该测试进入并行池
  go test -p=N 限制同时运行的包数
  每个包内的并行度由测试内部 t.Parallel() 调用数决定
```

## 数据流

### go test 的执行流

<pre>
*_test.go 文件
    │
    ├── TestMain 初始化（可选）
    │       │
    │       ├── 创建测试环境
    │       ├── 调用 m.Run()
    │       └── 清理
    │
    ├── 逐包发现测试函数
    │       │
    │       └── TestXxx(t *testing.T) 函数
    │
    ├── 按包并行执行（-p=1）
    │       │
    │       ├── -run 过滤
    │       │
    │       └── t.Run(name, func(t *testing.T))
    │               │
    │               ├── 创建子测试
    │               ├── 执行测试函数
    │               ├── 捕获 panic
    │               └── 报告结果
    │
    └── 汇总结果
</pre>

### 表驱动测试的执行模型

<pre>
测试用例表：
  cases = []struct{
      name     string
      a, b     int
      expected int
  }{
      {"正数", 2, 3, 5},
      {"负数", -1, -1, -2},
      {"零", 0, 5, 5},
  }

执行：
  for _, tc := range cases {
      t.Run(tc.name, func(t *testing.T) {
          got := Add(tc.a, tc.b)
          if got != tc.expected {
              t.Errorf("Add(%d, %d) = %d; want %d",
                  tc.a, tc.b, got, tc.expected)
          }
      })
  }

子测试执行顺序不确定（并行），但每个子测试内部顺序确定
</pre>

### Mock 注入的数据流

<pre>
生产代码：
  func NewService(store Store) *Service {
      return &Service{store: store}
  }

  func (s *Service) DoSomething() error {
      data, err := s.store.Get("key")  // 调用接口
      if err != nil {
          return err
      }
      return process(data)
  }

测试代码（注入 Mock）：
  mockStore := &MockStore{
      GetFunc: func(key string) ([]byte, error) {
          return []byte("test"), nil  // 固定返回值
      },
  }

  svc := NewService(mockStore)  // Mock 注入

  // 验证调用
  // mockStore.Calls[0].Method == "Get"
  // mockStore.Calls[0].Args[0] == "key"
</pre>

## 机制

### 为什么表驱动测试是 Go 的惯用模式？

```
表驱动测试的优势来源于其数学结构：

设测试逻辑为函数 L(input) → expected
传统方式：L 散落在 if 语句中
表驱动方式：L 集中，cases 是 L 的参数化

数学上：
  传统方式：L 与具体值耦合，扩展需修改 L 本体
  表驱动方式：L 与具体值解耦，扩展只需添加 case

合并同类型测试的必要性：
  - 测试用例数 = f(输入边界数)
  - 边界：正常值、边界值、异常值
  - 表驱动使边界枚举完整且不重复

失败定位的复杂度：
  传统方式：O(n) 线性搜索（需知道第几个 if 失败）
  表驱动方式：O(1) 直接定位（通过 tc.name）
```

### TestMain 的作用

```
TestMain 用于包级别的 setup/teardown：

典型使用：
  func TestMain(m *testing.M) {
      // setup
      db := setupTestDB()
      flag.Parse()
      exitCode := m.Run()

      // teardown
      db.Close()

      os.Exit(exitCode)
  }

关键点：
  - m.Run() 执行所有 Test 函数
  - 返回值是测试结果码（0=成功，非0=失败）
  - teardown 在所有测试后执行（无论成功或失败）
```

**为什么需要 os.Exit**：测试框架本身是 `main` 函数，`m.Run()` 返回后需要显式调用 `os.Exit` 将测试结果码传递给 go test。

### 子测试的并行控制

```
子测试并行化的数学约束：

设父测试创建 n 个子测试，每个子测试标记为 t.Parallel()
并行执行数 = min(n, GOMAXPROCS)

时间约束：
  T_parallel = max(T₁, T₂, ..., Tₙ)  // 理想情况
  T_actual = T_parallel + T_overhead  // 包含调度开销

死锁风险：
  若子测试之间有隐式依赖（共享状态），
  并行执行可能暴露串行执行未发现的问题
```

### 测试隔离的约束

```
单元测试的隔离性由以下约束保证：

1. 无共享可变状态
   - 测试之间不共享全局变量
   - 使用局部变量或显式传递

2. Mock 替代真实依赖
   - 网络调用 → Mock HTTP server
   - 数据库调用 → Mock store
   - 文件系统 → Mock fs

3. 确定性执行
   - 无时间依赖（sleep、timeout）
   - 无随机输入（使用固定 seed）

违反约束的后果：
   - 测试顺序影响结果（ flaky test）
   - 测试间隐式依赖（难以单独运行）
   - 难以复现 bug（时序相关）
```

## 参考存根

```go
// 表驱动测试
func TestAdd(t *testing.T) {
    cases := []struct {
        name     string
        a, b     int
        expected int
    }{
        {"正数", 2, 3, 5},
        {"负数", -1, -1, -2},
        {"零", 0, 5, 5},
    }

    for _, tc := range cases {
        t.Run(tc.name, func(t *testing.T) {
            got := Add(tc.a, tc.b)
            if got != tc.expected {
                t.Errorf("Add(%d, %d) = %d; want %d",
                    tc.a, tc.b, got, tc.expected)
            }
        })
    }
}

// Mock 实现
type Store interface {
    Get(id string) (string, error)
}

type MockStore map[string]string

func (m MockStore) Get(id string) (string, error) {
    return m[id], nil
}

// TestMain
func TestMain(m *testing.M) {
    // setup
    flag.Parse()
    exitCode := m.Run()
    // teardown
    os.Exit(exitCode)
}
```

## 覆盖率

```
覆盖率衡量被执行到的代码比例：
  go test -coverprofile=coverage.out
  go tool cover -func=coverage.out

注意：
  高覆盖率 ≠ 高质量测试
  测试应优先覆盖：
    - 关键路径和边界条件
    - 错误处理路径
    - 并发安全
```

**覆盖率的形式化局限**：语句覆盖率 `cov = |{stmt | executed}| / |{stmt}|` 不考虑分支条件。例如 `if cond { A } else { B }` 中，只执行 A 也能达到 100% 语句覆盖，但不测试 B 的正确性。分支覆盖率可以补充这一缺陷。

## 验证标准

- 每个测试函数无状态、无副作用
- 测试间互不依赖，可任意顺序执行
- 失败信息包含实际值和期望值
