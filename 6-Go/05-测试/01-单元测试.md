# 单元测试

## 定义

单元测试是通过隔离验证每个代码单元正确性的机制。Go 的 `testing` 包是标准库内置的测试框架，其核心约定是：以 `_test.go` 结尾的文件中，以 `Test` 开头的函数由 `go test` 自动发现并执行，失败时通过 `*testing.T` 报告。**单元测试的本质是验证 SUT（System Under Test）在给定输入下的输出是否符合预期**，其隔离性由 Mock 对象而非语言机制保证。

## 数学模型

### 表驱动测试的覆盖率

**表驱动测试的结构化描述**：

设测试用例集合 $C = \{c_1, c_2, \ldots, c_k\}$，每个用例 $c_i$ 包含：
- $\text{name}_i$：用例名称
- $\text{input}_i$：输入参数
- $\text{expected}_i$：期望输出

测试执行模型：

$$
\forall c_i \in C : \text{Test}(c_i.\text{input}) \stackrel{?}{=} c_i.\text{expected}
$$

**覆盖率形式化定义**：

设程序点集合 $P = \{p_1, p_2, \ldots, p_n\}$，执行路径集合 $E = \{e_1, e_2, \ldots, e_m\}$：

$$
\text{coverage} = \frac{|\bigcup_{i=1}^{m} \{p \in P \mid e_i \text{ 经过 } p\}|}{|P|}
$$

若 cases 覆盖了所有分支，则测试覆盖率 $= 100\%$。

**表驱动测试的复杂度上界**：

$$
T_{\text{table-driven}} = O\left(\sum_{i=1}^{k} T(c_i)\right) = O(k \times T_{\text{avg}})
$$

空间复杂度为 $O(k)$ 用于存储测试用例。

### Mock 的接口隔离模型

**依赖关系的形式化描述**：

$$
\text{SUT} \xrightarrow{\text{depends on}} I \xrightarrow{\text{implemented by}} \text{RealImpl} / \text{MockImpl}
$$

**Mock 的数学定义**：

$$
\text{Mock} : I \rightarrow \Sigma^*
$$

其中 $\Sigma^*$ 表示 Mock 可能产生的所有输出序列。

**Mock 的验证能力**：

| 验证类型 | 描述 | 形式化 |
|----------|------|--------|
| 进入验证 | 验证调用参数 | $\text{AssertArgs}(\text{mock.SomeMethod}, p_1, p_2, \ldots)$ |
| 退出验证 | 验证返回值 | $\text{AssertReturn}(\text{mock.SomeMethod}, r_1, r_2, \ldots)$ |
| 调用次数 | 验证调用频率 | $\text{AssertTimes}(\text{mock.SomeMethod}, n)$ |

**Mock 的组合爆炸问题**：设 SUT 有 $n$ 个依赖接口，每个接口有 $k$ 种 Mock 行为，则可能的 Mock 组合数为 $k^n$。实践中通过选择关键路径测试而非全组合测试。

### go test 的测试函数执行语义

**TestXxx(t *testing.T) 的执行语义机**：

```
创建 *testing.T
    │
    ├── 执行测试函数体
    │
    ├── 若 t.Fail() 被调用 → 标记为 FAILED（继续执行）
    │
    ├── 若 t.Fatal() 被调用 → 立即终止并标记为 FAILED
    │
    ├── defer 执行（用于 cleanup）
    │
    └── 返回测试结果
```

**子测试 t.Run 的执行语义**：

```
t.Run(name, func(t *testing.T))
    │
    ├── 创建子 *testing.T
    │
    ├── 在独立 goroutine 中执行（由 go test 调度）
    │
    ├── 父测试等待所有子测试完成
    │
    └── 汇总子测试结果到父测试
```

**并行约束的数学表示**：

设父测试创建 $n$ 个子测试，每个子测试标记为 `t.Parallel()`：

$$
\text{并行执行数} = \min(n, \text{GOMAXPROCS})
$$

理想时间：

$$
T_{\text{parallel}} = \max(T_1, T_2, \ldots, T_n)
$$

实际时间（含调度开销）：

$$
T_{\text{actual}} = T_{\text{parallel}} + T_{\text{overhead}}
$$

### 测试隔离的约束条件

**隔离性的三大约束**：

1. **无共享可变状态**：测试之间不共享全局变量，使用局部变量或显式传递
2. **确定性执行**：无时间依赖（sleep、timeout），无随机输入（使用固定 seed）
3. **资源释放**：每个测试执行完毕后释放所有申请的资源

**违反约束的后果**：

| 违反类型 | 后果 |
|----------|------|
| 测试间共享状态 | Flaky test，顺序影响结果 |
| 时间依赖 | CI 环境与本地环境结果不一致 |
| 资源未释放 | 内存泄漏，连接池耗尽 |

## 机制

### 为什么表驱动测试是 Go 的惯用模式？

**表驱动测试的数学优势**：

设测试逻辑为函数 $L(\text{input}) \rightarrow \text{expected}$：

| 模式 | $L$ 与具体值的关系 | 扩展方式 |
|------|---------------------|----------|
| 传统方式 | $L$ 散落在 if 语句中 | 修改 $L$ 本体 |
| 表驱动方式 | $L$ 集中，cases 是 $L$ 的参数化 | 添加 case |

**数学上**：
- 传统方式：$L$ 与具体值耦合，扩展需修改 $L$ 本体
- 表驱动方式：$L$ 与具体值解耦，扩展只需添加 case

**失败定位的复杂度**：
- 传统方式：$O(n)$ 线性搜索（需知道第几个 if 失败）
- 表驱动方式：$O(1)$ 直接定位（通过 tc.name）

### TestMain 的作用

**TestMain 用于包级别的 setup/teardown**：

```go
func TestMain(m *testing.M) {
    // setup
    db := setupTestDB()
    flag.Parse()
    exitCode := m.Run()

    // teardown
    db.Close()

    os.Exit(exitCode)
}
```

**关键点**：
- `m.Run()` 执行所有 Test 函数
- 返回值是测试结果码（0=成功，非0=失败）
- teardown 在所有测试后执行（无论成功或失败）
- `os.Exit` 是必须的，因为测试框架本身是 `main` 函数

**为什么需要 os.Exit**：测试框架本身是 `main` 函数，`m.Run()` 返回后需要显式调用 `os.Exit` 将测试结果码传递给 go test。

### 子测试的并行控制

**并行化的约束条件**：

```
子测试并行化的数学约束：

设父测试创建 n 个子测试，每个子测试标记为 t.Parallel()
并行执行数 = min(n, GOMAXPROCS)

时间约束：
  T_parallel = max(T₁, T₂, ..., Tₙ)  // 理想情况
  T_actual = T_parallel + T_overhead  // 包含调度开销

死锁风险：
  若子测试之间有隐式依赖（共享状态），
  并行执行可能暴露串行执行未发现的问题
```

### 测试隔离的约束

**单元测试的隔离性由以下约束保证**：

1. **无共享可变状态**
   - 测试之间不共享全局变量
   - 使用局部变量或显式传递

2. **Mock 替代真实依赖**
   - 网络调用 → Mock HTTP server
   - 数据库调用 → Mock store
   - 文件系统 → Mock fs

3. **确定性执行**
   - 无时间依赖（sleep、timeout）
   - 无随机输入（使用固定 seed）

**违反约束的后果**：
- 测试顺序影响结果（flaky test）
- 测试间隐式依赖（难以单独运行）
- 难以复现 bug（时序相关）

### 覆盖率的局限性

**覆盖率的形式化局限**：

语句覆盖率：

$$
\text{cov}_{\text{stmt}} = \frac{|\{\text{stmt} \mid \text{executed}\}|}{D:\cs-ai-knowledge\{\text{stmt}\}}
$$

**缺陷**：不考虑分支条件。例如 `if cond { A } else { B }` 中，只执行 A 也能达到 100% 语句覆盖，但不测试 B 的正确性。

**分支覆盖率**可以补充这一缺陷：

$$
\text{cov}_{\text{branch}} = \frac{|\{b \in B \mid \text{both exits reached}\}|}{D:\cs-ai-knowledge\{B\}}
$$

**高覆盖率 ≠ 高质量测试**：测试应优先覆盖：
- 关键路径和边界条件
- 错误处理路径
- 并发安全

## 验证标准

- 每个测试函数无状态、无副作用
- 测试间互不依赖，可任意顺序执行
- 失败信息包含实际值和期望值

## 版本基准

Go 1.24（stable）。本专题涉及的所有测试框架行为均基于该版本。

```go
// 表驱动测试
func TestAdd(t *testing.T) {
    cases := []struct {
        name     string
        a, b     int
        expected int
    }{
        {"正数", 2, 3, 5},
        {"负数", -1, -1, -2},
        {"零", 0, 5, 5},
    }

    for _, tc := range cases {
        t.Run(tc.name, func(t *testing.T) {
            got := Add(tc.a, tc.b)
            if got != tc.expected {
                t.Errorf("Add(%d, %d) = %d; want %d",
                    tc.a, tc.b, got, tc.expected)
            }
        })
    }
}

// Mock 实现
type Store interface {
    Get(id string) (string, error)
}

type MockStore map[string]string

func (m MockStore) Get(id string) (string, error) {
    return m[id], nil
}

// TestMain
func TestMain(m *testing.M) {
    // setup
    flag.Parse()
    exitCode := m.Run()
    // teardown
    os.Exit(exitCode)
}
```
