# 单元测试

## 定义

单元测试是通过隔离验证每个代码单元正确性的机制。Go 的 `testing` 包是标准库内置的测试框架，其核心约定是：以 `_test.go` 结尾的文件中，以 `Test` 开头的函数由 `go test` 自动发现并执行，失败时通过 `*testing.T` 报告。

## 数学模型

### 表驱动测试的覆盖率

```
表驱动测试的代码结构：
  cases = [
      {name: "case1", input: a, expected: b},
      {name: "case2", input: c, expected: d},
      ...
  ]

对每个 case 执行测试：
  for _, tc := range cases {
      // 每个 case 是一次独立执行
  }

若 cases 覆盖了所有分支，则测试覆盖率 = 100%（对于该测试函数）
```

### Mock 的接口隔离模型

```
依赖关系：
  SUT（被测系统）→ Interface I → RealImpl / MockImpl

Mock 的作用：
  - 隔离 SUT 的外部依赖
  - 提供可控的测试环境
  - 允许验证调用参数和次数

Mock 注入方式：
  func NewService(impl Interface) *Service {
      return &Service{impl: impl}
  }

  // 测试时注入 Mock
  svc := NewService(&MockStore{})

  // 生产时注入 Real
  svc := NewService(&RealStore{})
```

## 数据流

### go test 的执行流

<pre>
*_test.go 文件
    │
    ├── TestMain 初始化（可选）
    │       │
    │       ├── 创建测试环境
    │       ├── 调用 m.Run()
    │       └── 清理
    │
    ├── 逐包发现测试函数
    │       │
    │       └── TestXxx(t *testing.T) 函数
    │
    ├── 按包并行执行（-p=1）
    │       │
    │       ├── -run 过滤
    │       │
    │       └── t.Run(name, func(t *testing.T))
    │               │
    │               ├── 创建子测试
    │               ├── 执行测试函数
    │               ├── 捕获 panic
    │               └── 报告结果
    │
    └── 汇总结果
</pre>

### 表驱动测试的执行模型

<pre>
测试用例表：
  cases = []struct{
      name     string
      a, b     int
      expected int
  }{
      {"正数", 2, 3, 5},
      {"负数", -1, -1, -2},
      {"零", 0, 5, 5},
  }

执行：
  for _, tc := range cases {
      t.Run(tc.name, func(t *testing.T) {
          got := Add(tc.a, tc.b)
          if got != tc.expected {
              t.Errorf("Add(%d, %d) = %d; want %d",
                  tc.a, tc.b, got, tc.expected)
          }
      })
  }

子测试执行顺序不确定（并行），但每个子测试内部顺序确定
</pre>

## 机制

### 为什么表驱动测试是 Go 的惯用模式？

```
传统方式：
  func TestAdd(t *testing.T) {
      if got := Add(2, 3); got != 5 {
          t.Error()
      }
      if got := Add(-1, -1); got != -2 {
          t.Error()
      }
      ...
  }

问题：
  1. 每个断言独占一个 if，代码重复
  2. 难以快速定位哪个 case 失败
  3. 添加新 case 需要复制粘贴

表驱动方式：
  - 测试用例与测试逻辑分离
  - 失败时通过 tc.name 快速定位
  - 添加新 case 只需在表中添加一行
```

### TestMain 的作用

```
TestMain 用于包级别的 setup/teardown：

典型使用：
  func TestMain(m *testing.M) {
      // setup
      db := setupTestDB()
      flag.Parse()
      exitCode := m.Run()

      // teardown
      db.Close()

      os.Exit(exitCode)
  }

关键点：
  - m.Run() 执行所有 Test 函数
  - 返回值是测试结果码
  - teardown 在所有测试后执行
```

### 子测试的并行控制

```
子测试可以通过 t.Parallel() 标记为可并行：
  func TestXxx(t *testing.T) {
      t.Run("sub1", func(t *testing.T) {
          t.Parallel()  // sub1 和其他 parallel 子测试并行
          ...
      })
      t.Run("sub2", func(t *testing.T) {
          t.Parallel()
          ...
      })
  }

并行执行的前提：
  - 父测试已经启动子测试
  - 子测试内部调用 t.Parallel()
```

## 参考存根

```go
// 表驱动测试
func TestAdd(t *testing.T) {
    cases := []struct {
        name     string
        a, b     int
        expected int
    }{
        {"正数", 2, 3, 5},
        {"负数", -1, -1, -2},
        {"零", 0, 5, 5},
    }

    for _, tc := range cases {
        t.Run(tc.name, func(t *testing.T) {
            got := Add(tc.a, tc.b)
            if got != tc.expected {
                t.Errorf("Add(%d, %d) = %d; want %d",
                    tc.a, tc.b, got, tc.expected)
            }
        })
    }
}

// Mock 实现
type Store interface {
    Get(id string) (string, error)
}

type MockStore map[string]string

func (m MockStore) Get(id string) (string, error) {
    return m[id], nil
}

// TestMain
func TestMain(m *testing.M) {
    // setup
    flag.Parse()
    exitCode := m.Run()
    // teardown
    os.Exit(exitCode)
}
```

## 覆盖率

```
覆盖率衡量被执行到的代码比例：
  go test -coverprofile=coverage.out
  go tool cover -func=coverage.out

注意：
  高覆盖率 ≠ 高质量测试
  测试应优先覆盖：
    - 关键路径和边界条件
    - 错误处理路径
    - 并发安全
```

## 验证标准

- 每个测试函数无状态、无副作用
- 测试间互不依赖，可任意顺序执行
- 失败信息包含实际值和期望值
