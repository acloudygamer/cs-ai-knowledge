# 日期与时间

> 前置：[02-io与bufio](./02-io与bufio.md) · 后续：[04-正则表达式](./04-正则表达式.md)

> **版本基准**：Go 1.27（stable = latest）。本篇示例实测环境：go1.27.1 windows/amd64。

## 本质

`time.Time` 是一个**值类型**，内部存两样东西：**墙上时钟读数**（wall clock，日历时间）与**单调时钟读数**（monotonic clock，进程启动以来的经过时间）。

```console
$ go run .
Now()          : 2026-09-27 17:29:10.7805642 +0800 CST m=+0.000000001
Round(0) 剥离后: 2026-09-27 17:29:10.7805642 +0800 CST
```

第一行末尾的 **`m=+0.000000001`** 就是单调读数——`m=` 后面的值是"进程启动至今的秒数"。第二行是 `Round(0)` 之后的结果，`m=` 消失了。

**约束的由来**：这两个读数解决的是不同的问题，缺一不可。

- **墙上时钟**回答"现在几点"，但它会被 NTP 校正、被用户改、闰秒时跳变。用它算时间间隔，**可能算出负数**。
- **单调时钟**回答"过了多久"，它只增不减。用它算间隔，结果永远正确。

`time.Time` 同时带两者，`Sub`/`Since` 会**优先用单调读数**——所以 `t2.Sub(t1)` 永远是正数（只要 t2 在 t1 之后），哪怕期间系统时间被改过。

**边界**：单调读数**不参与序列化**。`time.Now()` 经过 `MarshalJSON` 往返后，`m=` 部分丢失（[05-序列化与编码](./05-序列化与编码.md)）。所以**不要序列化 `time.Time` 再用它算间隔**——用 `Unix()` 时间戳。

## 机制

### 布局字符串：Go 独有的格式化方式

**Go 不用 `%Y-%m-%d` 这样的格式符，而是用一个参考时间的字面写法**：

```
2006-01-02 15:04:05
```

这串数字是 **`Mon Jan 2 15:04:05 MST 2006`** 的数字形式——即 Unix 时间 1136239445，Go 团队选它是因为好记（1 2 3 4 5 6 对应月日时分的递增）。你写什么布局，就按那个布局输出：

```console
$ go run .
默认布局       : 2026-09-27 17:29:10
RFC3339        : 2026-09-27T17:29:10+08:00
自定义 2006/01/02 15:04:05: 2026/09/27 17:29:10
中文            : 2026年09月27日 17:29:10
12 小时制       : 3:04 PM
星期            : Sunday
时区缩写        : CST
数字时区        : -0700
```

`time` 包预定义了常用布局常量，优先用它们而不是自己写：

| 常量 | 布局 |
|---|---|
| `time.DateOnly` | `2006-01-02` |
| `time.TimeOnly` | `15:04:05` |
| `time.DateTime` | `2006-01-02 15:04:05` |
| `time.RFC3339` | `2006-01-02T15:04:05Z07:00` |
| `time.RFC1123` | HTTP 头里的日期格式 |

**易错点**：`15` 是 24 小时制、`03` 是 12 小时制（补零）；`01` 是补零的月，`1` 是不补零的月；`02` 是补零的日，`2` 是不补零的日。写错一位就静默给出错误结果，**不报错**。

**约束**：布局串里的普通字符按字面输出，所以 `"2006年01月02日"` 里的"年月日"原样保留。但这意味着**布局串里不能有歧义字符**——`"2006-1-2"` 里的 `-` 是字面量，`1` 与 `2` 是字段。

### 解析与错误

```console
$ go run .
Parse          : 2026-09-27 00:00:00 +0000 UTC <nil>
Parse 失败     : parsing time "27/09/2026" as "2006-01-02": cannot parse "27/09/2026" as "2006"
```

`time.Parse` 的布局必须与输入**逐字段对应**。失败时的报错会指出在哪个字段上对不上——上面说"在 `2006` 这个字段处无法解析 `27/09/2026`"。

**注意解析结果的时区是 `UTC`**，因为没有时区信息时 `Parse` 默认 UTC。带时区用 `time.ParseInLocation(layout, value, loc)`。

### `Duration` 与运算

```console
$ go run .
Duration       : 1h30m30s  秒数: 5430  类型: time.Duration
Duration 解析  : 1h30m0s
Add(-24h)      : 2026-09-26
Sub            : 1h0m0s
Truncate(1h)   : 17:00:00
比较 Before    : true
```

`time.Duration` 的底层类型是 **`int64`，单位纳秒**——它不是一个结构体。所以 `time.Second` 是常量 `1000000000`，`d.Seconds()` 是除法。

**约束**：`time.Duration` 的可表示范围受 `int64` 限制，约 **±292 年**。超大间隔会溢出，不会报错。

常用运算：

| 操作 | 方法 |
|---|---|
| 加减 | `Add(d)` / `Sub(t)` |
| 截断到粒度 | `Truncate(d)`（向下取整）/ `Round(d)`（四舍五入） |
| 比较 | `Before` / `After` / `Equal`（**不要用 `==`**，时区不同会不等） |
| 取字段 | `Year()` / `Month()` / `Day()` / `Hour()` / `Weekday()` |

**`==` 比较 `time.Time` 是陷阱**：两个表示同一时刻但时区不同的 `Time` 用 `==` 是 `false`，用 `Equal` 是 `true`。上面 `now.Equal(now)` 输出 `true`，因为同一个值。

### 时区

```console
$ go run .
纽约时间       : 2026-09-27 05:29:10
```

`time.LoadLocation("America/New_York")` 从**系统时区数据库**读取。Windows 上系统没有 IANA 数据库，Go 会退回内置的 `time/tzdata`——**但前提是你导入了它**：

```go
import _ "time/tzdata"   // 把时区库编译进二进制，约 +450KB
```

**约束**：面向容器部署时**必须显式导入 `time/tzdata`**——精简基础镜像（`scratch`、`alpine`）里没有时区文件，`LoadLocation` 会返回错误。这是"静态单二进制"（[00-概览/01](../00-概览/01-Go全景.md)）要付的一笔账。

### 时间戳

```console
$ go run .
Unix()         : 1790501350
UnixMilli()    : 1790501350780
UnixNano()     : 1790501350780564200
零值           : 0001-01-01 00:00:00 +0000 UTC  IsZero: true  Unix: -62135596800
```

`Unix()` 返回秒、`UnixMilli()` 毫秒、`UnixNano()` 纳秒。**`UnixNano()` 在 2262 年会溢出**（`int64` 纳秒的上限约是 2262-04-11），所以长期存储用秒或毫秒。

**零值是 `0001-01-01T00:00:00Z`**，`IsZero()` 是判断"未设置"的标准手段——它的 `Unix()` 是 `-62135596800`，不是 0。**不要用 `t.Unix() == 0` 判空**。

### `Ticker`、`Timer` 与 Go 1.23 的 GC 语义变更

```console
$ go run .
Ticker 触发 3 次
time.After 等待: 30ms
```

| 类型 | 语义 | 释放 |
|---|---|---|
| `time.After(d)` | 返回一个 channel，d 后收到一个值 | **无法停止**，到点前一直占着 |
| `time.NewTimer(d)` | 可 `Stop()` 的定时器 | `Stop()` |
| `time.NewTicker(d)` | 周期性触发 | `Stop()` |

**`time.After` 在循环里是内存泄漏**——每次调用都创建一个新 Timer，且在到点前不能被回收（`select` 里用它做超时时，如果其他分支先返回，这个 Timer 会一直挂着）。

```go
for {
	select {
	case <-time.After(time.Second):   // ❌ 每次循环都新建，旧的不会立刻释放
	}
}
```

正确写法是循环外建一个 `NewTicker` 并 `defer tk.Stop()`。

**Go 1.23 起语义有变**：`Timer`/`Ticker` 如果**不再被引用**（不可达），GC 可以回收它们，即使没调用 `Stop()`。这修掉了长期存在的一类泄漏，但**不改变"显式 Stop 更好"的建议**——GC 何时运行不确定，`time.After` 在热循环里仍然会堆积。

**与其它语言对照**：

| | 格式化 | 时区 | 单调时钟 |
|---|---|---|---|
| Java | `DateTimeFormatter.ofPattern("yyyy-MM-dd")` | `ZoneId` | `System.nanoTime()`（**独立的类型**） |
| Python | `strftime("%Y-%m-%d")` | `zoneinfo` | `time.monotonic()`（**独立的函数**） |
| **Go** | **参考时间布局 `2006-01-02`** | `*time.Location` | **藏在 `Time` 内部** |

Go 的"参考时间"写法在所有语言里是独一份——`strftime` 与 `DateTimeFormatter` 都用模式字符。**它的好处是布局串本身就是合法输出样例**（`now.Format("2006-01-02")` 一眼能看出结果长什么样），坏处是**没有任何检查**：把 `2006` 写成 `2007` 不会报错，只会输出 `2007`。

Java 与 Python 的单调时钟是**独立 API**，必须显式选用；Go 把它**内建进 `Time`**，`Sub`/`Since` 自动用。Go 的做法更不容易误用，代价是 `Time` 变成 24 字节（两个 8 字节读数 + 时区指针 + 标志位），比纯墙上时钟大一倍。
