# 字符串与字节

> 前置：[01-语言核心](../01-语言核心/) · 后续：[02-io与bufio](./02-io与bufio.md)

> **版本基准**：Go 1.27（stable = latest）。本篇示例实测环境：go1.27.1 windows/amd64，Intel i7-10750H（6 核 12 线程）。

## 本质

**Go 的 `string` 是不可变的字节序列，编码约定为 UTF-8。**

这两个定语都要紧：

- **不可变**：任何"修改"都返回新字符串，原字符串不变。
- **字节序列**：`string` 的长度是**字节数**，不是字符数。Go 没有"字符"这个内建概念——字符是 `rune`（`int32`，表示一个 Unicode 码点），是**另一层**的抽象。

```console
$ go run .
len=8 RuneCountInString=4 RuneCountInString(空)=0
子串 "Go" 与原文共享底层数组（零拷贝）
```

`"Go语言"` 的 `len` 是 8、`utf8.RuneCountInString` 是 4。**两个数都对，量的是不同的东西**——前者是存储占用，后者是可见字符数。

**约束**：不可变性是 `string` 能当 map 键、能被安全并发读、能零拷贝取子串的原因。代价是每次拼接都要分配（下面有实测）。

**边界**：Go 的 `string` **不保证**内容合法 UTF-8——可以从非法字节构造（`string([]byte{0xff})`），编译器不检查。`range` 遇到非法字节会产出 `U+FFFD` 替换符，不会 panic。**需要保证合法时自己用 `utf8.ValidString` 检查**。

## 机制

### 三种"字符串"的取舍

| 类型 | 是什么 | 何时用 |
|---|---|---|
| `string` | 不可变字节序列 | 传输、存储、键、常量 |
| `[]byte` | 可变字节切片 | 需要原地修改、二进制协议 |
| `[]rune` | 可变码点切片 | 需要按字符下标操作 |

```console
$ go run .
[]rune: [71 111 35821 35328] len= 4
[]byte: [71 111 232 175 173 232 168 128]
```

**转换都有代价**：`[]byte(s)` 与 `[]rune(s)` 都**拷贝**一份数据（`[]byte(s)` 在编译器能证明不逃逸且不修改时可优化掉，但不能依赖）。`[]rune` 还要解码 UTF-8，最贵。

**判据**：能留在 `string` 层就别转。要按字符取第 3 个字符，`[]rune(s)[2]` 是 $O(n)$ 且分配；反复取的话应转一次存下来。

### 内存侧的 Reader / Writer

`string` 与 `[]byte` 要被当作 `io.Reader`/`io.Writer` 用时，标准库提供了四个适配器（[02-io与bufio](./02-io与bufio.md) 的接口是它们的公共契约）：

| 类型 | 方向 | 底层数据 | 构造时是否拷贝 |
|---|---|---|---|
| `strings.Reader` | 只读 | `string` | **否** |
| `bytes.Reader` | 只读，可 `Seek` | `[]byte` | **否** |
| `bytes.Buffer` | **读写** | `[]byte`（自增长） | **否**（`NewBuffer` 接管切片；`NewBufferString` 要拷） |
| `strings.Builder` | **只写** | `[]byte` | 否；且 `String()` 也不拷 |

**实测**（同一份约 1.1 KB 的字符串，`io.Copy` 读空）：

```console
$ go test -bench=. -benchtime=20000x -count=3
BenchmarkStringsReader-12       	20000	  26.18 ns/op	  32 B/op	1 allocs/op
BenchmarkBytesReader-12         	20000	  23.99 ns/op	  48 B/op	1 allocs/op
BenchmarkBytesBufferString-12   	20000	 242.70 ns/op	1456 B/op	2 allocs/op
BenchmarkBytesBufferBytes-12    	20000	  22.00 ns/op	  48 B/op	1 allocs/op
```

**`bytes.NewBufferString` 是唯一拷贝的那个**——1456 字节（1.1 KB 载荷 + 缓冲区结构）、2 次分配、慢约 10 倍。另外三个都只分配一个几十字节的适配器结构。

**约束的由来**：**`strings.Reader` 能不拷贝，正是因为 `string` 不可变**——没有别的引用能改写这段内存，所以 Reader 可以直接指向它。`bytes.NewReader(b)` 同理：它不接管 `b` 的所有权，因此**调用方在 Reader 使用期间不能改写 `b`**，这是调用方的责任，编译期不检查。

**`strings.Builder.String()` 是零拷贝的**，源码只有一行：

```go
func (b *Builder) String() string {
	return unsafe.String(unsafe.SliceData(b.buf), len(b.buf))
}
```

**它用 `unsafe` 把 `[]byte` 直接重新解释成 `string`**——所以 `String()` 之后**不能再改 Builder**（改了会破坏 `string` 的不可变约定）。Builder 的 `copyCheck` 字段在 `String()` 后把 Builder 标记为不可再写，违反时 panic。

**判据**：

| 场景 | 用什么 |
|---|---|
| 只读一段已有的 `string` | `strings.NewReader` |
| 只读一段已有的 `[]byte`，需要 `Seek` | `bytes.NewReader` |
| 既要读又要写、或要当缓冲区 | `bytes.Buffer` |
| 只拼接、最后要 `string` | `strings.Builder`（[拼接：三种写法的实测差距](#拼接三种写法的实测差距)） |

**边界**：**`bytes.Buffer` 的 `Bytes()` 与 `String()` 都不拷贝**，返回的是内部切片——继续写 Buffer 会让之前取到的切片内容改变。要长期持有必须先 `Clone`。

### `strings` 包：不分配的操作

```console
$ go run .
ToUpper: ABC
Contains: true
Cut: k|v|true
CutLast: a/b|c|true
Fields: [a b c]
Repeat: ababab
TrimPrefix: x
```

大部分 `strings` 函数**不分配**——`Contains`、`Index`、`HasPrefix`、`TrimPrefix`（不需要裁剪时）都只是扫描或返回子串切片。判据是看它是否必须造新字符串：`ToUpper`、`Repeat`、`Replace` 会分配；`Contains`、`Index`、`Split` 的**每个子串仍共享原字符串的底层数组**。

`strings.Cut`（Go 1.18）与 `CutLast`（Go 1.27 新增）是"按分隔符切一刀"的专用工具，比 `SplitN` 更清晰：

```go
a, b, ok := strings.Cut("k=v", "=")    // "k", "v", true
```

**约束**：`Split` 返回的每个元素都指向原字符串的底层数组。如果原字符串很大而只留一个短子串，**整个大字符串会因这个子串被引用而无法回收**（[03-运行时与内存/03](../03-运行时与内存/03-垃圾回收.md)）。要断开引用得 `strings.Clone`。

### 拼接：三种写法的实测差距

```console
$ go test -bench=. -benchmem -run=^$
BenchmarkConcat-12     	   10000	    131992 ns/op	  530275 B/op	     999 allocs/op
BenchmarkBuilder-12    	  634272	      2191 ns/op	    3320 B/op	       9 allocs/op
BenchmarkBuffer-12     	  245006	      5212 ns/op	    3008 B/op	       6 allocs/op
```

拼 1000 个 `"x"`：

| 写法 | ns/op | 分配字节 | 分配次数 |
|---|---|---|---|
| `s += "x"` | **131,992** | 530,275 | **999** |
| `strings.Builder` | **2,191** | 3,320 | 9 |
| `bytes.Buffer` | 5,212 | 3,008 | 6 |

**`+=` 慢 60 倍**。原因是字符串不可变——每次 `+=` 都要**分配一块新内存并拷贝全部已有内容**，1000 次拼接累计拷贝约 50 万字节（等差数列求和）。

**`Builder` 比 `Buffer` 快一倍多**（2,191 vs 5,212），因为 `Builder` 的 `String()` 用 `unsafe` **直接把内部缓冲区转成字符串**，零拷贝；而 `Buffer.String()` 也做了这个优化、`Buffer.Bytes()` 才拷贝——差距主要来自 `Builder` 明确禁止拷贝内部状态带来的简化。

**约束**：`Builder` **不能被复制**（内部有 `noCopy` 哨兵），因此**必须用指针接收或按引用传**。同时 `Builder` 没有 `Reset` 之外的复用手段——`String()` 之后继续 `Write` 是合法的，但会分配新缓冲区。

**判据**：拼接次数在编译期可知且很少（`a + b + c`）时直接用 `+`，编译器会合并成一次分配；循环里拼或用时未知，一律 `strings.Builder`。

### `strconv`：数字与字符串

```console
$ go run .
Atoi: 42  Itoa: 42  ParseFloat: 3.14
Quote: "a\tb"
FormatInt 十六进制: ff
```

`strconv` 是数字 ↔ 字符串的唯一标准入口。几个要点：

- **`Atoi`/`Itoa` 是 `ParseInt`/`FormatInt` 的十进制特化**，语义相同但更快。
- `FormatInt(255, 16)` 给出 `ff`（小写、无前缀）；要 `0xff` 得自己拼。
- `Quote` 做 Go 字面量转义，调试打印字符串时比 `%q` 更可控。
- **`ParseXxx` 系列都返回 `(值, error)`**，不 panic（[01-语言核心/10](../01-语言核心/10-错误处理.md)）。

**不要用 `fmt.Sprintf("%d", n)` 转数字**——它走反射与接口，比 `strconv.Itoa` 慢一个数量级。`fmt` 是给人看的，`strconv` 是给机器用的。

### `unicode` 与 `unicode/utf8`

| 包 | 管什么 |
|---|---|
| `unicode` | **码点属性**：`IsLetter`、`IsDigit`、`ToUpper`、`IsSpace` |
| `unicode/utf8` | **编码层面**：`RuneCountInString`、`DecodeRune`、`ValidString`、`RuneLen` |

判据是**你手上是字节还是码点**：`strings.ToUpper` 处理字符串（可能改长度，如 `ß` → `SS`），`unicode.ToUpper` 处理单个 rune（长度不变）。需要逐字符判断属性时先 `range` 拿到 rune，再用 `unicode`。

**与其它语言对照**：

| | 字符串是什么 | 长度含义 | 可变性 |
|---|---|---|---|
| C | `char*` + `\0` | 字节数（`strlen` $O(n)$） | 可变 |
| Java | UTF-16 码元序列 | **码元数**（一个 emoji 算 2） | 不可变 |
| Python | Unicode 码点序列 | **字符数**（`len` 是码点数） | 不可变 |
| **Go** | **UTF-8 字节序列** | **字节数** | 不可变 |

四门语言里只有 Go 的 `len` 是字节数。Java 的 `length()` 是 UTF-16 码元数（`"😀".length() == 2`），Python 的 `len` 是码点数（`len("😀") == 1`）。**没有哪个是"正确"的**——它们量的是各自的存储单元。Go 的 `len` 是 $O(1)$（切片头里有长度），Python 的 `len` 也是 $O(1)$（字符串对象缓存长度），C 的 `strlen` 是 $O(n)$。
