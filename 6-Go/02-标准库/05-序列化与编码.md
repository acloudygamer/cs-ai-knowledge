# 序列化与编码

> 前置：[04-正则表达式](./04-正则表达式.md) · 后续：[03-运行时与内存](../03-运行时与内存/)

> **版本基准**：Go 1.27（stable = latest）。本篇示例实测环境：go1.27.1 windows/amd64，Intel i7-10750H（6 核 12 线程）。

## 本质

**序列化是"把内存里的结构映射成字节流"的过程，`encoding/json` 做的是其中最常用的一种映射：Go 值与 JSON 之间的对应。**

这条映射不是双向对称的，理解它的关键是把两个方向分开看：

| 方向 | 函数 | 信息来源 |
|---|---|---|
| Go → JSON | `json.Marshal` | **导出字段** + struct tag |
| JSON → Go | `json.Unmarshal` | 字段名匹配（tag 优先，其次大小写不敏感的名字匹配） |

**约束**：只有**导出字段**参与序列化（[01-语言核心/11](../01-语言核心/11-包与可见性.md)）。`json` 包用反射读写字段，而反射**不能设置不导出字段**（[03-运行时与内存/04](../03-运行时与内存/04-反射.md)），因此非导出字段被静默忽略——**不报错**。

**边界**：JSON 只有四种标量（字符串、数字、布尔、null）加两种容器（对象、数组）。Go 的类型远多于这个集合，映射必然有损：`int64` 大整数丢精度、`time.Time` 变成字符串、`map[非字符串键]` 无法表示、`chan`/`func` 直接报错。

## 机制

### 字段名与 tag

```console
$ go run .
Marshal: {"name":"张三","age":30,"nil_slice":null}
字段: map[age:30 name:张三 nil_slice:<nil>]
空切片: {"name":"张三","age":30,"nil_slice":[]}
```

三处细节：

**一、字段名默认用 Go 字段名**，`json:"name"` 覆盖它。**Go 社区惯例是全部小写**（`json:"user_name"` 或 `json:"userName"`），因为 JSON 消费方通常是 JavaScript/Python。

**二、`json:"-"` 完全排除字段**（上面的 `Secret`），非导出字段（`private`）自动排除。

**三、`omitempty` 决定零值是否省略**。注意它**对 nil 切片与空切片一视同仁**（都省略），而**没有 `omitempty` 时两者输出不同**：

| 值 | 无 `omitempty` | 有 `omitempty` |
|---|---|---|
| `nil` 切片 | `null` | 省略 |
| 空切片 `[]T{}` | `[]` | 省略 |
| `nil` map | `null` | 省略 |
| `0` / `""` / `false` | 原值 | **省略** |

**`omitempty` 对 `0` 也生效**——如果 `0` 是有意义的值（比如计数），用它会把数据丢掉。这是最常见的 JSON tag 陷阱。

**约束**：tag 的完整语法是 `json:"name,omitempty,string"`。`string` 选项让数字/布尔以**字符串形式**编码（`"age":"30"`），用于对接要求字符串的 API。

### 精度：`json.Number`

```console
$ go run .
json.Number 保精度: 12345678901234567890
float64 丢精度  : 12345678901234567168
```

JSON 的数字没有类型，Go 默认解析成 `float64`——**超过 $2^{53}$ 的整数会丢精度**（[01-语言核心/02](../01-语言核心/02-类型与变量.md) 讲的 IEEE 754 限制）。

`json.Number` 是 `string` 的别名，**保留原始文本**，需要时再自己转。解析到 `any` 时也会得到 `json.Number` 而不是 `float64`——但只有用 `Decoder.UseNumber()` 时才这样，`Unmarshal` 到 `any` 默认给 `float64`。

**判据**：涉及 ID、金额、雪花算法生成的整数，**必须用 `json.Number` 或 `int64` 字段**，不能用 `any`/`float64`。

### 流式处理：`Decoder` 与 `RawMessage`

```console
$ go run .
RawMessage: 30
1 2 3 
```

**`json.Decoder` 从 `io.Reader` 连续读多个 JSON 值**——`dec.More()` 判断还有没有下一个。这适合：

- **JSON Lines**（每行一个 JSON 对象）——日志、流式导出
- **HTTP 响应体**边读边解析，不必先 `io.ReadAll` 到内存
- **一个连接上连续收发多个消息**

**`json.RawMessage` 延迟解析**：它是一个 `[]byte`，`Unmarshal` 时**原样保留那段字节**。用途是"先看一个字段决定怎么解析其余部分"——典型场景是带 `type` 字段的多态消息：

```go
var env struct {
	Type string          `json:"type"`
	Data json.RawMessage `json:"data"`
}
json.Unmarshal(b, &env)
switch env.Type {
case "user":   json.Unmarshal(env.Data, &userPayload)
case "order":  json.Unmarshal(env.Data, &orderPayload)
}
```

### 错误类型

```console
$ go run .
类型错误: json: cannot unmarshal string into Go struct field User.age of type int
是 *json.UnmarshalTypeError: true  Field = age
```

`json` 的错误是**结构化的**——`*json.UnmarshalTypeError` 带 `Field`/`Value`/`Type` 字段，可以用 `errors.As` 取出来（[01-语言核心/10](../01-语言核心/10-错误处理.md)）做精细处理，比如返回"字段 `age` 应该是整数"这样的用户友好错误。

**注意 `Unmarshal` 是"尽力而为"**：遇到类型错误时**已经解析成功的字段会保留**，函数返回错误但目标对象是部分填充的。**不要用部分填充的对象**——错误返回时目标对象状态未定义。

### Go 1.27：`encoding/json/v2`

Go 1.27 引入了 `encoding/json/v2` 与 `encoding/json/jsontext`，并且**把 v1 的实现换成了 v2 支撑**（可用 `GOEXPERIMENT=nojsonv2` 退回旧实现）。

**v2 的默认行为更严格**：

```console
$ go run .
v2 重复字段 err: jsontext: duplicate object member name "name"
v2 非法 UTF-8 err: jsontext: invalid UTF-8 within "/name" after offset 9
```

| 输入 | v1（旧实现） | v2 |
|---|---|---|
| `{"name":"a","name":"b"}` | 接受，**最后一个赢**（`"b"`） | **报错** |
| 非法 UTF-8 字符串 | 接受，替换成 `U+FFFD` | **报错** |

**约束的由来**：RFC 8259 说重复成员名的行为**未定义**，且 JSON 规范要求文本必须是合法 UTF-8。v2 选择"拒绝歧义输入"，因为两个实现各取一个值会导致**跨系统的数据不一致**——这类 bug 极难排查。

**性能实测**（同一个 `encoding/json` v1 API，编译开关不同）：

```console
$ go test -bench=. -benchmem -run=^$        # 默认：v1 由 v2 支撑
BenchmarkUnmarshal-12    	  883528	      1324 ns/op	     192 B/op	       4 allocs/op
BenchmarkMarshal-12      	 1800154	       688.0 ns/op	     256 B/op	       3 allocs/op

$ GOEXPERIMENT=nojsonv2 go test -bench=. -benchmem -run=^$
BenchmarkUnmarshal-12    	  578583	      1924 ns/op	     480 B/op	      12 allocs/op
BenchmarkMarshal-12      	 2993384	       420.6 ns/op	     176 B/op	       2 allocs/op
```

| | 反序列化 | 序列化 |
|---|---|---|
| v2 支撑 | **1324 ns/op**，192 B，4 allocs | 688.0 ns/op，256 B，3 allocs |
| 旧实现 | 1924 ns/op，480 B，12 allocs | **420.6 ns/op**，176 B，2 allocs |
| 变化 | **快 1.45×，内存少 2.5×，分配少 3×** | **慢 1.64×，内存多 1.45×** |

**反序列化明显变快，序列化反而变慢**。这与 release notes 侧重宣传反序列化加速是一致的——序列化的回归是这次实现的账，如果你的服务是序列化密集（大量返回 JSON 的 API），值得实测确认。

**v2 的 API 形状**（`Options` 函数式选项）：

```go
import jsonv2 "encoding/json/v2"

jsonv2.Marshal(v, jsonv2.Deterministic(true))       // 确定性输出（字段排序）
jsonv2.Unmarshal(data, &v, jsonv2.RejectUnknownMembers(true))
```

**注意包名冲突**：`encoding/json/v2` 的包名也是 `json`，与 `encoding/json` 同名，同时导入必须起别名。

`encoding/json/jsontext` 是**更低一层**的包，提供 token 级读写：

```console
$ go run .
{ a 1 b [ 2 3 ] } 
```

它把 JSON 当作**token 流**（`{`、`a`、`1`、`[`…），适合需要精确保留格式、或者流式处理超大 JSON 的场景。

**边界**：v2 仍在演进，`GOEXPERIMENT=nojsonv2` 这个开关的存在本身就说明它还不是不可回退的。**生产项目升级前应实测自己的负载**。

### `encoding/xml` 与 `encoding/gob`

| 包 | 用途 | 何时用 |
|---|---|---|
| `encoding/xml` | XML 编解码，支持 struct tag 与流式 token | 对接遗留系统、SOAP、RSS/Atom |
| `encoding/gob` | **Go 专用**二进制编码 | Go 进程之间传数据（RPC、缓存） |

**`gob` 的关键约束是"Go 专用"**——它依赖 Go 的类型系统（发送类型描述符），其他语言解不了。换来的是：紧凑、无需 schema、支持 `chan`/`interface` 之外的几乎所有 Go 类型（需要注册具体类型）。

**跨语言一律用 protobuf**（[08-生态与框架/02](../08-生态与框架/02-gRPC与ProtocolBuffers.md)），它比 JSON 紧凑、有 schema 与代码生成、性能更好。

**与其它语言对照**：

| | 序列化 | 类型信息 | 精度 |
|---|---|---|---|
| Java Jackson | 注解 `@JsonProperty` | 有（类结构） | `BigDecimal` 可选 |
| Python `json` | `default=` 回调 | 无 | `int` 任意精度 |
| **Go `encoding/json`** | **struct tag** | **无** | **`json.Number` 可选** |

Python 的 `json` 没有类型信息也没有 tag，靠字典结构；Go 靠反射 + tag 在编译好的 struct 与 JSON 之间映射。**Go 的方式有编译期保障**（字段名拼错在运行时不报错，但至少 struct 是类型化的），Python 的方式更灵活但错误只能运行时发现。
