# Go 项目布局标准

## 定义

Go 项目布局是一套通过**目录约定**强制执行的封装边界与编译单元分组规则。它不依赖语言层面的强制结构（如 Java 的 `package-info.java` 或 Python 的 `__init__.py`），而是通过**导入路径语义**和 **go.mod 模块边界**实现编译图的物理隔离。布局的本质是**用目录结构表达可见性意图**，使编译器的静态检查能力与项目的可维护性对齐。

Go 的封装机制是**编译期强制的**，而非运行时：通过限制导入路径，编译器自动拒绝任何试图访问不可见包的代码，无需运行时检查，无性能损耗。

## 数学模型

### 编译依赖图的形式化约束

Go 项目的编译依赖关系构成一张**有向无环图（DAG）**。设节点为包，边 $(P_i, P_j)$ 表示 $P_i$ 导入了 $P_j$。

**DAG 的形式化约束**：

$$
\forall P : P \notin D^+(P)
$$

即依赖传递闭包中不存在自引用（循环依赖被编译器静态拒绝）。

**这个约束的物理意义**：若存在循环导入 $A \to B \to \cdots \to A$，编译器必须同时加载 A 和 B 的完整依赖链才能确定任一包的类型——这是一个不动点问题，在有限时间内无解。Go 选择直接禁止。

### internal 包可见性的数学约束

**internal 可见性约束**：若包 $P$ 位于路径 `$MODULE/internal/$SUBPACKAGE`，则 $P$ 仅对 `$MODULE` 内部包可见，对外部导入者不可访问。形式化地：

$$
\forall \text{ importer } I \notin MODULE \Rightarrow \text{import}(I, P) \text{ 被编译器拒绝}
$$

**可见性传播的边界**：internal 包内部的子包之间可以相互导入。internal 的限制仅对"模块外部"的导入者生效——这是一种**分层的可见性防火墙**，不是递归封闭。

### 模块边界约束与发布契约

go.mod 定义的 `$MODULE` 是公开 API 的发布单元。任何外部依赖只能引用 `$MODULE/*$` 路径下的包，不能依赖 `$MODULE/internal/*$` 下的实现细节。

**发布契约**：

$$
\forall \text{ external importer } E, \forall P \in \text{internal}(MODULE) : \text{import}(E, P) \text{ 非法}
$$

**违反后果**：编译器报错 `import cycle not allowed` 或 `package internal/... is not in your module`。这是静态约束，无法通过任何运行时手段绕过。

### 编译代价上界

设层数为 $L$（从入口到数据源的路径长度），则重新编译代价 $T_{\text{rebuild}}$ 与变更包所属层数正相关：

$$
T_{\text{rebuild}} \in O\left(\sum_{i=1}^{L} N_i\right)
$$

其中 $N_i$ 为第 $i$ 层的包数量。越底层（接近数据源）的包变更，触发越多上层包的重新编译。

**归约终点**：项目布局的数学本质是**约束编译图的可达性子集**——通过目录结构强制 DAG 形状，使可见性规则可静态验证，编译缓存可高效失效。

### 分层架构的圈复杂度约束

四层架构（handler/service/repo/model）的每一层对上层隐藏实现细节，这意味着：

$$
\text{CyclomaticComplexity}(S) \leq \text{Bound} \quad \forall S \in \text{service layer}
$$

业务逻辑集中在 service 层，需满足**事务不变量**：

$$
\text{Invariant}(S) = \forall s \in S : \text{pre}(s) \Rightarrow \text{post}(s) \land \text{post-condition never violated}
$$

Handler 层仅负责协议转换，不得包含任何业务不变量。

## 数据流

### HTTP 请求在分层项目中的完整数据流

<pre>
客户端请求
     │
     ▼
┌─────────────────────────────────────────────────────────────────┐
│  cmd/myapp/main.go                                              │
│  入口：context 初始化 → 信号注册 → 服务器启动                   │
│  数据形态：无 → 带 cancel 的 context                            │
└─────────────────────────────────────────────────────────────────┘
     │
     ▼
┌─────────────────────────────────────────────────────────────────┐
│  internal/server                                                │
│  HTTP/GRPC 服务器实例化，路由注册                                │
│  数据形态：context → 注册路由表（内存态）                        │
└─────────────────────────────────────────────────────────────────┘
     │
     ▼
┌─────────────────────────────────────────────────────────────────┐
│  internal/handler/xxx.go                                        │
│  请求解包 → 输入校验（DTO）→ 调用 service                       │
│  数据形态：HTTP Request → *model.XXX（领域对象）                │
└─────────────────────────────────────────────────────────────────┘
     │
     ▼
┌─────────────────────────────────────────────────────────────────┐
│  internal/service/xxx.go                                        │
│  业务逻辑编排 → 事务边界 → 依赖接口而非实现                      │
│  数据形态：*model.XXX → *model.YYY（可能的状态转换）           │
│  约束：事务边界内所有 repo 调用必须成功或全部回滚                │
└─────────────────────────────────────────────────────────────────┘
     │
     ▼
┌─────────────────────────────────────────────────────────────────┐
│  internal/repo/xxx.go                                           │
│  数据访问抽象（接口）→ 具体 repository 实现注入                  │
│  数据形态：*model.YYY → 持久化指令（SQL/NoSQL）                 │
│  约束：接口与实现分离，同一接口可切换不同数据库                  │
└─────────────────────────────────────────────────────────────────┘
     │
     ▼
┌─────────────────────────────────────────────────────────────────┐
│  internal/db/xxx.go 或 external postgres/mysql                   │
│  外部依赖，实际数据操作                                          │
│  数据形态：SQL → 物理行 → *model.YYY                            │
└─────────────────────────────────────────────────────────────────┘
</pre>

**数据所有权流转**：

| 层级 | 数据形态 | 所有权特点 |
|------|----------|-----------|
| Handler | HTTP Request → *model.XXX | 短暂所有权，处理完毕后传递给 Service |
| Service | *model.XXX → *model.YYY | 持有引用，可调用多个 Repository，事务结束时释放 |
| Repository | *model.YYY → SQL | 不持有数据所有权，仅负责转换 |
| Infrastructure | SQL → 物理行 | 数据库连接独立于业务对象生命周期 |

**错误传播方向**：错误沿调用链向上返回，每层可选择：
- 包装后继续上传：`fmt.Errorf("service layer: %w", err)`
- 转换后上传：将内部错误映射为对上层友好的错误类型
- 降级处理：记录日志但返回降级结果（如缓存数据）

### 编译依赖图的可达性传播

```
变更包位置          重新编译范围                    编译时间增量
─────────────────────────────────────────────────────────────────
cmd/myapp/main.go  仅该入口                        ΔT ≈ 1×package
internal/handler/  handler + 入口                  ΔT ≈ 2×package
internal/service/  service + handler + 入口        ΔT ≈ 3×package
internal/repo/     repo + service + handler + 入口  ΔT ≈ 4×package
internal/model/    所有引用 model 的包              ΔT ≈ N×package (N≥4)
```

## 机制

### 目录层次与封装边界的对应关系

Go 没有 Java 的 `private`/`protected` 访问修饰符。封装靠**导入路径**实现。`internal/` 机制的本质是语言层面的编译期可见性防火墙：

```
myproject/
├── api/              # 公开协议定义（protobuf, OpenAPI）
├── pkg/              # 公开可复用库（外部项目可导入）
└── internal/         # 编译期强制封装的代码
    ├── handler/      # HTTP/GRPC 入口
    ├── service/      # 业务逻辑（依赖 repo 接口）
    ├── repo/         # 数据访问抽象
    └── model/        # 领域对象
```

**为什么推荐这四层**：

| 层级 | 职责 | 违反封装的代价 |
|------|------|---------------|
| Handler | 协议解包/打包，输入校验 | 若在 handler 中直接操作数据库，业务逻辑分散，测试必须启动真实数据库 |
| Service | 业务不变量，事务边界 | 若在 service 中直接处理 HTTP 参数，协议变更（REST→gRPC）需改动所有 service |
| Repo | 数据访问抽象 | 若在 repo 中写业务逻辑，数据不变式可能在其他调用路径被绕过 |
| Model | 领域概念定义 | 若 model 包含业务逻辑，测试时难以 mock |

**约束条件**：每层只能导入其下层（service 导入 repo 接口，不得导入 handler），反向依赖通过接口注入实现。

**违反约束的后果**：
- 编译期：若存在反向导入，编译器报错
- 运行时语义：若通过全局变量或单例绕过依赖注入，测试无法替换实现，测试覆盖率下降

### cmd/ 入口的强制单入口原则

`cmd/` 目录下每个子目录对应一个可执行程序入口。main.go 只做三件事：

1. **配置加载**：环境变量 → 配置文件 → 默认值，优先级递减
2. **依赖注入容器初始化**：构建完整的依赖图
3. **启动/停止协调**：context 的 cancel 传播

**为什么不在根目录放 main.go**：

| 问题 | 根目录 main | cmd/ 子目录 |
|------|-------------|-------------|
| 多可执行程序 | 冲突（根 package 只能有一个） | 天然隔离（cmd/app1, cmd/app2） |
| 构建命令 | `go build .` 或指定文件 | `go build ./cmd/...` 一键全构建 |
| 模块名 | 与根 package 强绑定 | 解耦 |
| 测试入口 | 难以单独测试 main | 可单独编译测试 |

### pkg/ 的使用时机

`pkg/` 是向外部项目公开的可导入代码。**优先使用 internal/** 的原因：

1. **内部实现不应成为公开承诺**：放入 `pkg/` 意味着外部项目可能依赖它，一旦发布就难以修改内部实现
2. **编译图简化**：外部导入者只能看到 `pkg/`，内部依赖关系对外部透明
3. **重构自由**：internal 包可以随意重构重命名，不影响任何外部依赖者

**决策树**：

```
代码有独立复用价值吗？
  ├── 否 → internal/
  └── 是，外部项目会复用吗？
        ├── 否 → internal/
        └── 是 → pkg/ + 遵循语义版本
```

### 项目布局与编译缓存的关系

Go 1.10+ 的构建缓存基于**内容哈希**。包的重新编译条件：

- 包源码文件哈希变化
- 任何传递依赖的哈希变化

**缓存失效的触发链**：修改底层 model → model 包哈希变化 → 所有依赖 model 的包（如 repo, service, handler）传递失效 → 最终入口 cmd 也失效。

**布局对编译速度的影响**：

| 变更位置 | 受影响层数 | 典型重新编译包数 |
|----------|-----------|----------------|
| `cmd/` | 1 | 1（仅该入口） |
| `internal/handler/` | 2 | handler + 入口 |
| `internal/service/` | 3 | service + handler + 入口 |
| `internal/repo/` | 4 | repo + service + handler + 入口 |
| `internal/model/` | 4+ | 所有引用 model 的包 |

越底层的变更（接近数据源）触发越多重新编译。分层布局使变更的影响范围可预测——这是分层架构的**可维护性收益在编译行为上的体现**。

### go.mod 模块边界与发布约束

go.mod 定义的模块名是**外部世界的唯一标识**：

```go
module github.com/user/myproject

go 1.21
```

外部导入者只能引用 `github.com/user/myproject/...` 下的包。这意味着：
- `internal/` 下的包永远不会被外部直接导入（编译器保护）
- `pkg/` 下的包是公开 API，其变更需要遵循语义版本承诺
- `api/` 下定义的 protobuf/OpenAPI 文件是跨语言接口契约

**版本语义约束**：

| 变更类型 | 版本号递增 | 外部影响 |
|----------|-----------|----------|
| 内部实现调整 | patch (1.0.0 → 1.0.1) | 无影响 |
| 公开接口新增 | minor (1.0.0 → 1.1.0) | 向后兼容 |
| 公开接口删除/行为改变 | major (1.0.0 → 2.0.0) | 不兼容 |

### internal 包可见性的编译期强制

```
src/
├── module.go
└── internal/
    └── pkg/
        └── hidden.go

外部导入者尝试：
  import "module/internal/pkg"  // 编译错误
  // "import cycle not allowed" 或
  // "package module/internal/pkg is not in your module"

内部导入者可以：
  import "module/internal/pkg"  // OK
```

**编译器实现原理**：Go 编译器在解析导入语句时，检查目标包路径是否包含 `/internal/` 且导入者不在同一模块内。若是，拒绝。

### go.mod 与 vendor 的关系约束

```
vendor/ 目录在 go mod 时代的语义：

1. vendor/ 是构建缓存，不是依赖约束
2. go mod tidy 不会自动更新 vendor/
3. 构建时：go mod 优先于 vendor/

混用导致的问题：
  - go mod tidy 后 vendor/ 不同步 → 构建结果与预期不符
  - go mod download 后 vendor/ 不同步 → 离线构建失败

正确做法：
  - 仅在需要离线构建时使用 vendor
  - 使用 go mod vendor 同步 vendor/
  - CI 中：go mod download && go mod vendor
```

**约束的数学表达**：

$$
\text{BuildResult} = f(\text{go.mod}, \text{go.sum}, \text{vendor/})
$$

若三者不一致，`go mod` 是权威源，vendor/ 仅作缓存。

## 对比参照

| 属性 | 库项目 | CLI 项目 | 微服务项目 |
|------|--------|----------|-----------|
| 入口数量 | 0（无可执行入口） | 1（cmd/ 单根命令） | 1（cmd/server） |
| 公开 API | pkg/ 下全部公开 | 无公开 API | api/ 下定义协议 |
| 基础设施 | 无 | 无 | configs/, migrations/ |
| 分层深度 | 扁平（子包按功能） | 扁平 | 六边形/洋葱圈 |

## 反模式与约束违反

### 过深嵌套（违反编译图扁平约束）

```
反模式：src/pkg/utils/helpers/string/trim.go
      ↓
层级过深导致 import 路径过长，且容易产生循环依赖
```

**约束违反**：深层嵌套使同一逻辑单元的包被拆分到多个路径，编译图出现意外边。Go 的导入路径没有深度限制，但**可读性和维护性**随深度下降。

### 所有代码放在根包（违反可见性隔离约束）

```
反模式：根包 2000 行，所有 handler/service/model 混在一起
      ↓
无法对外部隐藏实现细节，任何外部导入者都可访问所有代码
```

**约束违反**：Go 的 internal 保护以目录为界，根包不受任何导入保护。根包的所有内容对外部世界完全可见。

### 混用 vendor 和 go mod（违反依赖解析唯一性约束）

**约束违反**：vendor/ 目录在 go mod 启用时是**缓存而非约束**，构建时优先使用 vendor 但 go.mod 仍是权威依赖列表。混用导致 `go mod tidy` 与 vendor 目录不一致。

## 版本基准

Go 1.24（stable）。本专题涉及的所有项目布局约定均基于该版本。

## 参考存根

```go
// cmd/myapp/main.go — 最简入口模式
package main

import (
    "context"
    "log"
    "os"
    "os/signal"
    "syscall"
)

func main() {
    ctx, cancel := context.WithCancel(context.Background())
    defer cancel()

    if err := run(ctx); err != nil {
        log.Fatalf("server error: %v", err)
    }

    quit := make(chan os.Signal, 1)
    signal.Notify(quit, syscall.SIGINT, syscall.SIGTERM)
    <-quit
    log.Println("shutdown complete")
}

func run(ctx context.Context) error {
    // 依赖注入，服务器启动
    return nil // placeholder
}
```

```go
// internal/repo/user_repo.go — 仓库接口定义
package repo

import "context"

type User struct {
    ID   string
    Name string
}

type UserRepository interface {
    GetByID(ctx context.Context, id string) (*User, error)
    Create(ctx context.Context, u *User) error
}
```

```go
// internal/service/user.go — 业务逻辑层
package service

import "context"

type UserService struct {
    repo UserRepository // 依赖接口而非实现
}

func (s *UserService) GetUser(ctx context.Context, id string) (*User, error) {
    return s.repo.GetByID(ctx, id)
}
```
