# Go 项目布局标准

## 定义

Go 项目布局是一套通过目录约定强制执行的**封装边界**与**编译单元分组**规则。它不依赖语言层面的强制结构（如 Java 的 package-info.java 或 Python 的 __init__.py），而是通过导入路径语义和 go.mod 模块边界，实现编译图的物理隔离。

## 数学模型

Go 项目的编译依赖关系构成一张有向无环图（DAG）。设节点为包，边 $(P_i, P_j)$ 表示 $P_i$ 导入了 $P_j$。

**约束条件**：

1. **internal 可见性约束**：若包 $P$ 位于路径 `$MODULE/internal/$SUBPACKAGE`，则 $P$ 仅对 $MODULE$ 内部包可见，对外部导入者不可访问。形式化地：

$$\forall \text{ importer } I \notin MODULE \Rightarrow \text{import}(I, P) \text{ 被编译器拒绝}$$

2. **模块边界约束**：go.mod 定义的 `$MODULE` 是公开 API 的发布单元。任何外部依赖只能引用 `$MODULE/*` 路径下的包，不能依赖 `$MODULE/internal/*` 下的实现细节。

3. **编译代价上界**：设层数为 $L$（从入口到数据源的路径长度），则重新编译代价 $T_{rebuild}$ 与变更包所属层数正相关：

$$T_{rebuild} \in O(\sum_{i=1}^{L} N_i)$$

其中 $N_i$ 为第 $i$ 层的包数量。越底层（接近数据源）的包变更，触发越多上层包的重新编译。

4. **循环依赖禁止**：Go 禁止包之间的循环导入。设 $D(P)$ 为包 $P$ 的直接依赖集，则：

$$\forall P: P \notin D^+(P)$$

即依赖传递闭包中不存在自引用。

**归约终点**：项目布局的数学本质是**约束编译图的可达性子集**——通过目录结构强制 DAG 形状，使可见性规则可静态验证，编译缓存可高效失效。

## 数据流

以下展示一个典型 HTTP 请求在分层项目中的完整数据流：

<pre>
客户端请求
     │
     ▼
┌─────────────────────────────────────────────────────────────────┐
│  cmd/myapp/main.go                                              │
│  入口：context 初始化 → 信号注册 → 服务器启动                   │
└─────────────────────────────────────────────────────────────────┘
     │
     ▼
┌─────────────────────────────────────────────────────────────────┐
│  internal/server                                                │
│  HTTP/GRPC 服务器实例化，路由注册                                │
└─────────────────────────────────────────────────────────────────┘
     │
     ▼
┌─────────────────────────────────────────────────────────────────┐
│  internal/handler/xxx.go                                        │
│  请求解包 → 输入校验（DTO）→ 调用 service                       │
│  数据形态：HTTP Request → *model.XXX（领域对象）                │
└─────────────────────────────────────────────────────────────────┘
     │
     ▼
┌─────────────────────────────────────────────────────────────────┐
│  internal/service/xxx.go                                        │
│  业务逻辑编排 → 事务边界 → 依赖接口而非实现                      │
│  数据形态：*model.XXX → *model.YYY（可能的状态转换）             │
└─────────────────────────────────────────────────────────────────┘
     │
     ▼
┌─────────────────────────────────────────────────────────────────┐
│  internal/repo/xxx.go                                           │
│  数据访问抽象（接口）→ 具体 repository 实现注入                  │
│  数据形态：*model.YYY → 持久化指令（SQL/NoSQL）                 │
└─────────────────────────────────────────────────────────────────┘
     │
     ▼
┌─────────────────────────────────────────────────────────────────┐
│  internal/db/xxx.go 或 external postgres/mysql                   │
│  外部依赖，实际数据操作                                          │
│  数据形态：SQL → 物理行 → *model.YYY                            │
└─────────────────────────────────────────────────────────────────┘
</pre>

**数据所有权流转**：
- Handler 层：拥有请求数据的短暂所有权，处理完毕后传递给 Service
- Service 层：持有领域对象的引用，可调用多个 Repository，事务结束时释放
- Repository 层：不持有数据所有权，仅负责将领域对象与持久化格式相互转换
- 数据库连接：由 infrastructure 层管理，生命周期独立于业务对象

**错误传播方向**：错误沿调用链向上返回，每层可选择：
- 包装后继续上传：`fmt.Errorf("service layer: %w", err)`
- 转换后上传：将内部错误映射为对上层友好的错误类型
- 降级处理：记录日志但返回降级结果（如缓存数据）

## 机制

### 目录层次与封装边界的对应关系

Go 没有 Java 的 `private`/`protected` 访问修饰符。封装靠**导入路径**实现。`internal/` 机制的本质是语言层面的编译期可见性防火墙：

```
myproject/
├── api/              # 公开协议定义（protobuf, OpenAPI）
├── pkg/              # 公开可复用库（外部项目可导入）
└── internal/         # 编译期强制封装的代码
    ├── handler/      # HTTP/GRPC 入口
    ├── service/      # 业务逻辑（依赖 repo 接口）
    ├── repo/         # 数据访问抽象
    └── model/        # 领域对象
```

**为什么推荐这四层**：
- Handler 层将协议问题（HTTP/GRPC）与业务逻辑分离，使 service 可独立测试
- Service 层承载业务不变式（invariant），是事务边界
- Repo 层抽象数据来源，同一个 service 可切换 MySQL/PostgreSQL 而不改业务逻辑
- Model 层定义领域概念，是层间传递的标准数据类型

**违反封装的后果**：
- 若在 handler 中直接操作数据库，业务逻辑分散到各处，测试必须启动真实数据库
- 若在 service 中直接处理 HTTP 参数，协议变更（从 REST 切到 gRPC）需要改动所有 service
- 若在 repo 中写业务逻辑，数据不变式可能在其他调用路径被绕过

### cmd/ 入口的强制单入口原则

`cmd/` 目录下每个子目录对应一个可执行程序入口。main.go 只做三件事：

1. 配置加载（环境变量 → 配置文件 → 默认值，优先级递减）
2. 依赖注入容器初始化（构建完整的依赖图）
3. 启动/停止协调（context 的 cancel 传播）

**为什么不在根目录放 main.go**：
- 根目录的 package 名为 `main` 时，多个 `cmd/` 子目录会冲突
- 多个可执行程序需要多个 `cmd/` 子目录（`cmd/app1`, `cmd/app2`），符合 Go 模块的惯例
- 工具链（`go build ./cmd/...`）可以一次性构建所有入口

### pkg/ 的使用时机

`pkg/` 是向外部项目公开的可导入代码。**优先使用 internal/** 的原因：

1. **内部实现不应成为公开承诺**：放入 `pkg/` 意味着外部项目可能依赖它，一旦发布就难以修改内部实现
2. **编译图简化**：外部导入者只能看到 `pkg/`，内部依赖关系对外部透明
3. **重构自由**：internal 包可以随意重构重命名，不影响任何外部依赖者

仅当代码确实有**独立复用价值**（如 `pkg/validator`, `pkg/redis`）时才放入 `pkg/`。

### 项目布局与编译缓存的关系

Go 1.10+ 的构建缓存基于内容哈希。包的重新编译条件：

- 包源码文件哈希变化
- 任何传递依赖的哈希变化

**布局对编译速度的影响**：

| 变更位置 | 受影响层数 | 典型重新编译包数 |
|----------|-----------|----------------|
| `cmd/`   | 1         | 1（仅该入口）   |
| `internal/handler/` | 2 | handler + 入口 |
| `internal/service/` | 3 | service + handler + 入口 |
| `internal/repo/` | 4 | repo + service + handler + 入口 |
| `internal/model/` | 4+ | 所有引用 model 的包 |

越底层的变更（接近数据源）触发越多重新编译。分层布局使变更的影响范围可预测。

### go.mod 模块边界与发布约束

go.mod 定义的模块名是**外部世界的唯一标识**：

```
module github.com/user/myproject

go 1.21
```

外部导入者只能引用 `github.com/user/myproject/...` 下的包。这意味着：
- `internal/` 下的包永远不会被外部直接导入
- `pkg/` 下的包是公开 API，其变更需要遵循语义版本承诺
- `api/` 下定义的 protobuf/OpenAPI 文件是跨语言接口契约

## 库项目布局

纯库项目（无可执行入口）的布局原则：

```
mylib/
├── mylib.go              # 根包，导出核心类型和函数
├── subpkg/               # 子包，按功能分组
│   ├── foo.go
│   └── foo_test.go
├── example_test.go       # 集成示例（以 _test.go 结尾，go test 可运行）
├── README.md             # 必须：godoc.org 会抓取
├── LICENSE
└── go.mod
```

**库命名约束**：
- 模块名 `github.com/user/mylib` 与包名 `mylib` 无须相同
- 但 go.mod 中的模块名必须与导入路径一致
- 根包避免与子包重名：`mylib` vs `mylib/cache`

## CLI 项目布局

命令行工具的特殊布局考虑：

```
cli/
├── cmd/
│   ├── root.go       # 根命令，定义全局 flags 和用法
│   ├── install.go    # 子命令
│   └── version.go    # 子命令
├── main.go           # 入口，仅调用 cmd.Execute()
└── go.mod
```

**Cobra 命令分层原则**：
- `root.go` 定义全局 flags（`--config`, `--verbose`）和持久 flags
- 每个子命令是独立文件，职责单一
- `Execute()` 是组合点，不在 `init()` 中注册子命令（init 仅用于 flag 解析配置）

## 微服务布局

微服务在标准项目布局基础上增加基础设施关注点：

```
microservice/
├── api/                    # IDL 定义（protobuf, OpenAPI）
│   └── proto/
├── cmd/server/             # 唯一入口
├── internal/
│   ├── domain/             # 领域模型（贫血 vs 充血的选择）
│   ├── service/            # 应用服务
│   ├── repository/         # 数据访问接口
│   └── infrastructure/     # 数据库、缓存、消息队列实现
├── configs/                # 部署配置（ConfigMap, Secret）
├── migrations/             #  schema 迁移（sql-migrate, goose）
├── Dockerfile
└── docker-compose.yml
```

**微服务分层与六边形架构的对应**：
- `domain/` = 核心业务逻辑（端口）
- `repository/` = 持久化端口接口
- `infrastructure/` = 适配器实现
- `service/` = 用例编排，协调 domain 之间的交互

## 反模式与约束违反

### 过深嵌套（违反编译图扁平约束）

```
反模式：src/pkg/utils/helpers/string/trim.go
      ↓
层级过深导致 import 路径过长，且容易产生循环依赖
```

**约束违反**：深层嵌套使同一逻辑单元的包被拆分到多个路径，编译图出现意外边。

### 所有代码放在根包（违反可见性隔离约束）

```
反模式：根包 2000 行，所有 handler/service/model 混在一起
      ↓
无法对外部隐藏实现细节，任何外部导入者都可访问所有代码
```

**约束违反**：Go 的 internal 保护以目录为界，根包不受任何导入保护。

### 混用 vendor 和 go mod（违反依赖解析唯一性约束）

**约束违反**：vendor/ 目录在 go mod 启用时是**缓存而非约束**，构建时优先使用 vendor 但 go.mod 仍是权威依赖列表。混用导致 `go mod tidy` 与 vendor 目录不一致。

## 参考存根

```go
// cmd/myapp/main.go — 最简入口模式
package main

import (
    "context"
    "log"
    "os"
    "os/signal"
    "syscall"
)

func main() {
    ctx, cancel := context.WithCancel(context.Background())
    defer cancel()

    if err := run(ctx); err != nil {
        log.Fatalf("server error: %v", err)
    }

    quit := make(chan os.Signal, 1)
    signal.Notify(quit, syscall.SIGINT, syscall.SIGTERM)
    <-quit
    log.Println("shutdown complete")
}

func run(ctx context.Context) error {
    // 依赖注入，服务器启动
    return nil // placeholder
}
```

```go
// internal/repo/user_repo.go — 仓库接口定义
package repo

import "context"

type User struct {
    ID   string
    Name string
}

type UserRepository interface {
    GetByID(ctx context.Context, id string) (*User, error)
    Create(ctx context.Context, u *User) error
}
```

```go
// internal/service/user.go — 业务逻辑层
package service

import "context"

type UserService struct {
    repo UserRepository // 依赖接口而非实现
}

func (s *UserService) GetUser(ctx context.Context, id string) (*User, error) {
    return s.repo.GetByID(ctx, id)
}
```
