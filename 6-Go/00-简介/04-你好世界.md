# 你好，世界！

## 定义

Go 程序以 `package main` 声明入口包，`func main()` 定义程序执行起点，静态编译为单一可执行文件。程序生命周期从 OS 加载二进制开始，经运行时初始化（调度器、GC、netpoll），执行 `main.init()` 依赖链，最后进入 `main goroutine` 执行用户代码。

## 数学模型

### 程序启动时间的分解

Go 程序从执行到 `main()` 的总时间 $T_{start}$ ：

$T_{start} = T_{load} + T_{link} + T_{runtime\_init} + T_{main\_init} + T_{main}$

| 阶段 | 描述 | 典型耗时 |
|------|------|----------|
| $T_{load}$ | 二进制从磁盘加载到内存 | $O(\text{binary\_size})$ |
| $T_{link}$ | 动态链接（静态编译模式下为 0） | $O(1)$ |
| $T_{runtime\_init}$ | 运行时初始化（调度器、GC、netpoll 等） | ~1ms |
| $T_{main\_init}$ | main 包级变量的初始化 | ~0.1ms |

**典型值**：Go 程序启动时间约 **1-5ms**，远低于 JVM 启动（~500ms）。

**数学意义**： $T_{runtime\_init}$ 与包数量无关（已静态链接），而 JVM 需要加载类路径上的所有类。

### 编译产物大小的约束

静态编译的二进制大小 $S_{binary}$ 由以下因素决定：

$S_{binary} = S_{runtime} + S_{reflect} + S_{app} + S_{debug}$

| 组成部分 | 说明 | 大小 |
|----------|------|------|
| $S_{runtime}$ | 运行时（调度器、GC、反射） | ~1.5MB |
| $S_{reflect}$ | 反射（type descriptor） | ~500KB |
| $S_{app}$ | 应用代码 | 取决于业务 |
| $S_{debug}$ | 调试信息（-s -w 剥离后） | 可忽略 |

总计：**最小可执行文件约 2MB**（纯运行时）。

**体积优化选项**：
- `go build -ldflags="-s -w"`：剥离符号表和调试信息
- `upx` 压缩：可压缩至 ~1MB
- `CGO_ENABLED=0`：禁用 CGO，减小体积

**关键数据形态变换**：

| 阶段 | 形态 | 机制 |
|------|------|------|
| 加载 | ELF/PE → 虚拟地址映射 | OS 内存管理 |
| 运行时初始化 | 顺序执行 → 并发调度 | GMP 调度器启动 |
| main.init() | 包依赖 DAG → 拓扑序执行 | 初始化顺序保证 |
| main() | goroutine → 可并发执行 | goroutine 创建 |

## 机制

### 为什么 Go 强制格式化

Go 使用 `gofmt` 强制统一代码风格，消除了**风格争论**这一无意义的协作成本。

**gofmt 的核心规则**：
- 缩进使用 Tab（而非空格）
- 行宽 80 字符
- 保留注释风格
- 导出成员大写，私有成员小写

**设计动机**：
- 代码风格不是个人偏好，而是**协作基础设施**
- 强制格式化让 code review 聚焦于逻辑，而非格式
- `go fmt` 和 `go vet` 是 CI 的基础检查

### 为什么 Go 选择静态编译

Go 编译产物是**单一可执行文件**，这使得：

1. **部署极简**：无需关心目标机器是否安装了运行时
2. **Docker 镜像可极小**：`FROM scratch` 无需运行时层
3. **版本一致**：构建时确定的依赖，运行时不可变

**数学约束**：静态编译消除了运行时动态链接的 **PLT/GOT 查找开销**：

$\text{函数调用成本} = \begin{cases} \text{直接跳转} & \text{静态链接} \\ \text{PLT 表跳转 + GOT 查找} & \text{动态链接} \end{cases}$

### 为什么入口必须是 package main

Go 以包为编译单元，`package main` 告诉编译器这个包需要生成**可执行文件**（而非库）。

**编译单元分类**：
- `package main`：可执行文件，必须有 `func main()`
- 其他包：库文件，不能独立运行

**项目结构约定**：
```
myapp/
├── go.mod
├── main.go      // package main
└── lib/
    └── utils.go // package utils
```

main 包的存在使项目结构清晰：**可执行项目的入口必然是 main 包 + main 函数**。

### 为什么 Go 没有动态链接支持（默认）

Go 默认静态链接的**利弊分析**：

**优势**：
| 优势 | 机制 |
|------|------|
| **安全** | 无外部依赖，无 DLL 劫持风险 |
| **隔离** | 运行时行为完全确定 |
| **简单** | 部署就是复制文件 |

**代价**：
| 代价 | 影响 |
|------|------|
| 无法共享运行时内存 | 多个 Go 程序各自持有运行时副本 |
| 镜像体积较大 | ~5-10MB vs ~1MB 动态链接 |
| 安全更新需重新编译 | 无法单独更新运行时 |

**历史背景**：Go 1.5 之前使用 gccgo（gcc 前端）支持动态链接，但后来统一为 gc 编译器的静态链接策略。

### main goroutine 的生命周期

`main goroutine` 具有特殊地位：

1. **main goroutine 结束 → 程序结束**：所有其他 goroutine 被强制终止
2. **main goroutine 返回 → 调用 `os.Exit()`**
3. **`runtime.Goexit()`** → 调用所有 defer，调用 `os.Exit(1)`

```go
func main() {
    // main goroutine 启动
    // 如果这里创建了后台 goroutine，它们在 main 结束后会被强制终止
    // defer 会在 os.Exit 之前执行
    defer cleanup()
}
```

## 参考存根

```go
// 运行时入口：src/runtime/rt0_go.s
// _rt0_go 是真正的入口（汇编层）
TEXT _rt0_go(SB),NOSPLIT,$0
    CALL    runtime·check(SB)        // 类型检查
    CALL    runtime·args(SB)         // 命令行参数
    CALL    runtime·osinit(SB)        // OS 初始化
    CALL    runtime·schedinit(SB)    // 调度器初始化
    CALL    runtime·mstart(SB)       // 启动主线程

// main 包初始化后调用 main.main()
CALL    main·main(SB)

// 如果 main.main 正常返回，调用 os.Exit(0)
CALL    runtime·exit(SB)
CALL    runtime·exitret(SB)

// 如果 main.main 调用 runtime.Goexit()
CALL    runtime·goexit(SB)
```

**关键点**：
- `_rt0_go` 是汇编入口，执行运行时初始化
- `schedinit()` 设置 GMP 调度器
- `mstart()` 启动主线程 M，进入调度循环
- `main.main()` 在 main goroutine 中执行
