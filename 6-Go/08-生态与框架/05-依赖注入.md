# 依赖注入

> 前置：[04-配置管理](./04-配置管理.md) · 后续：[06-认证授权](./06-认证授权.md)

> **版本基准**：Go 1.27（stable = latest）。本篇示例实测环境：go1.27.1 windows/amd64，`github.com/google/wire`、`go.uber.org/fx`。

## 本质

**依赖注入（DI）就是"把依赖从外部传进来，而不是在内部创建"。**

```go
type UserService struct {
	db     DB
	cache  Cache
	logger Logger
}

func NewUserService(db DB, cache Cache, logger Logger) *UserService {
	return &UserService{db: db, cache: cache, logger: logger}
}
```

**这就是全部的 DI**——构造函数接收依赖并存为字段。没有容器、没有注解、没有 XML。

**约束的由来**：Go 里 DI 不需要框架，因为**接口是隐式满足的**（[01-语言核心/08](../01-语言核心/08-接口.md)）——测试时直接传假实现（[07-测试与质量/02](../07-测试与质量/02-单元测试与mock.md)），不需要任何运行时机制介入。Java 需要 Spring 是因为 `implements` 是显式的，替换实现要靠字节码增强或反射。

**判据**：**先用手动装配**。上面 20 行的 `main` 就是装配代码——它显式、可读、零依赖。**只有当装配代码膨胀到几十上百行时才考虑工具**。

## 机制

### 手动装配

```console
$ go run .
Get(1) = 缓存命中
time=2026-09-27T18:17:44.143+08:00 level=INFO msg=缓存未命中 id=2
Get(2) = 结果来自 postgres://localhost/app
```

```go
func main() {
	// 1. 基础设施
	cfg := &Config{DSN: "postgres://localhost/app"}
	logger := slogLogger{slog.New(slog.NewTextHandler(os.Stdout, nil))}
	db := &postgresDB{dsn: cfg.DSN}
	cache := &memCache{m: map[string]string{"1": "缓存命中"}}

	// 2. 业务组件
	svc := NewUserService(db, cache, logger)

	// 3. 使用
	...
}
```

**这就是 [06-工程与工具链/04](../06-工程与工具链/04-项目布局.md) 里"`main.go` 只做装配"的具体形态**——所有对象的创建顺序、依赖关系，在这一个函数里一目了然。

**约束**：**依赖必须是接口**（`DB`/`Cache`/`Logger`），不是具体类型。这是可测试性的前提——传 `*postgresDB` 就没法在测试里替换。

**判据**：**接口定义在消费方**（[07-测试与质量/02](../07-测试与质量/02-单元测试与mock.md)）。`UserService` 需要什么，就在它所在的包里定义什么接口——不要照抄 `postgresDB` 的全部方法。

### `wire`：编译期代码生成

手写装配的问题在规模上暴露：一个有 50 个组件的服务，`main` 里的装配代码可能有 200 行，且**每次加一个组件都要改多处**。

`wire` 用**代码生成**解决——你声明"需要什么"，它生成装配代码：

```go
//go:build wireinject

package main

import "github.com/google/wire"

func InitService() *UserService {
	wire.Build(NewConfig, NewLogger, NewDB, NewCache, NewUserService)
	return nil
}
```

```console
$ wire ./...
wire: di1/wire: wrote wire_gen.go

$ cat wire_gen.go
// Code generated by Wire. DO NOT EDIT.
//go:build !wireinject
// +build !wireinject

func InitService() *UserService {
	config := NewConfig()
	db := NewDB(config)
	cache := NewCache()
	logger := NewLogger()
	userService := NewUserService(db, cache, logger)
	return userService
}
```

**生成的代码就是手写的那几行**——`wire` 不做运行时魔法，它只是把装配代码写出来。

**三条约束**：

**一、`//go:build wireinject` 让声明文件不参与正常构建**——它与生成的文件互斥（生成的是 `!wireinject`）。这样 `wire.Build` 里的 `wire` 依赖**不会进入最终产物**（实测 `go list -deps github.com/google/wire` = 1，只有包本身）。

**二、`wire` 是构建期工具，不是运行时依赖**——它应当用 `tools.go` 管理版本（[06-工程与工具链/05](../06-工程与工具链/05-构建交叉编译与发布.md)）。

**三、`wire_gen.go` 必须提交**（或在 CI 里生成后校验）。

**判据**：`wire` 的价值在**"依赖图由编译器验证"**——少提供一个 provider、类型不匹配、出现循环依赖，`wire` 生成时就会报错。手写装配的错误要到运行时才暴露。

**边界**：`wire` **不做运行时解析**——没有反射、没有容器、启动零开销。这是它与 `fx` 的根本差别。

### `fx`：运行时容器

```go
fx.New(
	fx.Provide(NewConfig, NewLogger, NewDB, NewCache, NewUserService),
	fx.Invoke(func(svc *UserService) {
		// 使用 svc
	}),
).Run()
```

`fx` 用**反射在运行时解析依赖图**。它提供 `wire` 没有的能力：

| 能力 | `wire` | `fx` |
|---|---|---|
| 依赖解析时机 | **编译期** | 运行时 |
| 生命周期钩子（`OnStart`/`OnStop`） | 无 | **有** |
| 优雅关闭编排 | 自己写 | **内建** |
| 运行时可替换 | 否 | 是 |
| 启动开销 | **零** | 反射 + 容器初始化 |

**代价实测**：`fx` 的依赖闭包是 **230 个包**（对照 `net/http` 的 190 个）——它带进了 zap、dig 等一批依赖。

**判据**：**需要"按顺序启动/关闭多个组件"时才用 `fx`**——数据库连接、消息队列消费者、HTTP 服务，它们有明确的启动顺序与关闭顺序，`fx` 的生命周期管理能省掉大量编排代码。

**边界**：**`fx` 的错误在运行时暴露**——依赖缺失或类型不匹配，要到程序启动才 panic。这是用灵活性换来的。

### 何时需要 DI 工具

| 规模 | 做法 |
|---|---|
| < 10 个组件 | **手动装配**（一个 `main` 函数） |
| 10–30 个组件 | `wire`（编译期验证，零运行时开销） |
| > 30 个组件 + 需要生命周期管理 | `fx` |

**约束**：**不要为了"架构好看"上 DI 框架**。手动装配的 20 行代码比一个框架的隐式装配更容易理解和调试——**当你能一眼看完装配代码时，它就是最好的方案**。

**边界**：`wire` 与 `fx` **可以共存**——用 `wire` 生成基础设施的装配，用 `fx` 管理生命周期。但多数项目只需要其中一个。

### 循环依赖

```go
// A 依赖 B，B 依赖 A —— 两者都无法构造
func NewA(b *B) *A { ... }
func NewB(a *A) *B { ... }
```

**`wire` 会在生成时直接报错**（循环依赖检测是依赖图分析的一部分）。

**约束**：**Go 的编译期循环导入禁令**（[01-语言核心/11](../01-语言核心/11-包与可见性.md)）**不覆盖依赖注入的循环**——`A` 与 `B` 在同一个包里时，导入没有循环，但构造函数互相需要。

**解法**：**引入接口打断环**。`A` 依赖 `B` 的接口（定义在 `A` 的包里），`B` 的实现去满足它——构造顺序变成"先建 B 的实现，再建 A"，环就断了。

**这是"接口定义在消费方"（[07-测试与质量/02](../07-测试与质量/02-单元测试与mock.md)）在架构层面的收益**——它不仅让测试可替换，还让依赖方向可以倒转。

**与其它语言对照**：

| | 主流方案 | 机制 |
|---|---|---|
| Java | **Spring**（事实标准） | 运行时反射 + 注解 + 代理 |
| Python | FastAPI `Depends` / `dependency-injector` | 运行时反射 |
| C# | **内建 DI 容器**（`Microsoft.Extensions.DependencyInjection`） | 运行时反射 |
| **Go** | **手动装配**（默认）／`wire`／`fx` | 手写 / 代码生成 / 运行时反射 |

**Java、C#、Python 的 DI 都是"框架先行"**——没有 Spring 的 Java 企业应用基本不存在。**Go 的默认答案是"不注入任何框架"**——20 行手动装配。

**这个差别来自接口的实现方式**：Java 的 `implements` 是显式的，运行时替换实现需要框架的字节码能力；Go 的隐式满足让"传个不同的 struct 进去"就够了。**当语言本身支持结构性替换时，DI 框架就失去了存在的大部分理由**。
