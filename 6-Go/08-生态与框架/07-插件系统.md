# 插件系统

> 前置：[06-认证授权](./06-认证授权.md) · 后续：无（本目录终篇）

> **版本基准**：Go 1.27（stable = latest）。本篇示例实测环境：go1.27.1 windows/amd64。

## 本质

**Go 的插件有两条路：`plugin` 包（进程内动态库）与子进程（跨进程 RPC）。前者受平台限制，后者跨平台但有 IPC 开销。**

| | `plugin` 包 | 子进程 |
|---|---|---|
| 平台 | **仅 Linux/macOS/FreeBSD** | **全平台** |
| 语言 | **必须也是 Go** | 任意（只要能读写管道） |
| 调用开销 | 接近直接调用 | **IPC 往返（实测 18–21 µs）** |
| 隔离性 | **无**（崩溃带走宿主） | **有**（插件崩溃不影响宿主） |
| 版本耦合 | **极严**（工具链版本必须完全一致） | 松（协议稳定即可） |

**约束的由来**：Go 的 `plugin` 包**在 Windows 上不可用**——它不是"未实现"，而是编译成一个返回错误的桩：

```console
$ go build -o plug.exe .    # Windows 上编译成功
$ ./plug.exe
<nil> plugin: not implemented
```

源码里的两个构建约束说明了原因：

```go
// plugin_dlopen.go
//go:build (linux && cgo) || (darwin && cgo) || (freebsd && cgo)

// plugin_stubs.go
//go:build (!linux && !freebsd && !darwin) || !cgo
```

**需要三个平台之一，且必须开启 cgo**——`plugin` 底层用 `dlopen`，而 Windows 的对应机制（`LoadLibrary`）没有实现。**`CGO_ENABLED=0` 时同样退化成桩**。

**判据**：**需要跨平台或需要崩溃隔离，一律用子进程**。`plugin` 只适合"Linux 上、纯 Go、信任的插件、追求零开销"这个很窄的场景。

## 机制

### 子进程插件：实测

```console
$ go run ./host
upper  输出="HELLO 世界"       单次往返=    21µs
rev    输出="界世 olleh"       单次往返=    18µs
进程内    输出="HELLO 世界"       单次调用=      0s
```

**协议是"一行请求，一行响应"**：

```go
func (p *procPlugin) Process(s string) (string, error) {
	if _, err := p.in.WriteString(s + "\n"); err != nil { return "", err }
	if err := p.in.Flush(); err != nil { return "", err }
	if !p.out.Scan() { return "", fmt.Errorf("插件 %s 无响应", p.name) }
	return p.out.Text(), nil
}
```

**三处关键点**：

**一、`Flush` 是必须的**——`bufio.Writer` 会攒够缓冲才发，不 flush 会让请求卡在缓冲区里，双方死等。

**二、必须有超时**——上面的实现**没有超时**：插件如果卡住不响应，`p.out.Scan()` 会永久阻塞。生产实现要加 `context` + `SetDeadline`（[05-IO与外部世界/02](../05-IO与外部世界/02-网络编程.md)）或者用独立的读 goroutine + `select`（[04-并发/02](../04-并发/02-channel与select.md)）。

**三、插件崩溃要能被发现**——`Scan()` 返回 `false` 且 `Err() != nil` 时说明插件进程退出了。上面的实现把它当成"无响应"，**应当区分"进程死了"与"进程慢"**。

**开销**：18–21 µs 的往返。对照 [03-运行时与内存/06](../03-运行时与内存/06-CGO与跨语言调用.md) 的 cgo 调用（43 ns），**IPC 慢了约 400 倍**。但对照一次 HTTP 请求（毫秒级），20 µs 完全可以接受。

**约束**：**插件的通信协议必须有版本号**——`{"v": 1, "method": "...", "params": {...}}`。没有版本号时，宿主与插件的升级必须同步，失去了插件化的意义。

### `hashicorp/go-plugin`：工业级实现

上面的 20 行 demo 缺少工业场景需要的东西：握手、双向通信、日志转发、崩溃检测、mTLS、多插件管理。

`hashicorp/go-plugin` 提供了全部这些——**Terraform、Vault、Nomad 的插件系统都用它**：

```go
// 插件侧
plugin.Serve(&plugin.ServeConfig{
	HandshakeConfig: handshake,
	Plugins: map[string]plugin.Plugin{
		"greeter": &GreeterPlugin{},
	},
	GRPCServer: plugin.DefaultGRPCServer,
})
```

**它的核心设计**：

| 机制 | 作用 |
|---|---|
| **握手**（`HandshakeConfig`） | 防止宿主加载错误的插件（magic cookie + 协议版本） |
| **gRPC 传输** | 用 protobuf 定义接口（[02-gRPC与ProtocolBuffers](./02-gRPC与ProtocolBuffers.md)） |
| **`Stdout` 保护** | 插件误写 stdout 会破坏协议——它把 stdout 重定向到日志 |
| **自动重启** | 插件崩溃后可选自动重启 |
| **mTLS** | 插件与宿主之间的双向认证 |

**约束**：`go-plugin` 的**协议版本与接口定义是耦合的**——改接口要同时更新宿主与所有插件。它用 `ProtocolVersion` 显式管理这个契约。

**判据**：**自己写插件系统时，先看 `go-plugin` 的设计**——它把"进程管理 + 握手 + 传输 + 生命周期"这四件事的坑都踩过了。

### 编译期插件：接口 + 注册表

**最"Go"的插件方案其实是编译期链接**——插件是实现了某个接口的包，通过 `init()` 注册自己：

```go
// plugin 接口
type Formatter interface {
	Name() string
	Format([]byte) ([]byte, error)
}

// 注册表
var registry = map[string]Formatter{}

func Register(name string, f Formatter) { registry[name] = f }

// 插件包
func init() { Register("json", jsonFormatter{}) }

// 宿主
import _ "example.com/app/plugins/json"
```

**这利用了 [01-语言核心/11](../01-语言核心/11-包与可见性.md) 的空白导入 + `init()` 顺序**——与 `database/sql` 的驱动注册完全同构（[05-IO与外部世界/04](../05-IO与外部世界/04-数据库访问.md)）。

| 优点 | 缺点 |
|---|---|
| **零开销**（直接函数调用） | **不能运行时加载**（要重新编译） |
| **类型安全**（编译期检查） | 插件与宿主一起发布 |
| 跨平台 | 插件崩溃带走宿主 |

**判据**：**"插件"的目的是"第三方扩展"还是"可选功能"？**

- **第三方扩展**（用户能写自己的插件）→ 子进程
- **可选功能**（按需编译进不同的发行版）→ **编译期注册**

**多数项目的"插件系统"其实是后者**——用 build tag 或不同的 `main` 包选择编译哪些功能，比动态加载简单得多且没有开销。

### 用 `build tag` 做功能开关

```go
//go:build enterprise

package main

func init() { Register("sso", ssoAuth{}) }
```

```console
$ go build -tags=enterprise -o app-enterprise .
$ go build -o app-community .
```

**这是"插件"最轻的形态**——同一份代码，不同的 tag 产出不同的发行版。**零运行时开销、零协议设计、零进程管理**。

**约束**：build tag 的**组合会爆炸**——3 个开关就有 8 种组合，每个都要测。**判据**：**开关数量超过 3–4 个时，考虑改成运行时配置**（[04-配置管理](./04-配置管理.md)）。

### 热加载

**Go 不支持真正的热加载**——不能替换正在运行的进程里的代码。

| 方案 | 做法 | 代价 |
|---|---|---|
| **进程重启** | 新进程起好，旧进程优雅退出 | 需要连接排空、状态迁移 |
| **子进程插件重载** | 杀掉插件进程，起新的 | **宿主不受影响**（这是子进程方案的核心优势） |
| **反射 + 重新解释** | 不存在 | — |

**约束**：**"优雅重启"是 Go 服务的标准做法**——监听 `SIGTERM`，停止接受新连接，等待在途请求完成，然后退出。这与插件的热加载是两件事，但常被混淆。

**`plugin` 包也不支持重载**——`plugin.Open` 打开的动态库**无法卸载**（没有 `plugin.Close`）。打开过的插件会一直占用内存。

**下游**：无——本目录终篇。

**与其它语言对照**：

| | 动态加载 | 隔离 | 跨语言 |
|---|---|---|---|
| Java | **ClassLoader + 反射**（成熟） | 无（同进程） | 否 |
| Python | `importlib`（成熟） | 无（GIL 内） | 否 |
| C/C++ | `dlopen` | 无 | 是 |
| **Go** | **`plugin`（仅 3 平台 + cgo）** | 无 | 否 |
| **Go（子进程）** | **`os/exec`** | **有** | **是** |

**Go 的动态加载能力是主流语言里最弱的**——Java 的 ClassLoader 能在运行时加载/卸载类，Python 的 `importlib` 能重新加载模块，C 的 `dlopen` 跨语言。**Go 的 `plugin` 只支持三个平台、只支持 Go 写的插件、不能卸载、工具链版本必须完全一致**。

**这个限制是设计选择的结果**：Go 的静态链接与"运行时编译进产物"（[00-概览/01](../00-概览/01-Go全景.md)）让动态加载在技术上很难做对——插件的运行时版本与宿主的必须完全匹配，否则类型系统的一致性无法保证。

**生态的应对是"用子进程代替进程内"**——Terraform、Vault、Docker 的插件机制全是子进程 + RPC。**代价是 20 µs 的 IPC 开销，收益是崩溃隔离、跨语言、跨平台、可独立升级**。对插件这个场景，这笔交易通常是划算的。
