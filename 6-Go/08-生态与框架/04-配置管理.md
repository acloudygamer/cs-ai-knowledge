# 配置管理

> 前置：[03-命令行工具](./03-命令行工具.md) · 后续：[05-依赖注入](./05-依赖注入.md)

> **版本基准**：Go 1.27（stable = latest）。本篇示例实测环境：go1.27.1 windows/amd64，`github.com/spf13/viper`。

## 本质

**配置管理要解决的是"同一份代码在不同环境跑出不同行为"**——而这个问题的核心不是"读文件"，是**优先级**：当标志、环境变量、配置文件、默认值给出不同值时，谁赢。

Viper 的优先级（从高到低）：

| 优先级 | 来源 |
|---|---|
| 1 | **`viper.Set(...)`**（程序内显式设置） |
| 2 | **命令行标志**（`BindPFlag`） |
| 3 | **环境变量** |
| 4 | **配置文件** |
| 5 | **远程 KV 存储**（etcd/Consul） |
| 6 | **`viper.SetDefault(...)`** |

实测：

```console
$ go run .
配置文件: config.yaml
server.host       = 0.0.0.0
server.port       = 9090  (文件里是 8080，环境变量覆盖为 9090)
server.timeouts   = read=5s write=10s
database.dsn      = postgres://env-host/app  (环境变量覆盖)
database.max_conns= 20
features          = [auth metrics]

Set 之后 server.port = 7070（程序内 Set 优先级最高）
未在文件里的默认值 idle = 1m0s
```

**约束的由来**：这个优先级顺序符合"**越靠近运行时的越优先**"——环境变量比配置文件更接近部署环境（同一个镜像在不同环境用不同的环境变量），程序内 `Set` 比一切都高（测试时可以直接改）。

**判据**：**配置项应当按"谁会改它"分层**：

| 配置 | 放哪 | 谁改 |
|---|---|---|
| 端口、日志级别、连接串 | **环境变量** | 运维/部署 |
| 业务参数、特性开关 | **配置文件** | 开发/产品 |
| 不会变的默认值 | **代码里的默认值** | 开发者 |

## 机制

### 读配置文件

```go
viper.SetConfigFile("config.yaml")
if err := viper.ReadInConfig(); err != nil {
	return err
}
fmt.Println("配置文件:", viper.ConfigFileUsed())
```

**Viper 支持 YAML/JSON/TOML/HCL/INI/env 等格式**，按扩展名自动识别。要按目录搜索（多环境配置）用 `SetConfigName` + `AddConfigPath`。

**约束**：**`ConfigFileUsed()` 应当被记录到启动日志**——排查"为什么配置没生效"时，第一件要确认的就是"读的是哪个文件"。

### 环境变量覆盖

```go
viper.SetEnvPrefix("APP")
viper.AutomaticEnv()
viper.SetEnvKeyReplacer(strings.NewReplacer(".", "_"))
```

```console
$ APP_SERVER_PORT=9090 go run .
server.port       = 9090  (文件里是 8080，环境变量覆盖为 9090)
```

**三行缺一不可**：

| 调用 | 作用 | 不调的后果 |
|---|---|---|
| `SetEnvPrefix("APP")` | 环境变量前缀 | 任何环境变量都能覆盖配置（**危险**） |
| `AutomaticEnv()` | 开启自动查找 | 环境变量完全不生效 |
| `SetEnvKeyReplacer` | `.` → `_` 映射 | `server.port` 找不到 `APP_SERVER_PORT` |

**约束**：**`SetEnvKeyReplacer` 是必须的**——环境变量名不能含 `.`，所以配置里的 `server.port` 必须映射到 `APP_SERVER_PORT`。漏掉这行会让环境变量覆盖静默失效（**不报错**）。

**边界**：`AutomaticEnv` **只对 `Get` 系列生效**，**对 `Unmarshal` 不生效**——这是 Viper 的一个已知不一致。用 `Unmarshal` 时要显式 `BindEnv` 每个键，或者先用 `Get` 取值再赋值。

### 映射到结构体

```go
type Config struct {
	Server struct {
		Host     string        `mapstructure:"host"`
		Port     int           `mapstructure:"port"`
		Timeouts struct {
			Read  time.Duration `mapstructure:"read"`
			Write time.Duration `mapstructure:"write"`
		} `mapstructure:"timeouts"`
	} `mapstructure:"server"`
	...
}

viper.Unmarshal(&cfg)
```

**`mapstructure` tag 不是 `json` tag**——Viper 用 `github.com/mitchellh/mapstructure` 做解码，tag 名不同。写 `json:"host"` 会被忽略。

**约束**：**Viper 的键名匹配默认大小写不敏感**（`host`、`Host`、`HOST` 都能匹配到同一个键）——这让 YAML 的 `camelCase` 与 `snake_case` 混用不会出错，但也意味着**无法用大小写区分两个键**。

**`time.Duration` 可以直接映射**——`read: 5s` 会被解析成 `5*time.Second`。这是 mapstructure 的 `StringToTimeDurationHookFunc` 提供的，**需要显式注册**（`viper.Unmarshal` 默认不带）：

```go
viper.Unmarshal(&cfg, viper.DecodeHook(
	mapstructure.StringToTimeDurationHookFunc(),
))
```

**约束**：**结构体字段必须是导出的**（[01-语言核心/11](../01-语言核心/11-包与可见性.md)）——mapstructure 用反射赋值，非导出字段会被静默跳过。

### 默认值

```go
viper.SetDefault("server.timeouts.idle", 60*time.Second)
```

```console
$ go run .
未在文件里的默认值 idle = 1m0s
```

**约束**：**默认值应当在代码里显式声明**，而不是藏在配置文件里。这让"程序不配任何东西也能启动"成为可能——配置文件的缺失应当是**可接受的**，而不是启动失败。

**判据**：**关键配置（数据库地址、密钥）应当"缺失即失败"**——用 `viper.GetString` 后检查空值并返回明确错误，而不是给一个错误的默认值（连到 localhost 比启动失败更危险）。

### 配置校验

**Viper 不做任何校验**——它只负责读取。校验要自己做：

```go
func (c *Config) Validate() error {
	if c.Server.Port < 1 || c.Server.Port > 65535 {
		return fmt.Errorf("server.port 非法: %d", c.Server.Port)
	}
	if c.Database.DSN == "" {
		return errors.New("database.dsn 不能为空")
	}
	return nil
}
```

**约束的由来**：**启动时校验比运行时失败好**——一个配置错误的进程如果启动成功了，会在第一次处理请求时才暴露问题。**在 `main` 里加载配置后立刻校验并 `os.Exit(1)`**。

**边界**：用 struct tag + 校验库（`go-playground/validator`，Gin 用的同一个，见 [01-Web框架](./01-Web框架.md)）能省掉手写校验，但**跨字段校验**（如 `min < max`）仍要手写。

### 热重载

```go
viper.OnConfigChange(func(e fsnotify.Event) {
	log.Println("配置已重载:", e.Name)
	// 注意：这里要重新 Unmarshal 并安全地替换运行时配置
})
viper.WatchConfig()
```

**约束**：**热重载的难度不在"读新配置"，在"安全地替换"**——正在处理请求的 goroutine 可能正读着旧配置。安全做法是用 `atomic.Pointer[Config]` 原子替换（[04-并发/03](../04-并发/03-sync与原子操作.md)）：

```go
var current atomic.Pointer[Config]

viper.OnConfigChange(func(e fsnotify.Event) {
	var c Config
	if err := viper.Unmarshal(&c); err != nil {
		log.Println("重载失败，保持旧配置:", err)
		return
	}
	if err := c.Validate(); err != nil {
		log.Println("新配置非法，保持旧配置:", err)
		return
	}
	current.Store(&c)          // 原子替换
})
```

**判据**：**校验失败时必须保留旧配置**——热重载把服务搞挂是比"配置没生效"严重得多的事故。

**边界**：**不是所有配置都能热重载**——监听端口、数据库连接池大小这类要在启动时确定。**判据**：能安全替换的才重载，其余的明确标注"需重启生效"。

### 密钥的处理

| 做法 | 评价 |
|---|---|
| 密钥写进配置文件并提交 | **绝对不行** |
| 配置文件里放占位符，环境变量注入 | **常见做法** |
| 环境变量直接给 | **推荐**（Kubernetes Secret 的标准形态） |
| 专用密钥管理（Vault、AWS Secrets Manager） | 大型系统的做法 |

**约束**：**Viper 的 `AutomaticEnv` 让环境变量覆盖配置成为标准做法**——配置文件里放 `dsn: ""`，部署时用 `APP_DATABASE_DSN` 注入。这样**配置文件可以安全提交**。

**边界**：**环境变量会出现在 `/proc/<pid>/environ`、容器 inspect、崩溃转储里**——它比配置文件好，但不是绝对安全。真正敏感的密钥需要 Vault 这类方案。

## 连接

**上游**：[03-命令行工具](./03-命令行工具.md) 的标志是 Viper 优先级链的一环（`BindPFlag`）；[02-标准库/05](../02-标准库/05-序列化与编码.md) 的 JSON/YAML 解析是配置读取的底层。

**下游**：[05-依赖注入](./05-依赖注入.md) 把解析出的 `Config` 装配到各组件；[06-认证授权](./06-认证授权.md) 的密钥从配置来。

**与其它语言对照**：

| | 主流方案 | 优先级机制 |
|---|---|---|
| Java | Spring Boot `@ConfigurationProperties` | **内建完整优先级链** |
| Python | `pydantic-settings` / `dynaconf` | 可配置 |
| Node.js | `dotenv` + `config` | 简单（环境变量优先） |
| **Go** | **Viper**（第三方） | 内建完整优先级链 |

**Spring Boot 与 Viper 解决同一个问题**——但 Spring 的配置是**框架核心的一部分**（`application.yml` + profile + 环境变量 + 命令行参数的优先级是 Spring 定义的），而 Go 的 Viper 是**可选库**。

**这是 Go 生态的典型形态**：标准库只提供 `os.Getenv` 与 `encoding/json`（[02-标准库/05](../02-标准库/05-序列化与编码.md)），完整的配置管理交给生态。**代价是选择成本**——Viper、koanf、envconfig 各有拥护者，没有 Spring 那样的唯一答案。

**判据**：**配置简单时不必上 Viper**——只读环境变量的话，`os.Getenv` + `strconv` 就够了（[02-标准库/01](../02-标准库/01-字符串与字节.md) 讲过 `strconv` 是给机器用的）。Viper 的价值在**多来源 + 优先级 + 多格式**这三样同时需要时。
