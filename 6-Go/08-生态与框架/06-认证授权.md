# 认证授权

> 前置：[05-依赖注入](./05-依赖注入.md) · 后续：[07-插件系统](./07-插件系统.md)

> **版本基准**：Go 1.27（stable = latest）。本篇示例实测环境：go1.27.1 windows/amd64，Intel i7-10750H（6 核 12 线程），`github.com/golang-jwt/jwt/v5 v5.3.1`、`golang.org/x/crypto v0.57.0`。

## 本质

**认证（Authentication）回答"你是谁"，授权（Authorization）回答"你能做什么"。**

| | 认证 | 授权 |
|---|---|---|
| 问题 | 你是谁 | 你能做什么 |
| 手段 | 密码、Token、证书 | 角色、权限、策略 |
| 失败码 | **401 Unauthorized** | **403 Forbidden** |
| Go 里的位置 | 登录端点 + 中间件 | 中间件 / 业务逻辑内 |

**约束的由来**：401 与 403 常被混用——**401 表示"没认证或认证失效"（该重新登录），403 表示"认证了但没权限"（重新登录也没用）**。混用会让客户端做出错误反应（反复跳登录页）。

**边界**：Go **标准库不提供认证授权组件**——`crypto/*` 提供密码学原语（哈希、签名、TLS），但 JWT、会话、OAuth 都要靠第三方库或自己实现。这与 `net/http`/`database/sql` 的"标准库生产级"形成对比（[00-概览/01](../00-概览/01-Go全景.md)）。

## 机制

### 密码存储：bcrypt

```console
$ go run .
哈希结果: $2a$10$GnecplfLWXhUjQwpgQqbg. ...
哈希长度: 60 字节（60 固定）
两次哈希是否相同: false （salt 随机）
校验正确密码: true
校验错误密码: crypto/bcrypt: hashedPassword is not the hash of the given password
```

**bcrypt 的三个性质**：

**一、输出定长 60 字节**——`$2a$10$<22 字节 salt><31 字节哈希>`。因此数据库列宽固定。

**二、salt 随机且包含在输出里**——同一密码两次哈希结果不同。**这是必需的**：不加 salt 的话，攻击者可以用彩虹表（预计算的哈希字典）批量破解。

**三、故意慢**——这是它与其他哈希函数的根本差别：

| cost | 耗时（实测） |
|---|---|
| 4 | 1 ms |
| 10（默认） | **51 ms** |
| 14 | **816 ms** |

**cost 每 +1，耗时翻倍**。默认 10 意味着验证一次密码要 51 ms。

**约束的由来**：**这个"慢"是设计目标**——攻击者拿到数据库后要暴力破解，每次尝试都要 51 ms，破解速度被限制在每秒约 20 次。而正常的登录流程中，用户 51 ms 的等待无感。

**判据**：**cost 的选择是"用户体验 vs 破解成本"的权衡**。10 是 2020 年代的合理默认；硬件升级后应当提高（12–14），但要注意登录端点的 QPS 上限——**cost=14 时单核每秒只能处理约 1 次登录**，会成为 DoS 面。

**边界**：**bcrypt 有 72 字节的密码长度上限**——超过部分被静默截断。超长密码要先 SHA-256 再 bcrypt（`bcrypt` 的 `GenerateFromPassword` 在 Go 里超过 72 字节会返回错误，不会静默截断）。

**替代方案**：`argon2id`（`golang.org/x/crypto/argon2`）是更新的推荐——它同时抗 GPU 与抗内存优化攻击（bcrypt 只抗 CPU 暴力，GPU 仍能加速）。OWASP 当前推荐 argon2id 优先。

### JWT：无状态令牌

```console
$ go run .
token: eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ ...
长度: 200 字节
解析成功: uid=42 role=admin sub=user:42
篡改后解析: token signature is invalid: signature is invalid
过期后解析: token has invalid claims: token is expired  errors.Is(ErrTokenExpired): true
错误密钥解析: token signature is invalid: signature is invalid
```

**JWT 是三段 base64url 用 `.` 连接**：`header.payload.signature`。**payload 是明文**（只是 base64 编码），任何人都能读——**不要在里面放敏感信息**。

**三种错误都能被检出**：

| 场景 | 错误 |
|---|---|
| 篡改 payload | `token signature is invalid` |
| 过期 | `token has invalid claims: token is expired` |
| 密钥不对 | `token signature is invalid` |

**约束**：**解析时必须校验签名算法**：

```go
jwt.ParseWithClaims(signed, &Claims{}, func(t *jwt.Token) (any, error) {
	if _, ok := t.Method.(*jwt.SigningMethodHMAC); !ok {
		return nil, fmt.Errorf("意外的签名算法: %v", t.Header["alg"])
	}
	return secret, nil
})
```

**这是 JWT 最著名的漏洞（`alg=none` 攻击）**：攻击者把 header 的 `alg` 改成 `none`，去掉签名——如果服务端不检查算法就直接接受，认证被完全绕过。**必须显式验证 `t.Method` 的类型**。

**判据**：`errors.Is(err, jwt.ErrTokenExpired)` 要单独判断——**过期不是"令牌无效"，而是"该刷新了"**，客户端反应不同（前者跳登录，后者静默刷新）。

**边界**：**JWT 无法主动撤销**——签发后在有效期内一直有效。要支持"登出立即失效"必须维护黑名单（那就失去了无状态的意义），或者用**短有效期 access token + 长有效期 refresh token** 的组合。

### JWT vs 会话

| | JWT | 服务端会话 |
|---|---|---|
| 状态 | **无状态**（服务端不存） | 有状态（存 Redis/内存） |
| 水平扩展 | **天然支持** | 需要共享存储 |
| 撤销 | **做不到**（除非加黑名单） | **删记录即可** |
| 体积 | 每次请求带 200+ 字节 | 只带 session id |
| 适用 | 微服务、跨域 API | 单体应用、需要即时登出 |

**约束**：**JWT 不是"更现代的会话"**——它解决的是**无状态水平扩展**，代价是**失去撤销能力**。单体应用用 JWT 通常是过度设计。

### 中间件：认证与授权

```go
// 认证中间件
func Auth(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		token := extractBearer(r)
		claims, err := verify(token)
		if err != nil {
			http.Error(w, "unauthorized", http.StatusUnauthorized)   // 401
			return
		}
		ctx := context.WithValue(r.Context(), claimsKey{}, claims)
		next.ServeHTTP(w, r.WithContext(ctx))
	})
}

// 授权中间件
func RequireRole(role string) func(http.Handler) http.Handler {
	return func(next http.Handler) http.Handler {
		return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
			c := r.Context().Value(claimsKey{}).(*Claims)
			if c.Role != role {
				http.Error(w, "forbidden", http.StatusForbidden)     // 403
				return
			}
			next.ServeHTTP(w, r)
		})
	}
}
```

**约束**：**`claimsKey{}` 必须是自定义的空 struct 类型**（[04-并发/04](../04-并发/04-context与取消传播.md)）——用 `string` 作 key 会让不同包冲突，且 `go vet` 会报错。

**401 与 403 的分工**：认证中间件返回 401，授权中间件返回 403。

### RBAC：角色与权限

| 模型 | 表达 | 适用 |
|---|---|---|
| **RBAC** | 用户 → 角色 → 权限 | 多数企业系统 |
| **ABAC** | 基于属性（用户、资源、环境）的策略 | 复杂规则 |
| **ReBAC** | 基于关系（谁是谁的什么） | 协作/社交场景 |

**RBAC 的最小实现**：

```go
var rolePerms = map[string]map[string]bool{
	"admin":  {"user:read": true, "user:write": true, "user:delete": true},
	"editor": {"user:read": true, "user:write": true},
	"viewer": {"user:read": true},
}
```

**约束**：**权限检查应当集中在中间件或统一的检查函数里**——散落在各 handler 里的 `if user.Role != "admin"` 无法审计"谁能做什么"。**判据**：能不能用一个表回答"角色 X 有哪些权限"？不能就说明权限逻辑散开了。

**边界**：**资源级授权（"只能改自己的订单"）无法只靠角色表达**——它需要检查资源归属。这类检查必须写在业务逻辑里，且**必须在数据库查询条件里带上 `user_id`**，而不是查出来再判断（后者有 TOCTOU 风险，且浪费查询）。

### 常见漏洞

| 漏洞 | 表现 | 防护 |
|---|---|---|
| **`alg=none`** | 攻击者去掉签名 | **显式校验算法** |
| **密钥硬编码** | 密钥在源码/配置里 | 环境变量或密钥管理（[04-配置管理](./04-配置管理.md)） |
| **弱密钥** | `secret`、`123456` | 至少 256 位随机 |
| **时序攻击** | 用 `==` 比较 token | **`subtle.ConstantTimeCompare`** |
| **密码明文日志** | 请求体被完整记录 | 日志脱敏（[05-IO与外部世界/05](../05-IO与外部世界/05-日志与可观测性.md)） |
| **JWT 存 localStorage** | XSS 可窃取 | HttpOnly Cookie 或内存存储 |

**时序攻击的防护**：

```go
import "crypto/subtle"

if subtle.ConstantTimeCompare(got, want) != 1 { ... }
```

**约束的由来**：`==` 比较字符串**在第一个不同字节处就返回**——攻击者可以通过测量响应时间逐字节猜出正确的值。`ConstantTimeCompare` 总是比较完所有字节。

**边界**：时序攻击在网络环境下需要大量样本才能利用，**但 token 与 API key 的比较是零成本的防护点**——没有理由不做。

### OAuth 2.0 / OIDC

**判据**：**不要自己实现 OAuth 服务端**——授权码流程、PKCE、state 校验、令牌轮换的细节极多，出错就是严重漏洞。**用现成的**：

| 场景 | 方案 |
|---|---|
| 作为 OAuth **客户端**（用 GitHub/Google 登录） | `golang.org/x/oauth2` |
| 作为 OAuth **服务端** | `ory/hydra`、`go-oauth2/oauth2` |
| 企业内部 SSO | **OIDC** + `coreos/go-oidc` |

**约束**：**OIDC 是 OAuth 2.0 之上的身份层**——OAuth 只解决"授权访问"，OIDC 增加了 `id_token`（一个 JWT）来表达"用户是谁"。**登录场景要用 OIDC 而不是裸 OAuth**。

**与其它语言对照**：

| | 密码哈希 | JWT | 框架支持 |
|---|---|---|---|
| Java | Spring Security 的 `BCryptPasswordEncoder` | jjwt / nimbus | **Spring Security（全家桶）** |
| Python | `passlib` / `bcrypt` | PyJWT | Django 内置 auth |
| Node.js | `bcrypt` / `argon2` | jsonwebtoken | Passport |
| **Go** | **`x/crypto/bcrypt`** | **`golang-jwt/jwt`** | **无（自己组合）** |

**Go 没有 Spring Security 那样的"认证授权全家桶"**——`x/crypto` 提供原语，JWT 库提供令牌，中间件要自己写（也就 20 行，见上）。

**这个差别与 [05-依赖注入](./05-依赖注入.md) 是同一个**：Java 的框架之所以必需，是因为语言缺少让这些组件自由组合的机制。**Go 的 `http.Handler` 中间件 + 接口隐式满足，让"自己组装一套认证"的成本低到不需要框架**。

**代价是安全性的"默认值"缺失**——Spring Security 的默认配置虽然啰嗦，但它把 `alg=none`、CSRF、会话固定这些坑都处理了。Go 里这些要靠开发者知道并自己防。
