# 日志与可观测性

> 前置：[04-数据库访问](./04-数据库访问.md) · 后续：[06-工程与工具链](../06-工程与工具链/)

> **版本基准**：Go 1.27（stable = latest）。本篇示例实测环境：go1.27.1 windows/amd64。

## 本质

**`log/slog` 是 Go 1.21 引入的结构化日志标准库**——它把日志从"格式化字符串"变成"**消息 + 键值对属性**"。

```go
slog.Info("请求完成", "method", "GET", "status", 200)
```

**约束的由来**：Go 1.21 之前只有 `log` 包，输出是**纯文本行**。要从里面提取 `status` 只能靠正则解析——脆弱且慢。结构化日志把属性作为**一等数据**交给 `Handler`，由 Handler 决定怎么序列化（文本、JSON、或者发到远端）。

**边界**：`slog` **不负责输出目的地**——它只负责"把属性交给 Handler"。写到文件、发到 Kafka、上报到 OTLP 都是 `Handler` 的实现。标准库提供 `TextHandler` 与 `JSONHandler` 两个，第三方（zap、zerolog）提供高性能版本。

## 机制

### 两种 Handler 的输出差异

```console
$ go run .
=== TextHandler ===
time=2026-09-27T18:03:02.433+08:00 level=DEBUG msg=调试信息 user=张三 attempt=1
time=2026-09-27T18:03:02.443+08:00 level=INFO msg=请求完成 method=GET path=/users/42 status=200 duration_ms=12.5
time=2026-09-27T18:03:02.443+08:00 level=WARN msg=连接池接近上限 open=9 max=10
time=2026-09-27T18:03:02.443+08:00 level=ERROR msg=数据库查询失败 err="connection refused"
=== JSONHandler ===
{"time":"2026-09-27T18:03:02.4437411+08:00","level":"DEBUG","msg":"调试信息","user":"张三","attempt":1}
{"time":"2026-09-27T18:03:02.4437411+08:00","level":"INFO","msg":"请求完成","method":"GET","path":"/users/42","status":200,"duration_ms":12.5}
{"time":"2026-09-27T18:03:02.4437411+08:00","level":"WARN","msg":"连接池接近上限","open":9,"max":10}
{"time":"2026-09-27T18:03:02.4437411+08:00","level":"ERROR","msg":"数据库查询失败","err":"connection refused"}
```

| | `TextHandler` | `JSONHandler` |
|---|---|---|
| 适合 | **本地开发、人读** | **生产、机器读** |
| 含空格的值 | 自动加引号（`err="connection refused"`） | JSON 转义 |
| 时间精度 | 毫秒 | **微秒**（`4437411`） |
| 解析成本 | 需正则 | `json.Unmarshal` |

**判据**：**生产一律用 JSON**——日志收集系统（Loki、Elasticsearch、CloudWatch）都原生解析 JSON。本地开发用 Text 更易读。

**约束**：`slog` 的**属性顺序与代码里一致**，但 JSON 对象的键顺序在规范上无序。不要依赖键顺序做解析。

### 错误值自动处理

```console
err="connection refused"
"err":"connection refused"
```

传进 `slog` 的 `error` 值会被自动转成字符串。**但只转 `Error()` 的结果**——错误的类型信息丢失了。

**判据**：需要保留错误类型时自己展开：

```go
slog.Error("查询失败", "err", err, "err_type", fmt.Sprintf("%T", err))
```

**约束**：`slog` **不会**自动调用 `errors.Unwrap` 或记录堆栈——Go 的错误默认不带堆栈（[01-语言核心/10](../01-语言核心/10-错误处理.md)）。要堆栈得用 `%+v`（需要第三方错误库）或自己加。

### `With` 与 `Group`：结构化上下文

```console
$ go run .
=== With + Group ===
{"time":"...","level":"INFO","msg":"请求","service":"api","http":{"method":"GET","status":200}}
{"time":"...","level":"INFO","msg":"请求","service":"api","http":{"req":{"path":"/a","id":1}}}
```

| 方法 | 效果 |
|---|---|
| `logger.With("service", "api")` | **返回新 logger**，后续每条日志都带这个属性 |
| `logger.WithGroup("http")` | 后续属性**嵌套进一个 JSON 对象** |

**约束**：`With` **返回新 logger**，不修改原 logger——所以：

```go
l := slog.Default().With("request_id", id)   // ✅ 用返回值
slog.Default().With("request_id", id)         // ❌ 丢弃了返回值，白做
```

**`With` 是处理请求上下文的标准手段**：在 HTTP 中间件里创建带 `request_id`/`user_id`/`trace_id` 的 logger，存进 `context`（[04-并发/04](../04-并发/04-context与取消传播.md)），下游各层从 context 取出使用。**这样每条日志都自带请求标识，不用手动传**。

**约束**：把 logger 存进 `context` 是 `slog` 唯一被官方认可的"context 传值"用法——但它仍然违反"context 只传请求作用域数据"的字面规定。判据是：**请求 ID 确实是请求作用域的横切数据**，符合 `WithValue` 的本意。

### 动态调级：`LevelVar`

```console
$ go run .
=== LevelVar 动态调级 ===
time=... level=WARN msg=可见
time=... level=INFO msg=调级后可见
```

```go
var lv slog.LevelVar
lv.Set(slog.LevelWarn)
handler := slog.NewTextHandler(w, &slog.HandlerOptions{Level: &lv})
lv.Set(slog.LevelDebug)     // 运行时生效，无需重启
```

**`HandlerOptions.Level` 接受 `slog.Leveler` 接口**——`LevelVar` 实现了它，因此可以在运行时改。**直接传 `slog.LevelDebug` 常量则无法改变**。

**约束**：`LevelVar` 是并发安全的，但**改变后只影响之后的日志**——已经写出去的不受影响。生产环境常见的做法是把它挂在 `expvar` 或管理端点上，运维可以动态开 Debug。

### `LogValuer`：延迟求值

```console
$ go run .
  [LogValue 被调用]
=== LogValuer（只求值一次）===
time=... level=INFO msg=这条会输出 v=expensive-result
```

`[LogValue 被调用]` **只出现一次**——`Debug` 级别的那条日志因为级别不够被丢弃，**属性根本没有被求值**。

```go
type expensive struct{}
func (expensive) LogValue() slog.Value { ... }   // 只在真的要输出时调用
```

**约束的由来**：`slog.Info("x", "v", computeExpensive())` 里的 `computeExpensive()` **总是会被调用**——它是普通函数实参，在调用 `Info` 之前就求值了。**要避免这个开销必须实现 `LogValuer`**。

**判据**：属性构造代价高（要查数据库、序列化大对象、做 DNS 查询）时**必须**用 `LogValuer`。否则高频 Debug 日志在级别关闭时仍会消耗 CPU。

### 接管 `log` 包

```go
slog.SetDefault(jsonLogger)
```

调用后，**标准库 `log` 包的 `log.Printf` 等函数会走 slog 的 Handler**（Go 1.21+）。这让依赖 `log` 的第三方库也输出 JSON。

**约束**：`log` 的输出会被包成一条 `slog` 记录，消息是原来的整行文本——**结构化属性只有 `msg` 一个**。因此接管后第三方库的日志仍然是"半结构化"的。

### 日志该记什么

| 该记 | 不该记 |
|---|---|
| **请求的入口与出口**（方法、路径、状态码、耗时） | 每个函数进入/退出 |
| **错误的上下文**（哪个操作、哪个 ID、什么参数） | 密码、token、完整身份证号 |
| **状态变更**（配置重载、连接池扩容） | 循环内的每条迭代 |
| **外部依赖调用的结果**（DB、RPC、缓存） | 库内部的调试细节 |

**约束**：**错误该包装后向上返回，日志只在边界处记一次**。层层都记会让一个错误产生十几条日志，真正的根因被淹没（[01-语言核心/10](../01-语言核心/10-错误处理.md) 的 `%w` 包装就是为了让上层能拿到完整信息）。

**判据**：**日志的级别决定它该不该存在**——

| 级别 | 判据 |
|---|---|
| `Debug` | 只在排查具体问题时有用 |
| `Info` | 记录"系统做了什么"，**每条都该有信息量** |
| `Warn` | 有问题但能继续，**需要有人看** |
| `Error` | 需要人工介入 |

**`Error` 级别滥用是常见问题**——如果 Error 日志不触发任何人的行动，它就不该是 Error。

### 可观测性的三个支柱

| 支柱 | 回答 | Go 的手段 |
|---|---|---|
| **Logs** | 发生了什么 | `log/slog` |
| **Metrics** | 有多少、多快 | `expvar` / Prometheus 客户端 |
| **Traces** | 一次请求经过了哪些环节 | **OpenTelemetry** |

```console
$ go run .
=== expvar 输出 ===
  requests_total = 42
  version = "1.0"
```

**`expvar` 是标准库里的最小 metrics 方案**——把变量注册到 `/debug/vars` 的 JSON 端点（[03-HTTP服务与客户端](./03-HTTP服务与客户端.md) 的 `net/http/pprof` 同源）。它够用但简陋：没有直方图、没有标签、没有聚合。

**生产用 Prometheus 客户端库**（`github.com/prometheus/client_golang`），它提供 Counter/Gauge/Histogram/Summary 四种指标类型与标签维度。

**追踪必须用 OpenTelemetry**——它是 CNCF 的行业标准，Go SDK 成熟。核心 API 是 `otel.Tracer("name").Start(ctx, "span")`，span 通过 `context` 传播（[04-并发/04](../04-并发/04-context与取消传播.md)）。

**约束**：**追踪的采样率必须可配置**——100% 采样在生产上会产生巨量数据。常见策略是"错误请求全采 + 正常请求按比例采"。

**与其它语言对照**：

| | 结构化日志 | 标准库？ |
|---|---|---|
| Java | Logback + SLF4J + Logstash encoder | 否（`java.util.logging` 很弱） |
| Python | `logging` + `structlog` / `python-json-logger` | 部分（`logging` 是标准库但非结构化） |
| Node.js | `pino` / `winston` | 否 |
| **Go** | **`log/slog`** | **是（1.21+）** |

**Go 是四者中唯一把结构化日志做进标准库的**（Java 的 `java.util.logging` 不是结构化日志，Python 的 `logging` 要靠 formatter 拼）。这与 `net/http`、`database/sql` 是同一个模式——**标准库把"生产可用的最小集"内置，第三方库解决的是性能与生态集成**。

**性能上 zap/zerolog 仍然更快**（零分配设计），但差距在多数场景下不重要——**日志往往不是瓶颈**，先 profile（[03-运行时与内存/07](../03-运行时与内存/07-性能剖析与调优.md)）再决定要不要换。
