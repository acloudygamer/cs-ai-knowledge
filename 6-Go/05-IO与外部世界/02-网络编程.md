# 网络编程

> 前置：[01-文件与文件系统](./01-文件与文件系统.md) · 后续：[03-HTTP服务与客户端](./03-HTTP服务与客户端.md)

> **版本基准**：Go 1.27（stable = latest）。本篇示例实测环境：go1.27.1 windows/amd64。

## 本质

**`net.Conn` 是一个 `io.Reader` + `io.Writer` + `Close` + 超时设置的接口**——与 [01-文件与文件系统](./01-文件与文件系统.md) 的 `*os.File` 是同一套 I/O 抽象的两种实现。

```go
type Conn interface {
	Read(b []byte) (n int, err error)
	Write(b []byte) (n int, err error)
	Close() error
	LocalAddr() Addr
	RemoteAddr() Addr
	SetDeadline(t time.Time) error
	SetReadDeadline(t time.Time) error
	SetWriteDeadline(t time.Time) error
}
```

**这条共性决定了 Go 的网络编程写法**：`bufio.NewReader(conn)`、`io.Copy(conn, file)`、`gzip.NewReader(conn)` 都直接可用——不需要为 socket 单独学一套 API。

**边界**：**TCP 是字节流，不是消息流**。这是本篇最重要的一条约束，也是"粘包"问题的根源（下面展开）。Go 的网络 API **不提供任何消息边界**——那必须由应用层协议自己定义。

## 机制

### 粘包与分包

```console
$ go run .
演示一：一次 Write 三条消息（无帧边界）
  Read 返回 15 字节: "msg1;msg2;msg3;"
```

客户端一次 `Write([]byte("msg1;msg2;msg3;"))`，服务端**一次 `Read` 拿到全部 15 字节**。服务端无法从这 15 字节里知道消息边界在哪——它看到的是 `"msg1;msg2;msg3;"` 这样一个字节序列。

**约束的由来（在协议层不在 Go）**：TCP 只保证**字节有序到达**，不保证**一次 Read 对应一次 Write**。具体行为取决于：

| 因素 | 影响 |
|---|---|
| Nagle 算法 | 小包会被合并发送（减少网络往返） |
| MTU / MSS | 大消息会被 IP 层分片 |
| 内核缓冲区 | 多次 `Write` 可能被合并成一次 `Read` |
| 调度时机 | 一次 `Write` 可能被拆成多次 `Read`（第一次实测就是这样） |

**"粘包"与"分包"是同一个问题的两面**：没有边界信息时，读方无法切分。**这个问题在 UDP 上不存在**（UDP 保留消息边界），但 UDP 不保证到达与顺序。

### 解法：长度前缀

```console
$ go run .
演示二：长度前缀协议（一次 Write 三帧，仍能正确切分）
  帧 1: 长度=9 内容="payload-1"
  帧 2: 长度=9 内容="payload-2"
  帧 3: 长度=9 内容="payload-3"
```

三帧被拼成一个字节切片一次 `Write`，服务端仍能正确切分——**因为每帧自带长度**。

```go
var lb [4]byte
io.ReadFull(r, lb[:])                      // 先读 4 字节长度
l := binary.BigEndian.Uint32(lb[:])
payload := make([]byte, l)
io.ReadFull(r, payload)                    // 再读 l 字节内容
```

**三处关键点**：

**一、必须用 `io.ReadFull` 而不是 `Read`。** `Read` 可能只返回部分数据——**一次 `Read` 读到的字节数是不确定的**，这正是分包。`io.ReadFull` 会循环直到读满或出错。

**二、长度字段必须校验上限。** 本示例的 `maxFrame = 1 MiB` 不是装饰——如果协议失同步（读到了错误的字节当长度），长度字段可能是个天文数字，`make([]byte, l)` 会直接 OOM。**这是协议解析里最危险的一处**：写代码时曾把残留字节读成长度 `1836279602`，申请 1.8 GB 内存。

**三、大端序是网络字节序。** `binary.BigEndian` 是惯例（`network byte order`），不是强制——但自定义协议里混用大小端会造成极难排查的跨平台 bug。

**其它成帧方案**：

| 方案 | 例子 | 缺点 |
|---|---|---|
| **长度前缀** | 本示例、protobuf、gRPC | 需要先读长度，无法流式 |
| **定界符** | HTTP 头、Redis 协议 | 内容里不能出现定界符（需转义） |
| **定长帧** | 某些工业协议 | 浪费带宽 |
| **自描述格式** | JSON（括号配对） | 解析器复杂，仍需流式处理 |

### 服务端骨架

```go
ln, err := net.Listen("tcp", "127.0.0.1:0")   // 端口 0 = 让内核分配
defer ln.Close()
for {
	conn, err := ln.Accept()      // 阻塞直到有连接
	if err != nil {
		return                     // 注意：Accept 出错通常该退出循环
	}
	go handle(conn)               // 每个连接一个 goroutine
}
```

**约束**：`ln.Accept()` **返回错误时不能简单 `continue`**——监听套接字出错（比如被关闭）会立刻再次返回错误，形成忙循环。**惯用做法是判断 `net.ErrClosed` 后退出**。

**每连接一个 goroutine** 是 Go 服务端的标准写法（[04-并发/01](../04-并发/01-goroutine与生命周期.md) 实测每个约 635 字节），不需要线程池。

### 超时：必须显式设置

```console
$ go run .
DialTimeout 不可达地址: 300ms, err=dial tcp 192.0.2.1:80: i/o timeout
```

`net.DialTimeout` 精确在 300 ms 超时（192.0.2.0/24 是 TEST-NET-1，保留给文档用，必定不可达）。

**`net.Dial` 没有默认超时**——它会用操作系统的 TCP 超时（Linux 上约 2 分钟）。**生产代码必须用 `DialTimeout` 或 `DialContext`**。

三种超时机制：

| 机制 | 作用范围 | 说明 |
|---|---|---|
| `DialTimeout` / `DialContext` | **建立连接** | 只影响三次握手 |
| `SetDeadline` / `SetReadDeadline` / `SetWriteDeadline` | **单次读写** | 每次调用后都要重设 |
| `context` + `DialContext` | 建立连接 + 可取消 | **推荐**（[04-并发/04](../04-并发/04-context与取消传播.md)） |

**约束**：`SetDeadline` 是**绝对时间点**，不是时长。而且它**只对当前及后续的阻塞操作生效一次**——循环里读要每次都设，或者用 `SetReadDeadline(time.Now().Add(d))` 在循环内刷新。**常见的错误是设了一次就以为永久有效。**

**正确做法是用 `context`**：

```go
d := net.Dialer{Timeout: 5 * time.Second}
conn, err := d.DialContext(ctx, "tcp", addr)
```

这样 `ctx` 取消时连接会被中断，且超时统一由 context 管理。

### 地址解析

| 函数 | 用途 |
|---|---|
| `net.ResolveTCPAddr` | 解析成 `*net.TCPAddr`（含 IP 与端口） |
| `net.LookupHost` | DNS 查主机名 |
| `net.LookupIP` | 同上，返回 `[]net.IP` |
| `net.ParseIP` / `net.ParseCIDR` | 解析 IP 字面量与网段 |

**约束**：`net.LookupHost` 走**系统解析器**（`/etc/hosts`、DNS），**可能阻塞**（没有超时控制），且**不能传入 `context`**。要可控就用 `net.Resolver` 加 `LookupHost(ctx, host)`。

### UDP

```go
pc, _ := net.ListenUDP("udp", &net.UDPAddr{Port: 0})
n, addr, _ := pc.ReadFromUDP(buf)
pc.WriteToUDP(reply, addr)
```

**UDP 没有连接概念**——用 `ReadFromUDP`/`WriteToUDP` 收发，每次都要带地址。**它保留消息边界**（一次 `WriteToUDP` 对应一次 `ReadFromUDP`），但有大小上限（通常 64 KiB 减去头部）且不保证到达与顺序。

**判据**：需要低延迟、容忍丢包、消息小且独立（DNS、指标上报、游戏状态）用 UDP；其余用 TCP。

### TLS

```go
cert, _ := tls.LoadX509KeyPair("cert.pem", "key.pem")
ln, _ := tls.Listen("tcp", ":443", &tls.Config{Certificates: []tls.Certificate{cert}})
```

`tls.Listener` 与 `tls.Conn` **也是 `net.Listener` 与 `net.Conn` 的实现**——握手在 `Accept` 时自动完成，之后的 `Read`/`Write` 就是明文，加密对调用方透明。

**约束**：`tls.Conn` 的 `Close()` **会发送 close_notify 并等待对端响应**——如果对端不响应，`Close` 会阻塞到超时。**在生产代码里给 `Close` 设超时**。

**Go 1.27 的新增**：`crypto/tls` 支持后量子签名方案 `MLDSA44`/`MLDSA65`/`MLDSA87`，`crypto/x509` 支持 ML-DSA 密钥（[10-版本演进/03](../10-版本演进/03-Go1.18至1.27.md)）。

**与其它语言对照**：

| | socket API | 并发模型 |
|---|---|---|
| C | `socket`/`bind`/`listen`/`accept` | `epoll`/`kqueue` 手动管理 |
| Java | `ServerSocket`/`Socket` | 每连接一线程 / NIO / Netty |
| Python | `socket` 模块 | `asyncio` / 线程 |
| **Go** | **`net.Listen`/`net.Conn`** | **每连接一 goroutine（运行时自动用 epoll）** |

**Go 的关键优势在最后一列**：它用 `epoll`（Linux）/`IOCP`（Windows）/`kqueue`（macOS）在**运行时内部**做非阻塞 I/O，但对用户呈现的是**阻塞式 API**。写代码时 `conn.Read` 看起来是阻塞的，实际上运行时把 goroutine 挂起、把 M 让给别的 goroutine（[03-运行时与内存/01](../03-运行时与内存/01-运行时总览与调度器.md) 讲的 syscall 解绑 P）。

**结果是**：C 里要手写事件循环的复杂度、Java NIO 里要手写 `Selector` 循环的复杂度，在 Go 里变成了"直接写阻塞代码 + `go` 关键字"。这是 Go 在服务端流行的最直接原因。
