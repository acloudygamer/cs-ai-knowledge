> **版本基准**：Go 1.27（stable = latest）。本篇示例实测环境：go1.27.1 windows/amd64，驱动 `modernc.org/sqlite v1.60.1`（纯 Go，无需 cgo）。

## 本质

**`sql.DB` 是一个连接池，不是一个连接。**

这是 `database/sql` 最容易被误解的一点。`sql.Open` **不建立任何连接**——它只是校验参数、创建一个池子的管理对象。真正的连接在第一次执行查询时才建立。

```go
db, _ := sql.Open("sqlite", ":memory:")   // 此刻没有连接
db.QueryRow("SELECT 1")                    // 此刻才建连接
```

**约束的由来**：这个设计是为了让 `*sql.DB` 可以**长期持有、并发共享**。如果它是一个连接，就得考虑"多个 goroutine 同时用会怎样"；作为池子，`*sql.DB` 本身是并发安全的，每个操作从池里取一个连接。

**判据**：**`*sql.DB` 应该在应用启动时创建一次，全局共享**。不要每次请求 `sql.Open` 再 `Close`——那会反复建池、反复握手。

**边界**：`database/sql` **只提供抽象层**，不含任何具体数据库的驱动。驱动通过空白导入注册自己（[01-语言核心/11](../01-语言核心/11-包与可见性.md) 的 `init()`）：

```go
import _ "modernc.org/sqlite"     // 注册驱动名 "sqlite"
```

## 机制

### 连接池的三个旋钮

```console
$ go run .
MaxOpenConns=10 MaxIdleConns=5
```

```go
db.SetMaxOpenConns(10)              // 最大同时打开的连接数
db.SetMaxIdleConns(5)               // 池里保留的空闲连接数
db.SetConnMaxLifetime(time.Hour)    // 单个连接的最长存活时间
db.SetConnMaxIdleTime(10*time.Minute) // 空闲多久后关闭
```

| 参数 | 默认值 | 不设的后果 |
|---|---|---|
| `MaxOpenConns` | **0（无限制）** | 高并发下连接数暴涨，打爆数据库 |
| `MaxIdleConns` | **2** | 并发稍高就反复建连接 |
| `ConnMaxLifetime` | **0（无限）** | 连接永不重建，遇到数据库端的连接超时或负载均衡切换时出问题 |
| `ConnMaxIdleTime` | 0 | 空闲连接一直占着 |

**约束**：`MaxOpenConns` 默认是**无限制**——生产环境必须设。它的合理值取决于数据库的最大连接数除以实例数，**不是越大越好**（数据库端的连接是稀缺资源）。

`ConnMaxLifetime` 的意义是**应对连接失效**：云数据库的负载均衡会定期断开长连接，连接池如果保留它们，下次使用就会拿到死连接。设一个小于负载均衡超时的值（通常 5–30 分钟）能让池子主动换新。

**边界**：**这些旋钮只影响池，不影响单次查询**。`SetMaxOpenConns(1)` 会让所有操作串行化——这是测试时的有用手段，生产上会成瓶颈。

### 查询的三种形态

| 方法 | 返回 | 用途 |
|---|---|---|
| `db.Exec` | `sql.Result`（`LastInsertId`/`RowsAffected`） | INSERT/UPDATE/DELETE |
| `db.QueryRow` | `*sql.Row`（`.Scan` 一次） | **确定只有一行** |
| `db.Query` | `*sql.Rows`（`.Next` 循环） | 多行 |

```console
$ go run .
LastInsertId=1 RowsAffected=1
QueryRow: {ID:1 Name:张三 Email:{String:z@example.com Valid:true}} err=<nil>
```

**约束**：**`*sql.Rows` 必须 `Close()`**，否则连接不会归还池子。惯用写法是 `defer rows.Close()`，**且在循环结束后检查 `rows.Err()`**：

```go
rows, err := db.QueryContext(ctx, sql)
if err != nil { return err }
defer rows.Close()
for rows.Next() {
	if err := rows.Scan(&a, &b); err != nil { return err }
}
return rows.Err()      // ← 容易漏掉
```

`rows.Next()` 返回 `false` 可能是"正常结束"也可能是"中途出错"——**只有 `rows.Err()` 能区分**。

**`QueryRow` 的错误延迟到 `Scan`**——`QueryRow` 本身不返回 error，错误在 `Scan` 时出来。

### 空值：`sql.NullString`

```console
$ go run .
可空列: email.Valid=false email.String=""
```

**数据库的 `NULL` 与 Go 的零值不是一回事**。`Scan` 到 `string` 时遇到 `NULL` 会报错（`converting NULL to string is unsupported`），必须用 `sql.NullString` 这类包装：

| 类型 | 字段 |
|---|---|
| `sql.NullString` | `String` + `Valid` |
| `sql.NullInt64` | `Int64` + `Valid` |
| `sql.NullTime` | `Time` + `Valid` |
| `sql.Null[T]`（**Go 1.22+**） | 泛型版本 |

**约束**：`Valid == false` 时其他字段是零值，**不能直接用**。Go 1.22 起有了泛型版本 `sql.Null[T]`，`sql.Null[string]` 等价于 `sql.NullString`。

### `sql.ErrNoRows`

```console
$ go run .
查不到: err=sql: no rows in result set  errors.Is(ErrNoRows)=true
```

`QueryRow(...).Scan(...)` 在**没有行**时返回 `sql.ErrNoRows`——这是**哨兵错误**（[01-语言核心/10](../01-语言核心/10-错误处理.md)），用 `errors.Is` 判断。

**约束**：**`ErrNoRows` 通常不是错误**，而是"查无此记录"的正常结果。把它当成 500 返回是常见的 API 设计错误：

```go
err := db.QueryRowContext(ctx, q, id).Scan(&u.ID, &u.Name)
if errors.Is(err, sql.ErrNoRows) {
	return nil, ErrUserNotFound    // 转成业务错误，映射到 404
}
if err != nil {
	return nil, err                 // 真错误，映射到 500
}
```

### 事务

```console
$ go run .
事务提交 err: <nil>
总行数: 3
回滚后总行数: 3
```

```go
tx, err := db.BeginTx(ctx, nil)
if err != nil { return err }
defer tx.Rollback()          // ← 惯用法：已提交时 Rollback 是空操作
...
return tx.Commit()
```

**`defer tx.Rollback()` 是标准写法**——它在函数提前返回（panic 或错误）时回滚，在已 `Commit` 的情况下返回 `sql.ErrTxDone`（无害，可以忽略）。**这样写就不会漏掉回滚路径**。

**约束**：**事务必须用同一个连接**。`tx.Query` 用的是事务绑定的连接，**不要在事务内用 `db.Query`**——那是池里另一个连接，看不到事务里未提交的修改。

**边界**：`database/sql` **不提供嵌套事务**。需要保存点（savepoint）要自己发 SQL（`SAVEPOINT`/`ROLLBACK TO`）。事务的隔离级别通过 `BeginTx(ctx, &sql.TxOptions{Isolation: ...})` 设置，但**具体支持程度取决于驱动与数据库**。

### SQL 注入：参数化是唯一解

```console
$ go run .
参数化插入注入串后 err=<nil> 表还在，行数=4
```

插入 `x'; DROP TABLE users; --` 之后**表还在，行数正常增加**——因为 `?` 占位符让驱动把它当作**数据**而不是 SQL 片段。

**约束**：**永远不要用字符串拼接构造 SQL**：

```go
// ❌ 注入漏洞
db.Query("SELECT * FROM users WHERE name = '" + name + "'")

// ✅ 参数化
db.Query("SELECT * FROM users WHERE name = ?", name)
```

**边界**：**占位符不能用于标识符**（表名、列名）。`SELECT * FROM ?` 是无效的——参数只能是值。需要动态表名时必须用**白名单**校验，不能靠参数化。

不同数据库的占位符不同（SQLite/MySQL 用 `?`，PostgreSQL 用 `$1`，Oracle 用 `:1`），`database/sql` **不做转换**——写跨数据库代码时这是必须处理的差异。

### 与 `context` 集成

```go
db.QueryContext(ctx, q)
db.ExecContext(ctx, q)
db.QueryRowContext(ctx, q)
```

**所有方法都有 `Context` 版本**，且**必须用它们**。`ctx` 取消时驱动会尝试中断查询（具体能力取决于驱动——`database/sql` 本身只是把 `ctx.Done()` 接进来）。

**约束**：`ctx` 取消**不保证数据库端真的停止了执行**——它只是让 Go 侧不再等待。要真正取消长查询需要数据库支持（PostgreSQL 的 cancel request、MySQL 的 `KILL QUERY`）。

### ORM 与查询构建器

| 方案 | 定位 |
|---|---|
| **`database/sql`** | 标准库，手写 SQL |
| `sqlx` | `database/sql` 的薄封装（`StructScan` 自动映射字段） |
| **GORM** | 全功能 ORM（模型定义、迁移、关联、钩子） |
| `sqlc` | **从 SQL 生成 Go 代码**（不是运行时 ORM） |

**判据**（Go 社区的普遍立场）：**先考虑 `database/sql` + 手写 SQL**。ORM 在 Go 里不如在 Java 里受欢迎，原因是 Go 的 struct 与 SQL 结果集映射本身就很简单（`Scan` 一行），而 ORM 引入的隐式行为（N+1 查询、意外的全表更新、难懂的生成 SQL）在 Go 的显式哲学下显得格格不入。

**`sqlc` 是近年最受认可的中间路线**——它读你的 SQL 文件，生成类型安全的 Go 函数。SQL 还是你写的（可读、可优化），类型检查由生成代码保证。

**与其它语言对照**：

| | 连接管理 | 参数占位符 | 结果映射 |
|---|---|---|---|
| Java JDBC | `DataSource` / 连接池库（HikariCP） | `?`（位置） | `ResultSet` 手动 / ORM |
| Python DB-API | 连接对象（需自己池化） | `%s` / `?` / `:name` | 元组 / ORM |
| **Go** | **`*sql.DB` 自带连接池** | **驱动相关** | **`Scan` 手动 / sqlx / sqlc** |

**Go 把连接池内置了**——Java 要引 HikariCP、Python 要引 SQLAlchemy 的 pool 或自己写。这是"标准库是生产级的"（[00-概览/01](../00-概览/01-Go全景.md)）在数据库这一层的体现。

**代价是 `Scan` 的手工映射**：Go 没有反射式的结果集自动映射（`sqlx` 用反射补上了），每个查询都要写 `Scan(&a, &b, &c)`。**列顺序或类型改动时是编译期还是运行期发现**——`Scan` 是运行期，这正是 `sqlc` 想解决的问题。
