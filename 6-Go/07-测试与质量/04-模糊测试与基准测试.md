# 模糊测试与基准测试

> 前置：[03-集成测试](./03-集成测试.md) · 后续：无（本目录终篇）

> **版本基准**：Go 1.27（stable = latest）。本篇示例实测环境：go1.27.1 windows/amd64，Intel i7-10750H（6 核 12 线程）。

## 本质

**模糊测试（fuzzing）与基准测试（benchmark）是 `go test` 的两种函数形态**，与 `TestXxx` 并列：

| 前缀 | 签名 | 做什么 |
|---|---|---|
| `Test` | `func(t *testing.T)` | 验证正确性 |
| `Benchmark` | `func(b *testing.B)` | **测量性能** |
| `Fuzz` | `func(f *testing.F)` | **用随机输入找 bug** |

**约束的由来**：把三种测试放进同一个 `go test` 命令，是"工具链是一个二进制"（[06-工程与工具链/01](../06-工程与工具链/01-go命令详解.md)）的又一处体现。Java 里 JMH（基准）与 jqwik（模糊）是两个独立框架，各有自己的运行器。

**边界**：`Benchmark` 与 `Fuzz` **默认都不运行**——`go test` 只跑 `Test`。要跑基准加 `-bench`，要跑模糊加 `-fuzz`。

## 机制

### 模糊测试：用随机输入找不变量违反

```go
func FuzzReverseBad(f *testing.F) {
	f.Add("hello")
	f.Add("世界")
	f.Add("")

	f.Fuzz(func(t *testing.T, s string) {
		r := ReverseBad(s)
		if ReverseBad(r) != s {
			t.Fatalf("反转两次不还原: %q -> %q -> %q", s, r, ReverseBad(r))
		}
		if utf8.RuneCountInString(r) != utf8.RuneCountInString(s) {
			t.Fatalf("rune 数变了: %q(%d) -> %q(%d)",
				s, utf8.RuneCountInString(s), r, utf8.RuneCountInString(r))
		}
	})
}
```

**`f.Add(...)` 是种子语料**——明确的、应当被测试的输入。**`f.Fuzz(...)` 里的函数会在种子 + 随机变异输入上反复执行**。

```console
$ go test -run=^$ -fuzz=FuzzReverseBad -fuzztime=10s .
failure while testing seed corpus entry: FuzzReverseBad/seed#1
--- FAIL: FuzzReverseBad (0.25s)
    --- FAIL: FuzzReverseBad (0.00s)
        fuzz_test.go:61: rune 数变了: "世界"(2) -> "\x8c\x95疸\xe4"(4)
```

**失败来自种子 `seed#1`（就是 `f.Add("世界")`）**——`ReverseBad` 按字节反转，把一个 UTF-8 三字节字符拆开了。**这条说明了种子语料的价值**：好的种子立刻暴露 bug，不需要等随机变异。

**约束**：模糊测试**必须写成"检查不变量"而不是"检查具体输出"**——随机输入下无法预知输出，但"反转两次应当还原""runes 数不变""序列化再反序列化应当相等"这类**性质**是恒定的。

**判据**：好的模糊目标应当满足：

1. **不变量明确**（round-trip、幂等、单调性、边界）
2. **输入空间小**（参数尽量少——每个额外参数都会让搜索空间指数膨胀）
3. **执行快**（`Fuzz` 函数会被调用百万次）

**边界**：`Fuzz` 函数的参数类型只能是 `string`、`[]byte`、`int`/`int8`/.../`uint64`、`float32`/`float64`、`bool` 以及它们的切片。**不支持自定义 struct**——要模糊一个 struct 得先把它编码成字节再解码。

### 模糊测试的语料与缓存

```console
$ go test -run=^$ -fuzz=FuzzSplitFirst -fuzztime=5s .
fuzz: elapsed: 0s, gathering baseline coverage: 0/4 completed
fuzz: elapsed: 0s, gathering baseline coverage: 4/4 completed, now fuzzing with 12 workers
fuzz: elapsed: 3s, execs: 907586 (302290/sec), new interesting: 0 (total: 4)
fuzz: elapsed: 5s, execs: 1576558 (318794/sec), new interesting: 0 (total: 4)
PASS
```

**5 秒跑了 157 万次，约 32 万次/秒**（12 个 worker 并行，等于 `GOMAXPROCS`）。

| 概念 | 位置 | 说明 |
|---|---|---|
| **种子语料** | 测试文件里的 `f.Add` | **应当提交到版本库** |
| **生成的语料** | **`$GOCACHE/fuzz`** | 不提交，本地缓存 |
| **失败的输入** | `$GOCACHE/fuzz`（自动保存） | 重跑时会自动复现 |

**约束**：**失败的输入会被自动保存并永久复现**——重跑 `go test -run=FuzzReverseBad` 时，Go 会先跑缓存的失败输入，因此 bug 不会"消失"。

```console
$ go test -run=FuzzReverseBad .
--- FAIL: FuzzReverseBad (0.00s)
    --- FAIL: FuzzReverseBad/seed#1 (0.00s)
```

**要提交的语料必须手工放进 `testdata/fuzz/<FuzzName>/`**——从 `$GOCACHE` 里复制过去。这样团队其他成员与 CI 都能复现。

**约束**：`-fuzztime` 默认是**无限**（一直跑到失败或手动中断）。**CI 里必须设时间上限**。

### 基准测试：正确写法

```console
$ go test -bench=. -benchmem -run=^$
BenchmarkIndex-12         	177257978	         6.837 ns/op	       0 B/op	       0 allocs/op
BenchmarkStringsCut-12    	180079161	         8.101 ns/op	       0 B/op	       0 allocs/op
BenchmarkSprintf-12       	28641189	        40.91 ns/op	       8 B/op	       1 allocs/op
BenchmarkAdd-12           	1000000000	         0.3353 ns/op	       0 B/op	       0 allocs/op
```

**`-run=^$` 是必加的**——它让 `go test` **跳过所有 `Test` 函数**（正则 `^$` 匹配空名字），只跑基准。不加的话会先跑完所有测试，浪费时间。

| 列 | 含义 |
|---|---|
| `-12` | `GOMAXPROCS` |
| `ns/op` | 每次操作耗时 |
| `B/op` | **每次操作的堆分配字节数** |
| `allocs/op` | **每次操作的堆分配次数** |

**约束**：**被测结果必须被使用**，否则编译器会优化掉整段代码：

```go
var sink string                      // 包级变量

func BenchmarkX(b *testing.B) {
	for i := 0; i < b.N; i++ {
		sink = Build(n)              // 赋值给包级变量，无法被优化掉
	}
}
```

**这是基准测试最常见的错误**——写成 `_ = Build(n)` 时，如果 `Build` 是纯函数且无副作用，编译器可能整个删掉。

**`b.N` 是框架自动调整的**——它先小规模试跑，估算出合适的迭代次数，让总耗时落在 1 秒左右（`-benchtime` 可改）。

### 基准测试的常见陷阱

| 陷阱 | 表现 | 解法 |
|---|---|---|
| **结果被优化掉** | ns/op 异常小（0.0001） | 赋值给包级变量 |
| **setup 计入耗时** | 数据准备占了大部分 | `b.ResetTimer()` |
| **循环内分配被测数据** | 测的是构造而非被测逻辑 | 在循环外构造 |
| **编译器内联** | 被测函数被内联，测的不是真实调用 | `//go:noinline` 或接受现实 |
| **只跑一次** | 结果波动大 | `-count=5` 取统计 |

```go
func BenchmarkWithSetup(b *testing.B) {
	data := generateLargeData()     // 昂贵的准备
	b.ResetTimer()                  // ← 从这里开始计时
	for i := 0; i < b.N; i++ {
		process(data)
	}
}
```

**约束**：**基准测试的结果波动可以很大**——GC、CPU 频率调节、其他进程都会影响。**`-count=5` 跑多次，看分布而不是单个数字**：

```console
$ go test -bench=BenchmarkX -count=5 -benchmem ./...
```

**`benchstat`**（`golang.org/x/perf/cmd/benchstat`）是比较两组基准结果的官方工具——它做统计检验，告诉你是"真的变快了"还是"噪声"。

### 性能回归门禁

**把基准测试接进 CI** 能防止性能悄悄退化：

```bash
# 1. 在基线 commit 上跑
git stash && go test -bench=. -count=10 ./... > old.txt
# 2. 在当前 commit 上跑
git stash pop && go test -bench=. -count=10 ./... > new.txt
# 3. 比较
benchstat old.txt new.txt
```

**约束**：**CI 机器的噪声会让门禁误报**——共享 runner 上的 CPU 争用足以造成 10% 以上的波动。**判据**：只对**超过阈值（如 20%）且统计显著**的退化报警，且只在**专用 runner** 上跑。

**边界**：**不是所有代码都值得基准测试**——只给**热路径**写。判断热路径靠 [03-运行时与内存/07](../03-运行时与内存/07-性能剖析与调优.md) 的 pprof，不是靠猜。

### 覆盖率与质量门禁

| 指标 | 能说明 | 不能说明 |
|---|---|---|
| 语句覆盖率 | 代码被执行过 | **断言是否正确** |
| 分支覆盖率 | 每个 `if` 两边都走过 | 边界值是否测了 |
| **模糊测试运行时长** | 输入空间探索了多久 | — |
| **基准回归** | 性能是否退化 | — |

**约束**：**覆盖率不应当作为硬性门禁**。把覆盖率设成"必须 80%"会导致两种反效果：写无断言的测试刷覆盖率；或者把难测的代码标记成忽略。

**判据**：覆盖率**作为趋势指标**（"这个 PR 让覆盖率从 75% 掉到 70%"值得问一句），而不是**作为通过条件**。

**与其它语言对照**：

| | 基准测试 | 模糊测试 |
|---|---|---|
| Java | **JMH**（第三方，需专门 harness） | jqwik / Jazzer |
| Python | `timeit` / pytest-benchmark | Atheris / Hypothesis |
| C++ | Google Benchmark / Catch2 | libFuzzer（**需手动接入**） |
| **Go** | **`BenchmarkXxx`（内置）** | **`FuzzXxx`（1.18 起内置）** |

**Go 是唯一两者都内置的**。C++ 的 libFuzzer 是成熟工具但要手工编译链接、写 `LLVMFuzzerTestOneInput` 入口；Java 的 JMH 需要 `@Benchmark` 注解 + 专门的 runner + 处理 JIT 预热。

**内置带来的差别是使用频率**——当写基准测试的成本是"加一个 10 行的 `BenchmarkXxx` 函数"，开发者就会真的去量；当成本是"配 JMH 的依赖、写 harness、处理预热"，多数人就不量了。**这也是 Go 社区"先测量再优化"这条纪律能落地的基础**（[03-运行时与内存/07](../03-运行时与内存/07-性能剖析与调优.md)）。
