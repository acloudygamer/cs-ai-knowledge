# 测试基础

> 前置：[01-语言核心](../01-语言核心/)、[06-工程与工具链](../06-工程与工具链/) · 后续：[02-单元测试与mock](./02-单元测试与mock.md)

> **版本基准**：Go 1.27（stable = latest）。本篇示例实测环境：go1.27.1 windows/amd64。

## 本质

**Go 的测试不是框架，是语言与工具链的约定。**

三条约定构成全部基础：

| 约定 | 内容 |
|---|---|
| 文件名 | 必须以 `_test.go` 结尾 |
| 函数签名 | `func TestXxx(t *testing.T)`（基准是 `BenchmarkXxx(b *testing.B)`，模糊是 `FuzzXxx(f *testing.F)`） |
| 运行方式 | `go test`（与 `go build` 同一个二进制，[06-工程与工具链/01](../06-工程与工具链/01-go命令详解.md)） |

**约束的由来**：`_test.go` 文件**不参与正常构建**——`go build` 会跳过它们，`go test` 才会编译。因此**测试代码可以 import 测试专用的依赖**，不会污染产物的依赖闭包。

**边界**：Go **没有断言库、没有 mock 框架、没有测试运行器**（标准库不提供）。这不是缺失——`t.Errorf` 就是全部断言机制，mock 靠接口（[01-语言核心/08](../01-语言核心/08-接口.md)）手写。第三方库（testify、gomock）存在，但**标准库的极简约定足够覆盖绝大多数场景**。

## 机制

### 表驱动测试

```go
func TestAddTable(t *testing.T) {
	tests := []struct {
		name string
		a, b int
		want int
	}{
		{"正数", 1, 2, 3},
		{"负数", -1, -2, -3},
		{"零", 0, 0, 0},
		{"大数", 1 << 40, 1 << 40, 1 << 41},
	}
	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {
			if got := Add(tt.a, tt.b); got != tt.want {
				t.Errorf("Add(%d,%d) = %d, 期望 %d", tt.a, tt.b, got, tt.want)
			}
		})
	}
}
```

```console
$ go test -v ./...
=== RUN   TestAddTable
=== RUN   TestAddTable/正数
=== RUN   TestAddTable/负数
=== RUN   TestAddTable/零
=== RUN   TestAddTable/大数
--- PASS: TestAddTable (0.00s)
    --- PASS: TestAddTable/正数 (0.00s)
    --- PASS: TestAddTable/负数 (0.00s)
    --- PASS: TestAddTable/零 (0.00s)
    --- PASS: TestAddTable/大数 (0.00s)
```

**表驱动是 Go 测试的默认形态**——用 `t.Run` 把每个用例变成**子测试**，好处是：

- 输出里能看到**哪个用例**失败（`TestAddTable/负数`）
- 单个用例可以用 `go test -run 'TestAddTable/负数'` 单独跑
- 加用例只需在表里加一行

**约束**：子测试的 `t.Run` 里的闭包捕获 `tt`——Go 1.22 起循环变量每轮新建（[01-语言核心/05](../01-语言核心/05-函数.md)），因此不需要 `tt := tt`。**但在 1.22 之前这是必需的**，老代码里会看到。

### 断言：`t.Error` 与 `t.Fatal`

| 方法 | 行为 |
|---|---|
| `t.Errorf` / `t.Error` | **记录失败，继续执行** |
| `t.Fatalf` / `t.Fatal` | **记录失败，立刻终止当前测试函数** |

**判据**：**能继续的用 `Error`，继续下去没意义的用 `Fatal`**。

```go
got, err := Div(10, 2)
if err != nil {
	t.Fatal(err)          // err != nil 时 got 无意义，继续没价值
}
if got != 5 {
	t.Errorf("Div(10,2) = %d", got)
}
```

**约束**：**`t.Fatal` 必须在测试函数自己的 goroutine 里调用**——它在别的 goroutine 里调用只会终止那个 goroutine，测试会挂起。`go vet` 的 `testinggoroutine` 分析器检查这个（[06-工程与工具链/01](../06-工程与工具链/01-go命令详解.md)）。

### `t.Helper`：让报错指向调用方

```go
func TestWithHelper(t *testing.T) {
	assertEqual(t, Add(2, 3), 5)
}

func assertEqual(t *testing.T, got, want int) {
	t.Helper()             // ← 关键
	if got != want {
		t.Errorf("got %d, want %d", got, want)
	}
}
```

**没有 `t.Helper()` 时，报错行号指向 `assertEqual` 内部的 `t.Errorf`**——那对排查毫无帮助。加了之后，Go 会把这一帧从堆栈里略去，**行号指向调用 `assertEqual` 的那一行**。

**约束**：**所有测试辅助函数都该调用 `t.Helper()`**。这是零成本的，但漏掉会让失败信息失去价值。

### 并行测试

```console
$ go test -v ./...
=== RUN   TestIsEven
=== PAUSE TestIsEven
=== RUN   TestIsEven/#00
=== PAUSE TestIsEven/#00
...
=== CONT  TestIsEven/#00
=== CONT  TestIsEven/#09
```

`t.Parallel()` 让测试**暂停**（`PAUSE`），等所有并行测试都注册完再一起**恢复**（`CONT`）。

**约束**：`t.Parallel()` **必须是被测函数的第一条语句**（在 `t.Run` 里则要放在闭包开头），否则调度不生效。且**并行测试不能共享可变状态**——它们会同时跑（[04-并发/05](../04-并发/05-并发模式与竞态诊断.md) 的 `-race` 就是查这个）。

**边界**：并行度由 `-parallel` 控制（默认等于 `GOMAXPROCS`）。**`t.Parallel()` 的价值在 I/O 密集的测试上**——纯 CPU 的测试并行不会更快。

### 测试缓存

```console
$ go test ./...
ok  	tst	(cached)
$ go test -count=1 ./...
ok  	tst	0.314s
```

**Go 会缓存测试结果**——如果源码、依赖、测试标志都没变，直接返回上次的结果（输出里带 `(cached)`）。

**约束**：`-count=1` 强制重跑。**在 CI 里通常加它**——虽然缓存理论上不会出错，但"看到真实执行时间"对排查性能问题有用。缓存失效的条件包括：源码变了、依赖变了、环境变量变了、命令行标志变了。

### 覆盖率

```console
$ go test -cover ./...
ok  	tst	0.405s	coverage: 100.0% of statements

$ go test -coverprofile=cover.out ./... && go tool cover -func=cover.out
tst/calc.go:7:	Add		100.0%
tst/calc.go:9:	Div		100.0%
tst/calc.go:16:	IsEven		100.0%
total:		(statements)	100.0%
```

`go tool cover -func` 给出**逐函数的覆盖率**，比单个百分比有用得多——它指出**哪个函数没被测到**。

| 标志 | 作用 |
|---|---|
| `-cover` | 打印覆盖率 |
| `-coverprofile=f` | 输出到文件 |
| `-coverpkg=./...` | **跨包统计**（不加只统计被测试包自身） |
| `-covermode=atomic` | 并发安全（配合 `-race`） |
| `go tool cover -html=f` | 浏览器里看哪些行被覆盖 |

**约束**：**`-coverpkg` 不加的话覆盖率会虚高**——一个测试如果调用了别的包的代码，那些代码不计入分母。做整体质量统计必须加它。

### 测试的组织

| 类型 | 写法 | 位置 |
|---|---|---|
| **白盒测试** | `package foo`（与被测同包） | 同目录 |
| **黑盒测试** | `package foo_test` | 同目录 |

**判据**：**默认用黑盒（`foo_test`）**——它只能访问导出符号，因此测试的是**公开 API 契约**。需要测非导出函数时才用白盒。

**约束**：同一个目录里**可以同时有 `package foo` 和 `package foo_test` 的测试文件**——Go 会把它们编译成两个包。这让"大部分测试用黑盒、少数需要探入内部的用白盒"成为可能。

**边界**：黑盒测试不能测试非导出函数。如果一个非导出函数复杂到需要单独测试，**说明它应该被提取成一个独立包**——这反过来成了拆包的信号（[06-工程与工具链/04](../06-工程与工具链/04-项目布局.md)）。

### `testdata/` 目录

**`testdata/` 是 Go 工具链识别的目录名**——`go build`/`go test`/`go vet` 都会跳过它（[06-工程与工具链/04](../06-工程与工具链/04-项目布局.md)）。

**用途**：放测试固件（输入文件、期望输出、测试数据库）。测试里用相对路径 `testdata/xxx` 访问——`go test` 会把工作目录设为被测包所在目录。

**约束**：**不要用绝对路径或 `../`** ——`go test` 的工作目录就是包目录，相对路径 `testdata/` 直接可用。

**与其它语言对照**：

| | 测试框架 | 断言 | 运行器 |
|---|---|---|---|
| Java | JUnit 5（**必须引依赖**） | `assertEquals` | Maven Surefire |
| Python | pytest / unittest | `assert` | pytest |
| JavaScript | Jest / Vitest | `expect()` | npm scripts |
| **Go** | **无（语言约定）** | **`if got != want { t.Errorf }`** | **`go test`（内置）** |

**Go 是唯一"不需要测试框架"的**——`_test.go` + `TestXxx` + `go test` 三样就够了，全部内置。**代价是没有断言 DSL**：Java 的 `assertEquals(expected, actual)` 输出漂亮的 diff，Go 里要自己写格式串。

**这个取舍与 Go 的整体设计一致**：**宁可多写几行，不要引入框架**。一个 Go 项目的 `go.mod` 里通常只有 2–5 个直接依赖，而一个等规模的 Java 项目可能有 20 个。
