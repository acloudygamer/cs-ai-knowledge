# 集成测试

> 前置：[02-单元测试与mock](./02-单元测试与mock.md) · 后续：[04-模糊测试与基准测试](./04-模糊测试与基准测试.md)

> **版本基准**：Go 1.27（stable = latest）。本篇示例实测环境：go1.27.1 windows/amd64，Intel i7-10750H（6 核 12 线程），驱动 `modernc.org/sqlite v1.59.0`。

## 本质

**集成测试测的是"多个部件接起来对不对"**——与单元测试的分界是**是否跨越了真实边界**。

| | 单元测试 | 集成测试 |
|---|---|---|
| 依赖 | **假实现**（mock/fake） | **真实**（数据库、网络、文件系统） |
| 速度 | 毫秒级 | 秒级到分钟级 |
| 失败原因 | 逻辑错 | 逻辑错 **或** 接线错 |
| 运行时机 | 每次保存 | **提交前 / CI** |

**约束的由来**：单元测试用 mock 换来了速度与稳定，但**mock 测不出接线错误**——接口签名对了但 SQL 写错、HTTP 路径拼错、事务隔离级别设错，这些 mock 全都看不见。

**判据**：**单元测试覆盖分支，集成测试覆盖接线**。两者不替代——只有集成测试会发现"`QueryRow` 的列顺序和 `Scan` 的参数顺序不一致"这类问题。

## 机制

### `//go:build integration`：把集成测试隔离出去

```console
$ go test ./...
?   	int1	[no test files]
```

**不带 tag 时，整个集成测试文件被排除**——`go test` 报告"没有测试文件"。

```console
$ go test -tags=integration -v ./...
=== RUN   TestCreateAndGet
    integration_test.go:55: 创建成功 id=1
    integration_test.go:66: 读回成功 name=张三
    integration_test.go:74: 404 分支正确
--- PASS: TestCreateAndGet (0.00s)
=== RUN   TestBadRequest
--- PASS: TestBadRequest (0.00s)
PASS
ok  	int1	0.103s
```

**约束的由来**：集成测试需要真实依赖（数据库、网络），在开发机上不一定可用。用 build tag 隔离，让 `go test ./...` 保持"永远能跑、永远快"。

**约束**：`//go:build` 注释**必须在文件最前面**，且**后面要空一行**再接 `package`。写成 `//go:build integration` 之后直接接 `package` 会报错。

**边界**：`//go:build` 是 Go 1.17 起的唯一形式，`// +build` 是旧语法。`go vet` 的 `buildtag` 分析器会检查格式（[06-工程与工具链/01](../06-工程与工具链/01-go命令详解.md)）。

### `TestMain`：包级 setup 与 teardown

```go
func TestMain(m *testing.M) {
	db, err := sql.Open("sqlite", ":memory:")
	if err != nil {
		fmt.Fprintln(os.Stderr, "打开数据库失败:", err)
		os.Exit(1)
	}
	if _, err := db.Exec(`CREATE TABLE items (...)`); err != nil {
		fmt.Fprintln(os.Stderr, "建表失败:", err)
		os.Exit(1)
	}
	testDB = db

	code := m.Run()      // ← 运行所有测试

	db.Close()
	os.Exit(code)        // ← 必须用 os.Exit，不能用 return
}
```

**`TestMain` 是包级的入口**——每个测试包最多一个。它替代了"每个测试各自建连接"的重复。

**三条约束**：

1. **必须调用 `m.Run()`**——不调用则所有测试都不执行。
2. **必须用 `os.Exit(code)` 退出**，不能 `return`——`return` 会让 `TestMain` 正常返回，但测试结果不会被正确上报。
3. **setup 失败要 `os.Exit(1)`**——直接 `panic` 也行，但 `os.Exit` 更明确。

**边界**：`TestMain` 只在**当前包**生效。跨包的共享 setup 要靠 `TestMain` 调用一个共享的 helper，或者用 `testing.Short()` 做条件跳过。

### `testing.Short()`：让长测试可跳过

```go
func TestSlowIntegration(t *testing.T) {
	if testing.Short() {
		t.Skip("短模式跳过集成测试")
	}
	// 需要真实数据库的测试
}
```

```console
$ go test -short ./...      # 跳过
$ go test ./...             # 全跑
```

**判据**：`-short` 与 build tag 解决同一问题的两个粒度——

| | `-short` | `//go:build integration` |
|---|---|---|
| 粒度 | **单个测试** | **整个文件** |
| 编译 | 总是编译 | **不编译**（快） |
| 适合 | 少数慢测试 | 大量依赖外部服务的测试 |

**约束**：`-short` 的测试**仍然会被编译**——如果它 import 了需要 cgo 的驱动，在 `CGO_ENABLED=0` 的环境里会编译失败。**这种情况必须用 build tag**。

### 真实 HTTP 往返

```go
srv := httptest.NewServer(NewMux(&Store{db: testDB}))
defer srv.Close()

resp, err := srv.Client().Post(srv.URL+"/items", "application/json",
	bytes.NewBufferString(`{"name":"张三"}`))
```

**`httptest.NewServer` 起的是真实的 HTTP 服务**——经过真实的 TCP、真实的 `net/http` 编解码、真实的路由匹配。**唯一被替换的是依赖（数据库）**。

**约束**：`defer srv.Close()` **应当用 `t.Cleanup(srv.Close)`**——在子测试里 `defer` 会在子测试函数返回时执行，而 `t.Cleanup` 会累积到测试结束（[02-单元测试与mock](./02-单元测试与mock.md)）。

**边界**：`httptest.NewServer` 只监听 `127.0.0.1`，**测不到跨主机的行为**（DNS、TLS 证书、负载均衡）。要测这些必须用真实环境或容器。

### 数据库集成测试的三种做法

| 做法 | 优点 | 缺点 |
|---|---|---|
| **内存数据库**（SQLite `:memory:`） | **快、无需外部服务** | 与生产数据库的 SQL 方言不同 |
| **容器**（testcontainers-go） | **与生产同款** | 需要 Docker，启动慢 |
| **共享测试实例** | 快 | 测试间互相污染，需清理 |

上面的实测用的是**第一种**——`sql.Open("sqlite", ":memory:")` + `TestMain` 建表。它的价值是**能测到 SQL 语法与列映射**（mock 测不到这些），代价是 SQLite 与 PostgreSQL/MySQL 的差异（`AUTOINCREMENT` vs `SERIAL`、`?` vs `$1`）。

**判据**：**内存数据库覆盖日常，容器覆盖发布前**。日常提交跑 SQLite 版（快），CI 的发布流水线跑容器版（准）。

**约束**：`:memory:` 的 SQLite **每个连接是独立的数据库**——`database/sql` 是连接池（[05-IO与外部世界/04](../05-IO与外部世界/04-数据库访问.md)），多个连接会看到不同的内存库。必须设 `db.SetMaxOpenConns(1)`，或者用共享缓存模式 `file::memory:?cache=shared`。

**本机未实测容器方案**——写作环境无 Docker。

### 容器化测试

```go
import "github.com/testcontainers/testcontainers-go"

func TestWithPostgres(t *testing.T) {
	ctx := context.Background()
	pg, err := postgres.Run(ctx, "postgres:17-alpine",
		postgres.WithDatabase("test"),
		postgres.WithUsername("test"),
		postgres.WithPassword("test"),
	)
	if err != nil { t.Fatal(err) }
	defer pg.Terminate(ctx)

	dsn, _ := pg.ConnectionString(ctx, "sslmode=disable")
	db, _ := sql.Open("pgx", dsn)
	...
}
```

**约束**：容器方案**需要 Docker 守护进程**，且在 CI 里要注意镜像拉取时间（**预热镜像或缓存**）。启动一个 PostgreSQL 容器通常要 2–5 秒。

**边界**：**不要用 `docker-compose` 起测试依赖再跑测试**——那要求 CI 脚本与测试代码协调，容易出现"测试跑得比容器启动快"的竞态。`testcontainers` 把生命周期管在测试代码里，避免了这个问题。

### 测试数据的隔离

| 策略 | 做法 | 适合 |
|---|---|---|
| **每个测试独立事务** | `tx := db.Begin()` + `defer tx.Rollback()` | 单表操作 |
| **每次重建 schema** | `TestMain` 里 drop + create | 小库 |
| **唯一前缀** | 数据带随机前缀，按前缀清理 | 大库 |
| **并行 schema** | 每个测试一个 schema/database | 高并发测试 |

**约束**：**集成测试的并行必须显式处理数据隔离**——两个测试同时往同一张表插数据会互相干扰。`t.Parallel()` 在集成测试里要慎用。

**判据**：**"每个测试独立事务"是最干净的方案**——测试结束 `Rollback`，数据自然消失，不需要清理代码。**但它测不了"提交后"的行为**（触发器、约束在提交时才生效的场景）。

### 集成测试的运行时机

| 时机 | 跑什么 |
|---|---|
| 保存文件 | 单元测试（`go test -short ./...`） |
| **提交前**（pre-commit hook） | 单元测试 + 快速集成测试 |
| **CI 的每个 PR** | 全部（含 `-race`，见 [04-并发/05](../04-并发/05-并发模式与竞态诊断.md)） |
| **发布前** | 全部 + 端到端 |

**约束**：**集成测试的稳定性（flakiness）是它最大的敌人**。依赖真实网络/容器的测试会因为超时、端口占用、镜像拉取失败而随机失败。**重试机制是必要的**——但要记录重试次数，频繁重试说明测试本身有问题。

**与其它语言对照**：

| | 隔离机制 | 容器方案 |
|---|---|---|
| Java | Maven profile / `@Tag` | Testcontainers（**Java 是它的发源地**） |
| Python | pytest marker（`@pytest.mark.integration`） | testcontainers-python |
| **Go** | **build tag** | testcontainers-go |

**Go 的 build tag 是编译期隔离**——被排除的文件**根本不参与编译**。Python 的 pytest marker 是运行期跳过，文件仍被 import（如果 import 了不存在的包，收集阶段就失败）。**Go 的方式更彻底**，代价是切换需要重新编译。

**Testcontainers 是 Java 生态发明的**（2015），后来移植到各语言。它解决的核心问题是"**测试依赖的生命周期管理**"——把容器的启动、就绪等待、清理都封装进测试代码，而不是靠外部脚本协调。
