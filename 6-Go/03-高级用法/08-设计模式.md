# Go 设计模式

> **版本关系**：Go 1.24（stable）→ Go 1.26（<latest>）。设计模式原则不变，Go 1.23 的 iter 包引入了新的组合模式。

## 定义

Go 没有类继承，惯用设计模式强调：**组合优于继承**、**接口优于抽象类**、**函数优于类**。这与传统 OOP 语言有本质区别——Go 的模式是**行为组合**而非**类型层次**。

**归约终点**：Go 设计模式可归约为**接口约束 + 函数组合 + 显式依赖注入**，通过最小化隐式依赖实现可测试性和可维护性。

## 数学模型

### sync.Once 的正确性证明

`sync.Once.Do` 保证传入函数**恰好执行一次**（exactly-once semantics）。其正确性基于：

```
设 C 为执行计数器，初始 C = 0
Do(f) 的伪代码：

  if C == 0:
      mu.Lock()
      if C == 0:    // 双重检查
          f()
          C = 1
      mu.Unlock()

当 C = 1 时，后续所有 Do 调用直接跳过

关键属性：
  - 互斥锁保护 C 的写入
  - 双重检查避免重复执行（性能）
  - C 的值在锁外检查（无锁 fast path）
```

**正确性的数学证明**：

**定理**：sync.Once.Do(f) 保证 f 至多执行一次，且若某次调用返回，则 f 已执行。

**证明**：
1. 若 C=0 时多个 goroutine 同时进入，第一个获得锁的 goroutine 执行 f 并设置 C=1
2. 其他 goroutine 在第一个 if 检查时发现 C=1，跳过执行
3. 若某次调用返回，则该调用要么已执行 f（C=1 的情况），要么正在执行 f（等待锁释放）
4. 由于锁的互斥性，不可能存在两个 goroutine 同时执行 f

**归约终点**：Once 的正确性可归结为**互斥锁 + 双重检查模式**，这是并发初始化的标准正确性证明模式。

### 接口组合的集合论

```
Go 接口是**行为集合**（而非类型层级）：
  io.Reader = { Read(p []byte) (n int, err error) }
  io.Writer = { Write(p []byte) (n int, err error) }
  io.ReadWriter = io.Reader ∪ io.Writer

类型实现接口 = 类型 ∈ 集合
  *os.File ∈ io.Reader  当且仅当 *os.File 实现了 Read 方法

接口组合满足分配律：
  (A ∪ B) ∪ C = A ∪ (B ∪ C)
```

**接口嵌入的数学语义**：

$Interface_{embedded} = \bigcup_{i} Interface_i$

嵌入接口的方法集合是所有被嵌入接口的并集。

## 数据流

### 单例模式（sync.Once）的执行流

<pre>
GetManager()
    │
    ├── C == 0？ ──► 否 ──► return instance（fast path，无锁）
    │
    ├── C == 0？ ──► 是 ──► mu.Lock()
    │                         │
    │                         ├── C == 0？ ──► 是 ──► f() 执行一次
    │                         │                      │
    │                         │                      ▼
    │                         │                  C = 1
    │                         ├── C == 0？ ──► 否 ──► 跳过（已有线程完成）
    │                         │
    │                         ▼
    │                     mu.Unlock()
    │
    ▼
return instance
</pre>

### 装饰器模式（Middleware Chain）的数据流

<pre>
请求 string
    │
    ├── AuthMiddleware(request) ──► 验证/拒绝
    │        │ 通过
    │        ▼
    ├── LoggerMiddleware(request) ──► 记录日志
    │        │ 通过
    │        ▼
    ├── Handler(request) ──► 业务逻辑 ──► response string
    │        │ 返回
    │        ▼
    └── LoggerMiddleware(response) ──► 记录响应
             │
             ▼
         AuthMiddleware(response) ──► （如需）
             │
             ▼
         返回 client
</pre>

### 建造者模式的构造流

<pre>
QueryBuilder{}
    │
    ├── Table("users") ──► query.table = "users"
    │                     return *QueryBuilder
    │
    ├── Select("id", "name") ──► query.fields = ["id", "name"]
    │                           return *QueryBuilder
    │
    ├── Where("age > 18") ──► query.condition = "age > 18"
    │                         return *QueryBuilder

                      │

                  SQL 生成：SELECT id, name FROM users WHERE age > 18
</pre>

## 机制

### 为什么 Go 选择组合优于继承？

继承的本质是**静态类型层次**，存在以下问题：

| 问题 | 继承中的表现 | Go 组合的解法 |
|------|------------|--------------|
| 脆弱的基类 | 基类改变破坏子类 | 显式接口依赖 |
| 菱形继承 | 方法解析顺序不确定 | 无多层继承 |
| 横切关注点 | AOP 需要继承层次 | 装饰器链显式组合 |
| 组合复用 | - | 嵌套结构体直接复用 |

Go 的组合是**命名组合**（通过字段嵌入），而非继承的**匿名子类型**。嵌入字段的方法会被提升到外包类型，但不改变外包类型的"是-一个"语义。

**约束条件**：
- 嵌入字段的方法与外包类型的方法冲突时，外包类型的方法优先
- 这可能导致意外的方法覆盖

### 策略模式 vs 继承的运行时选择

```
继承（传统 OOP）：
  Payment ──► CreditCardPayment / AlipayPayment / WechatPayment
              在编译时决定类型

策略模式（Go）：
  Checkout{ strategy: PaymentStrategy }
              │
              ├── CreditCardStrategy{}
              ├── AlipayStrategy{}
              └── WechatStrategy{}
              在运行时决定使用哪个策略

本质：Go 将"选择哪个算法"从类型系统移到数据，
      运行时通过接口动态分派。
```

**动态分派的数学语义**：

$Execute(strategy, args) = strategy.Execute(args)$

其中 strategy 的具体类型在运行时确定。

**策略模式的约束**：
- 所有策略必须实现相同接口
- 策略之间应相互独立（无共享状态）
- 策略切换不应影响 Checkout 的内部状态

### 观察者模式的同步约束

观察者模式需要解决**并发安全**问题：

```go
// 问题：通知过程中 observer 可能被修改
// 解决：读写锁 + 快照

func (s *Subject) Notify(e Event) {
    s.mu.RLock()              // 读取期间禁止写入
    observers := s.observers  // 复制快照
    s.mu.RUnlock()

    for _, o := range observers {
        o.OnEvent(e)         // 通知期间 observer 列表不变
    }
}

func (s *Subject) Subscribe(o Observer) {
    s.mu.Lock()
    s.observers = append(s.observers, o)
    s.mu.Unlock()
}
```

这体现了**读写锁分离原则**：读操作可以并发，写操作必须独占。

**观察者模式的数学约束**：

通知期间 observer 列表必须不变：
$\forall t \in \text{Notify}(e): \text{observers}(t) = \text{observers}(t_0)$

### 工厂模式的依赖注入变体

```
简单工厂（静态）：
  func NewCache() *Cache {
      return &Cache{backend: NewRedis()}  // 硬编码依赖
  }

工厂接口（依赖注入）：
  type CacheFactory interface {
      NewCache() *Cache
  }

  func NewCacheWithFactory(f CacheFactory) *Cache {
      return f.NewCache()  // 依赖外部注入
  }
```

**归约终点**：工厂模式将对象的创建延迟到运行时，允许替换具体实现。

**工厂模式的约束**：
- 工厂创建的对象必须满足相同接口
- 工厂不应持有被创建对象的可变状态

## 惯用 Go 模式小结

| 原则 | 实现方式 | 解决的问题 |
|------|----------|----------|
| 组合优于继承 | 嵌套结构体 + 接口 | 类型层次脆弱性 |
| 接口优于抽象类 | 小接口（`io.Reader`） | 隐式实现解耦 |
| 函数优于类 | 高阶函数装饰器 | 行为组合灵活性 |
| 显式依赖注入 | 构造函数传参 | 测试可替换性 |
| 零依赖单例 | `sync.Once` | 初始化竞争 |

## 模式选择的决策树

<pre>
需要扩展对象行为？
    │
    ├─ 是：需要运行时选择 → 策略模式
    │           │
    │           └─ 需要链式处理 → 装饰器模式
    │
    └─ 否：需要延迟创建 → 工厂模式
                 │
                 └─ 只创建一次 → 单例模式（sync.Once）

需要对象通信？
    │
    ├─ 是：一对多 → 观察者模式
    │           │
    │           └─ 多对一 → Channel/管道模式
    │
    └─ 否：需要状态共享 → sync.Mutex 或 sync.RWMutex
</pre>

## 组合的数学性质

### 嵌入与提升的数学表示

设外包类型 $E$ 嵌入内部类型 $I$ ：
$Method_E(m) = \begin{cases} E.Method(m) & \text{若 } E \text{ 定义了 Method} \\ I.Method(m) & \text{若 } E \text{ 未定义 Method} \end{cases}$

这体现了**方法提升**的确定性。

### 接口组合的封闭性

接口组合的结果仍是接口：
$A, B \text{ 是接口} \implies A \cup B \text{ 是接口}$

这保证了接口组合的递归适用性。
