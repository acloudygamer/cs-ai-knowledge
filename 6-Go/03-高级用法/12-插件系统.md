# 插件系统

## 定义

Go 插件通过 `plugin` 包加载 `.so` 共享对象，实现运行时动态加载。其本质是** ELF（Linux）/ Mach-O（macOS）共享库的符号表查询**——主程序通过动态链接器在插件中查找符号（变量或函数），实现行为扩展。

受限于 Linux/macOS 且需与主程序 Go 版本一致，实际生产使用较少。

## 数学模型

### 插件加载的符号解析模型

```
插件文件：plugin.so（ELF/Mach-O 格式）
    │
    ├── .symtab：符号表（导出符号）
    ├── .dynsym：动态符号表（运行时解析）
    └── .text：机器码

Lookup("SymbolName") 执行：
  1. 在插件的 .dynsym 中查找 "SymbolName"
  2. 获取符号的地址（R_X86_64_JUMP_SLOT 等）
  3. 返回可用的函数/变量指针
  4. 类型断言验证接口匹配

关键约束：
  - 主程序和插件的 Go 版本必须完全一致
  - 插件使用 runtime 包会导致 panic
  - 插件中的 goroutine 无法被主程序调度器管理
```

**归约终点**：插件系统的本质是**动态符号链接**，安全性由操作系统加载器保证。

### 插件接口契约

```
接口定义（主程序）：
  type Plugin interface {
      Name() string
      Execute(ctx context.Context) error
  }

插件实现：
  var PluginImpl = &MyPlugin{}

  func Register() (Plugin, error) {
      return PluginImpl, nil
  }

Lookup 契约：
  "Register" → func() (Plugin, error)  ← 必须返回接口类型
  类型断言：sym.(func() (Plugin, error))
```

## 数据流

### 插件加载的全链路

<pre>
plugin.so（磁盘文件）
    │
    │ dlopen(plugin_path)
    ▼
动态链接器加载共享库
    │
    ├── 映射 .text（代码段）到内存
    ├── 解析导入符号（主程序导出给插件的符号）
    ├── 重定位（relocations）
    │
    ▼
plugin.Open() 返回 *plugin.Plugin
    │
    │ p.Lookup("Register")
    ▼
符号查找（R_X86_64_JUMP_SLOT → 函数指针）
    │
    ├── 类型断言：fn.(func() (Plugin, error))
    │
    ▼
调用 fn() → 获取 Plugin 实例
    │
    ▼
Plugin.Execute(ctx) ← 插件逻辑在主程序调度下执行
</pre>

### 热加载的替换流程

<pre>
文件 mtime 变化
    │
    ├── 关闭现有插件：dlclose()（实际只是引用计数-1）
    │
    ├── 加载新版插件：dlopen(new_path)
    │
    ├── 重新 Lookup("Register")
    │
    ├── 新 Plugin 实例替换旧实例
    │
    ▼
新请求路由到新 Plugin
</pre>

### goroutine 在插件中的调度问题

<pre>
主程序 goroutine 调度器
    │
    ├── P1 ── G1（主程序）
    │
    ├── P2 ── G2（插件中执行）
    │         │
    │         │ 插件创建 goroutine G3
    │         ▼
    │       G3 由谁调度？
    │         │
    │         │ G3 由 P2 调度（共享 M）
    │         ▼
    │       G3 执行中...
    │
    └── 问题：GC 如何感知 G3 的根？
              GC 扫描 goroutine 栈时，无法感知插件分配的内存
              → 插件内存可能别误回收
</pre>

## 机制

### 为什么 Go 插件系统实际很少使用？

**版本强耦合问题**：
- Go 的 runtime、GC、scheduler 版本必须与插件完全匹配
- 插件和主程序使用不同 Go 版本 → ABI 不兼容 → 运行时 panic
- 这意味着每次升级 Go 版本，所有插件必须重新编译

**ABI 兼容性的数学约束**：
$$ABI_{compatible} \iff GoVersion_{plugin} = GoVersion_{main}$$
Go 的 runtime 结构（goroutine 栈、GC bitmap、调度器状态）在不同版本间可能变化。

**功能限制**：
| 限制 | 原因 |
|------|------|
| 仅 Linux/macOS | Windows 不支持 `.so`/`.dylib` 加载 |
| 不能使用 runtime 包 | 运行时状态冲突 |
| 不能使用 cgo | 符号表复杂化 |
| goroutine 不受管理 | 插件的 goroutine 在主程序调度下，但 GC 不知道 |

**安全性问题**：
- 插件 panic 会传播到主程序
- 插件可以修改主程序的内存（通过 unsafe）
- 没有资源隔离（CPU/内存）

### 插件接口设计模式

```
推荐模式：
  主程序定义接口（不依赖插件代码）
  插件实现接口并导出 Register 函数

interface Plugin in main ──────► 插件实现 Plugin
       ▲                                 │
       │                                 │
       └── 动态加载时实现匹配 ────────────┘

这样主程序不依赖插件的任何类型声明，
插件只需要实现接口即可。
```

### 插件与主程序的内存边界

```
主程序内存                    插件内存
┌─────────────────┐         ┌─────────────────┐
│ .text (主程序)   │         │ .text (插件)     │
│ .data (主程序)   │  <--->  │ .data (插件)     │
│ .heap (主程序)   │  符号表  │ .heap (插件)     │
└─────────────────┘         └─────────────────┘

问题：
  GC 只扫描主程序的堆，不知道插件堆中的对象
  插件分配的内存可能被误认为不可达

解决：
  插件使用主程序分配的内存（通过接口传递）
  或插件完全静态分配（无动态内存）
```

## 限制总结

| 限制 | 说明 |
|------|------|
| 仅 Linux/macOS | Windows 不支持 |
| Go 版本必须一致 | 主程序和插件 |
| 编译标签必须一致 | 构建时指定 |
| 无真正卸载 | 只能替换，无法卸载 |
| 无资源隔离 | panic 传播、内存共享 |

## 替代方案

| 场景 | 替代方案 | 原因 |
|------|----------|------|
| 配置热更新 | JSON/YAML 重载 | 简单、无版本问题 |
| 算法可插拔 | 接口 + 工厂注册 | 编译时绑定，无运行时开销 |
| 业务扩展 | 微服务 RPC | 进程隔离，版本独立 |
| WASM 沙盒 | golang.org/x/wasm | 跨平台，有资源限制 |

## 插件系统的图灵等价性

**定理**：Go 插件系统在理论上可以实现任意扩展，因为可以通过 `Lookup` 获取任意导出的符号。

**推论**：插件的能力上限等于主程序导出的符号集合。

**实际问题**：版本耦合使得实际使用受限。
