# 网络编程专题

## 定义

Go 的网络编程基于 `net` 包实现 TCP/UDP/HTTP 通信。其本质是**基于 epoll/kqueue 的 I/O 多路复用**配合 **goroutine per connection 模型**，以少量 goroutine（而非线程）处理大量并发连接。每个连接对应一个 goroutine，阻塞 I/O 不占用 OS 线程，调度器在 I/O 完成时自动唤醒对应 goroutine。

## 数学模型

### Go I/O 多路复用的调度模型

```
传统 I/O 多路复用（epoll）：
  线程池 ──► epoll_wait() ──► 就绪 fd 列表 ──► 逐个处理

Go 的 I/O 模型（netpoller）：
  goroutine A: conn.Read() ──► blocked ──► 被 park（不占线程）
  goroutine B: conn.Write() ──► blocked ──► 被 park
  goroutine C: ...

  底层：Go runtime 在首次 I/O 时将 fd 注册到 epoll/kqueue
       当 I/O 完成时，netpoller 唤醒对应 goroutine
       其他 goroutine 在此期间正常调度执行
```

**归约终点**：Go 的网络模型可归结为**事件驱动的协作式调度**，goroutine 主动让出 CPU 而非被抢占。

### 并发连接数的理论上限

```
OS 文件描述符上限：ulimit -n（通常 1024-65535）
每个连接占用 1 个 fd

Go 连接数上限 = min(OS fd 上限, 内存限制)
典型值：10000-100000 并发连接（轻量 goroutine 栈仅 2KB）

对比线程模型：
  10000 线程 × 8MB 栈 = 80GB 不可行
  10000 goroutine × 2KB 栈 = 20MB 可行
```

**内存约束公式**：
$$N_{connections} \leq \frac{Memory_{available} - Memory_{app}}{Size_{goroutine\_stack} + Size_{connection\_buffer}}$$

### TCP 拥塞控制模型

Go 的 `net.Conn` 底层使用操作系统的 TCP 栈。主要拥塞控制算法：

```
Reno → CUBIC（Linux 默认）→ BBR（可选）

关键参数：
  RTT（往返时延）：网络路径延迟
  cwnd（拥塞窗口）：发送方未被确认的最大数据量
  ssthresh：慢启动阈值

吞吐量 = min(cwnd, 接收窗口) / RTT
```

**BBR 的数学模型**：BBR 试图稳定在最优工作点：
$$Throughput_{BBR} = \frac{BDP}{RTT} = \frac{Bandwidth \times RTT}{RTT} = Bandwidth$$

### 粘包处理的数据分帧模型

```
TCP 是字节流协议，无消息边界：
  ┌─────────────────────────────────────────────────┐
  │ 字节流：[DATA][DATA][DATA][DATA][DATA]...       │
  │            ↑ 边界由应用层决定                     │
  └─────────────────────────────────────────────────┘

分帧方法：

1. 定长分帧（Fixed-length）：
   [DATA][DATA][DATA]（每帧固定 N 字节）
   缺点：浪费带宽，限制消息长度

2. 分隔符分帧（Delimiter）：
   [DATA\n][DATA\n][DATA\n]
   缺点：需要转义处理

3. 长度前缀分帧（Length-prefixed，TLV）：
   [4B length][payload][4B length][payload]...
   ┌──────────────────────────────┐
   │ length: uint32（字节数）      │
   │ payload: length 字节的数据     │
   └──────────────────────────────┘
   优点：精确、无浪费，HTTP/1.1 和 Redis 协议使用此方式
```

**分帧的数学约束**：长度前缀必须无歧义，即任意长度序列不能既是有效长度又是有效载荷。

## 机制

### goroutine per connection 为什么高效？

**线程的上下文切换开销**（~1-10μs）：
- 用户态 → 内核态切换
- 寄存器保存/恢复（通用寄存器、浮点寄存器）
- TLB 刷新（页表切换）
- 栈切换（内核栈/用户栈）

**goroutine 的上下文切换开销**（~10-50ns）：
- 仅保存必要寄存器（PC, SP, BP + 少数 callee-saved）
- 不触发特权级切换
- 不刷新 TLB（同一地址空间）
- 栈切换在用户态完成

当连接数 N 很大且每个连接 I/O 阻塞时间长时，goroutine 模型的吞吐量是线程模型的 10-100 倍。

**阻塞调用的调度优化**：
```go
conn.Read(b) // 阻塞
// 等价于：
//   1. 注册 fd 到 epoll
//   2. park goroutine
//   3. 当 fd 就绪时，唤醒 goroutine
```

### 连接池的复用模型

```
无连接池：
  req1 → [建连(3W) → 请求 → 断连(4W)] → req2 → [建连(3W) → ...]

有连接池：
  req1 → [建连(3W) → 请求] ──────────────────────────┐
  req2 → [请求（复用连接）] ──────────────────────────►│
  req3 → [请求（复用连接）] ──────────────────────────►│
  req4 → [请求（复用连接）]                              │
  req5 → [断连(4W)] ◄─────────────────────────────────┘

省去 4×RTT（TCP握手）+ TLS握手（如果用HTTPS）
```

**连接池大小的数学约束**：
$$N_{pool} = \min(N_{requests}, \frac{Memory_{limit}}{Size_{connection}})$$

### 超时设置的必要性

TCP 连接和 I/O 操作如果不设置超时，可能导致：

| 操作 | 无超时的风险 | 推荐超时 |
|------|-------------|----------|
| Dial | DNS 解析卡住/防火墙屏蔽 | 3-10s |
| Read | 对端崩溃/网络中断 | 30s-5min |
| Write | 对端缓冲区满 | 30s |
| Idle keepalive | 检测断开的连接 | 75s+ |

**超时设置的数学语义**：
$$T_{deadline} = T_{start} + T_{timeout}$$
当 $T_{now} > T_{deadline}$ 时，操作被中断并返回错误。

## 常见错误

| 错误 | 后果 | 修复 |
|------|------|------|
| 粘包未处理 | 数据错乱 | 长度前缀/TLV 分帧 |
| 未设置超时 | goroutine 泄漏 | SetReadDeadline/SetWriteDeadline |
| defer conn.Close() 漏配对 | 连接泄漏 | 错误路径也要 Close |
| UDP 不保证可靠性 | 丢包乱序 | 应用层处理/用 TCP |

## HTTP/2 和 HTTP/3 的演进

### HTTP/2 的多路复用

```
HTTP/1.1 问题：
  每个请求需要独立 TCP 连接（或串行使用同一连接）
  队头阻塞（HOL blocking）

HTTP/2 解决：
  Stream ID 复用单一 TCP 连接
  帧（Frame）交错传输
  真正并行请求
```

**帧调度的数学模型**：
$$Frame_{n} = \langle StreamID, Type, Payload \rangle$$
同一 StreamID 的帧有序，不同 StreamID 的帧可交错。

### HTTP/3 的 QUIC 替代

```
HTTP/3 基于 QUIC（UDP）：
  - 无队头阻塞（UDP 独立流）
  - 0-RTT 握手（理想情况）
  - 连接迁移（IP 变化时不断开）

Go 支持：golang.org/x/net/http2, quic-go
```
