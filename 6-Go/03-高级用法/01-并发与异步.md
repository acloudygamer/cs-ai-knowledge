# 并发与异步

> **版本关系**：Go 1.24（基础）→ Go 1.26

## 定义

Go 并发模型基于 CSP（Communicating Sequential Processes）理论：goroutine 通过 channel 通信而非共享内存——这解决了传统线程模型的高成本问题，万级并发下传统线程栈（MB 级）迅速耗尽内存，而 goroutine（KB 级栈）使轻量级并发成为可能。

## goroutine（轻量级线程）

### 定义
goroutine 是由 Go runtime 采用 M:N 模型映射到少量 OS 线程的轻量级执行单元：创建成本约 ~2KB 初始栈，可同时运行数万个。

### 数学模型

**M:N 调度模型**：
- M = Machine（OS 线程）
- G = Goroutine（轻量级执行单元）
- P = Processor（调度上下文，固定数量 = GOMAXPROCS）

调度器工作流程：每个 P 维护一个 runnable goroutine 队列。G 的生命周期状态机：
$$S_G \in \{空闲, 运行, 系统调用, 等待\}$$

**栈增长模型**：goroutine 栈初始大小 2KB，按需增长（分段栈），最大可达系统限制：
$$S_{stack}(n) = \min(2^{n} \cdot 2KB, 1GB)$$
其中 $n$ 是扩容次数，通常 $n \leq 10$。

**归约终点**：goroutine 调度是**工作窃取算法**的变体，每个 P 从自己的队列取任务，队列空时从其他 P 偷取，保证负载均衡。

### 数据流

<pre>
用户代码: go func() { doWork() }()

创建阶段：
  1. 分配 G 结构体（约 2KB，包含栈指针、状态、调度信息）
  2. 将 G 加入 P 的 runnable 队列
  3. 不创建新 OS 线程（复用现有 M）

调度阶段（M:P:G = 1:1:1）：
  P 的 runqueue:
    [G1(doWork), G2, G3, ...]
           │
           ▼
    选取 G1 执行
           │
           ▼
    G1 运行在 M 上（M 绑定 P）
           │
           ├─ 正常完成 → G1 状态转为 空闲（可被复用）
           │
           ├─ 阻塞 I/O → G1 状态转为 等待，M 解绑 P
           │                空闲 M 可执行其他 G
           │
           └─ 时间片耗尽 → G1 状态转为 runnable，重新入队
</pre>

### 机制

**为什么 goroutine 如此轻量**：
1. 初始栈仅 2KB（线程栈 1-8MB）
2. 创建无需系统调用（线程创建需要 clone 系统调用）
3. 栈分段增长（按需分配，而非预分配大栈）
4. 调度在用户态完成（不进入内核）

**M:N 模型的优势**：相比 1:1（每个 goroutine 一个线程），M:N 减少了上下文切换开销；相比 1:1（每个线程一个 goroutine），M:N 允许绑定数量远大于物理核心的 goroutine。

**分段栈的深层机制**：
- 旧栈分段：每个函数调用在栈底分配"断层检测块"（stack split chunk），跨段访问时触发 runtime 扩容
- 新栈连续：Go 1.14+ 使用连续栈（contiguous stack），栈增长时分配新段并复制数据，不再使用断层检测

**约束条件**：
- goroutine 栈最大 1GB，实际受 `GOMAXPROCS` 和物理内存限制
- 每个 P 关联一个 M，若所有 M 都阻塞（如 CGO），调度器可能饥饿

**违反约束的后果**：
- 栈溢出：runtime 调用 `abort()` 造成进程终止
- 过多 goroutine：每个至少 2KB，若创建百万级可能耗尽内存

## channel（goroutine 通信）

### 定义
channel 是 goroutine 之间的类型化管道：unbuffered channel 的 send 和 receive 必须 rendezvous（同时就绪），buffered channel 以 FIFO 队列解耦发送端和接收端。

### 数学模型

**channel 容量与阻塞概率**：设 channel 容量为 $C$，send 操作到达时队列长度为 $L$：
- 若 $L < C$：send 成功，队列长度 $L \rightarrow L+1$
- 若 $L = C$：send 阻塞，直到 receiver 取走元素

** rendezvous 语义（unbuffered channel, C=0）**：
$$\text{send}(ch, v) \iff \exists r: \text{receive}(ch, v) \text{ 同时就绪}$$
这意味着发送方必须等待接收方准备好，反之亦然。

**channel 的图灵等价性**：
- channel + goroutine 可模拟信号量、屏障、锁等所有同步原语
- 这意味着 channel 是 Go 并发的**完全图灵机基底**

### 数据流

<pre>
无缓冲 channel（C=0）:

  goroutine A ──send──▶ ┌────────┐ ──receive──▶ goroutine B
                          └────────┘
                    双方必须同时就绪
                    否则阻塞（A 等待 B，B 等待 A）

有缓冲 channel（C>0）:

  goroutine A ──send──▶ ┌─[buf]───────┐ ──receive──▶ goroutine B
                          └─────────────┘
                    队列满时 A 阻塞，队列空时 B 阻塞
                    容量 C 决定了解耦程度
</pre>

### 机制

**为什么 channel 设计为值传递而非指针**：channel 本身是指向 hchan 结构的指针，但发送给 channel 的值是**复制**的。这避免了数据竞争（receiver 无法修改 sender 的原始数据），也符合 CSP 的"通过通信共享内存"而非"共享内存来通信"的哲学。

**关闭 channel 的语义**：
- 发送到已关闭 channel 会 panic
- 接收已关闭 channel 返回零值（不阻塞）
- `for v := range ch` 在 channel 关闭且无数据时退出

**关闭的 Happens-Before 契约**：
- close(ch) happen-before 任何 receive 操作返回零值
- 这由调度器和内存模型共同保证

## 互斥锁和读写锁

### 定义
当需要共享状态而非通信时，sync.Mutex 强制互斥访问共享变量，sync.RWMutex 在读多写少场景下允许并发读但独占写——这避免了 channel 的额外簿记开销。

### 数学模型

**Mutex 状态机**：
$$S_{mutex} \in \{未锁定, 已锁定\}$$

- `Lock()`: 若 $S=未锁定$ → $S=已锁定$，返回；否则阻塞直到其他 goroutine 调用 `Unlock()`
- `Unlock()`: $S=已锁定$ → $S=未锁定$，唤醒一个等待中的 goroutine

**RWMutex 的读写公平性**：
- 读锁：$readers > 0$ 时，写操作等待所有读锁释放
- 写锁：独占，之后的读操作等待写锁释放

**饥饿与公平性**：
- Go Mutex 默认不保证 FIFO 公平，存在饥饿场景
- 长时间饥饿（> 1ms）的 waiter 会获得优先权

### 参考存根

```go
var mu sync.Mutex
m := make(map[string]int)

mu.Lock()
m["key"] = 42
mu.Unlock()

var rwmu sync.RWMutex
rwmu.RLock()
v := m["key"]
rwmu.RUnlock()
```

## sync.Once 单次执行

### 定义
sync.Once 保证函数只执行一次——用于单例初始化时替代锁的双重检查模式，既安全又避免重复初始化的开销。

### 机制

**Once 的实现原理**：内部使用一个 mutex + 一个 done 标记。首次调用 `Do(f)` 时，检查 done，若为 0，则加锁、执行 f、设置 done=1。之后所有调用检查 done 后直接返回，不加锁。

**为什么比双重检查更优**：双重检查在 Java 中需要 volatile，在 Go 中虽然 map 不是线程安全，但 `sync.Once` 保证了初始化的幂等性，同时避免了每次获取锁的开销。

### 参考存根

```go
var once sync.Once
var instance *DB

func getInstance() *DB {
    once.Do(func() {
        instance = &DB{}
    })
    return instance
}
```

## sync.Map（并发安全 map）

### 定义
sync.Map 内部采用读写分离优化（read + dirty 双结构），适合读多写少且 key 集合稳定的场景——大多数场景用 sync.Mutex 保护普通 map 反而更快。

### 机制

**read 和 dirty 的分离**：
- read：只读结构，存储所有数据（指针共享），无锁读取
- dirty：写操作的目标，包含 read 中不存在的新增 key

**性能来源**：大多数读取命中 read，无需加锁。只有 read 中不存在时（miss）才访问 dirty，并提升到 read。

**适用条件**：
- 读多写少（读不写，写操作少）
- key 集合稳定（少有新增删除）
- 无需精确计数（Store/Load/Delete 语义）

**违反适用条件的代价**：写多时 dirty 频繁升级，性能退化至不如普通 mutex+map。

## errgroup 协调多个 goroutine

### 定义
golang.org/x/sync/errgroup 将多个 goroutine 的错误汇聚：任一失败时通过 context cancel 其他 goroutine，实现"快速失败"语义。

### 机制

**快速失败语义**：当一个子任务失败时，其他仍在运行的任务应立即停止。这通过 context cancel 实现：
1. 任一 goroutine 返回非 nil error
2. `errgroup` 调用 `cancel()` 通知 context
3. 其他 goroutine 的 `ctx.Done()` 收到信号，主动退出

**错误汇聚的数学约束**：最多传递一个 error（第一个返回的），其他 error 被丢弃。这是**短路语义**的经济实现。

## Worker Pool 模式

### 定义
Worker Pool 预创建固定数量 goroutine 从 job channel 消费任务——避免了无限制创建 goroutine 导致的调度负担和内存爆炸。

### 数学模型

**无限 goroutine 的内存成本**：每个 goroutine 栈最小 2KB，若创建 10,000 个，则栈占用 20MB。即使实际使用不到 1KB，栈空间也已分配。

**Worker Pool 的资源约束**：
$$Memory_{workerpool} = N_{workers} \times 2KB + job\_channel\_size \times sizeof(job)$$
通过固定 $N_{workers}$，内存可控。

**调度公平性**：工作窃取保证负载均衡，但任务大小不一时可能出现短任务饿死长任务。

## 优雅关闭（Graceful Shutdown）

### 定义
Graceful Shutdown 通过 signal.Notify 捕获 OS 信号，调用 server.Shutdown(ctx) 停止接受新请求并等待正在处理的请求完成——避免强制关闭导致的连接中断。

### 机制

**两阶段关闭**：
1. **停止接受新请求**：关闭 listener，HTTP 服务器不再接受新连接
2. **等待现有请求完成**：所有 in-flight 请求在 ctx 超时前继续处理

**ctx 超时的作用**：防止某个请求永远不完成导致服务无法关闭。

**约束条件**：
- 若 ctx 超时设置为 0，则立即放弃等待
- 某些请求可能永远无法完成（如 WebSocket 长连接）

## 避免 Goroutine 泄漏

### 定义
goroutine 无法被 GC 回收，只能通过 channel 或 context 取消——无缓冲 send 如果没有接收者会永久阻塞，这正是 goroutine 泄漏的根源。

### 数学模型

**goroutine 状态与资源**：
$$S_G \in \{运行, 阻塞, 等待\}$$

- 运行中：占用 CPU + 栈内存（2KB-1GB 可变）
- 阻塞（channel send/receive）：不占 CPU，但栈内存无法释放
- 等待（select + channel）：等待条件满足

**泄漏条件**：goroutine 进入阻塞状态但永远无法唤醒，且没有其他 goroutine 持有其引用。

**泄漏的数学检测**：
- 若 goroutine 状态为阻塞且等待事件集合为空（或永不满足），则泄漏
- 实际中通过 tracing 观测 goroutine 数量是否收敛判断

### 数据流

<pre>
泄漏场景：
  ch := make(chan []byte)          // 无缓冲，无人接收
  go func() { ch <- fetch(url) }  // 永久阻塞在 send

修复方案（缓冲 channel）：
  ch := make(chan []byte, 1)      // 缓冲容量 1
  select {
  case ch <- data:
  case <-ctx.Done():
      // context 取消时退出
  }

修复方案（context 取消）：
  func safeFetch(ctx context.Context, url string) <-chan []byte {
      ch := make(chan []byte, 1)
      go func() {
          data, _ := fetch(url)
          select {
          case ch <- data:
          case <-ctx.Done():
              // 被取消，goroutine 退出
          }
      }()
      return ch
  }
</pre>

## sync.Cond 条件变量

### 定义
sync.Cond 基于互斥锁实现条件等待：一个 goroutine 在 cond.Wait() 中自动释放锁并阻塞，另一个在满足条件时通过 Signal/Broadcast 唤醒等待者——这比轮询更高效。

### 机制

**Wait 的原子性**：cond.Wait() 在阻塞前自动释放锁，在被唤醒时重新获取锁。这保证了 signal 发生时锁的状态一致性。

**Signal vs Broadcast**：
- Signal：唤醒一个等待者（通常唤醒等待时间最长的）
- Broadcast：唤醒所有等待者

**典型用法**：条件不满足时 Wait，条件满足时 Signal/Broadcast。

### 参考存根

```go
cond := sync.NewCond(&sync.Mutex{})
ready := false

go func() {
    cond.L.Lock()
    for !ready {
        cond.Wait()
    }
    cond.L.Unlock()
    fmt.Println("ready is true, proceeding")
}()

cond.L.Lock()
ready = true
cond.Signal()  // 唤醒一个等待者
cond.L.Unlock()
```
