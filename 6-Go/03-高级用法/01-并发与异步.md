# 并发与异步

> **版本关系**：Go 1.24（stable）→ Go 1.26（<latest>）。Go 1.26 引入更积极的抢占式调度和公平性优化，但核心模型不变。

## 定义

Go 并发模型根植于 CSP（Communicating Sequential Processes）理论：goroutine 通过 channel 通信而非共享内存。这解决了传统线程模型的**资源耗尽问题**——万级并发下，传统线程栈（MB 级）消耗内存高达数十 GB，而 goroutine（KB 级栈）将内存占用压至数十 MB。

**归约终点**：Go 并发模型可归约为**工作窃取（Work-Stealing）调度器**实现的**用户态协程多路复用**，其同步原语（channel、mutex）建立 happens-before 偏序关系。

## goroutine（轻量级线程）

### 定义

goroutine 是由 Go runtime 采用 M:N 模型映射到少量 OS 线程的轻量级执行单元。M:N 表示 M 个 goroutine 复用 N 个 OS 线程，创建成本约 ~2KB 初始栈，可同时运行数万个。

### 数学模型

**M:N 调度模型的形式化**：

- M = Machine（OS 线程，绑定 CPU 核心）
- G = Goroutine（轻量级执行单元）
- P = Processor（调度上下文，固定数量 = `GOMAXPROCS`，通常等于 CPU 核心数）

三者关系满足：
$M \leq N_{CPU} \quad \text{且} \quad |\{G: G \text{ 绑定到 } P_i\}| \geq 0$

**G 的状态机**：

$S_G \in \{\text{空闲}, \text{运行}, \text{等待}, \text{系统调用}\}$

| 转移 | 条件 | 触发者 |
|------|------|--------|
| $\text{运行} \to \text{等待}$ | channel send/receive 阻塞、syscall 阻塞 | 自身操作 |
| $\text{等待} \to \text{运行}$ | 条件满足、I/O 完成、锁释放 | 调度器 |
| $\text{运行} \to \text{空闲}$ | goroutine 正常返回或崩溃 | 调度器 |
| $\text{运行} \to \text{运行}$ （让出） | 时间片耗尽（抢占）、Gopark | 调度器抢占 |

**栈增长模型**：

goroutine 栈初始大小 2KB，按需增长（连续栈），最大可达 1GB：
$S_{stack}(n) = \min(2^{n+10} \cdot 2\text{KB}, 1\text{GB})$

其中 $n$ 是扩容次数， $n \leq 19$ （最大栈 1GB / 2KB =  $2^{19}$，约需 19 次扩容）。

**工作窃取算法的负载均衡**：

设 $Q_i$ 为第 $i$ 个 P 的 runnable 队列长度，窃取判定：
$\text{steal}(i, j) \iff Q_i = 0 \land Q_j > 0$

每次窃取移动 $\min(\lfloor Q_j / 2 \rfloor, 1)$ 个 goroutine，保证负载均衡的同时减少窃取开销。

**死锁的数学约束**：

goroutine 死锁当且仅当以下条件同时满足：
1. 所有 goroutine 处于 $\text{等待}$ 状态
2. 等待集合中不存在能够被唤醒的 channel send/receive
3. 不存在 idle goroutine 能够接管调度

形式化：
$\forall G_i: S_G(G_i) = \text{等待} \land \neg \exists ch: \text{channel\_ready}(ch) \implies \text{deadlock}$

**饥饿的公平性约束**：

Go 调度器不保证 FIFO 公平。当以下条件满足时，goroutine 可能饥饿：
$T_{wait}(G) > T_{max\_fair}$

其中 $T_{max\_fair}$ 由调度器内部实现决定（通常约 10ms）。Go 1.26 引入更积极的饥饿检测，降低长等待概率。

### 数据流

<pre>
用户代码: go func() { doWork() }()

创建阶段：
  1. 分配 G 结构体（约 2KB，包含栈指针、状态、调度信息）
  2. 将 G 加入 P 的 runnable 队列（尾部）
  3. 不创建新 OS 线程（复用现有 M）

调度阶段（M:P:G = 1:1:1）：
  P 的 runqueue:
    [G1(doWork), G2, G3, ...]
           │
           ▼
    选取 G1 执行（G1 状态: 运行）
           │
           ▼
    G1 运行在 M 上（M 绑定 P）
           │
           ├─ 正常完成 → G1 状态转为 空闲，结构体归还池
           │
           ├─ 阻塞 I/O → G1 状态转为 等待，M 解绑 P
           │                空闲 M 可执行其他 G
           │
           ├─ channel 操作阻塞 → G1 状态转为 等待
           │
           └─ 时间片耗尽 → G1 状态转为 runnable，重新入队（队尾）
</pre>

**goroutine 创建的所有权转移**：

```
用户代码（主 goroutine）
    │
    ├── 分配 G 结构体 → runtime 持有
    ├── 设置 G 的栈指针 → runtime 持有
    ├── 设置初始 PC 为 go func() → runtime 持有
    │
    ▼
G 加入 runnable 队列 → 调度器持有执行权
    │
    ▼
P 执行 G → G 的执行权转移给 P
    │
    ▼
G 正常返回 → G 结构体归还 runtime 的 goroutine 池
    │
    ▼
资源释放：栈内存归还 runtime 栈池（而非操作系统）
```

### 机制

**为什么 goroutine 如此轻量**：

1. **初始栈仅 2KB**（线程栈 1-8MB），原因：连续栈按需增长，无需预分配大空间
2. **创建无需系统调用**（线程创建需要 `clone`），用户态分配 G 结构体
3. **栈连续增长**：按需分配，函数级别栈段管理
4. **调度在用户态完成**：不进入内核态，无特权级切换

**M:N 模型的优势**：相比 1:1（每个 goroutine 一个线程），M:N 减少上下文切换开销（线程切换 ~1-10μs，goroutine 切换 ~10-50ns）；相比全共享（1:1 线程池），M:N 允许绑定数量远大于物理核心的并发 goroutine。

**连续栈的深层机制**（Go 1.14+ 抢占式调度）：
- 栈增长时分配新栈段（通常 2KB），复制原栈内容到新段
- 旧栈段在函数返回后释放
- 通过 `lessstack` 函数检测栈溢出触发扩容
- 栈收缩在 GC 时发生（如果栈使用率低于 25%）

**约束条件**：
- goroutine 栈最大 1GB，实际受 `GOMAXPROCS` 和物理内存限制
- 每个 P 关联一个 M，若所有 M 都阻塞（如 CGO），调度器可能饥饿
- 窃取操作可能引发负载不均衡（热点队列被频繁窃取）
- **Go 1.26 新增**：抢占式调度更积极，但无法完全消除饥饿

**违反约束的后果**：
- 栈溢出：runtime 调用 `abort()` 造成进程终止
- 过多 goroutine：每个至少 2KB，若创建百万级可能耗尽内存
- CGO 阻塞所有 M：有效调度容量降为 $\frac{N-1}{N}$

## channel（goroutine 通信）

### 定义

channel 是 goroutine 之间的类型化管道：unbuffered channel 的 send 和 receive 必须 rendezvous（同时就绪），buffered channel 以 FIFO 队列解耦发送端和接收端。

### 数学模型

**channel 容量与阻塞概率**：

设 channel 容量为 $C$ ，send 操作到达时队列长度为 $L$ ：
- 若 $L < C$ ：send 成功，队列长度 $L \rightarrow L+1$
- 若 $L = C$ ：send 阻塞，直到 receiver 取走元素

**rendezvous 语义（unbuffered channel, C=0）**：
$\text{send}(ch, v) \iff \exists r: \text{receive}(ch, v) \text{ 同时就绪}$

这意味着发送方必须等待接收方准备好，反之亦然——双方在 channel 上同步。

**channel 的阻塞概率模型**：

对于容量为 $C$ 的 channel，稳态下：
$P(\text{阻塞}) = \frac{\lambda_{send} - \lambda_{receive}}{C \cdot \lambda_{receive}}$

其中 $\lambda_{send}$ 和 $\lambda_{receive}$ 分别是发送和接收速率。当 $\lambda_{send} > \lambda_{receive}$ 时，阻塞概率增加。

**关闭 channel 的约束**：

设 $S_{closed}$ 为 channel 的关闭状态：
- $\text{send}(ch, v) \land S_{closed} = \text{true} \implies \text{panic}$
- $\text{receive}(ch) \land S_{closed} = \text{true} \implies (0, \text{false})$
- $\text{close}(ch) \land S_{closed} = \text{true} \implies \text{panic}$

**channel 的图灵等价性**：

channel + goroutine 可模拟以下同步原语：
- **信号量**：容量 1 的 channel
- **屏障**：N 个 sender 和 N 个 receiver 的同步
- **互斥锁**：容量 1 + 互斥 send
- **广播**：关闭 channel 唤醒所有等待 receiver

这意味着 channel 是 Go 并发的**完全图灵机基底**——任何并发模式都可以用 channel 表达。

### 数据流

<pre>
无缓冲 channel（C=0）:

  goroutine A ──send──▶ ┌────────┐ ──receive──▶ goroutine B
                          └────────┘
                    双方必须同时就绪
                    否则阻塞（A 等待 B，B 等待 A）

有缓冲 channel（C>0）:

  goroutine A ──send──▶ ┌─[buf]───────┐ ──receive──▶ goroutine B
                          └─────────────┘
                    队列满时 A 阻塞，队列空时 B 阻塞
                    容量 C 决定了解耦程度
</pre>

**channel 操作的所有权转移**：

```
send 端                              receive 端
    │                                    │
    ├── 值 v 的副本入队 ─────────────────►│ 队列出队
    │  所有权：send 端仍持有 v 的副本      │ 所有权：receive 端获得 v 的副本
    │  （send 端可安全使用 v）            │ （receive 端独享 v 的所有权）
    │
    ▼
send 返回（若无阻塞）
```

**关键约束**：发送给 channel 的值是**复制**的，receiver 获得独立副本。这避免了数据竞争，符合 CSP 的"通过通信共享内存"哲学。

### 机制

**为什么 channel 设计为值传递而非指针**：

channel 本身是指向 hchan 结构的指针（共享），但发送给 channel 的值是**复制**的。这避免了数据竞争——receiver 无法修改 sender 的原始数据。

**关闭 channel 的语义**：
- 发送到已关闭 channel 会 panic
- 接收已关闭 channel 返回零值（不阻塞）
- `for v := range ch` 在 channel 关闭且无数据时退出

**关闭的 Happens-Before 契约**：
- `close(ch)` happen-before 任何 receive 操作返回零值
- 这由调度器和内存模型共同保证

**死锁与 channel 的关系**：

当以下条件满足时，channel 操作导致死锁：
1. unbuffered channel：send 后无对应 receive
2. buffered channel 满：所有 send 后无 receive
3. 所有等待 channel 的 goroutine 形成环等待

**约束条件**：
- nil channel 的 send/receive 永久阻塞
- 已关闭 channel 的 send panic
- 重复关闭 channel panic

**违反约束的后果**：
- 向已关闭 channel 发送 → panic: "send on closed channel"
- 从已关闭 channel 接收 → 返回零值（不阻塞）
- nil channel 操作 → 永久阻塞，goroutine 泄漏

## 互斥锁和读写锁

### 定义

当需要共享状态而非通信时，`sync.Mutex` 强制互斥访问共享变量，`sync.RWMutex` 在读多写少场景下允许并发读但独占写。

### 数学模型

**Mutex 状态机**：
$S_{mutex} \in \{\text{未锁定}, \text{已锁定}\}$

- `Lock()`: 若 $S=\text{未锁定}$ → $S=\text{已锁定}$ ，返回；否则阻塞
- `Unlock()`: $S=\text{已锁定}$ → $S=\text{未锁定}$ ，唤醒一个等待中的 goroutine

**Mutex 的正确性约束**：

持有锁的 goroutine 数量必须始终为 0 或 1：
$|holders| \in \{0, 1\}$

**RWMutex 的读写公平性**：
- 读锁： $readers > 0$ 时，写操作等待所有读锁释放
- 写锁：独占，之后的读操作等待写锁释放

**饥饿与公平性**：
- Go Mutex 默认不保证 FIFO 公平，存在饥饿场景
- 长时间饥饿（> 1ms）的 waiter 会获得优先权

**RWMutex 的状态机**：

$S_{rwmutex} \in \{\text{未锁定}, \text{读锁定}(n), \text{写锁定}\}$

| 操作 | 前置状态 | 转移条件 | 后置状态 |
|------|---------|---------|---------|
| RLock | 未锁定 | — | 读锁定(1) |
| RLock | 读锁定(n) | — | 读锁定(n+1) |
| RUnlock | 读锁定(1) | — | 未锁定 |
| RUnlock | 读锁定(n>1) | — | 读锁定(n-1) |
| Lock | 未锁定 | — | 写锁定 |
| Lock | 读锁定(n) | 等待所有读锁释放 | 写锁定 |
| Unlock | 写锁定 | — | 未锁定（唤醒一个 writer） |

**饥饿的数学条件**：

goroutine G 在 RWMutex 上饥饿当：
$\exists T_{start}(G): \forall t > T_{start}, \text{writers\_waiting}(t) > 0 \land \text{G 始终等待}$

### 参考存根

```go
var mu sync.Mutex
m := make(map[string]int)

mu.Lock()
m["key"] = 42
mu.Unlock()

var rwmu sync.RWMutex
rwmu.RLock()
v := m["key"]
rwmu.RUnlock()
```

## sync.Once 单次执行

### 定义

`sync.Once` 保证函数只执行一次——用于单例初始化，替代锁的双重检查模式，既安全又避免重复初始化的开销。

### 数学模型

**Once 的状态机**：

```go
type Once struct {
    done uint32  // 0 = 未执行，1 = 已执行
    mu   Mutex
}
```

正确性约束：
$done \in \{0, 1\} \qquad done = 1 \implies f \text{ 已执行恰好一次}$

**双重检查的数学形式**：

```
if done == 0:           // 第一次检查（无锁，快速路径）
    mu.Lock()
    if done == 0:       // 第二次检查（有锁，确保互斥）
        f()
        done = 1
    mu.Unlock()
```

第一次检查避免每次调用都加锁（无竞争时的快速路径）。第二次检查确保只有一个 goroutine 执行 f。

**恰好一次语义的形式保证**：

设 $C$ 为执行计数器，取值 $\{0, 1\}$ ：
1. $C = 0$ 时，第一个调用者获得锁并执行 $f$ ，设置 $C = 1$
2. $C = 1$ 时，后续所有调用者检测到 $C = 1$ ，跳过执行
3. 锁的互斥性保证 $f$ 不会并发执行

### 机制

**Once 的实现原理**：内部使用一个 mutex + 一个 done 标记。首次调用 `Do(f)` 时，检查 done，若为 0，则加锁、执行 f、设置 done=1。之后所有调用检查 done 后直接返回，不加锁。

**为什么比双重检查更优**：双重检查在 Java 中需要 volatile，在 Go 中虽然 map 不是线程安全，但 `sync.Once` 保证了初始化的幂等性，同时避免了每次获取锁的开销。

### 参考存根

```go
var once sync.Once
var instance *DB

func getInstance() *DB {
    once.Do(func() {
        instance = &DB{}
    })
    return instance
}
```

## sync.Map（并发安全 map）

### 定义

`sync.Map` 内部采用读写分离优化（read + dirty 双结构），适合读多写少且 key 集合稳定的场景。

### 数学模型

**sync.Map 的状态机**：

```
read: atomic.Value[readOnly]  // 只读结构，共享指针
  ├── entries: map[string]any  // 指针共享，无锁读取
  └── amended: bool            // dirty 是否有 read 没有的 key

dirty: map[string]any          // 写操作目标
mu: Mutex                      // 写锁
misses: int                    // 统计 read 未命中次数
```

**Load 操作复杂度**：
$T_{load}(key) = \begin{cases} O(1) & \text{key 在 read 中} \\ O(1) + \text{锁} & \text{key 在 dirty 中} \end{cases}$

**miss 计数器的语义**：

每次 Load 在 read 中未找到 key 时，misses++。当 $misses \ge |dirty|$ 时，将 dirty 提升为新的 read：
$\text{misses} \geq |dirty| \implies \text{dirty} \to \text{read}, \text{misses} = 0$

### 机制

**read 和 dirty 的分离**：
- read：只读结构，存储所有数据（指针共享），无锁读取
- dirty：写操作的目标，包含 read 中不存在的新增 key

**性能来源**：大多数读取命中 read，无需加锁。只有 read 中不存在时（miss）才访问 dirty，并提升到 read。

**适用条件**：
- 读多写少（读不写，写操作少）
- key 集合稳定（少有新增删除）
- 无需精确计数（Store/Load/Delete 语义）

**违反适用条件的代价**：写多时 dirty 频繁升级，性能退化至不如普通 mutex+map。

## errgroup 协调多个 goroutine

### 定义

`golang.org/x/sync/errgroup` 将多个 goroutine 的错误汇聚：任一失败时通过 context cancel 其他 goroutine，实现"快速失败"语义。

### 数学模型

**错误汇聚的短路语义**：

设 $E = \{e_1, e_2, \ldots, e_n\}$ 为 goroutine 返回的错误集合。

errgroup 返回第一个非 nil 错误：
$\text{errgroup.Wait}() = \begin{cases} \min_{i}\{e_i | e_i \neq nil\} & \text{若 } \exists e_i \neq nil \\ nil & \text{否则} \end{cases}$

其中 $\min$ 表示"最早到达"（由调度顺序决定），而非数值最小。

**取消信号的传递**：

当第一个 goroutine 返回非 nil 错误时：
$e_i \neq nil \implies \forall j \neq i: ctx.Err() \neq nil$

这保证了其他 goroutine 能够感知到失败并主动退出。

### 机制

**快速失败语义**：当一个子任务失败时，其他仍在运行的任务应立即停止。这通过 context cancel 实现：
1. 任一 goroutine 返回非 nil error
2. `errgroup` 调用 `cancel()` 通知 context
3. 其他 goroutine 的 `ctx.Done()` 收到信号，主动退出

**错误汇聚的数学约束**：最多传递一个 error（第一个返回的），其他 error 被丢弃。这是**短路语义**的经济实现。

## Worker Pool 模式

### 定义

Worker Pool 预创建固定数量 goroutine 从 job channel 消费任务——避免了无限制创建 goroutine 导致的调度负担和内存爆炸。

### 数学模型

**无限 goroutine 的内存成本**：每个 goroutine 栈最小 2KB，若创建 10,000 个，则栈占用 20MB。即使实际使用不到 1KB，栈空间也已分配。

**Worker Pool 的资源约束**：
$Memory_{workerpool} = N_{workers} \times 2\text{KB} + queue\_size \times sizeof(job)$

通过固定 $N_{workers}$ ，内存可控。

**吞吐量的形式化模型**：

设任务处理时间为 $T_{task}$ ，Worker Pool 吞吐量为：
$\text{Throughput} = \frac{N_{workers}}{T_{task}}$

但若 $T_{task}$ 变化大，实际吞吐量受最慢任务影响（HOL blocking）。

**HOL Blocking 的数学描述**：

当任务队列按 FIFO 顺序处理时：
$\text{Throughput}_{actual} = \min\left(\frac{N_{workers}}{T_{slowest}}, \lambda_{arrival}\right)$

其中 $T_{slowest}$ 是最长任务的处理时间， $\lambda_{arrival}$ 是任务到达速率。

**调度公平性**：工作窃取保证负载均衡，但任务大小不一时可能出现短任务饿死长任务。

## 优雅关闭（Graceful Shutdown）

### 定义

Graceful Shutdown 通过 `signal.Notify` 捕获 OS 信号，调用 `server.Shutdown(ctx)` 停止接受新请求并等待正在处理的请求完成。

### 数学模型

**优雅关闭的两阶段形式化**：

```
Phase 1: 停止接受新请求
  listener.Close() → 不再接受新连接
  现有连接继续处理

Phase 2: 等待现有请求完成
  对于每个 in-flight 请求：
    若 ctx 未超时 → 继续处理
    若 ctx 超时 → 中断处理
```

**资源清理的约束**：

优雅关闭必须满足：
$\forall \text{connection}: \text{close}(conn) \text{ 在所有请求处理完成后}$

### 机制

**两阶段关闭**：
1. **停止接受新请求**：关闭 listener，HTTP 服务器不再接受新连接
2. **等待现有请求完成**：所有 in-flight 请求在 ctx 超时前继续处理

**ctx 超时的作用**：防止某个请求永远不完成导致服务无法关闭。

**约束条件**：
- 若 ctx 超时设置为 0，则立即放弃等待
- 某些请求可能永远无法完成（如 WebSocket 长连接）

## 避免 Goroutine 泄漏

### 定义

goroutine 无法被 GC 回收，只能通过 channel 或 context 取消——无缓冲 send 如果没有接收者会永久阻塞，这正是 goroutine 泄漏的根源。

### 数学模型

**goroutine 状态与资源**：
$S_G \in \{\text{运行}, \text{阻塞}, \text{等待}\}$

- 运行中：占用 CPU + 栈内存（2KB-1GB 可变）
- 阻塞（channel send/receive）：不占 CPU，但栈内存无法释放
- 等待（select + channel）：等待条件满足

**泄漏条件的形式化**：goroutine G 泄漏当：
$\exists S_G(G) = \text{阻塞} \land \neg \text{channel\_ready}(ch) \land \text{无人持有 } G \text{ 的引用}$

**泄漏的数学检测**：
- 若 goroutine 状态为阻塞且等待事件集合为空（或永不满足），则泄漏
- 实际中通过 tracing 观测 goroutine 数量是否收敛判断

### 数据流

<pre>
泄漏场景：
  ch := make(chan []byte)          // 无缓冲，无人接收
  go func() { ch <- fetch(url) }  // 永久阻塞在 send

修复方案（缓冲 channel）：
  ch := make(chan []byte, 1)      // 缓冲容量 1
  select {
  case ch <- data:
  case <-ctx.Done():
      // context 取消时退出
  }

修复方案（context 取消）：
  func safeFetch(ctx context.Context, url string) <-chan []byte {
      ch := make(chan []byte, 1)
      go func() {
          data, _ := fetch(url)
          select {
          case ch <- data:
          case <-ctx.Done():
              // 被取消，goroutine 退出
          }
      }()
      return ch
  }
</pre>

## sync.Cond 条件变量

### 定义

`sync.Cond` 基于互斥锁实现条件等待：一个 goroutine 在 `cond.Wait()` 中自动释放锁并阻塞，另一个在满足条件时通过 `Signal/Broadcast` 唤醒等待者。

### 数学模型

**Wait 的原子性保证**：

```go
func (c *Cond) Wait() {
    c.L.Lock()
    // 原子操作序列：
    //  1. 将当前 goroutine 加入 waiter 列表
    //  2. 释放锁 L
    //  3. 阻塞当前 goroutine
    // （被唤醒时自动重新获取 L）
    c.L.Unlock()
}
```

Wait 的原子性由 runtime 保证：释放锁和阻塞之间不会被打断。

**Signal 的唤醒语义**：

Signal 唤醒等待时间最长的 goroutine（但不保证 FIFO）：
$\text{Signal} \implies \exists G: G \in \text{waiters} \land G \text{ 被唤醒}$

**Broadcast 的广播语义**：

Broadcast 唤醒所有 waiter：
$\text{Broadcast} \implies \forall G \in \text{waiters}: G \text{ 被唤醒}$

### 机制

**Wait 的原子性**：cond.Wait() 在阻塞前自动释放锁，在被唤醒时重新获取锁。这保证了 signal 发生时锁的状态一致性。

**Signal vs Broadcast**：
- Signal：唤醒一个等待者（通常唤醒等待时间最长的）
- Broadcast：唤醒所有等待者

**典型用法**：条件不满足时 Wait，条件满足时 Signal/Broadcast。

### 参考存根

```go
cond := sync.NewCond(&sync.Mutex{})
ready := false

go func() {
    cond.L.Lock()
    for !ready {
        cond.Wait()
    }
    cond.L.Unlock()
    fmt.Println("ready is true, proceeding")
}()

cond.L.Lock()
ready = true
cond.Signal()  // 唤醒一个等待者
cond.L.Unlock()
```
