# 内存管理

> **版本关系**：Go 1.24（stable）→ Go 1.26（<latest>）。内存管理核心机制不变，Go 1.26 优化了 GC 调度和内存限制精度。

## 定义

Go 内存管理是自动的，但编译器通过逃逸分析决定变量分配到栈（极快，函数返回自动释放）或堆（GC 管理），这决定了程序的内存布局和 GC 压力。

**归约终点**：Go 内存管理可归约为**编译器驱动的分配策略选择 + 运行时并发三色标记 GC**，两者共同实现免手动内存管理的性能与安全性平衡。

## 逃逸分析（escape analysis）

### 定义

逃逸分析是编译器静态判断变量应该分配在栈还是堆的过程：变量如果"逃逸"（其指针超出函数作用域），就必须分配在堆上。

### 数学模型

**逃逸条件的形式化**：

变量 $v$ 逃逸当且仅当存在引用 $ref(v)$ 使得 $ref(v)$ 的作用域大于 $v$ 的字面作用域：

$\text{escapes}(v) \iff \exists p \in \text{refs}(v): \text{scope}(p) \supset \text{scope}(v)$

**逃逸路径分析**：
- 若 $v$ 的地址被返回（`return &v`）→ $v$ 逃逸
- 若 $v$ 的地址被写入 channel、interface{}、全局变量 → $v$ 逃逸
- 若 $v$ 的地址传播到已逃逸的变量 → $v$ 逃逸

**逃逸分析的复杂度**：

逃逸分析是**流敏感、路径敏感**的静态分析。设函数有 $N$ 条执行路径，逃逸分析需跟踪每条路径上变量的引用关系：

$T_{escape} = O(N \times |CFG|)$

其中 $|CFG|$ 是控制流图的大小。实际编译器实现使用高效的上下文敏感分析。

**归约终点**：逃逸分析可归约为**指针别名分析**，问题是确定哪些指针可能指向哪些变量。

### 数据流

<pre>
编译期逃逸分析过程：

  func foo() *int {
      i := 10            // i 分配在栈上
      return &i          // &i 被返回，指向栈内存
  }                     // 函数返回，栈帧被回收
                        // 但堆上有 i 的副本（逃逸）
                        // → 编译器将 i 直接分配在堆上

等价转换（编译器行为）：
  func foo() *int {
      i := heapAlloc(int, 10)  // 逃逸分析决定在堆上分配
      return &i
  }

接口逃逸：
  var i interface{} = 42
  fmt.Println(i)

  42 被装箱（boxing），装箱后的对象逃逸到堆
  因为 interface{} 可以被传递到任何地方
</pre>

### 机制

**为什么编译器决定而非运行时决定**：运行时决定需要维护对象的引用计数或使用 tracing GC，成本高。编译期静态分析可以提前决定分配位置，减少运行时开销。

**逃逸分析的准确性**：编译器使用流敏感、路径敏感的静态分析，尽可能保守（能证明不逃逸就栈分配）。无法证明时，保守地分配到堆。

**约束条件**：
- 逃逸分析是近似的，无法处理间接引用
- 某些情况下会保守地逃逸（即使实际不逃逸）

**违反约束的后果**：不必要的堆分配增加 GC 压力，但不会导致功能错误。

## GC 工作原理

### 定义

Go 采用三色标记并发 GC，目标是暂停时间 < 100μs（而非传统的 100ms）。STW 仅发生在 Mark Start 和 Mark Termination 两个极短阶段。

### 数学模型

**GC 暂停时间模型**：
- 传统 GC 暂停时间： $T_{pause} \propto N_{heap}$ （堆越大暂停越长）
- Go 并发 GC 暂停时间： $T_{pause} \approx O(\log N_{goroutine})$ （只扫描 goroutine 栈根）

**三色标记的数学性质**：

强三色不变性（Strong Tricolor Invariant）：
$\forall (b, w) \in E: b \text{ 是黑色的} \implies w \text{ 不是白色的}$

弱三色不变性（Weak Tricolor Invariant）：
$\forall w \in W: \exists g \in G: (g, w) \in E$

其中 $E$ 是引用边， $G$ 是灰色节点集合， $W$ 是白色节点集合。

**标记完成判定**：
$|G| = 0 \iff \text{Mark 阶段完成}$

当灰色集合为空时，所有可达对象已标记。

**GC 触发条件**：

$T_{trigger} = Memory_{lastGC} \times \left(1 + \frac{GOGC}{100}\right)$

GOGC=100 表示内存增长到上次 GC 后的 2 倍时触发 GC。

**Write Barrier 的形式化**：

在并发标记期间，Write Barrier 确保不破坏三色不变性：
$\text{WriteBarrier}(src, dst) \implies \begin{cases} \text{markGray}(dst) & \text{if } src \text{ 是黑色的} \\ \text{no-op} & \text{otherwise} \end{cases}$

### 数据流

<pre>
三色标记并发 GC：

Phase 1: Mark Start (STW, ~10-100μs)
  所有 goroutine 停止
  扫描全局变量和 goroutine 栈 → 标记根对象为灰色
  所有 goroutine 恢复

Phase 2: Mark (并发)
  灰色对象引用的对象 → 标记为灰色
  原灰色对象 → 标记为黑色
  重复直到没有灰色对象

Phase 3: Mark Termination (STW, ~10-100μs)
  所有 goroutine 停止
  完成最终标记，清理未标记对象
  所有 goroutine 恢复

Phase 4: Sweep (并发)
  遍历堆，回收未标记对象的内存
  不需要停止 goroutine

颜色状态机：
  白色 ──(扫描引用)──→ 灰色 ──(完成扫描)──→ 黑色
                          ↑
                          │
                    白色节点被灰色节点"保护"
                    防止黑色节点指向白色节点（破坏强三色不变性）
</pre>

### 机制

**为什么需要 STW 的 Mark Start**：并发标记开始前，必须停止所有 goroutine 以获取一致的根集合（栈帧、全局变量）。若 goroutine 继续运行，可能修改引用关系导致漏标或错标。

**Write Barrier 的作用**：在并发标记期间（Phase 2），应用程序仍在运行并可能修改堆引用关系。Write Barrier 拦截这些修改，确保不破坏三色不变性：
- 若将白色对象引用写入黑色对象 → 标记白色对象为灰色（保护）

**约束条件**：
- 标记必须在一个 GC cycle 内完成
- 若标记期间内存分配过快，可能导致".mark for"状态

**违反约束的后果**：若三色不变性被破坏，则可能产生悬挂指针（已死对象被误认为存活），导致内存泄漏或访问已释放内存。

## 垃圾回收（GC）

### 定义

Go 的 GC 是并发的、非分代的、基于三色标记的垃圾回收器。

### GC 阶段

| 阶段 | 说明 | STW |
|------|------|-----|
| Mark Start | 停止 Goroutine，准备标记 | 是（~10-100μs） |
| Mark | 并发标记可达对象 | 否 |
| Mark Termination | 完成标记，清理 | 是（~10-100μs） |
| Sweep | 并发清扫未使用对象 | 否 |

**GOGC 环境变量**：GOGC=100 表示内存增长到上次 GC 后的 2 倍时触发 GC。
$T_{trigger} = Memory_{lastGC} \times \left(1 + \frac{GOGC}{100}\right)$

## 内存分配

### 定义

Go 的内存分配器是 TCMalloc 的变体，将内存分为小对象（< 32KB）和大对象（>= 32KB）分别处理。

### 栈 vs 堆

| 特性 | 栈 | 堆 |
|------|-----|-----|
| 分配速度 | 极快（移动栈指针） | 较慢（需要分配算法） |
| 释放 | 自动（函数返回） | GC 管理 |
| 大小 | 较小（KB 级） | 较大（GB 级） |
| 内存布局 | 连续 | 可能碎片化 |

### 数学模型

**分配策略阈值**： $S_{threshold} = 32\text{KB}$
- $S < 32\text{KB}$ ：先尝试栈，逃逸则堆分配
- $S \geq 32\text{KB}$ ：直接堆分配

**TCMalloc 分层模型**：
- mcache：每个 P 的本地缓存（无锁）
- mcentral：每个 size class 的全局缓存（需要加锁）
- mheap：全局堆分配器（需要加锁）

**分配延迟的数学期望**：
- mcache 命中： $T_{alloc} \approx O(1)$ （极快）
- mcentral 请求： $T_{alloc} \approx O(1)$ + 锁竞争
- mheap 请求： $T_{alloc} \approx O(\log N_{free})$ + 锁竞争

其中 $N_{free}$ 是空闲对象数量。

**mcache 本地化的数学保证**：

每个 P 拥有独立的 mcache，因此：
$P_i.\text{mcache} \cap P_j.\text{mcache} = \emptyset \text{ (当 } i \neq j \text{ 时)}$

这保证了 mcache 分配无需任何锁，因为每个 P 只能在自己的 mcache 上操作。

**mcentral 的竞争模型**：

mcentral 是多个 P 共享的，因此：
$T_{mcentral} = O(1) + O(\text{锁竞争})$

锁竞争程度取决于 size class 的热度。

### 数据流

<pre>
分配路径（小对象 < 32KB）：

  请求：alloc(100 bytes)

  mcache（本地缓存）:
    ├─ size class = 100
    ├─ 检查 mcache.slots[sc] 是否有空闲对象
    ├─ 有 → 返回对象，弹出（无锁）
    └─ 无 → 向 mcentral 请求新 span

  mcentral:
    ├─ 检查 central[sc].nonempty span
    ├─ 有 → 移动 span 到 mcache，返回对象
    └─ 无 → 向 mheap 请求新 span

  mheap:
    ├─ 从 free list 分配 span
    ├─ span 是连续页面（通常 8KB 页）
    └─ 切分为相同 size class 的对象

大对象（>= 32KB）：

  直接从 mheap 分配：
    ├─ 分配 N 个连续页面
    └─ 不经过 mcache/mcentral
</pre>

**分配的所有权转移**：

```
mcache: 空闲对象列表头
    │
    ├── pop() → 返回对象指针
    │         所有权：从 mcache 转移到调用方
    │
    ▼
若 mcache 空：
  mcentral: span（内存块）
    │
    ├── 获取 span 的所有权
    ├── 将 span 切分为对象
    │
    ▼
若 mcentral 空：
  mheap: 页面（Page）
    │
    ├── 从 free list 分配页面
    ├── 组成 span
    │
    ▼
返回对象指针
```

## 减少分配技巧

### sync.Pool（对象池）

### 定义

`sync.Pool` 通过缓存临时对象减少 GC 压力，对象在 GC 时可能被清除。

### 数学模型

**Pool 的生命周期模型**：

```go
type Pool struct {
    local     []poolsLocal  // 每个 P 一个
    // ...
}

type poolsLocal struct {
    poolLocal
    // ...
}

type poolLocal struct {
    private any  // 只能被一个 P 访问
    shared  []any  // 可以被任何 P 访问
}
```

**GC 清除语义**：

Pool 在 GC 时可能被清除，形式化：
$\text{during GC}: \forall p \in \text{Pool}: p.\text{shared} = \emptyset$

**为什么设计为不确定**：若 Pool 明确保留对象，GC 无法回收这些内存，导致内存压力增加。不确定性换取了内存可控性。

### 机制

**生命周期**：Pool 中的对象在 GC 时可能被清除（被回收）。这意味着 Pool 不能用于存储持久对象。

**用途**：适合"用完即丢弃"的对象，如 bytes.Buffer、Parser 等临时对象。

**约束条件**：
- 对象可能在任何 GC cycle 被回收
- 不能依赖 Pool 返回特定对象
- 并发安全，无需加锁

**违反约束的后果**：若将持久状态存入 Pool，GC 后状态丢失。

### 预分配容量

```go
s := make([]int, 0, 1000)  // 预分配，避免多次扩容
```

## 内存分析（pprof）

### 定义

pprof 是 Go 内置的性能分析工具，通过采样收集 CPU、内存、goroutine 等信息，生成火焰图或文本报告。

### 数学模型

**采样定理**：pprof 基于统计学采样，采样频率 $f$ 决定精度。 $f$ 越高，精度越高，但开销越大。

**统计显著性**：要检测到 5% 的 CPU 差异，需要足够长的采样时间（通常 30s+）。

**采样偏差的数学描述**：

设真实 CPU 时间为 $T_{true}$ ，采样估计为 $\hat{T}$ ：
$\hat{T} = T_{true} \times \frac{\text{采样命中数}}{\text{实际执行次数}}$

当采样频率足够高时，偏差 $|\hat{T} - T_{true}|$ 可控制在 $\epsilon$ 以内。

### pprof 分析命令

```bash
go tool pprof http://localhost:6060/debug/pprof/profile?seconds=10
(pprof) top -10
(pprof) list funcName
(pprof) web  # 需要 Graphviz
```

## 内存监控

### runtime MemStats

```go
import "runtime"

var m runtime.MemStats
runtime.ReadMemStats(&m)

fmt.Printf("Alloc: %v KB\n", m.Alloc/1024)
fmt.Printf("HeapInuse: %v KB\n", m.HeapInuse/1024)
fmt.Printf("NumGC: %d\n", m.NumGC)
```

### GOGC 与内存限制

```go
debug.SetMemoryLimit(1024 * 1024 * 1024)  // 1GB
oldLimit := debug.SetMemoryLimit(-1)

// GOMEMLIMIT=8GB + GOGC=100 → 内存敏感场景
// GOGC=50 → 更积极回收，内存占用小
```

### debug.SetMemoryLimit 的数学约束

$Memory_{limit} = \text{HardLimit}$

当堆内存达到 $Memory_{limit} \times (1 + \frac{GOGC}{100})$ 时，GC 被强制触发。

**HardLimit 的约束**：

当堆内存接近 HardLimit 时：
$\text{HeapInuse} \approx \text{HardLimit} \implies \text{GC 强制触发}$

这可能导致 GC 频率增加，从而增加 CPU 开销。
