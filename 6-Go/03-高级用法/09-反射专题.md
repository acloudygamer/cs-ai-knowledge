# 反射专题

## 定义

反射是 Go 在**运行时**检查和操作对象的能力，通过 `reflect` 包实现。程序可以动态获取类型、调用方法、修改变量值。其本质是**编译器在运行时镜像出一个类型系统**——将编译时已知的类型信息以结构体形式暴露给程序。

反射开销较大（比直接操作慢 10-100 倍），应避免在热路径使用。

## 数学模型

### reflect.Type 的类型图

```
reflect.Type 本质是编译时类型的元描述：

对于任意类型 T：
  reflect.TypeOf(x) 返回 *reflect.rtype

*reflect.rtype 包含：
  - size:   uintptr  // 类型大小
  - align:  uint8    // 对齐
  - kind:   Kind     // 基础种类（int, string, struct...）
  - data    unsafe.Pointer // 指向类型数据的指针

Kind 集合（枚举）：
  Invalid, Bool, Int, Int8, Int16, Int32, Int64,
  Uint, Uint8, Uint16, Uint32, Uint64, Uintptr,
  Float32, Float64, Complex64, Complex128,
  Array, Chan, Func, Interface, Map,
  Ptr, Slice, String, Struct, UnsafePointer
```

### reflect.Value 的双重性

```
reflect.ValueOf(x) 返回 reflect.Value：
  ┌─────────────────────────────────────┐
  │ reflect.Value                        │
  │  struct {                            │
  │      typ  *rtype    // 类型描述      │
  │      ptr  unsafe.Pointer // 数据指针  │
  │      flag uintptr     // 元数据标志  │
  │  }                                   │
  └─────────────────────────────────────┘

Value 既是 "类型的值" 也是 "可寻址的左值"：
  - CanSet() = true  → 可以修改（必须通过指针获取）
  - CanSet() = false → 只能读取（值传递的副本）
```

**归约终点**：反射的代价可归结为**运行时类型查询的成本**，包括元数据查找、边界检查、内存分配。

### 反射调用的性能模型

```
直接调用：      T.Method(args)     → O(1)
反射调用：      v.MethodByName(...) → O(类型元数据查询 + 方法查找 + call)

反射调用开销分解：
  T_method_lookup = O(1)  // 编译时已知，map 查找
  call_indirect   = O(1)  // 函数指针调用
  但每次反射调用包含：
    - TypeOf   的边界检查
    - MethodByName 的字符串比较
    - ValueOf  的内存分配

实测：反射调用比直接调用慢 10-100x
     主要来自边界检查和字符串比较，而非间接调用本身
```

## 数据流

### 动态方法调用的执行流

<pre>
reflect.ValueOf(fn)
    │
    ├── typ = &rtype{kind: Func}
    ├── ptr = fn 的函数指针
    └── flag = 0
    │
    ▼
v.Call(args)
    │
    ├── 检查 v.flag & flag.method != 0
    ├── 获取函数指针：v.ptr（直接是 func 值）
    ├── 将 []reflect.Value 转换为 []interface{}
    │
    ▼
函数指针调用（间接）
    │
    ▼
返回 []reflect.Value
</pre>

### 字段标签的读取数据流

<pre>
type User struct {
    Name string `json:"name" validate:"required"`
}

t := reflect.TypeOf(User{})
    │
    ├── t.Kind() == Struct
    ├── for i := 0; i < t.NumField(); i++
    │       │
    │       ▼
    │   field := t.Field(i)
    │       │
    │       ├── field.Name = "Name"
    │       ├── field.Type = string
    │       └── field.Tag = reflect.StructTag(`json:"name" validate:"required"`)
    │               │
    │               └── field.Tag.Get("json") → "name"
    │
    ▼
遍历字段 → 按名查找 → 读取标签
</pre>

### 接口与类型断言的关系

<pre>
writerType := reflect.TypeOf((*io.Writer)(nil)).Elem()
    │
    ├── (*io.Writer)(nil) 是 nil 指针，类型是 *io.Writer
    ├── .Elem() 获取指针指向的类型：io.Writer
    │
    ▼
t.Implements(writerType)
    │
    ├── 检查 t 的方法集合 ⊇ writerType 的方法集合
    ├── 方法集合包含性判断：逐个比较方法签名
    │
    ▼
bool: 当前类型是否实现了 io.Writer
</pre>

## 机制

### 为什么反射慢？

反射的性能损失来自多个层次：

1. **类型推断的运行时开销**：`reflect.TypeOf` 需要查询类型的元数据，而不是直接访问编译时已知的信息
2. **字符串比较**：`MethodByName`、`FieldByName` 需要字符串比较（O(method_count) 或 O(field_count)）
3. **内存分配**：`reflect.ValueOf` 在堆上分配 `reflect.Value` 结构体
4. **边界检查**：每次字段/方法访问都检查 `CanSet` 等条件

但最大的开销是**编译器优化被阻止**——Go 编译器无法内联通过反射调用的函数，也无法进行逃逸分析优化。

### CanSet 的约束条件

`CanSet()` 检查的是**左值性**（addressability）：

```
var x int = 10
v := reflect.ValueOf(x)    // v.CanSet() = false（值传递，x 的副本）
vp := reflect.ValueOf(&x) // vp.CanSet() = false（vp 本身不可修改）
ve := vp.Elem()           // ve.CanSet() = true（解引用后是 x 本身）

根本原因：Go 的值传递语义——
  反射只能修改"通过指针指向的变量"，不能修改"值传递的副本"
```

### 反射与泛型的选择

| 场景 | 推荐 | 原因 |
|------|------|------|
| 类型在编译时已知 | 直接类型操作 | 零反射开销 |
| 类型在编译时未知，行为相同 | 泛型（Go 1.18+） | 编译时多态，无运行时开销 |
| 类型在编译时未知，行为依赖类型 | 反射 | 运行时动态分派 |
| 需要操作结构体字段名 | 反射 | 泛型无法按名字访问字段 |

## 常见错误

| 错误 | 原因 | 正确做法 |
|------|------|----------|
| `v.SetInt(20)` panic | ValueOf 返回副本，不可设置 | `reflect.ValueOf(&x).Elem().SetInt(20)` |
| 反射结果未检查 CanSet | 直接 Set 可能 panic | `if v.CanSet()` |
| 误用 Type 与 Kind | Type 是类型名，Kind 是种类 | `t.Kind() == reflect.Struct` |
