# 依赖注入

> **版本关系**：Go 1.24（stable）→ Go 1.26（<latest>）。依赖注入模式不变，wire 和 fx 框架稳定。

## 定义

依赖注入（DI）是通过**外部注入依赖**而非内部创建，提高可测试性和可维护性的设计模式。Go 中惯用**构造函数参数注入**，框架层提供 Wire（编译时）和 fx（运行时）两种自动化方案。

**归约终点**：依赖注入的构建顺序可归结为**有向无环图的拓扑排序**，循环依赖是唯一约束。

## 数学模型

### 依赖图的拓扑排序

```
依赖图：
  App → UserService → Repository → Database
                 ↘ Logger

拓扑排序（执行顺序）：
  1. Logger（无依赖）
  2. Database（无依赖）
  3. Repository（依赖 Database）
  4. UserService（依赖 Repository, Logger）
  5. App（依赖 UserService）

约束：若依赖图存在环 A→B→C→A，则无法拓扑排序
     → 循环依赖
```

**拓扑排序的存在性**：

$G \text{ 可拓扑排序} \iff G \text{ 是 DAG（有向无环图）}$

### Wire 的编译时解析

Wire 在**编译时**通过代码生成解析依赖图：

```go
// wire.go
func InitializeApp() (*App, error) {
    // 用户声明
}

// wire_gen.go（自动生成）
func InitializeApp() (*App, error) {
    // 编译器插入：
    //  db := NewDatabase()     // 先构造
    //  repo := NewRepository(db) // 后构造
    //  logger := NewLogger()    // 并行构造（无依赖）
    //  svc := NewUserService(repo, logger) // 最后构造
    //  return &App{svc}, nil
}
```

**Wire 的正确性约束**：

1. 所有 Provider 必须有对应依赖
2. 依赖图必须无环
3. Injector 函数必须返回 error

### fx 的运行时反射构建

fx 在**运行时**通过反射扫描所有 Provider，构建依赖图：

```
Provider 是返回值的函数：
  func NewLogger() *Logger     → 提供 Logger
  func NewDB() *sql.DB        → 提供 Database
  func NewRepo(*sql.DB) *Repo → 依赖 Database，提供 Repo

fx 内部：
  1. 收集所有 Provider 的返回值类型
  2. 构建有向图：返回值类型 → 参数类型
  3. 拓扑排序得到构造顺序
  4. 按顺序调用，缓存结果（单例或 Prototype）
```

**fx 的正确性条件**：
- 所有依赖必须被提供
- 不能有循环依赖
- 参数类型必须匹配

**fx 的依赖图构建**：

设 Provider 函数为 $P_i$ ，其参数类型为 $T_{i,j}$ ，返回类型为 $R_i$ ：
$依赖关系：R_i \rightarrow T_{i,j} \text{ 对所有 } j$

## 数据流

### 手动 DI 的依赖注入流

<pre>
App{}
    │
    │ 构造时注入
    ▼
NewApp(UserService, Logger)
    │
    ├── NewUserService(Repository, Logger)
    │       │
    │       ├── NewRepository(Database)
    │       │       │
    │       │       └── NewDatabase() → 真实/ mock DB
    │       │
    │       └── NewLogger() → 真实/ mock Logger
    │
    └── 返回 *App
</pre>

### fx 的生命周期钩子流

<pre>
fx.New(Provide..., Invoke...)
    │
    ├── 拓扑排序所有 Provider
    ├── 按顺序构造（依赖注入）
    │
    ├── 注册 OnStart 钩子
    │       │
    │       ▼
    │   server.Start()  ← 阻塞直到启动完成
    │
    ├── 应用运行...
    │
    ├── 收到 SIGINT/SIGTERM
    │
    └── 执行 OnStop 钩子
            │
            ▼
        server.Stop()  ← 优雅关闭
</pre>

## 机制

### 为什么 DI 优于内部创建？

```
内部创建（Bad）：
  type Service struct { db *DB }
  func (s *Service) Do() {
      s.db = &DB{}  // 每次调用可能重建，测试时无法替换
  }

依赖注入（Good）：
  type Service struct { db DB }
  func NewService(db DB) *Service { return &Service{db: db} }
  // 测试时传入 mockDB，生产时传入真实DB
```

关键区别：
- **控制反转（IoC）**：构造逻辑从使用方转移到外部
- **可替换性**：依赖的具体实现可自由替换
- **可测试性**：测试可传入 mock/fake 实现

**约束条件**：
- 接口必须足够小（单一职责）
- 接口隔离避免传递不必要的依赖

### Wire vs fx 的权衡

| 特性 | 手动 DI | Wire（编译时） | fx（运行时） |
|------|--------|----------------|-------------|
| 运行时开销 | 无 | 无 | 有（反射+图构建） |
| 循环检测 | 手动 | 编译时 | 运行时报错 |
| 延迟加载 | 支持 | 否（全量构造） | 支持 |
| 条件构造 | 易实现 | 困难 | 支持 |
| 复杂度 | 低 | 中 | 高 |
| 重构安全性 | 低 | 高 | 中 |

### 循环依赖的检测与解决

```
循环依赖：A → B → A

Wire 检测：编译时报错（无法生成拓扑序）
fx 检测：启动时报错（reflect 无法构建拓扑序）

解法：引入接口打断循环
  A 依赖 InterfaceB（接口）
  B 实现 InterfaceB
  A 不直接依赖 B，而是依赖 InterfaceB
```

**打破循环的数学约束**：

$A \rightarrow B \rightarrow A \implies \exists I: A \rightarrow I \leftarrow B$

引入接口 $I$ 打断循环， $A$ 依赖接口  $I$， $B$ 实现接口  $I$。

## 框架对比

| 特性 | 手动 | Wire | fx |
|------|------|------|-----|
| 运行时开销 | 无 | 无 | 有（反射） |
| 循环检测 | 手动 | 自动 | 自动 |
| 生命周期 | 手动 | 手动 | 内置 |
| 延迟加载 | 支持 | 否 | 支持 |
| 条件构造 | 易 | 难 | 支持 |

## 常见陷阱

```
循环依赖：  A→B→A  → 用接口解耦
初始化顺序：wire/fx 自动解析，但 init() 应避免
内存泄漏：  持有不需要的依赖引用
 Provider 错误：若返回 error 而未处理，fx 会终止应用
```

### Provider 返回错误的语义

```go
func NewDB() (*sql.DB, error) {
    db, err := sql.Open("postgres", connStr)
    if err != nil {
        return nil, err  // fx 会终止应用
    }
    return db, nil
}
```

**约束**：Provider 的 error 必须被处理，fx 没有"忽略错误"的选项。

## DI 的测试策略

### Mock 注入

```go
// 生产代码
type UserService struct {
    repo Repository
}

func NewUserService(repo Repository) *UserService {
    return &UserService{repo: repo}
}

// 测试代码
type mockRepo struct{}

func (m *mockRepo) FindByID(id int) (*User, error) {
    return &User{ID: id, Name: "test"}, nil
}

svc := NewUserService(&mockRepo{})
```

**约束**：Mock 必须实现相同的接口，否则编译失败。

### 接口隔离与测试

```
问题：若接口过大，Mock 实现困难

解法：接口隔离（ISP）
  type Reader interface { Read() }
  type Writer interface { Write() }

  // 只需要 Read 时，传入 Reader 而非完整接口
```

**接口隔离的原则**：

$|I| \text{ 应最小化} \implies \text{ Mock 成本降低}$

## DI 的图灵等价性

**定理**：DI 框架可以实现任意依赖图的构造，因为依赖图是有向无环图。

**推论**：DI 的能力上限等于可拓扑排序的依赖图。
