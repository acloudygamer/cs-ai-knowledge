# Go 全景

> 后续：[01-语言核心/01-安装与第一个程序](../01-语言核心/01-安装与第一个程序.md)

> **版本基准**：Go 1.27（stable = latest，见 [versions.json](../../versions.json)）。本篇示例实测环境：go1.27.1 windows/amd64。

## 本质

Go 是一门**编译型、静态类型、带垃圾回收的语言，它的运行时不是外部进程而是链接进产物的一个库**。

最后半句是理解 Go 全部结构差异的起点。Java 的程序跑在 JVM 上，Python 的程序跑在 CPython 上，JavaScript 的程序跑在浏览器或 Node 上——运行时是程序**外面**的东西，所以有启动参数（`-Xmx`）、有独立进程、有版本要装。Go 的程序里，`runtime` 包和你的 `main` 包一起被链接进同一个可执行文件：

```console
$ go build -o hello.exe .
$ stat -c "%s bytes" hello.exe
2496512 bytes
$ go version -m hello.exe
hello.exe: go1.27.1
	path	example/hello
	build	-buildmode=exe
	build	-compiler=gc
	build	CGO_ENABLED=1
	build	GOARCH=amd64
	build	GOOS=windows
```

`go version -m` 读的是二进制里的元数据段，不是外部配置文件——产物自带它自己的一切。由此派生的三件事贯穿全库：

| 后果 | 表现 | 主场节 |
|---|---|---|
| 调度器在进程内 | `GOMAXPROCS` 是进程内变量，不是启动参数 | [03-运行时与内存/01](../03-运行时与内存/01-运行时总览与调度器.md) |
| GC 在进程内 | 调优靠 `GOGC` 环境变量，不是 JVM 那样的启动标志 | [03-运行时与内存/03](../03-运行时与内存/03-垃圾回收.md) |
| 部署是拷贝文件 | 无运行时依赖，容器镜像可以只有二进制本身 | [06-工程与工具链/05](../06-工程与工具链/05-构建交叉编译与发布.md) |

**边界**：这三条只在**纯 Go**（`CGO_ENABLED=0`）时完全成立。一旦用了 `cgo`，产物就依赖 C 运行时，静态链接与交叉编译的便利都要打折——这是 [03-运行时与内存/06](../03-运行时与内存/06-CGO与跨语言调用.md) 要付的账。

## 版图

Go 这门语言由四层构成，从下往上：

| 层 | 内容 | 规模（go1.27.1 windows/amd64 实测） | 主场节 |
|---|---|---|---|
| 规范 | 语法、类型系统、并发原语、包与可见性 | [Go Spec](https://go.dev/ref/spec) 一份文档 | [01-语言核心](../01-语言核心/) |
| 运行时 | 调度器、分配器、GC、栈管理、`reflect`、`unsafe` 支持 | 与产物一起链接 | [03-运行时与内存](../03-运行时与内存/) |
| 标准库 | `strings`、`io`、`net/http`、`database/sql`、`encoding/json` 等 | 385 个包 | [02-标准库](../02-标准库/)、[05-IO与外部世界](../05-IO与外部世界/) |
| 工具链 | `go build/test/fmt/vet/mod/doc` 等子命令 | 一个可执行文件 | [06-工程与工具链](../06-工程与工具链/) |

385 这个数字来自 `go list std | wc -l`。但一个程序实际用到多少，取决于它的依赖闭包——上面那个打印一行字符串的程序：

```console
$ go list -deps . | wc -l
65
```

65 个包（含 `main` 本身），全部来自标准库。`fmt` 一条 `Println` 就拖进了 `os`、`syscall`、`internal/abi`、`internal/bytealg`、`unicode/utf8` 等一整条链。这解释了下面这个反直觉的数字。

## 约束：编译速度是怎么换来的

Go 的设计目标来自 2007 年 Google 内部的一个具体处境。据 [官方 FAQ](https://go.dev/doc/faq)：

> Robert Griesemer, Rob Pike and Ken Thompson started sketching the goals for a new language on the white board on September 21, 2007.

他们当时面对的是三选一的困境——FAQ 的原话是：

> One had to choose either efficient compilation, efficient execution, or ease of programming; all three were not available in the same mainstream language.

Go 要同时要这三样。**编译速度**是其中最硬的一条约束，它决定了语言的好几处形状：

**一、没有头文件，没有预处理器。** C/C++ 的 `#include` 让同一个头文件在不同翻译单元里被重复解析，且声明与定义可以不一致。Go 的包只有一份源码，`import` 的是编译好的包对象（`.a` 归档里的导出数据），解析一次、复用多次。

**二、包级依赖图可并行编译，且无环。** Go 禁止循环导入，导入图是 DAG，因此编译可以按层并行。这条禁令不是洁癖——它换来的是编译顺序无歧义，以及**增量编译的边界就是包边界**。

**三、语法刻意留小。** 没有运算符重载、没有隐式类型转换、没有宏、没有模板元编程。语法小意味着解析器快，也意味着"读一段 Go 代码需要同时理解多少上下文"这件事有上界。

代价实测如下（同一台机器，`hello.exe` 的构建）：

```console
$ go clean -cache && time go build -o hello.exe .
real    0m5.382s          # 冷缓存：编译整个依赖闭包（65 包）

$ rm hello.exe && time go build -o hello.exe .
real    0m0.677s          # 热缓存：无源码改动，只重链接
```

5.382 秒对 0.677 秒的差距就是**构建缓存**的作用：Go 按"源码 + 编译标志 + 依赖的导出数据"的内容哈希缓存每个包的目标文件。改一个包只重编它和它的下游，其余直接取缓存。这也是为什么 Go 的编译速度在**增量**场景下最明显——冷启动并不比别的语言快一个数量级，快的是第二次之后。

**交叉编译不需要额外工具链**，也是这条约束的产物：编译器前后端分离，`GOOS`/`GOARCH` 只是两个变量。

```console
$ CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build -o hello_linux_arm64 .
$ file hello_linux_arm64
hello_linux_arm64: ELF 64-bit LSB executable, ARM aarch64, statically linked, ...
```

在 windows/amd64 上，一条命令直接产出 linux/arm64 的静态 ELF，不需要装交叉编译器。这在 C/C++ 里要配一整套工具链，在 Go 里是内置的——因为编译器自己生成目标代码，不经过系统汇编器与链接器（`CGO_ENABLED=0` 时）。

**约束的边界**：`CGO_ENABLED=1` 时这条路走不通。cgo 要调用系统的 C 编译器与链接器，交叉编译立刻退化成"你需要一套目标平台工具链"的老问题。这是 Go 生态里"能不能交叉编译"这个问题的唯一变量。

## 连接：Go 在本库语言谱系中的位置

| | 执行模型 | 并发 | 内存管理 | 错误处理 | 泛型 |
|---|---|---|---|---|---|
| [Python](../../2-Python/) | 解释执行（CPython 字节码） | GIL 限制的真线程 + 协程 | 引用计数 + 分代 GC | 异常 | 动态类型，无静态泛型 |
| [Java](../../4-Java/) | 字节码 + JIT | 线程 + JUC 库 + 虚拟线程 | 分代 GC | 异常 | 类型擦除泛型 |
| [JavaScript](../../5-JavaScript/) | 单线程事件循环 | 无（并发靠异步 I/O） | 分代 GC | 异常 | 无（由 TypeScript 外挂） |
| **Go** | **直接编译为机器码** | **goroutine（语言原语）** | **并发标记清扫 GC** | **错误是值** | **GC shape 单态化（1.18+）** |

四列里有三列 Go 都选了与另外三门**都不同**的答案，这三处正是本库为 Go 单列目录的依据：

- **并发是语言原语**（`go`/`chan`/`select` 是关键字）→ [04-并发](../04-并发/) 与 [01-语言核心](../01-语言核心/) 并列，不像 Java 的 [04-并发编程](../../4-Java/04-并发编程/) 那样挂在 JUC 库下。
- **运行时是库**→ [03-运行时与内存](../03-运行时与内存/) 讲的是"程序里那一半你没写的东西"，而 Java 的 [03-JVM与运行时](../../4-Java/03-JVM与运行时/) 讲的是"程序跑在谁上面"。
- **错误是值**→ 没有异常，`error` 是一个接口，[01-语言核心/10](../01-语言核心/10-错误处理.md) 与接口、泛型并列。

至于**编译速度换来的代价**，最直观的是那个 2,496,512 字节的产物：一个打印字符串的程序，因为静态链接了运行时与 65 个标准库包，比等价的 C 程序大两个数量级。Go 用二进制体积换部署零依赖，这笔账在容器与云原生时代是划算的——镜像里只需要一个文件，没有基础镜像、没有依赖解析、没有版本冲突。

## 从 2007 到 1.27

| 时间 | 事件 | 出处 |
|---|---|---|
| 2007-09-21 | Griesemer、Pike、Thompson 在白板上画出语言目标 | [Go FAQ](https://go.dev/doc/faq) |
| 2008-01 | Thompson 开始写编译器（最初输出 C 代码） | 同上 |
| 2008-05 | Ian Taylor 独立开始 GCC 前端（gccgo） | 同上 |
| 2008 年底 | Russ Cox 加入，推动语言与库从原型走向可用 | 同上 |
| 2009-11-10 | 作为公开开源项目发布 | 同上 |
| 2012-03-28 | Go 1.0 发布，**Go 1 兼容性承诺**生效 | [Release History](https://go.dev/doc/devel/release) |
| 2022-03-15 | Go 1.18 发布，加入泛型 | 同上 |
| 2026-08-19 | Go 1.27.0 发布，加入泛型方法、`encoding/json/v2` | [Go 1.27 Release Notes](https://go.dev/doc/go1.27) |
| 2026-09-01 | Go 1.27.1 发布（本篇实测版本） | [Release History](https://go.dev/doc/devel/release) |

**Go 1 兼容性承诺**是本表里分量最重的一行：Go 1.0 之后不引入破坏性语言变更。它把 Go 的版本演进变成**纯增量**——1.27 的代码在 1.0 的语义下依然成立（除了少数 GODEBUG 控制的默认值翻转）。这是 [10-版本演进](../10-版本演进/) 能按"每版加了什么"来组织的前提，也是本库对 Go 只设单档版本口径的原因：没有 LTS，因为每个版本都在兼容承诺的保护下。

**发布节奏**：每 6 个月一个次版本（2 月、8 月），官方按"最近两个 major release"提供安全修复。写作时 go.dev/dl 上只有 go1.27.1 与 go1.26.8，Go 1.25 的支持随 1.27 的发布结束。完整编年见 [10-版本演进](../10-版本演进/)。
