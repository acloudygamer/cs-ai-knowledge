# 行为型模式

> 前置：[03-结构型](./03-结构型.md) · 后续：[10-版本演进](../10-版本演进/)

> **版本基准**：Go 1.27（stable = latest）。本篇示例实测环境：go1.27.1 windows/amd64。

## 本质

行为型模式回答"**对象之间怎么协作**"——谁在什么时候调用谁，控制权怎么转移。

这一组模式在 Go 里被语言机制吞掉的比例最高。C++ 里策略模式要一个抽象基类加一族子类，Go 里就是一个函数类型；C++ 里观察者要维护一张 `Observer*` 列表加虚函数回调，Go 里就是一个 channel。**原因是一致的：函数是一等值 + channel 是语言原语**，这两样把"调用谁"从类型系统搬到了数据里。

## 机制

### 策略：一个函数类型

策略模式解决的问题是"同一个动作有多种算法，运行时选一个"。Go 里选中的东西可以直接是函数值：

```go
type PriceFunc func(float64) float64

var strategies = map[string]PriceFunc{
	"normal": func(v float64) float64 { return v },
	"vip":    func(v float64) float64 { return v * 0.8 },
	"svip":   func(v float64) float64 { return v * 0.6 },
}
```

**标准库里的策略载体是 `context.Context`**——超时、取消、请求作用域数据都通过它传递，下游不需要知道上游选了什么策略：

```console
$ go run .
策略(context)结果: context deadline exceeded
```

`ctx.Err()` 返回 `context.DeadlineExceeded` 而不是某个自定义错误，是因为**策略的接收方需要的是"该不该继续"，不是"为什么停"**（需要原因时用 `errors.Is` 区分 `Canceled` 与 `DeadlineExceeded`，见 [04-并发/04](../04-并发/04-context与取消传播.md)）。

**约束**：策略之间必须无共享状态。上面的 `strategies` map 是包级变量，多个 goroutine 同时读没问题，但**不能有任何策略往 map 里写**——那是竞态（[04-并发/05](../04-并发/05-并发模式与竞态诊断.md)）。

### 责任链：函数切片 + 短路

```go
type chain struct{ hs []HandlerFunc }

func (c *chain) Run(v int) string {
	for _, h := range c.hs {
		if out, ok := h(v); ok {
			return out        // 短路：第一个认领的处理者结束整条链
		}
	}
	return "无处理者"
}
```

```console
$ go run .
    50 → 组长批准
   500 → 经理批准
  5000 → 总监批准
 50000 → 无处理者
```

链的语义由 `ok` 这个 bool 决定：**返回 `true` 表示"我处理了，链到此为止"**。这与 Web 中间件的链不同——中间件是"我处理一部分，再交给下一环"（装饰器，见 [03-结构型](./03-结构型.md)），而责任链是"谁认领谁负责，其余不看"。

**约束**：链上没有任何处理者认领时必须**有兜底返回**。上面的 `"无处理者"` 就是兜底；漏掉它会让函数返回零值，而调用方无法区分"处理结果是空串"与"没人处理"。

### 观察者：channel 当事件总线

C++ 的观察者模式要维护 `vector<Observer*>` 加回调接口。Go 里发布方与订阅方的连接可以直接是 channel：

```go
func (b *Bus) Publish(topic, msg string) {
	b.mu.RLock()
	subs := b.subs[topic]   // 快照：通知期间列表不变
	b.mu.RUnlock()
	for _, ch := range subs {
		select {
		case ch <- msg:
		default:            // 订阅者跟不上就丢，不阻塞发布方
		}
	}
}
```

```console
$ go run .
订阅者A: created
订阅者B: created
```

三处细节都有依据：

**一、先快照再通知。** 如果持锁遍历，`OnEvent` 里再调 `Subscribe` 会死锁（Go 的 `sync.RWMutex` 不可重入）。快照的代价是"通知期间新订阅的收不到这一条"——这是可接受的语义。

**二、`select` + `default` 做非阻塞投递。** 订阅者处理慢时，发布方不能跟着卡住。丢掉慢订阅者的消息是**有意的背压策略**；需要不丢就得用带缓冲的 channel 加独立投递 goroutine，代价是内存可能无界增长。

**三、channel 的缓冲大小决定了投递语义。** 上面用 `make(chan string, 1)`，容量 1 意味着"订阅者没及时取时还能存一条"。容量 0 时 `default` 分支几乎总被选中，消息基本全丢。

**边界**：channel 版观察者**只适合单进程**。跨进程要换成消息队列（[08-生态与框架](../08-生态与框架/)），那时"投递语义"变成队列的持久化与确认机制，channel 的 `select` 模型不再适用。

### 状态机：方法表

Go 没有枚举的封闭性（`iota` 常量可以被任意赋值），状态机通常写成**接口 + 每个状态一个类型**，或**转移表**：

```go
type State interface{ Next(Event) State }

var transitions = map[State][]struct {
	on   Event
	next State
}{ ... }
```

判据是：**状态少且转移规则简单用 `switch`，状态多或转移表需要从配置生成用方法表**。前者可读性更好，后者可数据驱动。两者的共同约束是**状态转移必须集中在一处**——把转移逻辑散进各个状态类型，就没法回答"这个事件在哪些状态下合法"。
