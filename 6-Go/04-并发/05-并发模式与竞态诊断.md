# 并发模式与竞态诊断

> 前置：[04-context与取消传播](./04-context与取消传播.md) · 后续：无（本目录终篇）

> **版本基准**：Go 1.27（stable = latest）。本篇示例实测环境：go1.27.1 windows/amd64（gcc 来自 MinGW-w64）。

## 本质

**竞态（race condition）是两个 goroutine 并发访问同一内存、至少一个是写、且没有同步。** 它的后果是**未定义行为**——不是"结果可能不对"，而是"结果无法预测，且换台机器可能完全不同"。

**诊断竞态的黄金工具是 `-race`**：Go 内置的竞态检测器（race detector），基于 ThreadSanitizer 的算法。

**约束的由来**：`-race` 是**动态检测**——它只报告**实际发生**的竞态。没报不等于没有：

> 它能证明有问题，**不能证明没问题**。

因此 `-race` 的正确用法是：**在测试里跑，让测试覆盖到并发路径**。测试没覆盖到的竞态，检测器也看不到。

## 机制

### `-race` 的实测输出

一个有真实竞态的程序（1000 个 goroutine 无锁自增）：

```go
func (a *Account) Deposit(n int) { a.balance += n }   // 无锁
```

不带 `-race` 时，**结果直接是错的**：

```console
$ go run .
最终余额: 962 （期望 1000）
```

38 次自增凭空消失——`+=` 是"读-改-写"三步，并发时互相覆盖。**这个错误是静默的**，程序不崩溃、不报错。

带 `-race` 时：

```console
$ go run -race .
==================
WARNING: DATA RACE
Read at 0x00c000098068 by goroutine 9:
  main.(*Account).Deposit()
      D:/.../main.go:12 +0x7d
  main.main.func1()
      D:/.../main.go:19 +0x12

Previous write at 0x00c000098068 by goroutine 8:
  main.(*Account).Deposit()
      D:/.../main.go:12 +0x8f
  main.main.func1()
      D:/.../main.go:19 +0x12

Goroutine 9 (running) created at:
  main.main()
      D:/.../main.go:19 +0x84
==================
```

**报告包含四样关键信息**：

| 信息 | 用途 |
|---|---|
| **两个访问的地址** | 确认是同一个变量 |
| **读 / 写 / 上一次写** | 判断竞态类型 |
| **两处代码位置**（含行号） | **直接定位到 bug** |
| **两个 goroutine 的创建位置** | 找到是谁起的它们 |

**约束**：`-race` 需要 cgo 与 C 编译器（它链接了 ThreadSanitizer 的运行时）。`CGO_ENABLED=0` 时无法使用。

**代价**：

| | 内存 | 速度 |
|---|---|---|
| 程序本身 | 5–10× | — |
| 运行时 | — | 2–20× 慢 |

**因此 `-race` 不该用于生产**——它是测试工具。`go test -race ./...` 应当进 CI。

### 检测原理与局限

`-race` 用的是 **happens-before 分析**：它记录每次内存访问的"向量时钟"，检查两个访问之间有没有同步关系。

**它的盲区**：

| 盲区 | 说明 |
|---|---|
| **未执行的代码路径** | 没跑到就不检测 |
| **未覆盖的 goroutine 交错** | 调度是随机的，某次交错可能没出现 |
| **超过 8192 个 goroutine** | 检测器只跟踪最近的一批 |
| **死锁** | 死锁不是竞态，`-race` 不报（用 `GODEBUG` 或 `go tool trace`） |

**约束**：因此 CI 里应当**多跑几次**（`-count=5` 或 `-race -count=10`）来增加交错覆盖。Go 官方的做法是在 `GOFLAGS` 里给测试加 `-race`。

### worker pool：固定 worker 消费任务

```console
$ go run .
worker pool: [1 4 9 16 25]
```

```go
in := make(chan int)
out := make(chan int)
var wg sync.WaitGroup
for i := 0; i < n; i++ {
	wg.Add(1)
	go func() {
		defer wg.Done()
		for j := range in {        // 消费直到 in 关闭
			out <- j * j
		}
	}()
}
go func() { wg.Wait(); close(out) }()   // 全部 worker 退出后关 out
go func() { for _, j := range jobs { in <- j }; close(in) }()
```

**三处关键设计**：

**一、`close(in)` 是 worker 的退出信号**——`for range in` 在 channel 关闭时自然结束。

**二、`close(out)` 必须等所有 worker 退出**——用一个专门的 goroutine `wg.Wait()` 后再关。**在 worker 里关 `out` 会 panic**（多个 worker 重复关闭）。

**三、`out` 无缓冲**——worker 处理完立即交给消费者，不排队。要平滑突发可加缓冲，但那会推迟背压（[02-channel与select](./02-channel与select.md)）。

**约束**：worker 数量 `n` 是**并发度上界**。它不等于 CPU 核数——如果任务是 I/O 密集的，`n` 可以远大于 `GOMAXPROCS`。

### fan-out / fan-in

```console
$ go run .
fan-in: [1 2 3 4 5 6]
```

**fan-out**：多个 goroutine 从同一个 channel 读（worker pool 就是一种 fan-out）。
**fan-in**：多个 channel 汇聚到一个。

```go
func fanIn(chs ...<-chan int) <-chan int {
	out := make(chan int)
	var wg sync.WaitGroup
	for _, ch := range chs {
		wg.Add(1)
		go func(c <-chan int) {
			defer wg.Done()
			for v := range c { out <- v }
		}(ch)
	}
	go func() { wg.Wait(); close(out) }()
	return out
}
```

**注意 `go func(c <-chan int)` 把 `ch` 作为参数传入**——如果直接闭包捕获循环变量 `ch`，Go 1.22 之前会全部捕获同一个变量（[01-语言核心/05](../01-语言核心/05-函数.md)）。1.22 起每轮新建，但**显式传参仍是更好的写法**——它让意图明确，且兼容旧语义。

### pipeline：多级处理

```console
$ go run .
pipeline (n²+1): [2 5 10 17]
```

```go
for v := range addOne(square(gen(1, 2, 3, 4))) { ... }
```

每一级是一个"接收 channel、返回 channel"的函数，级与级之间由 channel 连接。**每一级可以独立控制并发度**——`square` 里起 3 个 goroutine 就是这一级的并行度。

**约束**：**pipeline 的每一级都要负责关闭自己的输出 channel**，否则下一级永远不结束。另外**错误传播需要额外设计**——中间级出错时怎么通知前后？常见做法是让每级接受 `ctx`，或者用一个专门的 `errCh`。

**边界**：**pipeline 不适合低延迟场景**——数据要流过所有级才有结果，引入了流水线延迟。它适合**吞吐量优先**的批处理。

### 限流：带缓冲 channel 当信号量

```console
$ go run .
限流 limit=2, 6 个 20ms 任务: 60ms
限流 limit=6, 6 个 20ms 任务: 20ms
```

```go
sem := make(chan struct{}, limit)
sem <- struct{}{}            // 获取
defer func() { <-sem }()     // 释放
```

**容量为 `limit` 的缓冲 channel 就是一个计数信号量**。实测：6 个 20 ms 的任务，限流 2 时耗时 60 ms（3 批），限流 6 时耗时 20 ms（1 批）——**完全符合 `ceil(6/limit) × 20ms`**。

**约束**：`defer func(){ <-sem }()` 必须用**闭包**而不是 `defer <-sem`——后者在 `defer` 语句处就求值了接收操作（[01-语言核心/05](../01-语言核心/05-函数.md) 讲的 `defer` 参数求值时机）。

**`golang.org/x/sync/semaphore` 是它的加强版**——支持带权重的获取（一个任务占多个配额）与 `ctx` 取消。

### `errgroup`：并发任务 + 错误传播

```console
$ go run .
全部成功 err = <nil>  results = [0 10 20 30]
有失败 err = 任务 1 失败  被取消的任务数 = 3
SetLimit(2) 跑 6 个 20ms 任务，总耗时 60ms（无限制约 20ms，串行 120ms）
```

`errgroup` 是 `sync.WaitGroup` 的并发场景加强版：

| | `sync.WaitGroup` | `errgroup.Group` |
|---|---|---|
| 收集错误 | 不能 | **返回第一个错误** |
| 取消传播 | 不能 | **`WithContext` 派生可取消的 ctx** |
| 并发度限制 | 不能 | **`SetLimit(n)`** |

**关键行为**：`errgroup.WithContext` 派生的 `ctx` 在**任一任务返回错误时被取消**——上面第二个例子里，任务 1 立即失败，另外 3 个正在等待的任务全部走了 `ctx.Done()` 分支（`被取消的任务数 = 3`）。

**约束**：**`g.Wait()` 只返回第一个错误**。要收集所有错误得自己写，或者用 `errors.Join`（[01-语言核心/10](../01-语言核心/10-错误处理.md)）在任务内部累积。

**边界**：`SetLimit` 限制的是**同时在跑的 goroutine 数**，与 worker pool 的效果类似，但 `errgroup` 每次 `Go` 都新建 goroutine（worker pool 是复用的）。**高频短任务用 worker pool，低频长任务用 `errgroup`**。

**与其它语言对照**：

| | 竞态检测 | worker pool | 结构化并发 |
|---|---|---|---|
| Java | 无内置（靠 FindBugs/ThreadSanitizer） | `ExecutorService` | **`StructuredTaskScope`（21+）** |
| C++ | **ThreadSanitizer（需手动接入）** | 手写 | 无 |
| Python | 无（GIL 掩盖了大部分） | `concurrent.futures` | `asyncio.TaskGroup`（3.11+） |
| **Go** | **`-race`（内置）** | 手写 channel 模式 | **`errgroup`（第三方，事实标准）** |

**Go 的 `-race` 是内置的**——`go test -race` 一条命令，不需要装任何东西（[00-概览/01](../00-概览/01-Go全景.md) 说的"工具链是一个二进制"）。C++ 的 ThreadSanitizer 虽然也是成熟工具，但要手动编译、链接、配置。**这个成本差异决定了 `-race` 在 Go 社区是默认动作，在 C++ 社区是高级技巧**。

**Python 的 GIL 是另一回事**：它让大部分竞态"看起来不存在"——但只对纯 Python 代码有效，NumPy、C 扩展、`asyncio` 里照样有竞态，而且没有工具能检测。
