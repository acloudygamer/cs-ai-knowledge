# 02-构建系统与包管理

> 前置：[01-语言定位与编译模型](01-语言定位与编译模型.md)（编译链四段是这里要驱动的机器） · 后续：[03-链接与ABI](../04-性能与底层/03-链接与ABI.md)、[08-命名空间与模块](../01-语言核心/08-命名空间与模块.md)

> **版本基准**：C++20（构建工具链与标准无关的部分按 2026 年现状写）

承接编译模型：上一篇的四段链一次只编一个翻译单元，真实项目却有几百个 `.cpp` 加一堆第三方库。本篇讲清两件事：构建系统如何驱动编译链（多文件编排 + 增量重编），包管理如何把别人的库搬进项目。

## 本质

构建系统的本质是一台**依赖图驱动器**：把"哪些目标文件由哪些 `.cpp` 产出、可执行文件由哪些目标文件链接"声明成一张有向无环图（DAG），再由它决定两件事——构建顺序（拓扑排序）与重编范围（文件变化后只重编下游）。手工敲 `g++` 的崩溃点在于命令行随文件数线性增长且无人能记全依赖；构建系统把命令行收敛为声明。

包管理的本质是**依赖的获取与就位**：找到库、下载、按本机工具链编好（或取来预编译产物）、把头文件路径与库文件交给构建系统。C++ 没有官方包仓库（对照 Python 的 PyPI、JS 的 npm）——这是历史遗物而非设计：标准化进程从未覆盖分发环节，于是多个第三方方案共存至今。

## 机制

### 为什么必须有构建系统

单文件 `g++ main.cpp` 够用；三个痛点随文件数增长而爆炸：

1. **顺序**：目标文件必须先于其使用者产出——正是 DAG 的拓扑排序；
2. **增量**：改一个头文件，所有文本包含它的 `.cpp` 都要重编（见上一篇"头文件包含的文本本质"），手工无法追踪这份依赖；
3. **一致性**：全项目必须用同一份编译选项，否则跨单元 ABI 不一致（后果见 [03-链接与ABI](../04-性能与底层/03-链接与ABI.md)）。

Make 是第一代答案（规则 + 时间戳），但它只懂"文件 → 文件"，不懂 C++——头文件依赖要靠编译器 `-M` 家族选项反向生成。CMake 的定位是**元构建系统**：不直接驱动编译器，而是生成 Makefile、`build.ninja`、`.sln` 等原生构建文件，交给 Ninja/Make/MSBuild 执行。2026 年的现实：CMake 是 C++ 生态事实标准，IDE 与包管理器都以它为集成点。

### CMake 的中心概念：target

现代 CMake（3.x 风格）把一切都挂在 **target**（构建目标：一个库或可执行文件）上。每个 target 自带编译选项、include 路径、链接库等属性；`target_link_libraries` 在 target 之间连边，属性沿边**传播**。传播范围由关键字决定：

| 关键字 | 自身编译用 | 传播给使用者 | 典型用途 |
|---|---|---|---|
| `PRIVATE` | ✓ | ✗ | 只在 `.cpp` 里用到的实现细节 |
| `PUBLIC` | ✓ | ✓ | 头文件里暴露的类型来自该依赖 |
| `INTERFACE` | ✗ | ✓ | 纯头文件库（`add_library(x INTERFACE)`，无构建产物） |

判据一句话：**谁的头文件出现在我的头文件里，谁就是 PUBLIC**。写反的后果对称：该 PUBLIC 写成 PRIVATE → 使用者编译期报"找不到头文件"；该 PRIVATE 写成 PUBLIC → 无关使用者被迫继承依赖，增量构建的重编范围无谓放大。

`target_compile_features(greeter PUBLIC cxx_std_20)` 声明"本 target 要求至少 C++20"——比全局 `set(CMAKE_CXX_STANDARD 20)` 更现代：要求随 target 传播，链接它的消费者自动获得不低于此的标准模式。注意它是**最低要求**而非精确指定，编译器可用更新标准满足它。

### 构建类型与生成器

- **构建类型**：`Debug`（带调试符号、无优化）/ `Release`（`-O3 -DNDEBUG` 级别）/ `RelWithDebInfo` / `MinSizeRel`。单配置生成器（Ninja、Makefiles）在配置期用 `-DCMAKE_BUILD_TYPE=Release` 定死；多配置生成器（Visual Studio、Xcode）在构建期用 `--config Release` 选。按构建类型分条件时用生成器表达式 `$<CONFIG:Debug>`，不要写 `if(CMAKE_BUILD_TYPE ...)`——后者在多配置生成器下为空。
- **生成器**（`-G`）：`Ninja`（并行默认拉满、最快，跨平台首选）、`Unix Makefiles`、`Visual Studio 17 2022` 等。生成器只决定构建文件格式，不决定编译器；编译器由工具链决定。
- **两阶段**：`cmake -B build`（配置 + 生成，产出 `CMakeCache.txt` 与原生构建文件）与 `cmake --build build`（执行编译）分离；改了 CMakeLists 只影响前一阶段，后一阶段会按需自动触发重配置。

### 包管理：二维格局

选方案前先看依赖落在哪一维：

| 维度 | 含义 | 归谁管 |
|---|---|---|
| 系统库 | OpenSSL、CUDA、zlib——装在 OS 层，带 ABI 契约 | 系统包管理器（apt/brew/winget）+ CMake `find_package` |
| 源码依赖 | fmt、spdlog、Catch2——随项目版本走，要求可复现 | C++ 包管理器（vcpkg/Conan）或 FetchContent |

`find_package` 是 CMake 侧的查找入口，只管"找到"不管"下载"：模块模式找 `FindXXX.cmake`（CMake 自带或项目提供），配置模式找库作者安装的 `XXXConfig.cmake`——现代库的主流，直接给出导入 target（如 `fmt::fmt`），链接一行了事。

| | vcpkg | Conan | FetchContent |
|---|---|---|---|
| 出品 | 微软 | 社区（JFrog 运营） | CMake 内置（≥3.11） |
| 获取 | 源码，按 triplet 本机编译 | 预编译二进制为主，无匹配则源码编译 | 源码，并入本项目构建 |
| 集成 | toolchain 文件注入，`find_package` 照常 | 生成 CMakeDeps/CMakeToolchain 后 `find_package` | 无 `find_package`，target 直接可用 |
| 版本解析 | 清单模式 + baseline 锁定 | 版本范围约束 + 冲突求解 | 无求解器，锁定靠 `GIT_TAG` |
| 适用 | Windows/跨平台均可，与 MSVC 生态契合 | 版本矩阵复杂（多编译器×多配置）的大团队 | 小而纯 CMake 的依赖、原型 |
| 代价 | 首次全量编译慢；triplet（架构×系统×链接方式）要理解 | settings 与二进制 ABI 强耦合，配置面最大 | 依赖源码并入本项目构建图，每个使用者各自全量重编；依赖的构建配置与主项目耦合 |

经验法则：一两个轻依赖且都是 CMake 项目 → FetchContent；跨平台产品线或 Windows 团队 → vcpkg；要精确版本矩阵与私有制品仓库 → Conan。

## 示例

最小现代 CMake 项目（CMake 3.31 + Ninja + GCC 14.2 实测）：

```cmake
cmake_minimum_required(VERSION 3.20)
project(demo LANGUAGES CXX)

add_library(greeter STATIC src/greeter.cpp)
target_compile_features(greeter PUBLIC cxx_std_20)  # 要求 C++20，随 target 传播
target_include_directories(greeter PUBLIC include)  # PUBLIC：自己编译用，也传播给使用者

add_executable(app src/main.cpp)                    # main.cpp 里直接 #include <greeter.h>
target_link_libraries(app PRIVATE greeter)          # app 继承 greeter 的 include 路径与标准
```

```bash
cmake -B build -G Ninja -DCMAKE_BUILD_TYPE=Release   # 配置 + 生成 build.ninja
cmake --build build    # 4 步：编 greeter.cpp → 归档 libgreeter.a → 编 main.cpp → 链接 app
./build/app            # hello, cmake
```

FetchContent 拉第三方源码依赖（实测拉取并编译 fmt 11.1.4）：

```cmake
include(FetchContent)
FetchContent_Declare(
  fmt
  GIT_REPOSITORY https://github.com/fmtlib/fmt.git
  GIT_TAG 11.1.4        # 版本锁定靠 tag；FetchContent 无依赖求解
  GIT_SHALLOW TRUE
)
FetchContent_MakeAvailable(fmt)   # 下载源码，把 fmt 的 CMakeLists 并入本构建
target_link_libraries(app PRIVATE fmt::fmt)
```

两个包管理器的声明层（安装与集成细节见各自官方文档）：

```json
// vcpkg.json（清单模式）——配置时加 -DCMAKE_TOOLCHAIN_FILE=<vcpkg根>/scripts/buildsystems/vcpkg.cmake
{ "dependencies": ["fmt", "spdlog"] }
```

```ini
# conanfile.txt——conan install 生成 CMakeDeps 工具链文件，之后照常 find_package(fmt)
[requires]
fmt/11.1.4
[generators]
CMakeDeps
CMakeToolchain
```
