# 网络请求

## 定义

网络请求是通过操作系统的协议栈（TCP/IP 或 UDP）在进程地址空间与远程主机的进程地址空间之间建立字节流通道的过程。其本质是**跨地址空间的进程间通信**，核心挑战在于：往返延迟（RTT）远大于本地内存访问、网络带宽有限且不稳定、丢包与重传导致时序非线性。

## 数学模型

### TCP拥塞控制的状态机

TCP 拥塞控制抽象为有限状态自动机，状态变量为拥塞窗口（cwnd）和慢启动阈值（ssthresh）：

$$
\text{发送窗口} = \min(\text{cwnd}, \text{接收窗口})
$$

**四种状态及转换**：

| 状态 | 触发条件 | cwnd 变化 | 典型行为 |
|------|----------|-----------|----------|
| 慢启动（Slow Start） | cwnd < ssthresh | 指数增长：$\text{cwnd}_{n+1} = 2 \times \text{cwnd}_n$ | 初始探测可用带宽 |
| 拥塞避免（C-AVOID） | cwnd $\ge$ ssthresh | 线性增长：$\text{cwnd}_{n+1} = \text{cwnd}_n + 1$ | 逼近带宽上限 |
| 快速重传（Fast Retransmit） | 收到 3 个重复 ACK | ssthresh = cwnd/2, cwnd = ssthresh + 3 | 跳过等待超时 |
| 快速恢复（Fast Recovery） | 快速重传后 | cwnd = ssthresh + MSS | 维持发送能力 |

**吞吐量上界**（带宽-延迟积，BDP）：
$$
\text{BDP} = \text{带宽}(bits/s) \times \text{RTT}(s)
$$
若窗口大小小于 BDP，则瓶颈在拥塞窗口；若大于 BDP，则瓶颈在物理带宽。

### libcurl的multi接口状态机

libcurl 的 multi 接口基于 select/poll/epoll/kqueue 等 I/O 多路复用，运行一个事件循环状态机：

<pre>
easy handle        multi session         fd_set / epoll set        socket FD
   │                     │                       │                      │
   ├─ add ─────────────>│                       │                      │
   │                     │                       │                      │
   ├─ perform ─────────>│  执行 I/O  ──────────>│  监控可读/可写/出错 ──>│
   │                     │                       │<─────────────────────│
   │                     │<── socket 事件 ───────│                      │
   │<────────────────────┤                       │                      │
   │   CURL_MSG_DONE    │                       │                      │
</pre>

每次 `curl_multi_perform` 调用推进状态机，直到所有 easy handle 完成或出错。

### Asio的Proactor模式

Asio（Boost.Asio / C++20 Networking TS）实现 Proactor 模式：用户发起异步操作后立即返回，操作完成时通过回调通知。

<pre>
发起异步操作（应用）     操作请求（Asio）        操作系统         完成事件          完成处理（应用）
     │                       │                    │                  │                  │
     ├─ async_read_some ───> │                    │                  │                  │
     │                       ├─ 发起系统异步调用 >│                  │                  │
     │                       │                    │                  │                  │
     │<─ 立即返回 ───────────┘                    │                  │                  │
     │                       │                    │                  │                  │
     │                       │                    │<── 数据到达 ──────│                  │
     │                       │<── completion handler 触发（epoll）──┤                  │
     │<──────────────────────┤                    │                  │                  │
     │   用户回调被调用        │                    │                  │                  │
</pre>

与 Reactor（select/poll）相比：Reactor 在事件到达时"通知"应用让应用处理（半同步半异步），Proactor 在操作完成时才通知应用（完全异步）。

## 数据流

### TCP连接建立的数据流

<pre>
客户端                     服务器
   │                         │
   │──── SYN (seq=x) ──────>│  状态：SYN_SENT
   │                         │  状态：LISTEN → SYN_RCVD
   │<─── SYN+ACK (seq=y,    │  ack = x+1
   │        ack=x+1) ───────│
   │   状态：ESTABLISHED     │
   │──── ACK (ack=y+1) ────>│  状态：ESTABLISHED
   │                         │
   三次握手完成，连接建立
</pre>

**三次握手解决了什么问题**：序列号同步。TCP 是全双工协议，双方都需要知道对方的初始序列号（ISN），三次握手确保双方都收到了对方的 ISN 确认。

**RTT 测量**：第一个数据可发送的时刻距连接建立开始的时长为 $1.5 \times \text{RTT}$（第一次数据发送在收到对方 SYN+ACK 后）。

## 机制

### socket缓冲区的流量控制

每个 socket 有一对缓冲区：发送缓冲区（send buffer）和接收缓冲区（receive buffer）。

- 发送缓冲区：应用 `write()` 的数据先进入此缓冲区，TCP 协议栈从该缓冲区取数据发送。若缓冲区满，`write()` 阻塞（或返回部分写入）。
- 接收缓冲区：TCP 协议栈收到的数据放入此缓冲区，应用 `read()` 从该缓冲区取数据。若缓冲区空，`read()` 阻塞。

**流量控制**：接收方通过 TCP 头部的 window 字段通告剩余缓冲区大小。发送方确保未确认数据量不超过 window 大小。这防止快速发送方淹没慢速接收方。

**零窗口**：接收方缓冲区满时 window = 0，发送方停止发送。接收方腾出空间后发送 window update，发送方恢复。

### 非阻塞 I/O 与 EAGAIN

设置 `O_NONBLOCK` 后，若 socket 缓冲区不可用，操作立即返回并设置 `errno = EAGAIN`（或 `EWOULDBLOCK`，两者同值）：

- `read()`：无数据可读时返回 -1 + EAGAIN，而非阻塞等待。
- `write()`：发送缓冲区满时返回 -1 + EAGAIN，而非阻塞等待。

**轮询 EAGAIN** 是 busy-wait 模式，CPU 占用高。应使用 I/O 多路复用（select/poll/epoll）等待 socket 就绪。

### libcurl easy vs multi 接口

**easy 接口**（同步）：
- `curl_easy_perform()` 阻塞直到请求完成。
- 内部通过 `select()` 循环实现等待，线程安全（可多线程并发使用多个 easy handle）。

**multi 接口**（异步）：
- `curl_multi_perform()` 非阻塞推进所有活跃请求。
- 配合 `curl_multi_fdset()` 获取需要监控的文件描述符，配合 `select()` / `epoll` 等待。
- 适合管理大量并发连接，避免为每个连接创建线程的开销。

### Asio的strand序列化

`asio::strand` 保证同一 strand 上的操作顺序执行，不同行上的操作可并发：

```cpp
asio::strand<asio::io_context::executor_type> strand1(io_ctx);
asio::strand<asio::io_context::executor_type> strand2(io_ctx);

auto op1 = asio::post(strand1, [] { /* 操作 A */ });
auto op2 = asio::post(strand1, [] { /* 操作 B */ });  // 在 op1 之后执行
auto op3 = asio::post(strand2, [] { /* 操作 C */ });  // 可与 op1/op2 并发
```

strand 本质上是一个 mutex + task queue：所有任务入队到同一个队列，同一时刻只有一个任务在执行。

### POSIX socket的字节序转换

网络字节序（network byte order）统一使用大端序（Big Endian），主机字节序（host byte order）因平台而异（小端序 x86，大端序网络设备）。

```
htons() / htonl() / ntohs() / ntohl()
主机字节序 <════════════════> 网络字节序
```

**为什么需要转换**：TCP/IP 协议栈规定多字节整数必须使用大端序。当两台字节序不同的主机通信时，各自须将本地整数转换为网络字节序再发送，接收方再转换回本地字节序。

## 参考存根

```cpp
// Asio 异步 TCP 服务器（展示 Proactor 模式）
using asio::ip::tcp;
class Session : tcp::socket {
    std::array<char, 4096> d_;
public:
    Session(asio::io_context& ctx) : tcp::socket(ctx) {}
    void start() {
        auto h = [this](std::error_code ec, size_t n) {
            if (!ec) {
                asio::async_write(*this, asio::buffer(d_, n),
                    [this](auto ec, size_t) { start(); });
            }
        };
        asio::async_read_some(*this, asio::buffer(d_), h);
    }
};
```
