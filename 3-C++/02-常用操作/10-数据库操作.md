# 数据库操作

## 定义

数据库操作是通过**标准化接口**将程序数据存入**持久化关系结构**的过程。其本质是**客户端-服务端协议**：客户端发送 SQL 语句字符串，服务端解析、执行、返回结果集。核心问题是一致性（ACID）、并发控制（锁/ MVCC）、查询优化（代价模型选择执行计划）。

## 数学模型

**ACID 属性的形式化**：

- **原子性（Atomicity）**：事务 $T$ 的执行序列 $\{op_1, op_2, ..., op_n\}$ 要么全部成功（ $\text{commit}$ ），要么全部不生效（  $\text{abort}$）。形式化：  $\forall T: \text{commit}(T) \lor \text{abort}(T)$，且  $\text{abort}(T) \Rightarrow \forall o \in T: \text{undo}(o)$。

- **一致性（Consistency）**：数据库状态转换 $\sigma \xrightarrow{T} \sigma'$ 满足所有完整性约束 $IC$ ： $\sigma \models IC \land \text{valid}(T) \Rightarrow \sigma' \models IC$ 。

- **隔离性（Isolation）**：事务并发执行的结果等价于某串行执行的结果。设 $S$ 为调度集合， $S_{serial}$ 为串行调度，则：
$\forall T_1, T_2: \text{schedule}(T_1 \| T_2) \equiv_{conflicts} \text{schedule}_{serial}(T_1, T_2)$

- **持久性（Durability）**： $\text{commit}(T) \Rightarrow \forall \sigma' \text{ from } \sigma: \sigma' \models T_{committed}$ 。

**事务隔离级别**（ANSI SQL 标准）：

| 级别 | 脏读 | 不可重复读 | 幻读 |
|------|------|-----------|------|
| READ UNCOMMITTED | 可能 | 可能 | 可能 |
| READ COMMITTED | 不可能 | 可能 | 可能 |
| REPEATABLE READ | 不可能 | 不可能 | 可能 |
| SERIALIZABLE | 不可能 | 不可能 | 不可能 |

隔离级别通过**锁协议**或 **MVCC（多版本并发控制）**实现。

**并发控制的数学模型**：

**两阶段锁（2PL）**的形式化：
- **扩展阶段**：事务只能获取锁，不能释放锁
- **收缩阶段**：事务只能释放锁，不能获取新锁

设事务 $T_i$ 的锁获取集合为 $L_i$ ，释放集合为 $U_i$ 。2PL 要求：
$\forall i, j: i < j \Rightarrow U_i \cap L_j = \emptyset$

**MVCC 的版本化模型**：

每个数据项 $x$ 维护版本序列：
$x = \{x_1, x_2, ..., x_n\}$

每个版本 $x_k$ 关联事务 $T_k$ 的提交时间戳 $ts(T_k)$ 。读操作返回：
$\text{read}(x, T_i) = \max\{x_k \mid ts(T_k) < ts(T_i) \land x_k \text{已提交}\}$

**SQL 注入的数学本质**：

恶意输入 $I$ 突破 SQL 语法的边界。设原始查询结构为 $Q = \text{SELECT} \ldots \text{WHERE } c = \$1$ ，注入后变为 $Q' = \text{SELECT} \ldots \text{WHERE } c = \$1 \text{ OR } 1=1$ ，将条件从等价判断变为永真。

**SQL 注入的分类**：

| 类型 | 攻击向量 | 防御手段 |
|------|----------|----------|
|  UNION 注入 | 拼接额外 SELECT | 参数化查询 |
| 布尔盲注 | 构造永真/永假条件 | 参数化查询 + 输入验证 |
| 时间盲注 | `SLEEP()` 推断 | 参数化查询 + 最小响应时间 |
| 堆叠查询 | `; DROP TABLE` | 多语句禁用 |

**连接池的资源调度**：

<pre>
连接池（容量 N）
     │
     ├── 连接 1 ←─ 借用 ──→ SQL 执行 ←─ 归还 ── 连接 1
     ├── 连接 2 ←─ (空闲)
     └── ...
     │
     └── 连接 N ←─ (空闲)

调度约束：
  - 同时活跃连接 ≤ N
  - 归还超时 → 连接重置（防止死连接）
  - 池空 → 阻塞等待或超时错误
</pre>

**连接池的排队模型**：

设连接池容量为 $N$ ，请求到达率为 $\lambda$ ，服务率为 $\mu$ 。系统可建模为 $M/M/N$ 排队系统：

$P_{\text{阻塞}} = \frac{\frac{(\lambda/\mu)^N}{N!}}{\sum_{k=0}^{N} \frac{(\lambda/\mu)^k}{k!}}$

平均等待时间：
$W_q = \frac{P_{\text{阻塞}}}{N\mu - \lambda}$

## 机制

**SQLite3 的进程内嵌模型**：

SQLite 将整个数据库存储为单个文件（`*.db`），无独立服务进程。这决定了它的 ** WAL（Write-Ahead Logging）** 机制特性：

- 写操作记录 WAL 而非直接修改主文件
- 读操作无锁（除非有未 checkpoint 的 WAL 条目）
- 适合**单进程写 + 多进程读**的场景

**WAL 的数学保证**：

WAL 协议保证：
$\text{commit}(W) \Rightarrow \text{log\_flush}(W) \prec \text{data\_flush}(W)$

即日志刷新先于数据刷新，确保崩溃后可恢复。

**ACID 在 SQLite 中的实现**：

| 属性 | 实现机制 |
|------|---------|
| 原子性 | 事务日志记录所有页面修改，提交时写入或回滚 |
| 一致性 | 原子页写入 + checksum 校验 |
| 隔离性 | 文件锁（BEGIN EXCLUSIVE）或 WAL 读者/写者分离 |
| 持久性 | `fsync()` 确保日志/数据写入磁盘 |

**SOCI 的类型映射机制**：

SOCI 通过**滑动窗口**（sliding window）将 SQL 结果集映射为 C++ 类型：

```cpp
int id = 1;
std::string name;
sql << "SELECT name FROM users WHERE id = :id",
    soci::into(name),    // 输出绑定：SQL列 → C++变量
    soci::use(id);      // 输入绑定：C++变量 → SQL参数
```

`into`/`use` 的模板参数决定类型转换路径：int → `std::int32_t`，string → `std::string`，date → `std::tm`。

**类型映射的类型论本质**：

设 C++ 类型 $T_c$ 和 SQL 类型 $T_s$ ，映射函数 $f: T_s \rightarrow T_c$ 满足：
$f(\text{NULL}) = \text{std::nullopt} \quad \text{（可空类型）}$

**libpqxx 的参数化查询**：

参数化查询将数据与 SQL 结构分离：
```cpp
w.exec("INSERT INTO t VALUES ($1)", pqxx::params("Alice"));
// 参数 "Alice" 作为绑定变量传递，绝不参与 SQL 语法解析
```

参数化查询的数学本质：
$Q_{\text{param}}(p) = \text{SELECT} \ldots \text{WHERE } c = \text{escape}(p)$

其中 $\text{escape}$ 函数将参数值转义，防止语法注入。

**游标与结果集遍历**：

结果集不是一次性加载到内存，而是通过**服务端游标**逐行返回：

1. `DECLARE CURSOR` 在服务端创建命名的游标
2. `FETCH` 每次从游标读取 N 行
3. 客户端缓冲 N 行，`FETCH` 触发下一批次加载

游标的数学模型：
$C = (\text{name}, \text{position}, \text{buffer}, \text{batch_size})$

当前位置的语义：
$\text{current}(C) = \text{buffer}[\text{position} \mod \text{batch_size}]$

**连接池的数学约束**：

设池容量为 $N$ ，并发请求数为 $R$ ：

$\text{阻塞概率} = P(\text{所有} N \text{连接占用}) = \frac{\lambda^{N}}{\sum_{i=0}^{N} \lambda^i} \cdot \text{利用率修正}$

其中 $\lambda$ 是服务速率与到达率之比。连接池大小选择需权衡：过小导致阻塞，过大浪费资源（数据库连接本身是稀缺资源）。

**约束条件与违反后果**：

- **长事务持有连接**：若事务内包含网络 I/O 或计算，连接被阻塞，池吞吐量下降。
- **SQLite 并发写限制**：SQLite 写操作独占整个数据库文件，`BEGIN EXCLUSIVE` 锁住整个数据库。
- **参数化查询误用**：仍使用字符串拼接会导致 SQL 注入，如 `sql << "WHERE name = '" + user_input + "'"`.

**事务隔离的异常现象**：

| 现象 | 说明 | 隔离级别 |
|------|------|----------|
| 脏读 | 读取未提交事务的修改 | READ UNCOMMITTED |
| 不可重复读 | 同一事务两次读取同一行，结果不同 | READ COMMITTED |
| 幻读 | 同一事务两次查询，结果集行数不同 | REPEATABLE READ |

## ORM（Drogon）

**ORM将关系表映射为C++对象，通过元数据描述列与成员的绑定关系，隐藏SQL生成过程。**

### 参考样例

```cpp
class User : public drogon::orm::Model<User> {
public:
    int id;
    std::string name;
    static constexpr const char* TableName = "users";
};

User new_user;
new_user.name = "Alice";

orm::Mapper<User> mapper(app().getDbClient());
mapper.insert(new_user);
auto user = mapper.findByPrimaryKey(1);
mapper.deleteByPrimaryKey(1);
```

**ORM 的 SQL 生成代价**：

Drogon 使用编译期元编程生成 SQL，无需运行时反射。但 ORM 的**抽象泄漏**（leaky abstraction）可能导致非最优 SQL：

- `mapper.findByPrimaryKey(1)` 生成 `SELECT * FROM users WHERE id = 1`
- 批量操作 `mapper.insertMany(users)` 可能生成 N 次 INSERT 而非批量 INSERT

**N+1 查询问题**：

ORM 常见性能陷阱：加载 $N$ 个对象时，执行 1 次主查询 + $N$ 次关联查询。

数学分析：总查询次数 $Q = 1 + \sum_{i=1}^{N} f_i$ ，其中 $f_i$ 是第 $i$ 个对象的关联字段数。最坏情况 $Q = 1 + N$ 。

## 数据库选型

| 场景 | 适用数据库 | 库 |
|------|-----------|-----|
| 嵌入式/本地存储 | SQLite | sqlite3 |
| 企业级/复杂查询 | PostgreSQL | libpqxx |
| Web/高并发 | MySQL | mysqlclient |

**选型决策树**：

```
是否需要ACID？
  ├─ 是 → 是否需要高并发写入？
  │    ├─ 是 → PostgreSQL（行级锁 + MVCC）
  │    └─ 否 → SQLite（进程内嵌，零网络开销）
  └─ 否 → 是否需要分布式？
       ├─ 是 → MongoDB / MySQL Cluster
       └─ 否 → SQLite
```

## 参考存根

```cpp
// SQLite RAII 封装
class DB {
    sqlite3* db_ = nullptr;
public:
    explicit DB(const char* path) {
        if (sqlite3_open(path, &db_) != SQLITE_OK)
            throw std::runtime_error(sqlite3_errmsg(db_));
    }
    ~DB() { if (db_) sqlite3_close(db_); }
    DB(const DB&) = delete;
    DB& operator=(const DB&) = delete;

    template<typename F>
    void transaction(F&& fn) {
        exec("BEGIN");
        try {
            fn();
            exec("COMMIT");
        } catch (...) {
            exec("ROLLBACK");
            throw;
        }
    }

    void exec(const char* sql) {
        char* err = nullptr;
        if (sqlite3_exec(db_, sql, nullptr, nullptr, &err) != SQLITE_OK) {
            std::string msg = err ? err : "unknown";
            sqlite3_free(err);
            throw std::runtime_error(msg);
        }
    }
};
```
