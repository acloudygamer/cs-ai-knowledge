# 序列化

## 定义

序列化是将 C++ 对象转换为线性字节序列的过程，反序列化是其逆过程。本质是**对象图到字节流的同构映射**：对象的成员布局（基本类型、复合类型、指针/引用、继承关系）在序列化端编码为自描述格式，反序列化端根据格式约定重建对象结构。

核心挑战是**跨平台一致性**（字节序、类型大小、内存布局）和**版本演化**（旧版本数据被新版本代码读取，或反之）。

**指针的扁平化**：

指针值本身无意义（地址空间随机化），序列化时必须追踪**指向关系**，将指针展开为**偏移量或索引**：

 $\text{ptr} \xrightarrow{\text{deref}} O' \xrightarrow{\text{serialize}} \text{idx}(O')$ 

反序列化时根据索引重建指针图。

**Protocol Buffers 的 tag-length-value 编码**：

Protobuf 消息由一系列 $(tag, length, value)$ 三元组组成： 三元组组成：

 $\text{message} = \{(tag_i, len_i, value_i)\}_{i=1}^{n}$

 $\text{tag} = (\text{field_number} \ll 3) | \text{wire_type}$

## 机制

**字节序（Endianness）**：

现代处理器多为小端（little-endian），网络协议统一使用大端（big-endian）。字节序转换公式：

 $\text{uint32\_t\_network} = \text{htonl}(\text{uint32\_t\_host})$ 

**跨平台序列化的字节序陷阱**：

```cpp
// x86 (little-endian) 序列化
uint32_t id = 0x01020304;
v.insert(end, (uint8_t*)&id, (uint8_t*)&id + 4);
// 内存布局：[04][03][02][01]

// ARM (big-endian) 反序列化时若不转换
// 解析为 0x04030201（错误）
```

**Protocol Buffers 的 Varint 优化**：

Varint 将小整数编码为 1-5 字节，大整数编码为更多字节：
- $[0-127]$ → 1 字节（最高位 0 表示结束） → 1 字节（最高位 0 表示结束）
- $[128-16383]$ → 2 字节（最高位 1 表示还有字节） → 2 字节（最高位 1 表示还有字节）

这比固定 4 字节 `int32` 显著节省空间，尤其在整数普遍较小的场景。

对于均匀分布的小整数，Varint 可节省约 50-75% 空间。

**Protobuf 的 Schema 演化为什么这样设计**：

Protobuf 采用 **tag-based schema evolution**，这是精心设计的工程权衡：

1. **新增字段必须使用新的 tag 编号**：旧代码遇到未知 tag 跳过，保证前向兼容
2. **删除字段只是不再使用，但 tag 编号不能回收**：否则新代码序列化时可能复用旧 tag，被旧代码误读
3. **字段类型不可更改**：因为 tag 只标识"哪个字段"，不标识"什么类型"，类型由 proto 定义决定

这意味着 Protobuf 的版本演化是**单向的**：可以添加新字段，但不能回退到旧 schema（除非保持 tag 不冲突）。

**为什么不能删除字段并复用 tag**：

```
假设 schema v1: 字段 1 = name (string)
假设 schema v2: 删除 name，复用 tag 1 = id (int32)

v1 序列化: tag=1, value="Alice"  →  v2 解析: tag=1, value=?? (误读为 id=某个大整数)
```

**JSON 序列化的文本化代价与收益**：

JSON 是人类可读格式，每个字符、冒号、引号都占用空间：

 $\text{size}_{\text{JSON}} / \text{size}_{\text{Protobuf}} \approx 2\text{-}10\times$ 

但 JSON 的优势在于调试可读性和跨语言零配置。选择 JSON 的场景：
- **日志、配置、调试接口**：可读性 > 性能
- **跨语言 REST API**：JSON 是 Web 事实标准，无需 schema 定义文件
- **快速原型**：无编译步骤，字段可随时增删

选择二进制格式的场景：
- **高性能内部通信**：带宽/延迟敏感
- **持久化存储**：空间效率影响存储成本
- **跨语言严格接口**：schema 是协议契约

**序列化库的选型**：

| 库 | 格式 | Schema | 性能 | 跨语言 |
|----|------|--------|------|--------|
| nlohmann/json | JSON文本 | 无 | 低 | ✅ |
| protobuf | 二进制 | `.proto` | 高 | ✅ |
| boost::serialization | 多格式 | 无/有 | 中 | ❌ |
| msgpack | 二进制 | 无 | 高 | ✅ |

**约束条件与违反后果**：

- **指针序列化**：未正确处理指针会导致悬空引用。必须建立对象 ID 映射而非直接序列化地址。
- **浮点 NaN/Inf**：IEEE 754 的 NaN 不等于自身，序列化后比较会失败；某些二进制格式不支持 Inf。
- **循环引用**：对象图中的循环需要特殊处理（如 boost::serialization 的 `register_type`）。
- **大小端混淆**：直接内存拷贝 `*(uint32_t*)&float_val` 在跨平台场景会导致浮点数值完全破坏。

#include <arpa/inet.h>

std::vector<uint8_t> serialize(const Person& p) {
    std::vector<uint8_t> v;
    uint32_t id_net = htonl(p.id);
    v.insert(v.end(), (uint8_t*)&id_net, (uint8_t*)&id_net + 4);
    uint32_t name_len_net = htonl(p.name.size());
    v.insert(v.end(), (uint8_t*)&name_len_net, (uint8_t*)&name_len_net + 4);
    v.insert(v.end(), p.name.begin(), p.name.end());
    return v;
}
