# 错误处理

## 定义

错误处理是程序在遭遇异常状态（资源耗尽、非法输入、外部系统故障）时维持**数据不变性**与**资源可回收性**的机制设计。在 C++ 中，异常处理与 RAII 资源管理共同构成完整的错误处理基础设施：异常负责跨函数边界的控制流跳转，RAII 负责资源所有权的确定性回收。

## 数学模型

### noexcept 与异常规范的形式化

C++17 之前的异常规范是**类型系统的一部分**（`throw()` = 不抛异常）。C++17 起，`noexcept` 是**契约声明**而非类型组成部分，但违反时 `std::terminate` 被调用。

**noexcept 表达式**：`noexcept(expr)` 在编译期求值为布尔常量，表示 `expr` 是否可能抛异常。设 $E$ 为表达式集合， $T$ 为类型集合，映射： 为表达式集合， $T$ 为类型集合，映射： 为类型集合，映射：

$$
\text{noexcept} : E \to \{\text{true}, \text{false}\}
$$

**移动语义的强异常安全保证**：若移动构造函数是 `noexcept`，`std::vector::push_back` 选择移动；否则选择拷贝（可能抛出）。设移动失败的概率为 $p_m$，拷贝失败的概率为 $p_c$ （通常 $p_m \ll p_c$，因为移动不分配内存）。若移动不抛异常，则 $p_m = 0$。 ，拷贝失败的概率为 $p_c$ （通常 $p_m \ll p_c$，因为移动不分配内存）。若移动不抛异常，则 $p_m = 0$。 （通常 $p_m \ll p_c$，因为移动不分配内存）。若移动不抛异常，则 $p_m = 0$。 ，因为移动不分配内存）。若移动不抛异常，则 $p_m = 0$。 。

### RAII 析构函数的异常安全性

设析构函数中可能抛出异常的操作集合为 $E_{dtor}$。C++ 规定：**析构函数不应抛异常**（默认 `noexcept(true)`）。若析构函数主动 `throw`，栈展开时可能导致 `std::terminate` 调用。 。C++ 规定：**析构函数不应抛异常**（默认 `noexcept(true)`）。若析构函数主动 `throw`，栈展开时可能导致 `std::terminate` 调用。

**两次异常同时展开的不可恢复性**：若异常 A 正在栈展开，析构函数又抛出异常 B：

$$
\text{栈展开中} \xrightarrow{\text{析构}} \text{新异常 B} \Rightarrow \text{std::terminate}()
$$

这使得带有非 noexcept 析构函数的类型在栈展开场景下是危险的。

## 数据流

### 异常栈展开的数据流

<pre>
调用栈（自底向上）                    异常对象（堆）              栈帧回收
+-----------------------------+    +---------------+    +------------------+
| main()                      |    | std::exception|    | 释放 main 栈帧   |
|  └─ foo()                   |    | 的派生类对象   |    | 释放 foo 栈帧   |
|       └─ bar()              | ──> 异常构造      | ──>  释放 bar 栈帧  |
|            └─ throw;        |    （拷贝/移动）  |    | 析构局部对象     |
+-----------------------------+    +---------------+    +------------------+
         │                              │
         └────────── 栈展开 ───────────┘  所有权：异常传播
</pre>

**步骤**：
1. `throw` 表达式构造异常对象（拷贝/移动，调用拷贝或移动构造函数）。
2. 异常对象从抛出位置向上传播（栈展开），逐层寻找匹配的 `catch` 子句。
3. 每层栈帧被弹出前，先析构该帧内构造的所有局部对象（RAII）。
4. 找到匹配 `catch` 后，异常对象所有权转移给 `catch` 子句的参数。
5. 若无匹配 `catch`，调用 `std::terminate()`（程序终止）。

### uncaught_exceptions 的状态机

`std::uncaught_exceptions()` 返回当前线程的**活跃异常数**（正在栈展开的异常数）：

$$
\text{state} = \begin{cases}
0 & \text{正常析构（无栈展开）} \\
\ge 1 & \text{异常析构（栈展开中）}
\end{cases}
$$

设类 `X` 的析构函数调用了 `std::uncaught_exceptions()`，则：
- 构造 `X` 对象时，异常计数为 $n$。 。
- 析构时若异常计数变为 $n+1$，说明正在栈展开中。 ，说明正在栈展开中。
- 析构时若异常计数仍为 $n$，说明正常销毁。 ，说明正常销毁。

## 机制

### 三种异常安全保证的语义

| 保证级别 | 含义 | 操作失败时的状态 | 典型场景 |
|----------|------|-----------------|----------|
| **无抛出（nothrow）** | 操作保证不抛异常 | 数据不变 | `std::move`, `swap` |
| **强保证（strong）** | 失败则状态完全回滚 | 等价于操作前 | `std::vector::push_back`（需移动不抛） |
| **基本保证（basic）** | 失败后对象有效但未定义 | 有效但未知状态 | 大多数标准库操作 |

**强保证的代价**：强保证要求操作是**可逆的**（或实现为"复制-修改-交换"）。设操作修改状态 $S_0 \to S_1$，若失败则恢复到 $S_0$。这意味着操作可能需要额外复制一份完整状态，内存和时间开销翻倍。 ，若失败则恢复到 $S_0$。这意味着操作可能需要额外复制一份完整状态，内存和时间开销翻倍。 。这意味着操作可能需要额外复制一份完整状态，内存和时间开销翻倍。

### RAII 与资源获取模式

RAII 将资源生命周期绑定到局部对象的构造/析构周期：

$$
\text{Resource} \xrightarrow{\text{acquire}} \text{RAII-Guard} \xrightarrow{\text{release}} \text{Resource}
$$

构造函数获取资源，析构函数释放资源。资源释放时机严格绑定于**词法作用域的退出**（正常返回或异常展开），无需程序员显式调用释放代码。

**lock_guard 的例子**：

```cpp
std::mutex m;
void safe() {
    std::lock_guard<std::mutex> lg(m);  // 构造时加锁
    // ... 操作保护区 ...
}  // lg 析构，自动解锁
```

若操作期间抛出异常，栈展开触发 `lg` 析构，`mutex` 被正确解锁。若使用手动 `lock()/unlock()`，异常会导致 `unlock()` 不被调用（死锁风险）。

### noexcept 对移动语义的影响

`std::vector::push_back` 的选择逻辑：

```
push_back(const T& val):
  if (size == capacity) → reallocate
    新建临时 vector（拷贝旧元素）
    对新元素：若 T 的拷贝构造函数 noexcept → 拷贝
              否则若 T 的移动构造函数 noexcept → 移动
              否则 → 拷贝（移动失败则抛异常）
  else: 直接拷贝/移动 val
```

```cpp
// 决策伪代码
if (size_ == capacity_) {
    auto new_cap = grow();
    auto tmp = vector<T>(new_cap);  // 分配新内存
    // 旧元素转移到 tmp（移动不抛异常保证）
    // 新元素按以下规则插入：
    if (std::is_nothrow_move_constructible_v<T>)
        tmp.push_back(std::move(val));  // 移动
    else
        tmp.push_back(val);  // 拷贝
    swap(tmp, *this);  // O(1) 替换
} else {
    if constexpr (std::is_nothrow_move_constructible_v<T>)
        emplace_back(std::move(val));
    else
        emplace_back(val);
}
```

### static_assert 的编译期求值

`static_assert` 在编译期求值断言表达式，若为 `false` 则编译器报错并终止编译。这是 C++ 模板元编程中**约束传播**的核心机制：

```cpp
static_assert(std::is_same_v<int, float>);  // 编译期检测类型不匹配
// 编译器输出：错误：static_assert 失败
```

**为什么需要编译期断言**：运行时断言（`assert`）在 Release 编译时被禁用（`NDEBUG` 定义后），且在未定义行为发生之后才可能检测到。静态断言在编译期强制验证不变量，消灭了一类运行时错误。

### C++20 概念（concept）对错误处理的改进

C++20 `concept` 将约束从"模板错误信息"提升为"一等公民的编译期谓词"：

```cpp
template<std::integral T>
T add(T a, T b) { return a + b; }

template<typename T>
concept Addable = requires(T a, T b) { a + b; };

template<Addable T>
T add(T a, T b) { return a + b; }
```

约束失败时的错误信息清晰可读，而非模板展开失败时的大量模板内部错误。这改善了"错误处理的上游化"——约束检查提前到模板实例化点，而非延迟到深层调用栈。

### C++23 std::expected：非异常错误处理的数学模型

> **latest 预览**：本节使用 C++23 特性（`std::expected`），stable（C++20）等价实现见本节末尾（`std::variant<T, E>` + `std::get_if`）。

**[C++23]** `std::expected<T, E>` 提供了基于返回值的错误处理模式，将错误信息编码在类型系统中：

$$
\text{expected}(T, E) = \begin{cases}
\text{value}(t) & \text{成功} \\
\text{error}(e) & \text{失败}
\end{cases}
$$

**形式化语义**：

| 操作 | 成功状态 | 失败状态 |
|------|----------|----------|
| `value()` | 返回 `T&` | `std::bad_expected_access` |
| `error()` | 未定义 | 返回 `E&` |
| `has_value()` | `true` | `false` |
| `and_then(f)` | `f(*this)` | 原错误传递 |
| `or_else(f)` | 原值传递 | `f(error())` |
| `transform(g)` | `expected(g(*value()))` | 原错误传递 |
| `map_error(f)` | 原值传递 | `expected<T>(f(error()))` |

**与异常的对比**：

| 维度 | 异常 | `std::expected` |
|------|------|-----------------|
| 错误传播 | 自动栈展开 | 手动 `return unexpected(...)` |
| 检查时机 | 运行时 | 编译期可见 |
| 性能（无错误时） | 零成本 | 零成本 |
| 性能（有错误时） | 栈展开开销 | 直接返回 |
| API 契约 | 不明确（可能抛） | 类型系统强制 |
| 组合性 | try-catch | `and_then`/`or_else` |

**为什么需要 `std::expected`**：

异常的风险在于**隐式性**——函数签名不声明可能抛出的异常类型，调用者无法在编译期验证错误处理完整性。`std::expected` 将错误作为返回值显式化：

```cpp
// 异常版本：签名不暴露可能失败
int parse_int(std::string_view s);

// expected 版本：签名即契约
std::expected<int, std::errc> parse_int(std::string_view s);
```

**违反约束的后果**：

- 访问已包含错误的 `expected` 的 `.value()`：抛出 `std::bad_expected_access`（编译期捕获，必须处理）
- 对已包含值的 `expected` 调用 `.error()`：未定义行为
- 未检查 `has_value()` 直接访问：未定义行为

**数学归约**：`std::expected` 本质上是**Either monad**在 C++ 类型系统中的实现，支持 `and_then`（链式成功计算）和 `or_else`（链式错误处理），与 Haskell 的 `Either` 类型同构。

**C++20 等价实现**（`std::variant<T, E>` + `std::get_if`，无 `and_then`/`transform`，需手动解包与传播）：

```cpp
#include <variant>   // C++20
#include <system_error>

// 签名即契约：返回值或错误都在类型里
std::variant<int, std::errc> parse_int(std::string_view s);

// 调用方手动检查并传播
auto r = parse_int(s);
if (auto* p = std::get_if<int>(&r)) {
    use(*p);                      // 成功
} else {
    auto e = std::get<std::errc>(r); // 失败
    // 链式传播需手写 if-else，无法像 and_then 那样组合
}
```

## 参考存根

```cpp
// 展示强异常安全的"复制-修改-交换"模式
class Widget {
    std::vector<int> data_;
public:
    void modify() noexcept {
        std::vector<int> tmp = data_;  // 复制
        try {
            modify_impl(tmp);  // 修改副本
            data_.swap(tmp);   // O(1) 交换（不抛异常）
        } catch (...) {
            // data_ 保持不变，tmp 析构时自动清理
            throw;
        }
    }
    virtual void modify_impl(std::vector<int>&) {}
};
```

// uncaught_exceptions 用于区分正常析构与异常析构
class FileTransaction {
    std::ofstream f_;
    bool committed_ = false;
public:
    ~FileTransaction() {
        if (std::uncaught_exceptions() > 0) {
            // 异常正在栈展开，取消写入（回滚）
            f_.close();
            std::remove(path_.c_str());
        } else if (!committed_) {
            // 正常析构但未提交，同样回滚
            f_.close();
            std::remove(path_.c_str());
        }
    }
};
