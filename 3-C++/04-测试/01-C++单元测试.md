# C++ 单元测试

## 定义

单元测试是通过在**隔离环境**中执行受控输入并验证实际输出是否匹配预期，来证明代码正确性的**形式化方法**。它将"这段代码在边界条件下表现正确"这一命题转化为可自动执行、可重复的机械检查，将主观的"看起来对"提升为客观的"数学上可证伪"。

单元测试的本质是**形式化验证的成本-效益平衡点**：当穷举所有输入不现实时，通过有策略地采样输入空间，以高概率暴露缺陷，同时将测试成本控制在可接受范围内。

## 数学模型

### 测试覆盖的概率解释

设代码库有 $B$ 个潜在 bug，测试套件对每个 bug 的检测概率为 $p$（检测敏感性）。执行 $n$ 个测试用例后，至少发现一个 bug 的概率：

$$P(\text{发现 bug}) = 1 - (1-p)^n$$

当 $p < 1$ 且 $n \to \infty$ 时，$P \to 1$——但实践中 $p$ 取决于代码路径覆盖率与测试用例对 bug 的相关性。**路径覆盖率** $C$ 是关键杠杆：若 bug 位于未覆盖路径上，则 $p = 0$。

**路径覆盖率的量化**：设代码有 $N$ 条独立路径，测试套件覆盖 $C$ 条，则单次测试命中的路径数为 $n \cdot C / N$（假设均匀分布）。路径覆盖率的边际效益递减——从 90% 到 100% 的覆盖率提升需要指数级更多的测试用例。

### 断言的逻辑语义

断言宏将布尔表达式转化为证伪命题：

```
EXPECT_EQ(a, b)  ≡  ¬(a = b)  →  测试失败
```

`ASSERT_*` 失败时产生**短路求值**：立即终止当前测试函数，返回错误状态。这符合**前置条件检查**的语义——若前置条件不满足，后续测试无意义。

**断言的代价函数**：设断言计算时间为 $t_a$，失败时报告写入时间为 $t_r$，成功时无额外开销。测试套件总时间 $T = \sum_i (t_a^{(i)} + \delta_i \cdot t_r^{(i)})$，其中 $\delta_i \in \{0, 1\}$ 是失败指示器。优化目标是最小化 $T$ 同时最大化缺陷检测率——这驱动了 `EXPECT_*`（多故障报告）vs `ASSERT_*`（早期返回）的选择。

### 参数化测试的复杂度

参数化测试将测试数据空间 $D$ 划分为 $k$ 个等价类，每类选取代表值。设原测试逻辑时间复杂度为 $O(T)$，则参数化后总复杂度为 $O(k \cdot T)$——数据量线性增长，代码路径不复制的。

**组合爆炸的约束**：若参数空间是 $n$ 维且每维有 $m$ 个取值点，全组合数为 $m^n$。当 $n \geq 3$ 且 $m \geq 5$ 时，$5^3 = 125$ 已成为管理负担。常用约束策略：

1. **等价类划分**：将输入空间划分为有效/无效/边界类，每类只选一个代表 → $O(n)$ 而非 $O(m^n)$
2. **Pairwise 约束**：保证每对参数组合至少出现一次 → $O(m^2 \cdot n)$ 而非 $O(m^n)$
3. **随机采样**：`testing::Values()` → `testing::ValuesIn(random_generator())` → 期望覆盖 $\frac{k}{m^n}$ 的组合空间

**归约终点**：单元测试的代价归结为**测试执行时间 + 断言计算 + 框架开销**，三者受 CPU 流水线、内存带宽和测试框架实现制约。

### 测试隔离的代数模型

单元测试要求被测代码与依赖隔离。设被测单元为 $U$，依赖为 $D_1, D_2, ..., D_n$。隔离通过**替换**实现：

```
真实环境：U(D_1, D_2, ..., D_n)
测试环境：U(D_1', D_2', ..., D_n')  // mock/fake 依赖
```

替换的约束是**接口兼容性**：$D_i'$ 必须实现与 $D_i$ 相同的接口契约。形式化地，若 $D_i$ 的接口为 $\mathcal{I}_i$，则 $D_i'$ 需满足 $\mathcal{I}_i \subseteq \text{implemented\_by}(D_i')$。

### 死亡测试的数学语义

死亡测试（Death Tests）验证程序在特定条件下调用 `std::terminate` 或触发断言。这与正常测试的本质区别：

- 正常测试：$\text{postcondition}(U(\text{input})) = \text{true}$ → PASS
- 死亡测试：$\text{terminate\_called} \iff \text{expected\_condition}$ → PASS

**"期望死亡"的双重性**：当 `EXPECT_DEATH(statement, regex)` 执行时：
1. `statement` 必须触发死亡（否则测试 FAIL）
2. 死亡信息必须匹配 `regex`（否则测试 FAIL）

两个条件是**合取关系**，必须同时满足。这与 `ASSERT_DEATH` 的差异在于：前者允许报告多个失败，后者短路返回。

## 数据流

<pre>
[源代码]  ──编译时──> [测试二进制]  ──运行时──> [测试发现]
                              │
                              ▼
                    ┌─────────────────────┐
                    │  TEST_F (Fixture)   │  ← 套件级共享状态
                    │  ┌───────────────┐  │
                    │  │ SetUp()       │  │  ← 每次测试前
                    │  ├───────────────┤  │
                    │  │ 测试用例 1     │  │  ← ASSERT_* 失败 → 立即返回
                    │  │ 测试用例 2     │  │  ← EXPECT_* 失败 → 继续
                    │  │ ...           │  │
                    │  ├───────────────┤  │
                    │  │ TearDown()    │  │  ← 每次测试后
                    │  └───────────────┘  │
                    │  ┌───────────────┐  │
                    │  │ ~Fixture()    │  │  ← 套件结束时（RAII 保证）
                    │  └───────────────┘  │
                    └─────────────────────┘
                              │
                              ▼
                    [XML/JSON 报告]  或  [CTest 聚合]
</pre>

**所有权流转**：
- Fixture 对象：构造时获取资源（堆内存、文件句柄），析构时释放——RAII 保证即使测试崩溃也释放
- 测试数据：参数化测试中，`GetParam()` 返回的 tuple 只读引用，所有权在测试框架侧
- 测试结果：断言状态在每个检查点产生，不跨测试传递
- Mock 对象：创建时注入，测试结束时自动销毁——无需手动 `delete`

**数据流的不变量**：
1. 每个 `SetUp()` 必有对应的 `TearDown()`（RAII 保证）
2. Fixture 状态在测试间隔离（每个测试获得独立的 Fixture 副本）
3. 主进程死亡测试：子进程执行 `statement`，父进程验证退出状态

## 机制

### 断言宏的控制流语义

`EXPECT_*` 与 `ASSERT_*` 的差异不是语法糖，而是**错误恢复策略**的选择：

| 宏 | 失败时行为 | 适用场景 |
|----|-----------|----------|
| `EXPECT_*` | 记录错误，继续执行 | 验证点分散，允许报告多个失败 |
| `ASSERT_*` | 立即返回，不执行后续 | 前置条件检查、不可恢复状态 |

**约束**：在单个测试函数内混用两者时，记住 `ASSERT_*` 是**早期返回**。若在循环内使用 `ASSERT_*`，需确认这不是预期行为——循环中的早期返回可能漏检后续迭代。

**实现语义**：GoogleTest 中，`EXPECT_*` 展开为记录失败并继续的代码；`ASSERT_*` 展开为失败时 `return` 当前函数。这导致：
- `EXPECT_*` 失败后，当前函数内其后的代码仍会执行
- `ASSERT_*` 失败后，`TearDown()` 仍会被调用（GoogleTest 框架保证）

### Fixture 的 RAII 保证

GoogleTest 的 `SetUp()`/`TearDown()` 优于手工资源管理的根本原因：

```cpp
class DatabaseTest : public testing::Test {
protected:
    Database* db_{nullptr};
    ~DatabaseTest() override {
        delete db_;  // 即使测试崩溃也执行
    }
};
```

C++ 保证**栈展开**时析构函数被调用，无论是因为异常传播还是断言失败导致的非局部跳转。手工 `new`/`delete` 若测试中间抛出未捕获异常，`delete` 永远不会执行——内存泄漏。

**C++23 改进**：`testing::TempDir()` （C++17+ GoogleTest 扩展）自动管理临时目录生命周期，无需手动清理。底层实现通过 RAII 封装 `std::filesystem::remove_all`，保证即使 `std::terminate` 被调用也能清理。

### 参数化测试的组合爆炸控制

参数数量 $n$ 导致测试执行次数线性增长 $n \cdot T$。若 $n$ 过大（如边界值分析产生数百组），考虑：

1. **等价类划分**：将输入空间划分为有效/无效/边界类，每类只选一个代表
2. **随机采样**：`testing::Values()` → `testing::ValuesIn(random_generator())`
3. **标签过滤**：`--gtest_filter=*Math*` 在运行时选择子集

**约束**：参数化测试中，`GetParam()` 返回类型必须与 `INSTANTIATE_TEST_CASE_P` 声明一致，否则编译期报错。这是模板约束导致的，错误信息通常指向 `GetParam()` 调用处而非声明处。

### C++20 合约测试（C++26 移除）

> **C++23/26 变更**：C++20 引入的 `[[expect: condition]]` 合约属性在 C++26 中被移除，重新设计为 `std::contract_violation` 机制（原定 C++26，后延期）。

合约提供**编译期前置条件检查**，与运行时断言互补：

```cpp
int divide(int a, int b) [[ pre: b != 0 ]] [[ post: r, r * b == a ]];
```

合约失败时调用 `std::contract_violation` 处理程序，可配置为抛出、终止或忽略。

**合约 vs 断言的本质差异**：
- 断言：测试时检查，失败可恢复
- 合约：编译时（部分）+ 运行时检查，失败表示程序存在**逻辑错误**（而非输入错误）

### mock 的依赖注入

`std::function` + lambda 是 C++17+ 的轻量 mock 方案，无需重型框架：

```cpp
std::function<int(DataStore&, int)> get_fn = [](DataStore& ds, int key) {
    return ds.get(key);  // 真实实现
};
// 测试时替换为 mock
get_fn = [](DataStore&, int key) { return key * 2; };
```

**约束**：lambda 无法直接替代虚拟方法——需要运行时多态时仍需 `std::function` 包装或 GoogleMock 的 `ON_CALL`。

**依赖注入的代数约束**：设接口为 $I$，实现为 $\{C_1, C_2, ..., C_n\}$。注入要求：
$$\forall c \in \{C_1, ..., C_n\}: c \text{ 实现 } I \iff \text{测试可替换}$$

这保证测试环境与生产环境的接口兼容性。

### 死亡测试的进程模型

GoogleTest 支持两种死亡测试模式：

| 模式 | 实现 | 适用场景 |
|------|------|----------|
| `fast死亡测试`（默认） | 子进程执行，`_exit()` 快速返回 | 断言崩溃、死锁检测 |
| `膛线死亡测试` | `exec()` 替换进程映像 | `std::terminate`、构造时崩溃 |

**进程间通信语义**：
- 子进程退出状态编码死亡原因
- 父进程通过 `waitpid()` 获取状态
- 正则表达式匹配的是 `stderr` 输出

**约束**：在 `fork()` 后执行 `exec()` 前，父子进程共享文件描述符。这可能导致意外副作用——如父进程持有锁，`fork()` 后子进程也持有同一锁的副本（而非同一个锁对象）。

## 框架对比

| 维度 | GoogleTest | Catch2 | doctest (C++17+) |
|------|-----------|--------|------------------|
| 头文件 | 多文件（需编译） | 单头文件 | 单头文件 |
| 断言风格 | `EXPECT_*` / `ASSERT_*` | `REQUIRE` / `CHECK` | `CHECK` / `REQUIRE` |
| 参数化 | `TEST_P` + `GetParam()` | `TEST_CASE_METHOD` + 模板 | `SUBCASE` 组合 |
| 测试发现 | `gtest_discover_tests()` | 编译期宏 | 编译期宏 |
| 死亡测试 | `EXPECT_DEATH` | `REQUIRE`+信号 | ❌ |
| C++20 合约 | ❌ | ❌ | ❌ |

**选型原则**：
- 大型项目、需要死亡测试/XML 输出 → GoogleTest
- 快速引入、零配置、自然语言风格 → Catch2
- 仅需轻量验证、偏好单头文件 → doctest

## CMake 集成

<pre>
cmake_minimum_required(VERSION 3.16)
project(MyProject)
enable_testing()

include(FetchContent)
FetchContent_Declare(googletest GIT_REPOSITORY ...)
FetchContent_MakeAvailable(googletest)

add_executable(tests test_main.cpp)
target_link_libraries(tests PRIVATE GTest::gtest GTest::gtest_main)

include(GoogleTest)
gtest_discover_tests(tests)  ← 构建后扫描二进制，注入 CTest
</pre>

`gtest_discover_tests()` 在**构建后**运行，扫描已编译的测试符号，动态注册到 CTest——无需硬编码测试名称，支持 CMake 重新生成时自动更新。

**构建系统的数据流**：
```
CMake 配置 → 生成构建系统 → 编译测试二进制 → gtest_discover_tests() 扫描
                                                              ↓
                                                    测试列表注入 CTest
                                                              ↓
                                                    ctest -N 枚举测试
                                                    ctest -R <regex> 运行
```

## 常见反模式

### 断言不足（Under-Assertion）

仅验证返回值，不验证副作用：

```cpp
// 不足：只检查返回值
TEST(BadExample, PushBack) {
    std::vector<int> v;
    v.push_back(42);
    EXPECT_EQ(v.back(), 42);  // 未检查 size()
}

// 充分：验证所有可观测状态
TEST(GoodExample, PushBack) {
    std::vector<int> v;
    v.push_back(42);
    EXPECT_EQ(v.back(), 42);
    EXPECT_EQ(v.size(), 1);
    EXPECT_FALSE(v.empty());
}
```

### 过度 Mock（Test Envy）

Mock 所有依赖，失去单元测试的意义：

```cpp
// 过度：Mock 了所有东西
TEST(BadExample, UsesMockedEverything) {
    auto mock_db = std::make_unique<MockDatabase>();
    auto mock_cache = std::make_unique<MockCache>();
    auto mock_logger = std::make_unique<MockLogger>();
    service = std::make_unique<Service>(
        std::move(mock_db),
        std::move(mock_cache),
        std::move(mock_logger));
    // 这更像集成测试
}

// 适度：只 Mock 外部依赖（数据库、网络）
TEST(GoodExample, UsesRealCache) {
    auto mock_db = std::make_unique<MockDatabase>();
    auto cache = std::make_unique<RealCache>();  // 真实缓存
    service = std::make_unique<Service>(
        std::move(mock_db),
        *cache);  // 按引用传递真实缓存
}
```

### 时间相关的测试

使用 `std::this_thread::sleep_for` 使测试不可靠：

```cpp
// 不可靠：依赖时间
TEST(BadExample, Timeout) {
    async_operation();
    std::this_thread::sleep_for(std::chrono::milliseconds(100));
    EXPECT_TRUE(completed());
}

// 可靠：使用同步原语
TEST(GoodExample, Timeout) {
    async_operation();
    std::future<void> future = promise.get_future();
    EXPECT_EQ(future.wait_for(std::chrono::milliseconds(100)),
              std::future_status::ready);
}
```

## 参考存根

```cpp
// GoogleTest + C++20
#include <gtest/gtest.h>
#include <source_location>

TEST(MathTest, Addition) {
    EXPECT_EQ(add(2, 2), 4) << std::source_location::current().function_name();
}

// Catch2
#define CATCH_CONFIG_MAIN
#include <catch2/catch_test_macros.hpp>
TEST_CASE("Math operations", "[math]") {
    CHECK(add(2, 2) == 4);
}

// Fixture (RAII)
class TempFileTest : public testing::Test {
protected:
    std::FILE* file_{nullptr};
    ~TempFileTest() override { if (file_) std::fclose(file_); }
};
TEST_F(TempFileTest, Write) {
    file_ = std::fopen("test.txt", "w");
    ASSERT_TRUE(file_);
}

// 参数化 (C++17+)
class AddTest : public testing::TestWithParam<std::tuple<int, int, int>> {};
TEST_P(AddTest, Values) {
    auto [a, b, expected] = GetParam();
    EXPECT_EQ(add(a, b), expected);
}
INSTANTIATE_TEST_CASE_P(AddTests, AddTest,
    testing::Values(std::make_tuple(1, 2, 3)));

// 死亡测试
TEST(DeathTest, DivideByZero) {
    EXPECT_DEATH(divide(1, 0), "division by zero");
}

// Mock (GoogleMock)
#include <gmock/gmock.h>
class MockDataStore {
public:
    MOCK_METHOD(int, get, (int key), (const));
};
TEST(MockTest, ReturnsDouble) {
    MockDataStore mock;
    ON_CALL(mock, get(5)).WillByDefault(testing::Return(10));
    EXPECT_CALL(mock, get(5));
    // 使用 mock 进行测试
}
```
