# C++ 单元测试

## 定义

单元测试是通过在**隔离环境**中执行受控输入并验证实际输出是否匹配预期，来证明代码正确性的**形式化方法**。它将"这段代码在边界条件下表现正确"这一命题转化为可自动执行、可重复的机械检查，将主观的"看起来对"提升为客观的"数学上可证伪"。

单元测试的本质是**形式化验证的成本-效益平衡点**：当穷举所有输入不现实时，通过有策略地采样输入空间，以高概率暴露缺陷，同时将测试成本控制在可接受范围内。

## 数学模型

### 测试覆盖的概率解释

设代码库有 $B$ 个潜在 bug，测试套件对每个 bug 的检测概率为 $p$ （检测敏感性）。执行 $n$ 个测试用例后，至少发现一个 bug 的概率：

$P(\text{发现 bug}) = 1 - (1-p)^n$

当 $p < 1$ 且 $n \to \infty$ 时， $P \to 1$——但实践中 $p$ 取决于代码路径覆盖率与测试用例对 bug 的相关性。**路径覆盖率** $C$ 是关键杠杆：若 bug 位于未覆盖路径上，则 $p = 0$。

**路径覆盖率的量化**：设代码有 $N$ 条独立路径，测试套件覆盖 $C$ 条，则单次测试命中的路径数为 $n \cdot C / N$ （假设均匀分布）。路径覆盖率的边际效益递减——从 90% 到 100% 的覆盖率提升需要指数级更多的测试用例。

**归约终点**：测试覆盖率的极限受制于**可达路径数**（受程序逻辑约束）和**路径激活条件数**（受输入空间维度约束）。

### 断言的逻辑语义

断言宏将布尔表达式转化为证伪命题：

```
EXPECT_EQ(a, b)  ≡  ¬(a = b)  →  测试失败
```

`ASSERT_*` 失败时产生**短路求值**：立即终止当前测试函数，返回错误状态。这符合**前置条件检查**的语义——若前置条件不满足，后续测试无意义。

**断言的代价函数**：设断言计算时间为 $t_a$ ，失败时报告写入时间为 $t_r$ ，成功时无额外开销。测试套件总时间 $T = \sum_i (t_a^{(i)} + \delta_i \cdot t_r^{(i)})$ ，其中 $\delta_i \in \{0, 1\}$ 是失败指示器。优化目标是最小化 $T$ 同时最大化缺陷检测率——这驱动了 `EXPECT_*`（多故障报告）vs `ASSERT_*`（早期返回）的选择。

### 参数化测试的组合爆炸控制

参数化测试将测试数据空间 $D$ 划分为 $k$ 个等价类，每类选取代表值。设原测试逻辑时间复杂度为 $O(T)$ ，则参数化后总复杂度为 $O(k \cdot T)$——数据量线性增长，代码路径不复制的。

**组合爆炸的约束**：若参数空间是 $n$ 维且每维有 $m$ 个取值点，全组合数为 $m^n$ 。当 $n \geq 3$ 且 $m \geq 5$ 时， $5^3 = 125$ 已成为管理负担。约束策略将复杂度从 $O(m^n)$ 降为 $O(n \cdot m^2)$：

| 策略 | 复杂度 | 保证 | 适用场景 |
|------|--------|------|----------|
| 全组合 | $O(m^n)$ | 所有组合 | $n \leq 2$ |
| Pairwise | $O(n \cdot m^2)$ | 每对参数至少组合一次 | 交互Bug主要来自两两组合 |
| 等价类划分 | $O(n)$ | 每类代表值 | 边界值驱动的缺陷 |
| 随机采样 | $O(k)$ | 概率覆盖 | 大规模探索 |

**数学本质**：Pairwise 约束基于"大多数交互Bug来自两两参数交互"的经验假设。形式化：设 $B$ 是由 $t$ 个参数交互产生的 bug，若 $t \leq 2$ ，则 pairwise 测试必能发现 $B$ 。

### 测试隔离的代数约束

单元测试要求被测单元与依赖隔离。设被测单元为 $U$ ，依赖为 $D_1, D_2, ..., D_n$ 。隔离通过**替换**实现：

```
真实环境：U(D_1, D_2, ..., D_n)
测试环境：U(D_1', D_2', ..., D_n')  // mock/fake 依赖
```

**接口兼容性的形式化约束**：若 $D_i$ 的接口为 $\mathcal{I}_i$ ，则 $D_i'$ 需满足：
$\mathcal{I}_i \subseteq \text{implemented\_by}(D_i')$

这保证 $U$ 对 $D_i$ 的所有调用都能透明地转发到 $D_i'$ 。

**依赖注入的代数本质**：注入即**态射**（morphism）——$U$ 是从依赖接口到实现的函数对象，mock 替换是域的同构映射，保持了 $\mathcal{I}_i$ 的结构。

### 死亡测试的数学语义

死亡测试（Death Tests）验证程序在特定条件下调用 `std::terminate` 或触发断言。这与正常测试的本质区别：

- 正常测试： $\text{postcondition}(U(\text{input})) = \text{true}$ → PASS
- 死亡测试： $\text{terminate\_called} \iff \text{expected\_condition}$ → PASS

**"期望死亡"的双重性**：当 `EXPECT_DEATH(statement, regex)` 执行时：
1. `statement` 必须触发死亡（否则测试 FAIL）
2. 死亡信息必须匹配 `regex`（否则测试 FAIL）

两个条件是**合取关系**，必须同时满足。这与 `ASSERT_DEATH` 的差异在于：前者允许报告多个失败，后者短路返回。

**死亡测试的进程代数**：父进程等待子进程死亡事件 $\delta$ 。若 $\delta$ 发生且匹配 $R$ （正则表达式），则测试通过。形式化为：
$\text{PASS} \iff \delta.\text{occurred} \land \text{match}(\delta.\text{output}, R)$

## 数据流

<pre>
[源代码]  ──编译时──> [测试二进制]  ──运行时──> [测试发现]
                              │
                              ▼
                    ┌─────────────────────┐
                    │  TEST_F (Fixture)   │  ← 套件级共享状态
                    │  ┌───────────────┐  │
                    │  │ SetUp()       │  │  ← 每次测试前（RAII 之前）
                    │  ├───────────────┤  │
                    │  │ 测试用例 1     │  │  ← ASSERT_* 失败 → return
                    │  │ 测试用例 2     │  │  ← EXPECT_* 失败 → 继续
                    │  │ ...           │  │
                    │  ├───────────────┤  │
                    │  │ TearDown()    │  │  ← 每次测试后（RAII 之后）
                    │  └───────────────┘  │
                    │  ┌───────────────┐  │
                    │  │ ~Fixture()    │  │  ← 套件结束时（RAII 保证）
                    │  └───────────────┘  │
                    └─────────────────────┘
                              │
                              ▼
                    [XML/JSON 报告]  或  [CTest 聚合]
</pre>

**所有权流转**：
- Fixture 对象：构造时获取资源（堆内存、文件句柄），析构时释放——RAII 保证即使测试崩溃也释放
- 测试数据：参数化测试中，`GetParam()` 返回的 tuple 只读引用，所有权在测试框架侧
- 测试结果：断言状态在每个检查点产生，不跨测试传递
- Mock 对象：创建时注入，测试结束时自动销毁——无需手动 `delete`

**数据流的不变量**：
1. 每个 `SetUp()` 必有对应的 `TearDown()`（RAII 保证）
2. Fixture 状态在测试间隔离（每个测试获得独立的 Fixture 副本）
3. 主进程死亡测试：子进程执行 `statement`，父进程验证退出状态

## 机制

### 断言宏的控制流语义

`EXPECT_*` 与 `ASSERT_*` 的差异不是语法糖，而是**错误恢复策略**的选择：

| 宏 | 失败时行为 | 适用场景 |
|----|-----------|----------|
| `EXPECT_*` | 记录错误，继续执行 | 验证点分散，允许报告多个失败 |
| `ASSERT_*` | 立即返回，不执行后续 | 前置条件检查、不可恢复状态 |

**约束**：在单个测试函数内混用两者时，记住 `ASSERT_*` 是**早期返回**。若在循环内使用 `ASSERT_*`，需确认这不是预期行为——循环中的早期返回可能漏检后续迭代。

**实现语义**：GoogleTest 中，`EXPECT_*` 展开为记录失败并继续的代码；`ASSERT_*` 展开为失败时 `return` 当前函数。这导致：
- `EXPECT_*` 失败后，当前函数内其后的代码仍会执行
- `ASSERT_*` 失败后，`TearDown()` 仍会被调用（GoogleTest 框架保证）

### Fixture 的 RAII 保证

GoogleTest 的 `SetUp()`/`TearDown()` 优于手工资源管理的根本原因在于**异常安全**：

```cpp
class DatabaseTest : public testing::Test {
protected:
    Database* db_{nullptr};
    ~DatabaseTest() override {
        delete db_;  // 即使测试崩溃也执行
    }
};
```

C++ 保证**栈展开**时析构函数被调用，无论是因为异常传播还是断言失败导致的非局部跳转。手工 `new`/`delete` 若测试中间抛出未捕获异常，`delete` 永远不会执行——内存泄漏。

**RAII 的数学本质**：资源获取是**公理**，资源释放是**定理**。构造时获取资源是前提条件，析构时释放资源是必然结论——两者通过对象的生命周期绑定，不可分离。

**C++23 改进**：`testing::TempDir()` 自动管理临时目录生命周期，底层通过 RAII 封装 `std::filesystem::remove_all`，保证即使 `std::terminate` 被调用也能清理。

### 参数化测试的组合爆炸控制

参数数量 $n$ 导致测试执行次数线性增长 $n \cdot T$ 。若 $n$ 过大（如边界值分析产生数百组），考虑：

1. **等价类划分**：将输入空间划分为有效/无效/边界类，每类只选一个代表
2. **随机采样**：`testing::Values()` → `testing::ValuesIn(random_generator())`
3. **标签过滤**：`--gtest_filter=*Math*` 在运行时选择子集

**约束**：参数化测试中，`GetParam()` 返回类型必须与 `INSTANTIATE_TEST_CASE_P` 声明一致，否则编译期报错。这是模板约束导致的，错误信息通常指向 `GetParam()` 调用处而非声明处。

### C++20 合约测试（C++26 重设计）

> **C++23/26 变更**：C++20 引入的 `[[expect: condition]]` 合约属性在 C++26 中被移除，重新设计为 `std::contract_violation` 机制（原定 C++26，后延期）。

合约提供**编译期前置条件检查**，与运行时断言互补：

```cpp
int divide(int a, int b) [[ pre: b != 0 ]] [[ post: r, r * b == a ]];
```

合约失败时调用 `std::contract_violation` 处理程序，可配置为抛出、终止或忽略。

**合约 vs 断言的本质差异**：

| 维度 | 断言 | 合约 |
|------|------|------|
| 检查时机 | 运行时 | 编译时（部分）+ 运行时 |
| 失败语义 | 测试失败，可恢复 | 程序逻辑错误，不可恢复 |
| 语义含义 | 输入验证 | 不变量验证 |

### mock 的依赖注入

`std::function` + lambda 是 C++17+ 的轻量 mock 方案，无需重型框架：

```cpp
std::function<int(DataStore&, int)> get_fn = [](DataStore& ds, int key) {
    return ds.get(key);  // 真实实现
};
// 测试时替换为 mock
get_fn = [](DataStore&, int key) { return key * 2; };
```

**约束**：lambda 无法直接替代虚拟方法——需要运行时多态时仍需 `std::function` 包装或 GoogleMock 的 `ON_CALL`。

**依赖注入的代数约束**：设接口为 $I$ ，实现为 $\{C_1, C_2, ..., C_n\}$ 。注入要求：
$\forall c \in \{C_1, ..., C_n\}: c \text{ 实现 } I \iff \text{测试可替换}$

这保证测试环境与生产环境的接口兼容性。

### 死亡测试的进程模型

GoogleTest 支持两种死亡测试模式：

| 模式 | 实现 | 适用场景 |
|------|------|----------|
| `fast死亡测试`（默认） | 子进程执行，`_exit()` 快速返回 | 断言崩溃、死锁检测 |
| `膛线死亡测试` | `exec()` 替换进程映像 | `std::terminate`、构造时崩溃 |

**进程间通信语义**：
- 子进程退出状态编码死亡原因
- 父进程通过 `waitpid()` 获取状态
- 正则表达式匹配的是 `stderr` 输出

**约束**：在 `fork()` 后执行 `exec()` 前，父子进程共享文件描述符。这可能导致意外副作用——如父进程持有锁，`fork()` 后子进程也持有同一锁的副本（而非同一个锁对象）。

**死锁检测的局限性**：死亡测试只能检测 `statement` 本身的死锁。若死锁发生在 `statement` 完成后（通过 `atexit` 注册的清理函数），死亡测试无法检测。

## 框架对比

| 维度 | GoogleTest | Catch2 | doctest (C++17+) |
|------|-----------|--------|------------------|
| 头文件 | 多文件（需编译） | 单头文件 | 单头文件 |
| 断言风格 | `EXPECT_*` / `ASSERT_*` | `REQUIRE` / `CHECK` | `CHECK` / `REQUIRE` |
| 参数化 | `TEST_P` + `GetParam()` | `TEST_CASE_METHOD` + 模板 | `SUBCASE` 组合 |
| 测试发现 | `gtest_discover_tests()` | 编译期宏 | 编译期宏 |
| 死亡测试 | `EXPECT_DEATH` | `REQUIRE`+信号 | ❌ |
| C++20 合约 | ❌ | ❌ | ❌ |

**选型原则**：
- 大型项目、需要死亡测试/XML 输出 → GoogleTest
- 快速引入、零配置，自然语言风格 → Catch2
- 仅需轻量验证、偏好单头文件 → doctest

## 常见反模式

### 断言不足（Under-Assertion）

仅验证返回值，不验证副作用：

```cpp
// 不足：只检查返回值
TEST(BadExample, PushBack) {
    std::vector<int> v;
    v.push_back(42);
    EXPECT_EQ(v.back(), 42);  // 未检查 size()
}

// 充分：验证所有可观测状态
TEST(GoodExample, PushBack) {
    std::vector<int> v;
    v.push_back(42);
    EXPECT_EQ(v.back(), 42);
    EXPECT_EQ(v.size(), 1);
    EXPECT_FALSE(v.empty());
}
```

### 过度 Mock（Test Envy）

Mock 所有依赖，失去单元测试的意义：

```cpp
// 过度：Mock 了所有东西
TEST(BadExample, UsesMockedEverything) {
    auto mock_db = std::make_unique<MockDatabase>();
    auto mock_cache = std::make_unique<MockCache>();
    auto mock_logger = std::make_unique<MockLogger>();
    service = std::make_unique<Service>(
        std::move(mock_db),
        std::move(mock_cache),
        std::move(mock_logger));
    // 这更像集成测试
}

// 适度：只 Mock 外部依赖（数据库、网络）
TEST(GoodExample, UsesRealCache) {
    auto mock_db = std::make_unique<MockDatabase>();
    auto cache = std::make_unique<RealCache>();  // 真实缓存
    service = std::make_unique<Service>(
        std::move(mock_db),
        *cache);  // 按引用传递真实缓存
}
```

**原则**：mock 的边界是**责任边界**——被测单元只应对其直接依赖负责，不应 mock 依赖的依赖（否则变成集成测试）。

### 时间相关的测试

使用 `std::this_thread::sleep_for` 使测试不可靠：

```cpp
// 不可靠：依赖时间
TEST(BadExample, Timeout) {
    async_operation();
    std::this_thread::sleep_for(std::chrono::milliseconds(100));
    EXPECT_TRUE(completed());
}

// 可靠：使用同步原语
TEST(GoodExample, Timeout) {
    async_operation();
    std::future<void> future = promise.get_future();
    EXPECT_EQ(future.wait_for(std::chrono::milliseconds(100)),
              std::future_status::ready);
}
```

**约束**：时间相关的测试失败可能是**伪失败**——在负载高的机器上，100ms 可能不够。同步原语保证等待真正的状态变化，而非时间流逝。

# 调试与诊断

## 定义

调试是通过控制程序执行流程并在暂停点观察状态来定位缺陷源头的**系统性证伪假设**过程，其核心是 GDB/LLDB 的"暂停-检查-恢复"循环；诊断工具（Valgrind/SANITIZER）通过程序插桩在运行时检测内存安全违规和数据竞争，将未定义行为从不可见变为可观测。

调试的本质是**状态空间搜索**：程序状态空间 $S$ 包含所有可能的执行状态，缺陷导致状态偏离正常子空间 $S_{normal}$ 。调试过程是从异常状态 $s_{error} \in S \setminus S_{normal}$ 出发，通过反向追踪找到首次进入异常子空间的转移点。

## 数学模型

### 断点的硬件语义

x86 架构中，断点通过**调试寄存器**（DR0-DR7）实现：

```
DR7[15:0]  ── 启用位，每 2 位控制一个断点
DR7[19:16] ── 本地 breakpoint (仅当前任务)
DR7[23:20] ── 全局 breakpoint

每个断点：DRi (地址) + DR7[2i+1:2i] (条件: 执行/写入/读/IO)
```

**硬件断点的数学约束**：
- 可设断点数 $\leq 4$ （DR0-DR3）
- 断点条件编码为 2 位：00=执行，01=写入，11=读/写（I/O break 例外）
- DR7 的 L/G 位控制局部/全局范围

软件断点（`int3`，0xCC）则通过**指令替换**实现：调试器保存原始字节，插入 trap 指令，命中后恢复。硬件断点不修改代码，适合修改自校验代码。

**软件断点的状态机**：

```
正常执行 → (命中 int3) → 触发 #DB 异常
              ↓
         保存寄存器/PC
              ↓
         恢复原始字节
              ↓
         用户检查状态
              ↓
         (继续执行) → 重新插入 int3 → 正常执行
```

### 影子内存映射（AddressSanitizer）

ASAN 使用 1:8 影子映射：每 8 字节应用内存映射到 1 字节影子值。

**地址映射公式**：

$\text{shadow\_addr} = (\text{addr} >> 3) + \text{shadow\_offset}$

其中 `shadow_offset` 是链接时分配的影子区基址。影子值含义：

| 影子值 | 语义 |
|--------|------|
| 0 | 全部 8 字节可访问 |
| 负数 ($-k$, $1 \le k \le 7$) | 前 $k$ 字节可访问 |
| 正数 $k$ ($1 \le k \le 7$) | heap-left-redzone，距离边界 $k$ 字节 |
| ASCII 0xF0-0xFF | 特殊毒值（use-after-free） |

**ASAN 正确性的代数证明**：
- 映射比例 $1:8$ 保证了 $\text{shadow\_addr}$ 永远在合法影子区内
- 每个应用字节的状态可被独立查询
- 边界检查只需读取一个影子字节（ $O(1)$ ）

### 矢量时钟（ThreadSanitizer）

每个线程 $T_i$ 持有逻辑时钟 $VC_i$ ，初始化为全零。线程间同步时，时钟更新规则：

$VC_i = \max(VC_i, VC_j) \quad \text{（收到线程 } T_j \text{ 的消息）}$

每次线程 $T_i$ 执行内存访问 $W$ 时，记录：

$\text{record} = (\text{addr}, \text{value}, T_i, VC_i)$

数据竞争判定：两个线程对同一地址的访问无 `happens-before` 关系（无锁、无 mutex、无原子操作），且至少一个访问是写入。

**矢量时钟的数学性质**：
- **因果性**：若 $VC_i < VC_j$ ，则事件 $i$ 不可能影响事件 $j$
- **反称性**：若 $VC_i \leq VC_j$ 且 $VC_j \leq VC_i$ ，则 $VC_i = VC_j$ （不可区分事件）
- **并发性**：若 $VC_i \not\leq VC_j$ 且 $VC_j \not\leq VC_i$ ，则两事件并发

### 调试器的代价模型

调试器的总代价：

$C_{debug} = C_{interrupt} + C_{snapshot} + C_{symbol\_lookup}$

- $C_{interrupt}$ ：中断触发代价，受调试接口（ptrace/sejoln）制约
- $C_{snapshot}$ ：寄存器/内存保存代价， $O(1)$ （固定寄存器数）
- $C_{symbol\_lookup}$ ：符号表查找代价， $O(\log n)$ （DWARF 的 DIE 树）

诊断工具的代价：

$C_{diagnostic} = C_{instrumentation} + C_{state\_maintenance}$

- $C_{instrumentation}$ ：插桩检查代价，每次内存访问 $O(1)$
- $C_{state\_maintenance}$ ：状态维护代价（如 ASAN 影子内存、TSAN 矢量时钟）

**空间换时间的策略**：诊断工具的 overhead 来自于实时监控所有内存访问——这是用 CPU 和内存开销换取错误检测能力的trade-off。

### DWARF 行号表的状态机模型

DWARF 行号信息是**有限状态自动机**（FSM）的编码。编译时，编译器模拟这个 FSM 产生压缩的操作序列；调试时，GDB 解释这个序列来重建"源码地址 ↔ 机器指令"的映射。

```
状态 = (address, line, column, file, is_stmt, basic_block, ...)

转移操作：
- DW_LNS_copy:     advance_address(0), next_line(+1)
- DW_LNS_advance:  advance_address(delta)
- DW_LNS_const_add_pc: advance_address(255 * max_advance / max_advance_per_ instruction)
- DW_LNS_fixed_advance_pc: advance_address(delta)  // 显式地址推进
- DW_LNE_end_sequence: reset state
```

**单调性保证**：行号表中地址序列严格单调递增，支持二分查找。代价是编译器必须插入额外指令来记录"无操作"区域的行号变化。

### Valgrind VEX IR 的表达能力

Valgrind 将每条 x86 指令翻译为中间表示 VEX。VEX 是**图灵完备**的 IR：

- 支持无限虚拟寄存器
- 支持间接跳转（寄存器寻址）
- 支持条件执行（IR 条件码）

**图灵完备的意义**：VEX 可以表示任何可计算的程序行为，包括自修改代码、多线程同步、原生系统调用。这保证了 Valgrind 的**无漏报**特性——理论上能检测任何内存访问违规。

3. 将 PC 指向原始指令（而非 trap 后的下一条）
4. 用户执行 `next`/`step` 后，重新插入 0xCC

## 机制

### GDB 断点实现：软件断点 vs 硬件断点

**软件断点**（`break`）：
- 将目标地址的原始指令替换为 `int3`（0xCC）
- CPU 执行时触发 #DB 异常，OS 转交控制权给 GDB
- 优点：可设任意数量（仅受内存限制）
- 缺点：必须修改代码，不适合只读区域

**硬件断点**（`hbreak`）：
- 使用 DR0-DR7 调试寄存器，在 CPU 层面检测地址访问
- 优点：不修改代码，可设数据断点（写入/读取触发）
- 缺点：仅 4 个（x86），需 OS 支持

**条件断点的优化**：条件 `if` 判断在 trap 后执行，若条件不满足则立即恢复——断点仍每次命中，但 pause 代价只在条件满足时产生。对于高频代码路径，可设置计数器条件 `count > 100` 以跳过前期。

**Watchpoint 的硬件实现**：
- 数据断点通过 DR6 的 Bn 位指示触发
- DR7 的 Rw/len 字段指定监控的地址范围和访问类型
- 写入/读取触发取决于 DR7[2i+1:2i] 设置

### DWARF 符号表与行号映射

`-g` 生成的 DWARF 信息将每个机器指令地址映射回源文件+行号，并记录变量布局：

```cpp
// 源码
void foo(int x) {
    int y = x + 1;  // 行号 N
}
```

编译后 DWARF 条目：
```
DW_TAG_variable "y"
  DW_AT_location (DW_OP_breg5[RBP-0x10])  // y 在 [RBP-0x10]
  DW_AT_type (int)
```

`print y` 时，GDB 通过符号表找到 `y` 的 DWARF 描述，再通过当前栈帧的 RBP 寄存器计算实际地址 `[RBP-0x10]`。

**DWARF 行号表的数学结构**：
- 每个编译单元维护行号状态机（state machine）
- 特殊操作码（SPA/DW_LNS_extended_op）压缩状态转移
- 行号表是**单调递增**的地址序列，支持二分查找

**优化影响**：`-O2` 及以上时，变量可能被**寄存器优化**（不分配栈空间）或** SSA 形式**（常量传播、死代码消除），DWARF 信息描述的是优化后的布局，可能与源码不对应——这是调试信息的固有局限。

**clang -g vs -gdwarf-5**：
- `-gdwarf-5` 生成更紧凑的调试信息（40-50% 体积减少）
- `-gdwarf-5` 支持更好的压缩和并行加载
- 但部分旧版 GDB 不支持 DWARF-5

### Valgrind 的精确性保证

Valgrind 在**每条指令**级别重新解释程序，不依赖编译器插桩。这意味着：

1. **无漏报**：任何内存访问都被监控，包括库函数内部的
2. **无歧义**：立即报告违规，不延迟到后续检查
3. **无源码依赖**：二进制程序即可分析

代价是性能。Valgrind 维护整个进程的地址空间映射，每条内存访问都经过影子内存查找和边界检查。

**Valgrind 的局限性**：
- 无法检测**逻辑错误**（如错误的算法实现）
- 无法检测**数据竞争**（需 Helgrind/TSAN）
- 对自修改代码支持有限（JIT 场景需额外配置）

### ASAN 的内存 overhead

ASAN 的内存开销：
- **影子内存**：应用内存的 1/8（12.5%）
- **堆 redzone**：每次 `malloc` 前后各加 16-32 字节 redzone
- **栈 redzone**：每个栈帧前后加 16-32 字节（编译时插入）

总 overhead ≈ 2x 内存使用量。这是空间换时间的策略：将错误检测延迟到运行时，而非依赖静态分析。

**约束**：ASAN 无法检测**逻辑错误**（如使用错误的算法）和**数据竞争**（需 TSAN）。对于 use-after-return（而非 use-after-free），ASAN 无法检测，因为栈帧在返回时已释放。

### TSAN 的 happens-before 检测

TSAN 使用**矢量时钟**追踪 happens-before 关系。每次：
- 线程同步（原语）：互斥锁 lock/unlock、线程 join/spawn、原子操作
- 内存访问：记录 `(地址, 值, 线程ID, 时钟)`

判定数据竞争的两个必要条件：
1. **并发**：两个线程无 happens-before 关系（未通过同步原语建立）
2. **冲突**：对同一地址至少一次写入

```cpp
// 可能的竞争：两个线程同时写入同一地址
// T1: x = 1;       (write x)
// T2: x = 2;       (write x)
// 无 mutex/rlock 保护 → TSAN 报告竞争
```

**约束**：TSAN 无法检测**死锁**（需 ThreadSanitizer 的额外工具或 Helgrind）、**原子操作裸读/写**（需显式 `std::atomic`）和 **锁顺序反转**。

**TSAN 的 vector clock 实现**：
- 每个线程维护长度为 $n$ 的时钟向量（ $n$ = 线程数）
- join 时： $VC_{parent} = \max(VC_{parent}, VC_{child})$
- lock 时： $VC_{thread} = \max(VC_{thread}, VCLock)$

### MSAN（MemorySanitizer）

MSAN 检测**未初始化内存读取**：

- 跟踪每字节的"初始化状态"
- 读取未初始化内存时报告
- 适用于检测 `memcpy` 误用、模糊测试发现的数据流错误

**与 ASAN 的区别**：
- ASAN：检测越界访问、use-after-free
- MSAN：检测未初始化读取

**约束**：MSAN 要求所有代码都编译为 MSAN 版本（包括标准库），否则会产生"Wrapper absorbs uninitialized" 误报。

### UBSAN（UndefinedBehaviorSanitizer）

UBSAN 检测**未定义行为**：

| 类型 | 示例 | 行为 |
|------|------|------|
| 算术 | 除零、整数溢出 | 报告位置 |
| 空指针 | 解引用 NULL | 报告位置 |
| 非 POD | `memcpy` 到非 POD 对象 | 报告位置 |
| 转换 | 非法转换 | 报告位置 |

**约束**：UBSAN 不修复 UB，只是报告。程序仍以未定义方式运行。

### C++23/26 调试功能

**C++23 `std::print`**：格式化输出到 stderr，简化调试打印：

```cpp
std::print("x = {}, y = {}\n", x, y);  // C++23
```

**C++26 `std::source_location` 增强**：允许获取当前调用点的文件和行信息，用于运行时报告：

```cpp
void log_error(const char* msg, std::source_location loc = std::source_location::current()) {
    std::print("[{}:{}] {}\n", loc.file_name(), loc.line(), msg);
}
```

**C++26 调试容器**（提案）：
```cpp
std::vector<int> v{1, 2, 3};
std::println("v.size() = {}", v.size());  // 编译期格式化
```

|------|---------|----------|------|------|-------|

| 内存泄漏 | ❌ | 精确 | ✅ (leak sanitizer) | ❌ | ❌ |
| 数据竞争 | ❌ | Helgrind 部分 | ❌ | 精确 | ❌ |
| 未定义行为 | ❌ | ❌ | ❌ | ❌ | ✅ |
| 性能开销 | 无（运行时） | 10-50x | 2-3x | 3-10x | 1.5-2x |
| 需源码 | 否 | 否 | 是（重新编译） | 是 | 是 |

**选型决策树**：

```
崩溃？
├─ 段错误 → GDB (bt) + ASAN
├─ 内存泄漏 → Valgrind / ASAN (leak)
├─ 数据竞争 → TSan
├─ 逻辑错误 → GDB (断点/条件)
└─ 未定义行为 → UBSAN
```

## 编译配置

<pre>
Debug 构建（调试信息，关优化）:
  g++ -g -O0 -Wall -fno-omit-frame-pointer -o myapp myapp.cpp
                                      ↑ 保存帧指针，栈跟踪更完整

ASAN 构建（C++23 现代写法）:
  g++ -g -fsanitize=address -fsanitize=undefined -O1 -o myapp myapp.cpp
                                                      ↑
                                               ASAN 要求 O1+ 优化

TSAN 构建（检测数据竞争）:
  g++ -g -fsanitize=thread -O1 -fno-omit-frame-pointer -o myapp myapp.cpp
                                                         ↑
                                                  TSan 需要帧指针

MSAN 构建（检测未初始化读取）:
  g++ -g -fsanitize=memory -O1 -o myapp myapp.cpp

UBSAN 构建（检测未定义行为）:
  g++ -g -fsanitize=undefined -O1 -o myapp myapp.cpp

CMake 配置（C++20）:
  add_compile_options(
      $<$<CONFIG:Debug>:-O0 -g -fno-omit-frame-pointer>
      $<$<CONFIG:ASAN>:-fsanitize=address -fsanitize=undefined -O1>
      $<$<CONFIG:TSAN>:-fsanitize=thread -O1 -fno-omit-frame-pointer>
  )
</pre>

**优化级别的影响**：
- `-O0`：完整调试信息，但性能差
- `-O1`：最小优化，调试信息基本可用
- `-O2/-O3`：性能优化，部分变量可能被优化掉
- `-Og`（GCC 4.8+）：平衡调试体验和优化

## 常见问题诊断流程

### 段错误（Segmentation Fault）

1. `gdb ./myapp` → `run` → `bt` 定位崩溃位置和调用栈
2. `g++ -fsanitize=address -g -O1 ...` 重新编译，ASAN 报告 heap-buffer-overflow
3. 若 ASAN 无果，`valgrind --leak-check=full --show-leak-kinds=all ...` 提供更详细信息

**GDB 典型分析流程**：
```
(gdb) run
Program received signal SIGSEGV, Segmentation fault.
0x00000000004006f2 in process_data (ptr=0x0) at main.cpp:42
42          result = ptr->value;
(gdb) bt
#0  process_data (ptr=0x0) at main.cpp:42
#1  0x00000000004005a3 in main (argc=1, argv=0x7fffffffe380) at main.cpp:15
(gdb) print ptr
$1 = (Data *) 0x0
```

### 内存泄漏

- **Valgrind**: `valgrind --leak-check=full --show-leak-kinds=all --track-origins=yes ./myapp`
- **ASAN**: 编译时加 `-fsanitize=leak`，退出时报告（需链接 `libasan`）
- **MSAN**: `g++ -fsanitize=memory -g ...` 检测未初始化内存读取

**Valgrind 泄漏报告解读**：
```
==12345== 24 bytes in 1 blocks are definitely lost in loss record 1 of 2
   at 0x...: operator new(unsigned long) (vg_replace_malloc.c:...)
   by 0x...: main (main.cpp:25)
```
- "definitely lost"：确定泄漏，需修复
- "probably lost"：可能是泄漏（取决于指针位置）
- "still reachable"：程序结束前未释放，但可能是正常行为

### 数据竞争

```bash
g++ -fsanitize=thread -g -O1 -fno-omit-frame-pointer myapp.cpp -o myapp
./myapp
# TSan 报告格式:
# Write of size N at 0x... by thread T1:
#   Previous write of size N at 0x... by thread T0
```

**TSan 报告解读**：
- "Previous write" 不一定是真正的冲突写入，而是 happens-before 树中最近的写入
- 需结合代码判断是否真正竞争
- 常见误报：故意无锁共享的 `volatile` 数据

### 未定义行为

```bash
g++ -fsanitize=undefined -g -O1 myapp.cpp -o myapp
./myapp
# UBSAN 报告格式:
# main.cpp:42:3: runtime error: negation of -2147483648 cannot be represented in type 'int'
```

**常见 UBSAN 检测**：
- 有符号整数溢出
- 除零
- 空指针解引用
- 不合法的位移操作

### 调试符号缺失

```
(gdb) bt
#0  0x00000000004006f2 in ?? ()
```

缺少调试符号时：
1. 检查编译是否加 `-g`
2. 检查是否 strip 过：`file myapp` / `readelf -S myapp | grep debug`
3. 检查 DWARF 版本：`readelf -w myapp | head`

## 参考存根

```bash
# GDB 基础
gdb ./myapp
break main
break myapp.cpp:42
condition 1 count > 10  # 第11次才暂停
run
bt   # backtrace
print x
next / step / continue
watch x  # 数据断点（写入触发）
delete 1

# GDB 条件断点
break myapp.cpp:100 if x > 0 && y == NULL

# GDB 多线程
info threads
thread 2
break myapp.cpp:50 thread 2

# LLDB（macOS C++20+）
lldb ./myapp
breakpoint set --name main
breakpoint set --file main.cpp --line 42
thread step-over
frame variable
watchpoint set expression -- (int*)0x1000

# Valgrind（完整检查）
valgrind --leak-check=full --show-leak-kinds=all --track-origins=yes ./myapp

# Valgrind Helgrind（数据竞争）
valgrind --tool=helgrind ./myapp

# ASAN（内存错误检测）
g++ -g -fsanitize=address -fsanitize=undefined -O1 myapp.cpp -o myapp

# TSan（数据竞争检测）
g++ -g -fsanitize=thread -O1 -fno-omit-frame-pointer myapp.cpp -o myapp

# MSAN（未初始化读取检测）
g++ -g -fsanitize=memory -O1 myapp.cpp -o myapp

# UBSAN（未定义行为检测）
g++ -g -fsanitize=undefined -O1 myapp.cpp -o myapp

# C++23 调试打印
#include <print>
std::print("debug: x={}, addr={}\n", x, static_cast<void*>(&x));

# 调试宏（C++20 source_location）
#define LOG(msg) std::print("[{}:{}] {}\n", \
    std::source_location::current().file_name(), \
    std::source_location::current().line(), msg)
```
