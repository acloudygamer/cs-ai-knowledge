# 调试与诊断

## 定义

调试是通过控制程序执行流程并在暂停点观察状态来定位缺陷源头的**系统性证伪假设**过程，其核心是 GDB/LLDB 的"暂停-检查-恢复"循环；诊断工具（Valgrind/SANITIZER）通过程序插桩在运行时检测内存安全违规和数据竞争，将未定义行为从不可见变为可观测。

调试的本质是**状态空间搜索**：程序状态空间 $S$ 包含所有可能的执行状态，缺陷导致状态偏离正常子空间 $S_{normal}$。调试过程是从异常状态 $s_{error} \in S \setminus S_{normal}$ 出发，通过反向追踪找到首次进入异常子空间的转移点。

## 数学模型

### 断点的硬件语义

x86 架构中，断点通过**调试寄存器**（DR0-DR7）实现：

```
DR7[15:0]  ── 启用位，每 2 位控制一个断点
DR7[19:16] ── 本地 breakpoint (仅当前任务)
DR7[23:20] ── 全局 breakpoint

每个断点：DRi (地址) + DR7[2i+1:2i] (条件: 执行/写入/读/IO)
```

**硬件断点的数学约束**：
- 可设断点数 $\leq 4$（DR0-DR3）
- 断点条件编码为 2 位：00=执行，01=写入，11=读/写（I/O break 例外）
- DR7 的 L/G 位控制局部/全局范围

软件断点（`int3`，0xCC）则通过**指令替换**实现：调试器保存原始字节，插入 trap 指令，命中后恢复。硬件断点不修改代码，适合修改自校验代码。

**软件断点的状态机**：

```
正常执行 → (命中 int3) → 触发 #DB 异常
              ↓
         保存寄存器/PC
              ↓
         恢复原始字节
              ↓
         用户检查状态
              ↓
         (继续执行) → 重新插入 int3 → 正常执行
```

### 影子内存映射（AddressSanitizer）

ASAN 使用 1:8 影子映射：每 8 字节应用内存映射到 1 字节影子值。

**地址映射公式**：

$$\text{shadow\_addr} = (\text{addr} >> 3) + \text{shadow\_offset}$$

其中 `shadow_offset` 是链接时分配的影子区基址。影子值含义：

| 影子值 | 语义 |
|--------|------|
| 0 | 全部 8 字节可访问 |
| 负数 ($-k$, $1 \le k \le 7$) | 前 $k$ 字节可访问 |
| 正数 $k$ ($1 \le k \le 7$) | heap-left-redzone，距离边界 $k$ 字节 |
| ASCII 0xF0-0xFF | 特殊毒值（use-after-free） |

**ASAN 正确性的代数证明**：
- 映射比例 $1:8$ 保证了 $\text{shadow\_addr}$ 永远在合法影子区内
- 每个应用字节的状态可被独立查询
- 边界检查只需读取一个影子字节（$O(1)$）

### 矢量时钟（ThreadSanitizer）

每个线程 $T_i$ 持有逻辑时钟 $VC_i$，初始化为全零。线程间同步时，时钟更新规则：

$$VC_i = \max(VC_i, VC_j) \quad \text{（收到线程 } T_j \text{ 的消息）}$$

每次线程 $T_i$ 执行内存访问 $W$ 时，记录：

$$\text{record} = (\text{addr}, \text{value}, T_i, VC_i)$$

数据竞争判定：两个线程对同一地址的访问无 `happens-before` 关系（无锁、无 mutex、无原子操作），且至少一个访问是写入。

**矢量时钟的数学性质**：
- **因果性**：若 $VC_i < VC_j$，则事件 $i$ 不可能影响事件 $j$
- **反称性**：若 $VC_i \leq VC_j$ 且 $VC_j \leq VC_i$，则 $VC_i = VC_j$（不可区分事件）
- **并发性**：若 $VC_i \not\leq VC_j$ 且 $VC_j \not\leq VC_i$，则两事件并发

### 调试器的代价模型

调试器的总代价：

$$C_{debug} = C_{interrupt} + C_{snapshot} + C_{symbol\_lookup}$$

- $C_{interrupt}$：中断触发代价，受调试接口（ptrace/sejoln）制约
- $C_{snapshot}$：寄存器/内存保存代价，$O(1)$（固定寄存器数）
- $C_{symbol\_lookup}$：符号表查找代价，$O(\log n)$（DWARF 的 DIE 树）

诊断工具的代价：

$$C_{diagnostic} = C_{instrumentation} + C_{state\_maintenance}$$

- $C_{instrumentation}$：插桩检查代价，每次内存访问 $O(1)$
- $C_{state\_maintenance}$：状态维护代价（如 ASAN 影子内存、TSAN 矢量时钟）

### Valgrind VEX IR 的表达能力

Valgrind 将每条 x86 指令翻译为中间表示 VEX。VEX 是**图灵完备**的 IR：

- 支持无限寄存器（虚拟寄存器）
- 支持间接跳转（寄存器寻址）
- 支持条件执行（IR 条件码）

这意味着 Valgrind 可以模拟任何可计算的程序行为，包括自修改代码。

**断点命中时的状态恢复**：
1. trap 触发 → 保存当前寄存器快照
2. 恢复原始指令字节（0xCC 位置）
3. 将 PC 指向原始指令（而非 trap 后的下一条）
4. 用户执行 `next`/`step` 后，重新插入 0xCC

### Valgrind IR 插桩流程

<pre>
原始代码 (x86)          Valgrind 核心              IR (VEX)
   │                         │                        │
   │  mov [eax], ebx         │                        │

   │                         │───────────────────────>│  ISTore(4,Addr(eax),G(ebx))
   │                         │                        │
   │                         │  插入检查               │
   │                         │<───────────────────────│  if (!heap_addr(eax)) Die()
   │                         │                        │
   │                         │  JIT 重新生成代码       │
   │                         │<───────────────────────│
</pre>

Valgrind 将每条 x86 指令翻译为中间表示 VEX，执行检查后再生成目标代码。性能损失 10-50x，代价是**无漏报**——所有内存访问均被监控。

<pre>
线程 T1                    线程 T2                    共享内存

</pre>

happens-before 关系通过同步原语（lock/unlock）建立，矢量时钟保证因果顺序。

## 机制

### GDB 断点实现：软件断点 vs 硬件断点

**软件断点**（`break`）：
- 将目标地址的原始指令替换为 `int3`（0xCC）
- CPU 执行时触发 #DB 异常，OS 转交控制权给 GDB
- 优点：可设任意数量（仅受内存限制）
- 缺点：必须修改代码，不适合只读区域

**硬件断点**（`hbreak`）：
- 使用 DR0-DR7 调试寄存器，在 CPU 层面检测地址访问
- 优点：不修改代码，可设数据断点（写入/读取触发）
- 缺点：仅 4 个（x86），需 OS 支持

**条件断点的优化**：条件 `if` 判断在 trap 后执行，若条件不满足则立即恢复——断点仍每次命中，但 pause 代价只在条件满足时产生。对于高频代码路径，可设置计数器条件 `count > 100` 以跳过前期。

**Watchpoint 的硬件实现**：
- 数据断点通过 DR6 的 Bn 位指示触发
- DR7 的 Rw/len 字段指定监控的地址范围和访问类型
- 写入/读取触发取决于 DR7[2i+1:2i] 设置

### DWARF 符号表与行号映射

`-g` 生成的 DWARF 信息将每个机器指令地址映射回源文件+行号，并记录变量布局：

```cpp
// 源码
void foo(int x) {
    int y = x + 1;  // 行号 N
}
```

编译后 DWARF 条目：
```
DW_TAG_variable "y"
  DW_AT_location (DW_OP_breg5[RBP-0x10])  // y 在 [RBP-0x10]
  DW_AT_type (int)
```

`print y` 时，GDB 通过符号表找到 `y` 的 DWARF 描述，再通过当前栈帧的 RBP 寄存器计算实际地址 `[RBP-0x10]`。

**DWARF 行号表的数学结构**：
- 每个编译单元维护行号状态机（state machine）
- 特殊操作码（SPA/DW_LNS_extended_op）压缩状态转移
- 行号表是**单调递增**的地址序列，支持二分查找

**优化影响**：`-O2` 及以上时，变量可能被**寄存器优化**（不分配栈空间）或** SSA 形式**（常量传播、死代码消除），DWARF 信息描述的是优化后的布局，可能与源码不对应——这是调试信息的固有局限。

**clang -g vs -gdwarf-5**：
- `-gdwarf-5` 生成更紧凑的调试信息（40-50% 体积减少）
- `-gdwarf-5` 支持更好的压缩和并行加载
- 但部分旧版 GDB 不支持 DWARF-5

### Valgrind 的精确性保证

Valgrind 在**每条指令**级别重新解释程序，不依赖编译器插桩。这意味着：

1. **无漏报**：任何内存访问都被监控，包括库函数内部的
2. **无歧义**：立即报告违规，不延迟到后续检查
3. **无源码依赖**：二进制程序即可分析

代价是性能。Valgrind 维护整个进程的地址空间映射，每条内存访问都经过影子内存查找和边界检查。

**Valgrind 的局限性**：
- 无法检测**逻辑错误**（如错误的算法实现）
- 无法检测**数据竞争**（需 Helgrind/TSAN）
- 对自修改代码支持有限（JIT 场景需额外配置）

### ASAN 的内存 overhead

ASAN 的内存开销：
- **影子内存**：应用内存的 1/8（12.5%）
- **堆 redzone**：每次 `malloc` 前后各加 16-32 字节 redzone
- **栈 redzone**：每个栈帧前后加 16-32 字节（编译时插入）

总 overhead ≈ 2x 内存使用量。这是空间换时间的策略：将错误检测延迟到运行时，而非依赖静态分析。

**约束**：ASAN 无法检测**逻辑错误**（如使用错误的算法）和**数据竞争**（需 TSAN）。对于 use-after-return（而非 use-after-free），ASAN 无法检测，因为栈帧在返回时已释放。

### TSAN 的 happens-before 检测

TSAN 使用**矢量时钟**追踪 happens-before 关系。每次：
- 线程同步（原语）：互斥锁 lock/unlock、线程 join/spawn、原子操作
- 内存访问：记录 `(地址, 值, 线程ID, 时钟)`

判定数据竞争的两个必要条件：
1. **并发**：两个线程无 happens-before 关系（未通过同步原语建立）
2. **冲突**：对同一地址至少一次写入

```cpp
// 可能的竞争：两个线程同时写入同一地址
// T1: x = 1;       (write x)
// T2: x = 2;       (write x)
// 无 mutex/rlock 保护 → TSAN 报告竞争
```

**约束**：TSAN 无法检测**死锁**（需 ThreadSanitizer 的 TSan 的额外工具或 Helgrind）、**原子操作裸读/写**（需显式 `std::atomic`）和 **锁顺序反转**。

**TSAN 的 vector clock 实现**：
- 每个线程维护长度为 $n$ 的时钟向量（$n$ = 线程数）
- join 时：$VC_{parent} = \max(VC_{parent}, VC_{child})$
- lock 时：$VC_{thread} = \max(VC_{thread}, VCLock)$

### MSAN（MemorySanitizer）

MSAN 检测**未初始化内存读取**：

- 跟踪每字节的"初始化状态"
- 读取未初始化内存时报告
- 适用于检测 `memcpy` 误用、模糊测试发现的数据流错误

**与 ASAN 的区别**：
- ASAN：检测越界访问、use-after-free
- MSAN：检测未初始化读取

**约束**：MSAN 要求所有代码都编译为 MSAN 版本（包括标准库），否则会产生" Wrapper absorbs uninitialized" 误报。

### UBSAN（UndefinedBehaviorSanitizer）

UBSAN 检测**未定义行为**：

| 类型 | 示例 | 行为 |
|------|------|------|
| 算术 | 除零、整数溢出 | 报告位置 |
| 空指针 | 解引用 NULL | 报告位置 |
| 非 POD | `memcpy` 到非 POD 对象 | 报告位置 |
| 转换 | 非法转换 | 报告位置 |

**约束**：UBSAN 不修复 UB，只是报告。程序仍以未定义方式运行。

### C++23/26 调试功能

**C++23 `std::print`**：格式化输出到 stderr，简化调试打印：

```cpp
std::print("x = {}, y = {}\n", x, y);  // C++23
```

**C++26 `std::source_location` 增强**：允许获取当前调用点的文件和行信息，用于运行时报告：

```cpp
void log_error(const char* msg, std::source_location loc = std::source_location::current()) {
    std::print("[{}:{}] {}\n", loc.file_name(), loc.line(), msg);
}
```

**C++26 调试容器**（提案）：
```cpp
std::vector<int> v{1, 2, 3};
std::println("v.size() = {}", v.size());  // 编译期格式化
```

## 工具对比

| 场景 | GDB/LLDB | Valgrind | ASAN | TSan | UBSAN |
|------|---------|----------|------|------|-------|
| 内存越界 | 需断点+手动 | 自动 | 自动 | ❌ | ❌ |
| 内存泄漏 | ❌ | 精确 | ✅ (leak sanitizer) | ❌ | ❌ |
| 数据竞争 | ❌ | Helgrind 部分 | ❌ | 精确 | ❌ |
| 未定义行为 | ❌ | ❌ | ❌ | ❌ | ✅ |
| 性能开销 | 无（运行时） | 10-50x | 2-3x | 3-10x | 1.5-2x |
| 需源码 | 否 | 否 | 是（重新编译） | 是 | 是 |

**选型决策树**：

```
崩溃？
├─ 段错误 → GDB (bt) + ASAN
├─ 内存泄漏 → Valgrind / ASAN (leak)
├─ 数据竞争 → TSan
├─ 逻辑错误 → GDB (断点/条件)
└─ 未定义行为 → UBSAN
```

## 编译配置

<pre>
Debug 构建（调试信息，关优化）:
  g++ -g -O0 -Wall -fno-omit-frame-pointer -o myapp myapp.cpp
                                      ↑ 保存帧指针，栈跟踪更完整

ASAN 构建（C++23 现代写法）:
  g++ -g -fsanitize=address -fsanitize=undefined -O1 -o myapp myapp.cpp
                                                      ↑
                                               ASAN 要求 O1+ 优化

TSAN 构建（检测数据竞争）:
  g++ -g -fsanitize=thread -O1 -fno-omit-frame-pointer -o myapp myapp.cpp
                                                         ↑
                                                  TSan 需要帧指针

MSAN 构建（检测未初始化读取）:
  g++ -g -fsanitize=memory -O1 -o myapp myapp.cpp

UBSAN 构建（检测未定义行为）:
  g++ -g -fsanitize=undefined -O1 -o myapp myapp.cpp

CMake 配置（C++20）:
  add_compile_options(
      $<$<CONFIG:Debug>:-O0 -g -fno-omit-frame-pointer>
      $<$<CONFIG:ASAN>:-fsanitize=address -fsanitize=undefined -O1>
      $<$<CONFIG:TSAN>:-fsanitize=thread -O1 -fno-omit-frame-pointer>
  )
</pre>

**优化级别的影响**：
- `-O0`：完整调试信息，但性能差
- `-O1`：最小优化，调试信息基本可用
- `-O2/-O3`：性能优化，部分变量可能被优化掉
- `-Og`（GCC 4.8+）：平衡调试体验和优化

## 常见问题诊断流程

### 段错误（Segmentation Fault）

1. `gdb ./myapp` → `run` → `bt` 定位崩溃位置和调用栈
2. `g++ -fsanitize=address -g -O1 ...` 重新编译，ASAN 报告 heap-buffer-overflow
3. 若 ASAN 无果，`valgrind --leak-check=full --show-leak-kinds=all ...` 提供更详细信息

**GDB 典型分析流程**：
```
(gdb) run
Program received signal SIGSEGV, Segmentation fault.
0x00000000004006f2 in process_data (ptr=0x0) at main.cpp:42
42          result = ptr->value;
(gdb) bt
#0  process_data (ptr=0x0) at main.cpp:42
#1  0x00000000004005a3 in main (argc=1, argv=0x7fffffffe380) at main.cpp:15
(gdb) print ptr
$1 = (Data *) 0x0
```

### 内存泄漏

- **Valgrind**: `valgrind --leak-check=full --show-leak-kinds=all --track-origins=yes ./myapp`
- **ASAN**: 编译时加 `-fsanitize=leak`，退出时报告（需链接 `libasan`）
- **MSAN**: `g++ -fsanitize=memory -g ...` 检测未初始化内存读取

**Valgrind 泄漏报告解读**：
```
==12345== 24 bytes in 1 blocks are definitely lost in loss record 1 of 2
   at 0x...: operator new(unsigned long) (vg_replace_malloc.c:...)
   by 0x...: main (main.cpp:25)
```
- "definitely lost"：确定泄漏，需修复
- "probably lost"：可能是泄漏（取决于指针位置）
- "still reachable"：程序结束前未释放，但可能是正常行为

### 数据竞争

```bash
g++ -fsanitize=thread -g -O1 -fno-omit-frame-pointer myapp.cpp -o myapp
./myapp
# TSan 报告格式:
# Write of size N at 0x... by thread T1:
#   Previous write of size N at 0x... by thread T0
```

**TSan 报告解读**：
- "Previous write" 不一定是真正的冲突写入，而是 happens-before 树中最近的写入
- 需结合代码判断是否真正竞争
- 常见误报：故意无锁共享的 `volatile` 数据

### 未定义行为

```bash
g++ -fsanitize=undefined -g -O1 myapp.cpp -o myapp
./myapp
# UBSAN 报告格式:
# main.cpp:42:3: runtime error: negation of -2147483648 cannot be represented in type 'int'
```

**常见 UBSAN 检测**：
- 有符号整数溢出
- 除零
- 空指针解引用
- 不合法的位移操作

### 调试符号缺失

```
(gdb) bt
#0  0x00000000004006f2 in ?? ()
```

缺少调试符号时：
1. 检查编译是否加 `-g`
2. 检查是否 strip 过：`file myapp` / `readelf -S myapp | grep debug`
3. 检查 DWARF 版本：`readelf -w myapp | head`

## 参考存根

```bash
# GDB 基础
gdb ./myapp
break main
break myapp.cpp:42
condition 1 count > 10  # 第11次才暂停
run
bt   # backtrace
print x
next / step / continue
watch x  # 数据断点（写入触发）
delete 1

# GDB 条件断点
break myapp.cpp:100 if x > 0 && y == NULL

# GDB 多线程
info threads
thread 2
break myapp.cpp:50 thread 2

# LLDB（macOS C++20+）
lldb ./myapp
breakpoint set --name main
breakpoint set --file main.cpp --line 42
thread step-over
frame variable
watchpoint set expression -- (int*)0x1000

# Valgrind（完整检查）
valgrind --leak-check=full --show-leak-kinds=all --track-origins=yes ./myapp

# Valgrind Helgrind（数据竞争）
valgrind --tool=helgrind ./myapp

# ASAN（内存错误检测）
g++ -g -fsanitize=address -fsanitize=undefined -O1 myapp.cpp -o myapp

# TSan（数据竞争检测）
g++ -g -fsanitize=thread -O1 -fno-omit-frame-pointer myapp.cpp -o myapp

# MSAN（未初始化读取检测）
g++ -g -fsanitize=memory -O1 myapp.cpp -o myapp

# UBSAN（未定义行为检测）
g++ -g -fsanitize=undefined -O1 myapp.cpp -o myapp

# C++23 调试打印
#include <print>
std::print("debug: x={}, addr={}\n", x, static_cast<void*>(&x));

# 调试宏（C++20 source_location）
#define LOG(msg) std::print("[{}:{}] {}\n", \
    std::source_location::current().file_name(), \
    std::source_location::current().line(), msg)
```
