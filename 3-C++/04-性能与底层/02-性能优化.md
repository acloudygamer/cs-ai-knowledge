# 02-性能优化

> 前置：[01-内存模型与分配](01-内存模型与分配.md)（分配成本与缓存行）· 后续：[03-链接与ABI](03-链接与ABI.md)

> **版本基准**：C++20；C++23/26 特性行内标注。示例实测环境：GCC 14.2（MinGW-w64，Windows），`-std=c++20 -O2 -static`。

现代 CPU 的瓶颈不在算而在搬：一次 L1 命中约 4 个周期、主存约 200 个周期（典型值，x86-64 桌面平台；背景见 [0-计算机基础/硬件组成](../../0-计算机基础/01-计算机体系/01-硬件组成.md)），数量级的落差决定性能优化的大部分工作是**减少数据移动**，其次才是减少指令。本篇按工作流程展开：先测量找到账在哪，再看编译器能替你做掉哪部分，最后才是人工作业——数据布局是收益最大的一项；末尾纠两类常见误优化。

## 本质

性能优化是对硬件账本的核对，而账本只有测量能翻开。**直觉定位热点在优化里是系统性不可靠的**：花费与代码行数无关，常集中在意想不到的调用与被忽视的拷贝上。因此纪律只有一条：不测不改，改完再测。优化循环固定四步——测量定位热点 → 假设成因 → 修改 → 复测验证，缺了第一步和第四步的"优化"是装饰。

## 机制

### 测量工具链：三个层级

| 层级 | 工具 | 回答什么 |
|---|---|---|
| 微基准 | Google Benchmark（库，代码内计时循环 + 统计） | 这段函数/操作本身多快？自动处理预热、重复、方差 |
| 全程序剖析 | perf（Linux 内核计数器）、Intel VTune（采样 + 硬件 PMU） | 时间花在哪几个函数、哪几行；缓存未命中率、分支误预测率各是多少 |
| 手动计时 | `std::chrono::steady_clock` | 凑合用：必须多次重复取最优/中位，且防止被测代码被优化掉（`volatile` 接收结果或 `asm volatile("" :: "r"(x))` 屏障） |

两条测量纪律：**在优化构建下测**（`-O2`，测 `-O0` 的瓶颈是在优化一个不会发布的程序）；**看分布不看单次**（计时含调度噪声，取多次重复的最优值近似无干扰下界）。

### 编译器能替你做什么：四档机制

| 机制 | 是什么 | 边界 |
|---|---|---|
| `-O2` / `-O3` | 优化级别开关。`-O2` 启用全部"几乎不增代码体积"的优化（常量传播、死代码消除、循环变换、自动向量化等，GCC 12 起向量化在 `-O2` 默认开）；`-O3` 追加激进向量化与展开 | `-O3` 不保证更快：代码膨胀挤压指令缓存，可能反而变慢——测了再留 |
| 内联（inlining） | 把函数体展开到调用点：省掉调用/返回指令，更重要的是把被调体暴露给调用点上下文做后续优化 | 编译器自行决策，`inline` 关键字只是许可不是命令（其链接语义见 [03-链接与ABI](03-链接与ABI.md)）；定义须在头文件才可见 |
| LTO（Link-Time Optimization） | `-flto`：目标文件里存中间表示，链接期全程序可见，跨翻译单元内联与死代码消除 | 编译与链接变慢；与静态库配合需注意插件/符号可见性 |
| PGO（Profile-Guided Optimization） | 两阶段：`-fprofile-generate` 插桩构建跑真实负载收集分支/热点数据，`-fprofile-use` 按真实剖面重排基本块、校正内联决策 | 剖面必须代表真实负载，否则优化错了方向；构建流程翻倍 |

原则性的分工：指令级的事（寄存器分配、指令调度、展开）编译器比人强，把热源素地交给它；**结构性的事（算法、布局、分配策略）编译器动不了**，那才是人的工作面。

### 数据布局：AoS vs SoA

同一批逻辑对象有两种内存排法，缓存账完全不同：

- **AoS（Array of Structures）**：结构体排队成数组，`points[i].x` 自然直读。消费单个分量时，每载入一条缓存行，同行的 y、z 分量被白白搬运——缓存以行为单位搬运，不按字段（机制见 [01-内存模型与分配](01-内存模型与分配.md)）。
- **SoA（Structure of Arrays）**：同类分量各自成数组，消费 x 分量时载入的每一行 100% 是 x。代价是"一个对象"被拆散，整体读写（同时用 x、y、z）反而跨三个数组。

选择依据是访问模式：遍历只碰少数分量 → SoA；总是整对象进出 → AoS。下方示例实测单分量遍历：N 约 400 万、三分量 `Particle`，SoA 比 AoS 快 2~3 倍（GCC 14.2 `-O2`，具体比值随机器与负载波动：同一份代码在不同时刻复测曾得约 2.1 与约 3.0），带宽账的理论上限是 3:1（每行浪费 2/3 → 少 1/3 即 3 倍差距），比值落在区间内即说明瓶颈已从延迟转为带宽。配套手法是**分块（tiling）**：把工作集切到能装进某级缓存的块内逐块处理，让复用发生在片内（缓存层次的账见 [0-计算机基础/硬件组成](../../0-计算机基础/01-计算机体系/01-硬件组成.md)）。

### 常见误优化

- **手动 register 式思维**：替编译器安排寄存器、手写汇编、用 `register` 关键字（C++17 起已移除该关键字）。寄存器分配与指令调度依赖对流水线宽度的全局视图，人工局部干预多数负收益；写清楚的朴素代码，让 `-O2` 干活，才是对编译器友好。
- **过度内联**：给大函数标 `inline`/`__attribute__((always_inline))`。内联消除的是调用开销（纳秒级），付出的代价是代码体积膨胀挤压指令缓存——被内联函数越大、调用点越多，净收益越可能为负。内联决策交给编译器，或交给 PGO。
- **先优化后测量**：在没被测量的代码上动手。典型后果是优化了占总耗时 2% 的路径，还顺手引入了 bug。Amdahl 定律把账钉死：优化占比 $p$ 的部分加速 $s$ 倍，全局加速上限 $1/((1-p) + p/s)$—— $p$ 小， $s$ 再大也没用。

### 复杂度优先于常数

所有常数级优化都有一个天花板：输入规模涨上去，渐进复杂度决定结局。 $O(n^2)$ 的算法优化到常数减半，也只是在 $n$ 翻倍时把溃败推迟一步。因此优化顺序是钉死的：先确认算法复杂度已到位（账本的另一半在 [1-数据结构与算法/复杂度分析](../../1-数据结构与算法/01-复杂度与权衡/01-复杂度分析.md)），再谈常数——缓存布局、分配次数、分支形态。反过来也成立：常数优化只值得花在测量指认的热点路径上。

## 示例

（GCC 14.2 MinGW 实测，`g++ -std=c++20 -O2 -static`；绝对耗时随机器浮动，比值是结论。）

```cpp
#include <chrono>
#include <iostream>
#include <vector>

constexpr int N = 1 << 22;  // 约 400 万个粒子，工作集远超 L2

struct Particle { float x, y, z; };        // AoS：结构体排队成数组
struct Particles {                          // SoA：同类分量各自成数组
    std::vector<float> x, y, z;
};

template<class F>
double bench(F f) {  // 返回毫秒；多次取最优，抑制偶发抖动
    double best = 1e300;
    for (int rep = 0; rep < 5; ++rep) {
        auto t0 = std::chrono::steady_clock::now();
        volatile float sink = f();         // volatile：防整个循环被优化掉
        (void)sink;
        auto t1 = std::chrono::steady_clock::now();
        double ms = std::chrono::duration<double, std::milli>(t1 - t0).count();
        if (ms < best) best = ms;
    }
    return best;
}

int main() {
    std::vector<Particle> aos(N);
    for (auto& p : aos) { p.x = 1.0f; p.y = 2.0f; p.z = 3.0f; }
    Particles soa;
    soa.x.assign(N, 1.0f); soa.y.assign(N, 2.0f); soa.z.assign(N, 3.0f);

    // 只消费 x 分量：AoS 每载入一行浪费 2/3 带宽，SoA 全部用上
    // 4 个累加器打断 FP 加法依赖链，让循环变成带宽受限而非延迟受限
    double t_aos = bench([&]{
        float s0=0, s1=0, s2=0, s3=0;
        for (int i = 0; i + 4 <= N; i += 4) {
            s0 += aos[i].x; s1 += aos[i+1].x; s2 += aos[i+2].x; s3 += aos[i+3].x;
        }
        return s0+s1+s2+s3;
    });
    double t_soa = bench([&]{
        float s0=0, s1=0, s2=0, s3=0;
        for (int i = 0; i + 4 <= N; i += 4) {
            s0 += soa.x[i]; s1 += soa.x[i+1]; s2 += soa.x[i+2]; s3 += soa.x[i+3];
        }
        return s0+s1+s2+s3;
    });
    std::cout << "AoS(sum x): " << t_aos << " ms\n";   // 实测 2.5~3.8 ms（随机器浮动）
    std::cout << "SoA(sum x): " << t_soa << " ms\n";   // 实测约 1.2~1.3 ms
    std::cout << "ratio: " << t_aos / t_soa << '\n';   // 实测 2~3 倍，随机器波动
}
```
