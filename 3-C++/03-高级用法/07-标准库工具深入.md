# 标准库工具深入

> **版本关系**：C++17（string_view、optional）→ C++20（span、format）→ C++23（expected）→ C++26

**非拥有型视图（string_view、span）消除拷贝，std::format 替代 printf，std::expected 替代异常。**

## 定义

| 工具 | 一句话断言 |
|------|-----------|
| string_view | 字符串的轻量非拥有型视图 |
| span | 连续序列的轻量非拥有型视图 |
| format | 类型安全的字符串格式化 |
| expected | 函数式错误处理（替代异常或错误码） |

## 数据流

<pre>
string_view              span                 format
   │                      │                    │
   ├─ const char*        ├─ T* + size        ├─ "Hello {}"
   │                      │                    │
   ├─ std::string        ├─ vector           ├─ args...
   │                      │                    │
   ├─ 切片（无拷贝）      ├─ 数组切片          └─ 输出字符串
   │                      │
   └─ 不拥有数据          └─ 不拥有数据
</pre>

## 机制

**为什么 string_view 高效**：传统 `const std::string&` 在传入 `const char*` 时需构造 string（拷贝）。string_view 只存储指针+长度，不拷贝数据。注意：view 所指数据必须保持有效。

**为什么 span 统一数组类型**：函数参数用 `T* + size_t` 无法接受 `vector<T>`，用 `vector<T>&` 无法接受原始数组。span 统一这两种表示，且编译时确定是否静态大小。

**std::format 优势**：printf 类型不安全（`%s` 可匹配int），format 在编译时检查格式字符串类型是否匹配。Python f-string 风格更直观。

**expected 为什么是错误处理的最优解**：异常有隐藏的性能成本（即使不抛出也要初始化栈展开机制）。错误码容易被忽略。expected 强制检查，链式操作（`.and_then()`、`.transform()`）让错误路径优雅。

## 参考存根

```cpp
void process(std::string_view sv) {}
void process(std::span<int> s) {}

std::format("{} + {} = {}", 1, 2, 3);

std::expected<int, std::string> parse(int x);
auto r = parse(42).transform([](int v) { return v * 2; });
```
