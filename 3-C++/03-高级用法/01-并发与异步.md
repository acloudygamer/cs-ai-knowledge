# 并发与异步

> **版本关系**：C++20（基础）→ C++23 → C++26（std::execution）

## 定义

**并发（Concurrency）是多个执行流同时存在，异步（Asynchrony）是调用与完成之间的解耦。** 并发是结构属性（程序结构可同时执行），异步是通信属性（调用立即返回，结果稍后获取）。

从硬件视角：并发是多个执行单元同时活跃（可能物理并行或时分复用），异步是发起操作与等待结果之间的非阻塞关系。

## 数学模型

### 内存顺序的偏序语义

C++20 的内存模型建立于 **sequenced-before**（单线程偏序）和 **happens-before**（多线程协调序）之上。对每个内存位置 $M$，**修改顺序**（modification order） $\xrightarrow{M}$ 是该位置上所有原子操作的全序： ，**修改顺序**（modification order） $\xrightarrow{M}$ 是该位置上所有原子操作的全序： 是该位置上所有原子操作的全序：

 $hbo(x \xrightarrow{M} y) \iff \text{happens-before}(x, y) \lor \text{same}(x, y)$ 

**顺序一致性（seq_cst）** 要求所有线程观察到相同的全局修改顺序：
 $\forall T_i, T_j:$ `seq_cst_ops` $\text{ 在所有线程中顺序一致}$ 

**获取-释放（acquire-release）** 的核心不变量：
 $\text{release}(x) \xrightarrow{M} \text{acquire}(x) \implies$ `writer's_memory_effects` $\prec$ `reader_starts_execution`

## 机制

### 内存顺序的物理对应

**seq_cst（顺序一致性）**：相当于所有线程在单一全局总线上观察所有写操作。每次读写直接与内存控制器交互，无 CPU 缓存优化。性能代价最高，但推理最简单——所有线程看到完全相同的内存操作序列。

**acquire-release 的物理意义**：
- **release** 刷新该 CPU 的 store buffer 和无效化队列，强制所有先前的写操作对其他 CPU 可见
- **acquire** 刷新该 CPU 的 load buffer，确保后续读操作能看到 release 之前的写入

在 MESI 缓存一致性协议中：release 触发 **flush**（将修改行写回内存并广播 invalidation），acquire 触发 **invalidate acknowledgment**（确认其他 CPU 的无效化已完成）。

**relaxed 的本质**：仅保证原子性（无 torn read/write），不提供任何跨线程可见性保证。两个 relaxed 操作在任意线程中可能观察到不同顺序。

### 虚假唤醒的根源

条件变量的 `wait` 语义基于 **spurious wakeup**：Linux 的 `pthread_cond_wait` 实现中，等待队列上的线程可能因系统调度、信号处理或底层实现细节被唤醒，而无需 `notify_*` 调用。这不是 bug，是 POSIX 的规范允许行为。

因此 `wait` 必须配合谓词循环：
```cpp
while (!pred()) { cv.wait(lock); }  // 虚假唤醒后重新检查谓词
```

**违反约束**：若 `wait` 不带谓词，虚假唤醒会导致逻辑错误（如双重消费资源）。

### std::atomic_wait/notify 的锁粒度优势

相比 mutex 的内核调度，`atomic::wait` 使用 **用户态 polling**：
- `wait(old)` 将线程放入该地址的等待集合，内核态无干预
- `notify_one` 使用 Linux `futex` 的 **wait/wake** 机制，唤醒时仅在用户态切换
- 减少了 syscall 开销（context switch 到内核），适合高频场景（如无锁队列的 CAS 失败重试）

### 死锁避免的数学原理

四个必要条件（Coffman 条件）必须同时满足才可能死锁：
1. **互斥**：资源一次只能被一个线程持有
2. **持有并等待**：线程持有资源同时等待其他资源
3. **不可抢占**：资源不能被强制夺走
4. **循环等待**：存在线程-资源环

**破坏任一条件**即可避免死锁：
- 固定锁顺序：破坏循环等待（将偏序强加于全序）
- `std::lock`（死锁避免算法）：按全局顺序同时获取多个锁
- `scoped_lock`（C++17）：RAII 封装一次性获取

## std::execution（C++26）形式语义

std::execution 基于 **sender-receiver** 模型，将异步操作表示为数据流管道：

 $P ::=\ \text{sender} \mid P\ |\ \text{transform} \mid P\ |\ \text{then}(f)$ 

Sender 描述**计算的所有权转移图**，Receiver 描述**结果如何被消费**。管道操作符 `|` 是**函数组合**的形式化：

 $(S_1\ |\ f)(r) \equiv S_1(r \circ f)$ 

```cpp
auto r = std::execution::just(1)              // sender: 产生值 1
        | std::execution::then([](int x) {    // sender: 变换
            return x * 2;
        })
        | std::execution::let_value([](int x) { // sender: 依赖变换
            return std::execution::just(x + 1);
        });
```

**设计目标**：统一所有异步抽象（future、promise、coroutine）的接口，允许静态分析器在编译时验证异步数据流的完整性。

# 协程深入

> **版本关系**：C++20（基础）→ C++26（std::generator）

**协程是函数可以在挂起点暂停并在后续恢复执行的抽象，适合异步 I/O 和流式处理。其本质是编译器在编译期生成状态机，将控制流从"调用-返回"改造为"挂起-恢复"。**

## 定义

| 概念 | 本质操作 | 约束边界 |
|------|----------|----------|
| coroutine_handle | 对协程帧的指针句柄，控制生命周期 | 必须显式 destroy() 或让 promise 调用它 |
| promise_type | 协程行为的描述器，定义初始/最终挂起点、返回值、异常处理 | 必须有 get_return_object、initial_suspend、final_suspend |
| co_await | 在等待点挂起协程，让出控制权 | awaitable 必须满足 awaitable 概念 |
| co_return | 从协程返回值（隐式调用 promise.return_value） | 不能与 co_yield 混用 |
| std::generator | C++26 标准生成器，推迟产生值的惰性序列 | 必须有 forward declaration，C++26 仅 MSVC 支持 |

协程的本质是 **状态机编译**：编译器将协程函数编译为包含状态变量（local variables、resume position）的闭包类，co_await/co_yield 成为状态跳转指令。

## 数学模型

### 协程状态机的形式化

协程执行可以建模为 **有限状态自动机（FSA）**：

$$
M = (Q, \Sigma, \delta, q_0, F)
$$

- $Q = \{q_{\text{created}}, q_{\text{running}}, q_{\text{suspended}}, q_{\text{completed}}\}$：协程生命周期状态 ：协程生命周期状态
- $\Sigma = \{\text{resume}, \text{destroy}, \text{await}, \text{return}\}$：输入事件 ：输入事件
- $\delta$：状态转移函数 ：状态转移函数
- $q_0 = q_{\text{created}}$：初始状态 ：初始状态
- $F = \{q_{\text{completed}}\}$：接受状态 ：接受状态

每个 co_await 点是状态机的一个 **resume position**，用整数标签表示。编译器将协程体展开为：

```cpp
switch (resume_position) {
    case 0: /* 初始 */; co_await awaitable; /* resume position 1 */;
    case 1: /* ... */;
}
```

### 协程帧的内存布局

协程帧（coroutine frame）在堆上分配，包含：

$$
\text{frame} = \{\text{promise}, \text locals, \text{handle}, \text{awaiter-storage}\}
$$

**关键不等式**：协程局部变量越多，帧越大；**帧过大会破坏 cache 局部性**，使协程性能优势丧失。

帧大小上界分析：
- 局部变量总大小 $S_{\text{locals}}$ 
- promise 对象大小 $S_{\text{promise}}$ （由用户定义） （由用户定义）
- awaiter 存储 $S_{\text{awaiter}}$ （通常为指针大小） （通常为指针大小）
- handle 指针 $S_{\text{handle}}$ （通常 8 或 16 字节） （通常 8 或 16 字节）

$$
|\text{frame}| = S_{\text{locals}} + S_{\text{promise}} + S_{\text{awaiter}} + S_{\text{handle}} + \text{对齐填充}
$$

**cache 行冲突**：若帧大小接近或超过 L1 cache 大小（通常 32KB），协程恢复时的 cache miss 率显著上升，恢复延迟从 ~10ns 退化到 ~100ns。

### std::generator 的惰性求值语义

generator<T> 本质上是 **惰性列表**（Lazy List），满足：

$$
G_T \cong \text{Nothing} \mid \text{Just}(T \times G_T)
$$

即：generator 要么为空，要么产出一个 T 后跟另一个 generator。每次 `co_yield` 创建一个 Just 分支，暂停后返回，调用者用 `.begin()` 恢复。

**惰性求值的不动点语义**：

令 $Y$ 为组合子， $f$ 为生成器函数： 为组合子， $f$ 为生成器函数： 为生成器函数：

$$
\text{generator} = Y(\lambda g. \lambda. \text{Just}(v, g()))
$$

这保证了无限序列可以在有限内存中表示（每步只保留当前值和续体）。

## 机制

### 为什么 co_await 要区分三个阶段

`awaitable.await_ready()` 返回 `true` 时跳过挂起，等价于"操作已就绪，无需等待"。这避免了不必要的上下文切换。

`awaitable.await_suspend(handle)` 接收协程句柄，允许：
- 返回 `void`：继续挂起，控制权返回调用者
- 返回 `true`：继续执行（不挂起）
- 返回 `false`：继续执行（不挂起）
- 返回另一个 `coroutine_handle`：切换到另一个协程（实现 `when_all` 之类的调度器）

`awaitable.await_resume()` 在恢复后执行，其返回值就是 `co_await expr` 的值。

**三阶段设计的本质**：这是 **拉取式（pull-based）** 协作调度的基础。调用者通过 `resume()` 拉取协程执行，协程通过 `await_suspend()` 决定何时让出控制权。

### promise_type 四个关键点的设计理由

1. **get_return_object()**：协程创建后立即返回给调用者，但此时协程可能还没开始执行（依赖 initial_suspend）。调用者持有一个 handle，可以通过 handle 控制协程。

2. **initial_suspend()**：`suspend_always` 是默认值——协程体在创建后立即挂起，调用者先拿到 handle，再决定何时 resume。这避免了"协程执行完毕但 handle 还没返回"的竞态。

3. **return_value(v) / return_void()**：协程的返回值通过 promise 传递，而非通过寄存器直接返回。这是因为协程可能多次挂起，普通的返回值传递机制不适用。

4. **final_suspend()**：`suspend_always` 让调用者先处理返回值（如果有），再销毁协程帧。如果返回 `suspend_never`，协程帧在协程结束时立即销毁，调用者无法再访问 promise。

### 协程帧分配策略

**每个协程在堆上分配协程帧**。对于高频调用的轻量协程（如每帧执行几百次），堆分配开销可能超过异步本身带来的好处。

优化手段：
- **suspend_never**：协程创建后不挂起，不分配帧（内联执行）
- **分配器自定义**：使用内存池而非默认堆分配器
- **栈分配**（实验性）：将帧分配在调用者栈上

**分配器自定义的数学约束**：

$$

$$

### 违反约束的后果

| 违反场景 | 系统行为 | 后果严重程度 |
|----------|----------|--------------|
| 在 `noexcept` 移动构造函数中 `co_await` | 挂起点抛出异常 | `std::terminate` 被调用，进程终止 |
| 在 `co_await` 前 lock_guard，进入 `await_suspend` 后释放锁 | 死锁风险 | 协程永久挂起，线程阻塞 |
| 未调用 `handle.destroy()` | 内存泄漏 | 协程帧永远不会被释放 |
| 在 `final_suspend()` 返回 `suspend_never` 后访问 promise | 悬垂访问 | 未定义行为，可能崩溃 |

| 在多线程环境中不正确同步访问共享状态 | 数据竞争 | 未定义行为，可能崩溃或数据损坏 |

### C++26 std::generator 的语义

> **latest 预览**：本节使用 C++26 特性（`std::generator`），stable（C++20）需手写 `promise_type`（见下方"参考存根"中的 `Task` 示例，或将 generator 改写为迭代器/回调）。

`std::generator<T>` 是惰性序列，迭代器是 `std::coroutine_handle`：

```cpp
std::generator<int> g = []() -> std::generator<int> {
    for (int i = 0; i < 3; ++i)
        co_yield i;  // 暂停，返回值，恢复后继续
}();

for (int val : g)  // 每次循环恢复一次协程
    std::cout << val << '\n';
```

**约束**：generator 必须有前向声明，`co_yield` 隐式调用 `promise.yield_value()`。

**generator 的续体（Continuation）结构**：

每个 `co_yield` 点保存一个续体指针，指向恢复后应执行的代码位置。这形成了一个链表结构：

$$
\text{resume-chain}: p_0 \rightarrow p_1 \rightarrow p_2 \rightarrow \dots \rightarrow \text{terminator}
$$

## 参考存根

```cpp
#include <coroutine>
#include <iostream>
#include <generator>

// 手写 Task（用于异步）
struct Task {
    struct promise_type {
        Task get_return_object() {
            return Task{std::coroutine_handle<promise_type>::from_promise(*this)};
        }
        std::suspend_always initial_suspend() { return {}; }
        std::suspend_always final_suspend() noexcept { return {}; }
        void return_value(int v) { value_ = v; }
        int value_;
    };
    std::coroutine_handle<promise_type> h_;
    int get() { h_.resume(); return h_.promise().value_; }
};

Task compute() { co_return 42; }

// C++26 std::generator：stable（C++20）需手写 generator 的 promise_type
// （yield_value + suspend_always + 迭代器 begin/end），或改用回调/迭代器模式。
std::generator<int> integers(int start) {
    for (int i = start;; ++i)
        co_yield i;  // 惰性无限序列
}
```

## 编译器支持

| 组件 | 头文件 | GCC | Clang | MSVC |
|------|--------|-----|-------|------|
| std::coroutine_handle | `<coroutine>` | 10+ | 5+ | 16+ |
| std::suspend_always | `<coroutine>` | 10+ | 5+ | 16+ |
| std::generator | `<generator>` | 不支持 | 17+ | 19+ |

---

> **洞察**：协程可归约为 **编译器生成的状态机**（FSA），挂起点是状态转移，边触发是 awaitable 的三个方法。协程帧是堆分配的闭包，handle 是这个闭包的引用。
