# 01-测试与调试

> 前置：[02-构建系统与包管理](../00-概览/02-构建系统与包管理.md)（FetchContent/CTest）、[06-工具组件](../02-标准库/06-工具组件.md)（`std::function`）、[04-类与资源管理](../01-语言核心/04-类与资源管理.md)（智能指针） · 后续：[06-设计模式](../06-设计模式/README.md)

> **版本基准**：C++20；C++23/26 特性行内标注。实测环境：GCC 14.2（MinGW-w64，Windows）+ doctest 2.4.11；Sanitizer 相关实测在 Linux/macOS 工具链完成，MinGW 限制见下文标注。

本篇回答一个问题：一段 C++ 代码的正确性如何被机械地验证。分两层——**测试**（写好输入、断言输出，事前验证）与**调试/诊断**（程序跑出问题后，控制执行、观测状态，事后定位）。C++ 的特殊性在于：没有运行时反射（运行时自省类型信息的能力），也没有托管运行时的安全网，于是测试替身靠编译期机制注入，内存/并发错误要靠编译期插桩工具在运行时捕获。

## 测试框架：三代选型

| 维度 | GoogleTest（2008 起） | Catch/Catch2（2010 起） | doctest（2016 起） |
|---|---|---|---|
| 形态 | 库（需编译，CMake `FetchContent` 引入） | 库（v3 起需编译） | 单头文件，源码里 `#include` 即用 |
| 断言风格 | `EXPECT_EQ` / `ASSERT_EQ` | `CHECK` / `REQUIRE`（BDD 风格：`TEST_CASE`+`SECTION`） | `CHECK` / `REQUIRE` + `SUBCASE` |
| 参数化 | `TEST_P` + `INSTANTIATE_TEST_SUITE_P` | `GENERATE` 生成器 | 子用例组合 |
| 生态 | 最全：GoogleMock、死亡测试、XML 报告、IDE 集成 | BDD 语法可读性最好 | 编译开销最小（官方口径：比 Catch2 快一个数量级） |

选型判据：大型项目要 mock、死亡测试、CI 报告 → GoogleTest；偏好自然语言描述测试意图 → Catch2；只想最低成本给每个库加测试 → doctest（单头文件意味着把它扔进源码树就完成了集成，本篇实测示例用 doctest）。

### 断言的两级：记录继续 vs 短路终止

`EXPECT_*`/`CHECK` 失败后记录错误、继续执行；`ASSERT_*`/`REQUIRE` 失败后立即终止当前测试函数。分野的约束是**状态有效性**：断言失败之后程序状态已不可信，继续执行只会产生误导性结果（如对空指针解引用）时用短路级；各检查点相互独立、想看全所有失败时用记录级。`ASSERT_*` 短路的是当前函数而非整个进程，`TearDown()` 仍会被调用——清理职责由栈展开担保，这正是 RAII 在测试框架里的落点（机制见 [04-类与资源管理](../01-语言核心/04-类与资源管理.md)）。

### 参数化测试：一份逻辑 × N 组数据

边界值驱动的缺陷（空、最大、越界一格）要求同一套逻辑跑多组输入。GoogleTest 的值参数化把"测试逻辑"与"测试数据"解耦——`TEST_P` 写逻辑、`INSTANTIATE_TEST_SUITE_P` 喂数据，`GetParam()` 取当前组：

```cpp
// GoogleTest 骨架（本机未安装 GoogleTest，未实测；Linux/macOS 标准用法）
class AddTest : public testing::TestWithParam<std::tuple<int, int, int>> {};
TEST_P(AddTest, Values) {
    auto [a, b, expected] = GetParam();
    EXPECT_EQ(add(a, b), expected);
}
INSTANTIATE_TEST_SUITE_P(Boundary, AddTest,
    testing::Values(std::make_tuple(1, 2, 3), std::make_tuple(INT_MAX, 0, INT_MAX)));
```

参数空间的约束： $n$ 维参数每维 $m$ 个取值的全组合是 $m^n$，三维各取五值已 125 组。实践上用等价类划分（每类取一个代表值：正常、边界、非法各一）把规模压到线性。

## 测试替身与可注入设计

被测单元（如缓存）依赖外部环境（时钟、网络、磁盘）时，测试必须替换这些依赖，否则结果不可复现。Java/C# 靠反射在运行时替换实现；C++ 没有反射，替换点必须在编译期预留，两条路：

- **运行时多态注入**：依赖抽象基类，构造函数传 `Base&`，生产传真实实现、测试传 mock。代价：一次虚表间接跳转，对象必须按引用/指针持有。
- **模板参数注入**（编译期）：依赖作为模板参数，`Cache<SystemClock>` 是生产版、`Cache<FakeClock>` 是测试版。代价为零（静态绑定、可内联），约束是生产与测试是**两个不同类型**——不能在运行期互换。

GoogleMock 属于第一条路的机械化：`MOCK_METHOD` 生成实现了接口的替身，`EXPECT_CALL` 声明"应当被以参数 X 调用一次"。mock 的边界是被测单元的直接依赖——mock 依赖的依赖，测试就变成了集成测试的假扮者。

## Sanitizer 三件套：编译期插桩的运行时检查

Sanitizer 是编译器在生成代码时插入检查指令、运行时配套库捕获违规的工具族（GCC/Clang 内建，`-fsanitize=...` 启用）：

| 工具 | 启用 | 查什么 | 机制 | 开销（典型值） |
|---|---|---|---|---|
| ASan | `-fsanitize=address` | 堆/栈越界、use-after-free、泄漏 | 每 8 字节应用内存映射 1 字节"影子内存"记录可访问性，访问前查影子 | ~2x 内存、~2x 时间 |
| UBSan | `-fsanitize=undefined` | 有符号溢出、除零、空指针解引用、非法位移 | 在运算点插入条件检查 | ~1.5x 时间 |
| TSan | `-fsanitize=thread` | 数据竞争（两线程无同步地访问同一地址且至少一个写） | 矢量时钟追踪 happens-before 关系 | 3-10x 时间 |

三者互补不重叠：ASan 管"访问了不该访问的内存"，UBSan 管"做了标准未定义的操作"，TSan 管"访问顺序没有同步约束"。**平台锚点**：MinGW-w64 的 GCC 14.2 不含 libsanitizer（`g++ -fsanitize=address` 在链接期报缺 libasan，本机实测为 `cannot find -lasan`，报错文本随发行版而异），三件套在 Linux（GCC/Clang）与 macOS（Clang）可用；Windows 原生替代是 MSVC 的 `/fsanitize=address`（VS 2019 16.9 起，仅 ASan）。旧文所列 MSan（未初始化读取）仅 Clang 支持且要求全程序重编译，工程门槛最高。

## 静态分析与覆盖率：不运行的检查与没跑到的代码

Sanitizer 与调试器都要求程序先跑起来；还有两类工具在运行之外补位。

- **静态分析**：不执行程序，直接在源码/AST 上匹配缺陷模式。Clang 系的 **clang-tidy** 是主流前端：几百个检查器（未初始化变量、悬垂引用、`const` 机会、现代化改写建议），按 `readability-*`/`bugprone-*` 等族开关，接入 CMake 只需 `-DCMAKE_CXX_CLANG_TIDY=clang-tidy`。编译器内建一路：GCC 的 `-fanalyzer`（GCC 10 起，双释放/泄漏的路径敏感分析）与 MSVC 的 `/analyze`。与 Sanitizer 的分工：静态分析查"代码里写得出的模式"，零运行成本但只能报模式命中的嫌疑（有误报）；Sanitizer 查"这次执行真的发生了"，无误报但只覆盖跑到的路径。
- **覆盖率**：回答测试的反面问题——哪些代码从没被测试执行到。GCC 的 `--coverage`（gcov 数据）与 Clang 的 `-fprofile-instr-generate -fcoverage-mapping`（llvm-cov 出报告）都按行/分支统计执行次数；CI 里把覆盖率挂上门禁，防的是"测试全绿但关键路径没人测"。边界要说清：覆盖率度量的是**执行**不是**断言**——被执行过且没断言过的代码等于没测，100% 行覆盖不证明正确性，它是查漏工具不是质量证明。

## 调试器工作流：暂停—检查—恢复

GDB 的循环是三步：打断点（`break`）暂停进程 → 检查状态（`bt` 调用栈、`print` 变量、`info locals`）→ 恢复执行（`next` 逐行/`step` 进函数/`continue`）。实现机制两级：**软件断点**把目标地址的首字节替换为 `int3`（0xCC）陷入指令，数量不限但要改写代码段；**硬件断点**用 CPU 调试寄存器（x86 的 DR0–DR3，仅 4 个），不改代码，因此能监控只读内存，也是**观察点**（`watch x`，变量被写时暂停）的载体。

**反向调试**（GDB 7.0 起的 `record` + `reverse-step`/`reverse-continue`）：调试器记录每条指令的副作用，允许向过去执行。它回应的约束是缺陷定位的方向性——崩溃点是结果不是原因，正向重跑要碰运气重现，反向执行直接从错误状态回溯到首次偏离点。代价是记录开销大，只对短窗口实用。

调试信息来自 `-g` 生成的 DWARF 数据（机器地址 ↔ 源码行号、变量的栈/寄存器位置）。`-O2` 会把变量优化进寄存器或消除，DWARF 描述的是优化后的布局，`print` 出 `<optimized out>` 是常态——调试构建用 `-O0` 或 `-Og`（GCC 4.8 起，保调试体验的最小优化）。

## 连接

测试进 CI 的链路在构建篇已经铺好：CMake `enable_testing()` + `gtest_discover_tests()` 把测试二进制注册进 CTest，CI 里一条 `ctest` 收口（见 [02-构建系统与包管理](../00-概览/02-构建系统与包管理.md)）。Sanitizer 构建作为独立的 CMake 配置（`-DCMAKE_CXX_FLAGS=-fsanitize=address`）与正常构建并行跑，互不污染。

**质量闭环**：测试套件是重构的前提（[06-设计模式](../06-设计模式/README.md) 的"重构驱动"依赖它）；诊断工具是测试的补充——测试验证"给定输入输出正确"，Sanitizer 验证"执行过程没有越界/UB/竞争"，两者查的是不同性质的错误。

## 示例

doctest 参数化与模板注入（GCC 14.2 MinGW + doctest 2.4.11 实测编译运行，`g++ -std=c++20 -static`）：

```cpp
#define DOCTEST_CONFIG_IMPLEMENT_WITH_MAIN
#include "doctest.h"

// 模板参数注入：时钟是模板参数，测试注入可控的假时钟
template <typename Clock>
class Cache {
    Clock& clock_;
    int ttl_{60}, written_at_{-1};
public:
    explicit Cache(Clock& c) : clock_(c) {}
    void put()         { written_at_ = clock_.now(); }
    bool fresh() const { return written_at_ >= 0 && clock_.now() - written_at_ <= ttl_; }
};

struct FakeClock { int t = 0; int now() const { return t; } };

TEST_CASE("cache freshness") {
    FakeClock fc;
    Cache<FakeClock> c(fc);
    SUBCASE("fresh right after put") {          // 等价类：边界内
        c.put();
        CHECK(c.fresh());
    }
    SUBCASE("stale after ttl") {                // 等价类：边界外
        c.put();
        fc.t = 100;
        CHECK_FALSE(c.fresh());
    }
}
```

运行输出：

```text
[doctest] test cases: 1 | 1 passed | 0 failed | 0 skipped
[doctest] assertions: 2 | 2 passed | 0 failed |
[doctest] Status: SUCCESS!
```
