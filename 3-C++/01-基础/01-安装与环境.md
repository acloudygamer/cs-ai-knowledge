# 安装与环境

## 定义

**编译器是将高级语言源码映射为机器指令的翻译器，其本质是一个**有限状态机驱动的代码变换管道**，通过词法分析、语法分析、语义分析、优化和代码生成五个阶段，将符合语言规范的源码转换为目标文件。** 这个翻译过程不是一次性的字符串替换，而是**基于语言规范的语义保留变换**——源码和目标代码在语义上等价，尽管表现形态完全不同。

## 数学模型

### 编译阶段的复杂度

编译器的五个阶段具有不同的计算复杂度：

| 阶段 | 复杂度 | 备注 |
|------|--------|------|
| 词法分析 | $O(n)$ | 线性扫描源码，$n$ 为字符数 |
| 语法分析 | $O(n)$ 或 $O(n^3)$ | LL/LALR 为 $O(n)$，一般解析可达 $O(n^3)$ |
| 语义分析 | $O(n \cdot d)$ | $d$ 为最大嵌套深度 |
| 优化 | $O(n \cdot P)$ | $P$ 为 Pass 数量，可并行化 |
| 代码生成 | $O(n)$ | 寄存器分配是 NP 完全问题，通常用启发式 |

**词法分析的本质是有限状态自动机（NFA/DFA）**：
$$L = \{\langle Q, \Sigma, \delta, q_0, F \rangle\}$$
其中 $Q$ 是状态集，$\Sigma$ 是字符集，$\delta: Q \times \Sigma \rightarrow Q$ 是转移函数，$q_0$ 是初始状态，$F$ 是接受状态集。每个正则表达式对应一个 DFA，DFA 的状态数在最坏情况下与模式长度指数相关。

**语法分析的数学本质是上下文无关文法（CFG）的推导**：
$$S \Rightarrow^* \alpha$$
自顶向下解析从起始符 $S$ 推导输入串 $\alpha$；自底向上解析将输入串规约到 $S$。两者的冲突（如 shift-reduce、reduce-reduce）源于文法本身的歧义性或 LR(k) 的 $k$ 步前瞻不足。

**语义分析的约束传播**：
$$\Gamma \vdash e : \tau$$
在类型环境 $\Gamma$（符号表）下，表达式 $e$ 的类型为 $\tau$。类型检查是**可组合的**：复合表达式的类型由其子表达式的类型和操作符的语义规则决定。

**LLVM 的模块化设计**：将优化和代码生成组织为可插拔的 Pass 架构，使得 $T_{\text{总}} = T_{\text{前}} + \sum_{i=1}^{P} T_{\text{Pass}_i} + T_{\text{后}}$，可并行执行独立 Pass。

### 目标文件格式

| 格式 | 平台 | 结构 |
|------|------|------|
| ELF | Linux, Unix | .text/.data/.bss + 符号表 + 重定位表 |
| PE-COFF | Windows | .text/.data/.rdata + 导出/导入表 |
| Mach-O | macOS | .text/.data + dyld 信息 |

**ELF 的数学结构**：
$$\text{ELF} = \langle \text{Header}, \{\text{Section}_i\}, \text{StringTable}, \text{SymbolTable} \rangle$$
每个 Section 包含连续字节流；SymbolTable 将符号名映射到地址；重定位表记录需在链接时修正的位置。

### 链接器的符号解析模型

链接的本质是**名字到地址的绑定函数**：

$$B : \text{Symbol} \rightarrow \text{Address}$$

**链接错误的数学描述**：
$$\text{未定义符号} \осуществляет \text{外部引用} \Rightarrow \text{链接错误}$$
$$\text{重复定义} \Rightarrow \text{链接错误}$$

**两遍式链接的数学性质**：
1. 第一遍：建立全局符号表 $\Sigma = \{ (name, addr, strong/weak) \}$
2. 第二遍：重定位所有引用 $\rho: ref \rightarrow addr$

**强符号 vs 弱符号的数学规则**：
$$\text{强符号} \oplus \text{强符号} \implies \text{链接错误（重复定义）}$$
$$\text{强符号} \oplus \text{弱符号} \implies \text{选用强符号}$$
$$\text{弱符号} \oplus \text{弱符号} \implies \text{实现选择未定义}$$

**链接的数学约束**：
- **唯一性约束**：$\forall name : |\text{definitions}(name) \cap \text{strong}| \leq 1$
- **覆盖约束**：弱符号可被覆盖，但不能覆盖强符号

## 数据流

<pre>
源代码 (.cpp)
    │
    ▼ 词法分析 (Lexer) ─── 有限状态自动机
Token 流: [关键字][标识符][字面量][运算符][界符]
    │
    ▼ 语法分析 (Parser) ─── LL/LALR 解析器
AST（抽象语法树）: 节点 = {type, children, semantic_info}
    │
    ├──► 模板实例化 ─── 编译期求值
    │       │
    │       └──► 实例化点 (IP) 生成：T<int> → std::vector<int, std::allocator<int>>
    ├──► 宏展开 ─── 文本替换
    │       │
    │       └──► 预处理 token 流替换，不做语义检查
    │
    ▼ 语义分析 (Sema)
带类型标注的 AST + 符号表
符号表: Map<Name, {Type, Scope, Address}>
    │
    ▼ 优化 (Optimizer) ─── SSA 形式
┌─────────────────────────────────────┐
│ Pass 1: 常量折叠  (CSE, algebraic simplify) │
│ Pass 2: 内联      (函数调用 → 函数体)   │
│ Pass 3: 死代码消除 (DCE)               │
│ Pass N: ...                           │
│ 目标：将程序变换为等价但更高效的形式    │
└─────────────────────────────────────┘
    │
    ▼ 代码生成 (CodeGen)
目标代码 (.o / .obj)
┌─────────────────────────────────────┐
│ 机器指令序列（与源程序语义等价）       │
│ 符号表（导出/导入）                   │
│ 重定位信息（链接时填充）              │
└─────────────────────────────────────┘
    │
    ▼ 链接 (Linker)
┌─────────────────────────────────────┐
│ 符号解析：未定义 ↔ 定义               │
│ 重定位：相对地址 → 绝对地址           │
│ 库搜索：-l 指定库的路径解析           │
│ 输出：可执行文件 / 共享库            │
└─────────────────────────────────────┘
</pre>

**数据所有权变换**：
1. 源码 → Token流：所有权从文本转移给词法分析器
2. Token流 → AST：结构化重组，语义信息逐步丰富
3. AST → 带类型AST：类型环境逐步构建，符号表增长
4. 带类型AST → SSA IR：控制流图化，单赋值形式
5. SSA IR → 目标代码：寄存器分配 + 指令选择
6. 目标代码 → 可执行文件：符号地址绑定 + 重定位修复

## 三大编译器对比

| 编译器 | 输出格式 | 平台特性 | 设计取舍 |
|--------|---------|---------|---------|
| g++ (GNU) | ELF / PE-COFF | 广泛兼容 | 优化保守，兼容优先；GCC 是自由软件 |
| clang (LLVM) | Mach-O / ELF / PE-COFF | 错误信息友好 | 模块化，Pass 可替换；Clang 前端 + LLVM 后端 |
| MSVC | PE-COFF | Windows 原生 | 链接 MSV140 运行时；PCH 支持 |

**clang/LLVM 的设计原理**：
- 前端（Clang）：负责词法/语法/语义分析，输出 LLVM IR
- 中端（LLVM Core）：负责优化，SSA 形式的 LLVM IR 被一系列 Pass 处理
- 后端：负责指令选择、寄存器分配、机器码发射

**MSVC 的独特约束**：Windows 下的 C++ ABI 不完全统一，MSVC 的 name mangling 与 GCC/Clang 不兼容，导致跨编译器链接需要 `extern "C"` 或匹配的工具链。

**编译器选择的本质**：不同编译器的优化策略和目标平台支持不同。游戏引擎常用 Clang/LLVM（优化好、错误信息清晰），Windows 原生项目用 MSVC（运行时集成）。

## 编译过程与构建系统

### 编译与链接的分离

<pre>
两遍式编译：

第一遍（编译，不链接）：
g++ -std=c++20 -c main.cpp -o main.o
g++ -std=c++20 -c foo.cpp -o foo.o
     │
     ├──► main.o: 未解析的外部符号 (_foo 函数)
     └──► foo.o: 导出的符号 (_foo)

第二遍（链接）：
g++ main.o foo.o -o app
     │
     └──► 链接器解析 _foo: main.o 的未定义引用 ↔ foo.o 的导出
          生成可执行文件 app
</pre>

**分离编译的数学意义**：
编译单元 $C_i$ 的语义仅依赖其自身的源码和通过 `#include` 引入的头文件。链接时，符号解析函数 $B$ 将全局符号映射到地址。若 $B$ 在某个符号上未定义或多重定义，则链接失败。

**增量构建的数学模型**：设依赖图 $G=(V,E)$，$V$ 为翻译单元，$E$ 为 include 关系。当文件 $v_i$ 变化时，仅需重编译 $\{v_j \in V \mid \exists \text{路径 } v_i \rightarrow^* v_j\}$。

**依赖图的构建**：
$$D(v) = \{ w \in V \mid \exists \text{include } v \rightarrow^* w \}$$
增量构建的复杂度为 $O(|V| + |E|)$，通过 Make 的拓扑排序实现。

### CMake 工作流

<pre>
CMakeLists.txt（声明式构建描述）
    │
    ▼ cmake ..
配置阶段：检测编译器、平台、依赖
输出：生成器特定的构建文件（Makefile / Ninja / VS 项目）
    │
    ▼ cmake --build .
构建阶段：调用编译器逐单元构建
    │
    └──► 并行构建：cmake --build . -j N（N 个并行任务）
</pre>

**CMake 生成器表达式**（Generator Expressions）：

生成器表达式是在配置时计算、生成平台相关构建命令的语法：
$$E = \$\langle \text{条件}:\text{真值}:\text{假值} \rangle$$

```cmake
# 平台相关的编译选项
target_compile_options(myapp PRIVATE
    $<$<CXX_COMPILER_ID:GNU>:-Wall -Wextra>
    $<$<CXX_COMPILER_ID:MSVC>:/W4>
)

# 调试/发布模式差异
target_compile_definitions(myapp PRIVATE
    $<$<CONFIG:Debug>:DEBUG_MODE=1>
    $<$<CONFIG:Release>:OPT_LEVEL=3>
)

# 链接库路径
target_link_directories(myapp PRIVATE
    $<$<PLATFORM_ID:Linux>:/usr/local/lib>
    $<$<PLATFORM_ID:Windows>:C:/3rdparty/lib>
)
```

**生成器表达式的求值时机**：配置时而非构建时，因此不能引用构建时才能确定的变量（如 `$<TARGET_PROPERTY:...>` 除外）。

**CMake 依赖图遍历**：
```cmake
# 添加依赖，自动传播包含目录和链接库
target_link_libraries(myapp PRIVATE spdlog::spdlog)
# 等价于传播：
# - PUBLIC: spdlog 的 include 目录、链接库传播给 myapp 的依赖方
# - PRIVATE: 仅在 myapp 内部使用
# - INTERFACE: spdlog 自身无代码，仅传播接口
```

**传播属性的数学约束**：
- PRIVATE：$T_{\text{receiver}} += T_{\text{provider}}$
- PUBLIC：$T_{\text{receiver}} += T_{\text{provider}}$ 且 $T_{\text{consumer}} += T_{\text{provider}}$
- INTERFACE：$T_{\text{consumer}} += T_{\text{provider}}$

### Makefile 的依赖追踪

```makefile
# 模式规则
%.o: %.cpp
    g++ $(CXXFLAGS) -c $< -o $@

# 隐式规则搜索路径
VPATH = src:include

# 并行构建
.PHONY: all
all: myapp
    cmake --build . -j $(shell nproc)
```

**依赖追踪的数学形式**：
$$\text{make} \models \exists D : \text{文件变化} \Rightarrow \text{受影响的文件集} \Rightarrow \text{重新构建目标}$$

Make 的本质是**有向无环图（DAG）的拓扑排序**：若文件 $a$ 依赖于文件 $b$，则 $b$ 必须先于 $a$ 构建。Make 执行时按照拓扑序构建，直到所有目标就绪。

**Phony 目标的数学意义**：
$$\text{.PHONY} : t \implies \forall mtime(t) : \text{总是认为过期}$$
这不是物理文件，而是纯规则目标，用于声明式依赖（如 `clean`）。

## 包管理器

**包管理器的本质是编译期依赖解析器——将库的源码/头文件/元数据在首次构建时自动下载、编译并集成到项目。**

### vcpkg 工作流

<pre>
vcpkg install spdlog:x64-linux
    │
    ├──► 1. 查询 vcpkg_installed/ 目录
    ├──► 2. 克隆/解压 spdlog 源码
    ├──► 3. 配置：cmake -B build -DCMAKE_TOOLCHAIN_FILE=vcpkg.json
    └──► 4. 编译并安装到 vcpkg_installed/

使用：
CMakeLists.txt 中通过 find_package(spdlog CONFIG REQUIRED)
链接：target_link_libraries(myapp PRIVATE spdlog::spdlog)
</pre>

**vcpkg 三元组**（Triplet）：
$$\text{Triplet} = \text{架构} \times \text{系统} \times \text{工具链}$$

| 示例 | 架构 | 系统 | 工具链 |
|------|------|------|--------|
| x64-linux | x86_64 | Linux | GCC/Clang |
| x64-windows | x86_64 | Windows | MSVC |
| arm64-uwp | ARM64 | Windows UWP | MSVC |
| x64-osx | x86_64 | macOS | Clang |

**三元组的笛卡尔积性质**：每个维度独立，组合数是各维度选项的乘积。vcpkg 通过三元组实现跨平台交叉编译支持。

### Conan 工作流

```python
# conanfile.txt
[requires]
spdlog/1.12.0

[generators]
CMakeToolchain

# conanfile.py (更灵活)
class MyConan(ConanFile):
    name = "myapp"
    version = "1.0"
    requires = "spdlog/1.12.0", "fmt/10.2.1"
```

**Conan 的依赖解析**：
Conan 使用语义版本约束（Semantic Versioning）：
$$S = \text{major}.\text{minor}.\text{patch}$$
- `spdlog/1.12.0`：精确版本
- `spdlog/[>1.0 <2.0]`：范围约束
- `spdlog/~1.12`：修平约束（允许 patch 升级）

### conan + CMake 集成

```cmake
# CMakeLists.txt
include(${CMAKE_BINARY_DIR}/conan/conan.cmake)
conan_cmake_run(CONANFILE conanfile.txt
    BUILD missing)

# 链接
find_package(spdlog REQUIRED)
target_link_libraries(myapp PRIVATE spdlog::spdlog)
```

**依赖冲突检测**：当两个包依赖同一个库的不同版本时，Conan 构建依赖图并检测冲突：
$$\exists p_1, p_2 : \text{requires}(p_1, L, v_1) \land \text{requires}(p_2, L, v_2) \land v_1 \neq v_2 \implies \text{冲突}$$

## 机制

### 编译器优化的数学本质

**优化的前提是语义等价**：
$$P \cong P' \iff \forall \text{输入 } I : \text{eval}(P, I) = \text{eval}(P', I)$$

优化变换必须在保持语义等价的前提下，提升性能或减少资源占用。

**常量折叠的数学形式**：
$$\text{eval}(\text{const}_1 \oplus \text{const}_2) = \text{const}_3 \implies \text{用 } \text{const}_3 \text{ 替换表达式}$$

**死代码消除的前提**：
$$f \text{ 是死代码} \iff \forall \text{程序点 } p : f \text{ 在 } p \text{ 不可达}$$
不可达意味着 $f$ 的结果在任何执行路径上都不会被使用。

### 链接器的 Resolution 过程

**符号解析的数学模型**：
$$B(name) = \begin{cases}
addr(def) & \text{若存在唯一强定义} \\
addr(def) & \text{若存在唯一弱定义且无强定义} \\
\text{undefined} & \text{若不存在定义} \\
\text{error} & \text{若存在多个强定义}
\end{cases}$$

**COMDAT 解决弱重复定义**：
$$\text{COMDAT} : \text{同名弱符号} \implies \text{选择任一实现（未定义行为，但不报错）}$$

### 构建系统的并行性

**Amdahl 定律在并行构建中的应用**：
$$S(N) = \frac{1}{(1-P) + \frac{P}{N}}$$
其中 $P$ 是可并行部分的比例，$N$ 是并行任务数。当 $P=0.9, N=8$ 时，$S(8) \approx 4.7$。

**Make 的并行构建**：
$$T_{\text{并行}} = \sum_{i=1}^{k} T_{\text{关键路径}_i}$$
关键路径是依赖图中的最长路径，其长度决定最短构建时间。

## 环境验证

```cpp
#include <iostream>
#include <vector>
#include <memory>
#include <chrono>
#include <random>

int main() {
    // unique_ptr 演示 RAII：自动释放
    auto p = std::make_unique<int>(42);
    std::cout << *p << std::endl;

    // vector + lambda 演示 C++20 特性
    std::vector<int> v{1, 2, 3, 4, 5};
    auto is_even = [](int n) { return n % 2 == 0; };
    auto count = std::ranges::count_if(v, is_even);
    std::cout << "偶数个数: " << count << std::endl;

    // 随机数演示
    std::random_device rd;
    std::mt19937 gen(rd());
    std::uniform_int_distribution<> dist(1, 100);
    std::cout << "随机数: " << dist(gen) << std::endl;

    // 计时演示
    auto start = std::chrono::high_resolution_clock::now();
    volatile int sum = 0;
    for (int i = 0; i < 1000000; ++i) sum += i;
    auto end = std::chrono::high_resolution_clock::now();
    auto duration = std::chrono::duration_cast<std::chrono::microseconds>(end - start);
    std::cout << "耗时: " << duration.count() << " us" << std::endl;

    return 0;
}
```

## 约束与违反后果

| 约束 | 违反后果 |
|------|----------|
| 头文件改变时，所有依赖它的 .cpp 必须重编译 | 增量构建失效，完整重编译浪费时间 |
| 链接时所有未解析符号必须恰好有一个定义 | 链接错误：`undefined reference to ...` 或 `duplicate symbol` |
| C++ 标准库与编译器版本必须匹配 | 二进制不兼容，运行时崩溃或符号未找到 |
| vcpkg 三元组必须与目标平台匹配 | 编译出错或运行时链接错误 |
| CMake 生成器表达式在配置时求值 | 运行时才使用的变量不能放在生成器表达式中 |
| include guard 或 #pragma once 必须唯一 | 重复包含导致编译错误或重复定义 |
| extern "C" 用于 C++ 中调用 C 函数 | 不使用则 name mangling 不匹配，链接失败 |
