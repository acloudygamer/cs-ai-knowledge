# 安装与环境

## 定义

编译器是将高级语言源码映射为机器指令的翻译器，其本质是一个**有限状态机驱动的代码变换管道**，通过词法分析、语法分析、语义分析、优化和代码生成五个阶段，将符合语言规范的源码转换为目标文件。这个翻译过程不是一次性的字符串替换，而是**基于语言规范的语义保留变换**——源码和目标代码在语义上等价，尽管表现形态完全不同。

编译器作为**有穷状态自动机**的理论实例：源码是输入符号序列，词法分析将其分割为 token 序列，语法分析将其组织为树结构，语义分析为其赋予类型上下文，优化器在保持语义的前提下寻找更高效的形式，最终代码生成器将其映射为目标机器的指令序列。每一阶段都是**从一种表示到另一种表示的双射（bijection）**，保持可推导的语义等价关系。

### 链接器的符号解析模型

链接的本质是**名字到地址的绑定函数**：
 $B: \text{Symbol} \rightarrow \text{Address}$ 

链接过程的数学约束：
 $\text{未定义符号} \implies \text{外部引用存在但无定义} \Rightarrow \text{链接错误}$ 
 $\text{重复定义} \implies \text{多个强定义} \Rightarrow \text{链接错误}$ 

**强符号 vs 弱符号的选择规则**：
 $\text{强符号} \oplus \text{强符号} \implies \text{链接错误（重复定义）}$ 
 $\text{强符号} \oplus \text{弱符号} \implies \text{选用强符号}$ 
 $\text{弱符号} \oplus \text{弱符号} \implies \text{实现选择未定义（UB，不报错）}$ 

**两遍式链接的数学性质**：
1. 第一遍：建立全局符号表 $\Sigma = \{ (name, addr, strong/weak) \}$ ，收集所有符号定义 ，收集所有符号定义
2. 第二遍：重定位所有引用 $\rho: ref \rightarrow addr$ ，将相对地址修正为绝对地址 ，将相对地址修正为绝对地址

### 编译器前端到后端的数据契约

```
Clang 前端输出 LLVM IR（与目标无关）:
    define i32 @add(i32 %a, i32 %b) {
        %result = add i32 %a, %b
        ret i32 %result
    }

LLVM 后端生成 x86-64:
    add edi, esi          ; 参数在寄存器中
    mov eax, edi          ; 返回值在 eax
    ret
```

LLVM 的模块化设计将优化和代码生成组织为可插拔的 Pass 架构，使得：
 $T_{\text{总}} = T_{\text{前端}} + \sum_{i=1}^{P} T_{\text{Pass}_i} + T_{\text{后端}}$ 

独立 Pass 可并行执行。

## 三大编译器对比

| 编译器 | 输出格式 | 平台特性 | 设计取舍 |
|--------|---------|---------|---------|
| g++ (GNU) | ELF / PE-COFF | 广泛兼容 | 优化保守，兼容优先；GCC 是自由软件 |
| clang (LLVM) | Mach-O / ELF / PE-COFF | 错误信息友好 | 模块化，Pass 可替换；Clang 前端 + LLVM 后端 |
| MSVC | PE-COFF | Windows 原生 | 链接 MSV140 运行时；PCH 支持 |

**clang/LLVM 的设计原理**：
- 前端（Clang）：负责词法/语法/语义分析，输出 LLVM IR
- 中端（LLVM Core）：负责优化，SSA 形式的 LLVM IR 被一系列 Pass 处理
- 后端：负责指令选择、寄存器分配、机器码发射

**MSVC 的独特约束**：Windows 下的 C++ ABI 不完全统一，MSVC 的 name mangling 与 GCC/Clang 不兼容，导致跨编译器链接需要 `extern "C"` 或匹配的工具链。

**编译器选择的本质**：不同编译器的优化策略和目标平台支持不同。游戏引擎常用 Clang/LLVM（优化好、错误信息清晰），Windows 原生项目用 MSVC（运行时集成）。

## 机制

### 编译器优化的数学本质

**语义等价性是优化的前提**：
 $P \cong P' \iff \forall \text{输入 } I : \text{eval}(P, I) = \text{eval}(P', I)$ 

优化变换必须在保持语义等价的前提下，提升性能或减少资源占用。

**常量折叠的数学形式**：
 $\text{eval}(\text{const}_1 \oplus \text{const}_2) = \text{const}_3 \implies \text{用 } \text{const}_3 \text{ 替换表达式}$ 

**死代码消除的前提**：
 $f \text{ 是死代码} \iff \forall \text{程序点 } p : f \text{ 在 } p \text{ 不可达}$ 

不可达意味着 $f$ 的结果在任何执行路径上都不会被使用。 的结果在任何执行路径上都不会被使用。

### 链接器的 Resolution 过程

**符号解析的数学模型**：
$$B(name) = \begin{cases}
addr(def) & \text{若存在唯一强定义} \\
addr(def) & \text{若存在唯一弱定义且无强定义} \\
\text{undefined} & \text{若不存在定义} \\
\text{error} & \text{若存在多个强定义}
\end{cases}$$

**COMDAT 解决弱重复定义**：
 $\text{COMDAT} : \text{同名弱符号} \implies \text{选择任一实现（UB，不报错）}$ 

### 构建系统的并行性约束

**Make 的并行构建**：
 $T_{\text{并行}} = \sum_{i=1}^{k} T_{\text{关键路径}_i}$ 

关键路径是依赖图中的最长路径，其长度决定最短构建时间。

**约束条件**：
- 依赖图必须无环（拓扑排序的前提）
- 循环依赖导致构建失败
- 隐式依赖（如 generated header）需要显式声明

### 包管理器的依赖解析

**vcpkg 三元组**（Triplet）：
 $\text{Triplet} = \text{架构} \times \text{系统} \times \text{工具链}$ 

| 示例 | 架构 | 系统 | 工具链 |
|------|------|------|--------|
| x64-linux | x86_64 | Linux | GCC/Clang |
| x64-windows | x86_64 | Windows | MSVC |
| arm64-uwp | ARM64 | Windows UWP | MSVC |

**Conan 的语义版本约束**：
 $S = \text{major}.\text{minor}.\text{patch}$ 
- `spdlog/1.12.0`：精确版本
- `spdlog/[>1.0 <2.0]`：范围约束
- `spdlog/~1.12`：修平约束（允许 patch 升级）

**依赖冲突检测**：当两个包依赖同一个库的不同版本时：
 $\exists p_1, p_2 : \text{requires}(p_1, L, v_1) \land \text{requires}(p_2, L, v_2) \land v_1 \neq v_2 \implies \text{冲突}$

## 约束与违反后果

| 约束 | 违反后果 |
|------|----------|
| 头文件改变时，所有依赖它的 .cpp 必须重编译 | 增量构建失效，完整重编译浪费时间 |
| 链接时所有未解析符号必须恰好有一个定义 | 链接错误：`undefined reference to ...` 或 `duplicate symbol` |
| C++ 标准库与编译器版本必须匹配 | 二进制不兼容，运行时崩溃或符号未找到 |
| vcpkg 三元组必须与目标平台匹配 | 编译出错或运行时链接错误 |
| CMake 生成器表达式在配置时求值 | 运行时才使用的变量不能放在生成器表达式中 |
| include guard 或 #pragma once 必须唯一 | 重复包含导致编译错误或重复定义 |
| extern "C" 用于 C++ 中调用 C 函数 | 不使用则 name mangling 不匹配，链接失败 |
| 模板实例化需要完整定义（通常在头文件） | 链接错误：undefined reference to ... |
