# 05-数据库操作

> 前置：[04-正则表达式](04-正则表达式.md) · 后续：[04-性能与底层](../04-性能与底层/README.md)

> **版本基准**：C++20；C++23/26 特性行内标注。sqlite3 示例实测环境：GCC 14.2（MinGW-w64）+ SQLite 3.50.4 amalgamation；动态链接因环境 DLL 冲突加载失败（exit 127）时，加 `-static` 静态链接。其余第三方库示例为骨架示意，未实测。

数据库是替程序托管持久化数据的外部系统，C++ 通过各家数据库暴露的客户端库访问它。先分清两种形态，它们决定了后面所有的API形状：**进程内嵌**（SQLite——库即引擎，整个数据库是一个文件，没有服务进程、没有网络）与**客户端-服务端**（PostgreSQL、MySQL——独立的 DBMS 进程，客户端经网络协议发 SQL 文本、收结果集）。标准库同样不参与这一层：C++ 生态的答案是"原生 C API + 各家封装层"。

## 本质

以 SQLite 的 C API 为标本看原生接口的模型——它是两个句柄的手动流水线：

- `sqlite3*`：数据库连接句柄，`sqlite3_open` 打开、`sqlite3_close` 关闭；
- `sqlite3_stmt*`：编译后的语句句柄，生命周期是 `sqlite3_prepare_v2`（SQL 文本编译为字节码）→ `sqlite3_bind_*`（绑参数）→ `sqlite3_step`（逐行推进，每行一次调用）→ `sqlite3_finalize`（销毁）。

痛点有三，全都来自"C 接口 + C++ 资源纪律"的错配：

1. **无 RAII**：每个句柄都要配对一次手动释放，异常路径上漏 `finalize`/`close` 就是资源泄漏——正是 [04-类与资源管理](../01-语言核心/04-类与资源管理.md) 要消灭的形状。
2. **错误处理靠返回码**：每个调用返回 `SQLITE_OK` 等整数码，逐调用检查的苦役不做就静默吞错。
3. **SQL 是裸字符串**：拼接用户输入进 SQL 文本即注入漏洞；防线是参数化查询（`?1` 占位符 + bind），数据从此不进 SQL 语法解析。

## 机制

### 封装层选型

| 库 | 形态 | 覆盖 | 选型位置 |
|---|---|---|---|
| sqlite_modern_cpp | 单头文件，把 sqlite3 包成 RAII + 异常 + lambda 逐行回调 | 仅 SQLite | 用 SQLite 的默认答案 |
| soci | 多后端统一接口，`into()`/`use()` 绑定变量 | SQLite/PG/MySQL/ODBC… | 需要换数据库后端不换代码 |
| sqlpp11 | 类型安全查询：表结构编译期生成 C++ 类型，SQL 写作 C++ 表达式 | 多后端（经连接器） | 要编译期挡住"列名拼错"这类错误 |

一条横轴：**零封装（原生 C API）→ RAII 薄封装 → 类型安全查询**。越往右编译期挡下的错误越多，依赖与构建成本越高。

### 连接池与 ORM 的边缘地位

两个在 Java/Go 生态里的标配，在 C++ 都处于边缘，原因各异：

- **连接池**：C/S 数据库的连接建立要 TCP + 认证握手，高频短查询下池化是刚需；但 C++ 没有事实标准——Web 框架自带（如 Drogon 的 db client 池），否则几十行"队列 + 互斥量"自实现。它存在，只是没有成为"那个库"。
- **ORM**：ORM 依赖运行时反射（按名字把列映射到成员），C++ 没有。C++ 生态的对位答案是 sqlpp11 这类**编译期**映射——表结构经代码生成变成类型，查询是带类型的 C++ 表达式。重型运行时 ORM（如 ODB）存在但始终小众；多数项目的落点是薄封装 + 手写 SQL。

### SQLite 的两个工程事实

- **单写者**：SQLite 用文件锁，同一时刻只有一个写事务；WAL 模式（`PRAGMA journal_mode=WAL`）把并发上限提到**多读单写**——读者不阻塞写者，写者仍只有一个。嵌入式、单机、工具型数据存储是它的主场，高并发写不是。
- **零配置的代价反过来读**：没有服务进程也意味着没有用户体系、没有网络访问控制——边界由文件系统权限承担。

## 连接

数据库文件本身的原子写与崩溃恢复语义，与 [01-文件操作](01-文件操作.md) 的原子写惯用法同源（WAL 就是数据库界的"先写临时再切换"）；连接与协议的背景见 [02-网络编程](02-网络编程.md)。

## 示例

**实测**（GCC 14.2 MinGW + SQLite 3.50.4 amalgamation，`gcc -c sqlite3.c` 后 `g++ -std=c++20 -I. main.cpp sqlite3.o`）：内存库上的完整生命周期——

```cpp
#include <sqlite3.h>
#include <cstdio>
#include <stdexcept>
#include <string>

int main() {
    sqlite3* db = nullptr;
    if (sqlite3_open(":memory:", &db) != SQLITE_OK) return 1;  // 内存库：不落盘

    auto exec = [&](const char* sql) {   // 无参数语句的便捷入口
        char* err = nullptr;
        if (sqlite3_exec(db, sql, nullptr, nullptr, &err) != SQLITE_OK) {
            std::string msg = err ? err : "?";
            sqlite3_free(err);
            sqlite3_close(db);
            throw std::runtime_error(msg);
        }
    };
    exec("CREATE TABLE t(id INTEGER PRIMARY KEY, name TEXT)");
    exec("INSERT INTO t(name) VALUES('alice'),('bob')");

    sqlite3_stmt* st = nullptr;
    sqlite3_prepare_v2(db, "SELECT id, name FROM t WHERE id > ?1", -1, &st, nullptr);
    sqlite3_bind_int(st, 1, 0);   // 参数化：数据不进入 SQL 文本，注入无从谈起
    while (sqlite3_step(st) == SQLITE_ROW)
        std::printf("%d %s\n", sqlite3_column_int(st, 0), sqlite3_column_text(st, 1));
    sqlite3_finalize(st);
    sqlite3_close(db);
}
```

实测输出：

```text
1 alice
2 bob
```

对照骨架（未实测，本机未装封装层）：同一查询在 sqlite_modern_cpp 下收缩为——

```cpp
#include <sqlite_modern_cpp.h>
sqlite::database db(":memory:");              // RAII：析构即关库
db << "CREATE TABLE t(id INTEGER PRIMARY KEY, name TEXT)";
db << "INSERT INTO t(name) VALUES(?)" << "alice";
db << "SELECT id, name FROM t WHERE id > ?" << 0
   >> [](int id, std::string name) { /* 逐行回调 */ };
```

句柄配对、错误码检查、bind/step 循环全部被封装吃掉——这就是上面"三个痛点"各自的解法落点。
